Nulo Phase 2 — durable jobs target architecture

What "send a tx" looks like when we stop fighting the SW and start designing around it dying. The single biggest architectural shift surfaced by the comparative study, and the work that has to land before opening the door to real users.

Thesis post-merge calibration

Aztec proofs take seconds to minutes. The current popup → SW execution path defaults to a 60-second ServiceClient timeout. Healthy proofs routinely outrun that. "Timeout" is not "cancellation" — the SW keeps proving while the popup shows failure. PXE concurrency is globally serialized; in-flight prove state is not persisted; there is no chrome.alarms wake-up to keep us ready for incoming dApp messages between popup sessions.

Phase 2's premise: stop pretending the SW will stay alive. Treat any in-flight job that survives the worker as a feature, not a corner case. Submit jobs that return immediately with a jobId. Persist state aggressively. Subscribe to job state from the popup, not via blocking calls. Wire AbortController through prove and sim. Partition PXE concurrency per (profileId, chainId) so different chains don't block each other. Use chrome.alarms to resume work on cold boot. Use LazyListener so events that fire during initialization don't get lost.

Side-by-side — today vs Phase 2 contrast

Today (master @ v0.14.9)
  • 60s ServiceClient timeout (90s offscreen)
  • Popup blocks on the prove call
  • Global ReadWriteGuard on PXE
  • No AbortController in prove path
  • No mid-prove state persisted
  • Heartbeat keeps SW alive only while popup is open
  • Cold boot of dApp message = re-init BB-WASM (~5-10s)

Visible failure mode: popup says "Simulation failed, transaction not sent" while the chain confirms the tx. The 60s wins the race against a longer proof; UI lies.

Phase 2 target
  • submitJob() returns immediately with a jobId
  • Popup subscribes; never blocks
  • Per-(profileId, chainId) PXE concurrency
  • AbortController wired through prove and sim
  • Job state persisted on every transition
  • chrome.alarms wakes SW on cold boot to resume work
  • LazyListener buffers events fired pre-init

What changes for the user: closing the popup mid-tx is safe. The proof keeps going. Re-open the popup; subscribe to the same jobId; pick up where you left off.

Carries to Phase 2+ — design choices Phase 2 must make forward compatibility

Phase 2 and Phase 2+ are designed to be implementable as separate lifts: ship Phase 2, run it in production, then come back for Phase 2+ if real traffic shows the hardening is needed. Splitting works because Phase 2+ is mostly additive on top of Phase 2 — but only if Phase 2 makes a small handful of forward-looking design choices.

None of these are extra work. They're design choices, each a few lines. If Phase 2 makes them, Phase 2+ slots in as composition over replacement. If Phase 2 burns these bridges, Phase 2+ becomes a refactor.

#CarryWhy it matters for Phase 2+
1 Tag every job with (origin, profileId, kind) at create-time Phase 2 doesn't use the metadata, but Phase 2+ needs it for fairness caps and per-origin rate limiting. Adding it later means touching every job-create callsite.
2 Don't delete terminal jobs; keep them with a flag or long TTL Phase 2+ tombstones and idempotency dedup both resolve to an existing terminal jobId. Deleting them in Phase 2 means Phase 2+ needs a schema migration to bring them back.
3 Subscribe path uses Map<jobId, Observer[]> from day one Even if only one observer is supported at runtime in Phase 2, the data shape allows multi-observer attach later (Phase 2+ #6). Refactoring single-to-list later touches the whole subscribe API.
4 Progress-event payloads are extensible — { stage, ...rest } Phase 2+ adds a heartbeat field that the sweeper reads. Positional args in Phase 2 = breaking change in Phase 2+.
5 Don't collapse error categories at the prove boundary Preserve the raw error shape coming out of PXE. Phase 2+ retry policy needs to classify retryable-vs-terminal; if Phase 2 has mapped everything to a generic "Simulation failed", classification is dead on arrival.
Why split at all? Half of Phase 2+ is hardening for production-scale edge cases that Phase 2 traffic might never reveal. Fairness matters when you have queue contention. Idempotency dedup matters when dApps retry under timeout pressure. Sweepers matter when a measurable percentage of jobs get stuck. With single-digit-user traffic, you might never hit any of those, and Phase 2 alone could be enough for a long time. Let real failure modes (or their absence) tell you which Phase 2+ items are actually load-bearing.

Non-goals — what Phase 2 explicitly is NOT scope discipline

As important as what's in scope is what stays out. These are the things we do NOT touch in Phase 2:

  • Re-doing the package / layer model — it's already production-quality. Don't fix what isn't broken.
  • Cryptography churn — PasswordSecretBox and the M2.6 vectors stay as-is.
  • Aztec correctness rework — PR 8c shipped; no more sim-pipeline changes in this scope.
  • Storybook / visual regression / e2e infra — separate track (M6 + parallel-e2e-isolation plan).
  • Frontend / UI redesign — Phase 4 territory.
  • LavaMoat / Snaps — Phase 4+; not blocking Phase 2 ship.
  • Wider state-architecture refactor (Immer patches, ObjectMultiplex, @metamask/messenger) — Phase 2 keeps Pinia + Service<Methods,Events> as-is.
Phase 2 is infrastructure, not a redesign. Every visible UX flow in Nulo stays recognizable. What changes is what happens when those flows take longer than 60 seconds.
