# Independent Architecture Analysis: Grego `extension-wallet`

Scope: this report covers only the `extension-wallet/` package. I did not inspect Grego's Electron wallet surfaces (`app/`, `web/`, `extension/`) when forming this view. All citations below are relative to `extension-wallet/`.

One high-level framing matters before the details: this package is self-contained in runtime topology, not in total code ownership. The wallet runs inside the extension, with content script, service worker, offscreen document, popup, approval window, expanded view, and onboarding all packaged here, and the manifest explicitly describes that self-contained posture (`README.md:3-5`, `README.md:21-76`, `wxt.config.ts:45-75`). But the extension still delegates substantial Aztec/PXE/session behavior to shared imports such as `getOrCreateSession`, `getSharedResources`, `getRunningSessionIds`, `InternalWalletInterfaceSchema`, `StandaloneShell`, and `AuthorizationDialog`, all of which come from `@demo-wallet/shared/*` rather than from files inside this package (`src/offscreen/wallet-host.ts:47-55`, `entrypoints/expanded/main.tsx:4-7`, `entrypoints/approval/main.tsx:5-12`). That means the extension package is highly auditable as an MV3 integration layer, but not as the full implementation of Aztec wallet semantics.

## 1. Manifest & entry points

The package is built with WXT plus the React module, and its Vite config is tuned specifically for Aztec dependencies that expect Node globals at module-init time. Grego injects `buffer` and `process` polyfills globally and aliases `function-bind` to a CSP-safe stub because MV3 rejects `'unsafe-eval'` and one transitive dependency still wants dynamic function construction (`wxt.config.ts:10-44`, `src/shared/polyfills.ts:1-5`, `src/shared/function-bind-stub.cjs:1-22`). That is already a signal about the project's intended deployment target: this is not a toy extension; it has been forced through real MV3 runtime constraints.

The manifest is compact but purposeful. It asks for `storage`, `alarms`, `offscreen`, and `webNavigation`, plus `*://*/*` host permissions; sets `popup.html` as the browser action; exposes `approval.html`, `expanded.html`, and `onboarding.html` as web-accessible resources; pins a Chromium key for stable extension ID; and adds a Gecko ID for Firefox (`wxt.config.ts:45-75`). The CSP is intentionally narrow: only `'self'` plus `'wasm-unsafe-eval'` for extension pages, which is the right compromise when Aztec/WASM dependencies are involved and `'unsafe-eval'` is categorically forbidden in MV3 (`wxt.config.ts:50-55`).

Each entrypoint exists for a distinct surface, and the split is clean rather than ornamental. `entrypoints/background.ts` is the service worker router and discovery/session coordinator; `entrypoints/content.ts` is the page relay; `entrypoints/offscreen/main.ts` boots the wallet host in an offscreen document; `entrypoints/popup/Popup.tsx` is the small-state surface for unlock/discovery/session verification; `entrypoints/approval/main.tsx` is the per-request approval window; `entrypoints/expanded/main.tsx` is the full wallet shell; and `entrypoints/onboarding/Onboarding.tsx` is the first-install path (`README.md:65-76`, `entrypoints/background.ts:18-244`, `entrypoints/content.ts:14-23`, `entrypoints/offscreen/main.ts:1-14`, `entrypoints/popup/Popup.tsx:6-330`, `entrypoints/approval/main.tsx:13-121`, `entrypoints/expanded/main.tsx:31-63`, `entrypoints/onboarding/Onboarding.tsx:15-125`).

Architecturally, that split is very MetaMask-like. The popup is intentionally not the wallet runtime. The offscreen document is. The service worker only arbitrates traffic and surfaces UX when a human must do something (`README.md:21-61`, `README.md:63-90`).

## 2. SW as router

The service worker is thin in the sense that it does not own vault secrets, PXE objects, or the wallet database; those live behind the offscreen host. But it is not stateless. It owns a cached `PortClient`, an in-memory `pendingDappCount`, a `BackgroundConnectionHandler` instance from `@aztec/wallet-sdk`, and the approval-window queue state imported from `src/background/approval-window.ts` (`entrypoints/background.ts:18-21`, `entrypoints/background.ts:50-56`, `src/background/approval-window.ts:1-39`). So the right description is: router plus ephemeral coordination state.

`BackgroundConnectionHandler` is the important piece. Grego wires it with just two transport functions, `sendToTab` and `addContentListener`, then supplies three behavioral callbacks: `onPendingDiscovery`, `onSessionEstablished`, and `onWalletMessage` (`entrypoints/background.ts:50-149`). That keeps wallet-sdk in charge of page/session protocol while the extension decides approval UX and where wallet calls get executed.

`onPendingDiscovery` is origin- and network-aware. It extracts `chainId` and `version` from the discovery payload, checks whether this `appId` + `origin` + `chainId` + `version` tuple was remembered before, and either auto-approves discovery or opens the popup (`entrypoints/background.ts:57-67`, `src/background/remembered-apps.ts:21-51`). This is better than remembering only by origin because it prevents silently reusing trust across networks.

`onWalletMessage` is where the worker proves it really is “router only.” It first rejects if the wallet has not been initialized, then ensures the offscreen document exists, increments the in-flight counter, acquires a keep-alive port, bumps idle activity, optionally prompts the user to unlock, forwards the message into the offscreen runtime as `dapp.${message.type}`, and finally returns the result back through `BackgroundConnectionHandler.sendResponse` (`entrypoints/background.ts:79-146`, `src/background/offscreen-lifecycle.ts:87-101`). The worker never interprets transaction payloads itself. It just knows how to keep the pipe alive and how to convert an extension-uninitialized or vault-locked state into user-visible behavior.

The worker also exposes a small UI control plane over `chrome.runtime.onMessage`: ensure offscreen, mark offscreen ready, list pending discoveries, approve/reject discoveries, and list active sessions (`entrypoints/background.ts:167-238`). That makes the popup a view over worker/offscreen state instead of a second source of truth.

Statefulness question: the worker is stateful enough that suspending it would drop pending discovery/session lists held on `sessionHandler` and the cached `PortClient`, but the real wallet state is still externalized into the offscreen host and browser storage (`entrypoints/background.ts:19-27`, `entrypoints/background.ts:182-235`, `src/offscreen/wallet-host.ts:56-64`). So Grego chose the common MV3 compromise: durable wallet state off-worker, ephemeral connection state in-worker.

## 3. Offscreen as the wallet host

The offscreen document is the real process boundary in this architecture. `entrypoints/offscreen/main.ts` does only three things: import shared polyfills, instantiate `WalletHost`, and send an `offscreen-ready` message back to the worker after startup (`entrypoints/offscreen/main.ts:1-14`). That final ready signal is not decorative. `ensureOffscreen()` explicitly waits not just for `chrome.offscreen.createDocument()` to resolve, but for a separate readiness gate, because document creation resolves before `WalletHost.start()` has necessarily registered `onConnect` listeners (`src/background/offscreen-lifecycle.ts:13-33`, `src/background/offscreen-lifecycle.ts:35-64`).

That ready-gate is one of the best production details in the package. Without it, the popup or worker can open a runtime port into a document whose JS has not yet attached listeners, and the first connection simply disappears into the void. Grego solves that race with `readyPromise`/`readyResolver`, reset on each spawn and resolved only when the offscreen code calls back into the worker (`src/background/offscreen-lifecycle.ts:20-33`, `entrypoints/offscreen/main.ts:8-14`).

Chromium and Firefox are both handled. On Chromium, `ensureOffscreen()` uses `chrome.offscreen.hasDocument()` and `createDocument()` with a DOM parser reason and a justification string that explicitly calls out PXE, WalletDB, and vault hosting (`src/background/offscreen-lifecycle.ts:42-64`). On Firefox, where `chrome.offscreen` does not exist, the same function falls back to a hidden minimized window hosting `offscreen.html`, and reuses that window across calls (`src/background/offscreen-lifecycle.ts:67-85`, `README.md:95-99`). That fallback is pragmatic and exactly the sort of boring-but-necessary engineering Nulo should study.

Inside the offscreen runtime, `WalletHost` owns three things: a `VaultState`, a `PortServer`, and an in-memory `currentChainInfo` that defaults to localhost-style `chainId = 31337` and `version = 0` (`src/offscreen/wallet-host.ts:56-64`). `start()` brings up the port server and turns vault state transitions into broadcasts (`src/offscreen/wallet-host.ts:66-75`). `buildHandlers()` exposes vault, network, authorization, wallet, and dapp methods (`src/offscreen/wallet-host.ts:77-141`).

What the package does not show directly is PXE object creation or teardown. The README says the offscreen document hosts `PXE / WalletDB / shared session` resources (`README.md:39-46`). In code, `WalletHost` reaches those through `getOrCreateSession`, `getSharedResources`, and `getRunningSessionIds` imported from `@demo-wallet/shared/core` (`src/offscreen/wallet-host.ts:47-53`, `src/offscreen/wallet-host.ts:103-137`, `src/offscreen/wallet-host.ts:159-164`, `src/offscreen/wallet-host.ts:220-224`). So the extension package clearly places PXE in offscreen, but the actual PXE lifecycle is delegated out of package scope.

One consequence: there is creation logic, but no explicit destruction logic in this package. I see offscreen creation, reuse, and worker keep-alive management; I do not see an explicit `closeDocument`, PXE shutdown, or hidden-window teardown path (`src/background/offscreen-lifecycle.ts:35-101`). For a lean v1 wallet, that is fine. For long-lived scale, it means memory ownership is effectively “until browser/extension lifecycle ends.”

## 4. Port-based RPC

The extension’s internal transport is clean and explicit. `src/ipc/port-envelope.ts` defines a Zod discriminated union over three message shapes: `request`, `response`, and `broadcast`. Requests carry `id`, `method`, and `args`; responses carry `ok`, `result`, and optional `error`; broadcasts are restricted to a small event enum: `wallet-update`, `authorization-request`, `proof-debug-export-request`, `vault-locked`, and `vault-unlocked` (`src/ipc/port-envelope.ts:1-53`). This is a useful discipline point: the transport surface is intentionally small enough to reason about.

`PortServer` is the offscreen-side multiplexer. It listens only on the named offscreen port, validates incoming messages with Zod, dispatches to a handler map, and sends back a `PortResponse` (`src/ipc/port-server.ts:14-46`, `src/ipc/port-server.ts:91-113`). Two implementation details are particularly good. First, `broadcast()` catches port failures instead of letting one dead surface poison the event fanout (`src/ipc/port-server.ts:28-37`). Second, response serialization has a real fallback path: if `postMessage(response)` fails with `DataCloneError` or similar, the server retries with `jsonStringify(response.result)` and annotates the envelope with `resultIsJson`, so the client can parse it back (`src/ipc/port-server.ts:47-87`). Given Aztec class instances, BigInts, Buffers, Maps, and `toJSON()`-heavy objects, that fallback is not optional polish; it is survival.

`PortClient` mirrors that design on the UI/SW side. It optionally pings the worker with `ensure-offscreen` before opening the named port, maintains a pending-request map keyed by `crypto.randomUUID()`, and keeps event subscriptions in a per-broadcast-type map (`src/ipc/port-client.ts:11-25`, `src/ipc/port-client.ts:40-69`, `src/ipc/port-client.ts:72-122`). When a response returns with `resultIsJson`, the client transparently `JSON.parse`s it before resolving the original promise (`src/ipc/port-client.ts:93-109`). So callers largely get a normal async API, not a transport API.

The four namespaces are exactly the ones described in the README: `vault.*`, `network.*`, `wallet.*`, and `dapp.*` (`README.md:78-90`, `src/offscreen/wallet-host.ts:77-141`). `vault.*` and `network.*` are hand-written. `wallet.*` and `dapp.*` are generated by enumerating schema keys from `InternalWalletInterfaceSchema` and `WalletSchema` and attaching async wrappers for each method (`src/offscreen/wallet-host.ts:154-192`, `src/offscreen/wallet-host.ts:199-237`). That explicit enumeration is deliberate; the README explains that a Proxy spread would lose traps and break dispatch (`README.md:106-107`).

The dApp route is therefore: page -> `ContentScriptConnectionHandler` -> `BackgroundConnectionHandler` -> worker `onWalletMessage` -> `PortClient.call("dapp.<method>")` -> offscreen `WalletHost` -> per-session external wallet -> result back out (`entrypoints/content.ts:14-23`, `entrypoints/background.ts:71-146`, `src/offscreen/wallet-host.ts:194-237`). It is a good transport topology for an MV3 wallet because every privilege boundary is explicit.

## 5. Vault & lock state machine

The vault code is intentionally small and very clear. Password derivation uses Argon2id with defaults `m = 64 * 1024 KiB`, `t = 3`, `p = 1`, a 32-byte derived key, and a 16-byte salt (`src/vault/kdf.ts:3-15`). Grego documents those defaults as targeting sub-500ms unlock time on a 2024-era laptop, while the tests note that CI/sandbox load can stretch derivations into the multi-second range (`src/vault/kdf.ts:12-13`, `src/vault/kdf.test.ts:4-5`).

The password check is probe-based rather than hash-only. `makeProbe()` imports the derived bytes as an AES-GCM key, encrypts a fixed plaintext marker, and stores `{ iv, ciphertext }`; `verifyProbe()` decrypts with the candidate key and byte-compares the recovered plaintext against that known marker (`src/vault/kdf.ts:36-71`). That gives the extension a future-ready pattern for real encryption: the same derived key shape can later protect actual vault material instead of only a verification probe.

Metadata persistence is separate and minimal. `src/vault/vault-meta.ts` opens an IndexedDB-backed store named `vault-meta` using `@aztec/kv-store/indexeddb`, then serializes the KDF salt and probe byte arrays into plain JSON-friendly arrays before writing them under a fixed `v1` key (`src/vault/vault-meta.ts:1-31`, `src/vault/vault-meta.ts:34-64`). This store contains only enough information to verify a password and reconstruct the KDF parameters.

`VaultState` is a small two-state machine around that metadata. `initialize()` refuses re-initialization, derives a key, creates a probe, writes vault metadata, stores the raw key in memory, and notifies listeners that the vault is now unlocked (`src/vault/vault-state.ts:24-36`). `unlock()` reads metadata, derives a candidate key, verifies the probe, and either stores the key in memory and reports success or returns `false` (`src/vault/vault-state.ts:38-47`). `lock()` zeroes the in-memory key buffer before nulling it out and broadcasting a locked transition (`src/vault/vault-state.ts:49-64`).

The crucial caveat is explicit in the README: at-rest encryption is deferred, and account secrets remain plaintext in IndexedDB for now (`README.md:110-113`). That means the current lock model is a runtime access-control and UX lock, not true storage confidentiality. The code fully supports lock/unlock semantics and future encrypted persistence, but today the password protects live use of the wallet surface more than theft of the extension’s local database (`src/vault/vault-state.ts:12-18`, `README.md:110-113`).

## 6. dApp ↔ wallet path

The content script is intentionally dumb. It matches every origin and uses `ContentScriptConnectionHandler` from `@aztec/wallet-sdk` to relay messages between the page and background script, with a comment explicitly stating that content scripts never see private keys or shared secrets and only forward opaque payloads (`entrypoints/content.ts:1-23`). That is the right security posture for a browser wallet.

From there, the worker does origin gating through discovery approval rather than through content-injection scope. On a new discovery request, it checks whether the `(appId, origin, chainId, version)` tuple is remembered; if yes, it approves discovery immediately, and if not, it surfaces the popup for human approval (`entrypoints/background.ts:57-67`, `src/background/remembered-apps.ts:3-31`). Remembered apps are persisted in `chrome.storage.local`, including the network tuple, which avoids silently treating “same website, different Aztec network” as equivalent trust (`src/background/remembered-apps.ts:34-66`).

Once a session is established, the worker opens the popup again so the user can compare emoji fingerprints. The active session list exposed to the popup includes `verificationHash`, and the popup renders `hashToEmoji(verificationHash)` for unverified sessions, storing verified session IDs only in `chrome.storage.session` so the verification state survives popup reopens but resets on browser restart (`entrypoints/background.ts:68-70`, `entrypoints/background.ts:221-235`, `entrypoints/popup/Popup.tsx:34-64`, `entrypoints/popup/Popup.tsx:127-186`). That is a subtle but good trust model: connections are remembered for the session, not forever.

Actual wallet calls do not go page -> content -> popup. They go page -> content -> worker -> offscreen. The worker checks wallet initialization, ensures offscreen existence, optionally prompts unlock, forwards `dapp.<message.type>` with both session and message payloads, and returns a `WalletResponse` through the wallet-sdk session handler (`entrypoints/background.ts:79-146`). In offscreen, `WalletHost` revives `chainInfo` from JSON-safe forms back into `Fr` instances, obtains a per-session external wallet with `getOrCreateSession`, parses method args using the Zod function schema where available, and invokes the requested method on the external wallet instance (`src/offscreen/wallet-host.ts:32-45`, `src/offscreen/wallet-host.ts:199-237`).

The path is also defensive about session lifetime. When a tab is removed or a top-frame navigation begins, the worker tells `BackgroundConnectionHandler` to terminate that tab’s sessions (`entrypoints/background.ts:240-243`). That is the right place to kill dApp trust because the browser tab boundary is the user-visible security boundary.

## 7. Approval flow

Grego’s approval flow is intentionally one-window-per-request-stream rather than “any surface can subscribe and replay pending auth forever.” The offscreen wallet host forwards `authorization-request` events as broadcasts (`src/offscreen/wallet-host.ts:144-152`). The worker’s cached port client subscribes to that event, parses the JSON-stringified payload, and turns it into a queue entry with `{ id, type }` (`entrypoints/background.ts:22-35`, `src/ipc/parse-event-detail.ts:1-14`).

`src/background/approval-window.ts` then serializes user attention. It keeps a module-local queue array and a single `openWindowId`; on each enqueue it opens `approval.html?requestId=<id>` if no approval window is active, and when the active approval window closes it bumps auto-lock activity and opens the next queued request (`src/background/approval-window.ts:1-39`). This is lean, but it solves a real extension-wallet problem: approval spam should never explode into N parallel windows.

The approval UI itself does not subscribe to a live stream of authorization events. Instead, it reads the `requestId` from the URL, constructs a port-backed wallet API, calls `authorization.getPending`, filters the returned list for the matching request, and renders `AuthorizationDialog` from shared UI (`entrypoints/approval/main.tsx:24-50`, `entrypoints/approval/main.tsx:102-110`). On approve or deny, it calls `authorization.resolve` and closes the window; on `beforeunload`, it best-effort auto-denies unresolved requests (`entrypoints/approval/main.tsx:52-100`).

The worker README calls out why this design exists: `authorization.getPending` is used instead of broadcast-replay because replaying every pending auth to every open UI surface is noisy and unnecessary (`README.md:106-108`). The offscreen implementation backs that up with an important detail: `authorization.getPending` scans pending authorizations across every running session, not just the current UI chain, because the approval window only knows a request ID and the dApp request may belong to a different session/network than the UI that opened it (`src/offscreen/wallet-host.ts:97-113`). That is a good correction for a common multi-network wallet bug.

## 8. Aztec patterns Grego uses

This is the most important honest read for Nulo: inside `extension-wallet/`, Grego does not directly implement much Aztec transaction logic. The direct Aztec-facing imports in this package are mostly types, schemas, and wallet-sdk transport helpers: `BackgroundConnectionHandler`, `ContentScriptConnectionHandler`, `WalletResponse`, `hashToEmoji`, `Fr`, `ChainInfo`, and `WalletSchema` (`entrypoints/background.ts:2-3`, `entrypoints/content.ts:1-23`, `entrypoints/popup/Popup.tsx:3`, `src/offscreen/wallet-host.ts:1-4`, `package.json:19-36`). The extensionization work lives here; the deeper Aztec wallet logic mostly does not.

Where and how PXE is created: not directly visible in this package. The README says the offscreen document hosts `PXE / WalletDB / shared session`, and `WalletHost` reaches that world through `getOrCreateSession`, `getSharedResources`, and `getRunningSessionIds` from `@demo-wallet/shared/core` (`README.md:39-46`, `src/offscreen/wallet-host.ts:47-53`, `src/offscreen/wallet-host.ts:159-164`, `src/offscreen/wallet-host.ts:220-224`). So the extension package clearly chooses “PXE lives in offscreen,” but the actual constructor calls and teardown hooks are outside this package.

Kernel-less simulation: I found no direct `kernelless` or `noKernel` usage in the 28 TS/TSX files of this package. The closest visible mechanism is that `dapp.*` methods are generated from `WalletSchema`, and the README uses `dapp.simulateTx` / `dapp.sendTx` as examples, so the extension transport can forward simulation and send calls if the underlying external wallet exposes them (`README.md:82-87`, `src/offscreen/wallet-host.ts:199-237`). But the “kernel-less” detail itself is not implemented or referenced here.

“from NoAddress” execution: I found no `fromNoAddress` or `NoAddress` usage in this package. Same answer for `setPayer`, `feePayer`, `feePayment`, and `FeeJuice`: no direct matches in extension-owned code. If Grego is using those patterns, they are not expressed inside `extension-wallet/`; they would have to be inside shared-core wallet logic, which is outside this scope.

Auth witness creation: there is no direct `AuthWit` or `authWitness` usage in this package. Note discovery and syncing: no direct `noteDiscovery` or `syncNotes` usage. Account registration: no direct `registerAccount` or `registerSender` usage. Schnorr account contract usage: no direct `schnorr` usage. Those absences are meaningful for Nulo because they tell you that this package is not where Grego chose to expose or customize Aztec account semantics.

What is present is the extension-facing Aztec glue. `WalletHost` revives `Fr` values that crossed JSON port boundaries back into class instances, both for `chainInfo` and for method arguments parsed through Zod function schemas (`src/offscreen/wallet-host.ts:5-29`, `src/offscreen/wallet-host.ts:32-45`, `src/offscreen/wallet-host.ts:167-189`, `src/offscreen/wallet-host.ts:201-227`). The UI-facing `makePortWalletApi()` pushes a selected `(chainId, version)` into offscreen with `network.set` and then builds a Proxy-backed `InternalWalletInterface` whose methods route to `wallet.<method>` and whose event listeners subscribe to broadcast names (`src/ui/port-wallet-api.ts:15-45`). So Grego’s main Aztec-specific contribution in this package is not transaction logic; it is robust adaptation of Aztec wallet interfaces to MV3 transport constraints.

The biggest takeaway for Nulo is therefore negative but useful: if you want to study Grego’s choices around PXE hosting, offscreen lifetime, wallet-schema forwarding, auth approval routing, and JSON/structured-clone pain, this package is rich. If you want to study his fee-payer, NoAddress, AuthWit, note sync, or Schnorr account-contract patterns, this package is not the layer where those are expressed.

## 9. Production gotchas Grego already solved

The obvious one is CSP. Grego does not hand-wave “MV3 works with WASM.” He explicitly narrows CSP to `'self'` plus `'wasm-unsafe-eval'`, then neutralizes the specific transitive dependency (`function-bind`) that would otherwise need dynamic code construction, by aliasing both `function-bind` and `function-bind/implementation` to a CommonJS stub that uses native `Function.prototype.bind` instead (`wxt.config.ts:25-36`, `wxt.config.ts:50-55`, `src/shared/function-bind-stub.cjs:1-22`). That is exactly the sort of fix Nulo should steal rather than rediscover.

Second: Node globals in extension contexts. Aztec packages reach for `Buffer` and `process.env.*` early, so Grego uses `vite-plugin-node-polyfills` and also imports a tiny runtime `Buffer` polyfill into entrypoints (`wxt.config.ts:12-24`, `src/shared/polyfills.ts:1-5`, `entrypoints/background.ts:1`, `entrypoints/offscreen/main.ts:1`). The comment in `wxt.config.ts` is correct: a single-entry shim is not enough if code-splitting moves the offending import elsewhere.

Third: offscreen startup races. The create-document promise is not a readiness guarantee, and Grego explicitly treats it that way with `readyPromise`, `markOffscreenReady()`, and an `offscreen-ready` message emitted only after `WalletHost.start()` has run (`src/background/offscreen-lifecycle.ts:13-33`, `src/background/offscreen-lifecycle.ts:52-64`, `entrypoints/offscreen/main.ts:8-14`). If Nulo has ever seen “first popup open hangs, second works,” this is the fix.

Fourth: structured clone is not enough for Aztec values. `PortServer` catches `postMessage` serialization failures and falls back to `jsonStringify`, with `PortClient` transparently rehydrating results when `resultIsJson` is set (`src/ipc/port-server.ts:47-87`, `src/ipc/port-client.ts:93-109`). This is concrete experience encoded as code, not theory.

Fifth: JSON boundary revival. Grego knows `Fr`, `AztecAddress`, `Buffer`, and similar values will cross ports as hex strings or plain objects, so he uses schema-derived arg parsers and a `reviveChainInfo()` helper to reconstruct usable objects before passing them into shared-core wallet logic (`src/offscreen/wallet-host.ts:5-45`, `src/offscreen/wallet-host.ts:167-189`, `src/offscreen/wallet-host.ts:201-227`). This is one of the most reusable lessons in the package.

Sixth: schema-key enumeration instead of Proxy spread. The README explicitly says `wallet.*` and `dapp.*` dispatch use explicit enumeration because spreading a Proxy into a plain object loses the `get` trap, and the code really does iterate `Object.keys(InternalWalletInterfaceSchema)` and `Object.keys(WalletSchema)` to build handler maps (`README.md:106-107`, `src/offscreen/wallet-host.ts:168-189`, `src/offscreen/wallet-host.ts:201-234`). If Nulo is doing anything clever with generic RPC surface generation, this is worth checking.

## 10. UI

The UI stack is React 18 plus MUI 6 throughout, with a dark theme created independently per surface (`package.json:28-35`, `entrypoints/popup/main.tsx:1-12`, `entrypoints/approval/main.tsx:114-121`, `entrypoints/onboarding/main.tsx:1-12`, `entrypoints/expanded/main.tsx:22-23`, `entrypoints/expanded/main.tsx:58-63`). Grego is not trying to build a custom design system in this package; he is minimizing UI surface area and reusing shared components where possible.

The popup is intentionally a control/status view, not the full wallet. It tracks five states in priority order: “still loading,” “unverified active sessions,” “pending discovery requests,” “vault uninitialized,” “vault locked,” and finally “wallet unlocked” with a button that opens the expanded view (`entrypoints/popup/Popup.tsx:15-18`, `entrypoints/popup/Popup.tsx:120-242`, `entrypoints/popup/Popup.tsx:244-329`). That priority order is smart. A just-established session verification event should interrupt normal wallet browsing, and a discovery request should interrupt routine unlock status. The UI itself is still rough, though: discovery and uninitialized states are explicitly TODO placeholders, and even the session verification block is labelled as a simple v1 implementation (`entrypoints/popup/Popup.tsx:127-242`, `entrypoints/popup/Popup.tsx:244-270`).

The expanded view is where the real wallet UX lives. Grego simply mounts `StandaloneShell` from shared UI and feeds it extension-specific hooks: “do I already have a vault,” “am I already unlocked,” “verify this PIN by calling `vault.unlock`,” “initialize vault on first install,” and “build wallet API for a given chain/version via ports” (`entrypoints/expanded/main.tsx:31-55`). The one extension-specific patch here is important: the wrapper forces a remount on every `vault-locked` broadcast because the shared shell only checks unlocked state at mount time (`entrypoints/expanded/main.tsx:24-33`). That is a good example of local adaptation without forking shared UI.

The approval window is similarly thin. It hosts a single `AuthorizationDialog` from shared UI inside a `WalletContext.Provider` backed by the port wallet API (`entrypoints/approval/main.tsx:5-12`, `entrypoints/approval/main.tsx:102-110`). Onboarding is the only fully local flow: a three-step MUI Stepper that sets an initial password by calling `vault.initialize` (`entrypoints/onboarding/Onboarding.tsx:13-46`, `entrypoints/onboarding/Onboarding.tsx:48-125`).

So the UI story is: popup for urgent/security-critical interrupts, expanded view for full wallet behavior, approval window for per-request auth, onboarding for first install. That split is solid even if the popup still needs product polish.

## 11. Storage

There are three storage tiers in the package. First, `chrome.storage.local` holds long-lived extension settings such as remembered apps and auto-lock settings (`src/background/remembered-apps.ts:13-19`, `src/background/remembered-apps.ts:34-66`, `src/background/auto-lock.ts:7-21`). Second, `chrome.storage.session` holds ephemeral “I already verified this session’s emoji fingerprint” state, which persists across popup closes but dies on browser restart (`entrypoints/popup/Popup.tsx:47-64`). Third, IndexedDB via `@aztec/kv-store/indexeddb` stores vault metadata in the `vault-meta` data directory (`src/vault/vault-meta.ts:1-31`, `src/vault/vault-meta.ts:34-64`).

The remembered-apps format is worth calling out. Each entry stores `appId`, `origin`, `rememberedAt`, `chainId`, and `version`, and old-format entries without `chainId`/`version` get filtered out on load (`src/background/remembered-apps.ts:3-19`). That is a small data-model decision with real wallet consequences: it avoids cross-network trust bleed.

The auto-lock settings model is thinner. `getMinutes()` reads `SETTINGS_KEY` from local storage and falls back to `DEFAULT_AUTO_LOCK_MINUTES = 15` (`src/background/auto-lock.ts:7-21`, `src/shared/constants.ts:5-13`). There are min/max constants defined, but this package does not enforce clamping at read time (`src/shared/constants.ts:8-13`, `src/background/auto-lock.ts:11-20`).

For WalletDB and actual account persistence, the package again delegates. The README says the offscreen document hosts `WalletDB`, and the caveat says account secrets are currently stored plaintext in IndexedDB pending refactor (`README.md:39-46`, `README.md:110-113`). But the only IndexedDB code directly visible in this package is `vault-meta`; the account database itself lives behind shared-core abstractions (`src/vault/vault-meta.ts:20-31`, `src/offscreen/wallet-host.ts:47-53`).

## 12. What Nulo should steal

First, steal the offscreen readiness gate and Firefox fallback almost verbatim. The `readyPromise` / `offscreen-ready` handshake solves a real MV3 race, and the hidden minimized-window fallback makes the same architecture portable to Firefox instead of forking the whole runtime path (`src/background/offscreen-lifecycle.ts:13-33`, `src/background/offscreen-lifecycle.ts:35-85`, `entrypoints/offscreen/main.ts:8-14`).

Second, steal the port transport’s serialization strategy. `PortServer` trying structured clone first and then falling back to Aztec-aware `jsonStringify`, with `PortClient` auto-parsing on the far side, is exactly the kind of infrastructure that saves weeks of debugging once real wallet objects start crossing boundaries (`src/ipc/port-server.ts:47-87`, `src/ipc/port-client.ts:93-109`).

Third, steal the schema-driven RPC generation plus JSON-boundary revival. Grego does not manually maintain a giant method table for the wallet; he enumerates `InternalWalletInterfaceSchema` and `WalletSchema`, and uses schema-derived arg parsers plus `Fr` revival helpers to rehydrate values after port serialization (`src/offscreen/wallet-host.ts:5-45`, `src/offscreen/wallet-host.ts:167-189`, `src/offscreen/wallet-host.ts:201-227`). If Nulo wants a low-drift UI/offscreen contract, this is a strong pattern.

Fourth, steal the security UX around discovery/session trust. Remembered apps are scoped by origin and network, not just origin; active sessions expose verification hashes for emoji comparison; and those verification acknowledgements live only in session storage so they reset on browser restart (`entrypoints/background.ts:57-67`, `entrypoints/background.ts:221-235`, `src/background/remembered-apps.ts:21-51`, `entrypoints/popup/Popup.tsx:47-64`, `entrypoints/popup/Popup.tsx:127-186`).

Fifth, steal the approval queue shape. A single approval window keyed by request ID, with `authorization.getPending` and `authorization.resolve` scanning all running sessions, is simpler and safer than trying to build a generalized replay bus across popup, expanded view, approval modal, and content surfaces (`src/background/approval-window.ts:1-39`, `src/offscreen/wallet-host.ts:97-137`, `entrypoints/approval/main.tsx:39-100`).

Sixth, steal the keep-alive and idle-lock coordination. Grego keeps the service worker alive while dApp requests are in flight, suppresses auto-lock while an approval window is open or a request is mid-flight, and bumps activity on each meaningful transition (`src/background/offscreen-lifecycle.ts:87-101`, `entrypoints/background.ts:90-146`, `entrypoints/background.ts:152-160`). That is exactly the sort of “wallet feels reliable” behavior users notice only when it is missing.

## 13. Where Nulo's design might already be better

The biggest visible weakness on Grego’s side is at-rest protection. If Nulo already encrypts account secrets in IndexedDB, Nulo is ahead on the most important storage property because Grego explicitly has not shipped that yet (`README.md:110-113`). There is no softer way to say it: on this axis, a wallet either protects the database at rest or it does not.

If Nulo’s popup and approval UX are already fully productized, that is also better than Grego’s current extension package. Grego’s expanded view and approval dialog reuse shared UI successfully, but the popup still contains TODO placeholders for discovery approval and uninitialized-wallet UX, and the session-verification panel is intentionally minimal (`entrypoints/popup/Popup.tsx:127-270`, `entrypoints/approval/main.tsx:102-110`, `entrypoints/expanded/main.tsx:31-55`).

Nulo may also have an auditability advantage if more of its wallet runtime actually lives inside the extension package rather than behind shared external modules. In Grego’s package, critical behavior like session creation, shared resources, full wallet UI shell, and authorization dialog all come from `@demo-wallet/shared/*` (`src/offscreen/wallet-host.ts:47-53`, `entrypoints/expanded/main.tsx:4-7`, `entrypoints/approval/main.tsx:5-12`). That is efficient code reuse, but it means an “extension-only” review cannot see the full Aztec logic without leaving scope.

One smaller place Nulo can beat this design is idle/UX rigor. Grego defines a `ui-activity` port hook in the worker and comments that it should fire whenever popup, expanded, or approval surfaces connect, but in this package I only see the listener, not any UI surface opening that port (`entrypoints/background.ts:162-165`). Likewise, min/max auto-lock constants are defined but not enforced at read time (`src/shared/constants.ts:8-13`, `src/background/auto-lock.ts:11-20`). If Nulo already emits real UI activity pings and clamps idle settings, it is tighter operationally.

Finally, Nulo may already be better simply by matching Grego’s topology natively rather than retrofitting it onto shared web code. Your described stack already uses offscreen PXE and port-based RPC. Grego proves that topology is sound; he does not prove that his package is cleaner than a purpose-built extension architecture from day one (`README.md:21-61`, `src/offscreen/wallet-host.ts:47-53`, `entrypoints/expanded/main.tsx:31-55`).

## 14. Trade-offs

Grego is deliberately staying small. The service worker is kept close to “router only,” the offscreen host concentrates privileged runtime state, most UI complexity is reused from shared packages, and the internal transport surface is tiny and schema-driven (`README.md:65-90`, `entrypoints/background.ts:50-149`, `src/offscreen/wallet-host.ts:77-141`). That is a good way to get a serious extension wallet running without exploding scope.

The trade-off is that several scaling edges are already visible. `currentChainInfo` is a single mutable field on `WalletHost`, which means UI-driven network selection is effectively last-writer-wins across all UI surfaces, even though dApp requests route by session-specific chain info (`src/offscreen/wallet-host.ts:59-60`, `src/offscreen/wallet-host.ts:86-95`, `src/offscreen/wallet-host.ts:216-224`). The approval queue is single-window and single-threaded by design (`src/background/approval-window.ts:1-39`). `authorization.getPending` scans every running session linearly (`src/offscreen/wallet-host.ts:103-113`). Remembered apps are a local-storage array with linear scans (`src/background/remembered-apps.ts:13-31`).

There is also a package-boundary trade-off. Reusing `@demo-wallet/shared` gives Grego velocity and consistency across web and extension surfaces, but it means extension-specific analysis hits a wall exactly where deeper Aztec behavior begins (`src/offscreen/wallet-host.ts:47-53`, `entrypoints/expanded/main.tsx:4-7`, `entrypoints/approval/main.tsx:5-12`). For a solo or small-team build, that is probably the right choice. For a wallet that wants extremely sharp extension-specific ownership boundaries, Nulo may want less indirection.

The biggest intentional compromise is security staging. Grego clearly wanted the offscreen runtime, approval queue, vault UX, dApp discovery path, and Firefox fallback working before he tackled full encrypted persistence (`README.md:95-113`, `src/vault/vault-state.ts:24-54`). That is a reasonable v1 sequencing choice, but it is still a trade-off, not a free lunch.

One final practical note: I attempted to run the package checks, but the sandbox denied Yarn when it tried to create a repo-level `.yarn` directory outside my writable roots. So this report is based on direct source reading plus the package’s own test comments, not on executing `yarn test` or `yarn compile`.

## Bottom line for Nulo

1. Copy Grego’s offscreen lifecycle machinery first: ready-gated startup, Firefox fallback, and worker keep-alive are battle-tested extension engineering, not optional polish (`src/background/offscreen-lifecycle.ts:13-101`, `entrypoints/offscreen/main.ts:8-14`).
2. Treat `extension-wallet/` as an extensionization reference, not as the canonical source for Aztec transaction semantics; the interesting MV3 lessons are here, but fee payer/AuthWit/NoAddress/note-sync patterns are not (`src/offscreen/wallet-host.ts:47-53`, `README.md:39-46`).
3. Steal the schema-driven RPC and JSON-boundary revival patterns; they are likely to save Nulo from long-tail bugs once real Aztec objects cross ports (`src/offscreen/wallet-host.ts:5-45`, `src/offscreen/wallet-host.ts:167-237`, `src/ipc/port-server.ts:47-87`).
4. Do not copy Grego’s plaintext-at-rest stage unless you absolutely must; if Nulo can ship encrypted persistence, that is a decisive advantage (`README.md:110-113`).
5. Grego’s trust UX is stronger than many wallets: origin+network remembered apps, session emoji verification, and a serialized approval queue are all worth adopting (`entrypoints/background.ts:57-67`, `entrypoints/background.ts:221-235`, `src/background/approval-window.ts:1-39`, `entrypoints/popup/Popup.tsx:127-186`).

## Aztec-specific recommendations

- Keep PXE in offscreen and keep the service worker out of wallet execution; Grego’s package is strongest exactly where it enforces that boundary (`README.md:39-46`, `entrypoints/background.ts:90-146`, `src/offscreen/wallet-host.ts:56-75`).
- Expose wallet and dApp methods from schemas instead of hand-maintaining transport glue, then revive `Fr` and related values explicitly after JSON hops (`src/offscreen/wallet-host.ts:5-45`, `src/offscreen/wallet-host.ts:167-237`).
- If Nulo has custom Aztec transaction flows, hang them behind the same `wallet.*` / `dapp.*` transport pattern rather than inventing a second RPC stack (`README.md:78-90`, `src/ipc/port-envelope.ts:3-53`).
- Preserve a clear split between dApp discovery/session protocol and actual wallet execution; Grego lets wallet-sdk handle the former while the offscreen host owns the latter (`entrypoints/content.ts:14-23`, `entrypoints/background.ts:50-149`).
- Add Grego-style serialization fallbacks early if Nulo is moving Aztec objects across ports; waiting until later usually means debugging `DataCloneError` under pressure (`src/ipc/port-server.ts:47-87`, `src/ipc/port-client.ts:93-109`).
