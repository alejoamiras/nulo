The diagnosis — Phase 2 was the floor, not the ceiling codex pushback

The 8-item Phase 2 list builds a state machine and persists it. That gets us to roughly 4/5 on durable jobs. It does NOT get us to 5/5. The honest gap is that a state machine is not a job system — a job system also requires scheduling discipline, replay safety, recovery semantics, and observability.

The single most important reframe: a state machine is not a job system. A real job system also needs scheduling discipline (fairness), replay safety (idempotency), recovery semantics (retry + tombstones), and observability (sweeper + attach/detach). Phase 2 builds the FSM; Phase 2+ wraps it in the rest of the machinery a job system actually needs.

Six properties Phase 2 leaves on the table codex

1. Fairness
What: Priority queues. User-blocking jobs (a tx the user just approved) jump ahead of background work (history sync). Per-(origin, profileId) caps so a noisy dApp can't starve the rest.
Why: A FIFO queue under load means a user-approved tx waits behind a routine sync. That's a UX defect, not a correctness one — but it's the kind that destroys trust.
2. Idempotency
What: Every job carries an idempotency key derived from (origin, intent-hash, nonce, salt). Submitting the same intent twice (e.g. dApp retries after a perceived timeout) resolves to the same jobId instead of duplicating work.
Why: Without it, "I clicked once but it submitted twice" becomes a real bug class. Aztec txs aren't easily revertible.
3. Retry policy
What: Failed jobs distinguish retryable from terminal errors. Retryables get exponential backoff with a cap and a budget. Terminals (user reject, invalid sig, contract revert) skip retry and go straight to FAILED.
Why: "Retry forever" floods the chain. "Never retry" drops recoverable network blips. Both are wrong defaults.
4. Tombstones
What: Terminated jobs (cancelled, succeeded, failed-terminal) are not deleted — they're marked with a tombstone. A late chrome.alarms wake-up that finds status=PROVING for a job whose tombstone says CANCELLED does nothing.
Why: Without tombstones, an alarm firing after a user cancel can resurrect the job. Subtle but real.
5. Sweeper
What: A periodic scan moves stuck jobs (e.g. PROVING for > 10min with no heartbeat) into a dead-letter queue. User sees them in a "needs attention" surface; the system doesn't pretend they're still in flight.
Why: Bugs happen. Without a sweeper, a one-time progress-write failure looks identical to "still working" — forever.
6. Attach / detach
What: A freshly-opened popup can subscribe to an in-flight jobId at any time and detach without affecting the job. Multiple observers are allowed by the attach map (popup re-opened on a different tab, future side-panel surface, etc.) without coupling the job's lifecycle to any of them.
Why: The popup is ephemeral by design in MV3. The job system has to treat observation as optional and decoupled from execution.

The full job system — not just a state machine design

Chaos discipline codex

Everything above is hard to test in unit tests alone. Phase 2+ ships an ongoing chaos discipline as a first-class testing category, not a one-off audit:

  • SW-kill chaos — periodically kill the SW mid-prove in CI; verify recovery via alarms + tombstones
  • Approval-spam drills — fire 1000 approvals from one origin; verify per-origin rate limit + fairness
  • Malicious-dApp suite — adversarial test cases for the dApp surface (replay, double-submit, invalid sigs, permission escalation attempts)
  • Cold-boot fuzzing — fire dApp messages during the first 500ms of SW boot; verify LazyListener captures all of them

Storage corruption drills (inject malformed bytes into chrome.storage.local; verify fallback + invariant validator) move with the rest of the storage-safety work to Maximalist persistence-spine.

Realistic estimate scope

Phase 2 alone is ~3-6 weeks. Phase 2+ adds:

  • ~3-4 weeks for the six job-system properties + chaos discipline harness
  • ~1-2 weeks for narrow formal-methods setup (TLA+ or Alloy on the FSM + permission matcher)

Bottom line: Phase 2 → Phase 2+ is roughly 1.5-2× the work of the original 8-item plan, all on the same single browser-extension surface.

The cut you'd make if you only had one extra month after Phase 2: idempotency + retry policy + tombstones + sweeper. Skip fairness (acceptable in low-concurrency cases). Skip attach/detach beyond what subscribe-by-jobId already gives you. Hold back chaos discipline and formal methods for a follow-up sprint.

Considered, not pursued — product decisions product scope

Two ideas surfaced during the design conversation that are technically tractable but were ruled out as product decisions. Recorded here so the thinking isn't lost; not part of Phase 2+ scope.

decided against Dedicated progress window

A detached chrome.windows.create popout that owns minutes-long proofs, with the main popup as an observer. Rabby does this for approvals.

Why not: adds a second long-running UI surface to design, maintain, and explain. The popup stays as Nulo's single user-visible surface; subscribe-by-jobId (via the attach map) already gives us close-and-rejoin without a separate window.

decided against Desktop proving companion

An optional Tauri-style native daemon that hosts PXE + BB-WASM long-running, sidestepping MV3's SW-death entirely. Extension hands work to it via WebSocket when present.

Why not: introduces a parallel native distribution channel — separate install/update story, code signing, platform builds. The wallet stays browser-only; in-extension durability is what Phase 2+ delivers.
