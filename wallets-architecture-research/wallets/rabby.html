Rabby — pragmatic durable jobs in the wild

Verdict: Rabby is the wallet that takes "the SW will die" most seriously in shipped code. It doesn't have a formal job framework, but its service-level patterns — unlockPromise, persisted progress markers, per-origin rate limits — are the closest match to what Nulo's Phase 2 needs. Worth studying line by line.

Runtime shape diagram

Rabby is an MV3 Chromium extension with a service worker entry, popup UI (React + Redux), and a content script. There is no offscreen document — all signing happens inside the SW or via injected provider on the dApp page. The architecture leans heavily on services with persisted state in chrome.storage.local + IndexedDB.

How durable jobs work here analysis

Rabby doesn't have a "job registry" abstraction. What it has, and what makes durable work possible, is:

  1. unlockPromise in services — when a service method runs before the keyring has finished booting, the service returns a promise that resolves once boot completes, rather than throwing. The dApp-facing handler just awaits, transparently. R6 pattern
  2. Persisted progress markers — historyDbService stores per-(address, chainId) cursors in IndexedDB. If the SW dies mid-indexing, the next boot resumes from the last cursor instead of restarting. R7 pattern
  3. Per-origin notification rate limits — notificationService enforces per-origin caps so a busy dApp can't blow up the popup queue. Functions as a back-pressure mechanism. R5 pattern
  4. No chrome.alarms wake-up — Rabby relies on user interaction (popup open / dApp message) to revive the SW. It doesn't proactively resume work on a timer.
Pattern to internalize: Rabby treats its services as durable, not its jobs. Persistence lives at the service boundary, not in a separate job framework. That's a cheaper-to-ship design than MetaMask's approval state machine, and gets you most of the benefit.

Strengths research

DimensionWhy it stands out
dApp ergonomicsEIP-1193 conformance is meticulous; method handlers consistently await unlockPromise rather than throwing during boot. Far fewer "wallet not ready" bugs surface to dApps.
Service-level persistenceEvery service owns its state, persists it, and rehydrates on boot. No central state blob to migrate atomically.
History sync resumabilityhistoryDbService cursors make full-chain reindexing safe to interrupt — a model for any long-running work.
Per-origin rate limitingnotificationService's per-origin caps protect the UI from runaway dApps without a global queue.
Cross-service signalingPlain event emitters between services — no message bus framework, no schema. Stays readable.

Risks / anti-patterns research

RiskWhy
No formal job frameworkEach service rolls its own resume logic. Inconsistent across the codebase.
No chrome.alarms wake-upIf the SW dies and nothing pokes it, persisted progress sits idle.
Manual state migrationsNo numbered-migrations framework like MetaMask. Schema changes are ad hoc.
Mixed Redux + service-stateSome state lives in Redux (popup) and some in services (SW). Easy to drift.

What Nulo should steal phase 2

  • unlockPromise at every dApp-facing method — Nulo's port handlers should await profile-boot rather than throwing "wallet locked".
  • Per-service persisted cursors — any long sync (txHistory, balance index) writes progress on every increment, so SW death is a recoverable event, not a restart.
  • Per-origin rate limiting — when Nulo opens the door to "real users", a busy dApp must not be able to spam the approval queue.

What not to copy phase 2

  • Ad-hoc resume logic per service — Nulo can do better by introducing a single JobRegistry primitive instead of N copies of the pattern.
  • Skipping chrome.alarms — Rabby gets away with no proactive wake-up because EVM signing is fast. Aztec proofs are not; Nulo needs the wake-up.
  • Mixed Redux + service state — keep the existing Pinia + ServiceClient split; don't introduce a second source of truth.
