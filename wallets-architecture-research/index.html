The four findings research

① Nulo is already production-quality where it counts

Biome-enforced package layer rules, the M6 component model (L0–L6 + C0/C1), PasswordSecretBox with cross-version test vectors, and the NuloAccount adapter that delegates to upstream @aztec/accounts/schnorr with recursive payload chunking and first-tx multicall wrapping — all of this is real, not aspirational. Don't undo any of it.

② Long-running ops are the one big architectural gap

Default ServiceClient timeout is 60s. Aztec proofs routinely outrun it. "Timeout" is not "cancellation" — the SW keeps proving while the popup shows failure. PXE concurrency is globally serialized. No chrome.alarms wake-up. This is what Phase 2 fixes.

③ Grego's Aztec sim patterns are non-negotiable

Stub-account simulation overrides (real signing keys never enter the simulator). Public-static fast path via simulateViaNode + buildMergedSimulationResult. completeFeeOptions({forEstimation: true}) for one-codepath sim-vs-real gas policy. all shipped in PR 8b/8c/9

④ Stop trying to keep the SW alive. Design around it dying.

MetaMask writes a 2-second chrome.storage.session timestamp and explicitly calls it a hack. Rabby pings the offscreen every 5 seconds — acknowledged bet. The right pattern: persist enough state to resume, register listeners synchronously at top-level, treat any in-flight job that survives the worker as a feature.

Nulo today post-merge state

Durable jobs today: none. The ExecutionServiceClient blocks the popup; the SW doesn't persist mid-prove state. A tx may settle even if the popup says "failed" (the 60s timeout wins the race against a longer proof).

Three futures for Nulo target design

The original plan condensed everything into "Phase 2". Post-merge thinking (with codex pushback) split it into three views, ordered by ambition: the shippable cut, the same problem done right, and the full year-long maximalist program.

Phase 2 — shippable

The original 8-item plan: JobRegistry FSM, AbortController, chrome.alarms, LazyListener, PXEConcurrencyManager, IDB backup, migrations. 3-6 weeks. Stops the SW from lying to users; gets durable jobs to ~4/5.

Read Phase 2 →

Phase 2+ — durable jobs full

What 5/5 durable jobs actually requires in the existing browser-extension surface: fairness, idempotency, retry policy, tombstones, sweeper, attach/detach. Plus chaos discipline and narrow formal methods. ~1.5-2× Phase 2.

Read Phase 2+ →

Maximalist — 5/5 everywhere

Year-long, three-engineer vision: runtime spine + persistence spine + dApp/UX + surface + Aztec depth + hardening. Plus new dimensions (network privacy, supply chain, observability, chaos, formal methods). 1 year.
