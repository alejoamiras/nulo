Executive summary

The audit found 12 verified security issues in the Nulo wallet — none classified as Critical, but 8 High-severity and 4 Medium. All 12 were independently re-read against current source after dedup; none were refuted.

If you only read one thing: the recurring pattern is "coarse-grained trust is checked once, then reused too broadly." The wallet repeatedly validates a high-level identity or permission, then trusts it for finer-grained decisions later — even when the data has drifted, the session has been revoked, or the original validation never actually checked the right thing.

Cheapest fixes first (hours each, not days)

  1. F-007 — passkey unlock missing credential binding. Four-line patch.
  2. F-003 — accounts.canGet:false setting is decorative. Remove the exemption + add the check.
  3. F-004 — same shape: data.addressBook sub-grant is decorative. Add scope checkers.

What the audit ran

  • Phase 1 mapped 6 packages in parallel — entrypoints, trust boundaries, dependency direction, frameworks, test surfaces, dev-only paths.
  • Phase 2 ran 8 cluster audits, each with one Claude Opus pass + one Codex xhigh pass (different model families catch different blind spots). Produced 121 raw findings.
  • Phase 3 ran a Codex coordinator to dedupe by root cause + sink + boundary, assign CVSS bands, and surface cross-cutting themes. 121 → 12.
  • Phase 4 ran a Claude Opus verifier with an anti-anchoring protocol (form an independent verdict before reading the coordinator's claim). All 12 confirmed.

Methodology note: the formal /harden ultra spec calls for 4 agents per cluster (2 of each family). Practical implementation in this run was 2 agents per cluster (1 of each family), with the Phase 2.5 rebuttal round absorbed into the coordinator's cross-model dedup. Effective intensity sits between /harden max and full /harden ultra. The dedup ratio (121 → 12 = 90% reduction) suggests the negative list worked and remaining findings are well-grounded.

High findings (8)

High F-001 Third-party iframes are credited as the top-frame origin during wallet discovery
Found by Claude+Codex  confidence: high  CWE-346 · CWE-441  fix: days

What it is. Web pages can embed other pages inside themselves using iframes (think of an ad iframe on a news site — the news site is the "top frame," the ad is an "inner frame"). They have different origins (different URLs) and shouldn't share permissions. Today, when a wallet conversation starts from inside an iframe, the wallet records the parent page's identity instead of the iframe's. The iframe inherits any grants the user has given to the parent page.

What an attacker would do. Get their malicious iframe loaded on a page where the user has already approved Nulo (a news site that runs ads, a forum, anything with third-party content). The iframe asks Nulo to do things; Nulo thinks the trusted parent page is doing them; the user sees the parent's hostname in the popup and approves.

The fix. Bind the wallet session to the specific frame (URL + frameId), not the tab. Reject discovery from subframes by default unless the use case explicitly needs it.

Technical trace

Trace: extension/manifest/manifest.config.ts:31-37 injects the content script into all frames → iframe-local discovery is relayed by the upstream content_script_connection_handler.js:60-86 → upstream attribution uses sender.tab.url (top frame) instead of sender.url (the actual frame) at background_connection_handler.ts:187-188 → Nulo stores/looks up the session keyed by origin + chainId at wallet-sdk/background.ts:351-458 and dapp-session/service.ts:73-99 → later RPCs run under ctx.origin = session.origin at wallet-sdk/background.ts:516-520.

Note on upstream coupling: this is partially blocked on upstream @aztec/wallet-sdk 4.2.0 design choices. A Nulo-side defense-in-depth wrapper at wallet-sdk/background.ts:121-135 can land today even before upstream changes.

High F-002 Tab-wide discovery replies let sibling frames hijack or tear down a victim session
Found by Codex only  confidence: moderate  CWE-668  fix: days

What it is. When the wallet says "OK, you can connect," it broadcasts that answer to the entire browser tab, not to the specific frame that asked. Every frame in the tab hears the approval and can race to claim it. This is the same family of issue as F-001 (the iframe pretending to be the top frame) but a separate mechanism — even after you fix F-001, this one still bites.

What an attacker would do. A malicious iframe in the same tab as the legitimate dApp races to send the "key exchange" first. The first one wins. Even after the real frame has connected, the malicious iframe can still send a "disconnect" message keyed by the session ID and silently tear down the legitimate session.

The fix. Target every wallet → page message to the original frameId, not the whole tab. Reject unsolicited "approval" messages in the content script unless a matching local request is actually pending.

Technical trace

Trace: Nulo sends discovery replies to the whole tab via wallet-sdk/background.ts:118-135 → Chrome delivers them to every frame when no frameId is specified → every injected content script accepts DISCOVERY_APPROVED at upstream content_script_connection_handler.js:88-156 → first sibling to send KEY_EXCHANGE_REQUEST wins at background_connection_handler.js:133-166 → any sibling can later DISCONNECT by session id at background_connection_handler.js:68-71,200-221.

Coupled with F-001 — both should be fixed in the same change.

High F-003 accounts.canGet:false is not enforced on account disclosure
Found by Claude+Codex  confidence: high  CWE-862 (Missing Authorization)  fix: hours · CHEAPEST

What it is. The wallet's permission model has a flag called canGet on the "accounts" capability. A dApp can request "let me operate on accounts" without "let me read their addresses." The UI shows this distinction. The code ignores it.

What goes wrong. A dApp asks for accounts with canGet:false. The user approves, thinking the dApp can't read addresses. The dApp immediately receives the account list anyway, in the same approval response — and can keep re-reading it forever via getAccounts().

The fix. Stop exempting getAccounts from the capability checker, and respect the canGet bit on the approval-response path. Hours of work.

Technical trace

Trace: dApp requests accounts capability with canGet:false via wallet-bridge/dispatcher.ts:235-236,504-510 → selected accounts are persisted into session.accounts at dispatcher.ts:614-631 → the grant response still includes them at dispatcher.ts:658-669,689-713 → later getAccounts() returns session.accounts at dispatcher.ts:288-317,325-337 because capability-map.ts:14 exempts the method.

Fix: remove getAccounts from the exemption set in capability-map.ts; enforce AccountsCapability.canGet on both response and handler paths.

High F-005 Attacker-chosen account scope lists are forwarded to PXE without session allow-list validation
Found by Claude+Codex  confidence: high  CWE-862  fix: days

What it is. The wallet's scope-enforcement checks which contracts a dApp can touch but ignores which accounts it can read private state from. Several RPC methods accept extra parameters (eventFilter.scopes, opts.scopes, opts.additionalScopes) — these are lists of account addresses the wallet should expose private state for, and the dApp can put anything in them.

What an attacker would do. Get the user to approve one account ("read private events for account A"). Then call methods that take a scopes array and append accounts B, C, D — accounts the user has in the same wallet but never approved for this dApp. Private state for B, C, D gets exposed even though only A was approved. One granted account silently widens to all accounts.

The fix. Validate every scope entry against the session's approved accounts. Reject anything outside the allow-list. Close the related fast path that skips checks when the calls array is empty.

Technical trace

Trace: wallet-bridge/scope-enforcement.ts:90-167 checks only contract/function scope → attacker-controlled eventFilter.scopes, opts.scopes, opts.additionalScopes are forwarded unchanged by dispatcher.ts:382-432,788-793,829-857 → execution sinks feed those addresses directly into PXE at execution/service.ts:1638-1640,1803-1851,1966-1967,2098-2153. Empty-calls fast path at scope-enforcement.ts:96-97,115-116 makes the bypass easier.

High F-006 Deleting or expiring the stored dApp session does not revoke live access
Found by Codex only  confidence: high  CWE-613 (Insufficient Session Expiration)  fix: days

What it is. There are two parallel session concepts: the stored session (a record in chrome.storage) and the live transport session (the actual encrypted channel between the dApp's tab and the wallet). When the user clicks "Disconnect this app" in Settings, only the stored record is deleted. The live channel keeps working.

What an attacker would do. Get the user to grant a dApp some permissions. Wait until the user gets nervous and disconnects the dApp from Settings (or until the stored session expires). The dApp's tab is still open, the channel is still live — so the dApp keeps calling network-only methods (getPrivateEvents, getAddressBook, registerSender, registerContract) and they all succeed. Revocation didn't actually revoke anything visible to the dApp.

The fix. Tear down the live transport session when the stored record is deleted or expires. Network-only capability enforcement should fail-closed when the stored session is missing.

Technical trace

Trace: settings/connected-apps/[id].vue:120-126 deletes only the stored DappSession via dapp-session/service.ts:274-283 → live encrypted transport stays alive (only onSessionTerminated tears it down at wallet-sdk/background.ts:184-245) → when tryGetDappSessionByOriginAndChain misses, enforceCapability returns empty grant set at dispatcher.ts:735-736 → dispatcher still builds network-only operations at dispatcher.ts:755-814 → privileged sinks at execution/service.ts:1578-1705 still execute.

High F-007 Passkey unlock does not bind supplied credential data to the target profile
Found by Claude+Codex  confidence: high  CWE-345  fix: hours · CHEAPEST

What it is. When you unlock a passkey profile, the popup runs a WebAuthn ceremony and hands the resulting credential data to the wallet's unlock function. The wallet uses that data to derive a master secret — but it never checks that the credential is actually the one bound to the profile you're unlocking. If the credential id doesn't match, the wallet opens the wrong profile anyway, using the wrong key material.

What an attacker would do. This requires popup-side compromise or a buggy WebAuthn flow, so it's not a direct web-to-wallet vector. But the failure mode is bad: profile A opens with a session derived from profile B's credential. Downstream account derivation uses the wrong key, signing breaks, or worse — the wallet may sign for an account it doesn't think it's signing for.

The fix. Four lines. The exact same check already exists in exportPlain at profile/service.ts:641-660 and in the passkey-restore path. Just mirror it in unlockPasskeyProfile: reject unless recovery.credentialId === snapshot.credentialId before opening the session.

Technical trace

Trace: popup auth forwards credentialData into unlockPasskeyProfile(...) at auth.vue:68-74 → snapshot of stored credential id taken at profile/service.ts:281-311 → PATH-A recovery trusts caller-supplied data via acquireRecovery and passkey-recovery-coordinator.ts:102-109 → PasskeyCredential.create derives master secret from supplied id/prf at wallet-crypto/passkey-credential.ts:36-63 → phase 3 only checks the profile row didn't rotate at profile/service.ts:313-327, never compares against the supplied credential → session opens with unbound secret at profile/service.ts:328-329.

Verified test template exists at service.integration.test.ts:321-330 — the regression pin can land in the same PR.

High F-008 Transaction approvals are blind to calldata and argument values
Found by Codex only  confidence: high  CWE-451  fix: days

What it is. When a dApp wants to send a transaction, the wallet popup shows a card per call with the contract name and function name (e.g., "transfer on Token@0xabc..."). The arguments to that function — amounts, recipients, calldata — are hidden behind a "View JSON" link in a secondary viewer. Most users will approve based on the visible labels alone.

What an attacker would do. Make the function NAME look routine while hiding the dangerous effect in the arguments. "Token.transfer" looks like a normal send; the args might say "transfer 100 to the attacker." "Vault.deposit" looks routine; the args might say "deposit at terms only the attacker benefits from." The user approves the boring-looking call.

The fix. Show structured argument summaries on the PRIMARY approval surface for every popup-gated operation. Keep the raw JSON viewer as a fallback, not as the only place that exposes the actual semantics. For transfers specifically: recipient address + amount + token should be on the main card.

Technical trace

Trace: operation models carry argument arrays in wallet-bridge/action.ts:37-54 and operation.ts:97-183 → popup loads them at execute/index.vue:260-266 → main review cards show only function labels + contract addresses at OperationCard.vue:104-138,253-361,374-399 → real payload only visible via secondary JSON viewer at execute/index.vue:391-396,456-463 → JSON viewer at popup/windows/json/index.vue:46-57.

High F-011 Custom RPC endpoints accepted with no transport policy; restore bypasses re-probing
Found by Claude+Codex  confidence: high  CWE-20 · CWE-184  fix: days

What it is. When you add a custom network endpoint, the URL is validated with z.string().url() — which accepts way more than you'd expect. javascript:, data:, file://, chrome://, and any HTTP URL on any domain all pass. The persisted URL field has no validation at all. The restore-from-backup path doesn't re-probe imported endpoints. Once a malicious endpoint is in the network list, the wallet uses it as the trusted authority for chain state, fees, notes, and signing inputs.

What an attacker would do. Get the user to add a custom endpoint via phishing ("connect to our fast RPC for better performance") — the URL could be a server they control. Or get them to import a malicious backup. Now their wallet asks the attacker's server about the chain: gas prices (attacker can inflate them), notes (attacker can lie about what's been received), even chain ID (attacker can claim a different chain — see F-012).

The fix. Central allowlist at the node-factory boundary: allow https: generally, allow http: only for loopback/dev hosts, reject other schemes outright. Re-validate restored endpoints before persisting them. Land this together with F-012.

Technical trace

Trace: endpoint validation is only z.string().url() at network/spec.ts:120-145; persisted NetworkInfo.rpcUrl is plain z.string() at network/spec.ts:97-100 → addNetwork, addEndpoint, updateEndpoint persist user-supplied URLs at network/service.ts:235-252,328-348 → restore() writes imported endpoints without re-probing at network/service.ts:613-633,757-768 → runtime use-sites call createAztecNodeClient(rpcUrl, ...) at aztec-runtime/adapters/aztec-node-factory-adapter.ts:15-17 → ultimately fetch(host, ...) at aztec-runtime/utils/fetch.ts:42-47.

Medium findings (4)

Medium F-004 data.addressBook is decorative; getAddressBook and registerSender ignore the sub-grant
Found by Claude only  confidence: high  CWE-863  fix: hours · CHEAPEST

What it is. Same shape as F-003. The wallet has a "data" capability with a sub-toggle for "can read your address book." The toggle is decorative — the actual address-book methods only check that the dApp has some "data" grant, not whether the address-book sub-grant was specifically given.

What goes wrong. A dApp asks for "data" access for the legitimate reason of reading private events. User approves "data" with addressBook: false. dApp immediately calls getAddressBook() and gets the full address book, plus can call registerSender() to inject arbitrary aliases.

The fix. Add explicit scope checkers for these two methods that require addressBook: true. Or split them into their own capability type so the existing scope-enforcement pattern works.

Technical trace

Trace: capability-map.ts:38-40 maps both methods to the data capability → scope-enforcement.ts:269-279 defines no checker for either → dispatcher builds aztec_getAddressBook / aztec_registerSender operations at dispatcher.ts:802-803 → the DataCapability.addressBook?: boolean field at capabilities.ts:47-51 is never consulted.

Medium F-009 Approval popups treat attacker-controlled display metadata as trustworthy
Found by Claude+Codex  confidence: high  CWE-451 · CWE-1007  fix: days

What it is. The popup approval UI renders strings the dApp controls — its name, the token name/symbol, function names — without sanitizing them. There's a sanitizer in the codebase already (it's used on the capability detail screen) but the high-stakes approval surfaces don't call it. Separately, the "trusted dApp identity" gets reduced from the full URL to just the hostname, hiding scheme/port differences.

What an attacker would do. Pick a deceptive dApp name or token symbol using Unicode tricks: Cyrillic с for Latin c in "USDC" (looks identical, different character); right-to-left override character (U+202E) to reverse part of the displayed text; zero-width spaces inside a name to defeat string-equality checks the user might do mentally. The user sees what looks like the real "USDC" or the real "Uniswap" and approves.

The fix. Route every attacker-controlled label through sanitizeWireString (or equivalent canonicalization) before rendering. Display the full origin (scheme + host + port), not just the hostname. Visually mark dApp-supplied names as untrusted metadata.

Technical trace

Trace: dApp metadata persisted as name: discovery.appName ?? discovery.appId at wallet-sdk/background.ts:423-427 → popup reduces authority to new URL(url).hostname in useDappHostname.ts:9-25 and renders raw name in DappIdentityBlock.vue:37-47, verify/index.vue:200-210 → execute cards render raw method/artifact labels at OperationCard.vue:114,134,222-231,266,285,325,340,357,369-371,394-398 → on-chain token symbols/names feed IncomingTrustPopup.vue:49,90,102,135-137 → existing sanitizer at dapp-session/capability-meta.ts:104-166 is used in capability UI but not here.

Medium F-010 Incoming-transfer persistence is unbounded, including blocked and hidden contracts
Found by Codex only  confidence: high  CWE-400 (Uncontrolled Resource Consumption)  fix: days

What it is. The wallet stores a record for every incoming-transfer note it discovers, with no cap and no garbage collection. Even when you BLOCK a contract, the wallet keeps storing its notes — it just hides them from the UI. The "block" flag stops display, not storage.

What an attacker would do. Send dust (tiny tokens) to your address from a contract they control. Repeatedly. The records pile up in chrome.storage.local, which has a hard ~5MB cap per extension. Eventually writes start failing for legitimate state too, breaking the wallet.

The fix. Add bounded retention for incoming-transfer rows. When a contract is blocked, short-circuit persistence entirely — don't even write the row. Handle storage-quota errors gracefully.

Technical trace

Trace: incoming-transfer rows persisted in local storage at incoming-transfer/repository.ts:20,34-35 with no cap/GC at repository.ts:48-49,56-72,95-120 → once a token is watched, scans read raw notes at service.ts:573-576 and persist every new nullifier at service.ts:617-629,660-676 → blocked state only hides rows because setTrustReject() flips state at service.ts:322-329, but later scans still upsert hidden rows.

Medium F-012 Live node chain identity is not rebound to the selected network before signing/proving
Found by Claude+Codex  confidence: high  CWE-345  fix: days

What it is. When you sign a transaction, the wallet asks the connected Aztec node "what's your L1 chain id and rollup version?" and uses the answer in the signature. It doesn't compare that live answer to the network you actually selected. So if the node lies after you've enrolled it — or if a malicious endpoint serves drift values — your signature ends up valid for a chain you didn't mean.

What an attacker would do. This is the follow-on after F-011. A malicious RPC endpoint accepted as a custom network gets to choose what chain id it reports. The wallet trusts it and signs accordingly.

The fix. Before any signing or proving step, recompute the live composite from node.getNodeInfo() and compare it against the stored identity of the selected network. Fail-closed on mismatch. Stronger: persist l1ChainId and rollupVersion separately and compare each.

Technical trace

Trace: enrollment stores only the composite chain id via _getChainId(rpcUrl) at network/service.ts:726-733 → later runtime code reconstructs NetworkInfo from stored row at network/service.ts:542-547 and creates a node from network.rpcUrl at aztec-runtime/pxe/chain-runtime.ts:104-105 → NuloAccount.buildTxExecutionRequest() then trusts fresh node.getNodeInfo() at nulo-account.ts:99-103 without checking it still matches the selected network.

Cross-cutting observations

Patterns that span multiple findings — worth tracking as architectural hygiene items beyond the per-finding fixes.

1. Trust is checked at the wrong granularity

The code repeatedly validates a coarse identity once, then skips the finer re-check that actually matters later:

  • Frame vs tab — frame identity collapses to tab identity (F-001, F-002).
  • Capability type vs sub-grant — type is checked, sub-grant bits ignored (F-003, F-004).
  • Primary account vs scope lists — approved account checked, additional scope arrays not (F-005).
  • Stored session vs live transport — revoke deletes the record, leaves the channel open (F-006).
  • Selected network vs live node identity — network selected, live node not rebound (F-012).
  • Profile vs credential — profile snapshot taken, credential never bound to it (F-007).

The enforceScope primitive in wallet-bridge already demonstrates the right pattern. Extending it to the points above would close several findings with one architectural change.

2. The approval UX over-trusts metadata

Across discovery, execute, token, and trust popups, user decisions depend on dApp-controlled strings while the authoritative data is either hidden (full args, calldata, full origin), visually de-emphasized (contract address vs token name), or routed through lossy reductions (hostname vs full origin). The sanitizer sanitizeWireString exists and is correctly used in the capability UI — extending its use to every approval surface AND surfacing the authoritative data primarily would close most of F-008 + F-009 together.

3. Tests pin existing boundaries but not the missing ones

Throughout Phase 2, missing tests came up over and over: no port.sender validation test, no origin-spoofing test, no scope-array tampering test against enforceScope, no canGet:false enforcement test, no passkey-unlock binding test. The coordinator dropped most of these as "missing test" notes rather than findings, but the cluster of missing tests means future refactors won't catch regressions of the very issues this audit found. Recommendation: every remediation PR lands a regression test pin.

4. Crypto package itself is healthy

Phase 2 surfaced several "potential" crypto findings (unsalted passhash, non-constant-time compare, IV-derived salt). The coordinator's negative-space review showed each had no concrete exploit path beyond defense-in-depth violations. PBKDF2-SHA256 at 600,000 iterations + AES-256-GCM + HKDF-SHA256 with proper labels is correctly applied. The team should resist scope-creep into "fix the crypto" — the crypto is fine; the trust boundaries around it aren't.

5. Aztec ecosystem dependency surface is a meaningful coupling

F-001 + F-002 partially depend on upstream @aztec/wallet-sdk 4.2.0 design choices (sender.tab.url attribution, tab-scoped discovery). Nulo can ship defense-in-depth locally, but the full fix requires either upstream changes or a wholesale shadowing of upstream's connection-handler logic. Worth surfacing to upstream and tracking as a coordination item.

Suggested remediation order

Phase 1 — quick wins (1-2 days): F-007, F-003, F-004. All three are hours-of-work fixes; closing them lifts a meaningful chunk of the High band immediately.

Phase 2 — coupled pairs (1 week each): ship F-001 + F-002 together (iframe + tab-scoping); ship F-011 + F-012 together (RPC URL allowlist + live-node chain rebind). Each pair is a single architectural change.

Phase 3 — independent Highs/Mediums (2-3 weeks): F-005 (scope arrays), F-006 (revocation kill-channel), F-008 (calldata in approval UI), F-009 (sanitize display strings), F-010 (bounded incoming storage).

Every remediation PR should land a regression test pin (see Cross-cutting observation #3). Several of these tests already have templates in the codebase — F-007 has service.integration.test.ts:321-330 as the obvious model.
