Nulo Aztec wallet (extension + dependency packages) · 2026-07-06 · effort: max · run 2026-07-06-max

14 findings 1 Critical 2 High 4 Medium 7 Low 2 models × 12 clusters, cross-verified

Executive summary

Nulo is a non-custodial wallet that lives in your browser, holds your Aztec private keys, and signs transactions when websites (dApps) ask it to. This audit put on an attacker's hat: what could a malicious or hacked website do to a user who has connected their wallet to it? Two Claude Fable models and two Codex models reviewed twelve slices of the codebase independently, then argued with each other and re-checked the survivors against the actual source. Fourteen issues held up: 1 Critical, 2 High, 4 Medium, 7 Low.

Almost everything serious traces back to one design gap: when a website sends the wallet a request, the wallet checks the message is well-formed but not that it means what it claims. The wallet trusts labels the website supplies. Two attacks fall out of this. In the worst one (F-01), a website that holds a permission users grant routinely — and which the approval screen never actually shows them — can make the wallet silently sign a blank cheque, with no popup, that lets the attacker move the user's funds. In the second (F-02), a website can get approval for a harmless-looking action (“Transfer”) while a different action (“Approve”) is what actually runs and gets signed — and the confirmation popup shows the harmless name, so even a careful user is fooled. A third High (F-03) lets a malicious network endpoint trick the wallet into signing for the wrong blockchain.

The good news: the fixes cluster tightly. One focused change to how the wallet handles website requests (reject blank-cheque hashes, authorize the real function being called, and validate request data on the wallet's own side) closes the Critical, one High, and the systemic Medium underneath them — and makes the approval popup trustworthy again. After that, a handful of cheap hardening fixes (a one-line content-security-policy addition, safer storage parsing, clipboard clearing, sender checks) stop several “Low” issues from quietly turning into “High” ones after a future change. Nothing here is being exploited in the shipped build today, but F-01 and F-02 are reachable by any site a user connects to and should block release.

Cheapest fixes first — land these in the first PR (hours, not days):
  • F-01 guard: reject opaque raw-hash createAuthWit requests from dApps (or force a per-request confirmation). Small change, kills the Critical.
  • F-05: add img-src 'self' data: blob: to the manifest CSP — a one-liner that closes a latent tracking-beacon vector.
  • F-13: wrap ValueStorage's JSON.parse in the same drop-and-skip containment EntityStorage already uses.
  • F-14: clear the clipboard (and warn) after a seed/private-key copy.
Ship together — fixing one without the others leaves the gap open:
  • F-01 + F-02 + F-08 share one root cause (the wallet trusts website-supplied request data without server-side validation or selector binding). Fix them as a single dispatcher-hardening change.
  • F-02 + F-07 both let the confirmation popup misrepresent what's being signed — authorize the real function and sanitize/label it truthfully, or the popup is still lying.

Findings

Critical F-01 A website can make the wallet silently sign a blank cheque
Found by Claude+Codex confidence: high CWE-863 fix: hours · CHEAPEST

What it is. In Aztec, an “auth-witness” is the wallet's signature saying “I authorize this specific action.” The wallet is supposed to only sign one when it can see exactly what the action is. But if a website sends a bare, pre-computed hash (an opaque number) instead of a described action, the wallet's safety check finds “no information to check” and waves it through — then signs it, with no popup. The one permission this needs, “can create auth-witnesses,” is bundled into the ordinary “pick an account” approval and is never shown on the approval screen, so users grant it without knowing.

What an attacker would do. A malicious dApp the user has connected to computes the hash for “transfer all of the user's tokens to me,” sends it as a createAuthWit request, and receives a valid signature back — silently, no confirmation. It then uses that signature to move the user's funds.

The fix. Refuse bare hashes from websites — require the request to describe the actual call (contract + function) so the wallet can check it against what the user allowed, or pop a confirmation for opaque ones. Also show “can create auth-witnesses” on the approval screen so users see what they're granting.

High F-02 Approve “Transfer”, actually run “Approve” — and the popup shows the wrong name
Found by Claude+Codex confidence: high CWE-863 fix: ~1 day

What it is. Every contract function has a human name (“transfer”) and a machine id called a selector. When a website asks the wallet to run a function, it sends both — but the wallet checks permission against the name and then executes the selector, and nothing forces the two to match. The confirmation popup also displays the name, not the selector.

What an attacker would do. A dApp with permission for the harmless transfer sends a request labelled name: "transfer" but carrying selector for approve (which hands the attacker spending rights). The permission check passes on the name, the popup reassuringly says “Transfer,” and the wallet signs and runs approve. Both the automatic guard and the human double-check are defeated at once.

The fix. Authorize the thing that actually runs — resolve the selector against the contract's real ABI, reject the request if the supplied name disagrees, and show the ABI-verified name (never the website's raw label) in the popup.

The parseTransferIntent “verified transfer” block also keys on name, so even that badge is spoofable. Confirmed by both families at Phase 4.

Fix: resolve + authorize the selector against the artifact before authorization; reject name/selector mismatch; display only ABI-verified names.

High F-03 Chain identity is checked once, then re-fetched and trusted for signing
Found by Claude+Codex confidence: high CWE-367 (TOCTOU) fix: hours

What it is. Before signing, the wallet asks the network “which chain are you?” and validates the answer. But the signing code then asks a second time and signs using that second answer, which is never re-validated. A “check it, then use a different value” gap (a time-of-check/time-of-use bug).

What an attacker would do. If the user's configured network endpoint is attacker-controlled or intercepted, it answers correctly the first time (passing the guard) and differently the second time, so the wallet signs a transaction bound to a chain the user never intended — enabling cross-chain replay/confusion of the signed action.

The fix. Pass the already-validated chain info into the signing routine and delete the second fetch — or re-run the same validation on the second answer before using it.

Medium F-04 A page can flood the wallet with discovery requests
Found by Claude+Codex confidence: high CWE-770 fix: hours

What it is. The wallet has no rate limit on the “is a wallet here?” discovery messages a page can send.

What an attacker would do. A page loops discovery with unique ids/chain ids: while the wallet is locked it grows an unbounded in-memory queue; while unlocked it can spawn a stream of connect popups — a denial-of-service / nuisance.

The fix. Cap pending discoveries globally and per origin/tab, reject unknown chain ids before opening a popup, and coalesce locked-state discoveries by (origin, chainId).

Technical trace

Instances: apps/extension/src/content-script/content.ts:12, apps/extension/src/wallet/services/wallet-sdk/background.ts:475,503,552, packages/wallet-bridge/src/discovery-queue.ts:20, window-manager/window-manager.ts:83.

Fix: global + per-origin caps, chain allowlist before popup, coalesce locked discoveries.

Medium F-06 A crafted backup file can turn off a security control and persist the password bearer
Found by Codex confidence: high CWE-862 fix: hours

What it is. “Strict security mode” keeps a password-derived bearer out of browser storage. When restoring a backup, the wallet applies the backup's settings before activating the profile — including turning strict mode off — and the backup's checksum only detects corruption, not tampering.

What an attacker would do. Trick a user into importing an attacker-crafted plaintext backup with strictSecurityMode=false; on restore, the wallet writes the password bearer (a base64 passhash) into session storage, weakening the account.

The fix. Validate backup settings against a schema, and never silently restore a security downgrade — default to strict unless the user explicitly confirms.

Technical trace

Instances: apps/extension/src/composables/useFullBackupImport.ts:226,393-412, apps/extension/src/wallet/services/config/service.ts:45, session-manager.ts:211-214, profile/service.ts:1082.

Trace: config (incl. strictSecurityMode) restored before finalizeRestore (useFullBackupImport.ts:393-403) → passhash derived (profile/service.ts:1082) → SessionManager.open() persists it because strict is off (session-manager.ts:211). Checksum is recomputable-from-content integrity, not authenticity. Confirmed by the Fable verifier.

Medium F-07 The signing popup doesn't sanitize website-supplied text
Found by Claude confidence: high CWE-451 fix: hours

What it is. The transaction-confirmation card shows dApp-supplied method names and arguments through a helper that only title-cases and truncates — it skips the sanitizeWireString cleanup used everywhere else for dApp text.

What an attacker would do. Use right-to-left override or zero-width characters, homoglyphs, or an enormous string so the popup looks like it describes a benign call while the real action differs — visual spoofing of the signing decision (it compounds F-02).

The fix. Route all dApp-authored labels/args through sanitizeWireString (or a stricter method-label sanitizer) and clamp lengths in the fixed UI rows.

Technical trace

Instances: apps/extension/src/popup/windows/execute/OperationCard.vue:118,133,138,183,401,416,433, apps/extension/src/utils/tx-enrichment.ts:52.

Fix: sanitize + length-clamp all dApp labels/args at the confirmation surface; prefer artifact-verified names. Ship with F-02.

Medium F-08 The wallet never re-validates website request data on its own side (root enabler)
Found by Claude confidence: high CWE-20 fix: 1–2 days · HIGH LEVERAGE

What it is. The request-validation schema (Zod) runs in the website's copy of the SDK — not a control the wallet can trust. Inside the service worker, the dispatcher takes request arguments as unknown[] and runs permission/scope checks over raw type-casts, never validating the data itself.

What an attacker would do. Send raw protocol frames (bypassing the website-side schema) with malformed or inconsistent arguments. This is the substrate F-01 and F-02 stand on, and any future RPC method inherits the same exposure.

The fix. Add a wallet-side, per-method schema table and parse arguments before permission/scope checks and casts; reject unknown fields where meaning matters.

Technical trace

Instances: apps/extension/src/wallet/services/wallet-sdk/content-script-validator.ts:50, background.ts:637, packages/wallet-bridge/src/dispatcher.ts:275,328,544,1134,1162.

Fix: server-side per-method arg schema, parsed before authorization. Closes the class behind F-01/F-02, not just the instances.

Low (latent) F-05 dApp logo would load as an unrestricted image — no writer today, no img-src CSP
Found by Claude+Codex confidence: high CWE-1021 fix: minutes · CHEAPEST

What it is. Several approval/settings screens are wired to render a dApp's logo as an <img src>, and the extension's content-security-policy sets no img-src — so a remote image URL would be fetched. Verification found no code that actually populates the logo field in the shipped build, so the vector is dormant.

What an attacker would do. If a future change ever plumbs a dApp-supplied logo, a hostile site could set logo=https://attacker/beacon.gif?id=… and have the approval screen phone home (IP + timing) before the user clicks Approve. Today it can't fire.

The fix. Add img-src 'self' data: blob: to the CSP now (a one-liner), and if remote logos are ever wanted, re-encode them through a wallet-controlled blob: sanitizer.

Low (DiD) F-09 The offscreen crypto document doesn't check who sent it commands
Found by Claude confidence: high code / low reach CWE-306 fix: hours

What it is. The hidden document that runs the Aztec crypto engine accepts a message purely because it's addressed to: "pxe" — it never checks the sender is the extension's own service worker. Privileged operations (register account, prove, wipe) sit behind that.

What an attacker would do. Nothing today: a web page has no way to deliver such a message (the extension isn't externally connectable, and the page relay uses a fixed envelope that can't set to). This is defense-in-depth — the risk is a future change silently making it reachable.

The fix. Add a sender.id === chrome.runtime.id check and reject tab/content-script senders, mirroring the subframe defense the SW already uses; add a nonce to the lifecycle handshake.

Technical trace

Instances: packages/extension-messaging/src/offscreen/service.ts:36-48, apps/extension/src/offscreen/index.ts:14, wallet/utils/offscreen.ts:47,80.

Why Low: the offscreen leg rated this High via the content-script relay; three independent reads refuted web reachability (no externally_connectable; fixed SDK envelope). Real missing guard, not currently reachable.

Low F-10 On Firefox, a stale crypto window can double-handle secret operations
Found by Claude+Codex confidence: high CWE-664 fix: hours–day

What it is. Firefox lacks Chrome's offscreen API, so Nulo uses a hidden window tracked only in memory. If the service worker restarts, it forgets the old window and makes a new one, and both receive the same broadcast crypto commands.

What a user would trigger. On Firefox, after an SW restart a secret-bearing command (e.g. register account) can be executed by two crypto engines at once — an integrity/duplication hazard.

The fix. Give each offscreen instance a durable token, include it in every request, and have stale windows self-close or ignore mismatched tokens.

Technical trace

Instances: apps/extension/src/wallet/utils/offscreen.ts:45,183,201,215, packages/extension-messaging/src/offscreen/client.ts:104, offscreen/service.ts:36. The code comments already acknowledge the SW-restart leak.

Low F-11 The password bearer is weakly derived; some secret buffers aren't wiped
Found by Claude+Codex confidence: high CWE-759/916 fix: days

What it is. The token used to silently re-unlock is an unsalted single SHA-256(password) — offline-crackable for human passwords and password-equivalent — and the passkey-derived master secret is copied into a buffer that isn't zeroed afterward. (The core AES-GCM/PBKDF2 encryption itself is sound: random IVs, 600k iterations, integrity enforced.)

What an attacker would do. Only after local compromise (malware/heap read) — recover the bearer or crack a weak password offline. No remote/website path.

The fix. Make the silent-restore bearer a random wrapping token or salted-KDF output; zeroize the temporary passhash and master-secret buffers. Keep key-vectors.test.ts byte-identical.

Technical trace

Instances: packages/wallet-crypto/src/encryption-key.ts:77,97, password-secret-box.ts:80,122, passkey-credential.ts:60, zeroize.ts:17.

Note: Fable recalibrated the Phase-2 “universally reversible” claim — the practical risk is offline cracking of weak passwords plus bearer reuse, not universal reversal.

Low F-12 Stored dApp-permission rows aren't integrity-protected
Found by Codex confidence: high CWE-345 fix: hours–day

What it is. The wallet trusts dApp-session/permission rows in storage as-is — no signature, MAC, or schema check on load.

What an attacker would do. Requires an already-compromised machine (ability to write extension storage): plant a session row granting a hostile origin high trust, so later requests auto-approve. No web write path exists, hence Low.

The fix. Validate session rows on load (schema + range clamps) and MAC them with a profile-local key so tampering is detected.

Low F-13 One corrupt storage row can brick wallet startup
Found by Claude+Codex confidence: high CWE-248 fix: hours · CHEAPEST

What it is. ValueStorage.get() calls JSON.parse with no error handling, unlike EntityStorage, which already tolerates bad rows.

What a user would trigger. A single malformed nulo:config or session row (local corruption) throws on every read, repeatedly failing startup/restore.

The fix. Mirror EntityStorage's existing parseOrDelete: catch, log bounded metadata, quarantine/delete the bad row, return a default.

Low F-14 Exporting the seed/private key leaves it on the clipboard
Found by Claude confidence: high CWE-522 fix: hours · CHEAPEST

What it is. The seed-phrase and private-key export screens copy the full secret to the OS clipboard and never clear it; the key page doesn't even show the seed page's warning.

What a user would trigger. After copying to paste elsewhere, the secret lingers on a shared/synced clipboard where a clipboard manager, another app, or a later permitted page can read it.

The fix. Warn on both copy actions, and attempt a delayed clipboard clear when it still holds the copied secret.

Cross-cutting observations

The website→wallet boundary checks shape, not meaning

Validation confirms a request is well-formed; nothing binds the website-supplied name / selector / raw-hash to an authorized, artifact-verified action before the wallet signs. F-08 is the substrate; F-01 and F-02 are its sharpest exploits. The single highest-value structural change is wallet-side, per-method argument validation plus selector-based authorization at the dispatcher — it closes a class of bugs, not three instances.

The approval popup — the human's last line of defense — can be made to lie

F-02 (shows one name, runs another), F-07 (unsanitized bidi/homoglyph text), and the UI-invisible canCreateAuthWit grant behind F-01 all erode “what you see equals what you sign.” Treat them as one theme: a scope fix that still renders attacker-controlled text is only half a fix.

Several Lows are safe only by accident of the current manifest

F-09 (offscreen sender check), F-12 (unsigned session rows), and the messaging Port sender gap are non-issues today purely because there's no externally_connectable and the content-script relay uses a fixed envelope. A future permission or relay refactor would turn them into Highs with no change at the vulnerable line. Add the sender checks and row integrity now, so safety is enforced rather than incidental.

Local-attacker secret hygiene is soft (but not web-exploitable)

F-06, F-11, and F-14 don't help a remote dApp, but they weaken the wallet against local malware, a synced clipboard, or heap inspection. Reasonable to batch as a “local hardening” PR after the dApp-boundary fixes land.
