CLUSTER: aztec-runtime-signing

Scope audited: every non-test source file under `packages/aztec-runtime/src/` (account/, pxe/, adapters/, ports/, utils/, offscreen/). Deep focus on `account/nulo-account.ts` signing/chunking, with one handoff hop into the real caller `apps/extension/src/wallet/services/execution/tx-request-builder.ts` and the upstream `@aztec/entrypoints@5.0.0-rc.2` `DefaultAccountEntrypoint` to prove the binding argument.

## Findings

### [1] Chain-identity guard bypassed by a TOCTOU: `buildTxExecutionRequest` re-fetches `node.getNodeInfo()` and signs the authwit over the second (unvalidated) response

- **Title:** Signing boundary trusts a second, unguarded `node.getNodeInfo()` — a malicious/drifted RPC can bind the Schnorr authwit to a chain the user did not select.
- **Impact factors:** Integrity (primary) + Confidentiality of the resulting private tx. CIA property violated: the user's approved transaction is signed with `chainId`/`version` chosen by the RPC, not by the selected network. Blast radius: single user (the one whose profile points at the attacker-controlled/drifted RPC). Data sensitivity: high (moves value / reveals private notes on the drifted chain). Exploitability: attack vector network (RPC response), attack complexity low, privileges required none beyond controlling the RPC responses (the exact F-012 threat the codebase already recognizes), user interaction required (the user initiates+approves a normal transfer/tx). The account has the **same address on every Aztec chain** (see Finding 3), so the drifted chain is guaranteed to have a landing spot — the wallet will even deploy-and-execute via the first-tx init path (`buildWithInitialization`).
- **Evidence confidence:** high.
- **OWASP / CWE:** OWASP A01 Broken Access Control / A08 Software & Data Integrity Failures; CWE-367 (Time-of-check to Time-of-use), CWE-345 (Insufficient Verification of Data Authenticity), CWE-807 (Reliance on Untrusted Inputs in a Security Decision).
- **Trace (source → sink):**
  1. `tx-request-builder.ts:116` `const node = await this.networkService.getNode(network.chainId)` — the live JSON-RPC node proxy (`packages/aztec-runtime/src/adapters/aztec-node-factory-adapter.ts:55`, `createAztecNodeClient`; each `getNodeInfo()` is a fresh POST, not cached).
  2. `tx-request-builder.ts:119` `const nodeInfo = await node.getNodeInfo()` → `:124` `assertLiveChainIdentity(network, nodeInfo)` — the F-012 drift guard validates **this** response.
  3. `tx-request-builder.ts:343` `await account.buildTxExecutionRequest(node, pxe, payload, …)` — the **same** `node` object is handed to the runtime.
  4. `packages/aztec-runtime/src/account/nulo-account.ts:103` `const { l1ChainId, rollupVersion } = await node.getNodeInfo()` — a **second, independent** RPC round-trip; NOT passed through `assertLiveChainIdentity`.
  5. `nulo-account.ts:104-107` `chainInfo = { chainId: new Fr(l1ChainId), version: new Fr(rollupVersion) }` — built from the unvalidated second response.
  6. Sink: `nulo-account.ts:140` `this.entrypoint.createTxExecutionRequest(current, gasSettings, chainInfo, options)` (and `:137/:184` `buildWithInitialization` → `wrapExecutionPayload(payload, chainInfo, …)`). Upstream `DefaultAccountEntrypoint.#buildEntrypointCallData` computes `messageHash = computeOuterAuthWitHash(address, chainInfo.chainId, chainInfo.version, payloadHash)` and signs it — so the attacker's `chainId`/`version` are bound into the Schnorr signature and the `TxContext`.
- **Missing control:** `buildTxExecutionRequest` never validates the `getNodeInfo()` it consumes against the user-selected `network`. `chain-identity.ts:20-24` documents this exact gap: "NOT applied at: `nulo-account.ts:buildTxExecutionRequest` — no `networkInfo` parameter in scope. Would require an interface change (deferred follow-up)." The caller's guard at `tx-request-builder.ts:124` does not cover the runtime's internal re-fetch, and the two calls are separate network round-trips (classic TOCTOU).
- **Exploit story:** (a) User's active profile uses an Aztec RPC the attacker controls (user-added custom RPC, compromised endpoint, or malicious operator — F-012's stated model). (b) User clicks "send 10 TOKEN to Bob" on selected network A and approves. (c) `getNodeInfo()` call #1 returns A's `(l1ChainId_A, rollupVersion_A)` → `assertLiveChainIdentity` passes. (d) `getNodeInfo()` call #2 (inside `buildTxExecutionRequest`) returns B's `(l1ChainId_B, rollupVersion_B)`. (e) The entrypoint signs an authwit valid on chain B; `TxContext` targets B. (f) prove+send flow routes via the same malicious node to chain B, where the user's account exists at the identical address (Finding 3) — the tx executes on the wrong chain (fund movement / private-note disclosure the user never intended for B).
- **Preconditions:** attacker controls the RPC responses for the selected profile's node; user initiates+approves one ordinary tx. No forged signatures needed — the wallet willingly signs for the attacker-named chain.
- **Why mitigations fail:** `assertLiveChainIdentity` (the designed defense) runs only on the caller's first fetch; the signing path re-reads the node and is explicitly excluded from the guard. `isAllowedRpcUrl` (`aztec-node-factory-adapter.ts:32`) only allowlists the URL *scheme/host*, not the *contents* of RPC replies, so a fully-allowlisted `https:` endpoint still supplies attacker-chosen chain identity. Zod parsing on downstream PXE calls validates shape, not chain authenticity.
- **Instances:**
  - `packages/aztec-runtime/src/account/nulo-account.ts:103-107` (unguarded fetch → `chainInfo`), consumed at `:137`, `:140`, `:184`.
  - Real-send reachability: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:119/124/343` (guarded fetch #1, then unguarded runtime fetch #2 — the TOCTOU pair).
  - Simulation-only (lower impact, but same unguarded internal fetch): `apps/extension/src/wallet/utils/fn.ts:94` and `apps/extension/src/wallet/services/execution/helpers/batched-view-simulation.ts:439` call `buildTxExecutionRequest` for `simulateTx`; a manipulated chain here corrupts a displayed simulation/balance result rather than emitting a real tx.

### [2] `assertLiveChainIdentity` folds chain identity through a non-injective XOR — a malicious node can satisfy the guard while pointing at a different `(l1ChainId, rollupVersion)`

- **Title:** Chain-drift check compares a lossy `l1ChainId ^ rollupVersion` composite, so distinct chain identities collide and pass the guard.
- **Impact factors:** Integrity of the drift control itself. CIA: weakens the authenticity check that is supposed to pin the signing chain. Blast radius: single user. Exploitability: attack vector network, attack complexity high (requires a real target chain whose `(l1ChainId, rollupVersion)` XORs to the stored composite), privileges none, user interaction required. This is the ONLY chain gate on TOCTOU-free consumers such as `dapp-send-executor`/`buildNoFrom` (which use one guarded `nodeInfo` for both the check and the `TxContext`), so on those paths the XOR fold is the sole barrier to a cross-chain sign.
- **Evidence confidence:** moderate (mechanism is certain; a concrete two-real-chain collision is not demonstrated — the attacker controls the reported values but cannot change a real target chain's true params).
- **OWASP / CWE:** OWASP A02 Cryptographic Failures / A08 Data Integrity Failures; CWE-697 (Incorrect Comparison), CWE-345 (Insufficient Verification of Data Authenticity).
- **Trace:** `packages/aztec-runtime/src/utils/chain-identity.ts:52` `const liveComposite = (nodeInfo.l1ChainId ^ nodeInfo.rollupVersion) >>> 0` → `:53` `if (network.chainId !== liveComposite)`. The stored `network.chainId` is itself `(l1ChainId XOR rollupVersion) >>> 0` (per the file's own doc, `:41-45`). XOR is not injective: any `(a', b')` with `a' ^ b' == stored` passes. `^` also coerces both operands to signed 32-bit, silently truncating any `l1ChainId`/`rollupVersion` above 2^32 (e.g. Sepolia's `11155111` fits, but large/derived rollup versions can alias).
- **Missing control:** the check should compare the pair `(l1ChainId, rollupVersion)` field-by-field against the stored identity, not a folded scalar. No structural/tuple equality is used.
- **Exploit story / violation scenario:** On a single-fetch consumer, a malicious node reports `(l1ChainId', rollupVersion')` chosen so the XOR equals the victim's stored composite but the pair identifies a different real Aztec deployment the victim can transact on; the guard passes and the authwit is signed for that chain. Also serves as a second, TOCTOU-independent route for Finding 1.
- **Preconditions:** attacker controls RPC replies; existence of a reachable chain whose true `(l1ChainId, rollupVersion)` collides under XOR with the selected network's composite (or a >32-bit truncation alias).
- **Why mitigations fail:** the composite is the identity representation everywhere (stored + live), so there is no un-folded value left to compare; the fold is applied on both sides, guaranteeing collisions map to "match."
- **Instances:** `packages/aztec-runtime/src/utils/chain-identity.ts:52-53` (and the stored-side derivation this mirrors, documented `:41-45`).

### [3] Account salt hard-pinned to `Fr.ZERO` — deterministic same-address-on-every-chain (grinding/collision infeasible; residual is cross-chain replay landing + linkability)

- **Title:** `getContractInstanceFromInstantiationParams({ …, salt: Fr.ZERO })` makes the account address a pure function of the seed, identical across all chains.
- **Impact factors:** Confidentiality (cross-chain linkability) + Integrity amplifier for Finding 1. Blast radius: single user (self). Exploitability: not directly attacker-triggerable; it is a standing property that guarantees Finding 1's drifted chain always has the victim's account at the same address (and the first-tx `buildWithInitialization` path will deploy it there if absent).
- **Evidence confidence:** high (behavior); the exploit value is only as an amplifier.
- **OWASP / CWE:** OWASP A02; CWE-330 (Use of Insufficiently Random Values) — in the sense of an intentionally fixed salt removing per-deployment/per-chain domain separation.
- **Trace:** `packages/aztec-runtime/src/account/nulo-account.ts:66` `salt: Fr.ZERO` inside `NuloAccount.new`; the address (`:48`, `instance.address`) is therefore `f(deriveKeys(secret), Fr.ZERO)` — no chain or user entropy.
- **Missing control:** no chain-scoped or user-chosen salt; the same authwit-signing account address is reused on every network. Explicitly assessed: **address grinding / collision is NOT exploitable** — an attacker would need a Poseidon preimage over the full derivation to hit a target address (infeasible); two honest seeds colliding is ~254-bit-negligible. The genuine residual is (a) the cross-chain replay landing spot that makes Finding 1 concrete, and (b) activity linkability of one identity across chains.
- **Exploit story:** see Finding 1 step (f) — deterministic address is what guarantees the drifted-chain tx has an account to execute against.
- **Preconditions:** none standalone; pairs with Finding 1.
- **Instances:** `packages/aztec-runtime/src/account/nulo-account.ts:66`.

## Notes — checked and clean (with the key question answered)

- **KEY QUESTION — does the authwit bind EXACTLY the approved calls, and can a hidden/extra call ride along or a chunk boundary drop a binding? Answer: NO, the binding is sound.** Verified against upstream `@aztec/entrypoints@5.0.0-rc.2/dest/account_entrypoint.js`:
  - `createTxExecutionRequest`/`wrapExecutionPayload` sign `messageHash = computeOuterAuthWitHash(address, chainId, version, encodedCalls.hash())`; the signed `payloadHash` covers all `APP_MAX_CALLS(=5)` `function_calls` (each by `args_hash`, `selector`, `target`, `is_public`, `hide_msg_sender`, `is_static`) + `tx_nonce`, padded with `FunctionCall.empty()`.
  - Recursive `chunkHead` (`nulo-account.ts:157-172`): `head = calls.slice(0, 5)` and `tail = calls.slice(5)` are complementary and non-overlapping; the head is wrapped into one entrypoint call whose inner authwit signs the head, and the wrapper's `args_hash` (bound by the next level's signature) transitively commits the inner calls. Every original call ends up under some signature; the only added calls are the user's own account-entrypoint wrappers. Traced a 12-call payload end-to-end: all 12 bound, none dropped, none injected.
  - authWitnesses/capsules/extraHashedArgs are preserved across every wrap: upstream `wrapExecutionPayload` returns `[payloadAuthWitness, ...authWitnesses]`, `capsules`, `[...encodedCalls.hashedArguments, ...extraHashedArgs]`; `chunkHead` and `buildWithInitialization` re-concatenate them, so head-call args and pre-existing authwits remain resolvable on the final tx (no lost binding on the first-tx + chunked path).
- **Upstream design, not dApp-reachable (noted, not findings):** the entrypoint `fee_payment_method` and `cancellable` args are NOT inside the signed `payloadHash`; and `buildWithInitialization` wraps `[ctorCall, wrappedApp]` via `DefaultMultiCallEntrypoint`, which does not itself sign the combination. Both would require tampering *after* construction inside the trusted SW/offscreen boundary (not the dApp boundary), and an injected multicall sibling runs without the account authwit so it cannot spend the account's private notes. Out of the dApp threat model.
- **PXE service input validation is disciplined:** `pxe/service.ts` routes every RPC arg through Zod (`AztecAddress.schema`, `Fr.schema`, `TxExecutionRequest.schema`, `ContractArtifactSchema`, `AccessScopesSchema`, `NotesFilterSchema`, …) before hitting the PXE; `registerAccount` (which transports the master secret SW→offscreen) is extension-internal messaging only, not reachable from the wallet-bridge/dApp path. `ArtifactRegistry.resolve` recomputes+verifies the class-id for `pxe-local` artifacts (`artifact-class-id.ts`) and the `known` branch is keyed by load-time-computed class-id (map lookup == equality) — sound.
- **`getContractInstance` node-fallback** (`pxe/service.ts:201`) returns `node.getContract(address)` without asserting `instance.address === address`. In-cluster the only consumer (`nulo-account.ts:81 ensureContractRegistered`) uses it for an existence check only and registers the locally-computed `this.instance`, so no in-cluster sink trusts the node-returned instance's contents. Trust of that instance by token/contract services exits this cluster — flagged for the `ext-sw-services-storage` cluster rather than asserted here.
- **`isAllowedRpcUrl`** (`aztec-node-factory-adapter.ts:32-47`) correctly restricts to `https:` any-host and `http:` loopback-only; this bounds SSRF/scheme abuse but, as noted in Finding 1, does not authenticate RPC *content*.
