CLUSTER: aztec-runtime-signing

## Findings

### [1] Raw `createAuthWit` hashes are silently signed without payload scope binding

1. **Title** — Raw `createAuthWit` hashes are silently signed without payload scope binding.

2. **Impact factors** — Violates integrity and authorization for a single wallet user by producing a valid Schnorr `AuthWitness` for an attacker-chosen authwit hash. The signed hash can authorize future Aztec calls that are outside the dApp's granted transaction/simulation scope, including sensitive token or contract actions if the attacker precomputes the corresponding authwit message hash. Attack vector: network via malicious dApp page. Attack complexity: low once the dApp can compute/obtain the target authwit hash. Privileges required: low, an `accounts` grant with `canCreateAuthWit`. User interaction: required for the initial capability grant, not for each raw-hash signing call.

3. **Evidence confidence** — High.

4. **OWASP / CWE mapping** — OWASP A01: Broken Access Control; CWE-863: Incorrect Authorization.

5. **Trace** — A malicious dApp calls wallet RPC `createAuthWit(from, rawHash)`. The dispatcher enforces the method as an accounts capability and routes it as `aztec_createAuthWit` (`packages/wallet-bridge/src/method-descriptors.ts:107`, `packages/wallet-bridge/src/method-descriptors.ts:109`, `packages/wallet-bridge/src/method-descriptors.ts:110`). The scope checker only requires an accounts grant with `canCreateAuthWit` (`packages/wallet-bridge/src/method-scope-checkers.ts:258`, `packages/wallet-bridge/src/method-scope-checkers.ts:265`, `packages/wallet-bridge/src/method-scope-checkers.ts:266`) and explicitly performs no semantic validation for raw Fr hashes (`packages/wallet-bridge/src/method-scope-checkers.ts:306`). The dispatcher then casts untrusted `args[1]` into the operation payload (`packages/wallet-bridge/src/dispatcher.ts:1156`, `packages/wallet-bridge/src/dispatcher.ts:1162`) and forwards it to execution (`packages/wallet-bridge/src/dispatcher.ts:370`, `packages/wallet-bridge/src/dispatcher.ts:373`). Execution dispatches `aztec_createAuthWit` to `executeAztecCreateAuthWit` (`apps/extension/src/wallet/services/execution/service.ts:448`, `apps/extension/src/wallet/services/execution/service.ts:449`), parses the non-object payload as an Fr message hash (`apps/extension/src/wallet/services/execution/service.ts:680`, `apps/extension/src/wallet/services/execution/service.ts:682`), and signs it (`apps/extension/src/wallet/services/execution/service.ts:685`). The scoped account sink delegates directly to the Schnorr auth witness provider with no caller/call/consumer binding check (`packages/aztec-runtime/src/account/nulo-account.ts:92`, `packages/aztec-runtime/src/account/nulo-account.ts:93`).

6. **Missing control** — The wallet does not require dApp-originated authwit requests to be structured as `CallIntent` or `IntentInnerHash`, and it does not recompute the hash from scope-checkable fields before signing. Raw hashes should either be rejected for dApp RPC, require explicit per-request approval with unscopable-risk handling, or be bound to a previously approved call/consumer/scope record before `account.createAuthWit`.

7. **Exploit story / violation scenario** — A dApp first obtains an accounts capability with `canCreateAuthWit: true`, optionally alongside a narrow transaction scope such as one harmless method. It then computes the Aztec authwit message hash for a different target, for example an unauthorized token `transfer` or a protocol contract authorization outside the granted scope. Instead of sending a `CallIntent`, it calls `createAuthWit(authorizedAccount, "0x...precomputedHash...")`. Because the raw hash is neither a `CallIntent` nor an `IntentInnerHash`, the transaction/simulation scope checks never inspect the target contract or function. The wallet signs the hash and returns an `AuthWitness`, which the dApp can later attach to a transaction that consumes that authorization.

8. **Preconditions** — The user has an active dApp session for the origin and granted an accounts capability where `canCreateAuthWit` is true for the account. The attacker can compute or obtain the target authwit message hash for the selected chain metadata. The signing account is available/unlocked when the RPC is processed.

9. **Why mitigations fail** — Capability enforcement only checks that the method is allowed under the accounts capability, not what payload the authwit authorizes (`packages/wallet-bridge/src/method-descriptors.ts:107`). The structured-intent scope checks work only when `args[1]` is recognized as a call intent or inner-hash object (`packages/wallet-bridge/src/method-scope-checkers.ts:279`, `packages/wallet-bridge/src/method-scope-checkers.ts:291`); raw hashes deliberately fall through with no semantic validation (`packages/wallet-bridge/src/method-scope-checkers.ts:306`). Chain identity is checked before hashing/signing (`apps/extension/src/wallet/services/execution/service.ts:647`, `apps/extension/src/wallet/services/execution/service.ts:650`), but that only binds the hash to the selected chain and does not prove the hash corresponds to a permitted call.

10. **Instances** — `packages/wallet-bridge/src/method-scope-checkers.ts:306`; `packages/wallet-bridge/src/dispatcher.ts:1162`; `apps/extension/src/wallet/services/execution/service.ts:680`; `apps/extension/src/wallet/services/execution/service.ts:685`; `packages/aztec-runtime/src/account/nulo-account.ts:92`.
