CLUSTER: ext-sw-dapp-connection

Scope: `apps/extension/src/wallet/services/wallet-sdk/**` (background.ts, content-script-validator.ts, nulo-schema-patch.ts, session-baton.ts, queued-journal.ts, error-envelope.ts) + SW bootstrap `apps/extension/src/wallet/index.ts`. One handoff hop taken into `packages/wallet-bridge` (dispatcher.ts, discovery-queue.ts) and read-only confirmation reads of the upstream `@aztec/wallet-sdk@5.0.0-rc.2` handler, the manifest, and the direct sinks (`dapp-session/service.ts`, `dapp-interaction/service.ts`, `window-manager/window-manager.ts`, `capability-meta.ts`).

## Answers to the load-bearing questions (established before findings)

- **Origin source is trustworthy.** A connecting dApp's origin is derived by the upstream `BackgroundConnectionHandler.handleMessage` from `sender.tab.url` (the Chrome-provided top-frame URL), NOT from any page-supplied field: `background_connection_handler.ts:195` `new URL(sender.tab.url).origin`, threaded into `PendingDiscovery.origin` at `:257-266`. The page-supplied `requestId`, `appId`, `chainInfo` never influence origin. The manifest has **no `externally_connectable`** (`apps/extension/manifest/manifest.config.ts`), so arbitrary web pages cannot forge `chrome.runtime` messages; only the extension's own content script (injected `all_frames:true`) can, and Chrome stamps its `sender`. Nulo adds a correct subframe defense (`content-script-validator.ts:88-90` `isSubframeSender`, enforced at `background.ts:172-179`) that closes the upstream "iframe credited to top-frame origin" gap. **Not a finding.**
- **Session binding is sound.** Sessions are keyed `(origin, chainId)`; the DappSession auto-approve lookup is additionally **profile-scoped** (`dapp-session/service.ts:107` `x.profileId === profile.id`), so a session remembered under profile A cannot auto-approve under profile B. Cross-origin message injection is blocked by the per-session AES-GCM channel key derived at ECDH (`background_connection_handler.ts:352-364`): a message for another session's id fails to decrypt without that session's `sharedKey`. **Not a finding.**
- **`registerToken`/`isTokenRegistered`/`grantPublicAuthwit` schema patch** (`nulo-schema-patch.ts`) mutates the `WalletSchema` singleton with fixed Zod entries, guarded against upstream signature drift (throws at SW init). No dApp input flows into the patch; the added methods are gated downstream (capability map + popup). **Not a finding.**
- **`createAuthWit` silent signing is scope-bound.** It routes to execution without a per-call popup, but `checkCreateAuthWit` (`packages/wallet-bridge/src/method-scope-checkers.ts:255-300`) requires `canCreateAuthWit` on an accounts grant AND that the authwit's authorized call fall within the dApp's granted transaction/simulation scope. Enforcement lives in cluster `bridge-dispatcher`; verified present, **not a hole here.**

## Findings

### [1] Unbounded dApp-triggered discovery processing — SW memory growth + uncapped connect-popup flood via attacker-controlled `chainId`

1. **Title** — A single web page can force unbounded discovery work: unbounded in-memory queue/map growth while the wallet is locked, and unbounded connect-popup creation while unlocked, because `chainId` (attacker-supplied) multiplies the dedupe key and no cap/validation gates popup creation.
2. **Impact factors** — Availability (A). Blast radius: any user who visits an attacker page (all-users class). Data sensitivity: none directly; approval-fatigue can be chained into an unintended approval. Exploitability: attack vector **network** (any visited page; content script auto-injected at `document_start` on `*://*/*`), attack complexity **low**, privileges required **none**, user interaction **none** to start the flood.
3. **Evidence confidence** — high (memory growth + popup path); moderate on ultimate severity (MV3 SW ephemerality bounds the memory half; the popup half is unbounded real OS windows).
4. **OWASP / CWE** — OWASP A05 (Security Misconfiguration) / A04 (Insecure Design); CWE-770 (Allocation of Resources Without Limits), CWE-400 (Uncontrolled Resource Consumption).
5. **Trace** —
   - Source: page loops `window.postMessage(JSON.stringify({type:"aztec:discovery", requestId: crypto.randomUUID(), chainInfo:{chainId:<i>,version:...}, ...}))`. Content script forwards each (`@aztec/wallet-sdk` `content_script_connection_handler.ts:156-162`), background listener passes valid discovery envelopes through (`background.ts:187-192`; `content-script-validator.ts:92-108`).
   - Upstream stores one `PendingDiscovery` per distinct `requestId` in an unbounded `Map` (`background_connection_handler.ts:268`), then fires `onPendingDiscovery` → `handleDiscovery` (`background.ts:198-210, 461`).
   - **Locked path:** `background.ts:473-476` → `discoveryQueue.enqueue(...)` with no cap; `packages/wallet-bridge/src/discovery-queue.ts:20-24` pushes unconditionally to `this.queue` (no max) and spams `chrome.action.setBadgeText`.
   - **Unlocked path:** `chainId` is computed from dApp-supplied `chainInfo` (`background.ts:481, 740-745`) and used in the dedupe key `dedupeKey = ${origin}|${chainId}` (`background.ts:503`). Distinct `chainId` values ⇒ distinct keys ⇒ each reaches `dappInteractionService.discover(params, discovery.requestId)` (`background.ts:552`).
   - Sink: `dapp-interaction/service.ts` `interaction()` calls `windowManager.openAndAwait(...)`, which immediately `windows.create({type:"popup",...})` with **no concurrency cap** (`apps/extension/src/wallet/services/window-manager/window-manager.ts:83-84`). N distinct `chainId`s ⇒ N popups.
6. **Missing control** — No per-origin rate limit / concurrency cap on discovery processing; no upper bound on `DiscoveryQueue.queue` or on upstream `pendingDiscoveries`; no validation that the dApp-declared `chainId` corresponds to a configured network before a connect popup is opened. `pendingDiscoveryPromises` only dedupes identical `(origin, chainId)` tuples, which the attacker trivially defeats by varying `chainId`.
7. **Exploit story** — User has the wallet installed. (a) *Locked:* the user visits `attacker.com` (or an ad iframe—top-frame only, but the top page suffices); page fires 10⁵ discovery messages with unique `requestId`s. `DiscoveryQueue.queue` and upstream `pendingDiscoveries` grow until the SW is memory-killed; on unlock, drain walks the whole backlog. (b) *Unlocked:* page fires discoveries with `chainId = 1,2,3,…`; each opens a real connect popup. The discover popup renders only `{name,url}` (`DiscoveryParams`), so the user can't distinguish them; dozens of identical-looking "Connect to attacker.com?" windows bury the desktop and can be used for approval-fatigue.
8. **Preconditions** — Wallet installed; user visits an attacker-controlled top-level page. No prior connection, no unlock needed for the memory half; unlock needed for the popup half. No user interaction to begin.
9. **Why mitigations fail** — The `(origin, chainId)` dedupe (`background.ts:503, 549`) is the only throttle and is bypassed by varying the fully attacker-controlled `chainId`. `queuedCreationLock`/journal caps (`queued-journal.ts:33-39`) bound only the *journal* records for `sendTx`, not discovery. SW ephemerality reclaims the queue/map on restart but does nothing for the live popup flood.
10. **Instances** — `packages/wallet-bridge/src/discovery-queue.ts:20-24`; `apps/extension/src/wallet/services/wallet-sdk/background.ts:473-476` (unbounded enqueue), `:503` + `:549` + `:552` (chainId-keyed dedupe → uncapped `discover`), `:481` + `:740-745` (attacker-controlled chainId derivation); sink `apps/extension/src/wallet/services/window-manager/window-manager.ts:83-84`; upstream growth `background_connection_handler.ts:268`.

### [2] dApp channel verification (emoji handshake) is display-only — never gates message processing, and the "trusted" flag persists across silent hash rotation

1. **Title** — The wallet-sdk verification hash / emoji handshake is surfaced for the user to eyeball but is never enforced as a gate on any RPC or on message processing; on reconnect the stored hash is silently overwritten while `trustedVerification` persists, so the "verified" UI can diverge from the live channel.
2. **Impact factors** — Integrity/authenticity of the channel-verification signal (A04). Blast radius: per-connected-dApp. Sensitivity: the signal a security-conscious user relies on to detect a swapped/mismatched channel. Exploitability: vector local/adjacent (a user relying on the badge), complexity high, privileges low (an already-connected/known dApp), user interaction required.
3. **Evidence confidence** — high on the mechanism (verification is not consulted anywhere but display); low on independent real-world impact (compensating gates exist).
4. **OWASP / CWE** — OWASP A04 (Insecure Design); CWE-1390 / CWE-287-adjacent (insufficient verification of channel authenticity), CWE-345 (insufficient verification of data authenticity).
5. **Trace** — `background.ts:212-256` `onSessionEstablished`: the session is already live in upstream `activeSessions` (`background_connection_handler.ts:330`) before this callback runs; `onWalletMessage` (`background.ts:263-319`) → `handleWalletMessage` → `dispatcher.dispatch` process messages with **no** check of verification state. `needsVerification` (`background.ts:244`) only decides whether to `chrome.windows.create(... /windows/verify ...)` (`:247-254`); it gates nothing else. The stored hash is overwritten every (re)establishment (`background.ts:222` `setVerificationHash`) but `trustedVerification` is not reset. Consumers of `trustedVerification`/`verificationHash` are exclusively display: `apps/extension/src/popup/windows/verify/index.vue:154-155` and `apps/extension/src/popup/pages/settings/connected-apps/[id].vue:58,66`. No dispatcher path reads either (grep-confirmed across `packages/wallet-bridge/src`).
6. **Missing control** — No policy that "unverified" (or "verification mismatch") blocks or degrades a session; no re-verification prompt when a *trusted* session's hash rotates to a new value.
7. **Violation scenario** — A user who was taught to trust the emoji badge reconnects a previously-trusted dApp; a new ECDH yields a new hash that is stored silently and still shown as "Trusted" in settings without a fresh comparison, so the badge no longer proves the user ever verified *this* channel. Separately, a dApp is fully functional (capability-gated methods, `getAccounts`, `simulateTx`, `createAuthWit` within scope) before the user ever looks at the verify window.
8. **Preconditions** — A connected dApp; a user who treats the emoji/"Trusted" state as a security guarantee.
9. **Why mitigations fail** — The real authorization gates (capability grants in `dispatcher.enforceCapability`, per-`sendTx` popup in `handleSendTx`, scope checkers) are what actually protect funds — which is *why* this is low, not high — but they also mean the verification UI is a security signal with no backing enforcement, i.e. it can mislead without ever being false-negative-caught.
10. **Instances** — `apps/extension/src/wallet/services/wallet-sdk/background.ts:212-256` (esp. `:222`, `:244`); display-only consumers `apps/extension/src/popup/windows/verify/index.vue:154-155`, `apps/extension/src/popup/pages/settings/connected-apps/[id].vue:58,66`.

### [3] Catch-all error path returns internal exception messages verbatim to the dApp — leaks the internal profile UUID (cross-dApp correlation) and internal state

1. **Title** — `handleWalletMessage`'s error branch forwards any unrecognized exception's raw `.message` to the connected dApp; several internal throws embed the wallet's internal profile identifier and other internal state, giving a dApp data it should not see.
2. **Impact factors** — Confidentiality (C) — sensitive-info exposure (A01/A04). Blast radius: per-session, but the leaked profile UUID is stable across origins ⇒ enables **cross-dApp correlation** of the same wallet/profile, undermining per-origin isolation. Exploitability: vector network (any connected dApp), complexity low, privileges low (an established session), user interaction none.
3. **Evidence confidence** — moderate (leak mechanism is certain; reachability of the profileId-bearing throw specifically is narrow — needs an account-kind method past capability enforcement with zero accounts on the chain).
4. **OWASP / CWE** — OWASP A01 (Broken Access Control → over-exposure) / A04; CWE-209 (Generation of Error Message Containing Sensitive Information), CWE-200 (Exposure of Sensitive Information).
5. **Trace** — Source (internal exception): e.g. `packages/wallet-bridge/src/dispatcher.ts:1204` `throw new Error(\`No accounts found for profile ${ctx.profileId} on chainId ${ctx.chainId}\`)` (also `:1220`, `:1226`; `ctx.profileId` set at `background.ts:628`). Sink: `background.ts:639-648` catch → `response.error = toWalletResponseError(error)`; `error-envelope.ts:83` returns `error instanceof Error ? error.message : String(error)` for anything not in the recognised set. `background.ts:686` `handler.sendResponse(...)` encrypts and delivers it to the dApp, which unwraps the string (`extension_wallet.ts` `new Error(JSON.stringify(error))`). The recognised branches (`error-envelope.ts:49-82`) deliberately genericise timeout/disconnect messages ("no oracle on internal method names") — but the catch-all defeats that intent for every other throw.
6. **Missing control** — No allow-list / redaction for the catch-all: internal identifiers (profile UUID, network/account internals) are not stripped before crossing the dApp trust boundary. The genericisation applied to `RpcTimeoutError`/`RpcDisconnectedError` is not applied to generic `Error`s.
7. **Exploit story** — A connected dApp issues a request that trips an internal throw carrying `ctx.profileId` (a stable internal UUID). Two independently-malicious (or colluding) origins each harvest the same profileId from such an error and confirm they are talking to the same wallet/profile, defeating the origin-scoped session model used everywhere else in this cluster.
8. **Preconditions** — An established session (post-approval). For the profileId string specifically: a granted account-kind method reaching `resolveNetworkAndAccount` with an empty account set on the requested chain.
9. **Why mitigations fail** — The encrypted channel protects the message in transit but the dApp is the legitimate decrypting endpoint, so encryption does not prevent the leak. The per-branch genericisation in `error-envelope.ts` covers only four error classes; the terminal `return error.message` is the intended wire contract for "unrecognised", so the leak is by design, not an accident of a missing branch.
10. **Instances** — Sink: `apps/extension/src/wallet/services/wallet-sdk/error-envelope.ts:83`; `apps/extension/src/wallet/services/wallet-sdk/background.ts:648` (+ delivery `:686`). Concrete sensitive source (trace exits this cluster into `bridge-dispatcher`): `packages/wallet-bridge/src/dispatcher.ts:1204`. Other reachable throws echo the dApp's own input (`dispatcher.ts:396,606,649,1220`) — lower value but same uncontrolled path.

## Notes — checked and clean (with reasons)

- **`requestId` → `sessionId` is fully attacker-chosen** (`background_connection_handler.ts:281`), but yields no cross-principal effect: an honest dApp's `requestId` is `crypto.randomUUID()` (`extension_provider.ts:177`), unguessable and never exposed cross-origin, so an attacker cannot collide with a victim's live session; and even a forced same-id collision cannot decrypt or act as the victim (AES-GCM key + `sender`-derived origin binding). Session-fixation/eviction against a chosen victim is not feasible. Non-finding.
- **`chainInfoToChainId` parses dApp-supplied hex via `BigInt(...)`** (`background.ts:740-745`, `queued-journal.ts:48-53`): a malformed value would `throw`, but every reachable call is either inside `try/catch` (`handleDiscovery`, `handleWalletMessage`, the `onDappSessionDeleted` handler, `tryCreateQueuedJournal`) or runs only on a `chainInfo` that already passed the `handleDiscovery` parse before approval (`onSessionEstablished`). The `(chainId ^ version) >>> 0` 32-bit truncation is self-consistent across store/lookup and same-origin, so it produces no cross-principal confusion. Non-finding.
- **`toJsonSafe`** (`background.ts:704-730`) has a `WeakSet` cycle guard and processes wallet-*derived* results, not dApp input; `out[key]=…` on a fresh literal only mutates the local object's prototype (no shared-prototype pollution). Non-finding.
- **`index.ts:35-47` `nulo:open-toolbar-popup` listener** does no `sender` check and calls `chrome.action.openPopup({windowId})` with a message-supplied `windowId`. With no `externally_connectable`, only extension-controlled senders reach it, and the content script does not relay this type from the page, so it is not reachable by untrusted input. Noted as a hardening gap (add a `sender.id === chrome.runtime.id` guard), not a finding.
- **dApp display name** (`discovery.appName ?? discovery.appId`, `background.ts:535`) is attacker-controlled but sanitised at the persistence boundary via `sanitizeWireString` (strips bidi/zero-width/control, caps length; `dapp-session/capability-meta.ts`); the trustworthy origin URL is shown alongside. Non-finding.
- **Response broadcast to all frames**: `chrome.tabs.sendMessage(tabId, msg)` (no `frameId`, `background.ts:146`) delivers encrypted responses to every frame, but subframes hold no matching port and lack the session key, so no confidentiality leak. Non-finding.
- **Cluster boundary hand-offs for the `bridge-dispatcher` audit:** confirm (a) `createAuthWit` scope binding in `method-scope-checkers.ts:255-300` is complete for all intent shapes; (b) whether the catch-all error genericisation should move up to the dispatcher; (c) whether `ctx.chainId` (dApp-declared) should be validated against the active/known networks before any popup or execution, which would also blunt Finding 1's popup multiplier.
