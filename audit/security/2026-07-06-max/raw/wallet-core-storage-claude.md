CLUSTER: wallet-core-storage

## Findings

### [1] `ValueStorage.get()` deserializes with an unguarded `JSON.parse` — one corrupt row bricks config/session reads

1. **Title** — `ValueStorage.get()` crashes on any malformed persisted row (no `parseOrDelete` resilience), unlike its sibling `EntityStorage`.

2. **Impact factors** — Property violated: **Availability** (and, for the config store, functional integrity of the settings surface). Blast radius: single user / single browser profile. Data sensitivity: the affected rows are `nulo:config` (wallet configuration) and `nulo:core:session` (the unlocked-session record). Exploitability: attack vector **local** (no network write path to `chrome.storage.local/.session`), attack complexity **high** (requires a genuinely-malformed row to already exist), privileges required **n/a — not adversary-driven** (fault-tolerance gap, not an attacker primitive), user interaction none. Direction of failure is *fail-safe* for the session (a throw prevents restore → user must re-authenticate), *fail-broken* for config (every settings read throws).

3. **Evidence confidence** — moderate. The crash sink is concrete and in-cluster; what is unproven is an *adversarial* write path that plants the malformed row (see Preconditions / Why mitigations fail).

4. **OWASP / CWE mapping** — CWE-248 (Uncaught Exception) / CWE-755 (Improper Handling of Exceptional Conditions); adjacent to CWE-502 handling. OWASP A05:2021 (Security Misconfiguration) / availability facet of A08 (Data Integrity).

5. **Trace**
   - Sink: `packages/wallet-core/src/value-storage.ts:19-23` — `get()` does `return JSON.parse(res[this.root] as string)` with **no** try/catch. A syntactically-malformed stored string throws a `SyntaxError` synchronously out of `get()`.
   - Contrast (the mitigation that exists next door): `packages/wallet-core/src/storage/entity_storage.ts:47-60` `parseOrDelete()` wraps the identical `JSON.parse` in try/catch, logs, drops the bad row, and returns `undefined` so one poisoned row cannot throw into every reader. The authors' own comment at `entity_storage.ts:38-46` enumerates the real-world causes ("half-written mutation, a forward-incompatible shape, or genuine corruption").
   - Reachable callers of the unguarded path (one hop): `apps/extension/src/wallet/config/store.ts:10` (`new ValueStorage<Config>("nulo:config", chrome.storage.local)`) and `apps/extension/src/wallet/services/profile/session-manager.ts:138-139` (`new ValueStorage<Session>(SESSION_STORAGE_ROOT, ...session)`). Every `config.get()` / session restore funnels through `ValueStorage.get()`.

6. **Missing control** — the same corrupt-row tolerance `EntityStorage.parseOrDelete` provides. `ValueStorage.get()` has no try/catch, no drop-and-return-`undefined`, no schema/shape validation of the parsed value (it also blind-casts to `T`, see Notes §B).

7. **Exploit story / violation scenario** — a service-worker termination mid-`set` (or a forward/backward migration writing a shape an older/newer build cannot parse, or genuine `chrome.storage` corruption) leaves `nulo:config` holding a non-JSON string. On next popup open, `ConfigService`'s `get()` throws instead of falling back to defaults; the settings/config-dependent UI fails to initialize. The wallet has one persistence surface and no forensic recovery (per the `entity_storage.ts` comment), so the row stays poisoned until manually cleared.

8. **Preconditions** — a malformed value already resident under `nulo:config` or `nulo:core:session`. No dApp/web-page write path to these areas exists, so this is a robustness/availability gap, not an attacker-triggered exploit.

9. **Why mitigations fail** — there is no upstream guarantee the row is well-formed: `chrome.storage` is "shared, write-anywhere, and survives across SW lifetimes" (author's words, `entity_storage.ts:39-41`). The codebase's own decision to add `parseOrDelete` to `EntityStorage` is an admission the failure mode is real; `ValueStorage` was simply left unhardened, so the same class of corrupt row that `EntityStorage` now survives will still crash every `ValueStorage` consumer.

10. **Instances** — `packages/wallet-core/src/value-storage.ts:19-23` (the single unguarded `get`). Consumer entry points that inherit the crash: `apps/extension/src/wallet/config/store.ts:10`, `apps/extension/src/wallet/services/profile/session-manager.ts:138-139`.

## Notes

Everything below was examined and judged a **NON-FINDING** (no reachable adversarial trace at the certificate bar). Recorded so the coordinator can see the surface was covered and the reasoning is explicit.

**A. EntityStorage prefix-namespace collision (`${root}@${id}` + `startsWith`) — checked, not reachable.**
`getAll`/`getKeys`/`getValues` (`storage/entity_storage.ts:83-113`) select rows by `k.startsWith(`${root}@`)`. A cross-namespace read would require one storage root to be a proper prefix of another followed immediately by `@`. I enumerated every live root (`grep new EntityStorage`): `nulo:core:{token-balances,dappSessions→"nulo:core:dappSessions",networks,contacts,tokens,txs,fpcs,accounts}`, `nulo:core:auth-registry`, `nulo:core:auth-registry-enabled`, `nulo:journal`, `nulo:core:incoming-transfers`, `nulo:core:incoming-trust`, `nulo:core:profiles`. The tempting pair `nulo:core:auth-registry` vs `nulo:core:auth-registry-enabled` does **not** collide: root A's scan prefix is `nulo:core:auth-registry@`, but B's keys read `nulo:core:auth-registry-enabled@…`, and `@` ≠ `-` at the divergence point, so `startsWith` is false. No root is a prefix-plus-`@` of another → no static collision. `id` values cannot cross either: a key is always `${root}@${id}`, so it can only ever match its own root's prefix. The design is fragile (single unescaped `@` delimiter, no key-escaping) but has **no reachable exploit** with the current root set — flagged here only as a latent invariant future roots must preserve.

**B. Blind `JSON.parse(raw) as T` with zero runtime validation (`entity_storage.ts:49`, `value-storage.ts:21`) — root-cause enabler, sink is downstream.**
Both storage primitives return persisted bytes as a fully-trusted `T` with no Zod/shape check. Two consequences: (1) **type-confusion** — a valid-JSON-but-wrong-shape row (number/array/wrong fields) is handed to callers as `T`; (2) **prototype-pollution conduit** — an object persisted with an *own* `"__proto__"` (or `constructor`/`prototype`) key round-trips faithfully (`JSON.stringify` emits it, `JSON.parse` re-creates it as an own property). Critically, `JSON.parse` itself is **prototype-safe** (it does not mutate `Object.prototype`), so no pollution occurs *here*; harm requires a downstream consumer to feed the parsed object into an unsafe recursive merge / property-copy. That sink is out-of-cluster (the SW services, cluster `ext-sw-services-storage`, and any consumer of `EntityStorage.get`). Some consumers do validate downstream (e.g. the operation-journal's `safeParse`), but the core primitive does not *force* it. NON-FINDING in wallet-core (no in-cluster sink); recorded as the load-bearing enabler for the services-cluster agent to complete: any storage row that is (a) dApp-influenceable in content and (b) later consumed by prototype-sensitive code is a live pollution/confusion path.

**C. ReadWriteGuard reader/writer overlap via a synchronous `leaveWrite()`→acquire window — checked, not reachable.**
In `utils/rw-guard.ts:110-123`, `releaseWrite()` sets `writeActive=false` and resolves all `readWaiters`, but those readers only increment `readers` when their microtask later runs. A `write()`/`enterWrite()` issued *synchronously* in that same tick (before the readers resume) would see `readers===0` and grab the write (`acquireWrite`, `rw-guard.ts:98-108`), then overlap the just-released readers — violating write-exclusivity and desyncing the counter. The `write()`-then-`await` path is safe (reader microtasks are queued before the awaiter's), so the only trigger is a synchronous `leaveWrite()` followed by a synchronous re-acquire on the *same* guard. The sole `enterWrite`/`leaveWrite` caller — `packages/aztec-runtime/src/pxe/service.ts:521-546` `onProfileDeleted` — calls `leaveWrite()` in a `finally` and then only does `this.profileBarriers.delete(...)` (a `Map` delete, not a guard acquire) and discards the barrier. No synchronous re-acquire exists → not reachable. Latent fragility, documented; NON-FINDING.

**D. ReadWriteGuard / Lock force-release desync (negative reader counter + concurrent write) — checked, not concretely forceable.**
`rw-guard.ts:132-147` force-sets `readers = 0` and drains a writer after `MAX_READER_DRAIN_MS` (5 min); the still-running readers then decrement past zero (negative counter) and a writer runs concurrently with them — a genuine mutual-exclusion break. `Lock` has an analogous force-release (`utils/lock.ts:37-44`) that can hand the lock to a second holder while the first still "holds" it. Both are documented recovery aids ("should never fire in practice"). Exploiting them requires an attacker to reliably stall a single reader/holder for a full 5 minutes; I could not construct a concrete trace that forces that (proving time is circuit-bounded, and a malicious dApp cannot deterministically pin one op ≥ 5 min). Per "no concrete trace → NON-FINDING," recorded as a robustness hazard in the recovery path, not a finding.

**E. `getRandomHex(length)` odd-length entropy shortfall (`utils/random.ts:13-16`) — not triggered.**
`new Uint8Array(length / 2)` truncates a fractional length, so an *odd* `length` silently yields `length-1` hex chars. Every caller passes an even length (8/16/64, and `PROFILE_ID_HEX_LENGTH = 8`, verified via grep + `profile/repository.ts:30`), so no shortfall occurs, and the source is `self.crypto.getRandomValues` (CSPRNG). NON-FINDING; note the latent trap for any future odd-length caller. The 32-bit ids (`getRandomHex(8)`) are internal record ids checked for uniqueness (`network/service.ts:661`), not unguessable security tokens; the security-relevant session id uses `getRandomHex(64)` = 256 bits (`dapp-session/service.ts:132`).

**F. `array_equals` is non-constant-time (`utils/arrays.ts:1-11`) — no timing oracle in practice.**
Early-returns on first byte mismatch (CWE-208 shape). Its only secret-adjacent caller is `packages/wallet-crypto/src/password-secret-box.ts:171` comparing a decrypted `guard` against a constant. That comparison is reached **only after** AES-GCM has already authenticated the ciphertext (GCM verifies its tag before yielding plaintext), so a keyless attacker cannot produce input that reaches the compare, and the compared constant is non-secret. No remote/measurable timing channel is exposed to a dApp. Cross-cluster (crypto-core owns the crypto); noted, NON-FINDING here.

**G. `EventHandler.invoke` swallows all callback errors (`utils/event-handler.ts:22-28`), and `jsonSanitize`/`normalizeError` round-trip our own serialized data.** The empty `catch {}` is an observability/robustness choice, not a confidentiality/integrity/authz/availability violation. `serialization.ts` `jsonStringify`/`jsonSanitize` and `jobs/error.ts` `normalizeError` only serialize wallet-internal values (and `normalizeError` is explicitly hardened against hostile `toJSON`/Proxy traps with a bounded output, `jobs/error.ts:38-70`); prototype-safe. NON-FINDINGS.

**Scope note.** All production files under `packages/wallet-core/src/**` were read. `src/testing/**` (FakeBrowserApi, MockClock, FakeBackgroundTicker) was skipped per the negative list — confirmed **not production-wired** (only referenced from a doc comment in `src/index.ts:10` and from `*.test.ts`, never imported by app/runtime code). Pure type-only files (`ports/*.ts` interfaces, `logger/interfaces.ts`, `jobs/types.ts`, `base/topology.ts` pure algorithm) carry no runtime trust boundary and were clean.
