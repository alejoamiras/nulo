CLUSTER: ext-offscreen

Scope audited: `apps/extension/src/offscreen/{index.ts,index.html,is-benign-sw-disconnect.ts,is-benign-sw-disconnect.test.ts}`.
Permitted handoff hops taken: SW supervisor `apps/extension/src/wallet/utils/offscreen.ts`; SW→offscreen consume target `packages/aztec-runtime/src/offscreen/entry.ts` (`createPxeOffscreen`); the offscreen messaging base `packages/extension-messaging/src/offscreen/{service.ts,client.ts}` (messaging-base→service edge); the immediate PXE handler `packages/aztec-runtime/src/pxe/{service.ts,ipxe.ts,spec.ts,client.ts}` (signatures only); the SW-seam contrast `apps/extension/src/wallet/services/wallet-sdk/content-script-validator.ts`; the content-script relay `apps/extension/src/content-script/content.ts`. The offscreen shell (`offscreen/index.ts`) is intentionally thin — it bootstraps the PXE `Service`, so the security-relevant sinks live one hop out and are flagged for the owning clusters where the root fix belongs.

## Findings

### [1] Offscreen PXE message handler performs zero sender authentication — any intra-extension message invokes privileged PXE RPCs, bypassing the SW authorization pipeline

1. **Title** — Unauthenticated offscreen message trust: `sender.id` / `sender.tab` never checked; privileged PXE RPCs (`registerAccount`, `clearChainState`, `proveTx`, `getNotes`, …) are reachable by any intra-extension `chrome.runtime.sendMessage` matching `to === "pxe"`.

2. **Impact factors** — Property: Authorization (integrity + availability primarily; confidentiality of responses is *not* reachable by the page-adjacent attacker, see field 9). Blast radius: single user's active profile/chain (all of that user's PXE state). Data sensitivity: high — the offscreen is the extension's crypto host (WebCrypto key derivation + PXE). Exploitability: attack vector adjacent/local (must originate from an in-extension context; the realistic untrusted source is the content-script relay, which is page-driven); attack complexity high (requires coercing an attacker-shaped `chrome.runtime.sendMessage` out of the content-script relay — see field 9); privileges required none-to-low; user interaction none.

3. **Evidence confidence** — Missing control: **high** (the handler provably ignores `sender`). End-to-end external exploitability: **moderate** (gated by whether the `@aztec/wallet-sdk` `ContentScriptConnectionHandler` can be induced to emit an arbitrary-shaped runtime message — a cluster-7 / upstream question I could not confirm in-cluster).

4. **OWASP / CWE** — OWASP A01:2021 (Broken Access Control). CWE-306 (Missing Authentication for a Critical Function), CWE-862 (Missing Authorization); the trust-boundary root is CWE-940 (Improper Verification of Source of a Communication Channel).

5. **Trace** (source → sink):
   - `apps/extension/src/offscreen/index.ts:81` — `await createPxeOffscreen({ profiles, logger, factory })` bootstraps the PXE inside the offscreen document.
   - `packages/aztec-runtime/src/offscreen/entry.ts:43-47` — `createPxeOffscreen` constructs `new PxeService(...)` and `services.start()`.
   - `packages/aztec-runtime/src/pxe/service.ts:57` — `class PxeService extends Service<Methods>` (the offscreen messaging server base).
   - `packages/extension-messaging/src/offscreen/service.ts:32-41` — `subscribe()` registers `chrome.runtime.onMessage.addListener(this.onMessageListener)`; the listener is `(message) => { if (typeof message === "object" && message !== null && message.to === this.name) this.onMessage(message); return false }`. **The Chrome listener's second argument `sender` is never bound or inspected.**
   - `packages/extension-messaging/src/offscreen/service.ts:43-49` — `onMessage` checks only `message.type === Request`, `message.from`, `message.content`, then `void this.handleRequest(message.content, message.from)`. No authn/authz. (`handleRequest` dispatch resides in `packages/extension-messaging/src/core/base-service.ts` — trace exits this cluster there.)
   - `packages/aztec-runtime/src/pxe/service.ts:60-82` — exposed `rpcMethods`: `registerAccount`, `clearChainState`, `proveTx`, `simulateTx`, `getNotes`, `getRegisteredAccounts`, `registerSender`, `registerContract`, … Routing target is the static string `PXE_SERVICE_NAME = "pxe"` (`packages/aztec-runtime/src/pxe/spec.ts:22`).
   - Reachability of the listener: any extension context — including a **content script** (`apps/extension/src/content-script/content.ts:12`, `sendToBackground: (message) => chrome.runtime.sendMessage(message)`) — whose `chrome.runtime.sendMessage` is delivered to the offscreen document's `onMessage`. The SW→offscreen transport is itself unaddressed broadcast (`packages/extension-messaging/src/offscreen/client.ts:104`), confirming `to === "pxe"` is the *only* gate.

6. **Missing control** — No `sender.id === chrome.runtime.id` check, and (more importantly, since content scripts share the extension id) no `sender.tab === undefined` / frame check to reject content-script and tab senders. The SW seam has exactly this class of guard — `apps/extension/src/wallet/services/wallet-sdk/content-script-validator.ts:88-90` (`isSubframeSender`) plus the Zod envelope filter, and the SW's own listener binds `sender` (`apps/extension/src/wallet/services/wallet-sdk/background.ts:149`). The offscreen seam — the higher-value context — received none of it.

7. **Exploit story** — A malicious dApp drives its content script (or a compromised/buggy content-script relay) to emit `chrome.runtime.sendMessage({ type: <Request>, to: "pxe", from: "attacker", content: { method: "clearChainState", args: [...] } })`. The offscreen `PxeService` receives it (matches `to === "pxe"`), and — with no SW authorization, no capability-map approve/auto-approve gate, no scope-enforcement, no origin binding — executes it. Destructive/abusive reachable methods: `clearChainState` (wipes chain state), `registerAccount(secretKey, partialAddress)` (injects an attacker-chosen account/secret into the victim PXE), `proveTx`/`simulateTx` (CPU/memory exhaustion — proving is minutes-long). The SW's entire dApp-RPC gauntlet (content-script→SW→`BackgroundConnectionHandler`→wallet-bridge Zod-narrow→capability-map→scope-enforcement) is short-circuited by talking to the offscreen directly.

8. **Preconditions** — The attacker must get an attacker-shaped `chrome.runtime.sendMessage` emitted from an in-extension context. The in-scope path is the content-script relay being coerced by page input (or a content-script compromise). No user interaction, no prior grant.

9. **Why mitigations fail** — (a) `message.to === "pxe"` is a routing filter, not authentication — it authenticates nothing about the *sender*. (b) The SW-side `content-script-validator` / `isSubframeSender` guards never run here; they live on the SW's listener, not the offscreen's. (c) Confidentiality of *responses* is NOT a viable exfil path for the page-adjacent attacker: the offscreen replies via unaddressed `chrome.runtime.sendMessage` (`packages/extension-messaging/src/offscreen/service.ts:53-59`) which does not fan out to content scripts, and the SW-side `ServiceClient` filters `message.to === this.uid` (`packages/extension-messaging/src/offscreen/client.ts:62`). So the realistic impact is integrity/availability (state mutation, destructive wipe, resource exhaustion), not response theft. (d) The `registerAccount(secretKey)` request the SW legitimately sends does NOT leak the secret to pages — Chrome `runtime.sendMessage` broadcasts do not reach content scripts, and no `chrome.tabs.sendMessage` targets the offscreen (`chrome.tabs.sendMessage` is used only SW→content-script at `apps/extension/src/wallet/services/wallet-sdk/background.ts:146`) — verified and cleared.

10. **Instances** —
    - `apps/extension/src/offscreen/index.ts:81` (bootstraps the unauthenticated PXE listener into the offscreen — the in-cluster origin).
    - `apps/extension/src/offscreen/index.ts:14-19` (a second, separately-registered `chrome.runtime.onMessage` listener in the same document, also ignoring `sender` — see Finding [2]).
    - Root of the missing check: `packages/extension-messaging/src/offscreen/service.ts:36-49` (cluster `messaging-boundary`) — **flag for that cluster; the fix belongs there** (bind + validate `sender` in `onMessageListener`). Every `Service` subclass instantiated in the offscreen inherits the gap.

### [2] Offscreen lifecycle control messages (PING/PONG/READY/KEEPALIVE) are unauthenticated — spoofable health/readiness can wedge or mis-drive the PXE transport

1. **Title** — Unauthenticated offscreen liveness/readiness handshake: the SW supervisor and the offscreen shell trust any `OFFSCREEN_PONG` / `OFFSCREEN_READY` / `OFFSCREEN_PING` string with no `sender` check, enabling availability attacks on the offscreen lifecycle.

2. **Impact factors** — Property: Availability (integrity of lifecycle state). Blast radius: single user (the SW's view of its own offscreen). Data sensitivity: n/a (control-plane). Exploitability: attack vector adjacent/local (in-extension sender, same content-script-relay gate as Finding [1]); complexity high; privileges none; user interaction none.

3. **Evidence confidence** — Missing control: **high**. Reachability: **moderate** (same relay gate as Finding [1]).

4. **OWASP / CWE** — OWASP A01 / A07 (Identification and Authentication Failures). CWE-306, CWE-940, CWE-400 (Uncontrolled Resource Consumption via induced timeouts/hangs).

5. **Trace** (source → sink):
   - Offscreen ping responder: `apps/extension/src/offscreen/index.ts:14-19` — `chrome.runtime.onMessage.addListener((message) => { if (message === OFFSCREEN_PING) chrome.runtime.sendMessage(OFFSCREEN_PONG).catch(()=>{}); return false })`. No `sender` check; any sender can elicit a PONG or observe/liveness-probe the offscreen.
   - SW health gate: `apps/extension/src/wallet/utils/offscreen.ts:80-87` — `onPong` resolves `isOffscreenHealthy()` to `true` on ANY `OFFSCREEN_PONG` message, no `sender` check.
   - SW ready gate: `apps/extension/src/wallet/utils/offscreen.ts:47-55` — `onOffscreenReady` resolves the ready promise + clears the timeout on ANY `OFFSCREEN_READY_MESSAGE`, no `sender` check.

6. **Missing control** — Same as Finding [1]: no `sender.id === chrome.runtime.id && sender.tab === undefined` on any of the three control listeners.

7. **Exploit story** — (a) Spoofed PONG: an attacker-driven content script emits `chrome.runtime.sendMessage("OFFSCREEN_PONG")` while a real offscreen is dead/zombie. If it races an in-flight `isOffscreenHealthy()` probe (`offscreen.ts:73-97`), the SW concludes "healthy," skips `closeOffscreen()` + recreate (`ensureOffscreenRunning`, `offscreen.ts:205-213`), and subsequent PXE RPCs hang until the 90s per-request timeout (`packages/extension-messaging/src/offscreen/client.ts:20`) — a denial of the wallet's sign/prove path. (b) Spoofed READY: emitting `OFFSCREEN_READY` before the real document finishes init resolves the ready-gate early, so the SW dispatches PXE RPCs into a not-yet-initialized offscreen → request failures.

8. **Preconditions** — Same in-extension-message precondition as Finding [1], plus a timing race against a genuine probe for the PONG variant.

9. **Why mitigations fail** — The listeners compare only against magic strings; the sender is anonymous. `isOffscreenHealthy` resolves on the *first* matching PONG regardless of origin, and `onOffscreenReady` on the *first* matching READY. There is no correlation nonce binding a PONG to the specific PING the SW sent, and no sender identity to reject a foreign PONG/READY.

10. **Instances** — `apps/extension/src/offscreen/index.ts:14-19`; `apps/extension/src/wallet/utils/offscreen.ts:47-55` and `:80-87` (SW supervisor — the permitted hop; fix belongs jointly here and in the offscreen shell).

## Notes

- **Console-sniffer exfiltration surface (mechanism in-cluster; no concrete secret-log instance found → not a finding).** `apps/extension/src/offscreen/index.html:6` loads `apps/extension/src/utils/console-sniffer.ts`, which overrides `console.{trace,debug,log,info,warn,error}` unconditionally (no level gating, no redaction) and forwards every call to `self.on<method>`. `apps/extension/src/offscreen/index.ts:23-28` wires those to `logger.log("pxe", level, ...args)` → `LoggerServiceClient` → SW `LoggerStore` (persisted, user-viewable). Because the *same* offscreen document runs WebCrypto key derivation + the Aztec PXE + bb.js, **any** secret material those dependencies log at **any** level is captured and shipped cross-context into a persisted log. No concrete `console.log(<secret>)` is present in in-cluster code, and the Aztec/bb libraries are upstream (out of scope), so this is a Note, not a finding — but it is a real, sensitive-data-exposure (CWE-532) amplifier that the crypto (`crypto-core`) and `aztec-runtime-signing` auditors should weigh: a single debug log of an `Fr`/witness/secret key anywhere in the offscreen import graph becomes a durable, exportable leak. Recommend redaction/level-capping at the `self.on<method>` sink.

- **Firefox zombie-offscreen → duplicate PXE listener (self-acknowledged, feature-flagged, Firefox-only → low).** `apps/extension/src/wallet/utils/offscreen.ts:99-127` and `:178-203` document that on Firefox, after an SW restart the in-memory `firefoxOffscreenWindowId` resets to `null` while the old hidden window keeps running, so the next `ensureOffscreenRunning()` creates a second window — leaking the old one. Both windows host `PxeService` bound to the same static name `"pxe"` (`packages/aztec-runtime/src/pxe/spec.ts:22`) and both receive the broadcast request `to:"pxe"` → both execute it and both reply. Routing is by static name + `uid` only, with no binding to a specific document instance, so a request can be served by (or its result raced against) a stale PXE with different chain state. Chromium is largely protected — only one offscreen document is permitted and `createDocument` throws `"single offscreen document"`, handled by the ghost-retry at `offscreen.ts:148-160`. Low severity: Firefox-only, behind manual-verification feature-flagging, and self-documented as a known limitation.

- **IndexedDB read-trust: no in-cluster finding.** The PXE's IndexedDB (`packages/aztec-runtime/src/pxe/service.ts:151,158,173,468,538`) is scoped to the extension origin and is not writable by a dApp page, so there is no untrusted-write→trusted-read path from the web. Untrusted **chain-note** deserialization (a malicious on-chain counterparty crafting notes/events the PXE decrypts) is real but happens inside the upstream Aztec PXE library, outside this cluster — flag for `aztec-runtime-signing` if pursued. The destructive `init()` DB-deletion sweep (`service.ts:149-183`, keyed on `getProfiles()` before `connect()`) is an ordering/robustness concern, not attacker-driven.

- **`is-benign-sw-disconnect.ts` reviewed — clean.** Exact-shape predicate (`reason instanceof Error && reason.message === "Client disconnected"`); rejects string look-alikes (test at `is-benign-sw-disconnect.test.ts:13-17`). Only demotes a known-benign rejection to Debug; real errors still surface at `offscreen/index.ts:44`. No security impact.

- **Build-stamp globals (`offscreen/index.ts:54-70`) reviewed — clean.** Write static build-time constants to `globalThis`; no runtime/attacker input, anti-tree-shake only.
