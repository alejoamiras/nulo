CLUSTER: ext-sw-services-storage

## Findings

### [1] Backup restore can silently disable strict security and persist the passhash bearer

1. **Title** — Backup restore can silently disable strict security and persist the passhash bearer.

2. **Impact factors** — Violates confidentiality and authorization for a single user. The sensitive data is the password-profile passhash bearer stored in `chrome.storage.session`, which can later silently re-open the encrypted profile secret without re-prompting for the password. Exploitability: local/user-assisted attack vector through an attacker-supplied or tampered plain full-backup file; low attack complexity; attacker privileges required: none; user interaction required: the user imports the backup and enters a new profile password.

3. **Evidence confidence** — High.

4. **OWASP / CWE mapping** — OWASP A01 Broken Access Control / A05 Security Misconfiguration; CWE-862 Missing Authorization; CWE-20 Improper Input Validation.

5. **Trace** — Untrusted backup file is read and parsed as JSON in `apps/extension/src/utils/full-backup-helpers.ts:32` and `apps/extension/src/utils/full-backup-helpers.ts:41`. The import flow trusts the backup’s `data` object in `apps/extension/src/composables/useFullBackupImport.ts:200`-`apps/extension/src/composables/useFullBackupImport.ts:214`. The checksum is recomputed from attacker-controlled backup contents, excluding only the embedded checksum, in `apps/extension/src/composables/useFullBackupImport.ts:207` and `apps/extension/src/composables/useFullBackupImport.ts:226`-`apps/extension/src/composables/useFullBackupImport.ts:235`. The config slice is restored before session activation in `apps/extension/src/composables/useFullBackupImport.ts:381`-`apps/extension/src/composables/useFullBackupImport.ts:399`, then `finalizeRestore` opens the imported session in `apps/extension/src/composables/useFullBackupImport.ts:411`-`apps/extension/src/composables/useFullBackupImport.ts:412`. `ConfigService.restore` accepts each backup config prop and calls `setValue` without runtime schema validation in `apps/extension/src/wallet/services/config/service.ts:45`-`apps/extension/src/wallet/services/config/service.ts:51`; `setValue` forwards it directly in `apps/extension/src/wallet/services/config/service.ts:33`-`apps/extension/src/wallet/services/config/service.ts:35`. `ConfigStore.set` assigns arbitrary runtime `key`/`value` into the live config and persists it in `apps/extension/src/wallet/config/store.ts:28`-`apps/extension/src/wallet/config/store.ts:36`. `SessionManager` consumes `strictSecurityMode` updates in `apps/extension/src/wallet/services/profile/session-manager.ts:483`-`apps/extension/src/wallet/services/profile/session-manager.ts:495`. During `finalizeRestore`, password profiles pass a freshly derived passhash into `SessionManager.open` in `apps/extension/src/wallet/services/profile/service.ts:1082`-`apps/extension/src/wallet/services/profile/service.ts:1084`. `SessionManager.open` persists that passhash whenever `strictSecurityMode` is false in `apps/extension/src/wallet/services/profile/session-manager.ts:211`-`apps/extension/src/wallet/services/profile/session-manager.ts:218`.

6. **Missing control** — The backup-driven config restore lacks an allowlisted runtime schema for config keys and values, and lacks a separate authorization/confirmation gate for security-critical settings such as `strictSecurityMode` and `sessionTtl`.

7. **Exploit story / violation scenario** — An attacker gives the user a schema-version-2 plain backup whose `data.config` includes `{ "key": "strictSecurityMode", "value": false }` and optionally `{ "key": "sessionTtl", "value": 0 }`, then recomputes the backup checksum. The user imports the file and sets a password for the restored profile. The import restores config before calling `finalizeRestore`, so the live session manager is already in lenient mode. `finalizeRestore` opens the restored password profile and `SessionManager.open` writes the passhash into `chrome.storage.session`. The user never saw the security-settings confirmation that normally warns when disabling strict mode.

8. **Preconditions** — The user imports an attacker-controlled or tampered plain full-backup file with a valid recomputed checksum. For encrypted backups, the attacker must either know the backup encryption password or control the backup before encryption. The restored profile must be password-backed for immediate passhash persistence during `finalizeRestore`; the global setting also affects future password-profile unlocks.

9. **Why mitigations fail** — TypeScript `ConfigKey`/`Config[TKey]` constraints are erased at the RPC boundary. `ConfigStore.apply` type-checks stored config during load, but `ConfigStore.set` does not validate runtime `setValue` or `restore` input. The backup checksum is not an authenticity control because it is stored inside the same attacker-controlled file. The UI confirmation in `apps/extension/src/popup/pages/settings/security/index.vue:73`-`apps/extension/src/popup/pages/settings/security/index.vue:94` only protects the settings-page toggle; backup restore bypasses it by calling the config service directly.

10. **Instances** — `apps/extension/src/wallet/services/config/service.ts:33`, `apps/extension/src/wallet/services/config/service.ts:45`, `apps/extension/src/wallet/config/store.ts:28`, `apps/extension/src/wallet/config/store.ts:34`, `apps/extension/src/wallet/services/profile/session-manager.ts:211`, `apps/extension/src/wallet/services/profile/service.ts:1084`.
