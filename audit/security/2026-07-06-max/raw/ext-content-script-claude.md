CLUSTER: ext-content-script

Scope: `apps/extension/src/content-script/content.ts` (the entire cluster — a single 23-line file). Its security-critical logic is delegated to `@aztec/wallet-sdk@5.0.0-rc.2`'s `ContentScriptConnectionHandler` (`node_modules/@aztec/wallet-sdk/src/extension/handlers/content_script_connection_handler.ts`, verified byte-identical to the resolved bun-cache tarball). One handoff hop crossed into the SW receiver (`apps/extension/src/wallet/services/wallet-sdk/background.ts`, `content-script-validator.ts`) to resolve the origin-trust question.

## Findings

### [1] Content script relays page `postMessage` discovery to the SW with no rate limit (availability)

- **Impact factors**: Availability. The page→content-script discovery handler forwards every well-formed discovery message straight to `chrome.runtime.sendMessage` with zero throttling. A malicious page can loop `window.postMessage` and flood the single MV3 service worker's event loop. CIA+A: Availability only (no C/I). Blast radius: primarily the attacker's own tab; cross-tab degradation is possible but bounded (single SW is shared, so a sustained flood can delay other tabs' wallet ops). Data sensitivity: none. Exploitability: attack vector network (any web page in a tab where the extension is installed), attack complexity low, privileges required none, user interaction none (no approval needed to *emit* discovery — approval only gates session establishment).
- **Evidence confidence**: moderate. The unbounded relay is real and concrete; the *effective* blast radius is limited by Chrome's messaging throughput throttling and the SW-side per-`(origin,chainId)` discovery dedup, so severity is low.
- **OWASP / CWE mapping**: OWASP A04:2021 Insecure Design; CWE-770 (Allocation of Resources Without Limits or Throttling) / CWE-400 (Uncontrolled Resource Consumption).
- **Trace**:
  - Source (untrusted page input): `window.postMessage(JSON.stringify({type:"aztec-wallet-discovery",...}), "*")` from arbitrary page JS.
  - `@aztec/wallet-sdk` `content_script_connection_handler.ts:97-116` — `pageMessageHandler` accepts it (`event.source === window` passes for same-window posts), `JSON.parse`, dispatches `WalletMessageType.DISCOVERY` → `handleDiscoveryRequest`.
  - `content_script_connection_handler.ts:156-162` — `handleDiscoveryRequest` → `this.transport.sendToBackground(...)` with no rate limit / no dedup.
  - Sink: `apps/extension/src/content-script/content.ts:12` — `sendToBackground: (message) => chrome.runtime.sendMessage(message)`. Every iteration hits the SW.
  - SW receiver: `apps/extension/src/wallet/services/wallet-sdk/background.ts:149-194` — each message runs `isSubframeSender` + Zod `validateContentScriptMessage` + upstream handling on the SW event loop.
- **Missing control**: No per-tab / per-origin rate limit or coalescing on the outbound relay in either `content.ts` or the SDK handler. The content script is architecturally a dumb relay, so the correct enforcement point is SW-side (bounded queue / token-bucket per sender tab), which is absent — the SW dedups *identical* `(origin,chainId)` discoveries but still parses every inbound envelope before dedup.
- **Exploit story**: A malicious dApp (or any page that runs JS) executes `for(;;) window.postMessage(JSON.stringify({type:"aztec-wallet-discovery",requestId:crypto.randomUUID(),chainInfo:{...}}), "*")`. Each unique `requestId`/`chainInfo` slips past the SW's `(origin,chainId)` dedup partially (new requestIds still incur parse+validate cost), saturating the SW event loop and delaying legitimate wallet operations (balance refresh, pending approvals) in other tabs while the SW is busy.
- **Preconditions**: Extension installed; victim visits an attacker page in any tab. No wallet unlock or prior approval required to emit the flood.
- **Why mitigations fail**: The SW `(origin,chainId)` dedup (`background.ts` `pendingDiscoveryPromises`) collapses *duplicate* discoveries but does not cap the *rate* of distinct-keyed inbound messages, and it runs *after* the per-message `isSubframeSender`+Zod cost. Chrome's built-in messaging throttling reduces but does not eliminate event-loop pressure. There is no content-script-side backpressure at all.
- **Instances**: `apps/extension/src/content-script/content.ts:12` (relay sink); upstream trigger at `@aztec/wallet-sdk@5.0.0-rc.2/src/extension/handlers/content_script_connection_handler.ts:118,156-162`.

## Notes — considered and cleared (with reasoning)

The headline questions the audit asked, and why they do NOT yield findings:

**`event.source === window` IS validated; `event.origin` is NOT — but it is subsumed, not a vuln.** The page→content-script listener checks `if (event.source !== window) return` (`content_script_connection_handler.ts:98`). It does **not** check `event.origin`. This is *not* independently exploitable: `event.source === window` can only be true when a script in *this same frame* posted to its own `window`, which is necessarily same-origin. A cross-origin frame calling `victim.postMessage(...)` yields `event.source === attackerWindow ≠ victimWindow` → rejected. The manifest sets `all_frames:true` + `match_about_blank` unset, so no content-script instance runs in an origin-inheriting `about:blank`/`srcdoc` frame that could confuse this. Therefore `source===window` strictly implies `origin===self.origin`; the missing origin check is defense-in-depth with no concrete vector (per DO-NOT-FLAG). Confirmed present in the shipped compiled JS (`dest/.../content_script_connection_handler.js:64`).

**Origin trust for approval is bound SW-side from `sender.tab.url` (trusted), never from page content.** The content script forwards no origin field; the SW's upstream `BackgroundConnectionHandler` attributes origin via the browser-provided `sender.tab?.url`. A page cannot spoof its origin into an approval. Verified at the handoff: `apps/extension/src/wallet/services/wallet-sdk/background.ts:149-192`.

**The cross-origin-iframe origin-inheritance vector (historical F-001) is already mitigated at the SW.** Because upstream credits subframe messages to the *top-frame* URL, an evil iframe could inherit the parent's grants. Nulo rejects subframe senders (`sender.frameId !== 0`) before the upstream handler sees them, default-on, build-time-flag-gated: `apps/extension/src/wallet/services/wallet-sdk/background.ts:172-179` + `content-script-validator.ts:88-90`. The content script itself cannot set `frameId` (Chrome does), so it is a faithful relay and the policy is enforced at the correct layer.

**No wallet-state leaks to an unauthorized origin via reflected SW data.** SW→page reflections are: (a) `DISCOVERY_RESPONSE{walletInfo}` — public branding, posted to the frame's *own* window (`content_script_connection_handler.ts:217`); (b) `KEY_EXCHANGE_RESPONSE` — the SW's ECDH *public* key; (c) `SECURE_RESPONSE` — AES-256-GCM ciphertext only decryptable by the page-side ECDH key holder. All delivery is same-window/same-origin or over the transferred `MessagePort`; a `window.postMessage(...)` to one's own `window` is not delivered to parent/opener/child frames, so there is no cross-origin delivery path. The content script holds no keys.

**`window.postMessage(response, '*', [port2])` wildcard target — not cross-origin-exploitable here.** The `'*'` at `content_script_connection_handler.ts:217` is sloppy, but a self-`window` post is delivered only to that window's own listeners (same origin); `'*'` vs a scoped origin makes no delivery difference for self-posts. The transferred `MessagePort` reaches only same-origin page scripts. Same-origin page JS == the dApp (or its XSS); that is the intended trust boundary, gated downstream by SW approval + capability scope + per-tx signing approval. SDK-owned code, not `content.ts`.

**`addBackgroundListener` drops `sender` and forwards every `onMessage` — not web-reachable.** `content.ts:13-19` registers `chrome.runtime.onMessage` and forwards `message` with no sender check. `onMessage` (not `onMessageExternal`) is same-extension only; `externally_connectable` is unset (manifest), and web pages cannot call `chrome.tabs.sendMessage`, so no web page or foreign extension can reach this listener. The SDK handler additionally string-checks `message.origin === "background"` (`content_script_connection_handler.ts:123`). No trust-boundary crossing.

**No injected provider / inpage script — wallet-impersonation is a dApp-SDK property, not an extension bug.** The manifest declares one isolated-world content script and `web_accessible_resources` exposes only `logo.png` (`apps/extension/manifest/manifest.config.ts:31-38,56-61`); the extension injects no MAIN-world provider. The `walletInfo` identity is asserted by the SW over the discovery response. Page JS can trivially fake a `DISCOVERY_RESPONSE` to *other page scripts*, but a fake wallet cannot sign (no keys), and this is inherent to the postMessage discovery protocol owned by the dApp's own `@aztec/wallet-sdk` — outside the extension's control surface.

**Supply-chain drift on the delegated SDK is gated.** The security of this cluster rests on the SDK's `source===window` check. `@aztec/wallet-sdk` is exact-pinned (`apps/extension/package.json:47` → `"5.0.0-rc.2"`, no range) with `bun.lock` committed + `--frozen-lockfile` CI, so a malicious SDK update cannot silently drop the check without a reviewed lockfile change.

**Minor, SW-controlled, non-web-reachable:** `handleDiscoveryApproved` (`content_script_connection_handler.ts:164-218`) overwrites `this.ports.set(sessionId, …)` without closing a prior port for a re-used `sessionId` (orphaned-port leak only if the SW double-approves the same `sessionId` — SW-controlled, negligible). Not a page-reachable resource-exhaustion primitive; `ports` growth is bounded by distinct SW-approved sessions.
