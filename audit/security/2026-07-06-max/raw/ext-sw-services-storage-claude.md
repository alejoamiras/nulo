CLUSTER: ext-sw-services-storage

Scope audited: `apps/extension/src/wallet/**` EXCEPT `services/wallet-sdk/**`. Priority focus per tasking: `storage/migrate.ts`, `services/profile/` + `session-manager.ts`, `services/operation-journal/`, `services/config/`, `utils/offscreen.ts`, `utils/lock.ts`. (`utils/lock.ts` does not exist — the `Lock` primitive is re-exported from `@nulo/wallet-core/utils`, cluster 2; `SessionManager` receives its serializer via injected `runExclusive`.)

Trust-boundary determination (governs every finding below): the dApp→SW channel is `content-script → chrome.runtime.sendMessage → wallet-sdk handler` (content.ts is a pure SDK-envelope relay, `apps/extension/src/content-script/content.ts:11-22`; no port relay). The typed background services in this cluster are exposed over `chrome.runtime.onConnect` **ports** (`packages/extension-messaging/src/background/service.ts:32-44`), and the manifest declares **no `externally_connectable`** and there is **no `onMessageExternal`/`onConnectExternal`** (`apps/extension/manifest/manifest.config.ts`). Therefore the profile / config / operation-journal / dapp-session / dapp-interaction port-RPC surfaces are reachable only by the extension's own popup/pages (trusted) and by SW-internal code (the wallet-sdk dispatcher). A malicious dApp page cannot open a named port to these services. `chrome.storage.session` uses the MV3 default access level (no `setAccessLevel` call anywhere in `apps/extension/src` or `packages`), so the persisted session record (passhash in non-strict mode) and the persisted log buffer are **not** readable by content scripts. This collapses most theoretical vectors in this cluster; the two findings below are the residual concrete/latent issues.

## Findings

### [1] Global console hijack persists an un-redacted log buffer to `chrome.storage.session`; the sanitizer does not redact secret-bearing keys

1. **Title** — Secret-material can reach the persisted (`chrome.storage.session`) + rehydrated log buffer because the log sanitizer redacts crypto-artifact keys but not `secret`/`passhash`/`password`/`credential`/`masterKey`.
2. **Impact factors** — Confidentiality (sensitive-data exposure). Property: secret master key / passhash / signing material could be written to `chrome.storage` via the log pipe. Blast radius: single-user (the local profile whose material is logged). Data sensitivity: highest (master secret / passhash unseal the wallet). Exploitability: attack vector Local (requires the material to actually be logged by wallet code or a loaded dependency, and read access to `chrome.storage.session` — TRUSTED-context only today); attack complexity High; privileges required None-for-the-log-write / Local-for-the-read; user interaction None. This is a standing hardening gap, not an actively-demonstrated leak.
3. **Evidence confidence** — moderate (the persistence sink and the redaction gap are concrete and code-cited; no *current* in-cluster call logs a secret object — grep of `apps/extension/src/wallet` for secret-bearing variables passed to log/console sinks is clean).
4. **OWASP / CWE** — A09:2021 Security Logging & Monitoring / A02 Cryptographic-adjacent exposure; CWE-532 (Insertion of Sensitive Information into Log File), CWE-200.
5. **Trace (source → sink)**:
   - Source (amplifier): the SW installs a **global** hijack of every `console.{log,warn,error,debug,info}` → `logger.log(...)` at `apps/extension/src/wallet/index.ts:56-61`, and routes unhandled rejections through it at `apps/extension/src/wallet/index.ts:65-67`. This captures output from the whole SW context, **including third-party `@aztec/*` code** the SW loads — code this repo does not control.
   - Persist: `LoggerStore.log` stores every Info/Warn/Error record (Debug is dropped unless `debugMode`) — `apps/extension/src/wallet/logger/store.ts:27-43` — and `scheduleFlush()` writes the last 2000 records to `chrome.storage.session["nulo:logs"]` every 2 s — `apps/extension/src/wallet/logger/store.ts:80-92`. On next SW boot `rehydrate()` reads them back — `apps/extension/src/wallet/logger/store.ts:64-78` — so anything captured **survives SW restarts**.
   - Sink (missing redaction): the pre-store sanitizer `trim()` explicitly blanks `acir`/`authWitnesses`/`partialWitness`/`publicInputs`/`vk` — `apps/extension/src/wallet/logger/utils.ts:96-110` — but has **no branch for `secret`, `passhash`, `password`, `credentialId`, `masterKey`**. Any logged object carrying those keys is walked and stored verbatim (to depth 6).
6. **Missing control** — a deny-list (or allow-list) in `trim()` for secret-bearing property names, and/or not persisting the log buffer to storage at all for a key-holding wallet. The existing redaction switch proves the mechanism exists; the secret keys are simply absent from it.
7. **Exploit / violation scenario** — A dependency or a future wallet code path does `console.error("open failed", session)` / `console.log(activeSession)` / logs an object embedding the passhash or the `ActiveSession.secret` (`apps/extension/src/wallet/services/profile/spec.ts:56-63`). `trim()` does not strip it; it is flushed to `chrome.storage.session["nulo:logs"]` and rehydrated on the next SW lifetime. Any actor that later gains read access to extension session storage (local forensic access; a future `setAccessLevel('TRUSTED_AND_UNTRUSTED_CONTEXTS')` regression; a log-export/support-bundle feature) recovers material that unseals the wallet.
8. **Preconditions** — something in the SW context logs an object containing a secret field at Info/Warn/Error level. No dApp interaction required; the hijack is unconditional.
9. **Why mitigations fail** — `trim()` is the *only* sanitization layer and its redaction list omits the secret keys; `jsonSanitize` (in `BaseService`) is about serializability, not secret redaction. The wallet's own SW code presently avoids logging secrets (verified), but the global console hijack deliberately captures **all** console output, including from libraries outside this repo's control, so "we don't log secrets" is not enforced at the sink.
10. **Instances** — sanitizer gap: `apps/extension/src/wallet/logger/utils.ts:96-110`. Persist/rehydrate sink: `apps/extension/src/wallet/logger/store.ts:39-43,64-78,80-92`. Amplifier: `apps/extension/src/wallet/index.ts:56-61,65-67`.

### [2] Operation-journal read methods are not scoped to the active profile (latent cross-profile activity-history disclosure, gated on cluster-9 exposure)

1. **Title** — `getOperations` / `countOperations` / `getOperation` return records across **all** profiles and **all** dApp origins with no active-profile filter.
2. **Impact factors** — Confidentiality (activity metadata: `origin`, `recipientAddress`, `amountRaw`, `txHash`, `contractAddress`, `profileId`). Blast radius: all local profiles' history. Sensitivity: moderate (financial-activity metadata, not key material). Exploitability: contingent — no untrusted caller today (port-RPC popup-only). Attack vector would be Network/Adjacent **only if** the wallet-sdk dispatcher (cluster 9) ever routes a dApp request to a journal read.
3. **Evidence confidence** — low (concrete code-level scoping gap; **no** currently-reachable untrusted actor — this is why it is ranked here rather than as a live disclosure).
4. **OWASP / CWE** — A01:2021 Broken Access Control; CWE-863 (Incorrect Authorization), CWE-200.
5. **Trace** — `OperationJournalService.getOperations(filter?)` — `apps/extension/src/wallet/services/operation-journal/service.ts:381-394`: with no filter it returns `_loadAllValidated()` (every row); the `filter.profileId` predicate is **opt-in**, never enforced. Same for `countOperations` (`:406-417`) and `getOperation(id)` (`:375-379`, any id). Contrast `DappSessionService.getDappSessions()` which *does* scope: `requireActiveProfile(...)` then `.filter(x => x.profileId === profile.id)` — `apps/extension/src/wallet/services/dapp-session/service.ts:61-66`.
6. **Missing control** — an active-profile guard (like `require-active-profile.ts` + a `profileId` filter) inside the journal read path, so a caller cannot read another profile's / another origin's records.
7. **Violation scenario** — if cluster 9 exposes (now or later) any journal read to the dApp channel, a connected dApp calls `getOperations()` (no filter) and enumerates every profile's transfer/dapp-execute history, including counterparties and amounts of other dApps and of UI-initiated transfers.
8. **Preconditions** — a non-popup (dApp/lower-trust) caller reaches these methods. Not satisfied by the current wiring (`initWalletSdkHandler` does not dispatch journal reads — trace exits this cluster at `apps/extension/src/wallet/runtime.ts:186`).
9. **Why mitigations fail** — the FSM/schema validation (`_loadValidated`, `OperationRecordSchema.safeParse`) protects integrity of each row, not *who* may read it. There is no authorization layer on reads.
10. **Instances** — `apps/extension/src/wallet/services/operation-journal/service.ts:375-379,381-394,406-417`.

## Notes — priority items checked and found clean (with reasoning)

- **`storage/migrate.ts` destructive wipe — no attacker path (clean).** The version gate reads `nulo:core:storage-version` from `chrome.storage.local` and wipes when `version !== CURRENT_VERSION` (`migrate.ts:107-151`). The only writer of that key is the extension itself (`migrate.ts:149`), and every entry in `KEYS_TO_WIPE` / `KEY_PREFIXES_TO_WIPE_*` is a hardcoded constant — **no dApp/attacker-controlled input reaches either the version value or the wipe lists** (no `externally_connectable`; content-script cannot write `chrome.storage.local`). "Crafted version → unintended wipe/skip" is not reachable. The wipe is in the *safe* direction (any non-`9` value re-wipes; a string/float/`undefined` fails `=== 9` and wipes). The profile store (`nulo:core:profiles`, `profile/repository.ts:24`) and `nulo:core:contacts@` are deliberately **not** in any wipe list, so the encrypted master secret survives migration. Robustness-only (not security): the session-storage and IndexedDB wipes swallow errors (`migrate.ts:132-134,145-147`) yet the version is still bumped (`:149`), so a partial wipe can persist — this can strand stale PXE/journal data from an old chain but is a correctness/availability issue, not a CIA violation by an attacker.

- **Strict-mode secret/bearer non-persistence — VERIFIED correct (high confidence).** The `Fr` master secret exists only in-memory on `ActiveSession.secret` and is never part of the persisted `Session` shape (`profile/spec.ts:31-63`). In strict mode `open()` computes `persistPasshash = passhash !== undefined && !this.strictSecurityMode` and writes `passhash: undefined` (`session-manager.ts:202-230`); default `strictSecurityMode = true` (`config/config.ts:18`). The three other persist paths — `refresh()` (`:256-275`), `applyTtlChange()` (`:507-548`), `clearPasshash()` (`:288-321`) — all persist the in-memory `activeSession.session` object, and the strict-ON toggle scrubs that in-memory `passhash` first (`onConfigUpdated` → `clearPasshash`, `:483-496,305-308`), so a subsequent `refresh` cannot re-leak it. `restore()` refuses any leftover bearer under strict mode (`:357-368`) and refuses a password session with no bearer (`:369-373`), so a strict session cannot be silently rehydrated with a persisted secret. `strictSecurityMode` is cached and updated race-free via `onConfigUpdated`. In non-strict mode the passhash IS persisted (documented, default-secure opt-out, AUDIT A1) but only to TRUSTED-context session storage — content scripts cannot read it (no `setAccessLevel`).

- **Secret material never reaches logs in this cluster (clean).** All session/profile log lines are constant string breadcrumbs or `getErrorMessage(error)` (`session-manager.ts:167,228,249,273,317-319,341-389`; `profile/service.ts:581,768`); grep across the cluster for secret-bearing variables passed to any log/console sink returns nothing. `passkey/service.ts:95` logs `credential.id` (a public identifier). (The residual *capability* to leak via the persisted log pipe is Finding [1].)

- **Session TTL / close / wrong-credential paths — clean.** TTL close is heavily serialized against `refresh`/`open` via the injected facade lock (`runExclusive`, `service.ts:113-120`) precisely to prevent a `refresh()` writeback from resurrecting an alarm-closed session; the alarm handler re-checks `deriveLockedAt` inside the lock (`session-manager.ts:563-591`). `restore()` maps TTL-expiry, missing-profile, and wrong-credential/corrupt-ciphertext all to `silentClose` (`:335-373`). `getSecret(profileId)` throws `"Profile locked"` unless the active session matches (`:178-184`); `exportEncrypted` mirrors that gate (`profile/service.ts:671-697`, AUDIT A2). `unlockProfile`/`unlockPasskeyProfile`/`exportPlain`/`restore` bind the recovered credential to the target profile before opening a session (`service.ts:240-246,371-373,723-741,981-984`).

- **`operation-journal` integrity — well-hardened.** Every mutator calls `validateParams(...Zod schema...)` (`service.ts:175,224,326,376,382,407,420`); `_loadValidated`/`_loadAllValidated` re-`safeParse` each row against `OperationRecordSchema` and drop+delete invalid rows (`:127-155`) — a good defense against tampered/forward-incompatible persisted rows feeding the FSM. IDs are 128-bit CSPRNG (`getRandomHex(16)`, `:183`; `getRandomHex` = `self.crypto.getRandomValues`, `packages/wallet-core/src/utils/random.ts:13-14`). FSM legality + "error iff failed" + kind↔txHash invariants are enforced (`:238-310`).

- **`config` service — popup-only; `setValue` lacks runtime validation (defense-in-depth only).** `ConfigService.setValue` (`config/service.ts:33-35`) → `ConfigStore.set` (`config/store.ts:28-40`) writes `this.config[key] = value` with no runtime key allow-list or value-type check (unlike the load path `apply()`, which type-guards at `store.ts:46-56`). A `__proto__` key or a wrong-typed security value (`strictSecurityMode`, `sessionTtl`) would corrupt config — but the config service is **not dApp-reachable** (port-RPC popup-only), so there is no untrusted actor, and `__proto__` assignment mutates only the local `Config` instance's prototype (not global `Object.prototype`) and is not re-persisted by the `Object.entries`-based `props` getter. Recommend runtime narrowing regardless.

- **`utils/offscreen.ts` supervision message trust — not page-reachable.** The SW-side listeners `onOffscreenReady` (`:47-55`) and `isOffscreenHealthy`'s `onPong` (`:73-97`) match bare string constants on `chrome.runtime.onMessage` with **no `sender` validation**. A spoofed `OFFSCREEN_READY`/`OFFSCREEN_PONG` would only degrade availability (SW believes a dead offscreen is healthy). Not reachable by a dApp page: web pages have no `chrome.runtime` access (no `externally_connectable`), and content.ts forwards only SDK-enveloped messages, not bare constants. Same reasoning clears the two `chrome.runtime.onMessage` listeners in `wallet/index.ts:35-47` (`nulo:open-toolbar-popup`). Worth adding a `sender.id === chrome.runtime.id` guard as defense-in-depth.

- **Cross-cluster handoffs (outside this cluster's remit):**
  - The port-RPC transport does **not** check `client.sender` on `onConnect` — only `client.name` (`packages/extension-messaging/src/background/service.ts:36-44`, **cluster 3**). This is the single control keeping the profile/config/journal RPC surface trusted; it is safe today only because of the no-`externally_connectable` + relay-is-sendMessage-only facts established above. If `externally_connectable` is ever added or the content script gains a port relay, every service in this cluster becomes directly dApp-invocable. Flagging for the cluster-3 auditor.
  - dApp scope enforcement in `DappInteractionService.validateSession` (`dapp-interaction/service.ts:346-435`) checks per-operation account/method/chain/scope against the `DappSession`, and `isConfirmationNeeded` (`:437-465`) forces a popup for fund-moving ops (fee-payer/`register_token`). The `sessionId → origin` binding itself is issued/enforced by the wallet-sdk dispatcher (cluster 9); `validateSession` trusts the supplied `sessionId` (a 256-bit token, `dapp-session/service.ts:132`). CAIP parsing is strict (`utils/caip.ts:28-42`) and cannot widen a scope match. The authwit/tx-construction sinks (`execution/dapp-send-executor.ts`) re-validate profile identity and use the account contract's own signing — trace into signing exits to cluster 6 (`@nulo/aztec-runtime`).
