Files read in full: `packages/extension-messaging/src/**/*.ts` (all non-test, 24 files); `apps/extension/src/core/adapters/*.ts`; `apps/extension/src/offscreen/{index.ts,is-benign-sw-disconnect.ts}`; `packages/aztec-runtime/src/offscreen/entry.ts`; `apps/extension/src/wallet/utils/offscreen.ts`; `apps/extension/src/wallet/index.ts`; `apps/extension/src/wallet/base/index.ts`; `apps/extension/src/wallet/runtime.ts`; `packages/wallet-core/src/base/{index,topology}.ts`; `packages/wallet-core/src/utils/{serialization,error-json,errors,lock,keyed-lock,rw-guard}.ts`; `apps/extension/src/wallet/services/pxe/{client.ts,shallow-port.ts}`; `packages/aztec-runtime/src/pxe/{client.ts,spec.ts,descriptors.ts}` + dispatch/provisioning sections of `service.ts`; `apps/extension/src/wallet/services/{logger,log-viewer}/{service.ts,spec.ts}`; `apps/extension/src/wallet/services/wallet-sdk/{content-message-relay.ts,content-script-validator.ts}`; `apps/extension/src/content-script/content.ts`; the vendored `@aztec/wallet-sdk` `content_script_connection_handler.ts`; plus `core/sender-auth.test.ts` and `core/hardening.test.ts` as behavior evidence.

Findings: 1. Non-findings: 12 (covering all 8 assigned questions plus the July-remediation regression check).

### F-1: `offscreen/client.ts`'s inbound message listener performs no sender authentication, unlike every sibling listener in the package

1. **Title**: Missing sender check on the SW-side offscreen `ServiceClient` listener (asymmetric with the package's own F-09 invariant).

2. **Impact factors**: If exploited, an attacker-controlled message could be delivered directly into the PXE `ServiceClient`'s response/event dispatch on the SW side, without the same-extension-but-not-content-script check (`isTrustedInternalSender`) that gates every other inbound listener in this package. Attack vector: local (`chrome.runtime.sendMessage`, no network). Attack complexity: low to construct the message shape; as analyzed below, exploitability today is bounded to near-zero because the two things needed to turn this into a working exploit are absent from the codebase's current usage of this transport. Privileges required: none beyond "can call `chrome.runtime.sendMessage()` and have it delivered to the extension's SW" — which, per the analysis below, is narrower than it first appears. User interaction: none.

3. **Evidence confidence**: moderate (the missing check is unambiguous and verified; the practical reachability is bounded by two independently-verified facts, not by a third-party behavior we could not check).

4. **OWASP / CWE mapping**: OWASP A01:2021 (Broken Access Control) / A04:2021 (Insecure Design — trust-boundary asymmetry); CWE-346 (Origin Validation Error), secondarily CWE-306 (Missing Authentication for Critical Function).

5. **Trace**:
   - Source: any code that can invoke `chrome.runtime.sendMessage(msg)` and have Chrome deliver it to the extension's service-worker context. This includes (a) any same-extension page (popup, onboarding, options, offscreen) — always true regardless of this bug — and (b) the extension's own content script (`apps/extension/src/content-script/content.ts:12`, `sendToBackground: (message) => chrome.runtime.sendMessage(message)`), which runs in **every** page (`all_frames: true`, `matches: ["*://*/*"]`) and is therefore reachable from any website's page-side JS via the upstream `@aztec/wallet-sdk` discovery/key-exchange/secure-message protocol.
   - `chrome.runtime.sendMessage` broadcasts to **every** `chrome.runtime.onMessage` listener registered anywhere in the same extension — including the content script's own listener (`content.ts:15`) and the SW-side `PxeServiceClientBase`'s listener, regardless of which listener the sender "intended."
   - Sink: `packages/extension-messaging/src/offscreen/client.ts:60` — `private readonly onMessageListener = (message) => { if (!message) return false; if (message.to === this.uid || (message.type === MessageType.Event && message.from === this.service && message.to === undefined)) { this.onMessage(message) } return false }`. **No `sender` parameter is even declared**, so no sender-identity check of any kind runs before this predicate. Contrast with the three siblings that all call `isTrustedInternalSender(sender)` first: `background/service.ts:45`, `offscreen/service.ts:41` (and the Port client at `background/client.ts:86` is implicitly scoped by Chrome, since the caller itself created that private Port).
   - If the routing predicate matches, `this.onMessage(message)` (`offscreen/client.ts:68`) runs, and for an `Event`-shaped message calls `BaseServiceClient.handleEvent(event, payload)` (`core/base-client.ts:230`), which invokes `(this)[event].invoke(payload)` for any property that is a live `EventHandler` and not in `reservedEventNames`.

6. **Missing control**: a sender-identity check (`isTrustedInternalSender(sender)`) before acting on an inbound message, mirroring `background/service.ts:45` and `offscreen/service.ts:41`. The routing checks that exist (`message.to === this.uid`, `message.from === this.service`) are correlation/addressing, not authentication — `this.service` is a public constant (`PXE_SERVICE_NAME = "pxe"`, `packages/aztec-runtime/src/pxe/spec.ts:31`) that costs an attacker nothing to know, and it is the ONLY guard on the `Event` branch (the `uid` is not required for events, only for responses).

7. **Exploit story** (as far as it can concretely be constructed today): a hostile dApp page would need its content-script relay to emit a message shaped `{ type: 1 /* MessageType.Event */, from: "pxe", to: undefined, content: { event: "<name>", payload: <attacker-chosen> } }` via `chrome.runtime.sendMessage`, hoping to invoke a live `EventHandler` on the SW's PXE `ServiceClient` with an attacker-chosen payload.

8. **Preconditions**: (a) the content script (or some other same-extension code) would have to forward a message that is NOT filtered out before delivery, and (b) the target `ServiceClient` would need a live `EventHandler` property whose name collides with the forged `event` value.

9. **Why the mitigations fail — and why exploitation is bounded today.** I verified both preconditions above are currently **not satisfiable**, which is why this is reported as a low/bounded finding rather than a critical one:
   - **(a) is closed by the upstream SDK, not by this repo.** I read the actual vendored `@aztec/wallet-sdk` source (`node_modules/.bun/@aztec+wallet-sdk@5.2.0.../src/extension/handlers/content_script_connection_handler.ts:122-125`): `handleBackgroundMessage = (message) => { if (message.origin !== MessageOrigin.BACKGROUND) return; ... }`. Every message the content script ever sends via `sendToBackground` is constructed by the SDK itself with a **fixed** `origin: MessageOrigin.CONTENT_SCRIPT` and a `type` drawn from a **closed, hardcoded** set (`DISCOVERY_REQUEST`, `KEY_EXCHANGE_REQUEST`, `DISCONNECT_REQUEST`, `PING`, `SECURE_MESSAGE` — see `content_script_connection_handler.ts:156-207`); the page's `postMessage` payload only ever becomes the `content` field, never the envelope's `type`/`origin`/`from`/`to`. A hostile dApp therefore cannot make the content script emit a message shaped like the offscreen-transport's `{type: Event, from: "pxe", ...}` envelope — this is a real, verified closure of the most concerning attack surface (a website reaching this listener), not a theoretical one.
   - **(b) is closed by the current service graph.** `PxeServiceClientBase extends ServiceClient<Methods>` (`packages/aztec-runtime/src/pxe/client.ts:82`) declares **no `TEvents`** (defaults to `Record<string, never>`), and neither it nor its extension subclass (`apps/extension/src/wallet/services/pxe/client.ts`) defines any `EventHandler`-typed field. Per the repo map, this `ServiceClient` (offscreen transport) is the **only** consumer of `@nulo/extension-messaging/offscreen` in the whole codebase. So `handleEvent`'s `!(handler instanceof EventHandler)` check (`core/base-client.ts:232`) fails for every possible `event` name today — a forged event message reaches the listener but has nothing live to invoke.
   - The **Response** branch (`message.to === this.uid`) is separately hard to forge: `uid` is `getRandomHex(8)` (`offscreen/client.ts:38`, CSPRNG, 32 bits), generated once per `ServiceClient` construction and never transmitted to a page-reachable context in cleartext outside the SW↔offscreen channel (which the content-script relay also cannot reach, per the same origin filter above).
   - What the missing check genuinely buys an attacker today: nothing beyond what an already-compromised same-extension page (popup/onboarding/offscreen XSS) could do anyway, since `isTrustedInternalSender` would pass for such a sender regardless. The asymmetry matters as **defense-in-depth debt**: if a future change adds a second offscreen-transport `ServiceClient` with real declared events (the architecture explicitly allows this — see `packages/extension-messaging/README.md`'s "no service logic in this package" framing, which invites new consumers), or if the upstream SDK's message construction ever changes to let page-supplied data leak into the envelope's top-level fields, this becomes directly exploitable from a hostile dApp with no other bug required.

10. **Instances**: `packages/extension-messaging/src/offscreen/client.ts:60` (the only instance; confirmed by grep that no other inbound listener in the package omits `isTrustedInternalSender`).

**Recommendation**: add `isTrustedInternalSender(sender)` as a first-line guard in `offscreen/client.ts`'s `onMessageListener`, exactly mirroring `offscreen/service.ts:41`, for symmetry with the documented F-09 invariant and to remove the "one bug away from exploitable" status described above. This is a small, contained fix with an existing test pattern to copy (`core/sender-auth.test.ts`).

## Non-findings

- **Q1 — other listeners in the package**: `background/service.ts:45` (Port `onConnect`) and `offscreen/service.ts:41` (offscreen `Service.onMessageListener`) both call `isTrustedInternalSender` before accepting a connection/message; `background/client.ts:86` (Port `onMessage`) needs no per-message check because a `chrome.runtime.Port` is a private bidirectional channel Chrome scopes to the two connecting endpoints — a third party cannot inject messages onto an existing Port. Verified via `core/sender-auth.test.ts` (explicit content-script/foreign-extension rejection tests) and `core/hardening.test.ts` (adversarial sweep, though scoped to the `background/` transport only, corroborating the repo-map's own "thin spot" callout).
- **Q1 — `wallet/index.ts:37-49` toolbar-popup opener has no sender check**: verified unreachable from a hostile dApp. `registerContentMessageRelay()` filters on `message.origin === "content-script"` before the SDK handler ever sees a message, and even messages that fall through are all `origin`/`type` values the SDK itself controls (see F-1 point 9). The literal string `"nulo:open-toolbar-popup"` this listener matches on is never a value the SDK's `InternalMessageType` enum produces, so no dApp-controlled path can reach it. Its only real caller is `apps/extension/src/onboarding/pages/done.vue:40`, an extension page.
- **Q2 — Firefox instance token (`wallet/utils/offscreen.ts`)**: minted via `crypto.randomUUID()` (CSPRNG) once per SW lifetime (`firefoxInstanceToken()`), embedded in the offscreen window's URL query string and broadcast in the clear via `chrome.runtime.sendMessage({type: OFFSCREEN_ADOPT_INSTANCE, token})` (`offscreen.ts:301`). `isSupersededByAdopt` (`offscreen.ts:71-81`) requires `sender.id === chrome.runtime.id && sender.tab === undefined` — this rejects foreign extensions (Chrome-enforced, unspoofable) and content-script senders (a content script's `sender.tab` is always defined for the tab it's injected into), matching `isTrustedInternalSender`'s practical effect for this purpose even though it's a separately hand-rolled check. A **compromised** same-extension page (not itself in a tab, e.g. the toolbar popup) could send a spoofed ADOPT with an arbitrary token, causing a live Firefox offscreen document to `window.close()` — but this requires an already-compromised extension page (no stronger than direct RPC abuse from that same context) and the worst case is a self-healing DoS: `ensureOffscreenRunning()` recreates the offscreen document on the next PXE call. Not flagged as a finding — bounded impact, and the precondition (compromised own-extension page) is already assumed catastrophic elsewhere.
- **Q3 — dynamic dispatch / prototype pollution**: `BaseService.invoke` (`core/base-service.ts:125-127`) is gated by the explicit `rpcMethods`/`frameworkRpcMethods` allowlist checked at `core/base-service.ts:94` before dispatch is ever attempted; `defineRpcMethods` (`core/rpc-methods.ts`) is a compile-time-checked, per-service hand-written set — `__proto__`/`constructor`/`toString`/`start`/`emit` etc. cannot be registered as callable names by construction, and `core/hardening.test.ts:116-125` exercises exactly this set against a live `Service` and confirms no response/invocation. `BaseServiceClient.handleEvent` (`core/base-client.ts:230-242`) requires the named property to be a live `EventHandler` instance AND not in `reservedEventNames` — `core/hardening.test.ts:67-77` and `:141-153` cover hostile event names and forged lifecycle events. `requestId` must be `Number.isSafeInteger(...) && > 0` (`core/base-service.ts:91-95`; tested `core/hardening.test.ts:108-114,170-176`). Params arity is capped at 256 (`utils.ts:1-3,34-48`; tested `utils.test.ts`, and `core/hardening.test.ts:178-186` for the sparse-object DoS case).
- **Q3 — per-port isolation**: responses are NOT cross-delivered between popup instances — `BaseService.handleRequest`'s `sendResponse` writes to the `ctx` (the originating `chrome.runtime.Port`) captured at request time (`core/base-service.ts:141-143`, `background/service.ts:81-83`), and a `Port` is a private, non-broadcastable channel. **Events ARE broadcast to every connected client** of a given `Service` (`background/service.ts:85-94`, looping over `this.clients`) — verified this is a deliberate application-wide-state-sync design (every open popup/onboarding/approval-window is the same trust domain — the current user's own wallet UI, not a multi-tenant boundary), not a cross-tenant leak. No per-profile/per-session event scoping was found in this cluster's files, but no evidence of a cross-USER or cross-ORIGIN boundary being crossed by it either.
- **Q4 — hostile-payload error reconstruction**: `remoteErrorFromResponseContent`/`walletErrorFromPayload` (`errors.ts:328-401`) only run against a response that already correlated to a **live, caller-issued** `requestId` in the `pending` map (`core/base-client.ts:194-199`, drops anything that doesn't match with a warn-log); a forged response for the Port transport is unreachable (Port is private per Q3), and for the offscreen transport requires knowledge of the unguessable per-instance `uid` (see F-1). So a hostile party cannot make an arbitrary in-flight call resolve as `UserRejectedError`/`JobCancelledError`/etc. it didn't itself trigger. Confirmed the `TOO_MANY_PENDING` code is deliberately absent from the reconstruction switch (`errors.ts:328-341`) — this is an existing, tested "BUG PIN" (`errors.test.ts:166-178`) with no security consequence (only affects `instanceof TooManyPendingError` UX/retry classification, not an authorization decision).
- **Q4 — envelope logging on failure**: `core/base-service.ts:114-116`'s failure log (`this.logDebug("Request failed", requestId, getErrorMessage(error))`) logs only the requestId and the error's flat message, never `params`. `core/base-client.ts`'s send-side log (`this.logDebug(`→ ${methodName}`)`) logs only the method name. The malformed-envelope paths that DO log a summary (`core/base-service.ts:96,102`; `core/base-client.ts:197`) route through `summarizeContent`/`summarizeMessage` (`core/envelope-summary.ts`), which never echoes `params`/`result`/`payload` and reduces any unvouched string (including the `method` name itself, since on a malformed request it's attacker-shaped) to `[unregistered:<length>]`. Telemetry (`offscreen/telemetry.ts`) enforces the same allowlist (`sanitizeTelemetry`, `:78-90`) and explicitly documents params/response/error.message as DISALLOWED.
- **Q4 — BigInt/Buffer/Map/Error serialization (`serialization.ts`)**: `jsonStringify`'s type-sniffing branches (`value.type === "Buffer"`, `instanceof Map/Set`, `instanceof Error`) operate on values already produced by trusted service code, not on attacker-supplied wire input being deserialized — there is no `JSON.parse`-then-type-coerce path here that an attacker controls the shape of in a way that causes anything beyond re-encoding their own data. The `Error` branch does include `stack` (`serialization.ts:39-49` via `baseErrorJson`), which is a real place a secret COULD leak if a service ever threw a raw `Error` with a sensitive value interpolated into its message (the stack's first line embeds the message) — but no such call site was found within this cluster's files; this is a per-service concern (subject to the extension-wide `log-payload-ban.test.ts` static scan) rather than a transport-layer defect, and is noted here for the record rather than flagged.
- **Q5 — store-key provisioning (`provisionChainStoreKey`)**: the 32-byte key crosses `chrome.runtime.sendMessage` base64-encoded as a normal offscreen-transport **Request**, addressed `to: "pxe"`. The receiving side (`offscreen/service.ts:41`) DOES gate on `isTrustedInternalSender`, so only a same-extension, non-content-script sender can have it dispatched — confirmed the content script's own SDK-level filter (`origin !== "background"` early-return, see F-1 point 9) also means the content script's `addBackgroundListener` callback silently drops this message before doing anything with it, closing the "does the content script leak the key to the page" concern I traced concretely. Server-side, `PxeService.provisionChainStoreKey` (`packages/aztec-runtime/src/pxe/service.ts:775-806`) is fenced by the per-profile incarnation lifecycle (`profileLifecycles` map): rejects while `deleting`, rejects a replay of an already-`deleted` generation, and rejects a live-under-different-generation swap — a stale or replayed provision cannot silently re-open a deleted/erased profile's store. This is a well-hardened, already-tested path (issue #281 D4, referenced throughout).
- **Q6 — boot order / dispatch against half-initialized state**: `BaseService.handleRequest` does not itself wait for `init()` to finish, but I verified (grep across all `apps/extension/src/wallet/services/*/service.ts`) that essentially every public RPC method body starts with `await this.ensureInitialized()` (~190 call sites across all ~20 services, including every security-sensitive one: `profile`, `account`, `auth-registry`, `dapp-session`, `execution`, `network`). `ensureInitialized()` (`core/initialization.ts:13-21`) polls until `this.initialized` flips true or throws after 30s — so a request that arrives in the narrow window between a Port `Service`'s constructor registering its listener and `services.start()` completing that service's `init()` blocks (or eventually times out) rather than executing against incomplete internal state. The migration gate itself (`runtime.ts:182-259`) runs and fails closed BEFORE any service is even constructed (`registerServices` at line 230 happens after the gate, config load, and Barretenberg init), so no RPC surface exists at all before migrations are resolved.
- **Q7 — lock/guard forgery via a hostile popup**: `LockTicket` is a runtime-unforgeable branded `symbol` minted only inside `Lock.dispatch()` (`lock.ts:137`) and never serialized across the RPC boundary; `Lock.leave(ticket)` and `ReadWriteGuard`'s reader tokens are pure in-process primitives with no RPC method that accepts a caller-supplied ticket/token. A same-extension popup can only influence locking by calling the RPC methods it's always authorized to call (e.g., triggering a legitimate profile delete that acquires a write barrier) — this is not a privilege escalation, since that popup already has that authority. No path found for one context to force-release or wedge a lock another context legitimately holds beyond the documented, bounded watchdogs (`MAX_HOLD_MS` = 5 min, `MAX_READER_DRAIN_MS` = 90 min), which are debuggability backstops, not attacker-triggerable primitives.
- **Q7 — unbounded ports**: `background/service.ts`'s `clients: chrome.runtime.Port[]` has no explicit cap, but every connecting Port must first pass `isTrustedInternalSender` — an attacker would need existing same-extension code-execution capability to open enough ports to matter, at which point simpler and more direct abuses are already available. Not flagged.
- **Q8 — logger `log` RPC**: `LoggerService.log` (`apps/extension/src/wallet/services/logger/service.ts:22-24`) is reachable only from a same-extension `LoggerServiceClient` (gated the same way as every other Port/offscreen service by F-09 at connect time); it forwards verbatim to `LoggerStore.logWithContext`, whose key-name-based redaction (`REDACTED_KEYS`/`trim()`) and its documented interpolated-string blind spot are pre-existing, already-documented project policy (CLAUDE.md "Logging policy") enforced by the extension-wide static scan `log-payload-ban.test.ts` — not a new gap introduced by this transport. No call site within this cluster's file set constructs a template-string log line embedding dApp- or page-influenced content; the transport itself (`envelope-summary.ts`, `telemetry.ts`) never forwards raw params/results into any log line (see Q4 above).
- **July remediation regression check (fix G)**: `isTrustedInternalSender` (F-09) is intact and correctly wired at both of its two intended call sites (`background/service.ts:45`, `offscreen/service.ts:41`); the Firefox instance-token mechanism (fix G's other half) is intact per the Q2 analysis above. F-1 is the one asymmetry found, on a THIRD listener that F-09 was apparently never extended to (whether this was a scoping decision in the original fix or an oversight was not determinable from this cluster's files alone — recommend cross-checking against `audit/security/2026-07-06-max/report.md`'s disposition of fix G before treating F-1 as newly introduced).

## Handoff edges followed

- `chrome.runtime.sendMessage` (content script, page-mediated) → `registerContentMessageRelay`'s listener (`content-message-relay.ts:79`) and, independently (Chrome fan-out), the offscreen `ServiceClient.onMessageListener` (`offscreen/client.ts:60`) — traced one hop into each target's handling logic (F-1).
- `chrome.runtime.onConnect` (Port open) → `Service.onConnect` (`background/service.ts:38`) → `isTrustedInternalSender` gate — traced to the gate's own predicate (`sender-auth.ts:17`).
- `BaseService.emit` → `sendEvent` (background: broadcast to `clients[]`; offscreen: single `chrome.runtime.sendMessage`) → the respective client's `handleEvent` — traced the offscreen leg fully (F-1); the background leg's fan-out confirmed non-issue (Q3 non-finding).
- `PxeServiceClientBase.request` → `BaseServiceClient.request` → `sendEnvelope` (`offscreen/client.ts:135-137`) → offscreen `Service.onMessageListener` (sender-gated) → `PxeService.provisionChainStoreKey` (Q5 trace).
- `ContentScriptConnectionHandler.handleBackgroundMessage` (vendored `@aztec/wallet-sdk`) — read one level into the dependency to settle F-1's and Q5's reachability questions concretely rather than leaving them speculative.

## Cross-rebuttal

**5. Net position (this cluster).**

- **ADOPTED-2**: `provisionChainStoreKey` store-key broadcast readable by any same-extension `onMessage` listener, `offscreen/client.ts:135`. Confidence: high.
- **ADOPTED-3**: READY/PONG lifecycle listeners (`offscreen.ts:97,170`) lack sender checks; DoS-bounded, self-healing. Confidence: moderate-high.
- Recommended fix, unified: add `isTrustedInternalSender` to `offscreen/client.ts`'s listener (closes F-1/F-3's action surface); stop broadcasting security-sensitive content (the store key) via untargeted `sendMessage` — scope via a private `chrome.runtime.Port` or an application-level MAC/nonce (closes F-2 and the response-forgery observability gap together, since both stem from the same broadcast primitive); route `Error` objects, not pre-flattened strings, through `trim()` at every PXE log call site.
