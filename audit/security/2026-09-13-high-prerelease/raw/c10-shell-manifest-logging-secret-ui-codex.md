### F-1: Shared WebAuthn RP lets compromised Nulo web origins reproduce passkey wallet keys

1. **Title:** Passkey-derived wallet secrets share the `nulo.sh` web-origin trust boundary.

2. **Impact factors:** Confidentiality of the selected passkey profile’s master secret and integrity of its derived accounts. An attacker can reproduce the master outside the extension and derive account signing material. The vector is remote execution of attacker-controlled JavaScript on an eligible Nulo web origin. Exploitation requires website/subdomain compromise and user interaction with a WebAuthn prompt, including biometric/PIN verification. It does not require extension permissions, the wallet password, or access to extension storage. Password profiles and other unselected passkeys are outside this attack’s demonstrated blast radius. Imported accounts additionally require their encrypted key material/DEK envelope.

3. **Evidence confidence:** **High** for the code and standards-based trust-boundary violation. Actual master derivation was reproduced with synthetic credential ID and PRF bytes; no physical-authenticator cross-origin exploit was run.

4. **OWASP / CWE mapping:** [OWASP A01:2025 — Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); [CWE-863 — Incorrect Authorization](https://cwe.mitre.org/data/definitions/863.html) and [CWE-200 — Exposure of Sensitive Information](https://cwe.mitre.org/data/definitions/200.html), both represented in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** The extension authorizes a shared RP in `apps/extension/src/wallet/services/passkey/spec.ts:21` (`nulo.sh`). `apps/extension/src/wallet/utils/passkey-ceremony.ts:50` creates discoverable credentials for that RP; `:59` requires residency. `:35` computes the PRF input from the public label defined in `packages/wallet-crypto/src/constants.ts:10`; `:73` and `:76` request the same RP and PRF input during authentication. `:132` and `:133` extract the credential ID and PRF output. Those two values are sufficient for `packages/wallet-crypto/src/passkey-credential.ts:49`: credential ID contributes only public salt material at `:53`, PRF becomes the HKDF input at `:56`, and `deriveMasterSecret` produces the wallet master at `:79`–`:92`. There is no additional extension-exclusive secret in that derivation.

6. **Missing control:** The RP can release wallet-master-equivalent PRF material to ordinary web origins. The derivation has no additional secret unavailable to those origins. WebAuthn permits an HTTPS origin to request an RP ID equal to its domain or an eligible parent domain; the PRF belongs to the selected credential, rather than being independently separated by each invoking origin. Therefore `https://nulo.sh` and eligible subdomains can request this credential with `rpId: "nulo.sh"`. See [WebAuthn RP-ID rules](https://www.w3.org/TR/webauthn-3/#rp-id) and [PRF extension semantics](https://www.w3.org/TR/webauthn-3/#prf-extension).

7. **Exploit story or violation scenario:** An attacker obtains JavaScript execution on `https://nulo.sh` or an eligible HTTPS subdomain. The page presents a plausible Nulo authentication/recovery action and requests a discoverable credential using `rpId: "nulo.sh"` and the public Nulo PRF input. The user selects their Nulo credential and completes user verification. The malicious page receives the credential ID and PRF result, then applies the public HKDF/reduction procedure to reproduce the profile master offline. The extension’s session and transaction-approval machinery need not participate.

8. **Preconditions:** A PRF-capable passkey profile; control of an eligible RP web origin; access to the corresponding credential through the victim’s authenticator; and successful user verification. Mere website compromise without a completed ceremony does not silently reveal the secret.

9. **Why mitigations fail:** Random challenges protect authentication assertions but do not randomize this deterministic PRF result. User verification confirms the user’s presence/verification, not consent to disclose wallet signing authority. Wallet-side origin checks cannot prevent an eligible malicious page from deriving the key without contacting the wallet. Non-extractable HKDF keys and subsequent zeroization do not protect the PRF already returned to that page. `implementations-plan/passkey-e2e/PRF-NON-PORTABLE.md` describes CDP virtual-authenticator limitations; it does not establish real-authenticator isolation between origins sharing an RP. The manifest permission at `apps/extension/manifest/manifest.config.ts:20` does not itself grant websites access to extension APIs; this finding concerns WebAuthn secret release.

10. **Instances:** RP definition: `apps/extension/src/wallet/services/passkey/spec.ts:21`. Creation and authentication options: `apps/extension/src/wallet/utils/passkey-ceremony.ts:50`, `:64`, `:73`, `:76`. Both ceremony hosts use the shared dispatcher at `:146`. Master derivation: `packages/wallet-crypto/src/passkey-credential.ts:49`, `:73`; imported-key wrapping derivation: `:109`. Recovery consumes the same material in `apps/extension/src/wallet/services/profile/passkey-recovery-coordinator.ts:91`. These are one shared RP/key-derivation root cause.

### F-2: Production proving sends private witnesses to an unauthenticated loopback HTTP responder

1. **Title:** Automatic accelerator discovery trusts an unauthenticated local HTTP service with private circuit witnesses.

2. **Impact factors:** Confidentiality of private inputs/intermediate witness values for affected proving requests, plus proving availability. The attacker is a local unprivileged process, potentially another OS user sharing the network namespace, that can bind port `59833`. No extension access, root privileges, or wallet password is required. The user must initiate normal work that requires proving. Exposure is the submitted execution witness; it is not established that every request contains the master seed or every long-lived signing key. Acceptance of an invalid proof on-chain was **not** demonstrated.

3. **Evidence confidence:** **High.** Production factory wiring and the pinned SDK’s transport were traced. An in-memory test using the actual transport and mocked `fetch` accepted a synthetic HTTP health response and posted a synthetic proof-request body without authentication. No real witnesses or network services were used.

4. **OWASP / CWE mapping:** [OWASP A07:2025 — Authentication Failures](https://top10.owasp.org/2025/A07_2025-Authentication_Failures/); [CWE-306 — Missing Authentication for Critical Function](https://cwe.mitre.org/data/definitions/306.html) and [CWE-200](https://cwe.mitre.org/data/definitions/200.html), in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** Normal offscreen startup leaves the factory override unset in `apps/extension/src/offscreen/index.ts:100`–`:115`; `packages/aztec-runtime/src/pxe/service.ts:166` consequently selects `ProductionPxeFactory`. That factory constructs `AcceleratorProver` without requiring HTTPS or authenticated pairing at `packages/aztec-runtime/src/pxe/chain-runtime.ts:228`–`:229`, then supplies it to PXE at `:248`. The dependency is pinned to `5.2.0` in `apps/extension/package.json:31`. At that bounded handoff, `apps/extension/node_modules/@alejoamiras/aztec-accelerator/src/lib/accelerator-prover.ts:407` serializes private execution steps and `:426` posts them. `apps/extension/node_modules/@alejoamiras/aztec-accelerator/src/lib/accelerator-transport.ts:740`–`:758` sends the bytes with content type and Aztec-version headers, without authentication. The immediate witness serializer at `apps/extension/node_modules/@aztec/stdlib/src/kernel/private_kernel_prover_output.ts:60`–`:69` includes bytecode, serialized witness maps, verification keys and function names.

6. **Missing control:** The production adapter does not authenticate the local service before transmitting private proving material. Loopback addressing and a recognizable health response establish reachability/protocol compatibility, not server identity.

7. **Exploit story or violation scenario:** Before the legitimate accelerator is available, a malicious local process listens on `127.0.0.1:59833`. It answers health requests with `{"status":"ok","api_version":1}` and permits the browser request where necessary. The HTTPS endpoint is unavailable or fails validation. The wallet’s normal prover automatically selects the HTTP responder. When the user performs a transaction requiring proving, the wallet sends the serialized witness to the malicious process. That process can retain the private material and return an error, malformed proof, or delayed response. WASM fallback cannot undo the disclosure.

8. **Preconditions:** The attacker can bind the unprivileged loopback port; the legitimate service has not already occupied it; and HTTPS has not become mandatory through the SDK’s successful-HTTPS state. A proving request must occur. The legitimate accelerator need not be installed, because production autodetection is active by default.

9. **Why mitigations fail:** The SDK does prefer HTTPS on `59834` and prevents HTTP downgrade after a successful HTTPS association within that transport instance. This finding concerns **initial HTTP acceptance**, not a regression of that downgrade protection. Initial dual probing is at `accelerator-transport.ts:582`–`:605`, and HTTP can win after the HTTPS preference window at `:632`–`:677`. Health-shape checks at `:201` do not authenticate a responder. `accelerator-prover.ts:302`–`:330` also accepts a healthy response without `aztec_version`; a supplied version remains forgeable. There is no identity-bound nonce or authorization token on `/prove`. Response parsing and bounded reads limit malformed responses, but do not protect an already transmitted witness. Decoding at `accelerator-prover.ts:557`–`:576` does not itself establish cryptographic proof validity; no downstream invalid-proof acceptance is claimed.

10. **Instances:** Production defaults and endpoint configuration: `apps/extension/src/accelerator/config.ts:22`, `:26`; `apps/extension/src/offscreen/index.ts:100`; `packages/aztec-runtime/src/pxe/service.ts:166`; `packages/aztec-runtime/src/pxe/chain-runtime.ts:228`. The related onboarding status check trusts HTTP-reported availability at `apps/extension/src/onboarding/composables/useAcceleratorStatus.ts:38`–`:51`; it sends no witness itself but can display the spoofed service as available. Both are instances of unauthenticated local-service identification, rooted in the extension’s integration rather than a separate dependency finding.

### F-3: Flattened RPC errors bypass URL redaction and expose API credentials in logs

1. **Title:** RPC URLs retain embedded credentials when errors are converted to strings before logging.

2. **Impact factors:** Confidentiality of credentials embedded in RPC URL paths, query parameters or user information. The resulting credential can appear in the log buffer, console, developer-mode session retention, and exported CSV. The downstream impact depends on the credential’s API permissions, quota and billing authority. An ordinary network failure suffices; malicious node responses can also trigger the path. Disclosure to another party requires access to the diagnostics or the user exporting/sharing them. Automatic remote log exfiltration and arbitrary dApp access to the logger were not demonstrated.

3. **Evidence confidence:** **High.** An in-memory test used the actual production node adapter with mocked HTTP failure, then the actual redactor and CSV builder. A synthetic API key survived both the string-log path and CSV output. Passing the same failure as an `Error` object correctly removed the URL credentials.

4. **OWASP / CWE mapping:** [OWASP A01:2025 — Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); [CWE-200 — Exposure of Sensitive Information](https://cwe.mitre.org/data/definitions/200.html), in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** `packages/aztec-runtime/src/adapters/aztec-node-factory-adapter.ts:50`–`:55` passes the configured RPC URL to the production client and timeout transport. `packages/aztec-runtime/src/utils/fetch.ts:89` embeds the complete URL and node error message in an exception; network/timeout variants do likewise at `:76` and `:78`. The node-info consumer catches it at `apps/extension/src/wallet/services/network/service.ts:1003` and passes `getErrorMessage(error)` to the logger. `packages/wallet-core/src/utils/errors.ts:29` returns the raw message string. The logger receives that string through `packages/extension-messaging/src/core/base-service.ts:227`; `apps/extension/src/wallet/logger/store.ts:68` calls `trim`, whose primitive branch returns it unchanged at `apps/extension/src/wallet/logger/utils.ts:263`. The result enters the buffer and console at `store.ts:70`–`:73`, optionally session storage at `:117`, and CSV through `apps/extension/src/components/JsonViewer/logs-csv.ts:11`–`:25` and `LogsViewer.vue:141`–`:147`.

6. **Missing control:** Credential-bearing URLs are scrubbed in recognized `Error` objects and URL-named object properties, but not in arbitrary strings. Production error helpers erase precisely the type/key context on which that policy depends.

7. **Exploit story or violation scenario:** A user configures an RPC such as `https://rpc.example/v2/SYNTHETIC_API_KEY`. The server returns HTTP 401 with a JSON error, or the request times out. The transport constructs an error containing the full endpoint. Network probing logs its extracted message. The user exports logs for troubleshooting and supplies them to a recipient, revealing the API key. In the synthetic reproduction, `Error 401 from server https://rpc.example/v2/SYNTHETIC_API_KEY: synthetic quota rejection` retained the key after both redaction and CSV serialization.

8. **Preconditions:** A credential-bearing RPC URL, a failure containing that URL, and access to the resulting diagnostic material. Developer mode is required for retention across service-worker restarts, but not for the initial in-memory capture and console output. No debug-level setting is needed for the demonstrated error-level log.

9. **Why mitigations fail:** `projectError` scrubs URLs at `apps/extension/src/wallet/logger/utils.ts:169`, but never receives an `Error` in this path. Key-name redaction at `:252` cannot identify a bare message string. Log-count limits bound entries, not their sensitivity. The source-level policy in `apps/extension/src/utils/log-payload-ban.test.ts:19` and `:59` does not make arbitrary error strings safe. Developer-mode retention is an exposure limiter, not credential sanitization; memory capture and console printing already occurred.

10. **Instances:** The confirmed credential producer is `packages/aztec-runtime/src/utils/fetch.ts:76`, `:78`, `:89`; the demonstrated consumer is `apps/extension/src/wallet/services/network/service.ts:1003`; the shared deficient sink is `apps/extension/src/wallet/logger/utils.ts:263`, used by `store.ts:68`. Additional production consumers use the same flattening pattern: `apps/extension/src/wallet/services/execution/gas-balance-reader.ts:223`, `:229`; `apps/extension/src/wallet/services/note/service.ts:89`, `:103`, `:131`, `:155`, `:225`; `apps/extension/src/wallet/services/incoming-transfer/service.ts:1476`; and `apps/extension/src/wallet/services/account-state/service.ts:103`, `:145`, `:322`. Shared forwarding also strips error structure at `apps/extension/src/wallet/logger/console-forwarding.ts:19`, `apps/extension/src/offscreen/index.ts:63`, and `packages/extension-messaging/src/core/base-service.ts:115`; the execution UI does so at `apps/extension/src/popup/windows/execute/index.vue:146`, `:228`. These are shared redaction-bypass locations; sensitive URL reachability was reproduced for node probing, not independently for every error producer listed.

## Handoff edges followed

- **Passkey ceremony → credential materialization:** Followed the shared UI ceremony into `PasskeyCredential.create` and master/DEK-wrap derivation. Checked WebAuthn RP/PRF semantics and distinguished real credentials from the documented CDP virtual-authenticator limitation. The synthetic derivation check reproduced the same master from only credential ID and PRF bytes.

- **Offscreen bootstrap → production PXE → accelerator:** Followed the default factory selection and the immediate prover/transport/serialization handoff in pinned accelerator `5.2.0`. Dependency inspection was limited to establishing the owned integration’s behavior, not an independent dependency audit. Mocked transport verification demonstrated first-contact HTTP selection and an unauthenticated POST.

- **RPC failure → logger → export:** Followed the actual node adapter’s timeout/error transport into the network-service catch, then the logger’s redactor, retention and CSV export. Synthetic credential-bearing URL verification reproduced the leak without using real credentials.

- **Build constants → production imports → guard:** Followed the E2E configuration into runtime barriers, migration registration, token-seed replacement and price mapping. In-memory minification checked positive and negative marker behavior. A complete release build was not run, and no claim is made about an already published artifact.

- **UI sinks and window ownership:** Followed explorer builders into navigation sinks, secret copy helpers into clipboard writes, shared import inputs into their immediate rendering attributes, and approval creation into the window-close handler. No independent findings are assigned to excluded design-package or bridge-core bodies.

- **Execution limits:** No files were written, no local server was started, no real wallet secrets were used, and no browser/authenticator end-to-end exploit was executed.
