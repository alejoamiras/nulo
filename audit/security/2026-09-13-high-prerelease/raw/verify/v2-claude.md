### F-05 — Passkey wallet master is reproducible by any `nulo.sh`-eligible web origin

**Independent read (before reading the trace):**
- `apps/extension/src/wallet/utils/passkey-ceremony.ts:68-77` (`buildGetOptions`) builds `{rpId: RP_ID, extensions: {prf: {eval: {first: <SHA-256 digest>}}}}`; `RP_ID = "nulo.sh"` (`apps/extension/src/wallet/services/passkey/spec.ts:21`); the digest is `SHA-256(PASSKEY_PRF_LABEL)` (`passkey-ceremony.ts:33-36`) where `PASSKEY_PRF_LABEL = "nulo:profile:v1"` is a public, compile-time constant (`packages/wallet-crypto/src/constants.ts:9`).
- `packages/wallet-crypto/src/passkey-credential.ts:49-66` (`PasskeyCredential.create({id, prf})`) derives `baseKey` from `ikm = prf` alone; `salt = SHA-256("nulo:kdf:v1" ‖ credentialIdBytes)` — a function of the credential id, not the origin. `:73-92` (`deriveMasterSecret`) runs `HKDF-Expand(baseKey, salt, info="nulo:master:v1")` → 64-byte OKM → `Fr.fromBufferReduce` → master. **No origin, extension id, or any browser/install-bound value enters the derivation anywhere in this chain** — it is a pure function of `(credential id, PRF output)`.
- So the only question is whether an arbitrary web page can obtain the *same* `(credential id, PRF output)` pair the extension would. That is a platform (WebAuthn) question, not an extension-code question — see below.

**Verdict:** CONFIRMED.

**Strengthened trace:**
1. `apps/extension/src/wallet/services/passkey/spec.ts:21` — `RP_ID = "nulo.sh"` (the wallet's apex domain).
2. `packages/wallet-crypto/src/constants.ts:9` — `PASSKEY_PRF_LABEL = "nulo:profile:v1"` (public).
3. `apps/extension/src/wallet/utils/passkey-ceremony.ts:33-36,68-77` — `buildGetOptions()` → `navigator.credentials.get({publicKey:{rpId:"nulo.sh", extensions:{prf:{eval:{first: SHA256(label)}}}}})`.
4. **Platform gap:** per WebAuthn's RP-ID matching rule, an RP ID is valid for a calling origin iff the RP ID equals the origin's effective domain **or is a registrable-domain suffix of it**. I could not get a full-text fetch of the exact normative WebAuthn Level 3 clause (the W3C page is too large for the fetch tool's summarizer and returned "not found in excerpt" for the anchor-scoped sections), so I corroborated via two independent secondary sources instead of relying on model memory alone: MDN's `PublicKeyCredentialCreationOptions.rp` page states plainly that for an origin `login.example.com`, `example.com` is a *valid* RP ID (the parent apex), and explicitly: "a credential registered with RP ID `example.com` can be reused across `login.example.com`, `app.example.com`, and any other subdomain of `example.com`." The W3C's own PRF-extension explainer (`github.com/w3c/webauthn/blob/main/explainers/prf-extension.md`) states determinism directly ("the key will be constant for a given credential" for a given `eval.first`) and states the access-control rule explicitly: **"Access control is enforced based on RP ID and so origins that are authorised to get an assertion from a credential are also authorised to evaluate any PRFs."** Combining the two: since `nulo.sh` is the RP ID, *every* origin whose domain is `nulo.sh` or a subdomain of it is equally authorized to run the assertion ceremony and read the same deterministic PRF output for the same public `eval` input.
5. `packages/wallet-crypto/src/passkey-credential.ts:49-92` — that origin runs the identical, publicly-known HKDF chain and reproduces the master.
6. **Host inventory (grepped fresh, not taken from the finding):** first-party hosts that serve real application code today under `*.nulo.sh`:
   - `nulo.sh` — the landing app (`apps/landing/README.md:3,39`: "Marketing landing page for the wallet (nulo.sh)... Cloudflare Pages, from `main`"); manifest host permission `apps/extension/manifest/manifest.config.ts:20` is `https://nulo.sh/` (irrelevant to RP-ID eligibility, which is a browser/WebAuthn concept independent of the extension's own permissions).
   - `tools.nulo.sh` — the bridge/tools app, production build target (`apps/extension/src/popup/components/modules/send/fee-helpers.ts:215` default `FEE_JUICE_BRIDGE_URL`; `apps/tools/src/lib/network-targets.ts:103`).
   - `testnet.tools.nulo.sh` — the tools app's testnet build target (`apps/tools/src/lib/network-targets.ts:88`; `apps/tools/README.md:20,116`).
   - `CLAUDE.md:79` independently names the three live Cloudflare Pages projects: `nulo`, `nulo-tools-mainnet`, `nulo-tools-testnet` — i.e. exactly the three hosts above, confirmed as real deployed projects, not just URL strings in code.
   - `rpc.sandbox.nulo.sh` appears only as a default RPC-endpoint *value* in a form field (`apps/extension/src/popup/components/popups/NewNetworkPopup.vue:45`) — not evidenced as an application-code host.
   - `apps/playground` is a local/e2e-only test dApp (`apps/playground/README.md`) with no `nulo.sh` subdomain or CF Pages project found — not currently a live RP-eligible host.
   - The finding's own suggested mitigation subdomain, `passkey.nulo.sh`, does **not** exist anywhere in the codebase outside the audit document itself (grepped) — the fix has not been applied.
   So: at least 3 first-party, currently-live hosts (`nulo.sh`, `tools.nulo.sh`, `testnet.tools.nulo.sh`) are RP-eligible for the wallet's passkey credential today.

**Precondition, precisely:** script execution on one of those three origins (compromise, XSS, supply-chain, or a malicious/compromised deploy) **plus** one user-completed WebAuthn user-verification ceremony on that page (plausibly framed as "verify your Nulo wallet"). No extension code, CSP, or sender-guard is in the path — this is a bare browser API call from an unrelated page.

**Severity check:** Band High, confidence high(mechanism)/moderate(real-world) — matches the evidence exactly. I would not raise it (no zero-click / no-precondition path was found) nor lower it (the mechanism is fully spec-mandated, not a guess — my independent fetch of the PRF explainer's access-control sentence is the strongest single piece of corroboration here, since it states in as many words that RP-ID-sharing implies PRF-sharing). Keep as-is.

**Fix check:** The recommended fix (move `RP_ID` to a dedicated, application-code-free subdomain such as `passkey.nulo.sh`, update `check-rp-id.ts` + the manifest host permission) is the smallest safe change available — WebAuthn gives no way to scope an RP ID *narrower* than "this domain or any subdomain of it," so there is no cheaper code-only mitigation; the only material lever is which domain is chosen as `RP_ID`. Regression risk is exactly what the finding and the code's own comment (`spec.ts:6-9`, "Crypto-bound... changing this value invalidates every existing passkey credential") already state: this must happen before any real user creates a passkey wallet, or it bricks them — a one-way pre-production window, not an in-place patch. No existing in-repo pattern to mirror (this is an infra/domain decision, not a code idiom); `check-rp-id.ts`'s AST drift-scanner is the right place to also assert the new subdomain never appears as a `content_scripts` match or CF Pages project target, to keep it content-less going forward.

**Confidence:** high. The derivation chain was re-read from source end-to-end (not paraphrased from the finding), and the WebAuthn semantics were checked against two independently fetched external sources (MDN + the W3C PRF explainer) rather than asserted from training-data recall alone, per the task's ask. The host inventory was independently re-derived by grep against `CLAUDE.md` and each app's own README rather than trusted from the finding's Instances list.

### F-06 — Same-master sibling profiles share the dApp-session MAC key and can derive each other's PXE store key

**Independent read (before reading the trace):**
- `apps/extension/src/wallet/services/profile/service.ts:913-930` (`deriveDappSessionMacKey(profileId)`): `ikm = master secret bytes` fetched via `profileId` from the session manager; the HKDF call itself uses a **fixed** `salt = "nulo:dappsession-mac:salt:v1"` and **fixed** `info = "nulo:dappsession-mac:v1"` — `profileId` is used only to select *which stored secret* to read, it never enters the derivation's salt/info/AAD.
- `packages/wallet-crypto/src/pxe-store-key.ts:29-34` (`derivePxeStoreKey(master, profileId)`): `salt = "nulo:pxe-store-salt:" + profileId` (public, non-secret input), `ikm = master`.
- Both are therefore pure functions of `(secret bytes, public profile id)` with **no additional per-profile secret** (e.g. the profile's DEK) folded in. If two profiles hold byte-identical master secrets, both derivations collide for any given target profile id.
- `apps/extension/src/wallet/services/profile/service.ts:2004-2015` (`assertNotDuplicateWallet`): the "same master" precondition is not hypothetical — `allowDuplicate` is a supported, only-*warned* override that lets a second profile be created from the same recovery phrase (fingerprint clash detection is soft-bypassable by design).
- My independent read agrees with the finding's mechanism before comparing narratives.

I additionally wrote and ran a throwaway probe (never placed in the repo tree; lives under the session scratch dir) that:
- Imports the **real, shipped** `derivePxeStoreKey` directly from `packages/wallet-crypto/src/pxe-store-key.ts` (by absolute file path, to route around workspace package resolution from outside the repo — the imported code is unmodified repo source, not a rewrite).
- Reproduces `deriveDappSessionMacKey`'s exact WebCrypto call shape line-for-line from `profile/service.ts:917-930` (this one is a *reconstruction*, not an import — the method is private to `ProfileService` and needs the full session-manager/profile-repo stack to construct in isolation, so it isn't a standalone importable pure function like `derivePxeStoreKey` is).

Ran via `bun run <script>`, output:
```
=== F-06 probe: same-master sibling profiles A and B ===
PXE store key for B, computed starting from A's master, equals B's own PXE store key: true
PXE store key for B, from an UNRELATED master, differs from B's real key: true
MAC computed with A's derived key verifies under B's derived key (cross-verification): true
```
The middle line is a negative control (an unrelated master does *not* collide), ruling out the check being vacuously true / the functions being constant.

**Verdict:** CONFIRMED — both the MAC-key and PXE-store-key instances, one via direct execution of the shipped function, one via a faithful reconstruction of a private method's algorithm.

**Strengthened trace:**
- **(a) MAC forgery:** attacker already holds the shared master (sibling profile A, or raw `chrome.storage`/OPFS read access to A's in-memory-unlocked secret) → `profile/service.ts:917-930` reproduces B's exact non-extractable HMAC key (demonstrated byte-equal above) → attacker crafts a `SignableDappSession{profileId:"B", dappMetadata.url:<attacker origin>, accounts, capabilityGrants, ...}` → `integrity.ts` canonicalizes and the attacker HMAC-signs it with the shared key (`mac-storage.ts:30-34` shape) → when profile B is later unlocked and the row is read, `mac-storage.ts:85-104` (`verifyOrDrop`) calls `keyFor("B")`, gets the **same shared key**, and `verifyDappSession` returns true → the forged row is accepted as B's own legitimate session/grant. (The finding's downstream steps — `background.ts:647-650` auto-approving discovery, `dispatcher.ts` consuming the grants, and the `Transactions=5` capability ceiling at `dapp-interaction/service.ts:586-589` — I did not re-open independently this pass; I verified only the key-collision root cause, which is the load-bearing step.)
- **(b) PXE key:** shared master + B's public `profileId` → `pxe-store-key.ts:29-34` reproduces B's 32-byte OPFS ChaCha20 store key exactly (demonstrated above) → opens `pxe/<B>/<chain>`, including any imported-account privacy keys registered there. I did not independently re-open `packages/aztec-runtime/src/pxe/service.ts:388` this pass.
- **Existing control that stops short:** `packages/wallet-crypto/src/entropy-mac.ts:10-16` already solves *this exact* problem for the envelope-integrity MAC, and says so explicitly in its own comment: "KEYED BY `HKDF(master ‖ dek)`, not by the master alone: the threat model's attacker HOLDS the shared master (two profiles from one recovery phrase derive the same one), so a master-keyed tag is forgeable BY THEM." That comment is a verbatim admission of the exact attacker model F-06 exploits — it was simply never extended to `deriveDappSessionMacKey` or `derivePxeStoreKey`. `pxe-store-key.ts:15-16`'s own doc comment ("profiles also have distinct masters today") shows the omission was an unstated assumption, not a considered tradeoff.

**Severity check:** Band Medium — matches. The attacker precondition (already possesses the shared master — i.e., is a sibling-profile holder or has raw storage/OPFS read access) is a real but bounded privilege level; transaction confirmation is a separate, unaffected gate for fund movement. I'd keep Medium. One nuance: the PXE-store-key half, taken alone, grants direct offline decrypt of another profile's local privacy-key material with **no confirmation gate of any kind** (unlike the MAC-forgery half, which still has to pass through discovery/dispatch), so in isolation it's arguably the more serious of the two sub-findings — but it shares the same precondition ceiling, so the combined Medium band still holds.

**Fix check:** Smallest safe change is exactly the pattern already proven in `entropy-mac.ts` — fold the profile's DEK into the IKM (`ikm = master ‖ dek`) for both `deriveDappSessionMacKey` and `derivePxeStoreKey`. This is a genuinely existing, tested, key-vector-pinned in-repo idiom to mirror, which lowers regression risk considerably. The real regression risk is functional, not cryptographic: `pxe-store-key.ts`'s own comment shows the PXE-open code path was written assuming no DEK is needed, so every call site that opens a profile's PXE store (offscreen PXE lifecycle) would need to thread DEK availability through, and a locked/DEK-less session's PXE-store behavior needs an explicit product decision (the finding's own suggested fallback — refuse to open — is reasonable but is a behavior change, not just a key-derivation change). Pre-production, so no migration is required (consistent with this repo's "no migrations pre-production" rule in `CLAUDE.md`).

**Confidence:** high. Reproduced empirically: one derivation via direct execution of the actual shipped function, the other via a byte-for-byte reconstruction of a private method's documented algorithm (flagged as such, not overstated as a live import). The "same master is a supported state" precondition was independently confirmed as a real, shipped feature (`allowDuplicate`) rather than assumed.

### F-07 — Auth-registry rows carry no profile/chain provenance: address-only purge, sync-delete and read

**Independent read (before reading the trace):**
- `apps/extension/src/wallet/services/auth-registry/spec.ts:24-40` — the `Authwit` type is `{id, account, hash, content, pending?, txHash?}`. No `profileId`, no `chainId` field, confirmed by direct read of the type.
- `service.ts:132-134` (`getAuthwits(account)`) filters the single flat store by `account` only; the UI calls it with just an address (`apps/extension/src/popup/pages/settings/advanced/account-state/authwits/index.vue:47`, and the component's own list-filter at `:55` is address-only too, `aw.account === appStore.account?.address`) — no profile dimension anywhere in the read path.
- `service.ts:97-99`: `accountService.onAccountDeleted.add(account => purgeForAccounts([account.address]))` — this listener is registered once, globally, for the shared `AccountService` instance; it is not parameterized by which profile the deletion happened in.
- `service.ts:428-448` (`purgeForAccounts`): deletes every row (and the enabled-flag) matching `account ∈ addresses` from the single flat `AUTH_REGISTRY_STORAGE_ROOT`, with **no profile or chain predicate anywhere in the function**.
- `profile-deletion/coordinator.ts:119-121` (re-read at those exact line numbers): `txs.purgeForAccounts(s.addresses, profileId)` (119) and `balances.purgeForTokens(s.tokenIds, profileId)` (121) both pass `profileId`; `auth.purgeForAccounts(s.addresses)` (120) does not — a direct, in-context asymmetry, confirmed at the exact cited line numbers.
- `account/service.ts:835-855` (`reconcileImportedAccounts(profileId)`): finds the *calling profile's own* keyless `Imported` rows, deletes them from storage, and emits the same global `onAccountDeleted` — called unconditionally from `useFullBackupImport.ts:534`, which I traced to run against a **brand-new profile created by the restore flow itself** (`useFullBackupImport.ts:495-534`), before "late activation."
- `account/service.ts:689`: the restore path's own duplicate-guard collides on the full `(profileId, chainId, address)` tuple — meaning the codebase explicitly tolerates (does not reject) the same address existing as a live account in a *different* profile. This is an important independent finding on my part: it means "another profile P1 legitimately holds address A" is a normal, accepted, *designed-for* state, not a contrived edge case — which makes the cross-profile purge in step 5 below concretely reachable in ordinary use (same-phrase multi-profile setups, common per F-06's own precondition), not just via a hostile backup.

My independent read agrees with the finding before comparing narratives.

**Verdict:** CONFIRMED — all three sub-instances (address-only cross-profile read; hostile-backup-triggered cross-profile purge cascade; cross-network sync-delete).

**Strengthened trace (hostile-backup instance — the lowest-precondition of the three, requires no sibling profile at all):**
1. Victim imports a crafted full backup containing an `Account` row `{type: Imported, address: A, profileId: <new>, chainId: c}` with no paired `imported-account-keys` entry for `(new, c, A)`.
2. `account/service.ts:680-720` (`restoreRows`): the collision check is scoped to the full `(profileId, chainId, address)` tuple (`:689`), so a freshly-generated `profileId` never collides — the row is accepted and persisted.
3. `useFullBackupImport.ts:534`, inside that same new profile's own restore flow, unconditionally calls `accountService.reconcileImportedAccounts(newProfile.id)`.
4. `account/service.ts:835-855`: the row is detected as keyless → deleted from the new profile's own storage → `this.emit("onAccountDeleted", {chainId:c, address:A})`, a **global**, un-profile-scoped event.
5. `auth-registry/service.ts:97-99` (the one listener registered for the shared `AccountService`) fires → `purgeForAccounts([A])`.
6. `auth-registry/service.ts:428-448` deletes **every** row in the one flat `nulo:core:auth-registry` root where `row.account === A` and clears the `A` status flag — including rows belonging to a completely different, untouched profile P1 that legitimately holds address `A` (a state the codebase's own restore logic treats as normal, per step 2's tuple-scoped, not address-scoped, collision check).

**Cross-network instance**, independently re-traced: `syncRegistry(networkId, account)` (`service.ts:299-309`) resolves the **caller-selected** network's node, then `syncAuthwits` (`:346-350`) loads `getAuthwits(account)` — i.e. every row for that address across **all** chains it was ever used on — and `syncAuthwit` (`:365-376`) deletes any row for which `isAuthwitConsumable` returns false against that possibly-wrong-chain node. A row genuinely live on chain A is deleted by a sync call scoped to chain B.

**Existing control that these paths bypass:** `spec.ts:19-21` states the design intent explicitly: tracked authwits are "NEVER auto-evicted — eviction would destroy the only local revocation index," because hashes aren't enumerable from chain (`service.ts:115-119`, cited by the finding). All three traced paths evict anyway, silently, outside that stated policy.

**Severity check:** Band Medium — matches. No on-chain grant is created or revoked; the damage is (i) destruction of the wallet's own already-fragile, non-rebuildable local revocation index for an uninvolved profile, and (ii) incidental cross-profile disclosure of intent metadata via the address-only read. I'd keep Medium, but flag a prioritization note: the hostile-backup path is the cheapest of the three to trigger (no sibling profile, no multi-network setup — just "import this backup file," a plausible social-engineering vector e.g. "try restoring from this file to fix your issue"), so if remediation has to be sequenced, that instance deserves to go first even though the overall band doesn't change.

**Fix check:** The smallest safe fix already has a template **in the same coordinator file, one call away**: `token-balance/service.ts:574` (`purgeForAccounts(scopes: {chainId, address}[], profileId)`) and `transaction/service.ts:301` (`purgeForAccounts(addresses, profileId?)`) both already carry a `profileId` parameter that `profile-deletion/coordinator.ts` passes at lines 119/121 — `auth-registry`'s `purgeForAccounts` (called unscoped at line 120) is the one outlier. Adding `profileId` (and `chainId`, per the finding) to `Authwit` and the status key, threading it through `getAuthwits`/`purgeForAccounts`/`syncAuthwits`, and having `reconcileImportedAccounts`'s purge-subscriber skip the auth-registry purge entirely (a never-keyed account has no local grants under *this* profile to begin with — the cleanest fix for the hostile-backup path specifically) is a contained change that mirrors an existing, already-reviewed idiom rather than inventing a new one. Regression risk is low: pre-production means no migration is required for the schema addition (every existing `Authwit` row simply lacks the new fields on a clean reinstall, consistent with this repo's stated pre-production storage policy).

**Confidence:** high. Every cited file:line was reproduced exactly as claimed, including the specific 119/120/121 contrast in `coordinator.ts` and the 835/534/689 trio across `account/service.ts` and `useFullBackupImport.ts`. The tuple-scoped collision check at `account/service.ts:689` was an independent addition on my part (not called out in the finding's own Instances list) that further strengthens the trace by showing same-address-different-profile is a designed-for, not merely theoretical, state.
