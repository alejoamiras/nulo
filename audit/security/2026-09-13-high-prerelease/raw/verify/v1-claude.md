### F-01 — Chain-identity check compares only the XOR composite

**Independent read (before reading the trace):** `packages/aztec-runtime/src/utils/chain-identity.ts:31-33` — `SelectedNetworkChainInfo` has one field, `chainId`. `chain-identity.ts:53-61` — `assertLiveChainIdentity(network, nodeInfo)` computes `liveComposite = (nodeInfo.l1ChainId ^ nodeInfo.rollupVersion) >>> 0` and throws only if `network.chainId !== liveComposite`; it never reads `network.l1ChainId`. The real `Network` type (`apps/extension/src/wallet/services/network/spec.ts:36-39`) *does* carry `l1ChainId` as a required field, and every call site passes the full `Network`/similar object — but TypeScript structural typing means the extra field is simply invisible to the function's own logic. So yes: the control gap exists exactly as claimed — the function that gates every signing/proving call cannot distinguish `(l1ChainId, rollupVersion)` pairs that XOR to the same composite.

**Verdict:** CONFIRMED

**Strengthened trace:**
- `packages/aztec-runtime/src/utils/chain-identity.ts:34-36` (interface has only `chainId`), `:53-61` (composite-only compare), `:69-71` (`chainInfoFrom` forwards the raw live `l1ChainId`/`rollupVersion` into the `ChainInfo` that gets signed).
- Arithmetic reproduced with `bun -e`:
  ```
  (1 ^ 4248422647) >>> 0  === 4248422646   // stored mainnet composite
  (2 ^ 4248422644) >>> 0  === 4248422646   // attacker-chosen collision — MATCHES
  ```
  Confirmed exact equality, both ways: `bun -e 'console.log((1^4248422647)>>>0, (2^4248422644)>>>0, ((1^4248422647)>>>0)===((2^4248422644)>>>0))'` → `4248422646 4248422646 true`.
- Callers: grepped every non-test call site of `assertLiveChainIdentity` (`service.ts:230,875`, `tx-request-builder.ts:221,407`, `dapp-send-executor.ts:854`, `fast-path.ts:179`, `discovery-probe.ts:74`, `view-executor.ts:211`, `authwit-discoverer.ts:109`, `helpers/batched-view-simulation.ts:204,362`). None pass or check `l1ChainId` in addition to the composite; all pass `network` straight from `networkService.getNetwork(...)`. Traced one fully: `service.ts:867-935` (`executeAztecCreateAuthWit`) — `network = await this.networkService.getNetwork(op.networkId)` → `nodeInfo = await node.getNodeInfo()` → `assertLiveChainIdentity(network, nodeInfo)` (passes under the collision) → `metadata = {chainId: Fr(nodeInfo.l1ChainId), version: Fr(nodeInfo.rollupVersion)}` (the attacker's raw `l1ChainId=2`, not the stored `1`) → `computeAuthWitMessageHash(intent, metadata)` → `account.createAuthWit(messageHash)`. The transaction arm is structurally identical via `chainInfoFrom(nodeInfo)` at `tx-request-builder.ts:221,286`.
- What existing controls DO cover: `network/service.ts:565-572` (`addEndpoint`) and `:612-618` (`updateEndpoint`) already require `probed.l1ChainId === network.l1ChainId` in addition to composite equality, with a comment naming this exact XOR-collision risk ("a different (l1ChainId, rollupVersion) pair can XOR to the same value, and l1ChainId feeds key derivation"). That discipline was never carried into `assertLiveChainIdentity`, the signing-time gate — confirmed by direct comparison of the two code paths.
- What is NOT covered: local networks (`chainId === 0`) skip the check entirely by design (`chain-identity.ts:54`), which is fine — the loopback URL allowlist is the substitute there, and not implicated by this finding.

**Severity check:** Band (High) matches the evidence. The gap is total — every signing/proving/authwit path is affected, with a fully reproduced collision on real production constants — but it does require a malicious/drifted RPC endpoint (the wallet's own trust boundary, not a remote unauthenticated attacker with no foothold), and no cross-chain fund-redemption was demonstrated here, which is the stated line between High and Critical in this report's rubric. Recommend: keep High. Note for the record: combined with F-04 (hostile backup installs an attacker-controlled "mainnet" RPC with no seed fallback), the RPC precondition becomes trivially attacker-supplied, which is worth flagging as a compounding risk even though each finding is independently scored.

**Fix check:** The recommended fix (extend `SelectedNetworkChainInfo` to `{chainId, l1ChainId}`, require `nodeInfo.l1ChainId === network.l1ChainId` in `assertLiveChainIdentity` in addition to the composite) is the smallest safe change — it's a single-function edit plus passing an already-in-scope field, no interface churn at call sites since they already pass the full `Network` object. It has a direct, already-shipped mirror to copy: `network/service.ts:565-572` / `:612-618` (`addEndpoint`/`updateEndpoint`), which do exactly this exact-equality check today, with the identical rationale comment. Regression risk: low — legitimate nodes report the true `l1ChainId` for the network they're on, so the tightened check only rejects the drift/collision case; the local-network carve-out is unaffected since it's an early return before the new check would run.

**Confidence:** high — arithmetic reproduced firsthand, every call site enumerated by grep and one traced end-to-end into the signed message hash, and the "control exists elsewhere but wasn't carried over" claim independently verified by reading both code paths side by side.

### F-02 — Approval popup renders only a subset of what is signed

**Independent read (before reading the trace):** `apps/extension/src/utils/transfer-intent.ts:22` — `KNOWN_TRANSFER_METHODS = {"transfer_in_private","transfer_in_public","transfer_to_private","transfer_to_public"}`, strict 3-arg check at `:72`. The wallet's own token-function descriptor table (`apps/extension/src/wallet/services/token/functions/descriptors.ts:349-356`) scores `"transfer_private_to_private"` at 102 and bare `"transfer"` at 101 — both *above* `"transfer_in_private"`'s 100 — meaning the wallet itself treats these as equally or more canonical names for the same private-transfer function, yet neither is in `KNOWN_TRANSFER_METHODS`. `OperationCard.vue:135` gates the structured From/To/Amount block on `parseTransferIntent(call).kind !== 'unverified'`; there is no `v-else` and no other branch renders anything for the unverified case — the comment at `:113-116` promises an "indexed-args fallback with an explicit marker" that does not exist in the template. Separately, `humanizeMethodName` (`tx-enrichment.ts:68-76`) reads from a *different* table, `METHOD_LABELS`, which maps both `"transfer"` and `"transfer_private_to_private"` to the confident label `"Transfer (private)"` (`tx-enrichment.ts:17,22`) — so the top-line label looks exactly as confident for the calls the amount/recipient panel silently drops. This is a real, reproducible gap, not a hypothetical: a token contract's plain `transfer(to, amount)` call is a completely ordinary, non-adversarial shape (it's the wallet's own 2-arg descriptor variant), and it renders with zero recipient/amount disclosure.

For the authwit branch: `OperationCard.vue:357-386` renders "Target contract" (`call.to`) and "Function" (`call.name`) for the call-intent case, or "Consumer contract" for the inner-hash case — `caller`, `call.args`, and `innerHash` are read nowhere in this block.

**Verdict:** CONFIRMED for (a) transfer-vocabulary drift and (b) authwit caller/args omission — both independently reproduced at the cited lines with no fallback/fallthrough anywhere in the template. (c) discovered-authwit non-disclosure is architecturally consistent with what I read (`discovery-probe.ts:73-90` and `fee-juice-strategy.ts:32-39` push discovered `add_private_authwit` actions into `ctx.op.actions`, while the popup's `aztec_sendTx` branch iterates only `op.exec.calls`, `OperationCard.vue:109`) but I did not fully trace how `op.actions` vs `op.exec.calls` reconcile for every call shape end-to-end; the consolidated report itself already treats this instance as resolved-for-disclosure-only (weaker than a/b), which matches what I could confirm.

**Strengthened trace:**
- dApp call `sendTx({calls:[{to: TOKEN, name: "transfer", args: [ATTACKER, AMOUNT]}]})` → `packages/wallet-bridge/src/dispatcher.ts` forwards `exec` raw (not independently re-verified this file, but consistent with the rest of the pipeline: nothing filters or rewrites `call.name`/`call.args` before the popup) → `OperationCard.vue:109` iterates `op.exec.calls` → `:126` renders `humanizeMethodName("transfer")` = `"Transfer (private)"` (`tx-enrichment.ts:17`) + target address only → `:135` `parseTransferIntent({name:"transfer", args:[...]})` → `"transfer"` not in `KNOWN_TRANSFER_METHODS` → `{kind:"unverified"}` (`transfer-intent.ts:64-66`) → no structured block, no warning → user approves → `tx-request-builder.ts:181-184` (`case "call"`) encodes `action.args` verbatim into the signed call, unaffected by what was or wasn't shown.
- Authwit: `executeAztecCreateAuthWit` (`service.ts:909-935`) hashes `caller`, the full `call` (including `args`), or the raw `innerHash`, and signs it — none of `caller`/`args`/`innerHash` appear in `OperationCard.vue`'s authwit branch.

**Severity check:** High matches. This is a full defeat of the "informed consent" popup for the single most common wallet operation, triggerable by an ordinary (non-malformed) token call — no cryptographic trick needed, just calling the contract's actual default function name. It stays below Critical under this report's rubric because a user click is still required (the click is what's being deceived, per the band rationale already given) — recommend keep High.

**Fix check:** The four-part fix is sound and appropriately scoped. (1) Deriving the recognized-name/arity set from `TOKEN_FN_DESCRIPTORS` instead of the hand-maintained `KNOWN_TRANSFER_METHODS` list removes the exact vocabulary drift I found (the descriptor table's own `score` functions already enumerate every real variant name) — smallest safe change, single source of truth, mirrors the pattern the descriptor table already establishes for scoring/disambiguation. (2) Implementing the promised-but-missing fallback branch is purely additive UI (no logic change) — low regression risk. (3) Showing `caller`/args/hash on the authwit card is additive to an existing template block. (4) Surfacing discovered authwits requires threading a new field through `dapp-send-executor.ts`'s return value — the largest of the four, correctly flagged as higher effort ("days") elsewhere in the finding.

**Confidence:** high for (a)/(b) — reproduced directly from source, both the omission and the specific METHOD_LABELS/KNOWN_TRANSFER_METHODS divergence. moderate for (c) — consistent with the code but not independently traced through the full estimate→popup data flow.

### F-03 — Hostile backup plants a non-canonical `PrivateFpc` row

**Independent read (before reading the trace):** `apps/extension/src/wallet/services/fpc/service.ts:503-524` (`restore`) rejects only unknown `fpc.type` values and validates shape via `StoredFpcSchema.parse` — there is no comparison against the canonical protocol address anywhere in this function. `getFpcs` (`fpc/service.ts:155-190`) computes `protocols = await this.getOrComputeProtocolAddresses(chainId)` and checks `hasPrivateFpc = result.some(f => f.type === PrivateFpc && f.address === protocols.private)`; a poisoned row at a different address makes this `false`, triggering discovery which `result.push()`es the genuine canonical row — appended AFTER the existing (poisoned) entries in the same array, confirmed by reading the push order directly. `fee-helpers.ts:157` (`buildFeeMethods`) does `registeredFpcs.find(f => f.type === FpcType.PrivateFpc)` — first match by `type` alone, `isProtocol` never read — so the poisoned row (first in array order) wins the "Private Fee Juice" slot and the genuine row is unreachable through this UI path. Separately, `account-state/service.ts`'s `precheckContractAddress` (`:441-456`) only special-cases addresses `0..6`; any other backup-supplied `{instance, artifact}` gets registered into PXE via `registerContract` with no authenticity check. `fpc/handlers/private-fpc-handler.ts:8-19` (`validateArtifact`) only requires the artifact to expose a zero-arg/zero-return `pay_fee` and a `balance_of` function — trivially satisfiable by attacker-authored Noir. This composes into exactly the claimed chain.

**Verdict:** CONFIRMED — reproduced end-to-end from source: no canonical-address check at restore, first-match type-only selection ignoring `isProtocol`, and an independent registration path (`account-state`) that can seat an attacker contract+artifact behind that same address with a minimal, easily-forged artifact shape.

**Strengthened trace:**
- `fpc/spec.ts:15-18` — `FpcType.PrivateFpc = 2`.
- `fpc/service.ts:503-524` — `restore()` writes `{type:2, address:X, ...}` after only a type-enum + zod-shape check; `StoredFpcSchema` (not independently re-read line-by-line, but the restore body itself performs no address comparison, confirmed).
- `fpc/service.ts:155-174` — `hasPrivateFpc` false for a wrong-address row → discovery runs → `fpc/service.ts:187` (`result.push(await this.registerAndStoreProtocolFpc(...))`) appends the genuine row after the poisoned one.
- `fee-helpers.ts:157` — `.find()` returns the poisoned row (first by insertion/array order); `:191-207` — enabled iff `gasBalances.privateFeeJuice` is non-zero for that (poisoned) row's address, read via `gas-balance-reader.ts:180-184` against `fpc.address` directly.
- `account-state/service.ts:444-456` (`precheckContractAddress`) — `addressNum >= 0 && addressNum <= 6 ? "protocol" : "register"` — anything outside 0-6 is registered unconditionally via `registerContract` (`:397-399`).
- `fpc/handlers/private-fpc-handler.ts:8-19` — artifact validation requires only `pay_fee()` (0 params/0 returns) and the presence of `balance_of` — no ownership, no address binding, no signature-of-authenticity check.
- `fpc-strategy.ts:101-106` → `getFpcImpl` (ownership-only) → `private-fpc-handler.ts:22-30` — `getFeePayload` builds `{kind:"call", contract: fpc.address, method:"pay_fee", args:[]}`, i.e., a call into the attacker's registered contract, prepended into the user's signed private transaction.
- Contrast confirmed directly: `fpc/service.ts:362-369` (`updateFpcAddress`) permanently forbids changing a `PrivateFpc` row's address at all — the code comment states "Custom-salt PrivateFPC instances aren't publicly deployed and the wallet bundles a single artifact version, so we cannot validate an arbitrary address as a PrivateFpc." This means the product's own design intent is that *every* legitimate `PrivateFpc` row is the canonical protocol address — there is no legitimate use case for a non-canonical one, which matters directly for the fix's regression risk (see below).

**Severity check:** High matches the stated rubric (hostile backup redirecting fee payment = High). This is arguably at the upper edge of High — it's a full confused-deputy: attacker Noir code executes inside the user's signed private transaction, and the genuine payer becomes practically unselectable through the UI — but it stops short of Critical because the precondition (importing a hostile/tampered backup) is user-mediated and actual fund drain depends on what the attacker's `pay_fee` implementation does, which isn't demonstrated here. Recommend: keep High.

**Fix check:** Both parts of the recommended fix are the smallest safe change and each has a direct existing mirror. (1) Rejecting any restored `PrivateFpc`/`DefaultSponsoredFpc` row whose address doesn't match `getOrComputeProtocolAddresses` mirrors the *already-shipped* permanent-rejection logic in `updateFpcAddress` (`fpc/service.ts:362-369`) — same product invariant, just enforced at a second entry point that currently lacks it. Given that invariant already means "no legitimate non-canonical PrivateFpc row can ever exist," this fix has effectively zero regression risk for real users. (2) Selecting by `f.type === PrivateFpc && f.isProtocol === true` in `fee-helpers.ts`/`gas-balance-reader.ts` reuses a signal already computed and consumed elsewhere (`fpc-strategy.ts:115`, confirmed to exist in the codebase), so it's a drop-in predicate change, not new logic.

**Confidence:** high — every step in the chain (restore, discovery-append-order, first-match selection, PXE registration bypass, artifact-validation weakness, fee-payload construction) was independently read from source and composes exactly as claimed, and the "no legitimate non-canonical row" invariant was independently found (not merely quoted from the finding) in the live-edit code path, which strengthens rather than merely matches the recommended fix's safety.

### F-04 — Hostile backup mints a `kind:"mainnet"` network row bound to an attacker RPC

**Independent read (before reading the trace):** `network/service.ts:1046-1059` (`validateRestoredNetwork`) does exactly three things: a legacy-shape gate, `NetworkSchema.safeParse`, and a `(profileId, chainId)` collision check against existing rows. It never calls `assertCanonicalStoredL1` (`:346-355`, which exists and does check a seeded kind's `l1ChainId` against an in-code constant) and never probes the endpoint. `NetworkSchema` (`network/spec.ts:172-180`) accepts `kind: ChainKindSchema.optional()` as a free label with no cross-check against the endpoint, and `RpcUrlSchema` (`spec.ts:152-179`) allows `https:` for *any* host — so `{kind:"mainnet", l1ChainId:1, endpoints:[{rpcUrl:"https://attacker.example"}]}` passes validation cleanly. Separately, `getOrInitNetworks` (`network/service.ts:238-240`) returns early with `existing` the moment `existing.length` is truthy for the profile — i.e., a single restored row (hostile or not) unconditionally suppresses `DEFAULT_SEEDS` for that profile. Both claims check out exactly as described.

**Verdict:** CONFIRMED, with the same qualification the consolidated report itself already applies: the exploit as stated ("crafted `data.network[]]`" from an attacker-authored backup) glosses over how the attacker gets the *victim's* real account addresses to show up — `useFullBackupImport.ts:474` (`restoreProfileStep`) derives the new profile from `secretOut.restoreSecret`, which comes from the imported backup's own master-key material (`useFullBackupImport.ts:463,469`). An attacker-authored-from-scratch backup restores the *attacker's own* keys, not the victim's — so the "indistinguishable in the UI, same real addresses" framing only holds for a backup that is a doctored copy of the *victim's own* backup (master key intact, `network`/other rows modified), not an arbitrary attacker-crafted file. The consolidated report's own cross-model resolution already states this ("Codex's objection is correct on one exploit step... but does not touch the mechanism") — my independent read reaches the same correction, from the same code, without having relied on the report's wording for it.

**Strengthened trace:**
- `network/service.ts:1046-1059` — `validateRestoredNetwork`: shape → `NetworkSchema.safeParse` → `(profileId, chainId)` collision only. No call to `assertCanonicalStoredL1` (`:346`) or any live probe.
- `network/spec.ts:172-180` — `NetworkSchema` accepts `kind` as an optional free enum; `spec.ts:152-179` — `RpcUrlSchema` accepts any `https:` host.
- `network/service.ts:99-126` — `DEFAULT_SEEDS` includes the genuine `{name:"Alpha V5", kind:"mainnet", rpcUrl:"https://lb.drpc.live/...", l1ChainId: MAINNET_L1_CHAIN_ID}` — confirming a forged row really can mimic the seed's `kind`/`l1ChainId` fields while swapping only the endpoint.
- `network/service.ts:238-240` — `getOrInitNetworks`: `if (existing.length) return existing` — no per-kind backfill, all-or-nothing seeding.
- Entry path: `useFullBackupImport.ts:474` (`restoreProfileStep`, keyed off the backup's own `restoreSecret`) → `:485` (`normalizeAllIds(data, "profileId", newProfile.id)`, unconditional remap — read directly, matches the finding) → `:487-488` restore-networks stage → `network/service.ts:860-897` (`restore`) — independently confirmed: `candidate = validateRestoredNetwork(raw, existing)` (`:884`) → `stored = {...candidate, id}` → `await this.storage.set(id, stored)` (`:888`), with no canonical/probe check anywhere in `restore()` itself either — the gap is confirmed at both the helper and its only caller.
- Downstream: `networkInfoFrom(network).rpcUrl` (`spec.ts:91-95`) is exactly the attacker URL, and every subsequent `getNode`/`createNode` for that chain talks to it.

**Severity check:** High matches. Persistent, silent RPC-level MITM of a restored profile's mainnet traffic (balances, fee quotes, simulation, broadcast) is squarely in the "hostile backup redirects RPC" High band already defined by the report's rubric. The corrected precondition (doctored copy of the victim's *own* backup, or a backup the victim is otherwise induced to import and fund into) is narrower than "any attacker-crafted backup" but is still a realistic social-engineering / backup-handling threat model, not a stretch — recommend keep High, on the corrected precondition.

**Fix check:** The recommended fix — reject/relabel a restored row whose `kind` is a seeded kind unless its primary endpoint equals the in-code seed URL, and change `getOrInitNetworks` to backfill missing seeds per-kind rather than all-or-nothing — is minimal and has a direct existing mirror to build from: `assertCanonicalStoredL1` (`:346-355`) already does the "seeded kind ⇒ must match the in-code constant" comparison for `l1ChainId`; the same pattern (compare against `DEFAULT_SEEDS` by `kind`) extends naturally to the endpoint URL. Regression risk: low for the URL-pinning half (a genuine seeded-kind row from a real backup already uses the seed URL, by construction); the per-kind seed backfill in `getOrInitNetworks` needs care not to duplicate/collide with a legitimately-added custom network on the same `chainId` — worth a colocated test for "restore one hostile mainnet row into an empty profile, confirm Testnet/Local still seed."

**Confidence:** high on the mechanism (validation gap, seed suppression, URL allowlist scope) — all independently reproduced from source; moderate-to-high on the exploit's exact precondition, since I independently derived (rather than merely accepted) the "must be the victim's own backup, not an attacker-authored one" correction from `useFullBackupImport.ts`, matching the report's own resolution.
