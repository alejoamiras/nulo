### F-09 — Production prover accepts an unauthenticated loopback HTTP accelerator and posts the private witness to it

**Independent read (before reading the trace):**
- `apps/extension/src/accelerator/config.ts:22-24` fixes the accelerator at `127.0.0.1:59833`, health URL is plain `http://`.
- `packages/aztec-runtime/src/pxe/service.ts:166`: `new ChainRuntimeRegistry(factory ?? new ProductionPxeFactory())` — production path with no factory override at all.
- `packages/aztec-runtime/src/pxe/chain-runtime.ts:129-138`: `ProductionPxeFactory` constructor stores `this.host = options?.host`, `this.port = options?.port`, both `undefined` when constructed with no options (the production case above).
- `chain-runtime.ts:228-229`: `const accelerator = this.host !== undefined || this.port !== undefined ? {host,port} : undefined` → `undefined` in production; `new AcceleratorProver({simulator, onPhase, accelerator})` at `:229` (non-required branch, `onPhase` also `undefined`).
- SDK `AcceleratorTransport` constructor (`accelerator-transport.ts:368-380`): `httpsOnly = false` default parameter.
- `AcceleratorProver` constructor (`accelerator-prover.ts:96-149`): with `opts.accelerator` undefined, `httpsOnly` resolves to `httpsOnly ?? (envHttpsOnly === "1" || ...)`; `process.env` is not meaningfully populated in the offscreen-document/browser context, so this resolves to `false`.
- `#effectiveHttpsOnly` (`accelerator-transport.ts:455-457`) = `httpsOnly || !allowsHttpDowngrade`; `allowsHttpDowngrade` (`:477-480`) is `true` until an HTTPS endpoint has ever answered healthy at this endpoint (`#httpsWasHealthy` starts `false`). So on a fresh run, `effectiveHttpsOnly === false` and `probeHealth()` (`:582-606`) fires **both** an HTTPS and an HTTP probe (`#probePreferHttps`).
- `isRecognizedHealthBody` (`:201-205`) is a pure JSON-shape check (`status:"ok"`, `api_version:1`) — no signature, token, or credential.
- `#probePreferHttps` (`:632-690`): a healthy HTTP response wins after `HTTPS_GRACE_MS` if HTTPS hasn't answered healthy by then, or immediately if HTTPS never answers.
- `postProve` (`:740-758`): `POST {baseUrl}/prove` with only `content-type` and an optional `x-aztec-version` header — no `Authorization`, no shared secret, no mTLS.

**Verdict: CONFIRMED.** Every step of the claimed mechanism is present in the current tree exactly as cited: the extension never sets `httpsOnly` (nor any accelerator options at all) in production, the SDK's own default is insecure, health is a shape check not an authentication check, and `/prove` carries no credential. A process that binds `127.0.0.1:59833` and answers `{status:"ok", api_version:1}` before (or in place of) the genuine accelerator app wins the probe and receives the full serialized `PrivateExecutionStep[]` for the next proof.

**Strengthened trace:**
1. `offscreen/index.ts:100-116` → production build takes the `else` branch, `factory: undefined`.
2. `packages/aztec-runtime/src/pxe/service.ts:166` → `new ProductionPxeFactory()` (no args).
3. `chain-runtime.ts:129-138` → `host`/`port` both `undefined`.
4. `chain-runtime.ts:228-229` → `accelerator: undefined`; `new AcceleratorProver({simulator, onPhase: undefined, accelerator: undefined})`.
5. `accelerator-prover.ts:96-149` → `resolvedHttpsOnly = false` (no option, no env var reachable in-browser); `new AcceleratorTransport(host, port, httpsPort, false, false)`.
6. First `probeHealth()` call (from `checkAcceleratorStatus`/first `proveTx`) → `accelerator-transport.ts:599-606` → dual HTTP+HTTPS probe (since `#effectiveHttpsOnly === false`).
7. A squatter process bound to `127.0.0.1:59833` (no HTTPS listener needed) answers `/health` with the two-field JSON body → `#isHealthy` (`:619-621`) is `true` → wins per `#probePreferHttps` (`:663-677`) once the grace window elapses (or instantly if the real HTTPS accelerator isn't running).
8. `accelerator-prover.ts:407,426` serializes the `PrivateExecutionStep[]` and calls `postProve` → `accelerator-transport.ts:745-758` POSTs to `http://127.0.0.1:59833/prove` with no auth header.

**Precondition, precisely:** an unprivileged local process (could be another OS user on a shared host, or any other app on the user's own machine) binds TCP `127.0.0.1:59833` and serves the two-field JSON health body, before or in place of the genuine Aztec Accelerator app. No browser or extension compromise is required — this is a same-host squatting attack, not a web attack.

**Severity check:** Medium is right; **keep**. Confidentiality-only (serialized private execution steps: note preimages, app-siloed nullifier secrets, private circuit inputs — not shown to carry the master/signing key), reachable by any co-resident unprivileged process with zero user interaction and no browser compromise, and it's not gated behind an opt-in (every production build probes this fixed port). That combination (no privilege needed, zero interaction, but confidentiality-only and requiring local co-residency rather than remote/web reach) sits squarely at Medium — CWE-306/200 with a local-only attacker is the textbook Medium case, not High (no remote reach, no fund loss, no signature material shown to leak) and not Low (real per-transaction exposure, not a hardening nice-to-have).

**Fix check:** The recommended fix (construct with `httpsOnly: true`) is the smallest safe change, but it is not yet wireable as a one-line edit: `AcceleratorEndpoint` (`chain-runtime.ts:22-25`) only has `host?`/`port?` — no `httpsOnly` field — so the fix is (a) add `httpsOnly?: boolean` to `AcceleratorEndpoint`, (b) thread it into the `accelerator` object built at `chain-runtime.ts:228`. This mirrors an **already-existing** SDK-native knob exactly — `AcceleratorTransport`'s own `httpsOnly` constructor parameter (`accelerator-transport.ts:372`) and its env-var equivalent `AZTEC_ACCELERATOR_HTTPS_ONLY` (`accelerator-prover.ts:122-123,137-138`) — so no new pattern is introduced, only a missing pass-through is added. Regression risk: any user relying on an HTTP-only build of the desktop accelerator app falls back to WASM (slower proving, no silent failure) — stated by the finding as equivalent to today's no-accelerator UX, which is accurate given `onPhase`'s `"fallback"` handling is only enforced in CI (`required`) mode; production silently accepts the WASM fallback either way. This is a real but acceptable regression, not a functional break.

**Confidence:** high — every link in the chain (config defaults, class construction, SDK defaults, dual-probe logic, health-shape check, unauthenticated POST) was read directly in this tree, not inferred.

### F-18 — Discovery flood caps skip the existing-session and duplicate-waiter branches; every reconnect handshake opens an uncapped verify window

**Independent read (before reading the trace):**
- `background.ts:619-678` (`handleDiscovery`): after resolving `chainId`, it awaits `tryGetDappSessionByOriginAndChain` (`:647`). If a session exists: `autoApproveExistingSession(...)` then `return` (`:648-650`) — this happens **before** `checkDiscoveryPopupCaps` is ever reached (that call sits at `:670`, syntactically unreachable on this branch since the function already returned).
- If no session but a popup is already pending for the same `(origin, chainId)` dedupe key (`:663-668`): `awaitPendingPopupDedupe(...)` then `return` — again before `:670`.
- `checkDiscoveryPopupCaps` (`:748-761`) counts only `pendingDiscoveryPromises` keys (per-origin prefix match + global size) — it is called from exactly one place, `:670`, which only the **fresh, no-existing-session, no-pending-popup** branch reaches.
- `session-established.ts:143-154`: `needsVerification = isNewConnection || !dappSession.trustedVerification`; if true, `chrome.windows.create(...)` runs unconditionally — no count, no per-origin tracking, no check for an already-open verify window for the same session/origin.
- `dapp-session/spec.ts:56,87`: `trustedVerification?: boolean` is optional and absent by default.
- `popup/windows/verify/index.vue:71-75` (`handleConfirm`): `trustedVerification` is set to `true` **only** if the user ticks "always trust" (`alwaysTrust.value`) and confirms; otherwise it stays unset.
- For the auto-approved existing-session path, no `pendingVerification` marker is set anywhere in `autoApproveExistingSession` (`:701-709`), so `isNewConnection` is `false` in `handleSessionEstablished` — meaning the ONLY gate on repeated verify windows for a remembered origin is `!dappSession.trustedVerification`, which stays `true` (needs verification) for every origin the user never ticked the checkbox for.

**Verdict: CONFIRMED (both halves as banded).** `checkDiscoveryPopupCaps` is provably unreachable on the existing-session auto-approve branch (an early `return` at `:650` precedes the only call site at `:670`) and on the duplicate-waiter branch (`return` at `:668`). The verify window at `session-established.ts:145` has no cap, coalescing, or rate limit of any kind — it fires once per completed handshake, unconditionally, whenever `trustedVerification` is unset (the default for every session the user hasn't explicitly marked "always trust").

**Strengthened trace (window half, the high-confidence half):**
1. Attacker-controlled or ordinary page at an already-connected origin repeats the wallet-sdk discovery handshake with a fresh `requestId` (the dApp/page fully controls this; nothing server-side prevents re-running discovery).
2. `handleDiscovery` (`background.ts:619`) → `tryGetDappSessionByOriginAndChain` finds the remembered session (`:647`) → `autoApproveExistingSession` (`:649`) → `approveDiscovery` with **no cap check** (`checkDiscoveryPopupCaps` at `:670` is never reached on this path).
3. Upstream SDK completes ECDH key exchange → `handleSessionEstablished` (`session-established.ts:61`) runs with `marker === undefined` (no pending-verification entry was created for the auto-approve path) → `isNewConnection = false` (`:72`).
4. `:143` `needsVerification = false || !dappSession.trustedVerification` — `true` for any origin the user hasn't ticked "always trust" for (the default state).
5. `:145` `chrome.windows.create(...)` — a real OS window opens. Repeat step 1 as many times as desired; nothing anywhere counts or coalesces these calls.

**Precondition, precisely:** the origin must have been approved once before (an ordinary, common state — most connected dApps), and the user must not have ticked the "always trust" checkbox in a prior verify window (also the default state — the checkbox is opt-in). No compromise of the extension or browser is needed; this is reachable from an ordinary web page that can re-run the SDK's discovery/connect flow.

**Severity check:** Medium (low end) is right; **keep**. Pure availability/annoyance (spawns real OS popup windows, no auth/fund/secret exposure), zero interaction from the user once the precondition holds, and genuinely unbounded (no cap at all, vs. a merely-high cap) — that combination is exactly what separates it from Low (a capped-but-generous limit) and from High (no authorization or confidentiality effect is shown). CWE-770 with an unbounded, zero-interaction trigger and no cap at all is a fair Medium-low placement. Worth flagging for the write-up: repeated real `chrome.windows.create` calls are also a plausible **phishing-camouflage** vector (burying a genuine malicious approval among a flood of decoy verify windows) — this is a modest aggravating factor beyond pure annoyance, though not enough on its own to argue for raising the band given no trace shows it defeating the emoji-verification content itself.

**Fix check:** The three-part recommended fix is proportionate and each part mirrors an existing pattern already in the same file: (1) coalescing/capping `session-established.ts`'s `chrome.windows.create` mirrors `checkDiscoveryPopupCaps` itself (`background.ts:748-761`) — the same per-origin/global counting idiom, just applied to a second resource; (2) counting duplicate waiters is a small extension of the same function; (3) moving the cap check before the existing-session auto-approve (or rate-limiting auto-approvals) reuses the existing constants (`DISCOVERY_PENDING_GLOBAL_CAP`/`DISCOVERY_PENDING_PER_ORIGIN_CAP`, `:606-607`). Regression risk: the existing 4-per-origin/32-global constants were tuned for **connect** popups (rare, one-time approvals); reusing the same numbers for **verify** windows (which legitimately recur on every reconnect for a multi-tab dApp session) could reject a legitimate burst of tabs reconnecting simultaneously — the fix should size the verify-window cap independently rather than sharing the connect-popup constants verbatim.

**Confidence:** high on the window half (mechanism fully reproduced, no speculative step); moderate-to-low on the duplicate-waiter half by design of the original finding (memory-only, bounded by one popup's lifetime — confirmed at `background.ts:833-835`, where `pendingDiscoveryPromises.delete(dedupeKey)` runs in the `finally` after the single popup resolves; I did not re-run Codex's numeric harness, so I can only confirm the mechanism, not the specific 256-waiter figure).

### F-08 — `aztec_simulateTx` public-static fast path authorizes by `name` but executes by `selector`

**Independent read (before reading the trace):**
- `FunctionCall` (`@aztec/stdlib` `abi/function_call.d.ts:8-24`): `name: string` and `selector: FunctionSelector` are declared as two **independent** fields (plus `to`, `type`, `isStatic`, `args`, …) — nothing in the class or its Zod schema (`static get schema()`) cross-validates them.
- Scope check: `method-scope-checkers.ts:151-175` (`checkSimulationTransactions`, used by both `checkSimulateTx` at `:391-393` and `checkProfileTx` at `:395-397`) calls `matchesScope(String(call.to), call.name, scope)` at `:169` — **only** `to` and `name` are read; `selector` never appears in this function.
- Dispatcher: `dispatcher.ts:673-724` (`enforceMethodAndScope`) runs `enforceScopeWithSession`/`enforceScope` (→ the checker above) **before** `buildOperation` (`:663`) and before any execution. `buildAccountOperation`'s `"aztec_simulateTx"` case (`:1467-1474`) forwards `args[0]` as `exec` completely unchanged into the operation.
- Execution routing: `execution/service.ts:635-637` routes `"aztec_simulateTx"` straight to `this.viewExecutor.executeAztecSimulateTx(operation)`.
- Fast path: `view-executor.ts:242-246` calls `rehydrateOptimizablePrefix(op.exec?.calls)` (`fast-path.ts:87-114`), which for each call checks only `obj.type === FunctionType.PUBLIC && obj.isStatic === true` (`:96-101`) and then does a bare `FunctionCall.schema.parse(c)` (`:109`) — a shape parse, not a name/selector cross-check. The admitted calls flow into `runFastPath` (`fast-path.ts:172-230`), which calls `simulateViaNode(node, optimizableCalls, fromAddr, chainInfo, gasSettings, ...)` (`fast-path.ts:200-211` / `view-executor.ts:275-289`).
- Inside `simulateViaNode`/`simulateBatchViaNode` (`@aztec/wallet-sdk` `base-wallet/utils.js:46`): the on-chain calldata is built from `call.selector.toField()` — `call.name` is **never referenced** anywhere in this execution path.
- Contrast: `execution/service.ts:900-908` (the `createAuthWit` intent path) explicitly resolves the ABI function by `call.selector` via `findFunctionBySelector`, then throws if `call.name !== authwitFn.name` — the exact bind that is absent from the fast path.

**Verdict: CONFIRMED.** The scope checker authorizes purely on the dApp-supplied `name` string; the fast path executes purely by the dApp-supplied `selector`; nothing anywhere between dispatch and `simulateViaNode` compares the two. A dApp holding a `simulation.transactions` grant scoped to one function name can supply `{name: "<granted function>", selector: <selector of a different public-static function>, isStatic: true, type: "public"}` and have the **different** function actually execute, with its return value flowing back as if it were the granted call.

**Strengthened trace:**
1. dApp calls `simulateTx({calls:[{to: TOKEN, name: "balance_of_public" /* granted */, selector: <selector of a different public-static fn>, type:"public", isStatic:true, args}]})`.
2. `dispatcher.ts:707,711-722` → `assertAuthRelevantArgShape` (shape only) → `enforceScopeWithSession` → `checkSimulateTx` (`method-scope-checkers.ts:391-393`) → `checkSimulationTransactions` (`:151-175`) → `matchesScope(TOKEN, "balance_of_public", scope)` → **passes** (name matches the grant; selector is never read).
3. `dispatcher.ts:1467-1474` builds the operation, forwarding `exec` (including the mismatched `selector`) unchanged.
4. `execution/service.ts:635-637` → `view-executor.ts:223-246` (`executeAztecSimulateTx`) → `rehydrateOptimizablePrefix` admits the call (public+static shape parse only, `fast-path.ts:96-109`).
5. `view-executor.ts:275-289` → `runFastPath` → `fast-path.ts:200-211` → `simulateViaNode(node, [call], fromAddr, ...)` → `base-wallet/utils.js:46` builds calldata from `call.selector.toField()` — the **different** function actually runs, as `msg_sender = fromAddr`.
6. Its return value flows back through `buildMergedSimulationResult` (`fast-path.ts:229`) to the dApp as the `TxSimulationResult`.

**Why the Low band is right, given the reachable surface is public chain state:** confirmed correct. The only functions this path can reach are `type: "public", isStatic: true` — by Aztec's own semantics, a public+static function reads public contract state and cannot mutate it, and its result is queryable by anyone directly against a node (no wallet, no grant, no user interaction) — the wallet contributes exactly one piece of context beyond what a bare node RPC call already exposes: `fromAddr` as `msg_sender`. So the scope-enforcement bypass is real (a dApp can call a public-static function it was never granted, under the user's address, without a fresh approval), but it cannot produce a confidentiality loss beyond what a public node already discloses to anyone, cannot mutate state, and requires no signature. The one residual nuance (noted in the original write-up and worth restating): if some public-static function's return value is itself conditioned on `msg_sender` in a way that leaks address-specific information not otherwise derivable (e.g., a permissioned view keyed by caller), the "public chain state" framing is slightly optimistic — but no such function was demonstrated in the trace, and this is a property of the underlying contract, not of the wallet. Net: **Low is correct; do not raise.**

**Fix check:** The recommended fix (resolve the artifact by `selector` via `ContractResolver` and reject on name mismatch, in `executeAztecSimulateTx` before `runFastPath`) is the smallest safe change and is a direct mirror of an existing pattern in the same package — `execution/service.ts:900-908`'s `findFunctionBySelector` + `call.name !== authwitFn.name` throw, using the identical `ContractResolver`/`findFunctionBySelector` helpers already imported in `view-executor.ts:32`. `ContractResolver` is already a live dependency of `ViewExecutor` (not a new one to wire in), so the fix does not introduce new coupling. Regression risk is real but bounded: this reintroduces one artifact/ABI resolution per optimizable call into the path that exists specifically to avoid PXE-side resolution overhead, which could measurably cut into the fast path's performance win — the fix should confirm the resolver call is cheap (e.g., served from an already-populated in-memory cache after `registerContract`) rather than assume "hours" of effort covers a possible re-benchmark. No test currently exercises the mismatch case, as the finding states.

**Confidence:** high — the independent-field declaration in the SDK's own `FunctionCall` type, the name-only scope checker, the shape-only fast-path admission, and the selector-only calldata construction in `simulateViaNode` were each read directly, not inferred from the write-up.
