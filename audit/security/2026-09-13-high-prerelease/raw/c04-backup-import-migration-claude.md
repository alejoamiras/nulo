Findings: 2 (1 High-impact fund/integrity issue, 1 Medium display-spoofing issue). Non-findings: 11.

## F-1: Hostile full-backup can spoof the auto-selected "Private Fee Juice" fee payer to an attacker-controlled contract

1. **Title**: FPC-restore accepts an unauthenticated `address` for a canonical-typed row, and the Send UI's default private-fee-payment resolver trusts it without checking `isProtocol` — an attacker-crafted backup can redirect a real private-fee-payment transaction leg to a contract the attacker chose.

2. **Impact factors**: Integrity of transaction construction ("what you see is not what you sign" for the fee-payer leg of a real, victim-signed Aztec transaction) and potential Confidentiality/Availability/fund-loss impact on the user's private Fee-Juice ("wFJ") holdings — the code's own header comment (`fpc/service.ts:41-42`) characterizes a wrong PrivateFPC address as causing "unrecoverable loss." Attack vector: local/physical — requires the victim to import a maliciously-crafted or MITM-tampered ".json"/".txt" backup file through the wallet's own Import-Profile UI (Attack Complexity: Low once the file is obtained; the backup's checksum is "accidental-integrity, not authentication" per `backup-migration-registry.ts:11-14`, so any attacker who can hand the victim a file, or intercept one in transit, can rewrite it freely and still pass the checksum gate by recomputing it — `useFullBackupImport.ts:93`). Privileges required: none beyond persuading/enabling the victim to run Import → Full Backup. User interaction: required (the victim must import the file, then use the normal Send flow and either accept the default "Private Fee Juice" option or not notice the swap — no distinguishing UI signal is shown, see field 6).

3. **Evidence confidence**: High — every step of the trace below is a direct code read, not inference.

4. **OWASP / CWE mapping**: OWASP A08:2021 (Software and Data Integrity Failures — the backup's un-authenticated content is trusted to define a security-relevant identity); CWE-345 (Insufficient Verification of Data Authenticity) and CWE-441 (Unintended Proxy or Intermediary / confused deputy — the wallet acts as the user's proxy and is tricked into paying an attacker-chosen contract). Secondary: CWE-863 (Incorrect Authorization — `isProtocol` is the only authorization signal distinguishing "canonical" from "user-added" FPC rows, and the auto-select path ignores it).

5. **Trace** (source → sink):
   - **Source (backup content, fully attacker-controlled)**: `apps/extension/src/wallet/services/backup/backup-migration-registry.ts:197-223` — the `fpc` slice is registered as a plain `{ kind: "root", root: FPC_STORAGE_ROOT, idOf: stringAnchor("id") }` descriptor with no field-level authentication beyond zod shape-parsing. `apps/extension/src/wallet/services/fpc/service.ts:487-528` (`FpcService.restore`) accepts each row's `address` verbatim: `const stored: StoredFpc = { id, profileId: rest.profileId, chainId: rest.chainId, type: rest.type, address: rest.address, name: rest.name }` (line ~512-519), and the only structural check is `StoredFpcSchema.parse(stored)` (no address-vs-canonical-derivation check exists anywhere in `restore()`). Every restored row is unconditionally re-emitted as `{ ...stored, isProtocol: false }` (line 525) — a hostile row can freely claim `type: FpcType.PrivateFpc` (or `DefaultSponsoredFpc`) with `name: "Private Fee Juice"` and any `address`.
   - **Compounding step (contract gets registered so the malicious call actually executes)**: `apps/extension/src/wallet/services/account-state/service.ts:372-405` (`prepareContractRegistration`) registers **any** `{instance, artifact}` pair the `account-state` backup slice carries into the profile's PXE via `this.pxeService.registerContract(...)`, gated only by `precheckContractAddress` (`:444-456`), which skips registration ONLY for Aztec's reserved system addresses `0..6` — any real deployed address (including one the attacker deployed and fully controls) is registered with WHATEVER artifact the backup supplies (no artifact-shape check like `PrivateFpcHandler.validateArtifact` is ever invoked on this path — that validator only runs during the live *auto-discovery* path, `fpc/service.ts:245`). So a single crafted backup can (a) plant an `fpc` row of `type: PrivateFpc, address: X, name: "Private Fee Juice"`, and (b) register `X`'s instance+artifact into PXE via the `account-state` slice, in the SAME import.
   - **Auto-discovery does not neutralize the spoof — it duplicates the row, and the duplicate is then hidden**: `apps/extension/src/wallet/services/fpc/service.ts:134-197` (`getFpcs`) lazily auto-discovers the real canonical PrivateFPC/SponsoredFPC when `hasPrivateFpc`/`hasSponsoredFpc` (address-exact match against `getOrComputeProtocolAddresses`, `:109-121`) is false. Because the poisoned row's `address` does NOT equal the canonical address, discovery treats the canonical FPC as still-missing and APPENDS a second, genuine row (`result.push(...)`, `:187`) — so after the first post-import `getFpcs(chainId)` call (e.g. opening Send), storage holds BOTH the poisoned row (present from restore, earlier in the array) and the genuine row (appended after), both `type: PrivateFpc`. `buildFeeMethods` (`fee-helpers.ts:156-163`) then explicitly `continue`s past every OTHER `type === FpcType.PrivateFpc` row after picking the first — so the genuine canonical row isn't just deprioritized, it becomes **completely unselectable**, not shown as any option at all.
   - **Sink 1 (balance display)**: `apps/extension/src/wallet/services/execution/gas-balance-reader.ts:180-182` — `const bridgedFpc = fpcs.find((f) => f.type === FpcType.PrivateFpc)` picks the FIRST row by `type` alone (no `isProtocol` check), then reads `balance_of` against `bridgedFpc.address` — the displayed "private Fee Juice" balance can be read from the attacker's contract, and the attacker's own artifact controls what `balance_of` returns.
   - **Sink 2 (fee-payer selection — the fund-impacting one)**: `apps/extension/src/popup/components/modules/send/fee-helpers.ts:156-158` (`buildFeeMethods`) — `const privateFpc = registeredFpcs.find((f) => f.type === FpcType.PrivateFpc)` (same unguarded pattern) feeds `privateFeeJuiceOption(privateFpc, ...)` (`:191-199`), which becomes the single "Private Fee Juice" / "private" dropdown entry shown to the user in `FeeSettingsCard.vue`, carrying `fpc: privateFpc` (the poisoned row). The option is `disabled` when `gasBalances.privateFeeJuice` is `null`/`"0"` (`fee-helpers.ts:201-203`) — so the option is only ACTIONABLE if the attacker's own `balance_of` implementation reports a nonzero value. When it does, `settingsForMethod` (`fee-helpers.ts:89-96`, case `"private_fpc"`) turns the user's selection into `buildSettings({ kind: "fpc", fpcId: method.fpc.id }, priority)` — the poisoned row's `id`. `FpcStrategy.buildAndEstimate` (`execution/fee/fpc-strategy.ts:97-107`) resolves it via `this.deps.fpcService.getFpcImpl(fpcId)` (`fpc/service.ts:426-433`, which does NOT check `isProtocol` — only `requireOwnedRow` for profile ownership), then (since `type !== DefaultSponsoredFpc`, so `isSponsoredFastPathEligible` is false) runs `buildAndEstimateTwoPass`, which prepends `fpc.getFeePayload(...)` to the real transaction's actions. `PrivateFpcHandler.getFeePayload` (`fpc/handlers/private-fpc-handler.ts:23-32`) emits `{ kind: "call", contract: fpc.address, method: "pay_fee", args: [] }` — a private call to the attacker's registered contract built into the victim's simulated, signed transaction. (Whether such a transaction is then accepted as validly fee-paid at the protocol/sequencer level — i.e. whether the attacker's `pay_fee()` must itself genuinely front real Fee Juice to get the tx included — was **not** independently verified against protocol consensus rules; see Cross-rebuttal.)

6. **Missing control**: (a) `FpcService.restore()` never verifies a row claiming `type: PrivateFpc`/`DefaultSponsoredFpc` actually carries the canonical protocol-derived address (the same check `decorate()`/`getFpcs()` already compute at read-time via `getOrComputeProtocolAddresses`) — it could reject or force `isProtocol:false`-and-park such a row for explicit user review instead of silently accepting it as a first-class FPC. (b) Both `gas-balance-reader.ts:181` and `fee-helpers.ts:157` select the "the private FPC" by `type` alone; neither prefers/requires `f.isProtocol === true` even though that exact signal exists and is already used correctly at `fpc-strategy.ts:115` for the *sponsored* fast path. (c) `privateFeeJuiceOption` (`fee-helpers.ts:191-199`) surfaces no "verified"/"protocol" badge distinguishing a canonical PrivateFPC row from a user-added or restored one, so there is no UI signal even for an attentive user.

7. **Exploit story**: Attacker obtains or fabricates a Nulo full-backup file (e.g. intercepts one in transit to a "support" request, or hands the victim a "recovered wallet backup" — the checksum is self-consistent and recomputable, so the file need not be a real export at all). The backup's `data.fpc` array contains one row `{id:"x", profileId:<victim-profile-placeholder>, chainId:<target chain>, type: 2 /* PrivateFpc, per fpc/spec.ts:16-17 */, address: "0x<attacker-deployed-contract>", name:"Private Fee Juice"}`; `data["account-state"]` contains a matching `contracts` entry registering that same address with an artifact exposing `pay_fee()`/`balance_of()`. Victim imports the backup (normal Import → Full Backup flow); `normalizeAllIds` rewrites `profileId` to the newly created profile, so the row lands cleanly under the new profile — no cross-profile check blocks it. Victim opens Send; the wallet auto-discovers the genuine PrivateFPC too (now two rows exist) but the genuine one is never offered (see field 5) — only the poisoned "Private Fee Juice" entry is shown, enabled if the attacker's `balance_of` reports a nonzero figure. Victim (who has no reason to suspect a duplicate/spoof — there is no visual difference) selects it and sends a private transfer; the built transaction includes a `pay_fee()` call to the attacker's contract as part of the signed transaction.

8. **Preconditions**: Victim must import a backup file the attacker crafted or tampered with (social engineering / MITM on the file), then use the Send flow and pick the (indistinguishable, and now the ONLY offered) "Private Fee Juice" option, on a network where a PrivateFPC is expected to be used.

9. **Why mitigations fail**: The checksum (`useFullBackupImport.ts:93-100`) only detects ACCIDENTAL corruption — it is computed by the importer itself over the attacker's own bytes, so a crafted file passes trivially (this is explicitly documented, `backup-migration-registry.ts:11-14`). The `compat-epoch`/`backup-schema-version` gates constrain only the storage SHAPE, not row-level semantic trust. `requireOwnedRow`/profile-scoping (used by `getFpcImpl`) confirms the row belongs to the ACTIVE profile — which it does, by design, since the whole point of the attack is that the row is planted inside the victim's own newly-created profile. The account-integrity coordinator (`account-integrity/coordinator.ts`) only re-derives NULO-account addresses (`AccountType.Nulo_v1`); it has no concept of FPC-row canonicity and does not run over FPC rows at all.

10. **Instances** (same root cause — "trust `type`, ignore `isProtocol`, when auto-selecting the private FPC"):
    - `apps/extension/src/wallet/services/execution/gas-balance-reader.ts:181`
    - `apps/extension/src/popup/components/modules/send/fee-helpers.ts:157,161-163`
    - Root-enabling gap: `apps/extension/src/wallet/services/fpc/service.ts:487-528` (`restore`, no canonical-address check) and `apps/extension/src/wallet/services/account-state/service.ts:372-405` + `:444-456` (unconditional contract registration for any non-reserved address).

## F-2: Full-backup contact restore bypasses the bidi/homoglyph sanitizer applied by every other contact-name input path

1. **Title**: `ContactService.restore()` (the full-backup path) writes `name`/`address` with zero sanitization, unlike the plaintext-JSON contacts import and the backup-name preview — letting a hostile backup plant a contact whose name renders with bidi-override/zero-width/homoglyph characters in the address-book and the Send recipient autocomplete.

2. **Impact factors**: Integrity of the recipient-selection UI (a "what you see is not what you're sending to" spoof) — a maliciously-named contact can visually impersonate a name the user already trusts (or simply carry an invisible/reordering payload) in the exact list the user picks a payment destination from, potentially causing the user to send funds to the attacker's `contact.address` while believing they picked a different, legitimate contact. Attack vector: local — requires backup import (same precondition as F-1). Privileges required: none. User interaction: required (victim must import the file and later use the Send recipient picker).

3. **Evidence confidence**: High.

4. **OWASP / CWE mapping**: OWASP A03:2021-adjacent presentation-layer issue / A08:2021 (Software and Data Integrity Failures — untrusted backup content flows to a security-relevant UI unsanitized); CWE-451 (User Interface (UI) Misrepresentation of Critical Information) and CWE-1007 (Insufficient Visual Distinction of Homoglyphs).

5. **Trace**:
   - **Source**: `apps/extension/src/wallet/services/contact/spec.ts:24-30` — `ContactSchema` types `name`/`address` as bare `z.string()` (no length cap, no character-class restriction).
   - **Sink at write**: `apps/extension/src/wallet/services/contact/service.ts:280-309` (`restore`) — `const written = { ...contact, id }`; `ContactSchema.parse(written)` (line 303) is the ONLY validation; the row is written verbatim to storage. Contrast with the plaintext-JSON path in the SAME file, `importContacts` (`:179-190`), which explicitly runs `sanitizeString(c.name, 20)` / `sanitizeString(c.address, 66)` before ever constructing a contact — and with the backup-name PREVIEW in `useFullBackupImport.ts:376-380` (`sanitizedBackupName`), which applies the same `sanitizeString` before showing the profile name. `sanitizeString` (`apps/extension/src/utils/string.ts:33-42`) strips everything outside `[\p{L}0-9 \-._]` — i.e. it removes bidi-override (U+202E etc.), zero-width, and most homoglyph-adjacent characters. The full-backup contact-restore path is the one contact-name entry point that skips it.
   - **Sink at read/display**: `apps/extension/src/popup/components/modules/settings/contacts/ContactRow.vue:34` — `<span :class="$style.row_name">{{ contact.name }}</span>` (plain, unsanitized interpolation); `apps/extension/src/popup/components/modules/send/RecipientField.vue:129` — the autocomplete suggestion row `<Text ...>{{ c.name }}</Text>`, and line 102, the SELECTED-contact card `<RecipientCard :name="selectedContact.name" ...>` — the exact UI the user reads immediately before confirming a Send.

6. **Missing control**: `ContactService.restore()` should apply the same `sanitizeString` (or an equivalent bidi/zero-width strip) to `name` (and reasonably to `address`, though address is separately constrained by wallet-address parsing at Send time) that every other contact-name entry point already applies, closing the one path that currently doesn't.

7. **Exploit story**: Attacker crafts a backup whose `data.contact` array contains a row named e.g. `"Exchange Payout‮..."` or a homoglyph clone of a name the victim is known to already have saved (e.g. "Мом" using Cyrillic look-alikes for "Mom"), with `address` set to the attacker's own address. Victim imports the backup (merged into their existing profile data is not possible per-profile, but this is the victim's OWN new profile from THIS import — the attack is really "the imported backup's contact list is attacker-controlled and displayed as if trustworthy," which matters whenever a victim restores from a backup they did not personally create/verify, e.g. a "recovery service" support scam). Later, using Send, the victim searches or scrolls the recipient list and picks the spoofed entry, sending funds to the attacker.

8. **Preconditions**: Victim imports an attacker-influenced/tampered backup, then uses the contact-based recipient picker in Send rather than pasting/verifying a raw address.

9. **Why mitigations fail**: Vue's default `{{ }}` interpolation HTML-escapes but does not strip bidi-control or zero-width Unicode characters — those aren't markup, so escaping does nothing; the only defense the codebase actually deploys against this class (the July "truthful approval display" bidi/RLO/overlong `safe()` fix, and this file's own `sanitizeString`) is not wired into this one restore path.

10. **Instances**: `apps/extension/src/wallet/services/contact/service.ts:280-309` (root cause); display sinks at `apps/extension/src/popup/components/modules/settings/contacts/ContactRow.vue:34`, `apps/extension/src/popup/components/modules/send/RecipientField.vue:102,126,129`.

## Non-findings

- **`dapp-session` is NOT backup-restorable** — it has no `backup()`/`restore()` methods (`grep` over `dapp-session/service.ts` finds none) and no entry in `BACKUP_SLICE_REGISTRY` (`backup-migration-registry.ts:197-223`); a hostile backup cannot plant or widen a dApp session grant. Confirms the audit prompt's specific concern is closed.
- **`master-key` never enters the migration engine, scratch store, or any error path** — verified: `backup-migrator.ts` types `MigrateBackupOptions.data` as only the `data` object; `master-key` is read directly off the top-level envelope in `useFullBackupImport.ts`/`full-backup-restore.ts` and passed straight into `ProfileService.restore`'s `RestoreSecret`, zeroized in every `finally` (`profile/service.ts:2275-2283`, `2450-2461`) — matches `README.md:21`'s invariant.
- **Account-row cross-profile grafting is closed for DIRECT writes under the victim's profile ID**: `normalizeAllIds(data, "profileId", newProfile.id)` (`useFullBackupImport.ts:485`, called unconditionally before any child-row restore) rewrites every row's `profileId` regardless of what the backup claims, and `AccountService.restore` additionally cross-checks `parsed.l1ChainId` against the freshly-restored Network row (`account/service.ts:700-703`) and rejects blank addresses/in-batch duplicates (`:710-716`). **This does NOT close cross-profile impact via shared, un-scoped state — see the Cross-rebuttal section's adopted finding on `auth-registry` purge-by-address.**
- **Nulo_v1 (derived) account address spoofing is caught before session-open, not after**: `ProfileService.finalizeRestore` → `finalizePasswordRestoreHoldingLock`/`finalizePasskeyRestoreHoldingLock` (`profile/service.ts:2628,2681`) both call `openSessionVerified`, which (via `AccountIntegrityCoordinator.verifyBeforeSessionOpen`, `account-integrity/coordinator.ts:133-135,142-191`) re-derives every stored `AccountType.Nulo_v1` row's address from `(master, l1ChainId, type, index)` and throws `AccountAddressInconsistencyError` (blocking the session) on any mismatch — and this runs AFTER all account/network rows have already landed in storage (restore order: profile → networks → accounts → tokens → services → finalizeRestore), so a spoofed derived-account address is caught before the session (and any signing capability) is exposed. (`AccountType.Imported` rows are not re-derived here, but their signing key ciphertext is HKDF-bound to `(chainId, address)` per `account/service.ts:752-758`, so a mismatched address/key pairing fails to unseal rather than silently binding.)
- **Network RPC-URL allowlist (F-011) is enforced at restore, not just at manual add**: `NetworkSchema`/`NetworkEndpointSchema` (`network/spec.ts:181-196`) both use `RpcUrlSchema` (`:152-179`), which `validateRestoredNetwork` (`network/service.ts:1046-1059`) runs via `NetworkSchema.safeParse` on every restored row — `javascript:`/`data:`/non-loopback `http:`/userinfo URLs are rejected regardless of source.
- **Config restore allowlist (F-06) correctly blocks `strictSecurityMode`/`sessionTtl`/diagnostic toggles**: `ConfigService.restore` (`config/service.ts:61-79`) skips any key not in `RESTORABLE_CONFIG_KEYS`, confirmed the security-relevant keys are excluded from that set (`config/spec.ts`).
- **Migration engine (`Migrator`) footprint/guardCommit/journal hardening is currently INERT in production**: `realMigrations = []` (`wallet/storage/migrations/index.ts:26`) — pre-production, per `CLAUDE.md`'s migration policy — so `migrateBackupData` on every real backup today only normalizes/denormalizes with zero actual migrations to run (`kind: "noop"`); the engine's crash-safety/footprint-enforcement machinery (Q5 in the prompt) has no live migration to exercise yet. Not a vulnerability, but worth flagging that this surface is unexercised until the first real migration ships.
- **`EntityStorage.requireKeyIdentityMatch`/`keyIdentityMode` is opt-in on `profile`, `auth-registry`, and `token-balance` (numeric) only** (`grep` confirmed); other roots (`account`, `network`, `token`, `contact`, `transaction`, `fpc`, `incoming-transfer`, imported-keys) do not enable it. Constructed a row-transplant scenario (copying one profile's row bytes under another profile's key) for these roots: every consumer that makes an ownership decision on these roots reads `profileId`/ownership from the DECODED VALUE (e.g. `.filter(x => x.profileId === profile.id)`), never from the storage key, and the one root where the KEY itself carries composite identity used for security decisions (`account`, via `accountRowId`/`parseAccountRowId`) is defended by a byte-canonical round-trip check at the one place that matters (the profile-purge cascade, `account/service.ts:648-658`) rather than by `requireKeyIdentityMatch`. No reachable RPC or backup-import path was found where an attacker can cause a row to be WRITTEN under a foreign key with a mismatched value in the first place (all writers key by their own freshly-allocated or composite-derived id) — so this is a documented, opt-in-per-root design choice, not an exploitable gap, for the roots this cluster covers. **Caveat added post-rebuttal: this claim is about mismatched-key/value transplantation specifically, and is orthogonal to the auth-registry address-only purge issue adopted below, which needs no key/value mismatch at all — it needs only a shared, un-prefixed storage root.**
- **No UI code bypasses the migration-aware storage facade**: `grep -rn "chrome.storage.local" apps/extension/src/{popup,onboarding,stores,composables}` returns only test files and comments; every production hit is prose, not a call site.
- **Contacts plaintext import/export (`exportContacts`/`importContacts`) is otherwise sound**: sizes are implicitly bounded by the same 64 MiB backup-file ceiling class of concern doesn't apply (it's a separate JSON blob path with `sanitizeString(name,20)`/`sanitizeString(address,66)` caps applied at parse time, `contact/service.ts:187-190`) — see F-2 for the one path (full-backup restore) that does NOT share this hardening.
- **Restore atomicity / torn-restore is well-defended**: `restore-pending-repository.ts` fail-closed torn-import detection (a stranded marker blocks unlock with `RestoreTornError`, never silently re-seeds), `restore-fence.ts`'s per-row deletion-epoch capture-and-reassert (captured at each service's restore ENTRY, re-checked immediately before every row write with no intervening await) closes the window where a concurrent `deleteProfile` could let post-purge rows land as permanent orphans; `restoreRows` best-effort-per-row design means one bad row never aborts a whole slice, consistent with the documented design.
- **Token metadata spoofing via backup (symbol/decimals/name)**: `TokenService.restore` (`token/service.ts:790-834`) accepts arbitrary token metadata from the backup with only shape validation (`TokenSchema.parse`) and a chain-liveness cross-check — but this mirrors the EXISTING trust level of manually adding a custom token via the UI (any user can already register a token contract with attacker-chosen display metadata), so backup import introduces no NEW capability here; not flagged as a cluster-specific finding.

## Handoff edges followed

- `useFullBackupImport.ts` (composable) → `full-backup-restore.ts` stage functions → each service's `ServiceClient.restore(...)` RPC → the service's own `restore()` implementation (one hop each, per service, for account/network/token/token-balance/transaction/auth-registry/fpc/contact/config/account-state).
- `ProfileService.restore()` → `ProfileService.finalizeRestore()` → `openSessionVerified()` → `AccountIntegrityCoordinator.verifyBeforeSessionOpen()` (delegate registration/consumption, `profile/service.ts:1187` ↔ `account-integrity/coordinator.ts:68`).
- `FeeSettingsCard.vue`'s selected `FeeMethodOption` → `settingsForMethod` → `FeeSettings.paymentMethod.fpcId` → `FpcStrategy.buildAndEstimate` (event/data handoff from UI selection to the fee-strategy dispatch, one hop, per the context cap).
- `BackupMigrator.migrateBackupData` → `Migrator.run()` (`@nulo/wallet-core/migration`) — the in-memory scratch-store handoff into the shared engine.
- `AccountService.reconcileImportedAccounts` (`account/service.ts:835-859`, called unconditionally from `useFullBackupImport.ts:531`) → `onAccountDeleted` → `AuthRegistryService`'s subscriber (`auth-registry/service.ts:97`) → `purgeForAccounts` (`auth-registry/service.ts:428-446`) — traced during cross-rebuttal to confirm the adopted finding below.

## Cross-rebuttal

**1. Codex's findings, one line each:**
- **F-1 (cross-profile authwit purge via keyless-imported-account reconciliation): CONFIRM.** Verified end-to-end: `authwits`/`statuses` live in a single flat, non-profile-prefixed `EntityStorage` root (`auth-registry/spec.ts:8`, constructed at `auth-registry/service.ts:71-80`); `purgeForAccounts` filters `authwits` by `account` address only, with no `profileId` check (`auth-registry/service.ts:428-446`); `onAccountDeleted` unconditionally calls it (`:97`); `reconcileImportedAccounts` deletes any imported-type row lacking a matching key row and emits `onAccountDeleted` (`account/service.ts:835-859`); it runs unconditionally on every full-backup import (`useFullBackupImport.ts:531`); and the account-restore collision check (`account/service.ts:686-687`, keyed on `(profileId, chainId, address)`) can never fire against a different, pre-existing profile's address since `profileId` is always the freshly-created one. This is real and I missed it.
- **F-2 (imported-account row transplantation): DOWNGRADE — out of scope for this cluster, on Codex's own evidence.** Its own precondition (`F-2 field 8`, field 9) states raw local-storage tampering is required and "a backup file alone cannot manufacture this... because normalization derives keys from row identities" — i.e. it is not reachable via backup *import*, the cluster's actual RPC surface. Valid observation, but it belongs to a storage-tampering cluster, not c04.
