### F-1: DappSession row-integrity MAC key is not profile-scoped — same-master sibling profiles can forge each other's dApp capability grants

1. **Title**: `ProfileService.deriveDappSessionMacKey` derives an identical HMAC key for any two profiles that share a master secret, defeating the F-12 row-integrity control for `DappSession` (dApp capability/confirmation-level) rows.

2. **Impact factors**: Integrity + Authorization violation. A `DappSession` row's `confirmationLevel` (up to `AccessLevel.Transactions = 5`, the level that lets a dApp skip the usual per-tx confirmation prompt — `packages/wallet-bridge/src/session-types.ts:21-28`) and `capabilityGrants`/`accounts`/`permissions` fields are exactly what the extension's dApp-interaction layer trusts to decide whether a connected dApp may act on a profile's accounts without re-prompting the user. The row-integrity MAC (`apps/extension/src/wallet/services/dapp-session/integrity.ts:1-16`) exists specifically so a `chrome.storage.local` writer can't "mint capabilities the user never approved" by editing a row. That control provides **zero** protection whenever the attacker holds (or can create) any profile sharing the victim's master secret — the key it signs/verifies with is identical regardless of which profile "owns" the row. Attack vector: local (requires `chrome.storage.local` write access, the exact adversary this control targets), complexity low once the precondition holds, no user interaction needed for the forged row to later verify, privileges required: none beyond storage write + a sibling profile.

3. **Evidence confidence**: High — traced end-to-end in source, and corroborated by the project's own test doubles/tests (below), which model the *intended* per-profile behaviour that the real implementation does not provide.

4. **OWASP / CWE mapping**: OWASP A02:2021 – Cryptographic Failures (missing context/domain separation in key derivation) leading to OWASP A01:2021 – Broken Access Control. CWE-863 (Incorrect Authorization) / CWE-1391 (Use of Weak Credentials, root-cause framing: CWE-330-adjacent missing entity binding) — most precisely, this is a **key-derivation missing domain separation** bug (no CWE number is a perfect fit; closest is CWE-323 "Reusing a Nonce, Key Pair in Encryption" in spirit — the key is reused across security principals that are supposed to be isolated).

5. **Trace**:
   - Source (where the security decision is made): `apps/extension/src/wallet/services/profile/service.ts:913-933` (`deriveDappSessionMacKey`) — HKDF over `ikm = secret.toBuffer()` (the profile's *master* Fr) with **`salt: TextEncoder().encode("nulo:dappsession-mac:salt:v1")`** and **`info: TextEncoder().encode("nulo:dappsession-mac:v1")`** — both fixed string constants; `profileId` (the function's own parameter) is used *only* to fetch the active session's secret (`sessionManager.getSecret(profileId)`, service.ts:914) and is never mixed into the HKDF salt/info. Two profiles A and B created from the same 24-word phrase (a supported, only-*warned* path — `assertNotDuplicateWallet`, service.ts:2004-2015, `DuplicateWalletError` unless `allowDuplicate`) therefore get **byte-identical** `CryptoKey` material whenever *either* is active, because `secret` (the Fr master) is identical for both.
   - Consumption (sign): `apps/extension/src/wallet/services/dapp-session/mac-storage.ts:30-35` (`set`) — `key = await this.keyFor(session.profileId)` then `signDappSession(key, signable)`.
   - Consumption (verify): `apps/extension/src/wallet/services/dapp-session/mac-storage.ts:85-104` (`verifyOrDrop`) — `key = await this.keyFor(row.profileId)` then `verifyDappSession(key, signable, mac)`; a passing MAC is trusted as proof the row was written by that profile's own service (doc comment at `mac-storage.ts:9-22`: "F-12: MAC-verifying wrapper... Signs every row on write and verifies on read.").
   - Sink (where harm manifests): any RPC/UI path that trusts a verified `DappSession` row's `confirmationLevel`/`capabilityGrants`/`accounts` to skip re-confirming a dApp request (`apps/extension/src/wallet/services/dapp-session/service.ts:76-90` `getDappSessions`/`getDappSession`, consumed by the wallet-bridge dispatcher — out of this cluster's file list, but the row shape at `apps/extension/src/wallet/services/dapp-session/spec.ts:39-58` documents exactly these fields as the access-gating ones ("Exact on the access-gating fields... a drifted session row is HIDDEN" — i.e., the codec/MAC pairing is explicitly the only gate).

6. **Missing control**: the HKDF `info`/`salt` (or, alternatively, the DEK — which the codebase already treats as "the stated separator" for a same-master attacker, per `packages/wallet-crypto/src/entropy-mac.ts:12-15,34-38`) is never mixed into `deriveDappSessionMacKey`. Every sibling per-profile-key derivation in the same codebase gets this right — `derivePxeStoreKey(master, profileId)` salts on `"nulo:pxe-store-salt:" + profileId` (`packages/wallet-crypto/src/pxe-store-key.ts`), `computeEnvelopeMacV3`'s preimage binds `profileId` first (`packages/wallet-crypto/src/entropy-mac.ts:51-58`), and `SessionSecretBox.wrapPair` AAD-binds `profile.id` (`session-manager.ts:268`) — making `deriveDappSessionMacKey` the one outlier, which strongly suggests an oversight rather than a deliberate design choice.

7. **Exploit story**: (1) Attacker creates (or already owns) profile B from the same 24-word recovery phrase as victim's profile A — supported flow, only a dismissible warning. (2) While B is unlocked, the SAME `CryptoKey` bytes that would verify a row for A are available to any code that can reach `DappSessionService`'s legitimate write path for B's own sessions — but more directly, the attacker (who by hypothesis already has `chrome.storage.local` write access, matching `integrity.ts`'s own stated threat model) crafts a raw JSON row `{id, profileId: "<A's id>", chainId, dappMetadata, permissions, accounts: ["<A's account>"], confirmationLevel: AccessLevel.Transactions, expiry, mac}` and computes `mac` using the CryptoKey they can derive for their OWN active profile B (same master ⇒ same key). (3) The forged row is written under the extension's `nulo:core:dappSessions` storage root. (4) The next time profile A is unlocked and the dApp/UI reads sessions (`getDappSessions`), `verifyOrDrop` derives the "per-profile" key for `profileId="A"` (now legitimately obtainable since A is active) — which is the **same key bytes** — and the forged MAC verifies. The dApp origin encoded in the row is now treated as holding `AccessLevel.Transactions` for A's accounts with no further prompting.

8. **Preconditions**: (a) attacker has, or can create, a profile sharing the victim's master secret (same 24-word phrase) — no password or passkey knowledge required for this half; (b) attacker has write access to the extension's `chrome.storage.local` (the precondition this exact control — F-12 — was built to defend against, per its own doc comment).

9. **Why mitigations fail**: the schema/codec layer (`DappSessionSchema`) validates *shape*, not *authorship*; the MAC is the only authorship control, and it is keyed by a value (the shared master) that is not unique per profile. The MAC's own name ("per-profile... non-extractable HMAC key... a row signed under one profile can't verify under another" — service.ts:905-911 doc comment) is therefore not true whenever two profiles share a master.

10. **Instances** (same root cause): `apps/extension/src/wallet/services/profile/service.ts:913-933`; consumed at `apps/extension/src/wallet/services/dapp-session/mac-storage.ts:30-35,85-104`. Test-side corroboration that the real bug is masked: `apps/extension/src/wallet/services/dapp-session/service.test.ts:26-48` stubs `deriveDappSessionMacKey` with an explicit `Map<profileId, key>` ("one deterministic HMAC key **per profile**") — i.e. the test double encodes the *intended*, not the *actual*, behaviour; `apps/extension/src/wallet/services/dapp-session/integrity.test.ts:53-56` (test named "cross-profile / cross-key replay fails (per-profile key)") only signs/verifies with two independently-`generateKey()`'d random keys and never calls the real derivation at all, so it cannot catch this class of bug.

### F-2: Whole-envelope swap between same-password sibling profiles still opens a live (degraded) session under the wrong master — verified-still-open residual of the prior adversarial review's F-1

1. **Title**: `mac-identity-binding` (#446) closed the DEK/fingerprint holes from the internal adversarial review's F-1/F-2, but the *core* secret material (the row's `guard`/`secret`/`entropy` triple) still has no profile-identity binding, so a full-row swap between same-password sibling profiles opens a genuine, usable session keyed to the wrong wallet.

2. **Impact factors**: Integrity/Authorization (identity confusion) — the wallet opens a session, displays the victim's profile name, but every subsequent derivation (accounts, signing) uses the attacker-substituted master secret. Confidentiality impact is bounded (no *new* secret is disclosed — the swapped material is already the attacker's own), but a user could unknowingly transact under a wallet they don't control while believing it is their own profile. Requires local storage write access + knowledge of a shared password between two profiles (attack complexity: moderate; privileges required: storage write; user interaction: the victim must type their own — shared — password once).

3. **Evidence confidence**: High — confirmed by tracing the exact code path AND by an existing green integration test that already accepts (does not reject) the degraded-open outcome as passing behaviour.

4. **OWASP / CWE mapping**: OWASP A02:2021 – Cryptographic Failures / A07:2021 – Identification and Authentication Failures. CWE-287 (Improper Authentication) / CWE-863 (Incorrect Authorization) — the row's cryptographic identity (which profile it belongs to) is not bound into the check that gates the *primary* secret material, only into the check that gates the *derived* imported-keys DEK.

5. **Trace**:
   - Source: attacker (with storage-write access) overwrites victim profile A's row fields `guard`/`secret`/`entropy`/`dekSealed`/`envelopeMac` with profile B's values verbatim, keeping A's `id`/`name` — `apps/extension/src/wallet/services/profile/repository.ts` (`nulo:core:profiles@<id>`, raw JSON blob).
   - `unlockProfile(a.id, "shared-password")` — `apps/extension/src/wallet/services/profile/service.ts:589-660`. Phase 2: `secretBox.unseal(password, sealedTriple(snapshot))` (service.ts:597) decrypts B's ciphertext successfully (shared password) → `secret`/`entropy` are B's real values. `assertEntropyMasterPair(secret, entropy)` (service.ts:612, defined :1926-1934) passes — it only checks that the recovered words re-derive the recovered master, a check with **no profile-identity component at all**.
   - Phase 3: `unsealTrustedDekHoldingLock` (service.ts:643, defined :368-403) recomputes the envelope MAC v3 using `id = a.id` (the REQUESTED id) against B's copied `envelopeMac` (originally computed with `id = b.id`) — mismatch, so `dek = null` → session opens **degraded** (`openSessionVerified`, service.ts:644) instead of being rejected outright, and `onImportedKeysDegraded` fires (service.ts:645-647).
   - Sink: `SessionManager.open(profile=A-shaped-row, secret=B's-real-master, ...)` (`session-manager.ts:253-341`) commits a live, usable session whose `Fr` master is B's, displayed as profile "A".

6. **Missing control**: `PasswordSecretBox`'s AAD (`PROFILE_AAD`, `packages/wallet-crypto/src/password-secret-box.ts:56-60`) is deliberately **purpose-only**, not profile-scoped (its own doc: "Purpose-only ON PURPOSE (no profileId...)") — so the `guard`/`secret`/`entropy` ciphertexts decrypt identically no matter which row they're pasted into, as long as the password matches. The envelope MAC v3 (`packages/wallet-crypto/src/entropy-mac.ts`) *does* bind `profileId`, but per the documented "degradation state machine" (service.ts:637-642) it only gates the imported-keys DEK trust decision (rule 2, *degrade*), never the core session-open decision (rule 1, *block*, which is `assertEntropyMasterPair` alone).

7. **Exploit story**: identical setup/precondition/outcome to the codebase's own pinned test — see Instances below — which is why this is reported as a *verified-still-open residual*, not a new discovery: the fix shipped for the prior review's F-1/F-2 (mac-identity-binding, #446) closed the DEK/fingerprint side but left the core pairing check untouched, and the maintainers' own test accepts the degraded-but-live outcome rather than asserting a hard reject.

8. **Preconditions**: attacker has `chrome.storage.local` write access AND knows (or shares) the exact password of a profile the victim also uses that password for. Both together are a substantial bar, but it is precisely the bar the whole envelope-MAC-v3 feature was built to raise, and it is not fully raised here.

9. **Why mitigations fail**: mac-identity-binding's `profileId` binding is present only in the v3 MAC preimage, which the degradation state machine treats as advisory (DEK-only) rather than block-worthy for the primary secret.

10. **Instances**: `apps/extension/src/wallet/services/profile/service.ts:589-660` (`unlockProfile`), `:1069-1126` (`changeProfilePassword` — `unsealResealedVerifiedHoldingLock`, :958-996, has the same `assertEntropyMasterPair`-only core gate), `:1623-1669` (`exportPlain`), `:1746-1815` (`exportBackupMaterial`, which explicitly documents skipping the MAC check "DELIBERATELY" at :1792-1798), `:1879-1917` (`exportMnemonic`); core check defined at `:1926-1934`. Existing pinned test that already accepts the degraded-live outcome: `apps/extension/src/wallet/services/profile/service.integration.test.ts:536-569` ("a WHOLE-envelope swap between same-password profiles is rejected at unlock (identity binding)" — asserts `outcome !== "unlocked"`, which is satisfied by EITHER a reject OR the `"derived-only"` branch, and the `"derived-only"` branch is what the code actually produces). Prior documentation of the original finding: `implementations-plan/adversarial-key-model-review/findings.md` (F-1 MEDIUM, F-2 LOW).

### F-3: Profile deletion purges auth-registry rows without profile scoping — a live sibling profile's shared-address accounts silently lose their local revocation index

1. **Title**: `AuthRegistryService.purgeForAccounts` (called from the profile-deletion cascade) is the one purge step in the cascade that is **not** scoped to the deleting profile's id, so deleting profile A can silently wipe locally-tracked public-authwit rows that a still-live sibling profile B legitimately depends on, whenever A and B derive the same account address (which they do by construction for any shared index/chain, since address derivation has no profile component).

2. **Impact factors**: Availability / integrity of a local security-relevant index (the user's own record of granted public authwits), not confidentiality or fund loss — the underlying on-chain authorization state is unaffected; only the wallet's local revocation-tracking convenience is destroyed. No attacker interaction needed beyond the user's own (or an attacker-tricked) decision to delete one of two same-phrase profiles.

3. **Evidence confidence**: Moderate — the code path and the missing-scope fact are directly confirmed; the *practical* trigger (two profiles genuinely colliding on the same derived address) requires the same recovery phrase to be imported twice and an account created at the same `(chainId, type, index)` in both — the common case for a freshly-created default account, but not universal.

4. **OWASP / CWE mapping**: CWE-668 (Exposure of Resource to Wrong Sphere) / CWE-862 (Missing Authorization scoping) framed as a data-isolation gap between two local security principals (profiles) that are supposed to be independently manageable.

5. **Trace**:
   - `apps/extension/src/wallet/services/profile-deletion/coordinator.ts:116-131` (`purge`) — `await this.auth.purgeForAccounts(s.addresses)` (line 120) is called with **no `profileId`** argument, unlike its siblings on the same lines: `this.txs.purgeForAccounts(s.addresses, profileId)` (line 119), `this.balances.purgeForTokens(s.tokenIds, profileId)` (line 121).
   - `apps/extension/src/wallet/services/auth-registry/service.ts:428-449` (`purgeForAccounts`) deletes every `Authwit` row (and malformed raw rows) whose `.account` is in the deleted profile's address set — with no profile filter, because (own comment) `:456-459`: "authwit rows carry NO profileId (unscoped numeric keys)".
   - Address collision mechanism: `apps/extension/src/wallet/services/account/service.ts:260-268` scopes the next-index allocation to `x.profileId === profileId && x.chainId === chainId` (i.e., PER PROFILE), while the actual address derivation, `deriveAccountSeed(master, l1ChainId, type, index)` (`packages/wallet-crypto/src/derive-account-seed.ts`), has **no profileId input** — so profile A's account-0 and profile B's account-0 on the same chain, from the same recovery phrase, derive to the identical address.

6. **Missing control**: `AuthRegistryService.purgeForAccounts` has no `profileId` parameter/filter to mirror `TransactionService.purgeForAccounts(addresses, profileId)` and `TokenBalanceService.purgeForAccounts(scopes, profileId)`.

7. **Exploit/violation scenario**: a user imports the same 24-word phrase as two profiles (a supported, only-warned flow — e.g. one profile for daily use, one for a specific dApp/testing context). Both profiles' default accounts land at the same `(chainId, type, index=0)` and therefore the same address. The user later deletes one profile. The deletion cascade's `auth.purgeForAccounts` wipes every locally tracked `Authwit`/registry-enabled flag for that shared address — including entries the STILL-LIVE sibling profile's UI relies on to show/revoke previously-granted public authwits — with no warning and no restore path (the purge is unconditional and immediate, run inside the awaited deletion cascade).

8. **Preconditions**: two profiles sharing a recovery phrase, both having derived an account at the same `(chainId, type, index)` — the default/common case for each profile's first account on a given chain.

9. **Why mitigations fail**: the cascade's own snapshot (`ProfileDeletionCoordinator.snapshot`, coordinator.ts:86-99) collects addresses *without* distinguishing "this profile's account" from "an address this profile happens to share with another live profile" — there is no check anywhere in the cascade for "is this address still owned by a live, different profile" before purging address-keyed rows that (unlike accounts/tokens/networks, which ARE profile-scoped rows) are only address-keyed.

10. **Instances**: `apps/extension/src/wallet/services/profile-deletion/coordinator.ts:120`; `apps/extension/src/wallet/services/auth-registry/service.ts:428-449,456-459`; also reachable via the single-account path `apps/extension/src/wallet/services/auth-registry/service.ts:97-99` (`onAccountDeleted` → `purgeForAccounts([account.address])`, same missing scope, smaller blast radius since it is one address at a time).

## Non-findings

- **Password unlock secret flow** (Q1): `unlockProfile` (service.ts:589-660) never persists the raw password, passhash, or master `Fr` to `chrome.storage.local`; the only persisted secret-derived value is the F-11 random-token-wrapped bearer in `chrome.storage.session`, gated by `strictSecurityMode` (default ON). Grepped every `console.*`/`logger.*`/`this.log*` call in this cluster for password/secret/passhash/mnemonic/master/entropy/prf/dek arguments — all matches are literal log-message strings (e.g. `"Cleared passhash bearer (strict mode)"`), never the actual secret value; profile `id` is the only non-literal argument logged, which is not sensitive.
- **Passkey unlock secret flow** (Q1): PRF output and derived master never leave the SW process except as the RPC *return value* (a `ProfileInfo`, never the secret) — `passkeys/service.ts:86-88` `materializeCredential` is SW-internal (not in `rpcMethods`), and `PasskeyCredential` instances carry `CryptoKey`/buffer state that is zeroized via the existing `zeroize()` discipline (`service.ts` finally-blocks throughout `unlockPasskeyProfile`/`createPasskeyProfile`/`importPasskeyProfile`).
- **Session bearer readers/invalidation paths** (Q2): grepped the whole `apps/extension/src` tree for `SESSION_STORAGE_ROOT`/`nulo:core:session` — `SessionManager` is the only reader/writer. Every invalidation path is covered: lock (`lockActiveProfile` → `close()` → `session.delete()` + read-back via `hasPersistedSession()`), TTL alarm (`onAlarmFired` → `close()`, serialized via `runExclusive`), profile switch (`open()` fully replaces the single-key session record — no partial old-bearer residue possible), profile delete (`deleteProfile` closes the session before purge if it belongs to the deleted profile), password change (`reopenAfterPasswordChangeHoldingLock` re-opens with a fresh random-token bearer, replacing the old record), restore (F-11 shape gate rejects legacy/strict/missing bearers), integrity block (`openSessionVerified`'s catch closes any live session for the profile before rethrowing). The one documented residual (a storage-write failure during `open()` that also fails to confirm deletion) is explicitly narrated in code as "the user's own last durably-persisted session... never a secret exposure" and is pre-existing, not a new gap.
- **TTL alarm failure / SW death / clock manipulation** (Q3): `getActive()` (session-manager.ts:194-208) and `restore()` (session-manager.ts:530-534) both re-check `isExpired` reactively on every read, independent of whether the proactive `chrome.alarms` fire ever happened — confirmed by `session-manager.test.ts:759` ("SW restart with persisted lockedAt < now silentCloses (no emit)"). Clock manipulation would require OS-level control, outside this extension's threat model (equivalent to an attacker who already owns the machine).
- **Passkey credential↔profile binding, PATH A/B** (Q4): `unlockPasskeyProfile` explicitly checks `recovery.credentialId !== snapshot.credentialId` (service.ts:770) and re-checks post-relock (:786); `exportPlain`'s passkey arm does the same (:1691). The popup (`auth.vue:97-100`) additionally scopes the WebAuthn `get` via `getPasskeyCredentialId` + `allowCredentials`, so a discovery picker never lets the user select the wrong credential. `materializeCredential` (PATH A) is a SW-internal method reachable only via `isTrustedInternalSender`-gated RPCs (`createPasskeyProfile`/`unlockPasskeyProfile`/`importPasskey`/`exportPlain`/`restore`), i.e. only same-extension contexts (popup, offscreen) can supply `credentialData` — a web page cannot reach it (confirmed against the extension-messaging repo map's dApp-dispatcher call list, which never touches profile secret RPCs). The popup is architecturally the trusted party for PRF bytes in this design (same trust tier as the SW itself); no separate compromise vector for the popup was found in this cluster's files.
- **Embedded-id row-key transplant** ("F-1 r2" bypass attempt): `ProfileRepository`'s `requireKeyIdentityMatch: true` guard (repository.ts:43-49) hides a row whose embedded id disagrees with its storage key, closing the bypass where an attacker keeps B's row byte-identical (including embedded `id: "B"`) but stores it under A's key — confirmed passing test at `service.integration.test.ts:571-598`.
- **RP-ID / host_permissions / web-page interception of a ceremony** (Q11): `RP_ID = "nulo.sh"` is frozen and drift-checked at build time (`check-rp-id.ts` + `scripts/check-rp-id.ts`); WebAuthn ceremonies (`passkey-ceremony.ts`) run exclusively inside the extension's own popup/window frames (`PasskeyCeremonyDialog.vue`, `popup/windows/passkey/index.vue`), never inside a content script or a web page's DOM — no `window.postMessage`/content-script bridge exists in this cluster's files that could let a web page inject or intercept `PasskeyCredentialData`.
- **Envelope-MAC-v3 verify ordering** (Q5): every read path that trusts the DEK verifies the MAC before use (`unsealTrustedDekHoldingLock`, service.ts:368-403, used by unlock/finalizeRestore; `rekeyedDekForPasswordChangeHoldingLock`, :1011-1038, used by password change; silent-restore bearer path, `session-manager.ts:588-607`). Export paths (`exportPlain`/`exportMnemonic`/`exportBackupMaterial`) deliberately skip the MAC and rely only on the (id-agnostic) `assertEntropyMasterPair` core check — an explicit, documented, reasoned tradeoff (service.ts:1792-1798) since exporting a foreign-but-self-consistent DEK cannot itself cause harm (see F-2 for the one place this reasoning has a gap).
- **Password-change atomicity** (Q6): all four security-bearing fields (`guard`/`secret`/`entropy`/`dekSealed`) plus `envelopeMac` are mutated on one in-memory `profile` object and committed via a single `await this.repo.set(id, profile)` call (service.ts:1112) — `chrome.storage.local.set` commits one item atomically, so a crash before this call leaves the OLD row fully intact (old password still works) and a crash after leaves the NEW row fully consistent; no interleaved/partial state is reachable. The old session bearer is invalidated because `reopenAfterPasswordChangeHoldingLock` (:1048-1067) re-opens the session, and `SessionManager.open()` fully replaces the single-key session record.
- **Export authorization / tombstoned-profile export** (Q7): `exportPlain`/`exportMnemonic`/`exportBackupMaterial`/`getProfileDekSealed` all gate through `captureRowFence`/`runExclusive`, which check `deletionState.isReserved(id)` (tombstoned = "Invalid profile id") both before AND after the slow crypto/prompt work — a mid-delete profile cannot be exported.
- **Account-integrity block bypass via storage tamper / cross-consumer enforcement** (Q8): `isBlocked()` derives from raw storage KEYS (not decoded payloads), so a corrupt block record still blocks (fail-closed) — `blocked-repository.ts:36-39`. Clearing the block requires an explicit green re-verification (`coordinator.ts:189-190`); a bare storage delete of the key would clear it, but that requires the same `chrome.storage.local` write precondition already assumed catastrophic elsewhere in this report (and is the accepted local-attacker tier the whole feature set is built against, per the package's own ATTACK-SURFACE.md). The block is honoured by every downstream consumer *indirectly and correctly*: the coordinator's response to a mismatch is to close the SW-side session (`lockProfileIfActive`/`persistIntegrityBlockIfLive`), and every dApp-facing consumer (execution/dispatcher) requires an active session via `requireActiveProfile`/`getActiveProfile()` — so there is no separate "is this profile blocked" check needed at each consumer. Operation-time mismatches (not just unlock-time) are separately owned by `AccountService`, per the repo map, closing the startup-window gap.
- **Profile-deletion cascade — half-purged-but-unlockable profile** (Q9): phase 1 (row delete + session close + tombstone write) is committed under the facade lock BEFORE the awaited cross-service purge runs; once phase 1 lands, `repo.get(id)` returns `undefined` and `deletionState.isReserved(id)` is true, so unlock is blocked by two independent, redundant checks regardless of whether the later purge (phase 2) ever completes. A failed/aborted purge leaves the tombstone in place (by design) so `resumePendingDeletions` finishes it idempotently on the next boot — never a state where the profile row still exists and unlocks.
- **Config `strictSecurityMode` toggle authorization** (not attacker-reachable): `ConfigService.setValue` is a generic same-extension RPC (no separate re-auth), but it is only reachable by same-extension contexts (popup) — the intended Settings-screen UX, not remotely triggerable, and restoring a backup cannot silently flip it (`RESTORABLE_CONFIG_KEYS` allowlist excludes `strictSecurityMode`/`sessionTtl`/dev toggles, `config/service.ts:19-26,64-71`).
- **`AccountIntegrityCoordinator.verifyProfile` cross-profile leakage** (part of Q8/Q10): the blocked record and the per-account re-derivation are strictly keyed by the requested `profileId`; a mismatch on one chain blocks the WHOLE profile (by design — "session withheld" is profile-granular, not chain-granular) but never touches or reveals anything about a different profile's row.
- **Logging hygiene across this cluster's files**: no `console.*`/logger call in the reviewed files interpolates a secret value into a message string (the logging-policy redaction-by-key-name gap noted in project docs is not triggered anywhere in this cluster — every logged secret-adjacent call passes a literal descriptive string plus, at most, a profile `id`).
