### F-1: Signing still accepts a different chain identity with the same XOR composite

1. **Title:** Signing validates the composite instead of the selected chain tuple.
2. **Impact factors:** Authorization and integrity: an RPC operator can make the wallet sign material for a different `(l1ChainId, rollupVersion)` than the selected network. Affects the selected signing account and every signing path using this helper. Network attack vector; low complexity for an operator controlling the selected endpoint; requires an authorized signing operation. This report establishes incorrect-domain signing, not successful replay or fund loss on another deployed chain.
3. **Evidence confidence:** **High** for the validation bypass and signing trace; **unknown** for exploitable replay between deployed networks.
4. **OWASP / CWE mapping:** [OWASP A01:2025 Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-863, Incorrect Authorization, included in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).
5. **Trace:** Node response enters `apps/extension/src/wallet/services/execution/service.ts:872` → `packages/aztec-runtime/src/utils/chain-identity.ts:55` compares only `(l1ChainId ^ rollupVersion) >>> 0` → execution constructs the signing domain from that response at `apps/extension/src/wallet/services/execution/service.ts:876` → signs at `:935`. Transaction equivalent: `execution/tx-request-builder.ts:220` → composite check at `:221` → `chainInfoFrom(nodeInfo)` passed at `:286` → account entrypoint signing at `packages/aztec-runtime/src/account/nulo-account.ts:184`.
6. **Missing control:** Compare the selected exact L1 identity and rollup version before signing. `Network.l1ChainId` exists, but `SelectedNetworkChainInfo` exposes only the composite. Discovery also needs to use the transaction’s validated tuple rather than obtain another independently accepted tuple.
7. **Violation scenario:** Enroll/select a network represented by tuple `(1,4)` and composite `5`. After enrollment, its endpoint returns `(2,7)`, also composite `5`. The guard accepts this response and the wallet signs with `chainId=2, version=7`. The arithmetic was checked; these values demonstrate the signing-policy violation, not a claimed collision between particular production deployments.
8. **Preconditions:** The selected non-local endpoint is malicious, compromised, or changes identity; an account is unlocked and a signing path runs.
9. **Why mitigations fail:** Exact-L1 account derivation chooses a key; it does not authenticate the domain supplied to that key. Enrollment probing at `network/service.ts:994` does not constrain later responses. The July internal-refetch fix correctly threads one response through `NuloAccount`, but the acceptance predicate remains lossy. The exact-pair estimate-reuse check rejects drift relative to an estimate, not an incorrect tuple already accepted when that estimate was built.
10. **Instances:** Shared predicate: `packages/aztec-runtime/src/utils/chain-identity.ts:34`, `:53`. Standard transaction signing: `execution/tx-request-builder.ts:220`, `:286`. Direct authwit signing: `execution/service.ts:872`, `:935`. Discovery refetches: `execution/authwit-discoverer.ts:106`, `execution/discovery-probe.ts:73`, and `execution/dapp-send-executor.ts:853`; the last directly signs at `:863` without comparing the new tuple to the existing request’s `TxContext`. Batched account-backed simulation: `execution/helpers/batched-view-simulation.ts:203`, `:362`, `:538`. The public-static fast path also accepts the composite at `execution/fast-path.ts:179`, although that arm does not sign.

### F-2: Authwit records cross profile and network boundaries

1. **Title:** Account-address-only authwit storage exposes and deletes another scope’s revocation records.
2. **Impact factors:** Confidentiality and integrity: another profile sharing an address can display/export authwit intent metadata; synchronizing another network or deleting a shared-address account can remove the only local record of a still-live grant. Blast radius is every profile/network sharing that address. Local/profile workflow vector; low complexity; requires shared-address accounts or networks and normal profile/network interaction. No arbitrary signing-key access is established.
3. **Evidence confidence:** **High.**
4. **OWASP / CWE mapping:** [OWASP A01:2025 Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-863, Incorrect Authorization, in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).
5. **Trace:** Public-grant records are written without profile/network identity at `apps/extension/src/wallet/services/auth-registry/service.ts:166` → `getAuthwits` selects solely by address at `:132` → the settings screen fetches and displays that list at `apps/extension/src/popup/pages/settings/advanced/account-state/authwits/index.vue:47`. Destructive path: caller-selected network at `auth-registry/service.ts:299` → all address-matching rows loaded at `:349` → checked against that network at `:366` → absent grant deleted at `:371`.
6. **Missing control:** Store and enforce profile plus chain/network provenance on grants, registry status, reads, exports, reconciliation, and purges. Address equality is not sufficient ownership.
7. **Violation scenario:** A grant for account X exists on network A. Account X is also used on network B. `syncRegistry(B, X)` loads A’s record; B correctly reports the hash absent, and the wallet deletes A’s revocation record although A’s grant remains live. Independently, switching to another profile containing X displays the first profile’s stored intent contents. Deleting X in one scope purges records belonging to the other.
8. **Preconditions:** A shared account address across networks/profiles and at least one tracked grant. Shared addresses are explicitly anticipated elsewhere—for example, transaction-history filtering handles them at `apps/extension/src/stores/app.store.ts:564`.
9. **Why mitigations fail:** Row-schema and key/id validation establish record shape, not ownership. The UI’s account filter and switch watcher re-fetch the same address-only collection. Pending-grant reconciliation prevents premature confirmation but supplies no missing provenance. The tracking cap deliberately avoids eviction because hashes cannot be enumerated from chain, making erroneous deletion consequential.
10. **Instances:** Schema: `auth-registry/spec.ts:24`. Creation/deduplication: `auth-registry/service.ts:157`, `:161`, `:166`. Reads/cap: `:132`, `:142`. Reconciliation by transaction hash alone: `:177`, `:179`. Network synchronization/deletion: `:299`, `:349`, `:366`, `:371`. Registry-status keying: `:387`, `:393`. Backup: `:418`. Account-deletion listener and purge: `:97`, `:428`, `:432`. UI fetch/event filtering: `popup/pages/settings/advanced/account-state/authwits/index.vue:47`, `:55`.

### F-3: Discovery signs contract-emitted authorizations without checking their authority

1. **Title:** Discovery promotes contract output into signing authority without checking the requested signer or intent scope.
2. **Impact factors:** Authorization and signing integrity: a contract can cause real witnesses to be created for authorizations absent from the submitted operation’s displayed calls. Blast radius is the selected signing account and the emitting contract’s authorization domain. Remote dApp/contract vector; requires an operation reaching discovery and a contract emitting a valid authorization request. The demonstrated violation is unauthorized witness creation; this report does not establish extraction, replay, or theft using those witnesses.
3. **Evidence confidence:** **High** for issuance and omitted checks; **moderate** for the authorization interpretation because automatic discovery is an intentional transaction feature.
4. **OWASP / CWE mapping:** [OWASP A01:2025 Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-862, Missing Authorization, in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).
5. **Trace:** Contract-controlled offchain effects enter `apps/extension/src/wallet/services/execution/discovery-probe.ts:66` → request parsed at `:80`, but only emitter address and `innerHash` retained at `:82` → opaque `add_private_authwit` created at `:90` → `execution/fee/fee-juice-strategy.ts:37` appends it and rebuilds at `:39` → `execution/tx-request-builder.ts:154` accepts that hash and signs at `:161`. The shorter direct path is `execution/dapp-send-executor.ts:850` → `:858` → `:863`.
6. **Missing control:** Check the request’s `onBehalfOf` against the selected signer; retain and authorize its caller, function selector, and arguments; require approval for newly discovered authority outside the reviewed intent. Current discovery interfaces receive no session grants or approved authorization set.
7. **Violation scenario:** A dApp submits an allowed `M.run(...)` call. M emits a structurally valid authorization request naming a different function on M, without executing that function. Discovery accepts the request, discards its decoded preimage, and creates an account signature over its hash. The popup still displays the original `exec.calls`; estimation returns fee fields and an estimate ID, not the added authorization. Changing `onBehalfOf` likewise does not change which account signs.
8. **Preconditions:** A controlled contract can emit valid `CallAuthorizationRequest` fields, and the operation uses a discovery-enabled route. The signed hash remains bound to the actual emitting contract and the selected signing domain.
9. **Why mitigations fail:** Aztec 5.2.0’s parser checks consistency of the request’s argument/hash preimage; it does not authorize that request for this wallet. Stub simulation deliberately accepts missing account witnesses. A subsequent real simulation proves that generated witnesses work, not that the user approved their intent. The direct `createAuthWit` capability/popup rules are bypassed because discovery invokes the account signer internally.
10. **Instances:** Classic discovery: `execution/authwit-discoverer.ts:101`, `:115`, `:120`; appended by `execution/discovery-aware-estimator.ts:119`, built at `:125`. Folded discovery: `execution/discovery-probe.ts:66`, `:80`, `:90`, consumed by `execution/fee/fee-juice-strategy.ts:37` and the probe branches in `execution/fee/fpc-strategy.ts:155`, `:216`. Direct NO_FROM signing: `execution/dapp-send-executor.ts:858`, `:863`. Hash-signing sink: `execution/tx-request-builder.ts:146`. Omission from estimation response: `execution/dapp-send-executor.ts:293`, `:300`; original-call display: `popup/windows/execute/OperationCard.vue:117`.

### F-4: Contract-address validation occurs after unauthorized PXE registration

1. **Title:** A rejected `registerContract` request can still register an address outside its grant.
2. **Impact factors:** Authorization and integrity of the profile’s PXE contract registry. A dApp permitted to register A can cause registration of B. Remote dApp vector; low complexity; requires a contract-registration grant and a valid instance preimage/artifact. No additional per-call approval is required by this route. No on-chain deployment, successful malicious transaction, or fund loss is established.
3. **Evidence confidence:** **High.** The mutation-before-error behavior was checked against the required Aztec **5.2.0** registration API.
4. **OWASP / CWE mapping:** [OWASP A01:2025 Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-863, Incorrect Authorization, in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).
5. **Trace:** DApp-supplied `instance.address` is authorized at `packages/wallet-bridge/src/method-scope-checkers.ts:80` → execution parses the supplied instance at `apps/extension/src/wallet/services/execution/service.ts:824`, verifies its artifact’s class at `:854`, and forwards it at `:859` → `packages/aztec-runtime/src/pxe/service.ts:449` calls the mutating registration API → only afterward does `:450` compare the derived address and throw.
6. **Missing control:** Derive and compare the address before registering either the instance or associated class. The authorization check and mutation must use the same verified address.
7. **Exploit story:** Obtain `contracts.canRegister` for A. Submit an instance whose declared address is A but whose otherwise valid preimage derives B, together with its matching artifact. The grant check accepts A; artifact validation succeeds. PXE registers B, returns B, and the wrapper then reports an address mismatch. The error does not undo B’s registration. Different preimages permit repeated out-of-grant registrations.
8. **Preconditions:** A scoped registration grant, unlocked applicable profile/network, and a schema-valid preimage with a matching artifact. No forged contract-class hash is needed.
9. **Why mitigations fail:** Artifact-class matching is orthogonal to instance-address matching. The instance schema validates fields, not the derived-address relationship. `withPxeWrite` serializes the callback but does not roll back its mutations when the postcondition throws (`packages/aztec-runtime/src/pxe/service.ts:954`, `:959`). The legacy registration executor performs an earlier address check; the Aztec SDK executor does not.
10. **Instances:** Authorization: `packages/wallet-bridge/src/method-scope-checkers.ts:82`. Unchecked forward: `execution/service.ts:824`, `:859`. Mutation-before-comparison: `packages/aztec-runtime/src/pxe/service.ts:447`, `:449`, `:450`. The shared wrapper affects callers that rely on its postcondition; the legacy executor’s precheck at `execution/service.ts:693` protects that particular route.
