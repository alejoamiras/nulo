### F-1: Live chain-identity check (`assertLiveChainIdentity`) accepts any node response whose `l1ChainId ^ rollupVersion` collides with the stored composite, letting a compromised/drifted RPC bind signed transactions and authwits to an arbitrary chain identity

1. **Title**: XOR-composite chain-identity check is trivially satisfiable by a forged `(l1ChainId, rollupVersion)` pair, defeating the wallet's own "reject a drifted endpoint" control at every signing/authwit sink.

2. **Impact factors**: Integrity of signed material — the `chainInfo` (`{chainId: Fr(l1ChainId), version: Fr(rollupVersion)}`) embedded into every `TxExecutionRequest` and every `AuthWitness` message hash is sourced from a live, unauthenticated `node.getNodeInfo()` call and is accepted whenever `l1ChainId ^ rollupVersion` equals the network row's stored composite `chainId` — a relation any attacker can satisfy for a self-chosen `l1ChainId` by solving `rollupVersion = l1ChainId ^ storedComposite` (O(1) arithmetic, no brute force). Blast radius: every account-signing path in the extension (standard tx build, fast path, view/discovery simulation, dApp-facing `createAuthWit`, NO_FROM discovery authwits) — i.e. the entire "what chain am I signing for" trust decision. Attack vector: network (a malicious/compromised RPC endpoint the wallet is configured to talk to). Attack complexity: low once the endpoint is controlled (the collision itself is a one-line computation, not a grind). Privileges required: none from the wallet's side — the attacker acts as the network peer. User interaction: the victim just uses the wallet normally (send/approve) against the compromised endpoint; no unusual action needed.

3. **Evidence confidence**: high (the composite-only comparison is read directly from the function and confirmed unchanged at all 9+ call sites; the codebase's own comments in the sibling network-mutation code path independently document that the composite is collision-prone).

4. **OWASP / CWE mapping**: OWASP A08:2021 – Software and Data Integrity Failures (nearest ZK/wallet-specific bucket: "chain-id / rollup-version binding of signed material" / "node-response trust" per this audit's category list). CWE-354 (Improper Validation of Integrity Check Value) — primary; CWE-290 (Authentication Bypass by Spoofing) — secondary, since the check exists specifically to authenticate the live node's claimed identity against the previously-verified one.

5. **Trace** (source → sink, ~4 hops, representative instance):
   - Source: `node.getNodeInfo()` response — controlled by whichever RPC endpoint the active `Network` row points at. `apps/extension/src/wallet/services/execution/tx-request-builder.ts:220` (`const nodeInfo = await node.getNodeInfo()`).
   - Check: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:221` → `packages/aztec-runtime/src/utils/chain-identity.ts:53-61` (`assertLiveChainIdentity`): `if (network.chainId === 0) return; const liveComposite = (nodeInfo.l1ChainId ^ nodeInfo.rollupVersion) >>> 0; if (network.chainId !== liveComposite) throw ...` — compares **only** the XOR composite, never the exact `l1ChainId`/`rollupVersion` pair, even though `network` (a full `Network` row) also carries `network.l1ChainId` (the exact, previously-verified identity — see `apps/extension/src/wallet/services/network/service.ts:337-355` `assertCanonicalStoredL1`).
   - Propagation: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:286` — `chainInfoFrom(nodeInfo)` (`packages/aztec-runtime/src/utils/chain-identity.ts:69-71`) builds `{chainId: Fr(nodeInfo.l1ChainId), version: Fr(nodeInfo.rollupVersion)}` **from the unauthenticated, attacker-satisfiable values**, threaded into `finalizeStandardBuild` (`tx-request-builder.ts:257-304`).
   - Sink: `account.buildTxExecutionRequest(node, pxe, payload, options, chainInfoFrom(nodeInfo), gasSettings, buildMeta)` (`tx-request-builder.ts:277-289`) → `packages/aztec-runtime/src/account/nulo-account.ts:137-185`, which passes `chainInfo` straight into `this.entrypoint.createTxExecutionRequest(current, gasSettings, chainInfo, options)` (:184) or the first-tx `DefaultMultiCallEntrypoint.createTxExecutionRequest(combined, gasSettings, chainInfo)` (:243) — the account's real signing key signs a request whose chain-identity fields are the attacker's choice.
   - A second, equally reachable sink: `apps/extension/src/wallet/services/execution/service.ts:866-880` `executeAztecCreateAuthWit` (a dApp-facing RPC) builds the SAME unchecked `{chainId, version}` metadata (:876-879) and feeds it into the authwit message-hash computation immediately below — so a dApp-requested `aztec_createAuthWit` is bound by the same broken check.

6. **Missing control**: an exact-equality assertion `nodeInfo.l1ChainId === network.l1ChainId` (the wallet already stores and validates this exact value — see `assertCanonicalStoredL1`, `resolveVerifiedL1ChainId`) before trusting `nodeInfo` for anything signature/authwit-relevant. The codebase demonstrably knows how to do this: `apps/extension/src/wallet/services/network/service.ts:565-572` and `:612-618` (`addEndpoint`/`updateEndpoint`) explicitly compare `probed.l1ChainId !== network.l1ChainId` with the comment "The XOR composite alone is collision-prone... require EXACT L1 equality, not just composite equality" — this discipline was never carried into `assertLiveChainIdentity`, which is the function actually invoked at signing time.

7. **Exploit story**: (1) A network row exists with `l1ChainId = L`, stored composite `chainId = C = (L ^ V) >>> 0` for the genuine rollup version `V` at enrollment/seed time. (2) The RPC endpoint behind that row is later compromised, taken over, or MITM'd (see preconditions). (3) The attacker's endpoint answers `getNodeInfo()` with `{l1ChainId: L', rollupVersion: V' = L' ^ C}` for any `L'` it likes — `L' ^ V' === C` by construction, so `assertLiveChainIdentity` passes at every call site. (4) Every tx build, fee estimate, view simulation, and `createAuthWit` call from then on signs material whose embedded chain identity is `(L', V')`, not the real, user-selected `(L, V)` — with no error, warning, or UI signal that the endpoint's claimed identity silently changed. (5) Because account addresses derive from the row-stored `account.l1ChainId` (never from `nodeInfo`), the attacker's environment can present the same account address as valid, so nothing in the UI looks abnormal while the wallet operates against an identity of the attacker's choosing.

8. **Preconditions**: attacker controls, or can inject responses for, an RPC endpoint the wallet is (or becomes) configured to use — via compromise of a default third-party provider (e.g. the seeded `lb.drpc.live` endpoints), a user-added custom/devnet RPC, or a network-position attacker able to defeat TLS to the endpoint (state-level/CA-compromise/user-trusted rogue root — or trivially for the loopback-only `http://localhost` "Local Network" preset if that traffic path is interceptable). No wallet-side credential or user error is required beyond normal use of the wallet against the compromised endpoint.

9. **Why mitigations fail**: The July key-model-v2 fix (`deriveAccountSeed(master, l1ChainId, type, index)` using the exact, row-stored `l1ChainId`) protects address/key derivation but never consults `nodeInfo` at all — it is orthogonal to this path. `resolveVerifiedL1ChainId`/`addEndpoint`/`updateEndpoint`'s exact-`l1ChainId` checks run only at network-*configuration* time (adding a network/endpoint), never at the moment of signing, so they cannot catch drift that begins after the endpoint is already trusted. `assertLiveChainIdentity` itself IS invoked at every relevant call site (call-site coverage is not the gap — see instances below), but its comparison basis (the XOR composite) is exactly the value the code elsewhere documents as collision-prone, so invoking it provides no real defense against the class of attacker ("a malicious or drifted RPC endpoint", per the function's own F-012 docstring) it was written to stop.

10. **Instances** (all share the same root cause — `assertLiveChainIdentity`/`chainInfoFrom` compare/derive from the XOR composite only):
    - `packages/aztec-runtime/src/utils/chain-identity.ts:34-71` (the function definitions themselves).
    - `apps/extension/src/wallet/services/execution/tx-request-builder.ts:220-221,286` (standard tx build) and `:407` (a second call site in the same file).
    - `apps/extension/src/wallet/services/execution/service.ts:229-231` (estimate-reuse chain-identity getter) and `:871-880` (`executeAztecCreateAuthWit`, dApp-facing).
    - `apps/extension/src/wallet/services/execution/fast-path.ts:176-179`.

### F-2: Account-import confirmation shows only a 12-of-64-hex-nibble truncated address, enabling a vanity/prefix-suffix address-poisoning attack against the "confirm this matches the account you expect" control

1. **Title**: Truncated address display in the account-import preview undermines the only user-facing defense against a substituted signing key in an account-export file.

2. **Impact factors**: Integrity/authenticity of an imported account's identity as perceived by the user — a victim can be induced to import and trust an attacker-controlled signing key while believing (from the displayed address) that it is a specific, known address. Blast radius: one imported account per successful social-engineering attempt; once trusted, the attacker (holding the real key) can independently sign/spend from it if the victim later funds or otherwise treats it as authoritative. Attack vector: network/social (delivery of a crafted export file) combined with an offline, no-network-interaction vanity-key search. Attack complexity: moderate (an offline, parallelizable ~2^48-candidate search — computationally expensive but well within reach of a moderately resourced/targeted attacker; no wallet or protocol interaction needed to grind it). Privileges required: none. User interaction: required (the victim must pick the file, preview it, and click Import).

3. **Evidence confidence**: high for the code trace (the display code truncates exactly as described); moderate for real-world exploitability (depends on the attacker's compute budget and the social-engineering pretext succeeding).

4. **OWASP / CWE mapping**: CWE-451 (User Interface (UI) Misrepresentation of Critical Information). Nearest OWASP Top-10 slot: A04:2021 – Insecure Design (this audit's own category list names this exact class: "what-you-see-vs-what-you-sign").

5. **Trace**:
   - Source: an attacker-supplied `NULO-ACCOUNT-EXPORT` file whose `signingKey` is chosen so its derived address matches a target address's first 6 and last 6 hex nibbles.
   - `apps/extension/src/wallet/services/account/service.ts:739-742` `previewImportAccount` → `:726-737` `decodeAccountExport` correctly recomputes the FULL address from the signing key (`NuloAccount.fromSigningKey`, `packages/aztec-runtime/src/account/nulo-account.ts:77-80`) and returns it — the service-side value is correct and complete.
   - `apps/extension/src/popup/pages/settings/accounts/import.vue:87-89` `handlePreview` stores the full, correct address into `previewAddress`.
   - Sink: `apps/extension/src/popup/pages/settings/accounts/import.vue:227` renders only `trimAddress(previewAddress, 8, 6, '...')` — per `apps/extension/src/utils/string.ts:11-14`, this keeps `0x` + 6 hex chars + 6 trailing hex chars (12 of 64 hex nibbles, ≈48 of ≈256 bits) and hides the remaining ≈208 bits — while the UI copy at `:250-252` explicitly instructs the user: "The address is recomputed from the file. Confirm it matches the account you expect." This is the ONLY control the flow relies on to authenticate the imported key's identity to the human (the plaintext-export checksum is documented, in `packages/aztec-runtime/src/account/account-export.ts:16-20`, as corruption detection only, not authentication).
   - The subsequent `importAccount` call (`import.vue:110-117` → `account/service.ts:456-524`) re-checks the FULL `recomputed !== expectedAddress` string exactly (`:473`) — the software's own comparison is correct; only the human-facing display is degraded.

6. **Missing control**: showing (or providing an explicit, easy "reveal/copy full address" affordance for) the complete address before the user's confirmation click, rather than truncating to 12 visible hex nibbles for a decision whose entire purpose is address authentication.

7. **Exploit story**: (1) Attacker learns or guesses the full address the victim expects to import (e.g. a previously shared "shared/business account" address). (2) Offline and without any wallet/network interaction, the attacker repeatedly generates Grumpkin signing keys and computes `NuloAccount.fromSigningKey(key).address` until one matches the target's first-6/last-6 hex nibbles (~2^48 search space — expensive but parallelizable, no on-chain or wallet feedback needed). (3) Attacker packages that key into a self-consistent `NULO-ACCOUNT-EXPORT` file (`buildAccountExport`/`serializeAccountExport`, `packages/aztec-runtime/src/account/account-export.ts:84-99`) and delivers it via a social-engineering pretext ("here's the refreshed export for our shared account"). (4) The victim picks the file in `import.vue`, previews it, sees a truncated address that visually matches what they expect, and imports it. (5) Believing the entry to be the trusted account, the victim later funds it or treats it as an authoritative co-signer; the attacker (holding the real key) can independently sign/drain it.

8. **Preconditions**: attacker has the compute budget to grind a ~48-bit vanity address match (feasible for a targeted/motivated attacker, not casual), and can deliver the crafted file to the victim with a credible pretext that discourages independent verification (e.g. checking the address on a block explorer or copying the full string).

9. **Why mitigations fail**: The service-side address recomputation and comparison (`decodeAccountExport`, `importAccount`'s `recomputed !== expectedAddress`) are cryptographically exact and cannot be bypassed technically — the entire security property here is delegated to the human "does this match what I expect" step, and that step is given only 48 of ~256 bits of the identifier to inspect.

10. **Instances**: single flow, one file — `apps/extension/src/popup/pages/settings/accounts/import.vue:87-89,227,250-252` rendering via `apps/extension/src/utils/string.ts:11-14`. (The sibling export-side account picker at `apps/extension/src/popup/pages/settings/security/export/account.vue:232` truncates similarly, but there the picker is over the user's OWN already-derived, integrity-checked accounts identified primarily by their user-assigned name, not an externally-supplied key being authenticated for the first time — materially lower risk, not included as an instance.)

A ciphertext moved to a different `(chainId, address)` row, or unsealed under a different profile's DEK, derives a different AES key and fails GCM authentication closed (verified by reading both functions in full) — transplant and wrong-DEK cases are both caught, matching the module's documented claim.
- **A4 per-account failure isolation**: `apps/extension/src/wallet/services/account/service.ts:367-396` (`loadImportedAccountContract`) and `:404-447` (`exportAccount`'s imported branch) both fail closed with `ImportedAccountUnusableError` scoped to the single account on any unseal/decrypt/address-mismatch failure; no path found that escalates an imported-key failure to a profile-wide lock (that escalation path — `raiseRuntimeMismatch` — is reserved for `AccountType.Nulo_v1` rows only, per `:334-355` vs `:340-342`).
- **Import-before-persist address verification**: `apps/extension/src/wallet/services/account/service.ts:456-524` `importAccount` calls `decodeAccountExport` (which recomputes the address from the signing key) and rejects (`:473`) before any storage write; the key row is written before the account row with compensation on failure (`:487-515`) — no window where an unverified key/address pair is persisted.
- **Account-export encrypted-variant authentication coverage**: `packages/aztec-runtime/src/account/account-export.ts:146-151` `encryptAccountExport` AES-GCM-encrypts the ENTIRE serialized JSON body (not just select fields as AAD) under a fixed purpose AAD — every field (address, l1ChainId, regime/digests, signingKey, checksum) is tamper-evident in the encrypted variant; the AAD is purpose-only by design (no per-file identity needed, matching the package's stated pattern for other AAD-bound envelopes).
- **Plaintext-export substitution posture**: confirmed as explicitly documented and accepted (`account-export.ts:16-20`) — a hostile plaintext file can self-consistently substitute a signing key + recomputed address + checksum; the only defense is the human "confirm the address" step, whose degradation is captured separately as F-2 rather than re-flagged here.
- **Address-freeze digests enforced only by tests for the vendored artifact**: `packages/aztec-runtime/src/account/frozen-artifact.ts` and `address-freeze.ts` define `FROZEN_ARTIFACT_SHA256`/`FROZEN_ACCOUNT_CLASS_ID`/`FROZEN_DESCRIPTOR_DIGEST`/`NULO_KDF_DIGEST` but no runtime code path recomputes and asserts these against the loaded artifact at start-up or at account creation (`address-freeze.test.ts`/`artifact-freeze.test.ts` are the only enforcement found). Not flagged as a finding: the vendored JSON is a build-time-fixed local file, not reachable by any in-scope untrusted actor (dApp, RPC, or backup input) in this cluster's threat model — a runtime self-check would only add defense-in-depth against a build/supply-chain compromise, out of scope here.
- **No alternate account-address derivation path**: grepped `getContractInstanceFromInstantiationParams` / `computeContractAddressFromInstance` / `deriveKeys` repo-wide; the only OTHER call sites are `apps/extension/src/wallet/services/fpc/service.ts` and `packages/aztec-runtime/src/pxe/known-artifacts.ts` (SponsoredFPC/PrivateFPC — protocol contracts, not user accounts) and `packages/aztec-runtime/src/pxe/service.ts:387` (`deriveKeys` inside `registerAccount`, consuming an already-derived `secretKey` for PXE key registration, not an independent address derivation). Every user-account address in the codebase goes through `NuloAccount`/the frozen artifact.
- **Payload chunking / authwit-scope boundary** (`packages/aztec-runtime/src/account/nulo-account.ts:161-216` `chunkHead`): traced the recursive chunking logic — external authwits (`payload.authWitnesses`) pass through chunk boundaries unchanged and remain bound to their own call's message hash (callee/selector/args), which chunking does not alter; the ONLY new authwits chunking generates are the account's own self-authorizations for its nested multicall wrapping. No concrete cross-call authorization leak found. - **PXE key-material exposure**: `packages/aztec-runtime/src/account/nulo-account.ts:48-50,62-67,77-80,106` and `packages/aztec-runtime/src/pxe/service.ts:379-400` confirm the PXE/offscreen boundary receives only the derived privacy `secretKey`, never the account seed or the Schnorr signing key, at every account-registration call site found.
- **Cross-profile row isolation**: every mutate/sign/export path checked inline-verifies `account.profileId === profileId` (and `chainId`) before use — `getAccount` (`:177-181`), `getAccountContract` (`:334-339`), `patchAccountField` (`:320-324`), `exportAccount` (`:406-409`), `importAccount` (scoped by construction to the passed `profileId`/`chainId`). - **Account row-id codec forgery**: `apps/extension/src/wallet/services/account/spec.ts:44-60` `parseAccountRowId` re-encodes the parsed tuple via `accountRowId(...)` and rejects any key whose re-encoding doesn't byte-match the original id string — this closes the whitespace/escape/-0 JSON-encoding variants the docstring warns about; no bypass found.

A planted mismatched row is therefore caught at the first possible moment, closing the window this hypothesis depended on. Recorded as examined-and-ruled-out rather than a finding, per the "if you cannot provide a concrete trace, do not speculate" instruction — `exportAccount`'s missing per-export re-derivation check is real but not shown to be independently reachable.
