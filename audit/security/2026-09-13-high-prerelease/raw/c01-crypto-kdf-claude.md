# c01-crypto-kdf — security audit report

Files read in full: all 17 non-test `packages/wallet-crypto/src/*.ts` modules, `packages/wallet-crypto/{ATTACK-SURFACE.md,README.md}`, `packages/aztec-runtime/src/account/account-export.ts`, `packages/wallet-core/src/utils/{random.ts,encoding.ts}` + the mnemonic codec section of `mnemonic.ts`, the five named `*.test.ts` files plus `apps/extension/src/wallet/crypto/key-vectors.test.ts` (referenced), `implementations-plan/{key-model-v2/plan.md §A-C + Security section, adversarial-key-model-review/findings.md, key-model-v2-hardening/plan.md summary}`; one-hop handoff reads of `apps/extension/src/wallet/services/profile/session-manager.ts` (in full) and targeted greps of `profile/service.ts` and `account/service.ts`.
Findings: 2 (both moderate-confidence, defense-in-depth / race-condition class — no direct key-recovery or authentication-bypass found).
Non-findings: 14.

### F-1: `EncryptionKey.getPasshash` never zeroizes the raw password bytes it encodes

1. **Title**: Unzeroized plaintext-password buffer in the passhash derivation, on every password operation.
2. **Impact factors**: Confidentiality — extends the in-memory lifetime of the user's raw wallet password beyond the package's own stated hygiene policy. Blast radius is systemic (every unlock/create/reseal/import/restore call funnels through this one function), but the finding is defense-in-depth: on its own it requires a *second*, independent memory-disclosure primitive (heap/crash dump, a co-located memory-reading bug, physical access with a debugger) to actually recover anything. Attack vector: local. Attack complexity: high (needs a second primitive). Privileges required: none beyond that second primitive. User interaction: none — happens automatically on every password entry.
3. **Evidence confidence**: high (direct code inspection; the contrast with the package's own established pattern is unambiguous).
4. **OWASP / CWE mapping**: OWASP A02:2021 – Cryptographic Failures (sensitive data left exposed in memory). CWE-226 (Sensitive Information in Resource Not Removed Before Reuse), secondarily CWE-316 (Cleartext Storage of Sensitive Information in Memory).
5. **Trace**: A user-supplied `password: string` reaches `EncryptionKey.getPasshash` — e.g. `apps/extension/src/wallet/services/profile/service.ts:613` (`unlockProfile`) — which does:
   ```ts
   // packages/wallet-crypto/src/encryption-key.ts:122-125
   public static async getPasshash(password: string): Promise<Passhash> {
       const utf8 = new TextEncoder()
       return asPasshash(await globalThis.crypto.subtle.digest("SHA-256", utf8.encode(password)))
   }
   ```
   `utf8.encode(password)` allocates a fresh `Uint8Array` holding the password's raw UTF-8 bytes and passes it **inline** to `crypto.subtle.digest`. It is never bound to a local variable, so nothing in this function (or any caller — the buffer is never returned) can ever call `zeroize()` on it. The only reference to the plaintext-password bytes is dropped the instant `digest()` returns, leaving the buffer to whatever the V8 GC's own schedule is.
6. **Missing control**: capture the encoded bytes in a named local and `zeroize()` it in a `finally`, exactly like the sibling function three lines above the class boundary — `deriveBip39Seed` (`packages/wallet-crypto/src/mnemonic-master.ts:26-47`) does precisely this for the analogous "password-equivalent" mnemonic sentence: `sentenceBytes`/`saltBytes` are named, then wiped in `finally`, with a comment explicitly reasoning that "the local sentence copy is password-equivalent material... and may not linger." `getPasshash` handles a *literal* password the same way `deriveBip39Seed` handles a mnemonic sentence, but skips the wipe.
7. **Exploit story**: A user unlocks their wallet (or creates/reseals/imports a profile, or imports a full backup). At that moment `getPasshash` allocates a `Uint8Array` containing the exact UTF-8 bytes of their password. An attacker who separately has *any* means of reading process memory shortly afterward — a forensic RAM/swap capture of a suspended device, a crash-reporting pipeline that snapshots the heap, an unrelated memory-disclosure bug in another part of the extension or a co-installed extension with debugging access — can recover the plaintext password directly, rather than having to invert or brute-force anything cryptographic. Every other secret buffer in this same file/package is proactively wiped within microseconds of last use specifically to shrink this window; this one buffer is not.
8. **Preconditions**: (a) the user performs any password-driven operation (trivially common — this is the unlock path), and (b) the attacker has an independent memory-inspection capability. Precondition (b) means this finding is not independently exploitable; it removes a layer of defense-in-depth the codebase otherwise applies consistently.
9. **Why mitigations fail**: the codebase's only defense against this exact threat class is `zeroize()` (~90 call sites in the extension, its own dedicated `zeroize.test.ts` suite, and the package's stated invariant "secret material is allocated as `Uint8Array<ArrayBuffer>`... callers own the lifecycle and call `zeroize()` on drop"). Here the buffer is not caller-visible at all — it is allocated and orphaned entirely inside `getPasshash`, so no caller ever had the opportunity to zero it even if they wanted to.
10. **Instances** (all share the one root cause at `packages/wallet-crypto/src/encryption-key.ts:122-125`):
    - `packages/wallet-crypto/src/password-secret-box.ts:95,130,167,174` (`seal`, `unseal`, `reseal` ×2)
    - `apps/extension/src/wallet/services/profile/service.ts:613,1021,1618,1790,1849,2626` (unlock, password-change, mnemonic import, restore ×2, export-plain path)
    - `apps/extension/src/composables/useFullBackupImport.ts:390`
    - `apps/extension/src/popup/pages/settings/security/export/full.vue:334`

    Note: the sibling `getHashHex` (`encryption-key.ts:132-139`) has the same code shape but is only ever called on non-secret content (backup-file checksums — `useFullBackupImport.ts:93`, `full-backup-helpers.ts:145`), so it is not included as an instance of this finding.

### F-2: `SessionManager.open()` can persist a session bearer after Strict Security Mode is enabled (race)

1. **Title**: Strict-Security-Mode toggle races an in-flight unlock, allowing a silent-restore bearer to be persisted despite the setting being on.
2. **Impact factors**: Confidentiality of the `master‖dek` pair, and integrity of the "Strict Security Mode = no persisted bearer, ever" guarantee the class docstring makes. The package's own `ATTACK-SURFACE.md` states plainly that reading the session bearer "yields the master with no work" — so persisting one against the user's explicit opt-out is a real (if narrow) policy violation, not merely cosmetic. Blast radius: the current session only, until the next lock/TTL-expiry/browser-session end. Attack vector: local, timing-dependent — requires an unlock RPC and a `strictSecurityMode` config-update RPC to race within a few WebCrypto/lock/storage-write async ticks of each other. Attack complexity: high (narrow, real window; not remotely triggerable). Privileges required: none beyond the normal popup↔background RPC channel already used for both operations. User interaction: two near-simultaneous legitimate actions (by the user, a second popup instance, or an automated settings flow).
3. **Evidence confidence**: moderate — the race window is real and demonstrable by code inspection (multiple genuine `await` points separate the flag read from the flag-gated write, and the code's own more careful sibling method proves the authors know this class of race exists), but I did not build an executable proof-of-concept to force the interleaving under test.
4. **OWASP / CWE mapping**: OWASP A04:2021 – Insecure Design (a security-mode transition is not atomic with the operation it's supposed to gate). CWE-362 (Concurrent Execution using Shared Resource with Improper Synchronization / Race Condition), contributing to CWE-522 (Insufficiently Protected Credentials) via the outcome.
5. **Trace** (one-hop handoff from `SessionSecretBox`, per the prompt's Q4): `SessionManager.open()` reads the flag **once, synchronously**:
   ```ts
   // apps/extension/src/wallet/services/profile/session-manager.ts:260-268
   const persistBearer = passhash !== undefined && !this.strictSecurityMode && profile.type === "password" && dek !== undefined
   const bearer = persistBearer && dek ? await this.sessionSecretBox.wrapPair(secretBuffer, dek, profile.id) : undefined
   ```
   Between that read and the actual persist, the function crosses several genuine async boundaries: `sessionSecretBox.wrapPair` itself (`packages/wallet-crypto/src/session-secret-box.ts:69-102` — `importKey` + `deriveKey` + `encrypt`, three separate WebCrypto calls), then `this.artifactLock.withLock(...)` (`session-manager.ts:294`, lock acquisition), then `await this.session.set(session)` (`session-manager.ts:301`, the actual `chrome.storage.session` write that lands the bearer). `strictSecurityMode` can flip to `true` at any point in that window via `onConfigUpdated` (`session-manager.ts:709,718-727`), which runs synchronously off an independent, unserialized RPC and does not share a lock with `open()`'s critical section (`open()` uses `this.artifactLock`; the config-driven cleanup uses the differently-injected `this.runExclusive`). `open()` never re-reads the flag after its own async work, so the stale `persistBearer=true` decision still lands in storage.
6. **Missing control**: a re-check of `this.strictSecurityMode` immediately before `session.set(...)` — the exact mitigation the same class already applies to the analogous race in `restore()`:
   ```ts
   // apps/extension/src/wallet/services/profile/session-manager.ts:570-578
   // F-11 race: re-check strict AFTER the async unwrap, immediately
   // before committing `activeSession`. A strict-toggle ON that landed
   // mid-restore already cleared storage; do not resurrect an in-memory
   // bearer session past it.
   if (this.strictSecurityMode) { ... await this.silentClose(); return }
   ```
   No equivalent guard exists in `open()`.
7. **Exploit/violation scenario**: the user submits their password (`unlockProfile`); while that RPC is still resolving inside `SessionManager.open()` (mid-`wrapPair`/lock/storage-write), the user — or a second popup instance, or an automated settings-sync path — submits the Strict Security Mode toggle. `onConfigUpdated` fires immediately, sets `this.strictSecurityMode = true`, and its own `clearBearer()` finds nothing persisted yet (no-op, since `open()` hasn't written its row). Shortly after, `open()`'s in-flight write persists a real `master‖dek` bearer to `chrome.storage.session` anyway. The user now believes Strict Security Mode is protecting them, but a bearer capable of silently restoring the full session sits on disk until the next explicit lock, TTL expiry, or browser-session end.
8. **Preconditions**: an unlock (or profile-create/import) RPC and a `strictSecurityMode` config-update RPC racing within the same short window; both reachable through the extension's already-authenticated popup↔background channel — no additional privilege is required beyond what a legitimate session already has.
9. **Why mitigations fail**: the code's own comment at `session-manager.ts:260-266` claims the design is race-free "with a concurrent strict-toggle ON mid-unlock" — but that reasoning only covers a stale flag read *before* `open()` is called (e.g. if a caller had cached the flag), not a transition occurring *during* `open()`'s own async body. `restore()`'s explicit re-check does not run inside `open()`.
10. **Instances**: `apps/extension/src/wallet/services/profile/session-manager.ts:253-341` (`open`, the one occurrence of the unguarded pattern) — contrast with the correctly-guarded `restore()` (lines 570-578) and `clearBearer()` (lines 465-499), which is the evidence this is an oversight in one method rather than an accepted design gap.

## Non-findings

- **PBKDF2 salt = SHA-256(fresh CSPRNG IV) in `EncryptionKey.encrypt`** (`encryption-key.ts:41-58`) is safe and arguably stronger than an independent random salt: since the IV is drawn fresh from `crypto.getRandomValues` per call, the derived salt (and therefore the derived AES key) is effectively unique **per encryption**, not just per profile — every ciphertext is keyed independently, so compromising one derived key exposes nothing about any other ciphertext. Reusing the same 96-bit IV across encryptions under the fixed `baseKey` would reproduce the same derived key and thus become a real GCM nonce-reuse hazard, but at realistic wallet-lifetime encryption volumes the birthday-bound collision probability over 96 bits is negligible; `nonce-uniqueness.test.ts` additionally pins that no box ever repeats a nonce structurally.
- **`getPasshash`'s output (the passhash itself) never crosses an RPC boundary and is no longer persisted** (F-11, confirmed live): `session-manager.ts:253-268` treats an incoming `passhash` only as a presence signal to decide whether to mint a bearer; the actual bearer is a fresh-random-token wrap of `master‖dek` (`session-secret-box.ts`), and the passhash value itself is `zeroize()`d at every call site in `profile/service.ts` (e.g. lines 579, 651, 1035, 1120-1121, 1813, 1864) rather than persisted or transmitted.
- **HKDF-info delimiter injection in `imported-account-key-box.ts:28`** (`` `${INFO_PREFIX_V2}|${chainId}|${address}` ``) is not exploitable: `chainId` is always a JS `number`, and no `Number.prototype.toString()` output (decimal, negative, exponential, `NaN`, `Infinity`) can ever contain a `|` character. Because the numeric field is placed first and is guaranteed pipe-free, the two-field encoding is collision-free for any two distinct `(chainId, address)` pairs regardless of what characters `address` itself contains (proved by case analysis: a length mismatch or an early digit/`|` mismatch is unavoidable whenever the tuples differ).
- **entropy-mac.ts's `.`-joined MAC preimage** (`entropy-mac.ts:51-58`) is likewise collision-free in practice: `guard`/`secret`/`entropy`/`dek` are base64 (`[A-Za-z0-9+/=]`, no `.`) and `walletFingerprint` is hex — neither alphabet contains `.`. `profileId` is always either a CSPRNG hex id from `ProfileRepository.generateUniqueId` (`apps/extension/src/wallet/services/profile/repository.ts:105`) or a hex WebAuthn `userHandle` (`service.ts:682`) — never user-supplied text — so no field can smuggle a `.` to shift the preimage's field boundaries.
- **F-1 (whole-envelope swap / identity adoption) and F-2 (unauthenticated `walletFingerprint`) from `implementations-plan/adversarial-key-model-review/findings.md` are fixed**, confirmed by reading the shipped code: `MacEnvelopeV3`'s preimage now binds `profileId` first and `walletFingerprint` last (`entropy-mac.ts:41-58`), and both the unlock path (`profile/service.ts`) and the bearer-restore path (`session-manager.ts:588-607`) verify the full v3 MAC before trusting the envelope — a same-password sibling's authentic envelope transplanted into another profile's row now fails verification because the preimage's row-identity prefix differs, and blinding the plaintext fingerprint is now a detectable tamper. (`entropy-mac.test.ts`'s "WHOLE-ENVELOPE SWAP" and "F-2" cases pin both.)
- **PasskeyCredential cross-credential separation** (`passkey-credential.ts:49-71`) rests on the WebAuthn PRF extension's own per-credential secret, not on anything computed here: the fixed eval label (`constants.ts:10`) and fixed internal HKDF labels are safe to reuse across every profile *because* the IKM (the PRF output) differs per credential by construction. RP-ID scoping — preventing a different origin from invoking the same credential at all — is enforced by the browser/authenticator platform, outside this package's code; no in-package check substitutes for it, nor does the design assume one is needed here.
- **`userHandle` binding**: not mixed into the HKDF salt/info (only `credentialId` is, `passkey-credential.ts:53,57`), but this is not a gap — `credentialId` already uniquely identifies the credential and the PRF output is already credential-specific, so binding `userHandle` too would be redundant, not load-bearing.
- **No AES-GCM nonce reuse anywhere in this cluster.** Every sealing box draws a fresh `crypto.getRandomValues` IV per call (`encryption-key.ts:42`, `imported-account-key-box.ts:48`, `imported-keys-dek-box.ts:41`, `session-secret-box.ts:78`), and `nonce-uniqueness.test.ts` structurally pins zero collisions across up to 128 seals per box, including same-row re-seals.
- **No key is ever reused across an AES-GCM and an HMAC operation.** Every derived key is minted via `deriveKey`/`importKey` with an explicit, single algorithm (`"AES-GCM"` or `"HMAC"`), and WebCrypto binds a `CryptoKey` to its algorithm at the API level; even where the same IKM feeds multiple derivations (e.g. `master‖dek` in `entropy-mac.ts` vs. nowhere else), the HKDF `info` differs per purpose, so the derived key bytes differ too.
- **No ciphertext version byte is silently ignored.** `EncryptionKey.decrypt` rejects `payload[0] !== 0` (`encryption-key.ts:71-74`); `unsealImportedSigningKeyV2` rejects `bytes[0] !== 1` (`imported-account-key-box.ts:67`); `unsealDekUnderWrapKey` rejects `bytes[0] !== 1` (`imported-keys-dek-box.ts:57`); `SessionSecretBox.unwrapPair` rejects any `v !== 2`, explicitly including a legacy `v:1` bearer (`session-secret-box.ts:113`, confirmed by `session-secret-box.test.ts`'s "legacy v1 bearer → null" case).
- **No `Math.random()` or other non-CSPRNG source found anywhere in the derivation/encryption chain.** Every secret, nonce, salt, or id traces to `globalThis.crypto.getRandomValues`/`crypto.getRandomValues` (`encryption-key.ts:42`, `session-secret-box.ts:76-78`, `imported-account-key-box.ts:48`, `imported-keys-dek-box.ts:35,41`, `wallet-core/src/utils/random.ts:13`) or WebCrypto's own internal randomness (`generateKey` in tests only); a repo-wide grep of `packages/wallet-crypto`, `packages/wallet-core`, and `packages/aztec-runtime/src/account` for `Math.random` returned zero hits.
- **`array_equals(guard, ENCRYPTION_GUARD)` (`password-secret-box.ts:222`) is not a timing oracle.** `guard` only ever reaches this comparison after successfully passing AES-GCM tag authentication inside `tryDecrypt` (which returns `undefined` — short-circuiting before `array_equals` runs at all — on any wrong-key/bad-tag failure); a wrong password therefore never produces a partially-matching plaintext for the comparison to leak information about, so its non-constant-time implementation has no exploitable input.
- **`deriveAccountSeed`'s `(type, index)` domain cannot collide.** Poseidon2 takes `[master, l1ChainId, type, index]` as four independent fixed-arity field elements (`derive-account-seed.ts:25-30`), not a concatenated string, so there is no delimiter-style ambiguity between different `(type, index)` pairs (unlike a hypothetical string-encoded scheme). `assertCanonicalL1ChainId` (`:19-23`) and the inline `type`/`index` safe-integer/non-negative checks (`:27-29`) close the remaining input-validation surface (no negative, non-integer, NaN, or out-of-`u32`-range chain id reaches the hash).
- **`computeWalletFingerprint`'s plaintext exposure is a stated, owner-accepted tradeoff**, not a new finding: `wallet-fingerprint.ts:1-25` and `ATTACK-SURFACE.md` both quantify it precisely (an 8-candidate oracle only in the already-catastrophic 23-of-24-known-words case; otherwise a full ~253.6-bit preimage), and the one way a storage attacker could abuse its plaintext nature — blinding it to silence the duplicate-phrase warning (F-2 above) — is independently closed by binding it into the v3 envelope MAC.
- **`Fr.fromBuffer`/`Fr.fromBufferReduce` genuinely copy their input**, verified by `zeroize.test.ts`'s dedicated "Fr copy-semantics" suite (32-byte and 64-byte cases, both `fromBuffer` and `fromBufferReduce`): zeroizing the source buffer immediately after the call does not corrupt the derived `Fr`. This makes the zeroize-after-derive pattern in `mnemonic-master.ts:50-62` and `passkey-credential.ts:73-99` actually effective, not merely asserted.
- **Omitting AAD on the full-backup single-file encryption path** (`popup/pages/settings/security/export/full.vue:338`, `useFullBackupImport.ts:396`) is safe, not an oversight: it is a single-purpose whole-file ciphertext with no sibling ciphertext under the same key to be confused with, unlike `PasswordSecretBox`'s three-slot `guard`/`secret`/`entropy` layout where purpose-tagged AAD is load-bearing against slot-swap attacks (`password-secret-box.ts:52-60`, pinned by the "slot-swap AAD rejection" test).

## Cross-rebuttal

**1. Codex's findings (0 findings, 16 non-findings) — per-item disposition.** No REFUTEs; codex's traces are accurate everywhere I re-checked them.

- NF-1 (PBKDF2 salt from hashed IV), NF-6 (`|`-delimiter non-collision), NF-9 (passkey separation), NF-10 (KDF v2 reduction/account-seed), NF-11 (fingerprint oracle), NF-14 (nonce/version discipline), NF-15 (CSPRNG-only), NF-16 (envelope MAC v3 fixes) — **CONFIRM**, each matches my own non-finding on the same evidence (`encryption-key.ts:41-58`, `imported-account-key-box.ts:26`, `passkey-credential.ts:49-71`, `derive-account-seed.ts:19-30`, `wallet-fingerprint.ts:29`, `session-secret-box.ts:113`, `wallet-core/utils/random.ts:13`, `entropy-mac.ts:51-58`).
- NF-2 (full-backup AAD omission is safe) — **CONFIRM**, near-verbatim overlap with my own equivalent non-finding.
- NF-9's refinement that PRF output "does reach popup/SW memory" and should not be described as authenticator-confined, and NF-11's refinement that "exactly eight candidates" assumes the missing word is last — **ADOPT**, both precisions I did not state and neither weakens my conclusions.
- NF-5 (fixed-zero HKDF salt, RFC 5869-cited) and NF-4 (`array_equals` timing, extended to `service.ts:1926`'s entropy/master pairing) — **ADOPT** as sharper framing of ground I covered more loosely.

**2. What it missed.** Its NF-7/NF-8 correctly describe the session-bearer-as-shared-secret residual and normal-path cleanup, but neither traces the **interleaving** my F-2 identifies: `SessionManager.open()` (`session-manager.ts:260-268`) reads `strictSecurityMode` once, synchronously, then does real async work before persisting, while `onConfigUpdated` (`session-manager.ts:709-727`) can flip that flag and fire `clearBearer()` at any point in between. Codex's NF-8 states cleanup "prevent[s] subsequent refresh from rewriting" the bearer without examining whether it also catches a bearer written *during* an in-flight `open()` — that specific race is absent from its report.

**3. What I missed that it found.** NF-12/NF-13's broader zeroization inventory — `Buffer.from(token).toString(...)` in `wrapPair` (`session-secret-box.ts:93`) and the decoded-token intermediate in `unwrapPair` (`session-secret-box.ts:120`), plus `mnemonic.ts:2075` and `account-export.ts:148,156` — are legitimate additional instances of my F-1's root cause (verified: `zeroize()` on the named outer buffer cannot reach an intermediate `Buffer.from(...)` copy already consumed). **ADOPT, high confidence**, folded into F-1's instance list; same severity class, no new root cause.

**4. Overconfidence.** Re-tracing my own F-2 against `packages/wallet-core/src/utils/lock.ts` for this rebuttal, I find **my own report overconfident**: every `sessionManager.open()` call site is gated by `ProfileService`'s facade lock (`service.ts:617,691,773,1057,2117,2597` — all documented "Caller MUST hold the facade lock"), and `clearBearer()`'s `runExclusive` is the *same* lock instance (`service.ts:265-270,286-287`). So a strict-toggle mid-unlock queues `clearBearer()` behind the very operation racing it — it runs immediately once that facade-locked section releases, and self-corrects the bearer. My F-2 trace claiming the bearer "sits on disk until the next explicit lock, TTL expiry, or browser-session end" is **wrong**; the real exposure window is a same-microtask-chain gap bounded by the tail of the in-flight facade-locked operation, not indefinite. Codex is not overconfident here — it simply didn't find the (much narrower) race at all. One soft spot in codex's own report: NF-8's completeness claim about strict-mode cleanup is stated without tracing this interleaving, though it is otherwise carefully hedged ("Cleanup is not unconditional").

**5. Net position.**
- **F-1** (unzeroized `getPasshash` bytes, `encryption-key.ts:122-125`) — kept, confidence **moderate** (down from high): codex's parallel NF-12 classifies the identical fact as a non-finding under the "defense-in-depth without a concrete vector" rule, and that's a fair reading: it needs a second, independent memory-disclosure primitive. I keep it as a finding because it's a concrete deviation from the package's own enforced control (not a generic "consider validating" note), but the classification is a judgment call, not a factual dispute.
- **F-2** (strict-mode/open() race, `session-manager.ts:253-341`) — kept but **substantially downgraded**: real gap in the code's "race-free" claim, but self-correcting via the shared facade lock; the exposure window is microtask-scale, not persistent. Confidence **low** (down from moderate).
