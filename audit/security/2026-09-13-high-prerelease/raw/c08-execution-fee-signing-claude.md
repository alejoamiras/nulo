### F-1: Chain-identity assertion only compares the XOR-composite, not the exact `(l1ChainId, rollupVersion)` tuple — a lying RPC can trivially get transactions and authwits signed under an arbitrary chain identity

**Impact factors**: Integrity/authentication of every signed transaction and authwit the wallet produces — a WYSIWYS ("what you sign is what you see") violation of the wallet's own "F-012" chain-identity binding control. A malicious or compromised/MITM'd RPC endpoint the wallet already trusts (a custom network the user added, or the operator of a default seeded endpoint such as the bundled third-party `lb.drpc.live` URL) can, at the moment of building/signing/discovering a transaction or authwit, report a **different** `(l1ChainId, rollupVersion)` pair than the network the user actually selected while still passing the wallet's own drift check — because the check only verifies `l1ChainId XOR rollupVersion === storedComposite`, never that the pair itself is the expected one. Blast radius: essentially every dApp-facing send/authwit/discovery/simulate path this cluster covers. Attack vector: network/RPC-position, not a dApp. Attack complexity: low (XOR inversion is one arithmetic step: `rollupVersion' = storedComposite XOR desired_l1ChainId'`, not a hard cryptographic problem). Privileges required: none beyond controlling or tampering traffic for an RPC endpoint the wallet already uses. User interaction: none beyond the user's normal approve-tx flow — the popup does not display the raw chain-identity pair, only the network's display name.

**Evidence confidence**: high — verified directly against source across ten independent call sites; the collision is a one-line arithmetic fact, not speculative.

**OWASP / CWE mapping**: CWE-345 (Insufficient Verification of Data Authenticity) primary, CWE-354 (Improper Validation of Integrity Check Value) secondary — a weak, collision-prone value is used in place of a real identity check. OWASP A08:2021 – Software and Data Integrity Failures (trusting unauthenticated external node data for a security-critical binding decision) primary, A02:2021 – Cryptographic Failures (missing domain separation) secondary.

**Trace**:
1. Source (untrusted): the RPC node's `getNodeInfo()` response (`l1ChainId`, `rollupVersion`), fetched fresh at every signing/proving/discovery site: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:220` (`resolveBuildContext`, feeds `buildStandard`) and `:404` (`buildNoFrom`); `apps/extension/src/wallet/services/execution/fast-path.ts:176` (`runFastPath`, the `aztec_simulateTx` fast path); `apps/extension/src/wallet/services/execution/authwit-discoverer.ts:106` (`discoverPrivateAuthwits`); `apps/extension/src/wallet/services/execution/discovery-probe.ts:73` (`CollectingDiscoveryProbe.extractEffects`); `apps/extension/src/wallet/services/execution/dapp-send-executor.ts:853` (`addDiscoveredNoFromAuthwits`, the NO_FROM kernelless-discovery authwit path); `apps/extension/src/wallet/services/execution/service.ts:872` (`executeAztecCreateAuthWit`); `apps/extension/src/wallet/services/execution/view-executor.ts:207` (`executeAztecGetChainInfo`, which reports the identity straight back to the dApp); `apps/extension/src/wallet/services/execution/service.ts:228-229` (the `operationEstimateReuse`'s `getLiveChainIdentity` closure, used at estimate-reuse consume time).
2. "Validation": every one of those sites passes the fetched `nodeInfo` (paired with the stored `network`) into `assertLiveChainIdentity` (`packages/aztec-runtime/src/utils/chain-identity.ts:53-61`), which computes `liveComposite = (nodeInfo.l1ChainId ^ nodeInfo.rollupVersion) >>> 0` and throws only if `network.chainId !== liveComposite`. It never compares `nodeInfo.l1ChainId` against `network.l1ChainId` (the exact value) — its own parameter type `SelectedNetworkChainInfo` (`chain-identity.ts:34-36`) is `{ chainId: number }` only, so the exact `l1ChainId` cannot even be threaded through without a signature change, even though every single caller holds a full `Network` object that already carries `.l1ChainId` (`apps/extension/src/wallet/services/network/spec.ts:39`, `:69`).
3. Sink: once the (unvalidated-beyond-composite) `nodeInfo` passes the check, the SAME raw pair is committed, unmodified, into the signed/reported artifact via `chainInfoFrom(nodeInfo)` (`chain-identity.ts:69-71`): `tx-request-builder.ts:286` (`finalizeStandardBuild` → `account.buildTxExecutionRequest`'s `chainInfo` param, becoming the `TxContext.chainId`/`version` inside the signed+proved `TxExecutionRequest` — consumed at `packages/aztec-runtime/src/account/nulo-account.ts:137-185`), `tx-request-builder.ts:414-418` (`buildNoFrom`'s inline `TxContext` construction), `service.ts:876-879` (`executeAztecCreateAuthWit`'s authwit `metadata`), `authwit-discoverer.ts:110/162/213/227` (its three message-hash helpers), `discovery-probe.ts:75`, `dapp-send-executor.ts:854-862` (the NO_FROM authwit's `computeAuthWitMessageHash` metadata), and `fast-path.ts:180-183`.

**Missing control**: an exact `l1ChainId` equality check (not just the lossy XOR composite) at signing/proving/discovery time, against a value the wallet actually trusts — either the stored `network.l1ChainId` or, for seeded networks, the in-code pinned constant. The data to close this already exists on every `Network` row (`network/service.ts:70` declares `l1ChainId: number` as a first-class field, populated/validated at network-add and endpoint-update time) — `assertLiveChainIdentity` simply never receives or uses it.

**Exploit story**: the user's network row has stored composite `C = network.chainId` and exact `L = network.l1ChainId` (both public knowledge — e.g. the well-known values for Aztec Mainnet/Testnet). The endpoint behind that network (a custom RPC the user added, or a trusted default endpoint that is later compromised/MITM'd/drifts) computes, for any target identity `L' ≠ L` it wants: `rollupVersion' = C XOR L'`. On the next `getNodeInfo()` call at signing/discovery time, it returns `{l1ChainId: L', rollupVersion: rollupVersion'}`. `assertLiveChainIdentity` computes `(L' ^ rollupVersion') >>> 0 = C` — matches the stored composite — **passes silently**. The wallet signs/proves a `TxExecutionRequest` or `AuthWitness` whose embedded chain domain is `(L', rollupVersion')`, not the user's real selected chain — while the popup still displayed the original network's name. At minimum this breaks the wallet's own documented "F-012: refuse to sign/prove against a drifted endpoint" invariant outright; if `(L', rollupVersion')` also happens to be a genuinely live chain's real identity (a free attacker choice for an attacker-seeded custom network at add-time, or a coincidence the attacker can search for against any deployment sharing the wallet's frozen-per-major account-address derivation), the signed artifact becomes directly replayable/valid there — the user's real key material moving value or granting authwit-consumable authority on a chain they never selected or saw.

**Preconditions**: the wallet must be pointed at (or have its network's endpoint later swapped to, or be MITM'd against) an RPC endpoint the attacker controls or can tamper responses from; the target network row is non-local (`chainId !== 0` — local networks intentionally skip the check and rely on the loopback-URL allowlist instead, a separate, adequately-scoped defense unaffected by this finding).

**Why mitigations fail**: the July remediation (PR #272, "C") fixed the *threading* problem (one validated `getNodeInfo()` reused consistently, never re-fetched mid-flow) — confirmed still intact everywhere traced above (no call site re-fetches after asserting) — but explicitly left the composite-collision question open (CONTEXT.md: "HELD at the time ... re-examine whether the collision is closed everywhere signed material is bound"). It is **not** closed: the assertion function itself, shared by all ten call sites, still only checks the composite. `network/service.ts`'s `addEndpoint`/`updateEndpoint` (`:565-572`, `:610-618`) already implement the correct exact-`l1ChainId` check, with a comment naming this precise collision ("The XOR composite alone is collision-prone ... endpoint mutations require EXACT L1 equality") — proving the team understands and has already fixed this weakness for endpoint ADD/EDIT — but that check runs ONCE, at the moment a URL is added or edited, and is never re-verified against the live node at the moment of signing, which is the only place that matters for what gets embedded in a signature. The `key-model-v2` fix (deriving account *seeds* from the exact `l1ChainId`) protects a different asset (which address a seed derives to, fixed once at account creation from a value verified by a live probe at that moment) — it does not protect this repeatedly-executed signing-time gate. The estimate-reuse cache's own "exact pair" comparison (`service.ts:227-232`, `operation-estimate-reuse.ts:144-147`) only detects drift *since the original (already unvalidated-beyond-composite) build* — no protection against the original build itself being fooled.

**Instances**: `packages/aztec-runtime/src/utils/chain-identity.ts:34-36` (the type omitting `l1ChainId`), `:53-61` (the function itself — root cause); `apps/extension/src/wallet/services/execution/tx-request-builder.ts:220-221`, `:286`, `:404-407`, `:414-418`; `apps/extension/src/wallet/services/execution/fast-path.ts:176-183`; `apps/extension/src/wallet/services/execution/authwit-discoverer.ts:106-110`, `:162`, `:213`, `:227`; `apps/extension/src/wallet/services/execution/discovery-probe.ts:73-75`; `apps/extension/src/wallet/services/execution/dapp-send-executor.ts:853-862`; `apps/extension/src/wallet/services/execution/service.ts:227-232`, `:871-879`; `apps/extension/src/wallet/services/execution/view-executor.ts:204-212`. Contrast (the correct pattern, NOT applied here): `apps/extension/src/wallet/services/network/service.ts:565-572`, `:610-618` (`addEndpoint`/`updateEndpoint` exact-`l1ChainId` check), `:991-1006` (`_probeChainIdentity`, which already returns both the composite AND the exact `l1ChainId` from one probe — the exact value is available, just not threaded to any signing-time assert).

### F-2: `buildNoFrom` registers the account and resolves+registers contracts in the local PXE store BEFORE validating live chain identity, unlike its sibling `buildStandard`

**Impact factors**: Integrity of the profile's persistent, per-`(profileId, chainId)` encrypted PXE store. A malicious/drifted RPC can get contract-instance/artifact data written into that durable local store during a build that is ultimately rejected once the (weak, per F-1) drift check finally runs — the registration is not rolled back. Attack vector: network (malicious/drifted RPC); complexity: low; privileges required: none beyond serving traffic for the endpoint; user interaction: triggering any `aztec_sendTx` with `executionMode: "default_entrypoint"` (the NO_FROM/DefaultEntrypoint dApp path) while the target network's endpoint is drifted/malicious.

**Evidence confidence**: high for the ordering defect itself (directly read, contrasted against the sibling function's own documented invariant); moderate for the full downstream consequence (exactly how a poisoned PXE-local contract row is or isn't re-verified on a later, legitimate build) since the PXE package's artifact-caching policy is outside this cluster's explicit scope.

**OWASP / CWE mapping**: CWE-696 (Incorrect Behavior Order) primary — the codebase's own stated design rule for this build-context family ("the drift assert runs BEFORE any resolver/registration/action work") is violated by one of its two implementations. OWASP A04:2021 – Insecure Design.

**Trace**: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:366-453` (`buildNoFrom`): `account.ensureRegistered(pxe)` at `:381`, then contract-instance/artifact resolution and `ensureContractsRegistered` (which calls `pxe.registerContract` for anything not yet known) at `:385-396` — all BEFORE `node.getNodeInfo()` + `assertLiveChainIdentity` at `:404-407`. Compare `resolveBuildContext` (`:213-230`, used by `buildStandard` and every `fee/*.ts` strategy): the assert runs at `:221`, immediately after fetching `nodeInfo` and **before** any resolver/registration call (`:222-228`) — matching the function's own docstring at `:208-212`: "The drift assert runs BEFORE any resolver/registration/action work — a malicious or drifted RPC endpoint must be rejected before it can shape the signing context."

**Missing control**: `buildNoFrom` should fetch `node.getNodeInfo()` and call `assertLiveChainIdentity` immediately after resolving `network`/`node` — before `ensureRegistered`/`resolveInstances`/`resolveArtifacts`/`ensureContractsRegistered` — mirroring `resolveBuildContext`'s order.

**Exploit story**: a dApp invokes `aztec_sendTx` with `executionMode: "default_entrypoint"` while the wallet's configured endpoint for that network has drifted or is malicious. `buildNoFrom` first calls into PXE to resolve+register every contract the dApp's calls reference (the node can supply self-consistent-but-wrong instance/artifact data for those addresses — it cannot forge the address itself, since PXE's own `registerContract` independently re-derives it from the preimage, see Non-finding #8, but it CAN supply a wrong-but-internally-consistent class/artifact for an address not yet locally known). That registration write lands in the durable per-chain PXE store. Only afterward does the build fetch `getNodeInfo()`/assert, which then throws and aborts *this* build — but the registration write already happened and is not rolled back. A later, legitimate build against the real endpoint for the same chain would read the PXE's now-poisoned local metadata for those addresses unless PXE independently re-verifies previously-registered contracts on every subsequent use (not confirmed either way within this cluster's scope — flagged as the residual uncertainty above).

**Preconditions**: a NO_FROM/DefaultEntrypoint dApp send while the target network's endpoint is drifted/malicious; the endpoint must supply data for at least one address not already registered locally.

**Why mitigations fail**: the fix is entirely local to this one function's statement order and is covered by no other control — `assertLiveChainIdentity` still runs, just too late to prevent the PXE writes; PXE's own address-derivation check (Non-finding #8) defends a different property (address↔preimage integrity) than this one (drift must not be allowed to touch PXE state at all before being caught).

**Instances**: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:366-453` (the one call path — no other build path shares this ordering defect; `resolveBuildContext`, used everywhere else including every `fee/*.ts` strategy, is correctly ordered).

### F-3: dApp-supplied gas limits and fee cap are honored verbatim (bounded only by the protocol's absolute admission ceiling, never by measured usage) even when the wallet's own account is the one paying

**Impact factors**: Integrity of the wallet's own documented fee-safety design (`DEFAULT_FEE_MULTIPLIER`, `predictedWorstMinFees`-based padding, `admissionCap`) — bypassable by dApp input on a **self-pay** ("fj"/"fjwc" — the WALLET's own account pays from its own held Fee Juice, not an external/embedded FPC) path that is explicitly not supposed to trust the dApp for fee sizing. Concretely: Aztec's own `GasUsed.billedGas` semantics bill the teardown phase at the committed `teardownGasLimits` **limit**, not actual usage, and the wallet clamps a dApp-supplied `gasLimits`/`teardownGasLimits`/`maxFeesPerGas` only against the protocol/node's absolute per-tx ceiling — never against "reasonable relative to what this call actually needs" the way an auto-derived (non-custom) limit is (padded from MEASURED simulation usage). Attack vector: application (any dApp with an active sendTx-capable session). Complexity: low — a standard, unauthenticated `aztec.js` `opts.fee.gasSettings` field. Privileges required: an ordinary dApp session with sendTx capability. User interaction: **required** (mitigating factor, honestly bounded below).

**Evidence confidence**: high for the mechanism; moderate for real-world exploitability given the required user-visible approval step and the protocol-level cap on the price component specifically.

**OWASP / CWE mapping**: CWE-770 (Allocation of Resources Without Limits or Throttling) primary, CWE-1284 (Improper Validation of Specified Quantity in Input) secondary. OWASP A04:2021 – Insecure Design (a self-pay path documented to bound the fee cap can have that cap bypassed by the untrusted party supplying the sizing input).

**Trace**:
1. Source: dApp-supplied `opts.fee.gasSettings.{gasLimits,teardownGasLimits,maxFeesPerGas}` on an `aztec_sendTx`/`aztec_simulateTx`/`aztec_profileTx` call, parsed unconditionally into `FeeOptions` **regardless of the classified fee-payer route** (`apps/extension/src/wallet/services/execution/operation-planner.ts:88-107` `feeOptionsOf`, called from `processAztecJsPayload` at `:221-222` — the fields are not gated on `embeddedFeePayment`).
2. This `FeeOptions` (`ctx.op.fee`) reaches `FeeJuiceStrategy.buildAndEstimate` (`execution/fee/fee-juice-strategy.ts:24-58`) and `FeeJuiceWithClaimStrategy.buildAndEstimate` (`fee-juice-with-claim-strategy.ts:20-45`) whenever the user's chosen `feeSettings.paymentMethod.kind` is `"fj"`/`"fjwc"` (`PREEXISTING_FEE_JUICE`/`FEE_JUICE_WITH_CLAIM` — the wallet's own account pays) — a classification independent of what gas-limit fields the dApp's payload happened to set.
3. `suggestGasLimits(built.txRequest, ctx.op.fee)` (`fee/fee-strategy.ts:180-203`, called at `fee-juice-strategy.ts:28` and `fee-juice-with-claim-strategy.ts:30`) sets the pre-simulation gas settings to the dApp's values verbatim.
4. `finalizeGasLimits(..., ctx.op.fee, ...)` (`fee-strategy.ts:255-313`, called at `fee-juice-strategy.ts:49-58` and `fee-juice-with-claim-strategy.ts:37`) → `resolveLimitLimb` (`:320-339`): a dApp-supplied `custom` limit is honored **verbatim** as long as it is `<= admissionCap` (`:209-211`, `Math.min(node.txsLimits, MAX_TX_DA_GAS/MAX_PROCESSABLE_L2_GAS)` — the protocol's absolute per-tx maximum). An auto-derived (non-custom) limit, by contrast, is `measured × gasPadding` — proportionate to real usage. The same verbatim-honoring applies to `finalizeGasLimits`'s `maxFeesPerGas` branch (`:266-268`: `if (customLimits?.maxFeesPerGas) { maxFeesPerGas = new GasFees(...) }`).
5. Sink: `getEstimatedFee(txRequest)` (`execution/tx-fee-details.ts:14-21`) computes `(gasLimits.total + teardownGasLimits.total) × maxFeesPerGas` from these final, dApp-inflatable limits — this is both what the popup displays AND what is billed on send (per `GasUsed.billedGas`'s own documented semantics: teardown is billed at the LIMIT, not actual usage).

**Missing control**: no bound comparing a dApp-supplied `gasLimits`/`teardownGasLimits` against MEASURED simulation usage (e.g., "a custom limit beyond Nx measured usage is rejected or requires extra confirmation") — only the flat protocol/node ceiling, which can be orders of magnitude above what a specific call actually needs. On the `maxFeesPerGas` sub-field specifically, this branch should be gated the same way `applyEmbeddedFpcGasCap` gates its own dApp-trust decision (only honored when `embeddedFeePayment` is set — a genuinely dApp/FPC-controlled payer — never for `fj`/`fjwc` where the wallet's own account pays and the multiplier padding exists specifically to protect it).

**Exploit story**: a malicious/compromised dApp calls `sendTx` with an innocuous-looking call (e.g. a normal token transfer) but sets `opts.fee.gasSettings.teardownGasLimits` near the node's advertised per-tx admission limit (and/or an extreme `maxFeesPerGas`). Because the payload embeds no fee-payer route, the user is shown the wallet's fee-method picker and selects "Pay with my Fee Juice" ("fj"). The popup's fee estimate correctly reflects the inflated commitment as a big-but-plausible-looking number; lacking a "this should be ~X for a simple transfer" baseline, the user approves. On send, the protocol bills the FULL committed teardown-gas limit (not the transfer's tiny real teardown cost) at the real market fee rate, debiting the user's own FeeJuice balance for the padded amount.

**Preconditions**: dApp has an active session + sendTx capability for the target account (an ordinary connection, no elevated privilege); user clicks Approve on the resulting (inflated but not obviously absurd) fee screen; user (or the default flow) has selected Fee-Juice self-pay rather than an FPC.

**Why mitigations fail / honest impact ceiling**: `assertCustomGasLimitsWithinCap`/`resolveLimitLimb`'s cap targets truly-impossible-to-include requests (the network's hard per-tx ceiling), not "sanity vs. this call's actual measured need" — inflation up to that (large) ceiling passes silently, and the only defense is the popup's absolute fee number with no relative/expected-range indicator. On the `maxFeesPerGas` sub-field alone (independent of the gas-limit vector above), the actually-*debited* amount is further capped at the protocol level regardless of the wallet: verified against `@aztec/stdlib`'s `computeEffectiveGasFees` (`src/fees/transaction_fee.ts`) — `effectiveFee = realProtocolBaseFee + min(maxPriorityFeesPerGas, maxFeesPerGas − realProtocolBaseFee)`, and the protocol asserts `maxFeesPerGas ≥ realProtocolBaseFee` or the tx is invalid — so an inflated `maxFeesPerGas` alone, with the wallet's own (non-dApp-controlled) `maxPriorityFeesPerGas` staying at its normal small/zero value (confirmed: no code path threads a dApp-supplied `maxPriorityFeesPerGas` into the actually-committed `GasSettings` for a real send — only the fast-path's simulation-only `completeFeeOptions` reads it, `packages/aztec-runtime/src/account/fee-options.ts:73-75`, never the real send), does not by itself increase what the user actually pays. This is why the finding is framed around the **gas-limit** (teardown-billed-at-limit) mechanism as the concrete fund-impact vector, with the `maxFeesPerGas` override treated as a real-but-bounded defeat of the wallet's own intended-cap invariant rather than an independent fund-drain.

**Instances**: `apps/extension/src/wallet/services/execution/operation-planner.ts:88-107`, `:221-222`; `execution/fee/fee-strategy.ts:180-203` (`suggestGasLimits`), `:209-211` (`admissionCap`), `:255-313` (`finalizeGasLimits`), `:266-268`, `:320-339` (`resolveLimitLimb`); `execution/fee/fee-juice-strategy.ts:28`, `:49-58`; `execution/fee/fee-juice-with-claim-strategy.ts:30`, `:37`; `execution/tx-fee-details.ts:14-21`. Contrast (an intentional, documented, narrower analog for the genuinely dApp-paid "embedded" route, NOT itself flagged): `execution/fee/embedded-fpc-cap.ts:71-82`.

### F-4: User-added FPC rows are validated only by function-name/arity duck-typing, not cryptographic contract identity — a malicious "Private Fee Juice" or "Sponsored FPC" row is indistinguishable from the canonical one

**Impact factors**: Confidentiality/integrity of the user's private-execution context. A user tricked into adding a lookalike FPC (e.g. by a phishing site's "add this fee-payment contract to your wallet" instructions) gets a row the Settings UI cannot visually distinguish from the audited canonical PrivateFPC/SponsoredFPC — same `type` enum, no code-identity indicator. Selecting it for a private send makes the wallet build+sign+send a transaction that invokes attacker-chosen Noir code inside the SAME kernel proof as the user's real transfer, under the account's own private-execution scope — every subsequent fee payment through that row runs silently as routine fee handling, not a fresh "are you sure" moment. Attack vector: requires user interaction (adding the address, then selecting/relying on it as the fee payer) via a same-extension Settings RPC — NOT directly dApp-reachable (`FpcService` methods are absent from `WalletSdkDispatcher`'s dApp-facing method list, and `feeSettings.paymentMethod.fpcId` is never a dApp-wire-suppliable field — see Non-finding #14), so the realistic vector is social engineering, not a remote RPC call.

**Evidence confidence**: high — verified directly by reading both FPC handler implementations and the `addFpc`/`updateFpcAddress` service methods.

**OWASP / CWE mapping**: CWE-345 (Insufficient Verification of Data Authenticity) primary, CWE-829 (Inclusion of Functionality from Untrusted Control Sphere) secondary. OWASP A08:2021 – Software and Data Integrity Failures.

**Trace**:
1. Source: an arbitrary `address` + `artifact` a user supplies via `addFpc`/`updateFpcAddress` (`apps/extension/src/wallet/services/fpc/service.ts:276-333`, `:352-408`).
2. "Validation": `getFpcHandler(type).validateArtifact(artifact)` — for `PrivateFpc` (`apps/extension/src/wallet/services/fpc/handlers/private-fpc-handler.ts:8-21`): checks the artifact merely HAS a `pay_fee()` function (0 params/0 returns) and ANY function literally named `balance_of` (no arity/visibility/type check at all); for `DefaultSponsoredFpc` (`apps/extension/src/wallet/services/fpc/handlers/default-sponsored-fpc-handler.ts:8-16`): checks for a `sponsor_unconditionally()` function (0 params/0 returns). Neither check verifies the contract's actual on-chain identity (bytecode class id derived from a known/pinned artifact+salt) the way the CANONICAL protocol rows are derived — `getContractInstanceFromInstantiationParams(artifact, {constructorArgs, salt})` from a vendored, pinned artifact (`fpc/service.ts:43-44`, `:109-121`) — real cryptographic identity, never applied to user-added rows.
3. Sink: `Fpc.getFeePayload(...)` unshifts a `call` to the attacker's contract's `pay_fee`/`sponsor_unconditionally` into the SAME transaction as the user's approved calls (`execution/fee/fpc-strategy.ts:129,170,241,265`), executed under `scopes: [account.address]` — i.e. inside the account's own private-execution context, alongside its real transfer.

**Missing control**: cryptographic contract-identity verification (class-id / instantiation-parameter check, as the canonical protocol rows get) for user-added FPC rows — currently only structural duck-typing on function names/arities.

**Exploit story**: attacker publishes a "faster/cheaper fee payment contract — add this address to your Nulo wallet" post. Victim adds it as a Sponsored FPC (only needs a `sponsor_unconditionally()` stub to pass validation). Victim later selects it (or it becomes their default/last-used FPC) for a private send; the wallet signs a transaction whose kernel proof includes a call into the attacker's arbitrary Noir logic, executed with the account's own private-execution authority.

**Preconditions**: user must be socially engineered into adding the malicious FPC address AND later selecting/relying on it for a transaction.

**Why mitigations fail**: the UI/storage model treats `type` (PrivateFpc/DefaultSponsoredFpc) as the only identity signal; there is no cryptographic pin comparable to the canonical rows'. `updateFpcAddress` does hard-block re-pointing an EXISTING `PrivateFpc` row's address ("Private Fee Juice FPC address cannot be changed") — but that only protects an already-trusted row from later tampering, not the initial `addFpc` add path, which accepts any address passing the duck-type check for either type.

**Instances**: `apps/extension/src/wallet/services/fpc/service.ts:276-333` (`addFpc`), `:352-408` (`updateFpcAddress`); `apps/extension/src/wallet/services/fpc/handlers/private-fpc-handler.ts:8-21`; `apps/extension/src/wallet/services/fpc/handlers/default-sponsored-fpc-handler.ts:8-16`; sink at `execution/fee/fpc-strategy.ts:129,170,241,265`.

## Non-findings

1. **Chain-identity threading (single validated `nodeInfo`, no re-fetch after assert) has no regression.** Every call site traced under F-1 (and `view-executor.ts`'s `executeSimulateTransaction`/`executeAztecSimulateTxStandard`/`executeAztecProfileTx`/`executeAztecExecuteUtility`, all of which route through `TxRequestBuilder.buildStandard` → `resolveBuildContext`) fetches `getNodeInfo()` exactly once and reuses that same object for both the assert and the downstream `chainInfoFrom`/authwit-metadata construction — the July TOCTOU fix (PR #272 "C") holds; the remaining gap is F-1's comparison operator, not the threading discipline, and F-2 is the one exception to the *ordering* discipline (registration before assert), not the threading one.
2. **`feeSettings.paymentMethod` (including `fpcId`) is never dApp-wire-supplied.** `Operation`/`DraftOperation`/`requiresFeeSelection`/`isEmbeddedFeePayment` (`packages/wallet-bridge/src/operation.ts`, `operation-validation.ts:30-56`) make `feeSettings` a field the popup (or the silent-path materializer) must fill in before an operation is executable; the standard aztec.js wallet-sdk wire shape a dApp actually sends carries no such field. A dApp therefore cannot force payment through an arbitrary FPC row the user did not choose.
3. **`additionalScopes`/`opts.scopes`/`exec.scopes` (used to widen PXE viewing-key scope in `simulateTx`/`profileTx`/`sendTx`/`executeUtility`) are validated against the session's approved accounts one hop upstream of this cluster.** `view-executor.ts` and `dapp-send-executor.ts` forward these dApp-supplied address arrays to `pxe.simulateTx`/`pxe.proveTx`/`pxe.executeUtility` without a local check — but `packages/wallet-bridge/src/scope-enforcement.ts:82-106` (`enforceScopeWithSession` → `validateAccountScopes`, called from `dispatcher.ts:713-721` for every dispatched method with any grants) rejects any entry in `exec.scopes`/`opts.scopes`/`opts.additionalScopes`/`eventFilter.scopes` that is not in the session's approved-account set (F-005) — this generic check is keyed on the `opts`/`exec` positional shape, not a per-method allowlist, so it covers `aztec_executeUtility` too (whose "account" *is* `opts.scopes`, per `dispatcher.ts`'s own comment at `:186-189`). Closes what would otherwise be a serious "read another account's private notes via `additionalScopes`" vector. A narrower residual (a capability originally scoped for account A being usable to read account B, if the dApp's SESSION already includes both A and B under any capability) is an accepted, documented tradeoff ("A dApp never learns which accounts it lacks" — per-session, not per-capability, account scoping), not a new gap.
4. **`executeAztecRegisterContract` (dApp-facing `aztec_registerContract`, `service.ts:823-864`) omits the `computeContractAddressFromInstance(instance) !== op.address` check its Nulo-base sibling `executeRegisterContract` (`service.ts:663-699`) performs explicitly — traced to the actual sink and RULED OUT.** Both paths ultimately call `PxeServiceClient.registerContract` → `packages/aztec-runtime/src/pxe/service.ts:432-451`, which independently re-derives the address from upstream's own `pxe.registerContract(instance)` preimage call and throws `"registerContract address mismatch"` if it disagrees with `instance.address` — defense-in-depth at the true source of truth, applied regardless of which extension-layer entry point (or `ContractResolver.ensureContractsRegistered`, used mid-build by every strategy) is used. (Initially flagged as a candidate finding and disproved by reading the PXE-layer sink directly, per the audit's "verify, don't speculate" instruction.)
5. **Register-sender (`registerSender`/`aztec_registerSender`) accepting any address**: intentional and low-risk — sender registration only lets PXE watch for incoming notes tagged to that address; it grants no execution/spend privilege.
6. **`register_token` executor** (`service.ts:706-779`): network binding is tied to the captured `ExecutionFence.profileId` (`network.profileId !== fence.profileId` throws "unauthorized profile"); the popup's pre-fetched `previewedInterface` hint is only trusted after checking it identifies the same `(contract, chainId)` the dApp asked to register, else falls back to a fresh `parseTokenInterface`. Metadata (name/symbol/decimals) is attacker-controlled by design (simulating the contract's own views) — the documented invariant is that the UI must render the address, not just the name (out of this cluster's direct scope, but the binding contract between the popup and this executor is intact).
7. **Auth-registry address spoofing**: `getAuthRegistryAddress()` (`apps/extension/src/wallet/utils/auth-registry.ts:21`) returns a hardcoded protocol constant; `buildSetAuthorizedCall` (`tx-request-builder.ts:519-535`) always targets it — a dApp's `add_public_authwit` action cannot redirect the `set_authorized` call elsewhere.
8. **`revokeAuthwits` cross-account revoke**: `auth-registry/service.ts:198-208` checks `authwit.account !== account` and treats a foreign id as nonexistent (no existence oracle) — correctly scoped.
9. **`assertWithinCap` TOCTOU** (`auth-registry/service.ts:141-150`, called pre-send from `tx-request-builder.ts:269`): confirmed the cap check is local-bookkeeping-only (never cross-checked against actual on-chain `approved_actions` state) and not atomic against concurrent builds. Not scored: this is a soft product ceiling ("Revoke some first" — storage-growth protection), not an authorization or fund-safety boundary; exceeding it by a few rows via a race causes no privilege escalation or fund loss.
10. **PrivateFPC salt drift vs bridge-core**: `fpc/service.ts:35-42`'s comment states the salt match is "machine-asserted [in bridge-core], layering bars the import here" — confirmed no runtime cross-check exists in this file. Not scored as a live finding (no evidence of an actual current drift); it's a latent maintenance risk, not an active exploit path.
11. **Kernelless private-authwit discovery "signs whatever the callee asks for"**: confirmed real (`AuthwitDiscoverer.discoverPrivateAuthwits`/`CollectingDiscoveryProbe` only turn REAL `CallAuthorizationRequest` offchain effects, emitted by simulating the exact operation the user is already authorizing, into signed authwits — no cross-check against what's shown in the approval popup) but not a new/incremental risk: (a) mirrors aztec.js's own documented kernelless-discovery pattern; (b) fires only for the SAME send/estimate op the user already approved, never independently dApp-triggerable, and never accepts dApp-supplied caller/contract/selector/args directly; (c) the stub-account bypass is confined to fold-eligible strategies (`fj`/`fpc`, never `fjwc`/`embedded`) and excluded whenever the op already carries a pre-attached private authwit (the F-4 guard in `discovery-aware-estimator.ts:99-101`); (d) discovered authwits are attached only to that one `txRequest` and never returned to the dApp over any RPC — no exfiltration path for reuse outside the approved tx.
12. **`createAuthWit`'s wildcard/raw-hash rejection (July remediation "A") holds, and the `canCreateAuthWit` capability's inherent breadth is a known, already-audited tradeoff.** `packages/wallet-bridge/src/method-scope-checkers.ts` hard-rejects a raw `Fr` message hash and scope-checks both `CallIntent` (contract+function against granted scope) and `IntentInnerHash` (contract-only, function wildcarded — accepted, documented, pre-existing). Re-verified the signed content cannot diverge from ABI truth: `service.ts:882-937`'s `executeAztecCreateAuthWit` binds `call.name` to the selector's real function and rejects a mismatch before hashing.
13. **`predictedWorstMinFees`'s full trust in the node's `getCurrentMinFees`/`getPredictedMinFees` response (`packages/bridge-core/src/fee-juice.ts:30-68`) is self-limiting.** Verified against `@aztec/stdlib`'s `computeEffectiveGasFees`/`computeTransactionFee` — the actual fee debited at settlement is `gasFees(real, protocol-enforced) + min(maxPriorityFeesPerGas, maxFeesPerGas − gasFees)`; a lying node can only cause either a rejected-at-inclusion tx (under-priced cap) or a needlessly padded commitment (over-priced cap), never additional actual debit beyond the protocol's own price — see F-3's "why mitigations fail" for the same formula applied to the `maxFeesPerGas`-override sub-issue. `DEFAULT_FEE_MULTIPLIER=2` is inclusion-safety padding, not a fund-safety boundary.
14. **Estimate-reuse caches serving a stale/poisoned estimate for a different operation**: both `TransferEstimateReuse.tryConsume` and `OperationEstimateReuse.tryConsume` re-validate a byte-stable canonical fingerprint of the exact inputs (`operation-fingerprint.ts`'s exhaustive, type-tagged, length-prefixed encoder — explicitly NOT `JSON.stringify`, which previously allowed field-collision bugs per its own changelog comments), plus profile id, primary-endpoint identity, pending-tx set, base-fee basis, and (for the operation cache) the exact live chain-identity pair and FPC identity snapshot. Every check is single-shot and any mismatch discards the entry and forces a rebuild. No gap found. `EstimateCancelRegistry` additionally caps concurrent estimate admission per profile (`MAX_ACTIVE_ESTIMATES_PER_PROFILE=4`/`MAX_PENDING_ESTIMATES_PER_PROFILE=8`), so a dApp cannot mint unbounded parked estimate work.
15. **Execution-lane mutex DoS ("wedge until SW restart")**: real and explicitly, deliberately accepted by the team (`execution-lane.ts:1-24`'s own frozen-invariant docblock: "no timeout by design ... silent overlap is worse — nullifier double-spends"). Confirmed `cancelJob` does NOT preempt an in-flight `pxe.proveTx` (bb.js/WASM proving cannot be interrupted) — a cancel only prevents SUBMISSION after the (wasted) proof resolves, so a malicious dApp submitting a maximally-expensive-to-prove operation could hold the `(profileId, chainId)` mutex for the full proving duration, blocking OTHER dApp sends on that profile+chain — bounded per-`(profileId, chainId)` (never cross-profile/cross-chain), backed by admission caps on the queue side (`EXECUTION_ORIGIN_CAP=8`, `EXECUTION_LANE_CAP=32`), never affecting the user's own popup Transfer flow (a documented "zero-slot" exception), and self-healing on the next MV3 service-worker restart (in-memory only, never persisted). No new mechanism found beyond what the code already documents as an accepted tradeoff.
16. **`transaction/service.ts`/`operation-journal/service.ts` persist no secret material** (no authwit witness bytes, no note plaintexts, no signing/viewing keys) — only tx metadata (calls as strings, hashes, fee figures, and — for the activity feed — transfer amount/recipient/token, all necessary local wallet-history data; `pendingPublicAuthwits`/`Authwit` rows store only the message hash + intent description, never the witness). `operation-journal` rows are profileId-scoped at create time (`NewOperationInput` requires `profileId`; `purgeForProfile`/`getOperations({profileId})` filter by it) — `getOperation`/`getOperations` with no filter don't enforce a caller-supplied profileId, but these RPCs are reachable only from same-extension trusted senders (`isTrustedInternalSender`-gated, never from a dApp page, which is confined to the separate content-script → wallet-bridge dispatcher relay) — not attacker-reachable. `transaction/service.ts`'s `Tx.profileId` is intentionally optional/shared: `getTransactions(account)` filters by on-chain address only (`:126-128`), and the service's own comments (`:99-107`) explain this is deliberate — tx history for a given on-chain account address is the same objective truth regardless of which local profile discovered it; the `ambiguous` flag and `isSoleOwner` logic (`:279-330`) show the team has already reasoned through the "two profiles hold the same address" edge case, plus deletion-epoch fencing (`:174-186`), restore-time create-only + hash-collision rejection (`:589-598`), and a hard "never restore a Pending row" rule specifically to prevent a backup-controlled `submittedEndpointUrl` from leaking a tx hash to an attacker-chosen RPC (`:579-588`). No new gap found.
17. **`fee/fpc-strategy.ts`'s two-pass and canonical-Sponsored fast-path choreography (action-array mutation via `unshift`/`splice`, stubbed-then-validated re-simulation under a discovery probe) matches its own extensive structural-parity intent** (mirrored by `fee-structural-parity.test.ts`/`strategies-structural.test.ts`, skimmed) — no divergent action-count, missing fee-payload, or discovery-bypass path found.
18. **`helpers/get-view-simulation-deps.ts`, `helpers/block-header-anchor.ts`, and `helpers/batched-view-simulation.ts` (668 lines, read in full)**: correctly derive ONE validated `chainInfo` via `assertLiveChainIdentity` and share it between the fast (direct-to-node) and slow (PXE) arms (`batched-view-simulation.ts:357-366`, `:546-549`) — explicitly engineered to avoid the "validate once, use an unvalidated second fetch for the other arm" bug class. Inherits F-1's XOR-composite weakness (no additional gap). Not dApp-reachable: the only callers are `gas-balance-reader.ts` (the wallet's own FeeJuice balance display) and the token-balance projector — same-extension, trusted-caller internal reads, never exposed to a dApp RPC.
19. **User-added FPC contracts are a user-consented trust decision at the point of `addFpc`/`updateFpcAddress`, but the validation weakness itself is scored as F-4 above** (not fully dismissed): the risk is real enough — and specific enough to how an FPC call is silently re-run on every subsequent fee payment inside the account's own private-execution scope, rather than requiring a fresh explicit approval each time the way a plain token add/spend does — to warrant a finding rather than a blanket "same as adding any contract" dismissal, even though it is not independently dApp-exploitable (see Non-finding #2).
