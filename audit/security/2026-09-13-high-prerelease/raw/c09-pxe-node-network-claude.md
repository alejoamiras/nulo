### F-1: Full-backup restore lets an attacker bind a spoofed RPC endpoint to a "canonical" seeded network identity (mainnet/testnet), enabling persistent, undetectable RPC-level MITM

1. **Title**: Backup-restore network rows skip the seeded-identity (`kind` ↔ `l1ChainId`) and live-endpoint validation that every other network-mutation path enforces, letting an attacker-crafted backup silently repoint "Alpha V5"/"Testnet" at a hostile RPC server while keeping the genuine, publicly-known `l1ChainId` — so restored accounts derive to the user's real, expected addresses with no visible trust signal that anything is wrong.

2. **Impact factors**:
   - *Impact*: Full **confidentiality** loss (the attacker's RPC sees every subsequent chain interaction for the affected network: which contracts are touched, fee/balance/tag queries, and the raw signed transaction bytes before broadcast) and **integrity**/**availability** loss (the attacker can serve fabricated balances/contract state/fee quotes, selectively withhold or drop the victim's transactions while returning a fake "success," and stage fake incoming-transfer events). Blast radius: the entire "mainnet"/"testnet" chain identity for the restored profile, not a single transaction — this is the network the wallet treats as authoritative for every future action until the user manually notices and fixes it.
   - *Exploitability*: Attack vector is a supported product flow (Import Backup) requiring the victim to import a file the attacker controls — a live scam category against wallet users ("import this backup to recover your wallet"). Attack complexity is low: the two values needed to keep the seeded-identity check trivially satisfied (`l1ChainId = 1` for Ethereum mainnet, `11155111` for Sepolia/testnet) are public, well-known constants, also hardcoded verbatim in this repo. No special privileges are required beyond social engineering; user interaction (running the import flow) is required.

3. **Evidence confidence**: High — full source trace to the exact write path, cross-checked against the existing test suite (which does not cover this case) and against an adjacent, already-shipped defense (the account↔network cross-check) whose own code comment independently confirms the authors know backup content is unauthenticated.

4. **OWASP / CWE mapping**: OWASP A08:2021 (Software and Data Integrity Failures) / A07:2021 (Identification and Authentication Failures, endpoint identity). CWE-345 (Insufficient Verification of Data Authenticity) and CWE-923 (Improper Restriction of Communication Channel to Intended Endpoint).

5. **Trace** (source → sink):
   - Source: an attacker-crafted `network` array inside a full-backup blob the victim is made to import.
   - `apps/extension/src/composables/useFullBackupImport.ts:475` creates a **fresh** profile (`restoreProfileStep`), then `useFullBackupImport.ts:485` rewrites every child row's `profileId` to the new id (`normalizeAllIds(data, "profileId", newProfile.id)`), then `useFullBackupImport.ts:488` calls `restoreNetworksStage(data, networkService, profileService, newProfile.id, io)`.
   - `apps/extension/src/composables/full-backup-restore.ts:267`: `restoreNetworksStage` calls `networkService.restore(data.network)`.
   - `apps/extension/src/wallet/services/network/service.ts:860-901` (`NetworkService.restore`): for each raw entry, calls `validateRestoredNetwork(raw, existing)` (`:885`) and on success writes it straight to storage (`:889` `this.storage.set(id, stored)`), pushing it into `existing` for the next entry's collision check.
   - `apps/extension/src/wallet/services/network/service.ts:1046-1059` (`validateRestoredNetwork`): only checks (a) new-shape presence, (b) `NetworkSchema.safeParse` (`spec.ts:187-196`) — which validates `kind` is one of `mainnet|testnet|devnet|local|custom`, `l1ChainId` is an in-range u32, and each endpoint's `rpcUrl` passes the scheme allowlist (`RpcUrlSchema`, `spec.ts:152-179`: any `https:` host, or loopback-only `http:`) — and (c) a `(profileId, chainId)` collision against `existing`. **It never calls `NetworkService.assertCanonicalStoredL1`** (`service.ts:346-355`), the one function that ties a seeded `kind` to its immutable `SEED_L1_BY_KIND` constant (`service.ts:58-62`), and never live-probes the endpoint.
   - Sink 1 — no collision possible on first import: because the target profile is brand new, no existing `(profileId, chainId)` row exists yet, so the collision check in step above never fires; the attacker's `{kind:"mainnet", l1ChainId:1, chainId:<attacker choice>, endpoints:[{rpcUrl:"https://attacker.example"}]}` row is persisted verbatim.
   - Sink 2 — legitimate defaults never get a chance to seed: `apps/extension/src/wallet/services/network/service.ts:232-262` (`getOrInitNetworks`): `if (existing.length) return existing` (`:242`). Because the profile now already has ≥1 network row, the three real `DEFAULT_SEEDS` (`service.ts:99-126` — the genuine dRPC-backed Alpha V5 mainnet, Testnet, Local Network) are **never seeded**. The attacker's row becomes this profile's permanent, only "mainnet".
   - Sink 3 — every later use trusts it: `execution/tx-request-builder.ts:213-229`, `network/service.ts:718-733` (`getNode`), and `packages/aztec-runtime/src/pxe/chain-runtime.ts:147` (`this.nodeFactory.createNode(network.rpcUrl)`) all dial `network.rpcUrl` — the attacker's server — for every fee estimate, contract lookup, note-tag scan, and transaction submission on this "chain".
   - `assertLiveChainIdentity` (`packages/aztec-runtime/src/utils/chain-identity.ts:53-61`) is satisfied trivially: the attacker chose both sides of the comparison — the stored composite `chainId` (free choice in the crafted row) and the live `(l1ChainId, rollupVersion)` their own node reports (solve `rollupVersion = l1ChainId XOR desired_composite`).
   - Because the attacker set `l1ChainId` to the real constant, key-model-v2 account derivation on this "network" produces the user's genuine mainnet address — the UI shows the address the user expects, with no visual difference from an honest install.

6. **Missing control**: (a) no re-application of `assertCanonicalStoredL1` (or equivalent) at the restore boundary to reject a `kind ≠ "custom"` row whose fields didn't originate from the trusted seed path; (b) no live-endpoint probe/verification at restore, unlike the equivalent user-facing mutation paths `addEndpoint`/`updateEndpoint` (`service.ts:549-640`), which both require a live probe to report the **exact** same composite **and** `l1ChainId` as the stored network before accepting any endpoint change (`:560-572`, `:607-618` — the code's own comment there names precisely this attack: *"The XOR composite alone is collision-prone... endpoint mutations require EXACT L1 equality"*); (c) no schema-level binding between `kind` and any endpoint/host property — `NetworkSchema` (`spec.ts:187-196`) treats `kind` as a free label with no cross-field refinement, and it is otherwise NEVER settable to anything but `"custom"` by any user-facing RPC (`addNetwork`'s params, `spec.ts:225-228`, accept only `name`/`rpcUrl`; `service.ts:432-460` hardcodes `"custom"`), making restore the sole reachable path where an outside party can mint a `kind: "mainnet"/"testnet"` row.

7. **Exploit / violation scenario**:
   1. Attacker builds a full-backup file from scratch (they choose their own password/passkey — no need to break the victim's real backup's encryption) containing one profile whose `network` array has one entry: `{id:"n1", profileId:"<any>", chainId:4248422646 /* CHAIN_IDS.MAINNET */, l1ChainId:1 /* MAINNET_L1_CHAIN_ID, public knowledge */, name:"Alpha V5", primaryEndpointId:"e1", endpoints:[{id:"e1", rpcUrl:"https://mainnet-rpc.attacker.example"}], kind:"mainnet"}`, plus a matching `account` entry whose `l1ChainId` also equals `1` (so it also passes the account↔network cross-check the code already performs, see item 9).
   2. Attacker delivers the file to the victim under a "recover your wallet with this backup" pretext and the victim runs the extension's Import Backup flow with the attacker-chosen password.
   3. `useFullBackupImport`'s staged restore (traced above) creates a fresh profile, restores the spoofed network row with no rejection, and never seeds the real defaults because the profile is no longer network-empty.
   4. The victim's Home screen shows a network still called "Alpha V5" holding the victim's own, correctly-derived mainnet address — nothing on-screen differs from a genuine installation.
   5. From this point on, every balance read, fee quote, incoming-transfer scan, and outgoing transaction for "mainnet" is served/witnessed/relayed exclusively by the attacker's endpoint.

8. **Preconditions**: the victim must import a backup file the attacker crafted or tampered with (social engineering against the wallet's own recovery UX) — not a pure remote/passive attacker. No knowledge beyond two public chain-id constants and how the wallet's backup JSON is shaped (both are visible in this repository) is required.

9. **Why mitigations fail**: the RPC-URL scheme allowlist (`RpcUrlSchema`) exists to block dangerous *schemes* (`javascript:`, `data:`, plaintext non-loopback `http:`, userinfo) — it was never meant to authenticate *who* runs a given `https://` host, so an attacker's own HTTPS server passes it trivially (confirmed against the existing `restore rejects entries with disallowed RPC schemes (A-04)` test in `apps/extension/src/wallet/services/network/service.test.ts:1231-1261`, which only exercises scheme-based phishing, never a `kind`-spoofed row). The XOR-composite chain-identity check (`assertLiveChainIdentity`) is defeated because the attacker controls both operands. The one check purpose-built for this — `assertCanonicalStoredL1`/`SEED_L1_BY_KIND` — is simply never invoked on the restore path (confirmed: zero references to either symbol across every `network/*.test.ts` file), and even where it IS invoked elsewhere (`getL1ChainIdStored`, `resolveVerifiedL1ChainId`), it would pass here regardless because the attacker deliberately sets `l1ChainId` to the genuine constant — the check defends against a *wrong* l1ChainId, not against a *right* l1ChainId paired with a *wrong* endpoint.

10. **Instances** (same root cause — the restore path bypasses the endpoint/identity binding every other write path enforces):
    - `apps/extension/src/wallet/services/network/service.ts:1046-1059` (`validateRestoredNetwork`)
    - `apps/extension/src/wallet/services/network/service.ts:860-901` (`restore()`)
    - `apps/extension/src/wallet/services/network/service.ts:232-262` (`getOrInitNetworks` all-or-nothing seed gate — the amplifier that makes the spoofed row permanent and exclusive)
    - `apps/extension/src/wallet/services/network/spec.ts:187-196` (`NetworkSchema` — no cross-field refinement binding `kind` to `l1ChainId`/`chainId`/endpoint)
    - `apps/extension/src/composables/full-backup-restore.ts:260-267`, `apps/extension/src/composables/useFullBackupImport.ts:475-488` (the reachable production entry point)
    - Corroborating evidence the class of bug was known but only half-closed: `apps/extension/src/wallet/services/account/service.ts:696-702` (the account↔network `l1ChainId` cross-check's own comment: *"the backup checksum is integrity-not-auth, so a doctored blob can carry a self-consistent (chainId, l1ChainId) pair"* — this check defends the ACCOUNT row's consistency against whatever network row already exists, but nothing defends the network row's endpoint itself).

    **Suggested direction** (not prescriptive): reject any restored network row whose `kind !== "custom"` unless its `l1ChainId` (and ideally its primary endpoint) matches an already-live, honestly-seeded row for that `(profileId, kind)`, or simply force every restored row to `kind: "custom"` and let `getOrInitNetworks` seed the three real defaults independently (a `kind` label should not be restorable at all, since it is otherwise a purely internal marker never accepted from any user-facing RPC).

### F-2: Node- and backup-sourced `ContractInstanceWithAddress` values are never anchored to the address they were resolved for — only to themselves — so a lying RPC or a doctored backup can make the wallet classify an arbitrary address as an instance of any contract class it can supply an artifact for

1. **Title**: `ContractResolver.resolveInstance`/`ensureContractsRegistered` and the direct `fpc`/`account-state` consumers of `pxe.getContractInstance` never check that the returned instance's own `address` field equals the address it was queried/keyed under. The only "verification" on this path — `PxeService.registerContract`'s address-preimage re-derivation — checks that the instance is *internally self-consistent* (its fields hash to its own claimed address), which a hostile source can always satisfy trivially (it is free to choose every field, including the address). This is a distinct, narrower, but still concrete gap from F-1: it is not closed by "registration throws on mismatch," because the mismatch that check detects is never the one that matters here.

2. **Impact factors**:
   - *Impact*: Integrity of contract-identity classification for any address the wallet has not already registered. Confirmed, unconditional consequence: a hostile node/backup can get an address accepted as "a legitimate instance of known class Y" (e.g. the compiled-in Sponsored FPC, or the bundled Token standard) in flows that only ask a yes/no classification question — `FpcService.addFpc`/`updateFpcAddress` (fee-relevant: the wallet stores `{address, type: SponsoredFpc}` in its own FPC list on this basis) and `AccountStateService.restore`'s contract-registration slice (a backup can plant a phantom "verified" contract entry). For flows that go on to actually *build and simulate/execute* a call against the misclassified address (`tx-request-builder.ts`, `authwit-discoverer.ts`), the practical ceiling is lower than it first appears: `ensureContractsRegistered`'s `pxe.registerContract(...)` call registers the ATTACKER'S OWN `instance.address` field (which the attacker is free to set to anything self-consistent, generally **not** equal to the address that was actually queried) — meaning the queried address itself is never genuinely registered in PXE, so any later attempt to actually simulate a *private* call against it should fail with "contract not found" rather than silently misexecuting (private execution needs the callee's real registered artifact to witness-generate). This bound is reasoned from Aztec's private-execution architecture, not independently verified against a running PXE in this pass — flagged as moderate, not high, confidence for that reason. The bound is weaker (or absent) for *public* function calls, where callee bytecode is applied by the network/AVM rather than the local PXE, so a wrong-artifact-derived selector could conceivably be sent to a real public function without a local "not registered" failure — this sub-case was not conclusively resolved either way.
   - *Exploitability*: attack vector is a malicious/compromised RPC endpoint (the shared third-party dRPC seed, any custom/backup-restored endpoint per F-1, or a MITM) for the node path, or a doctored backup for the account-state path. No cryptographic effort is required (the attacker computes a hash forward for a class id it already has an artifact for; it never needs to invert anything to land on a specific pre-existing address, because nothing checks that it did). Privileges required: none beyond controlling the RPC the wallet is currently configured to use, or getting a backup imported. User interaction: an ordinary interaction referencing a not-yet-registered contract address (dApp send, add-FPC, backup import) — no unusual action needed.

3. **Evidence confidence**: moderate — the missing address-anchor check is confirmed at the exact lines below by direct reading; the ultimate on-chain blast radius (private-call fail-closed vs. public-call residual exposure) rests on a reasoned inference about PXE's registration requirements for private execution that was not independently exercised against a live PXE in this pass.

4. **OWASP / CWE mapping**: OWASP A08:2021 – Software and Data Integrity Failures. CWE-345 (Insufficient Verification of Data Authenticity).

5. **Trace**:
   - Source (node path): `PxeService.getContractInstance` (`packages/aztec-runtime/src/pxe/service.ts:313-331`) falls through to `resolveInstanceFallback` (`:335-361`) on a PXE-local miss, calling `node.getContract(address)`. The only check on the result is `assertNotUpgraded` (`packages/aztec-runtime/src/pxe/effective-class.ts:33-42`), which compares two fields **both self-reported by the same untrusted node** to each other — not to any external anchor.
   - `ContractResolver.resolveInstance` (`apps/extension/src/wallet/services/execution/contract-resolver.ts:127-133`) calls `pxe.getContractInstance(address)` and returns `[contract, instance]` keyed by `contract` (the address string queried) with **no comparison** of `instance.address` to `contract`.
   - `ContractResolver.ensureContractsRegistered` (`contract-resolver.ts:164-185`) then does, for each `[contract, instance]` pair not already in `pxe.getContracts()`: `await pxe.registerContract({instance, artifact: artifacts.get(instance.currentContractClassId.toString())})`. This registers whatever `instance` claims — including its own `.address` field — **not** a re-keying under `contract`. `PxeService.registerContract` (`packages/aztec-runtime/src/pxe/service.ts:434-456`) derives an address from the instance's preimage fields and throws only if that derived value disagrees with `instance.address` itself (`:449-454`) — a check the attacker satisfies by construction, since they choose every input including `instance.address`. Nothing here, or anywhere in this call chain, ever compares `instance.address` (or the derived value) back to `contract`, the address the wallet actually asked about.
   - Sink 1 (fee-relevant, unconditional): `apps/extension/src/wallet/services/fpc/service.ts:292-305` (`addFpc`) and `:376-389` (`updateFpcAddress`) resolve a user-supplied FPC `address` via `pxe.getContractInstance(address)` → `getContractArtifact` → `ensureRegistered` (same registration pattern as above, `contract-resolver.ts:80-90`) → `fpcHandler.validateArtifact(fpcArtifact)`. `validateArtifact` checks only that the ARTIFACT (resolved via the untrusted class id) has the right shape for an FPC — never that `address` itself hosts that artifact. On success, `apps/extension/src/wallet/services/fpc/service.ts:311-318`/`:392-400`(approx.) persists `{address, type}` into the FPC list using the ORIGINAL user-supplied `address`, decoupled from whatever `instance.address` the registration step actually used.
   - Sink 2 (backup-sourced, unconditional): `apps/extension/src/wallet/services/account-state/service.ts:372-405` restores a backup's `contract.instance`/`contract.artifact` straight into `pxeService.registerContract(...)`. `precheckContractAddress` (`:444-456`) validates only that `contract.address` parses and isn't a protocol address — it never compares `contract.address` to `contract.instance.address`. `normalize.ts` (`apps/extension/src/wallet/services/account-state/normalize.ts:77-83`) explicitly defers "deep instance/artifact validation" to this same PXE registration step, which (as shown above) only proves internal self-consistency.
   - Sink 3 (execution path, bounded — see impact factors): `apps/extension/src/wallet/services/execution/tx-request-builder.ts:222-229` (`resolveBuildContext`) builds `instances`/`artifacts` from `op.actions`-derived addresses and calls `ensureContractsRegistered` before any selector is resolved (`:180-196`); `resolveCallFn` (`:537-544`) then resolves a `"call"` action's function purely by name off the (possibly misresolved) artifact, and `newCallFunctionCall` (`:546-561`) builds the real `FunctionCall` against `action.contract` — the TRUE address — with a selector derived from the wrong artifact's parameter types.
   - Contrast (the one place this is done correctly): `apps/extension/src/wallet/services/execution/service.ts:663-699` (`executeRegisterContract`, the `aztec_registerContract` dApp handler) independently recomputes `computeContractAddressFromInstance(instance)` and compares it to `op.address` — the caller's intended address — which is exactly the check missing everywhere else on this list.

6. **Missing control**: an explicit `computeContractAddressFromInstance(instance).equals(<the address being resolved/keyed under>)` check at the point an instance is consumed for classification (in `ContractResolver.resolveInstance`/`ensureContractsRegistered`, or upstream in `PxeService.getContractInstance`'s node-fallback branch), not only inside the dedicated `aztec_registerContract` handler.

7. **Exploit / violation scenario** (FPC add path, the sink with no execution-time backstop): victim has (or is told to add) a "Sponsored FPC" at some address `X` recommended by a phishing site or a compromised dApp. The wallet's currently configured RPC is malicious or compromised (independently reachable via F-1, or simply a MITM'd connection). `FpcService.addFpc(networkId, FpcType.DefaultSponsoredFpc, X)` calls `pxe.getContractInstance(X)`; the malicious node picks the compiled-in SponsoredFPC's real class id `Y` (one the wallet already has an artifact for), fabricates arbitrary `salt`/`initHash`/`publicKeys`/`deployer`, computes `Z := H(Y, salt, initHash, publicKeys, deployer)` (a forward hash, no inversion needed), and returns `{address: Z, currentContractClassId: Y, ...}` as "the instance at X" (nothing anchors the response to the query). `ensureRegistered`/`PxeService.registerContract` register `Z` (self-consistent, no throw); `fpcHandler.validateArtifact` accepts `Y`'s artifact shape; the wallet stores `{address: X, type: SponsoredFpc}` in the user's FPC list. The user now believes `X` is a wallet-validated, free/sponsored fee payer, when nothing has verified that claim against reality.

8. **Preconditions**: attacker controls or is on-path for the RPC endpoint the wallet is using (for the node-path sinks), or can get a doctored backup imported (for the account-state sink). No dApp cooperation required for the FPC sink beyond the user choosing to add an FPC address.

9. **Why mitigations fail**: `PxeService.registerContract`'s internal `derived.equals(instance.address)` check only proves the tuple is internally consistent — trivially satisfiable by an attacker free to choose every field, including `instance.address`; `assertNotUpgraded` compares two node-self-reported fields to each other, not to an external anchor; `ArtifactRegistry.verifyAndCache`'s class-id verification (`packages/aztec-runtime/src/pxe/artifact-registry.ts:203-215`) confirms the ARTIFACT matches the CLASS ID, which is a real, working control, but does nothing to confirm the class id itself is the one truly deployed at the address in question.

10. **Instances**:
    - `packages/aztec-runtime/src/pxe/service.ts:335-361` (`resolveInstanceFallback`, node path)
    - `packages/aztec-runtime/src/pxe/effective-class.ts:33-42` (`assertNotUpgraded`, self-referential check only)
    - `apps/extension/src/wallet/services/execution/contract-resolver.ts:80-90, 127-133, 164-185` (`ensureRegistered`/`resolveInstance`/`ensureContractsRegistered` — the shared unverified pattern)
    - `apps/extension/src/wallet/services/execution/tx-request-builder.ts:222-229, 537-544` (call-building consumer; bounded by PXE's own private-execution registration requirement, reasoned not verified)
    - `apps/extension/src/wallet/services/fpc/service.ts:292-305, 376-389` (`addFpc`/`updateFpcAddress` — unconditional, fee-relevant)
    - `apps/extension/src/wallet/services/account-state/service.ts:384-405, 444-456` (backup-sourced instances, `precheckContractAddress`)
    - Contrast (correctly implemented): `apps/extension/src/wallet/services/execution/service.ts:663-699` (`executeRegisterContract`)

## Non-findings

1. **XOR-composite chain-identity collision at signing time (Q1/CONTEXT.md flagged residual)** — closed at every real signing/proving call site: `assertLiveChainIdentity` is invoked immediately before `chainInfoFrom` in `execution/tx-request-builder.ts:221,407`, `execution/fast-path.ts:179`, `execution/view-executor.ts:211`, `execution/authwit-discoverer.ts:109`, `execution/service.ts:230,875`, and `execution/helpers/batched-view-simulation.ts:204,362`. The one place the pairing is absent — `apps/extension/src/wallet/utils/fn.ts:94` (`chainInfoFrom(await node.getNodeInfo())` with no preceding `assertLiveChainIdentity`) — is reached only from `token/service.ts:711,716,720` (`previewTokenMetadata`/`fetchTokenMetadata`, a read-only `simulateTx` with `skipFeeEnforcement:true` used purely to preview a token's self-reported name/symbol/decimals). That data is already fully attacker-controlled by design (`token/service.ts:669-671`: *"a malicious contract can return any name/symbol"*), so the missing assertion adds no exploitable capability beyond what's already documented and UI-mitigated (contract address always shown alongside).

2. **Node-sourced contract instance trust (Q1: is `verifyArtifactClassId` on the path for node-sourced instances?)** — promoted to **F-2** above after reconciling a disagreement between the two independent passes over this cluster: the first pass concluded this was closed because `ensureContractsRegistered`'s `pxe.registerContract(...)` call "throws on mismatch" before any selector is resolved. Re-tracing that check line-by-line shows it only verifies that a returned instance is *internally self-consistent* (its own fields hash to its own claimed `.address`) — never that `.address` equals the address the wallet actually queried for (the map key in `ContractResolver.resolveInstance`). An attacker who controls every field of a fabricated instance, including `.address`, satisfies that check trivially. See F-2 for the full trace, the reasoned bound on execution-path exploitability (likely fail-closed for private calls specifically, via PXE's own registration requirement — not independently verified against a live PXE), and the two sinks (`fpc/service.ts` FPC validation, `account-state/service.ts` backup restore) where no such execution-time backstop exists at all.

3. **Seeded-network `l1ChainId` pinning (Q3, live-read half)** — `assertCanonicalStoredL1` (`network/service.ts:346-355`) independently validates a seeded row's `l1ChainId` against `SEED_L1_BY_KIND` on every live read (`getL1ChainIdStored`, `resolveVerifiedL1ChainId`), closing the originally-flagged "only the composite is pinned" concern for the general case. The restore-time gap is F-1 above.

4. **RPC-URL allowlist bypass via alternate host encodings (Q2)** — verified empirically against the pinned Bun runtime: hex/octal/decimal/shorthand IPv4 spellings of `127.0.0.1` (`0x7f000001`, `017700000001`, `2130706433`, `127.1`), IPv6 zero-padding forms (`[::0001]`, `[0:0:0:0:0:0:0:1]`), and a trailing dot on an IPv4 literal (`127.0.0.1.`) all canonicalize to a recognized loopback spelling under WHATWG `URL` parsing and are accepted only because they genuinely are loopback — no bypass to a non-loopback host was found. A trailing dot on a *domain* (`http://localhost.`) is rejected (hostname stays `"localhost."`, fails the exact-match check) — fails closed, not a bypass. `https:` is intentionally unrestricted by host per the design (F-011), so IDN/homoglyph hosts are a non-issue there; under `http:` a homoglyph domain cannot punycode-collide with the literal `"localhost"`. Userinfo (`user@host`) is explicitly rejected (`spec.ts:167`). No port-range restriction exists, but no exploitable consequence of an unrestricted port was found for either scheme branch.

5. **PXE data isolation across profiles in the shared offscreen document (Q4)** — extensively fenced and, per code comments, previously hardened against exactly this class of bug. OPFS directories are namespaced `pxe/<profileId>/<chainId>` (`packages/aztec-runtime/src/pxe/chain-coordinates.ts:30-32`); the 32-byte store key is derived per-profile and handed out only while that specific profile is unlocked, with a post-HKDF re-check against a live generation read closing a delete-during-derivation race (`apps/extension/src/wallet/runtime.ts:536-554`); every PXE operation carries an explicit `(profileId, chainId)` plus a `pxeGeneration` fence independently re-validated inside `PxeService`'s own guards (`packages/aztec-runtime/src/pxe/service.ts:858-869` `assertGenerationCurrent`, threaded through `withPxeRead`/`withPxeWrite`). `NetworkService`'s coarser `nodes` cache (keyed by bare `chainId`) is cleared on every profile switch (`service.ts:905-910`), and the one historically-risky cross-profile leak (pending-tx polling falling back to the active profile's node) was already found and fixed, with the rationale documented in the fix itself (`getNodeForUrl`, `service.ts:735-757`). No path was found where `profileId` is inferred rather than explicitly threaded end-to-end from the SW-side caller.

6. **PXE RPC surface reachability from a dApp (Q5)** — `registerContractClass`, `clearChainState`, `clearProfileState`, and `provisionChainStoreKey` are `ipxe:false` in the descriptor table (`packages/aztec-runtime/src/pxe/descriptors.ts:43-69`), meaning they never reach the per-network `IPXE` facade `NuloAccount`/execution consumers use. A repo-wide grep confirms `registerContractClass` has zero extension-side call sites (dead/unreachable), and `clearChainState`/`clearProfileState`/`provisionChainStoreKey` are called only from their intended internal callers (`network/service.ts:827` chain-purge cascade, `profile-deletion/coordinator.ts:130`, `runtime.ts:487` SW-boot key provisioning) — none reachable from a dApp-facing flow.

7. **Incoming-transfer trust prompts / notification spam (Q6)** — reviewed directly. Trust state is keyed per `(profileId, networkId, contract)`; only the first `unknown → pending` transition emits `onIncomingTransferPending` (`incoming-transfer/service.ts:1180-1199`), so repeated transfers from an already-`pending`/`blocked` contract are persisted hidden with no re-emitted prompt (`:1231-1235`) — a malicious sender flooding transfers from one contract cannot spam the popup. New-contract prompts are additionally bounded because receive-scanning is scoped to contracts the user has already added as a token (`incoming-transfer/spec.ts:14-18`), which the attacker doesn't control. Cursor/watermark writes (`persistCursorLocked`, `service.ts:1351-1365`) are the sole writer, gated by the same service-lock + epoch fence used throughout the file, and are always fed cursor values already produced by the hardened `packages/aztec-runtime/src/pxe/public-events.ts` (page-ordering + checkpoint-hash-pinned validation) — no additional unvalidated-write path was found. Dust filtering (`isReceiptAboveDustThreshold`, `service.ts:572-606`) is an explicitly fail-open, display-only UX filter, not a security control, and amount/decimals display trusts token metadata the same (already-accepted, industry-wide) way registration does.

8. **Accelerator prover endpoint, `127.0.0.1:59833` (Q9)** — this is a third-party dependency (`@alejoamiras/aztec-accelerator`) whose own README explicitly documents the exact scenario asked about ("while the accelerator app is not running, any local process can bind the port... and receive whatever your dApp sends to `/prove` [the witness]"), states it is an accepted same-user-only trust boundary shared by every unauthenticated localhost dev service, and already implements the concrete mitigation (HTTPS-first probing against a name-constrained local CA, pinned against silent downgrade once HTTPS has been seen healthy, per its own README section "Security: local service discovery is shape-matched, not authenticated"). Nulo's own code only supplies `{host, port}` (`apps/extension/src/accelerator/config.ts`) and never speaks the wire protocol itself — no additional wallet-side gap was found beyond what upstream already discloses and defends, and this posture is already recorded in a prior independent hardening report the upstream README cites.

9. **`fetch.ts` timeout/retry amplification (Q9)** — bounded per-request timeout (60s default) via `AbortController`, plus a 3-attempt exponential backoff on 5xx/network errors only (4xx is terminal, `NoRetryError`); worst case a call occupies the caller for a few minutes against an unresponsive/malicious endpoint the user already selected — no amplification of outbound traffic to third parties. The caller-owned single-attempt variant (`makeSingleAttemptFetch`) is correctly used everywhere a bounded probe budget matters (`probeChainId`, `probeNodeStatus`).

10. **Notes decode robustness / cross-account visibility (Q7)** — `apps/extension/src/wallet/services/note/service.ts:117-147` isolates every note's parse in its own try/catch (`parseNote`), so a malformed or attacker-crafted note degrades to a `renderError` card instead of blanking the whole list or crashing. `fetchContractNotes` (`:169-175`) always passes `scopes:[account]` to `pxe.getNotes`; no code path was found that widens or omits that scope before returning notes to the popup.
