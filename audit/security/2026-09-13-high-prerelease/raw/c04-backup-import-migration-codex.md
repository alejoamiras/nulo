### F-1: Keyless imported accounts can erase another profile’s authorization records

1. **Title:** Hostile backup import triggers cross-profile deletion of the public-authwit revocation index.

2. **Impact factors:** Integrity and availability of authorization-management data. An attacker can erase existing authwit records and cached registry-enabled flags for chosen account addresses across profiles. This does **not** revoke the corresponding on-chain authorizations; it removes the wallet’s records needed to discover and revoke them. Vector: crafted backup file. Complexity: low. Privileges: no victim credentials or storage access required. User interaction: importing the supplied backup.

3. **Evidence confidence:** **High.** A read-only, in-memory probe using the actual restore, reconciliation, and auth-registry purge method bodies reproduced deletion of a pre-existing authwit and status flag. Storage, network, lifecycle, and event delivery were mocked; no browser or chain transaction was executed.

4. **OWASP / CWE mapping:** [OWASP A01:2025 — Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-863, Incorrect Authorization, included in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** Backup children are rebound to the newly created profile at `apps/extension/src/composables/useFullBackupImport.ts:485` → `AccountService.restore` accepts an imported account claiming an existing victim address because collision detection uses the full `(profileId, chainId, address)` tuple and does not prove possession of its key (`apps/extension/src/wallet/services/account/service.ts:689`, `:695`, `:700`, `:718`) → import unconditionally calls reconciliation at `apps/extension/src/composables/useFullBackupImport.ts:534`; reconciliation deletes keyless imported rows and emits `onAccountDeleted` (`apps/extension/src/wallet/services/account/service.ts:840`, `:850`, `:851`) → the auth-registry listener discards profile and chain identity (`apps/extension/src/wallet/services/auth-registry/service.ts:97`) → `purgeForAccounts` deletes every matching address’s authwits and status flag (`apps/extension/src/wallet/services/auth-registry/service.ts:432`, `:435`, `:442`, `:446`).

6. **Missing control:** Cleanup of address-shared authorization state does not check whether another live profile still owns the address. A newly imported account’s unproven address claim can therefore authorize destructive cleanup outside the importing profile.

7. **Exploit story:** An existing profile owns address `A` and has tracked public authwits. The attacker constructs a valid password-profile backup using their own entropy, master, and source DEK. They include a valid network and an account row with `type: 1`, `address: A`, matching network identifiers, and a valid index, but omit the optional `imported-account-keys` slice. They recompute the checksum. Import stores the account under the new profile. Reconciliation correctly identifies it as keyless, but its deletion event also erases the existing profile’s records for `A`. The authorizations remain valid on-chain, and their hashes cannot be enumerated back from the chain (`apps/extension/src/wallet/services/auth-registry/service.ts:115`).

8. **Preconditions:** The victim imports the file; a targeted address has existing local auth-registry state. The attacker must know the address, not its private key. Multiple claimed addresses can target multiple profiles in one import.

9. **Why mitigations fail:** Profile rebinding prevents direct writes under the victim’s profile ID, but the destructive sink is address-scoped. Zod checks row shape, and the network check establishes chain consistency rather than key ownership. Reconciliation itself supplies the deletion trigger. Authwit key-identity validation protects numeric row IDs, not ownership of a purge request.

10. **Instances:** The shared deletion sink is `apps/extension/src/wallet/services/auth-registry/service.ts:428`, reached from the account-deletion listener at `:97` and from `apps/extension/src/wallet/services/profile-deletion/coordinator.ts:120`. The coordinator builds its address snapshot from typed and raw account rows at `:86` and `:95`, so rollback, profile deletion, and abandoned-restore cleanup share the same ownership problem. The automatic hostile-backup trigger is `apps/extension/src/wallet/services/account/service.ts:835`.

### F-2: Imported-account row transplantation substitutes the signing account

1. **Title:** A valid imported-account row stored under another account’s key selects the wrong signer.

2. **Impact factors:** Authorization and signing integrity. An operation authorized for account `A` can produce an authwit signed by imported account `B` in the same profile and chain. Vector: tampering with extension local storage. Complexity: higher, because the reliable authorization-bypass scenario requires replacement after account resolution and before signer lookup. Privileges: ability to replace an account metadata row, without extracting its DEK or signing key. User interaction: an authorized signing operation, through an existing grant or confirmation. Fund loss was not demonstrated.

3. **Evidence confidence:** **High** for signer substitution. A read-only probe using the actual `getAccountContract` body returned the imported signer selected by the transplanted row rather than the requested address. The imported-key verification and authwit sink were verified in source; the probe mocked the signer loader and did not perform real Schnorr signing.

4. **OWASP / CWE mapping:** [OWASP A01:2025 — Broken Access Control](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/); CWE-863, Incorrect Authorization, included in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** The account root uses schema validation without key-identity matching (`apps/extension/src/wallet/services/account/service.ts:84`). An attacker copies account `B`’s serialized row beneath account `A`’s composite storage key, whose format is defined at `apps/extension/src/wallet/services/account/spec.ts:25` → `getAccountContract(P, C, A)` checks embedded profile and chain, but not embedded address, then dispatches the transplanted row to the imported loader (`apps/extension/src/wallet/services/account/service.ts:336`, `:337`, `:341`) → the loader retrieves and decrypts `B`’s legitimate key and compares its derived address with embedded `B`, not requested `A` (`apps/extension/src/wallet/services/account/service.ts:368`, `:378`, `:384`) → execution requests a contract for `op.accountAddress` and signs with the returned contract without rechecking its address (`apps/extension/src/wallet/services/execution/service.ts:869`, `:935`).

6. **Missing control:** Single-account reads do not require the complete requested tuple to equal the embedded tuple. The imported signing branch loses the original requested address before validating the recovered signer.

7. **Exploit story:** Profile `P` contains accounts `A` and imported `B` on chain `C`; `B` has a valid encrypted signing-key row. An operation is resolved and authorized for `A`. Before execution’s account lookup, the attacker replaces `nulo:core:accounts@["account","P",C,"A"]` with `B`’s valid account row, retaining embedded address `B`. The service accepts its matching profile and chain, decrypts `B`’s existing key, and produces `B`’s signature for the operation presented as belonging to `A`.

8. **Preconditions:** Raw local-storage tampering, an unlocked profile with a usable imported account, and control of the replacement timing. This matches the tampered-storage threat model in `implementations-plan/key-model-v2/plan.md:181`. A backup file alone cannot manufacture this physical-key mismatch because normalization derives keys from row identities.

9. **Why mitigations fail:** `liveRows` checks the full tuple (`apps/extension/src/wallet/services/account/service.ts:103`), but the signing lookup bypasses it. The imported-key repository correctly validates its requested tuple, but receives `B` after the account lookup has already substituted the identity. The loader’s address check consequently succeeds. Derived accounts are different: their branch compares the reconstructed address with the original requested address at `apps/extension/src/wallet/services/account/service.ts:351`. Upstream authorization remains bound to `A` at `packages/wallet-bridge/src/dispatcher.ts:994` and `apps/extension/src/wallet/services/dapp-interaction/service.ts:522`.

10. **Instances:** Incomplete account-tuple checks occur in `getAccount` at `apps/extension/src/wallet/services/account/service.ts:179`, `patchAccountField` at `:321`, `getAccountContract` at `:336`, and `exportAccount` at `:406`. The demonstrated signing substitution uses `:341` and `:368`; metadata mutation also follows embedded identity when writing at `:327`. The imported export branch instead retrieves the key using the original requested address at `:418`, so the same imported-signer substitution is **not** claimed for that branch.

### F-3: A restored noncanonical FPC replaces the built-in private fee target

1. **Title:** Backup-controlled `PrivateFpc` rows override canonical private Fee Juice selection.

2. **Impact factors:** Integrity and availability of private fee payment. A hostile row can make the built-in private fee option query an invalid or unrelated contract and become unusable despite a funded canonical PrivateFPC. A usable noncanonical contract can also become the selected fee-call target. Vector: crafted or modified backup. Complexity: low. Privileges: control of backup contents. User interaction: import, then use of private fee payment. Impact is confined to the imported profile’s affected chains; unrecoverable deposit loss was not demonstrated.

3. **Evidence confidence:** **High.** A read-only probe using actual restore, discovery/decoration, and fee-selection method bodies accepted a noncanonical row, appended the canonical row, and selected the noncanonical row despite `isProtocol: false`. Unknown balance disabled private fee payment. Discovery/PXE dependencies were mocked; no live contract execution was attempted.

4. **OWASP / CWE mapping:** [OWASP A08:2025 — Software or Data Integrity Failures](https://top10.owasp.org/2025/A08_2025-Software_or_Data_Integrity_Failures/); CWE-20, Improper Input Validation, included in the [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html).

5. **Trace:** `FpcService.restore` accepts `type: PrivateFpc` and any string address, strips `isProtocol`, and persists the row (`apps/extension/src/wallet/services/fpc/service.ts:503`, `:511`, `:522`, `:524`; schema at `apps/extension/src/wallet/services/fpc/spec.ts:35`) → `getFpcs` retains restored rows and appends missing canonical contracts (`apps/extension/src/wallet/services/fpc/service.ts:142`, `:158`, `:187`) → `buildFeeMethods` selects the first row by type alone and suppresses every other private FPC (`apps/extension/src/popup/components/modules/send/fee-helpers.ts:157`, `:161`) → the private option is disabled when that target’s balance is unknown or zero (`apps/extension/src/popup/components/modules/send/fee-helpers.ts:192`, `:203`). The matching balance-reader arm also selects the first row by type and calls its address (`apps/extension/src/wallet/services/execution/gas-balance-reader.ts:181`, `:184`); repeated failure becomes `null` at `:230`.

6. **Missing control:** Built-in private fee selection does not require the deterministic canonical address or the recomputed `isProtocol` flag. Restore also lacks an address-format or canonical-address check for this protocol-specific type.

7. **Exploit story:** Modify a plaintext passkey backup’s FPC slice to contain a single row with `type: 2`, a valid chain ID, name `Private Fee Juice`, and address `not-an-address`; preserve its credential and sealed DEK and recompute the checksum. After legitimate passkey import, discovery appends the real canonical FPC behind the hostile row. Both balance lookup and fee selection choose the hostile row. Its balance query fails, the private option becomes unavailable, and the genuine canonical row is excluded from separate selection. No passkey secret is needed to modify this metadata.

8. **Preconditions:** The malicious row precedes other private FPC rows on the selected restored chain. The availability case requires the user to need private fee payment; other fee methods may remain usable.

9. **Why mitigations fail:** Recomputing `isProtocol` correctly marks the hostile row false, but the consumers ignore it. Discovering the real protocol contract also succeeds without repairing selection order. The normal edit path’s private-FPC address restriction at `apps/extension/src/wallet/services/fpc/service.ts:362` does not cover restore. Balance failure handling prevents proceeding with an unknown balance but leaves the canonical funded option inaccessible.

10. **Instances:** Type-only selection occurs at `apps/extension/src/popup/components/modules/send/fee-helpers.ts:157` and `apps/extension/src/wallet/services/execution/gas-balance-reader.ts:181`; suppression of the legitimate alternative occurs at `fee-helpers.ts:161`. If the selected target supplies a usable balance, settings retain its ID at `fee-helpers.ts:92`; `apps/extension/src/wallet/services/fpc/service.ts:429` resolves it, and `apps/extension/src/wallet/services/fpc/handlers/private-fpc-handler.ts:23` generates `pay_fee` against its stored address. The canonical derivation itself at `apps/extension/src/wallet/services/fpc/service.ts:113` is consistent; this finding concerns selection.

## Non-findings

- **NF-1 — Export shape [high]:** The JSON envelope is `{ "wallet-version", "aztec-version", "compat-epoch": 4, "backup-schema-version": 1, "master-key", entropy?, "imported-keys-dek"?, "imported-keys-dek-sealed"?, "active-network-id"?, data, checksum }`; `data` contains `profile: {id,name,type}` plus the `network`, `account`, `imported-account-keys`, `transaction`, `token`, `token-balance`, `account-state`, `auth-registry`, `fpc`, `contact`, and `config` slices. Producers returning null/undefined are omitted. Password backups carry the base64 master, entropy, and source DEK; passkey backups carry a credential ID in `master-key` and a sealed source DEK. Imported signing-key rows remain encrypted under that DEK. Sources: `apps/extension/src/popup/pages/settings/security/export/full.vue:96`, `:213`; `apps/extension/src/utils/full-backup-helpers.ts:139`.

- **NF-2 — Encrypted metadata authentication [high]:** Encryption covers the entire compact JSON, including version fields, profile type, secret carriers, and checksum (`apps/extension/src/popup/pages/settings/security/export/full.vue:338`). The frame is base64 of `0 || IV[12] || AES-GCM ciphertext-and-tag`; the key derives through PBKDF2-SHA256, 600,000 iterations, from SHA256(password), with SHA256(IV) as salt (`packages/wallet-crypto/src/encryption-key.ts:15`, `:41`, `:122`). Metadata needs no separate AAD because it is inside the authenticated ciphertext. The only supported frame tag is zero (`:71`). Optional gzip and the filename sit outside this authentication.

- **NF-3 — Checksum and version steering [high]:** The checksum is SHA256 of `JSON.stringify(envelope-with-data-without-checksum)`, not the pretty-printed file bytes (`apps/extension/src/utils/full-backup-helpers.ts:144`). Import orders checksum → supported epoch → integer/range-checked schema version → migration (`apps/extension/src/composables/useFullBackupImport.ts:93`, `:104`, `:114`, `:121`, `:136`). Plaintext checksums are recomputable and provide no authenticity. `aztec-version` and `wallet-version` are descriptive, not compatibility gates. Production has no registered migrations beyond baseline, so changing version fields cannot select an existing weaker migration (`apps/extension/src/wallet/storage/migrations/index.ts:26`).

- **NF-4 — Master-secret routing [high]:** Outer decryption occurs in the UI at `apps/extension/src/composables/useFullBackupImport.ts:396`; the parsed top-level master never enters `migrateBackupData`, which receives only `backup.data` at `:136`. Password restore decodes the master/entropy, verifies their derivation relationship, and seals the destination profile (`apps/extension/src/wallet/services/profile/service.ts:2220`, `:2241`). Passkey restore recovers the secret through the ceremony and checks credential identity (`:2403`, `:2409`). No normal export/import path logging the top-level master was found.

- **NF-5 — Secret lifetime limitations [high]:** Password restore wipes explicit master, entropy, and passhash buffers in its cleanup (`apps/extension/src/wallet/services/profile/service.ts:2276`); imported-key rewrap wipes key bytes and both DEKs (`apps/extension/src/wallet/services/account/service.ts:795`, `:800`). Passkey pending secrets are wiped on finalization/deletion, but their 30-minute sweep is lazy and excludes the currently finalized ID (`apps/extension/src/wallet/services/profile/service.ts:183`, `:2561`, `:2687`). UI decryption buffers/passhash are not explicitly wiped, and parsed base64 strings survive until selection reset or collection (`apps/extension/src/composables/useFullBackupImport.ts:390`, `:398`, `:797`). This is not guaranteed zeroization; no new unauthorized memory-reader path was established, and pending-secret lifetime was explicitly excluded by the prior audit.

- **NF-6 — Profile and account boundaries [high]:** Restore binds the secret discriminant to profile type and constructs a fresh destination profile (`apps/extension/src/wallet/services/profile/service.ts:2176`); every child `profileId` is overwritten with its actual destination ID (`apps/extension/src/composables/useFullBackupImport.ts:485`). Thus backup rows cannot directly graft accounts under a pre-existing victim profile ID. Account restore validates type, bounded index, u32 L1 identity, nonempty address, network agreement, and duplicate full tuples (`apps/extension/src/wallet/services/account/service.ts:689`, `:695`, `:700`, `:710`, `:715`). It does not prove imported-account key ownership before persistence; the resulting cross-profile cleanup failure is F-1.

- **NF-7 — Imported signing-key slice [high]:** Restore schema-validates key rows, decrypts them using the source DEK with chain/address binding, and reseals under a fresh destination DEK (`apps/extension/src/wallet/services/account/service.ts:778`, `:784`, `:790`). It does not recompute the account address during rewrap or require an accompanying account row. A mismatched recovered signing key is rejected when loading the account for signing (`:384`); retained ciphertext does not itself establish control of a victim’s key.

- **NF-8 — Restored network endpoints [high]:** `validateRestoredNetwork` uses strict `NetworkSchema` and rejects existing `(profileId, chainId)` collisions (`apps/extension/src/wallet/services/network/service.ts:1046`). Unsafe schemes, userinfo, and non-loopback HTTP do not regain acceptance through restore. Arbitrary permitted HTTPS endpoints remain importable; restore does not establish that their operators are trustworthy or probe every endpoint. Endpoint-ID uniqueness and a valid `primaryEndpointId` reference are not schema refinements. These limitations do not demonstrate a new F-011 scheme-validation regression.

- **NF-9 — Token slice [high]:** Restore applies `TokenSchema`, allocates fresh numeric IDs, and checks destination-chain liveness before and after persistence (`apps/extension/src/wallet/services/token/service.ts:808`, `:813`, `:821`, `:827`). Token metadata and configured function names are not re-derived from chain during restore; spoofed names, symbols, and other schema-valid metadata can be planted in the imported profile. No independent executable injection or authorization bypass was established from these fields.

- **NF-10 — Token-balance slice [high]:** Restore requires an owned destination token, rejects duplicate `(token, account)` pairs, validates `TokenBalanceRawSchema`, and overwrites profile/chain/contract identity from the destination token (`apps/extension/src/wallet/services/token-balance/service.ts:695`, `:705`, `:710`). The import coordinator filters account/chain membership before this stage (`apps/extension/src/composables/useFullBackupImport.ts:515`). Amounts and timestamps remain backup-supplied cached data rather than verified chain balances; cross-profile token-identity grafting was not reproduced.

- **NF-11 — Transaction slice [high]:** The coordinator filters restored transactions through imported account/chain membership, and the service applies `TxSchema`, rejects Pending status, and refuses existing hash keys (`apps/extension/src/wallet/services/transaction/service.ts:586`, `:593`, `:598`). Historical metadata and hashes are not independently verified against chain. Restored historical rows do not become pending polling jobs, so an imported `submittedEndpointUrl` does not by itself trigger the previously identified pending-transaction RPC path.

- **NF-12 — Auth-registry slice [high]:** Restore validates `AuthwitSchema`, deduplicates `(account, hash)` against raw existing rows, and allocates safe unoccupied numeric IDs (`apps/extension/src/wallet/services/auth-registry/service.ts:475`, `:489`, `:504`, `:510`). Rows have no profile/chain ownership fields, and their content/hash is not proven on-chain during restore. The address-membership assumption is insufficient in F-1. Restore intentionally has no normal grant-count cap (`:470`); the previously reviewed pending-row inflation issue is not repeated as a new finding.

- **NF-13 — dApp grant minting through backup [high]:** dApp sessions are absent from both the export producers and backup-slice registry (`apps/extension/src/popup/pages/settings/security/export/full.vue:96`; `apps/extension/src/wallet/services/backup/backup-migration-registry.ts:198`). Unknown slices are rejected at registry `:260`. Backup import therefore cannot restore a broad-grant session and have its MAC recomputed under the destination profile.

- **NF-14 — Config allowlist regression [high]:** Restorable keys are exactly `theme`, `sidePanel`, `showNode`, `showPopupFullscreen`, `disableAnimations`, `defaultExplorer`, `incomingTransfersVisible`, and `indicateFailures` (`apps/extension/src/wallet/services/config/spec.ts:14`). Service restore enforces this set, and `ConfigStore.set` validates the selected key’s schema (`apps/extension/src/wallet/services/config/service.ts:68`; `apps/extension/src/wallet/config/store.ts:55`). `strictSecurityMode`, session TTL, and diagnostic/security toggles cannot be restored through this path; July remediation E holds.

- **NF-15 — Full-backup contacts [high]:** Contact restore reallocates occupied IDs, checks `ContactSchema`, and applies the destination-profile fence (`apps/extension/src/wallet/services/contact/service.ts:299`, `:303`, `:304`). This path does not apply standalone contact-import address validation or name/count limits. Schema-valid lookalike names and arbitrary address strings can be stored, but no HTML execution or automatic transfer follows from importing them; full-backup authenticity is not assumed.

- **NF-16 — Account-state slice [high]:** The explicit normalizer caps input items at 16, networks at 8, senders at 64/network, contracts at 32/network, and serialized slice size at 40 Mi UTF-16 code units (`apps/extension/src/wallet/services/account-state/normalize.ts:14`). Restore scans at most 64 supplied networks, retaining schema-valid rows (`apps/extension/src/wallet/services/account-state/service.ts:282`), and the coordinator passes successfully restored destination networks. Nested artifact/instance objects are not fully validated by the normalizer; they reach PXE registration. Protocol addresses 0–6 are skipped (`:444`). No arbitrary extension-storage-root write was established.

- **NF-17 — Torn restore and activation [high]:** Full restore is deliberately not an all-or-nothing transaction: per-row failures can leave a completed, partially populated profile. Before finalization, however, the marker precedes profile persistence (`apps/extension/src/wallet/services/profile/service.ts:1358`), and matching or corrupt markers block ordinary session opening (`:1218`). Finalization clears the marker at entry after the coordinator’s storage-slice phase (`:2579`; `apps/extension/src/composables/useFullBackupImport.ts:524`, `:546`). PXE account-state restoration follows activation at `:557`, so a later crash can leave incomplete PXE state. That is distinct from unlocking an unfinished pre-finalization import.

- **NF-18 — Concurrent restore/deletion [high]:** There is no global whole-import mutex; separate UI instances can interleave restores. Account collision checks and writes share a restore lock (`apps/extension/src/wallet/services/account/service.ts:680`), profile operations serialize, and service restore fences check captured deletion epochs. Abandoned-profile deletion also rechecks both generation and the exact observed marker under the profile lock (`apps/extension/src/wallet/services/profile/service.ts:1299`). No additional same-profile overwrite or stale-sweep race was established; the address-shared cleanup exception is F-1.

- **NF-19 — Backup migration isolation and footprint [high]:** Normalization accepts only registered slices and rejects duplicate row anchors (`apps/extension/src/wallet/services/backup/backup-migration-registry.ts:260`, `:339`). It seeds a new `MemoryStorageArea`, and the migrator receives that scratch store exclusively (`apps/extension/src/wallet/services/backup/backup-migrator.ts:102`). Pending migrations must be branded backup-safe and avoid blocked/uncovered roots (`:165`, `:186`, `:192`). Commit guards reject undeclared writes and engine-reserved keys (`packages/wallet-core/src/migration/migrator.ts:288`). A migration failure cannot half-write the live store through this import path.

- **NF-20 — Journal validation, idempotence, and breaking default [high]:** Journal recovery checks backup/ref structure and registered version bounds (`packages/wallet-core/src/migration/migrator.ts:84`, `:328`, `:336`). Recovery is not authenticated and does not require every restored entry to fall inside its declared refs (`:390`), but backup normalization cannot inject a live migration journal, and arbitrary live-store mutation already requires the relevant storage privilege. `breaking` defaults true (`packages/wallet-core/src/migration/types.ts:72`). Run-twice safety is checked by the test/DSL machinery, not by automatically executing every production migration twice (`apps/extension/src/wallet/services/backup/footprint-coverage.test.ts:200`; `backup-migrator.test.ts:85`).

- **NF-21 — Storage identity inventory [high]:** Generic identity matching is enabled for profiles (`apps/extension/src/wallet/services/profile/repository.ts:46`), authwits (`auth-registry/service.ts:76`, numeric), and balances (`token-balance/balance-repository.ts:33`, numeric). It is absent for accounts, imported keys, networks, tokens, contacts, FPCs, transactions, and the underlying dApp-session EntityStorage; imported keys instead manually check the full tuple (`apps/extension/src/wallet/services/account/imported-keys-repository.ts:27`, `:43`), and dApp sessions have a MAC wrapper. Copying profile B’s network/contact row under profile A’s physical key fails A’s direct ownership check, while B’s bulk reads can still see its embedded identity and purges can trust embedded IDs (`apps/extension/src/wallet/services/network/service.ts:483`, `:923`; `apps/extension/src/wallet/services/contact/service.ts:136`, `:258`). Transaction lookup similarly trusts an embedded hash (`apps/extension/src/wallet/services/transaction/service.ts:134`). These are not additional demonstrated privilege escalations; the concrete signer exception is F-2. Invalid rows are kept but hidden by `EntityStorage`, and raw occupancy remains visible to allocators.

- **NF-22 — UI storage facade [high]:** Searching `popup`, `onboarding`, `stores`, and `composables` for direct Chrome/browser local-storage access found only comments mentioning `chrome.storage.local`. Actual facade access waits for the migration marker and rechecks after subscribing (`apps/extension/src/utils/storage.ts:32`, `:46`, `:68`). Its documented check-then-act window remains; it is not a mutual-exclusion lock. No current production migration exploit through a UI bypass was established.

- **NF-23 — Standalone contacts and file bounds [high]:** Standalone import accepts a legacy array or `{version:2, contacts:[...]}`, with 1,000,000-byte and 512-row limits (`apps/extension/src/utils/contacts-export-format.ts:38`). The picker carries the decompression cap; normalization limits names/addresses to 20/66 characters and deduplicates lowercase addresses (`apps/extension/src/popup/components/modules/settings/contacts/useContactImportExport.ts:120`, `:175`). The popup rejects non-64-digit hexadecimal addresses, renders escaped Vue text, and explicitly warns about replacement by matching name/address (`apps/extension/src/popup/components/popups/ImportContactsPopup.vue:125`, `:160`, `:203`). Hex syntax is not proof of an actual Aztec account or protection against lookalikes. The legacy service import is weaker, but the inspected popup uses this staged path. Full backups have a separate 64 MiB file/decompression ceiling; most ordinary slices lack individual row-count caps, but no concrete bypass of the common size limit was established.

## Handoff edges followed

- **Import → account reconciliation → deletion event → auth registry:** Followed the real coordinator call and immediate event listener into address-scoped purge; establishes F-1.
- **Profile deletion → dependent-service purge:** Followed the address snapshot into `AuthRegistryService.purgeForAccounts`; confirms the second F-1 entry path.
- **dApp authorization → account resolver → authwit execution:** Checked account binding at `packages/wallet-bridge/src/dispatcher.ts:986` and `apps/extension/src/wallet/services/dapp-interaction/service.ts:520`, then signer selection and the immediate signing sink. No `packages/bridge-core` body was inspected.
- **FPC service → fee selector / balance reader → fee payload:** Followed both type-only consumers and the private handler’s immediate `pay_fee` target. No bridge deposit or unrecoverable-loss claim is made.
- **Account-state restore → PXE registration:** Checked destination-network selection, normalization limits, and immediate registration preparation; deeper PXE internals remain outside this cluster.
- **Validation performed:** Three read-only in-memory method probes reproduced the reported behaviors. Required backup tests and profile restore cases were inspected. Full browser, integration, and on-chain suites were not executed; no files were modified.
