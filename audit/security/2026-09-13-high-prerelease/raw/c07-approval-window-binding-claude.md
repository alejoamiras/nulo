### F-1: Approval-popup "truthful display" for token transfers is defeated by a stale method-name/arity allowlist — the standard token contract's own `transfer` call shows no recipient or amount

1. **Title**: `parseTransferIntent`'s hardcoded transfer-method allowlist and fixed arity checks are out of date with the wallet's own token-function model, so the flagship "show what you sign" anti-phishing control for `aztec_sendTx` silently no-ops on the single most common real-world call — a standard token transfer.

2. **Impact factors**: Integrity/confidentiality-of-intent violation on the wallet's core "what you see is what you sign" control (CIA: Integrity of the user's informed-consent decision). Blast radius: every `aztec_sendTx` approval whose call uses a transfer method name outside a 4-name legacy allowlist — which, per the wallet's own token-function descriptor table, is most current token contracts, including the pinned `@aztec/noir-contracts.js` standard `Token` contract's own `transfer(to, amount)` method. Exploitability: network-adjacent is not required — attack vector is the wallet-sdk RPC surface any origin the user visits can reach (`sendTx`); attack complexity is low (any dApp just calls the standard method as documented); privileges required: none beyond an established dApp session with a "transaction" capability grant (routine for any connected dApp); user interaction: required (the user must click Confirm), but the interaction is the exact thing being deceived — the popup shows a confident-looking label ("Transfer (private)") with the recipient and amount omitted, so the "informed" part of informed consent is missing precisely where it matters most.

3. **Evidence confidence**: High. The code paths, the arity mismatch, and the real contract's function signatures are all directly inspected (see trace).

4. **OWASP / CWE mapping**: CWE-451 (User Interface (UI) Misrepresentation of Critical Information); OWASP A04:2021 – Insecure Design (the audit's own browser-extension-specific category calls this out by name: "what-you-see-vs-what-you-sign").

5. **Trace**:
   - Source (untrusted input): a dApp calls the wallet-sdk `sendTx(exec, opts)` RPC with a call whose `name` is the *real* Aztec standard token contract's private transfer method, `transfer(to, amount)` (2 args, no `from` — msg_sender is implicit). Confirmed against the repo's own pinned `@aztec/noir-contracts.js` `Token` artifact: the `transfer` function is present with exactly `[to, amount]` user parameters. `handleSendTx` forwards the raw `args[0]` object verbatim as `sendOp.exec` (`packages/wallet-bridge/src/dispatcher.ts:941,946-952`) after only a structural `{to, name}` shape check on `.calls` (`assertAuthRelevantArgShape` → `assertExecCalls`, `packages/wallet-bridge/src/dispatcher.ts:582-589,606-608`) — the method *name* and *arity* are never checked against a known-safe set at this layer.
   - The request reaches the approval popup as `payload.params.operations[i].exec.calls[j]` and is rendered by `apps/extension/src/popup/windows/execute/OperationCard.vue:110-157`. For each call it computes `parseTransferIntent(call)` (`apps/extension/src/utils/transfer-intent.ts:57-69`) and only renders the structured "From / To / Amount" block when the result is not `"unverified"` (`OperationCard.vue:135`); otherwise it renders only `humanizeMethodName(safeWire(call.name ?? call.selector, 64))` + the contract address (`OperationCard.vue:126,128`).
   - `parseTransferIntent` recognizes exactly 4 transfer names — `transfer_in_private`, `transfer_in_public`, `transfer_to_private`, `transfer_to_public` (`apps/extension/src/utils/transfer-intent.ts:23`) — and, for any of them, requires **exactly 3** args (`from, to, amount`) via `parseTransferArgs` (`apps/extension/src/utils/transfer-intent.ts:71-72,`"`args.length !== 3`"`). The plain `transfer` method name is **not in the set at all**, so `parseTransferIntent({method: "transfer", args: [to, amount]})` returns `{kind: "unverified"}` unconditionally (`apps/extension/src/utils/transfer-intent.ts:60-66`) — the arity check is never even reached.
   - Sink: `OperationCard.vue`'s `v-if="parseTransferIntent(call).kind !== 'unverified'"` (`:135`) is false, so the popup renders **no recipient, no amount** for this call — only `Transfer (private) on <contract address>` (the label comes from a *different*, broader table, `apps/extension/src/utils/tx-enrichment.ts:16-31`, which does list `transfer: "Transfer (private)"` at `:17` — a friendly, confident-looking label that gives the user no reason to suspect anything is hidden). The user clicks Confirm having seen only the contract address and a method label; `approve()` (`apps/extension/src/popup/windows/execute/index.vue:389-467`) forwards the untouched call (including its real `to`/`amount` args) to `interactionService.approveInteraction(...)` and it executes exactly as submitted.
   - Corroboration that this is a live drift, not a deliberately narrow scope: the wallet's own token-function registry (`apps/extension/src/wallet/services/token/functions/descriptors.ts:309-420`) recognizes and prioritizes as *more canonical* several transfer names `parseTransferIntent` does not know at all — `transfer` (private, score 101, arity-2, `descriptors.ts:362`), `transfer_public_to_public` (score 102, `:337`), `transfer_private_to_private` (`:361`), `transfer_public_to_private` (`:386`), `transfer_private_to_public` (`:407`) — and its own `buildArgs` for the two-variant descriptors documents the *actual* arity split the wallet uses when constructing these calls itself: 2 args (`[to, amount]`) for the 2-param variant, 4 args (`[from, to, amount, Fr.zero()]`, note authwit nonce) for the 4-param variant (`descriptors.ts:322-325`) — never 3. Cross-checked directly against the pinned `@aztec/noir-contracts.js` `Token` artifact (`token_contract-Token.json`): `transfer(to, amount)` = 2 params; `transfer_in_private/in_public/to_public(from, to, amount, authwit_nonce)` = 4 params; `transfer_to_private(to, amount)` = 2 params. None of the 4 "known" names actually carries exactly 3 args on the real contract, and the single most common name (`transfer`) is entirely absent from the allowlist.

6. **Missing control**: No fallback rendering exists for a call that fails intent recognition beyond a bare method-name + contract-address header. The code's own comment at `OperationCard.vue:115-116` claims "we render the indexed-args fallback with an explicit marker" for the unverified case — **no such fallback is implemented anywhere in the template**; the claim is stale relative to the code. There is also no automatic check that keeps `transfer-intent.ts`'s allowlist/arity assumptions in sync with `token/functions/descriptors.ts`'s live understanding of the contract shape (the two modules independently hardcode overlapping-but-different transfer semantics).

7. **Exploit story**: A dApp integrates a standard (or nearly-standard) Aztec fungible token and asks the user to approve a private transfer by calling `wallet.sendTx({calls: [{contract: TOKEN, name: "transfer", args: [ATTACKER_ADDRESS, AMOUNT]}]}, {from: USER})` (the exact call shape the real Token contract's own `transfer` method expects). The approval popup shows: `Transfer (private)` on `0xTOKEN…` — no recipient, no amount, no indication anything is hidden. A user who has learned to trust the wallet's structured "From/To/Amount" display on *other* transfers (the 4 names that DO happen to short-circuit into "unverified" too, per point 5, but that's incidental — the broader lesson users learn is "if it doesn't show a scary raw-args warning, it's fine") approves. Funds move to `ATTACKER_ADDRESS` for `AMOUNT`, exactly as in the drive-by phishing scenario the F-008/"truthful approval display" fix was built to prevent — except this specific, extremely common call shape was never covered.

8. **Preconditions**: The dApp already holds a "transaction" capability grant for the account/chain (a routine, low-friction grant most connected dApps request and users approve once per session) and the transfer is not otherwise embedded-fee-paid in a way that would route it to the silent path (it still shows a popup — the finding is about the *content* of that popup, not the popup's existence). No wallet bug or compromise needed; this is a stock dApp calling a stock contract method through the stock wallet-sdk API.

9. **Why mitigations fail**: The one mitigation that exists — `parseTransferIntent`'s structured-args block — is the *entire* defense for this class of attack, and it fails closed to the *dangerous* side: on any non-match it silently degrades to "just show the header," not "show a warning" or "show raw indexed args" (despite the code's own comment claiming the latter happens). The dApp-side `.calls[].name` "call.name↔selector bound at all signing sinks" fix (`CONTEXT.md` remediation A) only guarantees the *name* isn't spoofed relative to the real function being called — it does nothing to guarantee that the *display layer* recognizes that (correctly bound) name.

10. **Instances** (same root cause — the "recognized transfer/mint name" allowlist is too narrow/wrong-arity to fire for real contracts):
    - `apps/extension/src/utils/transfer-intent.ts:23` (`KNOWN_TRANSFER_METHODS`, missing `transfer`, `transfer_public_to_public`, `transfer_private_to_private`, `transfer_public_to_private`, `transfer_private_to_public`).
    - `apps/extension/src/utils/transfer-intent.ts:72` (`parseTransferArgs`'s fixed `args.length !== 3`, wrong for both the 2-param and 4-param real variants per `descriptors.ts:322-325`).
    - `apps/extension/src/popup/windows/execute/OperationCard.vue:110-157` (the sink — no fallback rendering for the unverified case, contradicting its own `:115-116` comment).
    - Same allowlist gap is reachable for a real `mint_to_private`/`mint_to_public` call too if a token names it differently than the 2 hardcoded strings, though the mint arity (2) does match `descriptors.ts` — lower confidence this one is exploitable against the pinned standard contract today (its mint names do match) but it inherits the same maintenance hazard.
    - `apps/extension/src/popup/windows/execute/OperationActionRow.vue:11-17` — the *same* "name/selector + contract only, no args" rendering exists for `send_transaction`'s `call`/`encoded_call` actions. Currently **not reachable from a dApp** (the only wire-level producer of `send_transaction` actions is `packages/wallet-bridge/src/dispatcher.ts:1081-1096`'s `grantPublicAuthwit` handler, which always emits a single, fully-rendered `add_public_authwit` action, plus two extension-internal, popup-free UI flows in `apps/extension/src/wallet/services/auth-registry/service.ts:210-225,258-268` that use `OriginType.UI` and never open this popup) — noted as a dormant instance of the same gap, not a live finding.

### F-2: `aztec_sendTx`'s dApp-suppliable `authWitnesses` / `capsules` / `extraHashedArgs` are incorporated into the signed transaction but are never shown anywhere in the approval popup

1. **Title**: The approval popup renders only `exec.calls`; a dApp can additionally supply raw `authWitnesses`, `capsules`, and `extraHashedArgs` on the same `sendTx` request (via both `exec` and `opts`), all of which are folded into the built/sent transaction with zero display and only structural (not semantic) validation.

2. **Impact factors**: Integrity-of-consent gap (CIA: Integrity) on the same "what you see is what you sign" boundary as F-1, but for a different field family. Blast radius: every `aztec_sendTx` approval — the popup's completeness as a disclosure surface is broken for any request that rides extra witnesses/capsules alongside its calls. Attack vector: the standard `sendTx` wallet-sdk RPC, reachable by any connected dApp; complexity low; privileges: an established session with transaction-scope, same as F-1; user interaction required (the same blind Confirm).

3. **Evidence confidence**: Moderate. The display omission and the unrestricted pass-through are both directly confirmed in code. What I could **not** fully verify within this audit's scope is Aztec's kernel-circuit-level semantics of authwit binding/replay resistance (i.e., whether a well-formed-but-irrelevant or replayed authwit can actually cause unintended authorization beyond what the displayed `calls` already imply) — that verification would require tracing account-contract/kernel-circuit internals outside this repo. I am flagging the display gap itself as the finding, with the deeper protocol question left explicitly open rather than asserted.

4. **OWASP / CWE mapping**: CWE-451 (UI Misrepresentation of Critical Information); OWASP A04:2021 – Insecure Design; overlaps the audit's own "ZK/Aztec wallet specific: authwit scope & replay" category.

5. **Trace**:
   - Source: a dApp calls `sendTx(exec, opts)` where `exec` and/or `opts` include `authWitnesses: [...]`, `capsules: [...]`, `exec.extraHashedArgs: [...]` — fields that exist on the standard `@aztec/stdlib/tx` `ExecutionPayload` shape aztec.js dApps construct. `packages/wallet-bridge/src/dispatcher.ts:941,946-952` forwards the entire raw `args[0]` as `sendOp.exec` verbatim; `assertAuthRelevantArgShape`'s `sendTx` case (`packages/wallet-bridge/src/dispatcher.ts:582-589`) validates only `exec.calls[].{to,name}` shape — it never inspects `authWitnesses`/`capsules`/`extraHashedArgs`.
   - The payload reaches the popup as `payload.params.operations[i].exec` (same object). `apps/extension/src/popup/windows/execute/OperationCard.vue:110-157` (the `aztec_sendTx` render branch) iterates only `op.exec.calls`; grep confirms zero references to `capsule` or to `exec.authWitnesses`/`opts.authWitnesses` anywhere in `OperationCard.vue` or `index.vue` — the only "authwit" hits in that window are for the unrelated `aztec_createAuthWit` operation kind.
   - Sink: on approval, the SAME `op.exec`/`op.opts` are forwarded to the executor. `apps/extension/src/wallet/services/execution/tx-request-builder.ts:347-358` parses `(op.exec.authWitnesses ?? []).concat(op.opts.authWitnesses ?? [])` and `(op.exec.capsules ?? []).concat(op.opts.capsules ?? [])` through `AuthWitness.schema.parseAsync`/`Capsule.schema.parseAsync` (structural validation only — shape, not meaning) and folds them into the built `ExecutionPayload` (`tx-request-builder.ts:275`) that gets proven and sent. `apps/extension/src/wallet/services/execution/operation-planner.ts:175,186,198` shows the same merge pattern is used for planning/fingerprinting too.

6. **Missing control**: No rendering, summary, or even a count/"this transaction includes N extra witnesses" indicator exists for these fields anywhere in the approval UI, despite them being fully dApp-controlled and directly incorporated into what gets signed and broadcast.

7. **Exploit/violation scenario**: A dApp's `sendTx` request bundles calls that look benign (or are themselves under-described per F-1) alongside an `authWitnesses` array containing a witness the dApp obtained or observed elsewhere (e.g., from a prior legitimate approval, from public chain data, or from a related account/session). The user's popup shows only the `calls` list — never that additional signed authority is riding along. Whether this specific bundling can cause the wallet's own account to authorize something the user did not intend depends on Aztec's authwit message-hash scoping/nonce semantics at the protocol layer (out of this audit's traced scope); regardless of that answer, the disclosure gap itself means the user is asked to approve a transaction whose full authorization envelope they cannot see.

8. **Preconditions**: Same as F-1 — an established dApp session with transaction-scope; the dApp must additionally possess or construct a well-formed `authWitnesses`/`capsules` entry (structural validity is enforced by the Aztec stdlib Zod schemas at `tx-request-builder.ts:347-358`, so malformed/raw-Fr entries are already rejected per the F-006/PR #272 "raw-Fr authwit" fix).

9. **Why mitigations fail**: The PR #272 remediation ("dispatcher hard-rejects raw-`Fr` authwits; `call.name`↔`selector` bound at all signing sinks") addresses forgery/shape attacks on `.calls` and rejects malformed authwit encodings — it does not address *disclosure*: a well-formed, schema-valid `authWitnesses`/`capsules` entry sails through both the dispatcher's shape guard and the builder's Zod parse with no popup visibility at all.

10. **Instances**: `apps/extension/src/wallet/services/execution/tx-request-builder.ts:347,351,355` (parse sites); `apps/extension/src/wallet/services/execution/operation-planner.ts:175,186,198` (planning-side merge, same fields); `apps/extension/src/popup/windows/execute/OperationCard.vue:110-157` (the sole render site for `aztec_sendTx`, which never touches these fields).

## Non-findings

- **`approveInteraction` executes exactly the `operations` array the popup returns, with no SW-side re-comparison against the originally-stored `interaction.payload`** (`apps/extension/src/wallet/services/dapp-interaction/service.ts:158-187,219-286`; narrowing only checks `feeSettings` presence, `packages/wallet-bridge/src/operation-validation.ts:65-69`). This is architecturally a single point of trust in the popup, but the popup is same-extension code with no `v-html`/`innerHTML`/`eval`/`new Function` anywhere in production `src/**` (confirmed via the shell repo-map's exhaustive grep, cross-checked against every file read in this cluster), every dApp-controlled string that reaches the popup is run through `sanitizeWireString`, and a hostile dApp has no code-execution channel into the popup's own JS to falsify `operations.value` independent of what was rendered. Absent a demonstrable code-execution bug *inside* the popup, this is a documented single-layer-of-defense observation, not a concrete finding — recorded because Q1 of the assignment specifically asked for it.
- **No window-id binding on `getInteractionPayload`/`approveInteraction`/`isInteractionCancelled`/`focusInteractionWindow`** — any extension-internal sender (`isTrustedInternalSender`, `packages/extension-messaging/src/core/sender-auth.ts:17-23`, trusts any `chrome-extension://<id>/*` page) can call these with any known `requestId`. This is the standard "all extension pages are one trust domain" model MV3 imposes (there is no cross-extension-page isolation primitive to bind an RPC call to the specific window that opened it), and `focusInteractionWindow` already includes an explicit belt-and-suspenders active-profile check (`service.ts:304-315`) precisely because the id-guessing surface is understood. Non-finding: expected behavior of the platform's trust model, not a code defect.
- **`verify` window's `verificationHash` URL param is not directly attacker-reachable**: `src/popup/index.html` is not in `web_accessible_resources` (`apps/extension/manifest/manifest.config.ts:55-60` lists only `src/assets/logo.png` for `*://*/*`), so a hostile web page cannot navigate to or embed `chrome-extension://<id>/src/popup/index.html#/windows/verify?...` at all; the URL is exclusively SW-constructed from the just-validated session (`session-established.ts`, per repo-map).
- **Homoglyph/confusable dApp-name and token-symbol spoofing is real but already a documented, accepted limitation**, not a regression: `capability-meta.ts:157-161`'s own doc comment states no UTS39/confusable normalization is applied, and every surface that renders an attacker-controlled name (dApp identity block, register_token symbol/name) also always renders the disambiguating raw address (`AddressDisplay`) alongside it, per the invariant already recorded in `CONTEXT.md`.
- **Capability-window default-OFF-for-unknown-types works as designed**: `apps/extension/src/popup/windows/capabilities/build-items.ts:63-84` sets `selected: !safe.isUnknown` and routes unknown `cap.type` strings through `getSafeDisplay` so the raw wire string never becomes a visible label; verified by direct read, not just the repo-map's claim.
- **`fpc`/`fjwc` fee-payer classification cannot be spoofed by a dApp to silently drain the user's own account**: `classifyFeePayer`/`isSelfPay` (`packages/wallet-bridge/src/fee-payer.ts:56-70`) route to the popup (`isConfirmationNeeded`, `dapp-interaction/service.ts:590-599`) whenever `feePayer` is unset or resolves to a genuine self-pay; a dApp naming a different address as `feePayer` routes to the `"fpc"` classification, but that address must actually be a cooperating account/contract at the protocol level for the resulting tx to validate — there is no wallet-level fallback that silently substitutes the user's own Fee Juice when a named external payer doesn't cooperate.
- **Embedded-FPC `maxFeesPerGas` honored verbatim from the dApp** (`apps/extension/src/wallet/services/execution/fee/embedded-fpc-cap.ts:71-82`) is a deliberate, twice-audited design tradeoff (per the file's own extensive header) whose blast radius is the dApp's own FPC budget, not the user's funds — the embedded path is by definition dApp/FPC-paid, not user-paid.
- **`assertCustomGasLimitsWithinCap`/`finalizeGasLimits`'s admission-cap enforcement is sound for `gasLimits`/`teardownGasLimits`** (`apps/extension/src/wallet/services/execution/fee/fee-strategy.ts:205-235,265-296`) — dApp/custom limits over the protocol/node cap always throw rather than silently clamp or pass. (`maxFeesPerGas` itself is not capped on the non-embedded path, but on that path it is popup/user-selected via `FeeSettingsCard`, not dApp-supplied, per `materialize.ts:82-102` — the dApp cannot set it directly for a self-pay send.)
- **`window-manager.ts`'s race guards hold up under direct review**: every async continuation (`openAndAwait`'s `.then` chain, `:88-134`) re-checks `this.handles.get(handleId) !== handle` (identity, not membership, precisely because an 8-hex id can be re-minted after settlement) before creating/adopting a window or attaching the `onRemoved` listener; `detach`/`settle`/`cancel`/`_settleUserClose` are all idempotent against an already-settled handle. No double-window, no late-resolve-after-cancel path found.
- **First-claim-wins + post-approval fences are intact**: `approveInteraction`/`resolveInteraction` both refuse on `interaction.cancelledAt !== undefined` before deleting the storage record (`dapp-interaction/service.ts:173-176,196-199`), and `executeAndResolve` re-captures the active-profile fence and re-checks the `DappSession` row's liveness against that same captured profile before executing (`service.ts:245-267`) — closes both the "approved after profile switch" and "approved after session torn down mid-interaction" windows described in Q2.
- **`apps/extension/src/e2e/*` is production-wired but inert by construction**: `config.ts`'s proverless/token-seed flags require a double opt-in (`FLAG` + `FLAG_CONFIRM`, exactly-one throws) that is build-time-only (`import.meta.env`), set exclusively by `scripts/e2e/agent.sh`/CI, and additionally negative-grepped out of production bundles in `_build-extension.yml` per the module's own header — no runtime/RPC path can arm it.
- **`json` window is a read-only escape hatch with no injection surface**: renders via `<JsonViewer>` (CodeMirror-based per the shell repo-map), no `v-html`; closes on profile logout.
- **`aztec_createAuthWit`'s silent-sign path is scope-bounded, not a blanket bypass**: `isCreateAuthWitCoveredByTxOrSimulationScope`/`checkCreateAuthWit` (`packages/wallet-bridge/src/method-scope-checkers.ts:270-310`) require the authorized call's `(contract, method)` to already fall within a granted transaction/simulation scope pattern the user approved via the capabilities popup; an uncovered call still routes through the full approval popup (`dapp-interaction/service.ts:1002-1012` equivalent path in `dispatcher.ts:1007`).
