# c11 — storage/journal/activity — security audit

Files read in full: `apps/extension/src/wallet/services/{operation-journal,activity-protocol,transaction,token-balance,contact,token}/*.ts` (non-test), `require-owned-row.ts`, `purge-rows.ts`, `restore-rows.ts`, `id-allocators.ts`, `storage-codecs.test.ts`, `cross-profile-isolation.test.ts` (as specs), `packages/wallet-core/src/{jobs/fsm.ts, activity/{causal.ts,model.ts,scope.ts}, utils/serialization.ts}`, `packages/wallet-core/src/storage/entity_storage.ts`, `dapp-session/{service.ts,mac-storage.ts,integrity.ts}`, `token/{service.ts,seeder.ts,default-tokens.ts}`, `fpc/service.ts` (getX paths), `network/service.ts` (getX paths), `profile/session-manager.ts` (`getSecret`), `profile/service.ts` (`deriveDappSessionMacKey`), popup consumers `RecentActivityView.vue`, `TokensView.vue`, `TokenImportRow.vue`, `ContactRow.vue`, `ContactFormFields.vue`, `journal/[id].vue`, `stores/{app.store.ts,activity.store.ts}`, `incoming-transfer/service.ts` (cross-reference call sites), `extension-messaging/src/core/{base-service.ts,base-client.ts,decode.ts}`, `utils/string.ts`.

Findings: 1. Non-findings: 15.

### F-1: Missing per-profile authorization on the operation-journal RPC surface discloses another wallet profile's token-import activity into the active profile's Tokens view

1. **Title**: `OperationJournalService`'s by-id/by-filter RPC methods never check row ownership against the caller's active profile, and the one popup consumer that omits the (elsewhere-standard) client-side profile filter renders a foreign profile's in-flight/recently-failed token-import row in the active profile's UI.

2. **Impact factors**: Confidentiality violation — cross-profile disclosure of activity metadata (token symbol/title, contract address, import-failure reason) inside a single-extension, multi-profile wallet whose entire design (see Non-findings) treats "which profile is active" as an authorization boundary for contacts, tokens, FPCs, networks and dapp-sessions. Attack vector is local or within the extension's own trusted-sender surface (any same-extension context reachable via `isTrustedInternalSender`, not a remote/network attacker); no elevated privileges beyond normal wallet use; no additional user interaction beyond opening the Tokens tab within a live window. Blast radius is limited to activity-log-shaped metadata, not funds, keys, or full addresses.

3. **Evidence confidence**: High — full source trace with concrete field values, and a companion regression-test gap that independently corroborates the root cause (see below).

4. **OWASP / CWE mapping**: OWASP A01:2021 — Broken Access Control. CWE-862 (Missing Authorization) as primary; CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) as secondary for the concrete disclosure.

5. **Trace** (source → sink):
   - Precondition established: `ProfileService.assertNotDuplicateWallet` (`apps/extension/src/wallet/services/profile/service.ts:2004-2012`) is a **soft** guard — a matching wallet fingerprint throws `DuplicateWalletError` only `if (!allowDuplicate)`; callers can pass `allowDuplicate: true` to import the *same mnemonic* into a second profile. Two profiles built from one mnemonic derive **identical account addresses** for the same `(l1ChainId, index)` — an intentional, owner-policy-accepted scenario the codebase defends against in multiple other places (see Non-findings and instance list below), establishing this is a real, reachable state and not a hypothetical.
   - Write: `TokenService` journals a token-import attempt with the shared address: `this.journal.createOperation({ kind: "token_import", ..., accountAddress: input.journal.accountAddress, ... })` (`apps/extension/src/wallet/services/token/service.ts:345-349`), where `accountAddress` is the account the (then-active) profile B used. The record's `profileId` is stamped from the caller's fence (`operation-journal/service.ts:261-285`), but nothing about the STORAGE ROOT partitions by profile — `nulo:journal` is one shared `EntityStorage<OperationRecord>` (`operation-journal/service.ts:108-110`) constructed **without** `requireKeyIdentityMatch` (contrast `packages/wallet-core/src/storage/entity_storage.ts:40-53` — an opt-in per root that operation-journal does not take).
   - Read (no ownership check): `OperationJournalService.getOperations(filter?)` (`apps/extension/src/wallet/services/operation-journal/service.ts:407-420`) filters only on `accountAddress` / `stage` / `kind` / `isTerminal` — **never `profileId`** unless the caller explicitly passes one. `getOperation(id)` (`:401-405`) has **no ownership argument at all**.
   - Consumer that fails to re-scope: `TokensView.vue`'s `fetchTokenImports()` calls `journalService.getOperations({ kind: TOKENS_VIEW_KIND })` (`apps/extension/src/popup/components/modules/general/TokensView.vue:204`) — **kind-only**, no `profileId`, no `accountAddress` filter server-side. The rendered computed, `visibleTokenImports` (`TokensView.vue:49-61`), filters only on `op.kind !== TOKENS_VIEW_KIND` and `op.accountAddress !== account` — it never compares `op.profileId` to `appStore.profile.id` (confirmed: the string `profileId` does not appear anywhere else in this file; `grep -n "profileId" TokensView.vue` returns only the unrelated `pinScopeOf(appStore.profile?.id, ...)` pin-key line).
   - Sink (render): `<TokenImportRow v-for="op in visibleTokenImports" :key="op.id" :op="op" />` (`TokensView.vue:428-429`) → `TokenImportRow.vue` renders `op.title`/derived `shortAddress` (from `op.contractAddress`, `TokenImportRow.vue:26-35`) and `op.subtitle`/`op.error?.message` on failure (`TokenImportRow.vue:37-43`) directly into the DOM (`data-testid="token-import-title"` / `"token-import-subtitle"`, `:46-57`).

6. **Missing control**: Two independent layers that would normally close this are both absent here: (a) server-side — `OperationJournalService` has no `requireOwnedRow`-style profile check on any of its by-id/by-filter methods (unlike `ContactService`, `TokenService`, `FpcService`, `NetworkService` — see Non-findings); (b) client-side — every *other* popup consumer of this exact same over-broad RPC shape re-applies an explicit `op.profileId === activeProfile.id` guard before rendering (see instances below); `TokensView.vue` is the one place that does not.

7. **Exploit / violation scenario**:
   1. User (or two co-users of one machine) imports the same recovery phrase into Profile A and Profile B via `importMnemonic(..., allowDuplicate: true)`, confirming the duplicate-wallet warning — a supported flow.
   2. While Profile B is active, the user (or a dApp via `registerToken`) starts adding a token; `TokenService.addTokenWithFence` journals a `token_import` operation stamped with Profile B's `profileId` and the account address shared with Profile A (`token/service.ts:345-349`).
   3. The import is slow (PXE simulation / registration in flight) or fails (bad contract, network blip) — either way the record is non-terminal (`terminalAt === null`, no time bound — the reaper's own grace window for `simulating`/`proving` is 10–35 minutes, `operation-journal/reaper.ts:74-84`) or terminal-failed within the last 30 seconds (`FAILED_RETENTION_MS`, `TokensView.vue:39`).
   4. User switches to / unlocks Profile A (same shared address). Opening the Tokens tab triggers `fetchTokenImports()` → `getOperations({kind:"token_import"})`, which returns Profile B's row (server-side filter never excluded it) alongside any of Profile A's own rows.
   5. `visibleTokenImports` keeps it (kind matches; `accountAddress` matches, because the addresses are identical by construction) and `TokenImportRow` renders Profile B's token symbol/short contract address, and — if it failed — the raw import-failure reason, inside Profile A's UI, with no indication it belongs to a different wallet profile.

8. **Preconditions**: (a) the (soft-guarded, user-confirmable) duplicate-mnemonic-import feature has been used to create two profiles sharing an account address on the same chain; (b) the foreign profile has a `token_import` operation that is still in-flight or failed within the last 30s at the moment the active profile's Tokens view is open/refreshed. No dApp or network attacker capability is required — the "over-privileged actor" is ordinary same-extension UI code lacking a check every sibling call site applies.

9. **Why mitigations fail**: The natural mitigation — profile-scoped storage or a server-enforced ownership check — is architecturally present for the sibling resources in this exact codebase (`ContactService.getContact`/`updateContact`/`deleteContact` via `requireOwnedRow`, `require-owned-row.ts:12-17`; `TokenService.getToken`/`deleteToken` via `requireOwnedRow`, `token/service.ts:222-232,545-548`; `FpcService`/`NetworkService` likewise per `cross-profile-isolation.test.ts:271-325`; `TokenBalanceService` via the identity-triple check `rowMatchesToken`, `token-balance/service.ts:179-206`; `DappSessionService` via MAC-key derivation bound to the active profile's master secret, see Non-findings) — but was never added to `OperationJournalService`. The one place that *would* need to compensate client-side for that absence (`TokensView.vue`) does not, unlike its sibling `RecentActivityView.vue`, which explicitly re-derives and checks `op.profileId` (`journalRecordInScope`, `RecentActivityView.vue:278-291`, with the comment "two profiles can hold the SAME account address (the same mnemonic imported twice), so account + network alone would let one profile's operations render under the other" — i.e., the codebase already understands and defends this exact class of bug everywhere except here) and `app.store.ts`'s `syncScopedTransactions`, which explicitly filters `TransactionService.getTransactions(address)` results through `txBelongsToScope(...)` for the identical reason (`stores/app.store.ts:562-585`, comment "The fetch is by ADDRESS alone, so it returns every profile's rows for a shared address"). `incoming-transfer/service.ts`'s `collectOutgoingTxHashes`/`collectInflightTxHashes` (`:2166-2200`) apply the same `profileId`/`networkId` re-check on the same two RPC methods.

10. **Instances** (same root cause — no server-side profile-ownership enforcement on this storage cluster's shared-account-address surfaces):
    - `apps/extension/src/wallet/services/operation-journal/service.ts:401-405` — `getOperation(id)`, no ownership argument at all.
    - `apps/extension/src/wallet/services/operation-journal/service.ts:407-420` — `getOperations(filter?)`, `profileId` is an optional filter the caller may omit.
    - `apps/extension/src/wallet/services/operation-journal/service.ts:297-334` — `transitionOperation(id, progress, error)`, no ownership check (impact bounded in practice by the FSM's terminal-state lock, `packages/wallet-core/src/jobs/fsm.ts:38-51`, so a foreign non-terminal record's *stage* — not a terminal one — is the only thing at risk, e.g. premature `cancelled`/`failed`).
    - `apps/extension/src/wallet/services/operation-journal/service.ts:349-370` — `setOperationMeta(id, meta)`, no ownership check (can rewrite a foreign profile's journal `title`/`subtitle`).
    - `apps/extension/src/wallet/services/operation-journal/service.ts:445-456` — `deleteOperation(id)`, no ownership check (can delete a foreign profile's journal row; low severity — the row is reconstructable history, per the codebase's own GC eviction rationale).
    - `apps/extension/src/wallet/services/transaction/service.ts:130-140` (`getTransaction(hash)` / `getTransactions(account)`) — same missing-authorization shape; currently **not** independently exploitable because every present-day caller (`stores/app.store.ts:562,583`, `incoming-transfer/service.ts:2179`) re-filters by `profileId`/`networkId` before use, but the RPC method itself grants any same-extension caller full cross-profile tx history (nonce, fee, gas details, calls, hash, block) for a shared address with no server-side check.
    - Concrete rendering path: `apps/extension/src/popup/components/modules/general/TokensView.vue:49-61,204,428-429` and `apps/extension/src/popup/components/modules/general/TokenImportRow.vue:26-57`.

## Non-findings

- **`OperationJournalService` records are not backup/restore-reachable** — no `backup()`/`restore()` methods on the service and `nulo:journal` is absent from `backup-migration-registry.ts`'s slice registry — so the "hostile backup row-transplant" vector (Q2) does not apply to this root; F-1's root cause is purely same-extension-caller reachable, not backup-reachable.
- **`ActivityProtocolCoordinator` is fully implemented, tested (`activity-protocol/coordinator.test.ts`), but never wired into production.** `grep -rln "ActivityProtocolCoordinator" apps/extension/src` outside its own file/test returns nothing; `ACTIVITY_PROTOCOL_SERVICE_NAME` (`activity-protocol/spec.ts:4`) is never registered in `wallet/index.ts`/`wallet/runtime.ts`; `transaction/service.ts`, `operation-journal/service.ts`, and `incoming-transfer/service.ts` contain zero references to `activityProtocol`/`currentIncarnation`/`retireScope`/`purgeScope`. Consequently the documented `causal.ts:172-181` KNOWN GAP ("a COLD slice accepts whichever snapshot arrives first... close this when the coordinator is wired into production") is **still open but inert** — `applyMutation`/`applySnapshot`/`resetScope`/`liveRecords` (`packages/wallet-core/src/activity/causal.ts`) have zero call sites in `apps/extension/src` outside their own tests, so the retired-incarnation-replay scenario the audit asked about cannot manifest today (dead code, no reachable sink). What actually protects the popup's activity feed from a chain-purge/account-re-add resurrection today is a *different*, independently-built mechanism: `stores/activity.store.ts`'s own per-scope `mutationVersion`/`incarnation` ABA fence (`activity.store.ts:110-155,242-252`) plus eager profile/chain-scoped row deletion at purge time (`transaction/service.ts:purgeForAccounts`, `token-balance/service.ts:purgeForAccounts`, execution-fence/deletion-epoch checks throughout). This is a maintainability/consistency observation, not an exploitable vulnerability.
- **`TokenBalanceService` by-id reads are robust against cross-profile/identity-reuse row confusion.** `getTokenBalance`/`getTokenBalances`/`refreshTokenBalance` (`token-balance/service.ts:179-215`) all gate on `rowMatchesToken(balance, token)`, and `this.tokens` is populated only from `tokenService.getTokensRaw(activeProfile.id)` (`:166-171`) — a foreign-profile balance row whose numeric `token` id happens to collide with an active-profile token id fails the identity-triple compare (`profileId`+`chainId`+`contract`) and is treated as absent. Confirmed pinned by `cross-profile-isolation.test.ts:259-269`.
- **`ContactService`, `TokenService`, `FpcService`, `NetworkService` correctly enforce `requireOwnedRow`/profile-scoping on every by-id getter/setter/deleter** (`contact/service.ts:75-166`, `token/service.ts:222-232,545-548`, and per `cross-profile-isolation.test.ts:271-325` for fpc/network) — consistent with the fail-closed contract in `require-owned-row.ts:12-17`. `getContacts()`/`getTokens()` list methods filter by `profile.id` server-side.
- **`DappSessionService`'s by-id surface (`getDappSession`, `patchSession`-backed setters, `deleteDappSession`) has no explicit `profileId` check in its own code, but is nonetheless cross-profile-safe by construction.** `DappSessionMacStorage.verifyOrDrop` (`dapp-session/mac-storage.ts:85-105`) derives the verification key via `keyFor(row.profileId)` → `ProfileService.deriveDappSessionMacKey(profileId)` (`profile/service.ts:913-933`) → `SessionManager.getSecret(profileId)` (`profile/session-manager.ts:214-220`), which **throws** `"Profile locked"` unless `profileId` equals the currently-active session's profile. A row belonging to a non-active profile therefore always fails key derivation and is hidden (not deleted) — an equivalent, cryptographically-enforced ownership boundary that happens to live one layer below the service methods themselves.
- **`operation-journal`'s FSM structurally prevents "resurrecting a cancelled/succeeded/failed record."** `LEGAL_TRANSITIONS` (`packages/wallet-core/src/jobs/fsm.ts:38-51`) gives `succeeded`/`failed`/`cancelled` empty outgoing-edge sets; `assertCanTransition` (`:77-79`) throws `IllegalTransitionError` on any attempt to leave a terminal stage, independent of caller identity. The kind↔`succeeded.txHash` invariant (`operation-journal/service.ts:547-564`) and the submitting↔succeeded hash-drift pin (`:572-581`) close the "fake success with attacker txHash" and "hash drift" sub-cases the audit asked about.
- **`JobCancelledSentinel` does not cross the RPC boundary.** Every throw site is inside `execution/*` (out of this cluster's file scope) and is caught by `execution/rpc-cancel.ts`'s shared handler, which converts it to the structured `JobCancelledError` before it can reach a client; `execution-lane.ts:21` states the invariant explicitly and nothing in this cluster's assigned files re-exports or serializes the sentinel.
- **Reaper/GC do not delete records execution still references.** `JournalReaper.reap()` uses a CAS transition (`transitionIfStage` with `ifUpdatedAtIs`, `reaper.ts:199-205`) so a record claimed or heartbeat-touched since the snapshot is never clobbered; `JournalGC.sweep()` only evicts `succeeded` records beyond a per-scope cap (`gc.ts:126-141`), never `failed`/`cancelled` (documented data-loss rationale, `gc.ts:17-25`).
- **Id allocation (`nextNumericId`/`nextRandomId`/`randomIdNotIn`/`preferOrReallocId`) is hardened against hostile keys and restore-time collision.** `nextNumericId` (`id-allocators.ts:17-37`) excludes non-canonical/unsafe-integer keys from the max computation and clamps + walks down on overflow; `nextRandomId`/`randomIdNotIn` use `getRandomHex` (CSPRNG) with a collision-avoidance loop; `preferOrReallocId` (restore path) only keeps a backup row's original id when it is *physically free* in the (profile-shared) storage root, otherwise rerolling — so a crafted backup id can never overwrite a live row of any profile (`id-allocators.ts:64-75`), consistent with `TransactionService.restore`'s independent create-only check (`transaction/service.ts:589-595`) and `ContactService.restore`'s use of the same allocator (`contact/service.ts:299`).
- **Transaction DROPPED-debounce and in-flight-write fencing are sound.** `DROPPED_GRACE_MS`/`DROPPED_CONFIRMATIONS`/`DROPPED_RESURRECTION_WINDOW_MS` (`transaction/service.ts:50-56`) require 3 consecutive dropped observations past a 60s grace window before declaring a tx dropped, with a 30-minute resurrection watch for late mines; the object-identity fence in `updateTx` (`:468-505`) — re-checking `this.pending.get(tx.hash) !== tx` under the lock — prevents a stale unlocked node-poll from resurrecting a row a concurrent profile-delete purge already removed (documented "finding D").
- **Token registry TOFU pin (`expectedClassId`/`expectedSymbol`) is enforced before any PXE registration, on the same fetched instance that is later used for metadata** (`token/service.ts:590-627`, `token/seeder.ts:346-362`) — no refetch window for substitution once the pin passes. Whether the underlying `pxe.getContractInstance`/`getContractArtifact` responses are themselves independently verifiable against rollup state (rather than trusted verbatim from the connected node) is a property of the vendored `@aztec/pxe` stack, not this cluster's code, and is out of scope for this audit pass.
- **Contact-name homoglyph/lookalike spoofing is a known, accepted, and already-mitigated risk class, not a new gap.** `sanitizeString` (`utils/string.ts:33-42`) strips non-letter/digit characters but does not normalize confusable Unicode letters (`\p{L}` admits Cyrillic/Greek look-alikes) — the same documented, accepted limitation as the dApp-name `safe()` sanitizer (`capability-meta.ts:157-161`, "no homoglyph/UTS39 normalization"). Every contact-rendering surface examined (`ContactRow.vue:34-36`) always displays the trimmed address alongside the name, matching the codebase's stated mitigation pattern for attacker-influenced display strings ("UI MUST render the contract address alongside", `token/service.ts:669-671`).
- **`ContactService.addContact`/`updateContact` perform no server-side string sanitization/length-capping (unlike `importContacts`, which applies `sanitizeString`)**, but this RPC surface is not reachable by any dApp (absent from the `WalletSdkDispatcher` method list) and the only production caller applies client-side `sanitize`/`maxLength` constraints (`ContactFormFields.vue:25-47`) — no concrete attacker-reachable path found; a defense-in-depth gap, not a violation.
- **`jsonStringify`/`jsonSanitize` (`packages/wallet-core/src/utils/serialization.ts:26-58`) throwing on a cyclic/hostile object is contained at the one place it matters for this cluster.** `base-service.ts:handleRequest`'s `jsonSanitize(result)` call (`:113`) sits inside the same `try` that already catches `this.invoke(...)`'s own errors (`:111-116`), converting a serialization throw into a normal RPC error response, not a crash. `emit()`'s `jsonSanitize(payload)` (`base-service.ts:130`) is not separately try/caught, but no traced instance in this cluster constructs an event payload from unvalidated/hostile input (`OperationRecord`, `Tx`, `Contact`, `TokenBalanceInfo` fields are all zod-typed primitives assembled server-side after validated writes) — no concrete exploit path found.
- **`purgeMalformedRows`'s snapshot-then-guarded-delete (`purge-rows.ts:58-84`) correctly narrows, not closes, its race window** for stores lacking a service-wide lock or key-based attribution, exactly as its own documentation states; every call site examined in this cluster (`operation-journal`, `transaction`, `contact`, `token-balance`) runs it under that service's own lock, so the residual gap does not apply here.

## Cross-rebuttal

**1. Its findings.**
- **F-1 (token-delete TOCTOU lets a queued delete destroy a replacement row): CONFIRM.** Verified the full split: `deleteToken` (`token/service.ts:545-548`) calls `requireOwnedRow` *before* awaiting the lock; `_deleteTokenById`/`_deleteTokenByIdHoldingLock` (`:565-580`) re-load by numeric id only and delete unconditionally — no re-check of profile/chain/contract identity against what was authorized. `restore()` allocates via `nextNumericId` (`id-allocators.ts:17-30`, called at `token/service.ts:808`) under the *same* lock, so a freed id from a completed delete is reusable by a concurrent restore/create before a second queued delete for that id wakes up. The mechanism is real and independent of my own trace.
- **F-2 (journal writes bypass execution-controller cancellation): CONFIRM.** `transitionOperation` (`operation-journal/service.ts:297-330`) has no ownership/controller check, matching my own instance list (item 10, line 40 of this file). Independently confirmed the sharper consequence: `TransferExecutor`'s `checkCancelled` (`execution/transfer-executor.ts:118-119`) reads only `controller?.signal.aborted`, never the journal stage, and `cancelJob` (`execution-lane.ts:163-198`) only aborts the controller *after* its own `transitionOperation(...,"cancelled")` call succeeds — so a direct `transitionOperation(id,{stage:"cancelled"})` call desyncs the two: the controller is never aborted, execution proceeds to broadcast, and a subsequent legitimate `cancelJob` hits the now-terminal FSM state and silently drops (`:198`). This is a materially worse consequence than anything I traced for this RPC surface — it can move funds contrary to a displayed "cancelled" status, not just leak metadata.
- **F-3 (hostile backup preserves a future-timestamped fabricated balance): CONFIRM, ADOPT.** Verified end-to-end: `TokenBalanceService.restore` (`token-balance/service.ts:676-716`) spreads `tb` (backup-controlled `publicBalance`/`privateBalance`/`updatedAt`) and overrides only `id`/`profileId`/`chainId`/`contract`; `TokenBalanceRawSchema.updatedAt` (`spec.ts:54`) is an unbounded `z.number()`; `classifyExistingRows` (`reconcile-pairs.ts:143`) only flags `updatedAt === 0` as needing reconciliation; `refreshBalances`'s staleness check (`utils/core.ts:142,160`) is a bare subtraction, so a future `updatedAt` yields a negative age and is treated as fresh. All four links check out exactly as stated.

**2. What it missed that I found.** My F-1 (`TokensView.vue`'s missing `profileId` re-check, the one popup consumer that omits the guard every sibling — `RecentActivityView.vue:278-291`, `app.store.ts:562-585`, `incoming-transfer/service.ts:2166-2200` — all apply). Its own ownership table documents the identical underlying gap (`getOperation`/`getOperations` "Absent") but explicitly declines to raise it, asserting it was "already recorded... in the July report" — a citation I could not locate anywhere in this repo (`grep -ri "july report"` finds only its own line). It never traces to the concrete `TokensView.vue` sink, so it neither confirms nor refutes the one place the mitigation is actually missing.

**3. What I missed that it found.** ADOPT all three of its findings at high confidence, per the independent verification above. I must also retract part of my own Non-findings: I asserted "`TokenService` ... correctly enforce `requireOwnedRow`/profile-scoping on every by-id getter/setter/deleter" (this file, Non-findings, citing `token/service.ts:222-232,545-548`) — true for the synchronous check, false for the commit path, which is exactly its F-1.

**4. Overconfidence.** Its "already recorded in the July report" dismissal (§1 above) is asserted without a locatable citation and is used to justify not elevating a gap it otherwise documents in full — the report should have traced to `TokensView.vue` itself rather than deferring to an unverifiable prior source. Its F-2 impact language ("affecting any known journal record, including another profile's records") slightly overreaches: the demonstrated fund-movement consequence (cancellation bypass) needs only same-profile access to the caller's own in-flight job; the cross-profile framing isn't independently traced for this specific sub-case.
