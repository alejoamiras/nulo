# c06-dapp-bridge-dispatch — dApp RPC boundary security audit

Files read in full: `packages/wallet-bridge/src/*.ts` (all 24 non-test files), `packages/wallet-sdk-schema-patch/src/{apply,register}.ts`, `apps/extension/src/content-script/content.ts`, `apps/extension/src/wallet/services/wallet-sdk/{background,session-established,content-script-validator,session-baton,content-message-relay,discovery-approval,tab-lifecycle,queued-journal,queued-wait-vouching,pending-verification,error-envelope,to-json-safe,profile-switch-teardown}.ts`, `apps/extension/src/wallet/services/dapp-session/{service,spec,integrity,mac-storage,capability-meta}.ts`, plus targeted reads into `apps/extension/src/wallet/services/execution/{tx-request-builder,view-executor,fast-path,contract-resolver,service,dapp-send-executor}.ts` and `node_modules/@aztec/stdlib` (`FunctionCall` shape) to trace the name↔selector binding claim end-to-end. 1 finding, 11 non-findings.

### F-1: `aztec_simulateTx`'s public-static fast path authorizes by name but executes by selector, letting a narrowly-scoped dApp read any other public view function on its granted contract

2. **Impact factors**: Confidentiality violated (CIA "C"). A dApp holding a deliberately narrowed `simulation.transactions.scope` grant (e.g. "this dApp may only simulate `balance_of_public` on contract X") can read the return value of **any other PUBLIC + STATIC (view) function on that same contract**, executed as the connected account, without ever being granted that function. Attack vector: already-connected dApp over the existing wallet-sdk RPC channel (no new access needed). Attack complexity: low — one crafted `simulateTx` call, no race/timing. Privileges required: the dApp must hold a `simulation` capability with a non-wildcard `transactions.scope` for the target contract (a real, UI-supported narrowing, not a hypothetical). User interaction: none beyond the original scope grant. Blast radius is bounded to the one granted contract address and to PUBLIC+STATIC functions (private state and state-mutating calls are not reachable via this path).

3. **Evidence confidence**: high — full source-to-sink trace read in the actual files, cross-checked against the `FunctionCall` wire shape (`node_modules/.bun/@aztec+stdlib@5.2.0.../dest/abi/function_call.d.ts:8-24`, where `name` and `selector` are independent, both dApp-supplied fields) and against the four OTHER call sinks that all correctly bind `name` to the real ABI function resolved from `selector` before executing.

4. **OWASP / CWE mapping**: OWASP Top 10 2021 A01:2021 – Broken Access Control. CWE-863: Incorrect Authorization (the authorization decision is made against a field — `call.name` — that is not the field that determines what actually executes).

5. **Trace** (source → sink):
   - Source: `exec.calls[]` in a dApp's `aztec_simulateTx` RPC call — fully dApp-controlled, including `to`, `name`, `selector`, `type`, `isStatic`, `args`. Arrives as `args[0].calls` at `WalletSdkDispatcher.dispatch("simulateTx", args, ctx)` (`packages/wallet-bridge/src/dispatcher.ts:641`).
   - Scope gate: `enforceMethodAndScope` → `enforceScopeWithSession` (`dispatcher.ts:711-723`) → `enforceScope` (`packages/wallet-bridge/src/scope-enforcement.ts:59-65`) → `METHOD_SCOPE_CHECKER["simulateTx"]` = `checkSimulateTx` (`packages/wallet-bridge/src/method-scope-checkers.ts:391-393`) → `checkSimulationTransactions("simulateTx", args, grants)` (`method-scope-checkers.ts:143-175`). The permission test is **`matchesScope(String(call.to), call.name, scope)`** (`method-scope-checkers.ts:166-170`, helper at `:38-52`) — it inspects only `to` and `name`; `selector`, `type`, and `isStatic` are never read by the checker (the `WireCall` type used here, `method-scope-checkers.ts:31`, doesn't even declare a `selector` field).
   - Operation build: `dispatcher.ts` `buildAccountOperation` case `"aztec_simulateTx"` (`dispatcher.ts:1467-1474`) forwards `exec` **unchanged** into the `Operation`.
   - Routing: `ExecutionService.executeOperations` → `case "aztec_simulateTx": return this.viewExecutor.executeAztecSimulateTx(operation)` (`apps/extension/src/wallet/services/execution/service.ts:635-637`).
   - Sink: `ViewExecutor.executeAztecSimulateTx` (`apps/extension/src/wallet/services/execution/view-executor.ts:223-246`) calls `rehydrateOptimizablePrefix(op.exec?.calls)` (`apps/extension/src/wallet/services/execution/fast-path.ts:87-110`). The boundary scan at `fast-path.ts:97-100` admits any call whose **wire-level** `type === FunctionType.PUBLIC && isStatic === true` into the "optimizable prefix", then parses it structurally via `FunctionCall.schema.parse(c)` (`fast-path.ts:109`) — a Zod shape check only, with **no lookup of the real ABI function by `selector` and no comparison against `name`**. `runFastPath` (`fast-path.ts:172-224`) then calls `simulateViaNode(node, optimizableCalls, fromAddr, chainInfo, gasSettings, blockHeader, ...)` (`fast-path.ts:202-210`, imported from `@aztec/wallet-sdk/base-wallet`) — this executes the call **identified by its `selector`** directly against the live node, as `fromAddr` (the connected account), and its return value flows back into the dApp's `TxSimulationResult`.

6. **Missing control**: a name↔selector re-binding check — "resolve the ABI function from the real `selector`, reject if it doesn't match the claimed `name`" — before invoking `simulateViaNode`. This exact control exists at every OTHER call-execution sink in the same codebase (see "Why mitigations fail" below) but was not extended to the fast path when it was added.

7. **Exploit story**:
   1. User approves a dApp's `requestCapabilities({ capabilities: [{ type: "simulation", transactions: { scope: [{ contract: TOKEN, function: "balance_of_public" }] } }] })` — intending "this dApp may only simulate `balance_of_public` on TOKEN."
   2. The dApp computes the real selector for some OTHER public view function on `TOKEN` it was never granted (e.g. `admin_dashboard_view`, `allowance_of_public`, or any other `pub fn ... view` — selectors are deterministically derivable from `name + parameter types`, and contract ABIs are generally available to anyone who can already interact with the contract).
   3. The dApp calls `simulateTx` with `exec.calls = [{ to: TOKEN, name: "balance_of_public", selector: "<real selector of admin_dashboard_view>", type: "public", isStatic: true, args: [...] }]`.
   4. `checkSimulationTransactions` matches `name === "balance_of_public"` against the granted pattern → passes (the lie is invisible to the checker).
   5. `rehydrateOptimizablePrefix` sees `type===PUBLIC && isStatic===true` → includes the call in the fast-path prefix, faithfully carrying the REAL `selector` into the `FunctionCall`.
   6. `simulateViaNode` executes `admin_dashboard_view` as the connected account and returns its result in the simulation response.
   7. The dApp now has a working oracle for any public view function on `TOKEN`, despite the user's explicit, narrower grant.

8. **Preconditions**: the dApp holds a `simulation` capability whose `transactions.scope` is a non-wildcard pattern list for at least one contract (a wildcard `"*"` grant is already unrestricted and not affected); the target contract exposes at least one other PUBLIC + STATIC function.

9. **Why mitigations fail**: the "F-02" fix (documented at `view-executor.ts:342-354`, `tx-request-builder.ts:306-336,569-582`, `apps/extension/src/wallet/services/execution/service.ts:884-914`, `apps/extension/src/wallet/services/execution/authwit-discoverer.ts:171-191`) explicitly closes this exact bug class — "bind the dApp-supplied name to the selector's real ABI function... a dApp scoped for `symbol` could send `{name:"symbol", selector:<balance_of_private>}`" — for `executeUtility`, the NO_FROM sendTx path, the standard `call`/`encoded_call` action processing (`tx-request-builder.ts:180-195`), and every authwit-signing sink. All of those routes funnel through `ContractResolver`/`TxRequestBuilder`, which resolve the ABI function BY SELECTOR and throw `Scope violation: call name "..." does not match selector's function "..."` on mismatch. The `aztec_simulateTx` fast path (`fast-path.ts`, added later as a performance optimization — "Public-static fast path for dApp `aztec_simulateTx`", header comment lines 1-31) bypasses `TxRequestBuilder`/`ContractResolver` entirely by calling `simulateViaNode` directly, so it never gets the bind. `fast-path.test.ts` (the only test file covering this module) tests only the boundary-scan classification (type/isStatic, malformed shapes) and never exercises a name/selector mismatch — the gap is untested as well as unfixed.

10. **Instances** (same root cause: name-trusted scope check paired with a selector-driven execution path that skips the bind):
    - `apps/extension/src/wallet/services/execution/fast-path.ts:87-110` (`rehydrateOptimizablePrefix` — no bind before including a call in the optimizable prefix).
    - `apps/extension/src/wallet/services/execution/fast-path.ts:172-224` (`runFastPath` → `simulateViaNode` — executes by selector).
    - `apps/extension/src/wallet/services/execution/view-executor.ts:223-246` (`executeAztecSimulateTx` — the only caller of the fast path).
    - Confirmed NOT reachable via `profileTx` (`checkProfileTx` uses the same `checkSimulationTransactions` checker, but `executeAztecProfileTx`, `view-executor.ts:389-402`, always calls `this.deps.txBuilder.buildStandard(...)` — no fast path exists for profileTx) or via `sendTx`/`executeUtility`/authwit paths (all bind name↔selector, see field 9).

## Non-findings

- **Subframe/iframe origin spoofing (Q1)**: `isSubframeSender` (`apps/extension/src/wallet/services/wallet-sdk/content-script-validator.ts:93-95`) rejects any `sender.frameId !== 0` when both `tab` and `frameId` are defined, enforced at `background.ts:305-314`. `sender.tab === undefined` (which would skip the check) is not reachable by an attacking page: the extension declares no `externally_connectable` (checked `apps/extension/manifest/`), so `chrome.runtime.onMessage` only ever receives messages from the extension's OWN content scripts / pages, and a real content script injected into any frame always carries `sender.tab` + `sender.frameId`. `about:blank`/`data:`/sandboxed-iframe cases still resolve to SOME `frameId !== 0` for a subframe (rejected) or, if the TOP frame itself navigates to `about:blank`/`data:`, upstream's `sender.tab.url` origin attribution is an upstream (not Nulo) concern already scoped out as "upstream coordination item" (`background.ts:300-304`).
- **Session establishment / SW-restart marker loss (Q2)**: `handleSessionEstablished` (`session-established.ts:61-169`) is fail-closed at every step (stale marker → terminate `:89-93`; missing DappSession row → terminate `:95-101`; approver/validator profile mismatch → terminate `:105-109`; two separate `isSessionLive` re-checks `:116,131`; the pending-verification marker is cleared in a `finally` so no leak survives). The marker-less "reconnect" branch (SW restarted mid-handshake, or a genuine returning-user reconnect) is explicitly documented (`:85-88`) as relying on the live-profile row lookup + `!trustedVerification` gate instead of the marker's cross-checks — an acknowledged, intentional floor, not a silent gap.
- **Concurrent same-`(origin,chainId)` discovery handshakes**: the pending-verification marker is keyed by the transport **request id** (which upstream reuses verbatim as the `sessionId`), not the `(origin,chainId)` tuple (`pending-verification.ts:1-21`), so two concurrent handshakes for the same tuple cannot consume each other's markers; `background.ts`'s `pendingDiscoveryPromises` (state field, `background.ts:231`) additionally coalesces concurrent discovery popups per tuple.
- **`requestCapabilities` accounts-widening enumeration (#582, Q3)**: re-verified `planAccountsWidening`/`applyAccountsWidening` (`dispatcher.ts:336-352,1209-1227`) only adds `accounts` back into the delta (triggering a popup) when there is a genuinely NEW ungranted profile account; when there is nothing new, the type is NOT re-added to the delta, `handleRequestCapabilities`'s Phase-2 early return (`dispatcher.ts:1144-1157`) fires, and `enrichGrantedCapabilities` echoes only the account list already known from the PRIOR grant (gated by the stored `canGet`, `dispatcher.ts:1295-1310`) — no new information crosses the boundary. `accountsAdditions` (`dispatcher.ts:434-463`) only accepts accounts the wallet itself offered (`plan.availableAccounts`), never the popup's raw echo, so a dApp cannot inject an unoffered address into the grant.
- **Scope enforcement per `METHOD_REGISTRY` row (Q4)**: every scope checker in `method-scope-checkers.ts` was read; `checkTransactionCalls`/`checkGrantPublicAuthwit`/`checkCreateAuthWit` all resolve the real function via `selector` before execution (see F-1 field 9), closing the encoded_call/call parity gap EXCEPT for the one instance reported as F-1. The empty-function-name rule (`matchesScope`, `:49`) and the `registerContractClass` hard-deny (`checkRegisterContractClassDisabled`, `:407-411`) both behave as documented. `batch` cannot carry `sendTx`/`registerToken` legs (`dispatcher.ts:898-902`).
- **createAuthWit / grantPublicAuthwit (Q5)**: `checkCreateAuthWit` (`method-scope-checkers.ts:276-332`) rejects a raw `Fr` message hash outright ("a dApp must pass a structured call intent"), binds the `from` account against the accounts grant, and binds the target call/consumer against the union of `transaction`/`simulation.transactions` scope. The dispatcher's silent-vs-popup routing (`isCreateAuthWitCoveredByTxOrSimulationScope`, `dispatcher.ts:990-1000`) only takes the silent path when the call is covered by an already-granted scope; anything else (including any `IntentInnerHash`) goes to the confirmation popup.
- **DappSession MAC canonicalization completeness (Q6)**: `DappSessionMacStorage.set`/`verifyOrDrop` (`mac-storage.ts:30-35,85-105`) sign/verify every field of `DappSession` EXCEPT `mac` itself (`{ mac: _drop, ...signable }`). Cross-checked against the full `DappSession` type (`dapp-session/spec.ts:42-64`): `accounts`, `capabilityGrants`, `capabilityRejections`, `accountAliases`, `verificationHash`, `trustedVerification`, `chainId`, `dappMetadata` (origin lives at `dappMetadata.url`), and `profileId` are ALL inside the signed payload — nothing authority-bearing is excluded. A tampered or MAC-less row is dropped and quarantine-deleted (`mac-storage.ts:88-91,100-103`); a row that fails to verify because the profile is LOCKED is hidden but not deleted (`:92-99`), matching the documented "fail-closed, never a broadened grant" contract.
- **Fail-closed capability enforcement (Q7)**: `enforceCapability` (`dispatcher.ts:1327-1370`) throws `CapabilityNotGrantedError` both when the session is missing (F-006, `:1337-1352`) and when the required type isn't granted (`:1356-1368`) — no path returns an empty grant list and continues to the execution sink. The two `catch` blocks in `dispatcher.ts` (`persistRejectionOnPopupFailure`, `:1249-1262`, and its caller at `:1178-1181`) either swallow a benign "already revoked, nothing to persist" or re-throw; neither grants anything.
- **Schema-patch reachability (Q8)**: `applyNuloSchemaPatch` (`packages/wallet-sdk-schema-patch/src/apply.ts:53-58`) installs exactly `registerToken`, `isTokenRegistered`, `grantPublicAuthwit`, `getWalletFeatures` — the same four methods (and no others) present in `METHOD_REGISTRY` (`packages/wallet-bridge/src/method-descriptors.ts:207-314`). `assertKnownMethod` (`method-descriptors.ts:386-390`) uses `Object.hasOwn` (not a truthy index), so prototype names (`toString`, `constructor`, …) and any future upstream method not yet added to the registry are rejected, not silently routed.
- **Discovery flood + locked queue (Q9)**: `DiscoveryQueue`'s `PER_ORIGIN_CAP=4` (`discovery-queue.ts:34`) can be defeated by an attacker who controls many subdomains of one domain (each a distinct `origin` string), but the `GLOBAL_CAP=32` (`:33`) bounds total queued memory regardless of origin diversity — spreading across subdomains buys no extra capacity, only fairness loss against other legitimate dApps, which is the cap's stated purpose (not a security boundary). The badge (`updateBadge`, `discovery-queue.ts:134-140`) renders only `String(this.queue.length)`, never any attacker-supplied string.
- **Response epoch / profile-switch suppression (Q10)**: `handleWalletMessage` (`background.ts:853-971`) captures `preEntryEpoch` BEFORE the first await (`:873`), fails closed via `enforceSessionProfileBinding` (`profile-switch-teardown.ts:45-69`) on a stamp/active-profile mismatch, and re-checks `switchEpoch.current() !== entryEpoch` AFTER dispatch (`background.ts:955-962`) before ever calling `sendResponse` — a response composed under profile A cannot be delivered to a session whose profile switched to B mid-dispatch, including the switch-then-lock case the epoch (not identity) comparison is designed to catch.

This should be **High**, not Moderate.
- **F-2** (chain-identity XOR-composite collision at signing): **REFUTE cluster placement, not substance.** `packages/aztec-runtime/src/utils/chain-identity.ts` and `execution/service.ts`'s signing path are outside c06's assigned file list (`raw/prompts/c06-dapp-bridge-dispatch.md` scopes to `wallet-bridge`, `wallet-sdk-schema-patch`, `content-script`, `wallet-sdk/*`, `dapp-session/*` only) and this is a verbatim restatement of **c08-execution-fee-signing-codex.md F-1**, already independently confirmed by `c08-execution-fee-signing-claude.md` F-1 (`chain-identity.ts:53-61`). Counting it here double-books one bug across two clusters — dedupe against c08 at consolidation, don't score it as native c06 work.
- **F-3** (discovery admission omits duplicate waiters + reconnect verify windows): **CONFIRM the reconnect-window half, DOWNGRADE the duplicate-waiter half.** Reconnect half verified independently: `handleDiscovery`'s `existingSession` branch (`background.ts:647-651`) returns before ever reaching `checkDiscoveryPopupCaps` (`:670`, only checked on the fresh-connection branch), and every session establishment — new or reconnect — opens `chrome.windows.create` whenever `!dappSession.trustedVerification` (`session-established.ts:143-152`); `trustedVerification` is `undefined` by default and flips `true` only via an explicit checkbox the user must tick in `popup/windows/verify/index.vue:73-76`. The duplicate-waiter half is real (`background.ts:664-668` skips the cap check entirely via the early `awaitPendingPopupDedupe` return, and `checkDiscoveryPopupCaps`'s accounting at `:750` counts only distinct `pendingDiscoveryPromises` keys) but I downgrade its severity: it produces no extra popup, window, or attacker-visible effect — only extra Promise/closure fan-in for the lifetime of the ALREADY-pending single popup, cleared the moment that one popup resolves (`:833-835`).
