You asked us to break the bridge contracts — swap, approve, permit2 — and find how someone steals user funds. The good news first: the swap/permit2/approve path you worried about is well-built. We actively tried about ten attacks on it across two AI model families and cleared them with proof — including a malicious swap contract, which is fenced in to exactly the trade the user signed. The real danger is somewhere you didn't ask about: how the bridge is switched on and who holds the keys.

⚠ One critical issue is LIVE right now

The L1 "portal" contract that the shipping faucet deposits into (0x9c41…11ea on Sepolia) can be re-configured by anyone — we proved it by re-pointing the real deployed contract from a random throwaway account in a test. Until it's migrated, treat that testnet portal and the L2 minter key as compromised-by-design. This does not block testnet experimentation, but none of F-001/F-002 may survive into any real-value deployment.

✅ Cheapest fixes first (land these in the first PR — hours of work)

  • F-003 — Turn on the contract tests in CI. The team already wrote the safety checks (content-hash equality, router invariants); they just never run automatically. This is the highest-value, lowest-cost fix — it prevents a future Aztec upgrade from silently freezing every deposit.
  • F-008 — Add one missing nonReentrant word to the swap contract's sweep (minutes).
  • F-005 — Make the reusable runSwapBridge helper refuse unsafe private-fuel inputs instead of silently stranding gas (hours). The shipping app is already safe; this protects future callers.

🔗 Ship these together

  • F-001 + its deploy-window twin — the portal needs both an "already initialized" lock and atomic deploy-then-initialize; one without the other still leaves a gap.
  • F-003 + the witness-hash check — same CI PR: also flip WitnessHash.t.sol from printing to asserting, so the L1↔JS signature pin is two-directional.
  • F-004 (router) + the swap-target note — binding the swap target into the signed message fixes both the router and swap-cluster versions at once.

Findings

CriticalF-001Anyone can re-configure the live L1 portal and drain it
Claude + Codex ×3confidence: highCWE-665fix: days · migrationPoC verified ✓

What it is. The L1 portal is the vault that holds bridged tokens and relays messages to Aztec. Its one-time "set up" function was copied from Aztec's example code, which never locks itself — so it can be "set up" again, by anyone, at any time, forever. The portal that real users are depositing into today has this flaw live.

What an attacker would do. Call the set-up function again, pointing the portal at a fake messaging system they control, then withdraw the real tokens sitting in the vault to themselves — the portal happily releases them because it now trusts the attacker's fake "this withdrawal is approved" answer. They can also silently redirect every future deposit. We deployed nothing malicious — we simply re-pointed the real deployed contract in a fork test and it accepted it.

The fix. Fork the portal to add a one-line "already set up? then stop" check, deploy-and-set-up in a single transaction, and have the deploy script read the values back to confirm. The current live portal can't be patched in place — it must be redeployed and the app pointed at the new one.

Technical trace + verified PoC

Trace. upstream/TokenPortal.sol:37-46 — initialize() has no owner check, no initializer modifier, no first-call guard, and re-derives rollup/outbox/inbox from the caller-supplied registry. Drain path: attacker fake-registry → fake-outbox, then withdraw() at :146-148 does outbox.consume() (attacker no-op) → underlying.safeTransfer(attacker, held). Live address pinned at faucet/public/testnet-bridge.json:5, UI-wired via bridge-deployments.ts:18. Deploy/init split across txs: bridge-core/scripts/deploy-bridge-testnet.ts:113,191.

PoC (VERIFIED PASSING, poc/PortalReinit.t.sol, Sepolia fork on real bytecode):

live underlying (before): 0xA40A2FE147b7e96325d7c7D974B1f11C3ED82c68  (real AZLO USDC)
[PASS] test_F001_attacker_reinitializes_the_LIVE_portal()
F-001 CONFIRMED: live portal is permissionlessly re-initializable

Fix. Forked portal: if (address(registry) != address(0)) revert AlreadyInitialized(); as line 1 of initialize; re-pin the keccak; atomic deploy+init; deploy-time read-back asserts. Migrate 0x9c41…11ea.

HighF-002The L2 "minter" key is a permanent print-money backdoor into the L1 vault
Claude + Codexconfidence: highCWE-266fix: days · redeploy

What it is. On Aztec, a "minter proxy" decides who is allowed to create the bridged token. Its owner can appoint new minters and mint unlimited tokens — and unlike the bridge contract, the proxy's owner can never be changed (it's a single account, frozen at deploy, with no way to hand it to a safer multisig).

What an attacker would do. If that one owner key is ever stolen, the thief appoints themselves a minter, prints a huge amount of bridged tokens, then "exits" them back to L1 — which makes the L1 vault pay out real funds. The bridge's pause switch doesn't help, because the proxy is a separate contract the attacker calls directly.

The fix. Give the proxy the same two-step ownership the bridge already has, move that owner to a multisig/timelock, and freeze the minter list to just the bridge after setup. At minimum, that key must never live on a hot wallet in a real deployment.

Technical trace

token_minter_proxy/main.nr:24-27 owner is initialize-only — verified no transfer/rotate function exists. :55-58 set_minter authorizes anyone; :68-88 mints arbitrary amounts → token_bridge/main.nr:126-145 exit_to_l1_* → TokenPortal.sol:146-148 releases L1 underlying. Deploy authorizes only the bridge today (deploy-bridge-testnet.ts:185) but nothing freezes the set. PoC sketch: TXE — owner set_minter(attacker,true) → mint → exit → L1 consume → assert portal balance dropped.

HighF-003The contract safety tests are never run automatically — a bad upgrade could freeze every deposit
Claude + Codex ×3confidence: highCWE-1059fix: hours · CHEAPEST

What it is. For a deposit to work, L1 and L2 must compute the exact same "message fingerprint." The team wrote a clever test that checks both sides match — but that test, and all the other contract tests, are not part of CI. Today everything matches; the safety net just isn't plugged in.

What gets triggered. The next time someone upgrades the Aztec libraries (routine maintenance), a fingerprint could drift. CI stays green, the change ships, and from that moment every deposit pulls the user's tokens on L1 but can never be claimed on L2 — funds frozen, with no automated warning.

The fix. Add a small CI job that runs the Solidity (forge test) and Noir (nargo test) suites on any change to the bridge folders, and make it required. Also flip one test that currently only prints its result to actually assert it. Hours of work; biggest safety return in this report.

Technical trace

Verified: rg 'forge test|nargo' .github/workflows → none. Quality / Status = Biome + vue-tsc + bun audit only. Guards that never run: bridge-aztec/keystone/src/main.nr, bridge-evm/test/ContentHash.t.sol, WitnessHash.t.sol (only console.log, no assertEq), SwapBridgeRouter.t.sol. Content-hash equality matches byte-for-byte today (selectors mint_to_public(bytes32,uint256)/mint_to_private(uint256)/withdraw(address,uint256,address) vs the Noir vectors). Fix: paths-filtered bridge-contracts.yml running both suites + verify:l1, required check.

MediumF-004The swap contract isn't locked into the user's signature — a compromised owner can skim slippage
Claude + Codexconfidence: highCWE-829fix: hours + redeploy

What it is. When a user signs a fueled bridge, the signature pins the route but not which swap contract runs it — and the owner can swap that contract out instantly. Strong guards stop a malicious swap contract from touching the user's principal, but they don't force it to give a fair price — only the user's minimum.

What an attacker would do. A compromised owner points the swap at a contract that returns exactly the user's worst-acceptable amount and pockets the difference — limited to the slippage band on the small fuel slice (~3%), never the main funds. Requires owner-key compromise, which is why it's Medium, not High.

The fix. Add the swap-target address to the signed message. Then changing it instantly voids every outstanding signature — closing this cleanly. Or make the target immutable/timelocked.

Technical trace

SwapBridgeRouter.sol:142-146 instant setSwapTarget; witness (:52-56) omits the target; guards :196/199/204 bound it to (==fuelAmount in, ≥minFuelOutput out) but not fair value. Fix: add address swapTarget as witness field #12 (+ JS mirror). PoC sketch: Foundry — malicious target pulls full fuelAmount, returns exactly minFuelOutput, keeps the rest; assert tx succeeds + target retains the skim.

MediumF-005The reusable bridge helper silently strands gas on bad private-fuel input (app itself is safe)
Codexconfidence: moderateCWE-20fix: hours

What it is. The shared runSwapBridge library function trusts its caller to pass the right private-fuel secret and recipient. If a caller forgets the secret, it quietly invents a random one — which permanently strands the fuel (the claimer can never reconstruct it).

What a user would trigger. The shipping faucet always passes the correct values, so end users are not affected. But any future integrator (or a refactor) that uses the helper directly with a private bridge and a missing secret loses the gas with no error.

The fix. Make the helper derive the secret/recipient itself for private bridges and reject unsafe overrides — fail loudly before signing instead of stranding funds.

Technical trace

bridge-core/src/flows.ts:259 const fuelSecret = p.fuelSecret ?? Fr.random(); fuelRecipient passed through unchecked (:276,:300); invariant is comment-only (:216-220). Faucet compensates at useDeposit.ts:530-543,646-650. Fix: when isPrivate, require claimer+bridgeSecretSalt, derive both internally, reject overrides.

LowF-006The swap contract is callable directly with zero slippage protection (self-harm/MEV)
Claudeconfidence: highCWE-668fix: hours

What it is. Anyone can call the swap contract directly (not just through the router) and set their minimum output to zero. The router path is safe (it pins the minimum in the signature); this only hurts someone who calls the raw contract carelessly.

What a user would trigger. A direct caller with min=0 gets sandwiched by an MEV bot. It's self-inflicted — no protocol or other-user funds at risk — so it's Low.

The fix. Restrict the swap to the router, or require a non-zero minimum.

Technical trace

UniswapFuelSwap.sol:88-115 permissionless; only bound is caller minOutput. The "hookless pool" route rule blocks hooks, not price.

LowF-007Private claims are bearer-secret (whoever has the secret can claim) — accepted risk
Claude + Codexconfidence: highaccepted-riskfix: deferred

What it is. For private deposits, the recipient isn't baked into the message — whoever holds the secret can claim to any address. This is inherited from Aztec's design, and binding the recipient (the planned end-state) requires forking + redeploying the portal and bridge.

What an attacker would do. Nothing, as long as the secret never leaks — it never appears on-chain, and the app encrypts it at rest. The one risk is off-chain: the secret is handed to the app in plaintext via a recovery hook; an integrator who logs or stores it unencrypted would let an observer claim first.

The fix. Until recipient-binding ships, document loudly that the plaintext secret must never be logged or stored unsealed. (Recipient-commitment = weeks, deferred.)

Technical trace

token_bridge/main.nr:104-122 private content hash omits recipient; TokenPortal.sol:90-112 carries only Poseidon(secret). Leak seam: flows.ts:46-64,263-268 RecoveryHooks.onSecret. Faucet seals at rest (useDeposit.ts), never logs.

LowF-008Swap contract's sweep lacks the reentrancy guard the router's has
Claudeconfidence: highCWE-691fix: minutes

What it is. The owner-only "sweep stuck tokens" function on the swap contract is missing the nonReentrant guard that the equivalent on the router has. Latent only — there's no accounted balance to exploit today.

The fix. Add the modifier for consistency. One word.

Technical trace

UniswapFuelSwap.sol:290-303 (no guard) vs SwapBridgeRouter.sol:287 (guarded).

InfoINFO-1/2/3Testnet-shaped shortcuts & a script glitch

INFO-1: the faucet token has permissionless minting + grants Permit2 infinite allowance for everyone — fine for a testnet faucet (Permit2 still needs a signature), but a severe footgun if copied to a real-value token. INFO-2: pausing the L2 bridge doesn't stop L1 deposits, so during an incident in-flight deposits sit unclaimable (recoverable on unpause; add a UI pre-check). INFO-3: a smoke-test script guesses the message index instead of reading the event, which can hang on concurrent deposits — script-only.

What we tried and could NOT break (proof the core is solid)

These were actively attacked by both model families and cleared with reasoning — they are the reassuring half of the report:

  • Permit2 replay / signature confusion — the signed message binds the router, chain, and Permit2 contract; the 11 fields are consistent across Solidity and JS; the fork test covers replay/expiry/tamper.
  • Malicious swap contract stealing principal — three guards (floor, balance-delta, exact-consumption) fence it to the signed trade; over-delivery only strands the attacker's own funds.
  • Weird tokens (fee-on-transfer/rebasing) — revert the whole transaction; self-harm only.
  • Native-ETH swap reentrancy — guarded, callback locked to the pool manager, V4 reverts on unsettled balances.
  • Minting bypass / pause evasion — only the bridge is a minter; the pause reverts the whole atomic transaction.
  • Withdraw double-spend / front-running — nullifier + recipient baked into the message; front-running only delivers funds to the right person.
  • JS payload / weak secret / zero slippage (the shipping app) — field order matches, secrets are cryptographically random, slippage floor enforced, secret sealed and never logged.

Cross-cutting themes

The weak axis is setup & authority, not logic

Every serious issue is about who can change configuration after deploy — not the swap/permit2/content-hash math, which is well-built. The remedy is the same throughout: bind it into the signature, lock it after first use, or move it off a hot key to a multisig and freeze it.

The safety checks exist but aren't plugged in

The team wrote the right guards (content-hash keystone, witness pin, router tests, verify-l1). They just don't run in CI, and one only prints instead of asserting. Wiring them up (F-003) is the single highest-leverage, lowest-cost action here.

Don't let testnet shortcuts graduate

The permissionless faucet token, the infinite allowance, the hot-key owners, and the re-initializable live portal are all reasonable for a testnet faucet — and all exactly the things that become incidents if the same artifacts/patterns are promoted to a value-bearing deployment. Gate the promotion.
