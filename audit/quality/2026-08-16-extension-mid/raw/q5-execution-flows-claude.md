### Finding: `initWalletSdkHandler` is a 375-line composition function wiring 4 protocol callbacks, a transport monkeypatch, and 4 listeners

1. **Title:** Long Method — `initWalletSdkHandler` fuses composition-root wiring with protocol-handler logic
2. **Smell name:** Long Method (Fowler)
3. **Maintenance impact:** structural. Blast radius: the whole wallet-sdk protocol surface (discovery, session-establish, message dispatch, decrypt serialization, tab lifecycle, dApp-session revocation) lives in one function's closure scope — any change to one concern risks touching variables shared with the others. Change frequency: 4 commits touching this file in the last 180 days (security-sensitive protocol surface, moderate churn).
4. **Concrete evidence:** `apps/extension/src/wallet/services/wallet-sdk/background.ts:76-450` — one function (`export function initWalletSdkHandler`) that: constructs `WalletSdkDispatcher` (86-101); declares 3 closure-scoped concurrency-control collections (`pendingVerification` Set, `pendingDiscoveryPromises` Map, `sessionQueues` Map — 109-131); constructs `BackgroundConnectionHandler` inline with a ~50-line `addContentListener` closure containing subframe-rejection + zod-validation security logic (135-196) and 4 more inline callbacks (`onPendingDiscovery` 198-210, `onSessionEstablished` 212-256, `onSessionTerminated` 258-261, `onWalletMessage` 263-320, ~120 lines combined); monkeypatches `handler.handleEncryptedMessage` with a second hand-rolled FIFO queue (`decryptQueues`, 332-344); then registers 4 more independent listeners (`onDappSessionDeleted` 356-380, `onActiveProfileChanged` 383-414, `chrome.tabs.onRemoved` 417-419, `chrome.tabs.onUpdated` 425-444) before `handler.initialize()` (446).
5. **Why it harms future change:** every one of the 9 distinct concerns (discovery, verification-popup dedup, session FIFO, decrypt serialization, revocation teardown, unlock-drain, tab-close, tab-navigate) is a top-level statement inside the same function body, sharing the same closure variables (`handler`, `pendingVerification`, `pendingDiscoveryPromises`, `sessionQueues`, `discoveryQueue`). A change to, say, tab-navigation termination requires scrolling through unrelated discovery/decrypt/session code to find the right block, and a future contributor adding a 10th concern has no natural extraction boundary to follow — the file will keep growing linearly in the same function.
6. **Smallest safe refactoring:** Extract Method — split into named private functions (e.g. `wireDiscoveryHandling`, `wireSessionMessageQueue`, `wireDecryptSerialization`, `wireTabLifecycle`, `wireDappSessionRevocation`, `wireUnlockDrain`), each taking the shared collaborators (`handler`, `dispatcher`, services) as parameters, called in sequence from `initWalletSdkHandler`. Mirrors the collaborator-extraction pattern already used in `execution/service.ts` and `runtime.ts` elsewhere in this cluster.
7. **What disappears after the refactoring:** the need to read 375 lines of unrelated protocol machinery to change one listener; the implicit coupling where every closure can accidentally read/mutate every other concern's state.
8. **Instances:** single instance, `apps/extension/src/wallet/services/wallet-sdk/background.ts:76-450`.

### Finding: Hand-rolled keyed-promise-chain FIFO serialization reimplemented independently 3 times, with no shared primitive

1. **Title:** Missing "per-key Lock" abstraction — `Map<string, Promise<...>>` chaining hand-rolled 3x
2. **Smell name:** Duplicate Code, with a Missing Abstraction analog (the codebase already has the two building blocks — `wallet-core`'s `Lock` class, used via `.withLock()`, and the per-key `Map<string, Lock>` idiom in `activity-protocol/coordinator.ts`'s `lockFor()` — but none of these 3 sites reuse either; each reimplements the "get-previous-or-resolved, chain `.then`, write back" shape from scratch).
3. **Maintenance impact:** structural. Blast radius: 2 files, 3 independent call sites, each carrying its own subtly different error-swallow/cleanup logic. Change frequency: `account/service.ts` 8 commits / `wallet-sdk/background.ts` 4 commits in the last 180 days.
4. **Concrete evidence:**
   - `apps/extension/src/wallet/services/account/service.ts:179-197` — `tupleLocks: Map<string, Promise<unknown>>` + `serializePerTuple()`: `const previous = this.tupleLocks.get(key) ?? Promise.resolve(); const next = previous.then(op, op); this.tupleLocks.set(key, next.catch(() => {}))`.
   - `apps/extension/src/wallet/services/wallet-sdk/background.ts:334-344` — `decryptQueues: Map<string, Promise<void>>`, monkeypatching `handleEncryptedMessage`: `const prev = decryptQueues.get(sessionId) ?? Promise.resolve(); const next = prev.then(() => origDecrypt(...)); decryptQueues.set(sessionId, next.catch(() => {}))` — structurally identical chain shape to the above.
   - `apps/extension/src/wallet/services/wallet-sdk/background.ts:120,131,263-320` — `pendingDiscoveryPromises`/`sessionQueues` Maps; `onWalletMessage`'s `const prev = sessionQueues.get(key) ?? Promise.resolve()` (265) is the same chain-and-store-back idiom, composed with the `createSessionBaton()` early-release helper.
   - Contrast (the idiom already exists correctly, unused by the above): `apps/extension/src/wallet/services/activity-protocol/coordinator.ts:83,85,94-101` — `lockFor(map, key)` lazily creates a per-key `Lock` instance and returns `.withLock(op)`, i.e., the same "serialize per key" need solved via the shared `Lock` primitive instead of a hand-rolled promise chain.
5. **Why it harms future change:** a bug fixed in one chain's error handling / cleanup (e.g., the dead cleanup callback in Finding 6 below) doesn't propagate to the other two — each site must be independently reasoned about and independently fixed. A future per-key serialization need (there are 3 so far) will likely become a 4th hand-rolled copy rather than reuse.
6. **Smallest safe refactoring:** Extract Class — a `KeyedLock`/`PerKeyQueue` utility in `@nulo/wallet-core/utils` (sibling to the existing `Lock`) wrapping the `Map<string, Lock>` idiom already proven in `activity-protocol/coordinator.ts`, then have `serializePerTuple`, the decrypt monkeypatch, and (where its early-release semantics allow) the session-message queue delegate to it.
7. **What disappears after the refactoring:** 3 independent, subtly-different implementations of the same concurrency primitive; the dead-code drift documented in Finding 6 (which a shared, tested primitive would not have).
8. **Instances:** `apps/extension/src/wallet/services/account/service.ts:179-197`; `apps/extension/src/wallet/services/wallet-sdk/background.ts:120-131`, `:263-320`, `:334-344`.

### Finding: Dead cleanup callback with a misleading comment in `account/service.ts`'s per-tuple lock

1. **Title:** No-op `finally` block that documents cleanup it never performs
2. **Smell name:** Dead Code, compounded by Comments-as-deodorant (the comment describes behavior — "cleanup the slot" — that the code directly beneath it does not implement).
3. **Maintenance impact:** local (single function), but high confusion cost: a future reader trusts the comment and assumes `tupleLocks` entries are reclaimed; it is not. Change frequency: part of `account/service.ts`, 8 commits in 180 days.
4. **Concrete evidence:** `apps/extension/src/wallet/services/account/service.ts:190-195`:
   ```
   void next.finally(() => {
       if (this.tupleLocks.get(key)?.then === undefined) return
       // Cleanup the slot only if no later callers chained onto it.
       // (We never know for sure without ref counting, but as a
       // best-effort the map entry stays harmlessly resolved.)
   })
   ```
   `this.tupleLocks.get(key)` is either `undefined` (early-return, no-op) or a `Promise` (whose `.then` is never `undefined`, so the guard never blocks that branch) — and in neither branch does the callback body call `this.tupleLocks.delete(key)` or mutate anything. The block has zero observable effect for any input; the three comment lines describe a cleanup step that was never written.
5. **Why it harms future change:** anyone debugging `tupleLocks` growth (e.g., while diagnosing a memory-retention report, or while extracting this into the shared `KeyedLock` from Finding 2) will read the comment, conclude cleanup already happens, and look elsewhere — wasting investigation time on a lead the code itself closes off.
6. **Smallest safe refactoring:** Remove Dead Code — delete the no-op `finally` block entirely (verify first whether the map is meant to self-prune; if so, implement the actual `if (this.tupleLocks.get(key) === next.catch(...)) this.tupleLocks.delete(key)` guard the comment describes). This naturally resolves once Finding 2's shared `KeyedLock` primitive is adopted (a single, tested cleanup path instead of a hand-rolled one).
7. **What disappears after the refactoring:** the discrepancy between documented and actual behavior; one less unexplained closure capturing `key`/`this` for no purpose.
8. **Instances:** `apps/extension/src/wallet/services/account/service.ts:190-195` (single instance).

Good design, not a smell.
