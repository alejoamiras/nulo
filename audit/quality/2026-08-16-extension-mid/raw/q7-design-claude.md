### Finding: Toast implemented twice with non-interoperable shapes (item-driven `Toast.vue` vs. singleton `ToastManagerBase.vue`)

1. **Title:** Duplicate toast concept, incompatible interfaces
2. **Smell name:** Alternative Classes with Different Interfaces (Fowler) — same domain responsibility ("show a transient status message") implemented by two classes with incompatible construction/data contracts.
3. **Maintenance impact:** structural. Blast radius: 2 components + 1 composable in `packages/design/src` (`ui/Toast.vue`, `ui/ToastManagerBase.vue`, `composables/toast.ts`) plus both downstream consumers — `apps/extension` (60+ `useToast()` call sites via the re-export shim `apps/extension/src/composables/toast.js`) and `apps/faucet` (`apps/faucet/src/composables/useToast.ts`, `apps/faucet/src/components/AppToastRegion.vue`). Change frequency: both files were last touched together in the `harden-quality` arc (`578861be`) and the original L2 externalization (`7ddf2196`), i.e. they move in lockstep whenever "toast" as a concept changes.
4. **Concrete evidence:**
   - `packages/design/src/ui/Toast.vue:6-15` — props-driven item: `kind?: "ok"|"error"|"info"`, `text: string`, `link?: {label,href}`, emits `dismiss`; `<style scoped>`.
   - `packages/design/src/ui/ToastManagerBase.vue:15-28` — composable-driven singleton: reads `useToast()` from `composables/toast.ts`, renders `toast.value.label`/`toast.value.icon`/raw `color?: "red"|"green"|"orange"` string, self-closes via internal timeout, `<style module>`, self-teleports.
   - `packages/design/src/composables/toast.ts:13-17,23` — `ToastOptions { label, icon?, color? }`, module-scope singleton `ref`.
   - Consumers are fully partitioned: `apps/extension` exclusively drives `ToastManagerBase` (`apps/extension/src/components/ui/ToastManager.vue:6,10`) through the shared singleton; `apps/faucet` exclusively drives `Toast.vue` (`apps/faucet/src/components/AppToastRegion.vue:12`) through its own independent multi-toast queue (`apps/faucet/src/composables/useToast.ts:22,26`) that never imports `@nulo/design/composables/toast`. Zero code path uses both.
5. **Why it harms future change:** anyone adding a new toast capability (e.g. an action button, a queueable multi-toast, a new severity) must decide which of the two shapes to extend and then re-implement it in the other, because the prop/option shapes (`ToastOptions.color: string` vs `Toast.vue`'s `kind: SeverityTone subset`) are not convertible without a translation layer. The two apps' toast behavior can silently diverge (already have: extension = single active toast, faucet = queue) with no shared test catching drift, and `severity.ts`'s doc comment only explains why the *color palette* differs — it does not justify or bound the full component/composable duplication.
6. **Smallest safe refactoring:** Extract Class + Template Method — pull a shared `ToastOptions`-shaped rendering primitive (`ToastItem`) that both `Toast.vue` and `ToastManagerBase.vue` compose, and let each app choose single-vs-queue behavior via a thin composable wrapper (`useToastQueue`) built on the primitive, rather than reimplementing the item markup/CSS twice.
7. **What disappears after the refactoring:** the second, independently-maintained toast item markup + CSS + prop contract; a single place to add fields like "action button" or a new severity tone that both apps get automatically.
8. **Instances:** `packages/design/src/ui/Toast.vue:1-70`; `packages/design/src/ui/ToastManagerBase.vue:1-105`; `packages/design/src/composables/toast.ts:13-44`; `apps/faucet/src/composables/useToast.ts` (parallel queue implementation, out-of-cluster but the other half of the duplication).

### Finding: Chip trio — Badge / Tag / DisclaimerTag with two disjoint variant vocabularies

1. **Title:** "Labeled chip" concept re-solved twice with incompatible tone/variant unions
2. **Smell name:** Duplicate Code / Alternative Classes with Different Interfaces analog — two components (plus a 7-line wrapper) solve the same UI problem ("small colored label chip") with separately-typed, non-shared variant vocabularies.
3. **Maintenance impact:** local-to-structural. Blast radius: 3 files in `packages/design/src` (`ui/Badge.vue`, `ui/Tag.vue`, `composite/DisclaimerTag.vue`). Change frequency: all three were touched together in the same two arcs (`578861be` harden-quality Q-11 severity unification, `4d245bbb` original L1/L2 primitives) — meaning every prior attempt to unify chip semantics touched all three but did not close this gap.
4. **Concrete evidence:**
   - `packages/design/src/ui/Badge.vue:6-14` — `BadgeVariant = Extract<SeverityTone, "info"|"warning"|"error"> | "purple"`, driven by `severity.ts`'s shared `SeverityTone` union.
   - `packages/design/src/ui/Tag.vue:2-4` — `type Tone = "neutral" | "test" | "warn"`, a **local**, un-exported union that does not reuse `SeverityTone` at all (no `"warn"` equivalent name reuse, no `"neutral"`/`"info"` mapping).
   - `packages/design/src/composite/DisclaimerTag.vue:1-7` — hardcodes `<Tag tone="test">`, i.e. it inherits `Tag`'s vocabulary, not `Badge`'s, so a caller wanting a disclaimer-styled badge instead has no equivalent.
   - `packages/design/src/severity.ts:1-16` — the doc comment explicitly acknowledges Badge/Banner/Toast share `SeverityTone` names post a prior unification (Q-11, `578861be`) but is silent on `Tag`; `Tag` was never folded in, so the fork is live, not just historical.
5. **Why it harms future change:** adding a new semantic tone (e.g. a "pending" status) requires updating `SeverityTone` in `severity.ts` for Badge/Banner/Toast **and separately** updating `Tag`'s local `Tone` union and its CSS, because the two are unrelated types — easy to update one and forget the other, producing visually inconsistent "pending" badges vs tags across the extension.
6. **Smallest safe refactoring:** Consolidate Conditional / Replace Type Code with a shared vocabulary — fold `Tag`'s `Tone` into `SeverityTone` (or an explicit `Extract<SeverityTone, …>` the way `Badge` already does), keeping per-component palettes as Badge already models, and have `DisclaimerTag` reference the same extracted subset name Badge/Tag/Banner/Toast share.
7. **What disappears after the refactoring:** the second, hand-maintained tone union (`Tag`'s local `Tone`) and the risk of a tone existing in Badge but not Tag (or vice versa) after a future addition.
8. **Instances:** `packages/design/src/ui/Badge.vue:7`; `packages/design/src/ui/Tag.vue:2`; `packages/design/src/composite/DisclaimerTag.vue:6`; `packages/design/src/severity.ts:1-16`.

### Finding: `Checkbox.vue` is a third, untyped prop-declaration style — the sole array-form `defineProps` in the package

1. **Title:** Checkbox drops all compile-time prop typing via array-form `defineProps`
2. **Smell name:** Primitive Obsession analog (type-erasure outlier) / Divergent Change at the convention level — the package has two documented, internally-typed conventions (see next finding), and `Checkbox.vue` uses neither: it uses the untyped array form, which erases all type information Vue/TS would otherwise check.
3. **Maintenance impact:** local. Blast radius: 1 component file + 2 direct consumers (`apps/extension/src/popup/pages/settings/security/reset.vue:156,159,162`) + 1 story file (`apps/extension/src/components/ui/Checkbox.stories.ts`). Change frequency: 1 commit total (`4d245bbb`, the original primitives extraction) — untouched since, so the gap has never been revisited.
4. **Concrete evidence:** `packages/design/src/ui/Checkbox.vue:5` — `const props = defineProps(["modelValue", "checked", "disabled"])`. Confirmed via a package-wide grep of every `defineProps` call site (`packages/design/src/{ui,core,composite}/*.vue`): 14 components use the runtime object-form with `PropType` casts (`Badge`, `Button`, `Banner`, `Toggle`, `SubPageHeaderBase`, `Flex`, `MaterialIcon`, `Tooltip`, `Text`, `LoadingState`, `SectionLabel`, `Icon`, `Popover`, `Input`), 9 use `defineProps<{...}>()` generics (`BrutalistTitle`, `Toast`, `ToastManagerBase`, `Tag`, `DripButton`, `BalanceRow`, `AddressDisplay`, `Spinner`, `EmojiGrid`), and exactly one — `Checkbox` — uses the bare array form with no type annotation anywhere on `modelValue`/`checked`/`disabled`.
5. **Why it harms future change:** every other component in the package gives callers and refactorers a compile-time signal (autocomplete, rename-safety, type errors) on its props; `Checkbox` gives none. A future rename of `checked` → `isChecked`, or a change of `modelValue`'s type, would silently type-check at both of `Checkbox`'s call sites even if wrong, unlike a rename on any of the other 23 typed components in the package.
6. **Smallest safe refactoring:** Replace Type Code / Parameterize — convert to `defineProps<{ modelValue?: boolean; checked?: boolean; disabled?: boolean }>()`, matching the generic convention already used by 9 sibling components (smallest-diff option since it needs no `PropType` import).
7. **What disappears after the refactoring:** the single unchecked prop surface in the package; `Checkbox` becomes traceable by the same tsc/rename tooling as every other component.
8. **Instances:** `packages/design/src/ui/Checkbox.vue:5`.

### Finding: Two coexisting, unenforced prop-declaration conventions across `packages/design/src`

1. **Title:** Runtime-`PropType` vs. generic-`defineProps<>` split has no lint gate
2. **Smell name:** Alternative Classes with Different Interfaces analog, applied at the authoring-convention level (per the mapping-phase lead) — two ways of declaring the same thing (component props) coexist with no rule steering new/changed components to one.
3. **Maintenance impact:** cosmetic-to-local on its own (each file is internally consistent and type-safe within its own convention), but it is the root cause that let the Checkbox outlier (previous finding) go unnoticed, and it means a contributor changing an existing "runtime PropType" component (e.g. adding a prop to `Button.vue` or `Input.vue`) has no in-repo example to copy from the "generic" half of the package, and vice versa. Blast radius: 23 of 24 prop-bearing `.vue` files in `packages/design/src` (excludes `Card.vue`, which has no props). Change frequency: the split was fixed at introduction time — 14 files trace to the original extension port (`4d245bbb`, "base/theme/font takeover... L1/L2 primitives"), the generic-style files trace to later "authored directly in the package" work (`7ddf2196`, "externalize the 9 L2 ui holdouts") — i.e. it is a structural fork by origin, not an active migration in progress.
4. **Concrete evidence:** grep of `defineProps` across `packages/design/src/{ui,core,composite}/*.vue` (listed in the previous finding) confirms a 14-vs-9 split plus the 1 untyped outlier, with no `biome.json` or eslint rule found constraining `defineProps` shape anywhere in the repo (checked `biome.json`; no `packages/design`-scoped eslintrc exists).
5. **Why it harms future change:** there is no automatic way to tell, from tooling, whether a new/edited component should look like `Button.vue` (`defineProps({...})` + `PropType`) or `Spinner.vue` (`defineProps<{...}>()` + `withDefaults`) — reviewers must catch inconsistency by eye, which is exactly how `Checkbox.vue`'s untyped array-form slipped in and has sat unnoticed since the package's introduction.
6. **Smallest safe refactoring:** Pick one convention (the generic `defineProps<{...}>()` form is already used by roughly 40% of the package and needs no `PropType` import) and either add a lint rule (`biome` doesn't currently support this Vue-specific check; an eslint-plugin-vue rule would) or fold the migration into the same pass that fixes the Checkbox outlier, converting file-by-file opportunistically rather than in one sweep.
7. **What disappears after the refactoring:** the "which pattern do I copy" decision point for new contributors, and the class of outlier this finding's sibling (`Checkbox.vue`) represents.
8. **Instances:** all `defineProps` call sites enumerated in Finding 3, item 4 above (14 runtime-`PropType` + 9 generic + 1 untyped-array across `packages/design/src/{ui,core,composite}/*.vue`).

### Finding: `internal/sanitize.ts` is a cross-package fork with no automated drift guard, despite a "byte-identical, keep it verbatim" claim

1. **Title:** Sanitize-string fork's "pinned" claim only pins one side
2. **Smell name:** Duplicate Code, compounded by Comments-as-deodorant — the code comment and test-file comment both assert the copy is guarded/pinned against drift from the extension's original, but the actual test only pins this file's own input→output behavior; nothing in CI compares the two source files or their outputs against each other.
3. **Maintenance impact:** structural (correctness-adjacent, but the finding itself is a maintainability/process gap, not the drift itself). Blast radius: 2 files across 2 packages (`packages/design/src/internal/sanitize.ts`, `apps/extension/src/utils/string.ts`), each with its own consumer surface (`packages/design/src/ui/Input.vue`'s `sanitize` prop; multiple extension service-layer callers per the map, e.g. backup + contact import). Change frequency: `packages/design/src/internal/sanitize.ts` has 1 commit (`7ddf2196`, its introduction as a fork); `apps/extension/src/utils/string.ts` has been touched independently since (`069a9e27`, unrelated to `sanitizeString` itself but demonstrating the file is still actively edited) — i.e. the two files are already on independent edit cadences.
4. **Concrete evidence:**
   - `packages/design/src/internal/sanitize.ts:1-18` — doc comment: "Byte-identical copy of the extension's `utils/string.ts` `sanitizeString`... Behavior is pinned byte-for-byte by `sanitize.test.ts`; do not 'improve' the regex." Implementation: `s.replace(/[^\p{L}0-9 \-._]/gu, "")` + length-cap.
   - `apps/extension/src/utils/string.ts:33-42` — identical implementation, identical regex, identical length-cap logic.
   - `packages/design/src/internal/sanitize.test.ts:4-6` — its own comment: "If this drifts from the extension's `utils/string.ts`, Input's `sanitize` behavior diverges across the two apps — keep it verbatim." The test suite that follows (lines 7-35) only asserts fixed input/output pairs against the **local** copy; it does not import, read, or execute `apps/extension/src/utils/string.ts` in any way.
   - `apps/extension/src/utils/string.test.ts` exists as a fully separate test file for the extension's own copy — confirming the two copies are tested in isolation with no shared fixture or cross-check.
5. **Why it harms future change:** a future edit to either regex (e.g. extending the allowed character set for a new locale) will pass both test suites independently even if the two files now diverge, silently reintroducing the exact bug class ("Input's `sanitize` behavior diverges across the two apps") the comments warn against — the comments describe a guard that does not exist.
6. **Smallest safe refactoring:** Introduce Assertion — add one cross-file test (in either package, importing both source files by relative/workspace path) that runs a shared fixture table through both `sanitizeString` implementations and asserts identical output; this converts the comment's claim into an enforced invariant without changing either implementation.
7. **What disappears after the refactoring:** the false sense of safety from a comment that describes a non-existent guard; a real CI signal on drift instead of a code-review-only expectation.
8. **Instances:** `packages/design/src/internal/sanitize.ts:9-18`; `apps/extension/src/utils/string.ts:33-42`; `packages/design/src/internal/sanitize.test.ts:1-35` (the unenforced claim).

### Finding: `Input.vue`'s `handleInput` mixes sanitize/maxLength/type-coercion concerns via type-code branching

1. **Title:** `handleInput` does sanitize + warning-state + 3-way type coercion in one function
2. **Smell name:** Long Method, compounded by Switch Statements (Fowler's type-code-branching variant, here via `if/else if` on `props.type`/`props.subtype` rather than a literal `switch`).
3. **Maintenance impact:** local-to-structural. Blast radius: 1 file (`packages/design/src/ui/Input.vue`), but `Input` is one of only 15 components the extension's `design-resolver.ts` auto-resolves bare (per the orientation map, §2), so behavior changes here affect every extension input field. Change frequency: 2 commits total (`578861be`, `7ddf2196`) since the package's introduction — moderate, tracks the package's two audit/extraction arcs.
4. **Concrete evidence:** `packages/design/src/ui/Input.vue:137-178` — `handleInput(event?)` sequentially: (a) conditionally sanitizes via `sanitizeString` (line 140), (b) manages `maxLength` warning state + slices + emits `maxLengthReached` (lines 142-154), (c) branches on `props.type === "number"` to emit a parsed float (156-160), else branches on `props.subtype === "int"` to re-derive the value from the raw DOM event, clamp against `props.max`, and coerce `text.value` to a **different type** (string vs number vs the literal `0`) than the string-sanitize path above (161-172), else emits the raw text (175-176). A 4th related branch, `handlePaste` (201-233), duplicates the maxLength-slice-and-reposition logic independently of `handleInput`'s own maxLength branch.
5. **Why it harms future change:** adding a 4th numeric subtype (e.g. `"float"`) means inserting another `else if` into an already-branching method that already mixes three different responsibilities (text sanitization, length-warning UI state, numeric coercion) and two different mutation targets for `text.value` (string vs number vs literal `0`) — a change to one subtype's branch risks breaking the shared `maxLength`-warning logic that all branches fall through, since `fillWarning`/`emit("maxLengthReached", …)` execute unconditionally before the type-specific branch runs.
6. **Smallest safe refactoring:** Extract Method / Replace Type Code with Strategy — split into `applySanitize(text)`, `applyMaxLengthWarning(text)`, and `coerceByType(text, event)` (with the `type==="number"` / `subtype==="int"` / default branches becoming three small, independently testable functions), called in sequence from a slimmed `handleInput`.
7. **What disappears after the refactoring:** the single ~40-line function doing three unrelated jobs; a future subtype addition touches only the coercion extraction point, not the sanitize/warning logic above it.
8. **Instances:** `packages/design/src/ui/Input.vue:137-178` (primary); `packages/design/src/ui/Input.vue:201-233` (`handlePaste`, duplicated maxLength-slice logic sharing the same root cause).
