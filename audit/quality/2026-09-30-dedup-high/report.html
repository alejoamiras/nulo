This review looked for code that is written more than once. A copy is cheap on the day it is made, but every later change to the rule it encodes has to find and update every copy by hand. The review kept 27 findings: 9 High, 16 Medium and 2 Low. Two different AI model families (Claude and Codex) checked the top ten independently against the code. All ten held up; three were trimmed where the reviewers showed a part was not a real copy.

The strongest evidence is copies that already disagree. In five of the High findings one copy was fixed or extended and its twin was not, and three of those are real bugs confirmed by the separate bug hunt. An edited Local Network is reported as the wrong chain and left out of backups. A saved fee estimate can abort a dApp send on a brief node hiccup that its twin handles. An account rename can bring back an account that no longer signs. The checking also found new mismatches. History shows cancelled operations from other networks. Two of the four new-password forms lack the browser's 'this is a new password' hint. A contact name with a trailing space slips past the duplicate check.

Most of the cost comes from one habit: a helper exists and some screens or services just do not use it. The recommended order is to fix the High findings that already have mismatched copies first, fixing the bug and removing the copies in the same change. Then come the half-day wins, with the trust screen's phishing check first. Last, add a simple automated check so the bypassed patterns cannot grow back. Anything that changes what a user sees goes to the owner with screenshots first.

  • found by Codex
  • confidence: high
  • wrong result, state invariant violation
  • fix: hours — save first, then update memory

What it is. When the user changes a setting, Nulo updates it in memory first and saves to disk second. If the save fails, trying again with the same value looks like 'nothing changed' and reports success without saving. Turning Developer Mode off also turns Debug Mode off in a second save that nobody waits for.

What a user would run into. A user switches to dark theme during a moment when browser storage refuses writes. It looks applied, but after the browser restarts it is back to light. Or they turn off Developer Mode, the second save fails, and after a restart the wallet keeps detailed debug logs with the Debug Mode switch hidden.

The fix. Save to disk first and only then update memory, and save the Developer Mode group of switches together in one write.

Technical trace

Where: (a) apps/extension/src/wallet/services/config/service.ts:50-51 → wallet/config/store.ts:61-66 (and apply() :93-98) mutate and emit before storage.set; a same-value retry hits the equality shortcut at :61. (b) popup/pages/settings/advanced/index.vue:108-127 fires updateSetting('debugMode', false) un-awaited; wallet/logger/store.ts:27 reads it after restart.

Fix: In ConfigStore.set/apply, persist a staged copy, then swap memory and emit. In the popup, await the cascade or write {developerMode, indicateFailures, debugMode} in one setValues call.

MinorB-18

A failed history save can leave a transaction stuck as 'Pending'

  • coordinator-checked
  • found by Codex
  • confidence: high
  • state invariant violation
  • fix: hours — build, save, then swap

What it is. Nulo regularly checks whether sent transactions have been confirmed. When the status changes, it updates its in-memory copy before saving. If that one save fails, every later check sees 'no change' and never tries to save again.

What a user would run into. A user's transaction is dropped by the network at the moment browser storage has a hiccup. The activity list keeps saying 'Pending' until the browser or extension restarts.

The fix. Build the new status, save it, and only then update memory.

Technical trace

Where: apps/extension/src/wallet/services/transaction/service.ts:375 → :478-479 sets tx.status on the object in the pending map → :486 txs.set rejects → every later poll returns early at :463 because the status already matches.

Fix: In updateTx, build a next-state object, persist it, then swap the pending and watch maps and emit.

MinorB-20

A failed storage read can bring back tokens the user deleted

  • coordinator-checked
  • found by Codex
  • confidence: low
  • silent corruption (conditional)
  • fix: hours — separate read errors from bad data

What it is. Nulo pre-installs some common tokens and keeps a list of which ones the user deleted, so they are not added back. If reading that list fails once, Nulo treats it as empty and saves it back, wiping the record of earlier deletions.

What a user would run into. A user long ago deleted 'Clean USDC'. Today they delete 'USD Coin' while browser storage briefly fails a read. The next time Nulo sets up default tokens, Clean USDC is back.

The fix. If the list cannot be read, stop instead of saving an empty list; only reset it when the stored data is actually malformed.

Technical trace

Where: apps/extension/src/wallet/services/token/service.ts:604 → token/seeder.ts:301,337 (updateMarker) → :683-686 readMarkerState swallows a read error as {} → :342 writes the whole blob back with only the new tombstone.

Fix: Let updateMarker, retry and commitSeedResult see read errors from readMarkerState; keep the reset-to-empty only for malformed shape.

Model disagreement: Claude: a defensible trade-off. Coordinator kept it at Minor/low: the doc justifies not throwing on bad shape, not overwriting after a read error.

Cross-cutting observations

Checking 'same profile?' before saving

The most common family of bugs: a piece of code notes which profile or item it is working on, waits for something slow, and then saves without checking whether the user switched profiles or changed that item in the meantime (B-04, B-05, B-12, B-15, B-17). Nulo already protects against the page being closed during the wait, but not against the profile changing underneath it. One shared helper that checks 'is this still the same activation?' right before every save would close these at once. It must compare an activation counter, not just a profile id, because switching A to B and back to A would fool an id check.

Fix the twin, not just the bug

Seven bugs are a safety check that exists on one of two sibling functions and is missing on the other: send and simulate versus profile (B-03), two network status checks (B-09), two estimate caches (B-08), account create versus import (B-12), two popup commit helpers (B-17), the transaction watcher versus task updates (B-06), and unlock versus profile creation (B-21). These are the cheapest bugs to fix and the cheapest to prevent: whenever a fix lands, search for its twin in the same change.

Save first, then update memory

Two bugs change the in-memory value before saving it to disk and then skip saving when the value 'has not changed' (B-14, B-18). One failed save becomes permanent until a restart. The safe order is: prepare the new value, save it, and only then update memory and tell listeners.

Screens that read their data only once

The popup reuses page and list components when only part of the address or list changes. Components that load their data only when first shown then display stale data (B-22, B-23, and the same shape on the transaction detail page). Loading from the current address or props whenever they change, and giving list rows stable identities, fixes the whole family.

Timers that must agree

Several features have two timers that must fit together. The authwit preview lasts 2 minutes while the approval lasts 10 and the dApp call 5 (B-02), and B-01's new confirmation wait must also fit inside those 5 minutes. When one timer is set, the other side should be checked in the same change.

Looked at and set aside (12)
  • The 'too many pending requests' error code never reaches dApps: deliberate and pinned by a test; the docs that promise it should be corrected instead.
  • The approval window's 10 minute timeout: the dApp's own 5 minute limit always fires first, so it never matters.
  • Imported notes with negative or hex amounts: amounts always come from a valid 128-bit number, so this cannot happen.
  • Switching to a network with no main endpoint: nothing in normal use creates such a network, and the next call fails loudly.
  • Duplicate balance rows on the home screen: the event that could duplicate them carries zero balances, so totals are unaffected.
  • Backup filename with slashes in the profile name: every way to set a name already strips them.
  • Error types lose their class when crossing to the popup: nothing checks the class there, and the messages survive.
  • Log viewer quirks (never pruning, a leaked timer, listeners after close): Developer-Mode-only window whose page is thrown away when closed; no wrong data.
  • Renaming a profile that is half-deleted: already pinned as known, and such a profile is hidden everywhere in the UI.
  • Event listeners skipped when one removes itself mid-dispatch: the only place this happens has a single listener, so nothing is skipped today.
  • Onboarding briefly uses the system theme: a one-frame colour flash on the next popup open, cosmetic only.
  • Stale entry in the third-party notices during watch builds: only a developer watch mode is affected; shipped builds start clean.
