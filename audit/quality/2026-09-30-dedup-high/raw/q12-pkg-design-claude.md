- **Maintenance impact:** local per component, but package-wide blast radius: every design-system pass (token rename, tone change, prop rename) must keep 7 unused components + 7 test files compiling and green. - **Evidence:** Repo-wide grep (`apps/**`, `packages/**`, `.vue/.ts/.js/.mdx`, excluding `packages/design` and generated `types/components.d.ts`) for tag use (`<Card`, `<Tag`…) and for `import {…} from "@nulo/design"` finds no consumer of: `Card` (`packages/design/src/ui/Card.vue`, 19 lines), `Tag` (`ui/Tag.vue`, 37), `Toast` (`ui/Toast.vue`, 70), `BalanceRow` (`composite/BalanceRow.vue`, 55), `DripButton` (`composite/DripButton.vue`, 34), `DisclaimerTag` (`composite/DisclaimerTag.vue`, 7, only importer is `Tag` inside the package), `AddressDisplay` (`composite/AddressDisplay.vue`, 69). Only their own tests + `index.ts` exports keep them alive. `Toast` was already noted by the 08-16 audit as a "judgment call" versus `ToastManagerBase`; it is simply unused.
- **Why it harms future change:** `AddressDisplay` exists twice with the same name and different contracts (design: `head/tail` slice + `…`, clipboard write inside the component, `—` for empty; extension: store-coupled, `trimAddress` `..`, `formatter`/`full`/`static` props). Anyone who imports `AddressDisplay` from the barrel (the natural autocomplete) gets different truncation and copy semantics than every other screen, and a truncation-rule change has two plausible homes. `Card`/`Tag`/`BalanceRow` also restate surface/border recipes (`--nulo-surface` + `--nulo-outline` box) that a token pass must keep in sync for zero users.
- **Smallest safe refactoring:** Remove Dead Code: delete the 7 SFCs, their `.test.ts`, their barrel lines in `index.ts:26-56`, and their `mount-all.test.ts` entries; update README. If `AddressDisplay`/`Tag` are wanted later, resurrect from git. Do not migrate the extension-local `AddressDisplay` into the package as part of this (it is store-coupled; a real L3 version would need its own plan).
- **What disappears:** ~700 lines (337 src + 364 tests), 7 files + 7 tests, 7 barrel exports, one same-name collision.
- **Instances:** `packages/design/src/ui/Card.vue`, `ui/Tag.vue`, `ui/Toast.vue`, `composite/BalanceRow.vue`, `composite/DripButton.vue`, `composite/DisclaimerTag.vue`, `composite/AddressDisplay.vue`; barrel `packages/design/src/index.ts:26-56`; shadowed twin `apps/extension/src/components/AddressDisplay.vue`.

## q12-pkg-design-C-2: Theme-dependent hairline/scrim/border values hard-coded ~35 times in extension CSS instead of tokens

- **Smell:** Duplicate Code of a magic value, which is Shotgun Surgery in practice (Change Preventers). Named analog: Config sprawl (same knob duplicated across N files), with a theme-divergence defect on top.
- **Maintenance impact:** structural, blast radius ~35 sites in ~28 extension files + the design package (missing tokens). Change frequency high: these are popup screens touched weekly (`RecentActivityView`, `TransactionCard`, `Settings/*`, `send.vue`).
- **Evidence:** the design package declares `--border` (`base.css:89`, = `rgba(74,70,63,.5)` dark / `rgba(124,116,104,.3)` light), `--border-hovered`, `--nulo-border` (#231f1c), `--app-bg` (#0a0908), `--white`, but has no soft-hairline or scrim token, so extension CSS inlines the dark-theme literal:
  - `rgba(74, 70, 63, 0.2)` ×11 and `rgba(74, 70, 63, 0.3)` ×7 (+ `.25/.45` in ContactRow): `components/composite/activity/TransactionTerminalCard.vue:103`, `TransactionIncomingCard.vue:93`, `TransactionAwaitingCard.vue:150`, `TransactionCardLayout.vue:198`, `capabilities/PermissionRow.vue:81`, `capabilities/DetailsTable.vue:137`, `ui/Settings/SettingField.vue:65`, `SettingValue.vue:70`, `SettingItem.vue:180`, `popup/components/Navigation.vue:61`, `modules/activity/TransactionCard.vue:213`, `modules/general/GasBalanceCard.vue:188`, `RecentActivityView.vue:883`, `modules/send/fee-shared.module.css:4`, `modules/settings/contacts/ContactRow.vue:92,170-171`, `pages/settings/glossary.vue:60`, `pages/settings/connected-apps/index.vue:206`, `windows/capabilities/AccountSelectRow.vue:140`.

The "fix" is itself copy-pasted per file, which is the duplication signature.
  - `rgba(35, 31, 28, 1)` (= dark `--nulo-border`) ×3: `CollapsingHeroLayout.vue:228`, `pages/send.vue:810`, `pages/settings/security/reset.vue:180`.
  - Overlay scrims `rgba(10, 9, 8, α)` (= dark `--app-bg`) with six different alphas (0.8, 0.8, 0.82, 0.85, 0.85, 0.92): `Popup/Popup.vue:148`, `composite/DappCancelledOverlay.vue:33`, `LegalAcceptanceSheet.vue:136`, `GlobalLoader.vue:33`, `passkey/PasskeyCeremonyDialog.vue:107`, `composite/BarrierOverlay.vue:31`.

  - The `var-undefined` guard (`theme-vars.ts`) only checks that referenced vars exist, never that a literal should have been a var, so nothing stops more.
- **Why it harms future change:** restyling the row divider or dimming the scrim (or making the light theme actually consistent) is a 20-35 file edit, and the three places that did handle light show the edit will be partial. A new theme would need every literal found by grep.

This is a **user-visible change in light theme** (hairlines there currently stay dark-hued), so per CLAUDE.md it needs owner sign-off with screenshots; a dark-only, byte-identical first step (token = today's literal) needs none. Lives in `packages/design` (lowest shared layer).
- **What disappears:** ~35 literals, 3 duplicated light-theme override blocks, six unexplained alpha variants collapse to 1-2.
- **Instances:** listed above.

## q12-pkg-design-C-3: Dark palette declared twice in `base.css` (`:root` and `[theme="dark"]`), 28 identical declarations with no equality test

- **Smell:** Duplicate Code (Dispensables), compounded by Shotgun Surgery for any dark-value change.
- **Maintenance impact:** structural; 1 file, but it is the token root for every consumer (extension popup, onboarding, landing via `base.css`). Change frequency: 7 commits to date (all since 2026-06-01), i.e. every theme tweak.
- **Evidence:** `packages/design/src/base.css:72-123` (`:root`) and `base.css:194-245` (`[theme="dark"]`) both declare `--app-bg --card-bg --tooltip-bg --dropdown-bg --border --border-hovered` `--txt-{primary,secondary,body,tertiary,support,white,inverse}`, `--white --black` and the ten palette colours (`--blue … --sand`), byte-identical values (28 of ~41 `:root` declarations re-appear verbatim; `:root` alone additionally owns `--nulo-*`, `[theme=dark]` additionally owns `--json-*`/`--log-*`, so the split is arbitrary). The `[theme="light"]` block (`:125-192`) repeats the 12 palette colours a third time (`:166-177`) and `--base-width/--base-height/--bezier` a third/fourth time. `theme-contrast.ts:themeMap` merges `:root` + `[theme]` (`:37-40`) so the contrast suite cannot notice a `:root`/`[theme=dark]` mismatch, and `tokens.parity.test.ts` only checks names one-way against the contract.
- **Why it harms future change:** a colour edit in `[theme="dark"]` (the one `data-theme` users get) silently leaves `:root` (what landing and any un-themed page get) stale, or vice versa; the contrast test passes either way because the later block wins.
- **Smallest safe refactoring:** Consolidate Duplicate Conditional Fragments: make the dark values live only in `:root` (selector `:root, [theme="dark"]` if the attribute selector is needed for specificity), keep only the `--json-*`/`--log-*` dark extras in a second block, and hoist theme-invariant values (palette colours, `--base-*`, `--bezier`, fonts) out of the light/dark blocks. Add one assertion in `theme-contrast.test.ts` that `themeMap("dark")` has no key whose value differs between `:root` and `[theme=dark]`. Generating `base.css` token blocks from `token-contract.ts` would finish the job but is larger than the smallest fix.
- **What disappears:** ~28 + 12 + ~8 declarations (~50 lines) and the silent-drift surface.
- **Instances:** `packages/design/src/base.css:72-123`, `:125-192`, `:194-245`.

## q12-pkg-design-C-4: Settings row shell CSS copy-pasted across `SettingField` / `SettingValue` / `SettingItem`

- **Smell:** Duplicate Code (Dispensables); candidate for Extract Component / shared style (`composes`).
- **Maintenance impact:** local, 3 files; the row shell is the visual spine of every settings screen. jscpd's biggest production CSS clone (42 lines). Low recent churn (4 commits since 2026-06-01) but any settings-row restyle touches all three.
- **Evidence:** `apps/extension/src/components/ui/Settings/SettingField.vue:34-75` and `SettingValue.vue:39-80` are byte-identical for the `.wrapper` block (padding 14px 16px, hover/active surfaces, `.disabled`, the `::after` hairline at `left/right: 16px`, `:last-of-type::after`); `diff` of the two files shows only template differences (Field stacks label/value in a column, Value puts them in a row with a value slot) and the `.value` block. `SettingItem.vue:~165-190` re-implements the same hover/active/disabled/`::after` divider with `20px` insets and `:last-child`. The divider colour is the hard-coded literal from C-2.
- **Why it harms future change:** a hover-state, disabled-opacity, or divider change is three edits and `:last-of-type` vs `:last-child` already diverged, which changes which row loses its divider when a non-row sibling is present.
- **Smallest safe refactoring:** Extract Style: `components/ui/Settings/setting-row.module.css` with `.wrapper` (+ a `--row-inset` custom property for 16px vs 20px) and `composes:` it from the three SFCs, the pattern the repo already uses (`RecentActivityView.vue:947` composes from `list-empty.module.css`).
- **What disappears:** ~42 duplicated lines in the two byte-identical files and ~20 more in `SettingItem`.
- **Instances:** `SettingField.vue:34-75`, `SettingValue.vue:39-80`, `SettingItem.vue:~160-190`.
