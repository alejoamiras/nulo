## q05-popup-modules-C-1: Live token-balance snapshot state machine hand-copied into BalanceView and TokensView (and a third, lighter copy in SelectTokenPopup)

- **Smell:** Duplicate Code (semantic, ~60 lines of protocol) leading to Shotgun Surgery; Vue analog: composable-extraction opportunity. Precedent for the extraction exists (`composables/runFence.ts`, `useScopedTokens`).
- **Maintenance impact:** structural. Blast radius 3 files in the popup plus `pages/send.vue` (a fourth, simpler variant); `BalanceView.vue` 17 and `TokensView.vue` 12 commits since 2026-06-01, both hot. The logic is race-fencing code, the kind that gets bug-fixed in one copy and not the other.
- **Evidence:** the same six-part protocol is written out twice, with only renamed identifiers:
  1. `inActiveScope(tb)`: `TokensView.vue:192`, `BalanceView.vue:179`, `SelectTokenPopup.vue:70` (byte-identical predicate).
  2. `fetchDirty` flag: a snapshot in flight is older than an event that lands meanwhile, so the event marks it dirty and the fetch refetches (`TokensView.vue:190,205,212,285,296`; `BalanceView.vue:185-188,236,241,248,275`).
  3. `onBalanceAdded/Updated/Deleted` triplet (`TokensView.vue:193-218`; `BalanceView.vue:235-252`; `SelectTokenPopup.vue:77-89`).
  4. "first connect is the mount's own, any later one is a port drop, so resnapshot" counter: `balanceConnectsSeen` `TokensView.vue:220-225`, `connectsSeen` `BalanceView.vue:254-259`, `connectsSinceShow` `SelectTokenPopup.vue:93-97`.
  5. `BALANCES_RETRY_MS = 2_000` + `fetchGeneration` + one timed retry + `loading|unavailable|loaded` state (`TokensView.vue:268-303`; `BalanceView.vue:262-292`).
  6. `forChain(rows, chainId)` and the empty-address short-circuit that sets `loaded` (same two fetch functions).
  `TokensView.fetchTokenBalances` and `BalanceView.fetchTokenBalances` differ only by TokensView adding a `scopeGen` check and `withTaskFlags`. `pages/send.vue:140-146` plus `pages/send-balance-events.ts` (`applyBalanceAdd/Update`) is a fourth hand-rolled event-apply of the same events, with no fence at all.
- **Why it harms future change:** changing the stale-snapshot rule (e.g. a new `refreshTokenBalance` event, a new scope dimension, a different retry policy, or fixing one of the failure modes the comments describe) must be made 3 to 4 times, and nothing ties the copies together. The copies already drifted: BalanceView `onBalanceAdded` pushes without the id dedupe TokensView has, and BalanceView `onBalanceDeleted` reassigns the array while TokensView splices.
- **Smallest safe refactoring:** Extract Composable (C1) `useTokenBalanceSnapshot({ client, scope, mapRow? })` in `apps/extension/src/composables/` returning `{ rows, state, refetch, dispose }`. The parent still owns connect/disconnect per the C1 rule. It takes the existing `runFence` for the generation. `inActiveScope` goes with it. TokensView keeps its `withTaskFlags` via `mapRow`; BalanceView reads `rows`/`state`; SelectTokenPopup uses `refetch` on show. Leave `send.vue` alone unless it wants the fence.
- **What disappears:** roughly 55 lines from each of BalanceView and TokensView and ~35 from SelectTokenPopup (about 150 lines net after the composable's ~70), 3 copies of the reconnect counter, 3 `inActiveScope`s, and the drift between them.
- **Instances:** `popup/components/modules/general/TokensView.vue:190-303`; `popup/components/modules/general/BalanceView.vue:179-292`; `popup/components/popups/SelectTokenPopup.vue:70-130`; (variant) `popup/pages/send.vue:140-146` + `popup/pages/send-balance-events.ts`.

## q05-popup-modules-C-2: `recent-activity-rows.ts` re-implements `txRows` / `incomingRows` from `utils/activity-rows.ts` line for line

- **Smell:** Duplicate Code (two functions with different names doing the same job, in a file whose header claims "deliberately not buildActivityRows"). The wrong half of the code was forked: only the journal leg and the token filter differ.
- **Maintenance impact:** structural-local. Blast radius 2 files plus the two surfaces (home preview, Archives page). The scope rules are security-adjacent ("a single missed guard can't leak another account's rows"). Low churn on `recent-activity-rows.ts` (1 commit since 06-01), but the rules it copies change whenever a new scope dimension appears (profile scoping was the last one, and it had to land in both).
- **Evidence:** `recent-activity-rows.ts:54-67` `scopedTxRows` vs `utils/activity-rows.ts:79-88` `txRows` (same three `continue` guards, same `key`/`sortKey`). `recent-activity-rows.ts:69-82` `tokenScopedIncomingRows` vs `activity-rows.ts:107-128` `incomingRows` (same account/network/profile guards plus the identical blockTimestamp*1000 vs `discoveredAt` sortKey rule, same 4-line comment rationale; the only delta is one leading `if (token && inc.tokenId !== token.id) continue`). jscpd lead `recent-activity-rows.ts:56-66` vs `utils/activity-rows.ts:80-90` confirmed real. `isForeignProfile` was already exported and shared, so the extraction stopped one step short.
- **Why it harms future change:** a new scope field or a change to incoming sort semantics (the `blockTimestamp` precedence was a deliberate fix) has to be applied to both, and the home preview and the Archives page would disagree silently if only one is updated.
- **Smallest safe refactoring:** Extract/Move Function: export `txRows` and `incomingRows` (taking `RowScope`) from `utils/activity-rows.ts`; `recent-activity-rows.ts` calls them and applies its token filter by pre-filtering `incomingTransfers` (`token ? list.filter(i => i.tokenId === token.id) : list`). Keep `buildRecentActivityRows`' own journal handling, which really does differ.
- **What disappears:** ~30 lines and one sortKey comment block; the "deliberately not" header shrinks to the journal-only difference.
- **Instances:** `popup/components/modules/general/recent-activity-rows.ts:54-82` vs `utils/activity-rows.ts:79-128`. Adjacent echo of the same profile predicate inlined instead of calling `isForeignProfile`: `TokensView.vue:66` and `RecentActivityView.vue:270` (`op.profileId && appStore.profile?.id && op.profileId !== appStore.profile.id`), and the whole `journalRecordInScope` account/profile/network filter (`RecentActivityView.vue:265-278`) parallels `visibleTokenImports` (`TokensView.vue:59-75`).

## q05-popup-modules-C-7: Every price consumer spins up its own `PriceServiceClient` + `usePrices` + dispose/disconnect quartet, including one per token row and one per tx card

- **Smell:** Duplicate Code (boilerplate that must change together) plus a Vue analog: over-instantiated per-instance service clients where a provided one exists (`app.vue` already owns `arrivalsPrices`, and `ARRIVALS_KEY` is provided).
- **Maintenance impact:** structural-local, blast radius 16 files (8 in this cluster: `TokenCard.vue:44`, `TransactionCard.vue:115`, `TransactionsList.vue:38`, `BalanceView.vue:91`, `RecentActivityView.vue:215`, `TokensView.vue:82`, `GasBalanceCard.vue:74`, `FeeSettingsCard.vue:169`; others `app.vue:69`, `pages/{holdings:63,activity:54,send:244,journal/[id]:52,received/[id]:79,tx/[id]:103}`, `SelectTokenPopup.vue:49`).
- **Evidence:** each site repeats `new PriceServiceClient(); usePrices(client); onBeforeUnmount(() => { prices.dispose(); client.disconnect() })` (`TokenCard.vue:44-52` documents the per-row instantiation: "mounted per-row from the tokens list; the shared cache keeps this cheap"). `usePrices` starts its own refresh (`refreshIfStale`) on each construction (`usePrices.ts:40-50`), so N rows mean N resnapshot requests and N `onConnected`/`onQuotesUpdated` subscriptions.
- **Why it harms future change:** any change to the price client's lifecycle (connect semantics, a new required option, moving the freshness ticker) touches 16 sites, and forgetting the `dispose`-before-`disconnect` order (CLAUDE.md "cleanup order") is easy to get wrong in a new copy. Per-row clients also multiply subscriptions for a list that is meant to cap at a handful.
- **Smallest safe refactoring:** Extract Function: a `PRICES_KEY` provided once by `popup/app.vue` (same pattern as `ARRIVALS_KEY`), `inject`-ed by rows and cards (`TokenCard`, `TransactionCard`, `TransactionsList`), with the client owned by the shell (parent owns lifecycle, honouring the C1 rule). Pages that want their own keep their own. Moderate confidence: verify the provided instance is acceptable to `e2e`/unit harnesses that mock the client per component.
- **What disappears:** ~4 lines and one `onBeforeUnmount` per consuming row component (TokenCard, TransactionCard, TransactionsList, and the other 5 in-cluster) and N-1 redundant price subscriptions per list.
- **Instances:** listed above.
