# ext-ui-popups — quality/dedup scan (claude)

Scope audited: `apps/extension/src/popup/components/{popups,modules}`, `apps/extension/src/popup/windows/`, `apps/extension/src/components/{composite,ui,flat}`. All 6 repo-map duplication candidates were independently re-verified against source (not taken on faith); one independent finding (clipboard duplication's error-handling drift) sharpens candidate #4 with a concrete correctness-adjacent gap. Candidate #6 (confirm-dialog shape) is confirmed as a non-finding.

## Findings

### 1. Byte-identical dead `<style module>` block copy-pasted across 4 files (+1 near-copy)

- **Smell**: Dead Code (Dispensables), compounded by Duplicate Code — the same dead block was propagated by copy-paste rather than written once.
- **Impact bucket**: local (each file's stylesheet is self-contained; no cross-module coupling) — blast radius 5 files, ~290 combined dead lines. Change frequency: **not dormant** — `git log` shows `NewAccountPopup.vue`/`EditAccountPopup.vue`/`NewNetworkPopup.vue`/`EditNetworkPopup.vue` were all touched by `#328` (activity siloing hardening), `#246` (storage-migration framework), and notably `#220` ("harden-quality arc — 21/22 audit findings, behavior-preserving") — a prior quality pass touched these exact files and still didn't remove this block.
- **Evidence**: `.network`/`.icons`/`.item` style rules (58 lines), md5-identical (`100d1e5576ba2f47c69d380f0c7eff80`) in:
  - `apps/extension/src/popup/components/popups/NewAccountPopup.vue:137-194`
  - `apps/extension/src/popup/components/popups/EditAccountPopup.vue:96-153`
  - `apps/extension/src/popup/components/popups/NewNetworkPopup.vue:194-...` (same body)
  - `apps/extension/src/popup/components/popups/EditNetworkPopup.vue:133-...` (same body)
  - `apps/extension/src/popup/components/popups/NewSenderPopup.vue:180-...` (same 3 classes + `.shake`/`@keyframes shake`, which in THIS file are the only ones actually wired)
  Verified zero live references: no static `class="...network..."` / `...icons...` / `...item...` in any of the 5 templates, and no `$style[` dynamic bracket access in any of them (checked via grep across each file). The block styles a network-list row that doesn't exist in any of these components' current templates.
- **Why it harms future change**: a future editor sees `.network`/`.icons`/`.item` still defined 5 times and has to independently re-derive, per file, that none of it is live before touching styling — the exact kind of check `#220`'s quality pass apparently skipped. It also inflates diff noise on any Biome/format touch to these files.
- **Smallest safe refactoring**: **Inline (delete)** the dead block in each of the 4 exact-duplicate files; for `NewSenderPopup.vue`, delete only the 3 unreferenced classes and keep `.shake`/`@keyframes shake` (that one IS used — see finding evidence for `EditContactPopup.vue`'s independently-dead `.shake` below, which looks like a copy of this file's *live* class that lost its trigger). No behavior change since nothing references the removed selectors.
- **Instances**: `NewAccountPopup.vue:137-194`, `EditAccountPopup.vue:96-153`, `NewNetworkPopup.vue:194-231`, `EditNetworkPopup.vue:133-170`, `NewSenderPopup.vue:180-217` (partial — only `.network`/`.icons`/`.item`, not `.shake`).

### 2. "Already exist(s)" uniqueness-validation triple duplicated across 10 sites, already diverged

- **Smell**: Duplicate Code (Dispensables), with early evidence of Shotgun Surgery — the string literal has already drifted (`"Already exist"` vs `"Already exists"`) across copies with no shared source to keep them in sync.
- **Impact bucket**: structural — no shared validator exists, so every new "must be unique" field re-derives the same 3-part shape by hand; blast radius 8 files / 10 call sites. Change frequency: these popups are edited whenever a new entity type (account/contact/endpoint/fpc/network/token) gets uniqueness rules — a recurring category, not a one-off.
- **Evidence**: the shape is always (a) a `useFormState` field `validate` returning the literal string, (b) a `computed` re-checking `form.fields.X.error.value === "<literal>"`, (c) an inline `<Text>` warning using the same literal in the template:
  - `NewAccountPopup.vue:33,41,123` ("Already exist")
  - `NewContactPopup.vue:53,64,76,78,189,209` (×2 fields: name + address, "Already exist")
  - `NewFpcPopup.vue:31,48,155` ("Already exist")
  - `NewNetworkPopup.vue:36,45,55,56,158,179` (×2 fields: name + url, **"Already exists"** — inconsistent literal)
  - `NewTokenPopup.vue:42,50,332` ("Already exist")
  - `EditContactPopup.vue:71,82,98,99,234,254` (×2 fields, "Already exist")
  - `EditNetworkPopup.vue:31,44,115` (**"Already exists"**)
  - `EditFpcPopup.vue:35,74,250` ("Already exist")
- **Why it harms future change**: the grammar drift ("exist" vs "exists") is live proof this is Shotgun Surgery in practice — a copy-editing fix to one string does not propagate, and a future contributor fixing the typo in one file has no way to know 9 other sites need the same fix. Adding a 6th "New\*/Edit\*" entity type means hand-rolling this triple again instead of composing it.
- **Smallest safe refactoring**: **Extract Function** — a small `useUniquenessValidator(existingItems, extractKey, message)` composable (or a plain helper returning `{ validate, isAlreadyExist }`) consumed by `useFormState`'s `validate` callback, with the warning row extracted as a tiny `<FieldConflictHint>` composite consuming the same computed. After extraction, all 10 sites collapse to a 1-line call each and the "exist" vs "exists" grammar becomes a single copy decision.
- **Instances**: all file:line references listed under Evidence above (18 line references across 8 files, 10 logical call sites).

### 3. Clipboard-copy hand-rolled at 9 sites, with inconsistent error handling (one already-fixed bug not propagated)

- **Smell**: Duplicate Code (Dispensables) — worsened into a de facto Shotgun-Surgery-missed-fix: a corrected version already exists (`header-copy-address.ts`) but 7 of 9 sites still carry the pre-fix shape.
- **Impact bucket**: local-to-structural — no shared coupling risk, but a real behavioral gap: `window.navigator.clipboard.writeText(...)` can reject (permission denial, transient platform error, focus-loss in Chrome), and 7 of the 9 sites fire the success toast unconditionally, without `await` or a `catch`, so the user can be told "copied" when nothing was copied. Blast radius: 7 files (+1 already-correct + 1 partially-correct).
- **Evidence**:
  - **Correct pattern** (awaited, try/catch, honest failure toast) — `components/header-copy-address.ts:11-21` (`copyAddressToClipboard`, used only by `Header.vue`) and independently re-derived correctly in `popups/IncomingTrustPopup.vue:74-82`.
  - **Fire-and-forget, no error handling** (success toast unconditional):
    - `components/ScopeAddress.vue:47-54` (`handleClick`) — ships the exact same `stripWireControl` pre-processing as the correct helper, but without `await`/`catch`.
    - `components/ScopeClassId.vue:21-25` (`handleClick`)
    - `components/JsonViewer/JsonViewer.vue:72-78` (`handleCopy`)
    - `popup/components/popups/AccountsPopup.vue:44-50` (`handleCopyAddress`)
    - `popup/components/popups/EditFpcPopup.vue:146-149` (`handleCopyAddress`)
    - `popup/components/popups/TokenMetadataPopup.vue:39-42` (`handleCopyAddress`)
    - `popup/components/popups/ReceivePopup.vue:26-29` (`handleCopyAddress`)
    - `popup/components/modules/general/BalanceView.vue:135-138` (`handleCopy`)
  - `ScopeAddress.vue`'s own strip-then-write is byte-identical in intent to `copyAddressToClipboard`'s core line, confirming the two were forked from the same origin, not independently designed. `CapabilityDetailPanel.vue`'s header comment already self-flags this gap (referenced in repo map, not re-quoted here).
- **Why it harms future change**: a transient clipboard failure (documented Chromium behavior when the extension popup loses focus mid-click) currently produces a false-positive "copied" toast at 7 sites; the bug was already found and fixed once (`header-copy-address.ts`) but the fix's existence didn't stop 7 near-identical reimplementations elsewhere. Each new copy-button add is another coin-flip on whether the author copies the correct or the stale pattern.
- **Smallest safe refactoring**: **Extract Function**, generalize `copyAddressToClipboard` (rename to `copyToClipboard(text, openToast, { successLabel, failureLabel })`) out of `header-copy-address.ts` into a shared location (e.g. `src/composables` or `src/utils`), then **Inline** every hand-rolled `handleCopy*` at the 7 sites above to call it. After the refactor, the await/catch behavior is uniform and a future clipboard-API quirk fix (e.g. a Safari/Firefox fallback) is a one-file change instead of 9.
- **Instances**: `components/header-copy-address.ts:11-21`, `components/ScopeAddress.vue:47-54`, `components/ScopeClassId.vue:21-25`, `components/JsonViewer/JsonViewer.vue:72-78`, `popup/components/popups/AccountsPopup.vue:44-50`, `popup/components/popups/EditFpcPopup.vue:146-149`, `popup/components/popups/TokenMetadataPopup.vue:39-42`, `popup/components/popups/ReceivePopup.vue:26-29`, `popup/components/popups/IncomingTrustPopup.vue:74-82`, `popup/components/modules/general/BalanceView.vue:135-138`.

### 4. Near-duplicate "identity strip" component, two independent implementations

- **Smell**: Duplicate Code (Dispensables), component-level clone (not just a fragment).
- **Impact bucket**: local — only 2 files, but each is a full component clone including its entire `<style module>` block, so the blast radius per future visual tweak is 2x. Change frequency: unknown (no distinguishing git-log signal beyond the monorepo restructure commit).
- **Evidence**: `apps/extension/src/components/composite/DappStatusStrip.vue` (used by `popup/windows/discover/index.vue:6,143` and `popup/windows/capabilities/index.vue:6,262`) and `apps/extension/src/popup/windows/execute/SignerIdentityStrip.vue` (used by `popup/windows/execute/index.vue`) both render: a `status_${status}`-driven dot, account name, `·` separator, network name, and a trailing "NULO" brand mark. The entire `<style module>` block is identical class-for-class (`identity_strip`, `status_dot`, `status_ready/loading/cancelled`, `identity_account`, `identity_sep`, `identity_network`, `identity_brand`) — `SignerIdentityStrip.vue` adds exactly one extra rule (`identity_warn`, for its multi-signer "MIXED" case) on top of an otherwise byte-for-byte copy. `SignerIdentityStrip.vue`'s own header comment ("Different from `DappStatusStrip` because...") confirms it was deliberately forked from the other rather than designed as a variant of a shared base.
- **Why it harms future change**: any visual tweak to the identity-strip look (spacing, font, status-dot palette) has to be applied twice and re-verified for drift each time; `SignerIdentityStrip`'s multi-account branch already shows the components will keep diverging in behavior even while their CSS/skeleton stays copy-locked.
- **Smallest safe refactoring**: **Extract Superclass**-equivalent for Vue: pull the shared skeleton (dot + account/network line + brand mark + the identical CSS) into a base `IdentityStrip` composite taking `{ accountLabel, networkLabel, status, warn? }`, and have both `DappStatusStrip` (single-account call) and `SignerIdentityStrip` (pre-computing the "N accounts · MIXED" label) become thin wrappers that pass computed props into it. The duplicated `<style module>` block disappears from one of the two files entirely.
- **Instances**: `components/composite/DappStatusStrip.vue:1-96` (whole file), `popup/windows/execute/SignerIdentityStrip.vue:1-105` (whole file); consumers `popup/windows/discover/index.vue:6,143`, `popup/windows/capabilities/index.vue:6,262`, `popup/windows/execute/index.vue` (import + usage).

### 5. Five New\*/Edit\* popup pairs share an un-extracted structural shape

- **Smell**: Duplicate Code / Divergent Change (Change Preventers) — each pair independently re-derives the same service-lifecycle + form + submit skeleton, so any shared bug fix (e.g. the clipboard issue in finding 3, or the validation-string drift in finding 2) has to be hunted down and re-applied per pair rather than fixed once.
- **Impact bucket**: architectural — 10 files, ~2,400 combined lines, all built on the same `useFormState` + `FormPopup` + (`usePopupEntity` or a manual `watch(() => props.show, ...)`) skeleton. Change frequency: high — these are the most frequently touched popups per the inventory (Fpc/Network/Account/Contact/Endpoint CRUD is core wallet functionality).
- **Evidence**: confirmed common shape across all 5 pairs (`Account`, `Contact`, `Endpoint`, `Fpc`, `Network`):
  - `NewAccountPopup.vue` / `EditAccountPopup.vue` — both use `useFormState` + `FormPopup` + `usePopupEntity`; Edit adds `isStartedEditing` gating (`EditAccountPopup.vue:33`, mirrored by `isStartedEditingName`/`isStartedEditingAddress` in `EditContactPopup.vue:95-96`, `isStartedEditingName` in `EditNetworkPopup.vue:43`, `nameChanged`/`addressChanged` in `EditFpcPopup.vue:70-72`, `isStartedEditing` equivalents in `EditEndpointPopup.vue`).
  - `NewFpcPopup.vue` / `EditFpcPopup.vue` — both independently re-implement: connect/disconnect an `FpcServiceClient` on a `watch(() => props.show, ...)` (`NewFpcPopup.vue:94-114`, `EditFpcPopup.vue:151-180`), the same 3-event subscription (`onFpcAdded`/`onFpcDeleted`/`onFpcUpdated`), an identical Enter-to-submit `onKeydown` guard restricted to `HTMLInputElement`/`HTMLTextAreaElement` (`NewFpcPopup.vue:121-127`, `EditFpcPopup.vue:189-194` — the code comment in `EditFpcPopup.vue`... actually `NewFpcPopup.vue:122` literally says "see NewContactPopup for rationale", confirming the pattern is known to be copied across pairs, not just within one), and the same `processingError = { show, title, tooltip }` ref shape with matching `aboveSubmit` Tooltip markup (`NewFpcPopup.vue:178-207` vs `EditFpcPopup.vue:274-295`, near-identical JSX/template).
  - `NewEndpointPopup.vue` / `EditEndpointPopup.vue` and `NewContactPopup.vue` / `EditContactPopup.vue` confirmed to follow the same `useFormState` + `FormPopup` skeleton via direct grep (both present in all 4 files).
- **Why it harms future change**: this is the connective tissue that makes findings 2 and 3 possible — because there's no shared "entity CRUD popup" base, each pair's author re-derives validation, clipboard, service-lifecycle, and keydown-submit logic from whichever sibling pair they copied from, so fixes and improvements don't propagate. A 6th entity type (there is prior art for this — Token has New but no Edit) means another ~150-300 line fork.
- **Smallest safe refactoring**: not a single mechanical step (this is the higher-order pattern findings 2/3 are instances of) — **Extract Function** the FPC-service-lifecycle watcher (connect/disconnect + 3-event subscription) into a small composable (e.g. `useEntityServiceLifecycle(ServiceClient, { onAdded, onUpdated, onDeleted })`) shared by `NewFpcPopup`/`EditFpcPopup` first, as the two files with the most duplicated non-trivial logic (not just markup); the Enter-to-submit `onKeydown` guard is a 5-line **Extract Function** on its own, directly reusable by all 10 files.
- **Instances**: `NewAccountPopup.vue`, `EditAccountPopup.vue`, `NewContactPopup.vue`, `EditContactPopup.vue`, `NewEndpointPopup.vue`, `EditEndpointPopup.vue`, `NewFpcPopup.vue`, `EditFpcPopup.vue`, `NewNetworkPopup.vue`, `EditNetworkPopup.vue` (all in `apps/extension/src/popup/components/popups/`).

## Non-findings

- **Confirm-dialog invocation shape** (`cacheStore.confirm.{...}` + `popupStore.open("confirm")`) — verified defined exactly once in `ConfirmPopup.vue` and not re-invoked anywhere else under the audited directories (callers live in `popup/pages/**`, out of this cluster's scope). Repo map's candidate #6 confirmed correct as a non-finding.
- **`FormPopup` / `ItemsContainer`/`SettingItem`/`SettingField`/`SettingValue` / `usePopupEntity` / `useFormState` shared primitives** — these ARE the extraction points already in place (11, 10-11, 5, and 9 consumers respectively); they're the deliberate convention, not the smell. Not re-flagged.
- **`components/ui/Dropdown/*` internal structure** (`DropdownRoot` 310 LOC, `DropdownTrigger`, `DropdownItem`, etc.) — genuinely decomposed by responsibility (root/trigger/item/title/divider), not a Large Class; no duplication found across the 5 files.
- **Copy-icon-button visual pattern** (`Icon name="copy"` + `Tooltip`, seen in `AccountsPopup.vue`, `EditFpcPopup.vue`, `ContactRow.vue`, `FpcRow.vue`, `ReceivePopup.vue`, `TxDebugPanel.vue`, `Header.vue`) — this is markup-level reuse of the shared `Icon`/`Tooltip` primitives, not duplicated *logic*; the actual duplicated logic is the click-handler body, already captured in finding 3. Not double-counted as a separate finding.
- **Inline numeric/timestamp formatting** (`formatTimestamp` in `TxDebugPanel.vue`, `formattedAmount` in `IncomingTrustPopup.vue`) — each is a single-site, component-local computed with no sibling duplicate found in-scope; speculative to extract.
- **`RecentActivityView.vue` (963 LOC) / `FeeSettingsCard.vue` (714 LOC) size** — plausible Large Class candidates, but flagging them would require reading past the trace cap to confirm internal duplication vs. legitimately cohesive size; not pursued given the declared DUPLICATION focus and the stronger, cheaper-to-verify findings above.
- **`.shake`/`@keyframes shake` in `EditContactPopup.vue`, dead `.icon_btn` in `EditProfilePopup.vue`, dead classes in `AccountsPopup.vue`/`RevokeAuthwitsPopup.vue`/`SelectProfilePopup.vue`/`SelectTokenPopup.vue`/`BalanceView.vue`/`SelectNetworksPopup.vue`** — each is real dead code (verified no live reference) but single-instance per file, not cross-file duplication; keeping finding 1 scoped to the verified byte-identical 5x block per the "few findings that matter" guidance rather than listing 8 more one-off dead-code findings.
