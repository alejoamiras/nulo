# Repo map — bridge trio (wallet-bridge / wallet-sdk-schema-patch / bridge-core)

Scope: `packages/wallet-bridge`, `packages/wallet-sdk-schema-patch`, `packages/bridge-core` (incl. `scripts/`). `*.test.ts` excluded.

## 1. Module inventory

**`packages/wallet-bridge/src/`** (wallet-sdk protocol layer, consumed only by `apps/extension`) — 21 files, ~4.7k non-test lines. Largest: `dispatcher.ts` (1383, the RPC dispatch table), `method-descriptors.ts` (395), `method-scope-checkers.ts` (419), `operation.ts` (219), `dapp-interaction-protocol.ts` (156). Domain groups: protocol wire-types (`types.ts`, `operation*.ts`, `fee.ts`, `session-types.ts`, `transaction-origin.ts`, `authwit-content.ts`), scope/capability (`capabilities.ts`, `capability-map.ts`, `scope-enforcement.ts`, `method-scope-checkers.ts`), discovery (`discovery-queue.ts`, `caip.ts`, `account-resolution.ts`), and the dispatcher itself + its service contract (`services-contract.ts`).

**`packages/wallet-sdk-schema-patch/src/`** — 2 files, ~90 lines. `apply.ts` (the `registerToken`/`isTokenRegistered`/`grantPublicAuthwit` zod-schema patch, single source of truth) + `register.ts` (side-effect entry). Deliberately tiny — this is the package that *removed* a 3x inline duplication (extension/faucet/playground), per its own doc comment.

**`packages/bridge-core/src/`** (framework-agnostic L1↔L2 bridge logic, consumed only by `apps/faucet` + selectively by `apps/extension`'s fee code) — 25 files, ~5.5k non-test lines. Largest: `flows.ts` (428, orchestrated deposit/claim flows), `journal.ts` (275, write-ahead deploy journal), `backup.ts` (218), `l1.ts` (192), `recovery-crypto.ts` (200), `candidate-schema.ts` (186). Domain groups: fee/gas (`fee-juice.ts`, `quote.ts`), fuel/routing (`fuel.ts`, `private-fuel.ts`, `route.ts`, `router-abi.ts`), L1/L2 chain glue (`l1.ts`, `l1-receipt.ts`, `l2.ts`), deploy lifecycle (`journal.ts`, `candidate-schema.ts`, `promotion.ts`, `status.ts`), and backup/recovery (`backup.ts`, `recovery-crypto.ts`, `claim-secret.ts`, `seal-trust.ts`, `reuse-token.ts`, `content-hash.ts`).

**`packages/bridge-core/scripts/`** (operational — deploy/canary/smoke conductors, in scope per task) — 24 files, ~6.1k non-test lines. Largest: `live-intent.ts` (631, signer-intent gate), `deploy-bridge-testnet.ts` (559), `deploy-bridge-mainnet.ts` (526), `fuel-testnet.ts` (468), `deploy-sandbox.ts` (394), `smoke-existing-testnet.ts` (353). Shared low-level helpers already exist: `deploy-manifest.ts` (journal/candidate I/O), `deployer-keys.ts` (deterministic key resolution), `portal-artifact.ts` / `build-portal-artifact.ts` (forked-portal rebuild+verify), `live-intent.ts` (pinned-signer gate).

## 2. Public exports / entrypoints

- **`@nulo/wallet-bridge`** — single entry `"."` → `src/index.ts`, barrel re-exporting 17 of the 21 modules (excludes `capability-map`, `method-descriptors`, `method-scope-checkers`, `transaction-origin` from the top-level barrel — those are internal-only or re-exported transitively).
- **`@nulo/wallet-sdk-schema-patch`** — dual entrypoints: `./apply` (pure function `applyNuloSchemaPatch`) and `./register` (side-effect import), no default `"."`. Must be the FIRST import in any module constructing an `ExtensionWallet` proxy.
- **`@nulo/bridge-core`** — 4 declared entrypoints: `"."` → `src/index.ts` (barrel, 20 modules), `./artifacts`, `./fee-juice`, `./private-fpc-artifact` (the last two deliberately excluded from the main barrel — lazy-loaded to avoid eager bytecode pull; see `private-fpc-artifact.ts` header).
- **bridge-core script entrypoints** (invoked via `bun scripts/<name>.ts`, 2 wired into `package.json#scripts`: `deploy:sandbox`, `verify:l1`; the rest are ops-run-by-hand per their header comments): `deploy-bridge-{mainnet,testnet}.ts`, `deploy-private-fpc-{mainnet,testnet}.ts`, `deploy-sandbox.ts`, `deposit-testnet.ts`, `discover-mainnet-fuel.ts`, `drip-canary-testnet.ts`, `fee-juice-canary-testnet.ts`, `fpc-dust-canary-mainnet.ts`, `fuel-testnet.ts`, `relay-claim-testnet.ts`, `restore-swap.ts`, `smoke-existing-{mainnet,testnet}.ts`, `smoke-swap-existing-testnet.ts`, `check-fpc-version.ts`, `verify-l1.ts`, `build-portal-artifact.ts`.

## 3. Coupling surfaces + cross-package deps

- **No direct import** between `wallet-bridge` and `bridge-core` in either direction (grep confirms zero `@nulo/bridge-core` refs in `wallet-bridge/src`, zero `@nulo/wallet-bridge` refs in `bridge-core/src`). `wallet-sdk-schema-patch` is also not imported by either.
- `wallet-bridge` declares `@nulo/wallet-sdk-schema-patch` as a **devDependency only** (typecheck-time, not runtime wiring — the real activation import lives in `apps/extension`'s `wallet-sdk/background.ts`).
- **Indirect coupling via `apps/extension`**: `fee-strategy.ts` and `fpc-strategy.ts` (`apps/extension/src/wallet/services/execution/fee/`) both import `predictedWorstMinFees` from `@nulo/bridge-core/fee-juice`, while the same extension's popup/dispatcher layer consumes `wallet-bridge`'s `fee.ts` wire types (`FeePaymentMethod`, `PriorityLevel`, `GasBalances`). The extension is the ONLY consumer that pulls fee-related exports from both packages side by side — no shared "fee" package mediates between the wire-shape (wallet-bridge) and the domain-computation (bridge-core) halves.
- **`bridge-core` fan-out** is much wider than `wallet-bridge`'s: ~45 files across `apps/faucet` import it (composables, components, contracts), vs `wallet-bridge`'s consumers confined to `apps/extension`'s wallet-sdk/dapp-interaction/capabilities/execution layers.
- Both `wallet-bridge` and `bridge-core` independently pin the full `@aztec/*` 5.0.1 line as direct deps; `bridge-core` additionally pins `@alejoamiras/private-fee-juice`, `@aztec-foundation/aztec-standards`, and a `viem` fork — none of which `wallet-bridge` needs (it never touches L1).

## 4. APPARENT DUPLICATION candidates

**(a) L1+L2 client-bootstrap boilerplate, repeated near-verbatim across ≥8 `bridge-core/scripts` files — no shared helper.** The `createPublicClient/createWalletClient/defineChain/http` (viem L1 side) + `createAztecNodeClient` + `EmbeddedWallet.create(...)` (L2 side) + `--config <path>` CLI-arg parsing + `readFileSync`/`JSON.parse` manifest load block appears essentially copy-pasted in `deploy-bridge-mainnet.ts`, `deploy-bridge-testnet.ts`, `smoke-existing-mainnet.ts`, `smoke-existing-testnet.ts`, `smoke-swap-existing-testnet.ts`, `fee-juice-canary-testnet.ts`, `fpc-dust-canary-mainnet.ts`, `deposit-testnet.ts`. `deploy-manifest.ts`/`deployer-keys.ts`/`live-intent.ts` already extract *some* shared pieces, but the client/env bootstrap itself was never factored out. Highest-leverage target — touches the most files.

**(b) `deploy-private-fpc-mainnet.ts` vs `deploy-private-fpc-testnet.ts` — near-identical deploy conductor (74 vs 76 lines, diff ≈92/150 lines).** Both share, essentially verbatim: the `t0`/`mins()` elapsed-timer helper, the "already deployed at pinned address → early return" existence check via `node.getContract(pinned)`, and the closing `PrivateFPCContract.deploy(...).send(...)` → pinned-address assertion → success-log block. Only the fee-payment/account-bootstrap middle section differs (mainnet: funded deployer via claimed public FJ; testnet: throwaway account via SponsoredFPC). A shared `runPrivateFpcDeploy(node, ewallet, from, feePaymentMethod)` core would leave only the two networks' account/fee setup as the delta.

**(c) `deploy-bridge-mainnet.ts` / `deploy-bridge-testnet.ts` conductor pair (526 / 559 lines) and the `smoke-existing-mainnet.ts` / `smoke-existing-testnet.ts` pair (270 / 353 lines) — same structural skeleton, network deltas inlined rather than parameterized.** Both conductor pairs independently reimplement: write-ahead journal resume (`appendJournal`/`readJournal`/`resolveResume`), candidate-manifest emission (`writeCandidateAtomic`), portal artifact rebuild+verify, and expanded on-chain read-back assertions. The header comments in both mainnet variants explicitly document themselves as "the mainnet sibling of X-testnet.ts with these deltas" — i.e. the duplication is acknowledged-but-accepted (mainnet variants call the testnet file "battle-proven, left untouched"), not accidental. Lower-priority than (a)/(b) given the explicit no-touch rationale, but still ~250-300 lines of structural overlap per pair that a shared conductor-core + network-config object could collapse.

**Not duplication (checked and ruled out):** `wallet-bridge/src/fee.ts` (serializable wire-types: `FeePaymentMethod`, `PriorityLevel`, string-typed `claimAmount`/`claimSecret`/`messageLeafIndex`) vs `bridge-core/src/fee-juice.ts` (aztec.js domain logic: `predictedWorstMinFees`, `publicFeeJuicePayment`, bigint/`AztecAddress`-typed). Field-name overlap (`claimAmount`/`claimSecret`/`messageLeafIndex`) reflects the same protocol concept surfacing at two layers (wire vs domain), not copy-pasted logic — no shared function bodies, no candidate to merge. Flagged in §3 as a coupling/consistency risk instead (nothing mediates the two shapes today).
