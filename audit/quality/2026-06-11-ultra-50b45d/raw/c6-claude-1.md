## F1: Console-hijack block copy-pasted across all four entry shells

1. **Title**: Console-hijack block copy-pasted across all four entry shells.
2. **Smell name**: Duplicate Code (Fowler), producing Shotgun Surgery on any forwarding-behavior change.
3. **Impact bucket**: structural. Blast radius: 4 production entry files + 1 test shim + 4 sniffer wiring points. Change frequency: low per git (1–2 commits each), but every new HTML entry or logging-pipeline change touches all copies.
4. **Evidence**: the identical ~10-line block — `for (const [method, level] of consoleMethods) { (self as any)[`on${method}`] = (...args) => logger.log(<source>, level, ...args) }` plus `self.onunhandledrejection = (e) => logger.log(<source>, LogLevel.Error, getErrorData(e.reason))` — appears at:
   - `packages/extension/src/wallet/index.ts:54-67` (logger = `LoggerStore`, source `"wallet"`)
   - `packages/extension/src/popup/index.ts:5-17` (logger = `LoggerServiceClient`, source `"ui"`)
   - `packages/extension/src/offscreen/index.ts:20-47` (source `"pxe"`, plus the `isBenignSwDisconnect` demotion variant)
   - `packages/extension/src/onboarding/index.ts:13-24` (source `"ui"`)
   The mechanism is additionally split: the receiving `console.<m> → self.on<m>` shim (`src/utils/console-sniffer.ts`) is wired four different ways — HTML `<script>` tags at `offscreen/index.html:6`, `popup/index.html:8`, `onboarding/index.html:8`, and a static import at `wallet/index.ts:14` — and `tests/vitest.setup.ts:8-14` re-implements the `console._<m>` alias install a fifth time because unit tests don't load the sniffer.
5. **Why it harms future change**: adding a console method, changing the rejection envelope, or porting the offscreen benign-disconnect demotion to the popup (it already differs silently — popup/onboarding rejections flood the log on SW disconnect, offscreen demotes) requires finding and editing four near-identical blocks whose only discoverable link is visual similarity. A new entry (e.g. a side-panel-specific shell) must remember both the handler block AND the sniffer script tag; forgetting one buffers logs forever (`pendingLogs` never flushes).
6. **Smallest safe refactoring**: Extract Function — `installConsoleForwarding(logger: { log(src, lvl, ...a): void }, source: string, opts?: { demoteRejection?: (reason: unknown) => boolean })` colocated with `consoleMethods` (wallet-core/logger or `@/wallet/logger`). Each entry becomes one call; the offscreen variant passes `isBenignSwDisconnect`.
7. **What disappears**: 4 hand-synced blocks collapse to 1 implementation; the rejection-handling divergence becomes an explicit option instead of silent drift; the test shim can import the same constant list.
8. **Instances**: `packages/extension/src/wallet/index.ts:54-67`, `packages/extension/src/popup/index.ts:5-17`, `packages/extension/src/offscreen/index.ts:20-47`, `packages/extension/src/onboarding/index.ts:13-24`, `packages/extension/tests/vitest.setup.ts:8-14`; wiring: `src/utils/console-sniffer.ts` + `offscreen/index.html:6`, `popup/index.html:8`, `onboarding/index.html:8`, `wallet/index.ts:14`.

## F3: Browser config wrappers mutate the imported base config in place

1. **Title**: Chrome/Firefox wrappers mutate the shared base vite config object.
2. **Smell name**: Mutable Data (Fowler, Refactoring 2nd ed.) — module-scope mutation of a shared singleton; carries a temporal-coupling analog (correctness depends on "only one wrapper is ever imported per process", enforced nowhere).
3. **Impact bucket**: local (two 23-line files), latent-architectural failure mode. Blast radius: any tool that imports both configs (a future "build both browsers" script, a vitest config reusing the base, an IDE plugin evaluating configs). Change frequency: low.
4. **Evidence**: `packages/extension/vite.chrome.config.mts:7-18` and `packages/extension/vite.firefox.config.mts:7-18` both do `viteConfig.plugins?.push(crx({...}))` and `viteConfig.build.outDir = ...` directly on the default export of `vite.config.ts`. ES module instances are cached per process: importing both wrappers in one process pushes BOTH `crx` plugins into the same array and last-writer-wins the `outDir`. Today the two builds run as separate `vite build` CLI invocations (`package.json` `build:chrome` / `build:firefox`), so the bug is latent, not live.
5. **Why it harms future change**: the first person to write a single-process orchestration (a release script building both targets, a programmatic `build()` call in CI tooling, or a vitest config importing the base) gets a double-crx, wrong-outDir build with no error — the failure surfaces as a corrupted artifact, far from the cause. It also blocks the obvious F2 cleanup (sharing the base config with vitest) because importing it is unsafe.
6. **Smallest safe refactoring**: Replace Derived Variable with Query / Extract Function — export a factory from the base (`export const createBaseConfig = () => defineConfig({...})`) or have wrappers use vite's `mergeConfig(baseConfig, { plugins: [crx(...)], build: { outDir } })`, which returns a fresh object instead of aliasing.
7. **What disappears**: the shared-mutable-singleton hazard; the wrappers stop reaching into the base config's internals; the base config becomes safely importable elsewhere.
8. **Instances**: `packages/extension/vite.chrome.config.mts:7-18`, `packages/extension/vite.firefox.config.mts:7-18`.

## F7: Three bespoke JSON-stringify replacers inside wallet-core with divergent encodings

1. **Title**: Three hand-rolled safe-stringify variants in one package, two of which encode bigint and Error differently.
2. **Smell name**: Duplicate Code (Fowler); the serialization/error pair is also Alternative Classes with Different Interfaces (same job — "JSON-encode rich/hostile values without throwing" — two incompatible contracts).
3. **Impact bucket**: structural (wallet-core is the foundation layer; its outputs persist in storage and cross the message wire). Blast radius: `jsonStringify`/`jsonSanitize` have 7 external consumer files; `normalizeError` output lands in every persisted journal record. Change frequency: low since extraction (1 commit each), but jobs/ is the package's only repeat-change surface per the map.

   - `packages/wallet-core/src/utils/serialization.ts:24-57` — `jsonStringify` replacer: bigint → `"123"`, Buffer → base64, Map/Set → arrays, Error → `{name,message,stack?,code?,details?}`.

7. **What disappears**: the undocumented encoding fork; future Error-serialization changes become a one-module edit; the third (arrays) variant can document why it intentionally differs or reuse the scalar encoder.
8. **Instances**: `packages/wallet-core/src/utils/serialization.ts:24-57`; `packages/wallet-core/src/jobs/error.ts:60-77`; `packages/wallet-core/src/utils/arrays.ts:23-39`.

   - `packages/wallet-core/src/utils/serialization.ts:6-7` docstring justifies the naked-`Buffer` hack with "wallet-core's tsconfig ships with `"types": []`"; `packages/wallet-core/tsconfig.json:11` actually has `"types": ["node"]` — the documented premise of a deliberately tricky workaround is false, so the next maintainer cannot evaluate whether the hack is still needed.
   - `packages/wallet-core/README.md:17-28` file map omits `src/jobs/` entirely — the package's only repeat-change surface (FSM, JobError, types).
5. **Why it harms future change**: these are exactly the docs the repo's own conventions designate as the entry point ("read `packages/<name>/README.md` once before you start"); wrong crypto parameters and phantom APIs send maintainers and auditors down false paths, and the serialization docstring drift may cause someone to preserve (or break) the Buffer workaround for the wrong reason.
6. **Smallest safe refactoring**: not a code refactoring — Correct the Comment/doc (the remedy Fowler prescribes for the Comments smell): fix the iteration count, delete the phantom method row, re-verify and rewrite the serialization premise against the current tsconfig, add `src/jobs/` to the file map.
7. **What disappears**: four false statements in first-read documents; the crypto README becomes safe to cite in an audit.
8. **Instances**: `packages/wallet-crypto/README.md:17,19`; `packages/wallet-core/src/utils/serialization.ts:6-7` vs `packages/wallet-core/tsconfig.json:11`; `packages/wallet-core/README.md:17-28`.

## Non-findings

- **`Lock` (wallet-core) vs the extension's execution-mutex** — divergence (timeout/force-release) is documented as deliberate in both places; no measurable duplication cost.
- **`lastActiveProfile.ts` vs `core.ts` sentinel helpers** — the "duplicated" pattern is a 4-line one-key `chrome.storage.local` get/set; extracting a generic helper would add indirection for zero saved maintenance.
- **`mnemonic.ts` 2,160-line outlier** — 95% is the frozen BIP-39 English wordlist (spec-locked, change frequency zero); the codec has one consumer (`profile/service.ts`). Splitting the wordlist into a data module is cosmetic; the substantive issue (hand-rolled crypto-adjacent codec) is a security concern, noted out-of-scope below.
- **`sanitizeString` (string.ts) vs `sanitizeJournalSubtitle` (journal-state.ts)** — same word, different transformations (charset strip vs URL-scheme bracketing) with different threat rationales; no shared logic to extract.
- **`journal-state.ts` / `card-subtitle.ts` / `activity-rows.ts` trio** — each is a cohesive pure module with exhaustiveness test pins and explicit cross-references; the prior duplication these files *removed* is documented in their headers. Not a smell; an example of the fix.
- **`entity_storage.ts` parseOrDelete vs getVersion log+delete duplication** — real, but it disappears entirely under F4's deletion of the dead `getVersion`; not counted separately.
- **`tx-enrichment.ts:4-6` re-export of `FEE_METHODS`/`pickPrimaryMethod`** — two import paths for the same symbols (wallet side imports `@/utils/primary-method`, UI auto-imports resolve to `tx-enrichment`) is mild Middle Man, but the split itself is a documented layering fix (wallet services must not depend on popup-util modules) and the shim is one line with a stated rationale; inline-and-delete is a nice-to-have below this report's bar.
- **Four vitest e2e configs sharing pool/forks/retry settings** — the smoke and network configs document genuinely different rationales for the same values; merging would couple knobs that have already needed to diverge (`testTimeout`, `globalSetup`, aztec aliasing). The `"@"` alias duplication is counted once under F2.
- **`VITE_*` env vars read in 5 scattered files** — read-at-use-site is idiomatic Vite; propagation is actively asserted post-build by `scripts/e2e/agent.sh` greps. The assertion is a symptom worth knowing about, not a smell to fix by centralizing reads.
- **Manifest ×3 (base + chrome 8-line + firefox 29-line)** — thin per-browser deltas over one base; the right shape.
- **`utils/index.ts` re-exporting only `files` + `string` while auto-import covers the whole dir** — inconsistent but consequence-free (all consumers resolve via auto-import); flagging would be naming preference.
- **Mixed `"@/utils/amount.js"` vs `"@/utils/amount"` import specifiers (10 vs 5 files)** — cosmetic; Biome tolerates both and resolution is identical.
- **`console-sniffer.ts` writing `console._<method>` aliases** — undeclared console augmentation, but typed via `src/types/console.d.ts` and consumed by the logger's print path; the duplication aspect is counted in F1.

## Out-of-scope observations

- Hand-rolled BIP-39 encode/decode + SHA-256 checksum in `packages/wallet-core/src/utils/mnemonic.ts` instead of a battle-tested library (e.g. `@scure/bip39`) — conflicts with the repo's own "battle-tested crypto only" policy; security review concern, not quality.
- `refreshBalances(_minutes, ...)` in `packages/extension/src/utils/core.ts:109-127` ignores its `_minutes` parameter and hardcodes `30` at the call into `checkAge` — misleading signature / possible behavior bug.
- `comma()` returns number `0` for falsy input but string otherwise (`packages/extension/src/utils/amount.ts:12`) — union-return footgun; behavior concern.
- `SelectBalanceTypePopup.vue:131,153` formats what appears to be a raw token balance with float-based `comma()` — potential precision/display correctness issue.
- `typeIntoInput` (placeholder-based) and `clickButtonByText` (text-based) in `tests/e2e/fixtures/extension.ts:1101,1108` violate the repo's strict "e2e selects only by data-testid" rule — test-correctness/convention enforcement, not a smell.
- `normalizeAmount` (`amount.ts:46-60`) falls through to `undefined` on its happy path — surprising contract; behavior concern.
