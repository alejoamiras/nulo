## F1: Adding one wallet method requires synchronized edits to seven string-keyed surfaces in five files

1. **Title:** Adding one wallet method requires synchronized edits to seven string-keyed surfaces in five files.
2. **Smell name:** Shotgun Surgery (Fowler), compounded by Duplicate Code in the form of three parallel method tables that must agree by convention only. The per-method facts (required capability, exemption, operation kind, network-vs-account context, arg unpacking, scope checker) are scattered across independent `Record<string, …>` tables and switches instead of one descriptor.
3. **Maintenance impact:** architectural. Blast radius: 5 files inside wallet-bridge (`capability-map.ts`, `dispatcher.ts` ×4 sites, `scope-enforcement.ts` ×2 sites, `operation.ts`, `dapp-interaction-protocol.ts`) plus the extension's execution-service sink per method. Change frequency: dispatcher.ts 8 commits / scope-enforcement.ts 4 / capability-map.ts 3 / operation.ts 3 / dapp-interaction-protocol.ts 3 in the last 6 months — and the co-change is empirical: commit `f3eb249` (registerToken RPC) touched exactly `capability-map.ts + dapp-interaction-protocol.ts + dispatcher.ts + operation.ts + scope-enforcement.ts`; commit `336ea6f` (F-001..F-012 fixes) touched `capability-map.ts + dispatcher.ts + scope-enforcement.ts`.
4. **Concrete evidence:** the same method-name string keys appear in: `EXEMPT_METHODS` + `METHOD_CAPABILITY_MAP` (`packages/wallet-bridge/src/capability-map.ts:18,21-46`); `METHOD_TO_KIND` (`dispatcher.ts:163-178`); `NETWORK_ONLY_KINDS` / `ACCOUNT_KINDS` (`dispatcher.ts:184-192,198`); the `buildNetworkOperation` switch (`dispatcher.ts:867-902`, 7 cases); the `buildAccountOperation` switch (`dispatcher.ts:916-956`, 4 cases); `METHOD_SCOPE_CHECKER` (`scope-enforcement.ts:348-362`). The sync is enforced by comment only — `scope-enforcement.ts:9-10` literally says "must be kept in sync with buildNetworkOperation / buildAccountOperation in dispatcher.ts". All tables are `Record<string, …>` / `Set<…>`: nothing type-checks that a key present in `METHOD_TO_KIND` is also present in `METHOD_CAPABILITY_MAP` — a missing entry there makes `getRequiredCapability` return `null` and `enforceCapability` silently returns `[]` ("Unknown method — let dispatch() handle it", `dispatcher.ts:782`), i.e. the omission failure mode is silent, not a compile error. `createAuthWit` alone appears at 7 distinct definition sites across 4 files.
5. **Why it harms future change:** every new wallet-sdk method (the package gained `registerToken` this cycle, and the README contract anticipates more Nulo-custom RPCs) is a 5-file scavenger hunt where forgetting any one table degrades enforcement or routing silently. Reviewers must re-derive the full table set from memory on every method PR; the F-003 incident (a method sitting in `EXEMPT_METHODS` while its sub-grant checker was "decorative") is precisely the class of drift this shape invites.
6. **Smallest safe refactoring:** table-driven method registry (Code Complete's "table-driven methods"; Fowler family: Consolidate Conditional Expression + Move Statements to Callers' inverse). One `const METHODS: Record<MethodName, { capability: CapabilityType | "exempt"; context: "network" | "account" | "special"; kind?: Operation["kind"]; build?: (args, networkId, account?) => Operation; scopeCheck?: Checker }>` keyed by a `MethodName` string-literal union. `getRequiredCapability`, `isCapabilityExempt`, `METHOD_TO_KIND`, both `Set`s, both build switches, and `METHOD_SCOPE_CHECKER` become lookups into it.
7. **What disappears:** seven sync-by-convention surfaces collapse into one; missing-entry failure mode flips from silent runtime exemption to compile error (exhaustive keys); adding a method becomes one registry entry + one `Operation` variant.
8. **Instances:** `packages/wallet-bridge/src/capability-map.ts:18`, `packages/wallet-bridge/src/capability-map.ts:21-46`, `packages/wallet-bridge/src/dispatcher.ts:163-178`, `packages/wallet-bridge/src/dispatcher.ts:184-192`, `packages/wallet-bridge/src/dispatcher.ts:198`, `packages/wallet-bridge/src/dispatcher.ts:867-902`, `packages/wallet-bridge/src/dispatcher.ts:916-956`, `packages/wallet-bridge/src/scope-enforcement.ts:348-362`, `packages/wallet-bridge/src/scope-enforcement.ts:9-10` (sync comment).

## F2: caip helpers forked line-for-line across packages, with both copies claiming to be the source of truth

1. **Title:** `caip.ts` is duplicated line-for-line between wallet-bridge and the extension, and the two headers each point at the other as authoritative.
2. **Smell name:** Duplicate Code (Fowler), cross-package variant; the contradictory headers are sync-by-comment (config-sprawl analog: the same wire-format parsing knowledge maintained in two files that must agree).
3. **Maintenance impact:** structural, cross-package. Blast radius: 2 definition files + 9 extension consumer files of the extension copy + dispatcher/scope-enforcement consumers of the bridge copy. Change frequency: 1 commit each in 6 months (both landed in the open-source import) — dormant today, but the duplicated logic is wire-format validation, where divergence means two different parsers for the same CAIP strings on the two sides of the protocol boundary.
4. **Concrete evidence:** `formatCaipChain` (`packages/wallet-bridge/src/caip.ts:24-26` ≡ `packages/extension/src/wallet/utils/caip.ts:22-24`), `formatCaipAccount` (bridge `:29-31` ≡ extension `:27-29`), `parseCaipAccount` including all four error branches (bridge `:34-51` ≡ extension `:49-66`), `NetworksQuery` interface (bridge `:54-56` ≡ extension `:71-73`), `resolveNetworkByChainId` (bridge `:64-70` ≡ extension `:81-87`). The extension header (`utils/caip.ts:2-9`) declares itself "the single source of truth for parsing and formatting CAIP identifiers anywhere on the extension side (dispatcher, …)" — but the dispatcher actually imports the bridge copy (`dispatcher.ts:54`). The bridge header (`caip.ts:5-9`) declares the extension file "remains the source of truth… this file mirrors only the subset the bridge requires." Each file's "do not fork" warning is itself sitting in a fork. Notably the *types* are already unified — extension `utils/caip.ts:16` imports `CaipAccount`/`CaipChain` (transitively) from wallet-bridge — only the function bodies are duplicated.
5. **Why it harms future change:** any fix to CAIP validation (e.g. tightening address-segment checks, supporting a second namespace) must be applied twice, and the lying headers actively route a maintainer to the wrong file: someone following `utils/caip.ts`'s "single source of truth" claim will patch it and believe the dispatcher is covered when it is not. That is silent validation drift across a trust boundary's two halves.
6. **Smallest safe refactoring:** Move Function direction is already legal — extension may import wallet-bridge (top of the layer order). Replace the four duplicated bodies in `packages/extension/src/wallet/utils/caip.ts` with `export { formatCaipChain, formatCaipAccount, parseCaipAccount, resolveNetworkByChainId } from "@nulo/wallet-bridge"`, and either move `parseCaipChain` + `AZTEC_NAMESPACE` down into the bridge copy or keep them extension-local. Rewrite both headers to state the now-true ownership.
7. **What disappears:** one of two parsers of the same wire format; the contradictory source-of-truth headers; the standing risk that a CAIP validation fix lands on only one side of the dApp↔wallet boundary.
8. **Instances:** `packages/wallet-bridge/src/caip.ts:24-70` and `packages/extension/src/wallet/utils/caip.ts:22-29,49-66,71-87`; headers `packages/wallet-bridge/src/caip.ts:5-9` and `packages/extension/src/wallet/utils/caip.ts:2-9`.

## F3: scope-enforcement checker family — one byte-identical pair, one triplicated skeleton, one duplicated pair, and a 10× repeated invariant

1. **Title:** The 12 per-method scope checkers are hand-copied variations of three skeletons.
2. **Smell name:** Duplicate Code (Fowler); fix is Parameterize Function (Fowler).
3. **Maintenance impact:** structural, within one module (`scope-enforcement.ts`, 421 lines). Blast radius: 1 source file + its 531-line test file. Change frequency: 4 commits in 6 months; the F-003/F-004 additions (commit `336ea6f`) grew the family by copying the skeleton again, demonstrating the duplication actively reproduces.
4. **Concrete evidence:** (a) `checkGetAddressBook` (`scope-enforcement.ts:300-306`) and `checkRegisterSender` (`:313-319`) have byte-identical bodies — same `grantsOfType<DataCapability>(grants, "data")`, same `caps.some((c) => c.addressBook === true)` — differing only in the error string. (b) `checkRegisterContract` (`:53-64`), `checkGetContractMetadata` (`:66-76`), `checkGetContractClassMetadata` (`:78-88`) share an identical 4-step skeleton (extract arg → `grantsOfType` → empty-pass-through → `caps.some(flag && inAddressList)` → throw), varying only in cap type, flag name, list field, and label. (c) `checkTransactionCalls` (`:90-107`) and `checkSimulationTransactions` (`:109-130`) are the same calls-array checker differing only in cap type and scope selector (`c.scope` vs `c.transactions?.scope`) and label. (d) The empty-grants pass-through convention `const caps = grantsOfType<…>(…); if (!caps.length) return` is repeated 10× (`:58`, `:70`, `:83`, `:99`, `:118`, `:141`, `:158`, `:288`, `:302`, `:315`) with no shared helper expressing the semantic ("no grant of this type → defer to type-level enforcement").
5. **Why it harms future change:** every new sub-grant checker is written by copying the nearest sibling (F-004's pair is the proof), so the file grows linearly in near-clones; a change to the shared convention — e.g. deciding empty-grants should fail closed instead of pass through, or standardizing the error format dApps parse — is a 10-site edit where missing one site silently changes enforcement semantics for that one method.
6. **Smallest safe refactoring:** Parameterize Function: `makeFlagChecker(capType, flag, methodLabel)` collapses (a) and `checkGetAccounts`; `makeAddressChecker(capType, flag, listField, label)` collapses (b); `makeCallsChecker(capType, scopeSelector, label)` collapses (c). Error messages stay verbatim (they are a public contract pinned by ~70 tests), passed as parameters.
7. **What disappears:** roughly 80 lines of clone bodies; the empty-grants invariant gets exactly one expression site; new checkers become one-line factory calls instead of copied functions.
8. **Instances:** `packages/wallet-bridge/src/scope-enforcement.ts:53-64`, `:66-76`, `:78-88`, `:90-107`, `:109-130`, `:286-292`, `:300-306`, `:313-319`; pass-through convention at `:58,70,83,99,118,141,158,288,302,315`.

## F4: handleRequestCapabilities is a 170-line method with its rejection-merge logic duplicated across the catch and grant paths

1. **Title:** `handleRequestCapabilities` bundles delta computation, popup orchestration, grant merging, and two copies of rejection persistence into one method.
2. **Smell name:** Long Method (Fowler) + Duplicate Code (the rejection-merge block exists twice).
3. **Maintenance impact:** structural (it is the session-mutation heart of the dispatcher). Blast radius: 1 file, but it is the single most-modified region of the hottest file in the package (dispatcher.ts: 8 commits / 6 months; the Phase-1.5 field-aware accounts diff and the reject-persistence arc both reworked this method).
4. **Concrete evidence:** `dispatcher.ts:531-701` — 170 lines covering: empty-manifest early return (542-548), grant/rejection snapshot (551-554), shape-aware delta computation (564-573), early-return enrichment (576-588), popup-input assembly including an inline network+accounts load (591-606), popup call with catch-path rejection persistence (608-631), safety-net grant patching (634-643), account merge + alias write (646-662), grant merge persistence (665-675), grant-path rejection persistence (678-684), session reload + enrichment (687-700). The rejection-merge is duplicated: catch path `:622-630` (`rejectedAt = Date.now()` → `newRejections = delta.map(…)` → `deltaTypes = new Set(delta.map(…))` → `mergedRejections = [...existingRejections.filter((r) => !deltaTypes.has(r.capabilityType)), ...newRejections]` → `setCapabilityRejections`) vs grant path `:678-684` (identical skeleton, filtered by `!approvedTypes.has(…)`). The `deltaTypes` set is built twice from the same `delta` (`:627`, `:682`).
5. **Why it harms future change:** the two rejection-persistence copies must stay semantically aligned (one is "user closed popup → reject all delta", the other "popup returned → reject non-approved delta"); a future change to the rejection record shape or merge rule edits both or silently forks the persisted shape depending on how the popup exits. The method's 11 sequential responsibilities also make every capability-flow PR diff against the same 170 lines, maximizing merge friction in the file's most-churned region.
6. **Smallest safe refactoring:** Extract Function ×4: `computeCapabilityDelta(requested, existingGrants, existingRejections)`, `persistRejections(sessionId, delta, existingRejections, approvedTypes)` (catch path passes an empty `approvedTypes`), `loadAvailableAccounts(ctx)` (also de-duplicates the resolve+getAccounts pair — see F5), `mergeAndPersistGrants(…)`.
7. **What disappears:** the duplicated rejection-merge block (single function, two call sites); the double-built `deltaTypes`; the 170-line scroll becomes four named phases matching the docblock's own "3-phase" description.
8. **Instances:** `packages/wallet-bridge/src/dispatcher.ts:531-701`; duplication pair `:622-630` vs `:678-684`.

## F6: DispatchHooks and IExecutionHooks are twin hook bags maintained by hand, re-packed field-by-field — the exact shape that already caused a field-name-drift bug once

1. **Title:** Two near-identical hooks interfaces plus a manual field-by-field repack.
2. **Smell name:** Alternative Classes with Different Interfaces (Fowler) — two types model the same hooks bag at adjacent pipeline stages — with the repack site adding a small Shotgun Surgery cost per new hook field.
3. **Maintenance impact:** structural. Blast radius: 4 files (`dispatcher.ts`, `services-contract.ts`, extension `dapp-interaction/spec.ts` alias, `wallet-sdk/background.ts` producer). Change frequency: services-contract.ts 4 commits / 6 months; the hooks surface was reshaped twice during the durable-jobs and FIFO-baton arcs.
4. **Concrete evidence:** `DispatchHooks` (`dispatcher.ts:90-107`) = `{ onExecutionEnqueued?, queuedJournalId? }`; `IExecutionHooks` (`services-contract.ts:56-60`) = the same two fields + `originKey?`. They are not type-related — the dispatcher converts one to the other by hand at `dispatcher.ts:458`: `{ onExecutionEnqueued: hooks?.onExecutionEnqueued, queuedJournalId: hooks?.queuedJournalId, originKey: ctx.origin }`. The repo's own comments document that this exact shape already failed once: `background.ts:287-292` — "a past field-name drift here is exactly what left this release dead before". The extension side mitigated its half with an alias (`dapp-interaction/spec.ts:62` `export type ExecutionHooks = IExecutionHooks`, justified as "a one-sided rename on either side is a build error"), but the `DispatchHooks` ↔ `IExecutionHooks` pair got no such link.
5. **Why it harms future change:** adding a hook field (the journal/backpressure arcs added one each) requires editing both interfaces *and* remembering the field-by-field repack at `:458`; forgetting the repack compiles clean and silently drops the hook downstream — the precise bug class the codebase already shipped once and now wards off with comments instead of types.
6. **Smallest safe refactoring:** Extract Superclass / derive: `export type DispatchHooks = Omit<IExecutionHooks, "originKey">` (originKey is dispatcher-owned, which the Omit makes self-documenting), and repack via spread: `{ ...hooks, originKey: ctx.origin }`.
7. **What disappears:** the second hand-maintained field list; the silent-drop failure mode on new hook fields (a field added to `IExecutionHooks` flows through the spread automatically; one intentionally withheld must be added to the `Omit`, which is a visible decision).
8. **Instances:** `packages/wallet-bridge/src/dispatcher.ts:90-107`, `packages/wallet-bridge/src/dispatcher.ts:458`, `packages/wallet-bridge/src/services-contract.ts:56-60`; context: `packages/extension/src/wallet/services/dapp-interaction/spec.ts:62`, `packages/extension/src/wallet/services/wallet-sdk/background.ts:287-292`.

## F7: The capability discriminator set is declared three times — once as a union, once as a hand-copied literal union, once as an unkeyed Record — synced by comment

2. **Smell name:** Primitive Obsession (stringly-typed keys where a derivable union exists) + config sprawl analog (the same six-discriminator set maintained at three sites, one of which carries an explicit "keep in sync" comment).
3. **Maintenance impact:** structural. 7. **What disappears:** two hand-maintained copies of the discriminator set; the sync comment; the silent "new capability ships with Unknown-permission UI" failure mode becomes a compile error.
8. **Instances:** `packages/wallet-bridge/src/capabilities.ts:53-59`, `packages/wallet-bridge/src/capability-map.ts:11`, `packages/extension/src/wallet/services/dapp-session/capability-meta.ts:31-34`.

## F9: The same bridge types are importable through 3-5 alias paths, and consumers have already split between them

1. **Title:** Re-export shim sprawl — bridge types reach extension code through divergent import paths, and the shims grow with every new bridge type.
2. **Smell name:** Middle Man (Fowler) at module level / "divergent import paths" (community analog of Shotgun Surgery for renames: changing or relocating one type touches every alias hop), plus change amplification: each new wallet-bridge type the extension needs requires a matching edit to a shim's hand-maintained export list.
3. **Maintenance impact:** structural. Blast radius: 4 shim/alias files + ~10 consumer files currently split across paths. Change frequency: `execution/models/index.ts` and the spec shims were each touched in the recent type-migration commits; every bridge type addition lands another line in one of them.
4. **Concrete evidence:** `AccessLevel` is importable (and imported) via at least four paths: origin `@nulo/wallet-bridge`, shim `@/wallet/services/dapp-session/spec` (`spec.ts:11`), star-re-exports `dapp-session/client.ts:17` and `dapp-session/service.ts:20` (used by `confirmation-policies.ts:1` and `wallet-sdk/background.ts:42` respectively), and a fourth-hand re-export at `utils/confirmation-policies.ts:3`. `Capability` consumers are already split: 4 UI files import it straight from `@nulo/wallet-bridge` (`popup/windows/capabilities/index.vue:21`, `CapabilityCard.vue:23`, `build-items.ts:11`, `components/composite/capabilities/CapabilityDetailPanel.vue:10`) while the service layer goes through the dapp-session shim chain — so the shim's stated purpose ("backward compatibility with existing consumers", `spec.ts:5-10`) no longer describes a converging state. `CaipChain`/`CaipAccount` travel a 3-hop chain: `wallet-bridge/caip.ts` → `wallet-bridge/index.ts` → `dapp-interaction/spec.ts:24-25` → `utils/caip.ts:16` — a utility importing its own domain types from an unrelated service's spec. `execution/models/index.ts:4-62` is five consecutive hand-maintained `export type {…} from "@nulo/wallet-bridge"` blocks (~38 names) serving one non-test importer (`auth-registry/client.ts`).
5. **Why it harms future change:** renaming or relocating a bridge type means chasing 3-5 alias paths; "find all references" fragments across aliases; new contributors must learn which of the four `AccessLevel` paths is house style (there currently isn't one — the codebase itself disagrees); and the hand-maintained export lists are pure ongoing tax (every bridge addition = one more shim line) bought for a backward-compat window that direct-importing consumers show is already over.

7. **What disappears:** 2-4 alias hops per type; ~75 lines of hand-maintained re-export lists; the per-bridge-addition shim edit; the ambiguity about the canonical import path.

## F10: Dead defensive branches in the dispatcher and a never-used "test fixture" interface

1. **Title:** Four no-session guards of which two are unreachable, a dead `enforceScope` else-branch, and the unused `IDispatcherServices` export.
2. **Smell name:** Dead Code + Speculative Generality (Fowler). The duplicated guard text across four handlers is also a small Duplicate Code instance.
3. **Maintenance impact:** local. Blast radius: 2 files (`dispatcher.ts`, `services-contract.ts`). Change frequency: dispatcher 8 commits / 6 months — dead branches in a hot file get re-read (and re-reasoned-about) on every change.
4. **Concrete evidence:** (a) `dispatcher.ts:419-421` — `handleSendTx`'s `if (!dappSession) throw "No dApp session found…"` is unreachable two ways: `resolveNetworkAndAccount(ctx, dappSession)` at `:411` always throws first when `dappSession` is undefined (`:995-1005` — the optional-chain skips the only return path), and `dispatch()` already threw `CapabilityNotGrantedError` in `enforceCapability` (`:784-803`) because sendTx requires the `transaction` capability. (b) `dispatcher.ts:312-314` (`handleGetAccounts`) and `:485-487` (`handleRegisterToken`) — same guards, unreachable through their only caller (`dispatch()`) since F-006 made `enforceCapability` fail-closed on missing sessions for all capability-mapped methods; the package's own tests pin that the thrown error is `CapabilityNotGrantedError` from the earlier check, not these guards (`dispatcher.test.ts:341`, `:965`). Only `handleRequestCapabilities`' copy (`:537-539`) is reachable (the method is exempt). (c) `dispatch():244-249` — the `else { enforceScope(...) }` branch is dead by the inline comment's own admission ("shouldn't happen when grants.length>0 since enforceCapability would have returned []"); post-F-006 it is stronger than "shouldn't": `grants.length > 0` implies a session was found. (d) `IDispatcherServices` (`services-contract.ts:94-104`) has zero inbound references anywhere in the repo — including the dispatcher tests it was "exported for"; its own doc admits the constructor doesn't accept it. No DI/reflective registration applies to wallet-bridge (plain library package; the extension auto-import carve-out covers `extension/src/*` only).
5. **Why it harms future change:** each unreachable guard advertises an error contract ("No dApp session found for origin …") that can never fire on three of four paths, so maintainers and dApp authors reading the code infer wrong observable behavior; defense-in-depth intent is currently encoded as four divergent copy-paste guards rather than one auditable site, so tightening or instrumenting the no-session policy means re-discovering which copies are live.
6. **Smallest safe refactoring:** Extract Function `requireSession(dappSession, ctx): IDappSessionRef` used by all four handlers — this preserves the fail-closed redundancy (legitimate in a security layer) while collapsing the duplication and making the one reachable site share the dead sites' contract; delete the dead `else` at `:247-249` (or fold into `enforceScopeWithSession(…, new Set())` which the F-005 docblock already says fails closed on an empty set); Remove Dead Code for `IDispatcherServices`.
7. **What disappears:** two-to-three unreachable branches with misleading diagnostics; the 4× guard duplication; one zero-consumer export and its stale rationale comment.
8. **Instances:** `packages/wallet-bridge/src/dispatcher.ts:244-249`, `:312-314`, `:419-421`, `:485-487` (guard family incl. the reachable `:537-539`); `packages/wallet-bridge/src/services-contract.ts:94-104`.
