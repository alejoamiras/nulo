## F1: Startup ordering enforced by 81 hand-copied polling guards instead of the existing declarative dependency mechanism

1. **Title**: Startup ordering enforced by 81 hand-copied polling guards instead of the existing declarative dependency mechanism.
2. **Smell name**: **Temporal coupling** (named analog — operations must happen in a specific order with no structural enforcement; canon: Hevery/"Guide: Writing Testable Code", also catalogued by Ousterhout as "obscure dependency") combined with Fowler's **Temporary Field** (the `= null!` service refs are invalid until `init()` runs) and **Duplicate Code** (the `await this.ensureInitialized()` preamble). The mapping: every public method on every service must remember to open with `ensureInitialized()` because the base class dispatches RPC messages directly into methods (`packages/extension-messaging/src/background/service.ts:62-102` has no init guard) while collaborator fields are `null!` until `init()` fires — yet a declarative ordering mechanism (`IService.dependencies` + `topologicalPhases`, `packages/wallet-core/src/base/index.ts:21-70`) already exists and is used by exactly one in-scope service.
3. **Maintenance impact**: **architectural**. Blast radius: all 10 in-scope service files (and the other 11 in the fleet) + the base class. Change frequency: every newly added RPC method must re-instantiate the preamble — this is the highest-recurrence pattern in the cluster; omissions are invisible until a cold-start race.
4. **Concrete evidence**:
   - Preamble counts (`grep -c "await this.ensureInitialized()"`): network 17, profile 24, fpc 9, contact 8, token 7, account 7, auth-registry 4, dapp-session 3, transaction 2, config 0 — **81 sites** in scope.
   - Temporary fields (`grep -c "= null!"`): token 6, auth-registry 6, transaction 4, fpc 3, network 2, profile 2, contact/account/dapp-session 1 each — **26 fields** in scope.
   - Declarative mechanism used once in scope: `contact/service.ts:19` (`public readonly dependencies = [ProfileService.name] as const`); fleet-wide only contact + incoming-transfer declare. Everyone else lands in phase 0 (`packages/wallet-core/src/base/index.ts:65-70`) and falls back to the base-class 500 ms-poll/30 s-timeout (`packages/extension-messaging/src/background/service.ts:187-199`).
   - The application is inconsistent, proving the rule is unenforced: `transaction/service.ts:109` (`addTransaction`, which dereferences the `null!`-initialized `this.networkService` at :131) has no guard; `auth-registry/service.ts:73` (`trackAuthwit`), `dapp-session/service.ts:53` (`getDappSession`), `account/service.ts:138` (`changeAccountName`) likewise; their siblings in the same files do have it.
5. **Why it harms future change**: a contributor adding a method has to know an unwritten rule; forgetting it produces either a null-deref or a silent 30-second stall depending on timing — bugs that only reproduce on cold SW start. The 81 copies also bury the two methods where the guard is doing real work. Migrating a service to declared `dependencies` (the intended end state per the base-class TSDoc) requires auditing every preamble to know which are load-bearing.
6. **Smallest safe refactoring**: **Introduce guard in the template method** (Fowler: *Move Statements to Callers* inverted / *Pull Up Method*): add one `await this.ensureInitialized()` to the base `onMessage` before `this.requests[method](...)`, making every RPC entry safe by construction; then **declare `dependencies`** per service for the cross-service direct-call edges (mechanism already shipped and tested — `packages/wallet-core/src/base/topology.ts`), following the ContactService pattern.
7. **What disappears**: 81 preamble lines, the "did I remember the guard" review burden on every new method, and the cold-start timing bug class; the `null!` fields become initialization-order-safe rather than convention-safe.
8. **Instances**: packages/extension/src/wallet/services/network/service.ts (17 preambles, e.g. :169,:204,:214), profile/service.ts (24, e.g. :88,:100,:105), fpc/service.ts (9), contact/service.ts (8), token/service.ts (7), account/service.ts (7), auth-registry/service.ts (4), dapp-session/service.ts (3), transaction/service.ts (2); missing-guard counterexamples transaction/service.ts:109, auth-registry/service.ts:73,89,145, dapp-session/service.ts:53,142,274, account/service.ts:138,151; base dispatch packages/extension-messaging/src/background/service.ts:62-102; mechanism packages/wallet-core/src/base/index.ts:21-31,65-70; sole adopter contact/service.ts:19.

## F2: Services hard-wire their infrastructure collaborators (chrome.storage + PxeServiceClient), stranding the half-finished ports migration

1. **Title**: Services hard-wire their infrastructure collaborators (chrome.storage + PxeServiceClient), stranding the half-finished ports migration.
2. **Smell name**: **Shotgun Surgery** (Fowler) — changing how storage or the PXE client is provisioned touches 8+ files — plus **Divergent Change** within the fleet: two provisioning idioms (constructor-injected `BrowserApi` with fallback ternary vs. hard-coded `chrome.storage.local` / `new PxeServiceClient(...)`) coexist for the same concern, so each new service must pick one and each migrated service changes for a different reason than its neighbors. The duplicated fallback ternary itself is **Duplicate Code**.
3. **Maintenance impact**: **architectural**. Blast radius: 8 in-scope service files + runtime.ts + (fleet-wide) 4 more PxeServiceClient constructors. Change frequency: low per-file, but it is the direct blocker on testing the fleet — the map records zero tests for exactly the non-migrated services (auth-registry, fpc, token, transaction, dapp-session, config, account), while the two migrated ones (profile, contact) have the largest test suites in the layer.
4. **Concrete evidence**:
   - Hard-coded `chrome.storage.local` in `EntityStorage` construction: token/service.ts:42, transaction/service.ts:36, network/service.ts:143, fpc/service.ts:43, auth-registry/service.ts:29-30, account/service.ts:23, dapp-session/service.ts:29. Raw `chrome.storage.local.get/set/remove` for the active-network pointer: network/service.ts:687,752,758.
   - The browserApi-fallback ternary duplicated verbatim: contact/service.ts:37-40, profile/repository.ts:43-46 (ValueStorage variant in profile/session-manager.ts per map).
   - `new PxeServiceClient(this.logger)` inside `init()`: token/service.ts:57, transaction/service.ts:52, network/service.ts:163, fpc/service.ts:60 (in scope); account-state:36, execution:342, note:46, token-balance:67 (fleet). Not injectable anywhere; `NetworkService` accepts an optional `nodeFactory` (service.ts:153-157) yet hard-codes the PXE client three lines into `init()` — the same file uses both idioms.
   - runtime.ts:104-131 documents the split: "Services migrated to ports accept `browserApi`; remaining services still reach into `chrome.*` directly until their migration lands" — only Contact, OperationJournal, Profile receive the port.
5. **Why it harms future change**: any test for the 8 non-migrated services requires a global `chrome.*` stub instead of `FakeBrowserApi`, which is empirically where testing stopped; a future storage-area change (e.g. moving a key to `session`, adding quota handling, the Firefox port) means editing 8 constructors plus 3 raw call sites instead of one composition-root line; and every new service copies whichever idiom its author saw last, widening the divergence.
6. **Smallest safe refactoring**: **Introduce Parameter** (Fowler) per remaining constructor — thread `browserApi` exactly as ContactService does (optional, chrome fallback), updating runtime.ts call sites; extract the repeated ternary into a tiny factory (`Extract Function`, e.g. `entityStorage(key, browserApi?)`) so the fallback policy lives once. For the PXE client, **Replace Constructor with Factory/Injected Collaborator**: construct one `PxeServiceClient` in runtime.ts and pass it (or register it in the ServiceCollection) instead of 8 private `new` calls.
7. **What disappears**: the two-idiom split (one provisioning pattern fleet-wide), 8 hard-coded storage bindings + 3 raw chrome calls, the duplicated ternary, 8 redundant PXE client instances, and the structural excuse for the zero-test services.
8. **Instances**: as itemized in field 4; composition root packages/extension/src/wallet/runtime.ts:104-131; donor pattern contact/service.ts:35-40 and profile/repository.ts:42-46.

Mechanical sed-level migration; message text preserved for compatibility.
7. **What disappears**: ~110 lines of guard boilerplate, the 4-way string drift, and the impossibility of one-place changes to locked-wallet behavior; the ownership-check twin can ride the same helper (`requireOwned(entity, profile)`).
8. **Instances**: all file:line locations in field 4.

## F4: The backup()/restore() accumulate-Restored loop is re-implemented in 8 services and has already drifted

1. **Title**: backup()/restore() accumulate-Restored loop re-implemented ×8 with drifted error shaping.
2. **Smell name**: **Duplicate Code** (Fowler); the fix is *Form Template Method* — each service re-writes the identical "iterate items, try persist, push success or `{...item, restoreError}`" skeleton differing only in the per-item persist step.
3. **Maintenance impact**: **structural**. Blast radius: 8 service files (~190 lines of near-identical loop). Change frequency: low (backup format is stable), but the full-backup flow is user-facing and safety-critical, and the copies have measurably diverged already.
4. **Concrete evidence**:
   - The loop: token/service.ts:532-558, transaction/service.ts:302-324, contact/service.ts:290-319, config/service.ts:43-59, network/service.ts:614-657, fpc/service.ts:470-520, auth-registry/service.ts:285-311, account/service.ts:213-234.
   - Drift inside the "identical" copies: 7 of 8 shape the error as `err instanceof Error ? err.message : err`; **contact/service.ts:310 pushes the raw `err` object** — a raw `Error` does not survive `jsonSanitize` the way a string does, so contact's restore-failure rows render differently from every other service's. fpc adds an inline legacy-type rejection (:482-488); account throws wholesale on any address intersection instead of per-row errors (:218-219); network validates per-row with zod. The variation that matters (per-item persist + validation) is ~5 lines; the copied scaffold is ~20.
   - Twin backup() implementations: transaction/service.ts:279-300 and auth-registry/service.ts:262-283 are line-for-line the same double loop (guard → getNetworks → return undefined if empty → for networks → for accounts → collect by account).
5. **Why it harms future change**: a change to restore semantics (e.g. structured `restoreError` codes, partial-failure reporting, progress events for big backups) is an 8-file edit where one file (contact) is already on a different contract; reviewers cannot tell intended variation (fpc's legacy rejection) from rot (contact's raw err).
6. **Smallest safe refactoring**: **Form Template Method / Extract Function** — a shared `restoreEach<T>(items, persistOne: (item: T) => Promise<T>): Promise<Restored<T>[]>` helper (wallet-core utils or a protected method on the base `Service`); each service supplies only its persist/validate lambda. The transaction/auth-registry backup twin: **Extract Function** `collectPerAccount(profiles, networks, accounts, getter)`.
7. **What disappears**: ~150 lines of scaffold, the contact error-shape divergence (fixed by construction), and the two-file backup twin; future restore-contract changes become one edit.
8. **Instances**: all file:line locations in field 4.

## F5: 67 hand-rolled lock enter/leave ceremonies with three divergent acquisition idioms

1. **Title**: 67 hand-rolled lock enter/leave ceremonies with three divergent acquisition idioms.
2. **Smell name**: **Duplicate Code** (Fowler) + **Alternative Classes with Different Interfaces** (analog at the idiom level — three mutual-exclusion idioms coexist for one concern: the fleet's `try { await lock.enter() } finally { lock.leave() }`, token's `holdsLock` boolean variant, and account's hand-rolled promise-chain serializer). Account's serializer additionally contains **Dead Code**.
3. **Maintenance impact**: **structural**. Blast radius: 7 in-scope files, 67 enter sites. Change frequency: every new mutator re-instantiates the ceremony; the Lock class itself (wallet-core) is shared infrastructure whose API shape is locked in by the 67 call sites.
4. **Concrete evidence**:
   - `await this.lock.enter()` site counts: profile 21, network 13, dapp-session 12, fpc 7, contact 5, auth-registry 5, token 4 — 67 in scope, each wrapped in a 4-line try/finally.
   - Divergent idiom A: token/service.ts:151-153,199-201 introduces `holdsLock` so `finally` doesn't release a never-acquired lock — the only site that defends against this; the other 66 put `enter()` *inside* the `try`, a footgun that `withLock` would remove by construction.
   - Divergent idiom B: account/service.ts:118-136 `serializePerTuple` — a from-scratch promise-chain mutex (keyed map, `then(op, op)`, swallow-catch) instead of the fleet's `Lock`. Its cleanup block is a literal no-op: account/service.ts:129-134 — `void next.finally(() => { if (this.tupleLocks.get(key)?.then === undefined) return /* nothing after */ })`; the callback body performs no action on either branch (Dead Code), and the map entry is never evicted.
   - Divergent idiom C: named/logged locks only in newer code — `new Lock("network", logger)` network/service.ts:155, `new Lock("fpc", this.logger)` fpc/service.ts:44; the other 5 services construct anonymous `new Lock()` (token:43, contact:26, auth-registry:31, dapp-session:30, profile:30), so the Lock's contention logging and force-release diagnostics (packages/wallet-core/src/utils/lock.ts:22-44) are silently unavailable exactly where locking is heaviest (profile: 21 sites).
5. **Why it harms future change**: any cross-cutting change to lock behavior (timeout policy, contention metrics, deadlock tracing) requires touching 67 sites or accepting that 5 of 7 services are invisible to it; new mutators copy one of three idioms at random; account's no-op cleanup block actively misleads readers into thinking eviction exists.
6. **Smallest safe refactoring**: **Extract Method** onto `Lock` itself — `async withLock<T>(fn: () => Promise<T>): Promise<T>` (acquire-before-try by construction); migrate call sites mechanically. Pass `(name, logger)` at the 5 anonymous construction sites (*Introduce Parameter* — two donor examples exist in-cluster). For account: **Remove Dead Code** on :129-134 and either keep the keyed serializer (it is genuinely keyed, which `Lock` is not) behind the same `withLock`-shaped API or extract it to wallet-core as `KeyedLock`.
7. **What disappears**: ~270 lines of try/finally scaffold, the unguarded-enter footgun, the three-idiom split, the misleading no-op block, and the logging blind spot on 5 services.
8. **Instances**: lock constructions token/service.ts:43, contact/service.ts:26, auth-registry/service.ts:31, dapp-session/service.ts:30, profile/service.ts:30, network/service.ts:155, fpc/service.ts:44; holdsLock variant token/service.ts:151-153,199-201; hand-rolled serializer account/service.ts:118-136 (dead block :129-134); 67 enter/leave pairs per counts above.

## F6: The "purge rows for a dead profile/chain, emitting per row" cascade is re-implemented 10 times with inconsistent lock discipline

1. **Title**: Profile-deleted / chain-purged cascade loop re-implemented ×10 with inconsistent locking.
2. **Smell name**: **Duplicate Code** (Fowler); the divergence in lock discipline across copies is the *Shotgun Surgery* consequence — a policy change to cascade semantics must be applied in 10 places.
3. **Maintenance impact**: **structural**. Blast radius: 6 services, 10 methods. Change frequency: this family was just extended (chain-purge subscribers are recent, per the AUDIT comments) — each new profile- or chain-scoped service must hand-copy the loop again.
4. **Concrete evidence**:
   - `onProfileDeleted` copies (filter storage by `profileId` → loop → delete → emit `onXDeleted`): account/service.ts:194-202, token/service.ts:515-521, contact/service.ts:256-270, dapp-session/service.ts:325-338, fpc/service.ts:447-461, network/service.ts:671-691.
   - `clearChainState` copies (same loop keyed by `(profileId, chainId)`): token/service.ts:72-79, transaction/service.ts:74-82, fpc/service.ts:71-80, account/service.ts:43-50.
   - Inconsistent discipline across the "same" operation: contact/dapp-session/fpc/network take the service lock around the purge; account and token do not; token's profile purge routes through `deleteToken` (lock per row, N acquisitions) while its chain purge bypasses the lock entirely (:72-79). None of the four `clearChainState` loops lock. Whether any individual choice is correct is out of scope — the point is the copies make the policy unreviewable.
5. **Why it harms future change**: adding the next profile-scoped service means re-deciding (and probably re-diverging on) lock policy, event policy, and error policy for the same loop; changing cascade semantics globally (e.g. batch-delete + single summary event to cut storage churn, or making purges transactional) is a 10-site edit with 3 local variants to reconcile.

Per-service emit/decoration (fpc's `decorate`, network's `purgeChain` chaining) stays in the lambda.
7. **What disappears**: 10 hand-rolled loops (~90 lines), and the silent lock-policy divergence between siblings doing the same operation.
8. **Instances**: all file:line locations in field 4.

4. **Concrete evidence**: dapp-session/service.ts:142-165 (`updateDappSession`, 3 fields), :192-204 (`setVerificationHash`), :206-218 (`setTrustedVerification`), :220-232 (`setAccountAliases`), :234-246 (`setCapabilityGrants`), :254-266 (`setCapabilityRejections`). Identical scaffold: `lock.enter` → `storage.get(sessionId)` → `throw new Error("Invalid id")` → mutate → `storage.set` → `emit("onDappSessionUpdated", session)` → `lock.leave`. Note none of the six re-checks expiry or profile ownership while `getDappSessions` does — divergence within the same file (the ownership aspect itself is out of scope; the asymmetry is the duplication cost).
5. **Why it harms future change**: each new session field (the trajectory is clearly more capability metadata) adds another 13-line clone; a cross-cutting change (expiry re-check before mutation, ownership guard, audit logging on session mutation) is a 6-site edit that history shows will be applied unevenly.
6. **Smallest safe refactoring**: **Extract Function** — `private async patchSession(sessionId: string, patch: (s: DappSession) => void): Promise<DappSession>`; the six methods become one-liners. Pure mechanical extraction (Fowler's *Extract Method*), behavior-preserving including the emit.
7. **What disappears**: ~65 lines; future session fields cost 2 lines; cross-cutting mutation policy gets a single insertion point.
8. **Instances**: the six file:line ranges in field 4.

## Non-findings

- **spec/service/client triple** — house convention, explicitly excluded by the prompt; no measurable duplication beyond what F3/F4 capture.
- **Added/Updated/Deleted EventHandler triples ×9 in scope** — convention; the fields double as the events map consumed by the base class; declarations are 3 lines/service with no logic to drift. No cost beyond declaration.
- **runtime.ts 21× `services.add(new X(logger))` list** — composition root; single location; adding a service is a one-line edit. Not Shotgun Surgery.
- **Service-locator resolution (`services.get(X.name)`) instead of constructor injection** — consistent fleet-wide; its real cost (ordering) is already captured by F1; flagging the locator itself would be a style preference.
- **`do { id = getRandomHex(n) } while (await storage.contains(id))` id-gen idiom ×9** (contact:96-99,300-302; fpc:191-194,270-273,490-493; network:641,713-719,721-728; dapp-session:118-121; profile/repository.ts:101-107) — considered Duplicate Code; rejected as a standalone finding: 3 lines per site, one donor extraction already exists (repository.generateUniqueId), and it would collapse for free inside F4/F6 helpers.
- **`sameLocalNetworkUrl` vs `normalizeRpcUrl` (network/service.ts:104-131)** — two URL comparators look like duplication but have documented, deliberately different semantics (seed comparison vs preserve-user-input); comments carry the invariant. Not a smell.
- **account `changeAccountName`/`changeAccountVisibility` near-twins (account/service.ts:138-167)** — 2 instances, ~10 lines; below extraction value.
- **config/service.ts as Lazy Class** — considered; rejected: it's the RPC bridge over ConfigStore, the thinness is the point (single responsibility), and it carries backup/restore behavior.
- **`export * from "./spec"` + `export * from "./functions"` from service modules** — widens import surfaces (and feeds F9), but it's the uniform fleet convention; flagged only where it materializes a cycle (F9).
