## F1: PXE RPC contract is hand-copied across five surfaces
1. Title: PXE RPC contract is hand-copied across five surfaces.
2. Smell name: Shotgun Surgery. This is Shotgun Surgery because adding or reshaping one PXE RPC verb requires coordinated edits to the wire contract, service implementation, client wrapper, proxy adapter, and in-process interface.
3. Maintenance impact bucket: Architectural; blast radius is 5 core files plus the extension shim and 16 in-repo `IPXE` consumers; change frequency is already 1-2 commits per file since 2026-05-19, with coordinated edits on 2026-06-05.
4. Concrete evidence: `packages/aztec-runtime/src/pxe/spec.ts:24-80` defines `Methods`; `packages/aztec-runtime/src/pxe/service.ts:166-427` re-implements the same verbs; `packages/aztec-runtime/src/pxe/client.ts:76-200` wraps the same verbs into requests; `packages/aztec-runtime/src/pxe/proxy.ts:32-102` forwards the same verbs onto a network-bound proxy; `packages/aztec-runtime/src/pxe/ipxe.ts:27-50` repeats the in-process subset. The split is already drifting: `getBlockTimestamp` and `clearChainState` exist in `spec.ts:74-80`, `service.ts:383-427`, and `client.ts:191-200`, but not in `ipxe.ts:27-50` or `proxy.ts:26-103`.
5. Why it harms future change: any new PXE capability or signature tweak forces mechanical edits across transport layers before the real domain change even starts, and every change must also decide whether `IPXE`/`PXEProxy` should grow with it.
6. Smallest safe refactoring: Named analog refactoring, single-source contract descriptor. Define one canonical `PxeRpc` surface, derive `Methods` and `IPXE` from it, and generate/shared-forward `PxeServiceClientBase` and `PXEProxy` from that descriptor instead of maintaining parallel method tables.
7. What disappears: parallel verb lists, manual forwarders, and per-method decisions about which copy of the contract has to change.
8. Instances: `packages/aztec-runtime/src/pxe/spec.ts:24-80`; `packages/aztec-runtime/src/pxe/service.ts:166-427`; `packages/aztec-runtime/src/pxe/client.ts:76-200`; `packages/aztec-runtime/src/pxe/proxy.ts:32-102`; `packages/aztec-runtime/src/pxe/ipxe.ts:27-50`; `packages/extension/src/wallet/services/pxe/client.ts:1-22`.

## F2: Background and offscreen RPC stacks are forked copies
1. Title: Background and offscreen RPC stacks are forked copies.
2. Smell name: Duplicate Code, drifting into Alternative Classes with Different Interfaces. The two transports solve the same request/response lifecycle with copied code, but their caller-visible error and telemetry contracts have already diverged.
3. Maintenance impact bucket: Architectural; blast radius is 4 base transport files plus 43 production background consumers and 4 production offscreen consumers; change frequency is low in git (1-2 commits per base file since 2026-05-19) but every transport-wide hardening change lands here.
4. Concrete evidence: `packages/extension-messaging/src/background/client.ts:27-227` and `packages/extension-messaging/src/offscreen/client.ts:29-245` both own request maps, request IDs, `onMessage`, timeout logic, request serialization, and log helpers, but background reconstructs typed errors (`background/client.ts:112`, `182`, `204-209`) while offscreen rejects plain strings (`offscreen/client.ts:110`, `206`, `237`) and adds a separate telemetry sidecar (`22-27`, `198-206`, `258-279`). `packages/extension-messaging/src/background/service.ts:10-226` and `packages/extension-messaging/src/offscreen/service.ts:16-187` both parse envelopes, invoke `this.requests[method]`, `jsonSanitize` results, retry clone failures with `jsonStringify`, and expose near-identical `ensureInitialized` loops (`187-199` vs `158-169`) plus identical log helper quartets (`201-214` vs `172-185`). The offscreen keepalive magic string is duplicated again in `packages/extension/src/wallet/utils/offscreen.ts:1-4`.
5. Why it harms future change: a transport-wide improvement such as structured errors, telemetry, timeout semantics, or clone-fallback handling has to be implemented and reviewed twice, and callers cannot rely on one consistent failure model across transports.
6. Smallest safe refactoring: Extract Superclass / Template Method. Pull shared request bookkeeping, timeout handling, response parsing, json-fallback behavior, and log helpers into a transport-agnostic core with pluggable transport hooks for connect/send/reconstruct-error/record-terminal.
7. What disappears: four mostly-parallel RPC engines, repeated `ensureInitialized` loops and log helpers, and the need for callers to remember transport-specific error semantics.
8. Instances: `packages/extension-messaging/src/background/client.ts:27-263`; `packages/extension-messaging/src/offscreen/client.ts:29-296`; `packages/extension-messaging/src/background/service.ts:10-226`; `packages/extension-messaging/src/offscreen/service.ts:16-187`; `packages/extension/src/wallet/utils/offscreen.ts:1-4`.

## F3: Unused utility subpaths still ship as public API
1. Title: Unused utility subpaths still ship as public API.
2. Smell name: Dead Code. These are exported, tested utilities with no production consumers anywhere in the repo.
3. Maintenance impact bucket: Structural; blast radius is 2 public subpaths and 420 lines of adjacent tests; change frequency is 1 commit each since 2026-05-19.
4. Concrete evidence: `packages/extension-messaging/package.json:6-15` exports `./lazy-listener` and `./subscribe-with-snapshot`; the implementations live at `packages/extension-messaging/src/lazy-listener.ts:1-129` and `packages/extension-messaging/src/subscribe-with-snapshot.ts:1-88`; repo-wide import search outside tests finds no imports of either subpath or file. There is no DI or framework registration caveat here: these are plain package exports, not auto-imported extension directories. Both still carry dedicated tests at `packages/extension-messaging/src/lazy-listener.test.ts:1-203` and `packages/extension-messaging/src/subscribe-with-snapshot.test.ts:1-217`.
5. Why it harms future change: package cleanup, API review, and type-surface changes must preserve and validate contracts that no production path uses, which obscures the real transport surface and adds dead maintenance load.
6. Smallest safe refactoring: Remove Dead Code. Remove both exports and their modules/tests until a real consumer appears, or move the helpers into the first consumer that actually needs them.
7. What disappears: two unused public subpaths, their dead-support tests, and the obligation to keep unused contracts stable.
8. Instances: `packages/extension-messaging/package.json:6-15`; `packages/extension-messaging/src/lazy-listener.ts:1-129`; `packages/extension-messaging/src/subscribe-with-snapshot.ts:1-88`; `packages/extension-messaging/src/lazy-listener.test.ts:1-203`; `packages/extension-messaging/src/subscribe-with-snapshot.test.ts:1-217`.

## F4: Core transport contract tests live in the extension package
1. Title: Core transport contract tests live in the extension package.
2. Smell name: Test brittleness (close analog, mapping to Inappropriate Intimacy). The messaging package’s verification depends on another package’s harness, aliases, and directory layout.
3. Maintenance impact bucket: Architectural; blast radius is 2 packages and the shared extension test harness; change frequency is low in git (one commit per test file since 2026-05-19) but these tests cover the base transport layer.
4. Concrete evidence: the contract suites for the messaging package live under `packages/extension/src/wallet/base/background/client.test.ts:1-120`, `packages/extension/src/wallet/base/offscreen/client.test.ts:1-120`, `packages/extension/src/wallet/base/errors.test.ts:1-119`, and `packages/extension/src/wallet/base/zod-helpers.test.ts:1-83` instead of under `packages/extension-messaging/src`. The client suites reach into the extension harness via `packages/extension/src/wallet/base/background/client.test.ts:21` and `packages/extension/src/wallet/base/offscreen/client.test.ts:4`. Meanwhile `packages/extension-messaging/src/testing/setup.ts:1-16` already exists, but `packages/extension-messaging/package.json:6-16` exports no `./testing/*` path, and the package’s own file inventory contains no `background/*.test.ts` or `offscreen/*.test.ts`.
5. Why it harms future change: refactoring extension aliases or `packages/extension/tests/vitest.setup` can break messaging-package tests without changing the package, and package-level work cannot be validated in isolation inside `packages/extension-messaging`.
6. Smallest safe refactoring: Move Tests (named analog of Move Function). Relocate the transport contract suites into `packages/extension-messaging/src/{background,offscreen}` and either export `./testing/setup` or keep a package-local setup there.
7. What disappears: cross-package test ownership, dependence on extension-only aliases for package verification, and harness coupling to `packages/extension/tests`.
8. Instances: `packages/extension/src/wallet/base/background/client.test.ts:1-120`; `packages/extension/src/wallet/base/offscreen/client.test.ts:1-120`; `packages/extension/src/wallet/base/errors.test.ts:1-119`; `packages/extension/src/wallet/base/zod-helpers.test.ts:1-83`; `packages/extension-messaging/src/testing/setup.ts:1-16`; `packages/extension-messaging/package.json:6-16`.

## F5: PxeService concentrates lifecycle, locking, cleanup, and RPC handlers
1. Title: PxeService concentrates lifecycle, locking, cleanup, and RPC handlers.
2. Smell name: Large Class. One class owns unrelated responsibilities and therefore several independent reasons to change.
3. Maintenance impact bucket: Structural; blast radius is one 507-line hotspot at the center of the PXE path; change frequency is 2 commits since 2026-05-19, including a coordinated edit on 2026-06-05.
4. Concrete evidence: `packages/aztec-runtime/src/pxe/service.ts:60-123` owns profile/barrier state and guard allocation; `125-164` performs orphan-IndexedDB cleanup and profile-event wiring; `166-427` implements the full RPC surface; `429-468` owns generic lock-wrapping and timing/logging; `470-506` owns profile-delete teardown. The same file also repeats IndexedDB deletion scaffolding at `133-141`, `148-156`, and `416-423`, with another deletion path at `487-490`.
5. Why it harms future change: changing DB lifecycle policy, concurrency semantics, or a single PXE RPC verb all force work in the same file and reviewer context, which increases merge conflicts and makes safe extraction harder.
6. Smallest safe refactoring: Extract Class. Split lifecycle/cleanup (`init`, `clearChainState`, `onProfileDeleted`) and lock orchestration (`withPxeRead`/`withPxeWrite`) away from the RPC façade so `PxeService` becomes a thin transport adapter.
7. What disappears: one hotspot carrying unrelated concerns, repeated IndexedDB cleanup scaffolding, and the need to reason about profile teardown while changing one RPC handler.
8. Instances: `packages/aztec-runtime/src/pxe/service.ts:57-507`, especially `60-164`, `166-427`, `429-468`, and `470-506`.
