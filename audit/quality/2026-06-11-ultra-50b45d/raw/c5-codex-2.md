## F1: PXE contract is hand-synchronized across five files
1. Title: PXE contract is hand-synchronized across five files.
2. Smell name: `Duplicate Code`; this is also a form of `Shotgun Surgery` because adding or changing one PXE method requires coordinated edits to the wire contract, the service, the client, and the single-network proxy/interface subset.
3. Maintenance impact bucket: `architectural`; blast radius is 5 core files that define every PXE call surface; change frequency is medium in the visible history (this PXE cluster moved in 2 commits) but the centrality is high because all PXE consumers depend on it.
4. Concrete evidence: the same method families are repeated in `packages/aztec-runtime/src/pxe/spec.ts:24`, `packages/aztec-runtime/src/pxe/service.ts:57`, `packages/aztec-runtime/src/pxe/client.ts:62`, `packages/aztec-runtime/src/pxe/ipxe.ts:27`, and `packages/aztec-runtime/src/pxe/proxy.ts:26`; concrete repeated signatures include `getContractInstance` at `spec.ts:32`, `service.ts:166`, `client.ts:76`, `ipxe.ts:28`, `proxy.ts:32`, `simulateTx` at `spec.ts:54`, `service.ts:283`, `client.ts:157`, `ipxe.ts:42`, `proxy.ts:88`, and `getSyncedBlockHeader` at `spec.ts:64`, `service.ts:373`, `client.ts:183`, `ipxe.ts:49`, `proxy.ts:100`; the full RPC-only methods such as `getNoteSchemas` and `clearChainState` add yet another manual subset split across `spec.ts:41/80`, `client.ts:90/199`, and `service.ts:203/409`.
5. Why it harms future change: adding one PXE capability or changing one argument/return type is not local work; the editor has to remember which of the five surfaces are full, which are subset-only, and which are bound-to-network wrappers, so signature changes become bookkeeping-heavy before any behavior changes happen.
6. Smallest safe refactoring: `Extract Interface` around one canonical PXE contract module, then `Move Function`/adapter glue so client, service, and proxy derive from that contract instead of restating it.
7. What disappears: five-way signature maintenance, full-surface vs subset-surface drift, and repeated wrapper code whose only job is to restate the same API.
8. Instances: `packages/aztec-runtime/src/pxe/spec.ts:24`, `packages/aztec-runtime/src/pxe/ipxe.ts:27`, `packages/aztec-runtime/src/pxe/proxy.ts:26`, `packages/aztec-runtime/src/pxe/client.ts:62`, `packages/aztec-runtime/src/pxe/service.ts:57`.

## F2: Background and offscreen transports duplicate the same RPC lifecycle in four base classes
1. Title: Background and offscreen transports duplicate the same RPC lifecycle in four base classes.
2. Smell name: `Duplicate Code`; this is also a form of `Divergent Change` because timeout policy, request tracking, JSON fallback, logging, and error-boundary changes have to be re-applied across four near-parallel implementations.
3. Maintenance impact bucket: `architectural`; blast radius is 4 foundational base classes plus every caller built on them; change frequency is medium-high in the visible history (3 commits touched this transport area).
4. Concrete evidence: the client-side pending-request lifecycle is duplicated between `packages/extension-messaging/src/background/client.ts:20-25,37-39,134-227,233-246` and `packages/extension-messaging/src/offscreen/client.ts:22-27,36-39,176-245,282-295`; both independently parse the `resultIsJson` fallback at `background/client.ts:116-123` and `offscreen/client.ts:114-121`; the service-side dispatch/send lifecycle is duplicated between `packages/extension-messaging/src/background/service.ts:62-100,119-185,187-215` and `packages/extension-messaging/src/offscreen/service.ts:52-99,99-139,158-185`; even `ensureInitialized` is verbatim in `background/service.ts:187-199` and `offscreen/service.ts:158-170`; the duplicated stack has already drifted, with structured `WalletError` round-tripping only on background (`background/service.ts:88-90`, `background/client.ts:108-113`) while offscreen still rejects with plain strings (`offscreen/service.ts:84-95`, `offscreen/client.ts:109-121,206-237`).
5. Why it harms future change: any transport-wide concern, such as adopting structured errors everywhere or changing the JSON fallback contract, requires touching four files that mostly exist to do the same lifecycle work through different Chrome primitives.
6. Smallest safe refactoring: `Extract Superclass` plus `Template Method`, with transport-specific hooks for `Port` vs `sendMessage` and one shared implementation for request bookkeeping, fallback parsing, logging, and timeout cleanup.
7. What disappears: duplicated timeout/request maps, duplicated JSON-fallback handling, duplicated logging quartets, and the current drift where equivalent transports expose different failure contracts.
8. Instances: `packages/extension-messaging/src/background/client.ts:20`, `packages/extension-messaging/src/background/service.ts:62`, `packages/extension-messaging/src/offscreen/client.ts:22`, `packages/extension-messaging/src/offscreen/service.ts:52`.

## F3: Unused messaging helpers are still maintained as live library code
1. Title: Unused messaging helpers are still maintained as live library code.
2. Smell name: `Dead Code`; also `Speculative Generality`, because these abstractions add supported-looking library surface area even though nothing shipped in this repo consumes them.
3. Maintenance impact bucket: `structural`; blast radius is 2 production helper modules and their self-tests; change frequency is low-medium in the visible history (3 commits touched this slice).
4. Concrete evidence: the production helpers are `packages/extension-messaging/src/lazy-listener.ts:68` and `packages/extension-messaging/src/subscribe-with-snapshot.ts:54`; repo-wide search for `makeLazyListener` and `subscribeWithSnapshot` only finds those definitions, their self-tests (`packages/extension-messaging/src/lazy-listener.test.ts:3`, `packages/extension-messaging/src/subscribe-with-snapshot.test.ts:3`), and comments, with no production imports anywhere under `packages/extension`, `packages/aztec-runtime`, or `packages/extension-messaging`; because this is plain library code in `@nulo/extension-messaging`, not one of the extension package’s auto-imported directories, there is no DI or framework registration path that would make these live implicitly.
5. Why it harms future change: messaging refactors now have to preserve or consciously delete two extra patterns, their docs, and their tests, even though the shipped runtime never exercises them.
6. Smallest safe refactoring: `Delete Dead Code`; if a real consumer appears later, reintroduce the helper from the concrete call site instead of preserving speculative library surface now.
7. What disappears: two dormant abstractions, their self-test burden, and the false signal that extension-messaging currently supports these patterns in production.
8. Instances: `packages/extension-messaging/src/lazy-listener.ts:1`, `packages/extension-messaging/src/lazy-listener.test.ts:1`, `packages/extension-messaging/src/subscribe-with-snapshot.ts:1`, `packages/extension-messaging/src/subscribe-with-snapshot.test.ts:1`.

1. Title: Extension-owned tests verify extension-messaging contracts from outside the package.
2. Smell name: named close analog `test-location inversion`; this is a form of `Shotgun Surgery` and `Test Brittleness` because changing one library contract requires updating tests in a different package and sometimes in both places.
3. Maintenance impact bucket: `structural`; blast radius is at least 5 test files across 2 packages; change frequency is medium in the visible history (3 commits touched these tests/library files).
4. Concrete evidence: `packages/extension/src/wallet/base/background/client.test.ts:19-22`, `packages/extension/src/wallet/base/offscreen/client.test.ts:5-12`, `packages/extension/src/wallet/base/errors.test.ts:2-10`, and `packages/extension/src/wallet/base/zod-helpers.test.ts:3-4` all import `@nulo/extension-messaging/*` and act as contract suites for that library from outside its package boundary; the library also keeps its own overlapping error round-trip suite at `packages/extension-messaging/src/errors.test.ts:1-45`, which repeats the same `walletErrorFromPayload` contract already re-asserted in `packages/extension/src/wallet/base/errors.test.ts:90-133`.

8. Instances: `packages/extension/src/wallet/base/background/client.test.ts:19`, `packages/extension/src/wallet/base/offscreen/client.test.ts:5`, `packages/extension/src/wallet/base/errors.test.ts:2`, `packages/extension/src/wallet/base/zod-helpers.test.ts:3`, `packages/extension-messaging/src/errors.test.ts:1`.

## F5: PxeService concentrates four change axes in one 507-line class
1. Title: PxeService concentrates four change axes in one 507-line class.
2. Smell name: `Large Class`; also `Divergent Change`, because concurrency policy, IndexedDB lifecycle, profile-event cleanup, and RPC dispatch all modify the same service class.
3. Maintenance impact bucket: `structural`; blast radius is one central file that fronts every PXE RPC; change frequency is medium in the visible history (2 commits touched this PXE service area), with high centrality.
4. Concrete evidence: bootstrap/orphan-DB cleanup lives in `packages/aztec-runtime/src/pxe/service.ts:125-164`; the 19 RPC handlers fill `service.ts:166-426`; guard orchestration is embedded in `service.ts:429-468`; profile-delete lifecycle cleanup sits in `service.ts:470-506`; handler-local diagnostics also live inline, for example the duplicated sync-debug preambles at `service.ts:268-297`.
5. Why it harms future change: a storage-lifecycle tweak or guard-policy change is forced through the same class that owns request semantics and profile event wiring, so even local infrastructure edits require reloading a large unrelated mental model.
6. Smallest safe refactoring: `Extract Class`; move IndexedDB/profile-lifecycle concerns into a dedicated coordinator and move guarded runtime execution into a separate executor, leaving `PxeService` as a thin RPC facade.
7. What disappears: mixed responsibilities, inline lifecycle machinery around request handlers, and the need to touch a monolithic service for unrelated policy changes.
8. Instances: `packages/aztec-runtime/src/pxe/service.ts:57`, `packages/aztec-runtime/src/pxe/service.ts:125`, `packages/aztec-runtime/src/pxe/service.ts:166`, `packages/aztec-runtime/src/pxe/service.ts:429`, `packages/aztec-runtime/src/pxe/service.ts:470`.
