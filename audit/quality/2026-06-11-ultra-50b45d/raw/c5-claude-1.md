# C5 — PXE + messaging transport layer (Claude instance 1)

Scope audited: `packages/aztec-runtime/src/**`, `packages/extension-messaging/src/**`, `packages/extension/src/wallet/services/pxe/client.ts`, `packages/extension/src/wallet/utils/offscreen.ts`, `packages/extension/src/wallet/base/**`. All map claims re-verified against source; two map claims rejected (see Non-findings).

## F1: PXE method surface is hand-enumerated on five parallel surfaces (plus a half-migrated shim)

1. **Title:** Adding one PXE method requires editing five hand-maintained method lists; two of them can silently drift.
2. **Smell name:** Shotgun Surgery (Fowler, Change Preventers). The house `spec.ts`/`service.ts`/`client.ts` triple is excluded per scope rules — this finding is about the *two extra* surfaces beyond the triple (`ipxe.ts`, `proxy.ts`) plus the transitional re-export shim, and the lack of type-level derivation between them.
3. **Impact bucket:** architectural. Blast radius: 5 files per method addition (`spec.ts`, `service.ts`, `client.ts`, `ipxe.ts`, `proxy.ts`), 6th surface for type re-exports (`packages/extension/src/wallet/services/pxe/client.ts:24`). Change frequency: active — `spec.ts`/`service.ts`/`client.ts` each touched in 2 of the 6 commits since the 2026-05-19 import (`getBlockTimestamp`, `clearChainState` were added in this window).
4. **Evidence:** `Methods` declares 21 methods (`packages/aztec-runtime/src/pxe/spec.ts:24-81`). `PxeService` implements all 21 (`pxe/service.ts:166-427`), type-checked via `implements ServiceSpec<Methods>`. `PxeServiceClientBase` implements all 21 (`pxe/client.ts:76-201`), also checked. `IPXE` re-declares 18 of them by hand (`pxe/ipxe.ts:27-50`) — it is NOT derived from `Methods`, so a method added to `Methods` is silently absent from `IPXE` (already true for `getNoteSchemas`, `getBlockTimestamp`, `clearChainState`; the first two are plausibly wanted in-process). `PXEProxy` hand-writes 18 one-line delegations differing only in method name (`pxe/proxy.ts:32-102`). The extension shim re-exports the surface a 6th time (`packages/extension/src/wallet/services/pxe/client.ts:24`) with a "drop the shim" TODO comment — and the migration is stuck halfway: 14 extension files import via the shim, 14 import `@nulo/aztec-runtime/pxe` directly, so every consumer search needs two greps. The vestigial `<_T>` type parameter on `getPrivateEvents` is faithfully copy-pasted across three of the surfaces (`spec.ts:61`, `ipxe.ts:44`, `proxy.ts:96`) — copy-propagation evidence.
5. **Why it harms future change:** every new network-scoped PXE RPC costs five mechanical edits; the two unchecked surfaces (`IPXE`, `PXEProxy`) fail silently rather than at compile time, so an in-process consumer discovers a missing method only when it reaches for it. The dual import path means renames/moves of the PXE client touch an unpredictable half of 28 import sites.
6. **Smallest safe refactoring:** derive `IPXE` mechanically from `Methods` with a mapped type that strips the leading `NetworkInfo` parameter (Extract Interface, performed by the compiler instead of by hand), and replace `PXEProxy`'s 18 delegations with one generic `bindNetwork(client, network)` factory (Replace Derived Variable with Query analog — generate the delegation). Separately: finish the shim migration (Inline Function on the re-export, 14 import-path edits) so one import path remains.
7. **What disappears:** ~150 LOC of hand-kept declarations (`ipxe.ts` body + `proxy.ts` body), the silent `Methods`↔`IPXE` drift class, the `<_T>` fossil, and the dual import path.
8. **Instances:** `packages/aztec-runtime/src/pxe/spec.ts:24-81`; `packages/aztec-runtime/src/pxe/ipxe.ts:27-50`; `packages/aztec-runtime/src/pxe/service.ts:166-427`; `packages/aztec-runtime/src/pxe/client.ts:76-201`; `packages/aztec-runtime/src/pxe/proxy.ts:32-102`; `packages/extension/src/wallet/services/pxe/client.ts:24`.

## F2: Background vs offscreen ServiceClient — two forked correlation engines with divergent error contracts

1. **Title:** The request-correlation machinery (pending map, ids, timeout, A6 JSON-fallback parse) is implemented twice, and the two copies reject with incompatible error shapes.
2. **Smell name:** Duplicate Code + Alternative Classes with Different Interfaces (Fowler). Two classes do the same job — typed request/response correlation over a Chrome messaging transport — with different constructor options, hooks, and error surfaces.
3. **Impact bucket:** architectural. Blast radius: 23 extension `ServiceClient` subclass files ride the background copy; `PxeServiceClientBase` (and everything PXE) rides the offscreen copy. Change frequency: 1 commit each since import (dormant, but the A6 fallback and the timeout policy were both retro-fitted to BOTH copies already — historical evidence of double-fix cost).
4. **Evidence:** `packages/extension-messaging/src/background/client.ts` (263 LOC) vs `packages/extension-messaging/src/offscreen/client.ts` (297 LOC). Shared near-verbatim: pending-request map + `nextRequestId`/`getRequestId` (background:37-38,229-231 vs offscreen:36-39,247-249); request envelope `jsonSanitize(wrapParams(params))` (background:155-162 vs offscreen:187-196); `onMessage` validation + Event-branch dispatch (background:94-132 vs offscreen:88-137); the A6 `resultIsJson → JSON.parse` block with its explanatory comment duplicated nearly word-for-word (background:117-123 vs offscreen:114-121); the `logDebug/logInfo/logWarn/logError` quadruplet (background:233-247 vs offscreen:282-296). Divergences that are policy, not transport: background rejects with typed errors — `walletErrorFromPayload` (:112), `RpcTimeoutError` (:178-184), `RpcDisconnectedError` (:199-211) — while offscreen rejects with **plain strings** (`reject(error)` :110, `reject("Client disconnected")` :72, `` reject(`Offscreen request timed out: ${methodName}`) `` :206, `` reject(`Offscreen send failed: ${methodName}`) `` :237) and never reconstructs `errorPayload`. Timeout override is a ctor option in one (background:41-45) and a `getRequestTimeoutMs` hook in the other (offscreen:172-174). Telemetry and the 10s warn-timer exist on exactly one side each.
5. **Why it harms future change:** every cross-cutting improvement to the RPC layer (a new terminal status, request cancellation, error-payload enrichment, the next A6-class serialization fix) must be written twice and reviewed twice; history shows A6 and the timeout rework already paid that tax. The divergent rejection shapes force every consumer that touches both transports (e.g. execution-service code that calls PXE and background services) to maintain two catch idioms — `instanceof WalletError` works on one path and silently never matches on the other.
6. **Smallest safe refactoring:** Extract Superclass — a transport-agnostic `RequestCorrelator` owning the pending map, id allocation, timeout scheduling, terminal resolution, and the A6 parse; the two clients keep only their transport send/receive and their policy hooks (Form Template Method for `request()`). Unifying the rejection shape on `WalletError` is step two (behavior-affecting, do behind the consumers' existing string checks).
7. **What disappears:** ~120 LOC of duplicated correlation logic, the double-fix obligation for every RPC-layer change, and (after step two) the two-error-vocabulary problem.
8. **Instances:** `packages/extension-messaging/src/background/client.ts:37-46,94-132,134-227,229-247`; `packages/extension-messaging/src/offscreen/client.ts:36-52,88-137,176-249,282-296`.

## F3: Background vs offscreen Service — duplicated dispatch loop, A6 fallback twice, `ensureInitialized` verbatim, logger quadruplet ×4

1. **Title:** The service-side request dispatch (validate → unwrap → invoke → sanitize → respond, with jsonStringify fallback) is forked across the two Service base classes; `ensureInitialized` is character-identical.
2. **Smell name:** Duplicate Code (Fowler, Dispensables); the A6 fallback specifically is the same fix landed twice in two shapes (extracted method vs inline catch) — a sibling of Divergent Change waiting to happen.
3. **Impact bucket:** structural. Blast radius: 22 background `Service` subclasses + `PxeService` (offscreen) inherit whichever copy they extend. Change frequency: 1 commit each since import.
4. **Evidence:** `packages/extension-messaging/src/background/service.ts` (226 LOC) vs `packages/extension-messaging/src/offscreen/service.ts` (187 LOC). `ensureInitialized` is verbatim-identical including the 30 000/500 sleep-poll constants (background:187-199 vs offscreen:158-170). `init`/`start` are verbatim (background:29-38 vs offscreen:34-43), as are the `events`/`requests` casting getters (background:14-19 vs offscreen:19-25). The request-handling body — message-shape validation, `unwrapParams`, method dispatch, `jsonSanitize` of the result, error flattening — is near-verbatim (background:62-102 vs offscreen:52-98). The A6 structured-clone fallback is implemented twice in different shapes: extracted `trySendJsonFallback` (background:139-185) vs an inline catch block (offscreen:99-139), each carrying its own multi-line rationale comment. The `logDebug/logInfo/logWarn/logError` quadruplet appears here for the 3rd and 4th time (background:201-215, offscreen:172-186; ×4 across the package counting F2's pair — ~60 LOC of pure copy-paste). One asymmetry is a latent divergence trap: background round-trips `WalletError` via `errorPayload` (background:90-98) while offscreen never populates `errorPayload` (offscreen:87-95) even though the shared `ResponseContent` type declares the field (`src/messages.ts:48`).
5. **Why it harms future change:** the next change to the dispatch contract (param validation hook, structured errors on the offscreen wire, request tracing) must be discovered, ported, and kept consistent by hand across both files — the A6 fallback already demonstrates the drift mode: same fix, two shapes, two comment blocks to keep truthful. The `errorPayload` asymmetry means anyone who adds a `WalletError` to `PxeService` expecting client-side `instanceof` (as works everywhere else in the codebase) gets a string instead.
6. **Smallest safe refactoring:** Extract Superclass / Extract Method — pull `ensureInitialized`, `init`/`start`, the getter pair, the logger quadruplet, and a shared `buildResponse(requestId, fn)` + `trySendJsonFallback` into one base (or a composed `ServiceCore` if multiple-inheritance pressure appears); the two classes keep only port-fan-out vs sendMessage routing and the keepalive.
7. **What disappears:** ~140 LOC of duplication, the two-shape A6 fallback, four copies of the logger quadruplet (counting F2), and the place where the `errorPayload` asymmetry hides.
8. **Instances:** `packages/extension-messaging/src/background/service.ts:14-19,29-38,62-102,139-185,187-199,201-215`; `packages/extension-messaging/src/offscreen/service.ts:19-25,34-43,52-98,99-139,158-170,172-186`.

## F4: Two shipped, exported, fully-tested modules have zero production consumers — and both have live hand re-implementations

1. **Title:** `lazy-listener` and `subscribe-with-snapshot` are dead subpath exports; the patterns they codify are re-implemented inline at the real call sites.
2. **Smell name:** Speculative Generality + Duplicate Code (Fowler, Dispensables). The abstraction was built (and audited, per its own doc comment) but never wired; meanwhile the duplication it was meant to remove exists and grows.
3. **Impact bucket:** structural. Blast radius: 2 modules (217 LOC source) + 2 test files (~420 LOC) maintained for nothing; 2 re-implementation sites that can drift from the canonical race-closing logic. Change frequency: dormant since import — but `operation-journal/client.ts` (one of the re-implementations) is Phase 2 code under active QA.
4. **Evidence:** package exports declare both subpaths (`packages/extension-messaging/package.json` `"./lazy-listener"`, `"./subscribe-with-snapshot"`). Grep over all packages finds **zero** imports of either subpath or symbol outside the modules' own files (verified; the extension's auto-import covers only its own `src/` dirs, not workspace packages, so no hidden registration). `makeLazyListener`'s header even claims it "was confirmed by both Phase 2 audit rounds as a Phase 2 must-have" (`src/lazy-listener.ts:15-16`) — it was never attached anywhere. Meanwhile: (a) `packages/extension/src/wallet/services/operation-journal/client.ts:87-126` re-implements register-first/snapshot-second/reconnect-refire/late-snapshot-guard inline, citing the helper by name in a comment (":90 Same pattern as `subscribeWithSnapshot`"); (b) `packages/extension/src/wallet/services/profile/client.test.ts:38` defines a local `async function subscribeWithSnapshot(...)` — same name, third copy of the logic.
5. **Why it harms future change:** the snapshot-race pattern is subtle (the module's 28-line header explains exactly why ordering matters); three independent copies means a future fix to the race logic (e.g. handling a reconnect during an in-flight snapshot) lands in at most one of them. The dead modules also tax every package-wide change — they show up in typecheck, test runs, export-map maintenance — while delivering nothing.
6. **Smallest safe refactoring:** decide per module. `subscribe-with-snapshot`: Replace Inline Code with Function Call — adapt `subscribeJob` to the helper via a tiny `SubscribableSource` adapter (its three events fan into one `onChange`), and replace the test-local copy with an import. `lazy-listener`: either wire it at the SW entry it was designed for, or Remove Dead Code (delete subpath + test); keeping an audited-but-unwired buffer is the worst of both.
7. **What disappears:** two of the three copies of the race-closing logic, ~640 LOC of dead source+tests (if removed), and the misleading "must-have" claim.
8. **Instances:** `packages/extension-messaging/src/lazy-listener.ts:1-129` (+ `lazy-listener.test.ts`); `packages/extension-messaging/src/subscribe-with-snapshot.ts:1-88` (+ `subscribe-with-snapshot.test.ts`); re-implementations at `packages/extension/src/wallet/services/operation-journal/client.ts:87-126` and `packages/extension/src/wallet/services/profile/client.test.ts:38-…`.

## F5: Test-location inversion — the transport packages' real coverage lives in the extension's tree

1. **Title:** extension-messaging's four base classes (973 LOC) and aztec-runtime's registry classes are tested from `packages/extension/`, while the packages' own in-package tests cover mostly the zero-consumer modules.
2. **Smell name:** Inappropriate Intimacy (Fowler, Couplers) between package and consumer test trees, producing Shotgun Surgery on refactors: changing a package requires editing/running a sibling package's tests. Community canon: "tests live with the code under test."
3. **Impact bucket:** structural. Blast radius: 6 test files (~1 550 LOC) in the wrong package; every extraction/reuse of `@nulo/extension-messaging` or `@nulo/aztec-runtime` outside this repo silently drops their effective test suite. Change frequency: the tested code (offscreen client, chain-runtime) changed in 2 of 6 recent commits.
4. **Evidence:** in-extension tests of package code: `packages/extension/src/wallet/base/background/client.test.ts` (449 LOC, tests `@nulo/extension-messaging/background`), `wallet/base/offscreen/client.test.ts` (387 LOC), `wallet/base/errors.test.ts` (133 LOC), `wallet/base/zod-helpers.test.ts` (86 LOC), `packages/extension/src/wallet/services/pxe/chain-runtime.test.ts` (199 LOC, tests `@nulo/aztec-runtime/pxe` `ChainRuntimeRegistry`), `wallet/services/pxe/artifact-registry.test.ts` (297 LOC) — the latter two sit in a directory whose only source file is the 24-line shim `client.ts`. Inversion: extension-messaging's best in-package tests (`lazy-listener.test.ts`, `subscribe-with-snapshot.test.ts`) cover the two modules with zero consumers (F4), while its 973 LOC of production base classes carry zero in-package tests except a 46-LOC `errors.test.ts` that partially **duplicates** the extension's 133-LOC `wallet/base/errors.test.ts` (both pin `walletErrorFromPayload` round-trips). Gate split: the documented local pre-PR gate `audit:vue` runs `bun run test` = `--cwd packages/extension` only, so an extension-messaging refactor validated via the package's own `vitest run` exercises almost none of its real coverage; only CI's `test:all` runs both halves.
5. **Why it harms future change:** a contributor editing `offscreen/client.ts` won't find its tests by proximity and may ship against the package's near-empty in-package suite; conversely the extension's test tree accretes files with no neighboring source, confusing the colocation convention (`CLAUDE.md`: colocate `<Name>.test.ts` next to source). The duplicated errors coverage rots independently.
6. **Smallest safe refactoring:** Move Function (Move Tests) — relocate the six files into their owning packages next to the source (`src/background/client.test.ts`, `src/pxe/chain-runtime.test.ts`, …), merging the two `errors` test files. Chrome stubbing already exists in-package (`src/testing/setup.ts` exists for exactly this and is itself unused).
7. **What disappears:** the cross-package test intimacy, the duplicated errors suite, the empty-looking in-package suites, and the local-gate blind spot for transport refactors.
8. **Instances:** `packages/extension/src/wallet/base/background/client.test.ts`; `packages/extension/src/wallet/base/offscreen/client.test.ts`; `packages/extension/src/wallet/base/errors.test.ts` (vs `packages/extension-messaging/src/errors.test.ts`); `packages/extension/src/wallet/base/zod-helpers.test.ts`; `packages/extension/src/wallet/services/pxe/chain-runtime.test.ts`; `packages/extension/src/wallet/services/pxe/artifact-registry.test.ts`; unused in-package harness `packages/extension-messaging/src/testing/setup.ts`.

## F6: The `(profileId, chainId)` composite key and the `pxe/<profile>/<chain>` DB-name scheme are stringly-typed conventions interpolated at seven sites across two classes

1. **Title:** Two implicit string protocols — guard/registry keys and IndexedDB names — are rebuilt by hand wherever needed, including prefix-scan deletions that must match byte-for-byte.
2. **Smell name:** Primitive Obsession (Fowler, Bloaters) escalating to Shotgun Surgery: changing either format requires finding every interpolation and every `startsWith` scan.
3. **Impact bucket:** structural. Blast radius: 2 files, 7+ sites, plus the on-disk DB names themselves (a format change orphans existing DBs unless every site moves together). Change frequency: `service.ts` touched in 2 of 6 recent commits; the per-profile cascade (the prefix scans) is Phase 2 work.
4. **Evidence:** `${profileId}:${chainId}` built independently in `PxeService.chainKey` (`packages/aztec-runtime/src/pxe/service.ts:102-104`) and `ChainRuntimeRegistry.key` (`pxe/chain-runtime.ts:188-190`); the matching `` `${profileId}:` `` prefix-scan deletion loop duplicated at `service.ts:478-481` (chainGuards) and `chain-runtime.ts:264-277` (`disposeProfile`). The DB-name scheme `pxe/${profileId}/${chainId}` is written by `ProductionPxeFactory` as `dataDirectory` (`chain-runtime.ts:108`) and independently reconstructed for deletion in `clearChainState` (`service.ts:415`), as the prefix `` `pxe/${profile.id}/` `` in `onProfileDeleted` (`service.ts:488`) and the orphan scan (`service.ts:128,132`). The writer (factory) and the deleters (service) share no helper — the contract is "the strings happen to match".
5. **Why it harms future change:** any evolution of the keying scheme (e.g. adding a network slug, or namespacing DBs per Week-4 memory policy already flagged in the file's own comments) is a seven-site simultaneous edit across two classes where a missed `startsWith` site fails silently — cleanup loops just stop matching, leaking guards or DBs.
6. **Smallest safe refactoring:** Extract Class (a tiny `pxe-keys.ts` module): `chainKey(profileId, chainId)`, `profileKeyPrefix(profileId)`, `pxeDbName(profileId, chainId)`, `pxeDbPrefix(profileId)`, `PXE_DB_ROOT`. Both classes import it; the prefix scans call the same prefix function the writers used.
7. **What disappears:** the byte-for-byte string coupling between `PxeService` and `ChainRuntime(Registry)`, the duplicated prefix-scan loops' format knowledge, and the silent-mismatch failure mode.
8. **Instances:** `packages/aztec-runtime/src/pxe/service.ts:102-104,128,132,415,478-481,488`; `packages/aztec-runtime/src/pxe/chain-runtime.ts:108,188-190,264-277`.

## F7: PxeService inline duplication families (deleteDatabase wrapper ×3, withPxeRead/Write twins, SYNC-DEBUG block ×2)

3. **Impact bucket:** local (one file). Blast radius: 1 file, 8 sites. Change frequency: 2 of 6 recent commits — the most-edited file in the cluster.

## F8: Three hand-rolled "cached promise with reset-on-failure" lazy-init idioms, synchronized by comment

1. **Title:** The same lazy-init-with-retry-reset concurrency idiom is implemented three ways in three files, with a comment instead of a shared function keeping them aligned.
2. **Smell name:** Duplicate Code with sync-by-comment (named analog of Fowler's Duplicate Code; the comment "matches ArtifactRegistry pattern" is Comments-as-deodorant for the missing extraction).
3. **Impact bucket:** local/structural. Blast radius: 3 files in one package. Change frequency: dormant since import.
4. **Evidence:** (1) `ArtifactRegistry.ensureKnown` — `initPromise` field, `.catch` resets to null, result stored separately (`packages/aztec-runtime/src/pxe/artifact-registry.ts:99-112`); (2) `loadProductionNoteSchemas` — module-level `cachedSchemas` promise, caller-side try/catch resets to null, with the literal comment "Allow retry after transient failure (matches ArtifactRegistry pattern)" (`pxe/note-schemas.ts:64-94`); (3) `ChainRuntimeRegistry.getOrInit` — keyed `initPromises` map, `.then` deletes entry, `.catch` deletes entry and rethrows (`pxe/chain-runtime.ts:214-229`). Three structurally different encodings of one invariant (concurrent callers share the in-flight promise; failure resets so the next caller retries).
5. **Why it harms future change:** the invariant is easy to break in any one copy (e.g. forgetting the failure-reset reintroduces a poisoned-cache bug); a reviewer must re-verify the subtle promise lifecycle per copy because the encodings differ; the comment is the only thing tying copy 2 to copy 1 and goes stale on the first divergence.
6. **Smallest safe refactoring:** Extract Function — a `lazyInit<T>(loader): () => Promise<T>` (and a keyed `LazyInitMap<K, T>` for the registry case) in `@nulo/wallet-core/utils`, with the retry-reset semantics tested once.
7. **What disappears:** three bespoke promise lifecycles, the sync-by-comment, and the per-copy review burden on a known-tricky idiom.
8. **Instances:** `packages/aztec-runtime/src/pxe/artifact-registry.ts:99-112`; `packages/aztec-runtime/src/pxe/note-schemas.ts:64-94`; `packages/aztec-runtime/src/pxe/chain-runtime.ts:214-229`.

## F9: Dead and speculative export surface (verified case-by-case)

1. **Title:** A family of exports with zero (or test-only) consumers, one duplicated magic string, and one name-colliding constant pad the packages' public surface.
2. **Smell name:** Dead Code + Speculative Generality (Fowler, Dispensables); the keepalive literal is Config Sprawl (the same constant duplicated across packages, one copy dead).
3. **Impact bucket:** local/cosmetic per item; aggregate cost is API-surface noise on packages whose whole point is a tight contract. Blast radius: 6 sites across 3 packages. Change frequency: dormant.
4. **Evidence (each grep-verified, no DI/auto-import coverage — these are workspace-package exports, and the extension auto-imports only its own `src/` dirs):**
   - `_resetNoteSchemasForTests` (`packages/aztec-runtime/src/pxe/note-schemas.ts:97-99`, re-exported `pxe/index.ts:7`): **zero call sites anywhere, including tests.**
   - `ChainRuntimeRegistry.peek()` (`pxe/chain-runtime.ts:195-197`): callers are exclusively `packages/extension/src/wallet/services/pxe/chain-runtime.test.ts` — production code never peeks.
   - `isAllowedRpcUrl` (`adapters/aztec-node-factory-adapter.ts:32`): doc says "exportable for other call sites"; not re-exported by `adapters/index.ts`; zero external refs — speculative export.
   - `OFFSCREEN_KEEPALIVE` (`packages/extension/src/wallet/utils/offscreen.ts:4`): zero importers, while the live keepalive literal is privately re-declared as `KEEPALIVE_MESSAGE = "OFFSCREEN_KEEPALIVE"` in `packages/extension-messaging/src/offscreen/service.ts:13` — a dead export AND a cross-package duplicate of the same magic string.
   - `ArtifactRegistry`'s second `NetworkInfo` (`pxe/artifact-registry.ts:13-17`) + the unused `_network` parameter on `resolve()` (`:162`): "kept on the API for future per-chain policy hooks even though the current resolver doesn't read it" — textbook Speculative Generality, and the name collides with the *different-shaped* `NetworkInfo` in `chain-runtime.ts:42-46`, so imports in `service.ts` resolve by path, not by name.
   - `DEFAULT_REQUEST_TIMEOUT_MS` exported with **different values from two sibling packages**: 60 000 in `packages/aztec-runtime/src/utils/fetch.ts:18` (HTTP fetch) vs 90 000 in `packages/extension-messaging/src/offscreen/client.ts:20` (RPC) — identical name, different meaning; an autocomplete-level import mistake type-checks fine.
5. **Why it harms future change:** dead exports must be read, typechecked, and considered on every API review; the speculative `_network` parameter forces every `resolve()` caller to thread an argument nothing consumes; the keepalive duplicate invites "fix one, miss one" if the literal ever needs to change; the colliding timeout constants are a latent wrong-import trap.

7. **What disappears:** six items of API noise, one unused threaded parameter, one cross-package magic-string duplicate, one name-collision trap.
