## F1: Async edit forms outgrow `useFormState` and reimplement their own baselines
1. Title: Async edit popups hand-roll baseline, dirty-state, and reset behavior around `useFormState`.
2. Smell name: Duplicate Code, with a Shotgun Surgery mapping. `useFormState` only knows constructor-time `initial` values, so every popup that loads an entity asynchronously rebuilds the same “hydrate fields, detect edits against loaded state, reset to loaded state” layer by hand.
3. Maintenance impact: structural; blast radius is 7 files (`useFormState` plus 6 edit popups). Change frequency is low in local history (this group shows only the initial-import commit since 2026-03-11), which lowers urgency but not the cost of the next edit-popup addition.
4. Concrete evidence: `useFormState.reset()` always restores `defs[name].initial` from setup time, and `isDirty` compares against the same immutable baseline (`packages/extension/src/composables/useFormState.ts:82`, `:113`, `:153`, `:166`). Because of that, edit popups add custom baseline loaders and custom dirty flags: `EditProfilePopup.vue:26`, `:33`, `:142`, `:171`; `EditAccountPopup.vue:33`, `:41`, `:65`, `:115`; `EditNetworkPopup.vue:43`, `:53`, `:78`, `:137`; `EditEndpointPopup.vue:37`, `:43`, `:148`; `EditFpcPopup.vue:70`, `:92`, `:298`; `EditContactPopup.vue:120`, `:126`, `:149`, `:466`.
5. Why it harms future change: any change to edit-form semantics now means updating multiple bespoke reset/dirty implementations instead of one form primitive, and the popups can drift on what “unchanged”, “reset”, or “ready to submit” means.
6. Smallest safe refactoring: Extract/Move Function into `useFormState` by adding a `rebase()`/`setInitialValues()` API and using the composable’s own dirty tracking for loaded entities.
7. What disappears: the repeated `handleFillFieldsWithDefaultValues`/`fillFromEndpoint` helpers, custom `isStartedEditing*` flags, and per-popup reset buttons that exist only to compensate for the missing async baseline abstraction.
8. Instances: `packages/extension/src/composables/useFormState.ts:82`, `:113`, `:153`, `:166`; `packages/extension/src/popup/components/popups/EditProfilePopup.vue:26`, `:33`, `:142`, `:171`; `EditAccountPopup.vue:33`, `:41`, `:65`, `:115`; `EditNetworkPopup.vue:43`, `:53`, `:78`, `:137`; `EditEndpointPopup.vue:37`, `:43`, `:148`; `EditFpcPopup.vue:70`, `:92`, `:298`; `EditContactPopup.vue:120`, `:126`, `:149`, `:466`.

## F2: `RecentActivityView.vue` is a hotspot-sized god component
1. Title: The recent-activity widget owns too many unrelated responsibilities in one file.
2. Smell name: Large Class (Fowler bloater), with Divergent Change. The component mixes task syncing, journal syncing, incoming-transfer syncing, token lookup, feed budgeting, cancel wiring, navigation, and two render variants.
3. Maintenance impact: structural; blast radius is centered on one file but spills into 10 sibling helpers/components. Change frequency is high: `RecentActivityView.vue` has 5 local-history commits since 2026-05-19.
4. Concrete evidence: the file imports and coordinates five service clients plus multiple card types (`packages/extension/src/popup/components/modules/general/RecentActivityView.vue:11-25`); implements row budgeting/merge logic (`:77-109`); owns task enrichment and token lookup (`:120-190`); owns journal/incoming-transfer state machines and cancel cleanup (`:196-585`); and duplicates a large token/non-token render branch in the template (`:703-817`).
5. Why it harms future change: a change to any one concern, such as cancel behavior, incoming-transfer rendering, token scoping, or archive-link presentation, forces editing the same large file and revalidating unrelated behavior packed into it.
6. Smallest safe refactoring: Extract Composable for the data pipeline (`tasks`/`journal`/`incoming`/`cancel`) and Extract Component for the repeated activity-list rendering branch.
7. What disappears: service-listener sprawl from the view component, duplicated token/non-token list markup, and the single-file coupling between data acquisition, row policy, and rendering.
8. Instances: `packages/extension/src/popup/components/modules/general/RecentActivityView.vue:11`, `:77`, `:120`, `:196`, `:333`, `:472`, `:654`, `:703`, `:767`.

## F3: Onboarding reaches into popup-only passkey UI internals
1. Title: Onboarding pages depend directly on a popup-layer dialog with popup DOM assumptions.
2. Smell name: Inappropriate Intimacy (Fowler coupler), plus boundary-erosion analog. The onboarding flow imports a popup component that itself imports popup-only utilities and teleports into `#popup`, so onboarding is coupled to popup implementation details instead of a shared passkey overlay abstraction.
3. Maintenance impact: architectural; blast radius is 3 files across two entrypoints. Change frequency is moderate: the popup/onboarding import-create group shows 4 commits since 2026-05-20.
4. Concrete evidence: both onboarding pages import `PasskeyCeremonyDialog` from `@/popup/components/popups/PasskeyCeremonyDialog.vue` (`packages/extension/src/onboarding/pages/import.vue:10`, `packages/extension/src/onboarding/pages/create.vue:8`) and render it (`import.vue:470`, `create.vue:263`). The dialog itself documents popup-specific usage, imports `@/popup/utils/passkey-ceremony`, and teleports to `#popup` (`packages/extension/src/popup/components/popups/PasskeyCeremonyDialog.vue:10-14`, `:31`, `:82`).
5. Why it harms future change: changing the popup overlay host, popup passkey helper path, or dialog mounting contract now risks silently breaking onboarding, even though onboarding is a separate shell.
6. Smallest safe refactoring: Move Function/Extract Component into a shared entrypoint-neutral passkey overlay module, then have popup and onboarding each host it through their own shell adapter.
7. What disappears: the hidden `#popup` contract crossing entrypoints, popup-path imports from onboarding, and the need for onboarding pages to know popup dialog internals.
8. Instances: `packages/extension/src/onboarding/pages/import.vue:10`, `:470`; `packages/extension/src/onboarding/pages/create.vue:8`, `:263`; `packages/extension/src/popup/components/popups/PasskeyCeremonyDialog.vue:10`, `:31`, `:82`.

## F4: Popup and onboarding profile flows are maintained as parallel implementations
1. Title: Import/create orchestration is duplicated across popup and onboarding shells.
2. Smell name: Duplicate Code, with a Divergent Change mapping. The same profile-name validation, passkey ceremony wiring, profile creation/import orchestration, and completion flow are mirrored in separate popup and onboarding pages.
3. Maintenance impact: structural; blast radius is 4 large page files plus the shared dialog. Change frequency is moderate-to-high: both popup-side files and onboarding-side files each show 4 recent commits since 2026-05-19/20, indicating synchronized edits.
4. Concrete evidence: the import pair both wire `useToast`, `useFullBackupImport`, `usePasskeyCeremony`, `useProfileNameField`, per-method import handlers, and `completeImport` flow (`packages/extension/src/popup/pages/import.vue:21-255`, `packages/extension/src/onboarding/pages/import.vue:13-256`). The create pair both wire `usePasskeyCeremony`, `useProfileNameField`, `createPasskeyProfileWithRetry`, existing-name validation, and create-submit handling (`packages/extension/src/popup/pages/profile/new.vue:17-175`, `packages/extension/src/onboarding/pages/create.vue:10-136`).
5. Why it harms future change: every adjustment to profile-name rules, passkey cancellation handling, success routing, or import/create preflight checks must be replicated across two shells, which is exactly how logic drift starts.
6. Smallest safe refactoring: Extract shared flow composables such as `useProfileImportFlow` and `useProfileCreateFlow`, leaving each page to provide only shell-specific routing, copy, and error presentation.
7. What disappears: duplicated handler trees, duplicated existing-name checks, duplicated passkey ceremony orchestration, and the need to keep popup/onboarding behavior aligned manually.
8. Instances: `packages/extension/src/popup/pages/import.vue:21`, `:148`, `:167`, `:185`, `:211`, `:242`; `packages/extension/src/onboarding/pages/import.vue:13`, `:110`, `:134`, `:154`, `:177`, `:204`; `packages/extension/src/popup/pages/profile/new.vue:17`, `:61`, `:89`, `:95`, `:104`; `packages/extension/src/onboarding/pages/create.vue:10`, `:40`, `:73`, `:77`, `:85`.

## F5: Account-state pages repeat the same list-page scaffold four times
1. Title: Authwits, contracts, notes, and senders each copy the same fetch/error/empty-state page skeleton.
2. Smell name: Duplicate Code, mapped to Shotgun Surgery. A single account-state list-page convention change would require touching four separate pages because the data-loading and list-shell patterns are copied instead of parameterized.
3. Maintenance impact: structural; blast radius is 4 pages. Change frequency is low in local history (0 touches since 2026-03-11 beyond the initial import), so this is lower priority than the activity and onboarding findings.
4. Concrete evidence: all four pages own their own fetch/watch/disconnect lifecycle and the same loading/error/empty template scaffold: `authwits/index.vue` uses `useEntityCrud` plus `handleRefetch`, `watch`, `onMounted`, `onBeforeUnmount`, and `LoadingState`/`Tooltip`/`Banner`/empty state (`packages/extension/src/popup/pages/settings/advanced/account-state/authwits/index.vue:40-53`, `:73-121`, `:124-197`); `contracts/index.vue` repeats the same shape manually (`contracts/index.vue:23-58`, `:61-110`); `notes/index.vue` repeats it around a richer row mapper (`notes/index.vue:111-131`, `:184-224`); `senders/index.vue` repeats it with a different entity source (`senders/index.vue:34-44`, `:71-79`, `:82-155`).
5. Why it harms future change: a change to retry UX, loading wording, empty-state chrome, or account/network refresh triggers has to be propagated manually across multiple pages that are supposed to feel like one family.
6. Smallest safe refactoring: Extract Component for a generic `AccountStateListPage` shell plus optional hook/composable slots for fetch, filter, row rendering, and trailing actions.
7. What disappears: repeated `LoadingState`/`Banner`/empty-state blocks, repeated watch/mount/disconnect lifecycle code, and per-page divergence in what should be a consistent account-state list experience.
8. Instances: `packages/extension/src/popup/pages/settings/advanced/account-state/authwits/index.vue:40`, `:73`, `:124`; `contracts/index.vue:23`, `:45`, `:61`; `notes/index.vue:111`, `:184`, `:200`; `senders/index.vue:34`, `:71`, `:82`.
