## F1: Hidden startup ordering still depends on polling instead of declared dependencies
1. Title: Hidden startup ordering still depends on polling instead of declared dependencies.
2. Smell name: Temporal coupling (close analog to Shotgun Surgery). These services must become usable in a specific order, but that order is implicit in `init()` lookups and backstopped by `ensureInitialized()` polling rather than explicit dependency declarations.
3. Maintenance impact: architectural; blast radius: 10 scoped files plus the composition root; change frequency: moderate over the last 3 months (`token` 3 commits, `profile` 3, `network` 2, `runtime` 2, the other participating files 1 each).
4. Concrete evidence: `runtime.ts` says registration order is only visual and startup order comes from topological phases (`packages/extension/src/wallet/runtime.ts:105-109`), but among scoped services only `ContactService` declares `dependencies` (`packages/extension/src/wallet/services/contact/service.ts:18-19`). The other audited services still pull collaborators in `init()` without declaring them: `account/service.ts:31-35`, `dapp-session/service.ts:38-40`, `auth-registry/service.ts:44-50`, `fpc/service.ts:59-64`, `token/service.ts:56-64`, `transaction/service.ts:48-55`, `network/service.ts:159-163`, `profile/service.ts:69-81`. The fallback contract is a 30s poll loop in `packages/extension-messaging/src/background/service.ts:187-199`. The mismatch is already visible in registration order: `AuthRegistryService` is added before `ExecutionService`, `TaskService`, and `TransactionService` (`runtime.ts:112,118,126,129`), and `ProfileService` is added before `PasskeyService` (`runtime.ts:125,131`).
5. Why it harms future change: adding one real init-time call between collaborators turns into a graph-wide coordination problem: the author has to discover hidden ordering, update unrelated services, and otherwise gets a timeout-driven failure mode instead of an explicit dependency error.
6. Smallest safe refactoring: introduce explicit `dependencies` arrays for each service that reads collaborators in `init()` (named analog: replace implicit dependency with explicit dependency), then keep `init()` work phase-ordered by that declaration.
7. What disappears: implicit phase-order assumptions, manual reasoning about `runtime.ts` registration order, and `ensureInitialized()` acting as de facto dependency management.
8. Instances: `packages/extension/src/wallet/runtime.ts:105-125,131`; `packages/extension-messaging/src/background/service.ts:187-199`; `packages/extension/src/wallet/services/contact/service.ts:18-19,42-44`; `packages/extension/src/wallet/services/account/service.ts:31-35`; `packages/extension/src/wallet/services/dapp-session/service.ts:38-40`; `packages/extension/src/wallet/services/auth-registry/service.ts:44-50`; `packages/extension/src/wallet/services/fpc/service.ts:59-64`; `packages/extension/src/wallet/services/token/service.ts:56-64`; `packages/extension/src/wallet/services/transaction/service.ts:48-55`; `packages/extension/src/wallet/services/network/service.ts:159-163`; `packages/extension/src/wallet/services/profile/service.ts:69-81`.

## F2: Backup and restore contract is hand-coded across nine services
1. Title: Backup and restore contract is hand-coded across nine services.
2. Smell name: Duplicate Code. This is also a form of Shotgun Surgery because changing backup/restore reporting, collision handling, or error-shaping requires touching many unrelated services.
3. Maintenance impact: structural; blast radius: 9 scoped service files; change frequency: moderate (`token` 3 commits, `profile` 3, `network` 2, the other participating files 1 each in the last 3 months).
4. Concrete evidence: eight services repeat the same restore scaffold: initialize if needed, allocate `result`, iterate items, persist, and push either the restored item or `{...item, restoreError}`: `token/service.ts:532-555`, `transaction/service.ts:302-320`, `contact/service.ts:290-314`, `config/service.ts:43-58`, `network/service.ts:614-652`, `fpc/service.ts:470-519`, `auth-registry/service.ts:285-309`, `account/service.ts:213-230`. `ProfileService` keeps the same contract in singleton form, returning either restored profile info or `{...profile, restoreError}` in `profile/service.ts:830-963`. The paired export wrappers are also reimplemented service-by-service in `token/service.ts:523-529`, `transaction/service.ts:279-299`, `contact/service.ts:286-287`, `config/service.ts:39-40`, `network/service.ts:604-605`, `fpc/service.ts:463-467`, `auth-registry/service.ts:262-282`, `account/service.ts:204-210`, `profile/service.ts:826-827`.
5. Why it harms future change: a shared change like adding backup version metadata, standardizing duplicate-id behavior, instrumenting partial failures, or changing `restoreError` shape fans out into nine implementations with subtly different lock, id-allocation, and validation behavior.
6. Smallest safe refactoring: extract a shared `restoreAll` helper/template (Fowler: Extract Method; cross-class analog: Form Template Method) that owns result accumulation and error wrapping, with per-service callbacks for validation, key generation, and persistence.
7. What disappears: repeated `result` arrays, per-item try/catch wrappers, id-collision loops, and one-off export wrappers cluttering each service body.
8. Instances: `packages/extension/src/wallet/services/token/service.ts:523-555`; `packages/extension/src/wallet/services/transaction/service.ts:279-320`; `packages/extension/src/wallet/services/contact/service.ts:286-314`; `packages/extension/src/wallet/services/config/service.ts:39-58`; `packages/extension/src/wallet/services/network/service.ts:604-652`; `packages/extension/src/wallet/services/fpc/service.ts:463-519`; `packages/extension/src/wallet/services/auth-registry/service.ts:262-309`; `packages/extension/src/wallet/services/account/service.ts:204-230`; `packages/extension/src/wallet/services/profile/service.ts:826-963`.

## F3: Profile-deletion cleanup policy is scattered across six listeners
1. Title: Profile-deletion cleanup policy is scattered across six listeners.
2. Smell name: Duplicate Code. It also maps to Shotgun Surgery because one lifecycle event (`onProfileDeleted`) requires coordinated edits in many services to change teardown behavior.
3. Maintenance impact: structural; blast radius: 6 scoped service files plus the emitting profile service; change frequency: moderate (`token` 3 commits, `network` 2, the other participating files 1 each in the last 3 months).
4. Concrete evidence: six services each reimplement “find rows for `profileId`, delete them, emit per-row deletion events”: `account/service.ts:194-202`, `contact/service.ts:256-270`, `dapp-session/service.ts:325-336`, `fpc/service.ts:447-461`, `network/service.ts:671-690`, `token/service.ts:515-521`. The variations are ad hoc rather than abstracted: `account/service.ts` has no lock, `token/service.ts` delegates to `deleteToken()`, and `network/service.ts` also runs `purgeChain()` and removes the active-network key. `ProfileService.deleteProfile()` itself only emits the event and depends on all of these listeners for the real cleanup (`profile/service.ts:530-556`).
5. Why it harms future change: changing profile-teardown ordering, batching, telemetry, lock discipline, or failure handling means touching six separate listeners and re-verifying their cascades by hand.
6. Smallest safe refactoring: introduce a shared `purgeByProfile` helper or `ProfileScopedEntityStore` (analog to Form Template Method), then move service-specific extras like `NetworkService.purgeChain()` into narrow callbacks.
7. What disappears: repeated filter-delete-emit loops, inconsistent locking/error patterns, and the need to rediscover profile-cleanup rules in every service.
8. Instances: `packages/extension/src/wallet/services/account/service.ts:194-202`; `packages/extension/src/wallet/services/contact/service.ts:256-270`; `packages/extension/src/wallet/services/dapp-session/service.ts:325-336`; `packages/extension/src/wallet/services/fpc/service.ts:447-461`; `packages/extension/src/wallet/services/network/service.ts:671-690`; `packages/extension/src/wallet/services/token/service.ts:515-521`; emitter context `packages/extension/src/wallet/services/profile/service.ts:530-556`.

## F4: Storage backend choice is duplicated across constructors and raw call sites
1. Title: Storage backend choice is duplicated across constructors and raw call sites.
2. Smell name: Config sprawl (close analog to Shotgun Surgery). The same infrastructure choice, “use injected `browserApi.storage` or fall back to raw `chrome.storage`,” is encoded in many constructors and helper methods instead of one composition point.
3. Maintenance impact: architectural; blast radius: 10 scoped files plus the runtime composition root; change frequency: moderate (`profile` 3 commits, `token` 3, `runtime` 2, `network` 2, the others 1 each in the last 3 months).
4. Concrete evidence: `runtime.ts` explicitly calls out a split migration where some services accept `browserApi` and others still use `chrome.*` directly (`packages/extension/src/wallet/runtime.ts:105-125`). `ContactService`, `ProfileRepository`, and `SessionManager` each hand-roll the same fallback ternary (`contact/service.ts:35-39`, `profile/repository.ts:42-45`, `profile/session-manager.ts:130-132`). At the same time, other scoped services hard-code storage ownership: `token/service.ts:42`, `transaction/service.ts:36`, `network/service.ts:143,687,751-758`, `fpc/service.ts:43`, `auth-registry/service.ts:29-30`, `account/service.ts:23`, `dapp-session/service.ts:29`. The composition root only passes `browserApi` to `ContactService` and `ProfileService`, not to the other storage-owning services (`runtime.ts:115,125` vs. `110-124,126-127`).
5. Why it harms future change: finishing the ports migration, swapping storage areas in tests, or adding cross-cutting storage instrumentation requires constructor-signature edits in runtime plus one-off cleanup in every service that currently knows about `chrome.storage`.
6. Smallest safe refactoring: introduce a shared storage-factory/parameter object from `runtime.ts` (Fowler: Replace Constructor Logic with Factory Function; plus Introduce Parameter Object), then move direct `chrome.storage.*` access behind that factory.
7. What disappears: per-service fallback ternaries, constructor divergence, and raw `chrome.storage` knowledge spread through service code.
8. Instances: `packages/extension/src/wallet/runtime.ts:105-125`; `packages/extension/src/wallet/services/contact/service.ts:35-39`; `packages/extension/src/wallet/services/profile/repository.ts:42-45`; `packages/extension/src/wallet/services/profile/session-manager.ts:130-132`; `packages/extension/src/wallet/services/token/service.ts:42`; `packages/extension/src/wallet/services/transaction/service.ts:36`; `packages/extension/src/wallet/services/network/service.ts:143,687,751-758`; `packages/extension/src/wallet/services/fpc/service.ts:43`; `packages/extension/src/wallet/services/auth-registry/service.ts:29-30`; `packages/extension/src/wallet/services/account/service.ts:23`; `packages/extension/src/wallet/services/dapp-session/service.ts:29`.

## F5: ProfileService is a large class mixing CRUD, session, crypto, passkey, and backup flows
1. Title: ProfileService is a large class mixing CRUD, session, crypto, passkey, and backup flows.
2. Smell name: Large Class (Fowler), with Divergent Change tendencies because unrelated profile concerns already cohabit one file and one state object.
3. Maintenance impact: structural; blast radius: primarily one high-centrality file; change frequency: high for a single file in this cluster (`packages/extension/src/wallet/services/profile/service.ts` changed 3 times in the last 3 months).
4. Concrete evidence: the class owns storage/session collaborators and restore-only state at `profile/service.ts:22-67`; startup restore logic at `69-81`; password unlock orchestration at `144-202`; passkey/WebAuthn profile creation at `214-240`; destructive profile deletion plus rollback cleanup at `530-556`; import/export logic at `564-746`; full-backup restore at `830-975`; and finalize-restore session activation at `997-1045`. The public surface is also broad: more than 20 public methods span CRUD, crypto, passkey ceremony coordination, session lifecycle, import/export, and backup restore (`profile/service.ts:87-997`).
5. Why it harms future change: changing one axis of behavior, like session TTL handling, password flows, passkey recovery, or backup import, forces edits in the same 1k-line facade and increases the chance of incidental regressions in unrelated profile responsibilities. `pendingRestoreSecrets` already couples import-time restore behavior to later session activation.
6. Smallest safe refactoring: Extract Class first for backup/import/export/finalize flows, then Move Function for unlock/session-specific operations into a narrower session-focused collaborator.
7. What disappears: restore/import-specific state from the main facade, mixed crypto/session/UI-ceremony orchestration in one class, and the need to touch the same large file for unrelated profile changes.
8. Instances: `packages/extension/src/wallet/services/profile/service.ts:22-67`; `69-81`; `144-202`; `214-240`; `530-556`; `564-746`; `830-975`; `997-1045`.

## Non-findings
- `packages/extension/src/wallet/services/dapp-session/capability-meta.ts` is a deliberate single-source metadata/sanitizer module; I did not find duplicated logic or change amplification there.
- Repeated `new PxeServiceClient(this.logger)` calls in the scoped services are real repetition, but today they are a one-line construction with no drifted behavior; F4 is the broader infrastructure-wiring smell.
- The added/updated/deleted event triples across services are repetitive, but in this cluster the measurable maintenance cost comes from the duplicated teardown implementations in F3, not from the event field declarations themselves.
- `ConfigService` is thin, but I did not flag it as `Lazy Class` because the `spec/service/client` RPC boundary is a house convention and the concrete duplication cost is already captured by F2.
