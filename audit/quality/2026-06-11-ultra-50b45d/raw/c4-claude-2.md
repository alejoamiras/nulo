## F1: Popup and onboarding import/create pages are ~450-line parallel implementations

1. **Title**: Popup vs onboarding import + create page twins.
2. **Smell name**: Duplicate Code (Fowler), escalating to Shotgun Surgery — any change to an import path (new error kind, validation tweak, copy change) must be applied in two page shells that share no code beyond the L3 form components.
3. **Impact bucket**: architectural. Blast radius: 4 files (`src/popup/pages/import.vue` 668 LOC, `src/onboarding/pages/import.vue` 540 LOC, `src/popup/pages/profile/new.vue` 397 LOC, `src/onboarding/pages/create.vue` 377 LOC) + the 3 shared composables whose wiring is duplicated. Change frequency: high — git shows 4 changes each to `popup/pages/import.vue`, `onboarding/pages/import.vue`, `onboarding/pages/create.vue` in 3 months; all four are size outliers in the repo map.
4. **Evidence** (import pair):
   - `error` ref + `fillError`/`clearError`/`handleCopyError`/`handlePasswordInput`/`handleSecretInput`: `popup/pages/import.vue:92-118` vs `onboarding/pages/import.vue:62-88` — near-verbatim (popup is JS, onboarding is TS; logic identical).
   - `isAllowedToContinue`/`isAllowedToImportBySeedPhrase`/`ByPrivateKey`/`ByPublicKey`: `popup/pages/import.vue:122-138` vs `onboarding/pages/import.vue:92-108` — verbatim including the "Excludes the name check on purpose" comment.
   - `handleImportSeed`/`PrivateKey`/`PublicKey`/`Passkey`: `popup/pages/import.vue:167-276` vs `onboarding/pages/import.vue:134-234` — same latch/getProfiles/validateName/try-catch shape; the stringly-typed error→field mapping (`err.message === "Invalid secret length"` → `secret`, `"Invalid password"` → `password`) is duplicated in 4 handler bodies across the two files (`popup:201-205`, `popup:227-233`, `onboarding:167-171`, `onboarding:190-196`). Changing the service-side error string requires touching all four plus the service.
   - `useFullBackupImport` 13-field destructured wiring: `popup/pages/import.vue:279-315` vs `onboarding/pages/import.vue:236-274`; `parsedBackupName` guarded-prefill watch verbatim incl. comment: `popup:321-323` vs `onboarding:280-282`; `clearFormState`/`handleBack`: `popup:327-340` vs `onboarding:284-297`.
   - Template CTA stacks (decrypt/restore/continue/view-errors + per-method submit buttons): `popup/pages/import.vue:459-540` vs `onboarding/pages/import.vue:385-468` — parallel `v-if` ladders over the same state machine. `shakeInput` keyframes duplicated in all four files' styles (`popup/import:656-667`, `onboarding/import:528-539`, `profile/new:385-396`, `onboarding/create:365-376`).
   - (create pair): `handleCreate` vs `handleSubmit` — `popup/pages/profile/new.vue:104-175` vs `onboarding/pages/create.vue:85-136`: identical latch comment, identical `UserRejectedError` silent return, byte-identical notification payload (description + "Windows Hello" note), identical `createPasskeyProfileViaModal` wrapper (`profile/new:95-101` vs `create:77-83`). Divergence: post-create bootstrap is hand-rolled in `profile/new.vue:153-170` (`while (!appStore.isLogined) await sleep(100)` + manual `AccountServiceClient` + `initTransactionService`) while `create.vue:130` calls `useProfileBootstrap` — whose own doc (`src/composables/useProfileBootstrap.ts:2-5`) claims "Both the popup and the onboarding tab call this so the same orchestration runs in both shells". The popup create page does not.
5. **Why it harms future change**: every new import method, every error-kind addition, every fix to the latch/validate ordering is a 2-file (sometimes 4-file) edit with no compiler or test pressure to keep the copies aligned. The pair has already drifted in toast copy ("Profile imported — unlock to continue" vs "Profile imported. Unlock to continue."), notification title casing ("Profile Import Failed" vs "Profile import failed"), and bootstrap strategy — drift that is invisible until a user hits the divergent shell.
6. **Smallest safe refactoring**: Extract Function (Fowler) into composables — `useProfileImportFlow({ completeImport, showErrorLog })` owning the handlers + computeds + error mapping, and `useProfileCreateFlow({ onCreated })` for the create pair. The shells keep only routing, hero markup, and shell-specific completion. The error→field mapping becomes one function consumed by both.
7. **What disappears**: ~350 lines of duplicated script logic, the 4-site stringly-typed error mapping, the per-shell drift surface for toasts/notifications, and the third hand-rolled bootstrap variant in `profile/new.vue`.
8. **Instances**: `src/popup/pages/import.vue:92-138,167-276,279-340,459-540,656-667`; `src/onboarding/pages/import.vue:62-108,134-234,236-297,385-468,528-539`; `src/popup/pages/profile/new.vue:95-175,385-396`; `src/onboarding/pages/create.vue:77-136,365-376`.

## F5: Dead `displaceIdx` computeds in 8 popups + one prop name with two meanings

1. **Title**: Leftover `displaceIdx` computeds after the FormPopup migration; `displaceIdx` means `order` in one component and `len - order` in another.

3. **Impact bucket**: local (dead code) / structural (prop semantics). Blast radius: 8 files with dead computeds; every popup author must re-derive which semantics each consumer expects. Change frequency: low per file, but the popups directory as a whole changes monthly.
4. **Evidence**: each of these defines `displaceIdx` (`popupStore.len - popupStore.popups.X?.order`) and never references it — their templates pass `popupStore.popups.X?.order` straight to FormPopup: `NewContactPopup.vue:19` (template `:199`), `EditContactPopup.vue:21` (`:363`), `NewAccountPopup.vue:17` (`:96`), `EditAccountPopup.vue:14` (`:86`), `NewEndpointPopup.vue:17` (`:86`), `EditEndpointPopup.vue:17` (`:106`), `NewNetworkPopup.vue:15` (`:125`), `EditNetworkPopup.vue:14` (`:99`). Meanwhile hand-rolled popups (e.g. `SelectFpcPopup.vue:100-101`, `ConfirmPopup.vue:84-85`) pass `order` to `Popup` and the `len - order` computed to `PopupCard` — confirming the two-semantics split (`src/components/Popup/Popup.vue:48` uses it for z-index; `src/components/Popup/PopupCard.vue:19-21` uses it for stack displacement).
   Related dead CSS from the same copy-then-trim workflow: `.token` rule unused in `SelectTokenPopup.vue:104-121` and `SelectProfilePopup.vue:148-165` (both templates render `SettingItem`, never `$style.token`).
5. **Why it harms future change**: the dead computeds advertise a binding that doesn't exist — an author "fixing" stacking by editing the computed changes nothing; the dual semantics behind one prop name makes every new popup a coin-flip (FormPopup-based popups currently hand `PopupCard` an `order` where hand-rolled ones hand it `len - order`, so the displacement visual differs by construction path).
6. **Smallest safe refactoring**: Remove Dead Code (Fowler) for the 8 computeds + 2 CSS rules; then Rename Variable/normalize — make `FormPopup` (single owner) compute `len - order` internally from a passed `order`, or give the two props distinct names so the contract is visible at the call site.
7. **What disappears**: 8 misleading computeds, 2 dead CSS blocks, and the order-vs-displacement ambiguity for every future popup.
8. **Instances**: `src/popup/components/popups/NewContactPopup.vue:19-21`; `EditContactPopup.vue:21-23`; `NewAccountPopup.vue:17-19`; `EditAccountPopup.vue:14-16`; `NewEndpointPopup.vue:17`; `EditEndpointPopup.vue:17`; `NewNetworkPopup.vue:15-17`; `EditNetworkPopup.vue:14-16`; `SelectTokenPopup.vue:104-121`; `SelectProfilePopup.vue:148-165`; `src/components/composite/FormPopup.vue:21-22`.

## F7: useFormState's submit-gating API is used by nobody; every consumer re-derives it

1. **Title**: `useFormState` exposes `isValid`/`isDirty`/`touched`/`touch`/`touchAll`/`values` — zero production consumers; 10 popups hand-roll `isAvailableToX` instead.
2. **Smell name**: Speculative Generality (Fowler) on the composable + Duplicate Code in the consumers. The TSDoc also references a component that does not exist ("Used by `EntityForm`", `useFormState.ts:56` — `find src -iname "*entityform*"` returns nothing).

4. **Evidence**: `grep -rn "\.isValid|\.isDirty|touchAll|\.touched|\.touch()"` across `src/**/*.vue` (non-test) returns **zero** hits; the API is exercised only by `useFormState.test.ts`. 5. **Why it harms future change**: the composable advertises capabilities that silently don't match the house validation convention — a new popup author who trusts `isValid` ships a submit button enabled on empty forms; meanwhile the 10 hand-rolled predicates are 10 places to update when gating semantics change (e.g. adding touched-based error display).
6. **Smallest safe refactoring**: two options, pick one: (a) Remove Dead Code — delete `touched`/`touch`/`touchAll`/`values` and document `isValid`'s empty-form caveat; or (b) close the gap — add a `required?: boolean` (or `submittable` computed combining non-empty + no-error) to `FieldDef` and migrate consumers' `isAvailableToX` to `form.isSubmittable` (Replace Derived Variable with Query analog). (b) removes more duplication; (a) is smaller.
7. **What disappears**: either ~80 lines of untested API surface, or 10 hand-rolled gating computeds plus their subtle inconsistencies (some check `replace(/\s/g,"")`, some `length`, some `?.length`).
8. **Instances**: `src/composables/useFormState.ts:19-52,56,160-170`; consumer predicates at `src/popup/components/popups/NewContactPopup.vue:86-92`, `EditContactPopup.vue:126-140`, `NewFpcPopup.vue:50-55`, `EditFpcPopup.vue:70-90`, `NewNetworkPopup.vue:56-62`, `NewAccountPopup.vue:36-40`, `EditAccountPopup.vue:35-40`, `NewTokenPopup.vue:52`, `EditEndpointPopup.vue:43-54`.

## F9: OperationCard's 13-branch kind ladder duplicates its payload blocks
