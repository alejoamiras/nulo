The code-quality audit, in plain words

24 independent reviewers from two model families (Fable and Codex) each combed a slice of this repo for code that is expensive to change — not bugs, not vulnerabilities, just maintenance cost. They then spent two rounds attacking each other's findings, and every claim that survived was re-checked against the actual source by one verifier from each family. 23 real issues made it through; 0 fabrications did — every invented claim died in rebuttal or verification.

The one pattern behind most of it

Someone started building the better way of doing something, got it partly adopted, and stopped. Now both the old way and the new way are live, so every change in that area is paid twice — once per shape — and comments saying "keep in sync" are the only thing holding it together. Twice, those comments are outright false: they claim an extraction happened that never did.

Five findings are direct instances of this: Q10 (half the services get their storage injected, half still grab chrome.storage themselves), Q4/Q5 (the execution-pipeline extraction that a comment claims happened but didn't), Q8 (form abstractions that don't cover the async-edit case, so every dialog re-builds the missing half), Q7 (config sharing by copy-paste, with drift already shipped), and Q13 (a PXE interface subset maintained by hand in four files with nothing checking they match).

The cheapest leverage is almost always finishing (or explicitly abandoning) the existing migration — not inventing a new abstraction.

Where to start

  1. Q1 — small surface, hot files; 2–3 days kills the whole "forgot to update one of the 7 lists" failure mode in the bridge.
  2. Q5 — extracting the shared prove→send→record tail is the first concrete, test-backed cut into the 2,302-line monster, and it makes every later cut cheaper.
  3. Q4 — keep carving that file one concern at a time; each extraction ships on its own.
  4. Q2 — stop paying every profile-screen change twice across popup and onboarding.
  5. Q3 — stop paying every messaging-layer fix twice, and decide the error-contract question once, on purpose.
  6. Q7 — roughly a day of work, and it's the only finding where the drift has already shipped (the e2e:all config silently lost settings).

Big architecture stuff

Q1Adding one wallet method means editing 7 hidden lists

The bridge keeps seven hand-written tables that all restate the same facts about each wallet method — which capability it needs, what kind of operation it is, which scope check applies. Add or reclassify a method and you're on a scavenger hunt; miss one table and nothing complains, the method just silently behaves wrong. A "keep in sync" comment is the only guard.

Shotgun Surgery via parallel registries · architectural · 3 files, 7 parallel tables · hot code · confidence: high

Fix: One MethodDescriptor registry per method; derive all seven tables from it, preserving current names and behavior exactly.

Watch out: The three nulo-schema-patch.ts copies are a deliberate, test-pinned house contract — leave them out of this — and the AUDIT F-00x security markers must survive as descriptor fields.

Q2The "create a wallet" screens exist twice — popup and onboarding each keep their own copy

The import-profile and create-profile pages were duplicated between the popup and the onboarding flow, near line-for-line — down to the same input-shake animation keyframes. Fix a validation bug in one shell and the other still has it until someone remembers. The shared passkey dialog also still lives under popup paths even though onboarding uses it too.

Duplicate Code + Inappropriate Intimacy · architectural · 5 files (4 pages + shared dialog) · hot code · confidence: moderate

Fix: Extract shared useProfileImportFlow / useProfileCreateFlow composables (the shells differ only in routes, toasts, and completion), and move the passkey dialog to a neutral shared path.

Q3The background and offscreen messaging stacks are the same code, written twice

Two RPC transport stacks — one for the background worker, one for the offscreen page — each hand-rolled the same request bookkeeping, timeouts, JSON-fallback parsing, and init-wait loop (one function is byte-identical in both). Every transport bug fix is paid twice, and the two sides even fail differently: one throws typed errors, the other plain strings.

Duplicate Code — forked transport bases · architectural · 4 files (40+ consumers behind them) · hot code · confidence: moderate

Fix: Extract shared helpers first (response decoding, timeout bookkeeping, JSON fallback, ensureInitialized); the full shared core is a later, separate step.

Watch out: Unifying the error contracts changes offscreen rejections from plain strings to typed WalletError — that's a behavior decision to make on purpose, not a refactor side effect.

Q9Services ask "am I ready yet?" ~80 times instead of declaring what they wait for

The startup system already supports declaring "I depend on service X" — but only two services use it. Everyone else pastes await this.ensureInitialized() at the top of each method, backed by a 500ms polling loop, and whether a method gets the paste is a per-method judgment call. One service has 24 copies; another has zero.

Temporal coupling + Duplicate Code · architectural · whole service fleet (16+ services) · warm code · confidence: high

Fix: Gate readiness once in the shared base service class, and separately declare real startup dependencies — not at the RPC boundary alone, because many calls are in-process.

Q10Half the services get storage handed to them; half still grab chrome.storage directly

A migration to inject infrastructure (storage, PXE client) from the composition root started and stopped midway — the runtime comment literally says remaining services "still reach into chrome.* directly until their migration lands." So a storage or PXE wiring change fans out across ~20 constructor and init sites instead of touching one file.

Half-done composition-root migration · architectural · ~20 sites across ~15 files · warm code · confidence: high

Fix: Inject one collaborator at a time from runtime.ts (storage first or PXE first), service by service — no big-bang rewrite.

Q13The PXE function list is hand-copied across four files, and nothing checks they match

The full PXE spec declares 21 methods; three other files each hand-restate an 18-method subset of it — the facade interface, the proxy delegations, and the client with its response parsing. None of it is mechanically derived and no test pins them together, so adding a method to one and forgetting another fails silently. No drift yet — but only because everyone has remembered so far.

Manual subset interface projection · architectural · 4 files · warm code · confidence: high

Fix: One canonical subset key list plus type-level assertions, so a mismatch becomes a compile error instead of a review hope.

Watch out: Full mapped-type derivation has limits — it must drop the network param and promisify, and the client's per-method zod validation can't be generated; only partial mechanization is possible.

Structure problems

Q4One 2,300-line file is the wallet's everything-drawer

ExecutionService owns transfers, journal/cancel flow, gas-balance caching, fee-estimate reuse, dApp execution, registration handlers, and Aztec RPC adapters — 13 injected collaborators in a single class. Whatever you're changing, you start by reloading this whole monster into your head, and unrelated concerns keep colliding in the same file.

Large Class with Divergent Change · structural · 1 file (the central facade) · hot code · confidence: high

Fix: Extract one cohesive concern at a time (gas-balance caching, or one pipeline), keeping the RPC surface stable — each step ships on its own.

Q5The same "prove → send → record" ending is hand-copied into all four send flows

Four send pipelines each rewrite the identical lifecycle tail: register cancellation, walk the journal stages, prove, send, save history, clean up. Worse, a comment in execution-coordinator.ts claims this tail was already extracted into a proveAndSend method — that method was never written. The doc isn't stale; it's false.

Duplicate Code · structural · 2 files (4 copies in the hottest one) · hot code · confidence: high

Fix: Extract one shared tail helper with per-path callbacks for the parts that genuinely differ, and correct the lying comment in the same change.

Q6The dashboard's activity widget rebuilt the feed logic the activity page already shares

There's a shared buildActivityRows helper that the activity page uses — and the home-screen widget re-implements the same three-way merge by hand, while the helper's comment claims the extraction covered both surfaces (it didn't). The widget also duplicates its entire template for the token/no-token cases.

Large Component + Duplicate Code · structural · 3 files · hot code · confidence: moderate

Fix: Extract useIncomingTransfers and the awaiting-card props builder, collapse the two template branches into one, and parameterize buildActivityRows so the widget can use it.

Q7Seven build/test config files copy each other by hand — and one already drifted

Vite/Vitest aliases, defines, and runner settings are duplicated across seven config files under literal "Keep in sync" comments — and the sync already failed: the e2e:all config silently lost the noir aliases and retry settings the network config has, while still covering the network suite. The browser wrappers also mutate the shared base config in place.

Config Sprawl + Mutable Data · structural · 7 files · hot enough that drift shipped · confidence: high

Fix: Shared config helpers plus mergeConfig-style composition; validate by diffing resolved configs before/after.

Watch out: The host-specific noir-alias comment has to travel with the shared helper, not get lost in the move.

Q8Every edit dialog re-invents form refill and Enter-to-submit

useFormState can't re-baseline after async data arrives, so every edit dialog hand-rolls its own refill and dirty tracking around it. FormPopup doesn't handle the Enter key, so each dialog copies the same keydown guard. The abstractions exist — they just don't cover the cases the dialogs actually have, so a dozen dialogs each carry the missing half.

Duplicate Code / half-done abstraction · structural · ~12 files · hot code · confidence: moderate

Fix: Two independent tracks: add a rebase() API to useFormState and move Enter-key ownership into FormPopup; then migrate hand-rolled list sync to useEntityCrud dialog by dialog.

Watch out: NewContactPopup's comment documents an Enter double-fire hazard that any FormPopup-level submit fix must handle.

Q11The bridge dispatcher is a 1,000-line hub that forgot to use its own helper

One class routes every wallet-sdk request and also manages popups, grants, response shaping, and account resolution. It even has a helper (formatSessionAccounts) for projecting session accounts — and then re-implements that exact projection inline at three call sites anyway. Every local bridge change reopens the same file.

Large Class + Duplicate Code · structural · 1 file (the hub of the whole package) · warm-to-hot code · confidence: high

Fix: Route all session-account projection through the one helper, then extract account resolution as its own collaborator; grant management follows.

Watch out: formatSessionAccounts pins wire-format parity and dispatcher.test.ts pins the schema-patch tri-copy shape — extraction must preserve both byte-for-byte.

Q12The e2e harness pastes the same setup ladder four times

The 1,249-line fixture file holds four copies of the same launch→register→open-popup→connect ladder, four identical inline phase wrappers, and three near-identical capability-grant dances — plus a password constant re-declared in four test files. A comment in the file says "refactor once we have three or more such fixtures." That threshold is now met.

Duplicate Code + mixed-concern hotspot · structural · 2 files (mostly one) · warm-to-hot code · confidence: high

Fix: Extract phase, a shared connected-playground setup helper, a parameterized grant helper, and one exported TEST_PASSWORD.

Q14Ten services copy-pasted the same backup-restore loop, and the copies already disagree

The restore-from-backup loop — try each item, push {...entity, restoreError} on failure — is rewritten in ten services. The copies have drifted: one stores the raw error object where the others store .message, and some take a lock while others don't. Any change to the restore contract is a ten-file edit.

Duplicate Code · structural · 10 files · warm code · confidence: high

Fix: Extract just the per-item result/error accumulation helper; everything else stays per-service.

Watch out: Validation, locking, and id allocation genuinely differ per service — they stay as service-specific hooks, only the accumulation is shared.

Q15When a profile, chain, or account dies, nine services each run their own homemade cleanup loop

The "load rows, filter mine, delete, emit" purge loop exists at 13+ sites for profile/chain/account deletion — with inconsistent locking, and even one file disagreeing with itself on strategy. Changing cleanup semantics (batching, error policy) means editing a scattered family of near-identical listeners.

Duplicate Code — lifecycle purge cascade · structural · ~10 files, 13+ sites · warm code · confidence: moderate

Fix: One shared row-iteration/delete helper, with the side effects (predicates, events, cache eviction) staying service-owned.

Watch out: Per-service emit order and the lock-vs-lockless split must be preserved exactly during extraction.

Q17"Make sure this contract is registered" is pasted at 8 places, despite a resolver existing for exactly this

A ContractResolver already exists for instance/artifact lookups — but the register-before-use prologue is still hand-copied at 8 sites, the function-name lookup at 4, the selector scan at 3, and token/service.ts contains a near-clone method pair on top. The extraction simply stopped before the finish line.

Duplicate Code from stopped extractions · structural · 6 files, ~15 sites · warm code · confidence: high

Fix: Extend the existing ContractResolver with ensureRegistered, findFunctionByName, and findFunctionBySelector, preserving current lookup order.

Watch out: Per-caller error strings are frozen by doc contract and differ between callers — the helpers must parameterize messages, not unify them.

Q18Functions pass around 8-slot anonymous tuples — built[0] through built[7]

Execution helpers exchange results as positional tuples of up to eight slots, and the same 7-parameter transfer bundle is repeated across spec, client, service, and planner. Six adjacent slots share the same type, so swapping two compiles cleanly and corrupts behavior. Adding one field means manually auditing every consumer.

Data Clumps + Primitive Obsession · structural · ~10 files · warm code · confidence: high

Fix: Step 1: replace the internal tuples with named result objects (both ends ship together); the public-API parameter object is a separate, later decision.

Watch out: FpcStrategy is byte-parity-sensitive and deliberately different from the other three strategies — do not normalize it into the family.

Q19"Is the wallet unlocked?" is copy-pasted ~75 times, with three different error messages

Nearly every service method opens with the same get-active-profile-or-throw guard, and the copies have drifted: "Profile locked" 34 times, "Wallet locked" 12, "Wallet is locked" twice — one file disagrees with itself — plus one "Unauthorized" outlier and one site that silently returns undefined instead of throwing. Any lock-policy change is a method-by-method slog.

Duplicate Code · structural · ~15 files, ~75 call sites · warm code · confidence: high

Fix: Extract one requireActiveProfile() helper, keeping existing strings per-site or unifying them as a deliberate choice.

Watch out: The "Unauthorized" string is documented as load-bearing (don't absorb that site), and the silent-undefined site in dapp-session is intentional behavior to preserve.

Q16The shared packages export functions nobody calls

Two whole modules in extension-messaging, four exports in wallet-core, one index export in wallet-crypto, and one declared dependency have zero production consumers — only their own colocated tests. Dead surface isn't free: every reviewer and auditor has to read around it, and it sits in the public API of packages with no external users.

Dead Code (symbol-level) + one unused dependency · structural · ~7 files across 3 packages · warm visibility · confidence: moderate

Fix: Small per-symbol removals, each proven by grep plus a test run — explicitly not a bulk sweep (the verifiers refuted the bulk version of this claim).

Watch out: The ENCRYPTION_GUARD canary test imports it relatively (removing the index export must not touch the test), and IllegalTransitionError's index export IS consumed by a test via the package subpath.

Q20The CAIP address helpers exist twice — bridge and extension each keep a copy

Four CAIP parse/format functions are line-for-line duplicates across wallet-bridge and the extension. The extension copy's header even claims the dispatcher uses it — the dispatcher actually imports the bridge copy. No test pins the two together, so any CAIP rule change has to be remembered in both places.

Duplicate Code · structural · 2 files · warm code · confidence: high

Fix: Make the bridge (or a lower shared package) the single owner and have the extension re-export from it.

Watch out: Ownership must move downward — the reverse breaks the layering rules — and the extension's extra parseCaipChain must keep its behavior.

Q21The permission checkers are clones — two are byte-identical except the error text

The scope-enforcement file holds a family of checker functions that are near-copies of one another: same shape, same empty-grants pass-through, different capability flag and error label. Two of them are byte-identical apart from the label. New checkers get born by copy/paste, so any convention change has to be propagated by hand across all of them.

Duplicate Code · structural · 1 file (public policy surface) · warm code · confidence: high

Fix: Local helper extraction inside the file — no grand checker-factory; this is policy code, keep it boring.

Watch out: Exact error text and the "no grants ⇒ pass through" semantics are pinned by tests — the helpers must be byte-faithful on both.

Q23Cancel-during-send only works because four files agree on microtask timing

The claim/cancel logic depends on exact promise-interleaving across the claim helper, the execution service, the journal lock, and the execution mutex — a comment in the code literally calls it "correctness-by-microtask-interleaving" and "fragile against future refactors of either side." A refactor that looks local can silently break cancellation, because the ordering contract is implicit and spread across four files.

Temporal coupling · structural · 4 files · warm code · confidence: high

Fix: A small, explicit handshake abstraction around the controller/journal pair, gated on the existing race tests staying green — not a grand coordinator.

Watch out: The no-await invariant in the claim helper and _transitionLocked's pre-abort awaits ARE the ordering contract — any extraction must own both sides.

Q22Two helpers serialize BigInts and Errors differently, and neither knows about the other

wallet-core has two serializers with overlapping jobs: the wire one writes a bigint as "123", the job-journal one writes "123n" with a different Error envelope. Part of the divergence is documented and deliberate — but the overlapping Error-shaping logic can improve in one path and silently rot in the other, because nothing connects them.

Parallel serializer logic · structural · 2 files · warm code (drift is silent) · confidence: moderate

Fix: Share a low-level BigInt/Error replacer between the two only where the documented constraints allow — do not force one serialization core onto both.

Watch out: serialization.ts mirrors @aztec/foundation/json-rpc (its wire shape is frozen), and jobs/error.ts's divergence is deliberate audit-hardening — neither is a consolidation target.
