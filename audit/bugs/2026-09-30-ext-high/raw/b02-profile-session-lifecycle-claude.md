## b02-profile-session-lifecycle-C-1: [Minor] Account writers outside `createAccountInternal` have no deletion-epoch fence, so a profile delete that lands mid-operation leaves orphan account / imported-key rows

- **Severity**: Minor
- **Repro confidence**: moderate (the interleaving is deterministic once it occurs; the trigger needs a delete of the same profile in a second window during a ~1 s import)
- **Type**: race / state invariant violation (secondary: resource leak)
- **Counter-example**: Window 1 (profile P unlocked) calls `AccountService.importAccount(P, chain, encryptedFile, addr, pw)`. It takes `dek = getProfileDek(P)` (returns while P is not yet reserved), then `decodeAccountExport` runs `EncryptionKey.fromPassword` (PBKDF2 at 600k iterations) plus `NuloAccount.fromSigningKey` (bb WASM), roughly 0.3-1 s with no lock held. In window 2 the user confirms `deleteProfile(P)`: phase 1 (tombstone, row delete, session close) and phase 2 (`ProfileDeletionCoordinator.purge` → `AccountService.purgeForProfile`, which deletes the account rows and `importedKeys.forProfile(P)`) both complete inside that gap. Window 1 resumes: `serializePerTuple` → `liveRows` → `getL1ChainIdStored(P, chainId)` → `importedKeys.set(...)` → `storage.set(accountRowIdOf(account), account)`. Both rows for the erased profile now exist on disk. Nothing reclaims them: `sweepOrphanImportedKeys` keeps a key row whose Account row exists, `purgeForProfile` already ran, and the tombstone has been cleared.
- **Violated invariant**: a profile deletion is "atomic, awaited, privacy-erasing" (`ProfileService.deleteProfile` doc). Every sibling writer that can outlive the purge takes the fence: `createAccountInternal` captures `deletion.capture` before its first await and calls `assertCurrent` right before the write (service.ts:249-283), and `restore` / `restoreImportedKeys` use `captureRestoreEpochs` / `assertRestoreEpoch`. `importAccount` is the one row-creating path with a slow unlocked prologue and no fence.
- **Failing path**: `apps/extension/src/wallet/services/account/service.ts:458-526` (`importAccount`: DEK copy at 469, slow decode at 472, writes at 499 and 513, no `getDeletionState()` use). Secondary instance: `patchAccountField` (313-332) does `storage.get` then `storage.set(accountRowIdOf(account))` with no reserved/epoch check, so a rename racing `purgeForProfile` or `clearChainState` can re-create the purged row. That window is a few storage round trips, so in practice it is negligible.
- **Expected vs actual**: Expected is `importAccount` rejecting with the same "profile is being deleted" error as `createAccount`, writing nothing. Actual is that a sealed imported signing key (ciphertext under the deleted profile's DEK) plus its Account row persist for an id the user believes is erased, and are invisible to every UI and purge path.
- **Recommended fix**: In `importAccount`, capture `const deletion = this.profileService.getDeletionState(); const epoch = deletion.capture(profileId)` (and a `deletion.isReserved` check) before the first await, and call `deletion.assertCurrent(profileId, epoch)` inside the tuple lock immediately before `importedKeys.set`. Do the same in `patchAccountField` if the owner wants parity; the window there is too small to matter.
- **Instances**: `apps/extension/src/wallet/services/account/service.ts:499,513` (import), `:327` (patch).

## Leads adjudicated

- **q02 `account/service.ts:322-330` patchAccountField skips the address gate (lead 1)**: rejected as a non-adversarial bug. The mis-keyed row it needs (body address B stored under key(P,C,A)) cannot be produced by any writer. Every writer (`createAccountInternal`, `importAccount`, `restore`) derives the key with `accountRowIdOf(row)`, and `liveRows()` ignores non-canonical rows. Only a raw-storage writer can create it, so it is routed to security below. The resurrect-after-purge race on the same function is folded into C-1 as a negligible secondary instance.
- **q02 `profile/service.ts:1965-1985` exportMnemonic wrong-password string (lead 2)**: rejected. The only caller, `popup/pages/settings/security/export/seed.vue:59-67`, sets `isWrongPassword = true` on ANY thrown error and never matches on the error type or string, so the hard-coded message does not change behavior. (Side observation for the popup cluster: a real `"Profile storage corrupted"` throw is shown to the user as "wrong password". Cosmetic, so not filed.)
- **q13 `account/spec.ts:68` ImportedAccountUnusableError loses identity over RPC (lead)**: rejected. No popup code catches or `instanceof`-checks it, and the `.message` text still reaches the user unchanged, so there is no wrong result. A future UI repair CTA would hit this, but that is speculative.
- **q10 non-constant-time `array_equals` at profile/service.ts:2015,2330 (lead)**: rejected as a correctness bug. Both compares run on secrets the same caller already holds, and the path is not remotely timeable; security-flavored at most.

## Routed to security

- `apps/extension/src/wallet/services/account/service.ts:320-330`: `patchAccountField` trusts the row body's identity fields less than its siblings (`profileId`/`chainId` only, no `address`). A transplanted row would overwrite another account's row. Needs a storage writer, so it is an integrity-hardening item.
- `apps/extension/src/wallet/config/store.ts:46-66` and `services/config/service.ts:38-40`: `setValue` only type-checks `sessionTtl` with `z.number()`, so a caller can set a negative TTL and lock the wallet instantly, or a non-finite one. The fixed UI options make this unreachable in normal use, but the RPC is open to any extension page.

## Non-findings considered

- `config/store.ts:59-65` mutates memory and fires `onUpdate` (SessionManager picks up the new TTL / strict flag) before `storage.set`. A rejected persist leaves runtime and disk disagreeing until the next SW start. Requires a storage write failure, so not realistic.
- `SessionManager.getActive` (session-manager.ts:227) returns `undefined` when a successor session replaced the expired one mid-decision. The only off-lock callers are `getSecret` / `getDek` via `deriveDappSessionMacKey`, and the effect is one transient "Profile locked" that the next read clears. Needs expiry and unlock in the same tick.
- `deferBudgetEnd` is never refilled by `refresh()` (session-manager.ts:888). The code documents this ("nothing refills it"), so it is intended.
- `openSessionVerified` failure after `persistNewProfileHoldingLock` (create/import) leaves the new row in the list while the RPC rejects. The profile is complete and unlockable, and a crash-equivalent state is handled identically. Requires an integrity-delegate or storage fault on a brand-new profile.
- `deleteProfile` phase-1 throw after the tombstone write (e.g. `integrityBlocked.clear` rejecting) leaves the id reserved and the row hidden until the next boot resume. This is the designed fail-closed posture, and it needs a storage failure.
- Facade lock held across PBKDF2 / integrity re-derivation in `finalizeRestore`, `changeProfilePassword`, `verifyBeforeSessionOpen`: latency only, well under the 5-minute watchdog.
- `lockActiveProfile` sweeping every pending restore: its only caller is the user's Lock click (Header.vue:28), and the wipe is documented intent.
- Alarm listener registered after boot awaits (runtime.ts → SessionManager ctor): an alarm wake-event delivered before registration is lost, but `restore()` re-checks `isExpired` and silent-closes on every boot, so the outcome is identical.
- Single-flight `start()` memo reset timing (`single-flight-start.ts`): waiters of a rejected boot all observe the rejection, and retry is only re-enabled before the registration zone. Consistent with its documented contract.
- `PasskeyService.resolvePasskeyRequest` deleting `pending` before `PasskeyCredential.create` can strand the window until its timeout. PATH B has no production callers, so it is a dead-code claim and not filed.
- Restore/unlock deadlock hunt (facade lock ↔ artifact lock ↔ journal transition lock ↔ expiry-deferral predicate): `hasApprovedSendsInFlight` reads the journal lock-free and `getOperations` takes no transition lock, so no cycle exists.
- `unlockProfile` returning `InvalidPasswordError` when the password was changed in another window during phase 2: correct message for the new state, and needs two windows on the same profile within ~1 s.

## Cross-rebuttal (claude on codex)

### 1. Codex findings

- **X-1 (Major, patchAccountField resurrects a purged account)**: partially agree, severity inflated. Mechanism re-traced and real. `patchAccountField` (account/service.ts:320-327) locks the per-row key `accountRowId(...)`, while `clearChainState` (:148-157) and `purgeForProfile` take no lock and delete under no fence. A `storage.get` then `storage.set` straddling a delete recreates the row, and for an Imported account the key row is already gone, so the resurrected row throws "signing key missing". It is the same defect as my C-1 secondary instance. The window is a few storage round trips, and the trigger is a rename or visibility edit racing a chain-network delete in another window. No funds are at risk, the account is unusable but not corrupting, and deleting and re-adding the network is possible. Major is too high. Call it Minor, low likelihood. Codex's chain-purge variant (unusable imported account) is a real angle I did not spell out. I stand by "negligible window" but concede it should be filed, merged with C-1 as one "account writers outside the tuple lock or epoch fence" item. The fix should be the row lock in the delete paths or a re-check of the row after `set`.
- **X-2 (import lacks the deletion fence)**: agree, identical to my C-1. Codex's line anchors (469/493/499/513) match mine. Both found it independently, so confidence is high. Severity Minor for both.
- **X-3 (failed config write poisons the same-value retry)**: agree on mechanism, Minor, with a low-likelihood caveat. Source: `ConfigStore.set` (config/store.ts:59-66) mutates `this.config[key]` and fires `onUpdate` before `await storage.set`, and the equality shortcut at :61 returns success on retry. I listed the ordering under non-findings only as a "rejected persist leaves runtime and disk disagreeing until the next SW start" and did not trace the retry-returns-success consequence. Codex's consequence is correct and is strictly worse than what I considered. It needs a failing `chrome.storage.local.set`, which is rare (quota or an I/O error), and a same-value retry. I re-decide it as file, Minor. `apply()` (:93-98) has the same ordering.
- **Leads q02 (two), q10, q13**: same rejections as mine, confirmed from source. No disagreement.
- **Routed to security, session-manager.ts:858-861 (refresh persist rejection skips alarm rescheduling)**: I did not trace this. Codex itself notes lazy expiry remains, so there is no correctness gap beyond proactive lock timing. I am not contesting it.
