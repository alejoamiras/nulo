## b07-popup-boot-state-C-1: [Minor] Queued incoming-trust prompts open on the lock screen, then drain silently with no decision applied

- **Severity:** Minor
- **Repro confidence:** moderate
- **Type:** state invariant violation (secondary: lost update)
- **Counter-example:** Two contracts are in `pending` trust state (PopupManager's own comment: `replayPendingPrompts` emits N Pending events on (re)connect). Prompt A opens, B sits in `pendingTrustQueue`. The auto-lock timer fires while the popup is open. The lock path runs `lockedState.seal()`, which calls `popupStore.closeAll()` and then sets `isLogined = false` synchronously. `isOpened("incoming_trust")` flips true to false, and the pre-flush watcher at PopupManager.vue `watch(() => popupStore.isOpened("incoming_trust"), ...)` calls `dequeueNextPendingTrust()`. `appStore.profile/network/account` are not cleared on lock (`markLocked` only sets `isLogined = false`), so `payloadMatchesLiveTriple(B)` passes. `cacheStore.incomingTrust` is set to B and `popupStore.open("incoming_trust")` runs on the auth screen. The user taps Allow or Block. `setTrustAllow` / `setTrustReject` call `captureTrustFence`, which calls `profileService.captureExecutionFence()`. That rejects while locked, so it returns `undefined` and the method returns `false`. In `IncomingTrustPopup.decide`, `ok !== true` gives no toast, no error, and `emit("onClose")` still fires, so the next queued prompt opens and the same thing repeats until the queue is empty. After unlock the triple is unchanged, so the triple watcher does not fire and `replayedForKey` is still set, so `tryReplayForTriple` no-ops. The contracts stay `pending` (records hidden) until the popup is next reopened.
- **Violated invariant:** Every other locked-entry path closes popups and suppresses prompts (`lockedState.seal` closes all popups; `SelectTokenPopup` is explicitly mounted only while `appStore.isLogined`, "its price feed ... must never run locked"). `dequeueNextPendingTrust` is the one consumer that ignores the session state. A trust decision needs an open session (the fence), so offering one while locked cannot succeed.
- **Failing path:** apps/extension/src/popup/app.vue `lockedState` / `createLockedState.seal` (popup/locked-state.ts) -> `popupStore.closeAll()` -> PopupManager.vue `watch(isOpened("incoming_trust"))` -> `dequeueNextPendingTrust()` (no `isLogined` check) -> `popupStore.open("incoming_trust")` -> `IncomingTrustPopup.decide` -> `IncomingTransferService.setTrustAllow` returns false at `captureTrustFence` -> `emit("onClose")` -> watcher -> next dequeue.
- **Expected vs actual:** Expected: no trust prompt while locked; queued prompts survive the lock and resurface after unlock, or are replayed on unlock. Actual: prompt (token symbol and contract) draws over the lock screen, each decision is a silent no-op, and the queue is drained so no prompt returns this session.
- **Recommended fix:** In `dequeueNextPendingTrust`, `return` when `!appStore.isLogined`. Add `watch(() => appStore.isLogined, (on) => on && dequeueNextPendingTrust())` so the retained queue drains after unlock. Optionally treat a `false` result in `decide` as "keep the prompt" rather than closing.
- **Instances:** apps/extension/src/popup/components/popups/PopupManager.vue `dequeueNextPendingTrust` and the isOpened watcher; apps/extension/src/popup/components/popups/IncomingTrustPopup.vue `decide` (false result closes silently).

## Leads adjudicated

- `popup/pages/settings/advanced/index.vue:120-137` (developerMode un-awaited cascade): rejected. Both cascaded writes go through `updateSetting`, which catches and toasts, so there is no unhandled rejection. The stuck state (developerMode false, debugMode true, row hidden) needs the second of two back-to-back port writes to reject after the first succeeded, which means a worker restart inside a few milliseconds. The user gets a "Failed to update setting" toast at that moment, and the effect is a larger log buffer and debug-level logs, with no wrong result. Low repro confidence, so not reported.

## Routed to security

- None. (C-1 shows token symbol and contract on the lock screen. The contract address is a public on-chain value and the symbol is sanitized, so the primary impact is functional.)

## Non-findings considered

- Boot races (`loadProfile` / `resolveBootSession` / `reconcileLockedBoot`): every await has an `isCurrent` fence, the event-seq fence covers lock/unlock events landing mid-lookup, and `applyBootOutcome` settles the flags on the superseded path. No counter-example found.
- Route guard `lateDecision`: `getProfiles()` rejecting during a worker restart fails the navigation, but the reconnect watcher (`flush: "sync"`) starts a boot run that lands the shell. Documented in app.vue.
- `onActiveProfileChanged.add` on every `loadProfile` run: `EventHandler.add` dedups by identity, so there is no handler multiplication.
- `network-switch`: the run fence plus live-scope guard cover each await. `replaceAccountClient` disconnecting the previous client can reject an older run's pending call, but that run is superseded by then.
- Send double-submit: `isSending` latch plus `canSubmitNow`, `submitInFlight` ownership of the execution port disconnect, `cancelled` flag against a double `router.back()`. No second-submit interleaving found.
- Send stale `precomputedEstimateId` after an amount edit: the service-side consume validates inputs, per its own comment; not verifiable inside this cluster.
- `refreshInFlightOps`: a failed `journal.connect()` publishes empty ops and never retries (`connected` stays true), which fails open for the scope-change guard. It needs `connect()` to throw, which the client does not do on the normal path; `onConnected` refresh covers reconnects. Not reported (low confidence).
- `popupStore.open` computes `order` from key count: re-opening an already-open key resets its order to `len` (gap-free invariant only broken by a re-open of a mid-stack popup). No call site found that re-opens a mid-stack popup with a different expectation.
- Onboarding `app.vue` `onMounted`: a rejected `getProfiles()` during a worker restart leaves the shell on the welcome route with an unhandled rejection; the user can still proceed. Cosmetic.
- `tokenBalanceByType` divides by `10 ** decimals` as a JS number (display only; the submitted amount comes from the bigint `validateSendAmount`).

## Cross-rebuttal (claude on codex)

### 1. Codex findings

- **X-1 (late preference read overwrites newer profile): partially agree, severity Major is inflated (Minor).** The code is as described. `auth.vue` `onMounted` assigns `appStore.profile = profile` after two awaits with no fence, and `route-guard.ts` `lateDecision` assigns after `getProfiles()` and `getLastActiveProfileId()` with no re-check of `!appStore.profile`. The window is two RPC round trips, and a second window must complete an unlock of a different profile inside it. Unlock needs password or passkey entry, so this is practically unreachable on the auth mount. The route-guard variant needs an activation event to land between the guard's first read and its assignment, which only happens on a fresh boot. Real missing fence, small blast radius. Nothing shows the wrong profile is left uncorrected beyond the next event.
- **X-2 (pending account selection installs an account from a departed profile): agree on the code, disagree on Major (Nit/Minor).** `AccountsPopup.vue:37` passes `() => appStore.selectAccount(acc)` through `commitScopeChange` (`app.store.ts:252-258`), and unlike `commitAccountTarget` (`:439`) the callback has no `superseded()` check. The window is one `refreshInFlight` RPC, and the popup must see lock, unlock and a full bootstrap of a different profile inside it. `lockedState.seal` closes all popups on lock, so the user-visible surface is gone before the unlock. No realistic trigger (see "realistic scenarios only"). The inconsistency with `commitAccountTarget` is worth a one-line hardening fix, not a Major.
- **X-3 (lock during boot hides the unlock form behind a false failure): agree, severity Moderate rather than Major.** I re-traced it. `reconcileLockedBoot` (`reconcile-locked-boot.ts:39-40`) returns any non-`locked` result before the event-seq check. `resolveBootSession` (`boot-session.ts:57-60`) turns a bootstrap rejection into `failed`. `applyBootOutcome` then calls `settleUndecided("failed")`, which sets `bootOutcome` (`app.vue:257`), and `auth.vue:63` withholds the form. No lock event path clears `bootOutcome`. The trigger is realistic: auto-lock or a manual lock in another window while the popup bootstraps. The user recovers by pressing RETRY, which lands on the lock path. I missed this. The fix is the event-seq fence on `failed`.
- **X-4 (developerMode cascade; the lead I rejected): re-decided, now report as Minor / low repro, agreeing with Codex's mechanism.** I rejected it because each write is caught and toasted. Codex's point holds in source. `ConfigStore.set` (`wallet/config/store.ts:59-66`) mutates memory and emits before `storage.set`, so a failed persist leaves disk at `{developerMode:false, debugMode:true}`. The same partial state also results if the worker restarts between the two back-to-back `updateSetting` calls. `LoggerStore` reads `debugMode` at load, so debug logging returns with its toggle hidden (`advanced/index.vue:87-91`). Two limits keep it minor. The trigger is a storage rejection or a worker kill inside a few milliseconds. Any later successful config write persists the full in-memory config and self-heals it. Effect is debug-level logs and a larger buffer, with nothing sensitive exposed and no wrong result. Report as a hardening item, not Major.
- **Routed to security (PopupManager trust prompt over the lock screen):** same as my C-1. Agree. I kept it as a functional bug because the contract address is public and the symbol is sanitized. The silent drain after `captureTrustFence` returns `false` is the part Codex did not state.
