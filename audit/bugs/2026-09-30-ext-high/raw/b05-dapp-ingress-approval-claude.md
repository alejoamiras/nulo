# b05-dapp-ingress-approval — claude

Scope read: `apps/extension/src/wallet/services/window-manager/window-manager.ts`; `apps/extension/src/wallet/services/dapp-interaction/service.ts`; `apps/extension/src/wallet/services/dapp-session/service.ts` (+ `integrity.ts` lead); `apps/extension/src/wallet/services/wallet-sdk/{background.ts (380-1262), queued-journal.ts, session-baton.ts, queued-wait-vouching.ts, session-established.ts, discovery-approval.ts, tab-lifecycle.ts, verify-admission.ts, error-envelope.ts, stale-session.ts}`; `apps/extension/src/wallet/services/auth-registry/service.ts` (1-200 only); `packages/wallet-bridge/src/{dispatcher.ts (163-195, 825-1600, 1725-1794), account-resolution.ts, discovery-queue.ts, operation-result.ts}`; `apps/extension/src/composables/{useDappApprovalWindow,useDappInteractionPayload}.ts`; `apps/extension/src/popup/windows/{execute,capabilities,discover}/index.vue` (script blocks); handoff edges: `execution/{execution-lane,rpc-cancel,service.ts executeOperations}`, `packages/extension-messaging/src/errors.ts`.

Honest summary: this cluster is heavily hardened (fence capture, first-claim-wins cancel, detach-before-settle, identity-not-membership handle checks, admission reservations). The approve/close/cancel/SW-restart races I traced all resolve to exactly-once settlement. Two real but low-severity dApp-contract defects survive.

## b05-dapp-ingress-approval-C-1: [Minor] An unanswered or OS-closed approval popup reaches the dApp as the unclassified "could not process" error, not a classified refusal

- **Repro confidence:** moderate (timeout path: deterministic from code; window-close path: depends on the popup's `beforeunload` RPC losing the race to `windows.onRemoved`)
- **Type:** wrong result (error classification) / bad error path
- **Counter-example:** a dApp calls `sendTx` (or `requestCapabilities`); the approval popup opens and the user walks away. After `INTERACTION_TIMEOUT_MS` (10 min) `WindowManager` settles the handle with the bare string `"Timed out waiting for window"`. The dApp receives `{ message: "The wallet could not process the request." }` with no `code` and no `walletErrorCode`, indistinguishable from a wallet fault. The same holds when the window dies without the popup page's `rejectInteraction` RPC landing first (browser quit, crash, `beforeunload` message lost): `_settleUserClose` rejects with the bare string `"Window closed by user."`, so the dApp sees the generic failure instead of 4001.
- **Violated invariant:** `error-envelope.ts` header/tail: "An error a dApp is meant to act on has to be classified above and carry a `walletErrorCode`"; `UserRejectedError` exists precisely so a popup refusal is 4001 (`rejectInteraction` does this when the popup's own RPC wins). A user-dismissed or timed-out approval is the same semantic class and is wallet-authored.
- **Failing path:** `window-manager.ts:124-127` (`_settle(..., "Timed out waiting for window")`) and `:259` (`handle.reject("Window closed by user.")`) -> `dapp-interaction/service.ts:488` (`pending = handle.promise.finally`) -> `execute`/`requestCapabilities` -> `dispatcher.ts` `handleSendTx`/`askCapabilities` -> `background.ts:1211` `toWalletResponseError(error)` -> `error-envelope.ts:~170` falls through every `instanceof` to `UNCLASSIFIED_ERROR_MESSAGE`. The string is also what `failQueuedForError` writes into the journal row.
- **Expected vs actual:** expected: a classified, dApp-actionable refusal (4001 USER_REJECTED for a close, a timeout-distinguishable code for an expired prompt) so the dApp can suppress error UI / offer retry. Actual: the generic constant; a dApp that treats 4001 as "user said no" shows a wallet-error toast and may retry-loop.
- **Recommended fix:** reject with typed errors: `new UserRejectedError("Window closed by user.")` in `_settleUserClose`, and a classified timeout error (or `UserRejectedError` with a timeout message) in the timeout branch. `handle.reject` already accepts any reason; `Handle.reject` callers only compare on message in tests (`window-manager.test.ts:106,125,330,364,525,582` use `.rejects.toMatch`, which would need `.message`).
- **Instances:** `apps/extension/src/wallet/services/window-manager/window-manager.ts:126`, `:259`, and the "Failed to open window." strings at `:150`, `:176` (those are genuine wallet faults; generic is acceptable there). Passkey path shares `WindowManager` (out of cluster).

## b05-dapp-ingress-approval-C-2: [Minor] The dApp-facing `-32005 TOO_MANY_PENDING` backpressure signal is unreachable

- **Repro confidence:** high (static trace; the only production throw site is swallowed into a result)
- **Type:** wrong result (error contract) / other (dead documented contract)
- **Counter-example:** a dApp fires more concurrent `sendTx` than `ExecutionLane.EXECUTION_ORIGIN_CAP` (or the lane cap fills). `acquireSlot` marks the journal failed and `throw new TooManyPendingError()` (`execution-lane.ts:333`). That throw is inside `dispatchOperation`, so `ExecutionService.executeOperations` catches it in `classifyOperationCatch`; `TooManyPendingError` is not in `ridesCodeChannel` (pinned by `rpc-cancel.test.ts` N-15), so the result is `{ status: "failed", error: <message>, code: undefined }`. `unwrapOperationResult` (`dispatcher.ts:175`) then throws a bare `Error(message)`, and `toWalletResponseError` returns the unclassified constant. The dApp never sees code -32005 nor `walletErrorCode: "TOO_MANY_PENDING"`, so it cannot tell "retry after in-flight settle" from a hard failure. Same on the silent path (`silentInteraction` returns the same results) and the popup path (`executeAndResolve` settles with the same results).
- **Violated invariant:** `execution-lane.ts:331` ("Surface to the dApp as -32005"), `errors.ts` TooManyPendingError doc ("Maps to JSON-RPC code -32005 when surfaced to dApps"), and `error-envelope.ts:127-135`, which is dead code in production. The `BUG PIN` in `errors.test.ts:256` and the N-15 test admit only that the class reconstructs as base `WalletError` on the RPC client; they do not admit that the dApp contract is lost end to end.
- **Failing path:** `execution-lane.ts:329-333` -> `execution/service.ts` `executeOperations` catch (`classifyOperationCatch`, `rpc-cancel.ts:~85-99`) -> `dispatcher.ts:163-175` `unwrapOperationResult` -> `background.ts:1211`.
- **Expected vs actual:** expected -32005 + `TOO_MANY_PENDING` so the dApp backs off; actual generic failure (the journal row does read "Too many pending transactions", so the user sees it in the feed, the dApp does not).
- **Recommended fix:** add `TooManyPendingError` to `ridesCodeChannel` and make `walletErrorFromPayload` (or the unwrap) reconstruct it (it has a fixed message and no details, so reconstruction is lossless, unlike the detail-dependent classes the N-15 comment worries about); update N-15 and the BUG PIN to match.
- **Instances:** `apps/extension/src/wallet/services/execution/rpc-cancel.ts:~85-99` (`ridesCodeChannel`), `apps/extension/src/wallet/services/execution/execution-lane.ts:333`, `packages/extension-messaging/src/errors.ts` (`walletErrorFromPayload` known-payload table), `packages/wallet-bridge/src/dispatcher.ts:174`.

## Leads adjudicated

- `wallet-sdk/queued-journal.ts:143` (session address set without chain-prefix filter): **rejected.** Sessions are keyed per `(profileId, origin, chainId)` (`tryGetDappSessionByOriginAndChain` matches `x.chainId === chainId`), and `session.accounts` is written only by `applyCapabilityDecision.addAccounts` (CAIP entries built by the popup from `availableAccounts`, all on the session's own chain via `loadAccountsForPopup`/`resolveNetwork(ctx)`) and by `addDappSession(..., [])`. No writer produces a foreign-chain entry, and the journal's `walletAccounts` is fetched for this `chainId` so a foreign-chain address could not match a wallet account anyway. `extractSendFrom` and `requestedFromOf` also normalise identically (null/`NO_FROM` -> none, else `String`), and both call the one shared `resolveAuthorizedSessionAccount`.
- `dispatcher.ts:1072-1090` (`handleBatch` does not refuse `grantPublicAuthwit`): **rejected.** Reachable only by a raw protocol client that bypasses the SDK's batch schema; the leg still opens the normal approval popup and returns a correct result. The batch holds the session FIFO baton for the popup's duration, which is the documented cost of any popup-routed leg (`createAuthWit` legs behave identically and are allowed). No wrong result, corruption or invariant break.
- `dapp-session/integrity.ts:58-62` (dead `Buffer.from` catch): **rejected.** Correct observation (`Buffer.from` never throws on bad base64), but it is fail-closed via the length check and `subtle.verify`; quality only.

## Non-findings considered

- Approve vs. window-close race: `approveInteraction` deletes the record then `detach`es synchronously; a preceding `onRemoved` already removed the record via `pending.finally`, so the later approve gets "Invalid id" and nothing executes or double-settles.
- Approve vs. journal cancel: `cancelledAt` is checked before the claim and `claimOrCreate*` re-checks the record; approve-first deletes the record so the cancel finds nothing. Exactly-once.
- `rejectInteraction` after `approveInteraction` (popup `beforeunload` after approval): record already deleted, returns silently.
- SW killed mid-approval: `DappInteractionService.storage` is in-memory, so the popup's approve gets "Invalid id" and the dApp's channel is gone with the ECDH session (stale-session reply covers the page). Intended (ARCHITECTURE: sessions are memory-only); no dangling execution.
- Session expiry during a 10-minute popup: `executeAndResolve` re-reads the session row (`tryGetDappSession`, expiry-aware) and aborts; `execute`'s `validateSession` does the same at entry.
- Session terminated (tab close / revocation) while approval is open: execution is refused by `registerInFlight(...).live` / `refuseEndedSession` in the claim helper; the response to a dead channel no-ops.
- Per-session FIFO baton: released on `onExecutionEnqueued` or in the `finally` of the handler chain, so a popup timeout / rejection / throw cannot wedge the queue; `onSessionTerminated` deletes the queue entry.
- Queued journal creation: cap check and create run under `queuedCreationLock`; stamped-profile re-validation inside the lock; failures never block the handler.
- `WindowManager` create/close races: handle identity (not id membership) is checked after `getLastFocused` and after `create`; a window that arrives for a settled handle is removed. `handOver` with an in-flight create closes the window on arrival by design.
- Connect-popup dedupe: the lookup-to-registration sequence has no yield between `tryGetDappSessionByOriginAndChain` and `pendingDiscoveryPromises.set`; waiters are capped; all exits resolve and delete the dedupe entry in `finally`.
- Connect Allow after the 55 s B-16 freshness cutoff is rejected (and a fresh same-tuple twin waiting on that popup is rejected with it): documented intent (B-16), no stale session is persisted.
- `DiscoveryQueue.drain` processes entries serially, each awaiting a connect popup, so later queued discoveries can expire at 55 s and be rejected: documented ("re-read the clock per entry"), the dApp re-discovers.
- `VerifyAdmissionGate` token/window accounting (refill maths, `released` recursion through `serve`, `liveWindowIds` dedupe): no counter can underflow or leak on any traced exit.
- `cancelInteraction(cancellationToken)` has no production caller (not in `rpcMethods`); dead code, not a bug.
- `upgradeDappSession` emits `onDappSessionDeleted` (which tears down live sessions) but has no production caller.
- `applyCapabilityDecision` concurrent same-type approvals from two tabs are last-completion-wins: documented in its header.
- Capabilities/execute/discover popups: submit latch (`isLoading`) present on all three; `beforeunload` listener is removed on `completeInteraction`/`closeWindow(true)`; composable `dispose` is parent-called in the documented order.

## Cross-rebuttal (claude on codex)

**1. Codex findings**

- **X-1 (capability approval succeeds after session expiry): agree, Minor.** I re-traced it. `applyCapabilityDecision` (`dapp-session/service.ts:343-382`) only checks `storage.get` and never `expiry`. `requestCapabilities` validates expiry before the popup opens. `handleRequestCapabilities` (`dispatcher.ts:1355-1371`) then returns `granted` from the updated row, with no re-read through the expiry-aware getter. I missed this. My "session expiry during a 10-minute popup" non-finding covered only the execute path (`executeAndResolve` re-reads the row), not capabilities, so that non-finding was too broad and is retracted for capabilities. Likelihood is very low: the approval has to cross the expiry boundary inside the 10-minute popup window. The result is a self-healing "granted, then the next call fails and reconnect is required". Severity stays Minor, at the low end.
- **X-2 (closing a loading approval reports a wallet failure): agree, but it is the same root as my C-1.** I re-traced it. `useDappApprovalWindow.ts:123-124` registers `beforeunload` only after `options.init()` resolves. A window closed during init therefore reaches the dApp only through `windows.onRemoved`, then `_settleUserClose`, then the bare string at `window-manager.ts:259`, then the unclassified envelope. Codex's init-window gap is a deterministic trigger for that path. I rated it only "moderate, depends on the RPC losing the race". I upgrade C-1's window-close confidence to high on that basis. The two findings should merge into one id with one fix: type the close rejection as `UserRejectedError`. Codex's advice to keep timeout and open-failure handling separate is compatible with my fix.
- **Leads:** all three quality-run leads (queued-journal:143, grantPublicAuthwit in batch, integrity.ts:58) are rejected by both of us for the same reasons. There is no disagreement to re-decide.

**2. What Codex missed that I still stand by**

- **C-1 timeout half.** After `INTERACTION_TIMEOUT_MS` the bare `"Timed out waiting for window"` (`window-manager.ts:126`) also becomes the generic error. Codex's own fix text says "preserve distinct handling for timeout", but it never identifies the timeout as mis-classified.
- **C-2 (-32005 `TOO_MANY_PENDING` unreachable end to end).** Codex lists no non-finding on the execution-lane throw path. `execution-lane.ts:333` throws inside `dispatchOperation`. `classifyOperationCatch` does not carry it over the code channel (`ridesCodeChannel`, pinned by the N-15 test). `unwrapOperationResult` (`dispatcher.ts:163-175`) then throws a bare `Error`. I stand by this at high confidence.

**3. What both missed**

- **Related to X-1, not yet verified.** `applyCapabilityDecision` also does not check that the session is still bound to the same profile or chain as the popup's session. A chain mismatch is impossible because the row id is the key, and I found no profile-switch path that keeps a row while changing profile. I am not promoting it. No other new item survives a concrete counter-example.
