## Leads adjudicated

- q03 `commitScannedNote` no epoch re-check before `resolveNoteTrust` (incoming-transfer/service.ts:1383-1415): REJECTED. The function runs inside `withServiceLock` and checks `serviceEpoch !== epochAtStart` first. Every epoch bumper (onTokenDeleted, clear*) bumps inside the same lock, so the awaits between the guard and `setTrust` are storage/config reads that cannot interleave with a bump. The only window is a lock watchdog force-release, which needs a hold far longer than these reads; no realistic trigger. The PXE-bound awaits (`blockTimestampFor`) do have the re-check.
- q03 `parseNoteAmount` accepts negative/hex (service.ts:2445-2453): REJECTED. Its only input is `note.content.value`, which `NoteService.decodeField` (note/service.ts:26-28) produces via `BigInt(raw).toString()` for `u128`: always a non-negative decimal string. Hex never survives and a negative u128 is impossible from a real UintNote.
- q05 `BalanceView.onBalanceAdded` without id dedupe (BalanceView.vue:235-239): REJECTED. `TokenBalanceService.createTokenBalanceHoldingLock` emits `onTokenBalanceAdded` in the synchronous continuation of `await repo.set` (token-balance/service.ts:296-301). Any snapshot that already contains the row was read after that write and so its response travels the same ordered port after the event. The event therefore lands while the snapshot is in flight and sets `fetchDirty`, forcing a refetch that replaces the list. Post-landing stale `Added` needs an event older than the snapshot delivered later on the same port, which the port does not do; a reconnect resnapshots via `onReconnected`. TokensView's extra dedupe is belt-and-suspenders, not a fix for a reachable duplicate. Worst case if the ordering assumption broke: transient duplicate until next refetch.
- q-lead activity-rows `incomingRows` lacks `isForeignProfile` (activity-rows.ts:107-124): REJECTED as a bug, kept as a defense-in-depth gap. Incoming records do carry `profileId`, but the only feed source, `useIncomingTransfers`, resets synchronously on scope change (flush sync watcher), drops stale reads via `isStale`, and accepts Added/Updated only through `inLiveScope` (profile+network+account). `getIncomingTransfers` is queried per (profileId, networkId, account). No path places a foreign-profile record into `incomingTransfers`. Only the deletes are unscoped, and they are subtractive.

## Non-findings considered

- `ActivityProtocolCoordinator.retireScope`/`purgeScope` delete counter rows holding only the scope lock while `allocate`/`record` hold only the source lock (activity-protocol/coordinator.ts:122-137, 146-156), so a concurrent allocate can recreate a stale counter and stall the watermark. Real interleaving in principle, but `ActivityProtocolCoordinator` has no production importer (only coordinator.test.ts), so nothing is exposed. Worth revisiting at the moment it is wired in.
- Public-arm cursor advances past events for recipients unknown at scan time: handled, `onAccountAdded` resets the public cursor (incoming-transfer/service.ts:364-398).
- Note arm only sees ACTIVE notes, so a note received and spent between two polls produces no incoming record; balance (PXE) stays correct and this is inherent to the polling design, no wrong amount.
- `onTransactionAdded` late-delete uses the active profile rather than `tx.profileId` (service.ts:1305-1311); the tx store emits for the active profile and the match is additionally keyed on account+hash, no concrete wrong deletion.
- PriceService: generation/abort/backoff/monotonic merge and read-time validation are consistent; `refresh(gen)` returning the shared inflight regardless of `gen` is documented and the enable path clears inflight on disable. Staleness is bounded by `QUOTE_TTL_MS` read-time check.
- `token-amount`/`token-aggregate`/`token-order`/`token-fold`: decimals and balance parsing are regex/range guarded; zero-balance and malformed rows are handled consistently across the aggregate and ordering.
- TokensView `onBalanceUpdated` replacing the row object drops `isUpdating`/`isMinting`: cosmetic only (a dot vanishes while a coalesced second refresh runs); not a wrong result.
- BalanceView fetch generation/dirty/retry logic: each async path is fenced by `fetchGeneration`; `enterScope` clears rows before the new snapshot; no leak found (timers and handlers are released in `onBeforeUnmount`).

## Cross-rebuttal (claude on codex)

### 1. Codex findings and re-decided leads

- **X-1 (drain deletes the refresh marker across a lock/profile switch): AGREE, partially on severity.** Re-traced: `drainBalanceOutbox` captures the active profile once (incoming-transfer/service.ts:2230), then awaits `listOutbox`, the service lock and `getOutbox` before `requestRefreshOrKeep` (:2296). Nothing rechecks the active profile in between, and `drainOutboxRow` has no profile guard. `TokenBalanceService.onActiveProfileChanged` clears `this.tokens` synchronously (token-balance/service.ts:455-461). `requestBalanceRefresh` then finds no matching token and returns `{missing:true}` (:238-247), and the drain deletes the row (:2274). The incoming-transfer service's own `onActiveProfileChanged` (:360) only hydrates schedulers. It does not bump `serviceEpoch`, so `isCurrent()` stays true. My pass did not read this path in depth, so I miss it. The repair paths are thin: `reconcile-pairs.ts:145` requeues only `updatedAt===0 && !syncFailure`, and a re-discovered receipt does not recreate the marker. The window is several storage awaits and needs a lock or switch inside it, so I rate it Moderate repro, impact a stale balance until the next unrelated refresh trigger. I would call it Minor-to-Major, not plain Major. The fix is a profile re-check (or a generation) right before `requestRefreshOrKeep`, with an inactive map returning retryable instead of `missing`.
- **X-2 (seeder marker read failure erases tombstones): PARTIALLY agree, low realism.** The mechanics are right: `readMarkerState` returns `{}` on a rejected read (token/seeder.ts:683-686) and `updateMarker` writes the whole blob (:337-342). But the docblock at :670-678 states the swallow is deliberate, so that a failing read cannot block a deletion from recording its tombstone. A transient `chrome.storage.local.get` rejection that is followed by a successful `set` on the same key is very unlikely. I rate it Low confidence as a product bug and a defensible design trade-off. The fix is to rethrow for `updateMarker` and keep the fallback for status readers, but it is not a required change.
- **q05 BalanceView `onBalanceAdded` duplicate row (re-decided): still REJECTED.** The push at BalanceView.vue:235-239 has no id dedupe, but the sole emitter is `createTokenBalanceHoldingLock`, which emits right after `repo.set` (:300-301). A snapshot that includes the row is read after that write, so the event arrives while the snapshot is in flight, and `markDirty()` forces a refetch that replaces the list. Duplication needs an old Added delivered after a newer snapshot on the same ordered port. Codex's "zero balance, so no fiat double-count" argument is correct but secondary. I treat a transient duplicate row as the worst case, with no production trigger. A cheap `findIndex` guard would be defense in depth (TokensView has one), nothing more.
- **q09 `incomingRows` without `isForeignProfile` (re-decided): REJECTED as a bug, agree with Codex.** The filters at activity-rows.ts:107-124 check account and network only. The only feed, `useIncomingTransfers`, resets synchronously on scope change and gates events through `inLiveScope`. No foreign-profile record can reach it. Adding `isForeignProfile` like `journalRows` has would be consistency hardening.
- q03 `commitScannedNote` and q03 `parseNoteAmount`: both sides rejected, no change. q09 `mint_to_commitment` as Mint: not in my scope, no stance.
