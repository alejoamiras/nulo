The headline findings, in plain language

CRITICAL N-01 — Exporting a backup can hang forever or produce a file that refuses to import

What it is. The full-backup export page lets you start the same export twice, and if anything goes wrong mid-way it has no cleanup path. Two exports run side by side on the same connections; a single failure leaves a spinner that never ends, buttons permanently disabled, and copies of your secret keys stuck in memory with nothing able to reach them.

What a user would trigger. Click "Create Backup", get impatient, press Enter again while the password check runs — or the browser quietly restarts the wallet's background during the loop. Worst case, the downloaded backup carries a checksum computed from half-finished data: the file you just exported fails its own tamper check when you try to restore it later.

The fix. Refuse to start while an export is already running (one guard line), always clean up every connection in a finally block, and compute the checksum and the saved body from the same snapshot. The import page next door already does all of this correctly — copy its pattern.

Technical trace

full.vue:102 no latch · :164 status set after awaits · :169/:193-198 shared module binding + unguarded loop · :200 hash/assign gap · :245-258 Enter default re-fires during progress · :118-128 concurrent-ceremony error misrouted to navigate-away. Counter-examples and fix in report.md §N-01.

MAJOR N-02 — Ordinary tab reloads can burn the recovery budget and tell users to reinstall

What it is. When an update ships a data migration and it fails once (say, low disk space), the wallet shows "restart to retry." But every background wake — any dApp tab reloading, the popup opening, a price tick — counts as a retry. Three accidental ones later, the screen flips to "reinstall the extension."

What a user would trigger. Update lands, migration hits a transient error, user keeps browsing. Their tabs reload in the background a few times. Hours later the wallet demands a destructive reinstall for something a single manual retry the next day would have fixed. Dormant today only because no real migrations exist yet — it arms itself exactly at launch.

The fix. Before re-running the engine on boot, check whether a blocked state is already recorded; if so, show the recovery screen without spending another attempt.

Technical trace

Module-top-level runtime.start() (wallet/index.ts:103-111) runs Migrator.run() on every wake; each failure bumps the durable counter (migrator.ts:246) and ≥3 flips terminal (:254); nothing short-circuits on the persisted blocked status (runtime.ts:143-175). RED proof: proofs/c3-1-migration-ambient-burn.proof.test.ts.

MAJOR N-04 — A dApp connection quietly switches identities when you change profiles

What it is. If two profiles have both connected the same dApp before, the dApp's live channel survives a profile switch and starts speaking for whichever profile unlocks next — no prompt, no reconnect, no indication.

What a user would trigger. Connect your Work profile to a dApp. Lock. Unlock Personal in the same browser. The dApp now silently reads Personal's private balances through the old Work-era channel.

The fix. Terminate matching channels when the active profile changes (the session-deleted handler already does exactly this shape), or stamp the opening profile onto the channel and refuse mismatches.

Technical trace

ctx built from current active profile (wallet-sdk/background.ts:681-688); profile-change listener drains discovery only (:392-423); session lookup keyed to active profile (dapp-session/service.ts:114-129). Silent readers bypass popups entirely.

MAJOR N-03 / N-09 — Two ways destructive actions act on the wrong identity

N-03 — account creation racing deletion. Creating an account checks permission first and writes seconds later, unfenced. Delete the profile inside that window and the new account row lands after the purge snapshot — it survives every cleanup, forever, tied to an erased profile. Fix: re-validate the deletion epoch immediately before writing (the transaction service already models this).

N-09 — stale "Delete Profile" modal. After certain updates, a blocking modal asks users to delete their profile for compatibility. It stays until clicked — including across a lock, and across a profile switch done from another wallet window. The click then deletes whichever profile is currently active, not the one the warning was about. Irreversible, wrong-target key deletion. Fix: remember which profile the modal was about when building it.

Technical trace

N-03: account/service.ts:205 gate → :216-218 slow derivation → :229 unfenced write; correct pattern at transaction/service.ts:180-184. N-09: composables/notification.js:27-32; lock branch (app.vue:136-145) never clears notifications; side panel hosts the same shell (manifest.config.ts:28-30).

MAJOR N-05 / N-10 / N-08 — Rapid switching leaves stale work running

N-05. Flip networks twice quickly while the background is restarting, and an abandoned fetch can land last: the account list shows chain A under chain B, and the active account becomes a chain-A address. Balances, send validation, token lists all query the wrong identity until you switch again or reopen.

N-10. Switching A→B→A mid balance-refresh disarms the guards (the token map repopulates), so balances computed against profile B's private state get committed onto profile A's row and displayed.

N-08. The unlock screen's "wait for login" loop doesn't check WHO logged in. A unlock finishing out of order (or from another window) can repaint the UI as profile A while the actual unlocked session is B. And if the bootstrap RPC fails outright, the spinner sticks forever.

The fix family. Every async step that was started for a specific scope should re-check "am I still the current scope/identity?" after each await — the bootstrap code already has this fence; these three surfaces predate it.

Technical trace

N-05: app.vue:100-131 + readiness-before-registration immunity (base-client.ts:121 vs :143). N-10: balance-job-queue.ts:186-293, projector resolves live context (balance-projector.ts:157). N-08: auth.vue:82-84, :107-118; listener rejection unhandled (app.vue:133-146).

MAJOR N-06 / N-07 — Background janitors can destroy things that are merely hidden or waiting

N-06. A corrupted-but-parseable account row is deliberately kept on disk but hidden from normal reads. The orphan-key sweep compares hidden accounts' keys against raw storage and deletes keys whose account "isn't there" — permanently destroying the signing key of an imported account it couldn't see. Imported funds become unreachable from this install.

N-07. Queued dApp requests waiting in line behind a long approval popup are assumed dead after 10 minutes and marked failed — even though everything is alive. Queue three sends, take your time approving, and the third can report "cancelled" right as you approve it.

The fix family. Cleanup must enumerate storage the same way its twin writes do (raw vs decoded), and timeouts must distinguish "pipeline dead" from "waiting in line."

Technical trace

N-06: account/service.ts:114-127 vs raw enumeration imported-keys-repository.ts:49-56; hiding at entity_storage.ts:84-91. N-07: reaper.ts:72-82; heartbeat starts at lane wait only (execution-lane.ts:243). RED proof for N-07: proofs/c2-1-reaper-vs-fifo-waiter.proof.test.ts.

MAJOR N-11 — The safety-net lock timer can let two critical sections run at once

What it is. Locks force-release after five minutes as a deadlock safety net. But when the stuck operation eventually finishes, its cleanup unlocks whatever is holding the lock NOW — letting a third task in while the second still holds it.

What a user would trigger. Any wedged chain call (slow node, hung offscreen) longer than five minutes followed by continued use. Two "exclusive" sections overlap; downstream this exact theft resurrects records of deleted tokens (N-17).

The fix. Hand every acquisition an owner token and make release a no-op for anyone else. Ten lines; fourteen locks benefit. Known-and-deferred until now — this audit supplies the first concrete harm scenario plus a failing test.

Technical trace

wallet-core/utils/lock.ts:63-68 watchdog calls unconditional leave(); :92-106 leave clears the CURRENT timer + flag. RED proof: proofs/p1-1-lock-double-release.proof.test.ts. Harm instance: N-17 (incoming-transfer/service.ts:1045-1124).
