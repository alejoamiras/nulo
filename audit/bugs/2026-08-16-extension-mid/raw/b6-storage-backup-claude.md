# Cluster b6-storage-backup — Findings Report

## Findings

None. Every lead from the mapping phase was verified against source and either does not hold, or is explicitly characterization-pinned as intentional. Extended scanning across all in-scope files (edge cases, races, error paths, resource leaks, bounds, retries, init order, caching) did not surface a fresh issue meeting the certificate bar (concrete counter-example + high/moderate repro confidence). See non-findings below for the verification trail.

## Non-findings considered

- **Lead: `Lock` `MAX_HOLD_MS` force-release → double-release corrupting queue state.** Verified concretely: `packages/wallet-core/src/utils/lock.ts:50-59` arms one force-release `setTimeout` per acquisition; when it fires it calls `this.leave()` (line 53) which hands the lock to the next waiter. If the ORIGINAL holder's own `leave()` (e.g. from a `withLock` `finally`) later fires, it re-enters `leave()` (line 78), clears the *new* holder's timer, sets `this.locked = false` while the new holder is still mid-flight, and `dispatch()` (line 103-108) can grant the lock to a *third* caller — genuine concurrent-holder corruption. This is not a fresh finding: `lock.test.ts:231-269` ("withLock: force-release interplay is identical to a hand-rolled frame") explicitly exercises this exact sequence and its comment states it is "the pre-existing double-release hazard, pinned as today's behavior, deliberately NOT fixed in this arc." Per the negative list, a characterization-test-pinned behavior is intentional — dropped.
- **Lead: `ReadWriteGuard` per-token force-release racing a writer's mid-flight writeback.** Verified against `rw-guard.ts`: the force-release timer (`startForceReleaseTimer`/the callback at lines 160-194) only ever inspects/expires entries in `readerTokens` — there is no timer, ceiling, or expiry path for `writeActive`/`writeWaiters` anywhere in the class. Writers are never force-released; the doc comment explicitly says the mechanism is "NOT a mechanism for a writer to force past live work." The lead's premise (a writer being force-released mid-writeback) has no corresponding code path — non-finding. (The adjacent, real "reader force-released while its real work is still in flight, then hands the write slot to a new writer" behavior is a different, already-pinned scenario — see `rw-guard.test.ts:503-545`, "serialized long readers," and the extensive header comment referencing "concurrency audit HIGH #3" — also intentional.)
- **Lead: `row-map-migration.ts` `remapValues`/`retype` prototype pollution via `__proto__` as a row id or field.** Verified the full pipeline: `canonicalizeTransformMap`/`cloneJsonObject` (lines 154-214) reject any `__proto__` own key, symbol key, non-plain prototype, or accessor descriptor in the DSL data at define time; `validateTransform` (lines 218-281) rejects `__proto__` as a `rename` source/target or as any other clause's field name; `applyRowTransform`'s `{ ...row }` clone (line 291) uses spread's `CreateDataProperty` semantics, which — per JS spec — creates a literal own `"__proto__"` data property rather than invoking the inherited setter, so even a JSON-parsed row carrying a literal `"__proto__"` key cannot repoint the object's prototype; and the storage-key scheme (`${root}@${id}`) always contains a code-fixed root plus `"@"`, so no attacker-controlled row id can ever produce a literal `"__proto__"` storage key. `footprint-coverage.test.ts:303-405` ("accessor smuggling," "array species/iterator smuggling," "proto smuggling…") and `backup-migration-registry.test.ts:88` ("config toStored preserves a `__proto__` key faithfully…", using `Object.create(null)` at `backup-migration-registry.ts:160`) pin exactly this defense, called out in-file as "rejected 4× in audit." Non-finding.
- **Lead: `EntityStorage` drop-vs-keep dual policy causing a codec-validation failure to surface on a write-path read.** `EntityStorage` (`entity_storage.ts`) has no internal read-modify-write coupling — `get`/`getAll`/`getValues` (decode) and `set`/`delete` (write) are fully independent methods; nothing in the module itself chains a decode failure into a write. The scenario the lead gestures at (a caller doing `get()` → sees `undefined` for a validation-KEPT row → blindly `set()`s a fresh default over it, destroying the recoverable row) would require a caller pattern in one of the 29 `apps/extension/src/wallet/services/*` consumers, which are outside this cluster's scope and were not confirmed to exist. Per "if you cannot provide a counter-example, do not speculate," dropped.
- **Lead: `Migrator` "NEVER throws" contract, incl. journal-write failures mid-checkpoint.** Traced every path: `run()` (`migrator.ts:123-133`) wraps the entire `runInner()` call tree in try/catch, and since `runInner`/`applyOne`/`resumeIfInterrupted`/`restore`/`bumpAttempts` are all `async`, any synchronous throw or rejected promise anywhere in that tree becomes a promise rejection caught by `run()`'s outer try. The one edge case that looked promising — `stamped=true` but the subsequent `store.remove(SCHEMA_BACKUP_KEY)` cleanup throws (line 224-231) — is explicitly pinned by `migrator.test.ts:425` ("a cleanup failure AFTER the stamp is SUCCESS — never a restore under the stamped version") and correctly self-heals via `resumeIfInterrupted`'s debris-sweep branch (lines 277-282) on the next boot. The only thing that *can* throw outside `run()`'s guard is the `Migrator` constructor itself (duplicate/non-integer version — `migrator.ts:104-108`), but that requires a migration-authoring bug (not a user-triggered or environmental condition), `realMigrations` is currently empty, and `registry.test.ts` structurally guards against exactly this. Non-finding.
- **`apps/extension/src/utils/storage.ts` `migrationIdle()` check-then-subscribe race.** The file's own header comment already documents and accepts this exact TOCTOU ("Residual TOCTOU, accepted: the barrier is check-then-act, not a lock…", lines 20-25), and the implementation includes the standard re-check-after-subscribe mitigation (lines 42-49). Already-documented, accepted design — not a fresh finding.
- **`EntityStorage.decodeRow`'s fire-and-forget malformed-row delete racing a caller's immediate `set()` on the same id.** Plausible in the abstract (the delete in `decodeRow`, `entity_storage.ts:69-72`, is dispatched but not awaited before `get()`/`getAll()` return), but establishing it as a real lost-update requires (a) a concrete caller doing "read → if undefined, write a default" immediately after, which lives outside this cluster's scope, and (b) an assumption about `chrome.storage.local`'s cross-call completion ordering not documented anywhere in this code. Insufficient confidence to report; noted for awareness only.
- **`ServiceCollection.start()` partial-phase failure.** `base/index.ts:65-70` runs `Promise.all(phase.map(svc => svc.start(this)))` per topological phase; if one service in a phase rejects, `Promise.all` rejects immediately while sibling services in the same phase continue running in the background, uncoordinated, and no later phase starts. This is a boot fail-fast characteristic, not a data-corruption/wrong-result bug, and nothing in the module claims stronger guarantees — treated as a design characteristic, not a finding.

## Quality handoffs

- `apps/extension/src/wallet/services/backup/README.md` and `backup-migration-registry.ts` reference an `IMPORT_BLOCKING_ACK` acknowledgment mechanism (used by `footprint-coverage.test.ts`) that isn't itself in this cluster's file list — worth the quality pass confirming it's still exercised now that `realMigrations` is empty.
- Cross-cluster note (not this cluster's to fix): `runtime.ts`'s boot sequence runs the `Migrator` before `services.add(...)`, but `chrome.alarms.onAlarm` for `PRICE_REFRESH_ALARM_NAME` is registered synchronously at module scope in `src/wallet/index.ts`, before `runtime.start()` even begins. If that alarm fires during the migration window, its handler (in `price/service.ts`, outside this cluster) could write `chrome.storage.local` directly (SW-side code is allow-listed past the storage-facade ban) concurrently with the migrator's footprint snapshot/commit. Recommend whichever cluster covers `runtime.ts`/`price/` verify this window is actually unreachable (e.g., alarm handler no-ops until services are constructed).
