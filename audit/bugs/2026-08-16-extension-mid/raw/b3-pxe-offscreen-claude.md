### Finding: Timed-out `openChainStore` open leaves an unbounded zombie SQLite-OPFS worker holding the SAH-pool lock, letting a same-chain retry hang/deadlock indefinitely

1. **Title**: `openChainStore`'s 30s timeout doesn't cancel the underlying worker, so a retry against the same chain can wedge that chain's PXE for the rest of the session.
2. **Severity**: Critical — high-impact (that chain's PXE becomes permanently unusable: every send/receive/prove op on it fails) under a realistic but specific timing condition (slow/contended OPFS worker init), with no user-facing recovery short of a browser/extension restart.
3. **Repro confidence**: moderate — the code trace is exact and cross-checked against the vendored `@aztec/kv-store` sources, but triggering the underlying "worker init takes/exceeds 30s" condition depends on device/OPFS environment I can't execute directly.
4. **Type**: resource leak (primary) / bad retry-or-timeout (secondary).
5. **Counter-example**:
   - `openChainStore` (`packages/aztec-runtime/src/pxe/opfs-store.ts:56-95`) races the real `AztecSQLiteOPFSStore.open(...)` (`openPromise`) against a 30s `setTimeout`. Confirmed against the vendored SDK (`~/nargo/.../kv-store/src/sqlite-opfs/{store.ts,worker.ts}`): `AztecSQLiteOPFSStore.open()`'s own `worker.terminate()` cleanup only fires on an explicit rejection of its internal `#sendRequest`, never on a hang — and `worker.ts`'s own comment confirms `installOpfsSAHPoolVfs` "acquires an exclusive lock on the OPFS SAH directory" and can hang when a prior handle hasn't released it.
   - When the 30s timer wins, `openChainStore` throws (`opfs-store.ts:76`) and schedules a **fire-and-forget** `openPromise.then((s) => s.close()...)` (`opfs-store.ts:86`) — but nothing bounds `openPromise` itself; if it never settles, the worker (and the SAH-pool lock it holds/is acquiring) is never released.
   - This throw propagates unguarded through `ProductionPxeFactory.createChainRuntime` (`chain-runtime.ts:140-174`, the `openChainStore` call at line 158 is not wrapped in any cancellation) → `ChainRuntimeRegistry.ensure` (`chain-runtime.ts:304-315`) → `PxeService.withPxeWrite`/`withPxeRead`'s `chainGuard.write(...)`/`chainGuard.read(...)` callback (`service.ts:842-849`, `875-899`).
   - `ReadWriteGuard.write()`'s `finally { this.releaseWrite() }` (`packages/wallet-core/src/utils/rw-guard.ts:109-116`) releases the per-chain lock **as soon as the callback's promise settles** — i.e. at the 30s mark — regardless of whether the abandoned `openPromise` is still running.
   - A retry of the same op (confused user re-clicking "send", or any caller-level retry) re-enters `withPxeWrite`/`withPxeRead` for the SAME `(profileId, chainId)`, and `ChainRuntimeRegistry.ensure` calls `openChainStore` again on the SAME `chainDataDir` pool directory — spawning a second worker that competes for the SAME exclusive SAH-pool lock the first (zombie) worker may still hold or be acquiring. This can hang for another 30s, or forever if the first worker never resolves.
6. **Violated invariant**: the module's own stated intent — "close that abandoned store so it can't permanently wedge every later open of this dir" (`opfs-store.ts:82-85`) — depends on the abandoned open eventually settling, which is not guaranteed; the exact "permanently wedge every later open of this dir" outcome the comment is written to avoid remains reachable.
7. **Failing path**: `openChainStore` (`opfs-store.ts:56`) times out → `ProductionPxeFactory.createChainRuntime` (`chain-runtime.ts:158`) rejects → `ChainRuntimeRegistry.ensure` (`chain-runtime.ts:312`) rejects → `PxeService.withPxeWrite` (`service.ts:893`) releases the chain guard and rethrows → caller retries → `ChainRuntimeRegistry.ensure` → `openChainStore` again on the same directory, contending with the still-live zombie worker.
8. **Expected vs actual**: expected — a bounded 30s failure that a retry can cleanly recover from once the environment is no longer contended. Actual — the SAH-pool lock (and the Worker holding/racing for it) is unbounded, so a retry on the same chain directory can reproduce the same 30s hang indefinitely, with no automatic recovery until the offscreen document is torn down (the existing `isOffscreenHealthy` ping/pong check only verifies the document's message loop, not per-chain PXE liveness, so it never detects or recycles this wedge).
9. **Recommended fix**: track the in-flight (possibly abandoned) open per `chainDataDir` and single-flight subsequent opens against it (mirroring `apps/extension/src/wallet/utils/offscreen.ts`'s `ensureInFlight` pattern) instead of racing a brand-new worker against a zombie one; alternatively, terminate the underlying `Worker` deterministically on timeout so the lock is released synchronously rather than left to a best-effort background `.then()`.
10. **Instances**:
    - `packages/aztec-runtime/src/pxe/opfs-store.ts:56-95`
    - `packages/aztec-runtime/src/pxe/chain-runtime.ts:140-174`
    - `packages/aztec-runtime/src/pxe/chain-runtime.ts:304-315`
    - `packages/aztec-runtime/src/pxe/service.ts:842-849`, `875-899`

### Finding: Firefox `createOffscreen` has no pass-fence on `firefoxOffscreenWindowId`, so a late `chrome.windows.create()` clobbers a live successor pass's window handle

1. **Title**: unfenced `firefoxOffscreenWindowId` assignment in the Firefox offscreen-create path leaks the live window and mistargets future close/health checks.
2. **Severity**: Major — leaks a live offscreen window (with its own running `PxeService`) and breaks the module's liveness/close tracking; compounds into duplicate RPC processing given the un-scoped SW↔offscreen broadcast transport. Firefox-only, requires a specific timing window.
3. **Repro confidence**: moderate — the missing fence is directly verifiable in source and is asymmetric with the Chromium branch's explicit fence in the same function; the Firefox-only trigger timing isn't independently executable here.
4. **Type**: resource leak (primary) / state invariant violation (secondary).
5. **Counter-example**:
   - Pass A (Firefox build): `createOffscreen(passIdA)`'s Firefox branch (`apps/extension/src/wallet/utils/offscreen.ts:228-243`) calls `chrome.windows.create(...)`, which doesn't resolve within `READY_TIMEOUT_MS` (10s, `offscreen.ts:16`).
   - `onOffscreenTimeout` fires (`offscreen.ts:92-104`): bumps `passSeq`, calls `closeOffscreen()` — but `firefoxOffscreenWindowId` is still `null` (pass A's `windows.create()` hasn't resolved yet), so the Firefox branch of `closeOffscreen()` (`offscreen.ts:169-176`) is a no-op; the caller's promise rejects.
   - Pass B: a later `ensureOffscreenRunning()` call sees `isOffscreenAlreadyRunning()` (`offscreen.ts:260-270`) still false (`firefoxOffscreenWindowId === null`), so it creates fresh via `createOffscreen(passIdB)`; its `chrome.windows.create(...)` resolves quickly, sets `firefoxOffscreenWindowId = winB.id` (`offscreen.ts:237`), and the pass completes successfully (READY received).
   - Pass A's original `chrome.windows.create(...)` now finally resolves. Its continuation (still running, unlike the Chromium branch which checks `passId === passSeq` at `offscreen.ts:212`) executes `firefoxOffscreenWindowId = winA.id ?? null` (`offscreen.ts:237`) **unconditionally**, clobbering the tracked handle for the live, in-use `winB`.
   - Effect: `winB` (the actual live offscreen document/PXE host) is now untracked and never closed; a future `closeOffscreen()` targets `winA` instead (`offscreen.ts:169-176`); `isOffscreenAlreadyRunning()`'s Firefox check now reasons about the wrong window. The F-10 self-close mechanism doesn't rescue this: `firefoxInstanceToken()` (`offscreen.ts:57-61`) is memoized once per SW lifetime, not per pass, so `winA` and `winB` carry the SAME instance token and neither self-closes on the other's ADOPT broadcast (`isSupersededByAdopt` only fires on a *differing* token).
   - Amplifying consequence: the SW↔offscreen RPC transport (`packages/extension-messaging/src/offscreen/{client.ts:46,59-65; service.ts:34,41}`) is a `chrome.runtime.sendMessage`/`onMessage` broadcast matched only by the fixed `PXE_SERVICE_NAME`, not a per-document channel — so both `winA`'s and the leaked `winB`'s independent `PxeService` instances receive and independently process every subsequent PXE RPC (e.g. `proveTx`/`clearProfileState`), each against the same on-disk store, compounding the SAH-pool contention from the prior finding.
6. **Violated invariant**: the module's own documented purpose for `passSeq`/`offscreenPromise` — preventing "a timed-out pass's zombie continuation" from "tear[ing] down the new pass's live document" (`offscreen.ts:106-111`) — is enforced only in the Chromium branch of `createOffscreen`; the structurally parallel Firefox branch performs the equivalent state mutation with no such guard.
7. **Failing path**: `createOffscreen(passIdA)` (`offscreen.ts:228`) → `chrome.windows.create` resolves late → `firefoxOffscreenWindowId = winA.id` (`offscreen.ts:237`, no `passId===passSeq` check) → `closeOffscreen()` (`offscreen.ts:169-176`) and `isOffscreenAlreadyRunning()` (`offscreen.ts:260-270`) both now operate on the wrong window while `winB` runs untracked.
8. **Expected vs actual**: expected — a stale pass's late-resolving create should be recognized as superseded and closed (mirroring the Chromium ghost-bug handling), never adopted as the tracked window. Actual — it silently becomes the tracked window, orphaning the real live one.
9. **Recommended fix**: gate the Firefox branch's `firefoxOffscreenWindowId` assignment (and the ADOPT broadcast) behind the same `passId === passSeq` check already used in the Chromium branch (`offscreen.ts:212`); on a stale pass, close the just-created window instead of adopting it.
10. **Instances**:
    - `apps/extension/src/wallet/utils/offscreen.ts:224-243`
    - `apps/extension/src/wallet/utils/offscreen.ts:160-177`
    - `apps/extension/src/wallet/utils/offscreen.ts:260-270`
    - `apps/extension/src/wallet/utils/offscreen.ts:57-61`

## Non-findings considered

- MAP-FLAGGED HAZARD (ArtifactRegistry `knownMemo`/`clear()` race): verified `ArtifactRegistry.clear()` is never called anywhere in production (`clearChainState`/`clearProfileState` in `pxe/service.ts` don't call it, and no other call site exists repo-wide) — the flagged concurrent-clear race is unreachable; separately, since class-ids are content-addressed, even a hypothetical stale repopulation can't produce a wrong artifact for a given class-id. No counter-example.
- `chainGuards` never removed on `clearChainState`: confirmed intentional and documented (`service.ts:120-121`) — the guard is a bare mutex holding no chain-scoped data; resurrection is independently fenced by `chainPurgeEpochs`, so reuse across a purge epoch is harmless. No counter-example.
- `offscreen.ts` passSeq fence + `Promise.race([creating, ready])` interleavings (Chromium path): the exact interleavings named in the lead (health-check-timeout, createDocument-hang, adjacent ensure calls) are pinned by characterization tests (`offscreen.test.ts`: "createDocument hanging past the 10s gate...", "a timed-out pass's ZOMBIE create rejection cannot retry into a successor pass...") and traced correctly in source; the one gap found is Firefox-only (see Finding 2).
- `pxe/client.ts` (extension) module-level `storeKeyProvider`/`generationProvider` SW-restart ordering: traced `runtime.ts` — registration (`registerPxeStoreKeyProvider`/`registerPxeGenerationProvider`) runs synchronously, with no `await` between service construction and these calls, and the earliest point any `chrome.runtime` message could be dispatched to a service RPC listener is after `logger.rehydrate()`'s `.then()` in `src/wallet/index.ts`, by which point both providers are already registered. No reachable window found.
- `PxeServiceClientBase.request()`'s `PXE_STORE_KEY_MISSING` single-retry re-sending the same captured `pxeGeneration`/args (`pxe/client.ts:153-168`): traced for double-processing/duplicate-provision risk — the retry re-sends the identical args after an awaited `provisionChainStoreKey` completes; no interleaving found that duplicates a state-mutating op.
- `withPxeRead`'s `purgeEpochAtEntry` captured once before the 3-attempt rebind loop (`service.ts:828`) and reused across all attempts: this is the intended "did a purge happen since I entered" semantics, not a stale-capture bug.
- `Promise.race([creating, ready])` not `await`ing `creating` on the ready-win path (`offscreen.ts:330-337`): explicitly documented and accepted as a benign rare-race by the code comment; not pursued further.
