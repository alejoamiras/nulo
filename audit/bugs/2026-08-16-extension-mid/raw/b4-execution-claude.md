## Findings Report — Cluster b4-execution

### Finding: dApp-facing `send_transaction` operations bypass the ExecutionMutex, defeating its double-spend/interleaving protection

1. **Title**: `executeSendTransaction` never acquires the per-`(profileId, chainId)` `ExecutionMutex`, unlike its two sibling dApp-send pipelines.

2. **Severity**: Critical — high-impact (nullifier double-spend / tx rejection / racing PXE simulate-prove state) under a realistic, non-hostile timing/state (two approved dApp operations reaching execution close together for the same account/chain), which is exactly the scenario the mutex module documents as its reason for existing.

3. **Repro confidence**: high (fully verified by static trace of the production call graph; the omission is structural, not timing-dependent to observe in code).

4. **Type**: race (primary) / state invariant violation (secondary — violates the module's own documented "two approved sendTx must never interleave simulate/prove" contract).

5. **Counter-example**: A connected dApp calls the Nulo-custom `grantPublicAuthwit` wallet-sdk method twice in quick succession (or once, racing an in-flight `aztec_sendTx`/transfer on the same account). Both calls build a `{ kind: "send_transaction", ... }` operation (`packages/wallet-bridge/src/dispatcher.ts:802-818`) and flow through `DappInteractionService.execute()` → `ExecutionService.executeOperations()` → `case "send_transaction": this.executeSendTransaction(operation, ...)` (`apps/extension/src/wallet/services/execution/service.ts:530-532`) → `DappSendExecutor.executeSendTransaction()` (`apps/extension/src/wallet/services/execution/dapp-send-executor.ts:373-460`). That method never calls `this.deps.lane.acquireSlot(...)` — it goes straight from journal creation to `buildAndEstimateValidated` → `coordinator.proveAndSend`. Both calls can therefore run `pxe.simulateTx`/`pxe.proveTx` concurrently against the same PXE runtime/account, exactly the "T1 and T2 simulate against the same private-note snapshot" scenario `execution-mutex.ts`'s header says the mutex exists to prevent.

6. **Violated invariant**: `execution-mutex.ts:1-29` and `execution-lane.ts:66-74` document: "Hold the mutex from before authwit discovery through submit, for **both** send paths" and "two approved sendTx can both reach execution" once the popup-approval FIFO baton releases — the mutex is what re-serializes them. `dapp-send-executor.ts`'s own file header (lines 6-14) states as a class-wide invariant: "Unlike the transfer flow, dApp sends **DO** take an execution slot... The slot... all live behind `deps.lane`." `mark-failed-unless-cancelled.ts`'s header groups `executeSendTransaction` / `executeAztecSendTx` / `executeNoFromSendTx` together as "the three dapp-send pipelines." The implementation of `executeSendTransaction` breaks that invariant for itself while `runInSlot` (used by the other two, `dapp-send-executor.ts:175-237`) correctly enforces it.

7. **Failing path**:
   - `packages/wallet-bridge/src/dispatcher.ts:802-825` `handleGrantPublicAuthwit` builds a `send_transaction` op (dApp-reachable, no user-confirmation-bypass required if the session has a standing grant) →
   - `apps/extension/src/wallet/services/execution/service.ts:489-533` `executeOperations` dispatches `case "send_transaction"` straight to `this.executeSendTransaction(...)`, no lock acquired around the switch →
   - `apps/extension/src/wallet/services/execution/service.ts:720-724` thin RPC wrapper `ExecutionService.executeSendTransaction` → `dappSendExecutor.executeSendTransaction(...)` →
   - `apps/extension/src/wallet/services/execution/dapp-send-executor.ts:373-460` `DappSendExecutor.executeSendTransaction` — journal `beginJournal` → `markJournal({stage:"simulating"})` → `buildAndEstimateValidated` → `coordinator.proveAndSend` → `finally` releases only the controller, never a mutex slot (contrast with `runInSlot`, lines 175-237, used by `executeAztecSendTx`/`executeNoFromSendTx`, which explicitly does `await this.deps.lane.acquireSlot(...)` before any of this work).
   - Same unprotected path is also reachable from **UI** code: `apps/extension/src/wallet/services/auth-registry/service.ts:200` (`revokeAuthwits`) and `:247` (`setRegistryEnabled`) both call `executionService.executeSendTransaction(...)`, so a Settings-page authwit revoke can also race a concurrently-approved dApp `aztec_sendTx`/NO_FROM send on the same account.

8. **Expected vs actual behavior**: Expected — every operation kind that runs the build→simulate→prove→submit pipeline against a shared PXE/account is serialized per `(profileId, chainId)` via `ExecutionMutex`, as documented. Actual — `send_transaction`-kind operations (dApp `grantPublicAuthwit`, and UI `revokeAuthwits`/`setRegistryEnabled`) run this same pipeline with zero serialization against any other in-flight send (dApp or UI) on the same account/chain, so two such operations — or one of these plus an `aztec_sendTx`/NO_FROM send — can simulate/prove concurrently against stale private-note state, producing an on-chain-rejected (double-spent-nullifier) transaction or corrupted concurrent PXE simulation state instead of the documented FIFO-serialized outcome.

9. **Recommended fix**: Route `DappSendExecutor.executeSendTransaction` through the same `runInSlot` scaffold that `executeAztecSendTx`/`executeNoFromSendTx` already use (acquire the slot before the journal claim / any PXE work, release in `finally`), matching the pattern at `dapp-send-executor.ts:493-507` and `:660-674`. This also automatically gets it the origin/lane backpressure caps and abort-on-cancel wiring the other two paths already have.

10. **Instances** (same root cause — missing `acquireSlot`):
    - `apps/extension/src/wallet/services/execution/dapp-send-executor.ts:373-460` (`executeSendTransaction` itself)
    - `apps/extension/src/wallet/services/execution/service.ts:530-532` (dispatch site, no wrapping lock either)
    - `apps/extension/src/wallet/services/execution/service.ts:720-724` (direct RPC entry point)
    - `apps/extension/src/wallet/services/auth-registry/service.ts:200` and `:247` (UI callers of the same unprotected path)
    - `packages/wallet-bridge/src/dispatcher.ts:802-825` (dApp caller — `grantPublicAuthwit`, the externally-triggerable reproduction vector)

## Non-findings considered

- `JournalReaper`'s 35-min `proving`-stage grace window vs the ExecutionMutex's documented "no force-release" — verified NOT a bug: `PxeServiceClient`'s `proveTx` RPC has its own 30-min client-side timeout (`packages/aztec-runtime/src/pxe/client.ts:69`), and the journal enters `proving` immediately before that RPC call (`execution-coordinator.ts:168-170`), so a genuinely-live prove is always caught and failed by the client timeout with 5 minutes of margin before the reaper's grace would ever fire; SW-restart mid-prove is separately covered by the reaper's unconditional boot sweep.
- `bridge-core/fee-juice.ts`'s `predictedWorstMinFees` narrow regex catch (only "not found/not supported/unimplemented" messages fall back to `getCurrentMinFees`) — verified intentional and correctly conservative; every extension call site (`fee-strategy.ts`, `fpc-strategy.ts`, `transfer-estimate-reuse.ts`, `operation-estimate-reuse.ts`) either lets a thrown error propagate to the normal failure path or treats it as "don't reuse, rebuild" — no swallowed/mis-handled error found.
- `ExecutionMutex.laneDepth`/`originDepth` counter drift on abort — traced multiple overlapping-abort FIFO scenarios (abort while queued, GC-key ownership handoff to a later waiter, chained `prior.finally(release)`); the decrement is provably single-fire and always eventually happens, no drift found.
- `EstimateCancelRegistry` cancel-before-admit / cancel-after-settle / double-cancel — all three explicitly handled (silent no-op for unknown tokens, `settled` map for post-completion eviction, idempotent `abortEntry`); matches the module's own documented contract, not a bug.
- `GasBalanceReader` / `TransferEstimateReuse` / `OperationEstimateReuse` TTL caches across profile/network switches — all three are correctly keyed or actively invalidated: `GasBalanceReader.evictAll()` is wired to `onActiveProfileChanged` (`service.ts:354`), and the two estimate-reuse caches re-validate profile id, endpoint identity, chain identity, and pending-tx set on every `tryConsume` — no stale-read path found.
- `TransferExecutor`'s deliberate omission of the execution slot ("this flow takes NO execution slot... Do NOT harmonize with the dApp-send flow", `transfer-executor.ts:16-17`) — explicitly documented as an intentional preserved quirk, not flagged (distinct from the `executeSendTransaction` finding above, which contradicts its own file's stated invariant rather than documenting an exception to it).
- `JournalGC`'s per-scope cap only evicting `succeeded` records — verified intentional (QA feedback 2026-06-05, documented data-loss rationale for keeping failed/cancelled records uncapped).
- `EstimateCancelRegistry.sweep()` only running at the top of `admit()` (a fully-idle registry with a dead active entry isn't reaped until the next request) — self-heals on the very next `admit()` call from any profile; no observable wrong-result window.
