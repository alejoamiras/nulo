# Findings: b1-session-crypto

### Finding: `SessionManager.open()`/`close()` swallow storage-write failures, leaving the reported RPC outcome contradicted by actual session state
- **Severity:** Critical
- **Repro confidence:** high
- **Type:** wrong result (primary) / state invariant violation (secondary)
- **Counter-example:** Mock the injected `browserApi.storage.session.set` (or the real `chrome.storage.session.set`) to reject once — a realistic failure (`QUOTA_BYTES` exceeded, or "Extension context invalidated" firing mid-write during an MV3 SW-teardown race). Call `ProfileService.unlockProfile(id, password)` (or `createProfile`, `createPasskeyProfile`, `unlockPasskeyProfile`, `finalizeRestore`, any password-change reopen). `openSessionVerified` → `SessionManager.open()` at `apps/extension/src/wallet/services/profile/session-manager.ts:202-233` runs `await this.session.set(session)` (line 221) **before** `this.activeSession = {...}` (line 223); the storage-write throw is caught at lines 230-232, logged, and swallowed — `open()` resolves normally (`void`), never assigning `activeSession`. `openSessionVerified` (`apps/extension/src/wallet/services/profile/service.ts:804-865`) does not check `sessionManager.isActive(profile.id)` after calling `open()` — it only re-checks the *deletion* fence — so `unlockProfile` returns a resolved `ProfileInfo` to the popup as a success. The wallet is, in fact, still locked: the very next `getActiveProfile()`/`getSecret()` call throws "Profile locked". Mirror case: mock `session.delete()` to reject and call `lockActiveProfile()` — `SessionManager.close()` (lines 238-254) catches the delete failure at 251-253 and never reaches the `activeSession = undefined` assignment (241-244), so the RPC resolves as "locked" while the master secret stays live in memory.
- **Violated invariant:** `session-manager.ts`'s own header/method doc states the intended contract explicitly: *"Failures are logged but swallowed — historically `_openSession` did the same because a broken chrome.storage write at unlock time still leaves the in-memory secret usable for the current popup lifetime. We keep that behavior; the facade's test coverage pins it."* The code does the opposite of what's documented — the storage write is ordered *before* the in-memory mutation, so a write failure discards the in-memory session too. (Contrast with the sibling `refresh()` method at lines 259-278, which mutates `session.session.since/lockedAt` on the shared in-memory object *before* calling `this.session.set(...)`, so a write failure there does *not* lose the in-memory update — the asymmetry between `open()`/`refresh()` is itself a tell.) No test in `session-manager.test.ts` or `service.integration.test.ts` exercises a storage-write failure on `open()`/`close()` despite the doc's claim that "test coverage pins it" — confirmed via grep, no hits.
- **Failing path:** `ProfileService.unlockProfile` (`service.ts:300-366`) → `openSessionVerified` (`service.ts:804-865`, no post-open `isActive` check) → `SessionManager.open` (`session-manager.ts:202-233`) → `this.session.set(session)` throws (`session-manager.ts:221`) → caught + logged (`session-manager.ts:230-232`) → `open()` resolves → `openSessionVerified` returns normally → `unlockProfile` resolves `ProfileInfo` to the caller. Symmetric path for `lockActiveProfile` (`service.ts:551-556`) → `SessionManager.close` (`session-manager.ts:238-254`) → `this.session.delete()` throws (line 240) → caught (251-253) → `activeSession` never cleared.
- **Expected vs actual:** Expected — per the class's own doc — a storage-write failure during `open()` should still leave the in-memory secret usable (i.e., `activeSession` set), and the RPC caller's "success" should mean the wallet is genuinely unlocked. Actual — the wallet stays locked internally while the RPC reports success. Symmetrically for `close()`/lock: a storage-write failure should not silently leave the wallet unlocked while reporting "locked" to the caller.
- **Recommended fix:** Reorder `open()` (and `close()`) the same way `refresh()` already does: mutate the in-memory `activeSession` (or clear it) first, then attempt the storage write, so a persistence failure degrades to "in-memory-only, will re-prompt after next SW restart" instead of silently failing the whole operation. Additionally, `openSessionVerified`/`lockActiveProfile`/`lockProfileIfActive` should assert the post-call state (`sessionManager.isActive(...)`) matches what was requested before resolving success to the RPC caller, or `SessionManager.open`/`close` should rethrow so the facade can surface a real error instead of a false-positive success.
- **Instances:** `apps/extension/src/wallet/services/profile/session-manager.ts:202-233` (`open`), `:238-254` (`close`); `apps/extension/src/wallet/services/profile/service.ts:804-865` (`openSessionVerified`, missing post-open verification, reached from `createProfile:260-292`, `unlockProfile:300-366`, `createPasskeyProfile:377-423`, `unlockPasskeyProfile:443-511`, `changeProfilePassword` reopen `:690-709`, `importPasswordProfile:1254-1276`, `importPasskeyProfile:1282-1319`, `finalizeRestore:1541-1607`); `service.ts:551-556` (`lockActiveProfile`), `:564-571` (`lockProfileIfActive`).

### Finding: `unlockPasskeyProfile`'s F-007 credential-binding check throws before the recovered master secret is zeroized
- **Severity:** Major
- **Repro confidence:** high
- **Type:** resource leak (primary) / state invariant violation (secondary)
- **Counter-example:** Call `unlockPasskeyProfile(id, credentialData)` where `credentialData` resolves (via `acquireRecovery`/`recoverFromCredentialData`) to a credential whose id differs from the profile's stored `credentialId` — the exact scenario the code's own comment anticipates as reachable in normal operation ("Credential rotated (delete + reimport with different passkey) during prompt", `service.ts:499-502`), or simply a popup bug/stale snapshot passing the wrong credential. At `apps/extension/src/wallet/services/profile/service.ts:480-482`:
  ```
  if (recovery.credentialId !== snapshot.credentialId) {
      throw new Error("Invalid profile id")
  }
  ```
  This throw happens **before** the `try { ... } finally { zeroize(recovery.secret) }` block that starts at line 485. `recovery.secret` — the WebAuthn-PRF-derived 32-byte master secret for the (wrong) credential — is never passed to `zeroize()` on this path.
- **Violated invariant:** The package-wide "every exit path reaches `zeroize()`" discipline (`packages/wallet-crypto/src/session-secret-box.ts`'s `unwrap()` was explicitly restructured to fix exactly this class of bug — see its comment: "previously returned from the decode catch before either buffer was wiped"). The other two call sites implementing this identical F-007 binding check both correctly zeroize on the mismatch throw: `exportPlain` at `service.ts:1110-1117` wraps the check in `try { if (mismatch) throw } finally { zeroize(recovery.secret) }`, and `restore()`'s passkey branch at `service.ts:1451-1454` explicitly calls `zeroize(recovery.secret)` immediately before throwing. `unlockPasskeyProfile` is the one sibling that skips this.
- **Failing path:** `ProfileService.unlockPasskeyProfile` (`service.ts:443-511`) → phase 2 `acquireRecovery` (line 473) → credential mismatch check (`service.ts:480-482`) → `throw new Error("Invalid profile id")` → function exits without reaching the `finally` at line 507-510.
- **Expected vs actual:** Expected — matching the two sibling call sites — `recovery.secret` is zeroized regardless of which branch throws. Actual — on this specific (and, per the code's own comments, realistic) mismatch path, the raw master-secret bytes are left to linger un-zeroized until GC.
- **Recommended fix:** Wrap the F-007 check the same way `exportPlain` does: `try { if (recovery.credentialId !== snapshot.credentialId) throw new Error("Invalid profile id") } finally { if (thrown) zeroize(recovery.secret) }`, or simply call `zeroize(recovery.secret)` immediately before the `throw`, mirroring `restore()`'s passkey branch.
- **Instances:** `apps/extension/src/wallet/services/profile/service.ts:480-482` (bug). Correct sibling patterns for comparison: `service.ts:1110-1117` (`exportPlain`), `service.ts:1451-1454` (`restore()` passkey branch).

### Finding: Abandoned passkey full-backup restore leaves the recovered master secret parked un-zeroized in `pendingRestoreSecrets` indefinitely
- **Severity:** Major
- **Repro confidence:** high
- **Type:** resource leak (primary) / state invariant violation (secondary)
- **Counter-example:** Start a passkey full-backup import via `useFullBackupImport.restoreBackup()` (`apps/extension/src/composables/useFullBackupImport.ts`). It calls `profileService.restore(...)` which, on the passkey branch, writes the profile row and does `this.pendingRestoreSecrets.set(id, recovery.secret); storedPending = true` (`apps/extension/src/wallet/services/profile/service.ts:1499-1500`) — deliberately *not* zeroized on this path ("The map takes ownership — DO NOT zero in finally", line 1498). If the popup is closed (or its execution context is torn down by any means other than a JS exception — e.g. the user navigates away, or the extension UI is dismissed) before `finalizeRestore()` runs and before `deleteProfile()` runs, execution simply stops: no `catch` fires (nothing threw), so `useFullBackupImport`'s own compensating cleanup (`profileService.deleteProfile(createdProfileId)` in the outer `catch`, line ~727) never executes. Verified via repo-wide grep that `pendingRestoreSecrets` is referenced only in three places in `service.ts`: the `.set()` at restore (1499), the `.get()`/`.delete()`/`zeroize()` in `finalizeRestore` (1595-1605), and the `.get()`/`.delete()`/`zeroize()` in `deleteProfile` (919-923) — there is no timeout, GC sweep, or SW-boot cleanup path for an entry whose profile is neither finalized nor deleted.
- **Violated invariant:** The wallet-crypto package's load-bearing "secrets are zeroized after their last legitimate use" discipline (documented as the single most audit-worthy pattern class in the package's own map) is bypassed for the entire duration this Map entry survives — which, for an abandoned import, is until the service worker instance is torn down (could be seconds, or much longer if the SW is kept alive by other activity — alarms, open ports, etc.).
- **Failing path:** `ProfileService.restore()` passkey branch (`service.ts:1435-1519`) → `this.pendingRestoreSecrets.set(id, recovery.secret)` (line 1499) → popup context destroyed before `finalizeRestore(id, ...)` (`service.ts:1541-1607`) or `deleteProfile(id)` (`service.ts:891-945`) is ever called for `id` → entry (and the raw master-secret bytes it holds) remains resident in the SW's `pendingRestoreSecrets` Map for the rest of the SW's lifetime.
- **Expected vs actual:** Expected — every path that stashes a raw master secret eventually reaches a `zeroize()` call, matching the rest of the package's discipline. Actual — an abandoned (neither finalized nor deleted) passkey restore has no code path that ever revisits or clears its entry.
- **Recommended fix:** Add a bounded staleness sweep for `pendingRestoreSecrets` (e.g., stamp entries with a timestamp and zeroize+delete anything older than a short TTL on the next `restore()`/`finalizeRestore()`/`deleteProfile()` call, or via the existing periodic `JournalReaper`/`JournalGC`-style alarm pattern already used elsewhere in the codebase for exactly this class of "durable in-flight state that must not survive forever" problem).
- **Instances:** `apps/extension/src/wallet/services/profile/service.ts:107` (field declaration), `:1499-1500` (unzeroized stash), `:1595-1605` (`finalizeRestore` consumption — the only "happy path" cleanup), `:919-923` (`deleteProfile` cleanup — the only "abort" cleanup, requires the caller to know to call it).

## Non-findings considered
- `ProfileDeletionCoordinator.runFor`'s single-flight `inflight` Map (resume-vs-live-delete collision) — traced the full reservation chain (`ProfileDeletionState.initReserved` seeded at service `init()` before any RPC is accepted, `deleteProfile`'s phase-1 `isReserved` gate) and found a live `deleteProfile()` call for an already-tombstoned id is rejected before it could ever reach `runFor` a second time within one SW lifetime — no counter-example found.
- `SessionSecretBox.unwrap()` / `PasswordSecretBox.unsealInternal()` zeroize-on-every-exit-path discipline — read both fully; both correctly wrap every decode/decrypt branch (including early `return null`) in try/finally covering the buffers they own. This is the already-fixed pattern the lead pointed at; verified as fixed, not broken, in these two.
- `AccountIntegrityCoordinator.verifyRestoredSessionOnce()`'s fire-and-forget boot verification racing a concurrent unlock — the surrounding code has extensive, already-audited (per its own comments referencing multiple "codex audit" fixes) revalidation logic (epoch capture, `lockProfileIfActive`, stamp digest keyed off live storage); did not find a fresh counter-example within the context-cap trace depth.
- `SessionManager.refresh()`'s in-place mutation of the shared `activeSession.session` object before the storage write — traced the interaction with the TTL alarm's stale-fire gate (`onAlarmFired`'s `scheduledTime === expectedLockedAt` check) and confirmed a `refresh()` storage-write failure only causes the *old* alarm to be silently ignored as stale (self-healing via the gate), not a TTL bypass or lock loss — no counter-example.
- `EncryptionKey.encrypt`/`decrypt` 1-byte version tag vs. `SessionSecretBox.wrap`/`unwrap`'s unversioned framing (noted in the orientation map as a "real, if intentional, format divergence") — the two types are never cross-decoded (`SessionWrappedSecret` and `EncryptedProfileSecret` are structurally distinct, separately validated), so no confusion path exists; almost reported, dropped for lack of a counter-example.
- `PasswordSecretBox.reseal()`'s `newPasshash` escaping un-zeroized to the caller — this is the explicitly documented ownership-transfer contract (JSDoc: "the returned `passhash` ESCAPES — caller owns it"), and every call site in `service.ts` (`changeProfilePassword`) does zeroize it in its own `finally` — confirmed, not a finding.

## Quality handoffs
- `SessionManager`'s `open()`/`refresh()`/`applyTtlChange()` all hand-roll near-identical "persist Session + reschedule alarm" sequences with slightly different ordering guarantees (see Finding 1) — a shared internal helper enforcing "mutate memory, then persist, then reschedule" consistently would remove the asymmetry class of bug at its root.
