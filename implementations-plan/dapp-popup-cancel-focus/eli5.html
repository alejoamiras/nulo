Popup Cancel and Refocus

When a dApp asks the wallet to send a transaction, the wallet opens a small approval window. Two things are wrong with it today: cancelling the transaction from the wallet's own activity feed leaves that window open, and on a Mac with several displays the window can open somewhere you are not looking, with no way to bring it back. This plan fixes both, in two separate pull requests so each fix can be checked on its own.

The approval window is a fixed 400 by 800 popup. Chrome opens it near whichever of its windows was last active, which on a multi-display Mac is often not the one showing the dApp.

The plan, phase by phase

PR 1 · cancel closes the window

Cancelling from the activity feed closes the approval window and tells the dApp "cancelled by user"

  1. 1

    Let the window manager carry a real error. Today, when the wallet closes an approval window itself, the dApp receives a bare text message that the wallet then hides behind a generic "could not process the request". The window manager learns to pass a proper error object through, so the dApp gets the same structured "cancelled by user" signal it already gets when you cancel mid-proof. The same phase fixes the window's own Reject button, which has the same problem: it now reaches the dApp as the standard "user rejected" code, kept distinct from "cancelled" so a dApp can tell the two apart.

    Proves itself by: typecheck, lint, and unit tests that the error object arrives unchanged, that Reject produces the "user rejected" code, and that the dApp-facing envelope maps it.

  2. 2

    Make the wallet notice its own cancel. The wallet's transaction journal already announces every status change. The service that owns approval windows now listens for "cancelled", finds the matching open window, marks the request cancelled so a late Approve click is refused, closes the window, and rejects the dApp's request. Right after it registers a new window it also re-reads the journal once, so a cancel that lands in the split second before the wallet is listening still closes the window. If the transaction was already approved, the existing cancel path keeps handling it and nothing changes.

    Proves itself by: typecheck, lint, unit tests, and one end-to-end-in-process test with the real journal and real window manager: cancelling A closes A's window only, A's dApp request fails with the structured cancel, B stays open; plus unit cases for an unknown or already-approved transaction, a second cancel, Approve after a cancel, and the split-second race. Then the repo's full pre-PR gate.

PR 2 stacks on PR 1: it reuses the "find the window for this transaction" lookup that PR 1 introduces.

PR 2 · open in the right place, and come back when clicked

The approval window opens on the display you are using, and clicking the Queued card brings it to the front

  1. 3

    Teach the wallet's window layer two more moves. The thin layer that wraps Chrome's window API gains "focus this window" and "where is the window the user last used". Its test double gains the same, so everything above it stays unit-testable without a browser.

    Proves itself by: typecheck, lint, the shared package's unit tests for the test double, and two tests of the real Chrome adapter against a stubbed browser: it asks only for normal windows, and a failure or missing bounds falls back to "no anchor" instead of throwing.

  2. 4

    Open centered on the active window; be able to refocus. Before opening an approval window, the wallet asks Chrome which normal window was last active and centers the popup on it, keeping negative screen coordinates intact so displays to the left of or above your main one work. This is what stops the popup landing on the wrong display in the first place. The window manager also gains "bring this window to the front", which un-minimizes it and asks the system for attention. Passkey prompts use the same code, so they get the positioning for free.

    Proves itself by: typecheck, lint, and window manager unit tests for the centering math (including a display left of the main one), the "no active window" fallback, a timeout during the lookup, and focus on a live, missing, or already-closed window. Plus a manual check on your Mac that focusing actually switches Spaces (this cannot be tested headlessly).

  3. 5

    Make the Queued card clickable. While a dApp transaction is waiting for your approval, its card in the activity feed becomes clickable (with a "Show the approval window" hint). Clicking, or pressing Enter or Space on it, asks the wallet to bring that window forward. The wallet only does so for the profile you currently have open. The existing cancel button on the card keeps working and never triggers the focus. At any other stage the card is not clickable.

    Proves itself by: typecheck, lint, and component plus unit tests for: click, Enter, and Space at "queued" ask for the window; other stages do nothing; the cancel button still cancels and never focuses, by mouse or keyboard; the wallet-side lookup returns true or false, never an error, and false for another profile. Then the repo's full pre-PR gate.

Human context

  • "Queued" is the card the activity feed shows from the moment a dApp's request arrives until you approve it. Its small × is the cancel you used. Today that cancel only updates the wallet's journal; the approval window is a separate process that never hears about it.
  • Why the wallet must close the window, not the window itself. The approval window can be mid-load when you cancel, so a message sent to it can be lost. Only the wallet's background service knows the window's identity and the dApp's waiting request, so it is the one place that can close the window and answer the dApp in a single step.
  • The "cancelled by user" signal. dApps already understand the wallet's structured cancel code (4001, "JOB_CANCELLED") from the mid-proof cancel. PR 1 reuses it exactly, so a dApp sees no new error shape.
  • macOS Spaces. Chrome opens a popup near its last-active window, which can sit on another display or another Space. Centering the popup on the last-active normal window attacks the cause; the click-to-focus is the recovery when it still happens.
  • A click can be a no-op. "Queued" does not always mean a window is open: for a moment before the window appears, and again after you approve while the wallet waits its turn to execute, the card is still Queued but there is nothing to show. Clicking then does nothing. Tracking that precisely would cost a journal write on every window open and close; the plan accepts the no-op instead.

Open questions

  • Does focusing switch Spaces on your Mac? The plan asks Chrome to focus the window, draw attention to it, and restore it if minimized, in one call. The tests prove the call is made; only you can confirm Chrome moves you to the right Space. This is a manual check in phase 4, not a blocker for approval.
