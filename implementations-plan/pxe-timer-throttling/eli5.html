Make the Firefox wallet as fast as the Chrome one

On Firefox the wallet's engine runs inside a hidden, minimized window. Firefox slows hidden windows down on purpose, and that makes every transaction crawl. The plan moves the engine one step sideways, into a place Firefox does not slow down. Nothing else about the wallet changes.

Why it is slow, in plain terms

The engine talks to the Aztec network constantly. The network library it uses waits for a tiny timer — "zero milliseconds" — before sending each message, so that messages asked for at the same instant travel together.

In a normal window a zero-millisecond timer takes about a millisecond. In a hidden window Firefox makes every timer wait a full second. A transaction needs around forty of those messages, so it loses around forty seconds doing nothing.

Chrome does not have the problem: its built-in hidden page for extensions counts as visible. Firefox has no such page, which is why we used a minimized window in the first place.

The fix

Firefox extensions have a background page that Firefox treats as visible and never slows down. We load the very same engine page inside that background page, as an embedded frame, instead of in a minimized window. The frame inherits "visible", timers run at full speed, and the network library works exactly as its authors wrote it.

  • Chrome is not touched. The change lives in the three Firefox-only branches of one file.
  • No tricks with timers. The other working option replaced the browser's timers with our own. It was fast too, but it changed how messages get grouped and altered Chrome for no gain.
  • A side benefit: the minimized "Nulo" window disappears from the Firefox taskbar or dock. Users can no longer close the engine by accident, and a restart can no longer leave an old engine window behind.

What the big wallets do

MetaMask and Rabby avoid the question: on Firefox they still ship the older extension format, whose background page never sleeps, and run everything there. We cannot copy that cheaply — our build tool refuses the old format outright, so it would mean a second build pipeline and a second set of browser APIs. This plan borrows their idea (do the heavy work inside the background page) while staying on the modern format we just finished testing.

The one rule that differs from Chrome

The engine now lives exactly as long as the wallet's background page. A keep-alive the wallet already has holds that page open; we checked that it is what does the job, by removing it and watching Firefox put the page to sleep within two minutes.

If the background does stop — a crash, an update, a browser short of memory — the wallet comes back locked. That is deliberate and identical on Chrome: a stopped background drops the session. The user unlocks, the engine starts fresh, and things carry on; measured three ways above. On Chrome the engine page itself survives such a stop; on Firefox it restarts. The person using the wallet sees the same thing either way.

A correction to an earlier draft: I first reported that a restart breaks connected dApps on Firefox. That was my test's mistake — it never unlocked the wallet. There is no such bug. Separately, a dApp request that was in flight at the moment the background stops never gets an answer (on both setups); that is noted for a follow-up, not chased here.
