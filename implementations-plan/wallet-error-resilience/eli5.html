Wallet Error Resilience

One hour of a tools session on 15 September failed four different ways, and every failure reached the app as the same sentence. This plan makes the wallet retry once when the network's answers shift under it, name its errors so apps can act on them, teach the tools app to gate and recover, and remove the console noise that was hiding all of it.

Four failures, four fixes

What you sawWhat was really happeningWhat changes
Sends and balance syncs failed for an hour: "block hash not found, possibly a reorg", "not-yet-synchronized PXE", "RewindableRegister write originates behind the current version". The wallet's private engine asks the network "what is the latest block?" before every operation, then works from that answer. The network (a reorg, or several nodes behind one address disagreeing) kept changing its answer between the question and the work. Nothing retried, and nothing said what happened. On that family of errors the wallet re-asks once and retries the operation once. That is one more draw, not a guarantee: if it fails again, the app receives a named error, PXE_STALE_ANCHOR, instead of the generic sentence. Balance refreshes that hit it are quietly re-queued (twice, five seconds apart) while the background worker lives, instead of being stamped "sync failed".
A tools send failed: "Contract artifact not found for class 0x2015…". The app asked the wallet to use a contract it had never introduced to the wallet, most likely because the app reconnected (three times that afternoon) while its introductions were still in flight, and the send button was never waiting for them. The wallet answers with a named error, CONTRACT_NOT_REGISTERED. The tools app refuses to send until its introductions are done, and if it still gets that error it re-introduces the contracts and retries once.
"The wallet could not process the request." for everything. By design: an unrecognised error is replaced by one constant sentence so nothing private leaks to an arbitrary website. Only errors the wallet has explicitly classified get a code. These two were never classified. Both get classified, with constant messages and a machine-readable code. The privacy rule is untouched.
Console noise: uncaught "Client disconnected", "Receiving end does not exist", [object Object], and a passkey algorithm warning. Expected churn from the extension's background worker restarting was logged quietly internally but never told the browser "handled", so DevTools still printed it. The log viewer turned any object it could not serialise into [object Object]. The passkey request lists one signing algorithm; Chrome wants two. Mark the two expected rejections as handled, serialise big numbers and circular objects properly, add the second algorithm. Key material comes from a separate passkey feature, so the algorithm change cannot affect it.

Why the light tier

Six risk dimensions were scored: novelty, blast radius, irreversibility, migration cost, external coupling, security sensitivity. None is high. Every change adapts a pattern that already exists in the code (a typed-error family, a retry-once helper, a queue ticker, a rejection filter), no stored data changes shape, and the one trust boundary touched keeps its existing rule. Three packages are involved, which is why the work ships as two stacked pull requests rather than one, but the rubric does not call for a heavier plan.

Phases

Arc 1 — the extension (one pull request)

1. Two named errors, wired end to end

Add "the wallet's view of the chain was behind" and "contract not registered" to the family of errors that survive the trip from the wallet's engine to the app, and give each a code and a constant message. There are two hand-offs on that trip where an error gets flattened to plain text, not one; codex caught the second, and both now carry the code. The nine places that already throw the "not found" messages start throwing the typed version with the exact same wording, so nothing that matches on the text breaks. The app gets the code only, never the wallet's internal detail.

Proves itself by: unit tests that push each error through the whole chain, from the engine to the exact envelope an app receives, plus typecheck and lint.

2. Re-ask once, retry once

A small helper wraps the four engine operations (simulate, prove, run a view, profile). If the error is one of the three "the chain moved" messages, it forces a resync and runs the operation once more, under the same lock it already held. A second failure, or a resync that fails the same way, becomes the named error; a resync that fails for an unrelated reason keeps its own error. The wallet has one other, unrelated retry (re-supplying a storage key after a cold start); codex found that a hostile network could chain the two into four attempts by changing its error text between tries. That retry now trusts where an error came from, not what it says, so the chain is impossible by construction. Broadcasting a transaction is never retried, so nothing can be sent twice. The retry can cost a full second proof; that is the price of one more draw.

Proves itself by: unit tests for each branch (unrelated error untouched; fails then succeeds; fails twice; fails then a different error; resync fails; the "2 of 6 concurrent operations failed" wrapper shape; a message carrying both retry markers), a test that reads the installed Aztec packages to confirm the matched strings still exist, plus typecheck and lint. And, per your condition, a real one: a test that runs the real private engine against the local sandbox, forces an actual chain reorg on the local L1, and shows the operation fails without the helper and recovers with it, with the engine's pin genuinely moved. If the sandbox turns out not to reproduce the failure, the test says so and the delivery report lists it as unmet; it is never turned into a test that passes without proving anything.

3. Balance refreshes re-queue instead of giving up

Today a refresh that fails is stamped "sync failed" on the row and never retried on its own. Now a transient failure is put back in the queue after five seconds, at most twice; the third failure behaves exactly as today. This is an in-memory retry with explicit rules (a manual refresh during the wait replaces it; success or a final failure cancels it; a profile switch clears it). If the background worker dies inside that five-second window the row simply keeps its last-known balance with no stamp, and the next normal trigger refreshes it, the same as any healthy row. Making the retry survive a worker restart would mean a stored-data change; that is a decision for you below.

Proves itself by: queue unit tests over the interleavings (re-queued once, no stamp; third failure stamps as before; a manual refresh during the wait; success during the wait; a profile switch mid-flight; an entry from an older generation), plus typecheck and lint.

4. The noise sweep

Four one-commit changes: tell the browser the expected "Client disconnected" rejection is handled (and delete the duplicate check the offscreen page kept); do the same for the exact "Receiving end does not exist" message and stop a closed tab from surfacing as an error; make the log viewer print big numbers and circular objects and arrays instead of [object Object] (or looping forever); add the second passkey algorithm. The key derivation was confirmed to use the passkey's PRF output, not the signing algorithm.

Proves itself by: unit tests for each predicate and formatter, then the full local gate (typecheck, every package's unit tests, lint, build), the smoke suite including the passkey tests (Chrome's virtual authenticator with PRF), a new network test that forces a reorg and checks the whole extension recovers through the real wallet and node, and one full network run on the sandbox, run alone. Then on your Mac: a check that none of the four lines appears when the background worker restarts, and a real Touch ID passkey register, lock, and unlock. Hardware that only supports the second algorithm is not in the fleet; the plan says so rather than claiming it.

Arc 2 — the tools app (one pull request, stacked on arc 1)

5. Wait for the introductions; read the new codes

The session gets a single "contracts ready" flag that is false from the moment a connection starts until every contract has been introduced to the wallet, and false again if the wallet disconnects. Deposits, exits, and drips refuse with one plain sentence while it is false. A re-introduction that runs later follows the same ownership rules as the first one, so a stale completion from an old connection can never mark a new one ready. If an introduction fails, the session lands in its existing error state, where the existing "Retry connection" button reconnects; a send attempted in that state shows the session's actual error, and the "still setting up" refusal can only ever mean an introduction is genuinely in flight. The app's error reader learns to read the wallet's codes directly, with a new "your wallet's view of the network was behind, try again" category.

Proves itself by: session unit tests for the flag's whole lifecycle including a disconnect mid-re-introduction and a failed one, error-reader tests for the two codes, and a refusal test per flow, plus typecheck and lint.

6. Re-introduce and retry once

If a call still comes back with the wallet's "contract not registered" code (the code itself, never a text match, so another wallet's wording can never trigger it), the app re-runs its introductions and retries that one call once, and only if the session still holds the same wallet the call was made with (a call that outlives a reconnect is not retried against the new connection). This is applied only to four single calls that cannot have sent anything yet: creating an authorization witness, a simulation, a balance read, and the one-transaction drip. The multi-step deposit-claim and exit flows are deliberately not retried automatically (a retry there could replay a step that already went through); they get the ready-gate, which removes the race that caused the failure you saw, and their error display learns the two new categories so the message reads as a sentence rather than raw JSON. A new browser test injects the failure into the embedded test wallet and checks the app re-introduces and succeeds; a second case holds a re-introduction on a connected session and checks the drip is refused, not attempted.

Proves itself by: the helper's unit tests (including "text matches but no code: no retry"), the tools browser suite, and the tools build, plus typecheck and lint.

Human context

What an "anchor" is. Before doing private work, the wallet's engine pins itself to one specific block and does everything relative to it. If the network then says that block does not exist (a reorg) or its own pin is older than what it wrote last time, the work is invalid. Re-pinning and trying once more is the correct fix for a reorg; for a network whose nodes disagree it is a second draw, and after that the honest answer is a clear error.

Why the wallet cannot fix the network. The session's pattern, "2 of 6 concurrent operations failed", looks like several nodes behind one address answering differently. The wallet can retry and report; it cannot make two nodes agree. If this keeps happening on a stable node, that is a separate investigation.

What "registered" means. The wallet only executes contracts an app has introduced to it (address plus code). The tools app does this on every connect; the bug was that its send buttons never waited for the introductions to finish.

Why errors were opaque. A deliberate privacy rule: unknown errors are replaced by a constant so an arbitrary website cannot fish for wallet state. The fix is to classify the two actionable errors, not to loosen the rule.

Open questions

  • Is the "RewindableRegister" assertion recoverable by a resync? The plan assumes yes with moderate-to-low confidence. If not, the cost is one extra attempt (a full proof when it happens inside a send) before the named error, and the string can be dropped from the matcher on its own.
  • Was it one cause? The three "chain moved" errors most likely share one: nodes behind one address answering from different tips. Not proven; a reproduction against a single stable node would settle it. The plan works either way, and if it recurs on a stable node that is a separate investigation.
  • A1, decided: no. A delayed balance retry does not survive a background-worker restart; the row keeps its last-known balance with no failure stamp and the next normal trigger refreshes it. Five seconds is a scheduling delay, not a ceiling, since the queue works serially.
