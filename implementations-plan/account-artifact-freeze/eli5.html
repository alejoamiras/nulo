account-artifact-freeze

Your wallet computes each account's address from two things: the user's seed, and the compiled account-contract file that ships inside an Aztec npm package. The seed part was frozen earlier this month. The contract file was not — so every Aztec library update can silently change what address a seed produces. Today that mismatch surfaces as a cryptic error whose only way out is deleting the profile (the scare you hit). This plan copies that contract file INTO our repo as a frozen, fingerprinted artifact of "Nulo V5", makes any address change impossible to ship by accident, adds a dedicated test proving the frozen contract still executes after every Aztec update (the audits' biggest catch — freezing the file trades one risk for another if nobody checks this), replaces the cryptic error with a proper explanation screen, and writes the whole policy down: V5 addresses never change; a protocol break means shipping "Nulo V6" as a separate extension, never breaking V5 in place.

Why this tier was chosen

mid. Rubric: irreversibility HIGH (production account identity) and security sensitivity HIGH (key/address derivation) — which technically points at deep — but novelty is LOW: the 5.0.1 work already froze the seed-side derivation with the exact vector machinery this plan extends, and there are no migrations (pre-production). mid's dual audit was run and earned its keep: one auditor initially rejected the draft, and three audit rounds reshaped it (see plan.md's decision ledger).

Phases

Phase 1: Copy the contract file into our repo

Take the raw compiled account contract out of the Aztec package (recording exactly where it came from and its fingerprint) and make the wallet use OUR copy. Existing address tests must pass completely unchanged — proof the copy changes nothing today.

Proves itself by: lint + typecheck + the full all-workspaces test suite, address tests untouched.

Phase 2: Freeze the construction recipe

Besides the file, a few small setup values feed the address (which constructor, its two arguments, some zeros). Today they're read from Aztec's code in TWO places — one for computing the address, one for actually deploying the account. Both now read from ONE frozen recipe in our repo, so they can never disagree (an auditor showed that disagreement would brick account creation while every test stays green).

Proves itself by: address tests unchanged + a new test that both places use the identical recipe.

Phase 3: The "no accidental changes" lock

A small registry records V5's fingerprints (file, contract ID, recipe). Changing ANY of them turns the test suite red on every PR unless a new entry is added with a written justification that embeds the new fingerprint — editing an existing entry is never legal. One registry entry per extension major: changing addresses IS shipping a new major, by construction.

Proves itself by: deliberately corrupting the file/registry locally and watching the tests go red (then reverting).

Phase 4: The "still works" canary — REQUIRED

The audits' headline finding: freezing the file protects addresses but creates a new risk — a future Aztec update might no longer be able to run the old contract (fails at transaction time, worse than the address problem). So: a new dedicated browser test walks the full life of a frozen account — brand-new account, first transaction (which deploys the contract), simulation, a REAL cryptographic proof, network acceptance, a follow-up permission-based transaction, and recovery after a restart. Every future Aztec version bump must run this test green before merging; red means the bump is blocked.

Proves itself by: the canary green on a live local node with native proving, at today's versions.

Phase 5: A real answer instead of a scary error

If a mismatch ever does occur, the wallet checks for it up front (in the background, before anything can act on the account — deterministic math, so no false alarms from flaky network state) and shows one clear screen: what happened, that your seed phrase still derives your accounts on a compatible Nulo version, and what to do. It never asks for your seed, links nowhere, and offers no delete button — per your decision, deletion stays a deliberate settings action. dApps just see a generic failure, no internals.

Proves itself by: unit tests (tampered account → session blocked, state survives restarts) + a component test for the screen.

Phase 6: Write the law down

CLAUDE.md gets the policy (frozen addresses, the rotation procedure, the V5/V6 separate-extension strategy); the Aztec-update runbook gets the mandatory canary step; two small doc drifts found during audit get fixed.

Proves itself by: lint + typecheck + your read of the docs at PR review.

Phase 7: Full quality gates

The complete pre-PR audit, the full cross-package test suite, the smoke browser suite, and BOTH browser builds (Chrome and Firefox), plus a record of how much the vendored file grew the bundle.

Proves itself by: audit:vue + test:all + smoke + the Firefox build, all green.

Human context

An Aztec account address is like a fingerprint of three things mixed together: your seed, the exact bytes of the account contract, and the protocol's mixing formula. You can only freeze what you own — this plan freezes the middle ingredient (the bytes) and the setup values around it. The mixing formula itself belongs to the protocol: if Aztec ever changes that, no freeze can help, and that's exactly when "Nulo V6" ships as a fresh extension while V5 keeps working for existing users. The tests added here make sure that day is a conscious decision, never a surprise in a routine dependency update.
