# Review — release-please rollout v1 (Opus 4.7)

## Verdict

REJECT — the plan has at least two falsifiable mechanism claims (signed commits, automatic workflow chaining) that contradict release-please-action's own README and GitHub's documented `GITHUB_TOKEN` rule; the proposed `changelog-path: "../../CHANGELOG.md"` also escapes the documented "relative to *package* directory" semantic.

## Per-section findings

- §3 New files
  - `.github/release-please-config.json`: all six keys flagged (`release-type`, `package-name`, `changelog-path`, `tag-separator`, `include-component-in-tag`, `include-v-in-tag`, `pull-request-title-pattern`, `separate-pull-requests`, `changelog-sections`) exist in release-please's `schemas/config.json`. Defaults are: `include-component-in-tag=true`, `include-v-in-tag=true`, `separate-pull-requests=false`. Plan sets `include-component-in-tag=false` + `include-v-in-tag=true`, which yields `v0.20.0` — matches the existing `v0.17.0`/`v0.17.1` tag pattern (verified via `git tag --list`). Good.
  - `changelog-path: "../../CHANGELOG.md"`: the manifest-releaser docs say the path is "relative to the *package* directory", i.e. inside `packages/extension/`. Escaping with `../../` is **not documented as supported** and may either silently anchor to the package root (leaving CHANGELOG inside the package) or be rejected. Plan §13 also lists `CHANGELOG.md` at repo root as the seeded file, so the intent is unambiguous but the mechanism is unverified. The safer pattern is to set `path: "."` for the single package (root-as-package) and let `changelog-path` default to `CHANGELOG.md`.
  - `tag-separator: "v"`: combined with `include-component-in-tag=false` + `include-v-in-tag=true`, this is redundant and likely no-op. The schema describes `tag-separator` as "separator between the component and version" — with no component in the tag, there's no separator slot. Harmless but cargo.
  - `.release-please-manifest.json`: seeding with `0.20.0` while last tag is `v0.17.1` is the canonical "skip versions" pattern (confirmed by manifest-releaser docs: "Use `.release-please-manifest.json` to manually set the current version. This approach bypasses conventional commit parsing for the initial run"). Plan §3 says this is "the documented `bootstrap-sha`-adjacent path" — that conflates two distinct mechanisms (`bootstrap-sha` configures where commit history begins; manifest seeding sets baseline version). Pick one name in the plan. Mechanism itself: correct.
  - `release-please.yml`: the signing-claim sentence — "Commits via the token's GraphQL `createCommitOnBranch` mutation are auto-verified by GitHub (web-flow signature)" — is **the most load-bearing claim in the plan and it is not supported by any source I could verify**. GitHub's signature-verification doc says "Signature verification for bots will only work if the request is verified and authenticated as the GitHub App or bot and contains no custom author information, custom committer information, and no custom signature information, such as Commits API." release-please-action authenticates as `github-actions[bot]` via `GITHUB_TOKEN`, not as a GitHub App with its own signing key. **If this assumption is wrong, the Release PR will fail the "signed commits required" ruleset on `main` and the entire rollout deadlocks.** Verify on a throwaway branch before merging the rewrite.

- §4 Workflow rewrite
  - **Critical workflow-chaining bug**: §7 step 6 says "`release: published` event fires. Triggers `release.yml`." This **directly contradicts** release-please-action's own README, which states: "all resources created by `release-please`...will not trigger future GitHub actions workflows" and "You will want to configure a GitHub Actions secret with a Personal Access Token if you want GitHub Actions CI checks to run on Release Please PRs." If release-please uses the default `GITHUB_TOKEN` to create the Release, the `release: published` event will NOT trigger the rewritten `release.yml`. The artifact/build/zip chain never runs. **This is the second fatal flaw**. Either (a) provide a PAT (`token:` input on release-please-action), or (b) restructure so the same `release-please.yml` job calls reusable workflows directly via `if: steps.release.outputs.release_created`.
  - Trigger change from `workflow_dispatch` (today) to `release: published` removes the `dry_run` / `channel` / `run_network_e2e` inputs. Acceptable since release-please owns versioning; but the loss of `run_network_e2e=false` escape hatch means every release runs the 30-45 min network gate. Acknowledge or restore.
  - `concurrency.group: release-publish-${{ github.ref }}` — under `release: published`, `github.ref` is the tag ref. Two consecutive releases would have different refs and could run in parallel. Old workflow used `group: release` (workflow-wide). Tighter is safer.

- §7 First release cycle
  - Step 2 says release-please opens a PR with "CHANGELOG.md updated (no-op since we pre-seeded the entry)". release-please writes its own canonical changelog format which may not byte-match the §3 seeded markdown (different heading style, link format). Expect a diff, not a no-op. Cosmetic, not blocking.
  - Step 4 says "User merges the Release PR…main allows only `merge` per ruleset". Confirmed by `CLAUDE.md` lines 24–25. But release-please's default PR doesn't follow the dev→main promote naming convention from `CLAUDE.md` line 33 (`release: promote dev → main (...)`). Either accept that release-please PRs bypass that convention (they're release-management PRs, not promotion PRs) or set `pull-request-title-pattern` to match the convention.

- §8 Migration sequence
  - Commit 5 ("bump @nulo/extension + root package.json to 0.20.0") is a human `chore(release): bump extension to 0.20.0` commit — directly the pattern that `CLAUDE.md` line 219–220 calls deprecated. The plan acknowledges this in the parenthetical at §8 end ("the one-time 0.20.0 seed bump is necessary to bootstrap release-please"). Reasonable carve-out — but please word the commit subject so it cannot be misread as a release commit. Suggest `chore(release-please): seed extension package.json to 0.20.0 baseline` to make the bootstrap intent explicit.

## Cross-cutting findings

1. The plan's two technical safety nets — "signed commits work via web-flow" and "release.yml triggers off release-please's release" — are **both** unverified-against-source. Plan must be rebuilt on the assumption that (a) release-please commits won't be web-flow-verified out of the box, and (b) `GITHUB_TOKEN`-created releases won't trigger `release.yml`. Both have workarounds (PAT + a GitHub App with signing), but the plan does not mention either.
2. `cliff.toml` reviewed: the `--include-path 'packages/extension/**'` arg in the current `release.yml` line 206 scopes git-cliff to extension commits. The plan keeps this. Good — preserves the public-facing release-notes UX.
3. The seeded `CHANGELOG.md` references `[#7]`, `[#8]`, `[#9]` — `git log v0.17.1..HEAD` confirms those PR numbers map to the listed commits. Good.
4. Plan does NOT remove `.release-it.json` from `package.json` devDeps or `bunfig.toml`. Verify there are no transitive consumers before deleting (`bunx release-it` is what `release.yml:228` invokes — once rewritten, no consumer remains). Confirm.
5. `release-please.yml`'s `pull-requests: write` permission is correct; `id-token: write` is NOT needed for release-please-action@v4 (no OIDC). Plan omits, which is right.

## Verifiable claims to validate before merge

1. Run release-please-action@v4 on a throwaway branch protected by the same "signed commits required" rule. Confirm the auto-PR's commits show a "Verified" badge in GitHub's UI. If not, switch to a GitHub App with `actions/create-github-app-token` so the PR is signed.
2. Confirm that creating a GitHub Release via `GITHUB_TOKEN` (whether by release-please or `gh release create`) fires `release: published` to other workflows in the same repo. Quick test: empty workflow on `release: published` + `gh release create v0.0.0-test` from inside a workflow. If it doesn't fire, restructure §4 to call reusable workflows from within `release-please.yml` itself.
3. Validate `changelog-path: "../../CHANGELOG.md"` actually writes to repo root, not `packages/extension/../../CHANGELOG.md`-resolved (= repo root) but-only-when-it-doesn't-error. Easiest: dry-run via `release-please-action` with `skip-github-release: true` against a scratch branch.
4. Confirm `chore: release @nulo/extension 0.20.0` PR-title format passes `@commitlint/config-conventional` (no scope colon weirdness from `${scope}` empty-expansion).
5. Confirm `tag-separator: "v"` combined with `include-component-in-tag: false` + `include-v-in-tag: true` actually produces `v0.20.0`, not `v-v0.20.0` or `v0.20.0v`. Drop `tag-separator` from the config if it's redundant.
