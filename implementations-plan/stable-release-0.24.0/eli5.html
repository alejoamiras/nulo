First stable release — v0.24.0

This is the first stable (non-preview) release since we rebuilt the release pipeline. We take everything on dev — including the jump to Aztec 5.0.0-rc.2 and the new testnet — promote it to main, let the robot cut version 0.24.0, publish it, and deploy the two live sites (nulo.sh and faucet.nulo.sh).

Why this release is a "first"

The recent prerelease (0.24.0-rc.0) exercised most of the pipeline. This stable release is where three still-untested pieces finally run for real:

  • The apps/ restructure reaches main. main is still on the old packages/ layout; the promote brings the new apps/ layout over. That's what lets the publish use the normal --ref main (the prerelease had to work around it with --ref dev).
  • The "auto-unstick" switch stays OFF — so we do the 45-second manual tag+publish once, proving that path before ever flipping it on.
  • The main→dev sync runs live with the new bot-signed commit — so it should merge with a plain merge, no admin override.

Why "light" (and the caveat)

The rubric actually leans mid — a production release with live-site deploys and a testnet migration is high blast-radius. But this is essentially running a runbook the prerelease already validated end-to-end, the testnet config is confirmed good, and every step has a hard check + a rollback. So light + one thorough hostile code-review is enough. (Say the word to bump to mid.)

Phases

Phase 0: Pre-flight fixes (from the hostile review)

The audit caught two things that would bite a real release: (1) the release's "is the live faucet on the right chain?" check still had the old testnet's numbers baked in, so it would wrongly fail on a correct new-testnet deploy — fixed by making it read the single source the faucet already uses; (2) a stale leftover release branch (an abandoned "0.23.1" with the old folder layout) that could confuse the version robot — deleted.

Proves itself by: the release unit tests pass with the check now single-sourced, and the stale branch is gone.

Phase 1: Promote dev → main

Open a "promote" PR that fast-forwards main up to everything on dev (new testnet, apps/ layout, the pipeline fixes), resolve any conflicts favoring dev, and merge it. This is what puts the apps/ layout on main.

Proves itself by: the promote PR's three required checks (incl. the full 25-min network test) go green, and a grep confirms main now uses apps/extension — so the later publish won't hit the path error the prerelease did.

Phase 2: Cut 0.24.0, publish, deploy

The robot opens a "release 0.24.0" PR; we review the changelog and merge it. It gets stuck (a known upstream bug), so we do the 45-second manual unstick (tag + create the release). Then we fire the publish job (builds the Chrome + Firefox zips, smoke-tests them, attaches them), and the two live sites redeploy on the new testnet.

Proves itself by: the GitHub Release v0.24.0 exists (marked not prerelease) with both zips + checksums, and nulo.sh + faucet.nulo.sh load and the faucet talks to the new testnet (no "unknown chain" error).

Phase 3: Sync main → dev

After a stable release, main's release commit + the version bump flow back to dev, and the preview-version counter re-baselines to 0.24.0 (so the next preview is 0.25.0-rc.0). It merges with a plain merge (no admin override) — I sign the small manifest commit myself, since this first release keeps the auto-unstick switch off. (The fully-automated bot-signed version runs on a later release.)

Proves itself by: dev contains v0.24.0 in its history, the preview manifest reads 0.24.0, and a dry-run on dev previews 0.25.0-rc.0.

What could go wrong (and the guards)

The two scariest unknowns are already checked: the version really comes out 0.24.0 (not confused by the existing -rc.0 tag — verified by a dry-run), and the --ref main publish is safe because nothing builds until after the promote puts apps/ on main. The riskiest live piece is the prod deploy shipping the new testnet config — mitigated because you've confirmed that config is already validated, plus a live-site smoke check.

What I need you to approve:
  • The scope: promote → cut 0.24.0 → publish → full prod deploy (nulo.sh + faucet.nulo.sh) → sync back.
  • The tier: light (or bump to mid).
  • That AUTO_UNSTICK_ENABLED stays OFF for this first release (manual unstick).
  • That I pause for your go-ahead before firing the publish (the production point-of-no-return), same as the rc.
