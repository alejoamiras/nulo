## Architecture & Implementation

**Icons (`apps/extension/scripts/store-icons.ts`).** `Bun.Image` decodes `src/assets/logo.png` (512×512) and writes 16/32/48/96/128 PNGs into `src/assets/icons/`; the 128 is the art at 96×96 centred on a transparent 128 canvas when `Bun.Image` can pad, otherwise a plain 128 resize (Chrome's padding guidance is a recommendation; the gate records which). `manifest.config.ts` `icons` becomes `{16, 32, 48, 96, 128}` → the matching files (Firefox inherits the map; this clears `web-ext lint`'s four `ICON_SIZE_INVALID` warnings). `--check` regenerates in memory and fails on a byte difference; `scripts/store-icons.test.ts` runs it (the extension vitest config includes `scripts/**/*.test.ts`).

**Promo tile and screenshot frames (`apps/extension/scripts/store-art.ts`).** Puppeteer (already a devDependency) renders `store/templates/{tile,frame}.html` to PNG: the 440×280 tile (ring mark + "NULO V5" in Space Grotesk from `@nulo/design`'s font files, charcoal ground) and full-bleed 1280×800 frames embedding a popup capture as a data URI beside a one-line caption. Local-only; outputs committed. The same three screenshots serve both stores (AMO recommends 1280×800).

**Popup captures (`apps/extension/tests/e2e/store-captures.test.ts`).** Opt-in vitest file in the smoke suite (`describe.skipIf(!process.env.STORE_CAPTURES)`; `vitest.e2e.config.ts` already includes `tests/e2e/*.test.ts`, so CI collects it and skips it): `registerProfile`, `page.setViewport({width: 360, height: 600})`, screenshots of Home, Send and Settings → Security into `store/captures/`. Chrome build only; selectors by `data-testid`.

**Listing (`apps/extension/store/listing.md`).** One file, three parts. *Shared*: single-purpose statement (taken from `legal/privacy.md`'s appendix), long description, per-permission behavioural justifications, the data-handling table. *Chrome*: title (≤ 75), summary (≤ 132, equals `package.json#description` after it is shortened to fit), category, the Privacy-tab answers, written from a **data inventory table** in the shared part (one row per kind of data: where it lives, whether it leaves the device, to which destination). Google requires disclosure "even when data is processed or stored locally", so the ticked types are financial and payment information (balances, transactions), authentication information (passwords and keys: local only; for passkey profiles the profile-derived label and identifier are handed to the browser's WebAuthn API and on to the user's authenticator, whose provider may sync them, `wallet/utils/passkey-ceremony.ts:45-55`, `legal/privacy.md:157-160`), personally identifiable information (contact names and addresses, profile names: `contact/spec.ts:9-17`; local, except the passkey label just described) and web history (connected-app origins and URLs: `dapp-session/spec.ts:35-50`; local only); each destination is named separately (the configured Aztec node, CoinGecko, approved apps, the optional local prover on `127.0.0.1`, the public proving-parameter hosts of `legal/privacy.md` § 5.9); remote-code answer per Ask 4; privacy URL `https://nulo.sh/privacy`. *Firefox*: name (≤ 50), summary (≤ 250, no URL), categories, license `Apache-2.0`, support email `hello@nulo.sh`, homepage, privacy policy text pointer, **reviewer notes**: how to test without funds (create a password profile; testnet is selectable in Settings), that the build is bundled with source attached and rebuilt per `store/SOURCE-BUILD.md`, the modifications to third-party code, stated exactly (Ask 9): two packages patched at two versions each (`@aztec/noir-noirc_abi`, `@aztec/noir-acvm_js`; `patches/`, altering package resolution metadata), the `detect-node` shim (forces the browser logging transport, `apps/extension/vite.config.ts:54-58`), the `function-bind` CSP-safe stub, the `bb.js` fetch-code shim and the artifact debug-info stripping (`:61-108`), the residual linter warnings and their origin (bundled `@aztec` and WASM glue: `DANGEROUS_EVAL`, `UNSAFE_VAR_ASSIGNMENT`; feature-gated `chrome.offscreen`: `UNSUPPORTED_API`), and the remote-code note. `scripts/store-listing.test.ts` asserts: every permission and host permission in **both built-manifest sources** (`manifest.config.ts`, and the Firefox filter) has a justification heading; every permission row in `legal/privacy.md` § 6 has a counterpart (the policy and the listing cannot drift); the length caps above; the privacy URL; the Firefox `data_collection_permissions` value in the listing equals the manifest's; the reviewer-notes block exists, is non-empty and sits between the two marker comments the Firefox runner reads.

**Remote-code note (`apps/extension/store/remote-code.md`).** A cited description, written from `packages/aztec-runtime`, the offscreen/PXE host and the `@aztec` simulator, of: what arrives from a dApp (contract artifacts: ACIR and Brillig bytecode plus ABI, as data over the wallet-sdk channel); what executes it (the bundled ACVM/Brillig VM inside bundled WASM, no `eval`, no script injection, CSP `script-src 'self' 'wasm-unsafe-eval'`); what the bytecode can reach **directly** (nothing outside the VM) and **through mediation** (the oracle callbacks the PXE serves, enumerated with file references; they include public-storage reads from the configured node, `@aztec/pxe` `utility_execution_oracle.ts:536-547`, so contract execution can cause requests to a fixed endpoint it does not choose); what it cannot reach (extension APIs, DOM, arbitrary hosts); that the host document itself uses `chrome.runtime` messaging (`apps/extension/src/offscreen/index.ts:108`); which calls run without a per-request window (capability-granted calls under the session confirmation threshold, `dapp-interaction/service.ts:405-406`, `:658`). No claims about other wallets and no verdict: classification belongs to the stores and the owner (Ask 4). It feeds Ask 4 and the Firefox reviewer notes, and ends with the sentences in `legal/privacy.md` it bears on.

**Chrome publish (`scripts/release/publish-chrome-store.ts`, `-run.ts`).** The pure module builds requests and interprets responses; it never sees a credential source. `uploadRequest(publisherId, itemId, token, zip)` → `POST https://chromewebstore.googleapis.com/upload/v2/publishers/{p}/items/{i}:upload`, raw body, `Content-Type: application/zip`; `statusRequest` → `GET …:fetchStatus`; `publishRequest(type)` → `POST …:publish` with `{ publishType, blockOnWarnings: true }`; `interpretPreflight(json, version)`; `interpretUpload(json)`; `interpretPublish(json)`. The runner reads `MODE` (`publish` | `check`), `CWS_ACCESS_TOKEN`, `CWS_PUBLISHER_ID`, `CWS_ITEM_ID`, `CWS_PUBLISH_TYPE` (`DEFAULT_PUBLISH` | `STAGED_PUBLISH`, anything else exits 1), `ZIP_PATH`, `VERSION`, `DRY_RUN` (strict `true`/`false`). Versions are compared as **integer tuples padded to four parts** (`0.9.0.0` < `0.10.0.0`; string or semver comparison is wrong here), taken from the zip's `manifest.json` `version`, never from `VERSION`. `MODE` has no default; an unset or unknown value exits 1. **`MODE=check`** needs only the token and the two ids: mask the token, one `fetchStatus`, require the returned `itemId` to equal ours, print the published and submitted states, exit 0. It applies **no** publish-eligibility rule (right after the hand-made first submission the item is pending review at an equal version, which is exactly what the check must be able to read) and needs no zip. **`MODE=publish`** order: validate inputs → open the zip, require `version_name === VERSION`, a well-formed four-integer `version` and no `browser_specific_settings` (the Chrome zip, not the Firefox one) → **dry run stops here: zero network calls, no token needed** → `::add-mask::` the token → preflight `fetchStatus`: the returned `itemId` must equal ours; fail closed if `takenDown`, if `submittedItemRevisionStatus.state` is `PENDING_REVIEW` (message: cancel it in the dashboard or wait), or if any `crxVersion` in any `distributionChannels[]` of the published or submitted revision is not lower than ours; an absent revision object is valid (never published, nothing submitted), a present one with a missing or unknown `state` is not → upload → branch on the **upload response's own `uploadState`**: `SUCCEEDED` proceeds, after checking the returned `itemId` and that `crxVersion` equals ours; `IN_PROGRESS` or `UPLOAD_IN_PROGRESS` (the docs disagree with themselves) polls `fetchStatus.lastAsyncUploadState`, a field that exists only after an async upload, until `SUCCEEDED`; every request under `AbortSignal.timeout(15_000)`, the loop under a 3-minute deadline on an injectable clock; `FAILED`, `NOT_FOUND`, `UPLOAD_STATE_UNSPECIFIED`, an unknown value, a missing field while polling or an exhausted deadline fail closed and never reach publish → publish; warnings come in two envelopes and both are read: `warningInfo.warnings` on a 200, `error.details` on the 4xx that `blockOnWarnings: true` produces → one summary line with the actual `state` and its next action (`PENDING_REVIEW`: in review; `STAGED`: approved, publish from the dashboard within 30 days; `PUBLISHED`/`PUBLISHED_TO_TESTERS`: live; anything else fails with the bounded `warnings` list). Logging contract: never a request, header, token or raw exception; errors reduced to the API's `reason`/`description`/`message` strings truncated to 200 chars; non-JSON bodies reported by status code only.

**Firefox publish (`scripts/release/publish-firefox-amo.ts`, `-run.ts`).** Same shape, plain `fetch`, no `web-ext` in the credential-bearing job. `jwt(issuer, secret, now, jti)` → HS256 via `node:crypto`, `exp = iat + 60`, minted per request; `uploadRequest(zip)` → multipart `POST https://addons.mozilla.org/api/v5/addons/upload/` (`upload`, `channel=listed`); `uploadStatusRequest(uuid)`; `versionRequest(guid, uuid, approvalNotes)` → `POST /api/v5/addons/addon/{guid}/versions/` (JSON); `sourceRequest(guid, versionId, archive)` → multipart `PATCH …/versions/{id}/` (`source`); interpreters for each. The runner reads `MODE` (`publish` | `check`), `AMO_JWT_ISSUER`, `AMO_JWT_SECRET`, `ZIP_PATH`, `SOURCE_PATH`, `LISTING_PATH`, `VERSION`, `DRY_RUN`. `MODE` has no default. **`MODE=check`** needs only the key pair: mask the secret and the JWT, `GET /api/v5/addons/addon/` ("list all add-ons you are the author of"; the public detail endpoint would prove nothing, since anyone's valid key can read a public add-on), require `wallet@nulo.sh` among the results, print its status, exit 0; no zip, source or listing needed. **`MODE=publish`** order: validate → open the zip, require `version_name === VERSION`, retain the manifest's numeric `version` (`0.27.0.0` for `VERSION=0.27.0`: AMO speaks the manifest version, so every later comparison with an AMO response uses this value, never `VERSION`), `browser_specific_settings.gecko.id === "wallet@nulo.sh"` and `data_collection_permissions.required` equal to the settled declaration (both are constants in the module: the permanent AMO identity, and Ask 5's answer, so a build that regressed to `["none"]` is refused) → require the source archive to exist, be < 200 MB and contain `nulo-${VERSION}/apps/extension/store/SOURCE-BUILD.md` and `nulo-${VERSION}/bun.lock` (archive paths carry the prefix) → read the reviewer-notes block from `listing.md` between its two markers, non-empty → **dry run stops here** → `::add-mask::` the secret **and every JWT minted from it** → upload → poll until `processed` (same timeouts, 5-minute deadline: AMO validates a 41 MB zip server-side) → require `valid === true`, else print the validation **errors** (bounded: first 10, 200 chars each) and fail → create the version with those `approval_notes`; require the response to carry a version id, the manifest's numeric version and channel `listed` before continuing → patch the source → on any failure after the create request was sent (a patch error, or a create that timed out and may have succeeded remotely) the job fails with the **recovery procedure** in its message: do not re-run (the upload is consumed, AMO refuses a duplicate version number, and deleting a version never frees its number); open the version in the Developer Hub and attach the same `git archive` there, or re-send only the source `PATCH` → summary line: version id, channel, the state AMO returned for the version's file, and "source attached; follow it in the Developer Hub". No approval wait and no assumption about who reviews it: Mozilla escalates wallets to human review by risk score, not always. The create-then-patch order is the documented one and is what `web-ext sign` does.

**Source package.** The Firefox job builds it in place: `git archive --format=zip --prefix=nulo-${VERSION}/ -o source.zip "$SHA"` at the release commit (tracked files only, so no secret or build output can enter it; 27.5 MB today against a 200 MB cap). `store/SOURCE-BUILD.md` tells a reviewer on the default machine (Ubuntu 24.04, ARM64, 10 GB RAM, Node 24) exactly what differs and what to run: install the Bun version named by the archive's `package.json#packageManager` from the official release (pinned URLs + SHA-256 for linux-aarch64 and linux-x64), then run one script, `apps/extension/scripts/source-rebuild.sh <version>`, which **is** the procedure (the document invokes and explains it; there is no second copy of the commands to drift). The script refuses to run unless `apps/extension/package.json#version` equals `<version>` (release-please commits the version, so a stable tag's tree already carries it and CI's `version_override` is a no-op there, `_build-extension.yml:60-71`), runs `PUPPETEER_SKIP_DOWNLOAD=1 bun install --frozen-lockfile` (dependencies come only from the npm registry via `bun.lock`; the patched packages are listed with reasons), then `bun run build:firefox`; the reviewer diffs `apps/extension/dist/firefox` against the unpacked add-on; it states the measured peak memory (Phase 5 measures it; if it exceeds 9 GB the file says so up front, as Mozilla requires) and that the build makes no network request.

**Reproducibility (`.github/workflows/source-rebuild.yml`).** Advisory, no secrets, `permissions: contents: read`. Triggers: `workflow_dispatch` (input `tag`, optional), a weekly schedule, and, **only while Arc 2 is in development**, `push: branches: [worktree-chrome-store-launch-firefox]`: a new workflow file cannot be dispatched until it exists on the default branch, so a branch-scoped push is how Phase 5 runs it before any PR (every push to that branch, so a fix confined to `vite.config.ts` or `package.json` is covered). The trigger stays through Arc 2's whole fix loop and is deleted by an **isolated, trigger-only commit** just before the PRs open, so nothing fires on `dev` or `main`. A first job, `target`, resolves one SHA for everything: the tag's commit when `tag` is given, else `github.sha`; no independent `ref` input exists to select another tree. The **shipped** bytes come from one of two mutually exclusive jobs (a reusable-workflow caller cannot also hold steps): `reference-release` (`if: inputs.tag != ''`) downloads `nulo-firefox-<v>.zip` from that GitHub Release, unpacks it and uploads it as artifact `reference`; `reference-build` (`if: inputs.tag == ''`) calls `_build-extension.yml` (the workflow the release itself uses) with `target: firefox`, `upload_artifacts: true` and `ref` = the resolved SHA, producing `extension-firefox`. Jobs `rebuild-x64` (`ubuntu-latest`) and `rebuild-arm64` (`ubuntu-24.04-arm`): `git archive` the SHA → unpack under `$RUNNER_TEMP`, **outside any git checkout** (inside the workspace the archive's `prepare` would find the parent repo and hide the defect) → `source-rebuild.sh` → upload as `rebuild-x64` / `rebuild-arm64`. Job `compare` (`if: always()`, requires both rebuilds to have succeeded and **exactly one** reference job to have succeeded, the other skipped) downloads whichever reference artifact exists and runs `diff -r` for each rebuild against it; **any difference fails**, printing the first 50 paths. Mozilla's rule is "There must be no differences"; a documented difference is not a pass.

Both jobs: `needs: [resolve, attach-assets]`; `if: always() && !cancelled() && github.event.inputs.publish_<store> == 'true' && needs.resolve.result == 'success' && needs.attach-assets.result == 'success' && needs.resolve.outputs.is_prerelease == 'false'` (stores take stable releases only; **Trade-offs.** *Keyless over a refresh token*: nothing long-lived exists to steal or rotate, and the token is minted only inside a reviewer-gated environment on `main`; cost: a Google-maintained action in the job (SHA-pinned; it handles the OIDC exchange rather than a fourth hand-rolled request chain) and a one-time Cloud setup. No refresh-token fallback is built: MetaMask runs this path in production and a public run log shows it end to end; if the account session proves it unworkable, the fallback is a small follow-up, not dead code shipped now. *Fetch over `web-ext sign` for AMO*: the job holding Mozilla's key runs no third-party package tree (`web-ext` pulls hundreds of transitive dependencies through `bunx` at run time); `web-ext lint` stays, in jobs with no credential. *Manual first submission on both stores*: Chrome's API cannot create items; doing AMO's by hand too keeps listing text, screenshots and the privacy policy in one human-reviewed step and keeps the API surface to "add a version". *`git archive` over a curated source bundle*: reproducible from the tag, nothing to maintain. *One listing file*: the two stores ask the same questions in different forms; one tested source cannot disagree with itself or with `legal/privacy.md`.

## Phases

Two arcs, stacked. Arc 1 = Phases 1–3 (shared assets + Chrome). Arc 2 = Phases 4–6 (Firefox).

### Phase 1 — Icons and store name ✓

## Security & Adversarial Considerations

- **Either publish path can push code to every user; that is the asset.** An attacker's routes: a stolen long-lived credential; a malicious dispatch from a branch carrying a modified script or workflow; a dependency executing in the credential-bearing job; a swapped zip; log leakage; phishing the owner's Google or Mozilla login.
- **Chrome holds no long-lived credential.** The token is minted per run, lives 10 minutes, carries only the `chromewebstore` scope, and is masked. The Workload Identity provider's attribute condition (account checklist) is `assertion.repository_id == '1243703739' && assertion.repository_owner_id == '2982991' && assertion.environment == 'chrome-web-store' && assertion.ref == 'refs/heads/main' && assertion.event_name == 'workflow_dispatch' && assertion.workflow_ref in ['alejoamiras/nulo/.github/workflows/release.yml@refs/heads/main', 'alejoamiras/nulo/.github/workflows/store-check.yml@refs/heads/main']`: numeric ids survive renames; `ref` is pinned separately because an environment-scoped `sub` drops it; `workflow_ref` and `event_name` stop any *other* workflow on `main` that names the same environment (including a `pull_request_target` one) from minting the token; any job *inside* those two workflows that named the environment and held `id-token: write` would still qualify, which is why both files stay small and reviewed. A repository rename changes `workflow_ref` and must update the condition (runbook). A fork, another repo, another branch, another workflow or a job outside the environment cannot obtain a token; the service account has no Cloud roles at all.
- **Firefox holds one key pair**, only in the `firefox-add-ons` environment, on one step's `env`, masked, in a job that runs no third-party code after checkout and Bun setup. Mozilla revokes keys it finds inside uploads; `git archive` cannot contain one. Rotation: regenerate in the Developer Hub, replace the two secrets (runbook).
- **Both environments**: required reviewer = the owner (self-review allowed: single maintainer; the value is the deliberate click), deployment branches = `main` only, admin bypass off. `production` is left untouched (it serves the non-interactive `push: main` path). Until an environment exists its input stays off; a job pointed at a missing environment would create an unprotected one, so the checklist creates the environments **before** the first dispatch and the runbook says so.
- **The script runs from the release commit, and that commit must be on `main`**: `resolve.outputs.on_main` gates both jobs, because the dispatch ref and the OIDC claims authenticate the workflow file, not the tag's commit. A dispatch from another ref fails the environment's branch rule and the OIDC condition.
- **Provenance**: the published bytes are `attach-assets`' zip, verified against the release's SHASUMS and against `VERSION`; nothing is rebuilt in a credential-bearing job. Each runner refuses the other store's zip.
- **Fail closed**: unknown states, timeouts and missing fields never publish; AMO validation failure never creates a version; a version without source fails the job loudly.
- **Supply chain**: no new packages. One new action (`google-github-actions/auth`, SHA-pinned, Google-maintained). `web-ext` is used only via the existing exact-pinned `bunx web-ext@10.6.0 lint`, never with credentials.
- **Honesty surface**: the listing is tested against both manifests and `legal/privacy.md`; the Firefox data declaration stops saying "none" while the policy describes transmissions (Ask 5); the remote-code answer is an explicit owner decision backed by a cited technical note (Ask 4); Mozilla's rule that "Modifications to these libraries/frameworks are not permitted" is an **open review risk**, not something disclosure satisfies (Ask 9).
- **Account layer (done 2026-09-21)**: passkey + Advanced Protection on `alejo@nulo.sh`, third-party OAuth apps limited to sign-in scopes (the Cyberhaven vector); Mozilla account with TOTP. Residual: anyone who does compromise the Google login can upload by hand; verified CRX uploads would close that (Ask 7).
- **V6 coexistence**: both stores reject duplicates; V6 needs a stated distinct purpose (a different Aztec regime, not interoperable) and its own gecko id. Not a V5 blocker.

1. **Dedicated environments** `chrome-web-store` and `firefox-add-ons` (reviewer = owner, `main` only, bypass off), created before either input is ever set. Default: yes.
2. **Chrome publish type.** `STAGED_PUBLISH` (after Google approves, nothing reaches users until the owner clicks Publish in the dashboard, within 30 days) or `DEFAULT_PUBLISH` (goes live on approval). Default: staged for a wallet; it is one environment variable to change.

4. **Remote code, both stores.** Google's policy lists "Building an interpreter to run complex commands fetched from a remote source, even if those commands are fetched as data" as a violation and exempts "code run in contexts that are isolated from extension APIs"; Mozilla says add-ons must "not load remote code for execution". Nulo executes dApp-supplied contract bytecode inside a bundled VM. The bytecode reaches nothing directly, but through the PXE's oracles it can cause reads from the configured node, and the hosting document has extension messaging. Phase 2 writes that down precisely (`remote-code.md`). **Owner decision (2026-09-21): declare "No remote code" on both stores, without waiting for a policy read** (neither store documents a pre-submission channel, so a reply may never come). The declaration rests on the note: the package loads no code from anywhere; what apps send is data interpreted by a bundled VM whose only exits are the wallet's own oracle calls. Chrome gets the note's summary in the remote-code justification field, Mozilla in the reviewer notes. A rejection costs one review cycle and is appealed with the same note. The privacy policy's two "no remote code" sentences are true under this reading and stay as they are.
5. **Firefox data declaration.** `"none"` means "doesn't collect or transmit any data"; Mozilla counts anything "handled outside of the add-on or the local browser", and the privacy policy describes transactions and balance queries going to a node. Default: `required: ["financialAndPaymentInfo"]` (its definition names "transactions"; it is shown to the user at install). Firefox's taxonomy is about what is **transmitted**, so the other candidates were assessed against outbound flows only and left out: `authenticationInfo` (passwords and keys never leave the device), `browsingActivity` / `websiteActivity` / `websiteContent` (connected-app origins are stored locally and sent nowhere), `personallyIdentifyingInfo` as far as contacts go (they stay local). **One judgment call remains inside this Ask, and it covers two categories**: for passkey profiles a label built from the normalized profile name (`passkey-label.ts:51-53`) and an identifier go to the browser's WebAuthn API and on to the user's authenticator, whose provider may sync them (`legal/privacy.md:157-160`). A name is `personallyIdentifyingInfo` and a credential label is arguably `authenticationInfo`. The default leaves both out on one reading: the browser and the user's own credential manager are acting at the user's request, not the add-on sending data to a party of its choosing. That reading is contestable; the owner can add either or both (cost: one more line each in the install prompt), and Mozilla's reviewers may ask. Chrome's form is broader (it covers local handling), so its answers tick more boxes; the two differ by design. This supersedes firefox-first-class A2, whose comment asked for exactly this settlement. No Mozilla ruling exists; this is a reading (moderate-to-high confidence).

8. **Firefox channel.** Listed with the `experimental` flag (public page, reduced visibility; the nearest thing to Chrome's Unlisted) or unlisted self-distribution (signed file on the GitHub Release, no page, updates need an `update_url`). Default: listed + experimental.
