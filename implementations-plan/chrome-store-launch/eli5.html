Getting Nulo V5 onto the Chrome Web Store

This plan does the half that lives in the repo: the store name, real icons, the promo tile and screenshots, the listing text with honest answers to Google's questions, a privacy page on nulo.sh, and a publish button in the release workflow that talks to the store's current API. The half that needs you in the room (creating the Workspace account, paying the fee, the first upload, the API credentials, locking down the GitHub environment) is written up as a checklist at the end, for the session where I drive the browser and you supply the codes.

Why light

Every piece is bounded and reversible: a rename, generated images, text files, a static page, and one workflow job that stays switched off until you flip it. The one genuinely dangerous thing, the store credential, is handled by the plan's security section and the checklist, not by more ceremony.

Phases

1 · Icons and the name

The extension becomes "Nulo V5" (that name is what the store shows) and gets a proper 16/32/48/128 icon set generated from the existing 512px mark, with a test that fails if the files ever drift from the generator.

Proves itself by: typecheck, lint, the icon test, a production build whose manifest shows the new name and four icons, and the smoke test suite green on the renamed build.

2 · Pictures and words

Real screenshots of the popup (Home, Send, Settings) taken by the existing test harness, framed at the store's 1280×800, plus a 440×280 promo tile, plus the listing text: title, summary, description, why each permission exists, and Google's data-use answers written from what the wallet actually does.

Proves itself by: the files exist at the exact sizes, and a test checks the listing covers every permission in the manifest and stays inside the store's length limits.

3 · Privacy page

nulo.sh/privacy: what stays on your device, what leaves it (the node you use, the price lookup and how to turn it off), what we never collect, backups, passkeys, how to delete everything, how to reach us.

Proves itself by: the landing's checks plus a build, and a browser load of the page under the real security policy with no errors.

4 · The publish button

A small script, no third-party package, that uploads the exact zip from the GitHub Release to the store's v2 API, waits for the upload to process, and submits it for review. A dry-run mode makes no network calls. It only runs when you tick "publish_chrome" on a release; Firefox stays parked.

Proves itself by: unit tests (including "no secret ever appears in the output" and "dry run makes zero requests"), lint, actionlint, and a real dry run against a local zip.

What codex caught (and what changed)

Codex rejected the first draft, and it was right. The store API the draft used is being shut off on 15 October 2026, and I had misread its status words; the plan now uses the current API. The dry-run flag was read from a place that doesn't carry it, which could have published during a dry run; fixed. Turning on "publish" would also have fired the still-stubbed Firefox job and failed the release; Chrome now has its own switch. The publish job would have run whatever code was on the branch you dispatched from; it now runs the script from the release commit itself. "Collects no user data" was not an honest answer for a wallet; the answers now describe the real data flows. And two questions turned out to be yours, not mine (below).

Decisions I need from you

1. Lock the GitHub "production" environment before the first real publish. Right now it has no required reviewer, no rule about which tags can deploy, and admins can bypass it. Anyone with write access could dispatch a publish. The checklist has you add yourself as required reviewer, restrict deployments to v* tags, and turn bypass off. Default: required before the switch is ever used.
2. How we answer Google's data questions. Draft: the wallet handles sign-in data and financial data on your device; it sends transactions and balance queries to the network node (our default nodes, or yours) and one fixed price lookup to CoinGecko while unlocked (you can turn it off); we run no servers and collect nothing; nothing is sold or reused. Confirm this framing.
3. The "remote code" question. Google forbids extensions that run code fetched from elsewhere. Nulo runs contract bytecode that apps send it, inside the bundled Aztec simulator, only after you approve the request. That is data interpreted by shipped code, walled off from browser APIs, the same as every Aztec wallet. Proposed answer: "No remote code", with that explanation in the reviewer notes. Confirm, or ask me to get a policy read first.
4. Distribution stays Unlisted for the first release; the API keeps whatever visibility the dashboard has. Default: yes.

Already decided in chat, not re-asked: the name "Nulo V5"; the Workspace account; publish stays opt-in. One caveat for later: Google rejects duplicate extensions, so the V6 listing will need to state its distinct purpose (a different Aztec regime, not interoperable); a "V6" suffix alone isn't a guarantee.
