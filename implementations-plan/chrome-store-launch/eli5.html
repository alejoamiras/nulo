Getting Nulo V5 onto the Chrome Web Store and Firefox Add-ons

This plan does the half that lives in the repo: the store name, real icons, the promo tile and screenshots, one listing text for both stores, an honest Firefox data declaration, a source package Mozilla's reviewers can rebuild, and two publish buttons in the release workflow. The half that needs you in the room (the first upload to each store, the Google Cloud setup, the GitHub environments) is a checklist at the end.

What changed since the plan you last saw

  • Firefox joined. The Firefox build became first-class on dev on 2026-09-21, and you asked for it to be part of this plan.
  • Chrome publishing needs no stored secret. GitHub proves who it is to Google for a few minutes at a time, and Google lets it act as a service account that is linked to your store publisher. MetaMask publishes this way. Nothing long-lived sits in GitHub to steal.
  • The privacy page already exists. Another branch shipped nulo.sh/privacy and /terms from legal/. This plan only links them from the home page and tests that the store listing never disagrees with the policy.
  • Done on the account side: alejo@nulo.sh with a passkey, Advanced Protection and the third-party app block; the hello@nulo.sh group; the Chrome developer account as a non-trader; nulo.sh verified; the Firefox developer account with two-step sign-in.
GitHub job on main, in a locked environment→short-lived GitHub identity token→Google checks repo, branch, workflow, environment→10-minute store token→upload + submit for review

Firefox has no equivalent. Mozilla's API takes a key and a secret, so those two values live in their own locked GitHub environment.

Phases

Arc 1 · first PR · shared assets and Chrome

1 · Icons and the name

The extension becomes "Nulo V5" and gets real 16/32/48/96/128 icons generated from the 512px mark, with a test that fails if the files drift from the generator. This also clears four icon warnings from Mozilla's linter.

Proves itself by: typecheck, lint, the icon test, both production builds, Mozilla's linter at zero errors, and the Chrome smoke suite on the real production bundle.

2 · Pictures, words, and the remote-code note

Real popup screenshots framed at 1280×800, a 440×280 promo tile, and one listing file with a section per store. Its answers come from a data inventory: what each kind of data is, where it lives, and where it goes. A cited technical note describes exactly what contract bytecode from apps can and cannot reach. The home page gets links to the privacy policy and terms.

Proves itself by: exact image sizes, and a test that the listing covers every permission in both manifests and matches the privacy policy's own permission table.

3 · The Chrome publish button

A small script with no third-party packages uploads the exact zip from the GitHub Release, waits for processing, and submits it for review. It refuses a tag whose commit is not on main, refuses the Firefox zip, and fails closed on any state it does not recognise. A separate, read-only "store check" workflow signs in and reads the item's state without uploading anything.

Proves itself by: unit tests (the token never appears in output, a dry run makes zero requests, every unknown state stops before publishing), lint, actionlint, and a dry run against a real release zip.

Arc 2 · second PR, stacked on the first · Firefox

4 · The Firefox data declaration

The manifest stops saying the wallet transmits no data, which contradicts the privacy policy, and declares what it does send. The install prompt is checked in a real Firefox.

Proves itself by: tests, the linter at zero errors, and a screenshot of the consent line from a packaged install.

5 · A source package reviewers can rebuild

Mozilla rebuilds bundled add-ons from source on an ARM64 Ubuntu machine and requires byte-identical output. The plan ships one rebuild script plus a reviewer document, fixes an install hook that currently fails outside a git checkout, and adds a workflow that rebuilds from the source archive on x86 and on ARM and compares both with the build the release ships. Nobody knows yet whether the build is reproducible, or fits in the reviewers' 10 GB. This phase finds out.

Proves itself by: three local rebuilds with no differences, measured peak memory, and both CI rebuilds identical to the reference. Any difference fails.

6 · The Firefox publish button

Same shape as Chrome's, talking to Mozilla's API directly. It uploads the release zip, waits for Mozilla's validation, creates the version with the reviewer notes, and attaches the source archive. If anything fails after the version exists, the error message carries the recovery steps and says not to re-run.

Proves itself by: unit tests (neither the secret nor any token derived from it appears in output, wrong zips and an unsettled data declaration are refused before any request), lint, actionlint, and a dry run.

What codex caught this time

Codex rejected the first two drafts of this revision, conditionally approved the third and approved the fourth. All 33 findings held up when I checked them against the repo, and all were adopted. Its approval covers the plan only: whether the build is reproducible, whether the credentials work, and what the stores decide are still unknown. The ones that mattered most: a release tag on another branch could have supplied the script that runs with the store credential, so both publish jobs now require the tagged commit to be on main. The source install fails outside a git checkout, which I reproduced, so Mozilla's reviewers could not have rebuilt anything. My rebuild check compared two rebuilds with each other instead of with what ships, and tolerated "documented" differences that Mozilla does not. The Chrome script waited on a status field that need not exist after a fast upload. My credential check lived inside the release workflow, where it would have re-uploaded release assets and fired deploy hooks, and it would have rejected the very submission it was meant to read. I had written that disclosing our patched libraries satisfies Mozilla's rule against modified libraries. It does not. And my remote-code default turned silence from Google's support into a "No".

Decisions I need from you

1. Two locked GitHub environments, chrome-web-store and firefox-add-ons: you as required reviewer, main only, admin bypass off. The shared production environment stays as it is. Default: yes.
2. Staged or direct publishing on Chrome. Staged means that after Google approves a version, nothing reaches users until you click Publish in the dashboard, within 30 days. Direct goes live on approval. Default: staged. It is one setting to change later.
3. Chrome's data answers. Google's form covers data handled on the device, not only data sent. The draft ticks financial information, authentication information, personal information (contact names) and web history (the sites you connect to), and names each destination: your node, CoinGecko, approved apps, the optional local prover, the proving-parameter hosts, and your passkey provider. Default: as drafted.
4. Remote code, both stores. Google lists "building an interpreter to run complex commands fetched from a remote source" as a violation, and exempts code isolated from extension APIs. Nulo runs contract bytecode from apps inside a bundled virtual machine. The bytecode reaches nothing directly, but through the wallet it can cause reads from your node. Phase 2 writes this down precisely. Default: send that note to both stores' support, then you choose the declaration with their replies in hand. Silence is not a "No". The privacy policy's two "loads no remote code" sentences must end up saying the same thing.
5. The Firefox data declaration. "None" means the add-on transmits no data, and the policy says transactions and balance queries go to a node. Default: declare financial information, which Firefox shows at install. One judgment call: passkey profiles hand a label built from your profile name to your authenticator, whose provider may sync it. I read that as the browser and your own credential manager acting, not the add-on, so the default leaves out both "personal information" and "authentication information". That reading is contestable. You can add either, and Mozilla's reviewers may ask.
6. The draft banner on the legal pages. Both stores need a reachable privacy policy, and today's has a DRAFT banner and blanks only you can fill. Default: fill the blanks and set the privacy policy's date before the first submission. The terms stay draft until the listing links exist. None of it blocks the repo work.
7. Signed uploads on Chrome: defer. They would stop a hijacked Google login from uploading by hand, but every upload would need a signing key stored as a secret, which undoes the keyless setup, and a lost key costs up to a week. Default: revisit after the first public listing.
8. How Firefox lists it. Firefox has no link-only listing. The choice is a public page with the "experimental" flag, which reduces visibility, or a signed file you host yourself. Default: public page, experimental flag.
9. Mozilla's rule against modified libraries. The build patches two Noir packages and swaps three small modules so the bundle runs under a browser's security policy. Telling reviewers is necessary, but it is not permission. Default: list the changes exactly and ask Mozilla in the same message as decision 4. If they say no, the fix is upstream work, outside this plan. It blocks only the Firefox submission.

Already decided: the name "Nulo V5"; Chrome starts Unlisted; publishing stays opt-in; you sign in as alejo@ and hello@ is the public contact; non-trader on Chrome; the Firefox add-on ID and minimum Firefox 153.
