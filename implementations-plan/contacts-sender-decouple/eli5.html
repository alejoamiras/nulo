contacts-sender-decouple

Right now, when you add or edit a contact, the wallet also offers to "register them as a sender" — a technical step that used to be required for the wallet to notice tokens that contact sends you. The Aztec network changed: since v5, the very first transfer someone sends you makes itself discoverable on-chain (a "handshake" keyed to your address). For the token this wallet ships, that's guaranteed — no registration needed. So the toggle asks users to do something unnecessary, and the empty token screen tells them to add contacts "to receive" — which is no longer true. This plan removes the coupling everywhere in contacts (after an adversarial audit, it goes further than toggles: contacts will never silently touch sender registrations — no hidden migrations on edit, no hidden deletes on import merges) and leaves sender registration where it belongs: a niche tool in Advanced settings.

Why this tier was chosen

light. Rubric: novelty low (removing UI, not building), blast radius low (extension app only, service layer untouched), irreversibility low (pre-production, pure UI), no migrations, no external-coupling change, security-positive (it shrinks what connected dApps can learn about your address book). Zero high dimensions. The single codex audit came back conditional approve; all five conditions are folded into the plan below.

Phases

Phase 1: Decouple the contacts UI

Remove the register-as-sender toggle from add-contact and edit-contact, the "also unregister" question when deleting, and two hidden behaviors the audit flagged: editing a registered contact's address no longer silently moves the registration, and importing contacts no longer silently deletes old registrations during name-merges. Import keeps its one sanctioned power: rows explicitly marked "sender" in a file you exported earlier still get registered — now with a visible count. The little read-only "sender" chip on contact rows stays.

Proves itself by: lint + typecheck + the full unit/component suite, all green.

Phase 2: Fix the wording

The empty token screen's "Add contacts to send and receive X" becomes "Send or receive X to see activity here." Plus a sweep for any other copy claiming registration is needed to receive, a small typo fix, and rewording the Advanced senders screen to say what it's actually for now (legacy-delivery tokens only).

Proves itself by: lint + typecheck + tests + a grep sweep showing no stray old copy.

Phase 3: New focused tests

The three contact popups have no component tests today. This phase adds them, pinning the new behavior: saving a contact touches contacts only, imports count their sender additions, merges never delete.

Proves itself by: the new tests green inside the full suite.

Phase 4: Update the browser tests

The automated browser tests that click the removed toggles get reworked; sender add/remove coverage moves to the Advanced settings screen where the feature now lives.

Proves itself by: the reworked network e2e green against a live local node.

Phase 5: The proof test — REQUIRED

A brand-new test doing the thing this plan claims is safe: a separate account (never seen by your wallet, provably not registered) sends you tokens — and the wallet finds them anyway, with the exact balance change asserted. The audit insisted (and the plan agrees): there is no soft fallback. If this can't be made to pass, the plan stops and comes back to you.

Proves itself by: the no-registration receive test green on a live local node.

Phase 6: Full quality gates + docs

Run the full pre-PR audit (typecheck, all tests, lint, build) plus the smoke browser suite, and update the docs that describe the old flow.

Proves itself by: bun run audit:vue and the smoke e2e suite both green.

Human context

Private tokens on Aztec are like sealed envelopes in a public pile — your wallet must figure out which are addressed to you. It used to need a hint: "watch for envelopes from THIS person" (sender registration — why adding a contact offered it). Aztec v5 added a smarter scheme: the first envelope anyone sends you comes with a public sticker derived from your own address, which your wallet always watches for. For the token this wallet bundles, the sticker is enforced by the token's own rules, so discovery is guaranteed. One honest nuance the audit sharpened: for OTHER tokens using a looser delivery mode, the sticker is the ecosystem default but ultimately the sender's wallet's choice — which is exactly why the Advanced senders tool survives as an escape hatch. And a small privacy note: the sticker reveals that someone started sending to your address — not who, not what; that's a network property, not ours. Removing default-on registration is a privacy improvement on our side: registered senders were visible to connected dApps.
