contacts-sender-decouple

Right now, when you add or edit a contact, the wallet also offers to "register them as a sender" — a technical step that used to be required for the wallet to notice tokens that contact sends you. The Aztec network changed: since v5, the very first transfer someone sends you automatically makes itself discoverable (a "handshake" published on-chain, keyed to your address). So the toggle now asks users to do something they don't need to do, and the empty token screen tells them to add contacts "to receive" — which is simply no longer true. This plan removes all of that from the contacts flow and leaves sender registration where it belongs: a niche tool in Advanced settings, for rare tokens that still use the old delivery style.

Why this tier was chosen

light. Rubric: novelty low (removing UI, not building), blast radius low (extension app only, service layer untouched), irreversibility low (pre-production, pure UI), no migrations, no external coupling changes, security-positive (it shrinks what connected dApps can learn about your address book). Zero high dimensions → the lightest tier, with a single codex audit.

Phases

Phase 1: Add-contact popup

Remove the "Register as sender" toggle and the behind-the-scenes registration when you save a new contact. Saving a contact just… saves a contact.

Proves itself by: lint + typecheck + component tests, all green.

Phase 2: Edit-contact popup

Same removal there. One invisible behavior stays: if a contact who IS registered gets their address corrected, the registration quietly follows the new address so no stale entry is left behind.

Proves itself by: lint + typecheck + component tests, all green.

Phase 3: Delete flow + the little "sender" chip

Deleting a contact stops asking about unregistering senders — it just deletes the contact. The small read-only "sender" chip on contact rows stays (your call), so power users can still see who's registered.

Proves itself by: lint + typecheck + component tests (chip tests unchanged).

Phase 4: Fix the wording

The empty token screen currently says "Add contacts to send and receive X" — receiving needs nothing, so it becomes "Send or receive X to see activity here." Also sweep the app for any other copy claiming registration is needed to receive, and reword the Advanced senders screen to say what it's actually for now (legacy-delivery tokens only).

Proves itself by: lint + typecheck + component tests + a grep sweep showing no stray old copy.

Phase 5: Update the browser tests

The automated browser tests that click the removed toggles get reworked: sender add/remove coverage moves to the Advanced settings screen where the feature now lives.

Proves itself by: the reworked network e2e tests green against a live local node.

Phase 6: The proof test

A brand-new test that does the thing this whole plan claims is safe: a separate account (not in your contacts, not registered as a sender) sends you tokens — and the wallet finds them anyway. This turns the plan's core claim from "verified by reading Aztec's source" into "proven in our own app, every CI run."

Proves itself by: the no-registration receive test green on a live local node (documented fallback if the harness fights us).

Phase 7: Full quality gates + docs

Run the full pre-PR audit (typecheck, all tests, lint, build) plus the smoke browser suite, and update the docs that describe the old flow.

Proves itself by: bun run audit:vue and the smoke e2e suite both green.

Human context

Private tokens on Aztec are like sealed envelopes scattered in a public pile — your wallet has to figure out which ones are addressed to you. It used to need a hint: "watch for envelopes from THIS person" (that's sender registration, and why adding a contact offered it). Aztec v5 added a smarter scheme: the first envelope anyone sends you comes with a public sticker derived from your own address, which your wallet always watches for. After that first envelope, everything from that sender is findable. A tiny privacy note: the sticker reveals that someone started sending to your address — not who, and not what — and that's a property of the network itself, not of this change. Removing the default-on registration is actually a privacy improvement on our side: registered senders were visible to connected dApps that query your private events.
