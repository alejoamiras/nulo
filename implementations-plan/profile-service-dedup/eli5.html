Blueprint ELI5 · arc 1 of the complexity burn-down

Profile Service Dedup

Clean up the wallet's most sensitive file — the profile service — by collapsing its thirteen copy-pasted blocks into shared helpers, without changing what the code does.

What this is

One 2,600-line file guards unlocking, deleting, exporting, and restoring wallet profiles. Over time the same few shapes — "lock, fetch, check, capture" — were pasted into it thirteen times, and eleven of the repo's 230 grandfathered complexity waivers live here. This plan extracts the repeated shapes into small named helpers and splits the four giant functions at their natural seams, so the waivers can be deleted. Nothing user-visible changes: same errors, same events, same timing of secret wipes.

Why the lightest planning tier

One file, one test suite, no new features, fully reversible (revert the one PR). The risk rubric scored zero highs — but because it's wallet-critical code, the plan still went through two adversarial review rounds with a second model (Codex), which first rejected the draft, forced a safer design, then approved it with three conditions — all adopted.

The five phases

1 · Pin current behavior first

Before touching anything, write tests that freeze the exact error messages and event order today's code produces — including one deliberately preserved oddity (a mid-crash profile can still be renamed) marked as a known bug, not fixed here.

Proves itself by: new pins pass against the unchanged code.

2 · The safe, mechanical extractions

Four tiny helpers replace the blocks that are byte-identical everywhere they appear.

Proves itself by: full profile test suite + lint + typecheck green.

3 · The two unlock flows

Password and passkey unlock share their opening step; their differing security checks stay deliberately separate.

Proves itself by: the unlock race-condition tests stay green.

4 · Password change, deletion, cleanup

Three heavyweight functions split at their existing internal seams — one at a time, tests between each.

Proves itself by: deletion-safety tests green after each split.

5 · Backup restore (the riskiest, done last)

The 300-line restore function becomes two clear branches over one shared write-safely helper; the finalize step is split the same way. Then the duplication scanner re-runs to prove the clones are actually gone.

Proves itself by: everything above, plus the full pre-PR battery and the clone count dropping from 13 to ≤3.

What you're ratifying (post-hoc)

  • Scope: behavior-preserving refactor of one file; the waiver count in the repo drops from 230 toward 219.
  • Residue rule: zero waivers here is the target; if a function resists a natural split, it keeps its waiver with a one-line justification for your sign-off in the PR.
  • The pinned bug: renaming works on a profile that's mid-deletion after a crash — preserved and test-documented; fixing it would be a separate PR.
  • FYI: three stale worktrees on this machine still touch this file (all superseded by merged work) — worth deleting when convenient.
