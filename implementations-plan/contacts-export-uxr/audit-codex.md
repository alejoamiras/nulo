# Codex audit — Contacts export UX rework

Date: 2026-04-29
Model: gpt-5.4 with `reasoning_effort=xhigh`

## BLOCKING

- **The SW download path is not implementable as written because it relies on blob URLs inside a service worker.** The plan's core move is `ContactService.exportContactsAndDownload()` in the MV3 background worker, building a `Blob`, calling `URL.createObjectURL(blob)`, then `chrome.downloads.download(...)` and `URL.revokeObjectURL(...)` (`implementations-plan/contacts-export-uxr/plan-v1.md:46-65,229-232`). The repo's current blob-download helper does exactly that, but only from an extension page context (`packages/extension/src/utils/files.ts:46-80`). External verification matters here: `URL.createObjectURL()` / `URL.revokeObjectURL()` are not available in service workers, including extension service workers (MDN: `https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static`, `https://developer.mozilla.org/en-US/docs/Web/API/URL/revokeObjectURL_static`). The manifest and SW setup themselves are fine for `chrome.downloads.download` (`packages/extension/manifest/manifest.config.ts:18-35`), and the background RPC transport does support "popup closed after dispatch" semantics (`packages/extension-messaging/src/background/client.ts:69-82`, `packages/extension-messaging/src/background/service.ts:62-101,119-126`), so the architectural direction is salvageable. But the download materialization step must be re-planned before execution. Change shape: keep JSON generation in `ContactService`, but either hand the actual Blob/download work to the existing offscreen-document infrastructure (`packages/extension/src/wallet/utils/offscreen.ts:83-140`, `packages/extension/src/offscreen/index.ts:1-45`) or switch the SW-side download input to a DOM-free encoded `data:` URL if the team is comfortable relying on the small-export-size constraint. Do not execute the blob-URL-in-SW version, and do not write tests for that mechanism (`implementations-plan/contacts-export-uxr/plan-v1.md:188-193`).

## SHOULD-FIX

- **The orphan-timer bug in `useToast()` does affect the proposed export flow.** The plan treats it as a harmless pre-existing bug because the new success/failure toast arrives long before the 30s loading timer would fire (`implementations-plan/contacts-export-uxr/plan-v1.md:132-135`). That misses the real failure mode. `openToast()` overwrites `closeTm` without clearing the prior timeout (`packages/extension/src/composables/toast.js:15-20`). On the contacts page, users can easily have a short-lived toast already pending, for example "Address is copied" or "Contact successfully deleted" (`packages/extension/src/popup/pages/settings/contacts/index.vue:98-112`). If they start export during that 1.5s-4s window, the old timer will clear the new `"Exporting contacts…"` toast early, which directly weakens issue 2's loading-feedback fix. Change shape: clear the previous `closeTm` at the top of `openToast()`, then keep the planned `closeToast()` call before the completion toast.

- **If export ownership moves into the SW, move filename resolution there too.** The plan still does a popup-side `ProfileServiceClient.getActiveProfile()` round-trip before dispatching the background export (`implementations-plan/contacts-export-uxr/plan-v1.md:86-97,118-119,235-236`). `ContactService` already has `ProfileService` injected today (`packages/extension/src/wallet/services/contact/service.ts:31-43`), so the SW can derive the filename itself with almost no extra surface area. Leaving the popup-side profile lookup in place preserves a final popup-close hole after permission grant but before the background work starts. That is much smaller than the current 5s-7s sender-union window, but the whole point of the refactor is popup-close survival; this await is the last avoidable gap. Change shape: let `exportContactsAndDownload()` compute the default filename internally, with an override parameter only if product really needs it.

- **The plan's "non-time-based" parallelism test does not actually prove parallelism.** The proposed fallback is "one network throws while another resolves; assert the other network's `getSenders` was already invoked" (`implementations-plan/contacts-export-uxr/plan-v1.md:197-201`). In the current serial implementation, the loop catches a failure and then moves on to the next network (`packages/extension/src/wallet/services/account-state/service.ts:83-92`), so both calls can still happen without any parallelism. Change shape: use deferred promises / checkpoints instead of wall-clock timing. Example: leave network A's `getNodeStatus()` pending, assert network B's `getNodeStatus()` or `getSenders()` has already been called, then resolve A. That proves concurrency and stays deterministic under vitest.

## NICE-TO-HAVE

- **Once the blocking download mechanism is re-planned, align the tests with the chosen transport instead of the blob-URL path.** The current vitest setup only stubs `chrome.runtime` and related message plumbing (`packages/extension/tests/vitest.setup.ts:78-101`). It does not currently provide `chrome.downloads`, `URL.createObjectURL`, or `URL.revokeObjectURL`. If the final implementation still reuses `downloadFile()`-style Blob handling outside the SW, add explicit stubs for those globals; if it switches to a SW-safe `data:` URL or an offscreen helper, test that real mechanism instead.

- **A simple in-page export guard would prevent duplicate downloads if the user clicks Export twice quickly.** The current contacts page has no `isExporting` gate around `handleExportContacts()` (`packages/extension/src/popup/pages/settings/contacts/index.vue:117-181`). Pre-launch this is acceptable, but if QA sees doubled files or overlapping toasts after the refactor, a single ref-based guard on the page will contain it without changing the service shape.

## VERIFIED

- **The manifest and MV3 background setup themselves are compatible with background-side downloads.** The extension is a normal MV3 worker-backed extension (`packages/extension/manifest/manifest.config.ts:18-21`) and already declares `downloads` as an optional permission (`packages/extension/manifest/manifest.config.ts:33-34`). There is no project-specific manifest blocker here; the blocker is specifically the plan's choice of blob URLs inside the worker.

- **The permission-gesture chain is correct only if `ensurePermissions()` stays first, and the plan preserves that.** The helper checks `chrome.permissions.contains(...)` and, if needed, immediately calls `chrome.permissions.request(...)` in that click-originated callback chain (`packages/extension/src/utils/general.js:16-25`). The current export handler already does permission before the slow sender-union query and before filename lookup (`packages/extension/src/popup/pages/settings/contacts/index.vue:117-139,153-179`), which matches the working `f2b5d1e` fix the user described. Moving filename resolution or any other RPC ahead of `ensurePermissions()` would reopen the gesture-expiry problem; keeping it after permission grant is correct.

- **Popup-close survival after request dispatch is a sound property of this repo's RPC transport.** When the popup disconnects, the client rejects its own pending promise and tears down the port (`packages/extension-messaging/src/background/client.ts:69-82`), but the background service handler keeps awaiting the requested method and only later attempts to post the response (`packages/extension-messaging/src/background/service.ts:62-101`). If the port is gone, the response send is just swallowed/logged (`packages/extension-messaging/src/background/service.ts:119-126`). So if the long-running export work is moved behind a service method and dispatched before the popup dies, the service side can continue. The current problem is that the long wait still happens in the popup before `downloadFile()` is called (`packages/extension/src/popup/pages/settings/contacts/index.vue:129-169`).

- **Mixed Option A for export and Option B for import is architecturally fine here.** Export is a one-shot operation with no mid-flow user confirmation, so moving it behind a service method is coherent. Import still stages through `ImportContactsPopup` and remains popup-owned with deliberate per-row apply behavior (`packages/extension/src/popup/pages/settings/contacts/index.vue:183-260`). I do not see a structural reason that export and import must be symmetric in this branch.

- **The plan's parallelization claims are otherwise accurate.** `Promise.allSettled()` preserves input order, so index-based per-network error attribution is fine (`implementations-plan/contacts-export-uxr/plan-v1.md:154-169`). It also does not cancel slow promises, which means the known offline-single-network case remains slow even after the change; only multi-network users benefit. That matches the current sequential implementation and the user's QA report (`packages/extension/src/wallet/services/account-state/service.ts:71-95`).

- **Adding a fake AccountStateService to `ContactService` unit tests is a reasonable amount of boilerplate.** Today the ContactService tests only register a local fake ProfileService plus the real service under a `ServiceCollection` (`packages/extension/src/wallet/services/contact/service.test.ts:19-64`). Adding one more local fake for sender-union lookups is modest and should stay inline unless a second test file needs it.
