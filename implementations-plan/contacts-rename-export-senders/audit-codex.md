# Codex audit — Contacts rename/export senders

Date: 2026-04-29
Model: gpt-5.4 with `reasoning_effort=xhigh`

## BLOCKING

- **Commit 2 changes the wrong execution path.** The plan treats `ContactService.exportContacts()` / `importContacts()` as the contacts-settings flow (`plan-v1.md:40-43,107-111`), but the real UI bypasses both methods today. Export is built inline in `handleExportContacts()` (`packages/extension/src/popup/pages/settings/contacts/index.vue:115-149`), and import is parsed inline, staged through `ImportContactsPopup`, then applied via direct `addContact()` / `updateContact()` calls (`packages/extension/src/popup/pages/settings/contacts/index.vue:152-234`, `packages/extension/src/popup/components/popups/ImportContactsPopup.vue:65-129`). As written, the v2 envelope and sender restore work would not ship on the user-facing path, and a future v2 export would crash the current settings-page importer because it still does `JSON.parse(data).map(...)` (`packages/extension/src/popup/pages/settings/contacts/index.vue:157-164`). Change shape: pick one canonical path. Either move the settings page onto `contactService.exportContacts()` / `importContacts()` end-to-end, or keep the popup pipeline and implement the envelope + sender restore there. If `ImportContactsPopup` is truly deferred, then sender-persistence cannot be claimed as shipped in this branch.

- **Export failure semantics are underspecified and can silently destroy backup fidelity.** The proposed OR pass walks every network from `getNetworks()` (`plan-v1.md:76-80`), but `getNetworks()` returns every configured network for the active profile, not only healthy ones (`packages/extension/src/wallet/services/network/service.ts:168-175`), and `getSenders()` hard-fails on PXE errors (`packages/extension/src/wallet/services/account-state/service.ts:52-60`). The only nearby precedent, `AccountStateService.backup()`, explicitly gates on `getNodeStatus(n.id) === Active` before reading senders (`packages/extension/src/wallet/services/account-state/service.ts:103-145`). Change shape: the plan must choose and document one rule before implementation. My recommendation is fail closed for export if a participating network cannot be read, or explicitly adopt the same active-only gating as backup. Do not coerce a failed network to `isSender: false`; that writes a lossy backup with no signal.

- **`isSender` restore is attached only to the add path, but import also merges existing contacts.** The plan says “after `addContact` succeeds” run `addSender(...)` (`plan-v1.md:82-86`). The real import path updates existing contacts by address or name as a first-class success case (`packages/extension/src/wallet/services/contact/service.ts:218-239`, `packages/extension/src/wallet/services/contact/service.test.ts:202-210`). Implemented literally, importing `{ isSender: true }` for an already-existing contact would update the contact but skip sender re-registration. Change shape: run sender restore after any successful merge outcome, keyed off the returned `contact`, not only after the create branch.

## SHOULD-FIX

- **Keep the envelope; reject unknown versions explicitly.** I do not recommend switching back to a flat array with per-contact `isSender`; the `{ version, contacts }` envelope is the cleaner forward-compat hook for a user-supplied file format, and the pre-launch “no migrations” guidance is about persisted storage, not backup-file schemas. But the parser needs an exact contract: legacy arrays are v1; plain objects must be exactly `{ version: 2, contacts: [...] }`; anything else, including `version: 99`, `version: "abc"`, or `contacts: null`, should hard-fail (`plan-v1.md:88-105`). Change shape: add a dedicated parse helper that normalizes only those two accepted forms and throws on everything else.

- **Snapshot the active network once per import run, and handle `null`.** `networkService.getActiveNetwork()` does exist (`packages/extension/src/wallet/services/network/service.ts:188-197`, `packages/extension/src/wallet/services/network/spec.ts:121-126`), but resolving it per contact lets a network switch mid-import split sender registrations across chains. The method also returns `null`, not a guaranteed network. Change shape: resolve the active network once after parse and before the import loop. If it is `null`, keep importing contacts and record sender-registration failures for every `isSender: true` row.

- **Do not use `onSenderAdded` as the failure-reporting strategy.** The alternative in the plan is weaker than the current popup patterns. `onSenderAdded` only emits a bare address, with no network id and no failure channel (`packages/extension/src/wallet/services/account-state/spec.ts:34-61`). The existing UX for sender registration in `NewContactPopup` and `EditContactPopup` uses local `try/catch` plus a boolean outcome to shape the completion toast (`packages/extension/src/popup/components/popups/NewContactPopup.vue:83-106`, `packages/extension/src/popup/components/popups/EditContactPopup.vue:154-205`). Also, `ContactService.importContacts()` is extension-internal, not a wallet-bridge API; repo search shows no consumer outside extension/popup/tests. Change shape: if this branch makes the settings page call `importContacts()`, return a structured summary from `importContacts()` and let the popup toast off that summary.

- **The test plan understates the required fake setup and misses the lossy multi-network case.** The current test file only registers `FakeProfileService` (`packages/extension/src/wallet/services/contact/service.test.ts:25-64`); there are no fake `NetworkService` / `AccountStateService` collaborators yet, so the plan’s “likely uses fake AccountStateService + NetworkService” note is incorrect (`plan-v1.md:134-136`). It also needs an explicit multi-network round-trip test that proves the chosen semantics are lossy by design: OR export collapses per-network state, and import restores only onto the snapshotted active network, not the original source network (`plan-v1.md:127-132,152-156`). Add at least these cases: existing-contact + `isSender:true`, sanitized-out row + `isSender:true`, unknown-version rejection, and multi-network round-trip with sender registered on a non-active network.

- **If the settings page or import popup come into scope to fix the blocking issue above, budget the required brutalist cleanup in those edited files.** The current contacts import UI still uses red/orange/green state signaling inside the popup (`packages/extension/src/popup/components/popups/ImportContactsPopup.vue:143-190`), and the contacts page itself contains warning-state affordances (`packages/extension/src/popup/pages/settings/contacts/index.vue:141-143,214-230`). The repo rule from the request was “strip color from any file edited,” so the plan should acknowledge that scope if it touches these files.

## NICE-TO-HAVE

- **Rename the sender-specific test ids while touching the menus.** The plan covers the labels and routes, but not `data-testid="tokens-menu-senders"` / `data-testid="token-manage-senders"` (`packages/extension/src/popup/components/modules/general/TokensView.vue:216-223`, `packages/extension/src/popup/pages/tokens/[id].vue:162-169`). I did not find e2e hits for those ids, so this looks cheap and keeps future tests aligned with the renamed UX.

- **Shorten the empty-state copy.** “Add the people you transact with to your contacts so you can find them quickly” (`plan-v1.md:62`) is serviceable but soft for the repo’s tone. A shorter line such as “Add contacts to send and receive {{ token.symbol }}.” or “Add contacts for addresses you use often.” is more in-family. I would keep it plain text rather than adding another link; the renamed menu item already provides the route from the same surface.

- **If `ContactService.importContacts()` becomes the canonical entry point, document its partial-state contract.** The method is sequential and only locks individual `addContact()` / `updateContact()` calls (`packages/extension/src/wallet/services/contact/service.ts:86-150,190-248`; `packages/wallet-core/src/utils/lock.ts:19-67`). A service-worker restart or two concurrent imports can therefore leave partially applied results. That is acceptable for a pre-launch wallet, but it should be stated explicitly if the branch elevates this method from “unused helper” to “real import path.”

## VERIFIED

- **`getActiveNetwork()` is real and returns `Network | null`.** The plan does not need a new API for that (`packages/extension/src/wallet/services/network/service.ts:188-197`, `packages/extension/src/wallet/services/network/spec.ts:121-126`).

- **The export-side network scan is one PXE read per network, not per contact.** `AccountStateService.getSenders()` does one `networkService.getNetwork(networkId)` lookup and one `pxeService.getSenders(...)` call (`packages/extension/src/wallet/services/account-state/service.ts:52-60`). There is no contact-level PXE fanout in the proposed OR algorithm.

- **The “Manage senders” inventory is complete for user-visible direct-entry links.** I confirmed the two token-surface menu items plus the retained Advanced → Account State → Senders entry (`packages/extension/src/popup/components/modules/general/TokensView.vue:216-223`, `packages/extension/src/popup/pages/tokens/[id].vue:162-169`, `packages/extension/src/popup/pages/settings/advanced/account-state/index.vue:35-41`).

- **Removing the token-surface entry points does not strand the Senders page.** The page remains reachable from Settings → Advanced, and Advanced already advertises “Notes, authwits, contracts, senders” (`packages/extension/src/popup/pages/settings/advanced/index.vue:183-205`, `packages/extension/src/popup/pages/settings/advanced/account-state/index.vue:35-41`). I do not think extra prominence is required if sender registration remains centered in the contact popups.

- **`ImportContactsPopup` does not currently share `contactService.importContacts()`.** The popup path stages selected rows in `cacheStore.importContacts` and resolves them back to the settings page, which then calls `addContact()` / `updateContact()` directly (`packages/extension/src/popup/components/popups/ImportContactsPopup.vue:65-129`, `packages/extension/src/popup/pages/settings/contacts/index.vue:177-217`). So there is no accidental scope creep from changing `contactService.importContacts()` today; the scope creep only appears if the plan is revised to make the settings page use that method.
