# Backup-restore data-corruption fixes — plan (mid)

**Status:** v3 (dual audit + final fresh-codex pass folded; final-pass confirmation pending) → approval gate. · **Tier: mid.** · Closes the migration arc: the 3 high-severity data-corruption bugs the scoped bug hunt found (`storage-migration-backup/bug-hunt-findings.md` P1–P3) + 2 folded-in cheap ones (P6, P7), as ONE PR.

> **v3 changelog (final-codex-pass driven):** two HIGHs the v2 rework left open. (1) **P1 gains a tx-restore provenance filter** — codex proved a restored tx whose `account` matches an EXISTING account in another profile is NOT inert: it surfaces in that profile's activity (`getTransactions` filters by `account`; `app.store.ts:153`) and, after removing the subscriber, `onAccountDeleted` never purges it (the account row isn't deleted). Index-pairing is unforgeable. (3) P3 gains a duplicate-`(chainId,contract)` ambiguity guard (skip-and-record, not last-wins). (4) Triggers corrected (backup normalization already rejects duplicate root ids — the real triggers are live-storage id collision + ambiguous failed/successful same-`name+chainId`). (5) Async-deletion caveat noted (P4). (6) `entity_storage` cite → wallet-core path; e2e gate takes the concrete file path.
>
> **v2 changelog (dual-audit driven):** **P1 reworked** — both auditors proved `AccountService` is ALREADY a chain-purge subscriber, so both purge triggers cascade account deletion → `TransactionService.onAccountDeleted` already cleans txs profile-accurately. The buggy `clearChainState(chainId-only)` subscriber is redundant AND wrong. v1 proposed adding a `profileId` field to tx rows; v2 **removes the redundant subscriber** — no schema change, no executor threading, eliminating codex's HIGH that restore would trust an attacker-supplied `tx.profileId`. Inference #2 corrected (was false, and was the v1 rationale). P2 keeps `profileId` all-rows (fable S2). P3 sources `chainId` from the old token.

## Goal
Fix five pre-existing correctness bugs in the full-backup **restore** + profile-deletion paths so importing a backup (or rolling one back) never corrupts data — no cross-profile tx wipe, no cross-network row grafting, no same-contract balance collapse — plus two low-risk robustness fixes. "Done" = each bug has a failing-before/passing-after test, a **network-e2e round-trip** proves the multi-profile/multi-network case on a live sandbox, and `audit:vue` + the smoke/network gates are green.

## Decisions locked (user, this session)

- **Validation:** each phase gates on typecheck/lint + unit/component; the final phase adds a **network-e2e round-trip** reproducing the corruption on a live sandbox.

## The bugs (all verified against the code this session)

### P1 — profile deletion wipes OTHER profiles' tx history · high
`TransactionService` registers a chain-purge subscriber (`transaction/service.ts:60` → `clearChainState`), and `clearChainState` filters by **`chainId` alone** (`:79`, comment admits tx rows carry no `profileId`). `NetworkService.purgeChain` fires it on both triggers — whole-profile delete (`onProfileDeleted`, `network/service.ts:684`) and single-network delete (`deleteNetwork` → `purgeChain`, `:301`). So deleting profile P2 (on a chain P1 also uses) erases **P1's entire tx history on that chain**. Reached by every post-network rollback branch in import (`useFullBackupImport.ts:384/419/509`) — most commonly an accidental re-import of your own backup (duplicate-address → rollback → wipe).

**Root cause + fix (v2/v3, audit-corrected):** `AccountService` is ALSO a chain-purge subscriber (`account/service.ts:48`); its `clearChainState(profileId, chainId)` deletes `(profileId, chainId)` accounts and emits `onAccountDeleted` per account (`:56-64`). `TransactionService.onAccountDeleted` (`:170`) then removes that account's txs — **account-scoped = profile-accurate**, firing on BOTH purge triggers. So the chainId-only subscriber is **redundant with the already-correct `onAccountDeleted` path; its only distinct effect is the cross-profile over-wipe.** **Fix (2 parts):**
1. **Remove** `TransactionService`'s `registerChainPurgeSubscriber` call (`:60`) + its now-dead `clearChainState` (`:79`); rely on `onAccountDeleted`.
2. **Add a tx-restore provenance filter** (v3, codex HIGH): after removing the subscriber, a restored tx whose `account` matches an EXISTING account in ANOTHER profile is NOT inert — `getTransactions` filters by `account` (`transaction/service.ts:92`), so it surfaces in that profile's activity (`app.store.ts:153`), and `onAccountDeleted` never purges it (that account row isn't deleted). So `restore` must accept ONLY txs whose `account` ∈ the set of accounts SUCCESSFULLY imported by THIS restore — `newAccounts.filter(a => !a.restoreError).map(a => a.address)` (the composable has `newAccounts` in scope; pass the address set to `transactionService.restore` or filter before the call). A tx for an unknown/foreign/failed account is dropped-and-recorded (`restoreError`), never written. This also makes the "inert orphan" tradeoff genuinely true: the only un-purged txs left are those whose account was legitimately imported then later deleted — cleaned by `onAccountDeleted` when that happens.

No schema change, no new attacker-trusted field.

### P2 — `remapIdInBackupData("networkId", …)` rewrites EVERY row's `networkId` to one id · high
`full-backup-helpers.ts:94` ignores the old value: for each network whose restored id changed, it stamps that id onto **every** `networkId`-bearing row — other networks', failed networks'. `useFullBackupImport.ts:406` calls it per-network, so with ≥2 id-changing networks the last one's id lands on everyone; account-state (PXE contract/sender registrations) grafts onto the wrong chain. Trigger (v3-corrected): backup normalization already rejects duplicate root-row ids (`backup-migration-registry.ts:170`), so the real triggers are a **live-storage id collision** on restore (`network/service.ts:653` reallocates the id) and the ambiguous-match case below.

**Second defect (v3, codex HIGH) — the old→new pairing is attacker-ambiguous.** The pairing matches `data.network` rows to restored rows by field equality (`useFullBackupImport.ts:402`). But `NetworkService.restore` returns one `Restored<Network>` per input IN ORDER, and **spreads a FAILED input's raw fields back into its result** (`network/service.ts:627-666`). So a backup with an invalid network A and a valid network B sharing `name+chainId` makes the field-match pair B with A; the scoped remap then grafts A's `account-state` onto B, and `AccountStateService.restore` trusts `item.networkId` to pick the PXE target (`account-state/service.ts:215`) → registrations on the wrong network. **Fix: pair by restore-result INDEX** — `newNetworks[i]` corresponds to `data.network[i]` (unforgeable; the field-match is abandoned entirely).

### P3 — token-balance remap collapses same-contract tokens across networks · high
`useFullBackupImport.ts:452-456`: `contractToNewId` is keyed by `contract` ALONE. Two tokens with the same contract on different chains both rewrite their balances to the last-restored token id. **Fix: key by `(chainId, contract)`.** Note: token-balance rows carry NO `chainId` (`token-balance/spec.ts`) — source it from the OLD token via `oldIdToContract` (extend to `oldId → ${chainId}:${contract}`), and widen the `newTokens` cast to include `chainId` (restore returns the full `Token`).

### P6 — unit fixtures diverge from the real service/codec shapes · medium (folded in)
`useFullBackupImport.test.ts` builds OLD-shape network rows the real `NetworkService.restore` rejects with `BACKUP_TOO_OLD` (`network/service.ts:635`, needs `endpoints[]`), and schema-incomplete account/contact rows. Mocked happy paths are unreachable in prod; some assertions bless output the #220 read-codec would hide. Fixtures should be schema-sourced (`Schema.parse`).

### P7 — unawaited `completeImport`; client leaks on throw · low (folded in)
`useFullBackupImport.ts:503` never awaits `completeImport` (typed `Promise<void> | void`, `:40`): a rejected SW handshake hangs the "Finishing import…" spinner; a sync throw clobbers a success into "failed". And `tokenService.disconnect()` (`:443`) + the loop's `client.disconnect()` (`:481`) run only on the success path — a mid-loop throw leaks up to 7 connected clients (`accountService` alone has a `finally`).

## Architecture — chosen approach + the competing outline

**Chosen (root-cause, minimal, audit-corrected):**
- **P1 (two parts):** (a) REMOVE `TransactionService`'s chain-purge subscriber + dead `clearChainState`; tx cleanup flows through the existing account-scoped `onAccountDeleted`. (b) ADD a tx-restore provenance filter: `restore` accepts only txs whose `account` ∈ the SUCCESSFULLY-imported account set (`newAccounts.filter(a => !a.restoreError)`; drop-and-record foreign/unknown/failed-account txs). This closes both the cross-profile over-wipe (part a) and the foreign-account tx injection codex found (part b), and makes the "orphan tx" residue genuinely inert (only legitimately-imported-then-deleted accounts' txs remain, cleaned by `onAccountDeleted`).
- **P2:** pair networks by restore-result INDEX (`newNetworks[i]` ↔ `data.network[i]`), abandoning the forgeable field-match; `remapIdInBackupData(data, idKey, oldId, newId)` rewrites only `row[idKey] === oldId` for **`networkId`**. Keep the **`profileId`** call site ALL-ROWS (one profile per backup; all-rows normalizes any hostile row whose `profileId` ≠ the real one — a guard fable flagged we must not drop) via an optional-`oldId` form or a separate all-rows helper.
- **P3:** composite `(chainId, contract)` key sourced from the old token (balances lack `chainId`); widen the cast; skip-and-record on a duplicate old `(chainId, contract)` (no last-wins).
- **P6:** schema-sourced fixtures.
- **P7:** `await completeImport` in an isolated try/catch that cannot reach rollback; per-client try/finally disconnect.

**Competing outline (v1, rejected by the audit):** add `profileId` to tx rows + `TxSchema`, thread it from the owning account through every executor, filter `clearChainState` by `(profileId, chainId)`. **Rejected:** (a) codex HIGH — `restore` would then write an attacker-supplied `tx.profileId`, a new trust hole requiring provenance re-derivation from restored accounts; (b) it's a storage-shape change (invisible dev rows via the #220 codec) for NO benefit over removing the redundant subscriber; (c) the v1 rationale ("`onAccountDeleted` doesn't cover network-delete") was factually FALSE. The remove-subscriber fix is strictly simpler and safer. P2/P3/P6/P7 approaches are unchanged between outlines.

## Security & Adversarial Considerations
- **Threat model:** the backup blob is attacker-controlled (checksum = integrity detection, not authentication). Real crafted-backup cases (post backup-normalization, which already rejects duplicate root-row ids): a foreign-account tx (P1); a live-storage network-id collision + an ambiguous failed-A/valid-B same-`name+chainId` pair (P2); same-contract cross-chain tokens + duplicate `(chainId,contract)` (P3).
- **P1 removes trust surface, not adds it:** deleting the subscriber means restore/deletion no longer relies on any tx-carried scoping field — cleanup is driven by the authoritative account rows (`onAccountDeleted`). No attacker-controlled provenance (this is why v2 beats v1's `profileId`-field approach, which codex flagged as a new trust hole in `restore`).
- **P2 keeps the `profileId` all-rows normalization** (fable S2): a hostile row whose `profileId` ≠ the backup's real profile is still overwritten to the new profile id, so it can't smuggle a foreign owner. Only `networkId` (legitimately multi-valued) is scoped to old→new pairs — with presence + uniqueness guards (skip-and-record on a missing/ambiguous old id, never guess).
- **Foreign-account tx injection is CLOSED by the P1(b) provenance filter:** restore drops-and-records any tx whose `account` ∉ the SUCCESSFULLY-imported accounts (`newAccounts.filter(a => !a.restoreError).map(a => a.address)`), so a crafted backup can no longer plant a tx in another profile's activity. `hash` remains backup-supplied but is only a storage key (a collision fails the restore of that one row); reads are by `account`, which is now provenance-checked.
- **No new deps, no crypto, no network/privilege/workflow surface.**

## Assumptions
**Facts (verified this session, file:line):**
- `TransactionService` registers a chain-purge subscriber (`transaction/service.ts:60`) whose `clearChainState` filters by chainId alone (`:79`); it is the ONLY caller of that method (safe to remove both). `onAccountDeleted` is account-scoped (`:170`).
- `AccountService` registers a chain-purge subscriber (`account/service.ts:48`); its `clearChainState(profileId, chainId)` deletes those accounts + emits `onAccountDeleted` per account (`:56-64`). So both `purgeChain` triggers cascade account deletion → tx cleanup.
- `purgeChain` fires subscribers on `onProfileDeleted` (`network/service.ts:684`) and `deleteNetwork` (`:301`).
- `TransactionService.restore` writes each tx verbatim, keyed by `hash` (`transaction/service.ts:315`), no account-membership check — reads are by `account` address (`:92`); active-account activity shows txs by account (`app.store.ts:153`). So a foreign-account tx surfaces in the victim profile → the provenance filter is required (not optional).
- `NetworkService.restore` returns one `Restored<Network>` per input, in order, spreading a failed input's raw fields back (`network/service.ts:627-666`) → index-pairing is valid; field-match is forgeable. `AccountStateService.restore` trusts `item.networkId` for the PXE target (`account-state/service.ts:215`).
- Backup normalization rejects duplicate root-row ids pre-restore (`backup-migration-registry.ts:170`) → the P2 "duplicate in-backup ids" trigger is stale; real triggers are live-collision + ambiguous same-`name+chainId`.
- `deleteProfile` emits `onProfileDeleted` WITHOUT awaiting listeners (`profile/service.ts:568`; `EventHandler.invoke` doesn't await async listeners) → `deleteProfile` returning does NOT prove tx cleanup finished. Pre-existing (P4 territory); the plan must not rely on deletion-completion ordering. The tx-restore provenance filter (not deletion timing) is what makes P1 correct.
- `remapIdInBackupData` rewrites every `idKey`-bearing row, ignoring the old value (`full-backup-helpers.ts:94-106`); called for `profileId` (`useFullBackupImport.ts:378`) and `networkId` (`:406`); the network old→new match uses name+rpcUrl+chainId (`:402`). Also called from `full-backup-helpers.test.ts` (signature update needed).
- token-balance remap keys by contract only (`useFullBackupImport.ts:453`); token-balance rows carry no `chainId` (`token-balance/spec.ts`); `Token` carries `chainId`.
- `NetworkService.restore` rejects non-`endpoints[]` rows with `BACKUP_TOO_OLD` (`network/service.ts:635`); #220 row codecs validate-on-read, keep-on-fail → invisible (`packages/wallet-core/src/storage/entity_storage.ts:61-82`, re-exported by `apps/extension/src/wallet/storage/index.ts`).
- `completeImport` unawaited (`useFullBackupImport.ts:503`), typed `Promise<void>|void` (`:40`); `accountService` has a `finally` (`:439`), `tokenService`/loop clients do not.

**Inferences (attack these):**
- Removing the tx chain-purge subscriber leaves NO cross-profile-relevant gap: every tx has an `account`; both purge triggers delete the owning accounts → `onAccountDeleted` cleans the txs. With the P1(b) provenance filter, every restored tx's `account` is a legitimately-imported account, so the only txs ever left un-purged are those whose (real) account is later deleted — cleaned by `onAccountDeleted` at that point. (Attack: is there a purge path that removes tx-relevant state WITHOUT deleting the accounts / firing `onAccountDeleted`? e.g. subscriber ordering, an async cascade `purgeChain` doesn't await.)
- Index-pairing (`newNetworks[i]` ↔ `data.network[i]`) is unforgeable because `NetworkService.restore` returns exactly one result per input in order; the remap runs only when `newNetworks[i]` is a SUCCESSFUL restore (`!restoreError`). (Attack: any path where restore reorders or drops-vs-returns inputs so indices desync?)
- Only two source call sites of `remapIdInBackupData` (+ its tests).

**Asks:** none outstanding — the P1 mechanism (remove subscriber, per both auditors' Ask) and scope were decided this session. The orphan-tx lazy-sweep is explicitly deferred.
