Backup-restore data-corruption fixes

The last audit of the just-merged backup-import feature found that the restore path (and the profile-deletion it triggers on rollback) can silently corrupt data. This plan fixes the three serious corruption bugs plus two cheap robustness fixes, as one PR — the last thing standing between us and "the migration arc is closed."

Why this tier was chosen

mid. Rubric: 1 dimension is HIGH (security sensitivity — the restore path handles attacker-controlled backup files). The rest are low: it's contained to the backup/transaction services, reversible, no migration (pre-production), no external coupling, no novel surface. One-high → mid. The dual audit made it meatier but not broader.

The bugs (all found by the scoped bug hunt, all verified)

P1 (high) — deleting one profile wipes another's transaction history. When a restore fails and rolls back (the most common case: accidentally re-importing your own backup), the cleanup deletes every profile's transactions on that blockchain, not just the one being removed — because transaction records don't record which profile they belong to.
P2 (high) — importing multiple networks grafts data onto the wrong one. A bookkeeping step that renumbers network references rewrites all of them to a single new id instead of matching old→new one-to-one.
P3 (high) — same token on two chains collapses balances. If you hold the same token contract on two networks, restore mixes up which balance belongs where.

Plus P6 (test fixtures don't match the real data shapes, so some tests pass on data production would reject) and P7 (a hung "finishing…" spinner + leaked connections on error) — both cheap, folded in.

What the audit changed (the interesting part)

My first draft fixed P1 by adding a "which profile" tag to every transaction. Both independent auditors (Codex and a fresh Opus review) found a better answer: the code already has a correct, profile-accurate cleanup path (when an account is deleted, its transactions go with it) — and that path already runs on every deletion. The buggy cleanup is simply a second, redundant path that over-reaches. So the fix is to delete the redundant buggy code, not add new code. Simpler, safer, and it removes a security hole the first draft would have introduced (trusting a "which profile" tag that comes from an attacker-controlled backup file).

Phases

Phase 1: P1 — remove the redundant cleanup

Delete the buggy chain-wide transaction purge; rely on the existing account-scoped cleanup that's already correct for both deletion triggers.

Proves itself by: a new test where deleting profile B leaves profile A's transactions intact — red before, green after — plus the existing transaction tests, typecheck, lint.

Phase 2: P2 + P3 — precise old→new matching

Renumber network references one-to-one (only the row that had the old id), and match token balances by (chain + contract) instead of contract alone. Also fix the old→new network match itself, which the audit found silently broken for the current network shape.

Proves itself by: multi-network and same-contract-two-chains tests asserting no cross-graft, plus typecheck + lint.

Phase 3: P6 + P7 — real-shaped fixtures + spinner/leak fixes

Rebuild test fixtures from the real data schemas; await the final handshake in its own error-safe block; always disconnect service clients.

Proves itself by: composable + component tests, typecheck, lint.

Phase 4: live-sandbox proof

A new network end-to-end test that reproduces the multi-profile / multi-network corruption on a real Aztec sandbox and proves it's fixed.

Proves itself by: bun run e2e:agent backup-restore-integrity green on a quiet machine + audit:vue exit 0 + the existing smoke suite still green.

Human context

"Pre-production" is load-bearing: there are no real users, so a data-shape change would need no migration. That's why the first-draft P1 (add a field) was even on the table — but the audit found removing code is strictly better here, so no shape change happens at all. The backup file is treated as hostile input throughout (its checksum proves it wasn't accidentally corrupted, not that it came from us).

Open questions

  • None blocking. One deliberate tradeoff: after Phase 1, a transaction whose account was already deleted won't be swept by a later network purge — but such a transaction is already an inert orphan, not corruption. A lazy sweep for those is a possible future follow-up, not this PR.
