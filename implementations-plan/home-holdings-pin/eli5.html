Home + Holdings Plan

Today the wallet's first tab lists every token alphabetically under the big balance. That works with two tokens and falls apart with twenty-five: the valuable ones sink below test tokens, the recent-transactions feed scrolls off the screen, and every "pick a token" list grows without limit. This plan gives the wallet a Home tab that shows at most three tokens, a Holdings tab that owns the full list with a search box, and a way to pin up to three tokens to Home from each token's own menu.

Written on your Mac, executed by a fresh session on the homelab. The plan file is self-contained: bootstrap steps, every decision, every test.

Mid. Nothing here is novel or irreversible, no data migrates, no third party is involved. The one thing with reach is the bottom navigation, which every end-to-end test walks through; the plan keeps the existing route and test hooks so that reach stays contained. Mid buys two independent plan audits (Codex and a second Claude) plus a final fresh-eyes Codex pass, which is what caught the four blocking issues below before anyone wrote code.

What the audits changed

  • Pins remember the token's contract address, not its internal number. Internal numbers get reused when a token is deleted and another is added, so a stale pin could have attached itself to the wrong token.
  • Every browser test that checks the popup must build it first. The smoke suite only checks that a build exists; without this step it would silently test old code.
  • The full network test suite runs one shard at a time from one checkout. Running shards in parallel from the same folder makes them kill each other's browser.
  • Token names and symbols come from contracts and are capped at 32 characters wherever the pin flow shows them, so a hostile token can't wreck the popup.
  • Two simplifications, both flagged for you below: the Send screen's token picker keeps its current rows and only gains the new order and a search box, and the "Home is full" message reuses the existing confirm popup in a one-button mode instead of a brand-new popup.

Phases

Three arcs, three stacked pull requests. A phase is "green" only when its listed proof passes.

Arc A · PR 1

Phase 1 — Four tabs and an empty Holdings page

Rename the first tab to HOME, add a HOLDINGS tab that opens an empty page. The web address of Home does not change, so nothing else in the app or the tests moves.

Proves itself by: lint + typecheck + unit tests, the built popup's navigation smoke test walking all four tabs, and a check that the new icons exist in the bundled font.
Arc A · PR 1

Phase 2 — Home shows three tokens, ordered by value

Home orders tokens by what they're worth (pinned ones first, once pins exist), shows three, and offers a "View all" link when more exist. The old, unreachable "choose what the big balance shows" popup is deleted; the big balance always shows your total.

Proves itself by: unit tests for the ordering rules (including empty and unpriced tokens), lint + typecheck, the full smoke suite on a fresh build, and four targeted network tests that click Home's token rows.
Arc B · PR 2

Phase 3 — The Holdings page

The full list: a total at the top, a search box that stays put while you scroll, a value/name sort, pinned tokens above a dashed line, and one fold that tucks away empty tokens and anything under your existing "hide dust" threshold. Nothing is ever hidden without a row saying how many are hidden.

Proves itself by: unit tests for search, fold and dust rules (including hostile numbers), component tests for the list, and a network test that opens Holdings with real balances, sees a priced token rank first, searches, and sorts.
Arc B · PR 2

Phase 4 — The Send screen's token picker

The picker uses the same order as Home and Holdings and gets a search box once you have more than three tokens. Picking a token works exactly as before.

Proves itself by: a component test for order and search, lint + typecheck, the smoke suite on a fresh build, and a new network test that actually picks a different token on the Send screen (none existed before).
Arc C · PR 3

Phase 5 — Remembering pins

A small, well-guarded piece of state: which tokens are pinned, per profile and per chain, at most three, cleaned up when a token is deleted, and validated on every read so a corrupted value can only ever reorder rows.

Proves itself by: unit tests for every rule: the cap, hostile stored values, deletion cleanup across profiles, concurrent pin clicks, and network switching.
Arc C · PR 3

Phase 6 — "Pin to Home" in the token menu

Each token's "⋯" menu gains "Pin to Home" or "Unpin from Home". When three are already pinned, a popup titled "Home is full" names them and asks you to unpin one first. Home, Holdings and the Send picker all honour the pins.

Proves itself by: component tests for the menu states and the popup, lint + typecheck, the smoke suite on a fresh build, and a network test that pins from a token page, sees it first on Home, reopens the popup, and unpins.
Arc C · PR 3

Phase 7 — The whole network suite

Every network test, run shard by shard in a terminal session that survives the agent process. Optional two-at-a-time mode only after the first shard shows memory headroom.

Proves itself by: all five shard logs ending in exit 0.

Human context

Why not a star on every row? It read as "everything is starred", and stars in wallets read as "verified". The action lives where every other per-token action already lives: the token's own menu. Rows carry no marks; position is the signal.

Why three? Home's balance, gas, buttons and three rows fit above the fold with the Recent transactions header still visible. A fourth row pushes it under.

Why contracts, not internal numbers, for pins? The wallet reuses internal token numbers after a deletion. A contract address is the token's real identity on a chain, and a re-added token keeping its pin is what you'd expect.

Why reuse the "hide dust" setting? One number for what counts as dust across the wallet. Its description widens to say it covers holdings too.

What is not in this plan: pasting an address into the search to add a token (agreed direction, next plan), manual ordering of pins, any marks or controls on rows, backing up pins, a horizontal token strip.

Open questions

Send picker rows

You chose "the Send picker reuses the same list component". Both audits argued that what you actually want is the same order plus a search box, and that reusing the full component drags per-row price lookups and a button variant into a popup for no visible gain. The plan delivers order + search with the picker's existing rows. Say the word if you want identical rows.

The "Home is full" popup

The mockup showed the three pinned symbols as chips. The plan reuses the existing confirm popup in a one-button mode with the symbols written inline in the sentence. Cheaper by a file, a registration line and a test suite. Flip to a dedicated popup if you want the chips.

Small defaults the plan chose for you

No fold inside the Send picker; picker search appears only past three tokens; the list forgets its search when you close it; pinned tokens without a price sort after pinned tokens with one; the dust fold works even when fiat display is off; pins are per chain, not per network endpoint.
