Nulo wallet · concurrency plan & status

Capture-Await-Write Sweep

The wallet's big August audit fixed 28 concurrency bugs, and most of them had the same three-beat shape. This sweep hunts that exact shape in all the code the audit never looked at — and either proves each spot safe or fixes it with the same battle-tested guard patterns the audit work established.

// the shape being hunted, everywhere:
const snap = readSharedState() // take a snapshot (profile, network, row…)
await something() // pause — deletions & switches can sneak in here
write(basedOn(snap)) // write using the now-possibly-stale snapshot

What the hunt found

~300spots examined, every one verdicted
13real gaps — all fixed & pinned
restproven safe, with written reasons

The headline pattern: the audit fenced every backup-restore writer in five services, but the create buttons right next to them (add a network, add a contact, add a token…) were left bare — delete your profile at just the wrong moment and a ghost row belonging to the deleted profile gets written anyway. Same guard, five more doors. The other fixes are of the same flavor: a newer code path missing the re-check its older sibling already has, a cleanup task that can delete a store a re-imported profile just started using, two settings writes that can silently undo each other, a stray approval popup that never closes.

Nothing found is a stolen-funds or leaked-secret bug. These are orphaned-data, wrong-moment-write, and stuck-UI bugs — the kind that turn into support mysteries later. Two known deep issues stay deliberately parked (they need a multi-PR redesign the earlier audit already scoped), so the final bill of health is qualified, exactly as it should be.

Why this size of ceremony

You fixed the tier as light, escalating if more than two real bugs turned up. Thirteen did, and several sit near sensitive machinery — so the escalation applied in full: an independent second reviewer went over the fixes on top of the eight-round external-model loop. That redundancy paid for itself concretely — the second reviewer caught a deadlock the loop itself had introduced and then signed off on twice.

Phases

1 · Enumerate DONE

Three passes: six readers covered all 122 hot files line by line; a second pass hunted the sneaky variants (callbacks that fire later, fire-and-forget writes); a third re-checked every file the first census had dismissed — and caught the census being wrong twice. Proves itself by: every file accounted for, in writing.

2 · Judge every spot DONE

Each spot got a verdict with a written reason; the risky calls were re-read in the actual code. The external attack pass on the frozen table upgraded three "safe" verdicts into fixes — its demands are all folded in.

3 · Fix the thirteen DONE

Every fix reuses an existing guard pattern from the codebase, and ships in the same commit with a test that fails if the guard is ever removed — each one verified by actually removing it once (all red→green runs logged).

4 · Full battery + review loops DONE

Full unit battery green (4,880+ tests), smoke e2e green, targeted network e2e green three times over (the dApp token-registration and network-deletion flows re-validated live after each redesign). The external-model review loop ran eight rounds — it rejected five times, every finding was verified in the real code before adoption, and its own round-2 demand turned out to plant the branch's worst bug. The independent second reviewer caught that one: a lock-ordering deadlock that would have frozen the token and network surfaces for five minutes on an unlucky add-token × delete-network overlap. Fixed by inverting the design (the purge sweep runs lock-free; every token writer self-compensates instead), plus two more of its findings: a stale approval popup could execute under a re-imported profile, and one error path reported success for a deleted profile. Both reviewers signed off on the final state.
