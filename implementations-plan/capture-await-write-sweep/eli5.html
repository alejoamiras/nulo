Nulo wallet · concurrency plan & status

Capture-Await-Write Sweep

The wallet's big August audit fixed 28 concurrency bugs, and most of them had the same three-beat shape. This sweep hunts that exact shape in all the code the audit never looked at — and either proves each spot safe or fixes it with the same battle-tested guard patterns the audit work established.

// the shape being hunted, everywhere:
const snap = readSharedState() // take a snapshot (profile, network, row…)
await something() // pause — deletions & switches can sneak in here
write(basedOn(snap)) // write using the now-possibly-stale snapshot

What the hunt found

~300spots examined, every one verdicted
10real gaps to fix
restproven safe, with written reasons

The headline pattern: the audit fenced every backup-restore writer in five services, but the create buttons right next to them (add a network, add a contact, add a token…) were left bare — delete your profile at just the wrong moment and a ghost row belonging to the deleted profile gets written anyway. Same guard, five more doors. The other fixes are of the same flavor: a newer code path missing the re-check its older sibling already has, a cleanup task that can delete a store a re-imported profile just started using, two settings writes that can silently undo each other, a stray approval popup that never closes.

Nothing found is a stolen-funds or leaked-secret bug. These are orphaned-data, wrong-moment-write, and stuck-UI bugs — the kind that turn into support mysteries later. Two known deep issues stay deliberately parked (they need a multi-PR redesign the earlier audit already scoped), so the final bill of health is qualified, exactly as it should be.

Why this size of ceremony

You fixed the tier as light, escalating if more than two real bugs turned up. Ten did, and several sit near sensitive machinery — so the escalation applies: an independent second reviewer goes over the fixes, on top of the usual external-model review loop that has already rejected and reshaped this plan twice (its demands are folded in).

Phases

1 · Enumerate DONE

Three passes: six readers covered all 122 hot files line by line; a second pass hunted the sneaky variants (callbacks that fire later, fire-and-forget writes); a third re-checked every file the first census had dismissed — and caught the census being wrong twice. Proves itself by: every file accounted for, in writing.

2 · Judge every spot DONE — under external attack now

Each spot got a verdict with a written reason; the risky calls were re-read in the actual code. The full table is frozen and an external model is currently trying to break the "safe" verdicts before any fix lands. Proves itself by: verdict-for-every-spot parity + the attack pass resolving.

3 · Fix the ten NEXT

Each fix reuses an existing guard pattern from the codebase (never a new invention), and ships in the same commit with a test that fails if the guard is ever removed — verified by actually removing it once.

4 · Full test battery + review loop + PR PENDING

The whole unit/build battery, the browser end-to-end suites where touched, an automated code review, the external-model review loop until it has nothing left to say, an independent second reviewer, then one PR to dev. Merge stays yours.

Decisions that are yours

  • Merge — the PR will be opened green and reviewed; landing it is your call, as always.
  • Accepted-risk list — a handful of spots are judged "safe because the harm is a self-healing cosmetic blip". Each is labeled owner-ack-pending in the table and listed in the PR body; veto any and it becomes a fix.
  • One scope addition — the message-transport package (between popup, background, and prover) was screened too, on the external reviewer's insistence. Findings there are notes, not code changes, unless you say otherwise.
  • Parked design work — the activity-counter locking gap and a few hygiene items need real design, not a quick guard; they're written up as owner notes, mirroring how the earlier audit parked its two deep issues.

This ran autonomously under your sweep brief; everything above is revisitable at PR review.
