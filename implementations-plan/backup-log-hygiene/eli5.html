What the wallet writes down about you

Every console.log in the extension is quietly collected, kept, and made exportable. This is what ends up in there, what I got wrong on the way, and the four calls that are yours to make.

2026-08-276 recon sweeps · 2 adversarial auditsscope: apps/extension

The short version

Nothing here is a broken lock. The wallet's secret-handling is genuinely well built — the master key, the recovery phrase and your password never reach a log, and one function goes out of its way to keep them separate.

What leaks is the other half of a privacy wallet's promise: your decrypted note contents, private contract reads, contact names, which sites you visited, your balances. Plus one narrow path where a mistimed export really can spill the recovery phrase.

The fix is five stacked PRs, merged all-or-nothing. But the biggest win is a single decision about whether logs should be kept at all — which is question 1 below.

How logging actually works here

This is the part that makes an ordinary console.warn matter. In this extension, console.* is not the browser's console — it's replaced at startup in all four contexts and redirected into a collector.

  G --> I["CSV export → disk"]

The catch is trim(). It's the one thing standing between a log line and storage, and it only knows five field names — all of them cryptographic proof internals. It has no idea what an address, a contact name, or a note's contents are. And it can only look inside objects.

structural

79% of log calls are invisible to it

Of 365 call sites, about 289 build a string first — `balance: ${amount}` — and a finished string is opaque. trim() sees one blob of text and passes it straight through. Three sites even call JSON.stringify before interpolating, which defeats redaction on purpose.

So "make trim() smarter", which was my first instinct, reaches at most 8% of the problem.

What's actually in there

Ranked by how much it matters, not by how alarming it sounds. One thing worth knowing first: the collector throws away anything below Info level unless Debug Mode is on — so a chunk of the noise never reaches a normal user's machine at all.

worst

Decrypted note contents and private contract reads

A failed render logs the whole note object — including content, the decrypted payload. Another site logs the raw result of a private contract call made under your own account scope. Both are Warn/Error level, so they're collected for everyone, not just developers.

notes/index.vue:79 console.warn(..., note) view-executor.ts:127 logError(..., result) batched-view-simulation.ts :380 :411 :424

For a wallet whose entire purpose is private notes, this is the thing worth fixing.

key material

A mistimed export response can log the recovery phrase

When a reply arrives for a request that already timed out or already landed, the transport logs the whole reply — including its result. exportMnemonic, exportPlain and exportBackupMaterial all return through that path, and service workers die constantly, so a raced reply is routine rather than exotic.

base-client.ts:196 logWarn("Invalid response received", content)
privacy

Contacts, browsing history, balances

Contact names and addresses on every edit. The URL of the page you were on, whenever a subframe misbehaves. Every dApp tab navigation. Your gas balances. Individually mundane; together, a decent picture of your activity.

remote

One path leaves your machine entirely

Internal error messages are handed verbatim to whatever dApp asked. Not stored, not exported — sent. I'd originally reported there was no network egress at all; I'd only checked for analytics SDKs.

error-envelope.ts:106 return error.message
holding up

The secrets themselves are fine

Two independent sweeps found no password, recovery phrase, or signing key passed to any log call. The export screens log only the error, never the payload. And ProfileService.restore deliberately takes its secret as a separate argument from the record it dumps on failure — someone thought about this. The plan doesn't touch it.

Three things I got wrong

Two reviewers went at this independently and both found real errors in my first draft. Worth reading, because it's the difference between the plan working and the plan breaking your wallet.

would have broken restore

My fix would have corrupted live RPC calls

I wanted to redact earlier, before data crosses between extension processes. But the line I picked isn't the logger's path — it's the path every call takes. Once redaction knew the word masterKey, it would have rewritten the real parameter of a real restore to the literal text "[masterKey]", and profile restore, unlock and export would have failed. The ordering I'd argued for is exactly what would have armed it.

overstated

"2,000 entries on disk" — wrong

chrome.storage.session lives in memory and is wiped on browser restart, extension update, and reload. It is not written to disk. Real: the data survives service-worker restarts within a browsing session, and the CSV export does write a real file.

contradicted myself

"No key material leaks" — retracted

True of hand-written call sites, false at the transport layer. I'd already flagged the transport path as high severity, then wrote a headline that contradicted it. That's the base-client.ts:196 finding above.

The plan

Five arcs as a stack, landing together. Order matters: the redaction rules can't exist before the redaction is correctly placed, or you get the restore bug above.

ARC 0

Stop keeping logs nobody asked for

Only save logs when Developer Mode is on. Kills most of the problem for normal users without editing a single log line. Your call — question 1.

ARC 1

Close the transport leaks

Stop logging whole request/reply envelopes. This is the only path where real key material appears, so it goes first.

ARC 2

Fix and actually test trim()

It has no tests today. It also destroys error messages, and expands raw key bytes into a 32-field object instead of hiding them.

ARC 3

Fix the sites that leak regardless

Notes, contract reads, contacts, browsing history, balances — plus the dApp-facing error path.

ARC 4

The backup-restore error log

Failed rows are kept whole and shown in a viewer with a copy button. RPC URLs live there, and those often carry an API key.

ARC 5

Keep it from coming back

A guard test, plus a lint nudge. Honestly labelled: the lint reaches 69 of 365 sites and knows nothing about content. The test is the real control.

Four decisions for you

1 · Should logs be kept at all for normal users?

Gating log storage behind Developer Mode is the single biggest risk reduction available, and it costs almost nothing to build.

The cost is real. Turning the flag on later isn't retroactive. Today, a user who hits a bug can enable Developer Mode and export logs covering what already happened. Under this change, that history is gone — you'd only capture from that moment forward.

2 · Fold in packages/aztec-runtime?

It defines the account-export envelope with a plaintext signing key, and fell outside the packages you scoped. I'd include it.

3 · The CSV export — keep, gate harder, or remove?

You've said you've never used it, and it's already developer-gated.

Removing it doesn't fully close the door: the log view is a text editor, so select-all-copy still works. Retiring a shipped feature is your decision, never mine.

4 · The copy button on the error viewer?

One click copies the entire restore-error log — every failed row, whole. Gate it, or leave it?
