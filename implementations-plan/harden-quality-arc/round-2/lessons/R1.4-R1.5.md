# Lessons — R1.4 + R1.5 (the Q-13 security completion)

R1.4a merged `5e61a3a` (#234); R1.5 in flight (#235). **Together these close all 3 cross-profile gaps — the isolation gate is now FULLY GREEN (11/11, zero `test.fails`).** This was the security heart of round-2.

## gap#2 — the deleteToken guard-split (the BLOCKER both audits flagged)
Naively adding an active-profile guard to `deleteToken(id)` would break the profile-delete cascade: `onProfileDeleted` deletes an explicit, possibly-INACTIVE profile's tokens, so `requireActiveProfile` would throw and orphan them (opus added: even the *active* profile is at risk — `deleteProfile` removes the repo row before emitting). The split:
- `deleteToken(id)` PUBLIC RPC = `ensureInitialized` + `requireActiveProfile` + `requireOwnedRow(get(id), profile.id, "unknown token id")` + delegate.
- `_deleteTokenById(id)` PRIVATE = the ORIGINAL locked body (no guard). The cascade calls THIS.
The ownership check sits OUTSIDE the lock (a token's profileId is stable, so no TOCTOU on ownership; a concurrent delete just yields "unknown token id"), and `_deleteTokenById` re-reads + deletes inside the lock — so the lock is NOT re-entered (non-reentrant `Lock`). **The R1.0 cascade-completion test (written 4 phases earlier) is what proved the split survives** — delete an inactive profile, assert all its tokens purged. Classic value of writing the safety-net test first.

## gap#2 × the balance projector (opus-MED-2)
Guarding `getTokenRaw` means it now throws for a foreign/stale token. `balance-projector.ts` has TWO call sites: `project():64` already had `.catch(()=>undefined)`; `projectChunk():111` did NOT. Added `.catch(()=>undefined)` there + widened the `tokenCache` type to `Token | undefined` — the two passes already `continue` on `!token`, so a stale/foreign balance is simply skipped. **When you close a fail-open getter, grep its internal callers for the ones without a catch.**

## leak#1 — the marquee real leak (R1.5)
`TokenBalanceService.backup()` fetched the active profile then returned `repo.getAll()` — the `profile` was dead; every profile's balances shipped in the PLAINTEXT export (`full.vue` writes `backup.data` in cleartext; encryption is optional). Fix: `new Set(getTokensRaw(profile.id).map(t=>t.id))` then filter. Two subtleties that both audits pinned:
- **Authoritative source:** use `tokenService.getTokensRaw(profile.id)`, NOT the in-memory `this.tokens` (cleared mid-profile-switch → would export nothing). `getTokensRaw` (plural, arg-scoped) is NOT the guarded singular `getTokenRaw` — no conflict with R1.4a.
- **Exact partition:** token ids are one global sequence, so `balance.token ∈ active-profile-token-ids` is exact for non-corrupt data (opus). Export-only — restore tolerance untouched (decision #4).

## gap#3 — revokeAuthwits (R1.5)
Fetched authwits by id checking only existence → a caller could revoke another account's authwits by supplying its ids. Fix: `if (!authwit || authwit.account !== account)` — a foreign id is treated as "doesn't exist" (no cross-account existence oracle). auth-registry test wiring needs stubs for `onAccountDeleted` (account) AND `onTransactionUpdated` (transaction — the pending-authwit reconcile); the runtime `.add` on an unstubbed event was the only snag.

## The through-line
Every fail-open→fail-closed change was owner-authorized, landed behind a flipped pin, and is proven by the standing isolation gate — which stayed green at every phase and is now fully green with all real assertions. The cascade was preserved throughout. R1.4b (token restore-dedup + account) is the remaining NON-security cleanup.
