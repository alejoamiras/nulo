## Decision ledger (2 independent planning legs — [codex](./plan-leg-codex.md) `etx4Ao0w` + [opus Plan](./plan-leg-opus.md) — + main verification)

Both legs converged independently on the core architecture; where they differed, the opus argument won on strength (noted). Main leg independently verified the token-guard gap, the 3 repository.ts, and contact's clean pattern against the code.

- **NO base class / NO mixin — composable free functions.** Adopted (both legs). The decisive reason (opus, verified): **token-balance and auth-registry have NO `profileId` field** (they're FK-scoped via token/account), so a `ProfileScopedRepository<T extends {profileId}>` class (codex's first proposal) literally cannot type them. A base class also (a) hides the privacy guard — violating the same principle `requireActiveProfile`'s own JSDoc codifies — and (b) an auto-injected `requireActiveProfile` would **reintroduce the wrong-profile-wipe bug** that `incoming-transfer/service.ts:221-224` explicitly documents (it uses a caller-passed profileId precisely to avoid wiping the wrong profile). So: three small helpers beside `purge-rows.ts`:
  - **`restore-rows.ts`** — `restoreRows<TIn, TOut extends object>(rows, writeOne)`: the per-row `try → writeOne → catch → {...row, restoreError: toRestoreError(err)}` skeleton ONLY. **ID allocation stays inside the caller's `writeOne`** (cursors diverge: token shared-cursor `id=max+1;id++`, token-balance per-row `allocateId()`, fpc/contact/network keep-id-else-random). **Explicitly NOT account** (its restore throws the whole batch on a duplicate-address precheck — a different contract; keep hand-rolled).
  - **`id-allocators.ts`** — `nextNumericId(storage)` (= `array_max(getKeys().map(Number))+1`) + `nextRandomId(storage, len=8)` (= `while(contains) getRandomHex(len)`). auth-registry's current `max(getValues().id)+1` is provably equal to `nextNumericId` iff key===`${id}` — **verify with a characterization test, do not assume.**
  - **`require-owned-row.ts`** — `requireOwnedRow<T extends {profileId:string}>(row: T | undefined, profileId: string, message="Invalid id"): T` — throws unless `row?.profileId === profileId`. **`profileId` is an explicit argument** so the active-vs-arg choice stays visible at each call site (fpc/contact/network pass `requireActiveProfile(...)`, account passes its method arg). Fail-closed by construction (`undefined?.profileId !== profileId` throws). NOT applied to token-balance/auth-registry (no profileId — they keep FK-scoping).

- **THE HARD-LIMIT ITEM — token by-id guard gap → SURFACE, do NOT self-resolve.** `token.getToken(id)` / `getTokenRaw(id)` / `deleteToken(id)` / `getTokenInterface(networkId, id)` take an id with **NO profile-ownership check** (verified `token/service.ts:117,125,281,296`); ids are sequential (`max+1`) → cross-profile-enumerable. Same for token-balance/auth-registry by-id getters. **Assessment (main): a defense-in-depth gap, NOT an active exploit** — dApps cannot reach these (only the scope-gated `isTokenRegistered` is dApp-facing, verified in `dispatcher.test.ts`); internal callers only ever hold their own profile's ids. **Q-13's behavior-preserving dedup MUST keep these methods id-only (extract only the guards that already exist).** CLOSING the gap (adding `requireOwnedRow` to a by-id method) is a **fail-open → fail-closed change = HARD LIMIT** → surfaced to the owner as a decision, implemented ONLY behind a new failing test as a tracked behavior change, never auto-applied. See "Owner decision" below.

- **Restore must NOT overwrite `profileId`.** `restoreRows` writes `row.profileId` exactly as sourced from the (orchestrator-remapped) backup; `remapIdInBackupData` in `useFullBackupImport.ts:297` owns id remapping. The restore ORDERING (token before token-balance FK remap) in `useFullBackupImport.ts` must not be reordered.

## The 3 killer divergences (why "just extract it" is wrong)
1. **No `profileId`:** token-balance + auth-registry (FK-scoped) — can't be `requireOwnedRow`-guarded; keep indirect scoping + add asserting comments.
2. **Active-profile-scoped (fpc/contact/network) vs caller-profile-scoped (account/incoming-transfer, profileId as arg).** Conflating them = the wrong-profile-wipe bug. `requireOwnedRow(row, profileId)`'s explicit arg preserves the distinction.
3. **Account's restore throws the whole batch** (duplicate-address precheck) vs every other service's per-row catch. Account stays out of `restoreRows`.

## Security / adversarial (the point of this refactor)
**Isolation invariant:** every read/mutate/delete of a profile-scoped row R confirms `R.profileId === caller's authorized profile` before returning/mutating; a missing row, mismatched/absent profileId, or unresolvable active profile MUST deny (throw/undefined) — never fall back to all-rows or the active-profile default. **Fail-closed default everywhere.**
**Standing gate — cross-profile isolation test (Phase 0, written BEFORE any refactor):** new `apps/extension/src/wallet/services/cross-profile-isolation.test.ts` (template = `network/service.test.ts:174`, seed `FakeBrowserApi` with p1/p2 rows in EVERY store). With active=p1 assert: (a) foreign-id `get*`/`delete*` deny + p2 row survives; (b) lists return p1-only; (c) deleting profile p1 leaves ALL p2 rows intact across token/fpc/account/contact/network/token-balance/auth-registry/incoming-transfer; (d) restoring a p1 backup doesn't mutate p2 + allocates fresh non-colliding ids. **This file stays green through every phase** — it is the real Q-13 gate (dedup is only maintainability; a cross-profile leak is a security defect).
