# Lessons — Q-14 (popup/window lifecycle dedup) · deep, broad UI

Landing in increments. **P16.1 ✓ merged `bc36d0b` (#213)** — narrow `usePopupEntity` + 2 popups. P16.2 (3 more fitting popups) + P16b (window shell) remain.

## The codex audit SHRANK the finding — and that was the point
The finding said "extract a shell for 29 popups + 3 windows." codex's deep-audit verdict: "one composable for 29 popups" is TOO BROAD — a narrow helper (show-watcher + Enter-listener + reset/error state) is sound; a **CRUD/service-lifecycle owner is not**. It enumerated ~22 popups with bespoke service lifecycles (balance waits, dual services, chunked revoke, import-promise rejection, trust-boundary focus) that would be DANGEROUS to force into one abstraction. Lesson: for a broad "dedup N call sites" finding, the audit's job is to find the ~7 that are GENUINELY identical vs the ~22 that merely rhyme. Shrinking the scope is a successful audit, not a failure.

## `usePopupEntity` = narrow helper, NOT a lifecycle owner
It unifies ONLY the mechanical duplication: the `watch(show)` + document Enter listener + `onShow`/`onHide` hooks. It owns NO service client — the parent keeps `.connect()/.disconnect()` (the C1 rule). The value is killing the copy-pasted keydown/reset glue, not centralizing service lifecycles (which are legitimately per-popup).

## Per-popup verification catches the behavior-CHANGE traps
Migrating the "fitting" set, I read each popup's exact block. `NewEndpointPopup`'s `onKeydown` is `if (e.key === "Enter") handleCreate()` — NO input-focus guard, so Enter fires GLOBALLY. `usePopupEntity` has the input-only guard (matching the other 6). Migrating `NewEndpointPopup` would have SILENTLY ADDED the guard = a behavior change. So it's a resister — LEAVE it. Lesson: "looks like the same pattern" isn't enough for a behavior-preserving dedup; diff the exact guard/order of EACH call site before folding it in.

## Generated auto-import files: restore, don't commit (repo convention)
Adding an auto-imported composable regenerates `apps/extension/src/types/{auto-imports.d.ts,.eslintrc-auto-import.json}` on `vite build`. Per CLAUDE.md these are "dirtied by builds → git checkout to restore" + the CI build regenerates them. So: `git checkout` them, commit only the source; `typecheck:all` still passes without the entry (the `.js` SFCs aren't type-checked; the build resolves the auto-import at build time). Verified the production build resolves it BEFORE restoring.

## Merge-divergence recovery (local docs commit + squash)
I committed the re-scope docs on local dev-quality, then branched the code off it and opened the PR. On squash-merge, remote dev-quality got ONE commit (docs+code squashed); local dev-quality still had the un-squashed docs commit → `pull --ff-only` ABORTED (diverged). Recovery: `fetch`, VERIFY the remote squash contains both the docs and the code (`git show FETCH_HEAD:<file>`), then `git reset --hard FETCH_HEAD` — safe because local was a strict subset. Lesson: don't leave un-pushed docs commits on the integration branch as a PR base; if you do, verify-then-reset, never force the ff.
