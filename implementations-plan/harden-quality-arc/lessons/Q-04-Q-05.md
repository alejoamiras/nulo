## Resolve a permission-semantics conflict against the arc's OWN scope rule, not by fiat
codex's blueprint audit surfaced two real coverage drifts (`contractClasses` field-widening, `data.addressBook`) where the approved meta-plan said "fix (fail-CLOSED)" but codex said "preserve + surface." I first surfaced it as an owner decision (correct — it's a dApp-permission-semantics hard limit). Then the deciding evidence: both drifts are an **already-filed, named follow-up finding (`wallet-sdk-capability-field-diff`)** referenced in `dispatcher.ts` comments + `wallet-sdk-implicit-account-grant/plan-v3.md` — and it is **NOT one of the 22 quality-arc findings**. So fixing them in P15 = *scope beyond the 22 findings* = a HARD LIMIT. That makes **preserve** scope-*required*, not a judgment call. Lesson: when a surfaced permission decision has a scope dimension, check whether the "fix" belongs to a different tracked finding — the arc's scope boundary often resolves it without an owner round-trip. Preserve the drift, PIN it (`(DRIFT PIN)` characterization tests), let the refactor prove it didn't move.

## Parse-once can't naively narrow to `Capability[]` — unknown-type caps must survive
The finding says "parse once to `Capability[]`." But codex flagged (and the code confirms): unknown-*type* wire capabilities must reach the popup and render **default-off** (`popup/windows/capabilities/build-items.ts`). A bare `as Capability[]` would drop them (behavior drift, hides the warning path) OR coercing malformed known caps (defaulting a missing `scope`/list to `"*"`) is a fail-OPEN. So "parse-once" = a **known/unknown split**: known types are trusted as their variant (one boundary cast), unknown types keep the type-only default. Never filter or coerce at a capability trust boundary.

## The exhaustive discriminated switch is the cast-killer + the fail-safe
`isCapabilityCovered(cap: Capability, …)` switching on `cap.type` narrows each branch to the variant WITHOUT per-branch casts (the discriminated union does it). Making it **exhaustive over `Capability["type"]`** (all variants as `case`s, no `default`) means a NEW capability variant is a COMPILE ERROR until it's classified — so a future type can't silently default to covered (fail-open) or not (spurious re-prompt). Pair with a typed `grantsOfType<K>` accessor (one internal cast) so the existing-grants side is cast-free too. Net: ~10 scattered `as unknown as XCapability` casts → 2 well-placed ones, behavior byte-identical.

## Don't unify authz mirror pairs that aren't mechanically equal
The finding wanted one table for parse/covers/delta/**merge/enrich/check**. codex enumerated the dispatcher-coverage ↔ scope-checker (`method-scope-checkers.ts`) mirror pairs and found several are NOT mechanical: `createAuthWit` is an `accounts` method that also consumes `simulation.transactions` + `transaction` grants (cross-type coupling); `simulation`/`transaction` have wrapper coupling. **Merging two authz implementations is where a fail-open hides.** I did the SAFE slice (coverage/delta — the `covers` path) and deliberately left the enforcement (`check`) path in `method-scope-checkers.ts` untouched. Ship the contained, provable win; don't force the risky unification the finding's wording implies.
