Making the bridge tell the truth (and offer a way back)

bridge-journal-ux — plain-language companion to plan.md

During live testing, a bridge attempt died while Ethereum was confirming a boring permission step (the "approve"). The card then claimed "the deposit never confirmed" — scary and wrong: no money had moved at all. There was also no button to pick up where it left off. The machinery underneath is already safe (money is never lost); this project makes what the user sees match that safety, and adds a real RESUME button.

Why this size of plan (tier: mid)

It redesigns a user-facing flow (auto-trigger for planning), spans two packages, and RESUME feeds locally-stored data into real on-chain transactions — that's the one high-risk dimension (security). One high → mid tier: one plan, a competing alternative, two independent audits, one final fresh review. The audits mattered: they overturned two of the original design's assumptions (see "What the audits changed").

The phases

J1
Make the record REMEMBER how it died: which step, whether money moved, when — plus the approval transaction id. Today that knowledge evaporates on reload.
unit tests for every (step × outcome) combination + typecheck/lint/build.
J2
Build the safety net BEFORE any button exists: a strict validator that rejects tampered records, a "you must be the same account this was meant for" guard, browser-wide locking, and — the load-bearing piece — a one-shot resume ticket: each record gets exactly one resume attempt, and if that attempt ends ambiguously the record locks itself into review-only forever (double deposits are unrecoverable, so ambiguity must end resumability).
a tamper-fuzz table, a two-tab race, and crash-between-prompt-and-record fault injection.
J3
The card tells the truth: which step failed, "no funds moved" only when proven, honest hedging when the outcome is unknowable — plus a paste-the-transaction-id box for that unknowable case (the engine verifies the pasted id against the chain before trusting it). The right button per situation: RESUME / CLAIM / redo — and redo only ever appears when it's PROVEN nothing was spent.
a component test per card state + the full faucet suite.
J4
RESUME for the simple cases: gas top-ups (public and private) and plain token bridges. One click re-enters the flow on the same record — skipping the steps that already finished — and shows you amount + recipient before any wallet prompt.
per-variant flow tests: happy path, tampered-record rejection, race abort, skip logic.
J5
RESUME for the hard case (token bridge with gas top-up attached): reuses the exact one-time signature slot so the old signed permission can never execute twice. The private variant of this one case stays "redo-only" for now — its sealed backup doesn't yet cover the gas fields (follow-up filed).
signature-slot reuse tests (no double authorization) + the full suite.
J6
You test it on the live rig with a MANDATORY checklist: the old broken record narrates honestly; a forced failure RESUMEs to completion; a two-tab race (the second tab must refuse); a kill-right-after-wallet-confirm (the card must go review-only, and pasting the tx id must recover it); and the fueled-public resume including its signature edge cases.
your explicit go on the full checklist — then it merges, and the release (R) unblocks.

What the audits changed

  • overturned "Just sign a fresh permission on resume" — unsafe: the old signed permission could still execute later → two deposits. The plan now reuses the same one-time slot.
  • overturned "No recorded deposit = no money moved" — there's a crash window where the deposit WAS broadcast but never recorded. That case gets honest hedging and no RESUME.
  • added Browser-wide locking (a per-tab lock wasn't enough), a one-shot resume ticket per record (final review: no lock is atomic with a wallet broadcast, so ambiguity must permanently end resumability), and a paste-the-id recovery for the unknowable case.
  • narrowed "The record's id is a cryptographic self-check" was an overclaim (final review): it binds the secret, not the recipient/amount. Real intent safety = same-account guard + an explicit review screen before any signature.
  • deferred Private fueled-token resume (seal gap) — redo-only until its backup format is upgraded.

Human context

  • The journal lives in the browser's local storage — treated as hostile input everywhere it feeds a transaction.
  • "Approve" only grants permission; it can never move funds. That's why an approve-stage death is provably harmless — and why the card saying "deposit failed" was so misleading.
  • This work blocks the public release (your decision): the release ships with honest narration.

Open questions

None — the three the audits raised (unknown-outcome policy, who may resume, which variants) were decided and are recorded in the plan's decision ledger.
