ExecutionService PXE-injection spike

We can't cheaply test most of the wallet because the logic only runs once the real Aztec engine (the PXE) and the background worker are up — which means slow, flaky network tests. This spike proves a cheaper way: let one service (ExecutionService) accept a fake PXE, then write one fast test that runs the real wallet logic against that fake — no Aztec, no browser, no proving. If it feels good, it becomes the first step of doing the same for every service. If it's awkward, we found out in half a day.

Why this tier was chosen

Light. Rubric: 0 of 6 risk dimensions are high — the pattern already exists in the repo (two services already test this way), the change is behavior-preserving (production keeps the real PXE via a default), it's a single package, trivially reversible (one defaulted constructor argument), and there's no migration, security, or external-coupling surface. Bounded + low-risk = light.

Phases

Phase 1: Make the PXE swappable

Today ExecutionService builds its own connection to the PXE, hard-wired. We change it to accept one (the PXE client, since the service uses more than just the prove/simulate slice), defaulting to the real thing — so production behaves exactly as before, but a test can hand it a fake.

Proves itself by: lint + typecheck pass, the existing ExecutionService tests still pass, AND a new test confirms that with no fake supplied it still uses the real client (the old tests skip construction, so they wouldn't catch a broken default).

Phase 2: Build the fake + the test rig

A deliberately dumb stand-in for the PXE client that returns canned, correctly-shaped answers — it does NOT pretend to do real Aztec cryptography. Plus a small harness that snaps the real wallet pieces together around it (using fakes that already exist for the node and storage).

Proves itself by: typecheck passes (the fake satisfies the real client surface), the rig boots without error, and — stronger than a convention — a production build + grep confirms the fake is nowhere in the shipped bundle.

Phase 3: The one real test (cancel-mid-prove)

Through the wallet's real executeTransfer + cancelJob API (not a shortcut into the internals): start a transfer, pause it at the "proving" moment, cancel it, and check the wallet does the right thing — records the right states, drops the half-made proof, never sends, and reports a clean cancellation. Today this is only checkable by booting the whole Aztec sandbox.

Proves itself by: the new test passes in plain vitest (no sandbox), the existing tests still pass, lint + typecheck green.

Human context

The wallet is layered, and the boundary to the Aztec engine is an interface called IPXE. Faking at that one boundary lets all the wallet logic above it run in a plain test. The reason we can't already do this is small but real: the services build their PXE connection themselves instead of being handed one — so there's nowhere to slip a fake in. This spike fixes that for exactly one service, as a proof.

The big prize isn't this spike — it's that the same move unlocks the ~65% of "did we break the wallet?" surface that today only the slow sandbox tests can check, AND it fixes the over-mocked unit tests (same root cause). But we prove the shape on one service first.

Open questions — resolved by the codex audit (conditional approve)

  • Resolved: the execution path DOES use methods beyond IPXE (it calls the concrete client's getContractInstance/registerContract/registerSender…), so we inject at the client level and the fake covers both — not raw IPXE.
  • Resolved: the test is driven through the real executeTransfer + cancelJob public API (not the coordinator directly), so it can't pass trivially against the fake.
  • Resolved: the fake is kept out of the production build by a bundle-grep (not just convention), and a new test pins that production still uses the real client.
  • Out of scope here, flagged for the rollout: keeping the fake honest vs the real PXE (a few real-stack "contract canaries").
