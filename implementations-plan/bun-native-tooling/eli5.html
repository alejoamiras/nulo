Blueprint · light · Arc D of the Bun 1.4 adoption

Argv-Only Deploy Scripts

The bridge's deploy, verify and canary scripts (the ones an operator runs against Sepolia and mainnet) start other programs — forge, cast, git, bun — in eighteen hand-written places across six files. Three of those places build a shell command line by pasting text into a string; one hardcodes where cast lives; two copies of the same "find forge" helper drifted apart; and a failure can print the deployer's private key, because Node's error carries every argument that was passed. This plan replaces all eighteen with one small, tested primitive that only ever passes a list of arguments (never a shell string), never repeats those arguments in a failure, and finds the tools by one rule. The scripts keep doing exactly what they do today.

What the dossier expected, and why the plan says no

The Bun 1.4 dossier pencilled this arc in as "move these scripts to Bun's own process APIs (Bun.$, Bun.spawn)". Looking at the code changed that: the dangerous places are the shell strings, and the fix for those is a list of arguments — which Node's own API already does, and which these scripts already use for forge and cast. Bun's shell adds a different caveat (a value can still be read as a flag by the program it reaches), Bun's spawn has no "throw when it fails", and Bun's type definitions are not installed in this repo. Two independent codex reviews ruled the same way: harden on Node's API, no new dependency, no lockfile change, no waiting on Arc C.

Why this tier was chosen

light. Rubric: novelty low, blast radius low-to-medium (these scripts move real value when an operator runs them, but they never run in CI and the change is one revertable pull request), irreversibility low, migration cost low, external coupling medium (the Foundry and Aztec toolchains), security medium (a shell-string injection surface and a key in the arguments). Single package, one medium-high dimension → light, with the owner's standing rule that codex must converge before anything is built.

What we already know (measured, not assumed)

  • Eighteen call sites, six files, zero tests, zero CI workflows: the scripts are the aztec-update operator runbook.
  • Three shell strings paste unvalidated input into git commands; cast is pinned to an Aztec 5.0.0 folder even when a newer toolchain is installed; the private key is passed to cast as an argument and would appear in Node's error if that call failed.
  • Both live manifests carry the modern portal marker; the scripts' legacy branch is unreachable for them — but it stays (an operator can still point --config at an old manifest; removing it would be a feature removal, which is yours to decide).
  • On the planning machine forge is installed, so verify-l1 --dry-run runs without any key: it printed four "builds" lines before the change, and must print the same four after.
  • Bun's --no-orphans flag (kill everything a process started when it dies) is documented as a descendant walk, not a process-group kill — but nothing here starts long-lived children, so it stays off; the safe experiment that would clear it is written down for a later arc.

Phases

Phase 0 — The primitive and its tests

One new file, run.ts: run(program, [args]) runs a program with a list of arguments, returns its output, and throws a clear error on failure — exit code, signal, or "not found" — with the last 4,000 characters of the program's error output and never the arguments. resolveBin finds a tool by one rule (an environment override, then either the PATH or a list of known folders, in a stated order). git(...) is the eight-times-used shortcut. The tests start real child processes on both engines: success, failure, a missing program, a killed process, too much output, and two "secret in the arguments" checks that inspect every way an error can be printed.

Proves itself by: typecheck, the package's tests on Node (the current runner) and the new test on Bun explicitly, lint — all green; the dry-run baseline recorded.

Phase 1 — Six files, six commits

Each file is moved to the primitive in its own commit so any one can be reverted alone. Behaviour is preserved on purpose: the deploy scripts still only warn when source verification fails, the verifier still treats "already verified" as success, output that streams to the operator still streams. Three deliberate improvements: git commands take validated values with the separators that stop a value from being read as an option; cast is found by the same rule as forge (override → the current Aztec toolchain → the old 5.0.0 folder → PATH); failures never carry the arguments. Values that reach forge and cast are checked for shape first (addresses, contract names, chain id, the key).

Proves itself by: typecheck + tests + lint after every file; a search proving no direct process call is left outside run.ts; an 18-row audit (old call → new call, exit path, soft-fail kept?, validation added?); the dry-run printing the same four lines as before.

Phase 2 — Documentation

The bridge-core README states the rule ("spawn only through run.ts"), .env.example gains CAST_BIN, and the Bun dossier is corrected (its Bun-native premise, two wrong claims about Bun's APIs, and the --no-orphans semantics).

Proves itself by: lint + the whole-repo tests green; the last diff being documentation only.

Human context

Shell string vs argument list. A shell string is one line of text the shell has to re-parse — a value containing ; or $(...) becomes a command. An argument list hands each value to the program untouched. That closes command injection. It does not stop a value from being read as one of the program's own flags — which is why git gets explicit separators and why addresses and names are shape-checked before they reach forge or cast.

Why the tests start real processes. The primitive IS the risky part. A fake would test the fake. The tests run the engine that runs them as the child, so the same cases run under Node today and under Bun once Arc C lands.

What cannot be proven here. The live conductors need keys and a network; their proof is the next real aztec-update run. What can be proven is proven: the primitive, the static audit, and the key-free dry-run.
