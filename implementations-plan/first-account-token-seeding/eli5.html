Blueprint · light · plan for approval

The Missing Trigger

Your wallet's default tokens never show up for a brand-new account. Nothing is broken in the seeding logic itself — it simply runs at three moments, and the account it needs doesn't exist at any of them.

What's actually happening

The wallet ships with a short list of tokens it adds for you automatically, so a fresh wallet isn't empty. A background component watches for two moments to do that work: when a profile becomes active, and when the active network changes.

The problem is ordering. On a brand-new profile, both of those moments happen before your first account exists. The account is created a step later, by the popup — and nothing tells the seeder to look again.

01

Your profile is created and unlocked

The seeder wakes up, looks for the active network, and finds none — networks haven't been set up yet. It goes back to sleep.

02

The popup sets up networks and picks the active one

The seeder wakes up again. This time the network is there — but it asks "which accounts exist on this chain?" and the answer is none. It skips every token on the list.

03

Your first account is created

This is the moment the seeder was waiting for. But nobody is listening to it — there is no subscription to this event at all.

No listener · tokens never appear

This isn't a race that sometimes goes the wrong way. The popup deliberately sets up networks before accounts, so step 2 always comes before step 3. It fails the same way every time.

Why adding a second account seems to fix it

It doesn't, quite. Adding an account doesn't trigger seeding either, and switching between accounts is purely a screen change.

What actually happens is that some later time you open the popup, it re-picks the active network — which wakes the seeder, and by then an account exists, so the tokens finally get added. Your account switch is what makes the assets list re-read from storage and show them. Two separate things that happened to line up.

The fix

One line: also listen for "an account was created". The seeder already knows how to check whether it's still looking at the right profile and network, and how to avoid running twice at once — so it needs no new safety logic, just the third invitation.

Almost all the work in this plan is proving it, and making sure the fix doesn't quietly change how the existing test suites behave.

The awkward part. There's no honest way to test this end-to-end today. The automated test wallet runs against a throwaway local blockchain, and the real default-token list has no entry for it — by design. So the plan adds a strictly test-only way to inject one token into that list, wrapped in four separate guards to make certain it can never reach a real release build.

Why this tier

Scored as a light plan: no new territory, no data migration, no irreversible step, and the production change is a single line. The one dimension that isn't low is security — the default-token list is a trust boundary, since anything on it gets added to your wallet without asking you first. That's why the test-only injection got the heaviest scrutiny in review, and why the code review after implementation was raised a level.

The four steps

Step 1 · the actual fix

Listen for the account

Add the missing subscription, and pin it with tests that drive the real service wiring rather than a stand-in.

Proves itself by: lint, typecheck, and the token service's unit and composition tests all green.

Step 2 · test-only plumbing

A way to observe seeding on a throwaway chain

Build the injection path, behind two separate switches that must both be on. Add automated checks that a real production build contains no trace of it — and that a test build genuinely does, so the check isn't silently testing nothing.

Proves itself by: the usual checks, plus a real production build searched for the test markers and confirmed clean.

Step 3 · the regression test

Watch a token appear on its own

A browser test creates a fresh profile, switches to the local chain — which has no accounts, so it makes one — and then waits for the token to show up in the assets list without anyone importing it.

Proves itself by: the new test passing — and failing when the one-line fix is temporarily removed. A test that passes either way proves nothing.

Step 4 · make sure nothing else moved

Full sweep and docs

Run every suite end to end. The new trigger fires in every test that creates a profile, so the assumption that nothing else notices has to be demonstrated, not assumed.

Proves itself by: the full quality gate, the smoke suite, and the entire browser suite all green.

Deliberately not doing

  • Touching the assets screen. It already updates live through a different signal. A second path there would risk showing tokens twice.
  • Fixing the retry-budget hazard. The seeder spends one of three retries before the slow part, so a background process shut down mid-work burns a retry for nothing — and three of those permanently give up until the next release. It's real, but the current behaviour deliberately prevents an infinite crash-retry loop, and undoing that safely needs its own design. Recorded, deferred.
  • A missing-balance repair on restart. A pre-existing gap found during review, unrelated to this bug. Written down as a separate follow-up.

Where review landed

Codex reviewed the plan at maximum reasoning and returned a conditional approval with five conditions — all adopted. The two that changed the plan most:

  • It caught that the smoke test suite also boots the wallet pointed at the public test network. Once the fix lands, every fresh test profile would quietly make a live call to an outside service — turning a required check into something that depends on a server we don't own. Now handled.
  • It found one of my stated facts was simply wrong — I'd claimed restoring a backup emits the account event. It doesn't. Corrected.

What I need you to decide

  • The scope, and the three things deliberately left out.
  • Staying at light, given the security dimension isn't low.
  • The test-only injection path existing at all — the alternative is having no end-to-end proof this bug is fixed.
  • That release and nightly runs will now make a real call to the public test network when a profile is created. That's genuine production behaviour, so it's left alone on purpose.
  • Single pull request into dev.

Approve, conditionally approve with your own conditions, or reject with what blocks it.
