Service fences (batch 7 of the audit remediation)

Three places in the wallet's background services could finish a slow job and write its result after the world changed underneath it. This batch teaches each one to check "is my authorization still valid?" at the last moment before writing — the same trick the transaction service already uses.

1 · Creating an account vs deleting the profile (N-03)

Creating an account takes seconds (it probes the network and derives keys). If you delete the profile mid-way, the deletion's cleanup finishes first — then the account creation wakes up and writes a row for a profile that no longer exists. That orphan row survives forever. Fix: note the profile's "deletion counter" before the slow work starts; just before writing, verify the counter hasn't moved.

2 · Restoring a backup vs cancelling it (N-14)

If a backup import times out, the popup rolls everything back by deleting the half-created profile — but the background restore loop may still be writing rows. Those land after the cleanup and become invisible junk. Fix: every restore writer notes the deletion counter when it starts and re-checks it before each row; rows arriving after a deletion are recorded as errors instead of written.

3 · Balance refresh vs switching profiles (N-10)

A balance refresh computed under profile A can land after you switch to B and back — writing B-flavoured numbers onto A's row. Fix: the refresh notes the profile "generation" when it starts and drops its result if the generation moved.

What deliberately does NOT change

No UI, no storage shapes (no migration), no crypto. A similar-shaped gap in dApp-session storage was found during recon but is outside the audit's findings — logged, not touched. The audit's suggested getSecretWithFence helper doesn't exist; the real ProfileDeletionState API is used instead.
