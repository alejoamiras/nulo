token-identity

Right now the faucet and the bridge both hand out something called "USDC", which is confusing on sight. This arc gives every surface its own honest token: the faucet drips NULO (6 decimals) and OLUN (18 decimals), the bridge moves AZLO (18 decimals on both chains) - real on-chain names via fresh testnet deployments, not display aliases. The bridge's hardcoded 6-decimal math gets properly parameterized along the way. And the wallet learns one new trick: apps can ask "is this token already registered?" - but only for tokens they were explicitly granted, with the permission screen saying exactly that - so the "Add to wallet" buttons finally disappear when they're pointless.

Why this tier was chosen

mid, auto-fired: it crosses packages (extension + wallet-bridge + two frontends + deploy scripts) and adds a wallet RPC, which is protocol surface. The dual audit earned its fee three times over: both reviewers independently rejected my first gating design (a new permission type turns out to be impossible upstream - the wallet SDK's schema is closed), found the cheaper door that was already open (the existing contracts permission already carries the right address lists and permission screen), and the final fresh pass killed my session-reset workaround with the session model's actual keys - forcing the durable fix instead.

Phases

Phase 1: Deploy the three tokens (and only deploy)

Parameterize the deploy scripts (decimals were hardcoded to 6 in three places, with no check that the L1 and L2 sides agree - that check now exists, because a mismatch would mint wrong magnitudes), run the testnet deployments for NULO, OLUN, and the AZLO pair, and record the new addresses. The frontends don't change yet - flipping constants here would break every build until phase 3.

Phase 2: The "is it registered?" wallet feature, done honestly

The wallet answers registration checks only for token addresses an app was granted (same enforcement pattern as the existing contract-metadata checks), without any popup. Two honesty upgrades ride along: the permission screen's wording now names the new ability, and the wallet finally re-asks for consent when an app requests contract addresses beyond its old grant - which is also what makes the redeploy work for existing users, and fixes a known limitation for every future redeploy.

Phase 3: The frontend flip, atomically

Constants, names, decimals, copy, and the footer all land together: NULO/OLUN on the faucet tab, AZLO everywhere in the bridge (with new precision-safe amount math - 18 decimals breaks JavaScript's normal numbers, so amounts are handled as exact integers end to end), "MINT 100 AZLO", hidden add-token buttons when registered (shown again if the check ever fails - a broken probe must never hide functionality), and a footer documenting all three tokens.

Human context

Two things shaped this plan. First: token names and decimals live on-chain, so renaming means redeploying - the tempting "just change the labels" shortcut would leave wallets and explorers saying USDC under an AZLO UI, recreating the exact confusion this kills. Old in-flight bridges from the previous deployment will show their honest "different deployment" notice. Second: your instinct that the registration check belongs under capabilities was right, and the audits made it rigorous - it ended up gated by the contracts permission apps already hold, with the permission screen updated to say so, and a real re-consent mechanism when grants grow.
