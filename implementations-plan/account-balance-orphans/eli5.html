Orphaned Balances

Why a deleted account can leave its old balances haunting the wallet, and the schema-level fix — ruled architectural, not a patch — that two independent auditors converged on.

01The bug, in one story

Every token balance the wallet shows is a row keyed by (token id, account address) — and nothing else. The row doesn't know which profile owns it, which chain it lives on, or which contract it describes. That's the gap everything below flows from.

1You import a full backup. It carries an imported account without its signing key (corrupt — or hostile — backup).
2The restore writes the account's balance rows, then notices the missing key and deletes the account. Only the account. The balance rows stay behind. orphan
3Later you re-import the key. Same key → same address. The wallet goes to create fresh balance rows — and skips, because the stale rows already occupy the token:account slot.
4You see the pre-deletion balances, silently, until some unrelated refresh happens to run. The refreshes are user-action-dependent — there is no timer guaranteed to fix it.

The same missing fields also explain a family of workarounds already living in the code: a manual chain join, a token-map-only cross-profile guard, and a documented "not solvable from this schema" residual where a recycled numeric token id can attach old rows to a brand-new token.

02The ruling: fix the schema, not the symptom

The owner's question was whether this deserves architectural work or a point patch. Both auditors — Codex (GPT‑5.6 xhigh) and an independent Claude reviewer — ruled architectural. The decisive fact: a token's profileId/chainId/contract triple is immutable by contract (the service hard-rejects any change), so copying it onto each balance row creates a stable identity that can never silently drift.

The point patch (scope deletions through a token-id join) was seriously considered and rejected: it's ~40 lines, but it leaves every workaround in place, keeps the id-reuse residual open, and moves the schema decision to a future where it costs a real migration. Today — pre-production, zero migrations — the schema change is the cheapest it will ever be.

03What actually changes

  • Three required fields on every balance row: profileId, chainId, contract. Old-shape rows are swept once at startup and rebuilt fresh by the existing reconciler — balances are recomputable projections, so nothing of value is lost.
  • One shared identity predicate used at every place a raw row is read, refreshed, projected, exported, or counted — about a dozen sites, including two the audit proved were silently fail-open. Wrong-identity rows can never render, never export, never block a repair.
  • A real deletion cascade: purgeForAccounts, scoped to (profileId, chainId, address) tuples. The balance service registers it with the account service (an existing in-repo pattern), so account removal awaits the purge internally — no new RPC surface, and every future removal path inherits the cascade for free.
  • Safer ordering: list the doomed accounts → purge their balances → only then delete the account rows. A crash mid-way now leaves harmless missing balances (auto-repaired), never immortal orphans. A failed purge aborts the whole import into the existing rollback instead of committing damage.
  • Restore trusts nothing from the backup blob: the service derives all three identity fields from its own token table, rejects rows pointing at tokens the profile doesn't own, and collapses duplicate pairs a hostile blob could mint.

05The audit trail

Codex leg conditional approve

Found the multi-chain purge hazard, the occupancy-set gap that would have made the repair fiction, the duplicate-pair hole, and the fail-open refresh paths. All conditions adopted.

Claude leg conditional approve

Caught a false security claim in the draft, the registration pattern that eliminates new RPC surface, service-side stamping, and the purge-before-delete ordering. All conditions adopted.

Two genuine disputes were resolved in the decision ledger (in plan.md): stale-row deletion (the two rulings turned out compatible — delete only when a live token proves the row stale) and the legacy sweep (Codex's argument won: debris taxes every future row allocation, and swept rows rebuild themselves). Every load-bearing claim from both reports was independently re-verified against source before adoption — the trail is in lessons/phase-0.md.

06How it's proven

Five phases, each with a written gate: schema + stamping + a ≥200-row transition test → complete identity enforcement → the purge with two documented RED runs (each hazard above shown failing under the naive implementation before the fix goes in) → an end-to-end test replaying the exact bug story (doctored backup, re-import, assert fresh balances) with a documented pre-fix RED → full regression sweep.
