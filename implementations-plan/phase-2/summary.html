Architecture

Where the durable-jobs subsystem ended up: three execution surfaces (popup / SW / offscreen), a journal record as the single source of truth, and a small reaper that bridges SW-suspend gaps.

Component graph

Each box is a JS context with its own lifecycle. Arrows are message-channel calls (chrome.runtime port for popup↔SW, chrome.runtime.sendMessage for SW↔offscreen).

The FSM

Seven stages; cancel is only legal pre-submit. The diagram is the contract enforced inside OperationJournalService.transitionOperation via assertCanTransition.

Happy-path sequence

Every transition is journalled BEFORE the work for that stage runs (so the popup observes the real stage, not a delayed one). Codex W1+W2 review surfaced the original "simulating after build/estimate" ordering; that's now hoisted in the 3 dApp/transfer paths.

SW-restart recovery (the Phase 2 motivating bug)

SW suspends mid-prove. Pre-Phase 2 outcome: popup sees the disconnect, never gets the prove result back when a fresh SW boots, shows a stale "Proving…" forever. Post-Phase 2: journal record survives, the reaper transitions it on grace-window expiry, popup observes via onConnected resnapshot + subsequent onUpdated.

Why no resume? Aztec proofs are block-anchored and the in-memory state of the offscreen instance that started the prove may have died too. Even when alive, the original requestId isn't addressable from a fresh SW. The honest outcome is "declare it lost" — and that's what the reaper does. A future retry policy could re-issue a fresh job (using the journal's attempts carry as the counter), but that's a Phase 3 concern.

Cancel — pre-submit vs. post-submit

Two distinct behaviors depending on when the cancel arrives. The codex W1+W2 review's blocker fix was the bottom case — without it, journal said "cancelled" while a real tx existed in chain history.

Deferred items

Five items moved out of Phase 2's scope. Each has an explicit reason and a rough re-evaluation trigger.

D1 Migration framework absorbing storage v6 Mechanical refactor
What
The v6 wipe still lives inline in packages/extension/src/wallet/storage/migrate.ts. The original plan called for a small migrations framework (versioned migration entries that run on boot) to absorb it.
Why deferred
Mechanical refactor with zero behavior change. The current inline gate is already shipping the correct semantics (wipe pre-v6 journal/account/tx/balance state + PXE IDB). Building the framework only pays off when a v7 lands.
Re-evaluate when
The first time Phase 2.5 (token-imports-as-jobs) or any other schema-touching change needs a v7 migration — at that point the framework saves real time.
Risk
Low. Inline migrations are not technical debt at one entry; they become debt at three.
D2 IDB backup of journal (browser-restart durability) Out of useful scope
What
The journal lives in chrome.storage.session, which survives SW restart but is wiped on full browser exit. Plan called for an IndexedDB backup so records persist across browser restart too.
Why deferred
The recovery model for browser exit is unrecoverable: the offscreen document dies with the browser, taking the in-flight prove with it. Even if we preserved the journal record, there is no way to resume the prove from a fresh boot (proofs are block-anchored; the in-memory state is gone). The honest outcome is "declare the job lost" — which the reaper already does on SW boot (stuck_proving kind).
Re-evaluate when
If users start asking "where did my pending tx go after I closed Chrome?" — at that point IDB backup gives us a *record* to show them, even though we can't resume. Tombstone-only persistence.
Risk
Low. Today the user sees the tx disappear on browser restart; with the reaper running on next session boot they would see failed:stuck_proving in the activity feed if any record had been there. Without IDB, there's nothing to reap — but there's also no false signal.
D3 Phase 2.5 — token imports as durable jobs Path C decision
What
Token import flows (TokenService.addToken) currently use the in-memory TaskService for progress reporting. Plan Path C deferred making them jobs.
Why deferred
Explicit decision during the approval gate (2026-05-12): scope-limit Phase 2 to PXE prove flows; revisit token imports once the journal + reaper are validated in production. Token imports are simulation-only (no on-chain effect, no prove), so the "popup lies during proving" failure mode they share with sends is far less severe.
Re-evaluate when
Phase 2.5 — the natural next milestone. Will reuse the same FSM (with an "importing" stage substituting for "proving") and the same reaper machinery.
Risk
Low. Token import is a single async call; it doesn't have the multi-stage stall surface that sends do.
D4 Strict Zod validation on journal storage reads Codex W1W2 nice-to-fix #2
What
Codex flagged: EntityStorage returns raw parsed JSON without schema validation; transitionOperation trusts existing.progress.stage and indexes directly into LEGAL_TRANSITIONS. A malformed record that somehow survives the v6 wipe could throw a plain runtime error instead of a controlled IllegalTransitionError.
Why deferred
Defensive concern only. No production users today, so the v6 wipe's "best-effort" is fine — there is no pre-v6 corpus to be malformed-but-not-wiped. The reaper provides a safety net: any stuck record gets reaped to failed:stuck_proving eventually, even if a transition would have crashed on first attempt.
Re-evaluate when
Before the first production release. At that point: gate storage.get reads with OperationRecordSchema.safeParse; on failure, delete the record + log + continue. Cost is small once the schema is already canonical.
Risk
Low until production. Then medium — a single malformed record could surface as a hard crash on the popup. Should not ship to prod without fixing.
D5 Histoire / Lost Pixel for journal-aware RecentActivityView Visual regression
What
No story / visual-snapshot coverage for the new journal-primary in-flight card. M6 phase 10 covers Histoire setup repo-wide; this view should be in that batch.
Why deferred
Histoire wiring is not yet in bun run audit:vue; landing a one-off story before the framework is in place would be an orphan. The unit-tested reaper + manual smoke on a real extension reload covers the regression risk for now.
Re-evaluate when
M6 phase 10 — when the Histoire harness lands, RecentActivityView is in the first batch of stories.
Risk
Low. UI shape is conservative (existing card slot, new data source) and the manual smoke confirmed the journal-primary flow renders correctly.

Follow-ups not in Phase 2 scope

Items raised during Phase 2 work but explicitly outside its boundary:

  • Memory cap on warm profiles — W3 stopped disposing prior-profile PXEs on switch (necessary for durable jobs). Many-profile users could now keep N PXEs warm. Not urgent because PXE memory is dominated by per-chain data, not per-profile; bound when usage data justifies it.
  • "Cancel ignored" UX — Today, hitting Cancel during submitting is silently dropped and the tx proceeds. The popup should show a transient toast like "Cancel ignored — tx already broadcast" so users aren't surprised. Cosmetic, not correctness.
  • Cross-profile fairness — With multi-profile warmth, a future "fairness" policy could limit how many simultaneous proves run across all profiles. Not on the Phase 2 critical path; origin + profileId carries on every record are the seam for this when needed.
  • e2e refactor + copy polish — Was tentatively penciled in for W6 as a buffer; rolled into the Week 5 commit's UX copy update for journalSubtitle. e2e additions waiting on the M6 Histoire batch.
