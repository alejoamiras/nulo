The one-paragraph version

Two well-known Aztec websites — Nethermind's Fee Juice faucet and Wonderland's Token Dripper — break when users try to connect their Nulo wallet. They use a shortcut (getAccounts()) that our wallet currently answers with silence (an empty list). They display that as "you have no accounts" and stop. v3 fix: our wallet now throws a clear structured error (EIP-1193 code 4100, "Unauthorized") when this shortcut is taken without permission. Both sites have fallback code that catches the error and calls the correct permission flow — which triggers a single popup where the user grants everything the site needs. Smaller PR than v2, fixes the entire flow end-to-end, and aligns with what the Aztec wallet-sdk spec already recommends.

Why this matters to the user

Right now, anyone trying to use Nulo with these two sites hits a dead end at first connection. They've installed the wallet, gone through onboarding, set up an account — and the very first dApp they try doesn't work. That's the kind of bug that breaks trust quickly.

The v3 fix is also a quiet endorsement of the right pattern. By throwing a clear error instead of silently smoothing over the issue, we nudge dApp authors toward the spec-compliant flow. Other wallets aligned with the spec already do this; we're catching up.

The fix in one sentence

When a site takes the shortcut, our wallet throws a clear structured error that tells it "call requestCapabilities first" — both sites already have fallback code that catches this and does the right thing. One popup. Full permission grant. End-to-end fix.

The phases, in plain language

Phase 1 Throw a structured error

What: when a site calls getAccounts() before getting accounts permission, we throw a structured CapabilityNotGrantedError. This maps to EIP-1193 code 4100 ("Unauthorized") on the wire — the standard Web3 error code for "you need to ask for permission first."

Why this works: Nethermind's faucet code (and almost certainly Wonderland's) has a try/catch around getAccounts() that calls requestCapabilities() on any error. Today our silent empty array means the catch never fires. With v3, the throw triggers the catch → full manifest sent → one popup grants everything the dApp needs.

Smaller than v2: no new types, no time-based rejection memory, no popup hollow-state work, no inflight dedupe. Just a throw + the error class.

Phase 1.5 — CRITICAL Fix a quiet security bug we found

What: our wallet has a pre-existing flaw where, once a site has been granted basic account access, it can later upgrade to "sign things on the user's behalf" without showing a new popup. The wallet was checking "do you already have an accounts permission?" with a yes/no flag instead of comparing the actual permission shape.

Why it matters: this bug exists regardless of v2 vs v3. Both auditors flagged it as ship-blocking. The fix compares permission shapes properly so any upgrade triggers a fresh popup.

Honest caveat: we only fix the accounts permission shape in this PR. The same kind of flaw exists for other permission types (contracts, simulation, transactions) — filed as a follow-up plan with its own audit cycle, since the fix is more delicate for those.

Phase 1.4 Extract a testable helper

What: the bit of code that converts our internal errors into the standard wire format gets pulled into its own file so we can write unit tests for it.

Why: both auditors caught that my v3 plan tried to test this code where it's inlined inside a larger function — hard to mock, harder to assert. Extracting it into a pure helper means tests can just construct error objects and check the output shape.

Phase 2 Tests

What: 11 changes total — 1 in the error-class tests, 6 in the dispatcher tests, 3 in the new extracted-helper tests, 1 updated end-to-end test. Each pins one specific behavior of the new contract.

Important: one existing end-to-end test today actively asserts the BROKEN behavior ("the wallet returns an empty array silently"). We flip it to assert the new throw — using a flexible match because the wallet-sdk wraps our structured error inside a plain Error containing JSON, so the dApp doesn't see the code directly; it has to parse the message. The test accepts either format.

What we explicitly test:

  • The throw fires for pre-grant getAccounts with the right code and message
  • The fast path (post-grant getAccounts) is unchanged
  • Session-not-found still throws its old error (refactor protection)
  • Phase 1.5 security fix (no silent upgrade)
  • Phase 1.5 same-shape re-request doesn't over-trigger (no useless re-popup)
  • The error round-trips correctly through the wallet-sdk's JSON wrapper (the contract our README will document)

Phase 3 Verification matrix after deploy

Side-load the extension, connect both sites, verify:

  • Nethermind: ONE permission popup → approve → "Claim" works end-to-end
  • Wonderland (if their code has the same fallback pattern as Nethermind): same flow works
  • Wonderland (if not): page shows the new error string — we file an issue with their team
  • Returning visit: session is sticky, no popup needed
  • Existing CI tests still pass under the new contract

Phase 4 File issues with dApp teams

After the fix ships, file GitHub issues against Nethermind's open-source faucet and Wonderland's team pointing at the wallet-sdk spec recommendation. Suggest they invert their try/catch: call requestCapabilities() first, fall back to getAccounts() only for wallets that don't implement it. This is what the spec recommends and what other wallets enforce.

Open decisions — where your call matters

Most of the original questions are now resolved. What's left:

  1. The error message text

    The wallet throws "accounts capability not granted. Call requestCapabilities() first." Lower-case, terse — matches our brutalist style. The literal function name requestCapabilities() is in normal case because it's a function reference. This text is for dApp developers, not end users — it appears in dApp consoles. Does the wording feel right? Once we ship it, dApp authors will substring-match on it, so changing it later is hard.

  2. Wonderland response if they don't have a fallback

    Nethermind's open-source code definitely has a fallback that catches our throw. Wonderland is closed-source so we don't know. If they don't have one, their UI will show our error string instead of "no accounts" — the new error message at least tells their team what to fix. Want me to draft the GitHub issue text we'd send to Wonderland post-merge?

  3. Three follow-up plans we're filing (not implementing in this PR)

    1. wallet-sdk-capability-field-diff — broaden Phase 1.5's field-aware security fix to all permission types (contracts, simulation, etc). Needs its own audit cycle.
    2. wallet-sdk-requestcapabilities-rate-limit — add per-origin rate limit on permission popups. Pre-existing concern, not amplified by v3.
    3. wallet-sdk-error-envelope-typed-codes — explore making the wallet-sdk surface our structured error codes natively without requiring dApps to JSON.parse(err.message). Low priority, ecosystem-level.

    All three are documented in plan-v3.md §9. Want any of them moved into this PR's scope? Recommendation: no — keep this PR tight.
