backup-restore-residuals

The previous arc (#276) made profile deletion atomic and awaited, and fenced the transaction write path so a transfer finishing after you delete a profile can't recreate a "ghost" transaction. But it deliberately left two write paths un-fenced (token metadata + balance projection) as a documented pre-production follow-up. This plan closes those — plus a few small cleanups — so deletion is airtight with zero deferrals: no ghost tokens, no ghost balances, ever.

Why mid tier

Security-sensitivity is HIGH (a resurrection bug leaks/keeps data you asked to erase) — that's 1 high on the rubric → mid. It's a single package, and the fix reuses an already-proven mechanism (the deletion "epoch" fence from #276), so novelty is low. The dual audit revealed the concurrency surface is bigger than it first looked (≈6 writers, needs per-lock atomicity), so this sits at the mid/deep boundary — if the final review still finds a critical, we escalate to deep.

The idea, in one picture

Every profile owns rows (tokens, balances). When you delete a profile, a coordinator purges all its rows. The danger: a slow background job (fetching a token's name, computing a balance) that started before the delete can finish after the purge and write its row back — into the deleted (or a brand-new same-id) profile. The fix stamps each such job with the profile's "deletion epoch" when it starts, and — right before it writes, holding the same lock the purge uses — checks the stamp is still valid AND the profile isn't being deleted. If not, it throws (for user actions) or quietly skips (for background refreshes).

Phases

1. Fence primitive + token wiring

Add a reservation-aware check (isLive = not-being-deleted AND same epoch) and give the token service the shared deletion state + an internal "who owns this token" resolver.

Proves itself by: unit tests for isLive (reserved / stale-epoch / corrupt-tombstone / live) + typecheck + lint.

2. Token-write fences

Fence every token writer (add, update, chain-purge lock, restore) so a token-add finishing after a delete is rejected — and fix a related bug where a stale add leaves an orphan "journal" row.

Proves itself by: deterministic token tests with an injected "pause mid-fetch" hook + typecheck + lint.

3. Balance-write fences

Add a shared balance lock so the balance projector, the purge, the fire-and-forget balance-creation callbacks, and restore all coordinate — no balance row survives its profile.

Proves itself by: deterministic balance tests (pause mid-projection) + successor-id-reuse test + typecheck + lint.

4. Coordinator unit test

Directly test the 12-step deletion purge: everything awaited, correct order, PXE cleared last, a failure keeps the tombstone.

Proves itself by: the new coordinator test + a ProfileService integration pin for "tombstone retained on failure".

5. Reject duplicate token-ids in import

A hostile backup with two tokens sharing an id no longer silently collapses the relink map — the collision is dropped + recorded.

Proves itself by: a composable test with two same-id tokens.

6. Corrupt-tombstone telemetry (NOT auto-repair)

Both auditors flagged that auto-dropping a corrupt tombstone can silently abandon a real in-progress deletion (fail-open). So we only log/count corrupt tombstones for manual recovery — they stay fail-closed.

Proves itself by: tests that a corrupt tombstone is counted + logged + RETAINED.

7. Docs + end-to-end proof

Mark D13 COMPLETE in the index, and extend the live-sandbox e2e to add-a-token / refresh-a-balance mid-delete and assert nothing resurrects.

Proves itself by: bun run audit:vue green + the extended network e2e green.

Human context

"Epoch" = a counter bumped each time a profile deletion begins; it's never reset, so a job holding an old epoch is provably stale. "Reserved" = an id currently being deleted. "Lock" = a mutex; holding the same one the purge holds is what makes the check-then-write atomic (no gap for a delete to sneak in).
