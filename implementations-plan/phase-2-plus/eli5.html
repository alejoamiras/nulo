Token-import flow with the new architecture

User clicks "Add Token" in modal │ ├─ paste contract address, click Confirm │ ├─ TokenService.addToken(..., opContext: { origin: "popup" }) │ │ │ ├─ journal.createOperation({ kind: "token_import", contractAddress, … }) │ ├─ transition → simulating (modal subscribes via journal client) │ ├─ parseTokenInterface() + registerContract() + addToWatchlist() │ └─ transition → succeeded (no txHash for non-tx ops) │ ├─ modal sees succeeded event → closes itself │ └─ tokens view now shows the new TokenCard with the existing "initial sync" spinner (updatedAt === 0), until balance loads. If user closes modal mid-flow: • journal entry keeps running • tokens view shows a TokenImportRow (in-flight) • on completion: row vanishes, TokenCard takes over • NO modal reattach — reopening modal starts fresh. If import fails: • journal transitions to failed with error.kind • TokenImportRow stays for ~30s showing the error, then auto-dismisses • (or: user can refresh / retry by reopening modal)

Phase B — Expansion (planned, post-Phase-A)

After Phase A ships and validates in production, expand the template. Grouping by FSM/lifecycle shape (codex's call) — domains get mixed because behavioral shape is what matters for graduation, not what the op does.

batch B1 · same shape as token_import
Single-shot journal-only ops

No on-chain prove/submit. FSM pending → simulating → succeeded/failed. Each has a natural non-activity home surface.

  • Add sender — PXE register, 1-3s
  • Add contact (with sender registration opt-in)
  • Add network — RPC node probe
  • Add endpoint — RPC connectivity test

~20-25 unit + 1-2 e2e. Open question: add-sender has no visual home today — do we add one or just track durably without surfacing?

batch B2 · same shape as transfer
On-chain destructive writes

Full FSM pending → simulating → proving → submitting → succeeded/failed/cancelled. Activity feed is the natural surface (these ARE transactions, just non-fund-transfer ones).

  • Revoke authwits (batched)
  • Change authwits registry

~15-20 unit + 2 e2e. Open: revoke-batched = one journal op per chunk, or one op spanning all chunks?

batch B3 · multi-step with checkpoints
Long import/export flows

10-30s ops with multi-stage progress. May need extending JobProgress.simulating with per-stage fields (syncedAccounts, totalAccounts) or adding a new syncing stage.

  • Import backup
  • Import seed phrase
  • Import private key
  • Create profile (passkey) — retry on ProfileIdConflictError; uses attempts carry

~30-40 unit + 2-3 e2e.

deferred indefinitely
Approval / session flows

dApp connect-session approval, capability negotiation — different shape (user-decision gates, not async work). Phase 3 territory if at all.

Won't graduate (explicit non-goals)

Sub-second local writes don't benefit from journaling — the op completes before SW could die. Pure overhead.
