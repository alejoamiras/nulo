network-e2e-required

Make the Network e2e check on every pull request reliably green, then make it a required check on dev — so broken dApp-transaction behavior can't merge. We fix the real bugs, never paper over them with retries.

Why "deep"

A lighter (mid) plan was drafted first and rejected by audit — it was built on a wrong guess about the bug. Deep was chosen because two risk dimensions are HIGH: blast radius (a required check gates every PR) and security sensitivity (we're changing how the wallet records authorizations — a trust boundary). Three independent plans were drafted (me + codex + a planning subagent); they independently agreed on the core design, which is a strong confidence signal.

The story (plain version)

Three flaky tests blocked making the gate required. Two (F2, F3) are already fixed. The third (authwit-lifecycle) sent me down a rabbit hole — I assumed "the wallet doesn't record granted authorizations." The audit proved me wrong: it does record them. I never actually looked at the screen that was failing. Two real things turned up instead: (1) the bug behind that empty screen is still unmeasured — so we measure before fixing; and (2) the wallet records authorizations too early (when it estimates a fee, before you approve, even if you reject) — a genuine security bug worth fixing. Plus the gate itself is weak: it currently retries failures twice, so it would hide the very flakes we're fixing.

Phases

Phase 1: Land the finished fixes

Merge the branch that already fixes F2 (concurrent sends) + the settings-nav fix + a dropdown-disabled fix + the diagnostic tooling we'll need next.

Proves itself by: full pre-PR gate green + concurrent-sendtx 7/7 in a strict soak.

Phase 2: Make the gate honest (no app changes)

Turn off the gate's automatic retries (so a flake = a red, not a hidden pass). Add a precise "the sandbox failed to boot" detector so only that one infrastructure hiccup gets a single retry — a real test failure never does. Widen which file changes trigger the gate (the approve/revoke screens were slipping through).

Proves itself by: actionlint green; the boot-detector unit-tests correctly tell infra-fail from test-fail; a UI change now triggers the gate, a docs-only change still skips.

Phase 3: Measure the real authwit bug (no fix yet)

Capture what's actually on the failing screen + what's in storage + which account it's asking about, and classify the cause. No code change — just an evidence-backed diagnosis written down.

Proves itself by: three runs agree on one root-cause bucket, recorded in the lessons file.

Phase 4: Fix the measured cause

Fix exactly what Phase 3 found (most likely an address-format mismatch or an over-eager "delete not-yet-confirmed" sync) — not the guessed one. Then drive the whole authwit-lifecycle test green.

Proves itself by: new unit/regression tests + authwit-lifecycle 10/10 in a strict soak.

Phase 5: Fix the "record too early" security bug

Stop recording an authorization while merely estimating a fee. The build step describes the would-be grant; the wallet only writes it down after the transaction actually sends — and as pending until it's mined (so a sent-but-dropped grant doesn't leave a false entry). The "you've hit the limit" cap is checked before sending (you can't un-send), and a failed write is loud, never silently dropping a grant.

Proves itself by: tests proving estimate/reject/failed-send/dropped record nothing, one mined grant records once, the cap blocks before sending; send pipeline + real-proving canary still green.

Phase 6: De-flake the rest (the part the audit uncovered)

The audit found the suite was hiding flakes: ~8 tests quietly retry themselves 1–2× and one is skipped outright. Turning retries off (Phase 2) exposes the real flaky set. Here we root-cause each one to green — the same "measure, don't guess" discipline — with no retries left.

Proves itself by: each test green with zero retries; a grep confirms no retry:1/2 remains; the full sharded suite green.

Phase 7: Prove it's stable, then flip required

Run the real PR gate 5 times in a row, all green, on one commit. Only then make it required on dev. Document a time-boxed rollback for upstream outages (not a quarantine).

Proves itself by: 5 consecutive green real PR runs; the ruleset shows the check required.

Human context

The PR network check is proverless (fast fake-proving) — so the quick soaks we iterate with are representative of the real gate. "Required" means a red check blocks merging. The auth-registry is the wallet's local list of "authorizations you've granted," shown in Settings so you can revoke them; recording it at the wrong moment makes that list lie.

Scope grew (honestly). The final audit revealed the suite was hiding flakes: ~8 tests pass only because they retry themselves, and one is skipped. So "green on every PR" means fixing those too — not just the three flakes we started with. That's more work, but it's exactly the "fix everything, no patches" you asked for.

Decisions (resolved at approval)

  • Gate retries: 0 (strict).
  • Flood cap: 256/account, non-evicting, blocked before sending.
  • Rollback window: ≤24h time-boxed (not quarantine).
  • Fork PRs: dev doesn't take them — no secret-gating problem. Repo-admin available; flip via ruleset.
  • /harden security: yes, but narrow — scoped to the auth-registry change only.
