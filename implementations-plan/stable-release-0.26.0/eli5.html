Release blueprint · light tier

Ship Nulo v0.26.0

Move everything that's been merged into the day-to-day branch onto the stable branch, build the browser-extension files, publish a GitHub release, and refresh the two public websites. It's running a proven checklist for one specific version — not writing new code.

v0.26.0 tier: light 21 features landing + faucet

⏱ This takes a while — mostly waiting

Realistic wall-clock is roughly 1.5–2.5 hours, and almost all of it is CI running unattended. Three separate pull requests each run the full test suite including a live-network test that takes ~25–45 minutes, plus a ~15–25 minute build-and-publish step. Nothing is skipped to go faster.

What this is — and what it isn't

Your original ask mentioned "playground deployment." Heads-up: the playground isn't a thing that gets deployed. It's a local test dApp the automated browser tests drive — it has no website. The release actually refreshes two real sites: the landing page (nulo.sh) and the faucet (faucet.nulo.sh). Both happen automatically once the release publishes.

Also: this does not push the extension to the Chrome or Firefox stores. Those steps are disabled stubs. The build just produces the extension files and attaches them to the GitHub release — so a bad build can't silently auto-update anyone's browser. That's the single biggest safety margin here.

Why the "light" treatment

This is the sixth-plus run of a well-worn release checklist (v0.21 through v0.25 all shipped this way), there are no users yet so there's no data to migrate, and the release itself creates no new secrets. The scored risk came out low across the board, so it gets the lightweight treatment — one outside review (done), not the heavy multi-reviewer process.

One nuance the review flagged: the features being shipped aren't trivial — they include bridge, account-identity, and backup changes. But each was tested and reviewed when it was originally merged; a release cut doesn't re-review them. "Light" describes the release mechanics. Whether you want an extra security pass or a live test-network dry-run before pressing go is Open Question 2 below.

The plan, step by step

The steps are numbered because they're a strict chain — each depends on the one before. The amber-numbered steps are the ones where I merge onto a protected branch on your behalf.

1

Freeze the release & pre-flight

Record the exact commit we're shipping, and confirm the coast is clear: nothing unrelated waiting to merge into the stable branch, the auto-release switch is on, and the required checks are in place.

Proves itself by: the release commit is pinned, there are zero unrelated pull requests into the stable branch, and the live settings check out.

2

Promote day-to-day → stable merges to main

Open the pull request that moves the 21 merged features onto the stable branch. Wait for the full suite — including the ~25–45 min live-network test — to go green. Double-check nothing slipped into the branch since we froze it. Then merge.

Proves itself by: all three required checks green, the branch still sits at the frozen commit, and it lands as a real merge.

3

Merge the version pull request merges to main

A bot automatically opens a PR that stamps the version to 0.26.0 and writes the changelog. It also runs the full suite (another ~25–45 min live-network run). Review the changelog, confirm the version, and merge.

Proves itself by: the version reads 0.26.0, the changelog looks right, all three checks are green, and it lands as a real merge.

4

Build & publish (automatic)

Merging the version PR fires the pipeline: it tags the release, builds the Chrome + Firefox files, smoke-tests the real build, attaches the files with checksums, and redeploys both websites. I watch it and step in only if something goes wrong (including the rare "release exists but the files didn't attach" case).

Proves itself by: the release lists both extension files plus a checksums file, is marked stable (not pre-release), its tag matches the merge, and the websites redeployed.

5

Sync the version back to day-to-day merges to dev

A bot opens a PR bringing the version stamp back to the day-to-day branch. It runs the full suite again. Merge it as a real merge (not a squash) so future release-candidates count from the right baseline.

Proves itself by: the day-to-day branch now reads 0.26.0 and it landed as a real merge.

6

Verify live & wrap up

Open nulo.sh and faucet.nulo.sh and confirm they're serving this exact build (the faucet is checked by its build fingerprint, since it has its own separate version number). Record the outcome and close out.

Proves itself by: the landing page shows 0.26.0 and the faucet's build fingerprint matches this release.

Background you might want

Two branches. "Day-to-day" (dev) is where features land continuously; "stable" (main) is what a release is cut from. Merging onto stable is deliberate and protected — that's why steps 2, 3, and 5 are called out.

Why so much waiting? The long test is a live-network run: it drives the real extension against a real Aztec network with real cryptographic proving. It's the strongest signal the wallet actually works, and it's required on every merge onto stable — so it runs three times across this release. That's by design, not overhead to trim.
