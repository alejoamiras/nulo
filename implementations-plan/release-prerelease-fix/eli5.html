Fixing the prerelease (rc) flow

When we try to cut a "release candidate" (an -rc preview build) from the dev branch, the tool spits out the wrong version (0.23.0 — the version we already shipped — instead of 0.24.0-rc.0) and a changelog listing every commit since the repo was born. This plan fixes the real cause, proves the fix in a throwaway repo, then re-cuts and publishes the real v0.24.0-rc.0.

The one-sentence cause

Our release robot finds the version number by walking dev's history looking for the commit that the last release (v0.23.0) is tagged on — but that commit only lives on main, never made it into dev's history, so the robot gets lost and falls back to "start from the beginning."

Why isn't it in dev's history? After every release we sync main back into dev — but that sync is squashed (flattened into a brand-new commit). Squashing copies the content (the version number in the files) but throws away the link to main's actual release commit. So dev looks like it has 0.23.0, but the robot can't find the anchor it needs.

The fix (two parts, no hacks)

  1. One tiny config change: tell the prerelease config to number the series rc.0, rc.1, … (a one-word edit: "rc" → "rc.0").
  2. Put main's release commit back into dev's history with a real merge (not a squash), so the robot can find its anchor — and make the after-every-release sync do this merge from now on instead of squashing. That permanently stops the bug from coming back.

Proven already: in a scratch test, doing exactly this produced a clean 0.24.0-rc.0 with a 43-commit changelog (only the new work), not 186 commits of ancient history.

Why this is a "light" blueprint

Rubric: novelty low (release-please is well-understood), blast radius low (prereleases skip the live websites), irreversibility low (a bad rc is just deleted), migration cost none, external coupling low, security sensitivity low-moderate (it's release tooling, but guarded). 0–1 "high" → light. The fix itself is a one-line config edit plus a history correction. The one thing that pokes above "config-only" is a branch-policy decision (below), surfaced for you to choose.

Phases

Phase 1: Rehearse the whole lifecycle in the throwaway

Before touching the real repo, reproduce the bug and the fix in the private nulo-release-rehearsal repo, then do real cuts end-to-end: first rc (rc.0) → second rc (rc.1) → promote to a stable release. This is the only way to prove the parts a dry-run can't (the rc.1 bump and the stable promotion need real tags). It also answers a practical question: can an admin force a "merge" on a squash-only branch, or do we need a different mechanism?

Proves itself by: all three versions come out correct in the throwaway (rc.0, then rc.1, then stable), each with a clean changelog.

Phase 2: Apply the fix to the real repo

(a) Merge the one-line config change into dev. (b) Do the one-time history fix so main's release commit is in dev's ancestry. (c) Change the recurring sync so it merges instead of squashing, and write it into the runbook.

Proves itself by: a check confirms the release commit is now an ancestor of dev, and a dry-run on real dev prints 0.24.0-rc.0 with a clean changelog.

Phase 3: Re-cut and publish the real v0.24.0-rc.0

Re-run the prerelease workflow (it fixes the existing broken PR in place), review, merge, do the documented manual "unstick", and let the publish chain build the Chrome + Firefox zips and attach them — as a prerelease GitHub Release. Prereleases deliberately do not redeploy the live websites.

Proves itself by: the GitHub Release v0.24.0-rc.0 exists, is marked prerelease, and carries the two zips + checksums.

Human context you need to weigh the decision

Our two branches have strict rules: dev only allows squash merges (to keep its history a clean single line), main only allows merge commits. The squash rule on dev is exactly what breaks the release anchor — and fixing it requires landing one merge commit on dev, which the rule currently forbids. So this is unavoidably a small policy call, not just a config tweak.

The one open question — RESOLVED (2026-06-30)

Phase 1 rehearsal changed the answer. A squash-only rule turned out to hard-block merge commits for everyone — even an admin or a "bypass" bot couldn't force one through a pull-request merge. So the original "bypass bot" idea (Option 1 below) was proven impossible. Chosen instead: allow both squash and merge on dev, and have the sync use a merge. Humans still squash by habit (it stays the default button); the periodic sync adds a merge commit either way, so nothing extra is lost. The original options are kept below for the record.

How should we allow that history-preserving sync onto dev without weakening the squash rule for normal feature work?

  • Option 1 — Bypass for the release bot only (recommended). Let only the release robot land a merge-commit on dev; humans still must squash. Clean, automatic, keeps the linear-history guarantee for everyone else.
  • Option 2 — Allow merge commits on dev for everyone. Simplest to set up, but now nothing enforces squash on feature PRs (it's back to habit/convention).
  • Option 3 — Admin-force a merge each release. Keep the rule, and an admin overrides it once per release. Manual, and we're not 100% sure the override can pick "merge" on a squash-only branch — Phase 1 settles that.
