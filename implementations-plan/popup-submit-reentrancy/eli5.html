Popup Submit Re-entrancy

One held-down Enter key shouldn't create two accounts.

What's wrong

Most of the wallet's little forms (rename profile, add contact, add sender, add network…) show a spinner while they save — but they never actually refuse a second submit while the first one is still running. Pressing Enter again (or holding it — keyboards auto-repeat), or tabbing to the button and pressing Enter there, starts the same save again, in parallel. Worst case found: the "create account" form can produce two accounts with the same name from a single intent. The audit also caught this in the dApp capability-approval window — an approval surface.

The fix, in one sentence

Every save-button gets one shared rule: "while a save is running, the form is closed" — enforced in the code that runs the save (so every route is covered) and on the button itself (so it's genuinely disabled, not just dimmed).

Why the review round mattered

  • Two forms would have locked up forever after one failed save under the naive fix — their "saving…" flag never resets on error. Now repaired first.
  • One form drops its flag mid-save (network add keeps working after the flag clears) — the guard would have had a hole in the middle. Now spans the whole save.
  • Two surfaces we thought were safe weren't — one of them hidden by its own test's stub. Both pulled into scope.

What you'll see

Nothing, in normal use — except that mashing Enter now does exactly one thing. Tests: every fix class gets a pin that hangs a fake save and re-presses, proving one call; the existing end-to-end flows (rename, endpoints, accounts, contacts, senders) re-run as regression checks.

Decision made — Option B: while a save runs, the spinner keeps the button at its brighter loading look (one CSS line in the design package); the heavy dim stays reserved for "the form isn't valid". Chosen via the side-by-side design-system demo; the guard underneath is identical either way.
