Two pending transactions, one visible

A friends-QA bug, deep-debugged. ELI5 for the person who didn't read the code.

The thing that broke

Friends QA'ing the faucet hit something weird. They'd click "Get USDC (public)" twice in a row, expecting two pending transactions. The wallet showed only one. After the first transaction confirmed, the second would suddenly appear in "loading…" state, then confirm.

The user described it as "a visual bug" — meaning both transactions do eventually go through, but the wallet hides the second one until the first is done.

What we expected: two cards both showing "Proving…" at once, then both showing "Confirmed".

What happened: one card showing "Proving…", then "Confirmed", then a second card appearing from nowhere showing "Proving…", then "Confirmed".

The wrong answer I gave first

round 1

I went looking and found a mutex (a "lock" that lets only one thing at a time pass through) inside the part of the wallet that handles approval popups. I thought: "Aha — this lock is held too long. It blocks the second transaction's popup from opening until the first one finishes proving."

I wrote up a plan to release the lock earlier. I sent it to codex, my AI reviewer for these things.

Codex came back with BLOCKER and explained: I was wrong about where the lock was actually held.

In JavaScript, a piece of code like finally { release_lock() } at the end of a function runs immediately when the function's return statement is evaluated — not when whatever the function returned has finished. So the popup-lock I'd diagnosed was actually being released the moment the popup opened, not when the transaction finished. The wallet was fine on that lock.

The real chokepoint was a different mechanism — one layer up.

What was actually wrong

round 2

Each time a dApp (like the faucet) sends the wallet a message — "approve this transaction", "register this contract", "what's the balance?" — it goes into a queue. The wallet processes messages from the same dApp one at a time. This queue is deliberate: some messages depend on each other (you have to register a contract before you can call it), and processing them out of order would create bugs.

The queue is "first in, first out": when one message is done being handled, the next one starts. Simple.

The problem: "done being handled" was defined too broadly. For a sendTx (send transaction) message, the wallet considered the message "still being handled" until the transaction had:

  1. Shown the approval popup
  2. Been approved by the user
  3. Been simulated locally
  4. Been proven (this takes the longest — generating cryptographic proof)
  5. Been submitted to the blockchain
  6. Been confirmed in a block

All of steps 1–6 had to finish before the next message in the queue could even start. So if you submitted T1 and T2 back-to-back, T2 had to wait for T1's full lifecycle before its popup even opened.

WAITING ...... T2: ........... popup → approve → prove → submit → confirm (queue is still blocked by T1) (started right after T1's tx was built, while T1's proving was still running)

The fix, in one sentence

Let a sendTx handler tell the queue "I'm done depending on the queue's ordering" the moment it has built its transaction, not when the transaction has fully gone through.

Concretely: every time a wallet message arrives, the queue mechanism passes the handler a little callback called onTxRequestFinalized. The handler can call it whenever its work no longer needs to be serialized against subsequent messages.

  • For sendTx: the handler calls it right after the transaction request object is built (this is where the nonce — a unique number — gets baked in). After that, the proving and submitting can run alongside the next message.
  • For most other messages (registerContract, executeUtility, etc.): the handler doesn't call it explicitly. A safety net releases it when the handler finishes, exactly like today. Backward-compatible.

The corrections codex made on round 2

round 2 details

I sent the corrected plan back to codex. This time it came back needs-work (not blocker — meaning direction was right, but two real issues).

1

Don't put the callback on SessionContext

I'd planned to attach the new releaseFifo callback to an object called SessionContext that travels with every dispatched message. Codex pointed out: there's a separate message type called batch that runs multiple operations as one unit, and it recursively reuses the same context for each operation inside. If a batched sendTx released the queue early, the rest of the batch would no longer be serialized — letting the next session message cut in front of unfinished batch work.

Fix: pass the callback as a separate, internal argument that doesn't get forwarded into batch recursion.

2

The NO_FROM path was missed

The wallet has two code paths for sendTx: a standard one and a NO_FROM one (used when an account doesn't exist on-chain yet — first-time deploys). My plan only wired the callback into the standard path. The NO_FROM path would have stayed serialized.

Fix: fire the callback in both paths, at their respective "transaction built" moments.

3

Move the release point a tiny bit earlier

I'd planned to release the queue right after writing a "proving started" marker to a journal (a durable log of in-flight transactions). Codex pointed out: this couples queue progress to a small bit of disk I/O. Cleaner to release the queue right before that — the moment the transaction is built and the cancellation check passes.

Also renamed the callback from onProvingStarted to onTxRequestFinalized to match what's actually true at that point.

4

My nonce model was slightly wrong

I assumed PXE (the wallet's internal state engine) allocated transaction nonces sequentially. Codex showed me the actual code: the wallet generates each nonce as a random field element (a 254-bit random number). Two concurrent transactions get independent random nonces; collision is mathematically possible but astronomically unlikely (1 in 2^254). So the safety claim shifted from "FIFO guarantees uniqueness" to "random space is big enough that it doesn't matter".

This doesn't change the implementation — just my mental model and the comment text.

What stays serialized (the constraint I didn't choose)

Even with this fix, the proving step itself still runs one transaction at a time per wallet. There's a separate serialization deep in the Aztec runtime that protects the PXE's internal state. Two concurrent provings would race on shared state, so the runtime explicitly serializes them.

From the user's point of view, this means: with the fix, both approval popups appear in sequence (you approve T1, then T2's popup is RIGHT THERE — no waiting), both in-flight cards show up, and proving rapidly alternates between them. Both confirm at roughly the same time.

Without the fix: you approve T1, wait an eternity for it to finish, T2's popup finally opens, you approve, then wait again.

Lifting the proving serialization would be a much deeper change inside the runtime layer — out of scope here. The friends-QA complaint was about the popup/UI sequencing, which this fix addresses.

Open questions / things to watch

  • Out-of-order results. Once T1 and T2 run concurrently, T2 can finish before T1. The wallet SDK that dApps use to talk to the wallet correlates responses by a message ID (not by order of arrival), so this should be fine. There's a test specifically for this.
  • Settlement race. If a user closes a popup at the exact same moment they approve it (or the popup times out while the wallet is processing the approve), who wins? Codex flagged this as a pre-existing race, not made worse by this fix. There's a test for it too.
  • True parallelism is bounded by PXE serialization. Don't oversell this fix as "concurrent transactions". The UI is concurrent; the proving alternates. Worth being honest with the user about that.
