Deprecate simulate_views — ELI5

A refactor PR. Zero user-visible changes; this is cleanup of a leftover internal abstraction so the next contributor doesn't have to wonder what it's for.

The shape of the problem

The wallet has a "view simulation" feature: given a batch of view-only calls (like "what's USDC's balance_of_public?"), it runs them efficiently — utility-typed calls go through PXE one-by-one, but public-typed calls get bundled into a single simulated transaction. That's faster than doing N separate simulations.

This was originally exposed as a Nulo-custom RPC (simulateViews) that dApps could call. In the last PR (#50) we deleted the dApp-facing surface — that RPC is gone. But the underlying operation kind (simulate_views) and the public method that implements it (ExecutionService.executeSimulateViews) survived because two internal callers depend on it:

  • Balance projector — when the wallet's token list refreshes, it batches all the balance_of_* reads for every token through this method.
  • Gas balance — checks FeeJuice public balance + Private FPC balance via this method (one call each, but uses the same path).

So we have a "dispatch path" (op kind, switch case, type, request shape) that nothing dispatches anymore, plus a public service method that's actually only used internally. That's misleading code. Future maintainers will assume executeSimulateViews is a dispatched operation and treat it accordingly.

What we're doing about it

1. Extract the batching logic into a real helper

The body of executeSimulateViews becomes batchedViewSimulation(calls, deps) — a pure function in its own file (execution/helpers/batched-view-simulation.ts). No this, no class, just inputs → outputs. The dependencies (PXE, account, etc.) get injected so it's easy to unit-test by stubbing them.

Why: a "simulate a batch of views" helper isn't really an Operation in the way sendTx or simulateTx are. It's a derived utility used by other code. Putting it in its own module signals "this is a primitive, not a wire protocol."

2. Refactor the two callers to use the helper

The balance projector + gas balance code both stop calling this.execution.executeSimulateViews({kind: "simulate_views", ...}). Instead they call batchedViewSimulation(calls, deps) directly. Same logic, no fake operation wrapper.

3. Delete every trace of the simulate_views operation kind

The type definition, the request shape, the switch case in executeOperations, the dead branches in the dApp-interaction validation, the popup window's case, the materialize case, the humanize test. All gone.

Why now: in the last PR we kept some of these "in case the legacy popup path still hits them" — but with the op kind itself gone, there's no way to reach them.

4. Pin the new helper with unit tests

The split-by-FunctionType logic + payload-build + decode contract gets unit tests for the first time. Right now this batching logic only has e2e coverage (which is slow + indirect). Direct unit tests catch regressions in seconds.

5. (Bundled) Thread the register-token preview through

Codex deferred a small thing in the last PR's post-impl review: when the user clicks "Add USDC to wallet," the popup pre-fetches the token's name/symbol/decimals to show before Allow. After Allow, the executor re-fetches the same data. That's a wasted round-trip to PXE.

We thread the popup's fetched TokenInterface through the operation so the executor skips the second fetch. Same correctness, one fewer PXE call.

6. (Bundled) Drop the leftover dapp-interaction cases

Same as step 3 but specifically for the validateSession + materialize + popup window code paths that were kept defensively in #50. They're unreachable now — clean them up.

What could go wrong

This is a pure refactor — no behavior changes. The main risk is output parity: the new helper must produce exactly the same results as the old code, byte-for-byte.

  • Same call ordering in the simulated tx
  • Same fee-payment-method setting (PREEXISTING_FEE_JUICE)
  • Same simulatePublic: true + skipFeeEnforcement: true on pxe.simulateTx
  • Same error messages ("Contract not found", "Method not found") — callers may surface them
  • Same return-value mapping (public-typed vs private-typed slots in the returned tuple)

The safety net: before the PR ships, run the existing network e2e on dev AND on this branch, compare balance + gas readings. Same numbers = parity confirmed.

Bundled register-token security note

The "thread the previewed interface through" change has a security wrinkle: if the executor blindly trusted dApp-supplied metadata, a malicious dApp could lie about a token's symbol/decimals to fool the user. But our popup's pre-fetch runs in the extension's own context, not in the dApp's. The data is fetched by our offscreen PXE, never touched by the dApp. So threading it through is safe.

The risk is staleness, not forgery — the on-chain contract could theoretically change behavior between popup pre-fetch and executor execution. For a normal token contract this is near-zero risk (the contract's ABI doesn't mutate). Accepted.

What you get when this merges

  • One fewer "what is this for?" Nulo-custom op kind cluttering the codebase
  • The batching logic is testable in isolation and documented
  • One fewer PXE round-trip on every "Add to wallet" approval
  • Faster on-ramp for the next contributor: executeSimulateViews stops being a confusing tag they have to grep to understand

Zero user-visible UI changes. Token balances and gas balances render exactly as before.
