Restructuring tests to wait for the right thing

Companion to plan.md. Aimed at a reader who has zero context on this project.

Other docs: plan.md audit-codex.md audit-opus.md

What problem are we solving?

Nulo's test suite has a handful of tests that send a transaction through the wallet and wait for the dApp to receive an "ok" back. On a slow CI runner, those tests time out because part of the wallet's work (generating cryptographic proofs in WebAssembly) takes longer than the test budget allows.

We have to keep skipping those tests on CI. We want to stop skipping them.

Why didn't the previous PR fix this?

The previous PR (#67) installed a native proof-generator on the CI runner — way faster than WebAssembly. But it only speeds up the LAST step of proof generation. The wallet has to do several earlier proof steps that still run in WebAssembly, and THOSE are what take too long on slow runners.

We can't fix the WebAssembly speed problem in this PR (it'd require upstream changes to the proof tooling). But we can change what the tests wait for, so they don't have to wait for the slow part at all.

The plain-English idea

The wallet has an internal state machine for every transaction:

pending → queued → simulating → proving → submitting → succeeded

Today's tests wait for the WHOLE state machine to reach succeeded (or failed). That requires generating all the proofs (slow part).

The new tests will wait for the state machine to reach proving. That just requires the wallet to have built the transaction and started the proof process. Fast — happens in seconds, not minutes.

Same UI being tested. Same wallet code path being exercised. Just an earlier finish line.

What we keep testing

  • ✅ User clicks "Send" in the dApp
  • ✅ Wallet's "Execute" popup opens
  • ✅ Popup shows the right contents (fee picker, payload rows, etc.)
  • ✅ User clicks Approve
  • ✅ Wallet builds the transaction request from the dApp's input
  • ✅ Wallet successfully simulates the transaction (means: the inputs make sense + balances allow it)
  • ✅ Wallet enters the proof generation phase

What we stop testing

  • ❌ Wallet successfully COMPLETES all the proofs
  • ❌ Wallet successfully broadcasts the transaction to the L2 node

Important: even today's tests do not verify the transaction actually mines on chain. We thought they did, but the audit caught that the wallet's "I'm done" signal fires the moment the wallet broadcasts (not the moment the block mines). So the actual coverage gap is narrower than it first appeared.

Is anything else testing the "completes" part?

Yes — transfers.test.ts exercises the full prove + submit + mining cycle. It uses the wallet's OWN send flow (not a dApp), but it goes through the same proof-generation code. If the prove pipeline breaks structurally, that test catches it.

What's NOT separately covered: "the dApp-initiated path specifically completes its prove + submit pipeline." That's the residual risk. Mitigation: PR review + the test still runs all the EARLIER parts of the pipeline (so a wallet that broke in obvious ways would still fail).

How we wire it up

The wallet's popup already shows a card for in-flight transactions (a "tx-awaiting-card"). We add one new HTML attribute to that card: data-stage="proving" (or whatever stage is current). Tests look for that attribute. Done.

The Vue component already has a stage prop — we're literally just plumbing one extra value through to the DOM. Five lines of code in the wallet UI.

The plan, phase by phase

Phase A — Add the data-stage attribute

Edit two Vue files: TransactionCardLayout.vue (adds the attribute binding on the root element) and TransactionAwaitingCard.vue (passes its existing stage prop through to the layout). Add unit tests in two test files: one for the contract (the actual binding) and one for the wiring (the prop pass-through).

Phase B — New test helper

Add waitForSendTxProvingStage(walletPopup) — a one-purpose function that waits for the wallet's tx-awaiting-card to reach stage "proving". Deliberately narrow: a future PR can't quietly weaken this to "wait for stage 'pending'" by changing one string parameter; they'd have to rename the function, which is loud in PR diffs.

Phase C — Restructure the 3 quarantined tests

Edit tx-sendTx-default.test.ts, multi-account-from.test.ts, and tx-sendTx-multicall.test.ts. Replace "wait for dApp's full sendTx promise" with "open wallet popup, wait for stage = proving." Remove the quarantine gate that's been hiding these from CI.

Phase D — Restructure 3 more tests with the same pattern

The opportunistic ones: tx-sendTx-noFrom.test.ts, tx-sendTx-feePayer.test.ts, tx-sendTx-sponsoredFpc.test.ts. Currently passing on CI, but exhibit the same pattern. Restructure for consistency (and as a buffer against future slow-runner-pool flake).

One test that LOOKS like it qualifies but explicitly DOES NOT: tx-sendTx-reject.test.ts. That test rejects the transaction in the popup before approval — the wallet never enters proving. Its "wait for dApp result" IS the point of the test. Leave it alone.

Phase E — Workflow + docs cleanup

Now that the 3 quarantined tests don't need the quarantine env var, remove it from the GitHub Actions workflow + the local docker-ci-like script + the e2e README. Sanity check via grep that nothing else references it.

Phase F — Update the planning archive

Add resolution notes to the previous plan docs (e2e-stabilization, network-followups/slow-tests-hypotheses, network-e2e-unquarantine) marking the quarantine fully resolved.

Open questions (resolved during implementation, not blockers)

  • Q1: Does Vue properly forward data-stage to the rendered DOM with the explicit-prop pattern? (Audits confirmed yes; verified pattern at TransactionCardLayout.vue:93-96 for sibling data-tx-* attributes.)
  • Q2: Does the wallet popup auto-open after the dApp's approve, or does the test need to drive it open? (Mirror cancel-mid-prove.test.ts:112 — established pattern.)
  • Q3: Race window where the wallet enters "proving" before the popup card mounts? (Existing precedent at cancel-mid-prove.test.ts:111 waits for the card; same pattern handles this implicitly.)

Security in plain words

  • Risk: a future PR quietly weakens the assertion. Mitigation 1: the helper is named waitForSendTxProvingStage — a future PR can't degrade it via a single string-param change. Mitigation 2: PR review catches new waitForPgResult for sendTx in popup-shape files (this would be a regression to the old anti-pattern).
  • Risk: someone re-introduces the skipDeferredSlow env var to silently hide a regression. Visible in workflow YAML diff.
  • No production code path reads data-stage. The attribute is consumed only by tests. End users never see it.
  • No new dependencies. No supply-chain change.

How this links back to recent work

This is the third PR in the arc:

  1. PR #67: Installed accelerator-server in CI. Sped up the final proof step. But couldn't un-quarantine these 3 tests because earlier proof steps stay slow.
  2. This PR: Changes the tests to not wait on those slow steps. Un-quarantines.
  3. (Future): If accelerator-server upstream adds coverage for the earlier proof steps, OR if we restructure the wallet to expose more journal events, we could go even further. Not in scope here.

What would make me say "this isn't ready yet"

  • Phase A unit tests pass even when the binding is deliberately broken — would mean we tested the wrong thing.
  • Restructured tests flake on CI within the first 3 acceptance runs at the new (much smaller) 60s budget — would mean even the "proving" stage takes >60s to reach, which would be surprising and worth investigating.
  • The Phase D opportunistic sweep accidentally weakens a test that was deliberately e2e (audit was rigorous about this, but it's the kind of thing that's easy to over-do).
