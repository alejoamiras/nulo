On your specific questions: the Phase A mechanism is right as proposed. An explicit `stage` prop plus `:data-stage="stage"` on the `TransactionCardLayout` root is the better local idiom here; `$attrs` / `inheritAttrs: false` is not needed. The repo already uses explicit root `data-*` bindings in [TransactionCardLayout.vue:92](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/components/composite/activity/TransactionCardLayout.vue:92), and the root is a `Flex` component in [Flex.vue:75](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/components/core/Flex.vue:75). Current Vue docs support that: fallthrough attrs are for generic forwarding, while `inheritAttrs: false` is for rerouting attrs to a non-root target, and `null`/`undefined` remove attributes. Sources: https://vuejs.org/guide/components/attrs and https://v3-migration.vuejs.org/breaking-changes/attribute-coercion.html.

I agree with `"proving"` over `"simulating"`. It is stronger because it proves the wallet got through build/estimate/simulate, and it is also less racy with an exact selector because `proving` is the long-lived slow stage in the current failure mode, between [service.ts:512](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/wallet/services/execution/service.ts:512) and [service.ts:519](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/wallet/services/execution/service.ts:519). If upstream later accelerates all kernel proofs, revisit that helper and consider an “at least proving” check.

For §7, a cheap automation defense is feasible. I would not add a full AST rule here, but a small CI guard that forbids `waitForJournalStage(..., "pending"|"simulating")` in the `tx-sendTx-*` popup-shape files, and forbids new `waitForPgResult(..., "sendTx", ...)` in the allowlisted restructure targets, is realistic. An even simpler design defense is to expose `waitForSendTxProvingStage()` instead of a generic stringly helper for these tests.
