Verdict: Reject

## Critical (must fix before impl starts)
- Incoming-receive discovery has no passive trigger — `packages/extension/src/wallet/services/token-balance/service.ts:70`, `packages/extension/src/wallet/services/token-balance/balance-job-queue.ts:62`, `packages/extension/src/utils/core.ts:109` — the existing “ticker” only drains an explicit queue; it does not poll balances on its own. A transfer received from another device/account will not be discovered unless something else enqueues a refresh. Add a real enqueue source for watched balances/accounts first, then hang incoming-note discovery off completed refreshes.
- The planned incoming-note key/order model does not match the APIs you actually have — `packages/aztec-runtime/src/pxe/schemas.ts:11`, `packages/extension/src/wallet/services/note/spec.ts:3`, `packages/extension/src/wallet/services/note/service.ts:144`, `packages/aztec-runtime/src/pxe/spec.ts:50` — raw `NoteDao` already has unique/order fields (`noteHash`, `siloedNullifier`, `noteNonce`, `l2BlockNumber`, `txIndexInBlock`, `noteIndexInTx`), but `NoteService` strips them, and PXE does not expose `getTxReceipt`. Your proposed repo key `(networkId, accountAddress, contract, txHash, storageSlot)` can collide, and your planned receipt/timestamp lookup is based on a nonexistent API. Extend `NoteService` (or add a raw-note method) and key incoming rows by `siloedNullifier` or `noteHash`; order by the note’s block/index metadata instead of inventing a receipt fetch.
- The onboarding insertion plan is structurally wrong, not just numerically incomplete — `packages/extension/src/onboarding/components/StepIndicator.vue:3`, `packages/extension/src/onboarding/pages/learn.vue:26` — `StepIndicator` is a hard-coded 4-step component, welcome intentionally has no indicator, and `learn.vue` uses one handler for both Continue and Skip. “Just bump `:current` props” is false. Redesign `StepIndicator` itself, keep welcome indicator-free, and split `learn` into separate `continue -> /onboarding/fees` and `skip -> /onboarding/accelerator` flows unless you intentionally redefine what “Skip intro” means.

If you want one canonical rule, route that extractor through the same helper or explicitly accept fallback drift.
- The “known tokens only” pollution mitigation is softer than the plan claims — `packages/extension/src/wallet/services/dapp-interaction/service.ts:425`, `packages/wallet-bridge/src/dispatcher.ts:443`, `packages/extension/src/popup/windows/execute/OperationCard.vue:206`, `packages/extension/src/popup/windows/execute/index.vue:325` — `registerToken` is always popup-confirmed and shows metadata/address, but approval still adds the token profile-wide for that chain. Rewrite the threat model accordingly; if you want stricter protection, require a stronger trust bit than “user once approved a dapp token import”.
- The route/file plan has wrong paths — `packages/extension/src/popup/pages/tx/[id].vue:1`, `packages/extension/src/popup/pages/tokens/[id].vue:1` — the new journal page should follow the existing file-routed convention (`pages/journal/[id].vue`), and the token detail page is `tokens/[id].vue`, not `token/[id].vue`. Fix the plan now or the implementation/test file list will drift immediately.
- The hidden sixth open question is the real incoming-row discovery/order contract — same refs as the first two criticals. Right now the plan has five named open questions, but the missing one is bigger than all five: “what exact background signal discovers external receives, and what exact note identity/order fields back the repository?”

## Medium
- The self-mint race story is overstated, though the defensive dedupe is valid — `packages/extension/src/wallet/services/execution/service.ts:1148`, `packages/extension/src/wallet/services/execution/service.ts:1153`, `packages/extension/src/wallet/services/operation-journal/spec.ts:165` — `submitting.txHash` exists and is written before `addTransaction`, so the “neither source has the hash” window is narrower than the plan says. Keep the journal-txHash dedupe, but test the real edge: an unrelated pre-queued balance refresh observing the note before local status reconciliation.
- “Scan only when private balance increases” is not correctness-safe even if you add polling — same token-balance refs as above. Netting a receive against a spend in the same refresh window will miss a genuine incoming note. Scan on every completed watched-token refresh and dedupe at the note-record level.
- Raw journal error gating needs to include more than `message` — `packages/extension/src/popup/pages/tx/[id].vue:127`, `packages/wallet-core/src/jobs/error.ts:37` — the proposed `developerMode || debugMode` gate matches the tx page pattern, but `normalizedRaw` can include serialized stacks and internal strings. Default to `error.kind`/friendly subtitle only; gate both `message` and any raw debug blob.
- Cleanup is underplanned for the new repo — follow the existing chain-purge/profile-delete patterns rather than just `clearProfile`. Otherwise you will keep orphaned incoming rows after chain removal.

That makes this a summary-surface concern, not a consent-surface break. If you care, harden the filter with more context than bare method strings.
