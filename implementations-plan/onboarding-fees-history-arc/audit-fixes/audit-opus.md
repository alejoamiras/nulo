# Adversarial pre-implementation audit — audit-fixes plan v1

Reviewer: opus (subagent, this session)
Plan reviewed: [`plan.md`](./plan.md)
Date: 2026-06-03
Posture: read-only investigation of the plan + cited code sites; no edits to plan or source.

Verdict: **Approve-with-changes**

Plan accurately diagnoses every critical/high from the three parallel codex audits (modulo the FJWC deferral the user explicitly accepted), maps each finding to a concrete code site, and proposes fixes that actually close the loop. The scope discipline (9 commits, risk-ascending, all squash into the same arc PR) is right and the security threat model is reasonable. However, there are concrete defects: an incomplete `JobError.kind` whitelist (P2 will silently route a real reaper-emitted kind to "Error"), a queue design that still depends on the broken `replayPendingPrompts` shape (P7 keeps the underlying lossy emitter as the source of truth and lets the popup-side queue drift from it), a missed sanitize site in the home widget's awaiting card, and a `hydrateSchedulers()` choice in P5 that's correct but wasteful enough to be worth calling out.

I'd block on the items below labeled Critical and High before approval, but they're all bounded edits to the plan text (~1-2 hours of plan revision). The arc structure itself is solid.

## Critical (must fix before approval)

- **P2 whitelist is missing `stuck_queued`** — `packages/extension/src/utils/journal-state.ts` whitelist in the plan (plan.md line 80) lists 11 kinds. The reaper at `packages/extension/src/wallet/services/operation-journal/reaper.ts:192` emits a 12th: `"stuck_queued"` for queued records that exceed their grace window without ever progressing. Tested at `packages/extension/src/wallet/services/operation-journal/reaper.test.ts:102` and `:136`. With the plan as written, a real production reaper event surfaces as "Error" (generic fallback) on the journal detail page while leaking through telemetry. Fix the plan: add `"stuck_queued"` to the whitelist mapping (probably grouped with the other interrupted-flavored kinds like `stuck_proving` — same root cause: SW lifecycle aborted the FSM mid-stage). Either the plan needs to enumerate kinds exhaustively or the whitelist construction needs to be backed by the reaper.ts + execution/service.ts grep — picking and counting from documentation that's drifted is exactly the bug class this fix is meant to close.

- **P1 still misses one home-widget sanitize site** — `RecentActivityView.vue:344` (`cardOriginLabelFor`) is called out in the plan, but `RecentActivityView.vue:157-160` (`executingOriginLabel`, used by the orphan-fallback awaiting card at lines 716-724 + 770-777) returns `executingTask.value.origin?.name ?? null` with NO sanitization. The plan acknowledges this at line 66 ("Same for `executingOriginLabel`") and calls out wrapping in `sanitizeJournalSubtitle`, but the entire concept of a dApp's `origin.name` being a separate trust surface from `op.subtitle` deserves more explicit treatment. Per the codex spawn-2-f3 audit (line 4: "raw `executingTask.origin.name` for awaiting cards"), this is the same threat as the journal subtitle — a dApp registering itself with a URL-shaped `origin.name` and the wallet rendering it bare under "Cancel"/"Processing" decorations. The fix is one wrap call, but the plan should explicitly enumerate ALL dApp-controlled-label surfaces and check them off one by one in P1's commit body, not bury the awaiting card path inline. Also relevant: `TransactionAwaitingCard.vue:74` (`transferTypeLabel || originLabel`) is the actual render site and would benefit from defense-in-depth wrap — see Medium below.

- **P7 queue still bound to lossy `replayPendingPrompts` shape** — Plan §P7 leaves `replayPendingPrompts` in `service.ts:445` as-is and adds a popup-side queue. But the popup-side queue receives events from `onIncomingTransferPending`, which `replayPendingPrompts` emits one-at-a-time as it iterates the pending trust records (`service.ts:457-475`). The plan's queue catches them all via the push handler at PopupManager.vue:47 — fine — but it then de-duplicates against itself, NOT against `incomingTrust.contract` already-open. The result: if `replayPendingPrompts` fires while a trust popup is open (the existing watch at PopupManager.vue:96 calls it on every popup-close transition), the queue can grow indefinitely with stale references. The plan needs either (a) a dedup key (`contract` is the natural one) added to the queue push at PopupManager.vue:47, or (b) `replayPendingPrompts` should accept a callback / yield to popup-side enumeration instead of emitting events. The first is the smaller change and matches the existing `incoming_trust` open-coalesce guard at PopupManager.vue:53. The plan must spell it out — leaving "popup-side dedup" as a vague claim risks shipping a queue that still loses payloads under back-pressure.

## High

- **P2 whitelist source-of-truth is wrong layer** — The plan proposes the whitelist in `packages/extension/src/utils/journal-state.ts` (line 80). But `JobError.kind` is typed `string` at `packages/wallet-core/src/jobs/types.ts:73-82`, AND the producers are scattered across `packages/extension/src/wallet/services/execution/service.ts:568`/`:1172`/`:1820`/`:1987` (calling `normalizeError(err, "transfer" | "dapp_execute")`), `packages/extension/src/wallet/services/operation-journal/reaper.ts:184-194` (emitting `sw_restart_post_prove`/`stuck_proving`/`stale_on_resume`/`stuck_queued`), `packages/extension/src/wallet/services/wallet-sdk/background.ts:571` (`popup_bound`), and `packages/wallet-core/src/jobs/error.ts:37` (`unknown` default). The proper fix is to make `JobError.kind` a typed union at the wallet-core level — that would convert the missing-kind-from-whitelist into a TypeScript error rather than a silent "Error" fallback. The plan's humanize-at-render-site approach is pragmatic but it's a band-aid; should at least call out the proper fix as deferred follow-up. Alternative: enumerate kinds in `journal-state.ts` exhaustively + add a `// AUDIT` cross-ref pinning the producers, AND make the unit test assert the producer-set matches the whitelist via a grep-driven manifest.

- **P3 `await loadIncomingTransfers()` race risk** — The plan adds two awaits to `onMounted` at line 637-668 of RecentActivityView.vue (per plan §P3 at line 93): `await incomingTransferService.connect()` + `await loadIncomingTransfers()`. The existing onMounted body (lines 637-668 as currently shipped) is already doing 3 sequential awaits (`loadTokens`, `configService.connect`, `taskService.getTasks`) PLUS the journal load at line 660. The plan says to position "after `await configService.connect()`, before the journal/task replay". That's correct ordering for initial-load consistency, but it adds two more awaits to the popup's first-paint critical path. The journal load is already the biggest hitch (full journal getOperations). Recommended: load incomingTransfers in parallel with the journal load via `Promise.all([...])` instead of serializing all four. The plan should either pin the ordering rationale (sequential is intentional because of some race) or restructure to parallel. Otherwise this is a noticeable first-paint regression on the home widget for users with many tokens.

- **P5 `hydrateSchedulers()` on every `onAccountAdded` is overkill** — Plan §P5 line 118 proposes `accountService.onAccountAdded → hydrateSchedulers()`. Looking at the implementation at `service.ts:242-264`, `hydrateSchedulers` calls `clearInterval` on every existing scheduler, wipes the maps, then iterates ALL networks × ALL accounts × all tokens and re-spins each scheduler from scratch. Single-account-add fires this entire teardown for every other account/network on the profile. For a profile with 5 accounts × 3 networks × 10 tokens, that's 15 schedulers torn down and re-built every time the user clicks "+ New Account". The right shape: an additive `startScheduler(profileId, network.id, account.address)` per existing token list (mirroring the `onTokenAdded` handler at `service.ts:282-301`), plus a more surgical `onAccountDeleted` that only tears down the deleted account's schedulers. The plan's stated rationale "trade-offs" at the bottom of §P5 is a hand-wave — write down which one was picked and why. If `hydrateSchedulers` is chosen for simplicity, the plan should justify that the rebuild cost is bounded (no PXE calls inside, schedulers don't trigger immediate polls except for newly-registered keys). The cost is real though: every scheduler `startScheduler` triggers an immediate `poll()` per `service.ts:277-279`, so even an "idempotent re-build" causes a full PXE scan storm whenever any account is added/deleted.

- **P5 missing AccountService deps declaration cross-check** — The plan adds subscriptions to `accountService.onAccountAdded` / `onAccountDeleted` but doesn't verify that the subscription path is initialized before the events would fire. `IncomingTransferService.init` at `service.ts:110-140` already does `services.get(AccountService.name)` — that's fine — but `onAccountAdded` event subscriptions happen AFTER the init body completes. If `AccountService.init` is faster than `IncomingTransferService.init` AND an account is somehow created in between (unlikely but possible during the wallet-bootstrap restore flow), the subscription would miss the event. Plan should note: subscribe in `init` BEFORE the `await hydrateSchedulers()` call, OR rely on `hydrateSchedulers` to pick up any account created in the bootstrap window. The simplest fix is to register the listeners synchronously near the top of `init` (alongside `onTokenAdded.add` etc.) — the plan should spell out the registration ordering.

- **P4 "toggle off → on re-emit" subscription is correctly bundled but needs failure-mode spec** — Plan §3 line 205-206 says "when toggle flips back ON, `replayPendingPrompts` should run. Add a config-change subscription in `IncomingTransferService`". Yes, this belongs in P4 — but the plan doesn't pin WHICH `(profileId, networkId, accountAddress)` triple to replay for. There's no implicit "active profile / network / account" in `IncomingTransferService`; the existing `onActiveProfileChanged` handler at `service.ts:142-144` just hydrates schedulers. The new config-toggle handler would need access to the same triple — either by re-deriving from `profileService.getActiveProfile()` + `networkService.getActiveNetwork()` + `accountService.getActiveAccount()` (none of which the service currently calls), OR by emitting a service event that the POPUP-side subscriber re-fires `replayPendingPrompts` against the popup's appStore values. The latter is the more honest design (service is per-profile, popup knows the active triple). Plan should spell this out — as written, "add a config-change subscription" is ambiguous.

- **P9 e2e two new awaits add to a 2-minute test budget** — Plan §P9 line 178-180 adds two new assertions to the existing onboarding e2e. Each new e2e assertion includes `clickByTestId` (puppeteer evaluation) + `waitForHash(... 10_000)`. Looking at the existing test at `onboarding-tab.test.ts:24-106`, the happy-path walk is already structured as a single test that walks the full chain. Adding skip-route assertions either (a) requires the test to navigate back from `/accelerator` to `/learn`, which would need a manual hash-reset since there's no back-button affordance, OR (b) requires a separate test that opens onboarding to `/learn` (via direct hash navigation, mirroring the pattern at line 132-135). Plan should pick which approach and spec it. If (a), it complicates the existing happy-path. If (b), it's two new test functions with their own fixture setup overhead. Lean toward (b).

## Medium

- **Defense-in-depth at the card level (P1)** — Plan §8 open question 2 says "trust-the-callers (sanitize at the builder)". I'd flip this: ALSO wrap the `<span>{{ subtitle }}</span>` / `<span>{{ originLabel }}</span>` renders inside `TransactionTerminalCard.vue` and `TransactionAwaitingCard.vue` with `sanitizeJournalSubtitle`. The cost is one helper call per render; the benefit is that any future caller path that bypasses the builder (Storybook stories, ad-hoc demo pages, future component reuse) gets the defense for free. The plan rejects this as "belt-and-suspenders" but the bracket-the-URL helper is cheap and the same threat-model logic that justified sanitize-at-builder justifies sanitize-at-card.

- **P6 contract verification UX — focus management / a11y** — Plan §P6 line 130-138 proposes "two-element display: trimmed + full-address-monospace (toggle on click) + copy button". Missing from the spec:
  - Keyboard activation. The trimmed→full toggle should be a `<button>`, not a `<span>` with `@click` — keyboard users + screen readers need it to be reachable via Tab + activatable via Enter/Space. Same for the copy button.
  - Focus restoration after the toast fires. Existing pattern (`navigator.clipboard.writeText` + `openToast`) doesn't move focus by itself, but the popup is modal; the `confirm` action moves focus back to the page. Plan should note that the copy button should retain focus until the popup closes.
  - The expanded full address should be `aria-live="polite"` or paired with a visually-hidden label so the screen reader announces "Address copied to clipboard" rather than just toast text. Existing pattern in `EditFpcPopup.vue:147` + `TokenMetadataPopup.vue:40` uses the toast text as the announce surface — match that convention if it's a deliberate choice.
  - `data-testid="incoming-trust-contract-full"` and `incoming-trust-contract-copy` proposed in the plan — good. Add `incoming-trust-contract-toggle` if the trimmed→full transition is a separate affordance (which it should be, per the spec).

- **P7 service-side queue vs popup-side queue** — The plan's queue lives in `PopupManager.vue` (line 145-148 of plan). Service-side has merit: a queue inside `IncomingTransferService` would be authoritative across popup reopens (each popup mount could pull the current queue state rather than depending on `onConnected` + `replayPendingPrompts` to re-pump the pending set). But: the service-side queue would also need to track which contracts the popup has already opened-and-closed (to avoid re-prompting after a Reject), and that state is already encoded in the `IncomingTrustState` machine. So the popup-side queue is the right call. The plan should explicitly call this out — right now it reads like "queue here because that's where the existing watcher is", which is incidental. The real reason: trust state is the authoritative gate; the queue is just UI ordering, which belongs at the popup.

- **P8 test backfill scope (30-50 cases) is reasonable but uneven** — Plan §P8 line 159-168 enumerates: dedupe (3 sources), late-delete, trust transitions (4: unknown→pending, setTrustAllow ON/OFF, setTrustReject), visibility gating (4: ON × emit-Added, OFF × emit-Added, ON × emit-Pending, OFF × emit-Pending), cleanup wiring (clearProfile, clearChain). That's ~14 cases minimum for the service + 4-6 for the repository = ~20 cases. To get to 30-50, the plan needs more scenarios (e.g. concurrent scans on the same scheduler, slow-poll reentrancy via `this.polling`, order-stability of `replayPendingPrompts`, the symmetric "toggle off→on" re-emit path from P4). Without those, the 30-50 estimate is fiction. Either down-spec to ~20-25 cases or list the additional scenarios.

- **P3 has no component test** — Plan §P3 line 97 says "Component test was deferred under L4 minimums for the parent arc; backfill the same way (skip; e2e + integration coverage)." OK for the minimum, but P3 is fixing a Critical (F4: home widget incoming display non-functional). A real component test at this layer would catch a future regression — the original bug was "registers listeners but never connects". A test that mounts RecentActivityView with a mock IncomingTransferServiceClient and asserts `connect()` + `getIncomingTransfers()` were called would have caught the original miss. The plan defers this to e2e; e2e is heavier + slower + flakier. Recommended: add a minimal RecentActivityView.test.ts pin for the wiring (no need for the full 10+ cases — just one "calls connect + getIncomingTransfers on mount").

- **P1 `mailto:`/`tel:` regex widening — semantic shift** — Current regex `/^[a-z][a-z0-9+.\-]*:\/\//i` is "looks like an http-style URL". Widened to `/^[a-z][a-z0-9+.\-]*:/i`, it brackets `mailto:abc@example.com` (good — it's a clickable scheme in some contexts) but ALSO brackets benign strings like `node:warning`, `Aztec: a privacy network`, or any English text with a colon in the first word. Test pin existing: `journal-state.test.ts:316` was updated to assert `mailto:abc@example.com → "mailto:abc@example.com"` (unchanged), but the widened regex would change it to `[mailto:abc@example.com]`. Plan acknowledges this implicitly via "extend with `mailto:`/`tel:`/`javascript:`/`data:`/`http:evil`" at line 71 — but the existing test at line 316 needs to FLIP. False positives on plain English text with colons (e.g. dApp name like "Aztec: a privacy network") would surface as bracketed in the UI. The threat-model argument says false-positives-on-text are acceptable because the dApp shouldn't write English in `subtitle`, but the plan should explicitly state the false-positive trade-off rather than treating widening as pure win.

- **`replayPendingPrompts` design issue (separate bug)** — `service.ts:457-475` iterates `pending` and emits one event per contract. For a profile with N pending contracts, that's N emits to the event handler — fine, but it also means `PopupManager.onIncomingTransferPending` fires N times, queues N items, opens the popup for the first, and the watcher at PopupManager.vue:96-107 re-calls `replayPendingPrompts` on close — which then re-emits the same N events MINUS the just-resolved one. This is O(N²) in event volume for N pending contracts. The plan's popup-side queue inherits this. Recommended: `replayPendingPrompts` should be an enumeration (returns the array) rather than an emit-storm. The popup-side controller can then drain locally without the service re-emitting. Plan should propose this refactor in P7 or split into a new phase.

- **`incomingTransferService.onConnected.add(loadIncomingTransfers)` at line 213 fires immediately if already connected — verify** — Per `packages/extension-messaging/src/background/client.ts:48-67`, `connect()` only fires `onConnected.invoke()` once after the port connects. If P3's explicit `connect()` happens BEFORE the listener is registered (it's not in the current code — the `.add` happens at module-eval time at line 213), the listener could miss. After P3, the order is: register listeners at top of `<script setup>` (lines 210-213), then `onMounted → connect()`. That works because `connect()` won't fire `onConnected.invoke()` until the connect resolves, which is async. But the plan should pin this in a test: "register all listeners synchronously at module-eval, then connect in onMounted". This is a class of bug across multiple files (PopupManager, RecentActivityView, activity.vue all do the same pattern); a comment + test would help.
