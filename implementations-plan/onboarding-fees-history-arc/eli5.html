Onboarding + Fees + History ELI5

Four small but visible wallet improvements, shipping as one PR with four commits. The idea: round out the activity feed, fix one annoying label bug, and give new users an honest answer to "how do fees work here?"

The four pieces, in plain English

1. Don't call it "Sponsored unconditionally" while it's still proving

Phase 1 — bug fix

When you tap a button in a dApp, the wallet bundles the actual thing you wanted (say, "drip me some test tokens") with a fee-payment call ("the faucet pays my fee"). Those are two separate operations stitched into one transaction.

While the wallet generates the cryptographic proof, the card says "Sponsored unconditionally". Once the transaction lands on-chain, it flips to "Drip to private" — which is what you actually meant all along.

The fix: there's a list of "this is fee-payment plumbing, not what the user asked for" methods in the codebase. The settled-card label already skips them. We're routing the in-flight label through the same filter so both surfaces agree.

Five places in the code build the in-flight label today. After the fix, they all share one helper. One source of truth.

2. Tell new users what "fee juice" even is

Phase 2 — onboarding

Aztec has a native asset called fee juice. Like gas on Ethereum — every transaction needs some. There's also a private version: hold your fee juice privately and the fees you pay stay private too.

The wallet supports a third option: apps can pay your fees for you, or accept other tokens as fee payment. That's worth saying once, upfront, so the fee-settings panel doesn't feel like alien tech the first time you see it.

We're expanding the onboarding step indicator from 4 cells to 5 — adding a new Fees cell between Aztec and Speed. Three short cards in the same brutalist style the wallet already uses. Flow: setup → meet aztec → fees (new) → accelerator → done.

3. Let people open canceled / waiting transactions

Phase 3 — clickable history

Right now: if a transaction succeeds and lands on-chain, you can tap its history card and see the full details. If you cancelled the transaction, or the proof generation crashed mid-flight, the card just sits there — you can't tap it.

We're building a small "journal detail" page that opens when you tap one of those. It shows what stage the transaction reached, the dApp that asked for it (if any), the amount you were sending (if it's a transfer), and a one-line reason for the terminal state ("Cancelled", "Couldn't generate proof", "Transaction was interrupted"). Raw error text stays hidden unless you have developer mode on.

While we're there, we polish the page for transactions that are already openable but haven't mined yet: clearer banner, hide the explorer link until the tx actually exists on-chain, show the estimated fee with a "this might change" note.

4. Show incoming transfers in history

Phase 4 — incoming receives

Today the wallet's history only shows things you did. If someone sends you tokens, your balance goes up, but nothing shows up in your activity feed. That's wrong.

We're adding a new background service that watches for notes (Aztec's private-token unit) arriving on your account from token contracts you've added. Each new arrival becomes a "Received" row in your history, with the token symbol and amount.

The tricky part is telling apart "someone sent me something" from "I sent something and got a change note back". We compare every newly-arrived note's transaction hash against your own outgoing transactions. If it matches, it's your own activity already — no duplicate row.

Scope is locked to fungible tokens you've already added to your wallet. NFTs and random unknown-contract notes are out of scope for this PR.

Two extra defenses come with it. The first note you ever receive from a new token contract requires a one-shot confirmation popup (shows the contract address — guards against fake-USDC scams). And there's a settings toggle to hide incoming transfers entirely — useful if you run the same wallet seed on multiple devices and don't want each device tagging the other's outgoing as “received.”

Why one PR, not four

Three of the four items touch the same files (the helper that picks a transaction's display name, the history list, the transaction-detail page). Splitting into separate PRs would cause three merge conflicts and force you to track three sets of CI runs. One PR keeps the test coverage in lockstep.

Commits land in risk-ascending order — easiest to revert first, biggest service last — so a partial revert is still safe.

Security questions we asked ourselves

  • Could a malicious dApp hide a real call by naming it "sponsor_unconditionally"? The card title would skip it, but the consent popup shows the full call list. The user has already approved the payload.
  • Could a fake token mint to you and look real in your history? Only tokens you've explicitly added show up. Adding a token still requires a popup confirmation.
  • Could the new error-detail page leak internal state? Raw error messages are hidden unless developer mode is on. Same gate the existing debug panel uses.
  • What if our PXE crashes mid-sync? The service catches and logs. Existing records stay; nothing fake gets inserted.

Open questions (post-audit)

  • "Received from <contract>" label — resolved: blank. The icon + symbol identifies the row enough, and a contract address can read like a sender address.
  • Pending-tx banner placement — resolved: cut the banner. Reuse the existing pending status icon plus a "Pending settlement" subtitle on the fee row. Consistent across surfaces.
  • Should incoming receives count toward per-token "total transferred" stats? Plan defers — not in this arc.
  • Cross-device same-seed limitation: documented and backed by a settings toggle ("Show incoming transfers", default on). User can hide entirely if they run the same seed on multiple devices.
  • New (audit-flagged): Discovery loop architecture. The existing balance-refresh ticker only drains an explicit queue — it doesn't poll. We need a real passive trigger. Plan defaults to a NoteService watch loop; alternatives (PXE block-sync hook; TokenBalanceService extension) tracked for the F2 impl phase.
  • New: First-receive friction copy + UX placement. Plan defaults to a popup card mirroring token-import.
  • New: Settings toggle wording — "Show incoming transfers" vs. alternatives.
