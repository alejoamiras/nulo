Light Theme Fix — wallet repair + faucet toggle

The wallet's light theme is completely broken — dark cards on light backgrounds, invisible borders, unreadable text — so people who installed it on a light system assumed the whole product was broken. The faucet has no light/dark switch at all. The good news: the theming machinery already exists and works; it was just never finished. We finish it, properly, and prove we didn't break the (working) dark theme.

Why this tier was chosen

Picked deep. The rubric on its own says mid (only one high-risk dimension: blast radius — the fix touches a shared design foundation used by 555 places across two apps, so a wrong colour value would quietly degrade the working dark theme everywhere). It was escalated to deep because it's (1) cross-cutting across three packages, (2) production-visible — real users saw it broken, and (3) it needs a genuine design review (we're inventing a light colour palette). Three independent plans were drafted (main + codex + a second Opus architect), cross-checked against each other and the code, then double-audited.

What was actually wrong (plain version)

A theme is just a set of named colours. The dark set is complete. The light set was missing 8 of its core colours, so anything using them silently fell back to the dark colour — black cards on a white page. On top of that, ~37 places hardcoded dark colours directly (ignoring the theme system), plus a few "ghost" colour names that were never defined and quietly resolved to black. Fixing the 8 missing colours is one small edit that repairs the majority; the rest is careful clean-up.

The colour decision you'll make

Two directions for the light palette (you sign off after seeing them side-by-side in Storybook):

DirectionFeelAccent

The accent can't be near-black "ink": the same accent colour also paints links, the active tab, and toggle "on" states (43 places), so a near-black accent would make links look like plain text and an ON security-toggle look OFF — dangerous in a wallet. (An adversarial review caught this.) So the accent stays a saturated colour; the only real choice is the hue — warm amber vs cool blue — which you pick from the Storybook preview. A keeps the warm brand identity.

Phases

Phase 0 — Build the guardrails first

Before fixing anything, write two automated tests: (1) a colour-contrast checker over a hand-picked list of text/background colour pairs that fails on today's broken light theme (proving it catches the bug class that shipped), and (2) a "ghost colour" guard that fails if any component references a colour name that was never defined. Also give Storybook a real light/dark switch. The checker is honestly a curated list of pairs, not a magic full-page renderer — that's a deliberate, documented limit.

Proves itself by: contrast checker RED on light / GREEN on dark; ghost-colour guard flags the 4 known undefined names; Storybook toggles theme for real.

Phase 1 — Replace the hardcoded colours + kill the flash

Swap every hardcoded dark colour for the right theme variable (palette-agnostic — correct no matter which direction you pick — so it runs before the palette is finalised, using a CSS trick already in the repo, color-mix; no new colours, no risk to dark mode). Turn on a "ghost colour" guard so an undefined colour name can't sneak back in. And kill the "flash of dark" with a tiny script that sets the theme before the page paints — fully, for both apps. (Reviews proved two earlier attempts insufficient before landing on this one.)

Proves itself by: dark mode unchanged (mapping table + the contrast checker's dark checks stay green); ghost-colour guard green after the fix; no flash when the popup or faucet opens in light; lint, types, component tests green.

Phase 2 — Drop in the signed-off palette + your sign-off

Add the 8 missing light colours (your chosen direction) and fix the broken border colour, then show you the full Storybook matrix — both directions, side by side — for approval. The contrast checker flips to GREEN on light here.

Proves itself by: contrast test GREEN in both themes; design-system tests (incl. the file-hash pin) green; your palette sign-off.

Phase 3 — Faucet: add the Light/Dark/System switch

Add the same switch the wallet has (remembered across visits, follows your OS by default), set the theme before the page paints (no flash), and fix the faucet's own ghost colours.

Proves itself by: faucet unit + component tests green; manual check of all three tabs in light/dark/system with no flash on reload.

Phase 4 — Full validation

Smoke-test the security-sensitive screens in light (send amounts, dApp-connect, passkey dialog, addresses) and confirm interactive elements still look interactive (links read as links, ON toggles read as on). Run the whole test suite — explicitly including the contrast checker, because the wallet's normal audit command doesn't run the design-package tests on its own (a review caught that gap).

Proves itself by: audit:vue and the design contrast gate green; Storybook light matrix clean; smoke e2e green; manual security + affordance review.

Phase 5 — Clean up

Delete the dead duplicate stylesheets so there's one source of truth, and run the final full gate.

Proves itself by: audit:vue + design tests + smoke e2e green; final manual smoke.

Human context

A "design token" is a named colour (like --nulo-accent) that components reference instead of a raw colour. Swap the token's value and everything updates. The whole bug is that the light theme didn't give values to 8 important tokens. "WCAG-AA" is the accessibility standard for text being readable enough (a 4.5:1 contrast ratio) — we enforce it automatically so "readable" isn't a matter of opinion. "FOUC" is the brief flash of the wrong theme before the right one loads; we kill it.
