Key Model v2

One coordinated, pre-launch change to how Nulo creates keys and what it lets you export — so "recovery phrase" and "private key" finally mean what every wallet user expects them to mean.

Plan lives at implementations-plan/key-model-v2/plan.md · worktree key-model-v2

The problem, in one paragraph

Today the Settings → Backup screen offers a "Seed Phrase" and a "Secret Key" — but they are the same secret in two costumes, and neither changes when you switch accounts. On Ethereum, "private key" means one account and "seed phrase" means everything. Nulo's words also aren't real BIP-39: they're a raw re-encoding of the master secret with the standard key-stretching step skipped, which quietly rejects ~82% of phrases generated elsewhere and closes the door on ever adding an optional passphrase. Since nothing has shipped to real users yet, we can fix the model once, now, instead of living with it forever.

What changes for you

Backup gets simple: one Recovery Phrase (24 words — the real, standard kind) and one Full Backup file. The confusing base64 "Secret Key" export and its import disappear. Accounts get portable: each account gains its own Export / Import — a small, checksummed file (password-protected by default) that moves exactly one account between installs, which is what "export private key" should have meant all along. Under the hood: key derivation gets dedicated Nulo domain tags, chain separation keyed to the L1 chain id (so a rollup upgrade can never silently change your addresses), and strict validation on every import. Every derived address changes — the deliberate, one-time cost of doing this before launch.

Why this tier

Scored against the blueprint rubric: security sensitivity is the one HIGH dimension (this is key generation). Blast radius, irreversibility, and migration cost are all low because we're pre-production — no users, no data to migrate. That's one HIGH → mid: one plan, a competing alternative, and three independent adversarial audits, with the audit muscle deliberately over-weighted on the crypto per your instruction.

The phases

PHASE 1

New crypto primitives

The standard BIP-39 step, the Nulo domain tags, and the new derivation constants — each pinned by known-answer tests, including the official BIP-39 test vectors.

Proves itself by: lint + typecheck + the full unit suite, with every new vector committed.

PHASE 2

Chain identity done right

The L1 chain id gets stored where derivation needs it, and the one true seed formula becomes a single shared function — fixing a hidden duplicate that would otherwise have bricked profiles at unlock.

Proves itself by: unit + integration suites, including a new test that exercises the real (not mocked) integrity check.

PHASE 3

Profiles built on entropy

New profiles start from real entropy; the words re-display from storage; passwords, backups, and restores all verify that the words and the working key still agree — so a tampered backup can't hand you a lying recovery phrase.

Proves itself by: unit + integration suites, including create → export words → re-import → same address, plus tamper tests.

PHASE 4

The product cuts

The Secret Key page and plain-key import are deleted, copy becomes "Recovery Phrase", and every test that leaned on the old surfaces is reworked.

Proves itself by: the full pre-PR gate + smoke browser tests on the reworked flows.

PHASE 5

Export / Import Account

The per-account file format (encrypted by default), the import checks that refuse anything tampered or foreign, and the UI. Imported accounts are clearly badged: your recovery phrase does not cover them.

Proves itself by: the full pre-PR gate + smoke browser tests: round-trip, tamper rejection, duplicate rejection.

PHASE 6

Prove it on a live network

The full network suite, including the frozen-account canary with real proving and a new leg: import an exported account into a fresh install and send an actual transaction from it.

Proves itself by: the network e2e suite green, then the fast gates once more.

What the auditors said

Three independent adversarial reviews. Codex round 1: reject — four serious findings (a hidden formula duplicate, a password-change gap, missing service-side authorization, storage lifecycle holes), every one now folded into the plan. Independent Claude audit: conditional approve — seven conditions, including two more hidden breakage points and an honest restatement of the entropy math; all adopted. Final fresh-context Codex pass: reject on the revised plan too — four sharper findings against the fixes themselves (a recovery-degradation path through the always-on session, a backup binding that broke across restores, a poisoning window before first account creation, and an honest limit of what a checksum can prove); all adopted. Its re-verdict on the result: conditional approve, with three final conditions — also all adopted. Nothing is outstanding. The full transcripts are committed next to the plan.

Open questions — your call

  • A1 — Delete the "Encrypted Key" export/import too? It's a third mechanism (a raw ciphertext blob), redundant with the Full Backup. Both auditors and the plan say yes, cut it.
  • A2 — Rewrite the frozen "regime" record in place? The address-freeze rules say append-only, but nothing has ever shipped under the current entry. Recommendation: rewrite in place, one reviewed commit — and you're ratifying that no old build, backup, or exported file needs to keep working.
  • A3 — Same keys on two rollups that share an L1? Deliberate consequence of keying derivation to the L1 chain id (it's what makes upgrades safe). Recommendation: yes, accept it — it matches how every EVM wallet behaves.
  • A4 — If an imported account's stored key is tampered with, how loud is the alarm? Recommendation: quarantine just that account (disable it, show why) rather than locking the whole profile the way we do for derived accounts.
