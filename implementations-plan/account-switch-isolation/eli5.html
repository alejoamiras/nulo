Keeping your accounts from leaking into each other

Account-switch cross-account isolation · /blueprint deep · item 3 / PR-D

In one paragraph: The wallet lets you keep several accounts in one profile — often on purpose, to keep them separate. But right now, when you switch from account A to account B, the activity feed can still show A's stuff under B: A's past transactions linger, and worse, money that someone sends to A can pop up in B's feed. That's a privacy leak — a person glancing at your screen while you're "on B" could read A's balance changes, amounts, and timing. This plan fixes it so each account's feed shows only that account's activity, and proves the fix with a test that deliberately triggers the exact race and checks nothing leaks.

Why "deep" (the heaviest planning tier)

Two of the six risk dials are HIGH: it's a privacy/security bug, and it touches the core activity feed that everything reads from (broad blast radius). Two HIGH → deep. So we wrote three independent plans (me, codex, and Opus), merged them, then ran two adversarial audits that rejected the first draft and forced a much stronger v2.

What's actually broken (plain version)

  • The feed keeps its data in "current account" boxes that never get emptied or re-labelled when you switch.
  • A background poller checks all your accounts for incoming money and shouts the results to the whole UI without saying "this is only for account A" — so the UI paints it wherever you happen to be looking.
  • "Cancel" / "in-progress" markers are matched by loose clues, so account A's cancel can clear account B's in-progress card.

The approach: fix it now, harden it in stages

We do not rewrite everything at once (that's how you ship new bugs). Instead:

Phase 0 — Build the test lever test-only

A switch-controlled "pause button" for the incoming poller (only in test builds, stripped from real ones) so a test can freeze account A's poll mid-flight, switch to B, then release it and check nothing leaks.

Proves itself by: the test harness pauses a real note-scan and reports back it's held; the pause code is verified absent from a real Chrome build.

Phase 1 — Close the leak ship-now fix

Every piece of feed data now carries a full "who owns this" label (profile + network + chain + account), and the UI only accepts data whose label matches the account you're looking at — dropping anything that doesn't, rather than guessing. Received-money records are validated at the door. Switching now instantly clears the old account's view.

Proves itself by: unit + component tests for the drop-wrong-account logic, and the deterministic network test going from RED to GREEN.

Phase 1a — Give tasks a real ID design

Today an "in-progress" task has no reliable link to its journal entry, so we can't safely say which account it belongs to. We design that link properly. Until it exists, we simply hide the ambiguous "in-progress" cards (the journal already shows progress) rather than risk showing the wrong one.

Proves itself by: tests showing every task resolves to its owning account, and the ambiguous case fails safe.

Phases 2–3 — Move to per-account boxes hardening

Replace the shared "current account" boxes with one box per account. Now a late result for A physically lands in A's box and can never appear under B — the isolation is structural, not just a filter we have to remember to apply. Includes the tricky concurrency rules (ordering, deletes, tombstones) the audits demanded.

Proves itself by: a "placement" test that checks which box each record lands in with all the UI-side filters turned OFF — so a filter can't hide a routing bug.

Phase 4 — Clean up + re-audit hardening

Delete the old shared state, add guardrails that stop the bug being reintroduced, and hand the finished work to 2–3 independent codex auditors.

Proves itself by: full test + lint + typecheck + the race test green on 3 cold runs; auditors find no cross-account write.

Off-ramp: Phase 1 alone is a real, shippable privacy fix. If the deeper restructure (2–4) ever looks too risky at review, we can stop after Phase 1 — as a deliberate ship-now choice, not because guards-forever is the ideal end state.

Human context

Aztec notes are like envelopes anyone can send you — the sender controls what's inside, so we never trust any field the sender set. We only trust which account decrypted it (the wallet's own key decides that), and we scope everything on that. The audits caught us almost trusting a sender-set field; v2 forbids reading it at all.

Also: the popup and the side panel are two separate windows that don't share their "active account" — so the fix scopes each window on its own state, not one global value.
