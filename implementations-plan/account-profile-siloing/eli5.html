Blueprint · deep tier

Siloing profiles & accounts

Make the wallet's active scope — which profile, which network, which account — the one and only thing that decides what activity you see and what a transaction is allowed to sign as. So one profile's money and history can never bleed into another's, and switching feels instant.

The one-sentence version

Today, activity state is a single flat pile keyed on "whoever's active right now," and an in-flight transaction re-reads "active right now" while it works — so a background event or a mid-send switch can paint Account A's data under Account B, or even sign under the wrong profile. This arc replaces the flat pile with one labelled drawer per scope (a "slice"), makes every producer drop its record into its own drawer (never the active one), and binds a transaction to the profile that authorized it — if you switch away mid-send, it aborts cleanly instead of signing under the wrong identity.

Why "deep" and not something lighter

The blueprint rubric scores six risk dimensions. This lit up four: high blast radius (it touches the shared send path used by every transaction), high security sensitivity (it's a cross-profile privacy + signing-authority boundary), real concurrency (service-worker restarts, races between switching and sending), and a novel durable protocol. Two-or-more highs → deep. Deep means three people plan it from scratch in parallel, then two rounds of reviewers try to break the merged result.

The one that would have hurt

The first merged plan closed the "don't sign under the wrong profile" window by holding the wallet's main lock across the network send. Sounds safe. It isn't: that lock auto-releases itself after 5 minutes as a safety net, and a stuck network send can take ~4 minutes — under the ceiling with zero margin. If it ever tipped over, the lock would hand itself to a queued profile-switch while the send was still running — re-opening the exact leak it was meant to close, and corrupting the lock for the whole wallet. It would also freeze the emergency "lock wallet" button for minutes.

A fresh reviewer with no stake in the plan found this by reading the actual lock code. The fix is smaller and safer: don't hold any long lock across the network. Verify-and-dispatch the send in one atomic beat, then wait for the network outside the lock, and record the result unconditionally (a transaction that's already on-chain is a fact — you never drop it). This is why the deep tier exists.

How it works, in three moves

1 · One drawer per scope (structural isolation)

A single coordinator owns a map of slices, one per (profile, network, chain, account). The screen only ever reads the active slice. Every producer writes into the slice for the record's own scope — computed from the record, never from "active now." A foreign record therefore cannot reach your view; it's in a different drawer. Switching is just pointing at a different drawer → the last view you had reappears instantly (no clear-then-reload flicker).

2 · A durable "which-came-first" protocol (proven before it's wired)

Events, background fetches, and service-worker restarts arrive out of order. A small pure module decides, for each record, whether an update actually applies — using a per-source counter, a "committed-through" watermark, per-record tombstones (so a deleted row can't resurrect), and a monotonic lineage number (so a re-imported or reset scope can't be painted by its own ghost). It's built and property-tested in isolation first — thousands of random event orderings thrown at it — before it touches any UI.

3 · Don't let the ground move under a send (never mis-sign)

send starts→🔒 switching is blocked→ prove→send→record→🔓 switching allowed

The mis-sign danger is: you switch profiles while a transaction is being built, so it gets built under the wrong account. The simplest fix that fully closes it is to not let you switch while a send is in flight — a "finish or cancel your pending transaction first" guard. If the ground can't move, nothing can be built on the wrong ground. (Locking the wallet is always allowed; a send in flight when you lock is simply abandoned, exactly as today.)

Why this replaced a much bigger design. The first plan tried to let the switch happen and abort the send — which needed a fence, a session counter, an atomic hand-off, an orphan ledger, and a crash-recovery path. Three review rounds found ~10 serious bugs, all in that machinery, each fix spawning the next. Blocking the switch deletes all of it and covers the same hazard. This was a deliberate scope call, made because the reviews proved the fancy version wasn't worth it.
