# Codex audit — Registry removal + Stealth Mode removal + note parsing

Date: 2026-04-29
Model: gpt-5.4 with `reasoning_effort=xhigh`

## BLOCKING

- **PR 1 assumes `aztec_registerContract` already carries the artifact, but the wallet surface explicitly allows omission and resolves the artifact at runtime.** The plan treats contract registration as the mitigation for removing the HTTP registry (`implementations-plan/registry-stealth-notes/plan-v1.md:127-129,210-212`), but the bridge type makes `artifact` optional (`packages/wallet-bridge/src/operation.ts:152-157`), the dispatcher preserves that optionality (`packages/wallet-bridge/src/dispatcher.ts:644-650`), the approval UI also treats it as optional (`packages/extension/src/popup/windows/execute/index.vue:763-771`), and execution falls back to `getContractArtifact()` when no artifact is supplied (`packages/extension/src/wallet/services/execution/service.ts:893-905`). Dropping the registry is still a valid direction, but the plan must first choose a replacement contract. Change shape: either require `artifact` on `aztec_registerContract` and reject missing-artifact requests early, or add an explicit local/manual artifact-registration path before removing the last fallback.

- **The PR 1 risk register materially understates the blast radius of missing artifacts.** The current plan frames the main consequence as note parsing falling back to raw items for third-party contracts (`implementations-plan/registry-stealth-notes/plan-v1.md:127-129,228-229`), but several wallet-owned flows already hard-fail or silently degrade on missing artifacts: token interface parsing / add-token (`packages/extension/src/wallet/services/token/service.ts:240-256,325-341`), manual FPC add-by-address (`packages/extension/src/wallet/services/fpc/service.ts:191-206`), generic execution/authwit contract resolution (`packages/extension/src/wallet/services/execution/contract-resolver.ts:98-127`), and account-state backup, which silently skips contracts whose artifact cannot be resolved (`packages/extension/src/wallet/services/account-state/service.ts:156-169`). Also, the notes page does not scan arbitrary inbound contracts; it only iterates contracts already registered in PXE (`packages/extension/src/wallet/services/note/service.ts:87-93`). Change shape: expand PR 1 acceptance criteria to cover these surfaces explicitly, and state which failures are acceptable pre-launch instead of leaving them as accidental regressions.

- **PR 3.B is not implementable as written because the audited artifact surface does not expose a machine-readable `storageSlot -> note type` mapping.** The plan says to derive a note type from `artifact.storageLayout` and then decode against `artifact.outputs.structs` (`implementations-plan/registry-stealth-notes/plan-v1.md:169-180`), but `NoteDao` only provides packed note items plus `storageSlot`; it does not expose a `noteTypeId` (`node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/dest/note/note_dao.d.ts:11-23`). The audited `ContractArtifact` shape only guarantees `outputs.structs`, `outputs.globals`, and `storageLayout` (`node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/src/abi/abi.ts:336-346`), and `storageLayout` itself is synthesized from `outputs.globals.storage` as field-name plus slot metadata, not note-schema metadata (`node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/src/abi/contract_artifact.ts:247-297`). Change shape: before execution, pin the decoding strategy in the plan. The realistic options are an explicit per-contract/per-slot map for bundled artifacts, intentional parsing of source/file metadata, or a named upstream helper if one is found. Do not leave "verify exact path during impl" open.

## SHOULD-FIX

- **The plan overstates how alive the Stealth Mode onboarding/header flows are, and it misses two cleanup sites.** The promo popup is mounted, but `register.vue` never sets `showStealthPromo` true; it only reads `hasSeenStealthPromo` and renders the popup closed (`packages/extension/src/popup/pages/register.vue:24-26,52-54,106-111`). `profile/new.vue` only clears the in-memory `privacySettings` ref and flips `hasSeenStealthPromo` (`packages/extension/src/popup/pages/profile/new.vue:63-68`). `Header.vue` keeps a `stealthMode` ref and update handler, but there is no rendered stealth indicator in the template (`packages/extension/src/components/Header.vue:33-37,128-143,192-195,212-255`). The inventory also misses `packages/extension/tests/e2e/wallet-lock.test.ts:24-65` and stale stealth docs in `CLAUDE.md:180-189`. Change shape: reframe PR 2 as dead-code cleanup around the live privacy settings page, and add the missing test/doc touch points to the plan.

- **The plan's "snapshot/restore" description is inaccurate.** `Config` declares `stealthModeSnapshot`, but the live privacy page does direct fan-out writes when enabling/disabling stealth (`packages/extension/src/wallet/config/config.ts:5-9,26-39`, `packages/extension/src/popup/pages/settings/privacy/index.vue:83-125`). The only separate stealth-related store state I found is an in-memory `privacySettings` ref in `cache.store.ts`, and it is not actually applied during profile creation (`packages/extension/src/stores/cache.store.ts:4-9,43-45`, `packages/extension/src/popup/pages/profile/new.vue:63-68`). Change shape: remove "snapshot/restore" from the plan language and scope; the real deletion is master-toggle orchestration, not persisted state recovery.

- **PR 1 test work is broader than "drop registry-source tests."** The existing suite has registry assumptions throughout: default order, `allowRegistry`, pins to `"registry"`, config `onUpdate`, and policy preservation (`packages/extension/src/wallet/services/pxe/artifact-registry.test.ts:71-190`). Change shape: rewrite the test file around the new two-source policy rather than treating the change as simple fetcher-test deletion.

- **The branch ordering is only a product dependency, not a hard technical dependency, but the proposed PR split still overlaps heavily.** I agree the registry should not be replaced with a self-hosted equivalent; a local-only model is coherent once the artifact-dependent callers above are handled (`packages/aztec-runtime/src/pxe/artifact-registry.ts:34-53,225-267`, `packages/aztec-runtime/src/pxe/service.ts:156-160`). But PR 1 already edits `config.ts` and the privacy page (`implementations-plan/registry-stealth-notes/plan-v1.md:113-118`), and PR 2 edits those same files again (`implementations-plan/registry-stealth-notes/plan-v1.md:139-145`). Change shape: either keep PR 1 runtime-focused and let PR 2 own the UI/config deletion, or accept that the branches can be developed in parallel but will need rebasing before merge.

- **PR 3.A should state the real reason to bundle `PrivateFPC`, and Wonderland NFT should be an explicit decision instead of an afterthought.** The wallet already imports `@wonderland/aztec-fee-payment/target/private_contract-PrivateFPC.json` via alias (`packages/extension/vite.config.ts:45-49`, `packages/extension/vitest.config.ts:39-43`) and auto-registers that artifact during protocol FPC discovery (`packages/extension/src/wallet/services/fpc/service.ts:18-23,117-130`). So bundling `PrivateFPC` into `known-artifacts.ts` is not what keeps the wallet-owned private FeeJuice flow alive; it improves generic artifact resolution and note decoding for that class. The same post-PR-1 failure mode applies to Wonderland NFT if Nulo expects to support those contracts, since `known-artifacts.ts` currently bundles Wonderland Token but not Wonderland NFT (`packages/aztec-runtime/src/pxe/known-artifacts.ts:43-58`) and token-interface parsing fails hard on missing artifacts (`packages/extension/src/wallet/services/token/service.ts:240-256,325-341`). Change shape: rewrite PR 3.A around "classes we want locally resolvable after PR 1," and decide now whether Wonderland NFT is in or out.

- **The field-decoding details should not stay open in the plan, because one of them is already settled by the pinned stdlib.** On the pinned Aztec version, integer ABI values are encoded and decoded as a single `Fr`, including `u128` (`node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/src/abi/encoder.ts:158-166`, `node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/src/abi/decoder.ts:49-58`). The generic decoder already knows how to materialize nested structs and `AztecAddress` values once the correct ABI shape is known (`node_modules/.bun/@aztec+stdlib@4.2.0-nightly.20260413/node_modules/@aztec/stdlib/src/abi/decoder.ts:68-92,144-145`). Change shape: update PR 3.B to pin `u128 = 1 field` at the current lockfile and narrow the remaining open question to slot-to-ABI mapping.

## NICE-TO-HAVE

- **Keep the current per-note failure-isolation regression test as a non-negotiable invariant, but do not block PR 3 on a live-PXE integration test.** The existing tests already lock in the user-visible guarantee that one malformed note cannot blank the whole list (`packages/extension/src/wallet/services/note/service.test.ts:82-135`). That should stay. I would make artifact-backed unit tests the primary coverage for PR 3, and only add a live-PXE integration if the chosen decoding path ends up depending on PXE-specific note shapes beyond packed items.

- **If PR 3 ends up using an explicit slot map, keep that data with the artifact-bundling commit instead of the parser commit.** The current `3.A / 3.B / 3.C` split is reasonable (`implementations-plan/registry-stealth-notes/plan-v1.md:206-206`), but the slot-to-note-schema table is effectively artifact metadata, not parser behavior. Keeping it with the bundle commit will make the parser commit easier to review and easier to diff against future artifact-version bumps.

## VERIFIED

- **The wallet-owned PrivateFPC flow does not currently depend on the HTTP registry.** `FpcService` loads the PrivateFPC JSON directly (`packages/extension/src/wallet/services/fpc/service.ts:18-23`), computes the canonical zero-salt / zero-deployer instance (`packages/extension/src/wallet/services/fpc/service.ts:117-124`), and registers it into PXE locally (`packages/extension/src/wallet/services/fpc/service.ts:127-130`). The E2E fixture already encodes the same assumption about `Fr.zero()` stability (`packages/extension/tests/e2e/fixtures/aztec.ts:347-365`). The risk here is artifact/version drift, but that risk already exists today; bundling the artifact into `known-artifacts.ts` does not create it.

- **The activity feed does not appear to resolve artifacts for arbitrary inbound transactions.** Transaction history is stored and rendered from the wallet's own local tx records (`packages/extension/src/wallet/services/transaction/service.ts:84-85,109-155,196-239`). I did not find a registry-dependent artifact lookup on the Recent Activity path, so PR 1 is not obviously endangering that surface.

- **Removing stealth-related config keys will not crash dev installs with old `chrome.storage.local` contents.** `ConfigStore.load()` applies only keys that still exist on the current `Config` object and then writes the sanitized shape back (`packages/extension/src/wallet/config/store.ts:17-21,46-55`). Startup loads config before the destructive storage migration (`packages/extension/src/wallet/runtime.ts:88-98`), and the storage migration does not wipe `nulo:config` anyway (`packages/extension/src/wallet/storage/migrate.ts:13-29`). So the plan's "unknown keys are ignored at read time" claim is correct; the important mechanism is `ConfigStore.apply()`, not the storage-version wipe.

- **The notes UI is already wired for decoded content; the missing piece is data production, not a redesign.** `NoteService.parseNote()` is still a no-op that only emits `rawContent` (`packages/extension/src/wallet/services/note/service.ts:104-110`), while the `Note` type already has `type`, `location`, and `content` fields (`packages/extension/src/wallet/services/note/spec.ts:3-19`) and the notes page already prefers `note.content` / `note.type` when present (`packages/extension/src/popup/pages/settings/advanced/account-state/notes/index.vue:128-156`).
