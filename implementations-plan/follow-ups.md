## Grants and scopes

- **Account addresses in the grant check compare by exact string.** `resolveAuthorizedSessionAccount` (`packages/wallet-bridge/src/account-resolution.ts:54`, `:58`), `checkCreateAuthWit`'s accounts list (`method-scope-checkers.ts:289`), `validateAccountScopes` (`scope-enforcement.ts:37-45`), `sessionAccountsOf` (`dispatcher.ts:438-449`) and the membership filter in `projectSessionAccounts` (`dispatcher.ts:1046`) refuse an account spelled in another case: they fail closed. The dispatcher and the journal must change together (`account-resolution.ts:1-13`). From [grant-check-address-case](grant-check-address-case/plan.md), Fact 12.
- **`fee-payer.ts` compares by exact string.** A `feePayer` that differs from `from` only by case is classified `fpc` (`packages/wallet-bridge/src/fee-payer.ts:63`), and a claim that credits the payer in another case is not recognised as one, so the payload routes `self-pay` (`isClaimAndEndSetup`, `:46-54`). The Fee Juice address has no hex letters (`:14`), so only the payer can differ. From [grant-check-address-case](grant-check-address-case/plan.md), § Security.
- **A wildcard scope admits a call target before anything validates it as an address** (`packages/wallet-bridge/src/method-scope-checkers.ts:42`, `:55`, `:60`). What rejects a malformed target afterwards differs per method, and `isTokenRegistered` parses nothing; tightening the wildcard is a behaviour change. The per-method boundaries are the rejection-boundary table in [grant-check-address-case](grant-check-address-case/plan.md), § Non-obvious mechanics.

## Wallet safety

- **The address-keyed fee maps outlive a deleted profile off the live path.** `nulo:ui:feePaymentMethods` and `nulo:ui:sendFeePaymentMethods` hold `{ [address]: … }` (`apps/extension/src/popup/components/modules/send/FeeSettingsCard.vue:293-296`, and `withSendSlot` in `fee-send-selection.ts` beside it). Only the reset page removes them (`apps/extension/src/popup/pages/settings/security/reset.vue:85-87`), after the live delete returns, so the resume and torn-reap paths, and a popup closed mid-delete, keep the deleted profile's addresses. Pruning by address is unsafe, since two profiles can share one, and moving the global wipe onto the other paths changes their behaviour: it needs its own decision. From [wallet-safety-fixes](wallet-safety-fixes/plan.md), F-1.
- **The other scope refusals still interpolate request values.** Seven `Scope violation` messages in `packages/wallet-bridge/src/method-scope-checkers.ts` carry a request's addresses, ids or calls (`:81`, `:108`, `:127`, `:144`, `:178`, `:199`, `:216`); only the three `createAuthWit` refusals were given fixed text. The `sendTx` text reaches the queued journal row, which the journal page renders (`apps/extension/src/popup/pages/journal/[id].vue:137`), so changing it changes a surface. From [wallet-safety-fixes](wallet-safety-fixes/plan.md), F-2.
- **An Allow the watchdog displaced mid-un-hide leaves receipts hidden under `trusted`.** After a stall of five minutes or more inside the lock, a displaced Allow with no Block after it stops un-hiding, and only `setTrustAllow` writes `hidden: false` (`unhideLocked`, `apps/extension/src/wallet/services/incoming-transfer/service.ts:659-675`), so nothing un-hides the rest. The owner signed the state off as a residual; a `(BUG PIN)` in `service.scenarios.test.ts` holds it. Candidates: re-run the un-hide on replay, or un-hide before the trust write, which needs a `pending` trust row first because the floor skips a contract with none (`:865`). From [wallet-safety-fixes](wallet-safety-fixes/plan.md), F-4.
- **A pin or a token-deletion cleanup racing a profile deletion can recreate its pinned-tokens key** (residual R1, signed off by the owner). The purge removes `nulo:ui:pinnedTokens@<id>` on every deletion path, but a popup that has not yet seen the deletion can write it again (`pin` and `onTokenDeleted`, `apps/extension/src/composables/usePinnedTokens.ts:214-243`). A restore that reuses the id then shows those pins (`apps/extension/src/wallet/services/profile/service.ts:1526-1529` frees the id; `operation-journal/service.ts:266-267` says why ids come back); otherwise the key stays as an orphan. Fixes: fence the key by incarnation, or a sweep cheaper than reading the whole store at every background start. From [wallet-safety-fixes](wallet-safety-fixes/plan.md), F-5.
- **Two of the token add's compensations delete by id without lock ownership.** `persistToken`'s post-set deletion and network checks (`apps/extension/src/wallet/services/token/service.ts:419-431`) delete `token.id` even when the lock's watchdog displaced the add, so a same-id restore's row can go with it; the last check before `onTokenAdded` deletes only while the add owns the lock. At those two points the row may postdate the purge's snapshot, so skipping the delete can orphan it: the choice needs its own decision. From [wallet-safety-fixes](wallet-safety-fixes/plan.md), F-7.
- **Recovery phrase and Change password have no submit latch.** A mouse double-click on Retrieve runs `handleUnlock` twice (`apps/extension/src/popup/pages/settings/security/export/seed.vue:55-67`), and the second `countdown.start()` leaves a 5-minute close that "keep open" cannot cancel (`apps/extension/src/composables/useSecretCountdown.ts:26-35`). Change Password is disabled while loading (`apps/extension/src/popup/pages/settings/security/change-password.vue:228`), so only a same-tick double click reaches it twice. `seed.vue` also has no unmount fence (`full.vue`'s `generation` is the pattern), so a Retrieve that resolves after the page left sets the phrase on the dead page and arms that timer. Since both buttons refuse a repeat Enter, only a pointer reaches either twice. From [keyboard-guards](keyboard-guards/plan.md), FU-1.
- **Verify's OK accepts a repeat or composing Enter** (`apps/extension/src/popup/windows/verify/index.vue:221`, handler `:75-80`). It neither sends nor signs, so CLAUDE.md's rule does not bind it, but it records "Always trust". `connect-window` rewrites this window and applies `refuseRepeatEnter` there when it merges. From [keyboard-guards](keyboard-guards/plan.md), FU-2.
- **Two keyboard focus rings do not show.** The sub-page back arrow is a bare `<button>` (`packages/design/src/ui/SubPageHeaderBase.vue:36-45`) under the base stylesheet's `button { outline: none; }` (`packages/design/src/base.css:270-275`), on every page built on `SubPageHeader` or `CollapsingHeroLayout`, and onboarding's active method tab draws its `:focus-visible` outline in `--nulo-accent` over a fill of the same colour (`apps/extension/src/onboarding/pages/create.vue:253-261`). A keyboard user cannot see that focus is on Back. Drawing a ring changes how those screens look, so it is the owner's call. From [keyboard-guards](keyboard-guards/plan.md), FU-3.

The owner, 2026-09-29: "Follow-up (Recommended)". From [ux-owner-picks](ux-owner-picks/plan.md), Fact 16, and [its phase 4 log](ux-owner-picks/lessons/phase-4.md).
