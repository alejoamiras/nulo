## Round 1 — on rev 1 → conditional approve

### 1. Adversarial / security

**CRITICAL — a second dApp send entry has no fence and no atomic check.** `apps/extension/src/wallet/services/dapp-interaction/service.ts:457-520` (`silentInteraction`) is the no-popup path for self-paid dApp sends (`assertSilentExecutable` admits send-like ops). It calls `executionService.executeOperations(operations, origin, undefined, hooks)` — four args, no `authorizedFence` — after only a non-atomic `getActiveProfile()?.id !== payload.session.profileId` check (`:458-461`). Under the plan, `fence?` absent ⇒ "capture now" inside `executeSendTransaction` (`execution/service.ts:847`) / the `aztec_sendTx` arm (`:731`), which happens *after* `refreshSession`, the queued→pending fast-forward, and an unbounded FIFO wait. So an operation session-authorized under A can capture B's fence and then execute, submit and journal under B entirely self-consistently — the exact invariant the plan exists to establish. Neither plan.md nor recon.md mentions this path. Fix: capture the fence in `silentInteraction` exactly as `executeAndResolve:257-263` does (atomic capture + session compare, replacing the id read) and thread it; only then is "required on the dApp path" true. Blocking before Phase 1 lands.

**HIGH — the dialog's count is dApp-influenceable; §Security's "No dApp input reaches it" is false.** `utils/in-flight-send.ts:36-45` documents *why* detection is account-scoped: "A dApp can journal a queued send before any approval, so that gap would hand any connected site an indefinite hold on account switching." The plan's `profileInFlightSends` is profile-wide and includes `queued`. A connected site can therefore force "N transactions are still running" on every profile switch (and have them cancelled). Either exclude pre-approval `queued` rows or restate the count honestly.

**HIGH — the "switch" the dialog gates is not the switch.** `SelectProfilePopup` is opened only from `auth.vue:231` (the lock screen pill); `appStore.profile = profile` selects the profile the user will then *unlock*. So the dialog cancels in-flight sends at selection time, before authentication the user can abandon — irreversible cancellation for a switch that never happens. Two corollaries: D2's "dialog for switch, lock silent" is structurally odd (every switch is preceded by a lock), and other switch paths (`/popup/profile/new` activation, `finalizeRestore`) bypass the dialog entirely, leaving the sweep as the only cover. The plan should enumerate the switch paths.

**HIGH — dialog-confirmed switch can still be refused.** A send at `submitting` on the *viewed* account is excluded from `profileInFlightSends` (count 0) but still trips `hasInFlightSend` (`in-flight-send.ts:17`, stages include `submitting`) → `commitScopeChange` returns false → old toast, after the user already destroyed their other transactions.

**MEDIUM — post-prove checkpoint window and the frozen sequence.** `execution-coordinator.ts:293/298/303` verified exactly. Asserting after `:298` is the only legal slot (FSM `proving→failed` legal, `submitting→cancelled` illegal — `fsm.ts:46-47` verified). But `await toTx()` and `markJournal(submitting)` still follow, so a drift landing there is uncatchable — say so. And the new `await` inside a sequence documented "frozen — extracted byte-for-byte" adds a microtask on the *success* path; check it against the existing frozen-sequence pins and the deliberate synchronicity of `mark-failed-unless-cancelled`.

**MEDIUM — `ProfileDriftError` on the rpc-cancel code channel** conflicts with the pinned negative control `rpc-cancel.test.ts:84-92` ("detail-dependent classes lose details through the message-only channel"). A two-id class riding it reconstructs with `undefined` ids. Make it wire-detail-free by construction, or don't ride.

**Right, in one line each.** Sweep authority is sound: `abandonProfile` is lane-internal, previous-profile + pre-`submitting` only, not RPC-reachable; `EventHandler.invoke` (`packages/wallet-core/src/utils/event-handler.ts:47`) is synchronous and swallowing, so fire-and-forget is required — the handler must not await anything taking the profile facade lock, since `onChange` fires *inside* `runExclusive` (`session-manager.ts:299`) and `Lock` is non-reentrant (`profile/service.ts:290-293`). Inference 1 is verified fail-closed (`packages/aztec-runtime/src/pxe/client.ts:111-118`: provider `undefined` ⇒ original `PxeStoreKeyMissingError` propagates). Identity-compare survives `trackProfileSwitchEpoch`'s objection (an identity check "reads `undefined` and waves through" on switch-then-lock) because `assertFence` throws "Wallet locked" on `undefined`. `fence?` on the two entries is not forgeable into an advantage: a forged id must equal the active profile, a forged epoch fails `assertCurrent`. `executeSendTransaction` is not RPC-exposed (`service.ts:100-111`, `client.ts:21-32`).

### 3. Implementation critique

(a) **Identity over epoch: right**, plus the reason the plan misses (`assertFence` throws on `undefined`, so the switch-then-lock hole `trackProfileSwitchEpoch` guards against doesn't exist here). (b) Boundary leaks — see CRITICAL; once `silentInteraction` captures, make the fence **required** on `executeOperations` for `OriginType.DAPP` rather than relying on call-site discipline. Also: §Architecture adds an optional fence to `executeTransfer` while the change map doesn't; `executeTransfer` is RPC-exposed (`spec.ts:28`, `service.ts:102`) and already captures at `:437` — don't widen the wire surface. (c) `assertAuthorization` as a separate awaited hook is right (`checkCancelled` must stay sync); see the microtask caveat. (d) Sweep is worth keeping, and `failed/profile_drift` vs `cancelled` is the right pair. (e) Missed reuse: `ExecutionService` **already** subscribes to `onActiveProfileChanged` (`execution/service.ts:401`, gas eviction) — extend that subscriber. (f) Gates are real commands with one defect: **Phase 0 edits two packages but runs `bun run typecheck`, which is `vue-tsc --project apps/extension` only — use `typecheck:all`.** Composition plan: cases 1/4/5 are constructible; **cases 2, 3, 6, 7 are not, as written.** Reaching the prove gate on a *dApp* send needs a completed `TxRequestBuilder.buildStandard` — D3 (tx-request + account contract) and D6 (bb) — which the existing spike avoided by seeding the transfer reuse fast path (`service.composition.test.ts:159-198`). The dApp equivalent requires seeding `operationEstimateReuse` past the full consume ladder (`operation-estimate-reuse.ts:125-145`). Either state that explicitly or move those cases to `executeTransfer`/e2e. The Phase-2 pass criteria check D1/D2 but not D3/D6. **Arc 1 is not UI-free**: Phase 0 adds the 4900 envelope branch, a dApp-visible contract; the claim should be "no popup UI".

**Outline B.** Reject it. Between B's two assert points the mutex key (`execution-lane.ts:220`), the account contract (`tx-request-builder.ts:214,372`) and estimate reuse (`operation-estimate-reuse.ts:133`) still resolve from the live active profile, so a drifted op serializes on the wrong lane before any checkpoint sees it. There is no "fewer sites, one epoch" that is safe by construction while six call sites independently re-read the active profile; safety-by-construction *is* removing the re-reads. B's veto is separately unacceptable given the switcher lives on the lock screen (it would block unlock).

### Verdict

conditional approve (with conditions: (1) blocking — thread an atomically-captured fence through `dapp-interaction/service.ts` `silentInteraction`, and make the fence required for DAPP-origin `executeOperations`, before Phase 1 is marked ✓; (2) resolve the dialog's dApp-influenceable `queued` count and the count-0-yet-`hasInFlightSend` refusal, and state that the switcher is the lock-screen selector — dialog fires pre-authentication — plus the create/restore switch paths it does not cover; (3) restate Phase 2 cases 2/3/6/7 against D3/D6 (reuse fast path or e2e) and add D3/D6 to the phase gate; (4) make `ProfileDriftError` wire-detail-free or drop it from the rpc-cancel code channel; (5) fix the cited line numbers in Facts 1, 2, 8, 10, use `typecheck:all` in Phase 0, reuse the existing `onActiveProfileChanged` subscriber at `execution/service.ts:401`, and drop the optional fence from the RPC-exposed `executeTransfer`)
