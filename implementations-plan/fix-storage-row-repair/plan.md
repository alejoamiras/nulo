# Arc 3 — fix-storage-row-repair (F-B23: purge-blind malformed rows)

[light] tier of the 2026-08-16 remediation follow-ups ([spec](../remediation-followups/plan.md)). Recon-first; single codex audit; prove-first. Validation: repo gates + `audit:vue` + **armed smoke** + **SOLO proverless network e2e**.

## Recon verdict (against `dev@52c065a7`) — the arc REDIRECTS to purge-blindness; the sweep subsystem is REJECTED

1. **Repair-on-next-write already exists.** `EntityStorage.set(id, v)` is a whole-key overwrite of the malformed raw — shipped, pinned (`entity_storage.test.ts:151` "(B-23) a valid write to a key survives a prior malformed read"). Roughly half the stores self-repair through it (account's deterministic `accountRowIdOf` + `ensureDefaultAccount` recreate; activity-protocol mints-on-miss under its KeyedLock; transaction's `addTx` guards with `get` not `contains` and overwrites; auth-registry's values-derived cursor collides onto and overwrites the malformed key). The remaining "immortal" stores are random/cursor-id stores where immortality costs one wasted id.
2. **No producer exists on current dev.** Every restore path `Schema.parse`s BEFORE writing (hostile backups yield `restoreError` rows, never stored malformed rows); pre-production no-migration rule means no version skew for users; `JSON.parse` failures require chrome/LevelDB corruption or a raw non-string write (zero key collisions repo-wide). The realistic future producer (a degraded post-production migration) doesn't exist yet.
3. **The one durable harm: profile-purge blindness.** `deleteProfile` is contractually privacy-erasing (finding D), but **7 of 9** `purgeForProfile` paths enumerate through the codec (`getValues()`/`liveRows()`/`_loadAllValidated()`), so a malformed row with `profileId = <deleted>` survives the purge permanently — a data-retention leak. **Two paths already solved this**: dapp-session's `mac-storage.ts:75-83` (`rawEntries()` second pass, with a doc comment naming exactly this hazard) and incoming-transfer's `deleteKeysWhere` (`repository.ts:190-200`, "survives a row that failed codec validation … where a value-predicate sweep would silently skip it"). This is also exactly what arc 6 deferred (`fix-ui-storage/plan.md:31`: "so a profile purge iterating liveRows() also removes malformed rows — separate follow-up work").

## Decisions

- **REJECT (documented deviation): the boot/sweep repair subsystem (R2).** No producer, no consumer harm beyond purge-blindness, re-introduces the delete-vs-concurrent-write class B-23 retired for stores without a service-wide write lock, and both prior plan auditors already flagged auto-repair of undecodable rows as unsafe (tombstone doctrine). Repair-on-next-write is a property `set()` already has, not a thing to build.
- **SHIP (the fix): R1 — malformed-aware profile purges.** Extend the codec-blind `purgeForProfile` paths with a raw second pass matching the raw row's `profileId`, deleting by TRUE storage id, inside each service's existing serialized purge context — adopting the two shipped patterns (ANTI-OVERENGINEERING: adopt, don't invent; if ≥3 sites share the identical raw-pass shape, hoist it next to the existing shared `purgeRows` helper). JSON-syntax-broken rows in stores whose keys don't carry the profileId are **unattributable by construction** — accepted + logged (fail-closed; never delete what can't be attributed).
- **Doc-drift fixes** (assert removed behavior; mislead the next reader): `storage-codecs.test.ts:6` header ("JSON-SYNTAX failure → row dropped" — false since B-23) and `tombstone-repository.ts:29-32` ("decodeRow … asynchronously REMOVES a syntax-invalid row" — false since B-23; the raw-key rationale stays, the justification updates).

## Prove-first
RED per adopted store: seed a valid profile-bearing dataset + one validation-malformed row for the same profile (raw write), run `purgeForProfile(profileId)`, assert TODAY the malformed raw KEY survives (RED), post-fix it is gone; plus a guard pin that another profile's malformed row is NOT touched, and an unattributable syntax-broken row is left (fail-closed) where applicable.

## Codex audit (single, light tier) over complete arc diff — bounded (initial + max 2 resumes)

**Initial pass: `reject`** — 4 blocking findings, all judged real; the redirection itself (sweep rejection) was endorsed ("Rejecting a boot sweep is sound"). Round-1 remediation:

1. **Account raw pass lock-free (aliased-key loss).** A malformed row claiming profile A can sit at the canonical key profile B's `restore()` legitimately writes; the raw pass would delete B's fresh valid row by the stale storage id. Fixed twice over: `purgeMalformedRows` gained a **compare-and-delete** (snapshot the exact stored strings via new `EntityStorage.rawStringEntries()`; re-read `rawValue(id)` and refuse the delete unless the bytes still match), and account's raw pass now runs under `restoreLock` (excludes the one writer that can land another profile's valid row on a snapshotted key). Pinned at both layers (helper CAS unit pin; account purge ∥ restore race pin at the aliased canonical key).
2. **Token passes unlocked.** `purgeForProfile` now takes ONE `this.lock` hold across snapshot + typed deletes + raw pass (`_deleteTokenById` split into a lock-held body since the lock is non-reentrant); `restore()` writes under the same lock, so it can't land after either snapshot.
3. **Sweep incomplete.** (a) `transaction.purgeForAccounts` gained the raw pass in the same lock hold, mirroring the typed sole-owner/ambiguous semantics — an UNSCOPED malformed row is deleted only under sole ownership and otherwise LEFT (it cannot be marked `ambiguous`: rewriting bytes the codec can't read would launder garbage into a valid-looking row; fail-closed, codec-hidden). (b) `token-balance.purgeForTokens` gained the raw pass via `BalanceRepository.purgeMalformed` (no service lock exists on that store — the helper's CAS is the containment). (c) The coordinator's `snapshot()` now unions typed reads with raw harvests (`rawAddressesForProfile` / `rawTokenIdsForProfile`, id from the TRUE storage key) so a malformed PARENT's dependents still cascade.
4. **Unfenced post-purge late writers** (e.g. `addNetwork`'s probe completing after the purge, writing a valid row under the network lock). **Pushed back as out of scope**: a pre-existing failure class orthogonal to F-B23 — it involves fully VALID rows, reproduces identically without this arc, and generalizing the existing partial fences (D13 execution fence, account deletion-epoch fence) to every write path is a cross-cutting mid-tier arc of its own. Disposition: owned follow-up in the remediation ledger, not smuggled into a light arc. _Codex agreement recorded below._

Also from the pass: restored the three pre-existing `purgeRows` pins this arc had accidentally clobbered; fixed the test-file header that over-claimed per-service wiring pins; added `rawStringEntries`/`rawValue` contract pins in wallet-core.

**Resume 1: `reject` again — three sharper findings, all accepted; finding-4 scope agreement RECORDED** ("unfenced valid rows born after purge are a pre-existing, cross-cutting lifecycle-fence problem, not an F-B23 regression. Recording it as a separate owned follow-up is the correct disposition."). The findings all reduced to one principle — **attribution must come from the storage KEY, never the value's self-reported bytes**:

1. **The "CAS" is read-then-delete, not atomic** — and `restoreLock` does not exclude `createAccountInternal`'s canonical write, so a residual window remained. Round-2 fix: stop claiming atomicity (the helper doc now states the three safety layers: key-attribution → site lock → guarded re-read as window-shrinking residue), and make account's predicate key-attributed via the new `parseAccountRowId` (inverse of `accountRowId`): a row at ANOTHER profile's canonical key is never deleted whatever its bytes claim (it is that profile's junk, erased when that profile is deleted); non-canonical keys (which no writer produces) fall back to the value claim. The delete-set is now disjoint from every live writer's write-set — the race is gone by construction, `restoreLock` retained as belt-and-suspenders. Deterministic pins replace race-luck: foreign-key-claiming-p1 survives; p1-key-claiming-p9 deleted.
2. **Raw harvest trusted codec-invalid aliases** (a p2-keyed row claiming p1 could donate p2's address → p1's cascade deletes p2's authwits). Fixed: `rawAddressesForProfile` harvests identity ONLY from canonical keys (value never read; syntax-broken p1-keyed rows now covered too; non-canonical keys fail-closed). 4-row matrix pin + `parseAccountRowId` reject-matrix pin.
3. **`Number("01") === 1`** — a malformed alias key could donate a DIFFERENT valid token's id to the balance cascade. Fixed: `canonicalNumericStorageId` (`String(n) === id`, integer, ≥ 0) gates `rawTokenIdsForProfile`; nothing can reference a non-canonical key (a balance row's `token` field is a number), so skipping loses no coverage. Pinned.

**Resume 2 (final bounded resume): `conditional approve` → CONVERGED.** Condition: make `parseAccountRowId` **byte-canonical** before treating a key as ownership evidence — `JSON.parse` also accepts whitespace/escape/`-0` variants no writer emits, and a crafted variant key could donate an arbitrary address to the cascade (the unscoped auth purge would then delete a real account's authwits). Met: the parser now re-encodes and requires `accountRowId(profileId, chainId, address) === id`; whitespace/escaped-string/`-0` variants pinned rejected. Non-blocking items also taken: (a) the helper doc no longer claims syntax-broken rows are universally "unattributable by construction" — for the key-attributed account store the KEY could attribute them; such a parent row survives (its dependents still cascade via the key-based harvest) — an accepted gap owned as a follow-up alongside the lifecycle-fence item; (b) the guarded re-read test renamed away from "CAS"/"NEVER" (it pins the guard layer, not atomicity).

**Codex-agreed deviations/follow-ups (on the record):** (1) boot/sweep repair subsystem REJECTED ("Rejecting a boot sweep is sound… remains correct"); (2) post-purge lifecycle-fence generalization = separate owned follow-up ("pre-existing… no B-23 regression requires expanding this arc"); (3) syntax-broken parent rows at canonical account keys survive the purge (dependents cascade) — doc-corrected, owned follow-up.
