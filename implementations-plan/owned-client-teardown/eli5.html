Logger Port Leak Plan

Every wallet screen talks to the extension's background worker over long-lived connections called ports. Each service client on a screen quietly opens its own port just for log lines, and nothing ever closes it. A side panel or full-screen tab that stays open collects one more logging port per client every time you open a page, unlock, switch profile or import a backup. The fix: each page gets one shared logger that every client borrows, so a page holds one logging port however long it lives. Nothing is closed early because nothing is closed at all. A test counts the ports before and after; the smoke suite and the PR’s CI confirm nothing else moved.

The four phases

  1. Prove the leak

    Write a test that counts open logging ports while real wallet clients connect and disconnect, expecting one port. On today’s code it fails — five clients leave five ports, fifty connect-and-disconnect cycles leave fifty — and that failing run is saved as the proof. The test stays uncommitted until the fix lands beside it.

    Proves itself by: the new test failing on exactly the port counts and nothing else, lint passing, and the saved red run.

  2. One logger per page

    Every client borrows its page's shared logger instead of building one. The logger class is hidden, so no code can build a private one again: TypeScript files get a type error, plain JavaScript components fail the build. Unit tests get a silent logger, so a shared one can’t carry state from one test into the next — which also retires a quiet bug where any test that connected two clients left a retry loop ticking every second. The port test goes green.

    Proves itself by: typecheck, every unit test, lint and the production build passing; the test showing one port — opened once, never closed, carrying every page’s tag — where it showed five and fifty; and a one-off look inside the built extension confirming the logger code ships exactly once.

  3. Account clients A3: fold in

    Three places abandon a connected account client. Unlock and profile creation will keep the client the wallet just set up instead of replacing it; backup import will close its client when it's done.

    Proves itself by: three new tests, each seen failing before its fix — including one that checks the import closes its client only after its last call finishes — plus typecheck and lint.

  4. End-to-end check

    Run the smoke suite locally: it drives the real popup in a real Chrome, and every console line and every client’s “Connected” goes through the shared logger, so a share that breaks a page shows up there (a wrong tag or a silently dropped line would not — that is what the port test is for). The network suite runs on the PR, where CI already executes exactly the partition the earlier draft wanted to replay by hand — and this change touches no network path. If you want a local network pass anyway (A5), it runs CI’s five shards one after another, alone, and checks after each one that everything it started is gone before the next begins.

    Proves itself by: smoke green on the candidate commit (a red is re-run, then compared against dev before it counts as pre-existing); if A5 says yes, every shard green or a recorded local exception, and no leftover sandbox processes or Chrome windows.

Then: Codex reviews the whole change in rounds until it finds nothing material, the PR opens, and CI — including the job that uses real proving — goes green. Merging stays your call.

Background you need

Why borrow a logger instead of closing it?

The other design had each client close its own logger on disconnect. Both reviewers rejected it: disconnecting is also the first step of reconnecting after the background worker restarts, the client logs "Disconnected" after closing (which reopens the logger), and log lines still in flight get rejected. A page-wide logger sidesteps all of it — nothing is closed early because nothing is closed.

What does a leaked port cost?

A little memory and a listener pair on both the page and the background worker. A handful is nothing; a side panel or onboarding tab left open all day keeps adding them and never gives any back. Popups close within seconds and Chrome frees their ports, so this is real but not urgent.

What stays the same

Log lines keep their tags, so the log viewer and its CSV export look identical. Secrets are still scrubbed before a line leaves the page. The background worker still checks who is connecting. No new permissions, message types or dependencies.

What gets slightly worse

If a page's shared logging port stops answering without closing, every log line on that page times out instead of one client's. Log calls are never waited on, so the wallet's real requests are unaffected; a port that actually closes reconnects on its own, as today.

Your decisions

A1

Two nearby cleanups stay out

Every request sends two debug log lines that the background throws away when debug mode is off; skipping them at the source is a separate change. So is merging the test helpers for fake ports — two exist today, and the port-counting test adds a third, because the existing two are built to refuse a second port of the same name, the opposite of what a leak proof has to count.

Your answer: follow-ups

A2

Real proving only in CI

Three network tests need real zero-knowledge proving. Locally the suite runs with proving off, as CI's main pool does; those three run only in CI's canary job, which must itself pass on the PR — not just be skipped under a green summary — before this counts as done. Nothing here touches proving.

Your answer: yes

A3

Fix the account clients in the same PR?

The Claude reviewer found three spots — unlock, profile creation, backup import — that abandon a connected account client and leak the same way. They sit outside "inner clients", so they're your call: fold them in as Phase 3 (three small edits, each with a test) or leave them for later. Leaving them means the PR can't claim unlock and import stop leaking.

Your answer: fold in

A4

Logging failures behave as they do today

When a log line fails, the page logs that failure through the same logger, which can chain while the background worker is unreachable, and each waiting line keeps retrying its connection. That's today's behavior; this change doesn't cause it and trims the retry loops to one per page.

Your answer: accept

A5

Run the network suite locally before the PR?

You asked at the start for a local network run split into shards. The Claude reviewer pushed back and this draft follows it: the PR's required CI job runs exactly that partition, with no retries, on the same commit; this change touches no network path; and your own notes say the network suite falls over when runs share the machine, so the only safe local pass is the slow one. Options: none (smoke locally, CI decides) or one pool pass (CI's five shards one after another, alone, roughly an hour and a half).

Your answer: none
