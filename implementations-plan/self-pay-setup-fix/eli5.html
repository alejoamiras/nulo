Self-Pay Setup Fix

The bridge's "pay the claim from the gas you already hold" route broke on testnet. We know why, we know how to prove it, and this plan fixes it and adds the test that would have caught it, so a change to the wallet's fee path can never ship green again.

What actually went wrong

Every Aztec transaction starts with a short setup part where only a few approved things may happen (paying the fee, an authorisation registry write). The account contract is supposed to say "setup is over" (end_setup) before it runs whatever the app asked for. The node refuses any other public call it finds inside setup, and it says so with exactly the error you saw: Setup function not on allow list.

setup pay from own Fee Juice mint the bridged token (rejected here)
end_setup
app claim the message, mint the token where the mint belongs

The wallet only says "setup is over" when it knows the account itself is paying. To know that, it compares who the app named as payer with the account the request is running as. On testnet the two did not match, so the wallet built the transaction as if someone else were paying, never ended setup, and the mint landed on the wrong side of the line.

Why did they not match? The wallet has one code path for sending a transaction and another for simulating it first (the bridge always simulates a claim before sending). The sending path was fixed months ago to run as the account the app names. The simulating path (and its sibling, profiling) still runs as the first account in the session, whatever the app asked for. With two accounts granted and the second one selected, the simulation ran as the wrong account. Both reviewers found this in the code; it is not a guess. Whether it is exactly what your session hit depends on question A4 below.

Your first failed attempt (the private-gas route, "unknown nullifier") is a different symptom and is not explained by this. It gets its own candidate in the diagnosis phase: something the transaction read that the network had not settled yet at the moment of the simulation.

The green test we already had could not see it: it uses one account, and it only sends.

Why this is a mid plan

Two of the six risk dimensions are high: blast radius (every bridge claim, and every app that simulates as the wallet) and external coupling (the node's rules, two Aztec versions in play). The other four are low, and the design space is small and fully mapped, so a dual audit fits better than three parallel plans. You invoked mid; the reviews agreed.

The phases

0

Run the simulation as the account the app named

One change in the wallet's request dispatcher so simulate and profile honour the app's account the same way sending already does, and refuse an account the app was never granted. Utility reads and signing already name their account correctly and stay as they are (pinned by tests). Plus the cheapest possible repro: a two-account session simulating a self-paid transfer, with the node's validation switched on.

Proves itself by: unit tests in the wallet bridge; the two-account e2e green now, and on the old code red for the exact documented reason (wrong account, external payer, the node's error); its neighbour tests still green.

1

The gate: a real bridge claim, through the real wallet, on a real node

The test harness deploys the bridge onto its local network (the same node software as testnet, enforcing the same setup rules — the harness checks nobody widened the list), deposits from Ethereum to the extension's account, and drives the exact hub claim the tools app makes, paying from held gas. Eight cells: an account that has never sent × one that has; the first granted account × the second; simulate × send. Every landed cell must show a successful receipt, the token arriving, and the fee leaving; every simulate must reach the node's validator. Two more cases: the bridge package's own claim orchestration on a token the bridge has not registered yet (so registration and the visibility poll really run), and a deliberately wrong transaction that the node must reject, proving the check is live.

Proves itself by: every cell named in the log and ending in success or in a node-side error (never a harness failure); the wrong transaction rejected; the bridge package's own smoke unchanged.

Make it a required check

The new tests get their own CI job (they deploy a bridge, too heavy for the shared pool), the job builds the Ethereum contracts it needs, and the change filter learns every folder the fee path and the harness depend on. All of it pinned by the repo's CI-gating tests so nobody can loosen it quietly, and the branch's protection rules are read back to prove the status is actually required, not just present.

Proves itself by: a clean CI run of the job on the branch's final commit with every cell named, plus the branch-protection read-out, linked in the lessons.

Human context

  • Why the existing test was green. It used one account and only sent. The bug lives in the simulate path with two accounts. Neither dimension was in any test; the plan adds both as axes, not as one-off cases.
  • Why the fix comes before the big test. The defect is visible in the code today and has a two-minute repro. Building the bridge harness first would have meant three hours to confirm what a unit test confirms in seconds. The harness still gets built: your requirement is the real claim shape, and that is what the gate drives.
  • Why not drive the tools UI itself. The claim needs an Ethereum wallet in the browser for the deposit and a journal record for the card; the playground drives the identical wallet-SDK call chain with a tenth of the fixture. Driving the tools UI is a sensible follow-up; the harness can already start it.
  • Why two reviews said "reject". The first draft guessed a fix on the wrong path, wrote gates in commands that only cover the extension, and did not know the CI runner never builds the Ethereum contracts the harness needs. The second draft still aimed the fix at two wallet methods that were never broken, would have let the cheap repro skip the node's validation, and put the CI job in the wrong workflow. All of it is folded in; the decision ledger in plan.md (30 rows) lists each finding and what changed.
