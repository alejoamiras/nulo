What actually went wrong

Every Aztec transaction starts with a short setup part where only a few approved things may happen (paying the fee, an authorisation registry write). The account contract is supposed to say "setup is over" (end_setup) before it runs whatever the app asked for. The node refuses any other public call it finds inside setup, and it says so with exactly the error you saw: Setup function not on allow list.

setup pay from own Fee Juice mint the bridged token (rejected here)
end_setup
app claim the message, mint the token where the mint belongs

The wallet only says "setup is over" when it knows the account itself is paying. To know that, it compares who the app named as payer with the account the request is running as. On testnet the two did not match, so the wallet built the transaction as if someone else were paying, never ended setup, and the mint landed on the wrong side of the line.

Why did they not match? The wallet has one code path for sending a transaction and another for simulating it first (the bridge always simulates a claim before sending). The sending path was fixed months ago to run as the account the app names. The simulating path (and its sibling, profiling) still runs as the first account in the session, whatever the app asked for. With two accounts granted and the second one selected, the simulation ran as the wrong account. Both reviewers found this in the code, and you confirmed the session had two accounts with the failing one second: this is what you hit.

Your first failed attempt (the private-gas route, "unknown nullifier") most likely has the same cause seen from the other side: the fee contract deducts from whoever is executing, so running as the wrong account reads the wrong account's credit. It used to work, so it is in the gate, not a follow-up; if it stays red after the fix, the diagnosis phase treats it as its own problem.

The green test we already had could not see it: it uses one account, and it only sends.

Why this is a mid plan

Two of the six risk dimensions are high: blast radius (every bridge claim, and every app that simulates as the wallet) and external coupling (the node's rules, two Aztec versions in play). The other four are low, and the design space is small and fully mapped, so a dual audit fits better than three parallel plans. You invoked mid; the reviews agreed.

Human context

  • Why the existing test was green. It used one account and only sent. The bug lives in the simulate path with two accounts. Neither dimension was in any test; the plan adds both as axes, not as one-off cases.
  • Why the fix comes before the big test. The defect is visible in the code today and has a two-minute repro. Building the bridge harness first would have meant three hours to confirm what a unit test confirms in seconds. The harness still gets built: your requirement is the real claim shape, and that is what the gate drives.
  • Why no bridge deployment (your A5). Five review rounds designed a harness that deployed the whole bridge per run: a forge build in CI, a dedicated job, script changes in the bridge package. All of that bought the literal hub call — but the defect is in the wallet, and the node judges the wallet's transaction the same way whether the public call underneath comes from the hub or from a token mint. The playground reproduces the mechanism, the exact error text, and both fee routes, with nothing outside the extension, its tests and the playground. The real hub claim stays covered by the bridge package's own smoke and, later, a testnet canary.
  • Why three reviews said "reject" before one approved (and why rev 6 was not re-audited). The first draft guessed a fix on the wrong path, wrote gates in commands that only cover the extension, and did not know the CI runner never builds the Ethereum contracts the harness needs. The second draft still aimed the fix at two wallet methods that were never broken, would have let the cheap repro skip the node's validation, and put the CI job in the wrong workflow. The third draft's cheap repro could not reach the node's check at all, and its simulation oracle could not tell one claim from another. All of it is folded in; the decision ledger in plan.md (40 rows) lists each finding and what changed. Each round found something real; that is the review working, not the plan failing. Rev 6 removes the audited bridge harness on your instruction and keeps every audited rule for the tests themselves (validation on, argument-bound simulate checks, the negative control, no retries, branch-protection proof); it adds no new mechanism, so it was not sent round again.
