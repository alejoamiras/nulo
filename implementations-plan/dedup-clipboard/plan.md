## Architecture (Outline A — AMENDED per codex conditions)
- **`src/utils/clipboard.ts`**:
  `copyToClipboard(text, openToast, opts: { success: { label, icon?, duration? }; failure: { label, icon?, duration? }; sanitize?: boolean }): Promise<boolean>` — SEPARATE full success/failure toast specs (codex blocking #1: one shared icon/duration cannot represent the sites' real combinations — header failure warning/3000, IncomingTrust success copy/1500, received success+failure 2000, etc.). NO nullish-input guard in the generic helper (several sites can pass empty values today and their copied-byte behavior must not change); the `if (!address)` guard stays ONLY in `copyAddressToClipboard`, which becomes a thin delegation.
  `sanitize` (stripWireControl) defaults FALSE; the THREE sites that sanitize today pass true: header, `ScopeAddress`, **`ScopeClassId`** (codex blocking #2 — its tests pin the property).
- **Sync-relative-to-click preserved (codex #3)**: formerly-sync handlers stay sync and call `void copyToClipboard(...)`; UI flashes (`JsonViewer`/`AccountsPopup`/`useProfileImportFlow` 1.5s `isCopied`, `account-state/senders` 2s `copiedAddress`) keep starting REGARDLESS of write outcome, exactly as today; BalanceView keeps its post-`nextTick` fire-and-forget; only IncomingTrust + received/[id] (already async) stay async. No caller starts consuming the boolean return.
- **`src/composables/useSecretClipboardCopy.ts`** with codex #4's + fable L1's explicit ordering invariants: `copySecret(value)` invokes `writeText(value)` SYNCHRONOUSLY during the gesture (never after an await, and as the helper-path's first effect — gesture transience); the 60s scrub + 2.5s flash timers are scheduled IMMEDIATELY in the same tick (never in `finally`/post-await, so a never-settling clipboard promise cannot prevent the scrub — pinned by an unresolved-promise test); the flash starts regardless of outcome; re-copy clears only the previous scrub timer; NO timer captures the secret (`writeText("")` only); NO lifecycle hooks AND **no `dispose()` export, by design** (fable L3: the repo's composable-dispose convention would tempt a future reviewer to add one — the doc comment states the F-14 unmount-survival rationale explicitly so it can't be "fixed" into cancellation); the toast settles honestly on the kept promise (the authorized change). Supports key.vue's private/public two-value selection via the argument.
- Sites migrate with their EXACT current labels/icons/durations; **19 ordinary writer modules** + the 2 export pages + the header reference (22 total, codex-grepped).

## Competing outline (B — for the audits)
A `useCopyToast()` composable auto-wiring `useToast()` so callers don't pass `openToast`. Pros: less plumbing per site. Cons: unusable from non-setup contexts (the reference helper is called from a plain handler module today), hides the toast dependency, and diverges from the proven in-repo pattern. A preferred; audits may overturn.

## Security & Adversarial Considerations
- The scrub semantics (unconditional, no clipboardRead, no unmount cancel, no secret retained by the timer closure) are F-14's audited design — moved, not modified; the composable's timer closure must reference NO secret (writeText("") only), preserved verbatim.
- Sanitization scope is frozen (opt-in) so no site's copied BYTES change — only toast honesty changes, per the authorization.
- The false-toast fix narrows a real deception window (user believes a secret/address copied when it didn't).
