E2E Full Network Recovery

A walkthrough of what we’re doing, why, and what could go wrong — in plain language. No jargon you don’t need.

The setup, in one paragraph

The Nulo browser extension talks to dApps (websites that want to use the wallet). Tests simulate that conversation. Right now, most of those tests fail — not because they’re broken, but because the conversation between dApp and wallet is silently dropping messages in the middle. The previous PR (#46) made the failures visible instead of silently skipping; this plan’s job is to fix them.

Current score: 17 tests pass · 36 tests fail · 4 tests intentionally muted.

Target score: 61 tests pass · 0 tests fail · 0 tests muted.

The two real bugs

Bug 1 (Cluster A): The wallet stops responding after saying hi

The dApp connects successfully (“hi, I’d like to talk to your wallet”). After that, every follow-up message gets silence. The wallet receives it, presumably does something with it, but the response never comes back to the dApp.

22 different tests are affected by this. They all show the same pattern: 30-second timeout, then test gives up.

Why “ELI5” isn’t enough yet: we don’t actually know where the message gets dropped. That’s what the “probe-first” phase figures out. We’re going to put little tracers at 16 key points in the conversation, run the failing tests, and read the trail to see exactly where the conversation dies.

Our top two guesses (we’ll prove or disprove them with the probes):

  • Guess A: The wallet’s service worker (its brain) fell asleep. In Chrome’s extension model, the SW can go idle after 30 seconds of nothing happening, and when it wakes up, it forgets which dApps it was talking to. So messages from a dApp it “forgot” get silently dropped.
  • Guess B: The response makes it almost all the way back but gets lost in the last leg of the encryption channel. There’s a known place in upstream Aztec SDK code where send-failures are silently swallowed.

Bug 2 (Cluster B): Switching to the local test network takes 30 seconds

When the user (or test) clicks “switch to Local Network” for the first time, the wallet takes 30 seconds to actually switch. The second switch is fast. So something is being initialized lazily, on first demand, and that something is slow.

The non-obvious bit: we originally thought this was about the heavy crypto code (PXE) initializing. But the actual thing the test is waiting for is “the new active account address shows up in storage” — which is an account-provisioning problem, not a crypto-initialization problem. When you switch to a chain you’ve never visited, the wallet has to derive a brand-new account for that chain. That derivation is what’s slow.

The fix: pre-create the default account at startup, so by the time the user switches, the account already exists.

How we’re going to do this (the 8 phases)

Phase A — Add tracers for Bug 1

Put 16 console-log markers at every important step in the dApp→wallet conversation. Gated behind a build flag so they only fire in tests — never in production.

We need to know where the conversation dies before we can fix it. Guessing wastes time and risks fixing the wrong thing.

Phase A.1 — Un-mute one of the muted tests

Re-enable the connect-locked-queue test, which exercises a different part of the system. With probes already on, we get free signal about another surface.

Cheap to do alongside Phase A; gives us extra data points.

Phase B — Add tracers for Bug 2

Probe the network-switch code path so we can measure exactly where the 30 seconds is spent.

Same logic as Phase A: measure before fixing.

Phase C — Run probes, document findings

Run failing tests with all the probes on. Write down what the trail says. Pick the right hypothesis.

Now we know the actual bug, not the guessed bug. Approval gate here — I show you findings; you approve the fix direction.

Phase D — Fix Bug 1

Apply the fix that matches what the probes showed. If the SW is falling asleep: keep it alive while dApps are connected (carefully — see safety section).

This is the high-impact fix that unblocks 22+ tests.

Phase D.1 — Un-mute another test

Re-enable data-registerSender as a clean re-test of the Bug 1 fix.

Single-method test — if it passes, the fix is solid.

Phase E — Fix Bug 2

Pre-create the default account for built-in chains at wallet startup. So first “switch to Local Network” takes <1 second instead of 30.

Real user benefit, not just test-fix. Users today also see this 30-second lag on first switch.

Phase E.1 + E.2 — Un-mute remaining tests

Re-enable token-management and fee-methods, which depend on the network-switch path.

Both should “just work” after Phase E. If not, we have data to fix what’s left.

Phase F — Mop up remaining test failures

Two tests (Cluster C and D) are likely cascade victims of A and B. Re-run; if they pass, done. If not, investigate.

Usually most of the long tail goes away when you fix the root cause.

Phase G — Remove the tracers

Delete all the probe code we added in Phase A and B. CI verifies the production bundle has zero probe strings.

Probes are debugging code, not production code. Shipping them would leak protocol internals.

Phase H — Final check + ship

Run the full test suite three times. Update the PR description with final numbers.

One green run could be luck; three consecutive green runs is signal.

What could go wrong (the safety review)

The probe tracers leaking into production

If we forgot to strip them and shipped a release with probe code, the dApp’s browser console would log internal method names, session IDs, queue depths, etc. An attacker reading the console (or a sketchy other extension snooping on it) sees protocol internals.

How we prevent it:

  • All probes gated by a build-time flag. Off by default. Vite’s compiler replaces the flag check at build time.
  • A CI step that builds the production bundle, greps for any probe string, fails if it finds one. This is the actual safety guarantee — the build flag is the design intent, the bundle-grep is the proof.

Keeping the service worker alive too long

If Bug 1’s fix involves keeping the SW alive (so it doesn’t forget dApps), we have to be careful: we can’t just “always keep it alive”. That would keep encryption keys in RAM longer than the user intended.

How we prevent it:

  • Keepalive scoped to active dApp tabs, not just “a session exists”.
  • Periodic re-verification that the tab is actually still alive (a dApp can leave a session open and never explicitly disconnect — we must not pin the SW forever based on that).
  • The moment the last live dApp tab closes, keepalive stops.

Pre-creating accounts for chains the user hasn’t visited

Bug 2’s fix means we derive default accounts for built-in chains (Local, testnet) at startup, even if the user never goes to those chains. This is a conscious tradeoff:

  • Good: 30-second first-switch lag becomes <1 second. No network calls during derivation — nothing leaks to the network.
  • Cost: those accounts show up in storage exports, encrypted backups, profile imports. A user who never used the Local chain now has a Local-chain account in their backup. We’ll note this in the changelog for transparency.

Persisting encryption keys to disk (NO)

One tempting “fix” would be to save the dApp’s encryption session to Chrome’s storage so it survives SW restarts. We’re explicitly NOT doing this. The session contains an AES key derived from key exchange — putting AES keys on disk-IPC channels would be a security regression even though Chrome’s “session” storage clears on browser close.

Open questions (the things we’ll know after probes)

1. For failing requestCapabilities tests: does the capabilities popup actually approve, and does the approval reach the dispatcher?

This tells us whether the bug is in the popup-handling code or somewhere else. If popup approves but dispatcher never hears about it, that’s a specific bug to fix.

2. Between “dApp connects” and “dApp’s next message fails”, did the service worker restart or did a tab event fire?

If yes, that’s strong evidence for the “SW fell asleep” hypothesis (Guess A). If no, the bug is elsewhere.

3. For Bug 2: is the time spent in cryptographic account derivation, or in everything around it (storage writes, UI watchers, etc.)?

Determines whether the fix is “pre-create the account at startup” (most likely) or “fix something in the storage/watcher path” (less likely but possible).

4. For the muted connect-locked-queue test: does it just need a deterministic “queued” signal from the wallet, or is there a real bug under lock/unlock churn?

Determines whether un-muting it is a one-line change or a real investigation.

5. For the session-reconnect flaky test: where exactly does it fail — before the verify popup, during approval, or after popup close?

Each of those is a different code path with a different fix. Probes pin it down.

Why three plans + audits?

This is the “Tier A” protocol from our internal guide for big cross-cutting changes. Three independent plans get written: mine (the main agent), Codex’s (a different AI model family for an independent take), and an Opus subagent’s (also independent but parallel). Then I consolidate the strongest pieces from each, and Codex does one final review.

What this process actually caught:

  • My plan said Cluster B’s problem was PXE crypto init. Codex correctly pointed out it’s actually account provisioning. Different fix.
  • My probe set missed the capability-popup approval branch entirely. Codex caught that.
  • I had wrong file paths in 2 places (offscreen lives at packages/extension/src/offscreen/, not packages/extension/src/wallet/offscreen/). Codex caught that.
  • Opus contributed the upstream-SDK silent-drop discovery (where the wallet-sdk library will quietly throw away messages if it can’t find a session for them).
  • Opus contributed the bundle-grep approach instead of source-grep for probe leak prevention.
  • Both audits agreed on rejecting things I had as possibilities (persisting session keys to disk, global SW keepalive, timeout bumps).
