Monorepo restructure → apps / packages / contracts

The repo's packages all live in one flat packages/ folder. This plan sorts them into three role-based homes — apps/ (the things you ship: extension, faucet, landing, playground), packages/ (shared libraries), and contracts/ (the Noir + Foundry smart contracts) — in one big history-preserving move. The crucial fact that makes this safe-ish: nothing about the code changes. Package names stay @nulo/*, and Bun finds them by name, not by folder — so no import statement moves. Only directories and the tooling that points at directories change (CI filters, the linter's layer-rules, the type-checker, the release wiring, and a handful of test files that reach across folders by relative path).

Why this is a "deep" plan

It's a folder move, but the blast radius is large: the repo just rebuilt its CI gating to be derived from the dependency graph (with a guard test), and the release pipeline references package paths. Get a path wrong and a required check can silently stop running — exactly the class of bug the team spent a whole arc fixing recently. So: HIGH blast radius + HIGH migration cost → deep, with three independent plans (me, codex, and a 1M-context Opus planner) cross-checked against each other. That cross-check already paid off — between the three we found four hidden couplings the first pass missed (a second fragile test file, the contracts' two links, the extension's test config reaching into sibling libs, and two CI setup-actions).

⚠️ One decision needs your call: flat vs nested packages/

You leaned toward more nesting (e.g. packages/wallet/*). But the strongest analysis argues against sub-grouping packages/: the guard test and 13 linter rules are built on "folder name == package name", and grouping breaks that for cosmetic benefit — while apps/ vs packages/ vs contracts/ already gives you the meaningful nesting. I recommend FLAT packages/ (libraries stay one level deep), and keep the contracts/bridge/{aztec,evm} nesting you asked about (that one's free — contracts aren't packages). The plan's steps are identical either way; only the path strings differ. Your call at approval.

Human context

The single scariest failure mode isn't a crash — it's a CI filter left pointing at the old path, so a check silently skips and reports green while testing nothing. The plan's whole defense philosophy is "make every silent failure loud": the graph guard test, a literal grep, forced CI labels, a deliberate lint-violation probe, a forge build, and a local changelog smoke. The move changes zero runtime behavior (no data, no schema, no shipped-artifact change), so if anything slips through, rollback is one clean git revert.
