Aztec 5.2.0 Split Bump

Move the wallet's Aztec client software from 5.0.1 to 5.2.0 — while deliberately keeping every piece that fixes on-chain identity, compiled contracts, or the native prover exactly where it is. Two small pull requests, heavy safety gates, no live broadcasts.

The two questions that decide safety — both answered

1. Can the old (5.0.1) prover still prove what the new (5.2.0) wallet produces? Research went to the byte level: the entire set of proving circuits and verification keys is byte-identical between the two versions (same content hash upstream), and the simulator is unchanged too. So the pairing is expected to work — and a real end-to-end proving test (the "canary") runs early in the plan and is the final judge. If the canary fails and it's real, the default is to hold the whole upgrade, never to patch around it.

2. Does anything on-chain silently shift? One thing: the address of the ecosystem's shared fee-sponsor contract is derived from the installed package, so it changes generation with the bump. Probed live, read-only: the new-generation instance is already deployed AND funded (≈970 × 1018 fee juice) on the test network. Nothing else moves — the network itself did not reset (verified against its version counter).

Why a mid-weight plan

Scored against the risk rubric: blast radius is wallet-wide and outside services are involved (test network, npm, the accelerator), but nothing is irreversible — no network reset, no data migration, revertable pull requests. That lands at "mid": one plan plus a competing outline, two independent expert reviews, and a final fresh-eyes review. All three reviews have now happened (see below).
