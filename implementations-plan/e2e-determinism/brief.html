e2e Determinism — Plan Brief v3a

The deep follow-on from the stabilization work. We're replacing fixed-time sleeps in the e2e tests with state-driven signals — wait for the real completion event, not for "5 seconds, probably done." Three small PRs land the safe wins; two bigger items (popup handshake redesign + wallet anchor-gate) are documented as deferred.

Third revision after a philosophical pushback. The plan went through three rounds: v1 used the operation journal (codex-approved but implementation-coupled — read internal storage); v2 observed the awaiting-card DOM lifecycle (purer, but codex found it semantically wrong — the awaiting card unmounts at submit, not chain confirmation); v3a (this brief) observes the settled TransactionCard matching (amount, transferType, status) — the actual user-visible confirmation event.

Why this work

The premise

ELI5: after a click, the wallet does some async work in the service worker. The test wants to know "is it done?" Today we mostly answer with "wait 5 seconds, probably done." That's an opaque guess that hides bugs and slows tests. Better: wait for a concrete signal — a storage entry, a DOM element, a journal record — that proves the work finished.

Across the e2e suite we have 8 such fixed-time sleeps (plus a triple-navigation workaround in openPopup) that total ~22 seconds per network suite run. Most can be replaced with signals that already exist in the wallet today. One is a real wallet bug that we'll pin and file separately.

The mental model

  • Software is deterministic. Given the same inputs, it produces the same outputs.
  • Timing is not. The scheduler, GC pauses, IndexedDB compaction, and JIT warmup mean async work completes at slightly different wall-clock times each run.
  • Fixed-time sleeps observe at a random moment. They sometimes see the work as done, sometimes not. Result: "flake."
  • State signals observe at the right moment. They wait for the work to actually emit its completion. Result: deterministic test behavior.

How the design changed after audits

Three revision passes

Two independent investigations (mine + a parallel-Claude agent) produced separate plans. Three codex audits (sessions 019e2c76, 019e2cc5, 019e2d36) found real issues in each revision.

v1 → v2: your philosophical pushback

v1's design read the operation journal directly from chrome.storage.session.nulo:journal@<id>. Codex-approved, but you pushed back: "if we hook up state, we're testing the implementation, not the app." That landed. The test should synchronize on what the user observes, not on internal storage.

v2 → v3a: codex caught a semantic bug

v2 used the DOM of the TransactionAwaitingCard: wait for it to appear, then wait for it to unmount. Pure DOM, no storage reads. But codex's second audit caught: the awaiting card unmounts when the wallet's execute phase finishes (journal succeeded), which happens right after submit — not when the tx is mined. Using v2 would have meant "submitted" not "confirmed," and the nullifier race between consecutive transfers would still bite.

v3a (this brief)

Observe the settled TransactionCard — the post-confirmation row that appears on the activity list. Match by (amount, transferType-label, status) using four data-attributes on the card. When the card's data-tx-status flips to "confirmed", the user has just seen the green check. That's the confirmation event.

Codex's third audit (019e2d36) flagged that TransferType is a numeric enum (0|1|2|3) with names Private/PrivateToPublic/Public/PublicToPrivate, and recommended binding the user-visible label ("Public → Public") instead of the raw enum — both for DOM-purity and because the label IS what the user reads. Fixed in v3a.

Other audit outcomes that stayed across revisions

  • Dropped the popup-handshake signal from this stack. Codex flagged: chrome.storage.session survives MV3 service-worker suspension (so the proposed key is stale-prone); the Vue watcher would miss the initial connect; and the new signal would be observability, not a fix for the underlying handshake-drop bug. The triple-nav stays as a workaround. Real perf win (~37s/smoke) deferred to a separate, carefully-designed PR.
  • Keep waitForToast("Transaction submitted") in sendTransfer. The toast is the service-worker-acknowledgment signal AND the diagnostic on failure paths.
  • Pin the 5s post-fee-estimation sleep + file a wallet bug. Codex confirmed: it's masking a real simulate→prove anchor-freshness race that lives in both UI transfers AND dapp send paths. Not a test fix. Rename the sleep to PXE_ANCHOR_SYNC_WORKAROUND_MS; open a wallet issue.

The 3 PRs

PR-A  Misc small sleeps → state-driven waits

ELI5: nine "wait 100-500ms for Vue to settle" sleeps that all have a real state we can wait for instead. Open a dropdown? Wait for the menu item to appear. Click a toggle? Wait for its data-toggle-active attribute to match. None of these are dramatic by themselves; together they save a few seconds and make the test code honest about what it's actually waiting for.

What changes

  • 5 helper-level sleeps (dropdown waits, navigateByHash post-route, privacy-toggle, etc.) → waitForSelector / attribute polls.
  • 4 stale 500ms inline blocks in fee-methods.test.ts → existing setActiveSendType helper.
  • Bonus: rename the 5s sleep at helpers.ts:607 + fee-methods.test.ts:104,172 to PXE_ANCHOR_SYNC_WORKAROUND_MS with a link to the wallet issue we'll file. Same behavior; honest naming.

Risk

Low. Each sleep has a clear state-driven replacement and a small blast radius.

PR-B  Drop the 3s post-refreshBalances sleep

ELI5: in the private-from transfer path, sendTransfer refreshes balances then sleeps 3 seconds "to let PXE sync." But the next line already waits for the amount input to become enabled, which is gated on the balance landing. The 3s was double-defense; the downstream wait is the real signal.

Risk

Low-to-medium. If PXE refresh genuinely doesn't land before the downstream wait, the input stays disabled past 60s and the test fails honestly. Better than the silent guess.

PR-C  Tx confirmation via the settled TransactionCard — biggest win

ELI5: after a transfer, today the test waits 10 seconds for the tx to confirm. That's 40 extra seconds on the transfers scenario alone (4 transfers × 10s). After the wallet confirms a tx, the user sees a row in the activity list with the amount, the transfer-type chip (e.g. "Public → Public"), and a green check icon. The test observes that same row: when the card matching our amount + transfer-type flips to data-tx-status="confirmed", the user has just seen the green check. That's the confirmation event.

What changes

  • Add 4 optional props to TransactionCardLayout.vue that bind as data-attributes on the root Flex (which already carries data-testid="tx-card"): data-tx-amount-display, data-tx-transfer-type, data-tx-status, data-tx-hash.
  • TransactionCard.vue passes through the 4 props: amount string, formatTransferType(...) label (e.g. "Public → Public" — what the user sees), status string derived from existing isPending/isSuccess/isReverted/isDropped computeds with an explicit "unknown" fallthrough, and the tx hash.
  • waitForTxConfirmation(page, { amount, fromType, toType }) polls for a card matching (amount, transferType-label) whose data-tx-status is terminal ("confirmed" or "failed"); throws with hash diagnostic on non-confirmed terminal.
  • transfers.test.ts updates 4 call sites.

Why this is the right design (per your philosophical critique)

  • The data attributes mirror user-visible info: the amount text, the transfer-type chip label, the green/red icon, the hash slice. Nothing internal — tests observe what the user observes.
  • Survives wallet-internal refactors (tx-store reshape, journal renames, status enum changes) as long as the rendered card's user-visible info stays intact.
  • Catches UI regressions for free: if the activity card stops rendering, transfers tests catch it immediately.

Scope caveat

Safe for the transfers scenario (4 unique (amount, label) pairs, sequential submits). NOT a safe generic primitive for parallel or repeated identical-shape submits — a stale confirmed card from an earlier submit could false-positive. If we later need this elsewhere, we disambiguate with hash or pre-submit snapshot.

Risk

Medium. The biggest single contract change. Unit-test assertions on TransactionCard / TransactionCardLayout get ~8 new cases (one per attribute × pending/confirmed). E2e validation on transfers.test.ts 5× local + 1× CI. Note: "confirmed" here means first-mined state (Proposed | Checkpointed | Proven | Finalized), which is what the user sees as the green check — not on-chain finality.

Deferred (separate PRs)

Wallet anchor-freshness gate

The 5s post-fee-estimation sleep is a wallet bug, not a test bug. The simulate → prove pipeline doesn't gate proveTx on PXE having caught up to the simulate's anchor block. Same pattern exists in dApp send paths.

Real fix: a shared anchor-freshness helper that ExecutionService (UI) and the dApp interaction flow both use before proving. Codex confirmed the scope is bigger than my "10-case unit test" estimate; needs the helper factored as a pure unit first. Multi-day wallet PR.

Action this round: rename the sleep, file an issue, defer the wallet work.

Popup handshake signal

openPopup's triple-navigation workaround is a real cost (~500ms × 75 calls/smoke = ~37s). A signal-based replacement is feasible but needs a careful redesign per codex feedback:

  • The signal must be freshness-scoped (timestamps, not just "exists") because chrome.storage.session survives service-worker suspension.
  • The watcher must use immediate: true or write on initial mount — the current connect can happen before the watcher even registers.
  • The signal is observability; the underlying handshake-drop bug remains. Triple-nav stays as a fallback.

Action this round: none. Filed as a follow-up.

waitForToast audit

Many toast waits have stronger upstream signals (row rendered, storage write landed). But the toast is the only diagnostic for failure paths, so removal needs per-caller care. Land incrementally after the determinism PRs prove the pattern.

Decisions we need from you

Q1  Validation depth on PR-C

Signal 1 (DOM-pure via settled TransactionCard) is validated via ~8 new assertions on existing TransactionCard / TransactionCardLayout unit tests (one per data-attribute × pending/confirmed) + e2e on transfers.test.ts 5× local + 1× CI. No new harness needed — both components already have unit tests.

Self-resolved. v3a's design needs less validation than v1's because the new code path is just prop bindings on already-tested components. No decision needed.

Q2  Wallet anchor-gate timing

The anchor-freshness gate is bigger than I first scoped (shared helper covering UI transfers AND dApp send paths). Two paths: (a) pin the 5s sleep now + file the issue + ship determinism PRs without touching it; (b) block determinism work on the anchor-gate landing first.

My take: (a) pin + defer. The 5s sleep is opaque but not blocking; determinism PRs land independently.

Q3  Popup-handshake redesign priority

Dropping the triple-nav would save ~37s per smoke suite run but needs a careful redesign. Schedule it (a) after this stack lands, (b) before, or (c) skip indefinitely (the smoke suite is fine).

My take: (a) after this stack. Determinism PRs are lower-risk and give the team time to think through the handshake redesign without pressure.

Q4  PR ordering

A → B → C (smallest to biggest) or C first (biggest single win on transfers scenario)?

My take: A → B → C. A+B validate the pattern with tiny risk; C builds on confidence. Same approach we used for the stabilization stack and it worked well.
