Key Model Hardening

The follow-up to the key-model redesign: make each wallet profile's imported accounts private to that profile's password, warn you before you create two profiles from the same recovery phrase, fix a small statistical imperfection in how passkey wallets derive their keys, and write the safety tests the last round promised but never delivered.

tier: mid codex audit: conditional approve → adopted fable audit: conditional approve → adopted stacks on PRs #417–419 pre-production — no users affected

The story, plainly

Your wallet can hold several profiles, each locked by its own password. Profiles made from the same 24-word recovery phrase share the same mathematical root. That's fine for the accounts the phrase generates — but accounts you import from a file are outside material, and today they're locked with the shared root. So on a device with two same-phrase profiles, someone who reads the disk and knows just one profile's password could open the other profile's imported accounts. This plan gives every profile its own random inner key ("DEK") for imported accounts, locked by that profile's own password — structurally, not by policy.

Separately: two independent auditors confirmed the new mnemonic derivation is as strong as the standard everyone uses. The one blemish they found sits in the passkey path — it compresses randomness in a slightly lopsided way (a fraction of a bit; harmless in practice, but beneath the bar this project set). Since nothing has shipped, we fix it now for free, and we add the missing end-to-end tests, including a first-ever live proving test for passkey wallets.

Why tier mid

One HIGH on the risk rubric (security sensitivity — it's key handling), everything else low or moderate: no novel surface (it extends code this same stack just built and audited), pre-production blast radius, nothing irreversible, no migrations, no external coupling. mid = plan + competing outline, two independent audits, a final fresh-eyes audit — plus the crypto-attack rider you asked for after every crypto phase.

What already got challenged

Both auditors said "conditional approve" — what were the conditions?
Real catches, all adopted: the tamper-seal on profile data had to be re-keyed so the attacker (who knows the shared root) can't forge it; the duplicate-phrase warning would never have appeared on the restore path (errors get swallowed there — the flow was redesigned); a passkey-created profile would have shipped without its DEK (a sixth code path the plan had missed); and the passkey-restore flow would have lost the DEK until the next unlock. This is exactly what the audit rounds are for.
Didn't a third audit also run?
Yes — a fresh-eyes final pass, and it rejected the second draft with a catch everyone else missed: because you chose warn-and-confirm, restoring a profile's backup while the original still exists is allowed — and the draft would have let that clone share the original's inner key, quietly recreating the very attack we're closing. Fixed: a restore now mints a brand-new inner key and re-locks every imported account in the backup under it, so clones diverge. The fix is pinned by a dedicated test ("the clone cannot open what the original imports later").
The auditors disagreed twice. Who won?
(1) If a profile's DEK is corrupted, one said "refuse to unlock", the other "unlock, but quarantine imported accounts". We chose quarantine — refusing would let a disk-writer lock you out of your main funds by corrupting one field — with a loud warning and no silent background restore, so it can't fester. (2) For the passkey live test, one wanted a fragile deep-hook cross-check, the other a simpler run. We found a third option better than both: an independent reference calculation, written with raw browser crypto and none of the wallet's own code, that pins the expected result.

Honest fine print

  • The warning is a courtesy, not a wall. You chose warn-and-confirm, so a user can still deliberately make same-phrase profiles — the DEK alone carries the security guarantee. (That's why we build it.)
  • Passkey wallet addresses rotate. The math fix changes them. Nobody's in production; test wallets just re-sync.
  • Old export files stop validating. Extending the frozen spec changes its fingerprint, which account-export files embed. None exist outside tests — but this is yours to ratify below.
  • Unlock gets ~half a second slower on password profiles (one more decryption pass). Documented so nobody "optimizes" it into a hole later.
