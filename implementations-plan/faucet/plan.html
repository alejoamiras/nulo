01What is this thing, really?

A one-screen website that gives the Aztec Foundation team test tokens to play with, so they can try Nulo and the Wonderland AMM/swap without having to manually deploy contracts or beg someone for tokens.

The flow is exactly three steps:

  1. You land on the page.
  2. You connect your Aztec wallet (Nulo).
  3. You click "Drip 1,000 USDC to public" (or one of three sister buttons). A wallet popup asks you to confirm. A transaction goes through. Your balance updates.

That's it. The whole product. No backend, no rate limit, no rocket science.

The trick is that the contract that mints these tokens (the "Dripper") is permissionless — anyone can call it, no auth, no allowlist. Wonderland already built it. We just deploy it once, point our frontend at it, and the on-chain primitives enforce everything we need. No custodial wallet sitting on a server signing things on behalf of users.

02Glossary — the words we keep using

Aztec
A blockchain (think "ethereum-compatible") with privacy built in at the protocol level. Transactions can be public (visible to everyone, like normal blockchains) or private (encrypted notes that only the parties involved can decrypt).
Alpha-testnet
Aztec's public test network. It works like the real network but uses fake tokens. This is where the faucet runs.
Wallet
The software that holds your cryptographic keys and signs transactions. Nulo is a browser extension wallet for Aztec — like MetaMask, but for Aztec, and built by us.
Faucet
A website that gives you free test tokens. Same idea as "drinking fountain" — turn the tap, get tokens. Every test network has one or more.
Token
A digital asset on a blockchain. "USDC" and "ETH" on mainnet are real money; on testnets they're fake versions with the same names so testers don't have to learn new vocabulary.
Dripper
A specific smart contract from Wonderland's aztec-standards library. It has two functions: drip_to_public(token, amount) and drip_to_private(token, amount). No auth — anyone can call it.
Smart contract
Code that lives on the blockchain. Anyone can read it, anyone can call it (if it allows public calls). Deterministic, transparent, immutable once deployed.
Wallet SDK
A standard handshake protocol from the Aztec team that lets any website talk to any Aztec wallet. Think OAuth, but for crypto wallets. Our faucet uses it so the wallet choice is up to the user (in practice: Nulo).
Public vs private balance
On Aztec, your token balance lives in two slots. "Public" = visible to everyone (like a normal blockchain). "Private" = encrypted notes only you can decrypt. The faucet lets the user choose which slot to drip into.
Sponsored FPC
A "Fee-Paying Contract" run by the network that pays gas fees on behalf of users. Without it, you'd need to already hold some fee asset to do anything — chicken and egg. With it, even a brand-new account can transact. Crucial for a faucet.
Vue 3, Vite, Bun, Biome
The tech stack. Vue = the UI framework (same as Nulo extension). Vite = the build tool. Bun = the package manager / runtime. Biome = the linter + formatter. All already pinned in this monorepo.

05Phases — what gets built when, ELI5

The plan ships in seven small phases. Each phase ends with a green checkpoint before the next starts (typecheck + tests + build all pass). Total estimate: ~4 working days. v2 re-ordered Phase F earlier so Phases C–E test against real on-chain contracts, not placeholders.

AScaffold + brand foundation½ day

ELI5: Build the empty shell of the website. Make it look right — Nulo's dark style, the right fonts, the right colors. No buttons do anything yet, but the page renders and looks correct.

What lands: the package itself (packages/faucet/), config files for build/lint/type-check, a placeholder page, fonts, brand CSS variables copied from the extension, basic UI primitives (Button, Card, Tag, Spinner, Toast).

BContracts plumbing½ day

ELI5: Wire up the pieces of code that know where the smart contracts will live on the blockchain. Still nothing visible to the user — we're preparing the runway. Placeholder addresses for now; real ones land in Phase F (next).

What lands: the deployments JSON file (with placeholders), the helper that parses it and rebuilds proper on-chain contract instances, validations that addresses make sense, the helper that knows the Sponsored FPC address.

FContract deployment (moved early — v2)½ day

ELI5: One-time setup. You (the maintainer) run a command from your laptop that actually deploys the Dripper and the two Token contracts to alpha-testnet, then writes their addresses into a JSON file we commit. v2 moved this earlier so the remaining phases test against real on-chain contracts instead of placeholders. Re-running is safe — it doesn't re-deploy things that already exist.

What lands: a self-contained deployer script (~150 lines, vendored from Wonderland's deploy logic but with our token list), the real deployments.json committed to the repo, the deploy command documented in the README. Uses DEPLOYER_SECRET + AZTEC_NODE_URL env (separate from the frontend's VITE_AZTEC_NODE_URL).

CWallet connect flow1 day

ELI5: The "Connect wallet" button works. Click it → Nulo prompts. Two interactions: first you see a 3×3 emoji grid in both the website and the wallet — eyeball that they match (security check against impersonation). Then the wallet asks you to approve permissions (read balances, submit drip transactions). After both, you're connected and the page shows your address.

What lands: the connect button with all six states (idle/discovering/verifying/capability-approval/connected/error), the emoji verification modal, the capability-approval inline UI (new in v2 — was collapsed into one state in v1), the status indicator, an inline banner if your account isn't deployed on-chain yet, and all the SDK plumbing.

DToken reads (balances)½ day

ELI5: Show the user how many tokens they have. The two token cards (USDC, ETH) appear after connect, each showing both public and private balances. Balances auto-refresh every 15 seconds. Read-only — no transactions yet. Since Phase F already deployed real contracts, this now exercises the real chain (not a placeholder fake).

What lands: the balance-reading composable (polling every 15s via wallet.executeUtility — v2 corrected from the wrong API in v1), the formatter that turns big numbers into "1,234.50", token cards with balance rows but no buttons, the address-display component with click-to-copy.

EDrip flow — the main feature1 day

ELI5: The moment the faucet "works". You click a drip button. The button shows a spinner. Your wallet pops up asking you to confirm the transaction. You confirm. The transaction goes to the network, gets mined, the balance updates, a success toast appears with a link to the transaction on the block explorer. v2 simplification: only one drip can be in flight at a time — all four buttons disable until it completes (wallets serialize popups anyway, queueing was confusing).

What lands: the drip composable (calls Dripper.drip_to_public/private with the Sponsored FPC as fee payer, waits for the receipt), the four drip buttons fully wired, the toast notifications, and a robust set of error states (wallet rejected, network down, tx reverted, sponsor unavailable, account uninitialized, etc.). v2 cut: ActivityFeed — toast covers immediate feedback; the wallet's own history covers the durable record.

GSmoke e2e + polish + README½ day

ELI5: Write an automated test that pretends to be a user clicking through the whole flow — using a fake wallet (no real network needed) so it runs fast in CI. Clean up the README. Spot-check accessibility. Ship.

What lands: a 5-case smoke test, a mock wallet provider (supporting all 7 RPCs the faucet uses — v2 audit caught that v1's mock was missing registerContract), finalized footer copy, the README with dev/deploy/host instructions.

After each phase: bun run --cwd packages/faucet typecheck && bun run --cwd packages/faucet test && bun run --cwd packages/faucet build stays green before we move on. v2 fixed v1's shell-invalid && test && (would have run the shell builtin). Total: ~55 unit/component cases + 5 smoke (down from v1's 95 — trimmed per audit). Sub-30-second test run.

06Decision still needed (no rush)

One question remains — replaces v1's two-question §13 (which violated the brief). Neither sub-piece blocks development; sensible defaults work for dev, but the real values should land before public hand-off.

Question · alpha-testnet environment

Which exact alpha-testnet environment are we shipping against?

Four values that need to land in env before public hand-off:

  • AZTEC_NODE_URL (and frontend VITE_AZTEC_NODE_URL) — the canonical RPC URL
  • VITE_EXPLORER_BASE_URL — the explorer that success-toast tx links point at
  • VITE_CHAIN_ID — wallet-sdk discovery matcher (so we don't ship a wildcard in prod)
  • VITE_CHAIN_VERSION — matching protocol version

Bonus, only because it directly affects v1 fragility: is the Sponsored FPC known-good on the target environment right now? If it's down, every drip fails — we should know before we hand the URL out.

Default if no answer: wildcard chainId, mainline alpha-testnet RPC, Cloudflare's <project>.pages.dev. Works for dev; just less strict.

v1 also asked about a custom hosting domain (faucet.nulo.sh vs pages.dev). Audit asked us to drop one — we kept the chainId/environment question because it directly affects whether drips work; domain only affects link copy and can be swapped via env later.

07Honest risks

Not all risks are equal. These are the ones worth thinking about.

Alpha-testnet's Sponsored FPC reliability

externalno mitigation

The faucet pays gas fees via a "Sponsored FPC" run by the Aztec team. If their FPC goes down or hits quota limits, every drip fails until they fix it. We can't control this from our side. The faucet surfaces a clear error and tells the user to retry.

Account-not-deployed gotcha

internalmitigated

If someone connects a brand-new Aztec wallet account that hasn't been used yet, the first drip will fail with a cryptic "nullifier" error. Mitigation: on connect, we check if their account contract is on-chain. If not, we show a friendly banner: "Your wallet account isn't on-chain yet. Send any transaction from your wallet first to initialize it — then come back here."

Private drips are slow (30-90 seconds)

UXmitigated

Aztec's private path requires generating a cryptographic proof, which takes 30-90 seconds depending on network load. The UI shows "Submitting in wallet…" with a subtext warning. After 2 minutes we soften it to "Still working — check your wallet."

Bundle size (~5-6 MB)

internalaccepted

The Aztec wasm libraries are heavy. We accept this for an internal-only tool. If we ever open the faucet to the public and the cold-start latency becomes a complaint, we'd lazy-load the wasm behind the connect-button click. Not urgent.

Test token name confusion ("USDC" / "ETH")

UXpartially mitigated

Using mainnet brand names is convenient but could confuse a newcomer. We mitigate with the "Test token · no real value" chip on every card and in the footer. If Foundation feedback shows actual confusion, we can rename to tUSDC / tETH.

08What we're NOT building (explicit)

To keep the scope honest:

no backend no rate limiting no swap UI no transfer-between-users no balance history no multi-network switcher no custom amounts no wallet creation no i18n no mobile-specific UI no @nulo/ui extraction no extension refactor no auto-reconnect no Storybook no Sentry no light/dark toggle no marketing copy no network e2e in v1

Every one of these is a deliberate choice to keep this PR shippable in ~4 days. Any of them could become its own follow-up later.
