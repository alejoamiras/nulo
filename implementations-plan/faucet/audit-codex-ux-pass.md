The plan is directionally right, but it has one major miss and one important state-model gap.

The major miss is #1: you are treating the public-balance bug as still ambiguous when your installed SDK already narrows it a lot. In your code, [useTokenBalance.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/faucet/src/composables/useTokenBalance.ts:112) passes the entire `simulate()` return into `toBigInt`, which returns `0n` for plain objects. In the installed `@aztec/aztec.js` 4.2.0 source, `simulate()` returns a `SimulationResult` object with a `.result` field, including for public functions, at [contract_function_interaction.ts](/Users/alejoamiras/Projects/nulo/nulo-1/node_modules/.bun/@aztec+aztec.js@4.2.0+7524df1edfed9f02/node_modules/@aztec/aztec.js/src/contract/contract_function_interaction.ts:127). The official docs are a bit inconsistent, but the call-types docs also show destructuring `result` from `balance_of_public(...).simulate(...)`: [Call Types](https://docs.aztec.network/developers/docs/foundational-topics/call_types), [Aztec JS reference](https://docs.aztec.network/developers/docs/aztec-js/aztec_js_reference). So your “add a log and wait for user retry before fixing” step is too cautious. The log is still useful, but I would not block the fix on it.

Related to that, `useTokenBalance.test.ts: no change` is wrong. The current tests only mock bare `bigint`/`Fr` on the public path at [useTokenBalance.test.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/faucet/src/composables/useTokenBalance.test.ts:16), which is exactly why this bug slipped through. You want a regression test for the actual 4.2.0 shape: `{ result: 1000n, ... }`. If you want belt-and-suspenders coverage, also accept `.result` being an `Fr` or a singleton array, but the installed ABI decoder returns a scalar for single-return functions, so array unwrapping is secondary, not primary.

On the stale-PXE theory: plausible, but not my lead hypothesis. The PXE is responsible for syncing relevant network state, per the docs: [PXE](https://docs.aztec.network/developers/docs/foundational-topics/pxe). And `simulate` does not come with a correctness guarantee in the docs. So yes, short-lived staleness can happen. But your current symptom is “always 0”, not “lags for a few seconds”, and your drip path already waits for the tx before calling `balance.refresh()` in [TokenCard.vue](/Users/alejoamiras/Projects/nulo/nulo-1/packages/faucet/src/components/TokenCard.vue:53). That makes a deterministic envelope-parsing bug much more likely than sync lag. If `.result` fix lands and you still see intermittent delay, then add a short post-mine polling burst, not a blind 5-second sleep.

Dropping the banner is the right call. [useWalletConnection.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/faucet/src/composables/useWalletConnection.ts:157) is asking `node.getContract(address)`, which is the wrong semantic question for “can this account successfully drip right now?”, and it only probes during connection anyway, so the signal goes stale immediately. I would push this critique one step further than your plan: keeping the dead component and tests is probably not worth it. Git history is enough. Keeping dormant UI plus tests plus `TESTIDS.bannerAccountNotDeployed` means you keep paying maintenance for a feature you just decided is not trustworthy.

For #3, the new intermediate state is correct. `setting-up` is a better name than `registering`, `provisioning`, or `finalizing` because it is user-facing and future-proof. `registering` is too implementation-specific, `provisioning` sounds infra-heavy, and `finalizing` sounds like the end of a tx, not post-approval wallet prep. If you want a slightly cleaner label, `preparing` also works. But `setting-up` is already good enough, especially since you already use hyphenated status names like `capability-approval`.

The other real bug in your thinking is in #4/#5: the moment you move status to the card level, your current “latest” model is no longer trustworthy. In [TokenCard.vue](/Users/alejoamiras/Projects/nulo/nulo-1/packages/faucet/src/components/TokenCard.vue:38), `const latest = publicLast.value ?? privateLast.value` does not mean latest. It means “prefer public forever if public has ever completed.” If the user drips public successfully and then private fails, your card-level row can easily show the wrong outcome or the wrong tx link. Before you invest in nicer copy, you need a real notion of recency: timestamp, sequence number, or a local “last action on this card” state. Otherwise the UI becomes polished but misleading.

That connects to Q4: auto-resetting success to idle after 3 seconds is too aggressive if the card row becomes the main inline status surface. Toasts already disappear after 6 seconds and can be dropped from the queue; the card row disappearing after 3 seconds risks removing the only durable “view tx” affordance. I would decay emphasis after 3 seconds, not erase state after 3 seconds. In practice: let the bright green “Sent” settle into a quieter “Last tx” link until the next interaction. Error can persist until the next click. The “Retry” link is probably redundant if the main button label is stable again, because the button itself is now the retry affordance.

The CSS pass belongs last, and your priority order is good. I would only caution against letting the hero/subtitle work expand. The higher-signal polish items are the connected-header layout, card spacing, and modal contrast. The modal already dims the background fairly hard; if users still find it mushy, the issue may be the modal surface and separation, not just backdrop opacity.

Direct answers:

Q1. You are missing that the installed SDK already points strongly to `{ result: ... }` as the public simulate shape, so I would not assume a bare bigint first. PXE staleness is plausible, but it looks like a secondary hypothesis here, not the primary one.

Q2. `setting-up` is a good state name. If you want cleaner copy, `preparing` is the only alternative I’d prefer. I would avoid `registering`, `provisioning`, and `finalizing`.

Q3. Yes, dropping the banner is the right call. The current probe is both semantically wrong and operationally stale.

Q4. I would not let the success state vanish completely after 3 seconds. Let the emphasis fade, but keep a low-key “last tx” affordance until the next interaction.

One last underreach: if you touch #1, update the stale docs/comments too. The README still says both balances poll via `wallet.executeUtility(...)`, which is already false and will mislead the next pass.
