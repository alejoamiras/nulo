Documentation improvement — what we're about to do

Plan v2, post-audit (codex xhigh + opus 4.7 agent). Source of truth: implementations-plan/docs-improvement/plan-v2.md.

WhyThe problem in one paragraph

The repo grew fast — from a single-package fork into an 8-package Bun monorepo with a service worker, popup, content script, offscreen PXE, design system, and e2e harness. The docs didn't keep up. The root README.md is one marketing sentence. Seven of eight packages have no README at all. The CLAUDE.md exists but mixes "architecture humans need to read" with "rules Claude needs to follow", and its prose is sprinkled with milestone numbers (M4.10, A11.1, M6 phase 4b) that mean nothing to anyone outside the conversation where they were minted. Around 300+ code comments are tagged the same way.

We're going to fix all of that in one PR. Three (or eight — open question below) labeled commits, no behavior changes.

WhyWhat "good" looks like

  • A first-time contributor opens the repo and within ~15 minutes understands what Nulo is, where each package fits, how to build, how to test, and how the message bus works.
  • Anyone reading any file finds comments that explain why the code is the way it is — invariants, gotchas, external constraints — without dragging in milestone numbers nobody outside the original room remembers.
  • implementations-plan/ is the single quarantine for milestone vocabulary. Code points there only when the target is still load-bearing.

WhatThe work — five outputs

1. Root README rewrite

≤120 lines

ELI5 The front door. Right now it's one line; we'll make it a one-page intro: what Nulo is, what works, how to build, where to read next.

Why Anyone landing on GitHub for the first time bounces if the front page is empty.

2. New ARCHITECTURE.md at repo root

≤350 lines

ELI5 The map. Where every package lives, how the service worker talks to the popup, how the popup talks to the offscreen PXE, how storage migrates between wallet versions, how the offscreen document gets resurrected when Chrome kills it, how dApp sessions stay alive across SW restarts, how reads and writes are guarded against each other.

Why Right now that picture lives split between CLAUDE.md prose, a hundred separate code comments, and people's heads. Putting it in one human-facing doc means the next contributor reads one file instead of grepping.

What's new vs v1 plan Audits added these subsections: storage migration + destructive wipes, offscreen lifecycle, dApp-session lifecycle, strict-mode restore semantics, concurrency model (read/write guard), and the account-contract narrative.

3. CLAUDE.md rewrite (tighter)

≤350 lines

ELI5 The rulebook for AI assistants working in this repo. We strip out the architecture (that moves to ARCHITECTURE.md) and keep the rules: layer boundaries, component test conventions, cleanup order, SFC ordering, lint discipline, testid preservation. Plus a new section on how to comment code.

Why Mixed audience is mixed: humans read past architecture they already know, and AI agents get drowned in narrative when they need the rule.

Verbatim preserves (audit-driven) Six sections must survive the rewrite character-for-character: the onBeforeUnmount cleanup order, coverage minimums per layer, the SFC 10-section script-setup template, the chrome.* stub file:line citation, the data-testid preservation rule, and the lint-suppression discipline. These are exact rules the team got burned on; paraphrasing them loses what makes them load-bearing.

4. implementations-plan/README.md

~80 lines

ELI5 The "what's in this folder" doc for the planning archive. Explains why these plan files exist, when to make a new one, how to name them, and a 5-line table mapping each milestone prefix (M2, M3, M4, M6, A11) to what it actually did — so anyone digging up old code who hits an "M4.10" reference can decode it.

Why Right now the directory has 27 subdirectories and no front door. Future contributors need to know it's a quarantine for milestone vocabulary, not a place new code should reference.

5. Eight package READMEs

≤120 lines each

ELI5 One README per package, same template: what it owns, where it sits in the layer stack, scripts, file map, testing, key invariants. Currently only playground has one.

Why Each package is a coherent unit. People should be able to open packages/wallet-crypto/ and know it owns the KDF and the password secret box without grepping the codebase.

Voice Audits supplied opening sentences calibrated to the right voice: technical, precise, non-marketing. Example for wallet-core: "The foundation. Pure ports, types, and platform-agnostic utilities. No chrome.*; no I/O. Every package above depends on this; this depends on nothing."

6. Code-comment cleanup

~300+ comment refs · ~120 files

ELI5 The big one. Sweep every code comment that contains a milestone, phase, or PR tag — strip the tag, keep the insight if there is one, reword for clarity, or delete the comment entirely if the residue would just be noise.

Why Today a fresh reader hits "M4.10 PR-2: handle strict-mode toggle" and has no idea what M4.10 is. The fix is "Disabling strict mode is a security regression — confirm with the user." Same content, no archaeology required.

Six judgment buckets (audit-driven)

  • Keep, drop tag — body is useful; tag is noise.
  • Reword — tag was the structure; rewrite into a real WHY sentence.
  • Delete — tag was the only content.
  • Replace cross-ref — if it points to a still-load-bearing plan doc, keep the path; otherwise repoint or drop.
  • Split block — when one comment mixes a removable tag with a live invariant, split: keep the invariant, drop the tag-paragraph.
  • Out of scope: runtime phase docs — codex flagged this. Some phase 0/1/2/3 comments describe live service-startup behavior, not milestones. We whitelist wallet-core/src/base/** and similar before the sweep.

The audit catch that would have been a bug. My first-pass grep would have stripped live runtime documentation in wallet-core/src/base/index.ts describing how services start up in parallel-dispatch phases. Codex caught it. The revised plan explicitly whitelists these sites.

DecideOpen question — commit shape

You locked "one PR, three labeled commits". Both audits independently recommended splitting the third commit per-package, because the comment cleanup hits ~120 files with judgment-heavy edits — GitHub's diff viewer renders 100+ file commits poorly and reviewers can't meaningfully scroll a single mega-diff that spans the whole repo.

Same PR. Same total work. Different commit shape inside.

Shape A — three commits (the original lock)

Commit 1: top-level docs. Commit 2: package READMEs. Commit 3: all ~300 comment edits in one commit. Cleaner history, harder review.

Shape B — eight commitsaudit recommendation

Commits 1–2 same. Commit 3 splits into six per-package commits (wallet-core / wallet-crypto / extension-messaging / aztec-runtime / wallet-bridge / extension). Reviewer reads one package at a time. Same PR, same prose, easier review.

If you say "stay with Shape A", we ship Shape A and include a per-package checklist in the PR description so the reviewer (you) can mentally section the diff.

WhatValidation before the PR opens

  1. Baseline check on master. Run bun run audit:vue on master first; if anything is already failing, we record it as pre-existing in the PR description so this PR doesn't get blamed.
  2. bun run audit:vue on the branch — typecheck, unit + component tests, lint, build.
  3. bun run test:e2e smoke suite. Required because audit:vue excludes tests/e2e/**, and we will be editing comments inside e2e test files.
  4. Full Storybook build — bun run --cwd packages/extension build-storybook. Story headers are user-visible in autodocs; building everything catches render breakage.

No e2e:agent, no Aztec sandbox. We're not touching runtime code.
