C2 — the "lock re-entry guard" BOTH MODELS: CLOSE

What the lock is

A lock here is a single-key bathroom. Only one piece of code can be "inside" at a time; everyone else queues. It's non-reentrant: if the code that's already inside somehow tries to open the door and walk in again, it waits forever — for itself. That's a deadlock.

The arc added three new users of this lock in ProfileService (the alarm-close, plus C1's applyTtlChange and clearPasshash). So the question was raised: should we add a guard that detects a re-entry and throws an error immediately (fail fast), instead of relying on a code comment + the existing safety net?

Why both models said don't

  • No code actually re-enters. All three new users are fired from the alarm/config listener — never from inside a locked operation. Verified by both.
  • Permanent deadlock is already impossible. The lock has a 5-minute force-release safety net (the janitor who kicks the door open). So even a future re-entry bug self-heals after 5 minutes.
  • You can't reliably build the guard anyway. In single-threaded async JavaScript there's no clean way to tell "this is the same logical caller re-entering" without threading an owner-token through every call site (brittle) or AsyncLocalStorage (heavy). A naive guard would either false-alarm or miss the real case.
One nuance worth your awareness (not a fix request): that 5-minute force-release doesn't prevent a deadlock — it hides one for 5 minutes, then silently hands the lock to the next waiter while the stuck holder still thinks it owns it. On a money path, a reviewer could argue failing fast is better. If you ever want any guard, the safe shape is a tiny depth-counter assert on the extension-side runExclusive (dev-time only) — not a change to the shared wallet-core lock. Neither model thinks it's worth doing now.
My recommendation: close C2, no code change. Document it in the wrap-up (the deadlock-shape warning comment already lives at service.ts:101). This is genuinely a non-issue today.

C3 — node-pool clear on profile switch A REAL (NARROW) LEAK

The original worry — and why it's a non-bug

The mega-audit flagged: when you lock or switch profiles, NetworkService empties its pool of RPC connections (nodes.clear()). Could that disrupt a transaction that's mid-flight (being proven / sent)?

Both models: no. A transaction that's actively executing already grabbed its RPC connection and is holding it as a local variable. Emptying the pool (a lookup table for future requests) doesn't yank the connection out of an in-flight send. Verified safe.

But codex found a different, real problem — and I checked the code myself

The issue isn't the in-flight transaction. It's the pending transaction — one that's already been sent and is just waiting for confirmation. Here's the chain, in plain language:

Think of profiles as two identities, Alice and Bob, that are supposed to stay unlinkable. Each sends transactions through their own "post office" (RPC provider). The whole point of separate profiles in a privacy wallet is that Bob's post office should never hear about Alice's mail.

  1. Alice sends a transaction. The wallet remembers which post office it went to (the tx stores submittedEndpointUrl) and keeps asking that post office "confirmed yet?" on a loop.
  2. You switch to Bob. Switching wipes the wallet's cache of open connections (transientNodes.clear()).
  3. The loop is still tracking Alice's not-yet-confirmed transaction — the pending list is global, it isn't cleared on a profile switch.
  4. To poll, it asks "what's the connection for Alice's post-office URL?" The lookup (_isKnownEndpointUrl) only checks the currently-active profile — Bob. Alice's URL isn't in Bob's address book, so it's treated as "unknown."
  5. "Unknown" → it falls back to Bob's post office and asks Bob's provider about Alice's transaction.
The leak: Alice's transaction hash gets sent to Bob's RPC provider. Two identities that were supposed to be isolated just got correlated — Bob's provider now knows about a transaction that belongs to Alice. In a privacy wallet, that's a cross-profile isolation break.

How narrow is the trigger?

Real, but it needs all of these at once:

  • Alice has a transaction that's still unconfirmed when you switch.
  • Bob has a network configured on the same chain as Alice's tx (otherwise the poll just errors out — no leak, but the tx stops polling).
  • Bob's RPC endpoint URL is different from Alice's (if they share the same provider, there's nothing to leak).

So: two profiles, same Aztec chain, deliberately different RPC providers (which is exactly the setup a privacy-conscious user would choose) + a switch while a tx is pending. Plausible, not everyday.

Why the two reviewers split

claude said "safe" — it reasoned the submitted URL is pinned, so polling stays on Alice's endpoint. It missed that the pinning silently fails on the cache-miss path when the URL isn't in the active profile's address book. codex traced that fallback and called it a real fix. I read the code at each step and confirmed codex is right. (Files: network/service.ts:529-537,770-775, transaction/service.ts:192-219.)

Your options for C3

OptionWhat it doesCost / risk
1. Fix now (minimal)
my pick		 Make the wallet recognize a tx's submitted URL across all profiles, so Alice's tx always polls Alice's post office. This just makes the existing intent (pin to the submitting endpoint) actually work — the code already tries to do this; it silently breaks across profiles. Small, targeted change to network/transaction. No data-shape change. No residual leak to the wrong provider. Full dual-model + network e2e before merge.
2. Fix thoroughly Don't poll Alice's transactions at all while Bob is active — only poll the active profile's pending txs. Strongest isolation (the wallet doesn't even talk to Alice's provider while you're in Bob). Heavier. Transaction records don't currently store which profile they belong to (service.ts:76-78), so this needs a data-shape change + migration. And Alice's tx confirmation freezes until you switch back to her — a real UX regression.
3. Accept the risk Document the narrow leak, change nothing. Cheapest. But it leaves a known cross-profile isolation break in a privacy wallet — somewhat against your "no deferrals, no follow-ups" close-out goal.
My recommendation: Option 1. The code already means to pin each pending tx to the endpoint it was submitted to — that's what submittedEndpointUrl is for. The bug is that the pin quietly fails across profiles. Option 1 fixes exactly that, with the smallest blast radius, and it closes the serious part of the leak (Alice's hash reaching Bob's provider) with no residual. Option 2's extra isolation only buys protection against a much more exotic threat (a global network observer correlating your IP talking to both providers) at the cost of a data migration + frozen confirmations. Option 3 leaves a privacy hole open in the exact wallet whose job is privacy.
