# Store publishing research (2026-09-21)

Facts the plan depends on, each with its source. "Unverified" means no primary source was found; the plan treats those as inferences.

## Chrome Web Store

- **API v2 only.** v1 is supported "until 15th October 2026" ([blog](https://developer.chrome.com/blog/cws-api-v2)). v2 cannot create items or change visibility: "The new API does not support creating new items", "Items are always published with the existing visibility settings". The first submission is manual.
- **Endpoints** ([using-api](https://developer.chrome.com/docs/webstore/using-api), [reference](https://developer.chrome.com/docs/webstore/api/reference/rest/v2/)): `POST https://chromewebstore.googleapis.com/upload/v2/publishers/{p}/items/{i}:upload` (raw body; response `{name, itemId, crxVersion, uploadState}`; fails unless the manifest version increased); `GET …/v2/publishers/{p}/items/{i}:fetchStatus` (`publishedItemRevisionStatus`, `submittedItemRevisionStatus`, `lastAsyncUploadState`, `takenDown`, `warned`); `POST …:publish` with `{publishType, blockOnWarnings}`, response `{state, warningInfo}`.
- **Enums.** `UploadState`: `UPLOAD_STATE_UNSPECIFIED | SUCCEEDED | IN_PROGRESS | FAILED | NOT_FOUND`; prose on two doc pages spells the in-progress value `UPLOAD_IN_PROGRESS`, so accept both. `ItemState`: `ITEM_STATE_UNSPECIFIED | PENDING_REVIEW | STAGED | PUBLISHED | PUBLISHED_TO_TESTERS | REJECTED | CANCELLED`. `PublishType`: `DEFAULT_PUBLISH | STAGED_PUBLISH`; a staged item stays publishable for 30 days ([update](https://developer.chrome.com/docs/webstore/update)).
- **Service account** ([docs](https://developer.chrome.com/docs/webstore/service-accounts), updated 2025-10-15): enable "Chrome Web Store API" in a Cloud project, create a service account with no roles, add its email in the Developer Dashboard under Account. "At this time, you can only add one service account to your publisher." Scope `https://www.googleapis.com/auth/chromewebstore`.
- **Keyless from GitHub Actions.** `google-github-actions/auth` v3 with `workload_identity_provider`, `service_account`, `token_format: access_token`, `access_token_scopes`, `access_token_lifetime`; job needs `permissions: id-token: write`; the pool's principal needs `roles/iam.workloadIdentityUser` on the service account ([README](https://github.com/google-github-actions/auth)). The README's security notes recommend numeric ids: `assertion.repository_owner_id == '…' && assertion.repository_id == '…'`. With an `environment`, the OIDC `sub` is `repo:OWNER/REPO:environment:NAME` and drops the ref, so pin `assertion.ref` and `assertion.environment` separately ([GitHub OIDC](https://docs.github.com/en/actions/reference/security/oidc)).
- **Evidence it works against the store**: MetaMask's `upload-extension-to-cws.yml` uses exactly this (action v3.0.0, `chromewebstore` scope, one environment per target, v2 endpoints); `teddashh/multi-ai-chat` PR 40 has public run logs showing `uploadState: SUCCEEDED` then `state: PENDING_REVIEW`. Google documents no WIF example (unverified by Google, verified in the field). Whether `roles/iam.workloadIdentityUser` alone suffices for `access_token` is the README's claim; enable the IAM Service Account Credentials API.
- **Verified CRX uploads** ([blog](https://developer.chrome.com/blog/verified-uploads-cws), [docs](https://developer.chrome.com/docs/webstore/update#protect-package-updates)): opt-in per item; afterwards every upload must be a CRX signed with the owner's RSA-2048 key (`X-Goog-Upload-Protocol: raw`, `X-Goog-Upload-File-Name`); lost key = support ticket, "up to one week"; opt-out only through support. Google documents only Chrome's `--pack-extension` as the signer.
- **Remote code** ([MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)): "external resources must not contain any logic"; listed violation: "Building an interpreter to run complex commands fetched from a remote source, even if those commands are fetched as data"; exemption: "code run in contexts that are isolated from extension APIs (such as iframes and sandboxed pages) are exempt… it must still be possible to determine the full functionality". No documented pre-submission policy channel; [One Stop Support](https://support.google.com/chrome_webstore/contact/one_stop_support) handles "all other issues", replies within about 3 days (whether it answers a pre-submission question is unverified).
- **Listing** ([images](https://developer.chrome.com/docs/webstore/images), [privacy tab](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)): 128×128 icon (96×96 art plus 16px transparent padding); small promo tile 440×280 required; 1 to 5 screenshots at 1280×800 or 640×400, full bleed; manifest `name` ≤ 75 chars, `description` ≤ 132; version is 1–4 integers each ≤ 65535. Privacy tab: single purpose, one justification per permission, remote-code declaration, data-type checkboxes, certifications, privacy policy URL. "Extensions are required to disclose how they handle user data, even when data is processed or stored locally."

## Firefox Add-ons (AMO)

- **Auth is a stored key pair.** JWT, HS256, claims `iss`, `jti`, `iat`, `exp` with `exp` "no longer than five minutes past the issued at time", header `Authorization: JWT <token>` ([auth](https://mozilla.github.io/addons-server/topics/api/auth.html)). No OIDC option. addons-server revokes a key it finds inside an uploaded package.
- **API v5** ([docs](https://mozilla.github.io/addons-server/topics/api/addons.html)): `POST /api/v5/addons/upload/` (multipart `upload`, `channel`) → `uuid`; `GET /api/v5/addons/upload/<uuid>/` → `processed`, `valid`, `validation`; `POST /api/v5/addons/addon/<guid>/versions/` with `{upload, approval_notes?, release_notes?}`; source only via multipart `PATCH …/versions/<id>/` ("Version source files cannot be uploaded as JSON"). "An upload can only be submitted once." This create-then-patch order is what `web-ext sign` itself does.
- **`web-ext sign`** can create a listed add-on on first use and takes `--amo-metadata`, `--upload-source-code`, `--approval-timeout 0` ([reference](https://extensionworkshop.com/documentation/develop/web-ext-command-reference/)). web-ext 10.6.0 was published 2026-08-04, 10.7.0 on 2026-09-21.
- **Source submission** ([docs](https://extensionworkshop.com/documentation/publish/source-code-submission/)): required for bundled or minified code, "attached to every extension version"; reviewers' default machine: "Ubuntu 24.04.4 LTS (Desktop edition); ARM64 CPU architecture; 10GB of system memory (RAM), 6 cores of vCPU; Node 24.14.0 and npm 11.9.0; 35GB of free disk space"; "You must let the reviewers know if any of the above differs"; tools "must be open source" and "cannot be web-based"; the reviewer diffs the rebuilt output: "There must be no differences"; 200 MB cap. Bun is not named anywhere (acceptance unverified; it is open source and runs locally).
- **Policies** ([add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), 2026-04-30): "Add-ons must be self-contained and not load remote code for execution."; "Only release versions of third-party libraries and/or frameworks may be included with an add-on. Modifications to these libraries/frameworks are not permitted."; data transmission "refers to any data that is collected, used, transferred, shared, or handled outside of the add-on or the local browser"; testing information is required for review. Only miners are prohibited among crypto add-ons. Since 2025 AMO risk-scores wallet extensions and routes high scores to human review ([blog](https://blog.mozilla.org/addons/2025/05/30/crypto-wallet-scams-thwarting-a-new-threat/)).
- **Data consent** ([docs](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/)): mandatory for new extensions since 2025-11-03; `"required": ["none"]` means "doesn't collect or transmit any data"; `financialAndPaymentInfo` covers "credit card numbers, transactions, credit ratings, financial statements, or payment history" and is not eligible for implicit consent. No Mozilla ruling on wallets exists (the classification below is this plan's reading).
- **Channels**: listed (public page; `is_experimental` gives "reduced visibility") or unlisted (signing only, self-hosted, updates need `update_url`) ([self-distribution](https://extensionworkshop.com/documentation/publish/self-distribution/)). No link-only listing like Chrome's Unlisted.
- **Listing limits** (addons-server models): name ≤ 50, summary ≤ 250 with no URLs, up to 2 categories, a license slug (`Apache-2.0`), a privacy policy when data leaves the device, reviewer notes. Version regex allows 1–4 dot-separated integers. Deleting an add-on burns its id forever.
