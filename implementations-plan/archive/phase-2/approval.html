The problem (ELI5)

Today, Nulo lies to you about transactions.

When you send a transaction, the wallet does some math — a zero-knowledge proof — that takes 30 seconds to 2 minutes. The popup waits for the math to finish. But it has a 60-second timeout. So if the math takes longer than that, the popup gives up and tells you "Simulation failed, transaction not sent."

The catch: the math is still running. The transaction often actually does go through. The popup lied to you.

Worse: if Chrome decides to put the wallet's "service worker" to sleep mid-math (it does this aggressively to save power), the math gets killed entirely. You have to start over.

What we know about this problem

  • Aztec proofs routinely exceed the popup's 60-second timeout, especially on slower devices or busier transactions.
  • The 90-second timeout on the offscreen-side (where the math actually runs) is the second ceiling — sometimes the math hits that one too.
  • The PXE prover (the math engine, built by Aztec) cannot be interrupted mid-flight. Once it starts, it runs to completion.
  • Chrome's MV3 architecture wants the service worker to die when not actively in use. Fighting that is futile.

What Phase 2 does (ELI5)

Phase 2 stops treating "the wallet is alive" as a fact, and starts treating "the wallet might be alive" as the design principle. Every transaction becomes a job with an ID. The job's state lives on disk, not in memory. The popup just observes the job — it doesn't own it.

Today

Popup says "Send" → popup waits → popup tells you what happened (sometimes wrong).

After Phase 2

Popup says "Send" → wallet creates a job → popup observes the job's status → user can close the popup, come back later, see the truth.

Bumping the offscreen timeout

Audit caught this: today the offscreen side hard-times-out at 90 seconds, which is part of why long proofs fail. Phase 2 makes this configurable per-method — proveTx gets a generous limit or no limit at all (the job-sweeper handles stuck jobs instead).

The 7 job stages

A job moves through these states:

PENDING SIMULATING PROVING SUBMITTING SUCCEEDED FAILED CANCELLED

What you're not seeing here that I considered:

  • No AWAITING_USER state. The approval popup (where you click Confirm/Reject) stays as it is today — Phase 2 only makes the post-approval flow durable. Adding AWAITING_USER would require moving where jobs are created, which is much bigger work. Deferred to Phase 3 or later.
  • No CANCELLING state. When you cancel, the popup says CANCELLED immediately. The math finishes uselessly in the background and the result is thrown away. Better UX than making you wait staring at a "Cancelling…" spinner.

What changes for you, the user

Before
Hit "Send" → popup waits → "Simulation failed, transaction not sent" → tx actually went through, you find out an hour later.
After
Hit "Send" → popup says "Generating proof…" → user closes the popup → proof keeps generating in the background → user opens popup again → sees "Transaction submitted" or the real failure with the real error message.
Before
Chrome puts the wallet to sleep mid-proof → user comes back, tries again, has to redo everything.
After
Chrome puts the wallet to sleep mid-proof → wallet wakes itself up on a 30-second alarm → marks the proof as failed-by-Chrome-restart → user gets a clean error explaining what happened, can retry from the dApp.
Before
Generic "Loading…" / "Simulation failed" copy that doesn't distinguish stages.
After
Every stage has a named title, body, and action. PROVING gets a sub-message after 30s: "Still working. Complex transactions can take a minute or more." No more "Loading…" anywhere.

The cancel story

Trade-off you should know about: The math engine (BB.wasm) can't be interrupted mid-flight. So when you click Cancel, the popup says "Cancelled" instantly, but the math actually keeps running in the background until it finishes naturally (up to a few minutes). The result is thrown away silently when it arrives. Memory cost: roughly one cancelled-proof-sized chunk holds for that duration.

We accept this trade-off because the alternative is making you stare at a "Cancelling…" spinner for minutes. Engineering can't do better here without rebuilding the proof engine, which is upstream Aztec work.

The 6 carries

Phase 2 builds 8 things, but it also has to make 6 specific design choices ("carries") that don't matter today but will save weeks of rewrites when Phase 2+ ships. Each carry is roughly one design decision, not extra work.

#Carry (the choice)What Phase 2+ feature it unlocks
1Every job is tagged with (origin, profileId, kind) at create-time, even though Phase 2 doesn't use these fields.Fairness (priority queues per origin), per-origin rate limits.
2Terminal jobs (SUCCEEDED / FAILED / CANCELLED) are never deleted, just flagged.Tombstones (don't accidentally resurrect cancelled jobs), idempotency dedup.
3The "watch a job" subscription supports many watchers at once.Future side-panel UI can watch the same job as the popup.
4Progress info uses an extensible tagged-union shape { stage, ...extras }.Future per-stage progress details (% complete, phase name) slot in without breaking anything.
5Error categories preserved — never collapse a real error into a generic "failed".Retry policy can tell "user rejected" from "network blip" from "stuck job".
6Each job tracks an attempts: number counter, even though Phase 2 doesn't retry.Phase 2+ retry-with-backoff logic works without a schema migration.

Two future Phase 2+ costs we're deliberately accepting: (a) adding a dappRequestId field later for "reattach this popup to that earlier dApp request" — a one-line schema bump + propagation; (b) journal garbage collection — Phase 2's terminal jobs accumulate unbounded; Phase 2+ adds a sweeper. With current low traffic this is fine for months.

Decisions you need to make

Below are the decisions where my defaults are reasonable but you should sign off explicitly. Reply with any number + your call (or "default for all" if you're happy with the recommendations).

1 Drop AWAITING_USER from Phase 2 FSM?
The approval popup ("click Confirm / Reject") today is a blocking call. Adding AWAITING_USER as a durable state means moving where jobs are created — significantly larger scope.
Drop it — Phase 2 makes only post-approval flow durable. Pre-approval popup keeps blocking-await as today. (my recommendation)
Keep it — invest the extra weeks now.
2 Drop the CANCELLING state — go straight to CANCELLED?
When user clicks Cancel during proof: with CANCELLING, the popup says "Cancelling, prove still finishing…" for up to 5 min waiting for offscreen to confirm. Without it, popup says "Cancelled" immediately and the orphaned proof completes silently in the background.
Drop CANCELLING — instant feedback to user; accept the memory cost of the orphaned proof. (my recommendation)
Keep CANCELLING — honest semantics but worse UX.
3 Drop "resume SUBMITTING after SW restart"?
Audit found: Aztec proofs are anchored to a block-header at prove-time. A proof generated 30+ seconds ago will be rejected by the node as "stale anchor" when re-submitted. Resuming SUBMITTING would also require persisting the ~100MB proof artifact, which is expensive.
Drop it — SW restart during SUBMITTING just fails the job. User retries from the dApp. (my recommendation)
Keep it — invest the persistence work and accept stale-anchor rejections will happen.
4 Drop heartbeat-from-prove?
Audit found: the prove call blocks JavaScript synchronously. A periodic "I'm still alive" heartbeat can't actually fire while prove is running. So the heartbeat plumbing was fictional.
Drop it — record a single enteredProveAt timestamp at PROVING transition. Stale threshold relaxed to 20 minutes (down from 10 with heartbeat). (my recommendation)
Build a workaround — split prove into chunks with yields between (much larger upstream work).
5 Drop dappRequestId from Phase 2?
This field would link "this job came from THAT specific dApp request, page reload notwithstanding". Useful in Phase 2+'s reattach feature. Audit found it's not one line — it needs propagation through executeOperations, zod schema, one-to-many handling. Cost ~2-3 hours.
Drop it from Phase 2 — defer to Phase 2+ when actually needed (one-field migration + propagation then). (my recommendation)
Carry it now — pay the cost now, save the migration cost later.
6 Profile-level barrier vs scope registries per chain?
Phase 2 makes different chains stop blocking each other. But two shared registries (ChainRuntimeRegistry, ArtifactRegistry) are currently global. Either scope them per chain (invasive) or keep them global with a profile-level mutex above the per-chain locks (simpler).
Profile barrier — single mutex per profile gates guard creation; registries get a disposeProfile() method (~20 LOC). (my recommendation)
Scope registries — more parallelism but bigger refactor.
7 UX copy — sign off on the 7-stage table?
The proposed copy: PROVING splits into <30s and >30s variants ("Still working. Complex transactions can take a minute or more."). The privacy-first wording is "submit to the Aztec node" not "broadcast" (we never broadcast through middlemen). FAILED gets sub-variants per error category. Raw error text is shown in tooltip (preserved Carry #5).
Sign off on the draft — final polish comes in the Week 5 implementation. (my recommendation)
