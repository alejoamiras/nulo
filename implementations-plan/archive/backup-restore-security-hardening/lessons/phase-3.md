## What was built
- **Composable (`useFullBackupImport.ts`):** replaced the tx-only address filter with a shared `filterByAccount` over ALL three account-owned slices, run right after `accountService.restore`, BEFORE the generic restore loop writes them. tx keyed by the `(chainId, account)` TUPLE (`importedChainAddress`) — closes the wrong-chain-tx hole (F); auth-registry + token-balance keyed by address (`importedAddresses`) — closes the graft (A). Drops → `console.warn` (NOT `restoreErrorLog`, per #275: a security filter must not flip a clean import to "finished with errors").
- **`AccountService.restore`:** `AccountSchema.parse` (H) + reject empty/whitespace address (F) + within-batch dedupe (the existing storage-intersection check only covered pre-existing rows). Stores + returns the parsed row (D17).

## Key decisions / gotchas
- **Tuple keying needs the account's chainId in fixtures.** The composable tx tests mocked `accountClient.restore` returning `{ address }` with NO chainId → the tuple `${chainId}:${address}` was never built → txs falsely dropped. Fixed 2 tx fixtures + 4 token-balance fixtures (added `chainId`/an imported account). This is fixture debt from the address→tuple tightening, not a logic bug.
- **New account-filter on token-balance broke the #275 relink tests** (they mocked `accountClient.restore → []`). Correct behavior — a balance must reference an imported account — so the fix was to seed the matching account in those tests, not to weaken the filter.
- **Full `AztecAddress.fromString` canonicalization was NOT done** — it would reject every fake-address fixture (`0xMINE`, `0xa`) across the suite. A legit backup's addresses are already canonical (the wallet stores canonical), so exact address-match holds for real data; a crafted mixed-case address just gets its tx dropped (fine). The empty/whitespace reject closes finding-F's stated hole; full canonicalization is a noted stronger follow-up.
- **D3 "services authoritative" scoped down with justification:** `restore` is NOT in any service's `rpcMethods` (only `getTransactions`/`getTransaction` are) → NO untrusted page can reach it; the only callers are the composable + backup-migration + profile orchestration (all trusted). So the composable filter is the real enforcement boundary; per-service account-provenance verification is defense-in-depth against a non-existent attacker path — deferred for the post-impl audit to confirm/require.
- **Token-ownership + token/account chain-equality (final-pass #5) folds into P5**, where the token old→new map is built — a balance whose token isn't in the imported set is already dropped by the relink; chain-equality gets added there.
- **All new pins fail pre-fix by construction:** auth-registry/token-balance graft (pre-fix forwards the victim row); wrong-chain tx (pre-fix address-only admits it); blank address (pre-fix `set` writes it); batch-dup (pre-fix last-write-wins, both "succeed"); schema-malformed account (pre-fix written + codec-hidden).
