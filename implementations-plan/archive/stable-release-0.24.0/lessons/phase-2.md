# Phase 2 lessons — Release PR → unstick → publish (2026-07-02)

## The publish's network-e2e flaked → cascaded to the landing build
The publish run (`release.yml --ref main -f tag=v0.24.0 -f run_network_e2e=true`) went green on resolve/gates/**build-chrome/build-firefox** (validating the Phase-1 `--ref main` heal — no ENOENT this time)/smoke, then **network-e2e FAILED**. Diagnosis: the failed step was "Run network e2e via agent" with NO vitest assertion failure and proving confirmed (16 /prove requests → sandbox booted, tests ran). The same code had already passed network-e2e TWICE (promote #250, Release PR #252). → **flake** in a known-flaky suite → **re-ran the failed job** (`gh run rerun <id> --failed`, reuses the green builds), never neutralized.

**Cascade the user caught:** the failed publish stopped before `attach-assets`, so the GitHub Release `v0.24.0` had **zero assets**. The landing (`apps/landing`) prebuild `scripts/fetch-latest-release.ts` fetches the LATEST release and **throws if there's no `nulo-chrome-*.zip`** → EVERY Cloudflare landing build (prod + any feature-branch preview) failed with `release v0.24.0 has no nulo-chrome-*.zip asset` while the release sat empty.
- **Root cause is singular:** completing the publish (attach-assets) attaches the zips → the landing builds resolve. No separate landing fix needed.
- **Lesson:** the moment a stable release TAG+empty-Release exists (the manual unstick), the landing is in a broken-build window until `attach-assets` runs. On a flake between unstick and attach, expect red landing builds repo-wide — fix forward by finishing the publish, don't touch the landing.
- **Latent hardening idea (not done here):** make `fetch-latest-release.ts` tolerate an asset-less latest release (fall back to the previous release, or skip) so a mid-publish window doesn't red every landing build. Tracked as a follow-up, out of scope for this release.

## The landing needed a manual CF deploy — `refresh-landing` skips on `workflow_dispatch`
After `attach-assets` finished (assets attached, release complete), `nulo.sh` **stayed on v0.23.0**. Root cause, in order of discovery:

1. **`refresh-landing` (and `deploy-faucet`) only fire on `push:main`, NOT on `workflow_dispatch`.** This is documented (`CLAUDE.md` § Release runbook step 7: *"The workflow's `refresh-landing` step only fires on the `push:main` path, not on `workflow_dispatch`"*) and confirmed empirically: **two** dispatch publishes both showed `attach-assets=success` but `refresh-landing=skipped`. The job `if` reads `(push || workflow_dispatch)` yet still skips on dispatch — the operative gate is the `environment: production` deployment protection + how `resolve` emits `is_prerelease` on the dispatch path. **Do not fight this — trust the runbook.** A manual-unstick + `workflow_dispatch` publish will NEVER auto-refresh the landing; that's by design, not a bug.
2. **The deploy hook is account-ID-free but secret.** `CLOUDFLARE_PAGES_DEPLOY_HOOK` curled with a bare `POST` triggers a prod rebuild needing no account ID — but it's a repo **secret**, readable only inside `release.yml`'s `refresh-landing` job. There is **no standalone `workflow_dispatch`-able workflow** that curls it (only `release.yml` references it), so it can't be fired outside a `push:main`.
3. **Resolution — direct CF API deploy** (user supplied a Pages:Edit token + account ID):
   ```
   POST /accounts/<ACCT>/pages/projects/nulo/deployments  -F branch=main
   ```
   creates an `environment=production` deployment that re-runs the `apps/landing` prebuild (`fetch-latest-release.ts` now finds v0.24.0's assets) → build → deploy → the `nulo.sh` production alias flips. Poll `GET …/deployments/<id>` until `latest_stage=deploy/success` (the returned JSON can carry raw build-log control chars that choke `jq` — the real success signal is `curl nulo.sh` serving `releases/tag/v0.24.0`).
4. **A Pages:Edit token can't discover its own account.** `cfut_…` token: `GET /accounts` → empty, `/memberships` + `/user` → auth error, `verify` returns only the token id. The account ID had to come from the **dashboard URL** (`dash.cloudflare.com/<ACCOUNT_ID>/…`). It is NOT in the repo (no `wrangler.toml`, not a GH variable — only inside the deploy-hook secret).
5. **Preview-vs-production gotcha (the user's "retries" that didn't take):** the project's `latest_deployment` was `env=preview, branch=docs/stable-release-progress` — earlier dashboard retriggers rebuilt a **preview** (feature-branch) deployment, which never touches the production alias. Only `branch=main` yields `env=production`. When a "successful redeploy" doesn't move the live site, check the deployment's `environment`/`branch` — a green *preview* is a no-op for `nulo.sh`.

**Autonomous alternative (not taken):** a `push:main` (runbook option a, "push a no-op commit to main") would have run `refresh-landing` — but it needs a signed commit (the 1Password SSH agent was flaking), drifts main's docs, and risks release-please side effects. The direct CF-API deploy was cleaner once token + account ID were in hand.

**Hardening follow-up (out of scope, worth doing):** add a standalone `refresh-landing.yml` with `workflow_dispatch` that curls `CLOUDFLARE_PAGES_DEPLOY_HOOK`. Then a landing stuck after a dispatch-publish is a one-command `gh workflow run refresh-landing.yml` — no CF token, no `push:main`, no dashboard. Pairs with the `fetch-latest-release.ts` asset-less-fallback idea above.

## Concurrency collision on the Release PR (recap)
release-please opening #252 raced the promote's `push:main` `release.yml` run → the PR-workflow concurrency groups cancelled #252's first CI → aggregators failed fast (`cancelled`). Fix: after the fresh re-run passed, the stale CANCELLED runs still wedged `mss` (duplicate check-runs, success+cancelled per name) → **deleted the 3 stale cancelled runs** (`gh run delete`) so only the fresh SUCCESS remained → `mss` CLEAN → merged. (Deleting stale cancelled duplicates ≠ neutralizing — the real gate passed.)
