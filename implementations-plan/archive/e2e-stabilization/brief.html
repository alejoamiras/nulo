What's actually going on

The short story

A week ago we shipped the CI pipeline from zero (PR #77). To get the gates green, that PR quarantined 26 tests — literally commented them out with test.skip. Some of those tests had been investigated and fixed in PR #70 only days earlier. The comments saying why they were skipped don't always match the current code (e.g. one cites a waitForToast race in a helper that doesn't use waitForToast anymore).

That left us with paper-quarantines: tests skipped because we weren't sure, not because we knew they failed. Two of them (in batch-partial-failure and connect-locked-queue) predate PR #77 and have separate, real reasons to stay skipped.

Two passes of independent investigation (mine + a parallel Claude agent) plus a codex audit all converged on the same picture: most quarantines are defensive; a small handful are real bugs in the test helpers; one is a slow chain on under-powered CI runners.

Why this matters

  • Network e2e on main is a required check. A skipped test passes silently; it can hide regressions that ship to users.
  • Smoke e2e is currently advisory. If we get it stable, we can require it on dev too, catching regressions earlier in the PR flow.
  • Tests should be valuable, not a tax. Per your guidance: succinct, valuable, not over-verbose. Each test we touch will pass that bar or we'll delete it (with a reason).

The phases, in plain language

Phase 0  Find out what's actually broken — locally first

ELI5: imagine 28 tests in a "broken" pile. We don't know if they're all broken or just suspected. We un-skip everything, then run smoke and network 3× locally via the e2e agent (which already gives us cold-start isolation per run). After we know what's actually flaky locally, we push ONCE to CI for substrate confirmation. CI is the final check, never the iteration loop.

What we'll learn

  • Which quarantines are defensive (un-skip, done).
  • Which have real failures (move to Phase 1 or 2).
  • Which are hosted-only divergences — local passes, CI fails. Maps to runner-resource or substrate issues.

Cost

Local: ~30-40 min for smoke 3× + ~1-1.5 hr for network 3× via bun run e2e:agent (parallel-safe, per-run fresh ports). One Linux-container run for substrate- specific tests if needed. No CI run in Phase 0 — CI confirms per-PR later. Total: ~2-3 hr local.

Phase 1  Fix the smoke tests (8 quarantined)

ELI5: four small problems in the helpers. The tests are fine; the supporting code occasionally returns "done" before it's actually done, and that trips up downstream assertions. We're going to fix the helpers, not weaken the tests.

The four buckets

S1 — appearance 1 Skip looks defensive; codex couldn't find a credible race. Un-skip in PR-A. Reinvestigate only if it flakes.
S1 — security 1 Test runs third in a file after a password rotation; old session state contaminates it. Use a per-test fixture so the test gets a clean profile.
S2 — contacts delete 1 Skip comment claims a waitForToast race; the helper hasn't used waitForToast in months. The real issue is a brittle "no console errors" assertion that picks up benign teardown noise. Filter helper for benign disconnect noise.

S4 — passkey backup 1 11-service backup chain takes ~290s on a 2-vCPU hosted runner (vs ~10-15s locally). Real chain slowness. Profile the chain first. Either we find an optimization, or we accept the runner is too small and bump the test's timeout with diagnostic logs for the next regression.

Order

S2 (smallest), S1-security, S3, S4. Each PR independent.

Phase 2  Fix the network tests (20 quarantined)

ELI5: 18 of these were fixed by PR #70 days ago, then re-skipped during the CI bringup as a precaution. Phase 0 confirms whether the fixes still hold. If they do (very likely), we just un-skip and ship. The other 2 are pre-existing skips with separate reasons.

What happens

  • The 18 PR-#77 skips — one mechanical PR-A that flips them back on. If hosted CI shows ~97% pass-rate, that's it. We're done.
  • F (batch-partial-failure) — architectural mismatch in wallet-bridge. Stays skipped. Separate small PR later.
  • G (connect-locked-queue) — needs a "queued" signal from the extension before unlock. Could fold into the S3 SW work.

Rotating flakes

2-3 tests rotate flaky under cumulative load. Two of them already have scoped retry: 1. We wait for upstream aztec.js to migrate off IndexedDB — that's expected to materially reduce the surface.

Phase 3  Speed audit

ELI5: some helpers wait a fixed number of milliseconds "just in case." Replace those with explicit waits for the actual signal we care about. Result: tests pass faster on the happy path; they still fail clearly on the sad path. Real bugs surface sooner.

The biggest wins (ranked)

  1. Drop retry: 2 → 1 on smoke. Real bugs fail three times in a row; flakes don't. Surfaces real bugs faster.
  2. Replace hard 10s sleep in waitForTxConfirmation with a state-driven wait on the actual tx-confirmed signal.
  3. Drop 5s post-fee-estimation sleep in sendTransfer. May surface a real PXE sync race we've been masking.
  4. Replace 500ms+2s padding in refreshBalances fixture loops with a balance-loaded signal.
  5. Replace 200ms sleep in navigateToSettings with a per-route mount signal. Medium risk — needs a small per-page testid contract.
  6. Trim openPopup's triple navigation if the SW handshake is reliable enough now. Highest potential win (~75 invocations per smoke run) but highest risk — the triple-nav was a real workaround.

Ground rule

Speed changes never ship in the same PR as un-skip changes. If removing a sleep surfaces a real race, we want that to be attributable to one specific change.

Phase 4  Make it stick

ELI5: once the suite is reliable, promote it from "we run it but ignore failures" to "PRs can't merge if it's red." Then write down the rules so we don't slip back.

Outputs

  • Smoke required on dev (currently advisory).
  • Drop the "Known failures" section from the e2e README.
  • Document the retry policy: at most ~5% of tests can carry scoped retry. Above that is a real bug.

Decisions we need from you

Each card: short context, my recommendation, your call.

Q1  Phase 0 approach UPDATED

Iterate locally first because CI is too slow to be the feedback loop. Run smoke + network locally via bun run e2e:agent (parallel-safe, cold-start per run) 3× each. Drill into failing tests in isolation. Use a Linux container only where substrate matters (e.g. passkey-backup). No Phase 0 CI run — CI confirms per-PR later.

Approved. ~2-3 hr local iteration. CI never burns time in baseline.

Q2  PR strategy

Seven stacked PRs (A–G) onto dev, each fixing one cluster, vs one or two grouped fix-everything PRs.

My take: seven stacked. Past pattern (M6, network-triage) shows stacked lands cleaner; each is revertable in isolation.

Q3  Passkey backup (S4)

Path A: profile the 11-service backup chain first (4-6 hr; may reveal a perf opportunity). Path B: just bump the timeout (30 min; ships now, less learning).

My take: Path A. The profiling artifact is reusable for the next regression even if the chain ends up being inherently slow.

Q4  SW-resilience tests

Four tests for service-worker death recovery. Both audits and codex confirm they're NOT redundant with existing coverage. PR #77 called them "great locally, flaky on CI."

My take: harden the helper, keep them as first-class CI tests. Skip the "nightly only" middle ground — we should be able to make these deterministic.

Q5  retry: 2 → 1 on smoke

Smoke currently retries each failing test twice. That's three runs per flake hit. Real bugs fail thrice in a row anyway; flakes usually don't.

My take: drop to retry: 1 in PR-F (the speed pass). Measure CI wall-time change vs current baseline as part of the PR.

Q6  Promote smoke to required on dev

Currently smoke is advisory on dev, required on main. Once stable, requiring it on dev catches regressions earlier.

My take: flip it on after PR-A lands green plus 10 PRs through the gate.

Q7  R1 (PXE serialization) investigation

An earlier triage flagged PXE serialization as a real perf concern in @nulo/aztec-runtime. After PR #70's fixes, it's not blocking tests anymore but it's still real product perf.

My take: defer. Multi-day rabbit hole; not blocking. Revisit after upstream @aztec/aztec.js IndexedDB → KV migration lands.

Q8  Test deletion threshold

Phase 0 may surface a test that's both redundant with another and flaky. Currently we keep all tests by default.

My take: allow deletion with a clear rationale in the PR description. The codebase already pins regressions via test pins (CLAUDE.md hard rule #8) — we won't lose coverage we actually want.

Q9  Rotating-flake under cumulative load

2-3 tests rotate flaky on full network runs. Two already have scoped retry: 1. Upstream aztec.js is migrating off IndexedDB which should materially reduce the surface.

My take: wait for upstream. If a new flake appears, scope a retry: 1 to that specific test (not globally). Track upstream migration timing separately.
