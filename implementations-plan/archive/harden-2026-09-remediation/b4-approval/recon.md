### Collision / dedup risks
1. `tx-enrichment.ts` is journal/activity-wide; only its transfer subset can move to the descriptor source.
2. Two intent representations coexist: `@aztec/aztec.js` `CallIntent`/`IntentInnerHash` (the `aztec_createAuthWit` op) vs wallet-bridge `AuthwitContent` (`add_*_authwit` actions; `IntentAuthwitContent.intent: string[]`). Do not conflate.
3. Arity lives in closures; a derived table needs one pin, a hand map would need two.
4. The `message_hash` collapse is duplicated in `discovery-probe.ts` and `authwit-discoverer.ts`; a retained pair must land in both.
5. `OperationEstimateReuseEntry`/`TransferFeeEstimate` are shared with the Send page.

### Tests that red / need coverage
Red: `transfer-intent.test.ts`, `tx-enrichment.test.ts` (partial). New: the `unverified` fallback; the `aztec_createAuthWit` branch (caller, args, innerHash + warning); popup vocabulary == descriptors pin (names AND arities); `estimateOperationFee` surfaces `discoveredActions`; reuse entry preserves the list; network cells assert the new testids.

### Open questions (→ asks)
1. Mint recognition: keep a small documented mint set outside the descriptors, or let mint fall to the raw-args fallback?
2. Arity derivation: `abiBuilder` at init (one pin) vs hand map (two pins).
3. Retained `{consumer, innerHash}`: parallel SW-internal list vs widening the wire `message_hash` content.
4. Send-page symmetry for the optional estimate field (untraced).
5. The "L5 layer rule" is convention, not lint — the plan must not claim a CI boundary that does not exist.

### Decision points (evidence)
1. F-16 merge site: `approveInteraction`/`executeAndResolve` is the only place the stored payload and the RPC argument are both in scope (`service.ts:157-279`).
2. F-16 delta envelope: one index-aligned `deltas` parameter (`{feeSettings?, previewedInterface?}` per index; `estimateIds` may fold in or stay) — the `Operation` union is explicitly not to be loosened (`operation.ts:178-186`), and typing the delta removes the `as unknown as Operation` cast at `index.vue:425`.
3. F-16 "no `session`" reject = a discovery-shaped id; confirm no third caller of `approveInteraction` beyond `execute/index.vue` (repo-wide grep pending).
4. F-16 must keep `executeAndResolve`'s session/profile-fence checks and `interaction.hooks` threading unchanged (additive bind).
5. F-18 reconnect branch needs NEW per-origin state consulted at `background.ts:648-650`, not a reorder.
6. F-18 reservation home: (a) route the verify window through `WindowManager`/`WindowPort` and add an origin/kind index, or (b) inject a `WindowPort` into `SessionEstablishedDeps` and wire `onRemoved` there. "Queued, never dropped" is new logic either way: `DiscoveryQueue` rejects, `WindowManager` times out.
7. F-18 bucket key: `origin` (like `discovery-queue.ts:65`) vs `${origin}|${chainId}` (the dedupe key, `:661`) — multi-chain concurrent connections are intentional.
8. F-18 waiter bound value and site (before `awaitPendingPopupDedupe`, `:663-668`, reject-new shape) vs letting the bucket bound it upstream.
9. F-18 release timing: `approveVerify` awaits the OS close before the next sequential reconnect; the reservation must release on `onRemoved` fast enough that sequential reconnects never queue.
10. F-18 must not touch `runDiscoveryPopup`'s fresh-connection flow (`:769-833`) — the three named cells only exercise that path plus already-connected sessions.
