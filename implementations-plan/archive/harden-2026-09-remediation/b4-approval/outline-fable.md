## 2. Design decisions

**(A) Mint.** No mint descriptor exists (`types.ts:9-18`, nine kinds, five read + four transfer). Deriving "strictly from descriptors" therefore means mint falls to the raw-args fallback, which is honest: the wallet has no ABI knowledge of mint arity, and `KNOWN_MINT_METHODS` (`transfer-intent.ts:28`) was the same hand list F-02 removes. Decision: delete the mint set; mints render as `Unverified call — review arguments` with indexed args (`mint_to_private(to, amount)` shows `0: <to>, 1: <amount>` — everything is still visible, only the "To/Amount" labels are lost). The `METHOD_LABELS` mint labels stay (journal only, not a trust surface). If the owner wants structured mints later, the correct move is a mint descriptor, not a third list.

**(B) Arity.** `abiBuilder` at init. Evidence: arity is per VARIANT, not per name (`descriptors.ts:353-375`: `transferPrivate` has variants `params: 2` and `params: 4` and three `defaultNames`), so a hand map would have to encode the cross product and drift silently when a variant is added. `abiBuilder(name, impl)` (`:314-317`) is pure, synthetic (`transfer2Abi`/`transfer4Abi`, `:242-261`) and yields parameter NAMES, so the popup can label by ABI name (`from/to/amount/authwit_nonce`) and drop the positional guess entirely. The 2-arg `transfer(to, amount)` has no `from` param: `from` is the private-context `msg_sender`, which for an `aztec_sendTx` is the account named in `opts.from` (enforced equal to `op.accountAddress` at `dapp-send-executor.ts:567-569`). Render `From: <op.account.address> (this account)` — truthful and satisfies the "keep the explicit `from` rendering" rule at `OperationCard.vue:130-134`. One pin (the vocabulary test) is enough.

**(C) Retaining the pair; binding.** Both collapse sites (`discovery-probe.ts:80-90`, `authwit-discoverer.ts:115-123`) hold `effect.contractAddress` and the full `CallAuthorizationRequest` — `msgSender`, `functionSelector`, `args`, `innerHash` (upstream `call_authorization_request.d.ts:19-40`) — so a parallel SW-internal record costs one extra `push` in each file and no wire change. Do NOT widen `MessageHashAuthwitContent` (`authwit-content.ts:23-26`): it is the dApp-facing `AuthwitContent` union and a widened shape would let a dApp pre-attach a `message_hash` action decorated with plausible-looking consumer/args the wallet never verified. Binding: the estimate reuse entry (`operation-estimate-reuse.ts:53-82`) is the object that already ties "what the popup saw" to "what confirm sends"; add `discoveredHashes` there. On a reuse hit the bound is exact. On a miss (`dapp-send-executor.ts:658-706`) the rebuild recomputes; compare hash sets and fail closed on drift — the user re-opens and sees the new list. Embedded-fee ops skip discovery on both legs (`:694-699`) and the estimator never runs for `default_entrypoint` (NO_FROM discovers at confirm only, `:785`) — those show no discovered list and the card should say so ("Authorizations resolved at send") rather than imply an empty set.

**(D) Delta envelope.** Index-aligned `ApprovalDelta[]` (§1 Phase 1), mirroring `estimateIds` (`spec.ts:111-114`) which is already the precedent for popup-privileged, index-aligned, off-wire data. The SW materializes with `materializeRequest` (`materialize.ts:54-107`) — it already produces exactly the draft the popup builds at `index.vue:262-333` (same switch, same embedded-fee rule) — so no new code path, and the silent and approve legs finally share one materializer as its header promised. "Reject payloads without `session`" = `DiscoveryPayload` (`spec.ts:93-95`): the only `approveInteraction` caller is `execute/index.vue:441`; discover/capabilities use `resolveInteraction`; so the throw breaks nothing. `origin` must NOT be popup-supplied: it is a `LocalTxOrigin { type, name? }` (`transaction-origin.ts:18-21`) that lands in the journal and tx records; the session row already carries `dappMetadata.name` (`dapp-session/spec.ts:50`), sanitized at persistence (`background.ts:771-776`). Take it from there.

**(E) F-18.** The verify window is informational: `handleSessionEstablished` returns `true` after opening it (`session-established.ts:142-154`), so message dispatch (`background.ts:396-399`) never waits for the user. Two consequences drive the design: (1) the *reconnect rate* must be throttled at the auto-approve branch (`:650-654`) — that is the only place a flood can be slowed before it becomes a live session plus a window; (2) the *window* reservation must be non-blocking for establishment, or a queued second tab would have its messages stalled behind tab 1's verify window and the two-tab cells would hang (B-13 gates dispatch on this promise).
- Bucket at the auto-approve branch, keyed by `origin` (the seed says per-origin; `origin|chainId` would double a multi-chain dApp's flood budget; multi-chain concurrency is preserved because capacity ≥ 2). Values: capacity 3, refill 1 token / 20 s, queue bound 4 per origin. A reload loop at 1 Hz gets 3 immediate approvals, then one every 20 s while ≤ 4 sit queued; excess is `rejectDiscovery`'d (the dApp re-broadcasts). Queued entries are re-checked with `rejectIfExpired` when dequeued (`:690-701`) — the SDK's 60 s window (`discovery-queue.ts:16`) means anything queued longer than ~55 s is dead on both sides; with 4 × 20 s the last queued item is served at ~80 s, so the effective queue is 2 (bound stays 4 as a memory cap; document that the last two are expected to expire under sustained flood).
- Verify-window reservation: per-origin cap 2 open windows, global 8, release on `WindowPort.onRemoved`. Under cap → open inline (today's semantics, pin unchanged). At cap → enqueue `{sessionId, url}` and return `true`; on release, dequeue, check `isSessionLive`, open; open failure → `terminateSession`. This is "queued/reserved, never dropped". Do not route through `WindowManager.openAndAwait`: it imposes a timeout that CLOSES the window (`window-manager.ts:81-84, 218-222`) and rejects on user close — both wrong for a fire-and-forget informational window. Inject a `WindowPort` into `SessionEstablishedDeps` (recon option b), reusing the same port `WindowManager` is built on.
- Waiter bound (`:667-671`): 8 per `dedupeKey`, reject-new beyond, decremented in `awaitPendingPopupDedupe`'s `finally`.
- Sequential two-tab cells: handshake 2 happens after `approveVerify` awaited window close (`popups.ts:164-170`), and the bucket holds 3 tokens, so neither the bucket nor the reservation ever engages; `cold-wake-discovery` does one handshake. The three named cells use `connectPlayground` once and never reconnect.

**(F) Flood e2e.** `waitForPopup` snapshots pre-existing targets by URL (`popups.ts:35-40`), and every verify URL is unique (sessionId + hash), so it can find one new window but cannot count N. The cell should not use it for counting: fire N=12 reconnects from N tabs opened in a loop (each `openPlayground` + `pg-btn-connect`, no await on verify), sleep a bounded window (~5 s), then count `browser.targets()` whose URL includes `#/windows/verify` and assert `≤ 2` (per-origin cap) while `pg-status` on the first 3 tabs reaches `connected` and the rest either connect within the refill horizon or show `disconnected` (never hang). Then close the open verify windows via `approveVerify` and assert a queued one opens (`waitForPopup` works here because the queued URL is new). Precondition: one prior `connectPlayground` with `alwaysTrust: false`.

## 3. Security and adversarial considerations

- **F-02 attacker (connected dApp, transactions grant).** Wins today by naming a canonical method the popup does not recognize. After: unrecognized names show every argument indexed; recognized names show ABI-labelled args; a 4-arg `transfer` with a foreign `from` renders it. What stays trusted: the ABI-derived labels are the wallet's own descriptors, not the dApp's `name` (name↔selector is bound at `tx-request-builder.ts:576-578`, unchanged). Fail closed: any arity or projection mismatch → unverified, never a partial "To/Amount". Discovered authwits: the list comes from the wallet's own simulation, never from the dApp; a reuse miss with a changed list aborts.
- **F-16 attacker (compromised same-extension popup).** Cannot substitute operations, cannot forge `origin`, cannot approve a discovery-shaped id. What it can still do: choose `feeSettings` (it could pick the priciest method — the user picked it in the honest case anyway), supply a wrong `previewedInterface` (still cross-checked at `service.ts:745-749`), or hand an `estimateId` for a different op (the fingerprint ladder rejects, `operation-estimate-reuse.ts:126-128`). Fail closed: length mismatch, session-less payload, fence/profile drift all throw before `executeOperations`.
- **F-18 attacker (connected origin looping reloads).** Slowed to one approval per 20 s after a burst of 3; verify windows capped at 2 per origin; waiters bounded. What stays trusted: the profile binding and the per-session hash (B-06) are untouched; a queued window still shows its own session's emojis. Fail closed: a queued open that fails terminates the session; a dead session is never shown a window; rejected discoveries get an explicit `rejectDiscovery` so the SDK map never leaks (same reasoning as `background.ts:632-641`).

## 4. Risks the driver's plan is likely to miss

1. **Naive delta merge.** If the delta is applied by spread (`{...materialized, ...delta}`), a compromised popup sets `accountAddress`, `exec`, `opts.from` or `executionMode` through the "delta". Apply field-by-field per kind; never spread.
2. **Discovery divergence on `send_transaction`.** `estimateOperationFee` runs `estimateWithDiscovery` for BOTH send kinds (`dapp-send-executor.ts:274-283, 292`), but `executeSendTransaction` confirm uses `buildAndEstimateValidated` with no discovery (`:489`), and the reuse stash excludes it (`:307-313`). The card would show discovered authwits that confirm never adds (the estimator header at `discovery-aware-estimator.ts:4-6` even claims this path can't reach it — it does). Either suppress the list for `send_transaction` or route its confirm through discovery; suppression is the smallest change and must be pinned.
3. **`previewedInterface` still needs the executor cross-check** (`service.ts:745-749`): the popup fetches it via `previewTokenMetadata` against a contract the dApp named; a buggy popup can still map the wrong address. Keep the check; the delta only removes the cast.
4. **Reservation vs the two-tab cells.** If the plan makes `handleSessionEstablished` await a queued window open, B-13's dispatch gate stalls the second tab's messages until the first window closes; `session-tabClose` (tab 1 closed at `:38`, so its window may still be open) would hang. Establishment must not await the queue.
5. **B-13 pin drift.** The "failed open terminates" pin (`session-established.test.ts:85-91`) spies on `chrome.windows.create`; moving the open behind a port changes the spy target — re-express the pin, do not delete it, and add the deferred-failure variant.
6. **Stale marker after queueing.** `pendingVerification` is cleared in `finally` (`:166-168`) — fine — but a queued verify open must not read the marker later; capture `isReconnect` at enqueue time.
7. **Zero-token reconnect with the SDK's 60 s window.** A queued reconnect served after 55 s is rejected by `rejectIfExpired`; a plan that only slows without expiring leaves the SDK's `pendingDiscoveries` entry live until the SDK times out.
8. **Fresh-connection path double-counting.** A first-time connect also yields a verify window; if the reservation counts only reconnect windows, a flood of fresh `(origin, chainId)` pairs (cap 4 per origin at `:751-764`) plus reconnects could exceed the intended per-origin window count. Count all verify windows in one reservation.
9. **`feeEstimate` unmarshalling.** `TransferFeeEstimate` crosses the RPC as JSON; `args: Fr[]` must be stringified in the SW record (the `messageHash.toString()` idiom at `discovery-probe.ts:85`) or the card gets `{}`.

## 5. recon.md corrections

- `discovery-aware-estimator.ts` and Part 1's estimator row imply `send_transaction` never reaches discovery; `dapp-send-executor.ts:274-283, 292` routes its ESTIMATE through it — only the CONFIRM skips it (risk #2 above). Recon's "the list exists SW-side today; only the drop points change" is true but the bound is not, for that kind.
- Part 1 lists the pair as `{consumer, innerHash}` only; `CallAuthorizationRequest` also carries `msgSender`, `functionSelector` and `args` (upstream `.d.ts:19-40`), so the card can show the caller and arguments of a discovered authorization, not just an opaque pair.
- Decision point 6 frames `WindowManager` as a reuse candidate; its timeout closes the window and user close rejects (`window-manager.ts:81-84, 192-203, 218-222`), which is the wrong contract for verify. `WindowPort` is the right reuse.
- Part 2 says the verify window "bypasses" establishment gating; more precisely establishment RETURNS true after the open, so any design that awaits a queued open changes B-13 semantics (risk #4).
- Open question 5 ("L5 layer rule") is confirmed: `biome.json` has no override for `src/utils/**`; the plan must not claim a lint boundary for the vocabulary module.
