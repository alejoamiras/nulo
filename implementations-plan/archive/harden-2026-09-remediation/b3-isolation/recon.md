## Decisions the plan must make (mapper evidence)

1. Post-B3 "degraded" widens from imported-accounts-only to PXE + dApp sessions: `providePxeStoreKey` with no DEK → `undefined` → raw `PXE_STORE_KEY_MISSING` on every PXE op for an UNLOCKED profile (`client.ts:175`, `chain-runtime.ts:144-146`), contradicting rule A4 ("derived funds stay reachable", `service.ts:637-641`). Needs a real surface, not the toast.
2. `deriveDappSessionMacKey` on a missing DEK must THROW (→ `verifyOrDrop`'s hide branch, rows survive a later good unlock), never derive a placeholder key (→ every session quarantine-deleted). Signing sites need a mapped error like the fence's "Wallet is locked".
3. `provisionChainStoreKey` same-generation re-provision with different bytes would silently swap the key under an open store (`pxe/service.ts:802-805`): add a byte-equality guard.
4. Restore ordering (`full-backup-restore.ts:423-434`, pinned by `useFullBackupImport.test.ts:552-578`): a degraded `finalizeRestore` leaves `restoreAccountStateStage` without a key — absorbed by the finished-with-errors screen (`stages.test.ts:490-502`); every other degraded path has no absorption.
5. `dapp-session/service.test.ts:39-47` and `service.composition.test.ts:39` stub the derivation with a per-profile key unrelated to any master/DEK — blind to F-06 by construction; the plan adds a real-derivation cross-verify test (same master, different DEK → different key; same master+DEK → same key; missing DEK → throws).
6. Pre-production, no migration: existing PXE stores become unreadable (crypto-erase, `pxe-store-key.ts:11`), existing session MACs quarantine-delete on first read (dApps reconnect); legacy `Authwit` rows without provenance are kept-but-hidden by the codec unless swept — sweep them once via `purgeMalformedRows` (already imported in the service, `:440-444`).

## Collision / dedup risks

1. Three hand-rolled `master ‖ dek` blocks unless one primitive is extracted (and `macKeyV3` re-expressed on it under `entropy-mac.test.ts`).
2. The auth-registry restore dedup key must widen to `(profileId, chainId, account, hash)` in the same change as the schema.
3. Journal: reads gated by the active profile, writes removed from `rpcMethods` — do not gate the writes on the active profile (fence-captured `profileId` may differ).
4. Same address across profiles/chains is a designed-for state (`account/spec.ts` composite identity); the tuple is `(profileId, chainId, account)`.
5. A SW↔offscreen Port would re-derive `background/{client,service}.ts`; if pursued, adapt that shape for `provisionChainStoreKey` only.
