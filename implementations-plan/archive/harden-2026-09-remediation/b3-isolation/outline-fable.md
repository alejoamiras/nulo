## 2. Positions on the open asks

**A — degraded-session UX.** Today a DEK-less session fires `onImportedKeysDegraded` (`profile/service.ts:646,795,2633,2694`) and the popup shows one LONG toast "Imported accounts unavailable" (`app.vue:184-190`); nothing else changes because derived funds stayed usable (`entropy-mac.ts:25-26`). After the change every PXE-backed surface fails, so that toast becomes false. Position: (1) the provider THROWS a single recovery-mode message rather than returning `undefined` (`runtime.ts:541-544`), so the gas card (`GasBalanceCard.vue:67` / `FeeSettingsCard.vue:631` render `lastError`), token import and send all show the same sentence instead of the missing-key marker; (2) the toast copy changes to "recovery mode — export a backup and restore it"; (3) `ProfileInfo.recoveryMode` so a popup opened after the unlock renders a persistent `Banner` on Home — the event alone is lost for any popup not open at unlock time. Bearer restores always carry the DEK (`session-manager.ts:267,563`), so recovery mode is only reachable from a tampered/corrupt `dekSealed` or the passkey degraded path — a rare, attack-shaped state; backup/mnemonic export remain the repair path (`profile/service.ts:1007-1012`). Blocking the profile outright (the integrity-block screen pattern) is the alternative; I do not recommend it because export must stay reachable. Note the import consequence: `restoreAccountStateStage` (`full-backup-restore.ts:423-428`) needs the key, so a restore that lands degraded ends on the errors screen — honest, not silent.

**B — Port vs sender-check for F-14.** Sender checks only. Evidence: (i) the attacker in this finding is already a same-extension page (`consolidated.md:266`); `isTrustedInternalSender` admits every same-extension page (`sender-auth.ts:17-23`), so the mandated check closes only foreign extensions/content scripts — the exact-offscreen-URL narrowing above is what actually denies a forged response from a compromised popup, and it costs one line per listener; (ii) a `chrome.runtime.connect()` from the SW is delivered to every extension context with an `onConnect` listener, so a compromised popup can accept the same channel — the Port does not buy confidentiality against the stated precondition (worth a 5-line probe if Codex disagrees); (iii) size: `offscreen/client.ts` (165) + `offscreen/service.ts` (81) rewritten around Ports, `utils/offscreen.ts` (409) readiness/health semantics change (a live Port replaces PING/PONG, and the `requestAlreadyReady` bypass at `client.ts:111-133` interacts with reconnection after every SW restart), `KEEPALIVE` at `service.ts:77`, plus `client.test.ts` (618) and `service.test.ts` (306) and the whole network e2e suite as the blast radius — well over 1,500 lines for a Low. (iv) A compromised same-extension page already holds every popup RPC (`profile/service.ts:70-93`), so passive capture of the store key (`pxe/client.ts:198-200`) is not the cheapest thing it can do.

**C — non-popup internal callers of the journal write RPCs through the client.** None. `OperationJournalServiceClient` (`operation-journal/client.ts:35-67`) is constructed only in popup contexts (`app.store.ts:162`, `TokensView.vue:181`, `RecentActivityView.vue:224`, `activity.vue:39`, `journal/[id].vue:68`), and each of those calls only `getOperation`/`getOperations`. Every write goes through the in-process service: `execution-lane.ts:200`, `claim-helper.ts:140,256`, `dapp-interaction/service.ts`, `token/service.ts`, `gc.ts:135`, `reaper.ts:199`. `tests/e2e/fixtures/journal.ts` reads only. Removing the three is safe; see push-back 3 for the other two.

## 3. Threat model after the fix

- **F-06.** A sibling holding the shared master now also needs the victim's 32-byte DEK: in memory only while unlocked (`session-manager.ts:298`), sealed under the passhash at rest. Still trusted: SW process memory, WebCrypto HKDF, and the envelope MAC keyed by the same `master‖dek` (`entropy-mac.ts:12-15`) guarding `dekSealed`. New exposure: a storage writer who corrupts `dekSealed` DoSes the whole profile instead of only imported accounts (owner-accepted). Next target: the popup RPC surface, not the KDF.
- **F-07.** A hostile backup can now only plant or purge rows inside the `(profileId, chainId, account)` tuples it actually imported (provenance filter + threaded `profileId`); a sibling's deletion/reconcile cannot touch mine. Still trusted: the selected chain's node answer in `isAuthwitConsumable` (`utils/auth-registry.ts:51-57`) — a lying node on the right chain can still delete confirmed rows for that chain; B1's identity assert bounds which node, not its honesty. `reconcileAuthwits(txHash)` stays unscoped (hashes are chain-unique and the row already carries its profile).
- **F-11.** The popup sees only the active profile's rows and has no write path; the cancel desync (`transfer-executor.ts:106-112` swallow) is now reachable only in-process. Still trusted: every in-process caller and the reaper's cross-profile sweep — deliberately.
- **F-14.** Foreign extensions and content scripts are denied at every listener; forged responses require a sender at the offscreen URL. Still trusted, by documented boundary (`sender-auth.ts:4`): any same-extension page, which can still passively read the broadcast key. Accepted.

## 4. Where no-migration bites, and the cheapest honest handling

- **Authwit rows without `profileId`/`chainId`:** the stricter `AuthwitSchema` makes them schema-invalid; `EntityStorage` keeps-but-hides such rows (`operation-journal/service.ts:141-147`), so they vanish from every read, backup, sync and purge. Residue: `recordPendingAuthwits` computes `nextId` from decoded rows (`service.ts:162`) and may overwrite a hidden key — harmless debris replacement; `restore` uses `getKeys()` (`:489`) so it never does. Handling: nothing beyond the codec; reinstall locally (CLAUDE.md rule). No sweep.
- **Status flags keyed by bare address:** never read again (new tuple key); absence defaults to `true` (`service.ts:253`) and `syncStatus` rewrites the on-chain truth on the next sync. Handling: nothing.
- **MAC'd session rows under the v1 key:** first read after unlock fails verification → quarantine-deleted with the "tampered" log line (`mac-storage.ts:100-103,107-110`); dApps reconnect through the normal approval. Handling: nothing — this is already the designed path; the log wording is acceptable pre-production.
- **PXE stores under the v1 key:** `openChainStore` throws `WrongStoreKeyError` (`opfs-store.ts:163-166`), which nothing catches — the profile's PXE is unusable until the OPFS dir is gone. Handling: reinstall locally (the V11 comment already documents "state resets, not data loss"). Do NOT add wipe-on-wrong-key in this batch: a destructive action on an error path is a bigger decision than a pre-production reinstall.
- **Bearer sessions in `chrome.storage.session`:** unaffected — the bearer wraps master+DEK (`session-manager.ts:267-268`), not a derived key.

## 5. Push-backs / what Codex should challenge

1. **DEK mint at password change (`profile/service.ts:1030-1033`) is not in the seed but must change**: after Phase 1 it silently rotates the PXE key and every session tag. Refusal (my proposal) vs bump `pxeGeneration` + `clearProfileState` + drop sessions (re-key path). Codex: is refusal too blunt for a user whose `dekSealed` merely bit-rotted?
2. **`coordinator.ts:120`**: the seed says "pass `profileId`"; I propose `purgeForProfile(profileId)` because the tombstone snapshot has no per-address chain and the six sibling calls at `:123-129` already use the whole-profile shape. Codex: any reason to keep the address-scoped variant on the deletion path?
3. **`createOperation` and `countOperations` also have no popup caller** (same grep as ask C; `countOperations` is used only by `wallet-sdk/background.ts` in-process). Removing them too shrinks the surface to two reads. Codex: any reason to keep them RPC-reachable?
4. **Exact-offscreen-URL narrowing via a protected hook** (one override in `apps/extension/src/wallet/services/pxe/client.ts`) vs plain same-extension everywhere. It is the only F-14 change with teeth against the stated attacker; Codex should confirm `sender.url` is populated for Chrome offscreen documents and Firefox hidden windows before we rely on a prefix match.
5. **`ProfileInfo.recoveryMode`** is a wire-shape addition to an RPC result (not storage). Codex: is a transient toast plus the typed error enough, or does the persistent banner earn its ~25 lines?
6. **Shared `master‖dek` IKM helper** across `macKeyV3`, the PXE key and the session MAC key: three concrete callers vs "leave `macKeyV3` untouched". The envelope-MAC pin in `entropy-mac.test.ts` makes the refactor provable; Codex should say whether touching the envelope MAC in a batch that does not need to is worth the dedup.
7. **`reconcileAuthwits(txHash)` left unscoped** — a hostile backup's pending row with a foreign `txHash` still gets confirmed for the importing profile's own tuple. Bounded by the provenance filter; Codex to confirm it is not worth a profile compare.
8. **Threat-model comment drift**: `entropy-mac.ts:25-26` ("a storage writer can't DoS the user's main funds") and `pxe-store-key.ts:9-16` become false after Phase 1 and must be rewritten in the same commit — a reviewer reading the old text would reject the fix.
