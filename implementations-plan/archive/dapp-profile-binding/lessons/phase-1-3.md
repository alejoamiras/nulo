Not resource pressure (17-20 GiB free throughout); correlates with (a) the concurrent `vitest-on-bun` session's 50-worker load on the shared host and (b) the owner's interactive presence in this session (interrupts can reap background tasks). ## The failing profile-switch spec — a deaf instrument, not a product bug (2026-08-24 night)

The new `session-profileSwitch` e2e red-lined at "pg-status → disconnected" (20s timeout) while the other 70 network specs stayed green. Diagnosis arc, with two instrumentation lessons baked in:

1. **First probe was blind by construction**: dumping the SW's persisted log ring (`chrome.storage.session` key `nulo:logs`) from the wallet PAGE returned `[]` — not because the SW logged nothing, but because `storage.session` defaults to `TRUSTED_CONTEXTS` access (SW-only); a page-context read legitimately sees nothing. An empty read through an access-gated API is not evidence. Probe via page-readable `chrome.storage.local` breadcrumbs instead.
2. **The breadcrumb exonerated the product in one shot**: a temp `storage.local` write at the top of the switch listener showed `{profileId: <B>, sessions: 1}` — the listener fired, saw the A-era session, and (by code path) terminated it. So the wallet side worked; the signal must be dying dApp-side.
3. **Root cause — the playground harness never subscribes to wallet-initiated disconnects.** The full upstream push chain is live: `terminateSession` → `InternalMessageType.SESSION_DISCONNECTED` → content script → page port `WalletMessageType.DISCONNECT` → `ExtensionWallet.handleDisconnect()` → `onDisconnect` callbacks (+ in-flight rejects with "Wallet disconnected"). But the playground's `status: "disconnected"` was only ever set by its OWN `disconnect()` — both pre-existing "disconnected" e2e assertions are dApp-initiated clicks, so the gap was invisible until the first wallet-initiated-disconnect spec. Fix: subscribe `wallet.onDisconnect` after `confirm()` (apps/playground/src/lib/wallet.ts), mirroring the explicit-disconnect state reset. The subscriber is idempotent vs dApp-initiated disconnects via a status guard.

Durable lesson: when a NEW spec asserts a signal class no prior spec ever asserted, suspect the harness's ears before the product's mouth — and prove the emitting side with a breadcrumb before touching the product.

## Drain-gate wedge against a soak loop (2026-08-25)

The relaunched battery sat 60+ min in its pre-stage `drain()` — the gate demanded the co-agent worktree (`vitest-on-bun`) be fully process-free, but that session runs a unit-test SOAK LOOP whose iterations respawn within seconds, so a 60s poll never observes zero. Diagnosis was masked by stale logs: the battery's per-stage logs from the PREVIOUS run made it look mid-audit (always clear or timestamp-check stage logs when relaunching a resumable chain). Resolution, logged as an autonomous validation-orchestration call (no codex needed — not architecture): the goal's hard rule is only "never two NETWORK-e2e suites concurrently", and the empirical record showed the full 73-spec suite scoring 70/73 (real failures only) alongside the same soak, plus two single-spec repros green under it with no gate at all. The gate was narrowed to network-suite exclusivity (any `e2e:agent`/anvil/aztec owner OUTSIDE this worktree), unit-vitest host load tolerated. Durable rule: serialize on the RESOURCE CLASS the rule protects (network suite ownership), not on "the other agent is idle" — an agent running an infinite soak is never idle.
