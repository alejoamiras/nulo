The 30-second version

ELI5 (the whole bundle): three small architecture cleanups left over from the big PR 8c bundle. Two are safe to do (rename one helper + consolidate four duplicate code blocks). The third (a clever performance optimization for an edge case) sounded like a quick win when I drafted it, but both auditors caught real correctness bugs. Skipping it, documenting why.

The big plot twist

What I told you yesterday vs what I'm telling you now — I originally proposed three changes including dropping the embedded-FPC override entirely (Phase A1 "lean upstream") and shipping the first-tx normalizer (Phase B). Both audits independently said:

- Phase A: don't drop. The override does real work that I described inaccurately in the v1 plan. dApps using upstream-recommended embedded fee patterns (FeeJuicePaymentMethodWithClaim, sponsored-FPC with claim_and_end_setup) budget against node.getCurrentMinFees(), NOT the * 1.5 default — so the cap aligns Nulo's gas settings with what those dApps expect. Dropping it would regress them.

- Phase B: don't ship. My proposed normalizer leaves publicInputs.gasUsed stale — and that IS dApp-visible (via TxSimulationResult.gasUsed, which dApps consume for fee-estimation UI). Plus firstNullifier carries multicall init semantics that no longer match the projected tree. Not the "invisible" inconsistency I claimed.

Translation: the auditors saved us from shipping two real regressions. Plan v2 reflects what's actually safe.

Phase A — consolidate the embedded-FPC maxFeesPerGas cap

Phase A   Consolidate (not delete) the override
fix-then-ship ~2 hours 4 sites → 1 helper
ELI5: we have the same 10-line block copy-pasted in 4 places. The block exists to handle a quirk of how some dApps budget for fees. We move the block into one helper so future-us only has to fix it once.
Human context: When a dApp pays for its own transaction (via an "embedded FPC"), it has to budget upfront for the maximum fee. Most dApps budget against the network's current minimum fees (getCurrentMinFees()). But our default fee calculation adds a 50% safety padding on top of that. Without an override, a dApp's budget would be ~33% short and the transaction would fail.

The override caps the wallet's maxFeesPerGas to match what the dApp budgeted (no padding). It's defensive code aligned with the upstream-recommended dApp pattern.

We don't change the behavior. We just stop duplicating it 4 times. Extract to a helper, fix the stale comments that still mention the long-gone 10^18 defaults, ship.

What we'll actually ship

One helper file fee/embedded-fpc-cap.ts exporting applyEmbeddedFpcGasCap(txRequest, fee, node). Behavior identical to today; 4 copies become 1 call. Stale 10^18 comments rewritten to describe the actual current purpose.

3 new unit tests for the helper, filling a gap codex flagged:

  1. fee.embeddedFeePayment === undefined → no-op (early return; gas settings unchanged)
  2. fee.embeddedFeePayment === "fjwc" AND no maxFeesPerGas → uses node.getCurrentMinFees() (no *1.5); other fields preserved verbatim
  3. fee.embeddedFeePayment === "fpc" AND maxFeesPerGas provided → uses provided values; node NOT consulted

The existing e2e tests (tx-sendTx-feePayer, tx-sendTx-sponsoredFpc, tx-sendTx-default) accept both "ok" and "error" outcomes — they won't catch budget regressions. The new unit tests pin the contract.

Phase B — skip the first-tx mixed-payload normalizer

Phase B   SKIP. Document why.
skip doc-only
ELI5: there's a niche performance optimization we COULD add — saving ~3-5 seconds when a brand-new account does its very first dApp simulation with a mixed (read + write) payload. We thought it would be ~50 lines of code; both auditors found it would actually break the dApp's gas estimate UI. Not worth it. We write up why we're not doing it and move on.
Human context: When a brand-new account does its first transaction, Nulo bundles "deploy the account" + "your actual call" into a single multicall. This produces a deeply-nested execution tree.

The optimization would have rewritten this tree on the fly during simulation, so a public-static prefix could be optimized separately from the private remainder. But the rewrite would leave publicInputs.gasUsed stale (still showing multicall's gas), and dApps read that field for fee estimation UI. So we'd silently over-report gas to every dApp that simulates a mixed-payload transaction on a fresh account.

The performance gain (saves 3-5s on a one-time edge case) doesn't justify the correctness compromise. Skip.

What we ship instead

A TRACKED-FOLLOW-UP entry in wallets-architecture-research/synthesis/implementation-plan-p1-p3.md describing:

  • The optimization we're not doing (first-tx mixed-payload normalizer)
  • The correctness issues that block the naive approach (publicInputs.gasUsed staleness, firstNullifier semantic mismatch, upstream tree-shape drift fragility)
  • The trigger to revisit (a real dApp pattern that frequently does mixed simulateTx before any send)

Plus a comment in service.ts's orchestrator explaining: "we don't normalize because publicInputs.gasUsed staleness would over-report gas to the dApp."

codex "The returned object becomes semantically mixed: projected privateExecutionResult, but full-multicall publicInputs / publicFunctionCalldata. That is observable through the public API, not just internal code."
opus 4.7 "publicInputs.gasUsed includes ctor execution gas. The 'normalized' result will over-report gas vs what an already-initialized account would. Not 'invisible'. The 3-5s saving on first-tx-only sims is not worth shipping a subtly wrong tree projection."
