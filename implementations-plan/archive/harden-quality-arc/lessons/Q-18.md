# Q-18 — single aztec-runtime artifact catalog

**Status:** ✓ DONE. Squashed to `dev-quality` @ `9205fd8` (PR #191). Gate: full network `28467534955` + smoke + quality; aztec-runtime 34 units.

## What shipped
New `packages/aztec-runtime/src/pxe/artifact-catalog.ts` — single source of truth for the 12 compiled-in artifacts + their class ids (computed once, per-key cached). `known-artifacts.ts` + `note-schemas.ts` both resolve class ids via `getCatalogEntry(key)` instead of importing artifacts + calling `getContractClassFromArtifact` independently.

## Key lessons
- **The fix is structural, not a test.** The finding's hazard (note schemas keyed off a class id that diverges from known-artifact resolution) is now IMPOSSIBLE — both loaders read the SAME `getCatalogEntry(key).classId`. No code path can diverge.
- **Per-key cache, NOT eager all-12** (codex HIGH): note-schemas needs only 4 keys, so a transient failure hashing an unrelated protocol artifact must NOT break note rendering. `getCatalogEntry(key)` caches one promise per key; a key both callers request hashes once.
- **Byte-identicality requires preserving order + cache identity** (codex HIGH): `ALL_CATALOG_KEYS` keeps the known-artifacts map's 12-entry insertion order; note-schemas keeps its cached-map identity (same Map until reset).
- **Reset seam** (codex MED): `_resetNoteSchemasForTests` stays the single authoritative reset — it also clears the catalog so class ids re-resolve; a separate `_resetArtifactCatalogForTests` exists for catalog-specific use.
- **No real-artifact unit test possible in aztec-runtime** — no vitest config, no `@wonderland-token-artifact`/`@private-fpc-artifact` vite alias, + noir-contracts wasm. This is exactly why EVERY existing test here mocks the loaders. So the invariant is gated by: typecheck (structure) + the mocked `service.test.ts` (consumers) + **network e2e** (notes-viewer decode → real class ids must match deployed). Documented, consistent with the repo.
