## Oracle-FIRST is the whole game for a behavior-preserving concurrency refactor
Wrote characterization tests against the CURRENT inline scaffold BEFORE touching it — both slot paths' exact call order (`acquireSlot < claim < markJournal(simulating) < proveAndSend < deleteController < releaseSlot`) + `releaseSlot` fires on EVERY post-acquire throw (proveAndSend / recordTransaction / claim). Kept them byte-UNEDITED across the extraction. Green-before + green-after = the proof the `runInSlot` extraction preserved behavior. This is the concurrency-ordering analogue of the trust-boundary frozen-oracle discipline.

## codex adjudicated the scope DOWN (the recurring arc pattern)
The finding wanted `lane.withExecutionSlot(...)` + `recordTransaction` builder + `parseAztecPayloadParts`. codex (plan review) + main-leg agreed to SHRINK:
- Seam = a PRIVATE `runInSlot` on the EXECUTOR, NOT `withExecutionSlot` on the lane — the lane owns primitives (mutex/registry/claim/journal); a closure-runner on the lane would own executor control flow and weaken the lane-shaped-deps seam.
- Do NOT bake `markJournal(simulating)` into the template: the standard path marks it AFTER opts.from+parse (so those failures stay `pending→failed`), NO_FROM marks it at entry with NO post-simulating checkCancelled. A fixed template point changes both. Each path keeps its own checkpoint.
- DROPPED `buildAddTransactionArgs` (endpoint/fee/gas helpers evaluate INSIDE recordTransaction post-send — a pre-builder changes failure timing) and `extractPrimaryMethod` reuse (planner falls back to selector; inline extractors are name-only → selector-only calls would stop rendering "Transaction").
Lesson: on a concurrency/trust surface, the audit's job is to find the ~1 mechanically-safe extraction and DROP the rest as behavior-change traps.

## codex post-impl caught a real ordering regression the oracle missed
SHIP-WITH-FIXES: I'd hoisted the `primaryMethod` extraction BEFORE `runInSlot` → it ran BEFORE `acquireSlot`. Under large/adversarial `op.exec.calls` that delays the FIFO enqueue (a later request can overtake) and moves a throw out of the acquire-protected try. Fix: `runInSlot` takes a `getCalls` THUNK evaluated inside the try after acquire. Added a throwing-`exec.calls` oracle test that fails if it regresses (acquireSlot must be called + releaseSlot must fire). Lesson: a call-ORDER oracle that only asserts `acquire < claim` doesn't catch work moved BEFORE acquire — add an "acquire is the first slot-path op" pin (throwing input → acquire+release still fire).

## The smoke flake had a REAL PRODUCT RACE behind it — two fix attempts, don't attribute from memory
`security.test.ts > change password` failed on the documented `lockWallet` 60s flake (unrelated to the dApp-execution change; passes on every other arc branch). The saga + lessons:
- RED policy: re-ran once (still red). Then FIRST fix `c88179a`: I attributed it to a no-op `querySelector('[data-testid="header-lock"]')?.click()` (header not mounted after `router.back()`) and added `waitForSelector(visible)` before the click. **This was MISDIRECTED** — I trusted the memory note ("60s lockWallet wait") instead of reading the STACK TRACE. It failed a 3rd time.
- Confirmed via trace: the only 60s `waitForFunction` in the flow is `lockWallet`'s hash-wait; `extension.ts:934` in the trace is just the `patchPagePolling` wrapper all `waitForFunction`s route through (a red herring). So the click DID land (my selector-wait passed at 15s, the 60s hash-wait is what failed) — the redirect to `/popup/auth` simply never fired.
- codex xhigh root-caused a **real product race** (session `019f1ceb`): lock is `Header.vue:22-26` (set `isLogined=false` + fire-and-forget `lockActiveProfile()`); the `/popup/auth` redirect is EVENT-driven (`SessionManager.close()` → `onActiveProfileChanged(undefined)` → `app.vue:131-139` → `router.push`). A stale post-password-change `bootstrapActiveProfile` (`useProfileBootstrap.ts:63-77`) flips `isLogined=true` AFTER the lock → the route guard (`popup/index.ts:63-65`) bounces the auth push → hash never changes → 60s timeout. The session IS authoritatively cleared; only the UI redirect loses the race.
- SECOND fix `0548da2` (codex-recommended, TEST-ONLY): `lockWallet` waits on the authoritative `chrome.storage.session["nulo:core:session"]` removal (frozen `SESSION_STORAGE_ROOT`), then reloads if the redirect lost the race (a fresh popup derives locked state from storage). Strictly STRONGER than the old redirect check; no product behavior changed, no assertion weakened. All 3 gates green on `0548da2`.
- Lessons: (1) READ THE STACK TRACE before fixing a flake — don't attribute from a memory note (cost me a wasted CI round-trip). (2) A "known flake" can have a real product bug behind it — a fire-and-forget lock + an uncancelled post-auth bootstrap is a genuine `isLogined` race. (3) When the honest fix is in PRODUCT code but that's out-of-scope (trust-sensitive session/router), do the TEST-side hardening on the AUTHORITATIVE signal + SURFACE the product bug — don't paper it over in product code, don't weaken the assertion.

## SURFACED: product race for auth/session owners (owner action item)
Lock immediately after a password change can leave the popup showing the general page instead of `/popup/auth`, because the post-change `bootstrapActiveProfile` isn't serialized/cancelled against the lock and can re-set `isLogined=true` after `SessionManager.close()`. Narrow real-world window (needs lock within the bootstrap window), and the session is genuinely cleared, so low security impact — but it's a real latent `isLogined` race. Fix belongs in product (serialize/cancel bootstrap vs lock, or make the guard re-check authoritative storage state), OUT OF SCOPE for the Q-15 execution refactor. Tracked here for a dedicated fix.
