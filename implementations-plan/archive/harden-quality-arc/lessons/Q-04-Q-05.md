# Lessons — P15 (Q-04 OperationPolicy + Q-05 Capability strategy) · TRUST-BOUNDARY

Landing in gated increments. **Q-05 capability-coverage strategy ✓ merged `ce488a5` (PR #211).** Q-04 + the Q-05 grant-path residual remain.

## Resolve a permission-semantics conflict against the arc's OWN scope rule, not by fiat
codex's blueprint audit surfaced two real coverage drifts (`contractClasses` field-widening, `data.addressBook`) where the approved meta-plan said "fix (fail-CLOSED)" but codex said "preserve + surface." I first surfaced it as an owner decision (correct — it's a dApp-permission-semantics hard limit). Then the deciding evidence: both drifts are an **already-filed, named follow-up finding (`wallet-sdk-capability-field-diff`)** referenced in `dispatcher.ts` comments + `wallet-sdk-implicit-account-grant/plan-v3.md` — and it is **NOT one of the 22 quality-arc findings**. So fixing them in P15 = *scope beyond the 22 findings* = a HARD LIMIT. That makes **preserve** scope-*required*, not a judgment call. Lesson: when a surfaced permission decision has a scope dimension, check whether the "fix" belongs to a different tracked finding — the arc's scope boundary often resolves it without an owner round-trip. Preserve the drift, PIN it (`(DRIFT PIN)` characterization tests), let the refactor prove it didn't move.

## Parse-once can't naively narrow to `Capability[]` — unknown-type caps must survive
The finding says "parse once to `Capability[]`." But codex flagged (and the code confirms): unknown-*type* wire capabilities must reach the popup and render **default-off** (`popup/windows/capabilities/build-items.ts`). A bare `as Capability[]` would drop them (behavior drift, hides the warning path) OR coercing malformed known caps (defaulting a missing `scope`/list to `"*"`) is a fail-OPEN. So "parse-once" = a **known/unknown split**: known types are trusted as their variant (one boundary cast), unknown types keep the type-only default. Never filter or coerce at a capability trust boundary.

## The exhaustive discriminated switch is the cast-killer + the fail-safe
`isCapabilityCovered(cap: Capability, …)` switching on `cap.type` narrows each branch to the variant WITHOUT per-branch casts (the discriminated union does it). Making it **exhaustive over `Capability["type"]`** (all variants as `case`s, no `default`) means a NEW capability variant is a COMPILE ERROR until it's classified — so a future type can't silently default to covered (fail-open) or not (spurious re-prompt). Pair with a typed `grantsOfType<K>` accessor (one internal cast) so the existing-grants side is cast-free too. Net: ~10 scattered `as unknown as XCapability` casts → 2 well-placed ones, behavior byte-identical.

## Don't unify authz mirror pairs that aren't mechanically equal
The finding wanted one table for parse/covers/delta/**merge/enrich/check**. codex enumerated the dispatcher-coverage ↔ scope-checker (`method-scope-checkers.ts`) mirror pairs and found several are NOT mechanical: `createAuthWit` is an `accounts` method that also consumes `simulation.transactions` + `transaction` grants (cross-type coupling); `simulation`/`transaction` have wrapper coupling. **Merging two authz implementations is where a fail-open hides.** I did the SAFE slice (coverage/delta — the `covers` path) and deliberately left the enforcement (`check`) path in `method-scope-checkers.ts` untouched. Ship the contained, provable win; don't force the risky unification the finding's wording implies.

## The equivalence oracle is most of the safety net — extend it, don't rebuild it
The existing 142-test bypass suite (`dispatcher.test.ts` + `scope-enforcement.test.ts`) already pinned most allow/deny verdicts. P15.0 = ADD the 2 coverage-side drift pins (the specific gaps codex named), not rebuild a matrix. Then the refactor's proof is simply: that suite + the full 2704-test extension suite stay green with the frozen `method-descriptors.test.ts` byte-UNEDITED. For a trust-boundary refactor, "all pre-existing authz tests still green + oracle unedited" IS the behavior-preservation proof.

## Gate economy at a trust boundary
The loop mandates units + smoke + FULL network per PR. For a behavior-preserving type refactor the network e2e mostly re-proves unaffected flows — but per the trust-boundary rule the REAL authz proof is the frozen oracle + the adversarial-bypass suite (green + oracle-unedited), which is cheap and ran first. Land the increment when both the cheap authz proof AND the mandated full gate are green.

# Q-04 (OperationPolicy core) — merged `aad2197` (PR #212)

## "Share the type" often means MOVE-DOWN + REUSE, not create
The finding asked for a shared `DraftOperation` + `assertExecutableOperation`. Grep first: **the popup already built both** (`operation-validation.ts:72`, `types.ts`) — they were just stranded in an upper layer the materializer couldn't import from. So Q-04's core was a behaviour-neutral *relocation* down to `@nulo/wallet-bridge` (beside `Operation`) + thin re-export shims to keep the popup's imports/tests untouched. Always check whether the abstraction the finding wants already exists somewhere the layering hid it.

## Retype an assertion to NARROW, to kill a consumption cast
The erasure was `operations.push(materialized as unknown as Operation)`. The fix wasn't to validate harder — it was to give the producer (`materializeRequest`) an honest return type (`DraftOperation`) and retype the existing guard `assertSilentExecutable(m): void` → `(m: DraftOperation): asserts m is Operation`. After the assertion the compiler treats the value as `Operation`, so the push needs no cast. A `void` invariant-check that already runs at the right spot is often one signature away from being the cast-killer.

## Preserve a security-SPECIFIC message; don't merge it into the generic shared helper
Tempting to point the silent path at the shared `assertExecutableOperation` (generic "missing feeSettings" throw) and delete `assertSilentExecutable`. But the silent-path guard carried a DISTINCT drift-alarm message ("isConfirmationNeeded gate broken or bypassed") — a security signal that a permission gate was bypassed, not just a missing field. I kept `assertSilentExecutable` as its OWN narrowing assertion with that message (the popup uses the shared one). Two callers can share the TYPE-narrowing shape while keeping different diagnostic messages; don't collapse a security-specific signal into a generic one to save a function.

## Incremental typecheck-green steps for a multi-file trust-boundary refactor
Split into committable green checkpoints: P15.2a (move the types down, behaviour-neutral, commit) → P15.2b (retype the materializer + swap the cast, commit). Each `typecheck:all=0` + touched-package tests green before the next. When the retype tightened `MaterializedOperation`→`DraftOperation`, exactly one test broke (accessing `.accountAddress` on the now-precise union) — a precise signal, not a cascade, because each step was small.
