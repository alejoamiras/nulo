## What shipped
New Buffer-free `bytesToHex` / `toBase64` / `fromBase64` in `packages/wallet-core/src/utils/encoding.ts`; 6 of 8 cited sites routed through them. Dropped the `Buffer` dependency from the migrated paths (the finding's actual goal).

## Key technical lessons
- **`wallet-core` is deliberately Buffer-free** (`random.ts` header). The canonical impl MUST use `btoa`/`atob`/native, not `Buffer.from`. This turned out to be a feature, not a constraint: btoa/atob output is byte-identical to `Buffer` base64 for valid I/O, so the dedup also delivers the "drop the polyfill" win.
- **Base64 decode is the trap.** `atob` is STRICT (throws on `"____"`/`"Zm$9v"`/extra-padding/base64url); `Buffer.from(_,"base64")` is lenient. They only diverge on MALFORMED input. So:
  - The one site decoding untrusted input (`full-backup-helpers`) already used `atob` → byte-identical incl. edge behavior.
  - Crypto sites decode their own (always-valid) ciphertext → safe.
  - **Deferred** `password-secret-box`'s 2 decodes (guard decode sits outside the `try`; atob-strict would change the corruption→`null` contract — needs a security-sensitive restructure, out of scope for a light dedup) + 5 base64 decodes NOT in Q-09's instance list (`profile/service.ts`, `useFullBackupImport.ts`, `session-manager.ts` — codex-flagged, follow-up).
- **`String.fromCharCode(...bytes)` RangeErrors on large inputs** — chunk the latin1 build (0x8000) for `toBase64`.
- **`fromBase64` must return `Uint8Array<ArrayBuffer>`** (not bare `Uint8Array`, which TS widens to `<ArrayBufferLike>`) so `crypto.subtle.importKey`/`digest` accept it. `new Uint8Array(n)` is factually ArrayBuffer-backed — no cast lie.
- **`.buffer` whole-buffer semantics**: `password-secret-box` encodes `Buffer.from(x.buffer)` (whole backing buffer, not the logical view). Preserved verbatim via `toBase64(new Uint8Array(x.buffer))`. Test pins it with an **offset view** (a full-view test is trivially true).
