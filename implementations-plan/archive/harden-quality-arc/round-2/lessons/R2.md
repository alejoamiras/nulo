# Lessons — R2 (Q-15 lock/bootstrap product race)

Merged `91c116d` (#237). The product-code fix round-1 deferred (`../lessons/Q-15.md` §26-27) — round-1
hardened only the smoke test; R2 fixes the race itself.

## The fix, and why the re-read is authoritative
`bootstrapActiveProfile` (and `hydrateKnownProfile`) re-read `getActiveProfile()` right before the
`isLogined = true` write and only flip it on if the active profile is still the one we bootstrapped.
The load-bearing insight (codex `019f1f44`, verified against source): **`getActiveProfile()` and
`lockActiveProfile()` both run inside the profile service's `runExclusive` mutex**
(`profile/service.ts:150,431`). So a re-read serializes BEHIND an in-flight lock and observes the
COMPLETED lock (session cleared → `undefined` ≠ our profile → skip). "The lock wins" in every
interleaving: lock-before-read → undefined → skip; read-before-lock → set true, then the lock event
sets false. Single-threaded JS means the `await`→`if`→write runs with no interleaving.

## Codex corrected the design's framing (adopt the better signal)
My draft called session STORAGE authoritative. codex (HIGH): storage is a persisted MIRROR; live
authority is `SessionManager.activeSession` (they diverge on passkey-restore, `session-manager.ts:348`).
`getActiveProfile()` reflects the LIVE session, so approach A already uses the right signal — approach
C (route-guard storage-presence check) would have used the wrong one. Chose A over B (epoch counter,
over-broad) and C. Returning a `boolean` ("bootstrapped and still active") was codex's LOW suggestion —
adopted for a clean testable contract, even though no caller consumes it yet (`loadProfile`'s push
already self-corrects via the `isLogined` guard + route guard, so it was left untouched — touch-minimal).

## FAILING-TEST-FIRST caught a realistic-mock gap
The 3 race tests failed against current code (proving they catch the bug). Implementing the guard then
broke the EXISTING "flips isLogined to true" test — because its mock had `getActiveProfile→null` while
bootstrapping a profile, an UNREALISTIC setup that only passed because there was no guard. Fixed the mock
to return the just-activated profile (the real scenario). Lesson: a guard that reads back state exposes
tests whose mocks didn't model that state; update them to the realistic shape rather than weakening the guard.

## The CI flake was in change-detection, not the code
`quality-status` went red TWICE on `fatal: shallow file has changed since we read it` during
dorny/paths-filter's `git fetch --deepen` — an infra race in the CHANGE-DETECTION job, before any
lint/typecheck/unit ran (my code was never reached). A same-run re-run reused the bad shallow state and
re-flaked; a **fresh `workflow_dispatch`** (clean runner + clean clone) cleared it. Lesson: when a red is
in the paths-filter/checkout preamble, re-running the same run can reuse the poisoned git state — dispatch
a FRESH run instead. Do NOT edit the workflow's checkout depth to paper over an intermittent flake in a
feature PR (that's a separate CI-infra task).
