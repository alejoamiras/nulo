## What landed
- `token.restore()` → `nextNumericId` + `restoreRows`. The shared numeric cursor stays caller-side
  (`let id = await nextNumericId(this.tokens)`; `id++` inside `writeOne` AFTER the awaited write), so

  expression, now via the shared allocator.
- Retired the file's last `array_max` use and the direct `toRestoreError` import (now inside
  `restoreRows`). **This completed R1.4a's pre-placed `nextNumericId` import**, which had been sitting
  as a biome *unused-import WARNING* (not error → the R1.4a gate passed with it). An incomplete-refactor
  marker resolved exactly where intended.
- 2 restore tests added to the **composition** harness (`makeHarness` now also returns `api`): a
  shared-cursor consecutive-ids pin, and a failed-write pin (records `restoreError` **string** +
  cursor skips the failed id). `restore()` needs no PXE/simulate, so it sits within composition limits.

## The account decision (why account restore was LEFT hand-rolled)
`account.restore()` is per-row-loop-shaped and COULD adopt `restoreRows` (its distinctive pre-loop
dup-address whole-throw stays caller-side, exactly the helper's intended pattern). It was deliberately
left as-is because: (1) it's a **security-sensitive backup-import path** and decision #4 reserves
backup/restore for the owner's dedicated pass (preserve EXACTLY); (2) its by-id guards are **compound**
`profileId || chainId` (take explicit `(profileId, chainId)`), so `requireOwnedRow` (single profileId)
doesn't fit; (3) it has **no unit-test harness** yet, and the fpc precedent (R1.3a) declined to build
one for a helper adoption. The named R1.4b target was token restore; account consolidation belongs with
the owner's dedicated backup work, not a dedup PR.
