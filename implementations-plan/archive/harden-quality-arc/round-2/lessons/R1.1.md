## THE contract fix (the real lesson) — caught before ANY consumer
`restoreRows` started `void`-returning (`writeOne: (row) => Promise<void>`, push the input row on success). Then, prepping R1.2, I read `contact.restore`: it does **keep-id-else-random** and returns `{...contact, id}` with the POSSIBLY-NEW id. A `void` helper can only return the INPUT row → it would return the STALE id (the id before collision-reassignment) = a behavior change. **Fix:** `restoreRows<TIn, TOut = TIn>(rows, writeOne: (row) => Promise<TOut>)` — `writeOne` writes AND returns the persisted row; `restoreRows` pushes that on success, `{...input, restoreError}` on failure. This is exactly the `TIn→TOut` the Q-13 blueprint specified; I under-implemented it first, the code-read caught it.

**Lesson: when extracting a shared helper, read a REAL consumer's exact behavior before finalizing the signature** — not just the blueprint prose. The blueprint said `<TIn, TOut>`; I simplified to `void` and would have broken 5 restores' returned ids. Reading `contact.restore` (the first adopter) before merge surfaced it. Fixed on the branch (`f65ac5d`), re-gated, then merged.

## Adoption pattern proven (for R1.2–R1.5)
Guards: `const row = requireOwnedRow(await storage.get(id), profileId, "invalid id")`. Always-fresh id: `nextRandomId(storage)`. Keep-id-else-random restore: `restoreRows(rows, async (r) => { let id = r.id; while (await storage.contains(id)) id = getRandomHex(8); const w = {...r, id}; await storage.set(id, w); return w })`. Numeric-id restore (token/token-balance/auth-registry): `nextNumericId` inside `writeOne`.
