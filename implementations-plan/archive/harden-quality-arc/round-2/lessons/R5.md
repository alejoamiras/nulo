# Lessons — R5 (Q-01 durable-store codecs, batches 1+2) · deep, boundary

R5a merged `741d518` (#242, first-pass green); R5b merged `f636f6c` (#243, green after a REAL
canary catch). 11 stores across 10 consumers now read through injected zod row codecs with the
P19a decodeRow guarantees (validation-fail = kept-on-disk + read-undefined, never deleted).

## The canary caught exactly what the unit layer cannot — and that's the whole point
R5b's first cut passed 2833 unit tests and the 23-case corpus, then failed the real-proving
canary at transfers step 8: FOUR transfers succeeded, the activity list showed ZERO tx-cards.
Root cause: `AccountFeePaymentMethodOptions` and `TxExecutionResult` are NUMERIC enums — real rows
store `0|1|2`, my `z.custom(object-check)` false-rejected every live row, and the never-delete
policy dutifully hid them all. The unit fixtures fit my fabricated corpus row (`{kind:"embedded"}`
— a shape I invented); the REAL write site (`addTransaction`) stores the enum. **Corpus rows must
be derived FROM WRITE SITES, never invented** — the fix's corpus is transcribed from
addTransaction/updateTransaction literals. And when a schema-vs-runtime bug ships, the network
gate is the detector: re-run-once (it failed twice) → root-cause found MY code, not infra. The
RED policy's "re-run once then root-cause" ordering is what stopped a third blind re-run.

## Strictness direction is per-seam, and both directions appeared in one phase
- Storage reads: NEVER-stricter-than-written. `NetworkRowSchema` is deliberately laxer than the
  wire `NetworkSchema` (no RpcUrl refine/min(1)) — a legacy row must LOAD; the strict rules keep
  applying at add/update/restore. Enum fields are number-shaped (not `nativeEnum`) where the enum
  is `@aztec`-owned, so an upstream member addition can't false-reject stored rows.
- Trust stores: fail-closed is the SAFE direction. `DappSessionSchema` is EXACT on every
  access-gating field — a drifted session row hides, and the dApp must re-request.
- `z.custom` pass-through-verbatim is the tolerant-deep tool: it validates branched fields and
  CANNOT strip display fields (zod object schemas strip unknown keys — a silent data loss on the
  read→rewrite path that `.passthrough()`/custom avoids).

## Deferrals are surfaced rulings, not skipped work
profile store (a false-reject hides the VAULT — worse than any drift it catches; decision-#4
domain), session/config ValueStorage (a codec would ACTIVATE throw-on-drift in unlock/boot — a
failure-semantics change), and the RPC/dApp decoders (fail-open→fail-closed on the dApp seam, not
on the owner-authorized list) are all written into plan.md as owner questions with rationale.

## Ops lessons that cost real time
- **Commit before ANY branch operation.** A `reset --hard` while uncommitted R5a edits sat in the
  working tree destroyed them (replayed from the transcript's deterministic scripts); later,
  batch-2 edits landed on the WRONG CHECKOUT because a docs commit had switched branches. Both
  self-inflicted, both recovered, both preventable by the loop's own "commit eagerly" rule.
- **1Password agent outage** mid-phase killed commit signing AND SSH pushes. Per the standing AFK
  rule: per-commit `-c commit.gpgsign=false` (config untouched) + HTTPS pushes via
  `-c credential.helper='!gh auth git-credential'`; `--force-with-lease` against a bare URL has no
  tracking ref — use an explicit lease SHA. Owner: unlock 1Password; optionally backfill
  signatures on the handful of unsigned commits (they're on dev-quality; the #220 squash is
  web-flow-signed regardless).
