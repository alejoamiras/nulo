## War story #1 — the deletion deadlock (found by smoke, fixed by design change)
My first `init()` called `profiles.getProfiles()` unconditionally. When the offscreen boots BECAUSE of a deletion-triggered `clearProfileState`, the SW's deletion coordinator is awaiting that RPC while holding the ProfileService lock — the init-time getProfiles RPC back into the SW deadlocked the whole reset flow (the old code dodged it by only consulting profiles when legacy DBs existed). Fix: the orphan sweep is DEFERRED (void promise, error-logged), never on the init path; race-safe because the profile row still exists while its purge runs (the coordinator deletes the row last) and all removals are idempotent.

## War story #2 — the silent sqlite worker (the sibling lesson, extension-flavored)
`security-reset` kept failing at 40s+ (dev baseline: ~4s). Bisect + CDP probes pinned it: the kv-store sqlite worker LOADS (asset 200, no onerror) but NEVER answers `init` — its emscripten glue resolves `sqlite3.wasm` at runtime through the `locateFile` fallback that bundlers can't rewrite, requesting the BARE `assets/sqlite3.wasm`, which 404s in the packed extension (vite only emits the hash-renamed asset for the static `new URL` path). The failure is an unhandled rejection inside the worker → no error event → `AztecSQLiteOPFSStore.open` (whose protocol has NO timeout) hangs forever → the chain guard read never releases → `clearChainState`'s write waits forever → profile deletion wedges. THREE fixes shipped: (1) the `sqlite3mc-wasm-emit` plugin (unhashed copies — the accelerator repo's fix, ported); (2) a 30s bounded open converting any future silent worker failure into a loud, fail-closed, recoverable error; (3) the probe method itself documented here — SW-console CDP attach + storage-root census locates a wedged purge step in one run (the census shows which service's rows survive: ours stopped at `nulo:core:networks` → the per-chain PXE clear).
- Repro sequence that found it: `getContractInstance` (old-testnet sync) → KEY_MISSING → retry provisions → retried init opens the store → worker hangs → reset's `clearChainState` queues behind the stuck reader.
- Diagnostic breadcrumb: the offscreen target is CDP-attachable (`createCDPSession` + `Runtime.evaluate`) even though `target.page()` returns null for its `background_page` type.
