Aztec 5.0.0-rc.1 → rc.2 library bump

The wallet is built on Aztec's SDK, currently pinned at release-candidate rc.1. This bumps it to rc.2. You thought it'd be a clean bump — I double-checked the diff, and it's not trivially clean: rc.1→rc.2 is 187 commits and includes a few labelled "breaking" changes. The good news: those breaks are all in Aztec's internal node/protocol plumbing (things like how the network syncs blocks), and none of them appear in the code we actually call. So the plan is a careful bump — swap the version everywhere, prove it still compiles, tests pass, and — the real test — that real transactions still prove against a live rc.2 network.

Why this tier was chosen

mid. One genuinely HIGH-risk dimension: external coupling (the wallet's SDK must match the network it talks to). It's satisfiable — the proving helper auto-downloads the right version, and an rc.2 build exists as backup. We deliberately kept the riskiest bit — redeploying on-chain contracts — out of this arc (it becomes a follow-up only if the bump shifts contract identities). That scope cut is what keeps this mid and not deep. If the trial reveals deep compiler churn or a forced redeploy, we escalate that part.

Phases

Phase 1: Bump + install + typecheck

Change the version number everywhere (20 packages across 7 files), re-label the 2 small packaging patches, temporarily let the fresh rc.2 packages past the "wait 7 days" safety gate, re-resolve the lockfile, and check the TypeScript still compiles. This is the fast fail — if the SDK renamed something we use, we find out in minutes.

Proves itself by: a clean install (patches apply, lockfile resolves) + typecheck:all exit 0.

Phase 2: Tests + recompile + shift inventory

Run all unit tests, bump the Noir toolchain + git-tags, recompile the 3 bridge contracts, and measure exactly which contract identities shift (you expect: all of them). The old→new list becomes Phase 3's redeploy checklist. The PrivateFPC "conscious re-pin" test gets updated to the new values — deliberately, never silenced.

Proves itself by: test:all + lint + all 5 builds green, and a complete old→new identity inventory written down.

Phase 3: Redeploy the testnet contracts + re-pin + prove them live

Your call at the gate: the shift is expected, so we redeploy — with the same scripts that did it for rc.1. Check the testnet actually runs rc.2 first, redeploy the L1 portals (with the new rollup's addresses) and the L2 contracts (dripper, tokens, bridge, PrivateFPC), write the new addresses into the pinned manifests, then prove it all works live: a public bridge settles, a private fueled claim settles, a drip works.

Proves itself by: every live check green against the real rc.2 testnet — the deployed world and the code's pins agree again.

Phase 4: The protocol proof — native-proving network e2e

Run the end-to-end suite against a real rc.2 Aztec network with native (fast) proving. This is the one that actually proves rc.2 transactions work and the wallet↔network protocol still matches. We try the existing proving helper first (it fetches the right version on demand); only if that can't handle rc.2 do we swap in the rc.2-specific helper.

Proves itself by: the PR's network-e2e-status green with native proving required (a silent fallback to slow WASM proving is a hard fail).

Human context

"rc" = release candidate — a near-final version. Aztec ships these fast, so the wallet tracks them. Because rc.2 was published only days ago, our supply-chain rule (don't install anything younger than 7 days, to dodge just-published malware) would block it — so we make a temporary, tracked exception for exactly the Aztec packages, and a follow-up PR removes the exception once rc.2 is old enough. "Native proving" is a Rust helper that generates the cryptographic proofs ~10× faster than the browser fallback; the network test insists on it so we never accidentally "pass" on the slow path.

What the audits changed (the central story)

The two reviewers split the problem cleanly. Opus confirmed the network test deploys fresh contracts each run, so a shifted contract identity can't break that gate. But codex caught the other path: a separate check, verify:deployments, rebuilds the live faucet's contracts from pinned values — and it runs inside the build gate. So if rc.2 shifts contract identities, the build fails, and the live faucet would be broken. That means a shift is a hard blocker, not a "deal-with-it-later" follow-up. Codex's first pass rejected the original plan for exactly this. You then resolved it the direct way: the shift is expected, so the redeploy is part of this arc — Phase 3 executes it with the same scripts that handled the rc.1 cutover, and the PR only goes green once the live testnet and the code's pins agree again.
