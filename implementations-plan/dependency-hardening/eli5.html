Hardening our dependencies before something bites us

A plain-English walkthrough of the dependency-hardening plan, the decisions you need to make, and what we're explicitly choosing to skip.

Plan file: implementations-plan/dependency-hardening/plan.md 10 PRs (11 if Zod 4 in) Audited by Opus 4.7 + Codex 14-day age gate Aztec + Renovate descoped

The 30-second pitch

Our dependencies are old, and the npm world has had a rough year. Two structural changes do most of the work:

  1. Add a 14-day "cooling-off" window on new package versions. If a maintainer's npm account gets compromised and someone publishes a poisoned version, we don't install it for two weeks — way longer than the typical window for npm/security researchers to catch and pull it.
  2. Make our lockfile reviewable. Today it's a binary blob we can't read in PRs. After Phase 0, every dependency change shows up as a normal text diff that you can actually review for sketchy package names or suspicious URLs.

Everything else (the version bumps themselves) is just executing on the staleness backlog — phased so any single PR is small enough to revert. Renovate automation was in the plan but you've deferred it; the config is preserved in the plan file's §13 for whenever you want it.

Why this matters now

March 2026: axios got compromised. Someone stole a maintainer's npm token and published two poisoned versions. Within 2 seconds of running npm install, a cross-platform RAT (remote access trojan) was phoning home to a command-and-control server. Anyone whose CI happened to pull during the publish window — even briefly — was breached.

September 2025: chalk/debug. Same shape, different packages — both extremely common dependencies. Caught within ~6 hours because someone was paying attention. The cost to the ecosystem was still significant.

Bun shipped minimumReleaseAge in October 2025 specifically as the defense for this attack pattern. We're going to use it with a 14-day window — long enough that both attacks above (caught in ~6h and inside the publish window respectively) would be blocked with significant margin.

Phase 0

Lockfile migration + pin Bun

Low risk
In English

Our bun.lockb file is a binary blob — you can't read what's in it on GitHub. We're converting it to a text file (bun.lock) so every future dependency change is reviewable. Same content, just readable. We're also pinning the version of Bun used in CI (currently set to "latest", which is a footgun).

Why this is first: every later PR will touch the lockfile. If we don't migrate now, every dep PR is a binary-blob update we can't review. This unblocks everything.

Phase 1

Supply-chain age gate + audit check

Low risk
In English

Create a bunfig.toml that tells Bun: "don't install packages that were published less than 14 days ago." Also add a bun audit step to CI that warns when a known vulnerability is present in any installed package.

The trade-off: if a legit bug fix ships today, we don't see it for two weeks. If a malicious version ships today, we also don't see it for two weeks — by then it's been pulled. Aztec packages aren't in the allow-list (no carve-out today) because they're exact-pinned and not being bumped in this milestone, so the gate is moot for them anyway.

Low risk
In English

A. Zod 4 — in or out?
You asked if it's risky. My honest take: medium-risk but compartmentalized. ~10 files: messaging schemas, dApp RPC validators, content-script input validators, PXE messages, storage shape parsers. Main risks are (a) .errors shape changed (we may introspect it), (b) some methods renamed/removed, (c) extension-messaging's optional zod peerDep needs to read ^3 || ^4 during the transition. Mitigations: typecheck:all catches signature drift; smoke e2e catches end-to-end RPC parse failures; the changes are schema-localized — no service logic moves.
My recommendation: Pull in, as the LAST PR (after everything else is stable). Zod 3 is EOL eventually anyway.
B. TypeScript 6 — bump if vue-tsc supports it?
TS 6.0 was released recently. Each major brings new strictness. The blocker is whether vue-tsc 4.x (our Vue type-checker) supports TS 6. If it does, we bump. If it lags, we defer.
Recommended: Conditional bump. I'll verify vue-tsc compatibility before doing it.
C. Add bun pm scan alongside bun audit?
bun audit queries npm advisories. bun pm scan is a separate tool that scans the entire installed lockfile for known-bad packages (different data source / different surface). Belt-and-suspenders.
Recommended: Yes — add as a second advisory CI step. Cheap, different signal.
D. Write the CVE-on-Friday runbook into SECURITY.md in Phase 1?
When a CVE drops for a package within the 14-day gate, we need a documented procedure (temp allow-list the package, install, follow-up PR removing the allow-list). Draft is in plan §12.
Recommended: Yes — write it during Phase 1.
E. Q10 re-explained — out-of-scope CI hardening, in or out?
These three issues aren't npm-dependency problems; they're CI pipeline supply-chain holes Codex's audit caught:
  • release.yml:228,241 uses bunx --bun release-it@latest — every release pulls newest release-it from npm. If compromised, our next release builds with poisoned code.
  • setup-aztec/action.yml:40 does curl -fsSL ... | bash for the Aztec installer — no checksum, no signature.
  • actionlint.yml:62 does the same curl | bash pattern for actionlint.
The question is: tackle these alongside this milestone, or park for a separate "CI pipeline hardening" follow-up?
Recommended: Park. Different headspace, different validation pattern.
