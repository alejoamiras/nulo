Fee Estimation Speedup

Make the wallet's "estimating fee…" spinner — and the dead pause after you hit Confirm — dramatically shorter, by doing less redundant work behind the scenes. Nothing about the screens, the flows, or how fees are chosen changes. The full technical plan lives in the repo at implementations-plan/fee-estimation-speedup/plan.md.

Why it's slow today

On Aztec, the only way to know a transaction's fee is to actually run the whole transaction locally — a heavy cryptographic dry-run that takes seconds. The wallet can only run one dry-run at a time; they queue single-file. Today, one fee estimate runs two or three of these dry-runs, and when you confirm a dApp transaction the wallet throws all of them away and runs them again before it even starts proving. That's the wait you've been feeling.

What we're changing (five things, all invisible)

  • Stop re-doing the estimate when you confirm. The wallet already keeps Send-page estimates and reuses them at confirm; dApp approvals get the same treatment, with strict safety checks (anything changed since the estimate → it recomputes).
  • One dry-run instead of two for the default fee sponsor used everywhere except mainnet. We verified in the sponsor contract's source that the second run adds nothing there.
  • Let typing cancel stale work. Today, editing the amount mid-estimate leaves the old estimate hogging the queue. Cancellation stops it at the next checkpoint.
  • Delete a hidden network call the wallet makes before every dry-run and every proof, purely to print a debug log line.
  • Prep work for a bigger future speedup (details below), shipped as a pure refactor with zero behavior change.

What the audits changed — and why some numbers say "unchanged"

Two independent reviewers (Codex and a second Claude) attacked the first draft, and a third fresh Codex pass attacked the revision. All three reshaped it:

  • The mainnet fee contract genuinely needs its double dry-run — its code reads the transaction's gas budget internally. First draft would have broken it; it now stays exactly as is. That's why the mainnet row says "unchanged": correctness beat speed there.
  • A planned rewiring of how the wallet discovers required signatures turned out to save zero dry-runs in its safe form — while opening a subtle door for a malicious fee contract to get an auto-signed permission. It's cut from this plan entirely; only a tiny risk-free piece of its plumbing ships. It can return later, gated on real measurements this plan will collect.
  • The final pass caught a race that would have silently nullified the Confirm speedup (the cleanup that runs when a window closes would have thrown away the very estimate the confirmation was about to reuse — now there's an explicit hand-off), plus two narrower safety carve-outs: dApps that supply their own gas limits keep today's exact behavior, and a fee sponsor whose stored address was edited between estimate and confirm can never be paid at the old address.

Why the "mid" tier

One high-risk dimension (this touches how every transaction's fee is computed), but no novel territory — the reference implementation and every building block already exist and were mapped before drafting. Mid means: one plan plus a competing alternative, two independent audits, and a final fresh review before you approve.

The phases

Phase 0 — Preflight

Set up GitHub's new stacked-PRs tooling (with a plain fallback if it isn't available for this repo) and record today's baseline numbers.

Proves itself by: lint, typecheck and full unit suite green; the stacking decision written down.

Phase 1 — Delete the debug network call

Proves itself by: a repo-wide search showing it's gone, plus the full unit suite green.

Phase 2 — Cancellable estimates

Typing or closing the window stops stale estimate work at its next checkpoint (honestly: a dry-run already in flight finishes — it just can't start the next step).

Proves itself by: dedicated cancellation tests + full unit suite.

Phase 3 — One dry-run for the default sponsor

Proves itself by: tests pinning the exact dry-run counts, plus two real end-to-end transactions on a local network with real proofs.

Phase 4 — Reuse the estimate at Confirm (dApp)

The biggest felt win: Confirm goes straight to proving.

Proves itself by: tests for every way reuse must refuse (stale, wrong account, changed fees, changed network…), plus two end-to-end dApp transactions.

Phase 5 — Risk-free prep for the future speedup

Proves itself by: the existing behavior-pinning tests passing with zero changes — the proof nothing moved.

Phase 6 — Full validation + measurements

Proves itself by: the repo's full pre-PR gate, the smoke suite, the entire network e2e suite, and a recorded measurement table for the future decision.

Open questions (your call at approval)

  • Defer the bigger speedup? Both auditors say yes — collect measurements first. Recommended: defer.
  • Ship as three stacked PRs — quick wins → sponsor fast path → reuse? Recommended: yes.
  • Tiny fee-number drift. The sponsor fast path may show marginally different estimate numbers (same padding, same pricing basis). Does that still count as "no UX change"? Recommended: yes.
  • Keeping a signed, ready-to-send transaction in memory for up to 2 minutes after an estimate — settled: you asked for a shorter window; it dropped from 5 minutes to 120 seconds, everywhere (including today's Send page). Freshness itself is guarded separately: anything meaningfully changed (fees, pending transactions, network, the sponsor's address) forces a recompute regardless of age.
