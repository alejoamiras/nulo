Isolated Linker Store

Switch how Bun lays out installed packages so every workspace can only see the dependencies it actually declares — closing the "works by luck" gaps a shared pile of packages hides. The risk: a handful of our build tools assume the OLD layout. So they get fixed first, on the old layout, where nothing can break — and only then does the switch flip, one measured, reversible step at a time.

Implementation update — the headline changed, honestly. Measured on this machine, the new layout is not faster to install (1.22s vs 1.17s); the "7× faster" claim only materializes with an optional shared store (0.36s) that stays OFF in the committed config for supply-chain reasons. What the change actually buys is correctness: two undeclared dependencies found and fixed (one of them the source of a shipped database-engine file), six copy-pasted path-guessers replaced by one tested resolver, a permanent identity test, and a wallet-grade dependency refresh that retired 17 security advisories. The keep-or-abort call goes to the Codex gate on those terms.

Why the "mid" tier and a heavier gate

This changes install topology for a wallet's build — two risk dimensions run hot (blast radius across every build; supply-chain sensitivity of a full dependency re-resolution). Three independent auditors reviewed the plan: two in parallel (Codex + a second Claude), whose conditions were all folded in, and a final fresh-context Codex pass that acts as the approval gate — per your standing "resolve it with Codex to convergence" protocol.

What the recon found before any plan existed: six copy-pasted versions of the same path-guessing helper; one build step that locates a critical database engine via a package NOBODY declares (works today purely by hoisting luck); one script pointing at a package by its OLD name — dead code nobody noticed; and the contract-compiler config hard-wired to the old layout. Two of these were genuine pre-existing bugs, found because we looked.

Phases

PHASE 1 · SHIPS ALONE AS PR "B1"

Fix how tools find packages — before touching anything

One tiny shared helper replaces the six copies and the hard-wired paths; the two undeclared dependencies get declared; the dead script gets fixed; the contract compiler gets its mapping generated and verified instead of guessed. A new "identity test" then proves every special file is the RIGHT file from the RIGHT package — a proof that keeps running forever after. All of this is pure hardening: worth merging even if the switch is later abandoned.

Proves itself by: the full pre-PR battery + the new identity test + a clean strict install, all on the unchanged layout.

PHASE 2

Interrogate the shared store — in a sandbox, not the repo

The store's exact behavior is under-documented, so we test it on throwaway projects first: can it be turned off, what's the default, does it survive 5–10 simultaneous installs, kills mid-install, and two different patches of the same package. The result is a written risk memo — evidence, honestly labeled as evidence rather than proof.

Proves itself by: the probe matrix + the posture memo.

PHASE 3 · PR "B2" BEGINS

Flip the layout — with the dependency list frozen

The switch flips while the lockfile stays byte-identical, so if anything breaks it can ONLY be the layout. The gate is broad: both browser builds, the dev server (a specific blind spot an auditor caught), tests, and proof that the shipped extension bytes are identical to before.

Proves itself by: identity test on the new layout + full battery + dev-server boot + byte-identical WASM outputs.

PHASE 4

The one dependency re-resolution — reviewed like wallet code

First, expired exceptions to our 7-day new-package safety delay are removed (their own overdue TODO) so the safety net is real. Then the lockfile is regenerated once, and EVERY change is reviewed: checksums and sources — not just version numbers — must be untouched for the frozen Aztec packages, and anything reaching the shipped bundle gets a line-by-line package diff regardless of how innocent the version bump looks.

Proves itself by: the written review covering every change class + the full battery re-run.

PHASE 5

Measure, validate end-to-end, decide

Fresh-copy install timings confront the "7× faster" claim with real numbers; the full battery plus one real-network test round runs solo. Then the keep-or-abort decision — and aborting still keeps Phase 1's hardening.

Proves itself by: everything green including the network round + the timings table + the decision written down with its reasoning.

Decisions already made (via the convergence protocol)

  1. Fix-first beats bridge-first. A 10-line config bridge could fake the old layout — all three reviews steelmanned it and all three ruled it out: it preserves the disease (undeclared dependencies) and defers the same work. Kept only as a labeled emergency fallback.
  2. Flip-then-regenerate, not both at once. The two auditors split on the order; resolved: flip with the dependency list frozen (any failure is attributable), regenerate second. One root cause per step.
  3. The one flag still open for you: declaring @aztec/sqlite3mc-wasm at its EXISTING 5.0.1 pin (it's already in your tree — this just writes it down). Both auditors judged it sound and Codex approved it under your delegated gate, with a permanent test that keeps it locked to the copy Aztec's own packages use. Your objection window stays open until B1 merges.
