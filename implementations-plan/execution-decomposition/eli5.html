Execution Decomposition

The wallet's biggest, hottest file — the one that builds, proves, and sends every transaction — is 2,302 lines and contains four copies of the same "prove it, send it, write it down" sequence. This plan splits it into small, individually tested pieces without changing what it does. Every step is checked three ways: the automated test suite, a full end-to-end run on a local network, and a second AI model re-reading the diff for drift.

Why this tier was chosen

deep: blast radius is HIGH (every send flow in the wallet passes through this file) and the surface is security-adjacent (signing, proving, fees). Novelty and migration cost are LOW — it's our own code and no stored data changes shape. Two HIGH dimensions → deep per the rubric. Three independent plans were drafted (Claude main + Codex + Fable), consolidated with a decision ledger, contradiction-checked (7 fixes), double-audited, and finished with a fresh-context Codex pass. All three auditors: conditional approve, all conditions applied.

Phases

Phase 0: Take fingerprints before surgery (½–1 day)

Before touching anything, write tests that pin exactly how the current code behaves — including the weird corners (all 8+ reasons a cached fee estimate gets rejected, the exact text of cache fingerprints, fee-shape fixtures with distinct sentinel numbers in every slot). Also record one full green end-to-end run as the "known good" baseline. If a later phase changes behavior by accident, these tests scream.

Phase 1: Finish the contract-lookup helper (½–1 day)

A helper for "find this contract function / make sure this contract is registered" was started long ago, and the same lookup code got copy-pasted into 5+ places anyway. Finish the helper, delete the copies. Error messages stay byte-identical.

Phase 2: Name the boxes (1–1.5 days)

Functions currently return values as numbered lists — callers write built[7] and just have to know slot 7 is the fee. Several slots have the same type, so silently swapping two (say gas and fee) would compile fine and cost users money. This phase gives every slot a name (built.txRequest, built.nonce…) so mix-ups become impossible — plus a tripwire test with distinct values per slot to catch any swap made during the renaming itself.

Phase 3: One pipeline instead of four (1.5–2 days) — the keystone

The "prove → send → record → journal" tail exists four times. A helper file even promises a shared proveAndSend in its documentation — it was never written. This phase writes it for real and points all four paths at it. Differences between the paths (which accounts sign, how results are recorded) stay as explicit per-path data. Failure handling deliberately stays per-path — the audits proved the four paths fail differently today, and we're not changing behavior.

Phase 4 + 5: Move the two caches out (2 days)

Two self-contained subsystems live inside the big file: the fee-estimate reuse cache and the gas-balance cache. Each moves to its own file with its own tests (expiry, one-use rules, every rejection reason — including a security-relevant "wrong profile" check that today's tests would not notice losing).

Phase 6: Slim the big file to ≤1,200 lines (1.5–2 days)

Move the two big flow bodies (popup transfers; dApp sends) into their own executor modules with their own tests. Crucially, they receive their concurrency controls through an interface from day one, so Phase 7 can swap the machinery underneath without re-cutting them open. Tests also pin that the chain-identity safety checks still run on every moved path — the kind of deletion the local test network can't catch.

Phase 7: The concurrency seam (1.5–2 days, bounded)

The trickiest part — the choreography that queues transactions, lets you cancel mid-prove, and survives a service-worker restart — moves behind one "execution lane" module. Order-sensitive and unforgiving, so it goes last, when the gate pipeline is most proven. It carries a pre-agreed bail-out: if its gate fails twice, work STOPS and the decision comes back to you — the arc is already shippable without it.

Phase 8: Close (1–1.5 days)

Automated code review, a fresh adversarial Codex audit of the whole diff, docs, an RC build, and a manual QA script for you — including the authwit-revoke and registry-toggle flows, because that slice of the code has no automated end-to-end test today (your hands are its safety net).

Human context

The quality audit's number-one warning: this repo's most expensive pattern is the half-done migration — refactors that started, stopped midway, and left two ways of doing everything. This plan is designed against that fate: phases land as independent checkpoints, each leaves the code strictly better, and the riskiest piece is last so abandoning it orphans nothing. Total: ~9–12 focused days. One branch, one final PR, RC build + your manual QA before merge.

Open questions (the 4 Asks)

  • A1 — Is "≤1,200 lines" a hard rule? Recommendation: yes — if the leftover dispatcher keeps it over, the dispatcher moves too.
  • A2 — What evidence must a Phase-7 bail-out bring you? Recommendation: two failing gate logs, the parity findings, a root-cause hypothesis, and a recommendation.
  • A3 — Accept the byte-level residual? Structural fee tests cover shapes/amounts/ordering, but not literal byte-equality of every built transaction across every fee strategy. Recommendation: accept — a golden-byte harness is its own project.
  • A4 — The uncovered corner. The auth-registry flows (revoke, registry toggle) ride the generic send path but have zero end-to-end tests. Recommendation: unit pins + your manual QA cover them this arc; a dedicated e2e is a follow-up.
