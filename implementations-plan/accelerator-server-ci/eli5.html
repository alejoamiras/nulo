The accelerator-server CI integration, in plain words

Companion to plan.md. Aimed at a reader who has zero context on this project.

Other docs: plan.md plan-opus-draft.md plan-codex-draft.md

What problem are we solving?

Nulo is a browser-extension crypto wallet that sends private transactions on Aztec — a Layer-2 network where every transaction is a zero-knowledge proof. Before a transaction can be sent, the wallet has to generate that proof. Proof generation is computationally heavy.

Today, our test suite runs proof generation in the browser, in WebAssembly. WASM is portable but ~5× slower than native code. On our CI runners (shared cloud machines that vary in speed), some test runs finish in 2 seconds; some take over 3 minutes. That variance breaks our tests randomly — what we've been calling "CI flake."

The fix: run a small native program on the CI runner called accelerator-server that does the proving job. It uses a battle-tested Rust binary (bb) instead of WASM, so it's fast and consistent.

What the wallet already does (so we have less to change)

The wallet's proving code already knows about accelerator-server. There's a small library called @alejoamiras/aztec-accelerator that the wallet uses to construct its proof generator. The library does this:

  1. Check if accelerator-server is running on the local machine at 127.0.0.1:59833 (it pings a /health endpoint).
  2. If yes → send the proof job to the server. Fast native proving. Done.
  3. If no → quietly fall back to in-browser WASM. Slow but works.

So the change here is not a code change to the wallet. It's a workflow change on the CI side: install accelerator-server on the runner before the tests start. The wallet will auto-detect it. Magic.

The "but" — quiet fallback is dangerous

Step 3 above is the trap. If accelerator-server crashes mid-test, the wallet quietly switches to WASM. Tests still pass (maybe), but now we're silently running the slow path — which means we wouldn't notice the regression until much later. And the whole point of installing accelerator was to not run on WASM in CI.

So the plan needs a way to make this fallback loud. If the wallet ever falls back during a CI test, that test should fail. Hard.

The plan, phase by phase

Phase 1 — Install the binary on the runner

Create a small reusable "composite action" at .github/actions/setup-accelerator-server/action.yml. It downloads the accelerator-server tarball from the upstream GitHub release, checks its SHA-256 hash against one we've pinned in our own repo (not the one shipped alongside the binary — that one could be replaced together with a compromised binary), and unpacks it onto the runner.

Phase 2 — Wire it into the network-e2e workflow

Modify .github/workflows/_network-e2e.yml. After the existing setup steps, add three things:

  • Start the server in the background. Tell it where to find the bb binary (already on disk from our existing setup-aztec step) so it doesn't waste time downloading it.
  • Wait for it to be ready — ping /health for up to 30 seconds, checking that it knows about our Aztec version AND that bb is loaded.
  • After the tests run, look at the server's log. If we see zero proof requests came in, that means the wallet went WASM behind our back. Fail the workflow loudly.

Phase 3 — Make the wallet enforce "no fallback" too

Even with the server running, the wallet's library could still fall back silently (e.g. the server denies the request, or the response is malformed). To catch this at the exact moment it happens:

  • Add a small config module at packages/extension/src/accelerator/config.ts that holds the host/port and a required flag.
  • In packages/aztec-runtime/src/pxe/chain-runtime.ts, when required is on (set by the CI workflow via an env var), do two things: (a) check the server's health BEFORE starting the wallet, and throw an error if it's not ready; (b) install a callback on the prover that throws if it ever fires a "fallback" or "denied" phase.

That's a small code change but it gives us per-test enforcement: any test that triggers a silent fallback dies immediately with a clear error pointing at the prove call that broke.

Phase 4 — Documentation and a kill switch

Add an input disable_accelerator: true to the workflow. If something goes badly wrong post-merge, one manual workflow-dispatch click flips us back to the pre-merge WASM-only behavior while we fix forward. Document the bump procedure in SECURITY.md (version + SHA-256 always pinned together), update CLAUDE.md + CI.md to reflect the new enforcement.

How we make the fallback loud — three layers

One layer catches what the others can't. Defense in depth:

Layer 1 — Pre-test probe (workflow step) Did the server come up at all? Does it have bb loaded? Misses: mid-test crash, per-test fallback Layer 2 — Runtime throw (wallet code) onPhase callback throws if "fallback" or "denied" fires Catches the failure at the exact prove call Layer 3 — Post-test log scrape (workflow step) Did any proof requests reach the server at all? Catches: tests crashed before Layer 2 could throw

Why one PR, not three?

Both the opus and codex parallel-draft authors argued for splitting this into 3 sequential PRs. I'm consolidating to one because:

  • The wallet's proving code already creates an AcceleratorProver instance unconditionally. There's no "spawn the server but don't use it yet" mode — once the server is up, the wallet finds it automatically. So a "Phase 1: shadow run" PR isn't physically possible without a separate code change to disable the wallet's detection, which we'd then undo in Phase 2. Round trip for nothing.
  • The total surface is small (~80 lines across the wallet runtime + config module + new offscreen hook).
  • The kill switch IS the granular rollback that 3 PRs would give you. If something breaks post-merge, flip disable_accelerator: true in a workflow_dispatch run; we're back to WASM in 30 seconds.

The trade-off you should know: one PR has a bigger blast radius. If something subtle breaks (e.g. our offscreen chrome-extension:// Origin header gets rejected by the server), all 5 shards on dev go red at once. The kill switch is the mitigation, but it's still a worse first impression than a staged rollout.

Open questions (what I don't know yet)

Each must be answered before the PR can merge. Most are spike-during-Phase-1 items, not blockers for approval.

  • Q1 — Does the server accept our chrome-extension:// Origin header? The server has an ALLOWED_ORIGINS env var. When unset, all browser origins are auto-approved. We leave it unset for v1 and capture the actual Origin header from the log on the first run; tighten later if needed.
  • Q2 — Is the bb binary actually where we think it is after setup-aztec? Verified locally — it's at ~/.aztec/current/node_modules/.bin/bb. Need one CI spike to confirm the same path on a fresh ubuntu runner.
  • Q3 — Does the server's static binary actually run on ubuntu-latest's glibc? Likely yes (the upstream README claims static binary), but we run ldd on first install to surface mismatches loudly.
  • Q4 — What does the server's log look like? Affects how we grep for prove-request counts in Layer 3. Spike during Phase 1.
  • Q5 — What's the SHA-256 of the v1.0.1 tarball? Compute and pin in the workflow caller before opening the PR.

How this links back to recent work

Last sprint we landed 7 PRs (#60–#66) trying to stabilize the network-e2e suite under CI prover-pool variability. We had to quarantine one test (tx-sendTx-default) and bump another's wait budget from 30s to 90s (cancel-mid-prove) because some runs of the runner pool were 90× slower than others on the same proof.

If accelerator-server delivers what its README claims (native bb proving with consistent timing), both of those decisions become reversible. The follow-up plan would be:

  • Run the quarantined test with accelerator + see if it consistently finishes in <30 seconds. If yes → un-quarantine.
  • Restore cancel-mid-prove's 30s waits. If they pass → revert the 90s bumps.

But that's a separate plan, after we measure. The current plan is just "land accelerator + make CI hard-fail if it ever falls back to WASM." We earn the right to un-quarantine by measuring first.

Security in plain words

  • We're trusting a single-maintainer GitHub repo for the binary. The maintainer is the same person who owns Nulo, so the trust model is already what it is. We pin the SHA-256 in our own repo so a compromised release alone can't replace the binary without us noticing.
  • The server only listens on 127.0.0.1. It cannot accidentally be exposed to the public internet — the binding is hardcoded.
  • Our CI runners are single-tenant. Each test shard gets its own fresh ubuntu VM. Nothing else is on the box.
  • The binary is AGPL-3.0. We run it in CI; we never ship it to users. The AGPL "network deployment" clause (§13) is not triggered.
  • One person shouldn't be able to quietly bypass the enforcement. A defensive lint rule blocks any code from calling setForceLocal(true) outside test files. Reviewers can still inspect workflow YAML changes for trust-relevant edits.

What would make me say "this isn't ready yet"

  • If Q1 turns out negative — i.e. the server rejects our extension's Origin header — we need to either compute the chrome-extension ID at build time and pre-populate ALLOWED_ORIGINS, or get an upstream patch. Either is a delay.
  • If Q3 fails — i.e. the static binary needs a glibc newer than ubuntu-latest ships — we'd need to either build accelerator-server from source in CI, or switch to a different runner image. Significant delay.
  • If measurement shows accelerator is <10% faster than WASM on CI — the entire plan stops paying back and we should consider reverting. But this would be very surprising.
