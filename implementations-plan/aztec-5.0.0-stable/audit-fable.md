## Findings

1. **[High] Scope #4 / Phase 2.1 / Security §Crypto — seed→signingKey step not specified tightly enough.** No upstream seed→signingKey primitive exists in 5.0.0; the plan's two candidates produce DIFFERENT keys and the `fromBufferReduce` fallback is exactly the hand-rolled construction the plan forbids (256-mod-254 reduction bias). Vectors are regenerated by the implementation so they can't catch a bad initial choice. **Fix:** pin the exact construction in-plan before implementation: `sha512ToGrumpkinScalar([accountSeed, IVSK_M domain separator])` — the verbatim body of the removed deriveSigningKey (confirmed by the V7a comment in apps/extension/src/wallet/crypto/key-vectors.test.ts), inheriting upstream's domain separation, keeping signing keys byte-identical to rc.2 for a given seed, no collision path with deriveKeys(secretKey). Strike the fromBufferReduce option. Ledger entry D7.

2. **[High] Scope #5 / Phase 2.4 / Fact 6 — the currentContractClassId model is wrong twice.** (a) Not 4 production readers: ~28 reads across 11 production files (execution/service.ts ×5, view-executor.ts ×4, tx-request-builder.ts ×4, contract-resolver.ts ×3, authwit-discoverer.ts ×2, batched-view-simulation.ts ×2, fpc/service.ts ×2, token/service.ts ×2, + the 4 cited). (b) In published 5.0.0 `ContractInstanceWithAddress` RETAINS currentContractClassId — only the new `ContractInstancePreimage` type lost it; `PXE.registerContract(instance: ContractInstancePreimage): Promise<AztecAddress>`. "Schema loses currentContractClassId" is false; mass-migration to originalContractClassId would be a semantic downgrade. **Fix:** rewrite around the preimage/instance type split; let Phase 1's typecheck inventory enumerate the genuinely broken sites.

3. **[High] Phase 3 / Inference 1 — 5.0.0 sqlite-opfs createStore silently destroys per-(profile,chain) isolation; the planned purge rework targets a directory the store doesn't live in.** Verified in published @aztec/kv-store@5.0.0: `createStore(name, config, …)` uses config.dataDirectory ONLY in a log line, opens `AztecSQLiteOPFSStore.open(log, 'pxe_data' /* hardcoded by createPXE */, false)` with no poolDirectory ⇒ every profile+chain shares ONE store; `initStoreForRollupAndSchemaVersion` WIPES the shared store when a different-rollup chain opens; each store's SAH pool lock is exclusive (its own doc-comment) so a second concurrent PXE likely fails to open; "OPFS directory removal keyed on chainDataDir" purges nothing. rc.2's IndexedDB backend honored dataDirectory (verified) — an upstream regression against Nulo's architecture. Escape hatch verified: createPXE's `options.store` + `AztecSQLiteOPFSStore.open(log, name, false, poolDirectory, encryptionKey?)` + `store.delete()`/`close()`. **Fix:** explicit Phase 3 work item (inject options.store per (profile,chain), poolDirectory = chainDataDir) + extend the gate: two chains + two profiles concurrently open; purge of A leaves B intact; purge with NO live runtime still removes the OPFS dir; zero residual IndexedDB AND OPFS artifacts after profile erase.

4. **[Medium] Phase 2 gate vs Phase 4.6 — the PrivateFPC tripwire fires two phases early.** private-fuel.test.ts resolves the FPC artifact from node_modules (bumped in Phase 1), so it fires at Phase 2's test:all whose criterion is "all exit 0". **Fix:** move the conscious canonical re-pin (both cross-checks) into Phase 2, Phase 4 re-verifies; audit fuel.test.ts for the same coupling.

5. **[Medium] Phase 2.1 / Inference 3 — falsified: PXE.registerAccount now takes AccountPrivacyKeys** (4 privacy secret keys + message-signing/fallback PUBLIC keys; secrets withheld from PXE — verified in pxe.d.ts + key-store 5.0.0). Ripples through spec/ipxe/service/client, zod pins, descriptor pins. **Fix:** explicit Phase 2 work item + wire-shape decision (least churn: keep secretKey over the seam, derive the struct offscreen-side via deriveKeys) + pin that no signing-key material is ever a seam argument.

6. **[Medium] Scope #4 / Phase 2.3 — "createSchnorrAccount signing-key-first signature" is false.** Published 5.0.0 keeps `createSchnorrAccount(secret: Fr, salt: Fr, signingKey: Fq, alias?)` — both independent inputs; an unmigrated call passing the OLD relationship compiles and runs. **Fix:** each of the 9 sites gets the explicit two-step (signingKey = pinned reduction(seed); secret = await deriveSecretKeyFromSigningKey(signingKey)); enforcement points migrated same-phase: the e2e fixture parity throw (tests/e2e/fixtures/aztec.ts:388-392) and the nulo-account unit parity test.

7. **[Medium] Security / Phase 2.2 — no gate pins what NuloAccount registers into the PXE.** A NuloAccount that derives the right address but registers the SEED (today's ensureRegistered passes this.secret — nulo-account.ts:76) fails only as broken note sync at network e2e — after the Phase 5 live spend. **Fix:** one Phase 2 unit pin: the value(s) sent to pxe.registerAccount equal the derived privacy keys from the pinned vector pair and are provably NOT the seed or signing key.

8. **[Low] Security §Crypto — V3 mislabeled "non-Aztec".** The vector file classifies V3 as Aztec-stack-sensitive (Fr.fromBufferReduce). Keep it in the stop set AND label it correctly; V3 drift = STOP.

9. **[Low] Scope #1 / Fact 4 — 66 pins, not 67** (the 67th line is @aztec/viem@2.38.2, excluded by the same sentence). State 66 + viem excluded.

10. **[Low] Phase 4.3 / Fact 10 — consume_l1_to_l2_message has TWO call sites in token_bridge/src/main.nr (98, 115).** Fix the count.

11. **[Medium] Summary vs Scope — outage-recovery story incomplete.** Scope ends at a PR to dev; the deployed faucet redeploys on a stable release from main (or break-glass refresh-landing). **Fix:** add post-merge promote dev→main + release as the owed follow-up that actually restores the public faucet.
