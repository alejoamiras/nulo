Aztec 5.0.0 (stable) upgrade + testnet redeploy

Aztec shipped its stable 5.0.0 yesterday, and the shared testnet was rebuilt at the same time — so the wallet's dependencies are now one version behind AND every contract we deployed (faucet dripper, tokens, bridge, fee-payment helpers) lives on a network that no longer exists. The public faucet is broken right now because of this. This plan upgrades all the Aztec packages, adapts the wallet to three big upstream changes (a reversed account-key scheme, a reshaped PXE API, and a new browser storage engine), redeploys everything onto the new testnet, and finishes the move away from the old @defi-wonderland packages.

Why this tier was chosen

mid — you confirmed it at Phase 0. Novelty is LOW (this is the 4th Aztec bump here, and your other two repos — aztec-accelerator and ecosystem-tooling — already shipped this exact rc.2→5.0.0 migration this week, leaving detailed lessons we reused). But blast radius and irreversibility are HIGH (live Sepolia transactions, Fee Juice that can be lost forever if sent to a wrong address), so it got the full dual-audit treatment: fable audit + codex audit (gpt-5.6-sol at its max effort) + a final fresh-context codex pass. The codex round-1 reject caught real problems — including one that could have burned funds — all folded into v3.

Phases

Phase 1: Reference vectors + the mechanical bump

Before touching anything, we snapshot "known answers" from the CURRENT version's key-derivation code — these become the ruler the new code must match, so nobody can accidentally invent different crypto. Then: bump 76 package pins, re-key two patch files, rebuild the lockfile, and check the new packages' signatures/attestations (they're 0–1 days old, so we verify provenance instead of relying on the 7-day age gate).

Proves itself by: clean install, a lockfile diff where only Aztec-family packages moved, signature checks passing, and a written inventory of everything the type-checker says broke.

Phase 2: Adapt the wallet code (the big one)

Upstream reversed how account keys work: the signing key is now the root and the privacy secret is derived from it (before, it was the other way round). You chose to adopt this model. The exact derivation recipe is frozen in the plan (it reuses upstream's own removed formula, so it must reproduce Phase 1's snapshot answers exactly). Also here: the PXE API reshape, a security nicety (the PXE provably never sees your signing key — pinned by a test), re-rooting the fee-payment contract (PrivateFPC) onto its new canonical identity — the audit found its address "salt" changed, and our version-check script would have waved the wrong version through — and making old backups fail with a clear error instead of importing broken accounts.

Proves itself by: typecheck, all ~3,200 unit tests, lint, and all five app builds green — including the new key-derivation, FPC-identity, and backup-reject tests.

Phase 3: New browser storage engine (SQLite-OPFS)

5.0.0 switches the in-browser database from IndexedDB to SQLite-on-OPFS. The audits found the upstream default is dangerous for us: it would silently merge every profile and network into ONE database and wipe it on every network switch. So we explicitly create one isolated store per profile+network, rewrite the "delete profile" cleanup for the new engine, and wire the new WASM files into the extension build (your accelerator repo hit the exact same landmines last week — we reuse those fixes).

Proves itself by: smoke tests plus a committed script driving the REAL production-built extension: data survives restart, two profiles on two networks coexist, deleting profile A leaves profile B intact, and nothing is left behind after erase.

Phase 4: Smart-contract (Noir) toolchain + drift inventory

Bump the Noir compiler and contract dependencies to 5.0.0, point the token dependency at YOUR repo (ecosystem-tooling) instead of defi-wonderland's — the last live Wonderland reference — apply the one real contract-code change (a message secret becomes an array, two lines), recompile all three contracts, and measure exactly which on-chain addresses moved (spoiler: all of them — the network reset).

Proves itself by: all three contracts compile; the complete old→new address inventory is written down as Phase 5's checklist.

Phase 5: The live testnet redeploy (the irreversible one)

Redeploy everything onto the new testnet, in the safest order we know: first a written "deployment intent" (what we'll deploy, with which wallet, spending at most how much — with the target addresses double-checked against TWO independent sources, not just one RPC server); every command dry-run before broadcast; the new bridge written to a CANDIDATE file that gets fully proven — including the private fee-payment transaction that moves real Fee Juice — before it's promoted to "live". The audit specifically caught that the old plan ran that proof AFTER promotion; that's fixed. The fee-payment contract gets a hardened version gate (exact version + code fingerprint + live on-chain check) because sending Fee Juice to a wrong-version address is unrecoverable.

Proves itself by: the five live canaries — L1 verification, address re-derivation matches, a real bridge round-trip, a private self-paying transaction settling, and a faucet drip — all against the live network, spend within the stated ceiling.

Phase 6: The PR + full CI proof

Open the PR with both e2e suites forced on. The network suite proves real transaction proving works end-to-end on 5.0.0 (with the native accelerator — no silent fallback allowed). Docs updated in the same PR: the update runbook, the coupling checklist, the plans index.

Proves itself by: all three required CI checks green on the PR.

Phase 7: Actually fixing the public faucet (post-merge, needs your go)

The audit called out honestly: merging the PR does NOT fix the public site — that happens when a stable release goes out from main. So the release (promote → release PR → publish → check the live site serves the new build → one drip through the real faucet page) is a named phase with its own authorization gate. Your earlier "yes, deploy to testnet" does not cover this; you'll give a separate go.

Proves itself by: the live faucet page serves the new build and successfully drips.

Human context

Three things the changelog did NOT say that shaped this plan: (1) upstream's key-bundle function quietly stopped stubbing two public keys, so every account address changes no matter what we do — that plus the network reset makes this a "fresh start" upgrade, which is fine pre-production; (2) the new browser storage ignores the "data directory" setting entirely — discovered by the fable audit reading the actual published code; (3) the fee-payment contract's canonical address salt changed from "whatever the operator used" to a fixed constant — and three separate places in our code silently assumed the old one. The dual audit earned its cost: codex's round-1 reject found a genuine fund-loss window (proof-after-promotion) and a false-green version gate.
