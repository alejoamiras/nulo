Verdict: **Reject**

Public-wrapper deadlocks look covered, and the current `repo.setTrust` / `repo.upsertRecord` / `repo.deleteRecord` call sites are accounted for by Phases 1/3/4/5/6. The blocker is elsewhere.

## Critical

- The global lock does **not** subsume the old lifecycle-cancel races for `clearChain`, `clearProfile`, or `onAccountDeleted`. Phase 4 keeps PXE discovery outside the lock and only locks the per-note commit path ([plan.md:228-313](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:228)). Phase 3.5 / 6 then delete rows under the lock ([plan.md:197-223](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:197), [plan.md:348-372](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:348)). If a scan finishes `getNotesRaw()` before the clear/delete, the clear can run first, release the lock, and the stale scan can then reacquire and recreate rows from already-fetched notes. There is no fresh profile/network/account liveness check inside the Phase 4 critical section analogous to the token check. Current `scanGenerations`/`isStale()` around `hydrateSchedulers` are covering exactly this class today ([service.ts:363-395](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/wallet/services/incoming-transfer/service.ts:363), [service.ts:540-669](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/wallet/services/incoming-transfer/service.ts:540)). `LR7` only tests the opposite ordering (`scan` first). I would block until the plan adds a fresh cancel guard for clear/account-delete paths or keeps an epoch/generation for them.

## High

- `setTrustState` cannot stay an “ask”. The plan itself says arbitrary IPC callers can bypass the FSM ([plan.md:418-420](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:418), [plan.md:458-470](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:458)), but locked decision #4 is actor-only. It also makes `LR11` false as written: `setTrustState("blocked"|"unknown")` does not reconcile existing visible records ([service.ts:237-240](/Users/alejoamiras/Projects/nulo/nulo-2/packages/extension/src/wallet/services/incoming-transfer/service.ts:237)). Either remove `setTrustState` from public `Methods` in this PR or narrow LR11 to actor paths only.

- I1/I4 are not credible. The per-note locked block is not “repo reads + writes” only ([plan.md:462-465](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:462)); it also calls `collectOutgoingTxHashes()` and `collectInflightTxHashes()` inside the lock ([plan.md:263-265](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:263)). Today those route to `transactionService.getTransactions()` and `operationJournalService.getOperations()`, both storage scans, not O(1) lookups. The design may still be acceptable, but the “~5ms / imperceptible” claim is unsupported without measurement.

## Medium

- `LR1` is under-specified. To pin audit-6, the test must park `scanContract` **after** `liveTrust === "pending"` is read and **before** `repo.upsertRecord(record)` ([plan.md:284-303](/Users/alejoamiras/Projects/nulo/nulo-2/implementations-plan/incoming-trust-state-machine-refactor/plan.md:284)). “Parked on per-note CS” is too weak; it can collapse into a trivial ordering test where `setTrustAllow` simply runs first.
