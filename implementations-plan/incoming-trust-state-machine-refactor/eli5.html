IncomingTransfer trust-state-machine refactor

The wallet has a small piece of logic that decides when received tokens show up in your history: "I've never seen this token before → ask the user; user said Allow → show them from now on; user said Block → hide silently". Today, multiple parts of the wallet can change that decision at the same time (the background scanner, your Allow click, removing the token), and they step on each other. That's why you saw the bugs (records not appearing, popups closing late, weird ordering on remove+re-add). The fix: add a single "lock" so only one thing at a time can change the trust state.

The journey

This refactor went through significant planning ceremony — three independent plans (main agent, codex, opus), two adversarial audit rounds with push-back, and a final fresh-context codex pass. The audits flagged enough issues that we changed the architecture mid-planning: from a per-token lock (originally chosen for parallelism) to a single global service lock (simpler, eliminated multiple bug classes the audits found in the per-token design). The trade-off is small: scans for different tokens now serialize instead of running in parallel, but each lock-hold is sub-second and the slow part (PXE network calls) stays outside the lock.

Phases

Phase -1: Pin Lock primitive behavior

Add tests to the upstream Lock primitive (wallet-core) before we depend on it. FIFO ordering, force-release, idempotent leave, finally-release after thrown work. Codex audits flagged that the primitive has no test coverage today.

Phase 0: Add lock + epoch scaffold

Add one Lock instance to the service. Add a small "service epoch" counter (an int) bumped whenever lifecycle events happen (token delete, account delete, profile/chain clear). Scans capture the epoch BEFORE making network calls; inside the lock, they check the epoch hasn't changed — if it has, they bail. This closes a race the final audit found: a scan that's mid-network-call could otherwise resurrect records that a delete just wiped.

Phase 1: Migrate the trust-setting writers

Wrap setTrustAllow / setTrustReject / setTrustState in the lock. Drop several "compensating action" reverts we added during the prior six audit cycles — the lock makes them unnecessary. Remove setTrustState from the public IPC surface (it was bypassable via arbitrary state values — a footgun the audits surfaced).

Phase 2: Migrate replayPendingPrompts

This is the path that re-fires the trust popup when you reopen the wallet. Wrap each per-pending-row in the lock; re-read state inside the lock to catch concurrent token deletions.

Phase 3: Migrate onTokenDeleted

When you remove a token, wipe records + reset trust under the lock. Scheduler teardown happens inside the lock too so a concurrent scan can't slip records in between.

Phase 3.5: Migrate onAccountDeleted

When you remove an account, wipe its records (across all networks matching the chain) under the lock. Trust rows are contract-scoped, so they survive (other accounts may still have records).

Phase 4: Migrate scanContract (the big one)

The background scanner. Keep network calls (PXE) OUTSIDE the lock for responsiveness; only lock the per-note "decide + persist" critical section. Inside the lock: fresh re-reads of token registration, trust state, transaction dedupe sets. Drop the old generation-counter mechanism (scanGenerations) — the lock + epoch replace it.

Phase 5: Migrate onTransactionAdded

When an outgoing transaction confirms, delete any incoming records that matched its hash (those were actually our own outgoing notes). Wrap in the lock; drop the per-hash reentrancy guard (lock supersedes).

Phase 6: Migrate clearProfile + clearChain

Profile delete + chain purge paths. Lock the wipe + scheduler rebuild together. Bump the epoch to invalidate any scans that started before the wipe.

Phase 7: Test rewrites

Update existing race-condition tests to assert the new lock-based semantics. Add a new file with race-ordering pins — including LR1, which precisely pins the bug from the previous arc's six audit cycles. LR12 pins the lifecycle-cancel race the final audit found.

Phase 8: Post-impl audit + fix loop

Run code-review tool + codex post-impl audit. Address any high/critical findings.

Human context

The previous arc (the one that just merged) closed six rounds of concrete race-condition findings with ad-hoc patches: counters, sets, compensating-action reverts. Each fix worked, but the codex audit's final verdict was that the underlying architecture (multiple unsynchronized writers on the same row) is the real problem. This refactor replaces the patch stack with one proper synchronization primitive.

The original choice was a per-token lock (so two tokens can be scanned in parallel). Round 2 audits found that the per-token design has its own implementation complexity (TOCTOU races on a "wipe in progress" flag, drain patterns that leak late-discovered tokens, memory growth concerns on long-running browser sessions). The user pivoted to a single global service lock; the audits' subsequent attack surface shrunk dramatically. The cost — sequential scans across tokens — is bounded by the locked operations being sub-millisecond (network calls stay outside the lock).

Open questions

  • Should we defer churn-flooding mitigation (rapid register/revoke loops)? Currently planned as a follow-up PR. Product decision.
  • Should we fix the popup-misreads-async-throw bug now or later? Pre-existing; small popup-side fix. Currently planned as a follow-up.
  • I1/I4 performance assumptions need measurement during implementation. If lock contention causes user-visible latency, mitigate by caching per-scan-batch storage scans inside the lock.
