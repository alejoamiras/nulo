Implementation plan · deep tier · v4 gate-ready

Everything to 5.0.1, everything fixed, everything shipped

One mega-PR growing #282, then the release — under your standing authorization. Full plan: plan.md · audits: codex r1, fable r1, final pass

The one-paragraph version. We bump the wallet's Aztec engine to 5.0.1 first (it fixes the exact storage plumbing our bug lives next to), then fix the restore-boot deadlock and all of #281's concurrency hazards on that fresh base, then swap to the official @aztec-foundation/aztec-standards package — which changes contract fingerprints, forcing a fresh testnet deployment of the L2 contracts, faucet, and fee-payment contract — and finally promote to main, cut the stable extension release, and prove it by using the real public website.

Why the heavyweight process

Rubric: blast radius HIGH (restore/deletion paths + a public release), irreversibility HIGH (published release, live deploys), security HIGH (locks guarding encrypted stores; fund-moving deploys), external coupling HIGH (npm, testnet, RPC version skew). ≥2 HIGH ⇒ deep tier: 3 independent plans → consolidation → contradiction-check (9 findings) → double hostile audit (17 findings) → final fresh-context pass (6 conditions). Every round changed the plan; the ledger in plan.md records each fold and flip.

The phases

P0

Catch the bug in a jar

Reproduce the restore-boot hang locally and write a small fast test that fails because of the deadlock — before touching anything. If we can't reproduce it, we stop: the diagnosis would be wrong.

Proves itself by: the hang observed locally + the new pin test red on today's code for the exact suspected mechanism.
P1

Engine swap to 5.0.1 (nothing on-chain moves)

All @aztec/* + the accelerator go to 5.0.1 under the full supply-chain ritual (fresh lockfile, scripts disabled, signature audit in a scratch project, secret-free shell). The two packages that would change contract identities wait until P4, so the live deployment stays verifiably intact. One safety decision flips here: on storage-version mismatch our encrypted stores now refuse to open instead of wiping — the audits proved wipes could destroy user data and could be triggered by a lying RPC.

Proves itself by: full typecheck/tests/lint green, verify:deployments still green, derivation vectors byte-identical, and the P0 bug still reproducing the same way.
P2

Kill the deadlock class, not just the bug

Profile events stop firing while the profile lock is held (the root cause). The store-key path becomes lock-free, keys are pushed to the engine proactively, and both lock utilities get tamper-proof ownership — their old "force-release after 5 minutes" self-heal (which corrupted state) becomes a loud log instead.

Proves itself by: the P0 pin turning green + a battery of ordering/re-entrancy tests that fail on the old code.
P3

The deletion fence (#281 complete)

Every profile gets a permanent random "incarnation number". Deleting a profile burns its number forever, so no delayed message can ever resurrect a deleted profile's encrypted store — even across engine restarts (the final audit caught that our first design was literally impossible: the offscreen engine can't read extension storage, so the service worker is the sole authority). Plus: endpoint-switch races fixed, purge errors made loud, and a visible "waiting for an in-flight operation" state so deletion never looks hung.

Proves itself by: the full race-condition test matrix + the three previously-failing backup e2e tests green locally.
P4

New identities: official standards + fee-payment 5.0.1

The community-fork era ends: @aztec-foundation/aztec-standards replaces the personal-scope package — but only after a hard trust gate (npm provenance must cryptographically bind the package to the official repo's tag; if that attestation is missing, we stop and ask you). The fee-payment contract moves to 5.0.1, which moves the canonical PrivateFPC address, re-pinned under a new fund-safety gate that accepts exactly one audited combination of artifact + network. Noir contracts recompile on the 5.0.1 toolchain.

Proves itself by: trust gates green (or stopped), the FPC gate green against the live node, and the drift detectors turning red exactly where predicted — the proof a redeploy is needed.
P5

Sharpen the deploy tools before going live

The deploy scripts gain what this deployment needs and the audits demanded: a mode that reuses the existing AZLO token (today they always mint a new one), candidate files for the faucet so nothing touches live configs early, a tamper-resistant one-command promotion, and identity checks that compare the node's claims against what we already know to be true.

Proves itself by: unit tests over every new mode + the promote path.
P6

The live redeploy (real broadcasts, testnet)

Keep: the protocol portal, AZLO, all the swap/fuel plumbing. Redeploy: the app token portal (it's welded to the old bridge address), the L2 contracts, the faucet, and the new PrivateFPC. Candidate-first, verified before every broadcast group, proven by six canaries (smoke, fueled, private settle, direct fee-juice, drip, verify-l1), then promoted atomically with a receipt. Spend stays inside the ≤0.5 ETH cap — expected well under 0.1.

Proves itself by: all canaries + promotion receipt + post-promotion checks + spend reconciliation.
P7

Land it

Docs and lessons updated, a max-effort code review with fixes, a codex post-implementation audit over the sensitive surfaces, and one squash-merge of #282 with all three CI gates green. Any post-deploy code change gets classified — if it touches deploy-affecting files, the live proofs re-run before merge.

Proves itself by: quality + smoke + network e2e green on the final head; merged; dev green.
R

Release + prove it in public

Promote dev→main, let release-please + auto-unstick publish, flip verify-live to a required check, and then the part no robot can fake: with the released extension in a clean browser, do one real drip and one real Fuel deposit→claim through the actual public website. Rollback paths are pre-defined.

Proves itself by: release assets present, live site serving the new build + chain, both public flows recorded with hashes.

Where we will stop and ask you

Only three conditions surface mid-run (otherwise the standing authorization carries to the end):
  • The official standards package ships without a provenance attestation — we stop and bring you the alternative binding plan.
  • A second Aztec RPC exists and disagrees with the primary — unconditional stop (mere absence of a second RPC is the already-accepted capped-risk posture).
  • Reality contradicts a probe — the testnet resets mid-arc, or the token-reuse deploy turns out impossible as shaped.

Human context worth having

  • Why bump before fixing: your call, and the evidence agreed — 5.0.1 patched the exact storage layer (#24647 handle-release) our #281 work hardens. Fixing on 5.0.0 meant patching around bugs that vanish a phase later.
  • Why the redeploy is unavoidable: the new standards package compiles to different bytecode → different contract fingerprints → our own tripwires (correctly) refuse the mismatch until the testnet runs the new contracts.
  • What the audits changed: wipe→refuse on store mismatch; the trust gate became a cryptographic binding instead of metadata checks; the "atomic promote" became a receipt-backed verified sequence; the impossible offscreen-storage fence became SW-authoritative; the release gains a wired-hook preflight + defined rollback.
