E2E Stabilization Plan

Plain-language companion to plan.md · scope: Issues #58, #59, and the cold-shard rotation · ~20 hours, 2–3 working days

What we're trying to do: finish stabilizing the network end-to-end tests so the CI signal is trustworthy enough to merge other feature PRs. After PR #46 we're close but not there — 3 known problems remain, all fixable at the UI / test layer without touching wallet services.

The 3 problems, in plain English

1. The discover popup has a phishing-shaped bug HIGH

When a dApp asks "can I connect?", a popup appears with the dApp's name, logo, and hostname. The Allow button is currently clickable BEFORE those identity details finish loading. A malicious dApp could trick a user into approving a session they never identified.

Why isn't this just a test problem? Because in production, slow networks + auto-focused buttons + scripted Enter keys can race the same way.

2. One specific test does too much in one go MEDIUM

register-token.test.ts opens TWO popups in sequence (request capabilities, then register the token). On cold CI runners, both popups take a while to appear, and the combined time exceeds the test's 60-second budget. We've quarantined it for now; we want to un-quarantine.

Why not just give it more time? Because the inner waits sum to ~210 seconds in the worst case — no realistic budget actually catches it. The fix is to remove the redundant work, not extend the deadline.

3. Cold shards rotate — quarantine just moves the bullet MEDIUM

Our CI runs the network suite as 5 parallel shards, each on a fresh machine. The first popup-driven test in each shard pays a "cold start" tax because the wallet's service worker, WebAssembly crypto, and Aztec node all have to warm up. Quarantine the offender? The next test becomes the new victim.

Why does this only matter on CI? Locally, your machine is warm and fast; cold-start is invisible. On hosted CI, it's the dominant cost.

The plan in 4 phases

Phase 1 — Fix the discover popup (~5h)

Add a single isReady readiness flag that flips true only after EVERYTHING loads. Gate the Allow button on it. If a click sneaks through anyway (Enter key, weird timing), throw an error instead of silently doing nothing — silent guards are what cost us 19 iterations last time.

While we're in there: also verify the Authwits popups' Enter-key handlers check loading + error state (not just "is it allowed").

Phase 2 — Restructure register-token (~6h)

Create a small test fixture that pre-grants the accounts capability (the one register-token actually needs — codex caught us assuming it needed basic). Then the test only has to drive ONE popup instead of two. Drop the quarantine, run 5 times locally before pushing.

Phase 3 — Warm up the cold shard (~7h, includes a 1h probe)

Add a "warm-up tap": open a throwaway browser BEFORE any tests run, drive one cap-popup-and-reject flow to wake up the service worker + WebAssembly + Aztec node, then close it. Real tests start warm.

But first we need to prove the warm-up actually helps. Phase 3A is a 1-hour probe: launch browser A with warm-up, close it, launch browser B fresh, measure browser B's first cap-popup time vs without warm-up. If it doesn't drop by ≥30%, we fall back to a different layer.

Phase 4 — Acceptance gate (no code, just measurement)

Trigger the CI workflow 5 times in a row on a pinned branch (so the commit doesn't move). Count how many of the 5 runs are 5/5 green. 3 of 5 = done. 4 of 5 = comfortable. 5 of 5 = celebrate (and we can promote Network e2e to a required check).

Why "local-first" matters

You said it twice: "CI is the last gate. You can not run them in CI and expect green if we don't have greens locally." The plan codifies this — every phase has explicit local commands that must pass before any CI push. Local is ~10 minutes per shard; CI is ~15 + scheduling. Iterating on CI is the wrong loop.

Also documented now: bun run e2e:agent --shard=N/5 reproduces exactly the same files CI would run for that shard (deterministic SHA-1-of-filename distribution).

What's NOT in scope (deliberately)

  • The other 2 quarantined slow tests (multi-account-from, tx-sendTx-multicall) — different root causes, future PR.
  • Self-hosted CI runners — out of scope per your "test restructure / new fixtures OK" constraint (but not "spin up infrastructure").
  • Touching anything under src/wallet/services/** — all 3 problems fix at the UI / test layer.
  • Promoting Network e2e to a required CI check — only after Phase 4 hits 5/5 on 5/5.
  • Smoke suite changes — separate scope.

Open questions before approval

  1. Phase 3A probe outcome. If browser-A warm-up doesn't reduce browser-B's first cap-popup latency by ≥30%, we switch from global-setup.ts to a per-test fixture-layer warm-up. 1h spike will tell.
  2. Fixture naming. dappConnectedExtensionWithAccountsCap is accurate but long. Need a naming check against the existing 11 fixtures in extension.ts.
  3. Warm-up always-on or opt-in? Currently NULO_E2E_WARMUP=1 in CI. Adding ~30-60s to local dev if always-on. Recommend: opt-in for 2 weeks of stability data, then flip.
  4. Phase 1B verification. Codex says the Authwits Enter-key gates were already fixed by us; we verify in HEAD before assuming the work is done.

Risks we're tracking

  • Phase 1 → Phase 3 interaction. The isReady pattern in discover might interact with how the warm-up tap drives the same popup. Phase 1 must land first so Phase 3 has a clean target.
  • launchExtension() not callable from global-setup. Current code depends on inject("extensionPath"). Phase 3 needs to extract a non-vitest helper. Estimated half-day if needed.
  • Warm-up that silently grants caps would mask permission bugs. The plan REQUIRES the warm-up to reject the request (not approve), with a security check.
  • Advisory CI gate as attack window. If Network e2e stays advisory forever, a real network regression could ship under the noise. Phase 4's 5/5 bar is what gets it promoted to required.
