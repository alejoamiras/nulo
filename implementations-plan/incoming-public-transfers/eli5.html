incoming-public-transfers

Today the wallet only notices tokens that arrive privately (as encrypted notes). If someone sends you tokens publicly, nothing happens: no "Received" row in Activity, and your balance number doesn't move until you press refresh. This plan fixes both. The token contract already announces every public transfer with a little on-chain "event" (like a receipt stapled to the block); we'll read those receipts from the network node, page by page with a bookmark (a "cursor") so we never re-read what we've seen, show them as "Received" rows exactly like private ones, and — for BOTH private and public receives — automatically refresh the balance so the number is right without you touching anything.

Why this tier was chosen

mid. Rubric: 0 HIGH dimensions (novelty MODERATE — our first event-indexer, but the whole surface was mapped up front; blast radius MODERATE — activity feed + balances; irreversibility LOW — no production users, storage can change freely; migration LOW; external coupling MODERATE — one new node API that's already in our libraries; security MODERATE — spam/dusting, handled by the existing trust prompt). It spans three areas (runtime package, wallet services, UI), so light was out; nothing scored high enough for deep. The plan then went through the full mid ceremony: a competing design, TWO independent audits (Claude "fable" + codex), all 24 findings folded or rejected with verified reasons, and a final fresh codex pass.

Phases

Phase 1: Teach the runtime to fetch public transfer receipts

One new low-level call: "give me the next page of Transfer events for this token, after my bookmark." It only trusts what it can verify: pages must be in order, never past the chain's proven tip, and one garbled entry can't break the rest.

Proves itself by: named unit tests (page decoding, bookmark math, hostile-page rejection) + lint + typecheck, all green.

Phase 2: The scanner — find receipts meant for you (+ handle reorgs)

Every 30 seconds, for each of your tokens, read the next pages of receipts (at most 5 per tick, so it never hogs the node), keep only the ones addressed to you, and file them through the same "do you trust this token?" flow private receives use. Because we index fast-but-reversible checkpointed blocks, this phase also handles chain reorganizations: the node tells us (via a block-hash anchor) when something we indexed got reverted, and we clean up the affected rows, re-refresh the balance, and re-scan — crash-safely, so an interruption mid-cleanup just resumes. The feed's internal row IDs are upgraded here so private and public rows share one identity scheme.

Proves itself by: the full repo check (typecheck → tests → lint → build) with ~12 NAMED scenario tests (crash recovery, remove/re-add, mid-scan account add, reorg cleanup, mid-reconcile reorg…) + a live-node capability probe.

Phase 3: Balances that update themselves

When a receive is discovered (private OR public), a tiny persistent "to-do note" is written alongside it: "refresh this token's balance." The service works through those notes and only crosses them off once the refresh is queued — so even if the browser kills the extension mid-way, the note survives and the balance still gets fixed on next wake-up.

Proves itself by: the full repo check + named tests including a simulated crash-and-recover.

Phase 4: Show it nicely — detail view + dust filter

Received rows get their own detail page (today they just bounce to the token page). It shows a chip for how the tokens arrived (Received privately / Public → Public / Private → Public / Minted), an honest "From" (a real address only when we actually have one, otherwise clearly redacted), and an explorer link. Plus a Settings option to hide dust below a dollar value you set, using the live price service (unpriced tokens are shown, marked "price unavailable").

Proves itself by: the full repo check + component tests (chip + From per type, dust-filter behavior) + the no-network smoke e2e suite.

Phase 5: The real-world proof

A full end-to-end test on a live local network: a second wallet sends you tokens publicly → the Received row appears with the right chip AND the balance updates without anyone clicking refresh. Plus a re-run of the existing private-receive e2e to prove nothing regressed.

Proves itself by: the network e2e suite green on both test files + the full repo check.

Human context

Three background facts explain most decisions. (1) On Aztec, private transfers deliver encrypted notes only you can see — the wallet already scans those. Public transfers just change a number in public storage, so there's nothing to "receive" — but the standard token announces each one with a public event, and the node indexes those events per token, so reading them is cheap and precise. (2) Your address can receive tokens before anything about it ever touches the chain, so "start indexing from when the account was created" would silently miss real money — that's why we index each token's full history, with a saved bookmark so it's paid only once. (3) The extension can be killed by the browser at any moment, so every step (bookmark, refresh to-do notes) is written to disk in a way where crashing mid-step just means redoing a little work, never losing a receipt.

Audit trail (what the reviewers changed)

This plan was hardened hard: a Claude "fable" audit, then a fresh codex pass, then several codex re-checks as fixes and your design decisions landed. Real gaps caught and now designed in: the bookmark could get stuck on a partial page; it wasn't cleaned up when you remove a token; record IDs could collide across profiles; the self-updating balance took four designs before one was provably correct (fire-and-forget → lost on crash; timestamp compare → a stale refresh could falsely mark a receipt done; task-anchored → a coalesced task could mis-attribute; final: each refresh anchored to its own freshly-created task). Your two steers reshaped it further: checkpointed blocks (seconds, not minutes) with full reorg reconciliation — and hardening that took three rounds (rewind must use the finalized mark as of the last scan, every reconciliation page is fork-pinned by hash, and a crash between writing a receipt and its bookmark is caught on resume); and your pub→priv insight, which turned out to be observable-but-not-provably-yours, so we drop the sender rather than show a spoofable one. Two codex demands were rejected with receipts (an alpha SLA; a duplicate retry ledger). And you caught me citing a stale dev — the price service the dust filter needs is merged.
