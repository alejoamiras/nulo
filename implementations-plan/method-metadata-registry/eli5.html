One place to declare a wallet method

The browser-extension wallet exposes ~18 RPC methods to dApps (send a transaction, read a contract, grant an authorization, …). Today, the facts about each method — what permission it needs, how it's routed, how its scope is checked — are scattered across six separate hand-kept lists in three files. Adding or changing one method means editing up to six places, and forgetting one is a silent security hole (it already happened once: the "F1" bug, where a method skipped its permission check because it was missing from one list). This plan folds those six lists into one table — a MethodDescriptor registry — and rebuilds the old lists from it automatically. A method becomes one row. A forgotten method becomes a build failure, not a security hole.

Why this tier was chosen (deep)

Two risk dimensions scored HIGH: security sensitivity (this is the exact boundary that decides what a dApp is allowed to do) and blast radius (every dApp RPC call flows through here). Single-package doesn't downgrade an authz refactor. So: three independent plans (mine + a fresh opus + cross-family codex) → a contradiction-check → a double audit → a final fresh codex pass. The audits earned their keep — they caught a real flaw in the first draft (see "Human context").

Phases

Phase 0 — Safety net first

Set up an isolated test workspace and write down the current six lists exactly as they are today (the "frozen snapshot"). Nothing changes yet — this is the baseline everything is measured against.

Proves itself by: typecheck + lint + the wallet-bridge test suite all green before any edit.

Phase 1 — Build the new table beside the old ones

Add the one registry + the functions that rebuild each old list from it. Add two guard tests: a parity test (the rebuilt lists exactly match the frozen snapshot) and an exhaustiveness test (every real method has a row — a missing one fails the build). The old lists are still in place; the new table just has to match them in isolation.

Proves itself by: parity test exact against the snapshot + exhaustiveness green + every existing test still green.

Phase 2 — Switch over and delete the old lists

Point the code at the rebuilt lists, delete the six originals, and add a runtime guard: if a method reaches the dispatcher without a registry row, it's rejected immediately. This is the zero-change gate — every pre-existing test must still pass unchanged.

Proves itself by: all existing dispatcher + scope tests green and untouched + parity + exhaustiveness green.

Phase 3 — Look for (and fix) any hidden inconsistency

With everything in one view, check for a genuine bug the old scatter was hiding. The audits found the current setup is actually consistent, so this is expected to be a documented "nothing found." If something is found, it's fixed carefully: first a test pinning the old (wrong) behavior, then the fix, then a test for the right behavior — so a real fix is never confused with an accidental break.

Proves itself by: any fix is bug-pinned + tested; or a recorded "no inconsistency surfaced."

Phase 4 — Prove it live

Run the real end-to-end suites against a live network: a dApp transaction routes, a permission-violating call is rejected, an authorization is scope-checked, and the permission-free method still works.

Proves itself by: smoke e2e + network e2e green.

Phase 5 — Docs

Update the README so the next person knows the registry is the one place to edit.

Proves itself by: lint + the full pre-PR audit (typecheck→test→lint→build) green.

Human context

This is a refactor of a security boundary, so the whole game is "change the shape without changing the behavior — except where the old behavior was a bug." The proof is a test that says the rebuilt lists are byte-for-byte identical to the old ones. The interesting part is the safety guarantee: today the six lists are kept in sync by a comment ("must be kept in sync"). After this, they're kept in sync by the compiler and a build-failing test — forgetting a method can't ship.

The audits caught a real flaw in the first draft: the test that's supposed to catch a forgotten method was going to enumerate the wrong "universe" of methods (it referenced an upstream symbol that isn't even public). The fix anchors the check to the wallet's own dispatcher plus the upstream schema, so the guarantee actually holds. That's exactly what the deep ceremony is for.
