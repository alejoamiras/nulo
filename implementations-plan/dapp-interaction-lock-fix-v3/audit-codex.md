**Verdict**

`needs-revision`

**The load-bearing claim**

`HAS-A-HOLE`

I cannot prove silent fund loss from in-tree code alone, but I can falsify the stronger claim that the v3 mutex is “UX-sequencing only.” Once the FIFO baton moves to popup approval, concurrency starts before final `txRequest` construction, before final nonce sealing, and on the `default_entrypoint` path where there is no nonce at all. The likely failure mode is stale/rejected T2 rather than a clean “UX glitch only.”

**Per-item findings**

1. `#1` `P1` — There is a real stale-state interleaving on the standard path. After early approval release, T1 and T2 can both enter `executeAztecSendTx`. Before final prove, both paths do PXE work: authwit discovery can run `buildStandard` + `simulateTx` before the final build ([service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:1753), [authwit-discoverer.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/authwit-discoverer.ts:71)), and `buildAndEstimateTxRequest` does another build + one or two `simulateTx` passes depending on fee strategy ([fee-juice-strategy.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/fee/fee-juice-strategy.ts:20), [fpc-strategy.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/fee/fpc-strategy.ts:47)). `withPxeWrite` serializes each PXE call, not the whole lifecycle ([pxe/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/aztec-runtime/src/pxe/service.ts:425)). So T1 can simulate, drop the guard, and T2 can simulate against the same private-note/private-FPC snapshot before T1 proves. The repo already treats same-account pending-tx / note-selection drift as correctness-sensitive, not cosmetic ([execution/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:665), [transaction/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/transaction/service.ts:96)).

2. `#2` `P0` — The random nonce is not sealed before the proposed new release point. On the standard path it is created only inside `TxRequestBuilder.buildStandard` and sealed only when passed as `txNonce` into `buildTxExecutionRequest` ([tx-request-builder.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/tx-request-builder.ts:126), [tx-request-builder.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/tx-request-builder.ts:353)). Releasing at popup approval is earlier than both. Worse, `executeNoFromSendTx` has no such nonce at all; `NoFromTxRequestResult` omits it and history records `Fr.ZERO` ([tx-request-builder.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/tx-request-builder.ts:68), [service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:1968)). So the PR #53 “nonce sealed before baton release” model does not transfer to v3.

3. `#3` `P1` — The proposed `ExecutionMutex` does restore the conservative guarantee, but that makes it correctness-relevant, not UX-only. If it is acquired before `planner.processAztecJsPayload`, authwit discovery, claim, and build, and held through submit for both standard and `NO_FROM`, only one approved tx per `(profileId, chainId)` can touch PXE execution state at a time ([service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:1695), [service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:1831)). Popup concurrency by itself is fine; execution concurrency is the risky part.

4. `#4` `P1` — The popup approval seam in the plan is wrong as written. `interaction()` does not resolve on approval; it resolves when `executeAndResolve` settles the window handle ([spec.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/dapp-interaction/spec.ts:46), [dapp-interaction/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/dapp-interaction/service.ts:124), [window-manager.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/window-manager/window-manager.ts:51)). So `onInteractionApproved` cannot be fired “after `interaction()` resolves.” Popup path must fire from `approveInteraction()` just before `executeAndResolve`; silent path must fire in `silentInteraction()` immediately before `executeOperations()` ([dapp-interaction/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/dapp-interaction/service.ts:88), [dapp-interaction/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/dapp-interaction/service.ts:295)).

5. `#5` `P1` — Cancel-while-mutex-waiting can be sound, but not with the current “existing cancel infrastructure” alone. Today `cancelJob` flips the journal to `cancelled` and then aborts a controller from `activeControllers` ([execution/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:799)). Those controllers are only registered after claim/create ([claim-helper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/claim-helper.ts:129)). If claim moves after mutex acquire, a queued waiter has no controller yet, so `mutex.acquire(signal)` will not wake unless you add a waiter-abort registry before enqueueing. With that added, the 4001 chain is sound: sentinel -> cancelled result -> `JobCancelledError` -> wallet-sdk 4001 ([rpc-cancel.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/rpc-cancel.ts:47), [dispatcher.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/wallet-bridge/src/dispatcher.ts:117), [error-envelope.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/wallet-sdk/error-envelope.ts:22)). I do not see an inherent deadlock if acquire stays `exec-mutex -> journal` and cancel stays `journal -> waiter-abort`.

6. `#6` `P2` — Heartbeating `updatedAt` is better than a persisted `reaperExempt` flag. Current reaper uses `updatedAt` and boot-sweeps all non-terminal records unconditionally ([reaper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/operation-journal/reaper.ts:72), [reaper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/operation-journal/reaper.ts:121), [reaper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/operation-journal/reaper.ts:168)). A persisted exempt flag complicates restart semantics. Heartbeat churn is bounded by the existing caps and stops automatically on SW death. One correction: on restart the record is not merely allowed to “age out”; it is failed immediately by boot sweep.

7. `#7` `P2` — The lock-order claim holds on the traced code. I did not find a path that holds `chainGuard.write()` and then awaits the proposed exec mutex. `withPxeWrite` does not call back into `executeAztecSendTx`, and the dapp send path only reaches PXE after entering execution code ([pxe/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/aztec-runtime/src/pxe/service.ts:425), [execution/service.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/execution/service.ts:1695)).

8. `#8` `P2` — SW restart does not resume either T1 or T2 today, and v3 should preserve that. A fresh SW immediately reaps all non-terminal records; proving gets `sw_restart_post_prove`, queued gets `stuck_queued` ([reaper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/operation-journal/reaper.ts:121), [reaper.ts](/Users/alejoamiras/Projects/nulo/nulo-1/packages/extension/src/wallet/services/operation-journal/reaper.ts:185)). So T1 mid-execute and T2 queued-waiting are terminalized, not resumed.

**The one thing**

Rewrite the architecture statement so the exec mutex is acquired before any authwit/build/PXE execution work, and explicitly treat it as correctness-preserving once the baton moves to approval. That rewrite must also move `onInteractionApproved` to the real approval seams (`approveInteraction` for popup, `silentInteraction` just before `executeOperations`) and call out that the nonce argument does not cover `NO_FROM`.
