v3 — Parallel popups

ELI5 companion to plan.md · 2026-05-28 · status: plan ship-it — awaiting your go/no-go

One-sentence summary Make the second transaction's popup open the instant you approve the first (instead of waiting for the first to finish), while keeping the two transactions running one-at-a-time underneath so nothing breaks on-chain. Along the way we found — and will fix — a real bug from PR #53 that's been making popup #2 wait far longer than it should.

What you'll see when it's done

T1 sendTx → popup 1 opens T2 sendTx (you fire it while popup 1 is still open) You approve popup 1 → popup 2 appears RIGHT AWAY → T1's card shows "Estimating fee…" You approve popup 2 → T2's card shows "Queued" T1 runs: estimate → simulate → prove → submit → done → T2 leaves "Queued" and starts its own run T2 runs: prove → submit → done

The key word is "right away". Today popup 2 doesn't show until popup 1's transaction is fully finished. After v3, popup 2 shows the moment you approve popup 1.

Two things we discovered while planning

1. There's a hidden bug from PR #53 — and it's your exact complaint

PR #53 was supposed to release the "go ahead, next transaction" signal early — right after the first transaction builds. But the code that passes that signal and the code that reads it use two different names for the same thing (releaseFifo vs onTxRequestFinalized). So the early signal was never actually connected. It's been silently doing nothing since PR #53.

The fallback safety-net still works — it releases the signal, but only when the whole first transaction finishes. That's exactly why popup 2 waits so long. So v3 isn't only a new feature; step one is fixing this dead wire and adding the test that should have caught it.

2. The "traffic cop" we add is about correctness, not just looks

My first draft of the plan said the new traffic-cop (a "mutex" — a thing that lets only one transaction through at a time) was purely cosmetic — just to make T2 show "Queued". Codex proved that wrong, and it's an important catch:

If we let popup 2 open early and let both transactions run at the same time, they'd both look at the same private notes (your spendable balance pieces) and both try to spend them. The second transaction would then get rejected by the network for double-spending. The NO_FROM transaction type is even more exposed — it has no anti-collision number at all.

ApproachWhat happens
Today (dead wire)Both run strictly one-after-another. Correct, but popup 2 waits ages.
Naïve fix (open popup 2 early, no traffic cop)Popup 2 opens fast ✓ — but T2 gets rejected on-chain. Broken.
v3 (open popup 2 early + traffic cop on execution)Popup 2 opens fast ✓ and transactions still run one-at-a-time ✓.

So the traffic cop restores the safety that opening popup 2 early would otherwise remove. It's load-bearing.

How it's built (6 phases)

  1. Phase 0 — fix the dead wire. Connect the release signal correctly + add a test that drives the real path end-to-end (the kind that would've caught the PR #53 bug). This stabilises the ground everything else stands on.
  2. Phase 1 — release at approval. Move the "next transaction can go" signal to fire when you approve a popup, not when the transaction finishes building. (Subtlety codex caught: it has to fire from the exact approval handler, because the obvious-looking spot actually resolves much later.)
  3. Phase 2 — the traffic cop. A new one-at-a-time lock, keyed per (profile, chain) — matching how the underlying transaction engine already locks. Custom-built because the repo's existing lock auto-expires after 5 minutes, and proving can legitimately take longer. It wraps the entire execution of each transaction, both transaction types.
  4. Phase 3 — cancel + cleanup. Make "Cancel" work even while T2 is waiting its turn (needs a small piece of wiring so the cancel can interrupt the wait). Plus keep the janitor from prematurely cancelling a transaction that's legitimately just waiting in line.
  5. Phase 4 — automated tests. A cheap test that proves popup 2 opens fast; a heavier test that proves both transactions actually complete in order.
  6. Phase 5 — a build for you to try.

Is it risky?

  • The hard correctness question got the most scrutiny — codex specifically hunted for a way the two transactions could corrupt each other, found it (stale notes), and the plan now closes it with the traffic cop wrapping the full execution. Both reviewers signed off.
  • Cancel, restart, and janitor edge-cases are all explicitly handled in the plan with named fixes.
  • No new cryptography, no new dependencies. Pure wiring + a small lock, all in the wallet's own service layer.
  • Scope: ~600–800 lines + tests, across the 6 phases. Bigger than v2, smaller than the original PR #53.
