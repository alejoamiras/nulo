## Re-verify (STEP 1) — LIVE
The coupling persists post-#83. The mechanisms (both models independently mapped the SAME ones):
- controller pre-registered before the wait — `execution-lane.ts:227-232`
- mutex enqueues synchronously before its first await — `execution-mutex.ts:113-123`, `140-163`
- claim reuses that same controller — `claim-helper.ts:123-165`

- journal lock is the arbiter of claim-vs-cancel — `operation-journal/service.ts:223-307`

## Dual-model verdicts (OPPOSITE top-lines)

### claude `a7460098` (Agent/Plan) — **LEAVE IT**
- The "implicit microtask interleaving" premise is WRONG. Three independent serialization layers protect
  the handshake (journal transitionLock arbiter; pre-acquire reuseController always in activeControllers;
  post-claim checkCancelled re-reads signal.aborted) — any one is sufficient.
- Extracting an abstraction WIDENS blast radius: moving `_transitionLocked` out of the pure-storage
  `OperationJournalService` = layering violation / deadlock risk.
- Biggest risk = "abort-before-transition" reordering.
- Recommends: leave the structure, FIX the misleading comment, optionally add ONE deterministic lane test.

### codex `019ef195` (xhigh, read-only; dir `codex-rmDRk1G8`) — **REFACTOR (narrowly)**
- A safe abstraction exists, but ONLY as a very narrow queued-claim/cancel handshake seam. NOT a broad
  "cancellation coordinator."
- Design: an opaque `QueuedClaimHandle` (`queuedJournalId + controller`):
  - `prepareQueuedWait(jobId)` — create controller, register in `activeControllers`, return handle, called
    BEFORE `ExecutionMutex.acquire(...)`.
  - `claimQueuedOrPending(handle, …)` — owns queued|pending decision; NEVER creates/swaps controllers on
    claimed/reused/silent-pending paths; only re-binds/asserts the same controller identity; throws
    `JobCancelledSentinel` on any other stage.
  - `cancelQueuedJob(id)` — owns queued|pending→cancelled; aborts + deletes the controller ONLY after the
    journal transition resolves; if the FSM rejects, must NOT abort.
- Critical rule: "if a queued id exists, controller identity must be continuous from pre-acquire
  registration through claim and execution." Makes queued-claim-without-a-handle a loud failure.
- **Keeps the journal lock as arbiter** (does NOT move `_transitionLocked` out of the journal — so claude's
  main objection does not apply to this specific design).
- "Leaving it purely documented is worse" — the invariant is split across files and the comment describes
  the older, more fragile microtask story.

## Reconciliation (where they actually land)
- **AGREE (the safety substance):** no live bug; real safety = controller-identity-continuity +
  transition-before-abort + journal-lock-arbiter (NOT microtask luck); the `claim-helper.ts:160-162` comment
  is misleading/outdated; the heavy `concurrent-confirm` shard is the real gate; existing race tests cover
  most of it; biggest silent break = a fresh controller after claim OR an await before binding/aborting it

  path carries asymmetric downside).
