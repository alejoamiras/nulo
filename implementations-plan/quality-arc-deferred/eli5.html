Quality Arc — batch 2 (the 6 “supervised-later” findings)

We cleaned up six things a code-quality audit flagged in the wallet — the harder, riskier ones that the first batch deliberately left for careful, supervised work. This page explains, in plain language, what we changed, what to watch out for, and why we’re confident it doesn’t break anything.

Bottom line. All 6 findings are resolved on the dev-quality branch and bundled into promote PR #160 (waiting for your merge). The full network test suite ran green on that exact PR (8/8 Aztec jobs). There is one intentional behavior change to be aware of (proactive auto-lock — see Caveats) and a couple of small “keep an eye on this” notes. Nothing here is a known regression.

What we changed (the 6 findings)

Q4 — “One class doing too much” MOOT — no change

We suspected the ExecutionService was a bloated do-everything class. It turned out an earlier refactor had already split it into small focused pieces. Like opening a closet to tidy it and finding it’s already organized — we did nothing.

Q11 — Three copies of the same “connected accounts” builder DONE · #151

Three places built the same list of “accounts this dApp can see” in the same way. Copies drift apart over time. We replaced them with one shared helper (projectSessionAccounts), so the wire format dApps receive is now computed in exactly one place. Output is identical, character for character — pinned by tests.

Q10 — Services reaching directly into browser storage DONE · #152–#155, #159

Background services used to grab the browser’s storage drawer directly. We changed them to receive a “storage handle” instead — so everything is wired from one place and tests can swap in a fake drawer. The saved-data keys are byte-identical, so nobody’s existing wallet data moves.

Important side effect: the handle also carries the browser’s alarm clock, and wiring it switched ON a feature that was built but asleep — see the proactive auto-lock caveat.

Q19 — ~47 hand-written “is the wallet unlocked?” checks DONE · #156

About 47 spots each hand-wrote the same guard: “get the active profile; if there isn’t one, refuse.” We made one shared guard (requireActiveProfile). This is the most security-sensitive change, so we were extremely careful:

  • We kept the three refusal messages word-for-word (“Profile locked” / “Wallet locked” / “Wallet is locked”) — apps and tests depend on the exact text.
  • We did NOT touch the special guards: the “wrong profile” checks (which stop a different unlocked profile from acting on a session approved by another), the distinct “Unauthorized” message, and the deliberate “stay quiet, return nothing” ones. Both review models independently flagged one of these (a wrong-profile guard) as a landmine a careless sweep would have flattened — we excluded it and added a test proving it still rejects the wrong profile.

Q5 — Three copies of the same transaction error-cleanup DONE · #157

The three “send a dApp transaction” paths each ended with the same error handling: “if the user cancelled, leave it; otherwise mark it failed.” We factored that into one tiny helper (markFailedUnlessCancelled). The subtle part: cleanup (releasing the execution slot) must happen at the exact same instant as before. The first attempt shifted it by one tick; review caught it and we made the helper synchronous so the timing is identical.

Q23 — A scary comment on the cancel-a-transaction code DONE · #158 (comment-only)

The code that cancels an in-flight transaction had a comment calling itself “fragile, relies on lucky timing.” Two models looked closely and concluded the comment was wrong/alarmist — the code is actually protected by three solid mechanisms. We fixed the comment to describe the real safety. We deliberately did not restructure the code (that’s a bigger, riskier change we deferred — see below).

⚠️ Caveats & things to take care of

1. Proactive auto-lock is now ON (the one real behavior change)

Wiring the storage handle into the profile service also switched on a built-but-dormant feature: sessions now auto-lock when their timeout expires, even if you’re not using the wallet. Before, a session only locked the next time you touched the wallet (reactive). Now an alarm fires and locks it (proactive).

Why it happened: the storage handle and the alarm clock travel together in one port — you can’t wire storage cleanly without also lighting up the alarm. This is a security improvement and the intended end-state, and you explicitly accepted it. But it’s a user-visible change:

  • Users idle past the session timeout get locked sooner / more reliably.
  • A dApp mid-session could newly see a “Wallet locked” error if the timeout fires during use.

To watch: any uptick in mid-session “Wallet/Profile locked” reports after release. It’s pinned by a seam test so it can’t silently turn off (or on without the port), but the user-facing timing is worth a line in release notes.

2. Lock messages were kept drifted-but-centralized, NOT unified

The audit’s original gripe was that three slightly different messages had “drifted.” We preserved them word-for-word (tests + dApps depend on the exact strings), so they’re now in one helper’s call sites but still three different strings. Unifying them into one message is a separate, deliberate change for later — not done here.

3. NetworkService argument order (latent footgun)

We inserted the storage handle as the 2nd constructor argument, which pushed an optional “node factory” to 3rd. No current caller is affected. But if you later add a caller that passes the node factory by position, double-check the order. Low risk; flagged so it doesn’t surprise you.

4. Q23 is documentation-only — the structural fix is deferred

We corrected the misleading comment but left the cancel/claim code as-is. Making the safety explicit in code (a small “claim/cancel coordinator”) is the bigger change, deferred to PRs #125/#126, where the right cancel-mid-prove test harness already lives. No live race today — both models confirmed the current code is safe.

5. Deferred work (tracked, not dropped)

  • Q23 structural seam → PRs #125/#126.
  • Q10 PXE injection factory → PR #125 already carries it; we didn’t duplicate it.

6. Test hygiene for future contributors

The shared fake browser used in tests is a global singleton — every test must call .reset() in beforeEach or it sees stale data from the previous test. The arc’s tests all do this; new tests must too.

  • A final confidence pass (codex + claude) — codex caught the proactive-auto-lock behavior change; we documented + seam-tested it and codex re-confirmed.
