Backup-restore security hardening — the plain-language version

The one-liner: when you import a wallet backup, or delete a wallet profile, the extension currently has holes that let a malicious backup corrupt or spy on your other profiles, and lets "deleted" data secretly survive. This one PR closes all of them.

See plan.md for the full plan, findings.md for the verified bugs, and reviews/ + audit-*.md for the review trail.

Why this is a "deep" plan

Three things are all HIGH: it's security-sensitive (cross-profile data theft/destruction + privacy), it has a big blast radius (7+ services, the whole deletion cascade, PXE), and the core fix (an "awaited deletion coordinator") is novel for this codebase. So it went through the heavy process: three independent plans, a double audit (codex + Opus), a fresh final review, and a confirmation pass — five review rounds. Each round found real holes the last missed. It's approved now.

The bugs, in plain terms

  • A malicious backup could plant data in your other profiles. The old code only checked one of three "account-owned" data types. Now every restored row must belong to an account this very import created, on the chain it was created on.
  • A malicious backup could erase one of your real transactions by reusing its ID. Now a restore never overwrites an existing row.
  • A restored "pending" transaction could leak an attacker's chosen hash to whatever wallet's server was active. Now restored pending transactions are dropped (they're just transient sync state).
  • Deleting one profile could wipe another profile's transfer history (a shared bit of code used "whoever is active now" instead of "the profile being deleted"). Fixed.
  • "Deleted" didn't always mean deleted. The cleanup after deletion was fire-and-forget — a badly-timed shutdown could leave orphaned data, and re-adding the same network could resurrect it. Worse, some data (contacts, connected sites, storage on a network you'd removed) was never cleaned at all. The fix is a proper deletion coordinator: it takes a durable "tombstone" note, erases every kind of data while you wait, and only then frees the profile — surviving restarts and refusing to reuse the ID until erasure is confirmed.

The 9 phases (each proves itself with tests that fail on today's code)

  1. Validate every restore writer — reject malformed backup rows instead of silently storing invisible garbage. (core done)
  2. Transactions: create-only + drop restored pending txs — no overwrites, no attacker-controlled server calls.
  3. Provenance on every account-owned slice — a restored row must belong to a just-imported account on its own chain; verify token ownership too.
  4. One-pass network ID remap — no aliasing, reject duplicate attacker IDs.
  5. Token relink by index — simpler + no misgrafted balances.
  6. Token-deletion carries the right profile ID — stop wiping the wrong profile.
  7. PXE deletion tells the truth — don't report failed erasure as success; a profile-wide clear catches orphans.
  8. The awaited deletion coordinator + durable tombstones — the big one: atomic, restart-safe, privacy-erasing deletion.
  9. Coverage + a required end-to-end test — the sandbox test must fail (not skip) if it can't run.

How it gets validated

Every phase runs typecheck + lint + its unit/integration tests; the deletion phases add composition tests (real service graph) and a live-sandbox end-to-end test (import a doctored backup, delete + re-add, prove nothing leaks or resurrects). It all ships as one PR — splitting it would leave exploitable half-states.

The seeds that drive it

/goal and /loop are recorded in the session; the loop drives the phases to completion, consults codex gpt-5.6-sol at every fork, runs the gates, and opens + merges the PR to dev only when the three required CI checks are green.
