worse issue found: profile deletion can erase the active/new profile’s incoming-transfer history, so the P4 “orphan-only, no cross-profile corruption” rationale is false.

- **HIGH — wrong-profile deletion.** [`token/service.ts:544`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/token/service.ts:544>) deletes an arbitrary profile’s tokens and emits `TokenInfo`, which strips `profileId` ([`token/utils.ts:3`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/token/utils.ts:3>)). `IncomingTransferService.onTokenDeleted` then substitutes the *current active profile* and its network before deleting records and resetting trust ([`incoming-transfer/service.ts:479`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/incoming-transfer/service.ts:479>)). Trigger: delete inactive P2—or switch/unlock P1 while P2’s unawaited cleanup runs—where both use the same chain and contract. P1’s incoming-transfer history is deleted and its trust becomes `unknown`. This is concrete cross-profile destruction.

- **HIGH — `deleteProfile()` has a false completion boundary and can clobber its successor.** It deletes the profile row, emits cleanup, and returns while every async listener is still running ([`profile/service.ts:568`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/profile/service.ts:568>), [`event-handler.ts:22`](</home/homelab/Projects/nulo/nulo-review-275/packages/wallet-core/src/utils/event-handler.ts:22>)). Restore deliberately reuses the original profile ID once it is free ([`profile/service.ts:901`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/profile/service.ts:901>)). Trigger: await deletion, immediately restore the same backup. Late callbacks filtering that ID can delete the new generation’s networks, accounts, tokens, FPCs, contacts, dApp sessions, incoming transfers/trust, operation journal and PXE state. Token-balance and auth-registry cleanup are themselves nested fire-and-forget listeners ([`token-balance/service.ts:212`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/token-balance/service.ts:212>), [`auth-registry/service.ts:84`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/auth-registry/service.ts:84>)). PXE deletion also treats IndexedDB `error`/`blocked` as success ([`pxe/service.ts:468`](</home/homelab/Projects/nulo/nulo-review-275/packages/aztec-runtime/src/pxe/service.ts:468>)). Thus “profile deleted” provides no privacy-erasure guarantee.

- **HIGH — transaction resurrection is active, not merely displayed.** Address derivation is deterministic from `masterSecret, chainId, type, index`, and a cleared chain restarts at index 0 ([`account/service.ts:103`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/account/service.ts:103>), [`account/service.ts:200`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/account/service.ts:200>)). Orphan rows surface through address-only reads ([`transaction/service.ts:87`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/transaction/service.ts:87>)). Pending survivors are also loaded into `pending`, polled every second, rewritten, and emitted ([`transaction/service.ts:80`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/transaction/service.ts:80>), [`transaction/service.ts:179`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/transaction/service.ts:179>)). Rows lacking optional `submittedEndpointUrl` query the current profile’s chain node, disclosing the old hash to the wrong RPC provider ([`transaction/service.ts:199`](</home/homelab/Projects/nulo/nulo-review-275/apps/extension/src/wallet/services/transaction/service.ts:199>)). I found no `onChainPurged` consumers or later awaited subscriber that depends on tx cleanup; that narrow ordering claim holds.

**Recommended fix**

Fix the wrong-profile token bug immediately: include authoritative `profileId` in `onTokenDeleted` and scope IncomingTransfer cleanup to it; add an inactive-profile regression test.

There is no safe transaction-only GC patch. The smallest correct boundary is the proposed awaited coordinator: retain/tombstone the profile until cleanup succeeds; snapshot exact `Account[]`; pass their positive address set to awaited tx/auth/incoming cleanup before deleting account rows; similarly await token-balance cleanup from authoritative tokens. Critical local deletion failures must abort and remain retryable, not log-and-continue. Resume tombstones after restart.

Rate P4 **HIGH, release-blocking**. “Zero users” can justify sequencing on `dev`, but not closing/deprioritizing it; it must land before any user-bearing release.
