Fuel — bridge your $AZTEC straight into Aztec gas

Today the faucet can mint test tokens and bridge + swap a token into a little gas. This adds a third, simpler thing: a Fuel tab that takes the L1 fee asset you already hold ($AZTEC / the Fee-Juice token) and bridges it directly into L2 Fee Juice (gas) — no swap, no detour — with the same public / private choice the bridge already offers. Most of the hard machinery (the deposit/claim engine, the private-gas crypto, the public claim) already exists; this recomposes it into a standalone, simpler flow and adds the missing L1 deposit half + a safe new tab.

Why this tier was chosen

This ran as /blueprint deep (three independent planners → consolidate → audit twice → final cold review). Rubric: one clearly-HIGH dimension (security — it moves value across L1↔L2 and touches the private fee-payment contract), it spans two packages (bridge-core + the faucet), and you set the bar to Production. Novelty is LOW (we've shipped fee-juice bridging before), so this was dialed down from your "ultra": mega-deep exists to research brand-new surfaces, but here every building block is already in the repo — paying to "discover" code we wrote would be waste, not rigor. The value of deep showed up immediately: the reviewers caught a data-loss trap and a hidden integrity bug the first draft would have shipped.

The one thing to understand: "private gas" and the risky bit

On Aztec, "private gas" isn't a balance you hold — it's gas a special contract (the PrivateFPC) pays on your behalf so your identity isn't linked. The existing bridge claims private gas while claiming your tokens (the token claim is the "carrier" transaction the gas pays for). A Fuel-only bridge has no token claim — so the gas claim has to ride on a transaction with no real work in it, only the gas-payment setup. That shape is unusual, and we cannot prove it works without a live network (which is down). Everything we can check locally (does it build correctly? does it route to the right fee path? does it ask for the right permissions?) is gated; whether the live network actually accepts it is a deferred sign-off — the single biggest open risk. Public Fuel has no such question (that claim path is already proven).

Phases

Phase 0 — Plumbing + a safety floor that fails closed

Wire up the canonical fee-juice portal + asset addresses (from the network itself, not the dead swap config), with a check that refuses to run if they don't match. Add the pure deposit/claim helpers. Fix a latent bug: the minimum-gas floor today silently skips when the old config is absent — make it mandatory and fail-closed so a too-small bridge can never strand funds.

Proves itself by: bridge-core unit tests (incl. a test that a missing floor fails closed) + typecheck + lint, all green.

Phase 1 — De-risk the private claim FIRST (stop-gate)

Before building any UI, prove what's locally provable about the risky "no-work transaction": correct shape, correct fee-payer, routes to the private-FPC path, and the app actually requests permission for those calls. If this can't be constructed cleanly, STOP and surface it — don't build UI on a broken foundation. (This can't prove the live network accepts it — that's the deferred sign-off.)

Proves itself by: bridge-core unit tests asserting payload shape + fee-payer + capability scope; typecheck + lint.

Phase 2 — Teach the saved-bridges engine about a new asset kind

Add an assetKind tag so the journal can carry "fee-juice" bridges alongside token bridges — done additively so it never drops your existing saved bridges (an earlier draft would have wiped them; the audit caught it). Generalize the bits that are currently hard-wired to the token bridge (deployment-matching, backup, recovery keys) and tighten their validation.

Proves itself by: journal/backup/recovery tests + a test that loads an old saved-bridges file and recovers everything; the existing Bridge flow still passes unit + component + smoke.

Phase 3 — The actual deposit + both claims

Read your L1 fee-asset balance; deposit it into the canonical portal; claim it on L2 — publicly (a sponsored claim, already proven) or privately (the carrier-less claim from Phase 1, with the fail-closed floor and the "never fall back to public" guard). Durably save + seal the one secret (a salt) needed to recover a private claim.

Proves itself by: unit tests for both claim builders + the floor; smoke-e2e for public happy-path + private flow + too-small rejection (the private smoke proves orchestration, not live acceptance).

Phase 4 — The Fuel tab, done safely

Add the tab + form + receipt. The catch the audit found: the app keeps both tabs alive at once, and they'd fight over the same "what's in progress" state — a hidden tab could double-toast or show the wrong receipt. Fix it by lifting that "in-progress" surface above both tabs so there's exactly one owner.

Proves itself by: a NEW whole-app test that switches Bridge↔Fuel tabs and proves a single in-progress owner (the old test only mounted one tab, so it couldn't catch this) + the existing Bridge smoke still green.

Phase 5 — Harden + document

Security pass on the new flow (no secret logging, no private→public fallback, hard-block on address mismatch, keep the private-FPC out of broad permission registration), then docs + the live sign-off checklist.

Proves itself by: the full explicit local gate (bridge-core + faucet tests + e2e + build + lint + typecheck) + a /harden security pass with no unaddressed high/critical.

What the deep review changed (so you can trust it)

Three planners (me, codex, a separate Opus) drafted independently; two then attacked the merged plan. Real catches that changed the plan:

  • Data-loss trap: the first merge wanted to "bump the journal version." The reviewers proved that would make the loader silently delete every saved in-progress bridge (including the only recovery secret for a private one). Switched to a purely additive tag.
  • Hidden integrity bug: a naive new tab would fight the existing one over shared in-progress state. Fixed structurally (Phase 4).
  • Fail-open floor: the safety floor silently skips today when the old config is missing. Made mandatory + fail-closed.
  • Honesty fixes: the private claim's live risk was understated (now flagged as the dominant deferred risk); two validation gates claimed coverage they couldn't deliver locally (corrected).

The one risk to accept consciously

Private Fuel's claim shape ("a transaction with only gas-setup, no app work") is not provable without a live network, which is currently down. You locked "public + private, both, full parity," so private stays in and gets everything we can verify locally — but its live correctness is a deferred sign-off. If, when a network is back, the sequencer rejects that shape, the fix (a deferred-gas-reserve model, or temporarily public-only) is a future follow-up — explicitly out of this plan's scope.

Open decisions (your call at approval)

  • Config trust: pin the portal/asset in config plus a runtime check that hard-blocks on mismatch (recommended).
  • Private live-trust: acknowledge private ships locally-complete, live-deferred — and that the deferred sign-off depends on re-confirming the private-FPC address for the new network version.
  • Journal view: one shared "your bridges" list (recommended, least surface) vs a separate Fuel-only list.
  • Copy: call it "$AZTEC" on the L1 side, "Fee Juice" on the L2 side (recommended) — don't mix them.
  • Migration: do NOT pay for a downgrade-compatibility migration (recommended — the additive tag avoids it; old-build misread is a low-severity testnet-only edge).
