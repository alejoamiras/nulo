## Blocking findings (both auditors agree)

1. **I2 / Phase-1b mechanism unimplementable.** `value-projection` cannot carry the active pointer: (a) registry is one `SliceDescriptor` per service name and `NETWORK_SERVICE_NAME` already owns a `root` (`backup-migration-registry.ts:177`); (b) `value-projection.key` is a STATIC string (`:96-98`), but the active key is per-profile `nulo:core:active-network@<profileId>`; (c) nothing on restore writes the pointer — `NetworkService.restore` writes only rows (`service.ts:651-703`), and `profileId` is regenerated (`useFullBackupImport.ts:387 normalizeAllIds(...newProfile.id)`), so a pointer keyed by the OLD profile id is never read. **Correct mechanism:** export the active network's `chainId` as a TOP-LEVEL backup field (produced in `full.vue:145-159` from `getActiveNetwork()`), resolve on restore against `createdNetworks` (new id+chainId, `useFullBackupImport.ts:396`), write the pointer keyed by `newProfile.id` via a profileId-parameterized `NetworkService` write BEFORE `finalizeRestore` (mirroring how `restore` writes rows without `requireActiveProfile`). Unmatched/hostile chainId → primary/default.

2. **Phase-1a `kind === "mainnet"` regresses e2e.** `agent.sh:47-49,67,80` builds e2e with `VITE_NULO_E2E_DEFAULT_NET=testnet` specifically so import flows bootstrap on Testnet (CI can't reach Alpha's RPC; each blocked call eats the 60s-abort×retry envelope). A `kind==="mainnet"` fallback → imported profiles bootstrap on Alpha under the e2e flag → blackholed RPC → blown budget, AND fresh (seed primary=Testnet) vs imported (fallback=mainnet) DIVERGE. Must expose the primary from `NetworkService` reading the SAME `isPrimaryActive` signal. The Phase-1 gate "import on Alpha → resolves to Alpha" is self-contradictory under the e2e flag (primary=Testnet there).

3. **Item-3 fix mis-scoped → real cross-account leak.** Settled txs already refresh via `app.vue:87-96` → `syncTransactions()`. The under-specified stale surface is INCOMING TRANSFERS: `useIncomingTransfers` reads account reactively in `scope()` but has no scope watcher (`useIncomingTransfers.ts:74,80`), and the render loop pushes incoming rows with NO account filter (`RecentActivityView.vue:103-112`) → Account1's incoming rows keep rendering under Account2. The race (slow Account1 `refresh()` resolving after switch to Account2) is where the `cancellable-rejection.ts` guard actually matters — the plan points it at the already-scope-filtered journal. Fix = call `useIncomingTransfers.refresh()` + guard it; re-fetch only (no per-account subscription to tear down; disconnect/reconnect would churn ports).
