Fast-path for internal balance reads

A small, focused follow-up to PR #56. We make balance refresh and gas-balance reads measurably faster by sending the "easy" calls directly to the chain node — bypassing a slow gate they don't need.

1. What this PR does in one sentence

When our wallet asks "how much of token X do I own?" on a public token, it currently goes through a heavy proving pipeline. This PR lets it skip the pipeline for read-only public questions, which is what it was already doing for dApp simulations. We're closing the gap between "internal" and "external" balance reads.

2. The five-second background

Aztec has two ways to "ask" a contract a question:

  • Through the kernel (slow path): goes through the wallet's account contract, runs a kernel circuit, validates signatures and auth witnesses. Required for anything that does something (private transfers, complex public writes). Optionally also for asking things.
  • Direct to node (fast path): the chain node runs the function and returns the answer. No kernel. No auth. Only works for public + static functions — those marked read-only at compile time. Available since Aztec wallet-sdk 4.2.

The fast path is roughly an order of magnitude faster for read-only public calls because it skips the kernel proving setup AND a global lock the wallet holds while proving transactions.

3. What we already did, and what we missed

Place that asks balance questionsToday
A dApp asking through aztec_simulateTx✓ uses fast path (shipped v0.14.7)
Our own UI refreshing token balances (balance-projector)✗ slow path
Our own UI checking gas balance (FeeJuice)✗ slow path

This PR extends the same fast-path optimization to those last two — the wallet's own internal reads.

4. Why now / why this is worth doing

  • It's the same lock as proving. If you submit a transaction, the wallet starts proving (can take seconds to minutes). During that time, a balance refresh sits behind the same lock. Skipping the lock for reads removes that user-visible stall.
  • Every primitive already exists upstream. We're not inventing anything — we're calling the same simulateViaNode helper our dApp side already calls. The risk surface is small.
  • Free correctness improvement. Both arms (fast and slow) anchor at the same chain block, so the answers are identical. We pinned that invariant in tests.

5. What changes in the code

One helper file gets smarter. Today it splits calls into two groups:

          ┌── PUBLIC + PRIVATE bundled    →  slow path (one kernel pass)
calls  ───┤
          └── UTILITY reads (private balances)  →  parallel, off the kernel

After this PR, it splits into three:

          ┌── PUBLIC + isStatic           →  FAST PATH (direct to node)  ◀ new
calls  ───┼── everything else PUBLIC+PRIVATE  →  slow path
          └── UTILITY reads                →  parallel, off the kernel

The fast path and the slow path run at the same time (in parallel) when a batch has both kinds. The slow path goes away entirely when every call is fast-eligible — which is the common case for balance refresh.

6. What could go wrong (and what we do about it)

ConcernHow we handle it
The two arms anchor at different blocks → inconsistent balances on screenBoth arms use the same block header as their anchor. Same pattern upstream's BaseWallet already uses.
The fast helper had a class-rehydration bug twice in the dApp versionThat bug happened because data crossed an extension-process boundary. Our internal helper never crosses a boundary — the calls stay in the service-worker process the whole time.
Fast helper errors at runtime (network blip, node hiccup)Silent fallback: we re-route the fast calls through the slow path. User sees a slightly slower refresh, not an error.
A contract claims to be "static" but isn'tNoir's compiler enforces this at compile time. If the artifact says static, it's static.

7. How we'll know it worked

  • Unit tests: pin the routing decision (when does fast vs slow get picked?) and the silent-fallback behavior.
  • Integration test: spin up a real Aztec sandbox, run balance reads through the helper, assert the answers match what the slow path produces.
  • Manual smoke: open the popup, refresh tokens, watch it feel faster — especially while a transaction is proving in the background.

8. Open questions the plan calls out

  • Should we cache the block header across batches? balance-projector chunks 50 tokens into 5 batches of 12; each currently re-fetches the header. Small cost, probably skip for v1. → "follow up if measurable"
  • Should we also refactor the dApp-side fast-path orchestrator? No — different output contract (it must merge into one upstream result; ours unpacks per-call). Different problems, same primitive.
