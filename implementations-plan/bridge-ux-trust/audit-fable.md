### 0. Verified baseline (what exists today)

- **Double-sign on every private deposit.** `sealRecordSecret` signs the per-record message once to derive the AES key and a second time to self-test determinism (`packages/bridge-core/src/recovery-crypto.ts:70-84`). The same-session claim then signs a **third** time, because `doClaimAndConfirm` always unseals from the persisted record even seconds after sealing (`packages/faucet/src/composables/useDeposit.ts:173-180`). So a fresh private deposit today = 3 `signMessage` prompts + 3 L1 txs + 1 Aztec prompt.
- **Single-pending storage.** Deposit: `PENDING_KEY = "nulo-bridge-pending-deposit"` (`useDeposit.ts:49`), one JSON object, second deposit blocked (`useDeposit.ts:264-270`, commit `870b300`). Withdraw: `"nulo-bridge-pending-withdraw"` (`useWithdraw.ts:31`), no discard affordance at all.
- **HIGH (a) — tamperable metadata.** Resumed private claim takes `recipient` from localStorage and claims to it (`useDeposit.ts:168` → `claim_private` at :198). The private content hash binds **amount only** (`packages/bridge-core/src/content-hash.ts:55-57`), so the secret is a bearer credential; the only guard is connected-account equality (`useDeposit.ts:375-379`).
- **HIGH (b) — balance-heuristic completion.** `preBalance` persisted (`useDeposit.ts:296-297`), record cleared when balance ≥ pre + amount (`useDeposit.ts:184-192`, :236-243). An unrelated private credit clears the record and destroys the only sealed blob.
- **Mechanics that must survive:** sync-gate classifier `isMsgNotReady` with the testnet-verified private wording (`useDeposit.ts:101-102`); 300×6s simulate poll then single send (`useDeposit.ts:203-227`); module-level `claimInFlight`/`consumeInFlight` dedup; proven-epoch wait + receipt poll + witness + L1 consume (`useWithdraw.ts:105-188`); `consumeTxHash` persisted **before** awaiting (`useWithdraw.ts:179-182`); private resume account-mismatch refusal (`useDeposit.ts:375-379`).
- **Reusable but unused journal scaffolding.** `packages/bridge-core/src/recovery.ts` already implements KV-injected multi-record CRUD but **nothing imports it** except its own test. Right skeleton, wrong schema; this arc replaces it.
- **Crypto substrate is AEAD.** `EncryptionKey` = PBKDF2-600k → AES-256-GCM, version-tagged blob (`packages/wallet-crypto/src/encryption-key.ts:34-47`). GCM authenticates the plaintext; there is **no AAD parameter**, so authenticated metadata must live *inside* the sealed plaintext. The recovery key message already binds `chainId+portal+bridge+secretHashHex` (`recovery-crypto.ts:25-31`).
- **Completion-by-specific-tx is achievable with existing surfaces.** `TxStatus` includes `DROPPED…FINALIZED` and `TxReceipt.executionResult: "success"|"reverted"`. The exit capture pattern `(await ….send(opts)).receipt.txHash` already exists (`useWithdraw.ts:231-237`); the claim currently discards its send result (`useDeposit.ts:227`). `node.getTxReceipt` polling already exists (`useWithdraw.ts:134-138`).
- **Balances.** L2: `useTokenBalance` reads both privacies, 15s poll. L1: **no ERC20 balance reader exists** — must be built (canonical viem, `useL1Wallet.publicClient`).
- **Capabilities need no change** (`packages/faucet/src/lib/capabilities.ts:191-259`). Decimals 6 both sides. Legacy record shapes verified incl. pre-private dev shape via `git show 5470839`.
- **Conventions.** e2e selects only by `data-testid`; faucet has **no package-local `lint` script** — lint is root `bun run lint`; pre-PR gate root `audit:vue`; `audit:faucet` runs test+verify:deployments+build. Only the two dying cards reference the old testids (grep-verified).

### 1. Core design decisions

**D1. Journal storage schema** — one localStorage key `nulo-bridge:journal:v1`, versioned, array capped at `MAX_RECORDS=100`. Persist milestone FACTS; derive display stage at runtime (storage can't lie about progress). Deposits keyed `secretHashHex`, withdraws `exitTxHash` or provisional `wd-pending-<rand>` until the exit receipt returns the hash. Fields per record: kind, isPrivate, amount (display-only for private — authoritative copy in the envelope), createdAt, completedAt?, recipient (display-only for private), secret (public only), sealedEnvelope (private only), secretHashHex, sealerL1, depositTxHash (persisted the moment writeContract returns — leafIndex becomes chain-recoverable), leafIndex?, claimTxHash?; withdraw: recipientL1, exitTxHash?, exitBlock?, consumeTxHash?. Canonical stages: deposit `depositing→syncing|claimable→claiming→done`, withdraw `exiting→proving|consumable→consuming→done`, plus a runtime-only `attention` substate (`mismatch | tampered | unseal-failed | stale | unknown-outcome | error`).

**D2. Authenticated metadata — the sealed envelope.** v2 plaintext = `{"v":2,"secret","recipient","amount","leafIndex"?}`. Seal #1 before any irreversible L1 tx (no leafIndex). **Re-seal #2** after the deposit receipt yields the MessageSent index — same envelope + leafIndex, encrypted with the **in-memory `EncryptionKey` retained from seal #1** — zero additional signatures. Open+verify on claim: decrypt → legacy fallback for bare-secret blobs → enforce envelope.recipient/amount (+leafIndex when both present) vs the outer record; mismatch ⇒ stop before any send, `attention: tampered`, rewrite display from the envelope, require a second explicit Claim. Claim args ALWAYS from the envelope for private deposits. leafIndex resolution: envelope → L1 receipt of depositTxHash (`parseEventLogs(InboxAbi, "MessageSent")`) → never bare localStorage. Public deposits + withdraws get NO envelope (their messages bind recipient+amount on-chain; tamper = revert = DoS-only).

**D3. Seal self-test cache.** `nulo-bridge:seal-trust:v1` keyed `<chainId>:<l1addr lowercase>` → `{verifiedAt}`. Positive-trust only; absence ⇒ full two-signature self-test; presence ⇒ single signature. Invalidation: revoke on any GCM unseal failure (record untouched, `attention: unseal-failed`, Claim re-armed); no TTL; never negative-cache. **Same-session claims stop re-signing**: module-level in-memory `Map<id, {secretHex, key}>` (never persisted, cleared on done/discard) kills today's third signature. Plus: skip `approve` when `allowance(owner, L1_PORTAL) >= amount`. Signature economics: first-ever private deposit per wallet = 2 signs; every subsequent = 1; claims 0 (same-session) / 1 (post-refresh).

**D4. Completion by specific tx.** Deposit: capture `claimTxHash` from the send receipt, patch immediately (stage→claiming), poll `node.getTxReceipt`: success ⇒ completedAt; dropped ⇒ clear claimTxHash, back to claimable, manual retry; reverted ⇒ `attention: error`. **Delete the entire preBalance/isCredited machinery.** Withdraw already confirms via consumeTxHash — keep verbatim, per-record. A rediscovered record with claimTxHash/consumeTxHash is auto-FINISHED by waiting on that receipt (prompt-free; the send already happened — today's consume-recovery generalized).

**D5. Journal policy.** Per-record `inFlight: Set<recordId>`; different records may progress concurrently. `sessionLive: Set<recordId>` populated only by deposit()/withdraw() in this page session — the connect-watchers auto-drive only sessionLive records and prompt-free receipt-waits; everything else gets read-only stage pollers (withdraw: getTxReceipt + getProvenBlockNumber → proving/consumable; public deposit: prompt-free simulate-gate can pre-run honestly; private deposit: shows `claimable` ("Resume claim") once leafIndex exists — the simulate needs the secret, and unsealing costs a signature, so the sync wait happens after the click; a dummy-secret probe is impossible — wrong secret produces the same "No L1 to L2 message found" revert). Account-mismatch: per-record, enforced pre-click and post-unseal. Failure containment per record. **Write-and-verify before irreversible txs** (today `persistPending` swallows exceptions and would proceed into stranding). Done cards retain data (incl. the sealed blob) until explicit **Clear** (distinct from Discard; 7-day auto-prune).

**D6. Composable architecture.** Module-singleton `useBridgeJournal.ts` (reactive records, runtime map, migration, watchers, `runDepositClaim(id)`, `runWithdrawConsume(id)`, discard/clearDone). `useDeposit` → `useDepositFlow` (validation + trust-aware seal + record + L1 legs — allowance→approve?→deposit, **no mint** — + milestone persists + sessionLive + hand-off). `useWithdraw` → `useWithdrawFlow` (provisional record → burn authwit + exit → id upgrade → hand-off). New `useL1Usdc.ts` singleton: balance (15s poll + refresh hooks), mint(amount), allowance — ERC20 ABI moves here + balanceOf/allowance. Logging policy: ids (secretHash is public on L1), stages, tx hashes; never secret/envelope/signature/key.

### 4. Security & Adversarial Considerations

Assets in attack-value order: bearer secret; journal metadata; seal-trust verdict; user signing attention. Attacker with localStorage write: recipient/amount swap CLOSED (envelope-authoritative); preBalance forgery CLOSED structurally (field gone); claimTxHash forgery DOWNGRADED (blob retained until Clear ⇒ recoverable; capability ≡ deletion); leafIndex/depositTxHash/secretHashHex tamper = liveness-only; seal-trust poisoning = stranding-DoS, deletion-equivalent, mitigated by revoke-on-failure (cache deliberately not MAC'd — no key available without spending the signature the cache exists to save); journal flooding capped; forged stale records baited-discard countered by two-step + nothing-real-to-destroy. XSS beyond storage: can request signMessage + exfiltrate post-unseal — the per-record self-describing signed message is visibly odd out of context; secrets never in logs/reactive state; CSP = separate pass (Ask). At-rest theft gets GCM ciphertext under a 256-bit-entropy signature-derived key. Log policy + copy/phishing surface (CLEAR vs DISCARD distinct labels; mint card never reads as value; seal-note trains anti-blind-signing). Red-team targets: migration path (parse-isolate each record, write-before-delete), dropped-claim retry loop (manual-only retry), concurrent prompt racing (per-record inFlight + wallet mutex; manual test).
