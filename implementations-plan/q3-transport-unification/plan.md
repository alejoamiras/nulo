# Plan — Q3: unify the forked background/offscreen RPC transports (deep)

**Origin:** `/harden quality` finding Q3 (run `2026-06-11-ultra-50b45d`). De-fork the two parallel RPC transport stacks in `@nulo/extension-messaging` into one shared service-core + correlator, and fix the latent error-contract divergence.

**Tier:** deep. Rubric — blast radius HIGH (the wallet's whole RPC boundary: 21 background `ServiceClient` subclasses + PXE offscreen + the dApp error envelope), irreversibility MODERATE, migration cost MODERATE (consumer + dApp-envelope + test migration on the flip), external coupling LOW, security sensitivity MODERATE-HIGH. 3 HIGH ⇒ deep.

**Provenance:** main + codex + Plan-subagent drafted independently; consolidated here; then DOUBLE-AUDITED (codex + fresh hostile subagent), both `reject` Round 1 — findings folded below (v2). Drafts: `draft-main.md`, `draft-subagent.md`; audits: `audit-codex.md`, `audit-fable.md`.

## Core approach
Template-method extraction with transport seams as hooks. Two shared bases — a **client request-correlator core** and a **service core** — both transports extend; transport liveness (port reconnect vs one-shot sendMessage, keepalive, telemetry, uid) stays in subclasses. Reuse `errors.ts` `toPayload`/`walletErrorFromPayload`. **Service-side `errorPayload` emission is wire-ADDITIVE and unifies in P3 (the offscreen client ignores it until P4) — this resolves the P1/P3/P4 boundary contradiction the audit caught.** The client-observable offscreen flip (string→typed) + the dApp error-envelope handling land in P4. Each phase independently shippable + revertible.

**Standard gate (every phase):** `bun run lint` + `bun run --cwd packages/extension-messaging typecheck` + `bun run --cwd packages/extension-messaging test` + `bun run --cwd packages/extension test`. (extension-messaging tests ALREADY run in CI via `_unit-tests.yml → test:all → bun run --filter '@nulo/*' --if-present test` — no new wiring needed.)
**Network gate (behavior-sensitive phases):** smoke `bun run test:e2e`; network e2e via `e2e:network` label / `bun run e2e:agent` — judged green ONLY after syncing to latest `dev` incl. de-flake commits (Q22/Q7 base-staleness lesson). **Exactly-once correlator properties are UNIT-gated (network e2e is liveness-only — it cannot deterministically force timeout/late-response/send-throw interleavings).**

## Chrome-extension runtime realities (what unit can vs can't prove)
This entire plan is MV3-extension plumbing: the two transports ARE `chrome.runtime` APIs — a long-lived **Port** (`onConnect`, popup ↔ background SW) and one-shot **`sendMessage`/`onMessage`** (background SW ↔ offscreen document) — spanning three execution contexts (service worker, offscreen doc, popup). That has a hard consequence for validation: a mocked-`chrome` unit test and a real Chrome prove DIFFERENT things, and neither substitutes for the other.
- **Mocked-`chrome` UNIT proves LOGIC** (the bulk of the gates): id correlation, pending-map exactly-once, timer arm/clear lifecycle, success-decode + dispatch, per-transport error-shaping, telemetry record shape, the unknown-method guard, and that the reconnect/keepalive HANDLERS fire on synthetic events. These are deterministic and fast — they're where the correlator's correctness is actually pinned.
- **REAL Chrome (Puppeteer smoke + network e2e) proves LIFECYCLE** — things a fake `chrome` object cannot exhibit: actual **SW idle-death at ~30s → Port auto-reconnect → in-flight/next request still resolves**; **keepalive efficacy** (the SW genuinely survives a >30s PXE prove flow); the real set of values that trip **`DataCloneError`** through `postMessage`/`sendMessage` (the A6 fallback's reason for existing); and the offscreen-document spawn/teardown timing.
- **Therefore:** behavior phases (1–4) carry BOTH legs. The unit leg is load-bearing for correctness; the e2e leg is load-bearing for the Chrome-runtime behaviors. A gate that claims a lifecycle property (reconnect, keepalive survival, real clone failure) is satisfied by a unit test is wrong — those moved to the e2e leg in P2/P3 above. This is also why the network gate is "liveness + the specific real-Chrome behaviors," never the exactly-once proof (which is unit-only — the harness can't force the race interleavings deterministically in a real browser).

## Security & Adversarial Considerations
- **RPC trust boundary:** the shared core must not trust envelopes — today there are null/malformed throw paths (P1 fix) + the **callable-any-method** surface (`method in this` invokes inherited/prototype methods) — fixed at extraction (P3), hardened (P5).
- **dApp oracle (corrected — was wrong in v1):** the offscreen error flip DOES reach the dApp via `toWalletResponseError` (`background.ts:647`). Mitigation = explicit `Rpc*` cases in `error-envelope.ts` + a dApp-contract gate (P4). Do NOT widen what message/detail crosses to the dApp — `Rpc*` cases emit an intentional message, not raw internal detail.
- **Telemetry sanitizer** (`telemetry.ts:80-99` allow-list) must keep passing only the static `detail` category post-flip (typed errors carry richer, user-influenceable `message`/`details`); pin `not.toContain("rm -rf")`.
- **`walletErrorFromPayload`** rebuilds by `code`, base-`WalletError` fallback for unknown — no eval/proto risk; `details` opaque `unknown`.
- **`resultIsJson`** parses ONLY response `result`, never events/error strings.
- **Exactly-once terminal semantics** (timeout/disconnect/send-fail/late-response races) is the main foot-gun — unit-gated.
- No crypto, no new deps, no privilege change.
