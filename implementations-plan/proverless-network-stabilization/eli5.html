Proverless Network E2E Stabilization

Our networked end-to-end tests (a real wallet driving real transactions against a local Aztec sandbox) are flaky — they go red for reasons that aren't real bugs. That means we can't trust them, so they're only "advisory" on the dev branch. The plan fixes the flakiness at the root, proves it's gone with a repeated "soak" run, and only then makes the suite a required check so a broken network change can never sneak into dev again (which is exactly how PR #85 slipped a red suite in).

Why this tier was chosen (deep)

High on blast radius (this becomes a gate on every PR) and external coupling (anvil + Aztec sandbox + Chrome + WASM proving), plus real security surface (a required CI gate is part of the trusted "is this safe to merge" path). Two-plus high dimensions → deep. The ceremony paid off: three independent planners (me + codex + an opus architect) each caught a load-bearing factual error in my own brief, and the hostile double-audit found six real flaws I'd otherwise have shipped.

The big idea (the question you handed me)

You asked: should the test "proverless" mode be made broader so tests can reliably time the simulating/proving/submitting stages — or does that break the idea of an e2e? Answer: don't broaden it. A test-only "hold" point at the proving step already exists and is clean. The real fix is simpler: read the wallet's durable journal record as the source of truth (it doesn't vanish when proving is fast), and only look at the on-screen card when a test is specifically about rendering. Broadening the stub would mean faking the real simulator/network — which would break the e2e and risk the worst outcome (shipping a wallet that sends unproven transactions).

Phases

Phase 0: Lock the "never ship proverless" guards

Before touching anything, pin (as unit tests) the guards that stop the fake-proof test mode from ever reaching real users. We're about to edit test-mode-adjacent code, so we secure the catastrophe-prevention first.

Proves itself by: unit tests for the fail-closed double-opt-in, all green.

Phase 1: Fix the timing races at the real source (the journal)

Replace assertions that race the on-screen card with ones that count the wallet's durable journal records ("≥1 transaction active AND ≥1 queued in this session"). Retire the old, sloppy helper that accepted any record (even a finished one). This kills the whole Mode-1 family.

Proves itself by: the concurrent + single-tx tests pass 10 runs in a row locally.

Phase 2: Build the "see what actually failed" harness

The last debugging round failed because we guessed instead of looking. This phase adds a failure-classifier that, on any timeout, snapshots the journal + browser + sandbox health so we can tell a frozen browser apart from a stuck sandbox apart from a real bug — no more blind bisecting. Pull fresh failure artifacts (don't rely on old ones expiring).

Proves itself by: a fresh failing run is captured + classified for all 4 modes.

Phase 3: Fix the long hangs (resource starvation)

Some shards hang 17–21 minutes — the browser freezes under load on the CI machine. The fix is reducing memory pressure + a Node-side wall-clock guard that turns a 21-minute dead-air hang into a fast, labeled failure (we can't use a browser ping — the browser is the thing that froze). Critically, we prove the fix on the real CI machine, not just a local container (a container that never reproduces the freeze can't prove it's gone).

Proves itself by: a real-runner soak shows the freeze gone + before/after memory evidence.

Phase 4: Diagnose-then-fix the remaining two modes

A settle-timeout and a "transaction errored" mode could each be a real wallet bug OR just load. We read the captured error first, name the cause, then fix it — no blind gas-knob bumps that could hide a real concurrency bug.

Proves itself by: the cause is named in the commit + 8 green runs in a row.

Phase 5: Soak — prove it's really stable

Run the whole suite many times and require it green with zero retries used (a test that only passes on a retry is still flaky — the soak enforces that, it's not just a slogan).

Proves itself by: full matrix 5/5 with zero retries consumed, recorded in lessons.

Phase 6: Ship it — close the CI bypass holes (one PR)

Make the trigger fail-closed (run the suite unless the PR is docs-only — covering the shared packages + patched deps the old allowlist missed), pin the CI actions to exact versions (a floating tag in the trusted pre-gate job is a supply-chain hole), remove a dead secret, and update the docs. One well-validated PR — merged only when you're extra-sure.

Proves itself by: the full pre-PR gate is green; a shared-dep PR triggers, a docs PR skips+passes.

Phase 7: Make it required (your call, admin step)

After the PR lands and dev is green, flip the suite to a required check. This is a GitHub settings change, not code — so you do it (or approve it). With a documented admin-override for genuine CI/platform incidents (not test-skipping).

Proves itself by: a deliberately-red network PR is blocked; a docs PR still merges.

Human context

"Proverless" is a test-only speed-up: it fakes the expensive cryptographic proof so a transaction finishes in ~3 seconds instead of minutes. Real users always get real proofs. The flakiness appeared because that speed-up made the proving step so fast that tests watching for it "live" started missing it — and a separate set of tests just run out of resources on the modest CI machine and hang. Two different problems, one suite.

What the audits changed

The hostile review caught that my first draft (a) tried to scope a test helper to a specific transaction — impossible, because concurrent transactions in one session look identical (fix: count them instead); (b) had a Phase-3 "proof" that could pass while CI still hung (fix: require the real-machine soak); (c) left CI bypass holes through shared packages + patched deps (fix: true fail-closed); (d) used a browser-ping watchdog that hangs when the browser is frozen (fix: a Node-side timer); and (e) specced work that already existed in the repo (dropped).

The final fresh-context codex pass then conditionally approved, catching two more: the Phase-3 gate referenced a workflow not built until Phase 5 (fix: build it in Phase 2), and my Node-side timer would have killed legitimately-long tests like authwit-lifecycle (which runs up to 20 minutes) — so it's now a no-progress stall detector, not a fixed clock. Plus: protect the gate's own workflow files from being edited in the PR they're gating. All folded in.
