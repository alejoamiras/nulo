Release-pipeline hardening

When we shipped v0.24.0, the website (nulo.sh) stayed stuck on the old version and needed a manual Cloudflare poke to update. This plan fixes the actual cause so it can't happen again, adds a one-command "un-stick the website" button for emergencies, and turns on the auto-release helper that makes the whole thing hands-off next time.

Why this tier was chosen

Light. Rubric: novelty LOW (the exact fix — an always() guard — is already used elsewhere in the same file), blast radius MODERATE (a mistake breaks the release process, not the shipped extension), irreversibility LOW (CI edits revert; the on/off switch is a repo variable), migration NONE, external coupling MODERATE (Cloudflare, but we don't change the hooks — only when they fire), security LOW (no new secrets or permissions). Zero HIGH dimensions → light. Codex audited it: conditional approve, and its most important catch (don't weaken the safety-net check) is already folded in.

Phases

Phase 1: Fix the two deploy jobs so they stop skipping

Two jobs that redeploy the website + faucet (refresh-landing, deploy-faucet) silently switch themselves off whenever an earlier optional job (the long network test) is skipped — which happens on every manual release. The one-line-each fix is the same always() guard the neighbouring jobs already use, plus a "don't fire if the run was cancelled" safety. We deliberately do not touch the verify-live checker (it's the smoke alarm that caught this bug — muffling it would hide the next one).

Proves itself by: actionlint passing + a walk-through of the on/off conditions (optionally, a real dispatch that shows the jobs run instead of skip).

Phase 2: A one-command "refresh the website" button

A tiny new workflow you can run by hand (gh workflow run refresh-landing.yml) that pokes Cloudflare directly. If the site is ever stale for any reason, this fixes it in one command — no API token, no account ID, no dashboard hunting (all the things I had to do this time).

Proves itself by: actionlint passing + running it once triggers a real Cloudflare deploy.

Phase 3: Update the runbook + flip the auto-release switch ON

Rewrite the release runbook (the old manual "poke Cloudflare" steps are now obsolete) and turn on AUTO_UNSTICK_ENABLED — the helper that finishes a release automatically instead of needing a 45-second manual nudge. We flip it via a repo variable (an instant off-switch) and leave the code default OFF, so it stays reversible until one real release proves the automatic path.

Proves itself by: the stale runbook claim is gone (grep) + the variable reads on + actionlint passing.

Human context

GitHub Actions has a quirk: if job C depends on job B, and B depends on a job A that got skipped, then C can skip too — unless C says always(). The person who built this pipeline already learned this and put always() on the build/upload jobs (there's even a comment about it), but the two final deploy jobs were missed. That's the whole bug. The fix is to make those two consistent with the rest.
