How Nulo makes your keys

A plain-English tour of the wallet's key system as it exists today — and what a more "standard" version would look like.  ·  June 2026 · @aztec 5.0.0-rc.1 · @nulo/extension 0.24.0-rc.1

Read this first — the one-paragraph version

Nulo does not use a seed phrase as its starting point the way MetaMask does. Instead, every wallet ("profile") is built around a single 32-byte master secret. That secret is born in one of two ways: a password profile rolls a random number and locks it with your password; a passkey profile derives the secret from your fingerprint/Face-ID passkey every time you unlock. From that one master secret, the wallet mathematically grows every account, every signing key, and every privacy key. There is a 24-word seed phrase in here — but it's an export/backup feature for password profiles only, never shown during sign-up, and the passkey path has no seed phrase at all. The thing that actually signs your Aztec transactions is always a classic Schnorr key; the passkey itself never signs anything on-chain — it only reconstructs the secret in memory.

1 · What is a "key" here, really?

Crypto wallets throw the word "key" at a lot of different things. In Nulo there are four distinct layers, and keeping them separate is the whole game:

LayerPlain-English nameWhat it is
Master secret"the one true secret"A single 32-byte number (a point in Aztec's number field, called an Fr). One per profile. Whoever has this owns everything in the profile.
Per-account secret"this account's secret"A child number, mixed from the master + which chain + which account index. One per account.
Signing key"the pen that signs"A Schnorr key grown from the per-account secret. This is what actually authorizes a transaction.
Viewing / nullifier keys"the privacy keys"Aztec is a private chain. These keys let you see your own incoming private notes and spend them without revealing who you are. Also grown from the per-account secret.
ELI5

Think of the master secret as the master key to an apartment building. From it the wallet cuts a key for each apartment (per-account secret). Each apartment key is actually two keys on one ring: a pen that signs your name (Schnorr signing key) and a pair of special glasses that let you read invisible mail addressed to you (viewing keys). The passkey/password is just the thing that gets the master key out of the safe — it isn't any of these keys itself.

Two facts that surprise people:

  • The passkey never signs a transaction. On Aztec, the on-chain account contract checks a Schnorr signature. The passkey's only job is to rebuild the master secret in memory; the Schnorr pen does the signing.
  • There is no "private key" in the Ethereum sense. What the UI calls "Plain Key" / private_key on export is literally the raw 32-byte master secret in base64 — not an secp256k1 key.

2 · How a wallet is born — the two doors

When you create a profile, the code branches at the very top: password door or passkey door. Both doors end at the same place (a 32-byte master secret) — they just get there differently.

Door A — Password profile

  you type a password
        │
        ▼
  the wallet IGNORES it for a second and rolls a fresh random number
        │                          Fr.random()  →  32-byte master secret
        ▼
  password is used only to LOCK that random secret for storage:
        SHA-256(password) ─► PBKDF2-SHA256 (600,000 rounds) ─► AES-GCM-256 key
        │
        ▼
  store on disk:  { guard: ,  secret:  }
Key point

The password does not generate the secret — it only wraps it. That means your password is not your backup: if you wipe the device, re-typing the password on a fresh install gives you nothing, because the random secret it was protecting is gone. (More on this in §5.)

Door B — Passkey profile

  you tap your passkey (Face-ID / fingerprint / security key)
        │
        ▼
  WebAuthn runs with the "PRF" extension — a feature that asks the
  authenticator for a stable secret pseudo-random output:
        eval input = SHA-256("nulo:profile:v1")          (domain separation)
        │
        ▼  authenticator returns 32 secret bytes  ("the PRF output")
        │
        ▼  HKDF-SHA256 stretches/labels it into the master secret:
        salt = SHA-256("nulo:kdf:v1" ‖ credentialId)
        info = "nulo:master:v1"
        │
        ▼
  32-byte master secret   (nothing is stored on disk except the credentialId)
The crucial difference (the "KEK question")

A passkey profile does not store a random secret and unlock it with the passkey. The passkey output is the seed — the master secret is derived from it every single time. Nothing on disk but the credentialId. This is elegant (no secret at rest) but has a sharp consequence: your passkey is your wallet. Lose the authenticator and there is no encrypted blob to fall back on.

ELI5

Password door: the wallet writes a secret on a card, locks the card in a box, and your password is the box's combination. Passkey door: there is no card and no box — your fingerprint is a machine that prints the exact same secret on demand. If the machine breaks, the secret can never be printed again.

3 · One secret → many accounts (the family tree)

You don't sign with the master secret directly. The wallet grows a tree from it, so one profile can hold many accounts across many chains:

           MASTER SECRET  (per profile — from Door A or Door B)
                  │
                  │   per-account secret =
                  │   poseidon2Hash( master , chainId , type , index )
                  ▼
           PER-ACCOUNT SECRET   (one per chain + account number)
                  │
        ┌─────────┴───────────────┐
        ▼                         ▼
  deriveSigningKey()         deriveKeys()
   = Schnorr key              = nullifier key + incoming-viewing
   (Grumpkin scalar)            + outgoing-viewing + tagging keys
        │                         │
        └───────────┬─────────────┘
                    ▼
       SchnorrAccountContract   (salt = 0)
                    ▼
            your account address (0x…)

So the hierarchy is HD-wallet-like (one root → unlimited children), but it does not use the Bitcoin/Ethereum BIP-32 standard. It uses Aztec's native poseidon2 hash as the "derivation path." The index auto-increments per (chain, account-type) so "add account" just bumps a counter.

Both doors agree on…Detail
Signing schemeAlways Schnorr over the Grumpkin curve. Literally sha512ToGrumpkinScalar([secret, IVSK_M]).
On-chain accountAlways the stock Aztec SchnorrAccountContract at salt = 0. The Noir contract verifies schnorr::verify_signature(...).
Passkey's roleNone on-chain. A passkey account and a password account are indistinguishable on Aztec — both are plain Schnorr accounts. The door only changed how the secret was obtained.
This answers your "use the Schnorr K for passkey accounts" question

Passkey accounts already use a Schnorr key — passkey → master → per-account secret → deriveSigningKey → Schnorr, exactly like password accounts. There is no separate "passkey signature" type today. So if "make it actually use Schnorr" meant "it currently signs with the passkey natively" — it doesn't; it's Schnorr already. If you meant something else (native on-chain passkey verification), that's a real but much bigger change — see §7.

Worth knowing

The profile-row encryption is not the whole at-rest story. The moment you have a live account, the derived private keys for it sit in IndexedDB in the clear (this is upstream Aztec PXE behaviour, not Nulo-specific). Disk-encryption of the OS is doing the heavy lifting there, not the wallet.

5 · Backup & recovery — the part that bites

This is the section that matters most for "should we change it." Here's the honest matrix:

CapabilityPassword profilePasskey profile
Seed phrase (24 words)✓ export & import✗ blocked
Raw secret key export✓✗ returns only the credentialId
Encrypted key export✓✗
Full Backup (JSON file)✓ contains the master key~ contains only the credentialId
Recover after device lossOnly if you exported one of the above beforehand.Only if the same passkey still exists (synced / second device).
Password / passkey alone recovers?No — secret is random, not password-derived.No file helps — you need the authenticator itself.

The 24-word seed phrase — yes it exists, but read the fine print

There's a hand-rolled BIP-39 codec in the codebase (the real 2048-word English list, 11-bit packing, SHA-256 checksum). A 32-byte secret renders to 24 words. But:

  • It is only reachable via Settings → Security → Export → Seed, password-gated, password profiles only.
  • It is never shown at sign-up (unlike MetaMask, which forces it on you day one).
  • It's just a rendering of the already-random secret — there's no BIP-32/HD seed-stretching. The words are the entropy, reversibly. (Standard wallets run the words through PBKDF2 to a 512-bit seed first; Nulo doesn't.)
The two recovery traps

Passkey users have no portable backup. Their "Full Backup" file stores the credentialId, not the secret — restoring it just re-runs WebAuthn against that credential. If the authenticator is gone (lost phone, non-synced security key, the known PRF-non-portability issue), the funds are gone. There is no seed phrase to write down.

Password users who never exported are equally stuck. The password protects a random secret stored only on that device. No export = no recovery, full stop.

Also note

A plain Full Backup writes the raw master key into the JSON by default — "Protect with Password" is a separate, optional step. Easy to footgun a plaintext master key onto disk / cloud.

6 · "Strict mode" today vs. what you want

Strict security mode is ON by default. But here's exactly what it does and doesn't do today:

Today's behaviour
What strict mode doesStops the wallet from caching the SHA-256(password) bearer in session storage, so the service worker can't silently re-unlock itself after it sleeps. You re-auth more often. (Passkey sessions already never silent-restore.)
What strict mode does not doIt does not require a passkey tap or password at signing time. Once unlocked, the master secret sits in service-worker memory and every transaction signs from it with no prompt, until manual lock / TTL timeout / worker death.
  TODAY:   unlock once ──► master secret held in memory ──► tx, tx, tx, tx … (no re-prompt)

  YOU WANT: ── tx ──► [tap passkey / enter password] ──► sign ──► drop secret ──► repeat
The good news

The seam to change this is small and well-located. Signing pulls the secret through one chokepoint — SessionManager.getSecret() via ProfileService.getProfileSecret(), consumed in the execution/account services. A "strict-signing" mode would replace that in-memory read at the execution boundary with a fresh ceremony (passkey assertion or password), use the secret to sign, then drop it. No on-chain or account-contract change required for the password/derived-Schnorr path.

7 · How a more standard wallet would do it

Here's the contrast and three concrete directions, from cheapest to most ambitious.

DimensionStandard (MetaMask-style)Nulo today
Root of the wallet12/24-word BIP-39 mnemonic, shown at sign-up, IS the seed.Random 32-byte secret (password) or passkey-derived. Mnemonic is an after-the-fact export, password-only.
Backup modelWrite down the words once → recover anywhere.Must opt into an export; passkey path has no portable backup.
Key derivationBIP-39 → 512-bit seed → BIP-32 HD tree.master → poseidon2(master, chain, type, index).
Signingsecp256k1 / per-tx confirm.Schnorr/Grumpkin; in-memory, no per-tx auth.

Direction A — Make the seed phrase the root, not an export (cheap, high value)

Flip the model: at sign-up, generate BIP-39 entropy, show the 24 words, and derive the master secret from them (optionally with a passphrase). This is nearly free because the import path already converts words → entropy → master — you'd essentially make "import" the way "create" works, and surface the words. Result: a real, portable, write-it-down backup that works on any device, matching what users expect. Keep passkey as an optional unlock convenience layered on top, not the sole root.

Direction B — Per-transaction unlock in strict mode (cheap, exactly your ask)

As described in §6: gate getSecret() at the execution boundary so that, in strict mode, each signature (or each signature above an amount, or after N minutes) requires a fresh passkey assertion / password entry. The secret is reconstructed just-in-time, used, and dropped. This also lets you finally zeroize aggressively instead of holding a long-lived Fr in memory.

Direction C — Native passkey accounts (powerful, expensive)

This is the "make the passkey actually the signer" idea. Two sub-options:

Derived-Schnorr (today)Native P-256 passkey account
How it signsPasskey PRF → rebuild secret → Schnorr key signs.The passkey signs the tx hash directly; a custom Noir account contract verifies the WebAuthn secp256r1 (P-256) signature on-chain.
Secret ever in memory?Yes (the master Fr).Never — the private key stays in the secure element.
Per-tx touch?Bolt-on (Direction B).Inherent — every tx needs a real assertion.
Cost—Write + audit a Noir account contract doing P-256 verification (not Aztec-native — in-circuit secp256r1 is heavy), new address scheme, migration.
The insight tying B and C together

Your two wishes — "per-transaction unlock" and "passkey actually signs" — are the same wish at different depths. Direction C gives you per-tx touch for free (the chain itself demands a fresh passkey signature every time), at the cost of building a P-256 account contract. Direction B gets you the per-tx feel today, cheaply, while staying on the stock Schnorr account. A sane path: ship B now; evaluate C as a separate, audited account-contract project if true secure-element-resident signing is a product goal.

8 · Sharp edges we found along the way

Surfaced by three parallel codex audits + a manual read of the crypto core. None are "drop everything," but they're the security-relevant footnotes for any redesign.

  • Account derivation omits profileId. poseidon2(master, chainId, type, index) has no profile binding, so the same master imported into two profiles yields identical addresses — and account storage is keyed by address. Worth fixing if you touch derivation.
  • Signing-key domain separator is an upstream TODO. rc.1 derives the Schnorr key with the IVSK_M separator; if Aztec changes that, signing keys drift. Pinned by key-vectors.test.ts, so a drift would at least fail loudly.
  • Derived keys sit unencrypted in IndexedDB (PXE keystore) — see §4.
  • The password "bearer" is a single SHA-256(password). Cheap to brute-force if session storage leaks; strict mode is what stops it being persisted. (At-rest master is still behind 600k-round PBKDF2, so this is a session-theft concern, not an at-rest one.)
  • PBKDF2, not Argon2id. 600k rounds is OWASP-compliant but GPU-friendly; Argon2id would be the modern choice. Also the AES-GCM salt is SHA-256(iv) rather than independent randomness (unique per-encryption, so not exploitable, but unconventional).
  • Plain Full Backup writes the raw master key by default — see §5.
  • The long-lived master Fr isn't zeroized on lock — only the reference is dropped (the zeroizer can't wipe Fr/CryptoKey internals). Direction B's just-in-time model would shrink this window.
