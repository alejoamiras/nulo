Composition / PXE-injection test rollout (+ limits doc)

We have a gap between fast-but-fake unit tests and slow-but-real network e2e tests. A recent spike proved a middle layer: run the real wallet service code in-process against dumb fakes — no Aztec sandbox, no proving, no browser — in about a second. This plan rolls that pattern out to the three highest-value services that currently have almost no fast tests (Fpc, Token, DappSession), extracts a shared seam so it isn't copy-pasted, adds the CI guard that keeps the test fakes out of the shipped extension, and — most importantly — writes a rulebook so nobody (human or AI) accidentally rebuilds the PXE inside a fake.

Why this tier was chosen

By the strict rubric this scores around mid: novelty is low (the spike already proved the pattern), blast radius is moderate (it touches three production service constructors + adds a CI step), and irreversibility/migration/external-coupling are low. You explicitly chose deep anyway — and it paid off. Deep runs three independent planners plus a fresh, un-anchored hostile auditor. That fresh auditor caught two real High-severity blind spots that the other reviewers (and the spike's own framing) had silently inherited — a single-audit mid would have shipped both.

The two catches a "mid" would have missed: (1) the bundle-hygiene "guard" we leaned on didn't actually exist in CI (only a manual local grep), and (2) putting the shared fake in the tests/ folder would have silently disabled the very type-check that's supposed to stop the fake from drifting. Both are now fixed in the plan.

Phases

Phase 1: Shared seam + the real CI guard

Create the tiny shared "port" (one method: getPXE) that Token and Fpc will accept as an injectable dependency, and one shared dumb fake that lives inside src/ so the compiler checks it. Wire the seam into Token and Fpc without changing how they behave in production. Add a CI step that builds the extension and fails if any test-fake marker shows up in the shipped code.

Proves itself by: lint + typecheck clean, three exact new tests green (the port conforms both ways; Token and Fpc still build the real client by default), the workflow lints clean, and the production build contains zero fake markers.

Phase 2: Fpc composition test (the easiest target, first)

Fpc is the cleanest case — it only ever does shallow contract lookups/registration, no simulation. Drive its real auto-discovery + registration logic (including the "don't register twice" dedup and the lock that prevents duplicates) against the shared fake.

Proves itself by: a green Fpc composition test asserting real stored state + events, plus lint/typecheck/build-grep.

Phase 3: Token composition test (carefully scoped)

Token has two halves: a shallow "resolve + register the contract" half (safe to fake) and a deep "simulate the token's name/symbol/decimals" half (which needs the real PXE — that stays in e2e). The test drives only the shallow half, deliberately.

Proves itself by: a green Token composition test on the shallow path (never touching simulation), plus lint/typecheck/build-grep.

Phase 4: DappSession harness (no PXE; last + droppable)

DappSession touches no PXE at all — it's about session storage and scoping. Different fakes (storage only). Test the real lifecycle: create, scope-by-network (a security guard against cross-network trust bleed), mutate, upgrade, expire, and cascade-delete when a profile is removed. If time runs out, this is the phase to drop.

Proves itself by: a green DappSession lifecycle test, plus lint/typecheck.

Phase 5: The rulebook + drift guard

Write COMPOSITION-TESTS.md — the normative "when to use this, when to stop, never rebuild the PXE" doc — and link it from CLAUDE.md so it's a rule, not a suggestion. Finalize the drift guard (the compile-time conformance from Phase 1, plus one optional real-network seam smoke-test).

Proves itself by: the full pre-PR gate (audit:vue) green, smoke e2e green, the optional seam canary green in the network lane, and a final build-grep at zero.

Human context

The PXE is the wallet's private-execution engine (it resolves contracts, simulates, and proves transactions). The danger with faking it is the "second wallet" trap: a fake that grows until it re-implements Aztec's logic — at which point the test only proves the fake agrees with itself. The whole design here is built to make that trap impossible: the shared port is deliberately too narrow to even express simulation/proving, so a fake literally can't reach those methods through it. The rulebook then writes that discipline down with countable limits (e.g. "a fake may model at most 4 PXE methods; if you need a 5th, you're in the wrong test layer").
