Externalizing the shared component library

Round 1 — the ambitious version, run supervised. Approved, ready to implement.

We have three Vue frontends (the wallet extension, the faucet, and a vanilla-JS playground that's out of scope). A shared UI package, @nulo/design, already exists and the faucet uses it — but the extension uses none of it and keeps its own copies, including a drifted copy of the design tokens. This round makes @nulo/design the one true home for the tokens, the wallet's whole base stylesheet + fonts, and 9 basic building blocks — so both apps share one source.

Status: approved. Three independent plans + two hostile reviews + a final pass + a targeted re-check of the risky part. The reviews caught real defects each time; the plan was rewritten to fix them. The end-goal is a hard rule: the extension must look exactly the same as it does today.

The two big decisions you made

1. Go ambitious. Instead of leaving the deeper unification for later, this round moves the wallet's entire base stylesheet + fonts + theme system into the shared package, so there's a single source for everything — not just token names.

2. Run it supervised. The risky part (rewriting the global stylesheet) has no cheap automated way to prove "still looks identical" in this repo — the test tools here can't read resolved colors, and screenshot infra would be overkill. So instead of building that, you are the check: at the takeover step you open the wallet and confirm it looks right. That removes the need for any new visual-testing machinery.

The key safety idea: relocate, don't drop. The takeover does NOT delete the extension's global styles — the whole app still depends on them. It moves them verbatim into the shared package (tokens regenerated from one source; everything else copied exactly), and the extension imports them back. Nothing disappears, so the icons/scrollbars/ utilities/animations all keep working. Your visual check confirms the move was faithful.

What we're moving (and what we're NOT)

Moving this round: the tokens + the full base stylesheet + fonts, plus Flex, Icon, Text, MaterialIcon and Badge, BrutalistTitle, Checkbox, SectionLabel, Toggle (9 components).

Deferred to round 2: Button/SubPageHeader (router), ToastManager (app state), Spinner+Banner+ LoadingState (clashing Spinner versions), Tooltip/Popover/ Input (need page-level mount points the faucet lacks), and the faucet's button cleanup.

Phases

Build a single source for the tokens, generate the typed list from it, add a test that fails if anyone hand-edits a copy, and point CI at the shared package. No styles or components change yet.

Proves itself by: regen byte-match + both apps build; CI watches the package.

Then it stops and asks you to open the extension (Chrome + Firefox, light + dark, with/without the bottom nav) and the faucet, and confirm both look identical. It will not proceed until you say so.

Phase 3 — The 4 core building blocks (automated)

Move Flex, Icon, Text, MaterialIcon; rewrite them to stand alone with explicit imports; fix one latent Icon bug; a test actually renders + clicks through each (catches the "forgot an import" crash the type-checker misses).

Proves itself by: render/branch tests + style snapshots + build + smoke test.

Phase 4 — Five simple UI bits (automated)

Move Badge, BrutalistTitle, Checkbox, SectionLabel, Toggle the same way.

Proves itself by: render/branch tests + build (both apps) + smoke test.

Phase 5 — Tidy up, docs, full test — final glance

Remove scaffolding, write docs + the round-2 to-do list, run the full 25-minute network test, and a final visual confirmation from you.

Proves itself by: full audit + smoke + network e2e + your final look.

Why no visual-regression harness

A harness is only needed for one combination: rewriting the global stylesheet unattended (no human to eyeball it). You're supervising the takeover, so your eyes are the gate — exactly how a CSS refactor is normally verified. The automated checks still cover everything machine-checkable (token drift, faithful-port text match, both-browser builds, font loading, crashes, component output). The harness would be redundant.
