v3 follow-ups, in plain language

Two small clean-up jobs left over from the "parallel popups" work. Full detail in plan.md.

When we shipped parallel dApp popups, a careful review flagged two things we chose to do later rather than rush. This is what they are and why they matter — no jargon.

P1  A limit on how many transactions can pile up

What's the problem?

Think of one "lane" where your transactions are processed one at a time. Right now a dApp could shove an unlimited number of transactions into that lane at once. Nothing breaks on the blockchain — they still run one by one — but the pile can grow without bound, and the ones past a certain point become invisible and impossible to cancel. A buggy or hostile dApp could abuse that.

What we're doing

Adding a limit. Once a lane has too many transactions waiting, the next one is politely refused with a clear error the dApp can read ("too many pending"), instead of silently swelling the pile.

The twist the review caught

That one lane is shared by every dApp connected to the same wallet + network. So a dumb "limit the whole lane" rule would backfire: a bad dApp could fill the lane and your good dApp would start getting refused — even though it did nothing wrong. So instead we limit each dApp's own share of the lane (plus a generous overall ceiling for memory). One misbehaving app can't starve the others.

One more subtlety: we tie that per-dApp limit to the dApp's web address, not to its connection. Otherwise a sneaky site could just reconnect over and over to get a fresh allowance each time.

P2  Properly testing the "no-account" transaction path

What's the problem?

There's a special transaction path (called "NO_FROM") used when there isn't a normal account wrapper. It has no built-in safety nonce, so it relies entirely on the one-at-a-time lane to stay correct. That makes it the riskiest path — and our automated tests didn't actually cover two of them running at once.

The thing the review uncovered

Our existing test for this path looked like it "sometimes passed" — but it turns out it could basically never truly succeed: this path only accepts one private action, and the test was handing it a public one, which it refuses. So before we can test "two of these succeed together," we first have to figure out the right kind of action to use and set up the funding so a single one reliably works.

How we'll de-risk it

We investigate first (a short, time-boxed spike): get one such transaction to succeed reliably, prove it three times in a row, and only then build the "two-at-once, both succeed" test. If that investigation turns out to be a swamp, we stop and fall back to a cheaper, lighter test rather than pour in endless effort.

The one decision we need a human for

How strict should the per-dApp limit be vs. how much code do we want?

The simplest possible limit (one number for the whole lane) is a few lines — but it's the version that lets a bad dApp get a good dApp refused. The recommended version (per-dApp share + overall ceiling) avoids that but is a bit more plumbing. The review strongly favors the recommended one; we just want you to okay the extra complexity before we build it.

Why these are two separate changes

P1 (the limit) is ready to build and low-risk. P2 (the test) has a real "will this even work?" investigation in it. Bundling them would let the uncertain one hold up the ready one — so they ship as two separate pieces.
