# M4.8 — codex (xhigh) audit

Date: 2026-04-26

**Codex audit BLOCKING**: M4.8 depends on more than M4.2. Passkey pending requests are memory-only at `packages/extension/src/wallet/services/passkey/service.ts:26` (`private pending: Map<string, PendingPasskey> = new Map()`). On SW restart, every in-flight passkey request is dropped. The pre-existing audit (`architecture/codex-notes/08-passkey-flow.md:198`) already flagged this.
**Codex audit BLOCKING**: M4.2 must not be written as a normal implementation plan with default `(a)`. The current `SECURITY.md:73` security contract explicitly requires the replacement to be "a session token that cannot itself decrypt the secret." If we default to design `(a)` (device-local session key wrap) **and** the wrap-key is co-located with the wrapped secret in `chrome.storage.session`, design `(a)` is just "passhash with different packaging" — the threat model doesn't shift.
**Plan agent audit BLOCKING**: same conclusion via different reasoning — wrap-key extraction makes design `(a)` no better than today.
**Codex audit BLOCKING**: do NOT introduce a per-record `version` field. `EntityStorage` already has **collection-level** `getVersion()` / `setVersion()` (`packages/wallet-core/src/storage/entity_storage.ts:33-40`). M4.7 should:
**Plan agent audit BLOCKING**: write fence — per-collection mutex during migration. Re-use existing `Lock` primitive at `packages/wallet-core/src/utils/lock.ts`.
**BLOCKING** `implementations-plan/M4/8/plan.md:60-69,118-137` understates Design Y by assuming a recoverable in-flight request when the current primitives cannot do that. `PendingPasskey` persists only `handleId` (`packages/extension/src/wallet/services/passkey/service.ts:18-21`), but `WindowManager` handle IDs are random hex tokens, not `windowId`s (`packages/extension/src/wallet/services/window-manager/window-manager.ts:10-12,28-29,51-56,93`). `parseInt(entry.handleId)` is therefore wrong, and even a real `windowId` would not restore the lost awaiting promise because the old `handles` map and resolver closures die with the SW (`window-manager.ts:43,60-74`). Change the memo to either:
**BLOCKING** `implementations-plan/M4/8/plan.md:68,75,118` says Design Y is “M4.7 territory,” but M4.7 as written only boots migrations against `browserApi.storage.local` (`implementations-plan/M4/7/plan.md:136`) and its inventory even mislists `nulo:core:session` under `chrome.storage.local` before correcting it under `chrome.storage.session` (`implementations-plan/M4/7/plan.md:32-34,46-51`). So session-storage migration is not actually covered. Change the memo to either say “no migrator is needed for a brand-new session-only root,” or make M4.7 explicitly add a `storage.session` runner/registry before treating it as a dependency.
**SHOULD-FIX** `implementations-plan/M4/8/plan.md:80-91` calls the `PasskeyPendingStore` work “type-only,” but then immediately proposes rewiring `PasskeyService` onto an async store abstraction. Current `pending` access is a simple in-memory `Map` on the hot path (`packages/extension/src/wallet/services/passkey/service.ts:26,43-66,83-87`). For recommended Design X, that abstraction is speculative churn with no payoff. Change this to true prework only: inventory call sites and define the persisted envelope shape; defer the store interface/injection until Design Y is actually approved.
**SHOULD-FIX** `implementations-plan/M4/8/plan.md:99-109` points at the wrong execution touchpoints. `ProfileService.restorePasskeySession` does not exist. The live restart path is `SessionManager.restore()` leaving passkey sessions locked (`packages/extension/src/wallet/services/profile/session-manager.ts:215-235`), `auth.vue` detecting a passkey profile and offering passkey continuation (`packages/extension/src/popup/pages/auth.vue:37-61,163-169`), then `unlockPasskeyProfile()` reopening WebAuthn (`packages/extension/src/wallet/services/profile/service.ts:215-257`). Rewrite Step 1 around those concrete files. Also, M4.2 is a dependency for the *symmetry claim*, not for this Design X cleanup itself; say that explicitly.
**SHOULD-FIX** `implementations-plan/M4/8/plan.md:111-114` misses the key restart scenario. “Pending map empty post-SW-restart” is tautological; the user-visible failure is the stale passkey popup calling `getPendingRequest(requestId)` and getting `"Invalid request id"` (`packages/extension/src/popup/windows/passkey/index.vue:123-133`, `packages/extension/src/wallet/services/passkey/service.ts:43-45`). Add a test for stale `requestId` popup behavior after restart, and one for the auth-screen re-unlock path after `SessionManager.restore()` short-circuits. Also, don’t add a new M2.6 vector here: V3 already pins passkey PRF→master-secret derivation (`packages/extension/src/wallet/crypto/key-vectors.test.ts:132-148`).
