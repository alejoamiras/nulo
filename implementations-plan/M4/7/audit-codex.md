# M4.7 — codex (xhigh) audit

Date: 2026-04-26

- `BLOCKING` — The version-key design is internally inconsistent and will clobber `ValueStorage` roots. `implementations-plan/M4/7/plan.md:65` says M4.7 uses an EntityStorage-backed `${root}@__version__` sidecar, but the actual `EntityStorage.getVersion()/setVersion()` read and write the bare root key, not a suffixed sidecar (`packages/wallet-core/src/storage/entity_storage.ts:33-39`). That is only safe for EntityStorage rows stored under `${root}@id`; it would overwrite `nulo:core:session` and `nulo:config`, which already live at the bare root (`packages/wallet-core/src/storage/value-storage.ts:18-27`, `packages/extension/src/wallet/services/profile/session-manager.ts:10-14,112-113`, `packages/extension/src/wallet/config/store.ts:10`). Change M4.7-a to use a backend-agnostic version-metadata adapter: reuse bare-root versioning only for EntityStorage-backed roots, and use an explicit collection-level sidecar key for ValueStorage/IndexedDB. No per-record version field needed.
- `BLOCKING` — The runner API cannot migrate the roots the plan inventories. `implementations-plan/M4/7/plan.md:124-136` defines `migrateAll(area)` and wires it to `browserApi.storage.local`, but the same plan includes `chrome.storage.session` roots (`plan.md:46-52`) and IndexedDB roots (`plan.md:53-60`). With the current interface, `nulo:core:session`, `nulo:journal`, and all IndexedDB migrations are out of scope. Also, `plan.md:136` moves startup migration to `wallet/index.ts`, but current architecture intentionally keeps migration inside `wallet/runtime.ts` (`packages/extension/src/wallet/index.ts:9-10`, `packages/extension/src/wallet/runtime.ts:96-99`). Change M4.7-a so each registry entry carries its backend (`local` / `session` / `indexeddb`) and keep startup wiring in `runtime.ts`.
- `BLOCKING` — The write fence is not actually specified as a shared mutex. `implementations-plan/M4/7/plan.md:148-159` gives each `MigratingStore` its own private `new Lock("MigratingStore")`, while `plan.md:120-123,162-165` separately says `MigrationRunner` acquires “the” per-root lock. Those are different objects unless M4.7-a adds a shared lock registry keyed by root. The escape hatch at `plan.md:183` (“or just call `migrationRunner.migrate(root, area)` at service init”) also bypasses the fence entirely. Change the plan to introduce a shared per-root lock registry injected into both runner and store factory, or simplify the design to boot-only migrations and delete lazy migrate-on-read.
- `SHOULD-FIX` — The storage inventory is not actually “verified against `55f88a4`.” `implementations-plan/M4/7/plan.md:33,50` lists `nulo:core:session` in both local and session storage, but the code stores it only in `chrome.storage.session` (`packages/extension/src/wallet/services/profile/session-manager.ts:10-14,112-113`). The table also omits legacy `nulo:core:tx-cursors`, even though current migration code still wipes it (`packages/extension/src/wallet/storage/migrate.ts:13`) and M4.7 later proposes a drop-on-migrate for it (`plan.md:193-194,264`). Update the inventory to distinguish live roots from legacy-on-disk roots, and make `tx-cursors` an explicit migrator with an explicit drop-on-migrate test.
- `SHOULD-FIX` — `nulo:core:session` should not be called a required active M4.7 migration. `implementations-plan/M4/7/plan.md:187-189,216-217` says M4.7-c must add `lockedAt`, but M4.5 already made `lockedAt` optional and forward-compatible (`implementations-plan/M4/5/plan.md:24,151,157`). On the current plan sequence, session is baseline-only unless M4.5 changes its storage contract. Replace that item with the real active migration surface: legacy `tx-cursors` cleanup and the M4.10 PXE placeholder.
- `SHOULD-FIX` — Cross-root ordering is a known requirement already, so deferring it is too loose. `implementations-plan/M4/7/plan.md:249,262` says add `after: []` only if M4.7-c uncovers a case, but M4.10 already depends on reading `nulo:core:networks` before renaming `pxe/${profileId}/${chainId}` DBs (`implementations-plan/M4/10/plan.md:129-156,229,239`). Either add ordering/toposort support in M4.7-a now, or explicitly state that M4.10 owns that interface change. Also: drop `STORAGE_VERSION_KEY` in M4.7-d rather than “decide later”; the only current consumer is `runStorageMigration` (`packages/extension/src/wallet/storage/migrate.ts:10,28-30,50`).
