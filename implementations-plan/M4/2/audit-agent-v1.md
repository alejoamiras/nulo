# M4.2 + M4.8 — Plan-agent audit

Date: 2026-04-26
Plan: implementations-plan/M4/2/plan-v1.md

## Verdict

3 BLOCKING + 5 SHOULD-FIX + 4 NIT

## Findings

- **BLOCKING — Integration test breaks at startup, not at assertion time.** `service.integration.test.ts:88-94` registers only `FakePasskeyService` + `ProfileService` in `services`. The plan's Change 2 adds `services.get(ConfigService.name)` to `ProfileService.onInit()`. `ServiceCollection.get` THROWS when the service isn't registered (`packages/wallet-core/src/base/index.ts:47-51`). Every existing integration test will fail in `services.start()` before any assertion runs — the proposed `beforeEach({ strictSecurityMode: false })` mitigation is moot because the service never finishes init. The plan must either (a) register a fake/stub `ConfigService` in `makeService(...)`, or (b) avoid the registry roundtrip entirely (see SHOULD-FIX below).

- **BLOCKING — Two passhash-bearer write sites are missed.** Plan claims only `createProfile` (line 104) and `unlockProfile` (line 174) write `passhash` to Session. Reading `service.ts` shows two more sites that are NOT gated:
  - `service.ts:360` — `changeProfilePassword` calls `sessionManager.open(profile, secret, resealed.passhash)` whenever the user changes their password while a session is active. The plan explicitly lists `changeProfilePassword` as out-of-scope, but it WRITES the bearer.
  - `service.ts:628` — `importPasswordProfile` (private helper invoked by `importEncrypted` 484, `importPlain` 496, `importMnemonic` 504) calls `sessionManager.open(profile, secret, passhash)` on every password-profile import. Plan does not mention import paths at all.

  After this PR, a strict-mode user who imports a wallet (very common: dev workflow, recovery) silently gets the legacy bearer behavior. Same for password change. Default-ON loses its meaning. Both sites need the same `strict ? undefined : passhash` gate.

- **BLOCKING — Plan references a `Switch` component that does not exist; the binary toggle is `Toggle.vue`.** Change 5 prescribes `<Switch v-model="strictSecurityMode" @change="updateStrictSecurityMode" />`. Repo has `packages/extension/src/components/ui/Toggle.vue` (used by privacy/index.vue at lines 217-220, 238-241), no `Switch` component anywhere. The Toggle API is also different — it emits `update:modelValue`, not `change`, and takes a click-toggle handler. Settings UI snippet won't compile.

- **SHOULD-FIX — Use the constructor-injected `IConfig`, not a registry roundtrip.** ProfileService's constructor already takes `config: IConfig` (line 42). Today it only forwards to SessionManager. SessionManager itself subscribes to `config.onUpdate` directly without going through the messaging service (`session-manager.ts:122`). Plan's pattern (grab `ConfigService` from registry, await `getValue("strictSecurityMode")` per unlock) is heavier than necessary, breaks the integration tests, and inverts the layering — `ConfigService` is a messaging facade, the underlying `IConfig` is the read primitive. Cleaner: store the IConfig parameter (`private readonly config: IConfig`), call `config.get("strictSecurityMode")` synchronously inside unlock/createProfile (no `await`, no registry lookup), and add `config.onUpdate.add(this.onConfigUpdated)` in the constructor. Avoids BLOCKING #1 entirely.

- **SHOULD-FIX — `cacheStore.confirm.confirm_color = "warning"` is not a valid Button type.** Repo only uses `"red"` (destructive) or `"primary"` (per ConfirmPopup.vue:23 `isDestructive` predicate keyed on `"red"`, and grep over the 8 callers shows only those two values). Plan's `"warning"` will fall through Button's prop type without styling — the Disable button will render with default styling, no warning affordance. Use `"red"` to match the destructive-action convention (this is reducing security).

- **SHOULD-FIX — Toggle-OFF "no backfill" semantic is asymmetric with the only other settings precedent in the codebase.** `pages/settings/privacy/index.vue:84-115` shows that `stealthMode` toggle, when OFF, IMMEDIATELY mutates child flags — there is no "next session only" caveat. The plan's behavior matrix row "After user toggles OFF" says session storage stays passhash-free until next unlock, which is a hidden state. Combined with the disable-warning "A recovery key gets cached in browser session storage" — the user reads "will be cached" and reasonably expects "cached now," but it's actually "cached on next unlock." Either change subcopy to make the timing explicit ("…will be cached on your next unlock"), or trigger an immediate `lockActiveProfile()` on toggle-OFF so the next interaction forces re-unlock and writes the bearer (matching stealthMode's "effect happens now" mental model).

- **SHOULD-FIX — Test plan #5 ("fresh SessionManager / SW-restart simulation") doesn't compose with `service.integration.test.ts`'s fixture shape.** The integration test's `makeService()` always allocates a fresh `FakeBrowserApi` and `passkeys`/`service` pair, then calls `services.start()` once. To simulate SW restart while preserving FakeBrowser storage, the test must (a) keep the FakeBrowserApi instance, (b) construct a SECOND ServiceCollection + ProfileService against the same api, and (c) drive that fresh instance's start. The plan says "Construct a fresh SessionManager (same fake browser), call `restore()`" — but ProfileService is the test surface, not SessionManager. Add a `makeService2(api: FakeBrowserApi)` helper that re-uses the api without resetting it; otherwise the new tests can't be written with the existing fixture pattern. (This pattern already works in `session-manager.test.ts:540-569` for the `lockedAt < now` test, but only because that test drives SessionManager directly, which the integration tests don't.)

- **SHOULD-FIX — SECURITY.md cross-references not addressed.** Beyond the threat-model row at line 75-77 the plan calls out, SECURITY.md lines 81-88 (M4.2/M4.3/M4.5 future-work entries) and lines 89-92 (the "until M4.2 lands…" guard clause referencing `restorePasswordSession` and `EncryptionKey`) are stale. Lines 89-92 specifically reference `src/wallet/services/profile/service.ts:531-570` which doesn't even point to the real code path post-M2.1-e. Replace the entire 80-92 block, not just the table row.

- **SHOULD-FIX — Legacy `passhash`-bearing sessions are not addressed at all.** First boot under strict-default-ON: existing user has a Session in storage with `passhash` from a previous lenient session. `restore()` (`session-manager.ts:265`) does NOT check strict mode — if passhash is present and unseals, it restores. So the very first SW restart after upgrade silently re-unlocks (and the in-memory secret outlives the next manual lock). Strict mode only takes effect on the NEXT unlock. Plan's Migration section says "no user migration needed," but this is itself a behavioral gap worth noting in the matrix (or, fix by also gating restore: `if (strict && session.passhash) → silentClose`). Trivially easy to add — and the trade-off should be a deliberate decision, not an oversight.

- **NIT — Plan describes a generic registry pattern but ProfileService's existing layering is `services: ServiceCollection -> services.get(PasskeyService.name)` only because the PasskeyService PRF call inherently needs the messaging boundary (UI port). ConfigService doesn't have that need; the IConfig is already direct-call.** Recommend stating the rationale for the chosen pattern explicitly so the next reviewer doesn't relitigate.

- **NIT — Plan's E2E smoke "verify session storage does NOT contain `passhash`" assumes Chrome DevTools shows the `nulo:core:session` ValueStorage key in plain JSON.** ValueStorage stringifies the value (`session-manager.test.ts:89` uses `JSON.parse(raw[SESSION_STORAGE_ROOT] as string)`). DevTools renders that as a quoted string blob. The test step should specify `JSON.parse` of the value, or use `chrome.storage.session.get('nulo:core:session')` from the SW console.

- **NIT — Sentence "Use the existing `Switch` component (or whatever binary toggle pattern the codebase already uses for `stealthMode`-like flags — find one and match it)" leaves the implementer to figure out the Toggle name during execution.** Combined with BLOCKING #3, this is two missing-component bugs; just say "Use the existing `Toggle` component at `src/components/ui/Toggle.vue` — same shape as the stealth toggle in `pages/settings/privacy/index.vue:217`" so the implementer is anchored.

- **NIT — Test #3 ("Toggle ON clears existing bearer") should add a deterministic synchronization point.** "Wait for `onUpdate` event to propagate" is unspecified. The pattern in `session-manager.test.ts:512-514` (`await Promise.resolve()` × 3 to flush microtasks) is already established. Use the same idiom for consistency, or `vi.waitFor` against the persisted-passhash check.

## Architectural / completeness notes

- The default-ON re-decision is a clean architectural fit: SessionManager already had the `passhash?` optionality from the passkey path (`session-manager.ts:185`), `restore()` already short-circuits on `!session.passhash` (line 287), and the AES-GCM/Fr/zeroize chain doesn't depend on strict mode at all. M2.6 vectors will pass — this claim in "Critical invariants preserved" #1 is correct.
- Layering: ProfileService → ConfigService is technically fine (both in extension package), but if you take the SHOULD-FIX path (use injected IConfig directly), there's no ConfigService dependency to worry about and no boundary check to revisit. `IConfig` is exported from `@/wallet/config` (already imported by `service.ts:3`); the `ConfigProp` type is also exported there (`config/index.ts:2`). No new exports needed.
- M4.6 zeroize: traced all 11 zeroize sites in `service.ts`. Strict-mode toggle does not move the buffer-ownership boundary anywhere; the `zeroize(passhash)` calls fire regardless of whether passhash was used in `sessionManager.open` or not. Plan's "M4.6 zeroize unchanged" claim holds.
- M4.5 alarms: Strict mode doesn't touch `chrome.alarms` plumbing. The `clearPasshash` change only modifies the in-flight Session's passhash field; lockedAt + alarm scheduling are untouched. Plan's "M4.5 unchanged" claim holds.
- E2E impact: Reviewed `tests/e2e/wallet-lock.test.ts`, `auth-flows.test.ts`, `sw-resilience.test.ts`. All explicitly call `lockWallet(page)` before relying on /popup/auth — none depend on silent-restore. The `registeredExtension` fixture (per-file SW lifetime) keeps the in-memory secret alive across popup re-opens within the same file. No e2e regression risk; plan's "should remain green" claim holds.
- Scope creep risk: The two missed write sites (BLOCKING #2) imply the plan's "out of scope" list (`changeProfilePassword`, exports, etc.) is over-broad. `changeProfilePassword` IS within the scope of "passhash never persisted in strict mode." Imports likewise. The plan should reframe the scope by the principle ("any path that calls `sessionManager.open` with a passhash arg gets gated") and let the inventory follow from a grep.
