# M4.2 + M4.8 — codex (xhigh) audit

Date: 2026-04-26  
Plan: `implementations-plan/M4/2/plan-v1.md`

## Verdict

4 BLOCKING + 5 SHOULD-FIX + 1 NIT. No layer-boundary violation found, and “toggle OFF doesn’t backfill bearer” is the right semantic.

## Findings

- **BLOCKING** — The plan gates only `createProfile` and `unlockProfile` ([plan-v1.md:90](<(project root)/implementations-plan/M4/2/plan-v1.md:90>)), but password sessions are also reopened from `changeProfilePassword` ([profile/service.ts:360](<(project root)/packages/extension/src/wallet/services/profile/service.ts:360>)) and from `importPasswordProfile`, reached by `importEncrypted` / `importPlain` / `importMnemonic` ([profile/service.ts:456](<(project root)/packages/extension/src/wallet/services/profile/service.ts:456>), [profile/service.ts:487](<(project root)/packages/extension/src/wallet/services/profile/service.ts:487>), [profile/service.ts:499](<(project root)/packages/extension/src/wallet/services/profile/service.ts:499>), [profile/service.ts:628](<(project root)/packages/extension/src/wallet/services/profile/service.ts:628>)). Under strict ON, those paths would still persist a bearer. `confirmProfileOperation` and `exportPlain` / `exportMnemonic` / `exportEncrypted` do not call `sessionManager.open()` ([profile/service.ts:384](<(project root)/packages/extension/src/wallet/services/profile/service.ts:384>), [profile/service.ts:507](<(project root)/packages/extension/src/wallet/services/profile/service.ts:507>), [profile/service.ts:519](<(project root)/packages/extension/src/wallet/services/profile/service.ts:519>), [profile/service.ts:570](<(project root)/packages/extension/src/wallet/services/profile/service.ts:570>)), so they are not the leak.

- **BLOCKING** — The proposed `clearPasshash()` is storage-only ([plan-v1.md:126](<(project root)/implementations-plan/M4/2/plan-v1.md:126>)), but `SessionManager` is explicitly lock-agnostic ([session-manager.ts:40](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:40>)) and later persists the in-memory `activeSession.session` object on `refresh()` and TTL updates ([session-manager.ts:231](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:231>), [session-manager.ts:399](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:399>)). Popup open / route changes already call `refreshSession()` routinely ([Popup.vue:22](<(project root)/packages/extension/src/components/Popup/Popup.vue:22>), [popup/app.vue:263](<(project root)/packages/extension/src/popup/app.vue:263>)), and dapp execution does too ([dapp-interaction/service.ts:122](<(project root)/packages/extension/src/wallet/services/dapp-interaction/service.ts:122>), [dapp-interaction/service.ts:264](<(project root)/packages/extension/src/wallet/services/dapp-interaction/service.ts:264>)). If `activeSession.session.passhash` is not cleared together with storage, strict ON can be silently undone on the next refresh.

- **BLOCKING** — The race analysis is not benign. `unlockProfile` only serializes phase 3 under the facade lock ([profile/service.ts:157](<(project root)/packages/extension/src/wallet/services/profile/service.ts:157>)), while the proposed `onConfigUpdated` cleanup runs outside that lock ([plan-v1.md:149](<(project root)/implementations-plan/M4/2/plan-v1.md:149>)), and `SessionManager.open()` blindly persists any supplied `passhash` ([session-manager.ts:185](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:185>)). Interleaving: unlock reads `strict=false`, user flips strict ON, `clearPasshash()` sees no persisted session yet and returns, then the in-flight `open()` writes a bearer. That leaves strict ON violated until later cleanup; it is not just a “brief inconsistency” ([plan-v1.md:366](<(project root)/implementations-plan/M4/2/plan-v1.md:366>)).

- **BLOCKING** — `restore()` remains config-blind ([session-manager.ts:265](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:265>)). Any stale session record that still carries `passhash` will silently restore if it is readable, which contradicts the plan’s default-ON behavior matrix and migration note ([plan-v1.md:17](<(project root)/implementations-plan/M4/2/plan-v1.md:17>), [plan-v1.md:267](<(project root)/implementations-plan/M4/2/plan-v1.md:267>), [plan-v1.md:360](<(project root)/implementations-plan/M4/2/plan-v1.md:360>)). Relying on `clearPasshash()` alone is not enough for upgrade/dev-wallet cases or for the race above.

- **SHOULD-FIX** — `ProfileService` already receives reactive `IConfig` in its constructor ([profile/service.ts:42](<(project root)/packages/extension/src/wallet/services/profile/service.ts:42>), [config/index.ts:7](<(project root)/packages/extension/src/wallet/config/index.ts:7>)). Injecting `ConfigService` through the registry ([plan-v1.md:74](<(project root)/implementations-plan/M4/2/plan-v1.md:74>)) adds an unnecessary service-to-service dependency, makes the init-order discussion noisier than necessary, and complicates tests for no gain.

- **SHOULD-FIX** — The existing-test preservation strategy is incomplete. Current integration setup does not register `ConfigService`, and the local `fakeConfig()` has no `set()` API ([service.integration.test.ts:29](<(project root)/packages/extension/src/wallet/services/profile/service.integration.test.ts:29>), [service.integration.test.ts:77](<(project root)/packages/extension/src/wallet/services/profile/service.integration.test.ts:77>)). The plan’s `beforeEach` sketch ([plan-v1.md:233](<(project root)/implementations-plan/M4/2/plan-v1.md:233>)) needs extra harness work before it can even run.

- **SHOULD-FIX** — The planned coverage misses the highest-risk paths. There is no explicit test for toggle-ON during an in-flight password unlock ([plan-v1.md:244](<(project root)/implementations-plan/M4/2/plan-v1.md:244>)), and no strict-mode coverage for `changeProfilePassword` or the import flows that also reopen password sessions ([profile/service.ts:326](<(project root)/packages/extension/src/wallet/services/profile/service.ts:326>), [profile/service.ts:456](<(project root)/packages/extension/src/wallet/services/profile/service.ts:456>), [profile/service.ts:614](<(project root)/packages/extension/src/wallet/services/profile/service.ts:614>)). I would not spend test budget on “toggle during lock-screen” from the supported UI, because the Security page is auth-gated ([security/index.vue:1](<(project root)/packages/extension/src/popup/pages/settings/security/index.vue:1>)).

- **SHOULD-FIX** — The proposed `clearPasshash` tests are too shallow. They only assert field deletion ([plan-v1.md:286](<(project root)/implementations-plan/M4/2/plan-v1.md:286>)), but they miss the important `refresh()` / TTL / `restore()` interactions that can resurrect or bypass the bearer ([session-manager.ts:231](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:231>), [session-manager.ts:265](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:265>), [session-manager.ts:399](<(project root)/packages/extension/src/wallet/services/profile/session-manager.ts:399>)).

- **SHOULD-FIX** — The `SECURITY.md` edit plan is not complete enough. It updates rows and adds a new section ([plan-v1.md:215](<(project root)/implementations-plan/M4/2/plan-v1.md:215>)), but the current lead-in still says the password flow persists `passhash` as the “current design” ([SECURITY.md:51](<(project root)/SECURITY.md:51>)). That section needs to be rewritten into strict-ON and strict-OFF variants, not partially overlaid. The M4.8 anchor itself is present in the proposed heading.

If implemented literally, canceling the confirm can leave the visual toggle OFF while config remains ON.

Also, because all services are registered before `services.start()` and startup is phase-based ([wallet-core/base/index.ts:39](<(project root)/packages/wallet-core/src/base/index.ts:39>)), the real distinction here is “registered vs initialized”, not add order alone.
