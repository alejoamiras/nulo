# M4.5 — codex (xhigh) audit

Date: 2026-04-26

- BLOCKING: The alarm listener closes on name match only, so a queued stale delivery from an old alarm can lock a freshly refreshed or re-opened session. The plan ignores `scheduledTime` even though the port exposes it ([plan.md:89]((project root)/implementations-plan/M4/5/plan.md:89), [alarms-port.ts:22]((project root)/packages/wallet-core/src/ports/alarms-port.ts:22)). Change the plan to gate `close()` on `alarm.scheduledTime === activeSession.session.lockedAt` and ignore mismatches. Add a test that refreshes or re-opens, then delivers the old alarm event and asserts the new session stays unlocked; current coverage only checks registry replacement, not stale delivery ([plan.md:167]((project root)/implementations-plan/M4/5/plan.md:167)).
- BLOCKING: The config-change section needs a real rewrite, not just an execution-time note. `IConfig.onUpdate` is sync fire-and-forget: `EventHandler.add` takes `(...)->void`, `invoke` does not await, and `ConfigStore.set()` keeps going immediately ([event-handler.ts:9]((project root)/packages/wallet-core/src/utils/event-handler.ts:9), [store.ts:28]((project root)/packages/extension/src/wallet/config/store.ts:28)). On top of that, the proposed logic reschedules to `since + newTtl` even when that deadline is already in the past, leaving a live secret until Chrome eventually dispatches the alarm ([plan.md:127]((project root)/implementations-plan/M4/5/plan.md:127)). Change the plan to: keep `onConfigUpdated` sync, update `this.sessionTtl` synchronously, then `void` an internal async helper with its own error logging; inside that helper, if `since + newTtl <= Date.now()` call `close()` immediately, otherwise reschedule/persist. Add a test for “shorten TTL below elapsed age locks immediately”; current tests only cover future reschedules ([session-manager.test.ts:176]((project root)/packages/extension/src/wallet/services/profile/session-manager.test.ts:176), [plan.md:171]((project root)/implementations-plan/M4/5/plan.md:171)).
- SHOULD-FIX: The startup-fence explanation is inaccurate. Services register RPC connect listeners in their constructors, before `services.start()` runs, so `ProfileService.init()` is not “awaited before the service is registered for RPC dispatch” ([background/service.ts:22]((project root)/packages/extension-messaging/src/background/service.ts:22), [runtime.ts:104]((project root)/packages/extension/src/wallet/runtime.ts:104), [base/index.ts:65]((project root)/packages/wallet-core/src/base/index.ts:65), [plan.md:120]((project root)/implementations-plan/M4/5/plan.md:120)). The safe property is weaker: ProfileService public methods block on `ensureInitialized()` ([profile/service.ts:67]((project root)/packages/extension/src/wallet/services/profile/service.ts:67), [background/service.ts:129]((project root)/packages/extension-messaging/src/background/service.ts:129)). Rewrite this claim accordingly, or explicitly task execution with late listener registration / phase ordering if you need a true pre-dispatch fence.
