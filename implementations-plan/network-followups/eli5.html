Network E2E Follow-ups

A second pass on the test suite after PR #46. Three independent improvements bundled into one PR. Plain language.

What this PR is for

PR #46 (the previous one) restored the network e2e test suite from 0 tests running (silent-skipping) to 61/61 passing locally. But on CI it’s still 52-54 of 61 passing — 7-9 tests rotate-flake each run because all 45 test files share one Aztec sandbox process, and that sandbox gets sluggish under cumulative load.

PR #46’s body documented three follow-ups. This PR bundles them.

Goal: all 5 sharded CI runs green · token detail page shows fresh balance on entry without manual refresh · 2 specific slow tests either fixed or documented.

The three follow-ups

1. Suite sharding (the big CI win)

Currently CI runs all 45 test files sequentially against one Aztec sandbox. After ~30 files, the sandbox is sluggish. Late files time out.

Fix: split the test files across 5 parallel GitHub Actions runners. Each runner gets its own fresh Aztec sandbox, runs ~9 files, then dies. No cumulative load.

Why N=5 specifically: vitest's --shard flag distributes files by their SHA-1 hash. We empirically know that multi-account-from and tx-sendTx-multicall are the two slowest files. At N=4, those two hash into the same shard — one runner gets pummeled while the other three sit idle. At N=5, they split into different shards. The 25% extra runner cost is worth the wall-time reduction.

2. TokenBalance auto-refresh (the user UX win)

Right now, when you open a token's detail page in the wallet, you see whatever balance was last cached. If you just sent a transfer, that balance might be stale by a few seconds. You have to click a "Refresh" button to see the new value.

Fix: the page auto-fires a refresh when it opens. You see the cached value first (instant), and the fresh value arrives within ~1-3 seconds without clicking anything.

The subtle bit: the wallet’s background service already publishes "balance updated" events. The page already subscribes to them. The only missing piece is that the page wasn't triggering the refresh on mount — the user had to click. We just move that click into onMounted.

This also lets us delete a test-only helper (waitForTokenDetailBalances) that the e2e tests have been using as a workaround.

3. Slow-test investigation (the time-boxed bet)

Two tests are persistently slow on CI: multi-account-from takes 148 seconds (should be <30s), tx-sendTx-multicall takes 427 seconds (over 7 minutes). They time out repeatedly.

Approach: spend up to 2 hours wiring diagnostic probes + analyzing the traces. If we find a clear root cause, fix it. If we don’t in 2 hours, commit a slow-tests-hypotheses.md file documenting what we tried + the 3 leading theories, and ship the other two follow-ups without blocking on this.

Why time-box this: sharding alone might make these tests pass — each shard's load is now 1/5 of what one runner was doing before. So the "slow test" might actually just be "single-sandbox congestion under heavy serial load." If sharding makes the tests pass, we don’t need to fix anything wallet-side.

What could go wrong (safety review)

Probe code shipping to production

Phase C re-introduces probe code temporarily. If we forget to strip it, the production extension bundle would leak protocol details to the browser console.

How we prevent it:

  • All probes gated by a build-time flag (VITE_E2E_PROBE). When unset, Vite tree-shakes the probe call sites.
  • Phase A.2's bundle-grep CI step — this is the actual guarantee. Permanently in the workflow. If a probe string survives to dist/chrome, the CI fails.
  • Probe payloads contain only method names, timestamps, elapsed-ms, batch sizes. Never addresses, balances, or anything sensitive.

Sharding cost explosion

5 parallel runners instead of 1 = 5x the GitHub Actions concurrent cost.

How we manage it:

  • Paths-filter still restricts to PRs that touch network-relevant code.
  • Total runner-minutes: 5 runners × 18 min ≈ 90 vs current 1 × 35 = 35. That's ~2.6× the runner cost for ~2× faster wall-time feedback. Acceptable.
  • Each shard has a 30-minute timeout (down from 60), so a runaway shard can't burn extra budget.

TokenBalance auto-refresh causing flicker

Page reads cached value first, then async refresh arrives — user briefly sees old then new value.

How we handle it: the existing component already subscribes to balance-updated events — we're just triggering them more reliably. If the flicker is noticeable, the existing BalanceView component already uses a spinner pattern (subscribed to TaskService progress) we can apply later. Not a blocker for this PR.

The "wait: NO_WAIT" fix candidate weakening test coverage

If we switch the 2 slow tests to wait: "NO_WAIT", we stop waiting for the transaction to be mined before checking the assertion. This is fine IF the test's real assertion is about the popup UI or the dApp's RPC response shape, not about the on-chain mined state. Both target tests' assertions ARE popup-shape, so it's safe.

Why three plans + audits?

Same Tier A protocol from PR #46. Three plans written in parallel: main, codex (xhigh), opus 4.7 subagent. Codex final-reviewed the consolidated version.

What this process actually caught:

  • Main plan said N=4 shards. Codex traced vitest's SHA-1 distribution and identified that N=4 clusters both slow files together. N=5 splits them.
  • Main plan said "TokenBalance: await refresh on mount." Codex caught that refreshTokenBalance is enqueue-only — awaiting it gives nothing. Fixed to fire-and-forget.
  • Main plan didn't extend the extension-network paths-filter for TokenBalance code. Codex caught that future TokenBalance-only bugfix PRs would silently skip the network gate.
  • Main plan didn't include the bundle-grep CI step. Opus argued this was the recovery PR's outstanding follow-up; included.
  • Codex's final-review found 3 wording/spec corrections: bundle-grep step had a broken bash glob and wrong env-var visibility; probe table incorrectly attributed multi-account-from to the NO_FROM path; diagnostic test wouldn't actually be routed by filename prefix.
