faucet-wallet-picker

When you click "Connect wallet" on the faucet today, it broadcasts "any Aztec wallets here?" and then grabs whichever answers first — so with two compatible wallets installed, which one you get is a coin toss, and the flow can break. This plan makes the faucet list every wallet as it announces itself and lets you pick — always, even when there's only one. Your pick is remembered, so next visit connects straight to the same wallet, with a "use a different wallet" link to change your mind. Faucet only, by your call — the playground has the same coin toss and is recorded as a follow-up.

Why this tier was chosen

light. One app (the faucet), no storage migrations, no new dependencies — the wallet-discovery API already streams every wallet; the current code just stops listening after the first. Nothing scores high on the risk rubric. One plan-time codex audit, then your standing multi-round codex post-impl cadence.

Phases

Phase 1: The connection brain

Rewrite the connection state machine: keep listening as wallets announce, build a live list, add a "choosing" state, connect only on an explicit pick, and remember the pick only after a fully successful connection (a wallet that failed verification never becomes your default). A remembered wallet that stops working un-remembers itself instead of locking you out.

Proves itself by: lint + typecheck + the faucet unit suite, with new tests for every stream shape (0, 1, many, latecomers) and every path.

Phase 2: The picker UI

A small list component: each wallet's icon, name, and a badge saying whether it's an extension or a web wallet; a "Scanning for more wallets…" hint while discovery is live; Cancel; and the "use a different wallet" link when a preference exists. Names render as plain text — a wallet calling itself something sneaky can't inject anything, and the real security check (the emoji match) stays exactly where it was.

Proves itself by: component tests (rows, live appends, per-row connect, cancel, the spoof-safety render).

Phase 3: End-to-end + build + docs

Teach the faucet's browser test to click through the picker, prove the deployable faucet still builds, and write the docs (including the playground follow-up note).

Proves itself by: full lint/typecheck/faucet tests + the faucet e2e suite (named explicitly — it does not run inside the unit script) + the faucet build, all green.

Human context

Wallet discovery works like a roll call: the page asks, and each installed wallet raises its hand — but not simultaneously; answers trickle in over a few hundred milliseconds. The old code left the room as soon as the first hand went up. The fix is to keep the door open, show hands as they rise, and let you choose. The plan's first codex audit sharpened one thing considerably: a wallet's name tag is self-written — any extension can claim to be "Nulo", identical name, identical id. So the design fails closed: if two wallets ever claim the same remembered identity, the auto-reconnect turns itself off and you're shown both, side by side, to choose deliberately. The audit also caught (from the SDK's own source) that cancelled discovery can still deliver buffered stragglers — the state machine discards those — and found a dormant pre-existing bug (the "wallet disconnected" cleanup never actually fired) that gets fixed along the way.
