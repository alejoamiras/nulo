Vitest → Vite 8 dedupe (one Vite in the tree)

Our four apps already build with Vite 8. But two leftovers still drag in an older Vite 7, so the repo has two Vites at once: (1) the test runner (Vitest) secretly runs your tests on Vite 7 even though it's happy on Vite 8, and (2) a Vue developer tool we don't actually use anymore pulls in four more copies of Vite 7. The goal: exactly one Vite (8) everywhere, with every test still green and every build untouched.

Why this tier was chosen

mid. Rubric: only one dimension is "moderate" — blast radius (the test runner is shared by all 11 workspace packages). Everything else is low: it's a well-trodden dependency cleanup, fully reversible (just revert the lockfile/manifest), no data/migration, no external services, and it's actually a net reduction in supply-chain surface. One moderate → mid.

What the experts changed

Two independent reviewers (codex + a Claude planner) attacked the first draft. Codex rejected it — and caught the best simplification: the Vue devtools plugin is dead code (declared but never imported), so we should delete it, not upgrade it. Deleting it removes four Vite 7 copies for free. Both reviewers also showed the test-runner fix must be deterministic; after you flagged the lockfile edit as brittle, we switched to a one-line overrides — the idiomatic, durable way to force one Vite. The test command's local hang is fixed in Phase 1. All folded in — the plan got simpler.

Phases

Phase 1: Delete the dead dev tool + fix a test footgun

(a) Remove the unused vite-plugin-vue-devtools dependency (and a stale comment) — instantly evicts four Vite 7 copies and three packages we never used. (b) Flip the extension's test script to vitest run so the test command stops hanging locally.

Proves itself by: the devtools chain is gone from the lockfile, the extension still builds, and the whole test suite runs hang-free and green.

Phase 2: Move the test runner onto Vite 8

Add a one-line overrides entry (vite: ^8.0.0) so Vitest is forced to reuse the Vite 8 we already have instead of its private old copy. This is the standard, durable way to collapse a duplicated dependency — deterministic, not a fragile lockfile hand-edit. (There's no newer Vitest that fixes this on its own — even the latest still allows the old Vite.)

Proves itself by: zero Vite 7 left anywhere (checked in both the installed files and the lockfile), and all tests + typecheck + lint green.

Phase 3: Full check + ship

Run everything — all five app builds, the whole test suite, lint, typecheck, the frozen-lockfile check, plus smoke and full network end-to-end tests — and eyeball the final lockfile diff so it contains only the intended changes.

Proves itself by: every command exits cleanly, smoke + network e2e green, and the diff is only "devtools removed + Vitest deduped".

Human context

Vite is the build tool; Vitest is the test runner that piggybacks on Vite. If tests run on a different Vite than builds, a bug could hide in the gap. Bun (our package manager) accidentally gave Vitest its own private copy of the old Vite instead of sharing the new one — that's the "dedup miss" we're fixing. The devtools plugin was probably added long ago for local debugging and quietly stopped being wired up; nobody noticed because it still sat in the dependency list.
