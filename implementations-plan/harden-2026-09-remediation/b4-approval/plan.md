## Summary

Three approval-surface fixes. The dApp approval card renders what is signed: the recognized-transfer vocabulary and arities derive from the wallet's own `TOKEN_FN_DESCRIPTORS` instead of two drifted hardcoded lists, an unrecognized call renders a warning plus its indexed raw arguments (approve stays allowed), the authwit card shows the delegate (`caller`), the call arguments and the inner hash with an "opaque authorization" warning, and the private authwits discovered at estimate time are listed on the card and bound to the execution that is approved (F-02). Approval authority binds to the stored interaction payload: the service worker materializes the executable operations from what the dApp actually requested and accepts from the popup only wallet-generated per-index deltas (fee settings, validated against the requested fee path; an estimate id the SW minted for that same operation) — the estimate itself is computed by reference to the stored payload, never from a popup-supplied operation; a discovery- or capability-shaped id cannot be approved (F-16). Every handshake that will need a verify window reserves one per-origin slot at discovery admission, before the wallet approves it: a per-origin token bucket slows a reload loop, at most two verify windows per origin are open at once, excess handshakes queue (bounded, expiring with the dApp's own discovery window) and are served on refill or window close, duplicate same-tuple waiters are bounded, and the establishment gate (B-13) is unchanged (F-18). No storage shape changes; no migration.

## Architecture & Implementation (compact)

- **F-02 vocabulary.** New `apps/extension/src/utils/token-transfer-vocabulary.ts` imports `wallet/services/token/functions/descriptors.ts` DIRECTLY (a pure leaf: `@aztec/foundation`, `@aztec/stdlib/abi`, `./types`; never the barrel `token/functions/index.ts`, whose `runtime.ts` pulls aztec-runtime account/PXE code) and builds once, at module init, `TRANSFER_SIGNATURES: ReadonlyMap<name, readonly { kind: TokenFnKind; params: readonly string[] }[]>` — a LIST per name, because `transferPrivate` and `transferPublicToPrivate` carry a 2-param and a 4-param variant under the same names (`descriptors.ts:356-358,381-383`) — from the four transfer descriptors × `defaultNames` × `variants` via `abiBuilder(name, impl).parameters`; the parameter NAMES (`from`, `to`, `amount`, `authwit_nonce`) come from the synthetic ABI, so arity and positions are derived, not hand-mapped. `parseTransferIntent` matches `(name, args.length)` against the list and reads `to`/`amount`/optional `from` by parameter name; the 2-param `transfer(to, amount)` yields `from: undefined`: on ACCOUNT execution the card renders "From: this account" with the operation's `accountAddress` (`dapp-send-executor.ts:567-569` enforces `opts.from === accountAddress`, so the account contract is `msg_sender`), on `default_entrypoint` it renders "From: transaction entrypoint — not this account" (`tx-request-builder.ts:403` executes with no sender); the 4-param variant renders the explicit `from` as today; `authwit_nonce` is shown when non-zero. - **F-16 binding.** `approveInteraction(id, deltas: OperationApprovalDelta[])` replaces `(id, operations, origin, estimateIds?)`. `OperationApprovalDelta = { feeSettings?: FeeSettings; estimateId?: string }`, index-aligned with `payload.params.operations`, popup-privileged like today's `estimateIds` (`spec.ts:113-114`), never a field on the wire `Operation`. `previewedInterface` leaves the envelope: its contract+chain check (`execution/service.ts:745-749`) does not authenticate the function mappings it persists (`token/service.ts:385`), so the executor always parses the interface itself. BEFORE the claim (`storage.delete`), the service rejects unless `Array.isArray(payload.params.operations)` (a `CapabilityPayload` has `session` but no operations — approving it would kill the capabilities request) and unless `deltas.length` matches; the message is the non-disclosing "Invalid id". **Estimate by reference:** `estimateOperationFee(interactionId, index, feeSettings, estimateToken?, flowKey?)` replaces the popup-supplied operation (the execute window is its only caller): the SW materializes the operation from the stored payload, so no popup-shaped operation reaches the estimator, the reuse cache or the preview snapshot. Defense in depth: the encoded-call and encoded-authwit fingerprints (`operation-fingerprint.ts:130`) gain the optional `name`, so a name-only difference can never reuse a build (one test). Inside `executeAndResolve`, AFTER the fence and live-session checks (unchanged), the operations are materialized from `interaction.payload.params.operations` with `materializeRequest` (`materialize.ts`) through the same `MaterializeDeps` the silent path builds (extracted into `materializeDepsFor(profileId)`, using `authorizedFence.profileId`), then each delta is applied FIELD BY FIELD per kind — never by spread, which would let a "delta" carry `accountAddress`, `exec`, `opts.from` or `executionMode`: `feeSettings` only to `aztec_sendTx`/`send_transaction` AND only when the materialized op `requiresFeeSelection` (an embedded fee path stays embedded, `materialize.ts:91,100`), with the PATH validated — a self-pay request (`isSelfPay(exec, opts.from)`, `packages/wallet-bridge/src/fee-payer.ts:69`; today locked to `fj` only in the popup, `OperationCard.vue:75`, while execution picks the strategy from whatever settings arrive, `execution/service.ts:965`) accepts only `paymentMethod.kind === "fj"`, any other send accepts only a selectable method; `estimateId` threaded as the executor's per-index envelope (the SW checks it names a snapshot for THIS `(interactionId, index)`); `assertExecutableOperation` narrows each; `origin` is derived SW-side from `payload.session.dappMetadata.name` (sanitized at persistence, `background.ts:771-776`; the popup no longer supplies it). The discovery-shaped id is refused with the same "Invalid id" as an unknown id (non-disclosing) BEFORE the claim, so the record survives for `resolveInteraction`. `execute/index.vue` keeps `buildOperationsFromPayload` for display and its client-side draft state; `approve()` sends deltas built from `handleFeeUpdate`'s state, `tokenInterfaces`, `feeEstimates` (id + hashes). The `as unknown as Operation` cast at `index.vue:425` disappears. `ExecutionService.executeOperations` gains the per-index envelope in place of `estimateIds` (same positions, two fields).
- **F-18 design (ask D — the seed's mandatory consult; the plan's position after the dual audit).** A verify window is the user's only check on a live session, and `handleSessionEstablished` returns `true` — releasing message dispatch (`background.ts:396-399`, B-13) — the moment the window opens; so a session must never be established with its window merely queued (it would run live, unverified, for as long as other windows stay open). Admission therefore happens at DISCOVERY, before `approveDiscovery`, on every approval site: one per-`origin` gate in `wallet-sdk/verify-admission.ts` (`admit({ origin, deadline, needsWindow }, run) → "now" | "queued" | "rejected"`, state in `SdkHandlerState`, clock injected) combining (a) a token bucket for the reconnect RATE — capacity 3, refill 1 / 20 s — consumed by every remembered-session handshake, trusted or not, and (b) verify-window CAPACITY — 2 open-or-reserved windows per origin, 8 global — consumed by every handshake that will open a window (returning-untrusted, fresh after the connect popup, dedupe waiters after their popup; a trusted reconnect needs no window and no reservation). `"now"` runs the approval; `"queued"` (bound 4 per origin, FIFO) holds the request BEFORE key exchange — the SDK's key-exchange response is never delayed, only the wallet's approval — and a cancellable `clock.setTimeout` armed while the queue is non-empty drains it at the next refill or expiry; a queued entry past its discovery deadline (the existing 55 s cutoff, `rejectIfExpired`) is rejected explicitly (`rejectDiscovery` deletes the SDK's entry and does NOT notify the page — the dApp learns from its own 60 s timeout); beyond the bound → `"rejected"` immediately. A window reservation is held from admission until `handleSessionEstablished` opens the window against it and then until `WindowPort.onRemoved` fires for that window (`SessionEstablishedDeps` gains the `WindowPort` from `packages/wallet-core/src/ports/window-port.ts` — the same port `WindowManager` is built on, NOT `WindowManager.openAndAwait`, whose timeout closes the window); it is released on open failure (session terminated, B-13 fail-closed unchanged), on `onSessionTerminated`, and by the discovery deadline if the session never establishes. (c) **waiter bound** — before `awaitPendingPopupDedupe` (`:663-668`), a per-`dedupeKey` count, 8, reject-new beyond (the `discovery-queue.ts:60-81` shape), decremented in the waiter's `finally`. The establishment gate, `runDiscoveryPopup`'s popup flow and the trusted-reconnect path are otherwise untouched. Keying on `origin` (not `origin|chainId`): a reload loop is per origin; concurrent chains (`:661`) share the origin's budget. Sequential cells never engage the gate: each reconnect follows an `approveVerify` that awaited the OS close, and the bucket holds 3 tokens.
- **Alternatives not taken:** reordering `checkDiscoveryPopupCaps` before the auto-approve (counts a map the reconnect branch never touches); reusing/focusing an open verify window for a new session (its hash is session-specific, B-06); a hard reject on the reconnect branch (owner: slowed, not blocked); queueing the verify window AFTER establishment (the session would run live and unverified while other windows stay open); awaiting it inside `handleSessionEstablished` (stalls B-13 dispatch); `WindowManager.openAndAwait` for the verify window (timeout closes it); a popup-authored discovered-hash list (the popup is what the bind must bound); keeping `previewedInterface` (its identity check does not authenticate the mappings it persists); widening `MessageHashAuthwitContent` (a dApp could pre-attach a decorated `message_hash` action the wallet never verified); keeping `KNOWN_MINT_METHODS` (a second hand list beside the descriptors — a structured mint later means a mint descriptor); routing `send_transaction` confirm through discovery (suppression is the smaller change); a popup-supplied `origin`; an acknowledgement checkbox on the fallback (owner: warn, approve allowed).

## Security & Adversarial Considerations
- Threat model: a connected dApp with a transactions grant crafting a call the card would under-render (F-02 — every call now shows either a descriptor-verified intent or its raw arguments with a warning; the authwit card shows the delegate and the hash; discovered authwits are listed and a rebuild cannot add one the user never saw); a compromised or buggy same-extension popup (F-16 — it can no longer substitute operations or origin, feed the estimator a foreign operation, alter the fee PATH, or persist a token interface: only fee settings within the requested path and an estimate id the SW validates against its own snapshot); a remembered origin looping reloads or scripting handshakes (F-18 — slowed to one approval per refill after a burst of three, two verify windows per origin with excess handshakes queued before key exchange and expiring with the dApp's own window, bounded duplicate waiters; no session is ever live with its verification merely queued).
- Still trusted, by documented boundary: the descriptor table itself (the wallet's own model of a token); the estimate the popup shows (SW-produced); the verify window's emoji comparison (unchanged); the dApp's ability to keep a queued handshake alive within its own discovery window; a same-extension context's storage privileges.
- Fail-closed everywhere: an unrecognized name or arity renders raw arguments, never a guessed intent; a hostile `toString` renders "(opaque value)"; a payload without operations, a delta length mismatch, an off-path fee method, an estimate id for another operation, an unseen discovered hash (standard and NO_FROM) and a discovered hash with no snapshot all abort; a verify window that fails to open terminates its session; an empty bucket or a full window budget queues, never approves; a queued handshake past its deadline is rejected, never served.
- What this does NOT do: an acknowledgement checkbox (owner: warn, approve allowed); a bound on how long a queued handshake waits beyond the dApp's own window; per-chain buckets.
