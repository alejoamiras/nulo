## Summary

Three approval-surface fixes. The dApp approval card renders what is signed: the recognized-transfer vocabulary and arities derive from the wallet's own `TOKEN_FN_DESCRIPTORS` instead of two drifted hardcoded lists, an unrecognized call renders a warning plus its indexed raw arguments (approve stays allowed), the authwit card shows the delegate (`caller`), the call arguments and the inner hash with an "opaque authorization" warning, and the private authwits discovered at estimate time are listed on the card and bound to the execution that is approved (F-02). Approval authority binds to the stored interaction payload: the service worker materializes the executable operations from what the dApp actually requested and accepts from the popup only wallet-generated per-index deltas (fee settings, previewed token interface, estimate id, the shown authwit list); a discovery-shaped id cannot be approved (F-16). Reconnect handshakes from a remembered origin are throttled per origin and verify windows are reserved per origin with a queue instead of created unboundedly; a second handshake while a verify window is open waits its turn, duplicate same-tuple waiters are bounded, and the fresh-connection path is untouched (F-18). No storage shape changes; no migration.

## Architecture & Implementation (compact)

- **F-02 vocabulary.** New `apps/extension/src/utils/token-transfer-vocabulary.ts` imports `wallet/services/token/functions/descriptors.ts` DIRECTLY (a pure leaf: `@aztec/foundation`, `@aztec/stdlib/abi`, `./types`; never the barrel `token/functions/index.ts`, whose `runtime.ts` pulls aztec-runtime account/PXE code) and builds once, at module init, `TRANSFER_SIGNATURES: ReadonlyMap<name, { kind: TokenFnKind; params: readonly string[] }>` from the four transfer descriptors × `defaultNames` × `variants` via `abiBuilder(name, impl).parameters` — the parameter NAMES (`from`, `to`, `amount`, `authwit_nonce`) come from the synthetic ABI, so arity and positions are derived, not hand-mapped, and one pin test covers both. `parseTransferIntent` matches `(name, args.length)` against that map and reads `to`/`amount`/optional `from` by parameter name; the 2-param `transfer(to, amount)` yields `from: undefined` and the card renders "From: this account" with the operation's `accountAddress` (the account contract IS `msg_sender` for that variant — a fact, not a guess); the 4-param variant renders the explicit `from` as today; `authwit_nonce` is shown when non-zero. `KNOWN_MINT_METHODS` is deleted (ask A): no descriptor exists, a mint is a contract-owner call, and the new fallback renders its arguments anyway. `tx-enrichment.ts` keeps `METHOD_LABELS` for the non-transfer entries (`shield`, `claim`, … — journal/activity-wide, 12 consumers) but the transfer labels are produced from the vocabulary map by kind ("Transfer (private)", "Transfer (public)", "Transfer to private", "Transfer to public"); the hardcoded transfer names leave both files. Pin test (`token-transfer-vocabulary.test.ts`): the recognized name set equals the union of the four descriptors' `defaultNames`; every entry's `params` equals the descriptor ABI's parameters for that variant; `getMethodLabel` covers exactly that set for transfers. `UPDATE.md:45` gains one sentence.
- **F-02 card.** `OperationCard.vue:135` gains the missing `v-else`: `execute-op-unverified-args` — "Unverified call — review the arguments" (warning color) and one `execute-op-arg` row per argument, `#i: value`, each through the same projection `parseTransferIntent` trusts (canonical hex/decimal or the object's own `toString`, `safeWire(…, 64)`; an object without a usable `toString` renders "(opaque value)"). The `aztec_createAuthWit` branch (`:357-393`) renders, for `CallIntent`: `execute-authwit-caller` (the delegate — "Authorizes: 0x…"), the target and function as today, and `execute-authwit-args` (indexed, same projection); for `IntentInnerHash`: consumer, `execute-authwit-inner-hash` and `execute-authwit-opaque-warning` ("Opaque authorization — the wallet cannot show what this hash authorizes"). Every value passes `safeWire`. Component tests mount both branches.
- **F-02 discovered authwits.** `discovery-probe.ts:81-90` and `authwit-discoverer.ts:113-123` keep what they already hold: beside the wire action (unchanged `message_hash` content — `MessageHashAuthwitContent` is dApp-facing and is NOT widened) each pushes a SW-internal `DiscoveredAuthwit = { consumer, caller, selector, args, innerHash, messageHash }` (all strings — `effect.contractAddress`, and `CallAuthorizationRequest`'s `msgSender`, `functionSelector`, `args`, `innerHash`; stringified at the record, since the estimate crosses the RPC as JSON). `DiscoveryEstimateResult` gains `discovered`; `estimateOperationFee` (`dapp-send-executor.ts:292`) returns it as `TransferFeeEstimate.discoveredAuthwits?` (`packages/wallet-bridge/src/fee.ts`; optional; never set on the Send page) and `stashOperationEstimate` stores `discoveredHashes` on `OperationEstimateReuseEntry`. **`send_transaction` is suppressed**: its ESTIMATE runs discovery (`:274-283,292`) but its CONFIRM does not (`:489`, `buildAndEstimateValidated`), so a list would show authorizations confirm never adds — the field is omitted for that kind and pinned. The popup already receives the estimate as `unknown` (`execute/index.vue:133-140`, `OperationCard.vue:48`): the prop is typed `TransferFeeEstimate | undefined` and the card renders `execute-op-discovered-authwits` (one `execute-op-discovered-authwit` row per entry: consumer, caller, humanized selector, indexed args through the action-row pattern, trimmed inner hash — "found during estimation"); for embedded-fee and `default_entrypoint` operations, where no discovery runs before confirm, the card says "Authorizations resolved at send" instead of implying an empty set. Binding (ask C): the popup's approval delta carries `discoveredMessageHashes` (the hashes it displayed; `undefined` when no estimate result was available); at confirm, a REUSED estimate is bound by construction (`tryConsume` validates the entry that produced the shown list); a REBUILT estimate (`:696`) compares the recomputed hashes against the delta — any hash the user did not see aborts with "Authorizations changed since preview — re-open the request" (fail closed); `undefined` is treated as the empty set.
- **F-16 binding.** `approveInteraction(id, deltas: OperationApprovalDelta[])` replaces `(id, operations, origin, estimateIds?)`. `OperationApprovalDelta = { feeSettings?: FeeSettings; previewedInterface?: TokenInterface; estimateId?: string; discoveredMessageHashes?: string[] }`, index-aligned with `payload.params.operations`, popup-privileged like today's `estimateIds` (`spec.ts:113-114`), never a field on the wire `Operation`. The service rejects a payload without `session` ("approval requires an execution payload" — only `DiscoveryPayload` lacks it, `spec.ts:95`) and a length mismatch. Inside `executeAndResolve`, AFTER the fence and live-session checks (unchanged), the operations are materialized from `interaction.payload.params.operations` with `materializeRequest` (`materialize.ts`) through the same `MaterializeDeps` the silent path builds (extracted into `materializeDepsFor(profileId)`, using `authorizedFence.profileId`), then each delta is applied FIELD BY FIELD per kind — never by spread, which would let a "delta" carry `accountAddress`, `exec`, `opts.from` or `executionMode`: `feeSettings` only to `aztec_sendTx`/`send_transaction` (ignored elsewhere), `previewedInterface` only to `register_token` (the executor's `contract`+`chainId` cross-check at `execution/service.ts:737-756` stays), `estimateId`/`discoveredMessageHashes` threaded as the executor's per-index envelope; `assertExecutableOperation` narrows each; `origin` is derived SW-side from `payload.session.dappMetadata.name` (sanitized at persistence, `background.ts:771-776`; the popup no longer supplies it). The discovery-shaped id is refused with the same "Invalid id" as an unknown id (non-disclosing) BEFORE the claim, so the record survives for `resolveInteraction`. `execute/index.vue` keeps `buildOperationsFromPayload` for display and its client-side draft state; `approve()` sends deltas built from `handleFeeUpdate`'s state, `tokenInterfaces`, `feeEstimates` (id + hashes). The `as unknown as Operation` cast at `index.vue:425` disappears. `ExecutionService.executeOperations` gains the per-index envelope in place of `estimateIds` (same positions, two fields).
- **F-18 design (ask D — the seed's mandatory consult; the plan's position, converged with the fable outline).** The verify window is informational: `handleSessionEstablished` returns `true` right after the window OPENS (`session-established.ts:144-154`) and message dispatch (`background.ts:396-399`, B-13) waits for that promise, never for the user — so the reservation must be non-blocking for establishment or a queued second tab's messages would stall behind tab 1's window (the two-tab cells would hang). Three small mechanisms, all state in `SdkHandlerState` (no alarms; time read lazily from an injected clock): (1) **reconnect throttle** — a pure per-`origin` token bucket with a bounded FIFO (`wallet-sdk/reconnect-throttle.ts`: `admit(key, run) → "now" | "queued" | "rejected"`; capacity 3, refill 1 token / 20 s, queue bound 4 per origin) at the existing-session branch (`background.ts:648-650`) around `autoApproveExistingSession`; a queued entry is re-checked with `rejectIfExpired` when dequeued (the SDK's ~60 s discovery window means anything served past ~55 s is dead on both sides — expected under sustained flood, and the SDK map never leaks because every excess request gets an explicit `rejectDiscovery`, as at `:632-641`); a 1 Hz reload loop gets 3 immediate approvals then one per 20 s. (2) **verify-window reservation** — `SessionEstablishedDeps` gains a `WindowPort` (`packages/wallet-core/src/ports/window-port.ts`, the same port `WindowManager` is built on — NOT `WindowManager.openAndAwait`, whose timeout CLOSES the window and whose user-close rejects, both wrong for a fire-and-forget informational window) and a `verifyWindows: VerifyWindowReservation` (per `origin`: 2 open windows; global: 8; counts EVERY verify window, first-connect included). Under cap: reserve synchronously, `create`, return `true` (today's semantics). At cap: enqueue `{ sessionId, url }` with `isReconnect` captured NOW (the `pendingVerification` marker is cleared in `finally`) and return `true` — "reserved, never dropped"; on `WindowPort.onRemoved` of a verify window the slot is released, the next entry is dequeued, `isSessionLive` is checked (a dead session is skipped), the window opens; an open failure — inline or deferred — calls `terminateSession` (B-13 fail-closed preserved on both legs). The verify popup's own `closeWindow` is unchanged. (3) **waiter bound** — before `awaitPendingPopupDedupe` (`:663-668`), a per-`dedupeKey` count, 8, reject-new beyond (the `discovery-queue.ts:60-81` shape), decremented in the waiter's `finally`. The fresh-connection path (`runDiscoveryPopup`) and the trusted-reconnect path (`trustedVerification` → no window) are untouched. Keying on `origin` (not `origin|chainId`): a reload loop is per origin; a multi-chain dApp keeps concurrency because capacity ≥ 2. Sequential cells never engage either mechanism: `approveVerify` awaits the OS close before the next reconnect and the bucket holds 3 tokens.
- **Alternatives not taken:** reordering `checkDiscoveryPopupCaps` before the auto-approve (counts a map the reconnect branch never touches); reusing/focusing an open verify window for a new session (its hash is session-specific, B-06); a hard reject on the reconnect branch (owner: slowed, not blocked); awaiting a queued verify window inside `handleSessionEstablished` (stalls B-13 dispatch for the queued tab); `WindowManager.openAndAwait` for the verify window (timeout closes it); widening `MessageHashAuthwitContent` (a dApp could pre-attach a decorated `message_hash` action the wallet never verified); keeping `KNOWN_MINT_METHODS` (a second hand list beside the descriptors — a structured mint later means a mint descriptor); routing `send_transaction` confirm through discovery (suppression is the smaller change); a popup-supplied `origin`; an acknowledgement checkbox on the fallback (owner: warn, approve allowed).

## Security & Adversarial Considerations
- Threat model: a connected dApp with a transactions grant crafting a call the card would under-render (F-02 — every call now shows either a descriptor-verified intent or its raw arguments with a warning; the authwit card shows the delegate and the hash; discovered authwits are listed and a rebuild cannot add one the user never saw); a compromised or buggy same-extension popup (F-16 — it can no longer substitute operations or origin: only fee settings, a previewed interface the executor re-checks, an estimate id the SW validates, and the hash list it was shown); a remembered origin looping reloads or scripting handshakes (F-18 — slowed to one auto-approval per refill, one open verify window per origin with the rest queued, bounded duplicate waiters).
- Still trusted, by documented boundary: the descriptor table itself (the wallet's own model of a token); the estimate the popup shows (SW-produced); the verify window's emoji comparison (unchanged); the dApp's ability to keep a queued handshake alive within its own discovery window; a same-extension context's storage privileges.
- Fail-closed everywhere: an unrecognized name or arity renders raw arguments, never a guessed intent; a hostile `toString` renders "(opaque value)"; a payload without `session`, a delta length mismatch, an unseen discovered hash, and a foreign `previewedInterface` contract all abort; a verify window that fails to open terminates its session; an empty bucket waits, never approves.
- What this does NOT do: an acknowledgement checkbox (owner: warn, approve allowed); a bound on how long a queued handshake waits beyond the dApp's own window; per-chain buckets.

## Assumptions
**Facts (verified at source, `recon.md`):** (1) `parseTransferIntent`'s sole consumer is the card; (2) `descriptors.ts` is a pure leaf and `abiBuilder` returns parameter names; (3) both discovery paths compute `{consumer, innerHash}` and discard it; (4) `DiscoveryEstimateResult.discoveredActions` reaches `estimateOperationFee` and is dropped at `:292`; (5) the popup holds the estimate result as `unknown` and casts `estimateId`; (6) `approveInteraction` has one caller (`execute/index.vue:441`); only `DiscoveryPayload` lacks `session`; (7) `materializeRequest` is used by the silent path only; (8) `session-established.ts` calls `chrome.windows.create` bare and nothing observes the close; (9) no rate limiter exists in the repo; (10) `waitForPopup` snapshots pre-existing targets and waits for a new one.
**Inferences:** (a) the popup's Confirm can be reached without a successful estimate (gating is fee selection + token metadata, `index.vue:397-402,560`), so `discoveredMessageHashes` is optional and treated as empty — verified at Phase 1; (b) a queued reconnect served after ~55 s is rejected by `rejectIfExpired` and the SDK drops its own pending entry on `rejectDiscovery` — verified in the throttle unit test and the flood cell; (c) `CallAuthorizationRequest.args` are the authorized call's arguments (upstream `.d.ts`), so the discovered record can show them — verified at Phase 1.

F-18 parameters: bucket capacity 3 / refill 20 s / queue 4 per origin, 2 verify windows per origin / 8 global, waiter bound 8 — and whether the reservation should ALSO cap the fresh-connection window (it counts it; it never queues a first connect because the discover popup already serializes them); E. delta envelope: one `OperationApprovalDelta[]` replacing `operations`+`origin`+`estimateIds`; F. whether the raw-args fallback should also apply to `send_transaction`'s `call` actions (today `OperationActionRow` renders name + contract for a plain `call`, no args).
