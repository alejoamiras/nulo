## Summary

Three owner-locked reductions of surface: the full backup stops carrying fee-payer (FPC) rows and network rows — protocol FPCs re-derive and the default networks reseed on import, so a doctored backup can no longer plant a payer or an RPC endpoint (F-03 second half, F-04); "Add network" moves behind Developer Mode so the custom-chain surface is opt-in (F-04); and the passkey Relying Party ID moves to a content-less subdomain so no page on `nulo.sh` or its application subdomains can evaluate the wallet's PRF (F-05). No storage migration (pre-production rule), no crypto change, no new dependency. The one piece of new control flow is the reseed stage that replaces the network-restore stage.

## Architecture & Implementation (compact)

- **F-03 FPC slice.** Remove `[FPC_SERVICE_NAME]` from `BACKUP_SLICE_REGISTRY`, the `FpcServiceClient` entry from `buildSliceClients()` (`useFullBackupImport.ts:408`) and the export entry in `buildBackupServices()` (`export/full.vue`). Nothing else references the slice (recon). The B1 picker/`getFpcImpl` gate stays as defense in depth.
- **F-04 network slice → reseed.** Export: drop the `NETWORK_SERVICE_NAME` entry; replace the top-level raw `"active-network-id"` with `"active-chain-id"` (`appStore.network?.chainId`, a number — stable across installs, unlike a row id); `AccountStateService.backup()` writes `chainId: n.chainId` beside `networkId: n.id` on each item (the slice is `non-storage`, versioned by `aztec-version`; the field is additive). Restore: `restoreNetworksStage` becomes `reseedNetworksStage(networkService, profileService, profileId, io)` → new RPC `NetworkService.seedDefaultsForProfile(profileId)`: (i) the target must be a live profile (looked up through the profile service, not inferred from an epoch — `captureRestoreEpochs` accepts any unreserved id), (ii) the deletion epoch is captured before that lookup and re-asserted under the network lock before every write, (iii) idempotent — rows already stored for the profile are returned untouched, so a repeat call can neither duplicate `(profileId, chainId)` nor reset endpoint edits, (iv) it runs `seedOneNetworkLocked` for each of `DEFAULT_SEEDS` and writes the target's persisted active pointer to the primary seed via `_writeActive` ONLY — it never touches `this.nodes` (the cache is keyed by `chainId` alone, so `activateSeededLocked`'s cache write would replace the ACTIVE profile's node for that chain with the target's seed endpoint; codex round 1, blocking); the cache is populated on normal active-profile access as today. Zero seeded rows keeps the existing rollback ("Couldn't seed the default networks"). Then `remapNetworkIdByChain(data, seeded)` (sibling of `remapByMap`): the lookup is a strict numeric `chainId → seeded row id` (chain `0` included); an account-state item whose `chainId` is missing, non-numeric or unseeded is removed from the slice and recorded via `io.recordRestoreErrors(ACCOUNT_STATE_SERVICE_NAME, …)`; a transaction row is assigned the seeded id of its `chainId` whether or not it carried a `networkId` (rows on an unseeded chain are dropped and recorded likewise); an imported `networkId` is never used as a fallback. Custom networks are re-added by hand (owner decision); their state is not carried. `restoreActiveNetworkPointer` treats `active-chain-id` as an untrusted preference: strict numeric membership in the seeded rows (chain `0` included) selects that row, anything else leaves the primary seed active (`resolveRestoredActiveNetworkIdByChain` replaces `resolveRestoredActiveNetworkId`). `restoreAccountStateStage` keeps its signature (`createdNetworks` = the seeded rows).
- **Old backups.** `normalizeBackupData` keeps rejecting an unknown key, so a pre-B2 backup carrying `network`/`fpc` fails closed with "unknown backup slice: network". Pre-production, no users, no migration (CLAUDE.md rule); documented in `backup/README.md` and pinned by a registry test. No `IMPORT_BLOCKING_ACK` entry is needed (recon: it acknowledges migration versions, and `realMigrations` is empty).
- **Dead RPC surface.** `BaseService` already supplies null-returning `backup`/`restore` defaults (`packages/extension-messaging/src/background/service.ts:99-107`), so the four overrides (`NetworkService.backup/restore`, `FpcService.backup/restore`) are deleted with their now-unused helpers (`validateRestoredNetwork`, `ERR_BACKUP_TOO_OLD` and the user-facing mapping of it, the FPC legacy-row rejection) and their direct tests; the inherited defaults stay inert. Codex round 1: the retained network override was an internal RPC accepting arbitrary HTTPS endpoints — protected, but pointless to keep.
- **F-04 Developer-Mode gate.** `settings/networks/index.vue` renders the Add-network button under `v-if="isDeveloperModeEnabled"`, read exactly as `settings/advanced/index.vue` does (`configService.getProps()` on mount + `onUpdate`). Custom endpoints on seeded networks stay ungated. Existing custom rows keep rename/endpoint/delete management with Developer Mode off (the page never branches on `kind`; the gate is on creation only). The commented-out opener in `SelectNetworksPopup.vue:88-98` is deleted.
- **F-05 RP ID.** `RP_ID = "passkey.nulo.sh"`; `manifest.config.ts` `host_permissions` → `https://passkey.nulo.sh/`; `SECURITY.md` updated; `check-rp-id` needs no change (re-derives from `RP_ID`). The content script's `matches: ["*://*/*"]` already covers the RP host, so the manifest gains `exclude_matches: ["*://passkey.nulo.sh/*", "*://*.passkey.nulo.sh/*"]` on that entry — the wallet's own content script must not be a script on the RP origin or on any descendant (the domain-suffix rule keeps `*.passkey.nulo.sh` RP-eligible). `manifest.test.ts` pins the literal `RP_ID === "passkey.nulo.sh"`, the host permission `https://${RP_ID}/`, and EFFECTIVE injection (a small match-pattern evaluator over `matches` minus `exclude_matches`) for `https://passkey.nulo.sh/`, `https://x.passkey.nulo.sh/` (excluded) and `https://nulo.sh/` (still matched); a grep-shaped test asserts the RP host is not a Pages target in the repo (`apps/*/wrangler*.jsonc`, `apps/landing`, `apps/tools`) — it cannot see dashboard-managed hosting. No `.well-known/webauthn`: the extension uses host-permission RP authorization, not related-origin authorization, and that file would enable the latter. **Owner action (not this batch):** provision `passkey.nulo.sh` as a static page — strict CSP, no scripts, never application code — and keep every `*.passkey.nulo.sh` descendant content-free; DNS only needs to resolve for browsers that verify RP-ID registrability (Chrome does not fetch it). Must land before any real passkey wallet exists.
- **Alternatives not taken:** silently stripping retired slice keys on import (tolerant parsing widens the hostile-backup surface the batch is shrinking); keeping the network slice but re-validating rows (the owner dropped it); gating custom endpoints too (they already pass the exact-identity probe); a `chainId → networkId` remap inside each service's `restore` (one helper on the composable side keeps every slice's restore unchanged).

## Security & Adversarial Considerations
- Threat model: a doctored copy of the victim's own backup (F-03/F-04 — the slices it could poison no longer exist; the reseed only writes `DEFAULT_SEEDS`), a hostile web origin on `nulo.sh`/`*.nulo.sh` (F-05 — no longer RP-eligible), a casual user adding a chain by mistake (gate).
- The reseed writes only compiled-in seeds under the restored profile's deletion fence and never touches the shared node cache; nothing from the backup selects an endpoint. The `chainId` remap gives the narrower guarantee that imported data cannot define the destination network or endpoint — a backup author can still relabel an account-state item's `chainId` to a seeded chain (the backup is not authenticated provenance; the account-state restore's existing bounded validation applies), and `active-chain-id` can only choose among seeded rows.
- Fail-closed: unknown slice keys reject the whole backup; unseeded chains drop their rows with a visible report; zero seeds roll the import back.
- The RP ID change alone does not create extension-origin binding (the master is still PRF-derived); it narrows eligible origins to a host that serves no script. Landing it after real passkey wallets exist would brick them — the batch is ordered before release.
- Supply chain: no new dependencies. Crypto: no algorithm or vector change.

## Assumptions
**Facts (verified in recon.md):** (1) `IMPORT_BLOCKING_ACK` acknowledges migration versions only and `realMigrations` is empty; (2) `normalizeBackupData` rejects unknown keys before migrations; (3) the only live "Add network" opener is `networks/index.vue:54`; (4) every RP-ID reader goes through `RP_ID`, and `check-rp-id` re-derives the manifest expectation; (5) account-state items carry `networkId` and are matched by id in `AccountStateService.restore`; (6) `getOrInitNetworks` seeds the ACTIVE profile only, so a restore-time reseed needs a profileId-parameterized entry point.
(7) transaction rows carry `chainId: number` (`transaction/spec.ts:99`) beside `networkId?`, so the chain-keyed remap covers them; (8) `captureRestoreEpochs`/`assertRestoreEpoch` (`restore-fence.ts:19,35`) are the non-active-profile fence every service `restore` uses, and `activateSeededLocked` writes the active pointer through `_writeActive(profileId, …)`, so the reseed can activate the primary seed for the restore target without the profile being active.
**Inferences:** (a) Firefox/Chrome treat `passkey.nulo.sh` as a valid RP ID for the extension with the matching host permission exactly as they treat `nulo.sh` today — the mechanism is identical (Chrome-sanctioned host-permission RP use, per the verified finding).
**Asks — resolved by codex round 1 (`audit-codex.md`):** A. keep the chain-keyed remap + `active-chain-id`, treated as an untrusted preference (strict numeric membership, chain `0` included); B. keep fail-closed rejection of old backups (no compatibility requirement pre-production; tolerate-and-strip is not insecure, just unneeded); C. remove the four `backup`/`restore` overrides now (the base class supplies null defaults — no contract rewrite); D. creation-only gate is right (a UX gate, not authorization) — existing custom rows stay manageable, asserted; E. no `.well-known/webauthn` (host-permission RP authorization, not related-origin); F. registry edits only — `IMPORT_BLOCKING_ACK` records migration versions and the real list is empty. None open.
