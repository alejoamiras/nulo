## 2026-09-14 — blueprint codex round 2
Verdict `reject`, three blocking + three should-fix, all adopted. The blocking one that mattered: NO_FROM operations never get an estimate in the popup (only the fee handler schedules one; embedded ops hide the fee card) while confirm discovers AND signs — so a preview-snapshot guard alone would have rejected every NO_FROM transaction that needs a witness. Fix: a `previewOperationAuthwits` RPC that builds the same request confirm builds and runs the same discovery WITHOUT signing, scheduled at popup init, with the guard applied only to popup-approved executions (the silent path carries no interaction). The others: releasing a reservation on transport termination would free the counter while the OS window stays open (a tab close terminates the transport, not the window) — only unopened reservations release on termination; the fresh branch needs an explicit contract (await admission before the durable session write, keep the dedupe promise pending, release on a rolled-back approval); snapshots evict through the existing `evictStash` cancel hook; the admission tests promised three immediate approvals under a two-slot cap; `AddressDisplay` trims unless `full`. Codex withdrew its Ask-F request (plain action rows) on the fable evidence. Lesson: every guard added at confirm needs its positive control traced from the popup's first render — "which call produces the thing the guard compares against, and for which operation kinds?"

## 2026-09-14 — Phase 1 (F-16 + F-02(c)) implemented
Gate green: extension typecheck, `dapp-interaction` + `execution` + `execute` window + composables suites (83 files), wallet-bridge, biome. Shape as planned with three decisions made at the keyboard: (1) the execution service reaches the stored request through a narrow `InteractionOperationSource` looked up lazily by service name at first use — the dApp-interaction service depends on execution, so an init-time lookup would be a cycle; (2) a non-fingerprintable operation binds the snapshot on `(interactionId, index)` alone (a null fingerprint on either side matches) rather than aborting every confirm of an exotic-argument request; (3) the NO_FROM fingerprint JSON-round-trips witnesses, capsules and extras before encoding, because the same value is a class instance in-process and a plain object over the RPC and both must hash alike. One test wrinkle: the routed negative must run on `Object.create(ExecutionService.prototype)` — a bare object loses `dispatchOperation` and the test fails for the wrong reason.

## 2026-09-15 — Phase 3 (F-18) implemented; full sweep green
Gate: wallet-sdk suite (17 files / 144 tests), `audit:vue`, `test:ci-gating`, smoke on two shards of the armed build (16 + 16 files), the ten network cells in one sandbox run — nine ran green including the new `session-reconnect-flood` (30 s: two windows, third on close, fourth after the refill); `tx-sendTx-delegated-authwit` skipped on its own `hasStandardContracts` guard (the sandbox fixture, not this change). Design notes from the keyboard: (1) `admit` takes `consumesToken` beside `needsWindow` — the plan's bucket is for remembered-session handshakes, so a fresh connect (a user click) and a dedupe waiter reserve a window but spend no token; (2) an admitted-but-never-established reservation would hold a slot for the worker's lifetime (the SDK never terminates a session it never created), so the gate reclaims unstarted reservations at the discovery deadline plus a 10 s grace — the grace covers an honest key exchange that straddles the 55 s cutoff; (3) `handleSessionEstablished` fails closed when a window is due and no reservation exists — the cap is enforced only at admission, so an uncounted window is a bug, not a fallback; (4) three test scenarios were wrong on first run, not the gate: two assumed refills past the 55 s deadline would still serve (they expire), one established a session under a different chain than it was written for (the row lookup missed, the reservation was released as "no window needed").
