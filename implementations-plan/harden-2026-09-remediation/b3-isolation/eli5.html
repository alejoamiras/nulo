Harden B3 Isolation

The third of four batches fixing the 2026-09-13 security audit. Four fixes, all about keeping one profile's secrets, records and messages out of another's reach — and one honest new state for a wallet whose keys cannot be verified.

What this batch fixes

  • F-06. Two profiles created from the same recovery phrase derived the same dApp-session signing key and could derive each other's local database key. A second secret each profile owns (its data-encryption key, the DEK) is now mixed into both derivations. A session whose DEK cannot be verified enters recovery mode: chain data and dApp sessions are unavailable, a persistent banner says so, and backup export plus restore remain open as the repair path — including for passkey profiles, which have no recovery phrase.
  • F-07. Authorization-witness records carried only an address, so importing a doctored backup, cleaning up a sibling profile, or syncing another chain could delete or read a different profile's records. Every record now carries its profile and chain, and every read, purge, sync and restore is scoped by that triple — including the two racy paths the audit found (a sync that deletes whatever row holds an id after waiting for the node; a transaction-hash reconciliation that never looked at ownership).
  • F-11. The popup could call seven operation-journal methods with no ownership check. It can now call two reads, both filtered to the active profile, and the journal's live events are filtered the same way; the writes are unreachable from the popup.
  • F-14. The service-worker side of the offscreen transport accepted messages from any same-extension sender. Both directions now verify the sender: requests only from the wallet's background context, responses only from the offscreen document. No transport rewrite — a same-extension page can still stand up its own offscreen-URL context, which is the audit's documented boundary.

What resets once

The new key derivations mean every local encrypted chain store and every stored dApp session is unreadable under the old keys; legacy authorization records without a profile are hidden. There are no production users, so this redefines the launch baseline: reinstall the local extension once. No migration.

What the audits changed

Two independent reviews (Codex and a same-family audit) rejected the first draft on the same point: once the DEK matters, a corrupted DEK slot would have had no repair path — export refused it and pointed at a password change, the password change refused it and pointed at export, and passkey profiles had nothing at all. Export and passkey restore now tolerate a broken slot with a fresh key and say exactly what is lost. Codex then walked the repair path end to end through three more rounds: the backup assembler had to survive recovery mode, an already-open chain runtime had to be gated on the service-worker side rather than by an asynchronous toggle, the generic PXE error wrapper had to let the recovery error through, and cleanup calls had to stay allowed. Round four approved.

Phases and how each proves itself

1 · Keys and recovery mode

The two derivations, the recovery-mode surface, the tolerant export and restore, the service-worker admission guard, the vector pin.

Profile and chain on every row; scoped reads, purges, syncs, restore, dedup and live events.

Two reads at the RPC boundary, filtered events, the Tokens view compare.

Gate: operation-journal · general modules suites · lint · typecheck

4 · Offscreen transport and full sweep

Sender checks in both directions, then everything.

Gate: extension-messaging · bun run audit:vue · smoke e2e (armed build, two shards) · CI-gating tests · eight network cells in one local sandbox run. Full network suite on the PR in CI.
