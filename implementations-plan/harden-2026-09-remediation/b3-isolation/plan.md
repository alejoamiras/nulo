## Summary

Four isolation fixes. Two same-master sibling profiles no longer share the dApp-session MAC key or can derive each other's PXE store key: the profile DEK is mixed into both derivations, so a session that has no DEK (a tampered or corrupt DEK slot — "degraded") can neither open the PXE store nor sign or verify dApp sessions; that state gets an honest, persistent surface instead of the current toast (F-06). Auth-registry rows gain `(profileId, chainId)` and every read, purge, sync, dedup and backup path is scoped by the `(profileId, chainId, account)` tuple, so a hostile backup, a sibling profile's reconcile or a cross-chain sync can no longer purge or read another profile's authwits (F-07). The operation journal's popup-reachable surface shrinks to two reads, both filtered to the active profile at the RPC boundary (F-11). The service-worker side of the offscreen transport and its READY/PONG listeners verify the sender, with responses accepted only from the offscreen document itself; no Port refactor (F-14). No storage migration (pre-production: the change redefines the launch baseline — local PXE stores, dApp sessions and legacy authwit rows reset once).

## Architecture & Implementation (compact)

- **F-06 derivations.** One exported primitive in `packages/wallet-crypto` — `deriveKeyFromMasterAndDek(master, dek, { salt, info, usage })` — owns the 32+32 concatenation, the length asserts, the HKDF-SHA256 import and the `zeroize` of the IKM copy exactly as `entropy-mac.ts:61-83` `macKeyV3` does today; `macKeyV3` is re-expressed on it (the envelope-MAC vectors in `entropy-mac.test.ts` pin it byte-identical). `derivePxeStoreKey(master, dek, profileId)` (label → `nulo:pxe-store:v2`, profile-bound salt kept). New `deriveDappSessionMacKey(master, dek)` in wallet-crypto (non-extractable HMAC, `v2` salt/info); `profile/service.ts` `deriveDappSessionMacKey(profileId)` fetches `getSecret` + `getDek` and THROWS a typed `RecoveryModeError` when the DEK is absent — so `mac-storage.ts` `verifyOrDrop` takes its hide-not-delete branch (`:92-99`) and rows survive a later good unlock; every signing site behind `patchSession`/`addDappSession` maps that error the way the fence's "Wallet is locked" is mapped today. `runtime.ts` `providePxeStoreKey` fetches `getProfileDek` and THROWS the same error (never `undefined`): the PXE client awaits the provider outside its retry `try`, so the message reaches the caller as itself, not as the `PXE_STORE_KEY_MISSING` marker; the master copy is zeroized after derivation. `pxe/service.ts` `provisionChainStoreKey` rejects a same-generation re-provision whose bytes differ (a DEK-dependent key must never swap under an open store).
- **F-06 lifecycle.** The fresh-DEK mint at password change (`profile/service.ts:1030-1033`) is removed: with the DEK load-bearing, a mint would rotate the PXE key (→ `WrongStoreKeyError`, caught nowhere) and invalidate every session tag; the branch refuses with the message the sibling branch already uses ("export a full backup and restore it"). Invariant: the DEK never rotates within an incarnation; restore mints a fresh one for a fresh profile (unchanged).
- **F-06 degraded UX (ask A).** `ProfileInfo` gains `recoveryMode: boolean` (`session.dek === undefined`, set in the session manager's projection — a wire field, not storage); the popup's `onImportedKeysDegraded` toast copy becomes "Wallet keys need recovery — export a backup and restore it", and Home renders a persistent `Banner` while `recoveryMode` is true, so a popup opened after the unlock still sees it. Backup and recovery-phrase export stay reachable (they need only the master); every PXE-backed action surfaces the one recovery-mode sentence through the existing `lastError` paths. Blocking the profile outright is rejected: export must remain the repair path. A restore that lands degraded ends on the existing finished-with-errors screen (honest, not silent).
- **F-07 rows and scoping.** `Authwit` gains required `profileId: string`, `chainId: number`; the status key becomes a delimiter-safe tuple id (mirror `account/spec.ts` `accountRowId`). RPC: `getAuthwits(chainId, account)`, `getRegistryEnabled(chainId, account)`; the write RPCs keep `networkId` and derive `chainId` through the owned network; `profileId` is never a popup parameter — always the active profile. Service: `assertWithinCap`, `recordPendingAuthwits` (stamped from `sent.fence.profileId` + `sent.network.chainId` at `dapp-send-executor.ts:398-417`), `revokeAuthwits` (tuple ownership), `syncAuthwits` (scoped read — the cross-chain false delete disappears by construction), `syncStatus`, `backup` (active profile), `purgeForAccounts(scopes, profileId)` mirroring `token-balance/service.ts:573-598`, new `purgeForProfile(profileId)` and a chain-purge subscriber, `restore` (forces `profileId` to the threaded id; dedup key `(profileId, chainId, account, hash)` so a same-address sibling's row no longer blocks a restore). Registration: drop the address-only `onAccountDeleted` listener; register `accountService.registerAccountPurgeSubscriber` (awaited before the row delete) and `networkService.registerChainPurgeSubscriber` (the `deleteNetwork` path never runs the account subscribers). `profile-deletion/coordinator.ts:120` → `purgeForProfile(profileId)`. Backup import: the provenance filter tightens to the `(chainId, account)` tuple like the tx filter; `normalizeAllIds` already rewrites the new field. UI: the authwits page passes `network.chainId`. Legacy rows without provenance are kept-but-hidden by the codec (no sweep, no migration; reinstall locally).
- **F-11 journal.** `rpcMethods` shrinks to `getOperation`, `getOperations` (the three writes plus `createOperation`/`countOperations` have no popup caller — `countOperations` is in-process only; recon grep). The ownership gate lives at the RPC boundary — the journal overrides `invoke` (reached only from the Port path) to return `undefined`/active-profile rows only, `[]` when locked, existence non-disclosing like `execution-lane.ts:162-176` — NOT in the method bodies: the reaper and GC sweep every profile in-process, and claim/dApp paths read rows whose profile may not be active. `TokensView.vue:52` adds the profile compare (mirror `RecentActivityView.vue:279-291`).
- **F-14 transport (ask B).** Sender checks, no Port. `offscreen/client.ts` listener takes `(message, sender)` and consults a protected `isAcceptedSender` (default `isTrustedInternalSender`); the extension's PXE client overrides it to require `sender.url` to start with the offscreen document URL (Firefox's `?instance=` suffix passes the prefix), which is what actually denies a forged response from a compromised popup. READY/PONG get the same exact-URL check; ADOPT keeps its predicate; the offscreen PING listener gains `isTrustedInternalSender` for symmetry. A Port would not add confidentiality against the stated attacker (any same-extension page can `onConnect`), and the refactor touches ~1,500 lines for a Low.
- **Alternatives not taken:** `profileId` alone in the KDFs (a shared-master holder still derives it); a re-key path on DEK mint (bigger than refusing); gating journal writes on the active profile (breaks background execution for a switched-away profile); wipe-on-`WrongStoreKeyError` (a destructive action on an error path is not a pre-production reinstall); scoping `reconcileAuthwits(txHash)` (hashes are chain-unique and the row carries its tuple).

## Security & Adversarial Considerations
- Threat model: a sibling holding the shared master (F-06 — now also needs the victim's DEK, in memory only while unlocked and sealed under the passhash at rest), a hostile backup author and a sibling's reconcile/deletion/sync (F-07 — confined to the tuples it imported or owns), a compromised or buggy popup (F-11 — two reads, active profile only, no writes), a foreign extension or content script and a compromised same-extension page (F-14 — denied at every listener; forged responses need the offscreen URL).
- Still trusted, by documented boundary: service-worker memory and WebCrypto; the selected chain's node in `isAuthwitConsumable` (B1 pins which node, not its honesty); every in-process journal caller and the reaper's cross-profile sweep; any same-extension page can still passively read the broadcast store key (accepted; a Port does not change that).
- New exposure, owner-accepted: a storage writer who corrupts `dekSealed` now denies the whole profile (recovery mode) instead of only imported accounts; export and restore remain the repair path.
- Fail-closed everywhere: a missing DEK throws (hide, never a wrong key); unscoped reads return nothing; a foreign sender is ignored; a differing re-provision is rejected.
- Crypto: HKDF-SHA256 via WebCrypto only; new labels are versioned (`v2`); V11 is regenerated deliberately with the reason in the commit; no new dependencies.

## Assumptions
**Facts (verified in recon.md / outline-fable.md):** (1) `getDek` returns `undefined` for a degraded session and degraded sessions never persist a bearer; (2) `verifyOrDrop` hides on a `keyFor` throw and deletes on a MAC mismatch; (3) the PXE client awaits the key provider outside its retry `try`; (4) every internal journal writer holds the service instance and no popup code calls the three writes or `createOperation`; (5) `registerAccountPurgeSubscriber` is awaited before row deletion and `deleteNetwork` runs only the chain-purge subscribers; (6) no SW↔offscreen Port exists; `isTrustedInternalSender` admits every same-extension page; (7) `normalizeAllIds` rewrites any `profileId` field in an imported backup.
**Inferences:** (a) `sender.url` is populated for Chrome offscreen documents and Firefox hidden windows so a prefix match on the offscreen URL is reliable — verified at Phase 4 with the existing `deliver` harness plus a manual check in both browsers; (b) `EntityStorage`'s codec keeps-but-hides legacy authwit rows that fail the stricter schema, and `recordPendingAuthwits`'s `nextId` overwriting a hidden key is harmless debris replacement — verified at Phase 2.
**Asks (to codex and the fable audit):** A. degraded-session UX as specified (throwing provider + toast copy + `recoveryMode` banner, export stays reachable) vs blocking the profile; B. sender checks only vs a Port for provisioning; C. journal: removing `createOperation`/`countOperations` alongside the three writes; D. removing the DEK mint at password change (refuse) vs a re-key path; E. `coordinator.ts:120` → `purgeForProfile` vs the seed's "pass profileId"; F. the shared dual-secret helper vs leaving `macKeyV3` untouched; G. legacy authwit rows hidden-by-codec vs swept; H. `reconcileAuthwits(txHash)` left unscoped.
