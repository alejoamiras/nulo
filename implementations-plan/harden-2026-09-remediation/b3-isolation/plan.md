## Summary

Four isolation fixes. Two same-master sibling profiles no longer share the dApp-session MAC key or can derive each other's PXE store key: the profile DEK is mixed into both derivations, so a session that has no DEK (a tampered or corrupt DEK slot — "degraded") can neither open the PXE store nor sign or verify dApp sessions; that state gets an honest, persistent surface instead of the current toast (F-06). Auth-registry rows gain `(profileId, chainId)` and every read, purge, sync, dedup and backup path is scoped by the `(profileId, chainId, account)` tuple, so a hostile backup, a sibling profile's reconcile or a cross-chain sync can no longer purge or read another profile's authwits (F-07). The operation journal's popup-reachable surface shrinks to two reads, both filtered to the active profile at the RPC boundary (F-11). The service-worker side of the offscreen transport and its READY/PONG listeners verify the sender, with responses accepted only from the offscreen document itself; no Port refactor (F-14). No storage migration (pre-production: the change redefines the launch baseline — local PXE stores, dApp sessions and legacy authwit rows reset once).

## Architecture & Implementation (compact)

- **F-06 derivations.** One package-private helper in `packages/wallet-crypto` owns the shared block of `entropy-mac.ts:64-71,79-82` — the 32+32 length asserts, the concatenation, the HKDF base-key import and the `zeroize` of the IKM copy — and returns the HKDF base key; each site keeps its own `deriveKey`/`deriveBits` call inline. `macKeyV3` is re-expressed on it (the envelope-MAC vectors in `entropy-mac.test.ts` pin it byte-identical). Exported: only the concrete derivations — `derivePxeStoreKey(master, dek, profileId)` (256-bit bytes; label → `nulo:pxe-store:v2`, profile-bound salt kept) and the new `deriveDappSessionMacKey(master, dek)` (non-extractable HMAC key, `v2` salt/info). `profile/service.ts` `deriveDappSessionMacKey(profileId)` fetches `getSecret` + `getDek`: locked keeps throwing "Profile locked"; an OPEN session with `dek === undefined` throws a typed `RecoveryModeError` — so `mac-storage.ts` `verifyOrDrop` takes its hide-not-delete branch (`:92-99`) and rows survive a later good unlock; signing sites let that error propagate unchanged (its message is the surface; it is not folded into "Wallet is locked"). `runtime.ts` `providePxeStoreKey`: locked → `undefined` (today's contract — the PXE client rethrows its marker to background pollers); open but degraded → throws `RecoveryModeError` (the client awaits the provider outside its retry `try`, so the message reaches the caller as itself); the master copy is zeroized after derivation. `pxe/service.ts` `provisionChainStoreKey` rejects a same-generation re-provision whose bytes differ.
- **F-06 warm PXE.** Store keys and runtimes survive lock and profile switch by design (offscreen side), so a degraded re-unlock would never consult the provider and an already-open chain runtime would serve new work. Admission is therefore gated on the SERVICE-WORKER side, where the session state lives: `PxeServiceClient.request` (the app-side subclass of `PxeServiceClientBase`, the same seam that owns the missing-key recovery) consults a recovery guard registered by the runtime beside the store-key provider — `profileService.isRecoveryMode(profileId)`, a synchronous read of the active session's `dek === undefined` — for every OPERATIONAL profile-bound method BEFORE sending, and throws `RecoveryModeError`; the cleanup calls (`clearChainState`, `clearProfileState`) are exempt so a profile in recovery mode can still be purged. No new RPC, no toggle, no offscreen round-trip and no ordering race: the session state is set before `openSessionVerified` returns and before any unlock event publishes, so a request issued immediately after a degraded unlock against an already-open chain is rejected in the SW; already-admitted offscreen work finishes; a healthy re-unlock admits again. Popups reach PXE only through SW services, which all use this client.
- **F-06 lifecycle and the repair path.** The fresh-DEK mint at password change (`profile/service.ts:1030-1033`) is removed: with the DEK load-bearing, a mint would rotate the PXE key (→ `WrongStoreKeyError`, caught nowhere) and invalidate every session tag; the branch refuses. That refusal is safe only with a real repair path, and both audits showed there is none today once the DEK matters: `exportBackupMaterial` refuses an undecryptable slot and points at password change (`:1802`), and `restorePasskeyProfile` throws on an unopenable blob (`:2420`) while passkey profiles have no phrase. So: `exportBackupMaterial` exports a FRESH `generateImportedKeysDek()` when the slot will not unseal (the export comment at `:1795-1801` already argues exporting cannot leak; imported-key rows then fall into the restore-side orphan taxonomy); `exportPasskeyCredential` (`:1708-1715`) keeps its credential and fingerprint checks but, when the probe fails, seals a fresh DEK under the ceremony's wrap key already in hand and carries that `dekSealed` instead of refusing; `restorePasskeyProfile` tolerates an unopenable `dekSealed` (fresh destination DEK, no rewrap stash); and both the refusal and the two export paths say exactly what is lost (imported keys and local chain state) and what to do (export a full backup, or the recovery phrase on a password profile, then restore). The full-backup assembly must also succeed in recovery mode: `AccountStateService.backup()` catches `RecoveryModeError` per network and omits that network's contract/sender state the way it already omits a non-Active network (logged, and surfaced in the export flow's loss warning) — the assembler itself swallows nothing else. `viaPxe` (`account-state/service.ts:140-145`) today replaces every exception with `Error("PXE request failed")`, so it must let `RecoveryModeError` through unchanged (rethrow by type) or the catch never matches. The passkey export returns the replacement `dekSealed` to the popup in the authenticated export result (today `exportPlain` returns only the credential id and the popup fetches the stored blob separately, `export/full.vue:177-180`); the popup writes that blob into the file and the source profile row is never modified. Invariant: the DEK never rotates within an incarnation; a restored profile mints a fresh one (unchanged).
- **F-06 degraded UX (ask A).** `ProfileInfo` gains `recoveryMode?: boolean` (`session.dek === undefined`), set in `getProfileInfo`/`getActiveProfile` (the projection every popup read uses, `service.ts:497`) and in the session manager's `toInfo`, and excluded from the persisted `Profile` and the backup's profile slice; the popup's `onImportedKeysDegraded` toast copy becomes "Wallet keys need recovery — export a backup and restore it", and Home renders a persistent `Banner` while `recoveryMode` is true, so a popup opened after the unlock still sees it. Backup export (with the fresh-DEK tolerance above) and recovery-phrase export stay reachable; every PXE-backed action surfaces the one recovery-mode sentence through the existing `lastError` paths. Blocking the profile outright is rejected: export must remain the repair path. A restore that lands degraded ends on the existing finished-with-errors screen (honest, not silent).
- **F-07 rows and scoping.** `Authwit` gains required `profileId: string`, `chainId: number`; the status key becomes a delimiter-safe tuple id (mirror `account/spec.ts` `accountRowId`). RPC: `getAuthwits(chainId, account)`, `getRegistryEnabled(chainId, account)`; the write RPCs keep `networkId` and derive `chainId` through the owned network; `profileId` is never a popup parameter — always the active profile. Service: `assertWithinCap`, `recordPendingAuthwits` (stamped from `sent.fence.profileId` + `sent.network.chainId` at `dapp-send-executor.ts:398-417`), `revokeAuthwits` (tuple ownership), `syncAuthwits` (scoped read — the cross-chain false delete disappears by construction), `syncStatus`, `backup` (active profile), `purgeForAccounts(scopes, profileId)` mirroring `token-balance/service.ts:573-598`, new `purgeForProfile(profileId)` and a chain-purge subscriber, `restore` (forces `profileId` to the threaded id; dedup key `(profileId, chainId, account, hash)` so a same-address sibling's row no longer blocks a restore), `recordPendingAuthwits` allocating ids over the physical keys (`getKeys()`, as `restore` does — a codec-hidden key may hold a damaged current-format row, not disposable debris). `syncAuthwit` captures the operation's profile/chain once and, after the node await, re-reads the row under the lock and deletes only if its `(profileId, chainId, account, hash)` and `pending` still match the captured row (a purge + restore during the await can hand the numeric id to another tuple). `reconcileFromTx` threads `tx.profileId/chainId/account` into `reconcileAuthwits`, which matches them with the hash and skips a tx without provenance. `assertWithinCap` takes `ctx.network.profileId/chainId` (already on the owned network row; no `BuildContext` widening). Registration: drop the address-only `onAccountDeleted` listener; register `accountService.registerAccountPurgeSubscriber` (awaited before the row delete) and `networkService.registerChainPurgeSubscriber` (the `deleteNetwork` path never runs the account subscribers). `profile-deletion/coordinator.ts:120` → `purgeForProfile(profileId)`. Backup import: the provenance filter tightens to the `(chainId, account)` tuple like the tx filter; `normalizeAllIds` already rewrites the new field. UI: the authwits page passes `network.chainId`, its list predicate compares the full tuple on live events, and the enabled/disabled events carry the tuple. Legacy rows without provenance are kept-but-hidden by the codec (no sweep, no migration; reinstall locally).
- **F-11 journal.** The popup surface shrinks to `getOperation`, `getOperations`: `rpcMethods`, the `Methods` type (`defineRpcMethods` is exhaustive over it) and the five client wrappers are pruned together (a popup `createOperation` would let it forge journal history). The ownership gate lives at the RPC boundary — the journal overrides `invoke` (reached only from the Port path; delegates to `super.invoke` for the framework methods) to return `undefined`/active-profile rows only, `[]` when locked or when no `ProfileService` is wired (fail closed), existence non-disclosing like `execution-lane.ts:162-176` — NOT in the method bodies: the reaper and GC sweep every profile in-process, and claim/dApp paths read rows whose profile may not be active. Wire EVENTS are gated the same way: the journal filters its Port emits (`onOperationAdded/Updated/Deleted`) to records owned by the active profile, in-process events untouched — a background operation of a switched-away profile otherwise broadcasts its ids, metadata, errors and timing to every connected popup. `TokensView.vue:52` adds the profile compare (mirror `RecentActivityView.vue:279-291`). Documented limits: size-dependent scan timing and a popup's own storage privileges remain (no constant-time machinery for a Low).
- **F-14 transport (ask B).** Sender checks in BOTH directions, no Port. Responses: `offscreen/client.ts` listener takes `(message, sender)` and consults a protected `isAcceptedSender` (default `isTrustedInternalSender`); the extension's PXE client overrides it to require `sender.url` to be the offscreen document URL (exact path compare, query allowed for Firefox's `?instance=`; `sender.tab` permitted because Firefox's hidden-window document is tab-hosted). Requests: `offscreen/service.ts` accepts a request only from the wallet background context (Chrome: `sender.url` equal to the service-worker script URL; Firefox: the background page URL) — otherwise a compromised popup that observed `{from, requestId}` can send its own request under those identifiers and have the GENUINE offscreen settle the victim's pending call with a reflected response. READY/PONG get the same exact-URL check; ADOPT keeps its predicate; the offscreen PING listener gains `isTrustedInternalSender` for symmetry. What this buys and does not: it closes foreign extensions, content scripts, ordinary popup URLs and the reflected-response route; a compromised same-extension page can still open or embed the offscreen URL and forge from that context — F-14 stays Low by its documented boundary (`sender-auth.ts:4`), not by these checks. A Port would not change that (any same-extension context can `onConnect`) and the refactor touches ~1,500 lines. `sender.url` semantics are verified with positive controls in both browsers at Phase 4.
- **Alternatives not taken:** `profileId` alone in the KDFs (a shared-master holder still derives it); a re-key path on DEK mint (bigger than refusing + a tolerant export); gating journal writes on the active profile (breaks background execution for a switched-away profile); wipe-on-`WrongStoreKeyError` (a destructive action on an error path is not a pre-production reinstall); leaving `reconcileAuthwits(txHash)` unscoped (fable's "over-claiming is the safe direction" — rejected because the tuple is already on the tx row and an exception to the batch invariant is not worth an argument); a `{salt, info, usage}` derivation helper (one abstraction more than three callers need).

## Security & Adversarial Considerations
- Threat model: a sibling holding the shared master (F-06 — now also needs the victim's DEK, in memory only while unlocked and sealed under the passhash at rest; with an unknown DEK no offline derivation from the master remains, while a holder of the victim's full-backup material holds its DEK and is outside the guarantee), a hostile backup author and a sibling's reconcile/deletion/sync (F-07 — confined to the tuples it imported or owns, including the stale-sync and tx-hash paths), a compromised or buggy popup (F-11 — two reads and the wire events filtered to the active profile, no writes), a foreign extension or content script and a compromised same-extension page (F-14 — denied at every listener in both directions; a forged response now needs a same-extension context at the offscreen URL, which the stated attacker can still create).
- Still trusted, by documented boundary: service-worker memory and WebCrypto; the selected chain's node in `isAuthwitConsumable` (B1 pins which node, not its honesty); every in-process journal caller and the reaper's cross-profile sweep; a same-extension page's storage privileges, size-dependent scan timing, its ability to read the broadcast store key or to stand up an offscreen-URL context (accepted; a Port does not change that; ADOPT's no-tab predicate also admits a popup).
- New exposure, owner-accepted: a storage writer who corrupts `dekSealed` OR `envelopeMac` now puts the whole profile in recovery mode (PXE and dApp sessions unavailable) instead of degrading only imported accounts; the tolerant export, the recovery phrase (password profiles) and restore remain the repair path, and the messages say what is lost.
- Fail-closed everywhere: a missing DEK throws (hide, never a wrong key); recovery mode rejects new PXE admission even with warm keys; unscoped reads return nothing, and so do reads without a wired `ProfileService`; a foreign or wrong-direction sender is ignored; a differing re-provision is rejected; a sync deletes only the row it captured.
- Crypto: HKDF-SHA256 via WebCrypto only; new labels are versioned (`v2`); V11 is regenerated deliberately with the reason in the commit; no new dependencies.

## Assumptions
**Facts (verified in recon.md / outline-fable.md):** (1) `getDek` returns `undefined` for a degraded session and degraded sessions never persist a bearer; (2) `verifyOrDrop` hides on a `keyFor` throw and deletes on a MAC mismatch; (3) the PXE client awaits the key provider outside its retry `try`; (4) every internal journal writer holds the service instance and no popup code calls the three writes or `createOperation`; (5) `registerAccountPurgeSubscriber` is awaited before row deletion and `deleteNetwork` runs only the chain-purge subscribers; (6) no SW↔offscreen Port exists; `isTrustedInternalSender` admits every same-extension page; (7) `normalizeAllIds` rewrites any `profileId` field in an imported backup.
**Inferences:** (a) `sender.url` is populated for Chrome offscreen documents and Firefox hidden windows (tab-hosted there) and for the Chrome service worker / Firefox background page, so exact-path matching on those URLs is reliable — verified at Phase 4 with positive controls in both browsers, recorded in lessons; (b) `EntityStorage`'s codec keeps-but-hides legacy authwit rows that fail the stricter schema; a codec-hidden key may hold a damaged current-format row, so id allocation reserves every physical key (`getKeys()`) — verified at Phase 2.
**Asks — resolved by the dual audit (`ledger.md`):** A. throwing provider (open-but-degraded only) + toast + `recoveryMode` banner + tolerant export, profile not blocked; B. sender checks in both directions, no Port, claim corrected; C. `createOperation`/`countOperations` removed too, `Methods` and the client pruned; D. mint removed, password change refused, repair path restored through the tolerant export and passkey restore; E. `purgeForProfile`; F. the narrow package-private base-key helper; G. hidden-by-codec, no sweep, id allocation over physical keys; H. reconciliation scoped by the tx's tuple (codex over fable). None open.
