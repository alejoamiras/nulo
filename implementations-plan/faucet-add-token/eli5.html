Faucet "Add to Wallet" — ELI5

A button on the faucet that one-clicks the dripped USDC / ETH into the user's wallet popup — like Metamask's "Add Token" but for our Aztec extension. Here's what's happening, in plain language.

The shape of the problem

When you drip USDC from the faucet, the tokens land in your Aztec account — but the Nulo wallet popup doesn't know to show them. Today you have to copy the USDC contract address from somewhere, open the wallet, click "Add token", paste, confirm. Four steps. Most users give up.

EVM wallets solved this with wallet_watchAsset — a tiny RPC method the dApp calls. We want the same thing for Aztec, hitting our Nulo extension over the wallet-sdk channel that's already wired up.

The good news (most of it is built)

Recon found that the extension side is already wired:

  • Our dispatcher knows how to receive a registerToken RPC.
  • The execution service knows how to add the token to the user's list, with origin tracking ("Requested by faucet.nulo.app").
  • The popup knows how to render a confirmation card for it.
  • The capability system already gates it under the "accounts" permission.

So why doesn't it work today?

The catch

The standard @aztec/wallet-sdk library — used by dApps to talk to wallets — has a strict allowlist of methods. Anything not in WalletSchema gets rejected on both ends of the encrypted channel. Our registerToken isn't in the allowlist.

An earlier version of our code added it back via a small "schema patch" — but that was deleted during a cleanup pass ("dropped in the canonical refactor"). So today, the dispatcher's registerToken code path is literally unreachable. It's like having a working light bulb but the switch isn't wired to anything.

What we're doing about it

1. Re-add the missing switch (the "schema patch")

A tiny file that says "hey wallet-sdk, registerToken takes two addresses and returns nothing." Drop it on both sides — extension and faucet — and the existing wiring lights up.

Why two copies, not a shared package? It's literally one Zod entry. A shared package would expose @nulo/wallet-bridge to outside dApps, which we don't want yet. A unit test pins the shape on both ends.

2. Drop the dead RPCs we'll never use

Two other old methods (getCompleteAddress, simulateViews) are also dead today. We delete the dApp-facing wiring for both, but keep simulate_views as an internal operation — the wallet's balance projector still uses it under the hood.

Why now? Less surface = fewer footguns. If we're touching this layer anyway, this is the moment.

3. Add the button

Each token card on the faucet (USDC, ETH) gets an "Add to wallet" button next to the drip buttons. Click it, the extension pops up a confirmation card with the contract address. Approve → token appears in the wallet popup. Cancel → nothing happens (no error message, like Metamask).

4. Reinstate the playground tester

Our internal playground (used to dogfood custom RPCs) loses its old registerToken button. Add it back — same schema patch, same one-line button binding.

5. Test it end-to-end

Add a network e2e test that boots the whole stack (anvil + aztec sandbox + extension + faucet), simulates a user clicking the button, approves the popup, and asserts the token now shows up in the wallet popup's token list. The test runs in parallel with other agents on different worktree ports.

What could go wrong (security)

A malicious dApp could call registerToken with a fake USDC. The defenses:

  • The wallet shows a confirmation popup with the contract address. The user sees what's being added.
  • The popup also shows "Requested by <origin>" — so the user knows which dApp asked.
  • It's gated under the accounts capability — a dApp must already have been granted account access.
  • The token list is per-network and per-account, so a testnet faucet can't pollute your mainnet view.
  • Adding the same token twice silently no-ops, so spam loops can't bloat storage.

What we're not defending against in this PR: lookalike token names (a malicious "USDC" at a different address). The popup shows the address — the user is responsible for noticing. We've filed it as a follow-up.

Open questions worth your eyes

The popup confirmation today shows the contract address only. Should we also resolve and show the token name / symbol before the Allow / Deny? Cleaner UX, but it adds a second PXE round-trip before the popup renders. Filed as a follow-up — flag if you want it bundled.
Auto-fire registerToken right after a successful drip? Currently rejected (you said "user clicks the button") to avoid pop-up spam. Worth revisiting if real users don't notice the button.
Push wallet_watchAsset upstream into @aztec/wallet-sdk? Would let us delete the schema patch entirely. But it blocks on upstream review, and we want this feature now. Filed as a deferred parallel track.

What you get when this merges

  • One-click "Add to wallet" on the faucet, for USDC and ETH.
  • Playground gets its registerToken button back, so future custom RPCs have a tester.
  • Dead RPC surface (getCompleteAddress, dApp-side simulateViews) cleaned out.
  • Documentation explaining the schema-patch pattern, so the next person who sees it doesn't have to reverse-engineer it.
  • An e2e test that catches breakage on every network-suite run.
