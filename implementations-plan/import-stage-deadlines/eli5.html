Import Stage Deadlines

Make the wallet-import test wait honest: measure how long each restore step really takes, explain failures instead of timing out silently, and close the mystery of the console errors the tests could never see.

Tier: mid Codex round 1: reject → findings folded Fable: conditional approve → conditions folded Final fresh codex: conditional approve → all conditions folded

What this is about

When a test restores a wallet from a backup file, it currently waits up to five minutes for the whole thing to finish, watching only the final "success" screen. If anything goes wrong in between, the test learns nothing — it just burns the full five minutes and reports "timed out", with no clue which step got stuck. This plan keeps that five-minute limit exactly as it is (a hard rule: no limits get raised, ever), but teaches the wait to watch the steps: which stage the import is in, how long each stage took, and — when it fails — a full story of what happened.

Round 4 already shipped the progress markers. This plan is the second, final half the team's own ledger called for: measure real timing envelopes in both proving modes, then decide — honestly, from data — whether any stage deserves its own earlier deadline.

The honest surprise

Reading the code settled the deadline question before any stopwatch ran: only ONE stage has a real product-owned time budget (the chain-sync tail, 45 seconds) — and when it overruns, the app deliberately degrades and keeps going rather than failing. Both independent reviewers reached the same conclusion: adding test-side deadlines would create false alarms without catching anything new. So the plan's answer is "diagnostics everywhere, deadlines nowhere" — which the original design explicitly allows. The measurement table still gets built (it's the evidence), and the five-minute ceiling stays the only overall judge.

The console mystery — solved

A standing puzzle: tests that assert "no console errors" never saw the app's own error logs. Recon found why — it's not a bug in the tests. The wallet deliberately reroutes every page's console.* call to a central log inside its background worker, so the browser's own console never fires in the page, and the test framework (which listens to the page) structurally cannot see it. The plan confirms this with a small probe, then documents it permanently: crashes and unhandled errors ARE still caught (that channel works), the background log is readable through an existing helper when needed, and the test-suite documentation stops overpromising what "no console errors" means.

The one disputed call — and how it was settled

Should the test stop immediately when the wallet announces "this import failed" on screen, instead of waiting out the rest of the five minutes? The two first-round reviewers split (fable: yes, with guard rails; codex: no — beyond the original design's letter). A fresh third review with the full decision trail ruled no early stopping, on a new decisive fact: one of the proposed "failure" screens turns out to be a partial success the product deliberately lets the user continue from — stopping there would misread healthy-but-degraded imports as failures. So: every failure state becomes a clearly-labeled part of the timeout's story (you always learn exactly what happened and when), but nothing ends early. The five-minute ceiling stays the only judge.

Your options: accept the ruling (recommended — the diagnostics deliver nearly all the value), or overrule to early-stopping — which per the ruling first requires amending the team's design record as its own decision, recorded for later.

Phases

1

Teach the wait to watch the steps

One shared import helper gets a step-recorder (armed before the import starts, read once at the end — so nothing is missed and nothing is perturbed) and rich, labeled failure messages. Also removes a copy-pasted duplicate of the same flow. Public behavior of every existing test: unchanged.

Proves itself by: lint + typecheck + new focused unit tests for the recorder logic + the full smoke e2e suite green.

2

Measure — first leg

Repeated solo runs of the two real import tests, alternating both proving modes, no retries, recording every stage's timing into an attributed log.

Proves itself by: every run green on the first attempt; every import fully recorded.

3

Measure — complete the sample set

Keep alternating until at least five runs per proving mode exist, kept strictly separated by scenario (they measure different things — one even skips a whole stage by design).

Proves itself by: a complete per-scenario sample table, no mixing.

4

Publish the envelope table + close the ledger entry

The committed timing table with its honest caveats (solo-machine baseline, not a CI worst-case), the "no deadlines" conclusion, and the team ledger updated in place.

Proves itself by: lint green + a recorded codex verdict on the close.

5

Console truth — probe, then document

A tiny experiment proves the reroute mechanism (and that the crash-error channel still works), then the fixture comments, the testing skill, and the ledger all get the accurate story.

Proves itself by: probe evidence quoted in the log + smoke suite green.

6

Certify

Three consecutive solo runs of the three import-heavy network tests, zero retries allowed, all green on the first attempt — the same bar earlier rounds used.

Proves itself by: the recorded 3× certification + all fast checks green.
