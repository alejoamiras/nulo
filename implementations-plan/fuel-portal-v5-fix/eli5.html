Fuel-bridge Fee-Juice portal V5 fix

When you bridge tokens with fuel (swap a slice into Fee Juice so the arriving funds can pay their own gas), the gas part hangs forever — "message arrived, waiting for your wallet to sync" that never finishes. We traced it on-chain: the part of our bridge that hands Fee Juice across to Aztec was built with the address of the old (V4) Fee-Juice door. On V5, that door moved. So the Fee-Juice message gets posted to a dead door and never shows up where the wallet looks. The plain token transfer works fine because it uses a different door we deployed fresh. The fix is to point the fuel router at the new V5 door and re-deploy that one small piece.

Why this tier was chosen

Light. Rubric: only 1 high dimension — External coupling (the canonical Aztec fee-juice portal). Novelty low (we understand the surface), blast radius small (one feature path, testnet), irreversibility low (re-deployable contract, no data migration), migration cost none, security low (one constructor argument, no trust-model change). The root cause is confirmed on-chain and the fix's ABI is verified compatible, so there's no plan-space to search — single plan, single codex audit.

Phases

Phase 1: Point everything at the new V5 door + make the deploy router-only + prove it on a fork

Swap the old V4 portal address for the V5 one in the 5 places that hard-coded it (the live deploy, a sibling script, two fork tests, and the env template). Also tweak the deploy script so that — when we tell it to reuse the existing swap + pools — it really deploys only the router (today it also spins up an unused helper; codex caught this). Then run the fork test that forks the live Sepolia chain and actually pushes Fee Juice through the router into the V5 door, proving the new door works before we spend anything real.

Proves itself by: forge build compiles, and DeployFuelLive.fork.t.sol goes green — the "router points at the V5 door" assert passes AND the Fee-Juice-lands-at-the-door balance checks pass.

Phase 2: Re-deploy just the router (reuse the swap + pools)

Deploy a fresh router wired to the V5 door. Everything else — the Uniswap swap helper and the seeded liquidity pools — is untouched and reused (they don't depend on the door). Dry-run first, then broadcast, then read the deployed router back to confirm it points at the right door, the right swap, and is owned by the deployer.

Proves itself by: dry-run shows exactly ONE new contract (no swap, no helper, no re-seeding), broadcast says "ONCHAIN EXECUTION COMPLETE", and three on-chain read-backs confirm door = V5 portal, swap = existing swap, owner = deployer.

Phase 3: Smoke the candidate config → promote → prove the self-paying claim

Point the candidate faucet config at the new router + door, then run the candidate-smoke script (deployer-funded, not your wallet): a full swap → bridge → self-paying Fee-Juice claim, exactly the flow that was hanging. Only once that's green do we promote the candidate to live (the repo's safe-cutover discipline; codex flagged that testing the live file directly is backwards). We also confirm the Fee-Juice message now actually appears in the V5 inbox for that exact deposit.

Proves itself by: smoke-swap-existing-testnet.ts --config …candidate.json completes with the self-paying claim confirmed; the exact Fee-Juice message's checkpoint reads "defined" (it folded into the V5 inbox); lint clean; then candidate→live promotion.

Human context

An Aztec L1→L2 "message" (like a bridge deposit) is posted into an L1 inbox by a portal contract, then the receiving wallet claims it on L2 by its position (leaf index) in that inbox. Each rollup deployment (V4, V5) has its own portals at its own L1 addresses. Our fuel router was carried over from a V4-era reference with the V4 fee-juice portal baked in as a constant. The token portal was re-deployed fresh for V5, which is why tokens work and fuel doesn't. Crucially, the wallet's claim only needs the leaf index + secret — it doesn't care about the portal address — so once the message lands in the right inbox, the existing wallet code claims it with no change. Verified on-chain this session: the live V5 portal answers UNDERLYING() with exactly our Fee-Juice token, so the new door and the existing pools are compatible.
