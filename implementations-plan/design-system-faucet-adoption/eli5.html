Faucet adopts the shared design system

The faucet app barely uses our shared @nulo/design component library — it has its own hand-written markup almost everywhere. This plan makes the faucet reuse the shared building blocks where they genuinely fit, by adding the same auto-import "resolver" the extension uses (so templates can write a bare <Flex>/<Text> tag) and swapping hand-written layout/labels for those shared pieces — without changing how anything looks or behaves.

The honest headline (please read)

You said "we should be able to re-use a bit more." After three planning passes and three audits reading the actual files (which corrected the plan twice), the truthful answer is: yes — modestly and genuinely, and here's exactly where.

  • The real reuse is <Flex> (layout containers — the bulk), a fair amount of <Text> (labels), and likely the <Tag> status pill (which was originally lifted out of the faucet, so it should drop right back in).
  • The big brutalist forms stay hand-written. The shared Flex can't do CSS grid; the shared Input/Toggle are shaped differently (different DOM, test IDs, behavior); Text can't be a semantic heading/paragraph or carry the odd letter-spacing values. Forcing them would either break the look or require editing the shared package — both off-limits.
  • We deliberately do NOT churn the imports. Components the faucet already uses (Button, Card, etc.) stay as normal imports — turning them into bare tags would be busywork with zero reuse gain.

So the value here is: genuine-but-bounded reuse + consistency + the resolver plumbing that makes future reuse cheap — not a dramatic rewrite of the forms.

Why this tier was chosen (deep)

By the numbers it's borderline mid (only one elevated risk dimension: it touches the whole live faucet). It was run as deep at your request, justified by a known nasty failure mode on this exact surface (a past light-theme regression that slipped past every automated check). The extra ceremony paid for itself: the review rounds killed a zero-value "convert all imports" over-reach, caught a real bug that no test would have caught (a CSS rule deletion that would have left some links unstyled), corrected a false "fact" the plan was resting on, and turned an asserted "low reuse ceiling" into an evidence-based one.

Phases

Phase 1: Resolver plumbing + a real proof

Add the auto-import resolver (primitives only), a guard test that no local component name collides with it, a shared config helper so the build + both test setups stay in sync, and the lint/lockfile housekeeping. Then migrate one tiny tested swap to a bare tag — to actually prove bare tags resolve in the build AND the tests (the extension's tests don't use this plugin, so this wiring is new here and must be proven, not assumed).

Proves itself by: typecheck + lint + unit tests + a real production build all green, with the one bare-tag swap rendering correctly in tests and build.

Phase 2: Wallet + verification screens

Swap pure layout/label markup to shared primitives in the wallet panels + the emoji-verification modal. Two of the panels have no test today and are stubbed out of the smokes, so we add focused tests for them first — then the swaps are actually guarded. Security test IDs on the verification flow are left untouched.

Proves itself by: the existing + two new wallet-panel tests + the verification test stay green; build green.

Phase 3: Bridge journal / stepper / receipt

The shared bridge-progress screens — and the place we actually check the Badge candidates and adopt them where they visually match. The known "don't touch" spots (the receipt links, the empty-state box) stay hand-written for documented reasons.

Proves itself by: all five bridge-progress component tests + the smoke tests stay green; build green.

Phase 4: Forms + cards + leftover leaves

The biggest, riskiest files last (the bridge form has the most test IDs; the fuel form has no unit test so it leans on smoke tests + your eyeball). Only the clean layout rows get swapped; the bespoke inputs/toggles/mode-cards stay.

Proves itself by: the bridge-form test trio + token-card test + all three smoke tests stay green; build green.

Phase 5: Your visual sign-off (the gate machines can't replace)

Build + preview the faucet; you eyeball the light theme across all three tabs. The checklist will point at the exact spots most likely to drift (anything near a swapped wrapper, the untested fuel form, the badge adoptions). I build it, surface the checklist, and hold — I never mark this done myself.

Proves itself by: the full audit:faucet machine suite green + your explicit sign-off.

Human context

@nulo/design is the shared component package both the extension and the faucet pull from. A "resolver" is a build-time helper that lets a template use <Flex> without an import line — handy for tiny ubiquitous layout pieces. The faucet is light-themed; the shared package ships both light and dark palettes, so the pieces adapt — but a past incident proved that a missing CSS rule can break the light theme invisibly to every automated check, which is exactly why your visual sign-off is mandatory.

The alternative is converting all the faucet's existing design imports to bare tags too, purely for uniformity with the extension. I think that's churn with no payoff; flagging it in case you want the uniformity anyway.
