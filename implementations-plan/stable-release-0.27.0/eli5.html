Ship Nulo v0.27.0 — the stable release, end to end

Everything queued on the integration branch — the two-network tools, activity siloing, the fee-cap hardening, and this week's five-bug sweep — gets promoted to the stable branch, tagged v0.27.0, published as downloadable extension zips, and the landing + tools websites get refreshed. Frontend only: no smart contracts are redeployed. Most of the machinery is automation that has already shipped two releases cleanly; this plan is the checklist of guarded moments between the automated stretches.

Why the "light" tier

By the strict rubric this could be "mid" (a release is public and hard to un-ring), but the pipeline has shipped 0.24.0 and 0.26.0 with a written playbook, this plan reuses the proven 0.26.0 blueprint, and every change riding the release was already reviewed and gated on its own PR — including a dedicated adversarial audit of the fee change. One independent auditor (Codex) still reviewed this plan hard: it rejected the first draft over six real gaps (details in the plan file), and every one was fixed and re-verified before this page was shown to you.

The six phases

  1. 1Last-second state check Before touching anything, re-verify the world is as expected: the auto-release switch is on, the stable branch matches the last release, no v0.27.0 tag already exists, and the promotion PR is still green and unmoved. every check printing exactly the expected value; any surprise stops the release.
  2. 2Merge the promotion (#337) The already-green PR moves the release content to the stable branch. The merge is pinned to the exact reviewed commit — if anything moved underneath, the server refuses. a true merge commit lands on the stable branch with the pinned commit as its parent.
  3. 3Merge the version PR A bot opens "release 0.27.0" with the changelog. We confirm the number is exactly 0.27.0 (any other number stops the release), wait for the full test suite, and merge — checking the latest completed test batch, so a superseded, cancelled batch can't masquerade as a failure. all three required test suites green on the exact commit, then a pinned merge.
  4. 4Tag + publish (automated, watched) Automation tags v0.27.0, creates the release, builds the Chrome + Firefox zips, smoke-tests the actual built zip, attaches everything, and pokes the website deploys. We watch and only step in per a written recovery table (each stuck state has one prescribed action; a wrong-looking tag is a hard stop). tag points at the right commit, release lists exactly the three files, and the checksums verify after downloading them.
  5. 5Close the loop back to dev The bot's "sync main → dev" PR gets merged as a true merge (never squashed — the next release's version math depends on the ancestry). Dev stays frozen until this lands. dev shows version 0.27.0, the prerelease counter is re-baselined, and the release commit is provably in dev's history.
  6. 6Prove the live sites + wrap up The testnet tools site is verified automatically by build fingerprint; the mainnet tools site sits behind a login wall, so you spot-check it (and the "ETHEREUM" chip fix while you're there); the landing page must offer the 0.27.0 downloads. Then the plan + lessons land in the repo as a small docs PR. build fingerprints match the released commit; you confirm the mainnet site; docs PR green.

Human context

Two commits matter: the reviewed content commit (what you approved on the promotion PR) and the tagged release commit (created when the version PR merges). Every integrity check compares against the right one of these two — that distinction, plus "never squash the sync-back", is most of what past releases taught us. The publishing automation is real but has known sharp edges (a years-old bug in the release bot means it "sticks" once per release; our auto-unsticker handles it, and the recovery table covers the cases where it half-finishes).

Time expectation: roughly 1.5–2.5 hours, almost all of it waiting on two full test-suite cycles. The merges themselves are minutes.
