Source audit: audit/security/2026-06-08-ultra-e6759a/ — 12 findings, 11 in scope (F-010 deferred)

This plan implements 11 of the 12 security findings the audit surfaced — every High and every Medium except F-010 (incoming-transfer storage growth, which is significantly more expensive than the rest and was deferred for this cycle). The wallet code currently works; this work closes specific authorization holes, a passkey-binding gap, an RPC-URL trust gap, and rebuilds the transaction-approval UI so attackers can't hide what they're asking for.

Why mega-deep?

The user explicitly chose ultra. In the blueprint skill that maps to mega-deep — the heaviest planning tier. The rubric for mega-deep wants 2+ high-risk dimensions AND high novelty. This task has:

  • Security sensitivity: HIGH — every fix touches authorization, trust boundaries, or approval UX.
  • Blast radius: HIGH — wallet is self-custody; users lose money if something breaks.
  • External coupling: HIGH — F-001/F-002 partially depend on upstream @aztec/wallet-sdk.
  • Irreversibility: MEDIUM — mistakes in approval UI are user-facing immediately.
  • Novelty: MEDIUM — most fixes are well-defined patches; F-008 UX redesign is the genuinely novel part.

4 of 6 dimensions are HIGH/MEDIUM. Mega-deep was the right call.

The 11 findings in plain language

F-001 + F-002: An iframe (a page-within-a-page, like an embedded ad) currently can convince the wallet that it's the outer page. The wallet shows the outer page's URL in the approval popup, but the iframe controls the action. Fix: reject iframes from talking to the wallet by default; coordinate upstream for a deeper fix.
F-003: A dApp can request "access to your accounts" with a sub-setting that says "but don't let me read the addresses." The UI shows that setting; the code ignores it. The dApp reads the addresses anyway. Fix: actually honor the sub-setting. Hours of work.
F-004: Same shape as F-003 but for the address book ("data" capability with an addressBook sub-bit). Fix: honor it. Hours of work.
F-005: When a dApp calls certain methods, it can attach a "look at these accounts too" list. The wallet doesn't check whether those accounts were ever approved for this dApp. One approved account silently widens to all accounts. Fix: validate the list against the session's approved accounts.
F-006: When you click "Disconnect this dApp" in Settings, the wallet deletes a stored record but leaves the live encrypted channel open. The dApp keeps calling network-only methods. Fix: also kill the live channel; make missing-session calls fail closed instead of silently succeeding.
F-007: When you unlock with a passkey, the wallet doesn't check that the passkey is actually bound to the profile you're unlocking. Could open the wrong profile with wrong key material. Fix: a 4-line patch that already exists in another part of the codebase — just mirror it here.
F-008: When approving a transaction, the wallet shows "calling function X on contract Y" but hides the actual arguments (recipient, amount) behind a "View JSON" sub-link. Fix: structured argument summaries on the primary card. This is the biggest UX change in the plan and the user is rightfully nervous about it — the plan adds "don't guess" semantics: only show recipient/amount when the wallet can prove the typed shape; otherwise fall back to indexed args with an "Unverified summary" marker.
F-009: dApp names, token names, and function names are rendered without checking for Unicode tricks (Cyrillic 'c' in "USDC", right-to-left override, zero-width characters). Fix: route every dApp-controlled string through the existing sanitizeWireString helper. There's already a sanitizer in the codebase used in some places — just apply it everywhere.
F-011: Adding a custom RPC endpoint barely validates the URL — javascript:, data:, file://, anything on any host all pass. Fix: a central allowlist — HTTPS for any host, HTTP only for loopback (localhost, 127.0.0.1, ::1).
F-012: When the wallet signs a transaction, it asks the connected node "what chain ID are you?" and trusts the answer without comparing to the network the user selected. Fix: rebind the live chain identity to the selected network before signing.

Audit cycle (the value of mega-deep)

Round 1 audits found real problems with the initial plan:

  • The initial plan split F-005 out of Phase 1 to keep Phase 1 small. Both audits said reverse this — F-005 shares the same file and registry as F-003 + F-004; splitting them creates two PRs reviewing the same authorization story.
  • The initial plan proposed a single walletSdkSessionId field on stored sessions for F-006. Both audits said reverse this — one stored session can map to multiple live sessions (multi-tab same dApp), so a single field is wrong; iterate active sessions instead.
  • The initial plan's F-001/F-002 fix assumed Nulo could send messages targeted to a specific frame. Codex caught this is infeasible with the current upstream transport — the proposed mitigation would have looked right in tests but the real exploit path would have remained tab-scoped.
  • The initial plan missed that the dispatcher has six separate tryGetDappSessionByOriginAndChain calls — adding a 7th in Phase 3 would have widened a TOCTOU window. Opus caught this and proposed a Phase 0.5 to consolidate the lookups.
  • The initial plan's F-008 router fallback only caught thrown errors. Both audits caught the silent-mis-parse risk: a malicious dApp could craft a payload that looks transfer-shaped but isn't, and the new structured UI would render a precise-but-wrong "To/Amount" — a new phishing surface.

The plan was revised. All blocking findings addressed. A final fresh-context codex pass is running now (Phase 7 of the blueprint ceremony) — verdict pending.

Phases

Phase 0.5 — Consolidate dispatcher session lookups (NEW, from audit)

The dispatcher has 6 separate places where it asks "what session is this?" — closing one TOCTOU window at the entry point is cleaner than fixing it 6 times. ~1 day. Ships first.

Phase 1 — Scope-enforcement primitives (F-003 + F-004 + F-005)

The architectural setup. One PR that adds the sub-grant checker pattern + the account-scope allow-list. Closes 3 findings via shared registry. 1.5-2 days.

Phase 2 — F-007 passkey unlock binding

4-line patch + 1 test. Ships in parallel with Phase 0.5/1 (different file). <1 hour.

Phase 3 — F-006 session revocation teardown

Cross-package: dapp-session service emits a tuple; wallet-sdk subscribes and tears down matching live sessions. Make missing-session calls fail closed at the dispatcher. 2-3 days, codex consult before merge.

Phase 4 — F-001 + F-002 (Nulo-side defense-in-depth)

Subframe rejection (feature-flagged so we can roll back) + content-script pending-request correlation. Frame-targeted send is upstream-blocked; file a separate upstream issue. 2-3 days.

Phase 5 — F-011 + F-012 RPC endpoint trust

Scheme allowlist on URL (https + loopback HTTP only). Shared assertLiveChainIdentity helper at 6+ sink sites. Cache eviction on network change. 2-3 days.

Phase 6 — F-008 broad UX redesign

The big one. Structured argument summaries on the primary approval card for all 5 popup-gated op types. "Don't guess" semantics: shape-prove via wallet-owned builders, else indexed-args fallback. 6a (transfer) + 6b (other 4) develop separately, merge to dev in single landing event to avoid half-rollout phishing signal. 4-5 days.

Phase 7 — F-009 Unicode sanitization sweep

Apply sanitizeWireString to every dApp-controlled render site that Phase 6 didn't already cover. ~1 day.

Phase 8 — /harden security max re-run

Confirm the fixes hold + catch any regressions. Failure-mode protocol: triage new findings as related (re-loop) vs unrelated (audit-followup tag, new arc). 60-90 min wall + variable triage.
