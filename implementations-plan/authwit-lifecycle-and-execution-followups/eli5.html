Authwit lifecycle testability + execution follow-ups

Right now, nobody — not the test suite, not you — can prove that revoking an authwit actually works, because nothing in the project ever uses one. This plan makes the full story testable: grant a permission slip, watch it get used, revoke one and watch it stop working, flip the registry kill-switch and watch everything stop. You get buttons in the playground to do it by hand, and CI gets a test that does it automatically. Bundled in: three small cleanups left over from the execution refactor.

Why this tier was chosen

mid. Rubric: novelty MED (one untraveled wallet code path), security sensitivity MED (a permission check on job-cancelling + permission-slip semantics), everything else LOW. No HIGHs → mid. The ceremony earned its keep: the first draft was rewritten twice because the audits found the original test design would have passed while proving nothing (details below).

Human context: what's an authwit, again?

On Aztec, your account is a vault that only you can operate. Sometimes you want to let someone else move a specific thing once — like signing a permission slip: "the token contract may move 5 of my tokens to B, once." That slip is an authwit. Public slips get written into an on-chain registry; your wallet's Settings shows them and lets you revoke them, and there's a master switch that disables ALL of them at once.

The catch the audit caught: slips are single-use — using one burns it. So a test that grants once, revokes, then says "look, it stopped working!" proves nothing — it already stopped working because it was used. Every step of our test uses a fresh slip, and the revoke test revokes a slip that was never used. That's the difference between a test and theater.

Phases

Phase 0: Housekeeping (~2h)

Fix a missing index entry; write down the CURRENT (too-permissive) cancel behavior as a test so the next phase's change is visible and deliberate.

Proves itself by: lint + the lane unit tests, green.

Phase 1: Execution follow-ups (~half day) — deliberately FIRST

Three small fixes that don't depend on the authwit work at all: (1) cancelling a job now checks the job belongs to your profile — others are silently ignored; (2) two internal "start a job record" code paths become one; (3) the test harness now fails LOUDLY when its blockchain sandbox fails to start, instead of skipping everything and looking green (this exact trap bit us during the last arc). Front-loaded so it ships even if the authwit work stalls.

Proves itself by: full unit suite + lint green, including the new permission tests.

Phase 2: The grant button (~1 day, starts with a spike)

Surprise finding: the wallet code that records public permission slips has zero users — no dApp can currently trigger it. So before building anything, a short proof-of-life spike decides between two ways to expose it (a custom RPC like our existing registerToken pattern, vs the action-based path), each with a real permission-scope story. Then the playground gets "grant" and "consume" buttons (kept strictly separate — bundling them would secretly re-grant before every use) and an account picker. If neither path works, work STOPS and comes back to you — no improvising.

Proves itself by: a minimal "grant then consume once" browser test against the local network, green.

Phase 3: The lifecycle test (~1 day)

The full story, automated: fresh slip → used OK · fresh slip → revoked in Settings → use FAILS (and we assert it fails because of the revoke, not because it was already used) · fresh slip → master switch OFF → use fails → switch ON → use works. This finally covers the two Settings flows that have never had automated coverage.

Proves itself by: the new test green twice in a row locally, then the whole network suite green.

Phase 4: Close (~half day)

Code review pass, independent codex audit, docs, one PR to dev. The merge gate is YOU clicking through the new playground buttons once.

Proves itself by: CI green on the PR + your manual pass.

What the audits changed (the honest version)

  • The custom Noir contract was dropped. v1 wanted a purpose-built "consumer" contract. Codex found the wallet couldn't even load its artifact without extra plumbing; both auditors confirmed a plain two-account token transfer exercises the identical on-chain path with zero new contracts. The contract idea is parked as a future arc.
  • The test script was vacuous. Single-use semantics (above) — fable's catch, now fixed and re-verified by the final codex pass.
  • "The wallet auto-grants" was false. The grant path has no users; Phase 2 exists because of this.
  • One deliberate disagreement, decided: codex wanted the cancel-permission check to also match the exact account; we kept it at profile level — a profile is one human, and that human may cancel their own jobs from any of their accounts. Recorded as an explicit product decision.
