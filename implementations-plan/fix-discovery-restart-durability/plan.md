# Arc 4 — fix-discovery-restart-durability (F-B16: queued discoveries vanish on SW restart)

[mid] tier of the 2026-08-16 remediation follow-ups ([spec](../remediation-followups/plan.md)). Recon-first ([recon.md](./recon.md)); dual audit (codex + fable); prove-first RED. Validation: repo gates + `audit:vue` + **SOLO proverless network e2e** (arc-4 requirement; armed smoke not required for this arc).

## The harm, precisely

A dApp fires `discoverWallets()` while the wallet is locked → the discovery is queued in-memory (`DiscoveryQueue`) and the toolbar badge is set. MV3 kills the idle SW ~30s later. The user unlocks at t≈40-50s: the queue is gone (fresh empty `DiscoveryQueue` at boot), no popup ever appears, the dApp times out at 60s with "no wallet found", **and the badge still shows the ghost count with no backing data**. The value window for durability is bounded by the existing `DISCOVERY_STALE_MS = 55s` (deliberately under the dApp's 60s local timeout) — narrow, but it is exactly the common "queued → idle-kill → unlock" sequence. Failure mode without the fix is a retry papercut + a permanently stale badge, not data loss — which bounds how much machinery this arc may buy (ANTI-OVERENGINEERING).

## Chosen design — persist the projection; replay through the SDK's own front door

**Persistence (inside `DiscoveryQueue`, choke-point discipline).** `DiscoveryQueue` gains an optional injected store over `chrome.storage.session` (`EntityStorage<PersistedDiscovery>` on a new root, e.g. `nulo:bridge:queued-discoveries`; layer-legal — wallet-bridge already imports wallet-core; storage.session = survives SW restart, clears on browser exit, explicitly non-migratable tier, no backup surface). `enqueue(...)` is extended to receive the full projection `{requestId, appId, appName?, origin, chainId, chainInfo, tabId, timestamp}` (the caller `handleDiscovery` has the `PendingDiscovery` in scope) and writes the row exactly when an entry is ACCEPTED (post-caps, post-coalesce; a coalesce-replace deletes the replaced row). `drain()` deletes each row as the entry is consumed (processed, dropped-as-gone, or expired-rejected). All mutations flow through the existing enqueue/drain choke points, so the F-04 cap/coalesce pins stay valid and gain persistence assertions. Writes are best-effort (a storage failure must never break the live enqueue path).

**Rehydration (boot).** A `rehydrate()` step wired at the tail of `initWalletSdkHandler` (after `handler.initialize()`, mirroring the `resumePending` fire-and-forget shape): read all rows; delete + skip entries already expired (persisted timestamp vs `DISCOVERY_STALE_MS`) or whose `tabId` no longer resolves (`tabs.get` probe); for each survivor **replay via `handler.handleDiscoveryRequest({requestId, appId, chainInfo}, tabId, origin)`** — the SDK's public content-relay entry — which re-seeds `pendingDiscoveries` AND re-fires `onPendingDiscovery` → our `handleDiscovery` → re-enqueue through the normal choke points (locked) or straight to the popup path (already unlocked). Immediately after the call returns, restore the ORIGINAL timestamp on the live record (`handler.getPendingDiscovery(id).timestamp = persisted.timestamp` — `Map.get` returns the stored reference; the mutation lands synchronously before the async `handleDiscovery` resumes past its first await, so every staleness check reads the true age; replay must never extend the 55s budget). Finally, `updateBadge()` runs UNCONDITIONALLY (including → `""`) so the stale-ghost badge is reconciled even when nothing survives. Two canary pins guard the SDK facts this leans on (live-reference `getPendingDiscovery`; replay-then-restore ordering beats `handleDiscovery`'s first staleness read).

**Explicitly decoupled (anti-lost-tx).** No shared locks, no serialized boot queue, no journal roots: the sendTx arrival path (`onWalletMessage` → arrival-time `tryCreateQueuedJournal` off the FIFO baton) is untouched; `concurrent-sendtx*.test.ts` remains the pin. Rehydration touches only discovery plumbing.

**Out of scope, recorded:** (a) popup-side orphaning (open discover popup across restart — unserializable `WindowManager` handles) — owned follow-up; (b) the newly-observed cold-wake race (the SDK message listener registers async at the tail of `runtime.start()`, so a discovery message that itself wakes a dead SW can be dropped before any listener exists) — new discovery for the final report, separate surface; (c) queued-entry cleanup on `tabs.onRemoved` beyond the rehydrate-time probe — the SDK's `terminateForTab` + drain's gone-drop already bound it within a lifetime.

## Competing outline (for the audit): clean-loss semantics only

No durability: at boot, reset the badge unconditionally (one-liner in `initWalletSdkHandler`) and record F-B16 as NOT-DURABLE-BY-SDK-DESIGN (the SDK owns the pending map; the dApp times out locally; the loss window is ≤55s and self-heals by user retry). Cheapest possible arc; rejects the durability ask as not-worth-it. The audit should judge: does the replay design's cost (a store + a boot hook + two SDK-behavior canary pins) buy the ≤55s window honestly, or is the SDK-coupling (timestamp mutation on a live record; replay through `handleDiscoveryRequest`) too fragile to own? Note the SDK precedent: `terminateSession` itself re-seeds the map from session data.

## Prove-first — RED evidence (run against pre-fix dev, SOLO proverless agent runner)

Both legs of the original durability-shaped spec failed on `dev@96d2a823` with full retries: the queued discovery never re-surfaced after a real SW kill (popup wait timed out), and the ghost-badge assert failed with exactly `AssertionError: expected '1' to be ''` — the pre-kill badge count ghosting over an empty queue even after unlock. The second failure is the RED for the shipped clean-loss fix; the first documents the loss the deviation accepts.

## Original RED design (pre-audit, durability-shaped — superseded by the redirect)

1. **Unit/integration RED (wallet-bridge):** two `DiscoveryQueue` generations over one `FakeBrowserApi` (the `makeServiceFromExistingApi` idiom): gen-1 enqueues; gen-2 (fresh instance, same storage, handler with empty map) drains → TODAY processes nothing (RED) → post-fix rehydrate + replay processes the entry.
2. **E2E RED (network suite):** extend `connect-locked-queue.test.ts`'s scaffold into a new spec: lock → playground connect (queued) → REAL SW kill (`worker().close()` + `targetdestroyed` identity + `waitForLiveness` strictly-newer) → unlock → TODAY no discover popup (RED) → post-fix popup appears → approve → verify → connected. Plus the staleness leg: same but wait past 55s before unlock → cleanly rejected, badge cleared, no popup.

## Audit ledger — dual audit REJECTED durability; the arc REDIRECTS to clean-loss (the competing outline)

**Both legs independently rejected the replay design and independently recommended shipping the clean-loss outline.** Decision per the charter: SIMPLER wins; rejection is a success state.

**Fable (blocking):** B1 — the manifest grants no `tabs` permission, so the rehydrate probe can prove a tab EXISTS but never that it still shows the persisted origin; a navigation during the SW-dead window turns a replayed approval into a completed key exchange for the wrong site (the content script unconditionally posts the `MessageChannel` into the tab's CURRENT document), and closing that honestly requires a user-visible permission expansion. B2 — `handleDiscoveryRequest` replay unconditionally resets a same-requestId record to `pending` (dApp-chosen ids are replayable), silently killing an in-flight approved handshake. B3 — drain delete-ordering loses rows on a mid-drain re-lock. B4 — `chainInfo` carries `Fr`-typed values with no stated persistence-normalization contract. Also: the timestamp-restoration mutation is unnecessary (the SDK never reads `discovery.timestamp`; thread the true age into `isDiscoveryExpired` instead) — noted for any future revival.

**Codex (blocking):** the same tab/origin-continuity attack (independently constructed, with the content-script sink cited); incomplete persisted-row lifecycle (an unlocked-boot replay never deletes its row → a REJECTED discovery resurrects on the next restart within 55s; coalesce/cap-dropped replays leak; unsequenced set/delete lets a late enqueue write resurrect a drained row); hostile-row/timestamp validation gaps (a malformed `chainInfo` throws in `handleDiscovery`'s sync prefix → the SDK record is deleted before the timestamp restore runs → undefined dereference; future/string timestamps bypass `isDiscoveryExpired`).

**Both legs agree:** anti-lost-tx is decoupled (no counterexample exists — discovery is pre-session, `activeSessions` is empty at boot, journal creation stays arrival-time); the badge reconciliation, real-kill e2e shape, and caps are sound; `terminateSession`'s internal re-seed is not a supported restoration contract.

## Shipped fix (clean-loss semantics)

- **`DiscoveryQueue` constructor now reconciles the badge** (`updateBadge()` at construction = every SW boot). The badge is Chrome-level state that survives the kill while the queue boots empty; before this fix the ghost count was PERMANENT — the empty-queue `drain()` early-returns without touching the badge, so even unlocking never cleared it. Unit pins: construction repaints to `""`; enqueue still paints the live count.
- **E2E pin** (`connect-locked-queue-sw-restart.test.ts`, network suite): lock → discovery queued (badge `1`) → REAL SW kill (`worker().close()` + `targetdestroyed` identity) → replacement boot (strictly-newer liveness) → badge reconciled to `""` BEFORE unlock (the RED today) → unlock → no discover popup (pins the accepted clean loss) → badge stays clean.
- **Deviation recorded: F-B16 → NOT-DURABLE-BY-SDK-DESIGN** (codex + fable agreed): the SDK owns the pending-discovery map with no restoration contract; origin continuity across the SW-dead window is unverifiable without a `tabs` permission expansion (owner-gated surface); the loss window is ≤55s with a retry-papercut failure mode against a dApp that re-broadcasts. The durable harm — the ghost badge — is fixed here.

## New discoveries for the final owner report (out of arc scope)

1. **Cold-wake message loss (dominates F-B16):** the SDK message listener registers asynchronously at the tail of `runtime.start()` (`handler.initialize()`, `background.ts:446`) — a dApp message that itself wakes a dead SW can be dropped before any listener exists (the price-alarm listener was deliberately hoisted to module scope for exactly this race; the discovery path was not).
2. **Dead origin guard:** the `tabs.onUpdated` navigation guard (`background.ts:425-439`) keys on `changeInfo.url`, which Chrome suppresses without a `tabs` permission (or per-host grants) — for arbitrary dApp origins the guard never fires. Pre-existing; interacts with the same permission question as B1.
3. **Popup orphaning across restart:** an open discover/execute popup whose SW dies is orphaned (`Invalid id` / never-settling handles) — `WindowManager` promise closures are structurally unserializable; a durable-record barrier pattern (cf. `AccountIntegrityCoordinator`) would be the shape if this is ever prioritized.
