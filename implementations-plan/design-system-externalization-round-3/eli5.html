Design system — round 3 (close-out cleanups)

Round 1 and round 2 moved the wallet's UI building blocks into a shared @nulo/design package. Round 3 sweeps up what was deliberately left behind: a settled decision to keep the faucet and extension toasts separate (they're genuinely different things), dropping a broken dark color name, retiring the last duplicate button (AppButton), and deleting 9 dead "shadow" copies of primitives that the extension was still secretly using instead of the shared ones.

Why this tier was chosen

Light. Three of the four pieces are tiny and low-risk (rubric: 0/6 high). The fourth — deleting the 9 shadow copies — touches building blocks used everywhere, and codex's audit found it's actually a reconciliation, not a clean delete: the shared versions quietly gained real behavior (a disabled-Checkbox guard, a Toggle color option) the old copies lack. So that phase carries extra rigor (component-by-component checks + targeted tests + a real-network test run + a human eyeball), and whether it stays in this light arc or splits into its own follow-up is one of two decisions for you below. Codex's verdict: conditional approve.

Phases

Phase 1 — Record the toast decision (no code)

Write down, once and for all, that the faucet's toast (a queue of up to 4 messages with links) and the extension's toast (one quick popup message) stay separate — they're different by design because a web app and a 360px extension popup need different things. Removes "unify toasts" from the future-work list.

Proves itself by: lint + no-brand guard green; no broken doc links.

Phase 2 — Drop the broken dark color

color="dark" never worked (it points at an undeclared variable), so 8 places in the extension silently show full-strength text instead of the muted gray they intended. We remove the broken color name and repoint those 8 sites to a real muted token (proposed: tertiary).

Proves itself by: typecheck + design/extension unit tests + builds; zero traces of dark/--gray-15 left.

Phase 3 — Retire AppButton

The old AppButton has only one user left (DripButton). Point DripButton at the canonical Button and delete AppButton. One catch codex caught: the new Button doesn't auto-disable while loading, so we explicitly disable-on-loading to keep drip buttons from re-firing mid-request.

Proves itself by: typecheck + design + faucet tests + builds; no AppButton references remain.

Phase 4 — Delete the 9 shadow copies (the careful one)

The extension still renders its own local copies of Flex/Icon/Text/etc. instead of the shared package versions. Delete the copies so the shared versions take over. Most are byte-identical ports; the icon set is identical (verified). But Checkbox and Toggle diverged — the shared versions are better (guard disabled clicks; add a color option) — so adopting them is a real behavior change. Each of the 9 gets a port-vs-reconciliation verdict, the changed ones get pinned with tests, then a network test run + a human "looks the same" check.

Proves itself by: typecheck + all units + builds + storybook + smoke + network e2e + a human no-deltas sign-off (icons, layouts, the Checkbox/Toggle behavior, the dark→muted change). Not marked done without the sign-off.

Human context

"Shadow copies" exist because round 1 moved primitives into the package but didn't delete the originals, so the extension kept using the originals. They've drifted apart since. Deleting them is mostly safe, but it's the one place a mistake would be visible everywhere — hence the heavier checks. The toast decision matters because the obvious "unify everything" instinct is wrong here: forcing one toast system would either crowd the tiny popup or strip the web app's queue.

Open questions — your call at the gate

1. What color do the 8 dark sites become? They currently show full-strength text (the bug). Proposed: tertiary (muted) — likely the original intent. Alternatives: secondary (lighter mute), or keep full-strength (true no-change).
2. Phase 4 — keep it in this arc, or split it out? Codex flagged it as heavier than a "delete dead code" job. (A) Keep it here with the added rigor (per-component checks + targeted tests + network e2e + visual sign-off), or (B) ship phases 1–3 now and do phase 4 as its own focused follow-up.
