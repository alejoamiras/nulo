Onboarding width unification

A plain-language walkthrough of why the onboarding flow feels "toy-shaped" right now and how we'd fix it.

The problem in one sentence

The first six pages a new user sees each pick their own width independently, so the layout visibly jumps around between steps. That looks unintentional, which makes the product feel like a hobby project on first impression.

Why does this happen?

Each onboarding page is a separate file. Whoever wrote each file picked a width that "felt right" for that page in isolation:

  • create and done use ~440–480 px because they're mostly a form + one button — they look "right" at popup width.
  • learn uses 880 px because it has three cards side-by-side and needs the horizontal room.
  • import and accelerator landed somewhere in the middle (560 px).

Each choice makes sense alone. Together, you get four different widths in a row and the eye reads "this product can't decide what it is".

The user's instinct that it was "popup-inherited" is half-right. There's no actual popup component being imported — it's just that 440–480 px happens to be close to the wallet popup's own width, so the eye associates those onboarding screens with popup-shaped surfaces.

The plan, in plain English

Step 1 — Pick one width

We chose 640 pixels. Here's the why:

  • Wide enough that the four-step progress indicator (which has a natural width of about 560 px) doesn't get squashed.
  • Narrow enough that the simple forms (just a wallet name and a password) don't feel marooned in whitespace.
  • Wide enough for the three-card "Meet Aztec" layout to still render side-by-side instead of stacking.

Step 2 — Build a shared "Onboarding Page" wrapper

Instead of editing six files to all say max-width: 640px and hoping they don't drift apart again next quarter, we build one small Vue component that owns the width. Every page wraps its content in this component. If we ever want to change the width, we change it in one place.

This is the architectural-discipline answer instead of the duct-tape answer. Slight upfront cost; future drift becomes impossible.

Step 3 — Lower the "stack the cards" trigger

The "Meet Aztec" page has a rule that says "if the screen is narrower than 720 px, stack the three cards vertically instead of side-by-side." Since our new container is 640 px wide, that rule would always fire and we'd lose the side-by-side layout we wanted to preserve. We lower the trigger to 560 px so three columns survive inside our 640 px container.

Step 4 — Don't break the test selectors

The codebase has end-to-end tests that look for specific HTML attributes (like data-testid="onboarding-name-input") on form elements. The fix only swaps an outer wrapper; nothing inside the forms moves. The test selectors keep working without edits.

What could go wrong?

Pre-mortem — security & adversarial considerations from the plan, in plain language.

  • Test breakage: Low risk. The selectors are on inputs / buttons inside forms — we don't touch those.
  • Accessibility regression: Low risk. No new motion, no DOM reordering, the "current step" indicator still announces correctly to screen readers.
  • Visual regression for users mid-onboarding during release: Low impact. The onboarding tab is a single-session surface — closes itself when you open the wallet for the first time. Next time you open it, you'd see the new layout.
  • Bypassing the wallet-creation gate: Not introduced here. Already possible by deep-linking; the redirect logic in app.vue already prevents it for users without a profile.

Open questions

  • Auto-imports. The codebase auto-imports components from src/components/. We're putting the new wrapper in src/onboarding/components/, which might or might not be in the auto-import scope. If not, we add an explicit import — single line per page. To verify during implementation.
  • The top margin on "done". The "done" page sits 48 px down from the top today (more than the other pages' 16 px). After unification it sits 24 px down — a bit closer to the top. If this looks wrong in the manual smoke test, we add extra padding to the hero block on that page only.
