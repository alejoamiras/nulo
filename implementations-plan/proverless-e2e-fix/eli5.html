proverless-e2e-fix

The diagnosis found one reason our three flaky tests fail: a background helper thread gets drowned in log-messages from a separate component catching up on the blockchain, so transactions stall in a waiting room. This plan stops the flood — batch those log-messages so the thread stays free — plus adds a "smoke alarm" so a future stall fails fast instead of freezing for 5 minutes, proves it with repeated cloud runs, and makes the suite a required check.

Why this tier (mid) — and why it changed shape

It's a contained change touching one shared path (logging transport) — 1 high-ish risk dimension → mid. The first version was rejected by both auditors: a "test-only" fix turned out unbuildable (the signal it needed isn't readable from tests and didn't even track the real problem). So — with your OK — v2 makes a minimal production change at the real source. That also helps real users, not just the tests.

Phases

Phase 0: Prove the flood is really the cause (before building anything)

Measure the log-message flood, and check the make-or-break question: if we batch it, does the stall actually go away? If batching the logs doesn't help, we stop — we'd be wrong. Also design the batching (how often to flush, never lose error logs).

Proves itself by: a measurement showing the flood drops AND an early sign the stall eases (the built-in falsifier).

Phase 1: Batch the log-messages (the actual fix)

Buffer the background helper's log-messages and ship them in bundles instead of one-at-a-time, so the thread isn't drowned. Same content; errors/warnings still sent instantly; the receiving side processes a whole bundle in one go.

Proves itself by: unit tests for the batcher (bundles, flushes, never loses errors) + lint + typecheck, all green.

Phase 2: Add a smoke alarm (so a future stall can't hide)

A watchdog: if a transaction ever stalls again, the test fails in seconds with a snapshot of what happened — instead of a 5-minute freeze. Carefully scoped so it never false-alarms on the legitimately-slow real-proving test.

Proves itself by: a forced-stall test fails fast with the snapshot; a normal run and a slow-proving run are NOT false-failed.

Phase 3: Run it locally a few times

Confirm the three tests pass and nothing regressed, on the real build.

Proves itself by: 3 clean local runs of each test (retries off) + a clean full build.

Phase 4: Prove it in the cloud (the real test)

A soak: run each fixed test 20×, repeat the historically-failing shards, and run the whole suite 3× — all with retries OFF. All green = genuinely fixed.

Proves itself by: the soak coming back all-green at zero retries.

Phase 5: Make the suite a required gate

Change the suite to run on every code PR (not just ones touching a hand-listed set of files, which a sneaky change could dodge), skipping only doc-only PRs. Then — after we watch the CI cost for a bit — flip it to a required check (that switch is yours to pull).

Proves itself by: the workflow change passes lint + a dry-run (doc-only PR skips, a code PR runs); the required-flip is a written runbook for you.

Human context

Picture a receptionist (one background thread) who must do a quick check-in for your transaction, but a back-office clerk (the blockchain sync) keeps shouting an update for every page they process — so the receptionist never gets to you, and you sit in the waiting room. The fix: stop the clerk from shouting every single page — bundle it. Then the receptionist is free, your transaction starts, and the test passes. The earlier idea ("just make the test wait for the clerk to finish") couldn't be built without reading something the tests can't see — so we fix the actual noise instead.
