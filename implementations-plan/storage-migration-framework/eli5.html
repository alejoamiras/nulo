A real migration system for the wallet's saved data

When you ship a new version of the extension, users already have data saved in their browser from the old version. Migration is the step that transforms that saved data to the new shape — add a field, rename one, restructure a record — without losing it. Today the wallet has no real migrator, just a leftover "delete everything on a version bump" wipe inherited from the fork. This builds the actual production mechanism, learning from how MetaMask and Rabby (the two most production-hardened wallets) do it, and adds two safety features neither of them has: a pre-migration backup with restore, and a fail-closed stance so a bad migration can't quietly corrupt your data.

The two big ideas

Built for two doors, shipping one. Old data reaches a new build two ways: by updating the extension, or by importing an old backup. The engine is designed for both — but this plan ships the update door. Backup import turned out to be a genuinely different data shape (it's stored differently), so it's a queued follow-up plan (storage-migration-backup/) that plugs into the same engine later.

Safe by construction. Before each migration the engine takes a backup; it only marks a migration "done" if it fully succeeded; if the browser kills the background process mid-migration, the next launch restores the backup and resumes. And every migration is tested by running it twice to prove re-running is harmless.

Phases

Phase 1: The engine (shared, pure, no browser calls)

The migration runner in the shared package: applies numbered migrations in order, refuses to record success unless a migration fully completes, backs up before it starts, and restores + resumes after a crash. Built to run on either live storage or an imported backup.

Proves itself by: unit tests — in-order apply, checkpoint per success, backup→restore→retry, and every migration run twice = run once (idempotency).

Phase 2: Wire it into the extension + delete the old wipe

Connect the runner to Chrome storage (carefully mirroring how rows are stored), run it as the first thing on startup, delete the old migrate.ts wipe, and fix the crypto documentation that currently points engineers at the file we're deleting.

Proves itself by: the full audit:vue gate + unit tests — fresh install runs nothing, the backup is written atomically, a leftover old-version key raises a loud dev warning instead of being silently swallowed.

Phase 3: The "Updating…" barrier + what happens on failure

Stop a popup opened mid-update from scribbling old data over a migration in flight (a small "Updating…" gate). And decide failure behavior: a breaking migration that fails blocks with a recovery path ("your funds are safe — reinstall/recover"); an additive one lets you in with a warning.

Proves itself by: component tests — the barrier blocks reads while migrating; a breaking failure shows recovery; an additive failure boots degraded.

Phase 4: Prove it in a real browser (4 smoke tests)

Drive real migrations through the real extension: (1) a normal transform, (2) a failure that restores + retries, (3) a popup opening mid-migration, (4) a crash at each risky point mid-migration that resumes cleanly.

Proves itself by: the four smoke e2es green + a build check proving the test-only fixture never ships to production.

Phase 5: Docs + the networked end-to-end

Update the architecture docs + a worked "how to add a migration" example, then run the full networked test (real wallet boots, registers, syncs, and restores a backup after migrating).

Proves itself by: the network e2e + audit:vue gates green.

Human context

  • Why not just wipe? Because once real users exist, "delete their data on update" is unacceptable — the whole point is to keep it. We're building the real thing now, while mistakes are cheap.
  • The crypto exception. Your secret key is encrypted with your password; the migrator runs at startup before you unlock, so it has no password and physically can't re-encrypt. So changing the encryption scheme isn't a normal migration — it's a "re-encrypt when you next unlock, or reset" case. We document that boundary rather than pretend to auto-handle it.
  • The race we had to close. Some of the wallet's screens read/write browser storage directly (not through the background). Without a barrier, a screen opened mid-migration could overwrite it. The "Updating…" gate closes that — and only ever shows up on the rare launch right after an update that ships a migration.
  • Long-term: routing all screen storage through the background would kill this race class entirely — it's the cleaner end-state, noted as a separate follow-up, and this work leaves a seam for it.
