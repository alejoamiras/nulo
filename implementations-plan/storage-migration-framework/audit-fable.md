# Fable-leg audit (Opus 4.8) — storage-migration-framework plan (Round 1)

Independent top-tier leg of the `/blueprint mid` dual audit. Fable is deactivated → run on Opus 4.8 per the model-fallback note. Read-only Plan agent; verified every §8 Fact, all three backends, the boot path, offscreen/SW IndexedDB partition, the credential record shape, and the gate commands.

**Verdict:** `conditional approve` with 6 conditions (below). The plan is fundamentally sound and the credential-preservation invariant is genuinely airtight (credentials confined to `nulo:core:profiles@*` on `local`; session + IndexedDB carry no credential material). Conditions target a cross-context IndexedDB blind spot, an allowlist inversion, a safety-critical crypto-contract doc, and trimming Plan A's speculative generality.

## Adversarial
- **C1 [Critical] Cross-context IndexedDB ownership.** PXE DBs (`pxe/${profileId}/${chainId}`, `chain-runtime.ts:123`) + `keyval-store` are created in the **offscreen document** (`offscreen/index.ts:81`), not the SW where genesis runs (`runtime.ts:105`). Same origin → SW `deleteDatabase` reaches them, but if the offscreen holds an open connection, delete fires `onblocked` and the current code resolves-on-blocked = silent skip (`migrate.ts:87`). §7's "deletes idempotent ⇒ re-run completes" is FALSE when the blocker is a live cross-context handle: the version still stamps → next boot never retries → stale `pxe/*` survives a "completed" genesis, paired with wiped accounts. Bites the realistic path (SW idle-suspends + respawns while offscreen survives — `offscreen.ts` SW-restart-leak caveat). The codebase already solved this correctly at `aztec-runtime/pxe/service.ts:149-183` (blocked-aware, runs in the owning context). Fix: delegate IDB deletion to the offscreen/PXE context OR close the offscreen before wiping OR treat `onblocked` as a migration FAILURE (don't stamp). The §4.2 "list/delete DBs" hand-waves this.
- **C2 [High] Genesis wipe inventory incomplete → invert to a survivors-ALLOWLIST.** Full key enumeration found keys the plan never mentions: `nulo:core:session` + `:ttl`, `nulo:core:auth-registry-enabled`, `nulo:core:incoming-trust`, `nulo:core:tokens`, `nulo:core:contacts`, `nulo:config`, `nulo:ui:activeAccount`, `nulo:ui:lastActiveProfile`, `nulo:ui:sentinel`, `nulo:onboarding:*`, `nulo:logs`. A denylist is exactly how the current system accreted gaps. **Define genesis as preserve-exactly-`{nulo:core:profiles@*}` (+ bare index), wipe everything else** — self-healing vs the M4 denylist trap. Highest-leverage change; the plan under-commits.
- **C3 [High] Fresh-install-with-leftover-DBs.** "Harmless no-op over empty storage" is half-true: `chrome.storage.local` is cleared on reinstall but IndexedDB may persist across uninstall→reinstall / unpacked remove+re-add. Make the IDB wipe unconditional + verified on genesis (depends on C1's blocked-handling).
- **H1 [High] Boot re-entrancy / UI-bypass race.** `runtime.start()` is fire-and-forget (`index.ts:80`); `start()`'s `if (started) return` is a sync bool before the first await, so "migration done" is unobservable. Multiple UI surfaces read `chrome.storage.local` DIRECTLY, bypassing the SW (`app.store.ts:34/54`, `utils/core.ts:148`, `utils/lastActiveProfile.ts:8`, `BalanceView.vue`, `FeeSettingsCard.vue:127`) → can read mid-wipe. Benign for destructive genesis, dangerous for a future data-preserving migration (read pre-migration row, write back post-migration → resurrect old shape). Document the boot-ordering contract + add a "migration in progress" guard the UI can await.
- **H2 [High] Attacker keyspace.** Genesis enumerates attacker-influenceable keys (`get(undefined)`). The preserve-rule MUST use the `@` boundary (`nulo:core:profiles@`, not bare `nulo:core:profiles`) or injected `nulo:core:profilesX` junk survives. Explicit test: `profilesX` wiped, `profiles@abc` survives.
- **M1 [Medium] Downgrade is worse, not benign.** Genesis deletes the legacy `nulo:core:storage-version`. A tester who downgrades to an OLD build runs the legacy runner → reads absent key → `undefined !== 8` → re-fires the full legacy wipe (a second destructive wipe). §7's "no-op + safeParse tolerance" is wrong for the realistic downgrade vector. Correct the text.
- **M2 [Medium] BalanceView latent crash.** `BalanceView.vue:198-225`: if `oldKey in oldResult` but the value is falsy, `optionsMap` is undefined → line 220 throws. Deleting the migration + routing to `loadBalanceDisplayOption` (line 226, safe init) FIXES it. Gate (d) must assert the **caller is switched**, not just that the function is gone.

## Security / supply-chain / crypto
- **S1 [High] Crypto-vector ↔ version-bump coupling is INVERTED by the reset.** `wallet-crypto/README.md:37` says a vector/KDF change "requires a storage-version bump and a destructive-migration row in `migrate.ts`." Vectors are frozen at "V8" (`key-vectors.test.ts:184` `PASSKEY_PRF_LABEL === "nulo:profile:v1"`). The plan resets storage to 1 while vectors stay V8 → the two version numbers diverge, and the README points at a deleted file. **Rewrite the contract** (point at the new registry; state the storage-version↔crypto-epoch divergence; "vector change ⇒ new genesis-style destructive migration"). Safety-critical, not cosmetic — else the next person rotating `ENCRYPTION_GUARD` follows a stale README into a deleted file and ships a wallet-bricking change with no wipe.
- **S2 [Medium] Credential invariant is airtight but state it per-backend.** Confirmed: `Profile` carries encrypted `secret`/`credentialId`/`passhash` (`profile/spec.ts:23-35`) at `nulo:core:profiles@<id>` in local; master `Fr` is in-memory + the `nulo:core:session` mirror only. Preserve `profiles@*` on local; session+IDB carry no credential material. The invariant reduces to a single allowlist rule on one backend — state that as both proof and test spec.
- **S3 [Low] No new permission / no new dep — agree.** Reject `redux-persist`'s `createMigrate` for ~30 lines (drags in redux; MV3 SW attack surface). But push blocked-handling into the PURE engine (typed `MigrationResult`) so it's wallet-core-tested, not stranded in the untested chrome adapter.
- **S4 [Low] Delete PXE DBs where the data lives.** Most privilege-correct: the offscreen performs IDB deletion via a "wipe PXE state" command (the shape `pxe/service.ts:149` already implements), not the SW reaching across contexts.

## Assumption attack
- Facts: ARCHITECTURE.md is **repo-root** `/ARCHITECTURE.md:99` (not `packages/extension/`). The wipe-omits Fact undercounts (see C2). MISSING load-bearing Facts: PXE IndexedDB is offscreen-owned; multiple UI surfaces read `chrome.storage.local` directly bypassing the SW.
- Inferences: new-marker is sound forward, naive backward (M1). "Delete-only ⇒ little untrusted risk" true for values, false for the keyspace (H2). **A-vs-B crux:** Plan A's engine is over-engineered for a genesis-only v1 — the 3 M4 blockers don't BITE today (dedicated marker key fixes ①; genesis needs only 3 fixed ops not general routing ②; the lock is moot at boot ③). The M4 blockers need to be **not re-entrenched**, not fully **solved**, in v1. Plan A over-resolves them.
- Asks: re-frame Ask 4 as a survivors-allowlist approval. New Asks to surface: IndexedDB-across-reinstall + offscreen-open-handle acceptance; crypto-epoch reconciliation. Ask 1 (MM research) safely resolvable with own knowledge (MM's model = sequential `{version, migrate}` applied where `version > persisted`, no rollback, fail-closed — matches the plan).

## Phases / gates
- Phase 1 "sequencing decided at impl time" hedge violates blueprint gate discipline — commit to a sequence; make 1-3 atomic.
- **No gate tests C1** (open offscreen handle during genesis) — add to Phase 4: seed a `pxe/*` DB held open, assert genesis deletes-or-fails-closed-and-retries.
- **No gate tests the allowlist-survivor property** — add a unit test: snapshot with one key of every root + injected `profilesX` junk ⇒ only `profiles@*` + bare index survive.
- Phase 2 "lock serializes concurrent run()" tests speculative machinery (no v1 consumer) — keep as a forward test, be honest it isn't v1-correctness.
- Phase 5 network e2e (cold-boot + register/sync post-reset) is the right integration gate — keep; make explicit it runs against a build where the offscreen was previously alive.

## A-vs-B recommendation
**Plan A-minus (A's seam, B's scope):** build the `chrome.*`-free engine seam in `wallet-core/src/migration/` (isolated-testable, M4 blockers structurally addressable later), constrain v1 to `Migration {version, description, up(ctx)}` + a `MigrationContext` exposing `local`/`session`/`indexedDb` (the 3 genesis ops) + `Migrator.run` (fail-closed, stamp-last). DEFER cross-root ordering, the per-root lock registry, and the general version-metadata adapter until a real data-preserving migration demands them. Put blocked-handling in the pure engine; delegate `deleteDatabase` to the offscreen/PXE context.

**6 conditions:** (1) cross-context IDB: onblocked = fail-closed-retry, result in the pure engine, delegate delete to offscreen, Phase-4 e2e holds an open handle; (2) survivors-allowlist (preserve `profiles@*` + bare index, wipe everything else incl. the missing keys) + junk-key unit gate; (3) reclassify `wallet-crypto/README.md:37` as safety-critical, rewrite the vector↔migration contract; (4) adopt Plan A-minus, drop speculative generality; (5) correct 3 Facts (ARCHITECTURE path; downgrade text; add the 2 missing Facts); (6) replace the Phase-1 hedge with a committed sequence + a gate that actually invokes genesis.

# Fable-leg (Opus 4.8) — Round 2 (data-preserving design, plan v4)

Read-only Plan agent, verified against code + the MetaMask/Rabby studies. (Round 1 above audited the scrapped wipe design.)

**Verdict:** `conditional approve` — architecture sound + materially better than both references on its two safety axes; 4 blocking conditions, all fixable within the phase structure (specification/sequencing/enforcement gaps, not architectural flaws).

## Critical (blocking)
- **C1 — read-during-migration race.** UI reads `chrome.storage.local` DIRECTLY, bypassing the SW: `BalanceView.vue:204-250`, `FeeSettingsCard.vue:127-247`, `stores/app.store.ts:34-85`, `composables/syncedRef.js:7-14`, `config/store.ts:10`. Several are read-modify-write. The in-memory SW readiness gate lives in the SW and can't gate separate popup JS contexts. A mid-migration popup `get`→mutate→`set` races the migration write (last-writer-wins) or resurrects a just-deleted root. Fix: (a) a cross-context sentinel the UI blocks on before any storage access, (b) route UI storage through the SW (big refactor), or (c) scope migrations to roots the UI never writes-while-locked, proven per-migration.
- **C2/H1/H2 — crash-safe backup/restore + multi-root atomicity.** "Keep 1…N-1 durable" (checkpoint) contradicts "restore pre-migration backup." Narrow-slice `setRows` writes per-root incrementally; an SW kill between root A and root B leaves a torn multi-root state, and retry re-runs N against a half-applied store → migrations must be idempotent-on-torn-resume (stronger than stated). Need: backup = ONE atomic `chrome.storage.local.set({...})` incl. a `backup:complete` sentinel written last; restore only trusts a sentinel-matched backup; a durable phase journal (backup → mark-running → write → stamp → clear-running) restored crash-safely on boot.
- **C3 — test fixture must be BUILD-TIME excluded.** A writable `nulo:test:*` flag gates *firing*, not *shipping*. Use the repo's proven 3-layer pattern (static-false const + DCE + negative bundle-grep, `chrome-storage-proof-gate.ts:37-43`), and add the fixture's marker to the hardcoded grep list in `.github/workflows/_build-extension.yml:79`. A migration-in-an-array isn't DCE-friendly like a dead-`if` — gate via a static-false-const spread and PROVE tree-shaken. **Pushback on §7(b): a shipped, always-on, identity (no-op) v2 migration may be SAFER to ship than a DCE-gated fixture — it eliminates the entire C3 surface.**
- **C4/H7 — crypto-vector contract.** Move the `wallet-crypto/README.md:37` + `extension/README.md:82` rewrite to Phase 2 (co-located with the `migrate.ts` deletion; between Phase 2–4 the safety-critical pointer dangles). DEEPER: a vector/KDF rotation **fundamentally cannot data-preserve pre-unlock** — secrets are encrypted under the old KDF, re-encryption needs the password, the migrator runs locked. So the contract is "vector change ⇒ re-encrypt-on-next-unlock OR documented reset," NOT "just a numbered migration."

## High
- **H3** — don't silently remove a stale `nulo:core:storage-version` + init-at-max; that destroys the one breadcrumb proving a non-fresh install. LOUD dev-assert when it's present (contradicts the reinstall assumption).
- **H4** — `ctx.local.rows/setRows` must mirror EntityStorage `${root}@` scan + JSON parse EXACTLY, and must NOT trigger the malformed-row auto-delete (`entity_storage.ts:47-60`) during a migration read (would make the backup the only copy). Define atomic multi-root commit.
- **H6** — backup retention security: clear-after-success ONLY for secret-bearing roots (reject keep-last-N); add the backup key to the reset/uninstall wipe set (`reset.vue:52-61`); bound a backup that persists across failed retries. (H5: confirmed the backup is secret-SAFE — passhash is session-only, never in local profiles; local backup adds no new plaintext.)
- **H8** — "move migration before config.load()" is under-specified vs the `Promise.all` at `runtime.ts:96-101` (pull config.load out, don't serialize migration behind BB init).
- **H9/H10** — READMEs move Phase 4→2; ADD e2e specs for the C1 race (open popup mid-migration) and SW-kill-mid-multi-root (precedent: `sw-resilience.test.ts`).

## Medium (fold)
- **M1** idempotency must be STRUCTURAL — harness runs every migration twice, asserts equality (retry raises the bar MetaMask avoided by never retrying).
- **M2** fail-closed → boot-loop **bricks a wallet** if a shipped migration deterministically throws (Sev-1: locked out of funds). Bound retries → recoverable degraded mode, or at least document + escape hatch.
- **M3** `config.apply()`'s `typeof` guard (`store.ts:50`) silently drops a rename that changes a field's type.
- **M7** journal-now-local is a migration TARGET (secret-adjacent fields), not just doc drift.
- **M9** Phase 2 needs `MigrationContext` adapter + backup-atomicity unit tests.

## Assumption attack (key)
- **Single global version > per-collection**: HOLDS, but its safety is **load-bearing on PXE/IndexedDB staying OUT of scope** (the studies' strongest counter was IndexedDB's independent `onupgradeneeded` versioning). Flag that dependency.
- **Narrow-slice > whole-state**: HOLDS, but it TRADED whole-state atomicity for ergonomics — the backup is the COMPENSATING control, so the backup is NOT optional for multi-root migrations.
- **Always-backup**: HOLDS (`unlimitedStorage` at `manifest.config.ts:39` means the `set` can't fail on quota; store is small) — conditioned on H6 retention.
- Verify Zod is already a dep (else it contradicts "no new dependency").

**To move to approve:** resolve C1–C4 + add the two e2e specs. Architecture is the right design; blocking items are spec/sequencing/enforcement gaps.
