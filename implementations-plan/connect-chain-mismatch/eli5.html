Blueprint · light · connect-chain-mismatch

Connect on another chain without a dead end

When an app on Testnet asks to connect while the wallet sits on Alpha V5, the wallet says you have no account on Testnet and refuses. You do have one: it just has not been written down yet, because the wallet only prepares an account for the network you are currently looking at. This plan makes the wallet prepare it the moment an app asks, tells you plainly which network the app is on, and offers to move the wallet there. You can also just approve and stay where you are.

Why this tier

Light. Novelty low (the derivation already exists), blast radius low (one popup and one dispatcher helper), nothing irreversible, no migration, no external service, and security sensitivity low: the app can only pick among networks the wallet already knows, and you still choose which account to share. Zero high-risk dimensions.

Phases

1. The wallet prepares the account on demand

When an app asks for accounts on a network with none yet, the wallet derives that network's default account first, then lists it. Same routine the network switch already uses, with two limits: never for a user-added network that needs a live node check, and never when the chain already has any account (even a hidden one). Those cases keep today's error, now naming the network and the remedy.

Proves itself by: wallet-bridge + service unit tests (prepares once when empty, never when not, refuses the node check, re-reads the list) + lint + typecheck. bun run test in packages/wallet-bridge · bun run lint · bun run typecheck

2. One shared "switch network" routine

The Settings page already switches networks safely (it refuses while a send is in flight and recovers if the save fails). That routine moves into a small shared piece so the connect popup uses the exact same rules and messages.

Proves itself by: ten-plus unit cases on the shared routine + lint + typecheck. bun run test src/composables/useNetworkActivation.test.ts in apps/extension

3. The popup says which network, and offers the switch

A quiet banner: "Connecting on Testnet. Your wallet is on Alpha V5. Approve as is, or switch to see Testnet balances." with one action, "Switch wallet to Testnet". After switching it reads "Wallet switched to Testnet". Approve is never blocked by this; the buttons are only held for the seconds a switch is running. The line under the app's name says "is requesting permissions on Testnet".

Proves itself by: unit tests for the chain lookup, the design Banner test, popup tests, lint, typecheck, and the complexity baseline unchanged. bun run test src/popup/windows/capabilities · bun run baseline:complexity

4. A real browser test of the exact bug

The test wallet stays on Testnet, the test app connects on Local Network, asks for accounts, sees the banner and an account. One test approves as is; the other clicks the switch first. Both check the app receives the address. Fully inside the local sandbox.

Proves itself by: the new network e2e spec green, plus the existing accounts spec. bun run e2e:agent tests/e2e/network/cap-chain-mismatch.test.ts

5. Docs and wrap

Plan index, lessons, the e2e README line, and the full local gate.

Proves itself by: bun run audit:vue green (typecheck, tests, lint, build).

Human context

Accounts in Nulo are per network: the same secret gives a different address on Alpha V5 and on Testnet. The wallet writes an address down only when it first needs it, so a wallet that has only ever been on Alpha has no Testnet address on file. Apps connect to one network of their choosing, and everything the app does later happens on that network regardless of what the wallet's home screen shows. That is why "just approve" is safe today whenever the address exists, and why preparing it on demand closes the gap.

Open questions

  • Custom networks. Preparing an account on a user-added network would mean contacting its node. Decided after codex: an app never gets to trigger that; such networks keep the clear error until you switch to them yourself.
  • Failure handling. If preparing the account genuinely fails (a lock landing at the wrong instant), the app receives an error like any other failed request. Decided after codex: a failure is not evidence that you have no account.
Codex audit

approve after four rounds.
