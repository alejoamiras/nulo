What's a capabilities popup?

When a website (a "dApp") connects to your Nulo wallet, it doesn't just say "let me in." It hands the wallet a list of permissions it wants — read my accounts, send transactions on this contract, simulate things, etc. The wallet shows you a popup with that list, and you decide which to grant.

Each item in that list is called a capability. There are six types today:

  • accounts — see your account addresses, register tokens, optionally create scoped signatures.
  • contracts — register and read contract metadata on this network.
  • contractClasses — read contract class metadata.
  • simulation — run "what would happen if I called this?" locally, without sending anything.
  • transaction — request that you send transactions on certain contracts.
  • data — read your address book and private notes/events; register senders for decryption.

Granting a capability is NOT the same as letting the dApp do those things directly. It's just opening the door so the dApp can ask. For example, granting the transaction capability does not mean the dApp can quietly send sends. Every send still pops up another approval window. The capability is the gate; the per-call popup is the lock.

What's wrong with the current one?

Three things, all related to trust:

1. It lies, a little

The popup currently says "Submit transactions to the network on your behalf" for the transaction capability. Read in isolation, that sounds like blanket authority — "say yes here, I'll do it without bugging you again." That's wrong. Every send still triggers a popup. The current copy was honest about this in a single small footnote ("Each transaction still requires your approval") but the headline contradicted it.

Similarly, the accounts capability has an optional flag called canCreateAuthWit — short for "create auth witness". The detail panel says "Create auth witnesses." If you don't know what an auth witness is, that sentence is meaningless. If you do, it sounds like you're granting general signing power. The reality: an auth witness is typically a scoped signature, checked against your other granted permissions (transaction / simulation scope) before it's signed — narrower than "sign anything." But the scope-check is conditional: if the dApp has no transaction or simulation capability, only the account-level check applies; for raw-message authwits, there's no call-semantic check at all. So the honest framing is "may also request auth witnesses for shared accounts" — which is what v2.1 lands.

2. It's loud in a quiet family

Nulo's design is brutalist — sharp borders, monochrome surfaces, monospaced uppercase labels, sparing use of color. Look at the execute popup or the verify popup: borders and mono text, no chip backgrounds. But the capabilities popup is full of saturated chips: red HIGH / yellow MEDIUM / green LOW for risk, green check-circles in every checkbox, an orange "previously denied" badge. Visually it doesn't belong with its siblings.

3. It tells you less than it could

The detail panel shows scopes like:

  0xabc...123
    fn: transfer_in_private

That's fine. But the execute popup, which is the next surface the user sees, decodes function names into friendly labels ("Transfer (private)") and resolves contract addresses against the local address book (if you've named one of these contracts "Aztec Bridge", you'll see that name). The capabilities popup doesn't. Two popups, same data, different decode depth.

The seven steps to fix it

The plan has seven phases. Each one is independently shippable — no phase blocks reading the next — but they're ordered to make the layer-rule violation go away first.

Phase 0 — Move the capability metadata to a shared place

Today, the labels and descriptions for each capability live in three different files: the popup, the settings page helper, and the settings list helper. Three copies. The popup's copy lives in a "window-level" folder; the settings copy lives in a "settings module" folder. The repo has rules (enforced by Biome) about which folder can import from which — settings can't reach into windows. So we can't just point all three at the popup's file.

Solution: move the metadata into a lower-layer folder that both can import from. One source of truth. Pure data; no Vue, no Chrome APIs.

Why first: every later phase touches both surfaces. If we don't move the metadata first, we either lie about "single source of truth" or violate the layer rule.

Phase 1 — Rewrite the copy

Replace the dishonest labels with honest ones. "Send transactions" gets a clarifying sentence "Each transaction still requires your approval." "Account access" replaces "Share your accounts" and explicitly mentions both the read path AND the always-present registerToken path. The data capability stops claiming it's only "private notes" and acknowledges it also covers the address book and the registerSender write path.

For unknown capability types (a future-proofing case): the headline becomes the constant string "Unknown permission" instead of the raw type from the wire.

Why: the current copy contradicts itself across the head + detail panel. v2 makes them agree, and grounds the claims against what the protocol actually does.

Phase 2 — Replace the colored chips with brutalist mono glyphs

The risk indicator becomes three monospace tokens: ▲ HIGH, ● MED, — LOW. No color. Same information, fits the family.

Checkbox check-icons turn from green to "primary" (matches the rest of the popup family).

The "previously denied" badge keeps an orange border — both audits independently agreed the all-mono treatment we initially proposed was too quiet for a warning. The family does have targeted orange accents (the verify popup uses one for non-ASCII hostnames; the signer strip uses one for mixed signers). Keeping orange-on-transparent matches that pattern.

The new "UNRECOGNIZED" badge for unknown capability types gets the same orange-border treatment.

Why: visual consistency with the popup family. Mono surfaces, targeted accents, no chip fills.

Phase 3 — Decode the scopes more honestly

For each scope row, show both the raw method id AND the friendly label (if we recognize the method). Example:

  0xabc…123  (@Aztec Bridge)
    fn: transfer_in_private  ·  Transfer (private)

The raw method id is the authoritative thing. The friendly label is an annotation. We don't replace one with the other because humanizeMethodName is many-to-one — three distinct methods (transfer, transfer_in_private, transfer_private_to_private) all collapse to "Transfer (private)". Showing only the friendly label would hide which one the dApp is asking for.

Contract addresses get the same treatment: raw trimmed address as primary, parenthetical (@local-contact-name) annotation only if the user has named that address in their own address book.

Contract class IDs (a different beast, despite looking like addresses) are rendered as plain trimmed strings — no contact lookup, no name resolution.

Strings on the wire (cap.type, function names, contract addresses) all pass through a sanitizer that strips bidi-control unicode characters (which can flip text direction and visually scramble labels) and clamps long strings.

Why: a careful user verifies what they're approving. Raw IDs + sanitization keep the dApp from cosmetically misrepresenting a scope.

Phase 4 — Popup-level orchestration polish

Section headers say "New permissions requested" / "Already granted." The DappIdentityBlock action label says "is requesting permissions."

Unknown capability cards default to unchecked. Today, every card defaults to checked; if you click Approve without thinking, you grant the unknown one too. v2 forces a deliberate click for anything the wallet doesn't recognize. The risk indicator is forced to ▲ HIGH for unknown types.

Why: misclicks on unknown capabilities can persist in the session and a future wallet version could honor them. Default-off makes the misclick path harder.

Phase 5 — Settings page parity

The settings → connected apps → [dApp] page shows the same capability detail panel. Inherit all the visual changes from Phase 2-3 (mono, raw IDs, address rendering). Rename "Granted capabilities" → "Granted permissions" to match the popup.

The connected-apps list (the top-level summary view) used a third, separate set of short labels — they now read from the same source as the popup.

Why: visual + terminology consistency across the whole capability-related surface area. One source of truth, top to bottom.

Phase 6 — Test sweep

Run the unit tests, the typecheck, the build, and the audit:vue gate (which bundles all four). Then run the 9 end-to-end network tests that exercise the capability + send-tx + authwit paths. Then a manual smoke through the unpacked extension to eyeball the visual changes.

Why: codex's first audit pointed out that running only one e2e test (the basic capability request) wasn't enough — we need the authwit + send-tx-with-feePayer tests to confirm the protocol claims in the copy are actually true.

The security bit (worth reading)

A capability popup is one of those rare UI surfaces where every byte the dApp can influence is a potential attack surface. The plan treats every dApp-controlled field as untrusted:

  • Capability type. Could be an unrecognized string designed to look friendly. v2: never used as the head label; only displayed in a sanitized + clamped + escaped mono row.
  • Function names in scopes. Could be a real-looking method that maps to something else, or a long Unicode string with bidi-control chars to flip text. v2: length-clamped, control-char-stripped, displayed with the raw alongside any friendly annotation.
  • Contract addresses in scopes. Could be addresses the user has named misleadingly in their address book. v2: raw address is always primary; the local name is parenthetical and clearly marked with an @ prefix.
  • "Previously denied" badge. Already protects against re-request mis-clicks. v2 keeps it visually loud (orange border) but in the brutalist style.

One thing the plan does not fix: the dispatcher's current handling of capability upgrades (e.g., a dApp granted scope ["A"] later asks for ["A", "B"]). For non-accounts capability types, the diff today is type-only, which means the upgrade slips through without a popup or the "previously denied" badge. That's a separate, known issue filed as wallet-sdk-capability-field-diff. v2 documents this gap honestly and does not pretend the badge covers it.

Open questions for you

1. "Capabilities" → "Permissions" rename scope

The plan renames the user-facing word from "capabilities" to "permissions" in three places: the popup section headers, the popup identity-block action label, and the settings detail page header. The internal type names (the Capability type, the cap-* testids) stay — they're protocol-level.

Confirm — full rename across user-facing copy? Or popup-only?

2. Default-OFF on unrecognized capability cards

If a dApp asks for a capability type the wallet doesn't know about, the card defaults to unchecked. The user has to deliberately click it to approve. This guards against future protocol drift and against attackers padding their request with unknown types hoping for an autopilot Approve click.

Confirm — default-OFF on unknowns is the right call?

3. PREVIOUSLY DENIED badge: orange border, mono text

Both audits agreed that the all-mono version was too quiet for a warning state. The family does use targeted orange accents elsewhere. v2 lands on orange border, transparent fill, mono uppercase text. The new UNRECOGNIZED chip uses the same treatment.

Confirm — keep an orange accent on warning chips?

4. The "May" hedge in the accounts head description

The accounts capability can include an optional flag for creating scoped signatures. Some grants will have it; most won't. The proposed head description hedges with "May also create scoped signatures…" The detail panel below decodes whether that flag is actually set.

The hedge is honest but reads a little awkward. The alternative is to drop the clause entirely and rely on the detail panel — but many users never expand the detail panel, so dropping the clause means signing flag is invisible at a glance.

Keep the "May" hedge? Or drop it and rely on the detail panel?

5. Risk glyph choices: ▲ ● —

HIGH gets a filled triangle, MEDIUM a filled circle, LOW an em-dash. The em-dash at 10px in a mono font may render thinner than the triangle/circle (a subtle visual inconsistency). An alternative is the middle-dot (·) for LOW, which is geometrically closer to the others.

Keep — for LOW, or swap to ·?

6. Confirmation-policy footnote?

The popup copy assumes the default session policy. A power user can tighten the policy in settings, which would cause more operation types to trigger popups. The plan does not add a footnote about "if you've changed your confirmation policy, more steps may require approval." The settings page is the right surface for that explanation; we'd rather not clutter the popup.

Confirm — no policy-related footnote in the popup?
