## Core architecture (convergent across all three plans)

The shared part of both flows is the **orchestration**: state refs → name validation → passkey ceremony / secret entry → the `managers.profile.import*`/`create*` call → error routing. The part that differs per shell is the **post-create/import activation + routing tail**, and it differs *architecturally*:

- **Popup** relies on `popup/app.vue`'s `onActiveProfileChanged` SW-event listener (`popup/app.vue:130-132`) to run the heavy bootstrap and flip `appStore.isLogined`. Popup import does no bootstrap; popup create *waits* on that listener (`while (!appStore.isLogined) sleep(100)`) then runs a small extra sequence.
- **Onboarding** has no such listener (it only `hydrateKnownProfile` once at mount, `onboarding/app.vue:59`), so it calls `bootstrapActiveProfile` (`useProfileBootstrap`) explicitly.

`bootstrapActiveProfile` does strictly *more* than popup-create's manual sequence (`ensureDefaultAccount`, `setupActiveAccount`, profiles-list refresh, `syncTransactions`; `useProfileBootstrap.ts:63-77`) and differently (popup writes `nulo:ui:activeAccount`; bootstrap does not). The service layer already opens the session (`profile/service.ts:104,214,761,788`); the shells differ only in how the UI *reacts*.

⇒ **Decision: the composable owns everything up to activation and injects a per-shell `onComplete(profile): Promise<void>`** (activation + routing + toasts) **plus a few narrow reporting adapters** (`showErrorLog`, `notifyImportFailed`/`notifyCreateFailed`, `openToast`). The composable *body* never bootstraps, routes, or toasts — those live in the injected callbacks (so e.g. onboarding's injected `onComplete` legitimately *does* bootstrap; the constraint is on the composable body, not the callback). This reuses the seam `useFullBackupImport({ completeImport, showErrorLog, … })` already established — proven, not novel; the same single `completeImport`/`onComplete` reference is threaded into `useFullBackupImport`, so there is no double-injection. Composable returns **flat** refs/computeds/handlers (no nested controller object); **`onKeydown` stays page-local** (the two create shells have different submit architectures — see Phase 3); templates stay page-local (they differ structurally) and bind to the returned refs. Scope discipline (codex): the composables must NOT reach for `router`, stores, `managers.account`, or bootstrap helpers — those stay in pages/injected callbacks.

## Security & Adversarial Considerations
- **WebAuthn ceremony integrity** — the relocation must not alter abort/cancel/`UserRejectedError` normalization, `allowedCredentials`, PRF wiring, or the create→get fallback; a regression could mishandle cancel or weaken the non-dismissible overlay during a live OS prompt. The relocated dialog test is the regression net.
- **Secret material in memory** — seed/private key refs: error routing must never embed raw secret values in `fillError`/notifications/logs (existing `console.error("Failed to import profile:", err)` logs the error, not the inputs — preserve). Zeroing stays page-owned; do not "helpfully" add it to popup (behavior change + out of scope).
- **Error info leak** — keep generic typed strings ("Wrong password"); the catch-all is preserved per shell, so no NEW exposure is introduced (onboarding already surfaces `err.message`).
- **Double-create race** — preserve the pre-fetch latch (two profiles otherwise); Quirk 2 removes one Enter double-fire vector.
- **Ceremony reentrancy** — `usePasskeyCeremony.runCeremony` rejects if one is in flight; the `isImporting`/`isCreating` latch double-guards. Preserve both.
- **Layering** — moving the dialog out of `@/popup/**` *tightens* onboarding's import story (removes a cross-shell `@/popup` reach). No new deps, no crypto changes, `bun.lock` untouched → supply-chain / least-privilege N/A.
