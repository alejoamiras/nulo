Why this tier was chosen

mid for the campaign (one plan + a competing sequencing outline + a two-model audit + a final fresh-Codex pass). The rubric actually scores 2+ HIGH (security-sensitivity + blast-radius on the auth boundary; irreversibility on the crypto/storage change) — normally deep — but the findings and fixes are already pinned by the audit, so planning uncertainty is low. Instead of over-ceremonial-izing the index, the two genuinely risky fixes (the dispatcher and the crypto bearer) each get their own deep design pass at build time. The audit already earned its keep: both reviewers refuted a wrong assumption in my first draft (see "What the audit changed").

The 11 fixes (each becomes its own PR)

Colour = design rigor before coding: red = deep, amber = mid, green = direct/light. Each "proves itself by" line is its local validation gate (unit PRs get no GitHub CI — that runs once on the promote PR).

A · Dispatcher trust-boundary DEEP Critical + High

The big one. A malicious website can currently (1) get the wallet to silently sign a blank cheque (a raw hash), and (2) get approval for "Transfer" while "Approve" actually runs. Fix: reject raw hashes, and — at all three places it happens — make the wallet check that the function actually being run matches the one that was authorized, rejecting mismatches. Plus validate website request data on the wallet's own side.

Proves itself by: wallet-bridge + execution unit tests (mismatch/raw-hash rejected at each sink), a faucet serialization test, and the network e2e suite (real dApp flows still work).

B · Honest approval screen LIGHT→MID

Stop the confirmation popup from being fooled: clean up website-supplied text (no invisible/right-to-left trickery), verify the shown name against the real function, and show the hidden "can create auth-witnesses" permission that today is granted invisibly. Depends on A.

Proves itself by: component tests (including tricky-Unicode cases) + smoke e2e.

C · Chain-identity double-check MID

The wallet checks which blockchain it's on, then asks again and signs using the second (unchecked) answer. Fix: sign using the answer it already validated.

Proves itself by: aztec-runtime unit tests + network e2e (signing path).

D · Discovery flood limit MID

A page can spam the wallet with "are you there?" messages. Fix: rate-limit them, cap the queue, reject unknown chains before popping a window.

Proves itself by: wallet-bridge unit tests + network e2e (discovery path).

E · Safe backup restore MID needed before L

A tampered backup file can silently switch off a security setting and leak the password bearer. Fix: validate what a backup is allowed to change; never silently downgrade security.

Proves itself by: config/import unit + component tests + smoke e2e.

F · Content-Security-Policy tighten DIRECT

Add an image-source rule so a website logo can never phone home. One-line hardening (currently a dormant risk).

Proves itself by: the build succeeds + smoke e2e (popup renders).

G · Who-sent-this checks (offscreen) MID

The hidden crypto document accepts commands without checking the sender is the wallet's own service worker. Fix: verify the sender (and reject page/content-script senders), and give Firefox's fallback window a token so a stale one can't double-handle secret work.

Proves itself by: messaging unit tests (incl. Firefox sender shapes) + Firefox build + network e2e.

I · Tamper-proof website permissions MID

Stored website-permission rows aren't integrity-checked. Fix: validate + clamp them on load and add a tamper-detecting seal keyed to your profile secret; drop rows that fail.

Proves itself by: wallet-core unit tests + a real grant→reconnect check on network e2e (a bad seal could brick reconnects).

J · Storage read can't brick startup DIRECT

One corrupt storage row currently crashes startup. Fix: mirror the existing "skip the bad row" handling.

Proves itself by: wallet-core unit test (malformed row) + lint.

K · Clipboard secret hygiene LIGHT

Exporting your seed/private key leaves it on the clipboard forever. Fix: warn, and clear it after a delay.

Proves itself by: component tests + smoke e2e.

L · Password bearer redesign DEEP after E · crypto

The token that silently re-opens your session is a weak, password-equivalent hash. Fix: replace it with a random token that unwraps a session-stored encrypted secret (no longer crackable / password-equivalent), and actually wipe secret buffers. Touches frozen crypto test-vectors, so it pairs with a storage-version bump (a destructive wipe — safe because there are no production users). This is the riskiest fix and the one decision I need from you (below).

Proves itself by: wallet-crypto unit tests (new vectors + wipe) + migration assertions + network e2e (unlock/restore across a service-worker restart).

What the audit changed (so you can trust the plan)

  • My first draft put the "check the function matches" fix in the wrong layer. Both reviewers proved with code that the contract info isn't available there — it must go in the execution layer. Fixed.
  • The fix isn't one place, it's three — including the silent auth-witness path. Fable found the third. Now all three are in scope.
  • "Zeroize the passkey secret" was a no-op (the type it's stored in can't be wiped). Now the plan moves it to a wipeable buffer first.
  • Per-fix PRs into the integration branch get no GitHub CI (workflows only run for PRs to dev/main). So each fix runs its full gate locally; the one promote PR runs real CI.
