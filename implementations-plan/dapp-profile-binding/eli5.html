Dapp Profile Binding

Profiles exist so your identities stay separate. But today, a website connected to your wallet under profile A keeps its live connection when you switch to profile B — and if B ever approved that site too, the site's requests quietly start answering from B's world instead. Even without that, the site learns that A and B live in the same wallet — the exact thing profiles are meant to hide. Two smaller flaws ride along: closing a tab at the wrong moment makes the wallet needlessly re-run its emoji verification on every future reconnect, and a quirk in how responses are packaged can corrupt values a website receives.

What changes, in plain words

  • Connections belong to one profile, forever. Every connection is stamped at birth with the profile that approved it. Switch profiles, and connections stamped to the old one are cleanly disconnected — the site sees the same "disconnected" it would if you'd clicked disconnect yourself, and can simply reconnect under the new profile if it's welcome there.
  • Even split-second stragglers can't cross identities. A request already in progress during the switch finishes entirely under the profile that accepted it — the lookup that used to "helpfully" read whichever profile is active now uses the stamp instead. And an approval caught mid-handshake by a switch is refused outright rather than mis-assigned.
  • No more phantom re-verification. The little marker that says "this connection still needs the emoji check" is cleaned up when its tab closes and expires on its own as a backstop — a closed-at-the-wrong-moment tab no longer haunts future reconnects. First-time verification is enforced by a separate mechanism and is untouched.
  • Honest response packaging. The serializer confused "the same value appears twice" with "infinite loop" and stamped the second appearance "[Circular]". It now only flags true loops.

Why this level of ceremony (tier: mid)

Profile isolation is a core promise of the product — one high-risk dimension — but the surface is one service layer with well-tested teardown machinery already in place. Mid tier: plan, competing options, two independent reviewers, fresh-eyes final pass.

Phases

Phase 1 — The two clean fixes

Fix the response serializer (with tests adopted from the audit's proof) and give the verification marker its timestamp and cleanup.

Proves itself by: the service layer's unit suites, extended, all green.

Phase 2 — Stamp, guard, and switch teardown

Stamp connections with their approving profile, refuse mismatched requests (politely — the site gets a proper error, then the disconnect), disconnect old-profile connections on switch, and anchor the request pipeline to the stamped identity so nothing can cross even mid-flight.

Proves itself by: a matrix of unit tests covering every ordering the reviewers could think of — switches landing before, during, and after requests and handshakes.

Phase 3 — Prove it in a real browser

A new live-network rehearsal: connect a real test dApp under profile A, switch to B in the wallet, watch the dApp show "disconnected", confirm a follow-up call fails cleanly, reconnect under B. This drives the in-wallet profile switcher in automation for the first time — some test scaffolding gets built along the way.

Proves itself by: the full check battery plus the live-network suite, run solo, all green.

Human context

The reviewers earned their keep a third time. One proved the original plan's "stamp at connection time" read the wrong source — a switch during the handshake could stamp the NEW profile onto a connection the OLD one initiated (now the approval itself carries the identity, and a mismatch refuses the connection). The other showed a request already inside the pipeline could still consult the new profile's permissions mid-flight (now the pipeline is anchored to the stamp). Both changes came out of a formal reject verdict — the process working as designed.

Open questions
