Why every PR hangs orange — and the one-line cause

For weeks, every pull request on dev and main has shown three required checks stuck on "Expected — Waiting for status to be reported", forcing you to merge with --admin every single time. It was never flaky CI, missing signatures, or stacked branches. The cause is a name typo in branch protection: it requires checks called Quality / Status, but GitHub Actions actually produces a check called just Status. Those two strings never match, so the required checks can never report — they hang forever. This plan renames the checks so the names are unique, re-points branch protection to the real names, and proves the fix with a live PR that merges cleanly with no --admin — while a deliberately broken PR still gets blocked.

Why this tier was chosen mid

Rubric: 2 dimensions are HIGH — blast radius (this is the merge gate for the whole repo) and external coupling (it depends on GitHub's exact check-name matching semantics). Two HIGHs would normally push to deep. It's held at mid because the change is bounded CI config, fully and instantly reversible (branch protection is one API call to revert), and the real risk is retired by doing it live and watching — observe the produced names before writing, keep the old gate in place until the new one is confirmed green, and run a negative test — not by more planning ceremony. The plan still got the full mid treatment: a competing approach, a dual adversarial audit (codex + a Claude planning agent), and a final fresh-context codex pass.

The two things that confused us for so long

1. The name rule. A normal GitHub Actions job produces a check named exactly its job's name: — just Status, with no workflow prefix. Only reusable (uses:) jobs get a Workflow / Job two-part name. So Quality / Status was a name that can never be produced — someone typed it into branch protection by hand, guessing at GitHub's display format. The fix is to give each gate a unique one-word name like quality-status and require that.

2. There are actually two locks on the door. The repo also requires signed commits. --admin bypasses both the broken check-name lock and the signature lock at the same time — which is exactly why we kept mis-diagnosing it: the symptom (forced --admin) couldn't tell the two locks apart. We got this wrong twice (once blaming signatures, once blaming the name). This plan refuses to guess a third time: the name mismatch is the proven cause of the orange hang, and Phase 3 measures whether signatures add a second block — the docs will say whatever the live test shows.

Phases

Phase 1 — Rename the three stuck checks

Give the aggregator job in the Quality, Network e2e, and Smoke e2e workflows a unique one-word name (quality-status, network-e2e-status, smoke-e2e-status). Only the label changes — the pass/fail logic is untouched.

Proves itself by: bun run lint:actions green, and the job's logic is byte-identical except the name.

Phase 2 — On dev first: look at the real names, then re-point the lock (carefully)

After the rename ships to dev, read the names GitHub actually produced on a live PR (never guess). Then update branch protection — but add the new names while keeping the old ones first (so the gate is never open for even a moment), confirm the new ones are green, and only then remove the old broken ones. The update is done as a careful read-then-write so it can't accidentally flip main's "branch must be up to date" setting or drop another check.

Proves itself by: the live dev PR shows the three checks matched (not "Expected"), and dev's config lists exactly the three new names.

Phase 3 — Prove it both ways on a real dev PR

Positive: a normal signed PR goes green and merges with a plain gh pr merge --squash — no --admin. Negative: a PR with a deliberately broken check (break a lint rule so it really runs and fails) still gets blocked. Both matter — "green merges" alone could also mean "the gate is gone."

Proves itself by: positive PR merges clean without admin (squash signed); broken PR is refused without admin.

Phase 4 — Promote the rename to main, then re-point main

main can't be re-pointed until the rename is actually on main — otherwise a PR branched from the old main still produces the old check name and re-hangs. So the rename rides a normal promote PR to main, we confirm the new names appear there, then re-point main the same careful way (preserving its strict setting).

Proves itself by: main's config lists the three new names with strict intact, and a main-targeted PR shows them matched.

Phase 5 — Fix the docs that lied

Update the required-check tables in CLAUDE.md + CI.md to the new names, correct the --admin explanation to the true two-locks story (recording what Phase 3 measured, scoped to self-authored PRs), and fix the stale line that calls Smoke "advisory" when it's actually required.

Proves itself by: the brand/path guard is clean and the doc tables match the live branch-protection config on both branches.

Human context

"Branch protection" is GitHub's rule that a PR can't merge until certain named checks pass. It matches by exact string. "Required signatures" is a separate rule that commits must be cryptographically signed. --admin is the override that ignores all protection rules — handy in emergencies, but if you need it on every merge, something is misconfigured. That "something" is this name typo.

Open questions — all resolved by the final audit

The final fresh-context codex pass rejected the first consolidated draft and closed each of these. Nothing here is left for you to decide.

  • Does breaking a lint rule actually turn quality-status red? Yes — confirmed by tracing the aggregator: lint always runs on PRs, and its failure propagates to the "always" aggregator, which exits non-zero. The negative test is real.
  • Pin to GitHub Actions' app id? Yes, but observed live at write time, never hard-coded — so a future id change can't silently orphan the check. (And there's no merge queue on this repo, so that re-hang path doesn't exist.)
  • Is the signatures question determinable? Partly yes — GitHub only lets you squash-merge a signed branch when you're the PR author. So for your own PRs (almost all of them), signatures never block, and the orange hang was purely the name typo. The plan states this and scopes the live test to the self-authored case.
  • (New, caught by the final pass) Can main be re-pointed at the same time as dev? No — it must wait until the rename is on main, or in-flight PRs re-hang. This split the rollout into a dev-first, then-promote-to-main sequence, and forced the branch-protection update to be a careful read-then-write that preserves main's strict setting.
