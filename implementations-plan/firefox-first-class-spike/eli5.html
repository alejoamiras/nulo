Blueprint · mid tier · approved 2026-09-18

Firefox, tested like Chrome

Today the Firefox build of the Nulo extension is built and shipped with every release, but nothing ever runs it. This plan makes Firefox a real test target: the same smoke and network test suites that guard Chrome also run against Firefox, on every pull request, every night, and before every release. It also fixes a bug we found on the way: creating a profile with a passkey fails on Firefox.

What the trial run already proved

Four things worked on a real headless Firefox

  • Our test tool (Puppeteer) can see and click inside the approval windows the extension opens. An older note said this was impossible; it was our own popup closing itself when no profile existed.
  • Firefox can be given a fake passkey device for tests, the same way Chrome can. It needs a second helper program (geckodriver) and two browser settings switched on.
  • With that fake device, the wallet's real passkey math (the "PRF" secret it derives keys from) works inside the extension on Firefox.
  • The passkey bug is real and the fix works: after it, the actual "create profile with passkey" screen reaches the home screen.

Why "mid" tier

The work is contained (one app, its tests, its CI) and mostly reversible. Of the six risk dimensions, one scores high: external coupling (Firefox, geckodriver and a browser protocol we do not control). Novelty is moderate, not high, because the risky unknowns were already run. Blast radius is the thing to watch: the shared test helpers guard Chrome's required checks, so the plan never rewrites Chrome's side, it only moves it behind a switch.

The plan went through three hostile reviews. The first draft was rejected by one reviewer and conditionally approved by the other; they agreed on the problems. A fresh reviewer then rejected the second draft on three narrower points: a guard test placed where it would never run, a missing permission on the new workflows, and calling the plan finished before the nightly and release jobs had been seen green. All of it is fixed in this version. The biggest change since the first draft: it rewrote how Chrome's tests find windows. Now Chrome's code is left exactly as it is.

The six steps, each its own pull request

They stack: each builds on the one before. Steps 1 and 2 can also land on their own.

  1. 1

    Fix passkey profile creation on Firefox

    When a passkey is created, Chrome hands back the secret straight away. Firefox says "this passkey supports it" but hands nothing back until you ask a second time. Our code treated that as an error. The fix asks the second time, checks the answer came from the passkey we just made, and keeps the profile's identity intact.

    Proves itself by: six new unit tests covering each branch, plus the full typecheck, test, lint and build gate.

  2. 2

    Firefox manifest housekeeping

    Mozilla now requires new add-ons to declare what data they collect and which Firefox versions they support. We add both, and settle the add-on's permanent ID. The values are your call (questions 1 to 3 below).

    Proves itself by: the manifest unit test, a Firefox build, and Mozilla's own add-on linter reporting zero errors.

  3. 3

    Put the browser behind a switch, Chrome only

    The test helpers assume Chrome in about fifty places: how the browser starts, what the extension's address looks like, how a test closes the browser. This step moves those behind one switch without adding any Firefox code and without changing what Chrome does. A small guard test stops the old patterns creeping back.

    Proves itself by: the full Chrome smoke suite locally, then the complete Chrome CI run (all five network shards, the heavy lanes, the canaries) on the branch.

  4. 4

    The Firefox driver, five make-or-break checks, then the smoke suite

    We build the Firefox side of the switch, then run five short checks before investing further: can tests find windows the usual way, does a real dApp approval window work, does a confirm window work, can the Firefox build send a real proved transaction, and does closing and reopening the browser keep the wallet's data. If the approval window or the proved transaction fails, the network suite on Firefox is not achievable and we stop and ask you. Then the smoke suite runs on Firefox.

    Proves itself by: all five checks printing PASS, then the Firefox smoke suite green twice in a row, Chrome smoke still green, and no leftover browser processes.

  5. 5

    The network suite on Firefox

    The same network tests Chrome runs: the five fast shards, plus the slow lanes that produce real cryptographic proofs. Ten test files stay Chrome-only because they work by killing Chrome's background worker or by a Chrome-only interception trick; each says why when it is skipped.

    Proves itself by: every shard and every portable lane green on Firefox, run locally one at a time.

  6. 6

    CI lanes and docs, all advisory

    Firefox gets its own workflow files for pull requests, plus jobs in the nightly run and the release chain. "Advisory" means a red Firefox job is visible but cannot block a merge or a release. The runbook gets dated switches for promoting them to required later: the release smoke after one clean release, PR smoke after 14 green nights, PR network after 30.

    Proves itself by: the workflow linter and the CI-gating tests before the PR; then the Firefox lanes going green on this step's own pull request. The nightly and release jobs can only be confirmed after merge, so they are a short checklist for you. Until you tick both, the plan is "delivered", not "completed".

Background you need for the decisions

  • Why two helper programs. Puppeteer talks to Firefox over a newer protocol that has no "fake passkey device" command. The older protocol does, and geckodriver speaks it. We run both against the same browser. One extra process per test run.
  • Why Chrome's required checks are safe. The two workflow files that produce the required checks are not edited at all. Firefox results can never appear under a required check's name, and a test pins that.
  • Why the nightly and release jobs cannot be tested before merge. The nightly workflow always builds the dev branch whatever you point it at, and the release workflow can reach the production environment. Running either from a feature branch tests the wrong code and risks side effects, so the plan forbids it.
  • What "same treatment" costs. On every pull request that touches network code, Firefox adds roughly five shard jobs plus the slow proving lanes, each doing a full extension build. This is the option you chose over a thin canary. The account-wide run-start throttle has bitten us before; draft PRs are skipped to soften it.
  • A known local-machine trade-off. geckodriver listens on a local port with no password. Any program on the same machine could drive the test browser. We accept that, the same way we already do for Chrome's debugging port and the local Aztec node, and only local test keys are ever loaded.
Approved by the owner · 2026-09-18

The six decisions, as answered

  1. Add-on ID. wallet@nulo.sh stays.
  2. Data collection declaration. "None".
  3. Minimum Firefox version. 153. That is above the version where passkeys start working, so no extra hiding logic is needed. The add-on will not install on older Firefox, including the long-term-support release, and the test launcher refuses to run on anything below 153.
  4. Two canaries stay Chrome-only. Accepted for now; no follow-up scheduled.
  5. CI cost. Confirmed. Firefox and Chrome lanes run side by side as separate workflows, so Firefox adds job starts and runner minutes, not waiting time, as long as runners are free.
  6. Two passkey prompts. Accepted as is; no extra dialog copy.

Also approved: the six-PR split, the validation plan, and no whole-codebase hardening pass.
