# Fable (Opus, fresh hostile) — plan audit, round 1

**Verdict: conditional approve** (with the 5 conditions below). Findings folded into plan.md v2.

## HIGH
- **H1 — the parity test proves a tautology.** Identical seeds → a deterministic engine trivially yields identical output (that's #246, already proven). It says nothing about the only thing that differs: the scratch input is a profile-scoped / aggregated / projected SUBSET, not the live rows. Concretely: `account.backup()` filters by profileId (`account/service.ts:224`); `transaction.backup()`/`auth-registry.backup()` are AGGREGATED from live queries (networks×accounts) (`transaction/service.ts:296-301`, `auth-registry/service.ts:411-416`) — they can DROP rows and return `undefined` with no networks. A future migration that reasons across rows (e.g. backfill a FK by matching content) writes wrong values on a backup but passes parity. Fix: enforce a row-local constraint (no cross-row/cross-profile/aggregate/cardinality logic) via a CI test, OR a real parity fixture (multi-profile superset live vs single-profile projected backup).
- **H2 — fpc "rehydrate isProtocol" is backwards; fpc is a faithful `root` slice.** `StoredFpc = Omit<FpcInfo,"isProtocol">` (`fpc/service.ts:38`); stored + restored rows have no `isProtocol` (`:478`); it's read-time decoration (`decorate()`, `:114`). Backup element === on-disk row already. Rehydrating it makes the scratch store DIVERGE from what a real migration sees, and computing the real value needs async protocol derivation → violates the no-PXE/no-crypto least-privilege claim. Delete the fpc projection.
- **H3 — config IS a lossy projection, not a faithful `value`.** `props = Object.entries(this.config)` over a typed `Config`; load/apply only copy keys already in the default (`config/store.ts:14,46-54`). Any on-disk `nulo:config` key not in the current `Config` class is silently dropped by `backup()`. A config key-rename/reshape — the migration `runtime.ts:103-105` explicitly anticipates — reads it on live, finds nothing on the folded backup → silent loss. Reclassify config as `projection`; add a fixture proving a config-rename preserves keys outside the typed class.

## MEDIUM
- **M1 — account-state lane keyed to the wrong axis.** account-state slices carry Aztec `instance`/`artifact` whose shape drifts with `aztec-version` (`full.vue:130`), NOT the storage schema. A `backup-schema-version` number can't express "shape changed because Aztec bumped." The lane must key off `aztec-version` (and it forgoes journal/guardCommit/run-twice — the very things C-scoped is praised for inheriting).
- **M2 — "same migrations array" vs "split out the 9001 fixture" is a real contradiction.** The split means the backup path uses a DIFFERENT (real-only) array than live boot, undermining the "same objects, no divergent copy" selling point over D. Defensible but must be stated, not glossed.
- **M3 — reject-on-missing-slice can't distinguish tampering from a network-less backup.** transaction/auth-registry/account-state `backup()` return `undefined` with no networks; the export loop drops undefined slices (`full.vue:139`). "Missing slice a migration reads → reject" would false-reject a valid network-less backup unless these are explicitly optional-as-empty.
- **M4 — cardinality-changing migrations break the downstream ID-remap.** I-C only bars renumbering. A migration that adds/drops/splits rows desyncs `remapIdInBackupData` (`full-backup-helpers.ts:94`) + the token-balance remap (`useFullBackupImport.ts:369`). Extend I-C to forbid cardinality changes.
- **M5 — the engine now processes ATTACKER-controlled input (threat-model shift).** verify-then-migrate is a genuine improvement, and a plain checksum isn't authentication (acknowledged) — but the consequence is under-weighted: an attacker recomputes SHA-256 and feeds adversarially-crafted rows through the migration `up()` bodies, a surface that didn't exist when data flowed straight to restore. The engine's fail-closed was audited against OUR-OWN-corrupt storage, not hostile input. Standing rule: every migration `up()` must treat its input as hostile.

## LOW
- **L1 — master-key handling is structurally sound** (top-level sibling of `data`, not a slice; can't enter scratch via `normalize(data)`; integrity-gated; flows only to `profileService.restore`). One tension: Phase-5 smoke e2e MUST embed a working test master-key for restore to succeed — clarify "never in the migration-scratch fixture" vs the necessary end-to-end key.

## Claims tried and could not break (not padded)
Checksum trust ordering (verify→migrate→drop) sound; account-state non-storage carve-out correct (genuinely PXE); transaction keyed by `hash`, restore preserves it (no remap needed).

## Conditions
1. Delete fpc projection → plain `root` (H2). 2. Reclassify config as `projection` + rename-preserving fixture (H3). 3. Replace the tautological parity test with superset-vs-projection OR an enforced row-local constraint + CI test (H1). 4. Extend I-C to forbid cardinality changes (M4). 5. Key account-state off `aztec-version` + mark the aggregated slices optional-as-empty + resolve M2 in the text (M1/M3/M2).
