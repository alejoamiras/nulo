## Architecture — C-scoped (consolidated pick; codex + fable converged independently)
The live migrations transform storage ROWS via `MigrationArea`. A backup is profile-scoped, per-service slice-arrays consumed by `service.restore()`. Where the vN→current transform lives was the fork; four candidates were drafted:

- **C-scoped (PICK).** Normalize each mapped slice into a **fresh in-memory `MinimalStorageArea`**, seed `nulo:schema:version = backup-schema-version`, run the **real `Migrator` verbatim** (same `migrations` array, same class the live boot uses), read rows back, re-slice, hand current-shape slices to the unchanged `service.restore()` pipeline. A **small hybrid carve-out** excludes slices that are not `chrome.storage.local`-backed (`account-state` → PXE) or are lossy projections needing rehydration (`config`, `fpc`, `auth-registry`).
- **A. Adapter-over-MigrationArea + custom runner** — reuses migration `up()` bodies but re-implements version-filter, sequencing, staging, failure handling, and the footprint guard. Rejected: duplicates exactly what `Migrator` centralizes (the divergence #246 eliminated). Its adapter is only a building block.
- **B. Version each `service.restore(slice, fromVersion)`** — scatters migration logic into 11 services, forfeits the single numbered source + CI guardrails. Rejected outright (the pre-#246 anti-pattern). Its shape is borrowed ONLY for the `account-state` non-storage carve-out, centralized as one numbered `backupSliceMigrations` list, never scattered.
- **D. Extract a journal-free shared apply-core from `Migrator`** (main's draft) — principled "single source," but **refactors the just-shipped, 10-audit-round engine**. Rejected: the dead journal on a scratch store is inert and harmless, so C-scoped reuses the WHOLE audited engine unchanged — *more* single-source than extracting a core, with a **provable parity test** (run the same engine both ways, assert byte-identical) that D cannot offer without trusting the extraction. D's only edge (no inert journal keys) is bought by filtering reserved `nulo:schema:*` keys on read-back — cheap.

**Why C-scoped wins:** inherits `Migrator`'s ordering, staging, marker validation, run-twice idempotency, and `guardCommit` footprint enforcement (`migrator.ts:258`) **for free and unchanged**; the backup path adds only the slice↔storage registry + the trust-boundary validation. Zero risk to the audited engine.

**Honest tension (audit M2):** the backup path runs a **real-only** `migrations` array (the e2e `9001` fixture split out), so it is NOT byte-identically "the same array" the live boot uses in an E2E-stamped build — the parity guarantee is "same *real* migrations, fixture excluded." This is a slightly weaker claim than the raw "same objects, no divergent copy" pitch over D, but it is still single-source for every real migration (the split only removes a test-only entry), and it is necessary: reusing the live array verbatim would let a backup accept `backup-schema-version` up to `9001` and run the fixture over scratch. Stated, not glossed.

- **Reuse verbatim (zero forks):** the `Migrator` class + its journal/`guardCommit`/idempotency (run over the scratch store unchanged); `Migration`/`MigrationContext`/`MigrationArea`/`StorageRef`/`MinimalStorageArea` types; `defineMigration` (the imperative form); the engine tests' in-memory store fake (export + reuse it as the scratch store rather than a second impl); `EntityStorage`/`ValueStorage` key formats (`${root}@${id}`, JSON-string values) so normalize matches exactly; `EncryptionKey` for the checksum. `defineRowMapMigration` is a thin factory that COMPILES to a standard `Migration` — it does not reimplement the engine.

## The mapping registry (not derivable — explicit, pinned)
`apps/extension/src/wallet/services/backup/backup-migration-registry.ts`. `serviceName → SliceDescriptor`:
```
type SliceDescriptor =
  | { kind: "root";       root; idKey: (v)=>string; optional?: boolean }   // slice element IS the stored row value
  | { kind: "projection"; root; idKey; toStored; fromStored; optional? }   // slice is a LOSSY projection of stored rows
  | { kind: "value-projection"; key; toStored; fromStored }               // ValueStorage, lossy (config)
  | { kind: "non-storage" }                                                // not chrome.storage-backed — carved out
```
`optional: true` = the slice may be legitimately absent (aggregated services return `undefined` with no networks — audit M3); a missing optional slice normalizes as an empty root, NOT a reject. Per-service (verified against the code, post-audit corrections applied):
- `account`→root `nulo:core:accounts`, idKey `v.address` (profile-filtered slice, `account/service.ts:224`)
- `network`→root `nulo:core:networks`, idKey `v.id`
- `token`→root `nulo:core:tokens`, idKey `v.id`
- `token-balance`→root `nulo:core:token-balances`, idKey `v.id` *(I-A: verify exact set-key; note token-balance does NOT profile-filter — `token-balance/service.ts:259`)*
- `contact`→root `nulo:core:contacts`, idKey `v.id`
- **`transaction`→root `nulo:core:txs`, idKey `v.hash`, `optional`** (NOT `id`, `transaction/service.ts:154`; AGGREGATED from networks×accounts, `undefined` when no networks — `:290`,`:296`)
- **`fpc`→root** `nulo:core:fpcs`, idKey `v.id` **(NOT a projection — audit H2).** `StoredFpc = Omit<FpcInfo,"isProtocol">`; the stored row already omits `isProtocol` (it's read-time `decorate()`, `fpc/service.ts:114`), so the backup element === the on-disk row. Rehydrating it would fabricate state a migration never sees on disk AND require async protocol derivation (violating no-PXE). Plain `root`.
- **`config`→value-projection** key `nulo:config` **(NOT a faithful fold — audit H3).** `backup()` returns `ConfigProp[]` enumerated from the current typed `Config` (`config/service.ts:41`), which SILENTLY DROPS any on-disk `nulo:config` key not in the current class (`config/store.ts:14,46-54`). `toStored`/`fromStored` must preserve absence distinctly (never fabricate current defaults for missing keys) so a config key-rename migration — the one `runtime.ts:103-105` explicitly anticipates — sees the real old shape.
- **`auth-registry`→projection**, `optional` root `nulo:core:auth-registry`, idKey `v.id`; AGGREGATED (`:411`), `undefined` with no networks. The second root **`nulo:core:auth-registry-enabled` is backup-absent-by-design** (`:62`) and **defaults `true` when absent** (`:242`) — a migration touching it must REJECT (treating absence as empty would erase disabled states — audit M2), declared in the footprint guardrail.
- **`account-state`→non-storage, `optional`** (writes PXE/IndexedDB, `account-state/service.ts:192`; also `undefined` when network-less, `:147` — explicitly missable, final-pass note). Carries Aztec `instance`/`artifact` whose shape drifts with **`aztec-version`**, not the storage schema (audit M1) — a future account-state backup change keys off `aztec-version`, deferred (Ask A4).
- **`profile`→block-list** (audit H3-codex). `nulo:core:profiles` IS a real persisted root, but backup exports only `ProfileInfo` (`profile/service.ts:878`) and restore re-derives the encrypted rows from `master-key` (`:886`). A migration touching `nulo:core:profiles` is therefore **NOT backup-migratable** → the footprint guardrail blocks import for such a migration (a deliberate release decision), rather than silently skipping or corrupting.

**Pinned by parity tests:** import each service's own root constant; assert the registry root+idKey match (a service relocating its root or changing its key fails CI, not silently mis-migrates).

## compat-epoch vs backup-schema-version split + trust-gate reorder
Two orthogonal top-level fields replace the conflated `schema-version: 2`:
- **`compat-epoch: <N>` — NON-migratable.** Account-contract generation (what `2` really guarded). Baseline stamps `2`. A blob whose epoch ∉ supported set = genuinely un-importable → the ONLY hard version reject.
- **`backup-schema-version: <M>` — migratable.** Shares the storage `nulo:schema:version` number space; baseline stamps `BASELINE_VERSION` (currently `1`). Drives the scratch seed.

Export (`full.vue:128-134`): stamp both, drop the legacy `schema-version` (clean break — no pre-baseline compat). Constants live in the registry module (export + import share one source).

Import trust-gate order (`useFullBackupImport.ts`) — codex's reordering, adopted:
1. Parse/decrypt.
2. **Strip checksum, verify over the original body** (integrity gate — BEFORE any transform).
3. Validate `compat-epoch` (reject "Incompatible backup" — unchanged copy).
4. Validate `backup-schema-version` range: reject `<1`, missing, or `>currentMax` (downgrade/forward guard).
5. Migrate (pure, in-memory).
6. Restore (unchanged pipeline).

A blob with neither new field (old `schema-version:2`-only) fails `isSupportedCompatEpoch(undefined)` → rejected with a clear re-export message. Intended fail-closed for pre-baseline blobs.

## Checksum trust ordering (security-critical)
Verify-then-migrate; **never** trust a recomputed post-migration checksum. The pre-migration checksum over the ORIGINAL bytes is the SOLE integrity gate. Migration is a pure function of already-verified bytes → the guarantee transitively covers the output. The migrated blob's checksum is a derived artifact, not exporter-signed: recomputing-and-trusting it downstream is the **migrate-then-trust inversion** — explicitly designed out. Migrated slices flow straight into `service.restore()` in-memory (never re-read from disk), so there is no downstream re-verification to satisfy; drop the checksum post-verify. (Also: a plain-backup checksum is not *authentication* — an attacker can edit + recompute SHA-256; treat it as accidental-integrity detection, per codex.)

## The row-local migration constraint — STRUCTURAL (audit H1 + final-pass reject)
The v1 parity test was a **tautology**; the v2 "reads ⊆ writes roots + cardinality-invariance" metadata test was **still insufficient** (final codex pass): a migration touching a single root can reason across ROWS *within* it (sort/dedupe/index/first-wins), because `MigrationArea.rows(root)` hands the migration the whole array — and metadata can't see row-level dependencies. Concrete break: a migration reads/writes only `nulo:core:accounts`, sorts the rows, writes `{primary: index===0}` → satisfies every metadata rule yet gives a single-profile backup different output than multi-profile live. Enforcement must be **structural — impossible to violate by construction**, not a checked-after-the-fact test.

**Reality (final-pass, v3 reject):** compile-time structural row-locality of *arbitrary* code is **unattainable** — a `rowMaps: (row)=>row` function can still close over `let i=0; i++` and observe call order/sibling count. So the enforcement is NOT "structural by construction" (impossible) but the exact **metamorphic invariant** that DEFINES row-locality, mechanically enforced on *every* backup-migratable migration.

**The mechanism: a finite declarative DSL (NO executable author code), engine untouched.** The v4 `mapField` function escape was still arbitrary JS — a value-gated closure (`if v!=="trigger" return v; else i++`) passes finite metamorphic samples yet is order-dependent in production. The only airtight answer (codex's prescription): **a backup-safe migration contains ZERO author functions.**
- **Backup-safe form — pure DATA only.** `defineRowMapMigration({ version, description, rowMaps })` where each `rowMaps[root]` is a **finite declarative transformer**: `{ rename?: Record<old,new>, addDefault?: Record<field, JSONValue>, drop?: field[], retype?: Record<field, "string"|"number"|"boolean">, remapValues?: Record<field, Record<oldValue, newValue>> }`. All entries are DATA — no closures, no author code, so row-locality + 1:1 cardinality are **genuinely structural** (data cannot observe sibling rows or call order). The engine-side interpreter applies them deterministically per row; the factory compiles to a standard `Migration` (**engine untouched**), branded `backupSafe`. Covers the realistic migration surface (field rename/add-default/drop/retype/enum-value-remap — the #246 template's "add a default flag" is `addDefault`). A value transform not expressible as a finite `remapValues` table is out.
- **Imperative `up(ctx)` (full power, NOT backup-safe):** existing `defineMigration`. Any arbitrary computation lives here → `backupSafe:false` → the footprint guardrail **blocks backup import** at any version it covers (deliberate release decision, like `profile`/`auth-registry-enabled`), with a clear "this update can't upgrade old backups — re-export" message. This is the honest escape hatch for migrations too complex for the DSL.
- **Defense-in-depth (not the primary guarantee, since the DSL is now structural):** the generic metamorphic guardrail (subset×permutation×duplication per-row invariance) still runs on every backup-safe migration, and a per-migration superset-vs-projection fixture — both now catch only interpreter/descriptor bugs, since there's no author code left to close over state.

**Non-forgeable `backupSafe` (codex — runtime brand + integrity freeze):** membership in a module-private `WeakSet` added ONLY by `defineRowMapMigration`, AND the branded migration is `Object.freeze`d (deep — `up`, `reads`, `writes`, the compiled descriptor) so an author cannot brand-then-reassign `m.up = imperativeCrossRowLogic` after the fact (the WeakSet brands the object, not its contents). The backup path checks WeakSet membership on a frozen object. A raw `defineMigration` cannot brand itself. Pinned by a test (attempt post-brand mutation → throws; membership + frozen asserted).

## Missing/unknown-slice · ID-remap · idempotency/atomicity
- **Unknown `serviceName`** (not in registry) → **reject** (tampered/future blob). Stricter than today's silent-ignore; justified at the trust boundary. *(Ask A3 — resolved: adopt.)*
- **Missing slice:** a slice absent for a service marked `optional` (aggregated services with no networks — audit M3) normalizes as an empty root, NOT a reject — else a valid network-less backup false-rejects. A missing slice for a NON-optional service that a migration reads → reject.
- **Cross-system footprint-coverage guardrail (the anti-drift keystone):** a CI test asserting every registered `Migration`'s read/write roots are either registry-covered, explicitly "backup-absent → block import" (`nulo:core:auth-registry-enabled`, `nulo:core:profiles`), or non-storage. Fails CI the moment someone authors a migration touching a block-listed root — forcing an explicit release decision. Also enforces the row-local constraint above (reads ⊆ writes roots) + codex's runtime preflight (fail-closed if any migration ref isn't registry-represented).
- **ID-remap interaction (I-C, extended per audit M4):** migration runs BEFORE restore, on original-ID slices, transforming **shape only** — it must never renumber `address`/`id`/`hash`/`contract`/`profileId` or the restore-anchor fields (network `name`+`rpcUrl`+`chainId`; token `contract`), **and must not change row cardinality** (add/drop/split desyncs `remapIdInBackupData`, `full-backup-helpers.ts:94`, and the token-balance remap, `useFullBackupImport.ts:369`, which assume post-migration slices are 1:1 with what child rows reference). Cardinality-invariance is subsumed by the row-local constraint and enforced by the same tests.
- **Atomicity:** migration runs entirely on the in-memory scratch store BEFORE any `service.restore()` touches live storage → a mid-migration failure mutates ZERO live state (nothing to roll back). Only `noop`/`migrated` = success; any `failed` (even non-breaking) or `needs-recovery` → reject the import. Run-twice idempotency inherited from the engine; live duplicate-address guard still blocks double-restore. (The pre-existing restore-phase rollback gap is **hardened in Phase 4** — see ledger M6.)

## Security & Adversarial Considerations
- **Threat model:** the backup blob (plain or encrypted bytes) is UNTRUSTED input. A plain-backup checksum is NOT authentication (attacker can edit + recompute SHA-256) — treat as accidental-integrity detection only. Trust boundary = the import parse.
- **Threat-model SHIFT — the engine now processes attacker-controlled input (audit M5 — STANDING RULE):** #246's engine fail-closed (`rows()` throw, `guardCommit`) was audited against OUR-OWN possibly-corrupt live storage. This feature feeds it adversarially-crafted rows (an attacker recomputes SHA-256 and imports). **Every migration `up()` body must therefore treat its input as hostile:** no unguarded `JSON.parse`, no trusting a field's type, presence-guard every access (the `MigrationArea` type params are assertions, not validation — `types.ts:24`). This rule is added to the migration template + enforced by review; a migration that trusts its input is a vulnerability, not just a bug.
- **Checksum ordering:** verify original before migration; never migrate-then-trust a recomputed checksum (inversion designed out).
- **Input validation:** validate top-level fields, data keys, slice shapes, row-id consistency, version range BEFORE the scratch migration. Malformed rows THROW via the engine's `rows()` (fail-closed) → reject import (the engine's throw-on-malformed is the wanted behavior here, unlike `EntityStorage`'s drop-malformed).
- **Least privilege:** the BackupMigrator touches only an in-memory scratch store + the pure `migrations` list — no live chrome.storage, no PXE, no network, no secrets. Live writes only in the unchanged restore pipeline, after migration fully succeeds.
- **Footprint enforcement:** inherited `Migrator.guardCommit` (`migrator.ts:258`) bars writes outside the declared footprint + the reserved namespace — a primary reason to reuse the real engine (pure A would lose it) + the backup-registry preflight.
- **Master-key handling:** `master-key` NEVER enters the scratch store, logs, restore-error details, or migration fixtures. It is not a slice, has no descriptor; `profile` is excluded. Flows only through the existing `profileService.restore` re-derivation. (Strings can't be zeroized — avoid extra copies.)
- **Downgrade/replay:** allow same-epoch old backups `1..current`; reject `<1`/missing/`>current`. Replay of a valid old blob is bounded by the live duplicate-address guard (re-restore collides + aborts).
- **Non-storage slices:** `account-state` (PXE) cannot be engine-migrated; any future shape change needs an explicit backup-only migration, never accidental pass-through.
- **Supply chain:** no new deps; reuse in-repo `EncryptionKey`.
