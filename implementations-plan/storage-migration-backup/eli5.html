Backup-import migration

When you export a full backup of the wallet and later re-import it, the file is stamped with the schema it was made under. Today, if that schema is even slightly old, the wallet refuses the import. This plan teaches the importer to upgrade an old backup on the fly — running it through the exact same numbered-migration engine we just shipped for live storage (#246) — so an old backup restores cleanly instead of bouncing. It stays dormant until the first real format change ships; today it's build-now, gate-ready plumbing.

Why "deep" was chosen

The rubric scored two clear HIGHs — migration-cost (it's a data-migration by definition) and security-sensitivity (the backup carries an encrypted master-key and a checksum trust boundary) — plus borderline-high irreversibility (a bad import writes real wallet data). Novelty was only moderate (we have direct #246 experience), so it's deep, not mega-deep. Deep bought three independent plans, a double adversarial audit, and a final fresh pass — which paid off: the audit caught two mis-classifications and a hollow test that would have shipped a false "green" on the very first real migration.

Phases

Phase 1: The mapping registry (slice ↔ storage)

A backup stores each service's data as a flat array; live storage stores keyed rows. This is the translation table between them — one entry per service, with the messy cases pinned down (transactions keyed by hash not id; fpc is a plain row; config is lossy and must not drop keys; account-state can't be migrated at all).

Proves itself by: round-trip unit tests (translate there and back = identity) + a test that each entry matches the service's own storage constant, so a service moving its data fails CI.

Phase 2: The backup migrator (reuse the real engine)

Pour the backup's translated data into a throwaway in-memory store, run the real migration engine over it (unchanged — zero risk to the audited code), read the upgraded rows back out, translate to the new format. Plus the safety rails: a rule that migrations must be "row-local" (safe on a partial backup) and a guardrail test that blocks anything unsafe.

Proves itself by: a parity test (a real migration on a multi-profile live store vs a one-profile backup produces matching results) + fail-closed tests (bad/unknown/missing data rejects) + the engine's own tests still green.

Phase 3: New format fields + smarter reject (clean break)

Stamp two new fields on export — one for "which account-contract generation" (never migratable, the real reason to reject) and one for "which schema version" (migratable). Rewire the importer to reject only genuinely-incompatible backups, and to verify the checksum before anything else.

Proves itself by: component tests — incompatible rejects, too-new rejects, a current backup still restores, checksum is checked first.

Phase 4: Wire it into the import flow + fix a rollback bug

Insert one migrate step between "checksum verified" and "restore begins." Because migration happens on the throwaway store before any real write, a failed migration touches nothing — the import just aborts cleanly. Also folded in (a pre-existing bug you asked to bug-bash): today, if a restore fails partway, the half-created profile is only cleaned up for two specific errors; any other failure leaves a broken ghost profile behind. This hardens the catch-all to delete the orphan — while keeping the one intentional case (a "finish opening" failure) where the profile is deliberately kept because your data is already saved and you can unlock it later.

Proves itself by: a test that a failed migration aborts before any restore runs; a pre-finish restore failure now deletes the orphan profile; a finish-step failure keeps it.

Phase 5: Real-browser smoke test + docs

Load an old-format backup file through the actual import screen in a real Chrome and confirm the restored data is in the new shape. Update the docs.

Proves itself by: a smoke e2e that fails (not skips) if the fixture is missing, plus the full pre-PR gate green.

Phase 6: Network round-trip test

On a live sandbox, import an old-format backup, let it upgrade, restore it, and confirm the restored wallet actually works on-chain (the account signs, the network syncs). The real value: this harness means every future upgrade automatically gets on-chain coverage — no manual human check needed at each new migration.

Proves itself by: a network e2e (owns its own anvil+aztec+playground, parallel-safe) proving a migrated wallet transacts, run on a quiet machine.

Human context

Two facts the audit surfaced that shape everything: (1) a backup slice is not a clean copy of stored rows — some are filtered to one profile, some are aggregated summaries that can drop data, two were even mislabeled in the first draft. (2) The migration engine was originally audited assuming it only ever reads our own data; a backup file is attacker-controllable, so every future migration must treat its input as hostile. Both are now baked into the plan as enforced rules, not hopes.

Decisions (all resolved)

  • Clean slate. First-time users, no backward compatibility — the current format is the only format, no grace code for old blobs.
  • Network e2e: added. Rather than a manual human check at each future migration, we build the on-chain round-trip harness now so every future upgrade is auto-covered.
  • Rollback bug: folded into Phase 4 (one bug-bashed change, not a follow-up PR).
