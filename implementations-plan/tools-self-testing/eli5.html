nulo · blueprint mid · plan: implementations-plan/tools-self-testing · 2026-09-08

Tools tests itself, the bridge tests itself, and CI says which is which

Today the bridge's real round-trip check is a script someone runs by hand, and the tools app has never been driven in a real browser. This plan turns both into gates that run on every relevant pull request, without the Nulo extension anywhere in the loop, and renames the CI checks so a red one tells you which product broke.

Codex r1
Reject. Every blocking finding was adopted: the local build had to be a real build target, not a dev-mode trick; the test wallet needed the schema patch and a stricter origin check; the flows must not share state; CI jobs must build the contracts first; the enumerated matrix replaced a loose spec list.
Fable r1
Conditional approve with five conditions. All five are in the plan.
Codex final
Fresh-context pass on v2: reject. Its findings became v3: no sponsored fees in any tools cell (the app forbids them), the local target lands before the spike, app-owned decisions are tested only in the browser, the wallet page defends itself the way the SDK expects, and the branch-protection switch happens per branch. A resumed pass on v3 found six more (account grants, the fueled-claim discriminator, explicit fee budgets); all adopted into v3.1. Verdict on v3.1: see plan.md § Audit verdicts.

Why this tier

mid. Novelty is medium-high (nobody has yet connected Aztec's embedded wallet to a dApp through the wallet-sdk's iframe channel; a half-day spike de-risks it before anything is built on it). Blast radius is medium (renaming a required check blocks merges only until a one-command update). Irreversibility, migration cost, external coupling, and security sensitivity are all low. One dimension high-ish, none irreversible: mid, with two independent reviewers instead of one.

What you decided already

  • Gas leg on the sandbox: a stand-in Uniswap "quoter" that answers the app's price questions at a fixed rate, over the fixed-rate swap mock that already exists. Real Uniswap math stays proven by the existing Sepolia-fork contract test.
  • Rename the required checks to app-prefixed names, with a one-command script you run per branch: on dev right before merging the rename, on main right before merging the first promote that carries it.
  • New gates are advisory first; after seven days of first-try green, you promote them to required with the same script.
  • The full matrix runs in both layers: once through the code the app calls (fast, per-flow pass/fail) and once through the real UI in a browser (slower, sharded across runners).
  • No /code-review in the loops; the codex fix loop is the review.

The three arcs

Arc 1 · CI names say the app · one pull request

1

Rename workflows, checks, labels, and docs; ship the protection script

"Smoke e2e" becomes "Extension smoke e2e", "Network e2e" becomes "Extension network e2e", the contracts check becomes "bridge-contracts-status"; the quality check keeps its neutral name. Every doc and script that hardcodes the old names is updated. A script prints and, on request, applies the new required-check names to both protected branches, refusing if the live settings changed under it, and prints the rollback.

Proves itself by: workflow lint + the CI-gating unit test green; a repo-wide search finds only the new names; the PR itself shows the new check names green.

Arc 2 · Bridge integration suite · one pull request, stacked on arc 1

2

Turn the sandbox script into a library and stop fetching from the internet

The 1,358-line smoke script is split into modules (boot, fixtures, accounts, flows) with no hidden shared state, so each flow can run on its own. The two canonical Ethereum contracts the sandbox copies from a public Sepolia node are vendored into the repo with an independently checked fingerprint. Per-flow timings are recorded for the first time.

Proves itself by: package typecheck + unit tests green; the existing smoke still passes end to end with no network fetch in its log.

3

Make the gas leg reachable; add the missing flows

A small test-only contract answers the app's price questions exactly as the swap mock will settle them, so "arrive with gas" paths work locally. The sandbox's bridge description gains the swap block the app looks for. Flows that never existed are added: private token+gas, private gas-only, sends from accounts with no gas at all, a withdrawal attempted before it is provable, and more.

Proves itself by: the contracts' own test suite green including the new contract; the smoke green including the new flows.

4

Every flow becomes a named test; the faucet joins the sandbox

A vitest suite boots the local network once, then runs one file per family (deposits, gas leg, fee states, registration races, exits, pause, drip, recovery), each with its own fresh accounts and tokens. The faucet's Dripper and its two test tokens are deployed on the sandbox too.

Proves itself by: test:integration green with every matrix cell listed as its own test; the everyday unit run untouched.

5

CI runs it on every contracts or bridge change

A new job installs the right Aztec toolchain, builds the contracts, and runs the suite, on any PR touching the contracts, the bridge library, or the published bridge description files. The Noir hub's own test suite is tried in CI too; if the runner cannot host it, that is recorded and the job dropped.

Proves itself by: workflow lint + gating test green locally; the arc's PR shows the job green.

Arc 3 · Tools in a real browser · one pull request, stacked on arc 2

6

A real "local" build target for tools

Tools currently knows two networks, testnet and mainnet, chosen at build time. A third, "local", points at the sandbox and carries its identity, the faucet's local addresses and the test wallet's address, injected at build time so nothing leaks into the other two builds. One small compatibility fix rides along: a wallet that simply lacks the "add token" method is treated as unsupported, not as an error.

Proves itself by: tools' typecheck, unit and jsdom smoke green; a local build passes the target verifier and contains the sandbox addresses; testnet and mainnet builds contain none of them.

7

Spike: can an embedded wallet connect to tools through the standard wallet channel?

Half a day, nothing permanent. A tiny page hosts Aztec's embedded wallet behind the wallet-sdk's iframe handler; the real local build of tools (from the previous phase) is pointed at it; one connection, one added account and one faucet drip must land. Each known risk is checked and written down: the 10-second discovery window, the cross-origin headers, the SDK's floating panel, and where the "pay from my own public gas" behavior plugs in.

Proves itself by: a drip receipt on screen and the balance moving on chain; a go / no-go note per risk, with the fallback route recorded if any is no-go.

8

Playwright scaffold, the fake Ethereum wallet, first flow

Playwright drives Chromium. An 80-line fake Ethereum wallet is injected into the page (it signs with one of the local chain's well-known dev keys). Every request that would leave the machine is blocked, and the public token list is served from a file. A runner script boots the sandbox, builds tools, checks the build really contains the sandbox addresses, runs the tests, and cleans up only what it started.

Proves itself by: one deposit flow green first try; nothing left running afterwards; zero outside requests recorded.

9

The matrix in the browser

Forty-four cells, each a named test with its exact starting balances and expected payer: deposits (token only, token + gas, gas only; public and private; first-time and repeat), every "not enough gas" message, recovery after an interrupted claim, declined permissions, wrong Ethereum network, exits (public, private from one note and from three, paused, no credit), the token catalog and paste-to-add, the mint strip, the faucet, backups and the dock. Three wallet profiles: a plain wallet with only standard methods, one that also advertises and routes "pay from held public gas", and one that additionally offers the add-token convenience. No cell relies on sponsored fees: the app forbids them on every bridge path, so plain-wallet sends pay from private credit the harness funds first.

Proves itself by: the whole suite green first try, locally and split in two shards; timings recorded to size CI.

10

CI for the tools suite; delete the dead extension plumbing; docs

A "Tools e2e" workflow with a "tools-e2e-status" check runs on any PR touching tools, the contracts, or the bridge library, sharded. The extension's test runner loses the unused hooks it kept for driving tools. CI.md, CLAUDE.md, and the app README describe the new gates and who promotes them.

Proves itself by: workflow lint + gating test + the extension smoke green locally; the arc's PR shows every shard and the status check green first try.

Human context

Why not drive tools with the Nulo extension? Because tools must work with every wallet that speaks the standard, and the extension must work with every dApp. Testing them against each other proves the pair, not either product, and couples two release trains. The embedded test wallet is a third-party wallet as far as tools can tell, which is exactly the claim to prove.

Why a fake Uniswap? The sandbox has no Uniswap. Forking Sepolia would still not help: the local network mints its own Fee Juice, so Sepolia's pools cannot price it. A fixed-rate stand-in that answers the same questions the real quoter does exercises all of the app's routing code; the real pool math is already proven against Sepolia by a contract test.

Why not snapshot the chain between tests? Rewinding the Ethereum side looks like a reorg to the Aztec node and desyncs it. Fresh accounts and fresh tokens per test file are cheaper and honest.

Why the rename needs a script. Required checks are matched by name in the branch settings. The moment the rename merges, the old names stop appearing, so the settings must switch at the same time. The script makes that a single command with a rollback.

Open questions

  • The spike might say no. Nobody has run Aztec's embedded wallet behind the SDK's iframe handler against a real dApp. If it cannot complete the handshake, the fallback is a wallet that imitates the extension's message channel, which is a bigger phase and gets re-planned. Everything in arcs 1 and 2 stands regardless.
  • Can the CI runner host the Noir hub's test oracle? Unknown until phase 5 tries; the job is dropped with evidence if not.
  • How many browser shards? Nothing is timed today. Phases 2 and 9 measure; the shard count follows.
