Release dev → main

/blueprint deep · execute-only runbook · awaiting your approval

Everything that's been piling up on the dev branch goes out to the public main branch in one coordinated release — the browser extension (a versioned GitHub Release with downloadable zips), the faucet site (faucet.nulo.sh), and the landing page. The extension is the only thing with a version number; the two sites are just static pages that re-deploy themselves from main. We use the release pipeline exactly as it already exists — no new automation — including its one known 45-second manual hiccup.

The single biggest thing to decide: the version number. This batch contains a breaking change (the Aztec 5.0 protocol upgrade). The release robot reads that and — because of how it's configured — will want to call this release v1.0.0, not the 0.24 you might be expecting. Going to "1.0" publicly says "this is production-ready," while the wallet is still on a test network and a release-candidate protocol. So: do we ship 1.0.0, or pin it to 0.23.0 (a one-word note in the release PR, no automation change)? All three independent reviewers flagged this as the #1 blocker. Nothing else proceeds until you decide.

Why this tier (deep)

deep. Four of six risk dials are HIGH: irreversibility (a pushed tag + a public release + two live sites can't be cleanly un-shipped), blast radius (every user; first release carrying the breaking protocol fork), external coupling (Cloudflare ×2, GitHub Releases, a live test-network gate), and migration (the 5.0 fork + version-tracking files). There's no code to write here — so the deep ceremony was spent on three independent reviewers red-teaming the release order, the failure modes, and the rollback path. They converged hard, which both reassures and warns (shared agreement can be a shared blind spot — the final review attacks exactly that).

The plan, step by step

Steps marked irreversible are the ones you (the human) approve before I touch them.

0 · Pre-flight checklist

Before anything moves: confirm dev is green, all four secret keys exist, there's no leftover release PR sitting open, the faucet's test-network contracts are actually deployed, and the version is decided.

Proves itself by: dev's required checks green + 4 secrets listed + no stale release PR + faucet check passes + version/flake-policy decided.

1 · Promote dev → main irreversible

Open and merge the big "promote" PR. The moment main moves, the faucet auto-deploys on the new protocol — so this is the point of no return for the faucet. (Undo = a revert PR, which redeploys the old state.)

Proves itself by: the merge commit is on main + faucet.nulo.sh loads, is cross-origin-isolated, and shows the new Fuel tab.

2 · Version check, then merge the Release PR irreversible

The robot opens a "release X.Y.Z" PR. STOP and check the number matches your decision (this is where the 1.0.0-vs-0.23.0 call gets enforced) — then merge. Before merging it's totally reversible (just close it).

Proves itself by: the PR's version == the number you chose, across its title, changelog, and package.json.

3 · The known 45-second nudge irreversible

The release tool has a long-standing bug: after merge it stops short and refuses to tag. We do the documented manual nudge — create the tag + an empty release by hand. (Pushing a tag is the irreversible bit; it can be deleted but people may have seen it.)

Proves itself by: the tag points at exactly the release-PR's merge commit (guards against tagging the wrong thing) + the placeholder release exists.

4 · Build & publish

Kick the build chain by hand: it runs the tests (including a 30-45 min real test-network run), builds Chrome + Firefox, and attaches the zips + checksums + real release notes (overwriting the placeholder).

Proves itself by: the build succeeds + the release shows 3 files (chrome zip, firefox zip, checksums) + real notes, not the placeholder text.

5 · Refresh the landing page

Because step 4 was a manual kick, the landing didn't auto-refresh. Poke Cloudflare (the deploy hook) after the files exist, so the download button points at the new release. (If poked too early, the landing build fails loudly rather than showing a broken link — safe, but we wait.)

Proves itself by: the landing page references releases/tag/v<version> and shows the new version.

6 · Confirm all three are actually live

Extension release is "Latest" with working downloads; landing download works; and you do one real test drip of NULO/OLUN on the faucet — the single best proof that 5.0 + cross-origin isolation + the contracts all work together in production.

Proves itself by: all three surfaces confirmed + checksums verify + one successful real drip.

7 · Tidy up afterwards

Sync main back into dev, then fix the version-tracking file (it's stale — currently points at an old 0.20.2). Skipping this makes the next pre-release flow reopen old PRs.

Proves itself by: dev + the prerelease-tracking file both show the new version.

Human context (the bits worth understanding)

  • "Release to latest" = three different things. The extension gets a real version + GitHub Release. The faucet and landing aren't versioned — they're websites that just redeploy from main. There's only one version in this whole release.
  • The faucet jumps the gun. It redeploys the instant we promote (step 1), ~30-45 min before the extension's release exists (step 4). For that window the faucet runs the new protocol while the "Latest" extension is still the old one. We either accept + announce it, or pause the faucet's auto-deploy until the end.
  • The landing fails safe. Its build refuses to publish a download button that points at a release with no zip — so bad ordering produces a loud red build, not a silently broken site.
  • The 45-second nudge is expected. It's a documented upstream bug, not something going wrong. You chose to accept it rather than fix the automation in this plan.
