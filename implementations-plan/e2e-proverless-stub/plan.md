# e2e-proverless-stub

Make network e2e fast and CDP-stable by skipping real proof GENERATION for most tests (keeping simulation + on-chain execution — what tests assert on), with a controllable stub prover so the sequencing/cancel tests stay deterministic. Tier: **deep** (novelty: controllable prover seam; security: a proverless / controllable prover is a production catastrophe if it leaks). Consolidated from three independent plans (main + Plan subagent + codex).

## The seam (verified across all three plans, with source)

- `chain-runtime.ts:166` → `createPXE(node, config, { proverOrOptions, simulator })`. `proverOrOptions?: PrivateKernelProver | BBPrivateKernelProverOptions` (`@aztec/pxe/.../pxe_creation_options.d.ts:14`) — an arbitrary prover is injectable.
- **Plain proverless is a config one-liner, no custom prover:** `proverEnabled: false` → `pxe.js:282` builds `PrivateKernelExecutionProver(..., fakeProofs=!proverEnabled, ...)`; `private_kernel_execution_prover.js:50-51` sets `skipProofGeneration` and `generateWitnesses=false`, so it runs the kernel-circuit **simulation** path (`simulateInit/Inner/Reset/Tail`, real public inputs/nullifiers from kernel sim — NOT witness-gen, NOT `generate*Output`), skips the hiding kernel (`:193`) and `createChonkProof`, returns `ChonkProof.random()` (`:242`). The expensive BB SNARK is skipped; **WASM kernel simulation still runs** (so the stage is fast, not free — see Design F2).
- **Proof of acceptance:** `fixtures/aztec.ts:77` already mints/deploys with `proverEnabled:false`, and those txs MINE on the local node (it doesn't verify proofs).
- **`PrivateKernelProver`** (`@aztec/stdlib/.../private_kernel_prover.d.ts`, 11 methods) splits `simulate*` (keep real) from `generate*`/`createChonkProof` (the proof; faked). `proveTx` is on the PXE, not the prover.
- **`@nulo/aztec-runtime` is chrome-free** (`offscreen/entry.ts:10-12`, `chain-runtime.ts:24-25`) — it must NOT call `chrome.storage`. The barrier is injected as an opaque `() => Promise<void>` from the extension shell. **Which process owns that injection is approach-dependent (audit C1):** approach 1 (stub prover) holds inside the OFFSCREEN doc (where the prover lives) → inject from `offscreen/index.ts`; approach 2 (wrap `proveTx`) holds at the SERVICE-WORKER coordinator (`execution-coordinator.ts:157` → `PXEProxy.proveTx` → RPC → offscreen) → the barrier read + `onChanged` listener run in the SW. Both SW and offscreen are trusted extension contexts with `chrome.storage` access, so either works — but Phase 0b MUST record the chosen process and prove a release written from `walletPopup.evaluate` is observed across that process boundary.
- **`VITE_*` auto-exposed to `import.meta.env`** (no `define` needed; `accelerator/config.ts:26` works with no `vite.config.ts` entry), and statically substituted → enables dead-code elimination + bundle-grep guarantees.

## Quality bar (user directive — "very pretty and lovely, not a monkey patch")

The controllable stub MUST be a first-class, typed, single-responsibility collaborator held to the same bar as the existing `AcceleratorProver` + `onPhase` seam — NOT an inline `if (proverless)` smear. Concretely:

- **Typed seam in `@nulo/aztec-runtime` (chrome-free):** a `ProofGate` interface — `interface ProofGate { wait(): Promise<void> }`. The default is a shared no-op (`NoopProofGate`, `wait` resolves immediately). The runtime awaits `gate.wait()` at the prove boundary and **never references `chrome.*`**. Injected through the existing factory exactly like `AcceleratorProver`/`onPhase` (a constructor/factory param, not a global).
- **Chrome impl in the extension shell:** `ChromeStorageProofGate` (presence-only `chrome.storage.session`, `onChanged`, remove-on-release, safety-timeout) lives in `packages/extension/src/e2e/`, constructed STRICTLY inside the `if (E2E_PROVERLESS)` branch in `offscreen/index.ts` (source-structure invariant). It implements `ProofGate` so the runtime stays oblivious to storage.
- **Symmetry:** the new `src/e2e/config.ts` reads like `src/accelerator/config.ts`; the gate reads like a sibling of `AcceleratorProver`. A reviewer should not be able to tell the proverless seam was added later.
- **Hygiene:** TSDoc on the public surface; comments explain WHY/invariants (repo style); unit tests for the gate (instant-by-default, holds, releases, times-out-loud); all `data-testid`s preserved verbatim in any touched component.

## Design

- **Plain proverless** (the ~45 bulk files): build with `VITE_NULO_E2E_PROVERLESS=1` → `chain-runtime.ts` sets `proverEnabled:false` and does NOT construct `AcceleratorProver` (keeps the static `WASMSimulator` — still needed for the kernel-circuit simulation path). No barrier.
- **F2 (audit, load-bearing on the barrier rationale):** the proving stage does NOT collapse to ~ms — proverless still runs WASM kernel simulation (`simulateInit/Inner/Reset/Tail`); only the BB SNARK (`createChonkProof`) is skipped. So the stage drops from **BB-proving (seconds–minutes)** to **kernel-sim (sub-second–low-seconds)**, a large win but a non-trivial residual window. The barrier exists because that residual window is too short/variable for a *deterministic* ordering assert, not because proving is instant.
- **Controllable stub** (the 3 sequencing/cancel tests): SYNTHESIZE a deterministic holdable window via a barrier the test controls, at the `proving`-stage boundary (`proveTxTask` at `execution-coordinator.ts:106-116` wraps `pxe.proveTx:116`, invoked at `:157`). **Mechanism is the one disputed item (D1) — resolved by the Phase-0 spike:**
  - **Approach 2 (recommended, lower-risk):** wrap `pxe.proveTx` at the SW-side `proveTxTask`/`proving`-stage boundary behind the flag — gates the exact call the stage measures, sidesteps the 11-method interface, needs NO real-prover delegate. Barrier listener runs in the SW (audit C1). Must be DCE-guarded as strictly as the flag.
  - **Approach 1 (fallback):** a stub `PrivateKernelProver` (`proverOrOptions`) that awaits the barrier inside the offscreen prover's `simulate*` path (codex). Risk (confirmed by audit I2): createPXE passes it as the `proofCreator` and the execution prover calls `simulateInit/...` on it, so the stub MUST provide a real WASM-backed `simulate*` delegate — the MV3-offscreen delegate-sourcing risk is real.
- **Barrier protocol:** key `nulo:e2e:proof-gate` in **`chrome.storage.session`** (codex: session not local). **Presence-only semantics (codex security):** key PRESENT ⇒ hold; key ABSENT ⇒ release. The listener `remove()`s the key on release AND on safety-timeout, so a forgotten `hold` can't bleed into a later test in the same browser session (a stale `{mode:"release"}` value would otherwise survive the whole session). Event-driven (`chrome.storage.onChanged`) + a hard **safety timeout** that resolves-and-logs-loud so a missing release never hangs the suite. **Timeout sizing (audit A1):** the network vitest `testTimeout` is **30 000 ms** (`vitest.e2e.network.config.ts:27`), so the safety timeout must be **well under 30s (target ~20s)** AND each STUB test sets an explicit per-test `{ timeout }` **above** the safety timeout — otherwise a missing release dies with the generic 30s vitest timeout instead of the loud barrier log. Test drives the gate from the EXTENSION context: `walletPopup.evaluate(() => chrome.storage.session.set(...))` (audit S2 — `page` is the dApp playground page and has no `chrome.storage`).
- **Prover-ON build** (no flag): unchanged real proving, for the canary jobs.
- **Mutual exclusion (codex D4):** `VITE_NULO_E2E_PROVERLESS` and `VITE_NULO_ACCELERATOR_REQUIRED` must be mutually exclusive. Enforcement point (audit A2): an **init-time throw in `offscreen/index.ts`** (where both configs are already read) — lowest-effort, mirrors the existing stamp pattern.

## Test classification

- **STUB + barrier** (proverless, deterministic): `cancel-mid-prove`, `concurrent-sendtx-approve`, `concurrent-sendtx-confirm` (gains the deterministic ordering assert: T2 `queued` while T1 held mid-prove).
- **PLAIN proverless** (~45): authwit-* (drop `RUN_AUTHWIT_E2E` gate), cap-request-*, contracts-*, data-*, meta-*, session-*, connect-*, sim-methods, register-token, tokens, token-*, batch-*, `concurrent-sendtx` (reject), fee-methods, `tx-sendTx-noFrom` (never proves), **`multi-account-from` (D7 RESOLVED → PLAIN, 3/3 in Phase 0)**, etc.
- **KEEP REAL PROVING** (prover-ON dedicated CI jobs). **Codex correction:** the original bucket was both mis-counted ("5" canaries but `transfers` + 5×`tx-sendTx-*` = **6 files**, and `tx-sendTx-multicall` has 2 cases) AND over-justified — `tx-sendTx-noFrom.test.ts:19-29` never reaches prove, and `tx-sendTx-{default,...}` only assert an *active journal stage*, not submit/mine, so they are NOT genuine proof-path canaries. Phase 4 wires CI from an **explicit file list**, not a count. The bucket's real job: at least **one true mined dApp `sendTx` canary** (a test upgraded to wait through submit→mine under real proving) + the wallet-UI `transfers` canary. `tx-sendTx-noFrom` does NOT belong here (no prove path) — it goes to PLAIN proverless.
- **Discriminator (audit C3) — why the two concurrent tests split:** `concurrent-sendtx-approve` (STUB) *approves* popup #1, advancing T1 INTO prove, so it must be held mid-prove for the "T1 active + T2 queued" snapshot — needs the barrier. `concurrent-sendtx` reject (PLAIN) holds T1 in `pending` via an UNAPPROVED open popup, so `expect(stages).toContain("queued")` (`concurrent-sendtx.test.ts:160`) is stable proverless WITHOUT a barrier.
- **multi-account-from — D7 RESOLVED → PLAIN (Phase 0, 3/3 plain proverless):** the Plan subagent's "safe PLAIN" was correct. The `waitForSendTxActiveStage` allowlist (`simulating|proving|submitting`, `popups.ts:408`) tolerates a collapsed `proving` — `simulating`/`submitting` stay observable. Codex's race concern (terminalize-before-observable) did not materialize across 3 consecutive runs. (Audit trail of how this reached UNRESOLVED before the spike is preserved in Assumptions/Audit verdicts below.)

## Security & Adversarial Considerations
- **Prod catastrophe if leaked**: a proverless or externally-gated prover in production = the wallet broadcasts unproven / attacker-timed txs. The defense is layered, but **NOT every layer is independently sufficient** (codex HIGH — the original "each independently sufficient" claim was false; corrected):
  - **(1) Source-level hard fail — the load-bearing guard (codex HIGH).** `src/e2e/config.ts` (and the proverless branch in `chain-runtime.ts`/`offscreen/index.ts`) throws unless BOTH `VITE_NULO_E2E_PROVERLESS=1` AND a second explicit opt-in (e.g. `VITE_NULO_E2E_PROVERLESS_CONFIRM=1`) are set. This protects EVERY build path, not just CI. **Why needed:** Vite auto-loads `.env*` files (`.gitignore:16-19` only ignores them — it does not prevent Vite reading a present one), and direct builds bypass the workflow grep: root `package.json` `build*` scripts, `packages/extension/package.json` build scripts, and `_smoke-e2e.yml:54-56` all run `bun run build:chrome` without going through `_build-extension.yml`.
  - **(2) compile-time flag → DCE** removes the proverless branch + stub module + barrier listener from any build where the flag is unset.
  - **(3) positive AND negative bundle-grep** — stamp present-when-flagged (`agent.sh`), stamp + `nulo:e2e:proof-gate` ABSENT in non-proverless `dist/{chrome,firefox}` (`_build-extension.yml`). **Sufficient only for workflows that route through `_build-extension.yml`** (release.yml, pr-quick, pr-smoke); `_smoke-e2e.yml` direct build is covered by layer (1), not this grep.
  - **(4) PROVERLESS⊥ACCELERATOR_REQUIRED fail-fast** (init-time throw in `offscreen/index.ts`).
  - **(5) barrier**: presence-only key in `chrome.storage.session`, `remove()`d on release/timeout, safety-timeout; **prod has no listener (DCE) so even a written key is inert.**
- **Source-structure invariant (final-codex, MUST hold for layers 2+5):** the barrier listener, the `proveTx` wrap (a2), and the stub prover (a1) MUST be constructed **strictly inside the `if (E2E_PROVERLESS)` branch** — NEVER via a top-level side-effect import. A top-level `import "./proof-gate"` would defeat DCE and ship the listener even with the flag off. Enforce with the negative bundle-grep (layer 3) which would catch the leaked `nulo:e2e:proof-gate` literal.
- **Accepted residual risk (final-codex, explicit):** the double-opt-in stops *accidental* single-line `.env` leaks, but a developer who *deliberately* sets BOTH flags AND runs a direct `bun run build*` outside the grep-guarded workflows can still produce a proverless artifact. That is an intentional-insider action, not an accidental leak; we accept it (a third predicate wouldn't stop an insider who controls the build). The official release path (`release.yml` → `_build-extension.yml`) IS grep-guarded, which is the path that ships to users.
- **The trust boundary is the absent listener, NOT chrome.storage (codex).** A dApp page cannot write `chrome.storage` (no `externally_connectable` in `manifest.config.ts:20-40`; `content.ts` is relay-only) — but a compromised content script or any other extension context CAN, because the extension holds the `storage` permission. So storage-write-access is NOT the boundary; the boundary is that the barrier-reading listener does not exist in shipping builds (layers 1–3). State this explicitly so no one later "hardens" the wrong thing.
- **Barrier hang**: missing release → safety timeout fails loud, never deadlocks CI.
- **Supply chain / crypto / least-privilege**: no new deps; no crypto changes (we SKIP proving in tests, never weaken it in prod); flags are build-only, no creds.
