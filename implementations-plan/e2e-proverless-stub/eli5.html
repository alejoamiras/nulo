e2e-proverless-stub

Our browser-extension wallet's network end-to-end (e2e) tests are slow and flaky because each test makes the wallet build a real zero-knowledge proof — the expensive cryptographic step that, in production, proves a transaction is valid without revealing its secrets. Building that proof in the browser eats CPU for seconds-to-minutes per transaction, which starves the test driver's connection to Chrome and causes timeouts. The insight: the local test blockchain doesn't actually check the proof, and almost none of our tests are about proving — they're about menus, approvals, balances, and ordering. So we build a special test-only version of the wallet that skips making the real proof (it still does everything else — simulation, on-chain submission). For the handful of tests that genuinely need to catch the wallet "mid-proof" (cancel, queueing), we add a controllable pause: a switch the test flips to hold the fake-proof step open, look at what it needs, then release it. Real proving stays ON for a few "canary" tests that guard the real proof path.

⚠ The danger this plan takes seriously: a wallet that skips proving is a catastrophe if it ever ships to real users — it would broadcast unproven transactions. The entire design is built around making that impossible to leak into production.

Why this tier was chosen (deep)

Rubric: Novelty HIGH (a controllable prover seam is first-of-its-kind here), Security sensitivity HIGH (a leaked proverless build = unproven txs in production). Two HIGH dimensions → deep, even though it's mostly one package. The deep ceremony ran three independent plans (me + a planning subagent + codex), consolidated them with a decision ledger, then a fresh-context audit round (a new subagent + codex) and a final fresh codex pass. That ceremony already paid off: it caught a real production-guard hole, a real timeout-sizing bug, and a genuine disagreement between the two reviewers about one test — all before any code was written.

Phases

Phase 0: Feasibility spike (mandatory, no CI changes)

Prove the two risky assumptions before touching anything else. (0a) Build one proverless wallet; confirm a normal wallet transfer AND a dApp transaction both still land on-chain. (0b) Wire a minimal pause-switch; confirm the test can hold the proof step, release it, and that a forgotten release fails loudly instead of hanging. If either fails, STOP and tell the human — the whole plan rests on these.

Proves itself by: a proverless transfer + a dApp transaction both mine on the local chain; the pause-switch holds/releases across the process boundary; a missing release trips a loud safety timeout (not the generic test timeout). Must run with the Accelerator desktop app OFF.

Phase 1: Build flag + plain proverless + production-leak guard

Add the test-only build flag and make it impossible to ship. The flag needs two separate switches both turned on, or the build throws. Production builds are checked (by reading the shipped bundle) to confirm the proverless code and the pause-switch key simply aren't in there.

Proves itself by: unit tests (flag off → real proving wired); a production build with the flag off, then grepping the bundle to prove the test-only markers are absent; one bulk test green proverless.

Phase 2: The controllable pause (barrier + stub)

Build the real pause mechanism the spike validated, with a helper the tests call (hold / release) and a safety timeout so it can never deadlock CI.

Proves itself by: unit tests (instant by default, holds when told, releases, times-out-loud) + the cancel + concurrent-approve tests green and deterministic.

Phase 3: Ordering test + reclassify + drop the authwit gate

Use the pause to add a deterministic "second transaction waits while the first is held" assertion, and re-enable the authorization tests that were previously skipped because they were too slow.

Proves itself by: the confirm-ordering test + both authwit tests run, pass, and are fast (not skipped).

Phase 4: CI two-build split

CI builds the wallet twice: a fast proverless build for the big shared pool of tests, and a real-proving build for the few "canary" tests that guard the actual proof path.

Proves itself by: workflow lint (actionlint) + a full CI run — pool materially faster, no Chrome-connection timeouts, canary jobs show real proof activity.

Phase 5: Close the arc

Self-review (/code-review max --fix), a codex post-implementation audit focused on the production guard, docs update, single PR to dev.

Proves itself by: review applied + committed; codex audit clean; PR opened (never merged autonomously).

Human context

A "proof" here is the client-side zk-SNARK the wallet generates before sending a private transaction. Generating it is the slow part; simulating the transaction (working out its effects, nullifiers, balances) is separate and stays ON — that's what almost every test actually checks. The local test chain runs in a mode that accepts transactions without verifying their proofs, which is exactly why skipping proof-generation is safe in the test environment only. The "barrier" is just a flag in the extension's session storage that a test flips; the wallet's proof step waits for it. The reason this is a deep plan and not a quick hack is the blast radius if the test-only behavior ever escaped into a shipped build.

Open questions (all resolved during the audit; here for transparency)

  • Which pause mechanism? Two options (wrap the proof call in the service worker, vs a stub prover in the offscreen document). The two reviewers leaned different ways; we deferred the choice to the Phase-0 spike, which will pick empirically. Both audits confirmed nothing else depends on the choice beforehand.
  • One specific test (multi-account-from): the two reviewers disagreed on whether it's safe in the fast mode. We default it to the safe (paused) bucket until the spike proves otherwise.
  • Does fast mode behave identically for dApp transactions, not just wallet transfers? Only proven for transfers so far — Phase 0 now explicitly pins one dApp transaction end-to-end before trusting the rest.
