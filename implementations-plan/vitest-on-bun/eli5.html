Blueprint · mid · Arc C of the Bun 1.4 adoption

Vitest on Bun

Every package's automated tests currently run on Node, even though Bun installs and runs everything else in this repo. Bun 1.4 officially runs Vitest. This plan switches each package's test command to Bun, proves with repeated runs — same commit, both runtimes — that Bun is at least as reliable as Node, and lands it as one pull request that touches no CI workflow file and no dependency. The browser end-to-end tests keep running on Node for now.

Why this tier was chosen

mid. Rubric: novelty medium (first time tests execute on Bun here, but already de-risked by measurements), blast radius medium (if a switch is wrong, every pull request's quality check goes red — and each switch is one line to revert), irreversibility low, migration cost low, external coupling medium (one real bug between Vitest and Bun, already fixed upstream in Vitest's next major, worked around here), security low. One medium-high dimension → mid: plan + competing outline, codex + fable audits, a fresh-context codex final pass.

What we already know (measured, not assumed)

  • Switching a package is one line: vitest run → bun --bun vitest run. CI never names Vitest directly, so no workflow changes.
  • Run once on Bun, seven of the ten suites give exactly the same results as on Node. The other three fail — all for a single reason.
  • That reason: JavaScript modules can carry a small "I was converted from an older module style" marker. Bun answers "yes, it's there" for modules where Node answers "no". Vitest trusts that answer and, for one library (zod, used for input validation across the wallet), throws away the export the code needs. Vitest fixed this in May 2026 (issue #10359, fix #10363) — but only in Vitest 5, not the Vitest 4 we use. Turning off that one Vitest feature makes the extension's 4,635 tests pass identically on both runtimes.

Phases

Phase 0 — Foundation (nothing changes runtime yet)

Add one shared test setting (the workaround above, with a note saying exactly when to delete it), give the four packages that had no test config a tiny explicit one, and build a small "soak" tool: it runs a package's real test command N times, records which runtime actually ran (so a "Bun" report can never secretly be Node), and compares two reports strictly — same commit, same list of tests, zero failed runs, no test failing more often than before. The tool ships with tests that make it fail on purpose (a crash, a hang, an unhandled error, missing output), so CI proves the gate can say no.

Proves itself by: lint + typecheck green, every suite still green on Node with the new setting, the tool's own tests green.

Phase 1 — Switch, then prove it at one commit

Switch every package's test command to Bun (one commit per package, so any one can be reverted alone). Then, at that single commit and after a fresh install from the lockfile, run each of the twelve suites 30 times on Node and 30 times on Bun and compare all twelve pairs strictly (same commit, same installed packages, same list of tests, zero failed runs on either side, every run's engine recorded); run the whole-repo test command five times the way CI runs it (all packages at once); and trigger the real CI pipeline on the branch to see it on GitHub's runners before any pull request exists. Any code change after that proof re-runs the whole proof. A Bun-only failure is never "a flake to retry": either the test assumed something Node-specific and gets fixed to be runtime-neutral, or Bun really differs — then that package stays on Node and the decision comes back to you.

Proves itself by: the recorded fresh install, 24 soak reports with zero failed runs, 12 strict comparisons passing, the 5× whole-repo run green, the CI run tied to that exact commit green.

Phase 2 — Documentation

State the new runtime and the workaround's expiry in the repo's operating docs, fix two stale sentences found on the way (which packages CI tests; the test-suite table), and correct the Bun-adoption dossier.

Proves itself by: lint green, and the final diff matching the planned file list — nothing outside it.

Human context

Node vs Bun. Both run JavaScript; Bun is the one this repo already uses to install packages and run scripts. Running the tests on Bun too removes a second runtime from the picture and, as a side effect, pins the test runtime to an exact version in CI (today's Node there is whatever the runner image ships).

Why not flip one global switch? Bun has a setting that would make everything run on Bun at once — including the build, Storybook, and the browser tests you asked to keep on Node. Per-package lines are explicit and revertable one at a time.

Why 30 runs? A test that fails one time in ten is caught with 96 % confidence; one in twenty with 78 %. It is the agreed budget, not a proof of perfection — which is why the whole-repo run is also repeated and a real CI run is required.

What stays on Node: the Puppeteer browser tests (smoke and network suites) and their helper scripts; the watch-mode commands unless a quick hands-on check shows watch mode behaves on Bun.

Open questions

  • Upstream: the Vitest bug is fixed in Vitest 5 only. Do you want to ask the Vitest maintainers for a Vitest 4 backport (a comment on issue #10359), or simply wait for Vitest 5 and delete the workaround then? Either way the plan works; this only changes when the workaround retires.
  • If Node itself turns out flaky: should any suite fail even once in its 30 Node runs, the plan stops and asks you — accepting a known flake budget is a policy decision.
  • If a package genuinely cannot run on Bun: the plan stops and asks whether to abort or ship a reduced scope.

Approval decision needed from you

  • Confirm tier mid.
  • Confirm the validation plan: 30 runs per suite on both runtimes at one commit, strict comparison, 5× whole-repo run, one real CI dispatch before the PR.

  • Pick the upstream option (backport request vs wait) — or defer it; it does not block the work.
