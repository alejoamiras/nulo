Closing the Firefox arc

Three loose ends came out of the last Firefox pull request. This plan ties off two, consciously drops the third, and — your main ask — adds the tests that stop any of it from quietly breaking again on either browser.

Nothing a user sees changes. No new permissions, no stored keys, no new dependencies. Roughly a hundred lines of wallet code; the rest is tests, CI lists and documentation.

The one real bug, to scale

If the wallet's background process dies while a dApp is waiting on a transaction, the dApp is never told. It just waits. We measured 210 seconds of silence on Chrome and on Firefox and stopped watching; the dApp's own give-up timer is 300 seconds.

Dashed line: 210 s, where the earlier measurement ended. Target after the fix: 15 s or less, measured; the test itself fails hard at 30 s.

Why it hangs. The encrypted link between a dApp and the wallet lives only in the background's memory. A restarted background has no memory of it, so when the dApp asks "are you there?" every five seconds, the new background doesn't recognise the question and says nothing.

The fix. The Aztec SDK already has a "you've been disconnected" message that needs no encryption, and dApps already react to it by failing every pending call at once. Nobody sends it after a restart. So: when a message names a link this background has never heard of, reply "disconnected" — to that tab only. The dApp shows "disconnected", the person reconnects, and carries on.

Words you'll meet

Background
The wallet's always-on engine. The browser may kill it at any time; the wallet then locks itself on purpose.
Heartbeat
The dApp's "are you there?" every 5 seconds while it waits for an answer.
Canary
A long end-to-end test that creates accounts and sends real transactions, to catch an Aztec upgrade that would break people's accounts. There are two: one for normal accounts, one for passkey accounts.
Real proving
Generating actual cryptographic proofs — slow, so most tests skip it ("proverless"). A canary is only meaningful with it on.
Lane
A CI pipeline: Chrome on pull requests, Firefox on pull requests, and each browser nightly. Four in all.
Fence / pin
A small test whose only job is to turn red if a specific fact stops being true.
Mutation check
Breaking the code on purpose to confirm the test really does go red. A test that can't fail protects nothing.

What recon turned up that you didn't ask for

The passkey canary has never run with real proving in CI. It isn't listed in any pipeline, so it falls into the fast no-proving pool by accident — green every time, proving nothing. You chose to fix it here. The plan also adds a pin so no canary can land in the wrong pool again, in any of the four lanes.

The passkey canary can run on Firefox after all. On Chrome a test passkey dies with the popup that made it, so that test keeps a popup open while it kills the background — which Firefox refuses to do. But on Firefox a test passkey outlives its window, so there the test can close the popup first. That difference goes where every browser difference goes: on the driver, not in the test.

  1. Pull request 1 — the fix

    Catch the bug on camera

    CI lists and the pool pins

    Both canaries join the real-proving job in all four lanes and leave the fast pool. Pins: every canary sits in a real-proving job everywhere; Firefox runs exactly Chrome's files; no job can fail behind a green summary check. And a new CI step reads the test run's own results: if a canary's real test — named, not just "something in that file" — did not pass, or anything was skipped, the job goes red. Today nothing would notice — another test's proofs would keep the check green.

If the job would run past 22 of its 30 minutes it is split in two — and both ways a split could have weakened a check are closed in the same commit.

New written rule: on an Aztec upgrade, a red Firefox canary holds the upgrade just as a red Chrome one does. A closing ledger lists what is done, what was consciously accepted, and what is only waiting on the calendar.

    Proves itself by: a checklist of every place the rule lives plus a search for leftovers; the full gates; a second codex loop, then one across both pull requests.

Honest limits — documented, not fixed

  • On Firefox, a call that has to wake a sleeping background is itself lost — the wallet's cold-start code only keeps connection requests, by design. The dApp's heartbeat, five seconds later, is what gets the "disconnected" answer. Still seconds, not minutes.
  • A dApp built on an old SDK with no heartbeat still waits out its own timer; a later call fails at once.
  • A tab in the background has its timers slowed by the browser, so "seconds" means a visible tab.
  • If the extension itself is reloaded or updated under an open page, that page must be refreshed — as today.
  • A connection that was still being set up when the background died times out on the dApp's side, as today.

Dropped on your call: the few-millisecond window in the Firefox kill helper. The reviewer rated it acceptable for a test tool; closing it would need lines only you can write. The ledger records it as accepted.

Three places the work stops and comes to you

Coverage is never reduced on the session's own say-so. Each of these is decided in advance as a stop, not a judgement call:

  • The measured rejection takes more than 15 seconds on either browser. Proposed remedy: also answer during start-up — it edits the delicate cold-start code, so it's yours to allow.
  • On Firefox, the dApp's traffic turns out not to wake the background — seen twice, not once. No wallet-side design can help then; the success criterion would be restated per browser.
  • The passkey canary's last stage can't pass on Firefox. No skip lands without your decision.

Why "mid"

One of six risk dimensions is high — blast radius: every dApp connection on both browsers passes through the changed code. Security and SDK coupling are medium; novelty, irreversibility and migration are low. The risk is contained by fences rather than by more planning, so: one plan plus a competing outline, two independent audits, a decision ledger, a final fresh audit. /code-review stays off, per your standing instruction.
