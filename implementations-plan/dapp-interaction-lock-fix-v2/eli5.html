What problem is v2 even trying to solve?

PR #53 shipped a fix for the bug you reported during friends QA: when a dApp fires two transactions at once, only one card was showing up. The fix had three internal layers (you don't need to remember them — they just work). It merged.

But during your manual QA you found two more issues:

  1. A transaction card briefly disappeared when one tx finished while another was still queued. Codex's final audit confirmed my fix for this was partial — it only worked in a narrow timing window. The general case is still broken.
  2. The "queued" UX feels wrong: popup #2 only opens after popup #1's full transaction-build completes. You wanted popup #2 to open the moment popup #1 is approved, with T1's card running through "Estimating fee → Simulating → Proving" while T2 waits.

v2 was supposed to fix both. The plan got needs-revision from both audits.

What the audits actually told me

I sent the v0 plan to two independent reviewers — codex (Anthropic) and an opus subagent — in parallel. Both came back with similar verdicts. Worth surfacing the convergent points first, then where they differ.

Both audits agree

  • Split the work into two PRs. Don't bundle.
  • "Layer A" (the small bug-fix closeout) is mechanical and ships fast. Four code sites get a small change. One filter gets flipped. One invariant gets pinned. ~150 lines. Closes the bug your QA hit.
  • "Layer B" (parallel popups) is underspecified and has architectural ambiguities. Treat as a separate planning pass.
  • The proposed change moves load-bearing concurrency boundaries. Until those are nailed down, audit cycles will just keep re-flagging the same gaps.

Where they disagree (this is the interesting part)

Opus argues: don't even add a per-account "wait your turn" lock for parallel popups. Instead, just move when the existing FIFO baton releases + add a small interaction queue inside one service. The existing Aztec PXE write lock already serializes the dangerous parts of transaction building. Prototype the simpler design first; if it works, you skip a major refactor.

Codex argues: specify the lock primitive precisely before approval. The repo's current Lock force-releases after 5 minutes, which would silently break the very race a new exec mutex was supposed to prevent. Get the contract right or skip it entirely.

These aren't contradictory — they're complementary. Opus's "spike the simpler design first" implicitly answers codex's "specify the lock or skip" by trying to skip.

Three concrete mistakes in my v0 plan

Useful to flag these out loud so future-me doesn't re-introduce them:

1. I picked the wrong stage for "approved but waiting"

My v0 plan said the second transaction (T2) could sit in pending stage while waiting for T1 to finish. Codex pointed out that the journal reaper sweeps pending-stage records after 2 minutes. A real transaction with prove time longer than 2 minutes would get killed by the reaper, leaving the dApp's promise hanging.

The right stage for approved-but-waiting is queued (10-minute reaper window). Different design.

2. I'd silently picked the wrong lock primitive

The repo has a Lock class used in lots of places. It has a 5-minute auto-release built in — designed to prevent deadlocks if some code path forgets to release. But for a per-account "wait your turn while T1 proves" lock, that auto-release would let T2 cut in line if T1's prove crosses 5 minutes. Proving regularly crosses 5 minutes on slow CI runners.

Either use a different lock primitive (no auto-release) or skip the lock entirely (opus's anti-suggestion).

3. My proposed safety test for transaction-hash propagation was nonsense

I'd written: "verify tx.getTxHash() matches what node.sendTx(tx) returns." Codex caught that node.sendTx returns nothing — it's a fire-and-forget call. The hash is a purely local computation from the proven transaction bytes. So my proposed test compared a value to undefined.

The right test is pinning the invariant that the submitting stage's txHash matches the succeeded stage's txHash. Both are local computations off the same tx; if they drift, the bug is in the local hash function and worth catching.

What the new plan looks like

Layer A — v2 PR (small, ships first)

  • Plumb submitting.txHash at four sites in execution/service.ts. The hash is already computed (it's used on the next line for succeeded.txHash); we just also write it to the submitting transition.
  • Flip the disappearing-card filter in RecentActivityView.vue to journal-first. Drop the blanket "any in-flight task hides all pending chain txs" branch. Use the per-hash filter that becomes live now that submitting.txHash is populated.
  • Add an invariant pin in transitionOperation: submitting.txHash === succeeded.txHash on the same record.
  • Update the synthetic "intended-contract" unit tests to assert live production behavior.

This is mechanical, deterministic, and closes the bug your QA hit. ~150 LOC. One PR.

Layer B — separate plan + PR (parallel popups)

  • Spike opus's simpler architecture first: move the existing baton release point + add a per-session interaction queue inside DappInteractionService. No new locks. Trust PXE's existing serialization.
  • If the spike works (one day max): ship the simpler design.
  • If the spike fails: write a proper plan with the exact lock contract codex demands (which primitive, abort semantics, SW restart recovery, reaper-stage interaction).

What I'm asking you

Earlier you said "bundle parallel popups into v2." Both audits are pushing back on that with new technical information. I want your call:

  1. Split (audits' recommendation): v2 = Layer A only. Layer B becomes v3 with the spike + new plan.
  2. Keep bundled, but rewrite: I re-do the plan addressing every audit gap, do the spike inside the plan, re-audit. Bigger PR but ships everything together.
  3. Drop Layer A entirely: accept the partial filter fix from #53 is good-enough; the disappearing-card hole only matters in narrow timings. Move directly to Layer B.

I'd recommend #1 because the audits' arithmetic on Layer B is right — the architectural ambiguities aren't worth carrying through Layer A's review.
