Passkey display-name branding

/blueprint light · extension-only · awaiting your approval

When you make a passkey wallet, the passkey shows up in iCloud Keychain (and Google/1Password) under an ugly machine label like profile-a3f29b14. This plan changes that label to something you'll actually recognize: nulo-{your-profile-name}-{id} — e.g. nulo-alice-a3f29b14. It's a cosmetic label change only: it does not touch your keys, your wallet address, or anything that can spend money. Existing passkeys keep their old label; only new ones get the nice name.

Why this tier was chosen

light. Rubric — all six risk dimensions scored LOW: no novelty (the passkey flow is fully mapped), tiny blast radius (only the label of new passkeys), reversible (it's a code constant), zero migration (no key/address change — verified), no new external coupling, low security sensitivity (one privacy trade-off, surfaced and accepted). Single package, bounded, low-risk → light. Codex reviewed it and gave conditional approve; all conditions are now folded in.

Phases

Phase 1 — Build the "name cleaner"

A small standalone function that turns a raw profile name into a safe, tidy label piece: lowercases it, removes emoji / accents / weird invisible characters, caps the length, and — if nothing usable is left (e.g. an all-emoji name) — falls back to a generic nulo-profile-{id}. Kept separate from the passkey code so every messy-input case is easy to test.

Proves itself by: a focused unit-test file covering spaces, Élodie→elodie, emoji, invisible/right-to-left characters, length cap, and empty/non-Latin fallback — plus lint & typecheck, all green.

Phase 2 — Carry the name to the passkey & flip the label

Pass the profile name down through both registration paths (the normal in-app one and a secondary background one codex caught) to the single place that builds the passkey, and set the visible name to nulo-{name}-{id}. The name is made a required field on purpose, so the TypeScript compiler refuses to build until every path is wired — no path can be silently missed.

Proves itself by: the typechecker forcing every path to pass the name; a regression test proving only the label changed (the crypto fields are byte-identical); the full audit:vue suite green; then you eyeballing a freshly-made passkey in iCloud Keychain.

Human context

A "passkey" stores two human-readable labels when it's created (user.name and user.displayName). Your password manager shows one of them. Today the wallet sets them to profile-<random-id> because, at the moment the passkey is made, the code simply never received your chosen profile name — it only had the internal id. The whole change is really just "hand the name to that one spot, after tidying it up."

The one honest trade-off (you already accepted this). Putting your profile name in the passkey means that name syncs to Apple/Google's cloud along with the passkey. For a privacy wallet that's a real (if small) change from today's leak-nothing profile-<id>. We reduce it by only ever sending a cleaned-up slug (lowercase, plain characters), and the fallback for empty/non-Latin names contains no personal text. You chose the nulo-{name}-{id} format knowing this.

Open questions (please confirm)

  • O1 — non-Latin names. Default: a name in CJK/Arabic/Cyrillic (e.g. "山田") can't be ASCII-slugged, so it falls back to nulo-profile-{id} (no name shown). Alternative: keep Unicode so it shows nulo-山田-{id}. Default is ASCII (safer, predictable). OK?
  • O2 — two tiny defaults codex asked me to surface. (a) The "friendly" displayName is set to the same nulo-{slug}-{id} as the main name, so every manager shows the same thing (vs. showing a raw "Alice"). (b) The name part is capped at 24 characters. Keep both, or change?
