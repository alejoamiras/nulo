# Codex audit - Fee estimate reuse

Date: 2026-04-28
Model: gpt-5.4 with `reasoning_effort=high`

## BLOCKING

1. `fingerprintFeeSettings()` does not fingerprint nested `paymentMethod` fields, so the reuse gate can treat materially different fee settings as identical. The implementation is `JSON.stringify(fs, Object.keys(fs).sort())` (`packages/extension/src/wallet/services/execution/service.ts:169-173`), which drops `paymentMethod.kind`, `fpcId`, `inPublic`, and all `fjwc` claim fields even though those fields change the execution path (`packages/wallet-bridge/src/fee.ts:1-35`). `tryConsumeTransferEstimate()` relies on that hash as part of its "input drift" guard (`packages/extension/src/wallet/services/execution/service.ts:494-505,596-606`). I confirmed the collision locally: both `{ paymentMethod: { kind: "fj" }, priorityLevel: "normal" }` and `{ paymentMethod: { kind: "fpc", fpcId: "abc", inPublic: false }, priorityLevel: "normal" }` serialize to the same fingerprint. Proposed change: replace this with a deep stable serializer or an explicit fingerprint over `priorityLevel` plus `paymentMethod.kind` and each variant's discriminant fields.

## SHOULD-FIX

1. Private-FPC dApp transactions still persist `pay_fee` as the primary call, so the settled activity card and tx detail page can still render "Pay Fee". Both dApp execution paths pass the raw `txCalls` array to `addTransaction()` (`packages/extension/src/wallet/services/execution/service.ts:890-914,1579-1605`), while `getPrimaryCall()` only filters `sponsor_unconditionally`, `fee_entrypoint_private`, `fee_entrypoint_public`, and `set_authorized` (`packages/extension/src/utils/tx-enrichment.ts:29-30,56-60`). PrivateFPC injects `pay_fee` (`packages/extension/src/wallet/services/fpc/handlers/private-fpc-handler.ts:35-42`). The tx detail page also keeps its own stale `FEE_METHODS` copy for both fee labeling and the visible calls list (`packages/extension/src/popup/pages/tx/[id].vue:43,108-112,179-181,425-445`). The in-flight journal title is already fine because both dApp paths capture the pre-mutation primary method before fee injection (`packages/extension/src/wallet/services/execution/service.ts:881-887,1550-1556`); the remaining bug is in the persisted tx record. Proposed change: export a shared `FEE_METHODS` or `isInfrastructureCall()` helper, add `pay_fee`, consume it in both `tx-enrichment.ts` and `tx/[id].vue`, and extend the detail-page fee label mapping for `pay_fee` (and optionally `fee_entrypoint_public`, which is filtered today but still unlabeled).

2. The reuse snapshot still misses runtime state that can invalidate a prebuilt `txRequest` even when inputs, endpoint, and base fee all match. The normal build path re-registers missing contracts and artifacts into PXE before the tx is proved (`packages/extension/src/wallet/services/execution/tx-request-builder.ts:107-120`), and the codebase explicitly treats PXE-local registration as execution-critical for simulation (`packages/extension/src/wallet/services/execution/service.ts:1364-1367`). The reuse path skips that preparation and goes straight from `getPXE()` to `proveTxTask()` (`packages/extension/src/wallet/services/execution/service.ts:381-387,411-416`). I did not find a direct in-tree statement that `proveTx()` itself needs those registrations, so this is an inference from the normal path always priming PXE before execution. Separately, "pending nonce mutation" is not the real race here because `buildStandard()` uses a fresh random nonce (`packages/extension/src/wallet/services/execution/tx-request-builder.ts:127`); the real uncovered drift is same-account pending tx / note selection / private-FPC balance changes after estimate. Proposed change: either snapshot a PXE-generation token and invalidate reuse when it changes, or run a lightweight "prepare PXE for these actions" step on reuse; also snapshot the same-account pending tx set at estimate time and reject reuse if it changes before confirm.

3. The base-fee fingerprint is sampled after `buildAndEstimateTxRequest()` returns, not from the exact fee sample that finalized the cached `txRequest` (`packages/extension/src/wallet/services/execution/service.ts:563-587`). If `node.getCurrentMinFees()` changes between the strategy's internal finalize step and this second fetch, the cache stores fingerprint B for a request built with fee sample A. Proposed change: have the builder/strategy return the exact fee fingerprint it used, or snapshot the finalized `txRequest.txContext.gasSettings.maxFeesPerGas` and compare reuse against that derived value instead of performing a second live fee read.

## NICE-TO-HAVE

1. Add direct coverage for the new reuse contract. I found no service tests for `fingerprintFeeSettings()`, `tryConsumeTransferEstimate()`, or the new `estimateId` flow; the only `pay_fee` coverage in tree is an e2e that proves submission succeeds (`packages/extension/tests/e2e/network/fee-methods.test.ts:118-180`), not that the persisted card title/filtering stays correct. Targeted tests for nested fee-settings hashing, pending-account invalidation, and PrivateFPC dApp activity rendering would make this branch much safer to maintain.

2. Profile drift could be made more explicit, but I do not think it is a correctness blocker. A profile swap already fails closed because `getNetwork()` and `getAccountContract()` are scoped to the active profile (`packages/extension/src/wallet/services/network/service.ts:178-185`, `packages/extension/src/wallet/services/account/service.ts:117-131`), and `executeTransfer()` re-resolves both before proving (`packages/extension/src/wallet/services/execution/service.ts:381-387`). If you want cleaner diagnostics, add `profileId` to the reuse snapshot so the cache can be rejected before the entry is consumed.

## VERIFIED

1. The `executeTransfer()` fix itself is clean from the popup-Send activity-feed perspective. The in-flight task and journal record are transfer-owned (`packages/extension/src/wallet/services/execution/service.ts:313-315,323-328`), and the settled tx record now always materializes a transfer-only call shape from `token` / `fnName` / `args` rather than from the FPC-mutated `txCalls` array (`packages/extension/src/wallet/services/execution/service.ts:365-454`). In-flight rendering reads token/network data from the journal (`packages/extension/src/popup/components/modules/general/RecentActivityView.vue:121-171`); settled rendering reads the persisted transfer call (`packages/extension/src/popup/components/modules/activity/TransactionCard.vue:35-95`). I did not find another popup-Send persistence path that leaks FPC-mutated calls into the activity title/subtitle path.

2. Discarding `_txCalls` inside `estimateTransferFee()` is mechanically safe. The full planner/builder/strategy pipeline still runs (`packages/extension/src/wallet/services/execution/service.ts:553-566,1802-1837`), and `txCalls` is only one returned data slot from `buildStandard()` after all registration/authwit/build side effects have already happened (`packages/extension/src/wallet/services/execution/tx-request-builder.ts:123-362`). Ignoring the variable does not skip any work that downstream callers depend on.

3. Single-shot consumption is the right retry behavior here. `tryConsumeTransferEstimate()` deletes the entry on access (`packages/extension/src/wallet/services/execution/service.ts:472-486`), while the popup immediately navigates away once `executeTransfer()` is dispatched and re-estimates on any later retry (`packages/extension/src/popup/pages/send.vue:235-292,324-372`). Keeping the same cached `txRequest` alive across prove/send failures would increase stale-state and duplicate-send risk more than it would help.

4. Active-profile swaps, account deletion, and network deletion all fail closed rather than sending under the wrong identity. `executeTransfer()` re-resolves the active-profile network and account before reuse (`packages/extension/src/wallet/services/execution/service.ts:381-387`), `getNetwork()` rejects networks outside the active profile (`packages/extension/src/wallet/services/network/service.ts:178-185`), and `getAccountContract()` rejects unknown or deleted accounts (`packages/extension/src/wallet/services/account/service.ts:117-131`). Contact mutation is irrelevant to reuse because the cached input is already the resolved recipient address (`packages/extension/src/popup/pages/send.vue:244-260`).

5. The 5-minute TTL is defensible as a UX cache bound. Once the fee-fingerprint issue above is fixed, the exact base-fee match is what prevents fee-market skew; the remaining uncaught risk over that window is account/FPC state drift, not "five minutes is too long" by itself (`packages/extension/src/wallet/services/execution/service.ts:235,488-491,631-637`).
