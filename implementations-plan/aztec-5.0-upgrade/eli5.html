Aztec 4.2.0 → 5.0.0-rc.1 upgrade

Protocol hard fork · mega-deep blueprint · awaiting your approval

We're moving the whole wallet (and the faucet, playground, and the L1↔L2 bridge) from Aztec 4.2.0 to 5.0.0-rc.1. This isn't a routine version bump — 5.0 is a hard fork: the way account addresses are computed changes, the signature math changes, and the wallet's local database gets wiped on first open. So existing test wallets and accounts on the test network stop working by design. We agreed to document that reset rather than build migration screens (it's a release candidate on a test network).

Status: approved (2026-06-19)

You chose the strictest proof: full network end-to-end tests on a real 5.0 network with native (fast) proving. Earlier this looked blocked on a 5.0-specific build of the accelerator-server helper. It isn't — you confirmed the helper downloads the requested proving backend (bb) on demand, so the existing one proves 5.0 by fetching 5.0's bb on first use. So there's no external release to wait on; CI just needs its version pin refreshed (Phase 0, small). Native proving stays the bar, and it's reachable now.

Why mega-deep

All six risk dials are HIGH: it's the first 5.0 hard-fork bump (novelty), it touches every package (blast radius), the test-network reset can't be undone (irreversibility), the local DB + Noir contracts must be migrated (migration cost), it pulls 3 external prerelease libraries + a pinned binary (external coupling), and it changes signature + key crypto (security). So we did the heaviest planning: deep research, a second independent plan, and an adversarial codex audit (which rejected the first draft and forced real fixes).

Phases (plain language + how each proves itself)

Phase 0 — Refresh the CI proving-helper pin (small; not a blocker)

The helper downloads 5.0's proving backend on demand, so no new release is needed. Just bump the CI version pin (v1.0.1 → current) + its checksum, and make sure the CI machine can do the one-time download.

Proves itself by: against a 5.0 network the pinned helper reports bb_available=true and a native-proving test transaction succeeds.

Phase 1 — Bump dependencies + unblock the install

Change all the version numbers, temporarily allow the brand-new 5.0 packages past the 7-day supply-chain delay, re-key the two patches, and prove the risky-but-invisible assumptions early (do the import paths still exist? does the WASM extractor still find its files?).

Proves itself by: a clean frozen-lockfile install + the build reaching the WASM step + import-resolution probes passing.

Phase 2 — Core runtime (fees, PXE, accounts)

Re-derive the copied fee logic from 5.0 (and add tests for the new gas-limit path), fix the PXE setup so it loads the AuthRegistry, and update the tx-building calls.

Proves itself by: aztec-runtime typecheck + unit tests (incl. new fee cases) + lint, all green.

Phase 3 — Extension + the custom RPC patch + DB wipe

Fix the receipt/gas call sites, carefully re-check the 3-copy schema patch against 5.0, and bump the storage version (which re-triggers the PXE database wipe).

Proves itself by: audit:vue + test:all (so the wallet-bridge registry tests actually run) + the note-slot tripwire test, all green.

Phase 4 — Faucet + playground

Mirror the schema-patch edits, resolve the wallet-creation option name, migrate the faucet's bridge screens, and re-pin the deterministic contract addresses (computed offline — no live deploy needed).

Proves itself by: audit:faucet (incl. offline deploy-verify) + playground typecheck & build.

Phase 5 — Recompile the Noir bridge contracts + bridge code

Bump the 3 Noir crates to 5.0, migrate the message-passing API, recompile, and fix the bridge TypeScript + its deploy manifests.

Proves itself by: Noir compile + keystone aztec test + bridge-core tests (incl. the address tripwire) + a bridge deposit/withdraw smoke run on a 5.0 network.

Phase 6 — Network end-to-end on real 5.0

6A (now): proverless run to validate the migration without the binary. 6B (the real bar, blocked on Phase 0): native-proving run that cannot silently fall back to slow WASM proving.

Proves itself by: 6B — the network-e2e suite green with the canary shards running native proving (required-mode build stamp + accelerator up + zero WASM fallback). Bulk shards stay proverless by design. This is the definition of done.

Phase 7 — Docs + supply-chain cleanup

Document the reset, then a follow-up PR removes the temporary supply-chain exception once 5.0.0-rc.1 ages past 7 days (~2026-06-22).

Proves itself by: Quality check green + actionlint clean + docs reviewed.

Human context

The wallet doesn't ship its own account contract — it rides Aztec's SDK — so the scary "Schnorr signature scheme changed" item is mostly absorbed by the dependency bump. The genuinely fiddly bits are: a copied fee file that can be wrong without the compiler noticing; a runtime patch that fails at startup (not at compile time) if an import moved; and the Noir contracts, which are a separate compiler toolchain. The codex audit's most important catch was that running the network tests the obvious way would silently use slow WASM proving and look green without actually proving anything on 5.0 — so the final gate now explicitly demands the native-proving stamp.

Decisions (resolved 2026-06-19)

  • Proving-helper sequencing — dissolved (downloads bb on demand; native proving unblocked now).
  • Supply-chain delay — add the temporary 7-day-gate exemption for first-party @aztec/* now; a follow-up PR removes it once 5.0.0-rc.1 ages out (~2026-06-22).
  • PR shape — one feature-branch PR. A green-per-step stack into dev isn't viable: the single lockfile means a deps-only intermediate state doesn't compile.
  • /harden security — recommended at pre-release time (crypto + supply chain); not scheduled now.

Approved — scope, tier, and validation confirmed

Everything (incl. Noir + bridge), mega-deep, documented-reset posture; definition of done = native proving enforced on the canary shards (6B). Implementation drives via the /loop seed below.
