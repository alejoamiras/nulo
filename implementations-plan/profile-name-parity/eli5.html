Profile-name parity

A plain-English companion to plan-v2.md. No file paths, no acronyms, no "ProfileServiceClient." Just what we're changing, why, and what could go wrong.

The problem in one paragraph

Nulo has two ways for a user to create a wallet account — the first-run onboarding tab, and the in-app "create" page inside the extension popup. On the onboarding tab, the user types a name (like "Spending" or "Work") before the account is created. Inside the extension, they don't — Nulo makes one up automatically, calling it "Profile 3" or whatever, and the user has to rename it later. That's the first half of the issue.

The second half: the onboarding tab calls these accounts wallets, and the rest of the extension calls them profiles. Same thing, two words. A new user picks a wallet name on day one, then opens the app and sees "Edit profile" and gets briefly confused.

What we're doing

Two changes, landing together as one PR:

  • Add the name field to the extension's create + import pages, so people pick the name before the account is created — same as onboarding does today.
  • Pick one word for user-facing text. The choice: "Profile." The extension already uses it everywhere; the onboarding tab swaps "Wallet" → "Profile" in headings, placeholders, buttons, and error messages.

Code that lives behind the scenes (function names, variable names, internal APIs) keeps its existing names. The word swap is only in things the user sees.

The two surprises we found during planning

Surprise 1 — the import-from-backup path silently ignores typed names

When someone restores from a backup file, the file already contains a name ("My Vault" or whatever the user picked when they made the backup). The restore code happily uses that, ignoring anything the user types into the name field on the restore page.

This is actually a pre-existing bug in the onboarding flow — the "Wallet name" field there does nothing on the full-backup path. The fix: when the user picks a backup file, we read the name out of it and put it in the input field for them. If they want to rename, they can — and that override now actually works.

Surprise 2 — many tests break because they relied on the auto-name

The auto-naming behavior wasn't just a UI convenience — it was load-bearing for the automated test suite. Many tests clicked "create profile" without typing a name, expecting the auto-name to kick in. After this change, those tests would just hang on the empty-name shake animation.

The plan now spells out every test file that needs an extra "type a name here" step, plus two tests that hardcoded the expected name as "Profile 1" (which only existed because of the auto-naming sequence).

Decisions we locked in

Decision 1
Which word wins? "Profile." Onboarding switches from "Wallet."
Decision 2
How deep does the rename go? Only user-visible text and end-to-end test IDs that contain the loser term. Internal code keeps its current names.
Decision 3
Which surfaces get aligned? All of them — Create, Import, Edit, Select, Settings, the auth pill at the top. No "Profile" left next to "Wallet" anywhere a user can see.
Decision 4
What happens with the backup path? Prefill the name field from the backup when the user picks the file. They can override. The override is honored.
Decision 5
What if a user types a name that already exists? Block them at the create/import step with a clear inline message ("This name is already in use."). They have to pick a different one. Exception: when restoring two backups with the same name, the app silently appends a number — that's existing behavior and we kept it.
Decision 6
How long can a profile name be? 32 characters everywhere. The Edit dialog was capped at 25 — pre-existing inconsistency. Now it matches.

The phases, in order

P0 — Shared name-input toolkit

Build a small reusable piece (an "input field with validation, error shake, and a duplicate check") that all four create/import pages share. Then refactor the two onboarding pages to use it. No visible change yet.

Why first? Doing the toolkit before the feature work means the feature work is "use the toolkit" rather than "copy-paste twice and try to keep them in sync."

P1 — Fix the backup name drop

Change the backup-restore code so it actually uses the typed name when the user provides one, and exposes the backup's embedded name so the form can prefill it.

Why second? Fixing this before adding the name field to the extension's import page means both pages (onboarding and extension) get the fix at the same time, without an intermediate "extension shows a field that doesn't work" state.

P2 — Extension's Create page

Add the name input, plug it into the toolkit, drop the auto-name.

Why now? Foundation is ready; user-visible feature can land cleanly.

P3 — Extension's Import page

Drop the "My Profile 3" pre-fill, add the same name input, wire it to the now-fixed backup-restore.

P4 — Edit dialog + Storybook tidy

Edit dialog's character limit goes from 25 to 32. A Storybook story that still says "Wallet" flips to "Profile."

P5 — Onboarding copy sweep

Change "Wallet" to "Profile" everywhere on the onboarding pages. Tiny, mechanical, one-by-one.

P6 — Test suite fixup

Update every test that relied on the auto-name behavior to type a name first. Update two tests that hardcoded "Profile 1." Rename one test constant for cleanliness.

Why so late? Test changes touch the most files; doing them after the source changes keeps the commits clean and reviewable.

P7 — Final guard rail

Re-search the entire extension for any leftover "Wallet" string. Run the full local test gate. If anything new pops up, address it.

P8 — Implementation review

After the code is written, send the diff to an independent reviewer (another model, different family) and ask "what would an attacker exploit? Where's the silent failure?" Fix whatever it finds.

What we're explicitly NOT doing in this PR

  • No rename of "Lock wallet," "Open wallet," "Wallet version" on the About page. Those refer to the app itself, not the account record. Keeping "wallet" there is correct.
  • No defense against look-alike characters. A user could type "Acme" with a Cyrillic 'А' instead of Latin 'A' — they'd look identical but be different strings. This is real but rare; we'd rather ship the main feature now and harden against confusables in a focused follow-up.
  • No server-side validation of backup-file names. If someone crafts a malicious backup with a 5,000-character name, the restore code will accept it. Defense-in-depth is a separate task.
  • No internal-code rename. The terms "profile" and "ProfileService" stay in the source files. Renaming user-visible text is enough to make the app coherent.

Risks worth knowing about

  • End-to-end tests need careful updating. Eight test files reach into the create or import flow. Each needs a small change. The risk: one of those tests is used by another test we haven't found yet. Mitigation: run the suite after every couple of files, not at the end.
  • Race on the backup-prefill. If someone is mid-typing when they pick a file, the auto-prefill could clobber their input. The fix: only prefill when the input is empty, so half-typed names don't vanish.
  • Existing 30-character profile names were possible via onboarding but couldn't be fully edited in the Edit dialog (capped at 25). Bumping the cap to 32 is permissive — no migration risk.
