Multi-RPC failover, in plain language

Companion to plan.md — what we're changing and why.

What this fixes

Right now, when you set up an Aztec network in Nulo, you can configure multiple RPC endpoints — but the wallet only ever talks to one of them at a time (the "primary"). If that one goes down, you have to manually open Settings, find the network, and flip the primary endpoint to another one. The wallet won't try to recover on its own. It won't even tell you "your primary RPC is unreachable" — operations just hang or error and you have to figure out why.

This plan adds automatic failover: if the primary endpoint fails twice in a row, the wallet silently switches to the next endpoint in your list, runs a quick sanity check that the new one's actually on the right chain, and shows you a small toast saying "Switched to backup RPC: label". The header gets an amber "Degraded" dot so you know you're not on your preferred endpoint anymore. Settings shows both your "Preferred" endpoint and the "Active" one when they differ, with a "Retry preferred" button to snap back.

The tricky bit: PXE state

Aztec wallets keep a thing called the PXE (Private eXecution Environment) — basically a local cache of decrypted notes, contract data, and chain sync progress. The PXE is tied to one specific RPC endpoint because the block stream comes from there. If we change the endpoint, we have to rebuild the PXE.

Naive approach: tear down everything on failover, rebuild against the new endpoint. This wipes your decryption progress. Bad UX — a flaky endpoint shouldn't cost you minutes of resync.

Smart approach (what the plan does):

  • In-flight operations stay pinned to whatever endpoint they started on. If you're mid-transaction and the endpoint flakes, the receipt polling continues against the original URL.
  • Only new operations see the post-failover endpoint.
  • The PXE rebuild happens under a write-lock so existing readers finish before the swap; no half-state.
  • We NEVER wipe the chain database on failover. The notes/senders/contracts stay valid because the chain didn't change, only the endpoint serving it. This is the single most dangerous landmine in this work — there's a function called clearChainState() that would do exactly the wrong thing if called here; the plan flags it loudly.

Threshold + recovery

The wallet doesn't fail over on a single error. It uses a small state machine:

  • 2 hard failures in a row = failover. (Hard = network down, HTTP 5xx, rate-limit, RPC server error.) A single hiccup is forgiven. The fetch layer already has its own retry-with-backoff, so by the time we count a failure, it's "this endpoint replied wrong despite trying multiple times."
  • 60 seconds of healthy traffic after a failure = the counter resets. One bad day doesn't permanently sour an endpoint.
  • After failover, the dead endpoint gets a 5-minute cooldown. After cooldown, it's eligible for re-promotion (but only on next user-driven traffic — no background pinging).
  • If a candidate endpoint reports the wrong chain ID (it claims to be on Aztec mainnet but actually isn't), it gets permanently quarantined for the session. The wallet won't try it again until you restart the service worker or fix the URL.
  • If all endpoints fail, you see a banner: "All endpoints for <chain> are unreachable" with a "Retry preferred" button. The wallet doesn't keep retrying in a loop.

What about transactions?

This is the part where you really don't want bugs. The plan is conservative:

  • Transactions are NEVER auto-retried across failover. If you submit a tx and the endpoint dies mid-submit, the wallet shows you an error. You decide whether to retry — and if you do, the wallet regenerates the tx (same nonce, deterministic) so the second submission gets the same tx hash, which means mempool deduplication handles the "what if both endpoints accepted it" case correctly.
  • Receipt polling stays pinned to the endpoint the tx was submitted to. Even after failover changes the live route, receipts for in-flight txs come from the original endpoint until that endpoint gives up.
  • Reads also don't retry automatically. When a read fails, the wallet fails over (so the next read uses the new endpoint), but the failing read itself returns an error. Polling loops naturally recover because they re-fire on the next tick; user-facing reads either re-fire when the user clicks "refresh" or when the next ambient refresh kicks in. The reason: silently retrying anything (even reads) opens a class of double-execute bugs we'd rather not have.

The 4 phases

Phase 1 — Routing core

Build the failure-classifier, the in-memory route-state, the failover state machine, and the new acquireBinding() API. Drop primaryEndpointId from persisted state (endpoints[0] is now implicitly preferred). Extend the existing onPrimaryEndpointChanged event with a source field that says "failover" or "manual."

Why first: this is the engine. Until it works in isolation, nothing else lands.

Phase 2 — PXE-safe rebind

Wire the PXE service to subscribe to network failover events and rebind the chain runtime under the per-chain write lock. Crucially: never call clearChainState() on rebind. Test that in-flight readers/writers drain cleanly before the new endpoint takes over.

Why second: this is the correctness-critical piece. Phase 1 alone would work without PXE coherence (until the user does anything private), but the moment notes get involved, you need the rebind to be lock-ordered and DB-preserving.

Phase 3 — Caller adoption

~20 call sites across execution/, token/, fpc/, note/, account-state/, transaction/, tx-request-builder.ts. Each one switches from networkService.getNode(chainId) to networkService.acquireBinding(chainId) and uses the binding's bundled { network, endpoint, info, node } for everything in that logical op. Recording submittedEndpointUrl on tx submission switches to the live endpoint, not the persisted preferred.

Why third: this is the biggest grep-and-replace surface. Doing it after Phase 1+2 means the new API is stable when we hit these sites.

Phase 4 — Popup surface

Listen to the new events in the Vue store. Add the amber "Degraded" header dot. Add Preferred/Active markers in Settings. Show the "Retry preferred" banner when all endpoints are exhausted. Wire the toast for failover events.

Why fourth: nothing user-visible should ship until the underlying behavior is correct. The UI is the last layer on top.

Failover state machine

LIVE_PREFERRED (active = endpoints[0]) │ │ 2 hard failures (or 8 soft) ▼ FAILOVER │ │ next endpoint passes chainId probe ▼ LIVE_FALLBACK (active != endpoints[0]) │ ↑ │ │ failover again if backup fails │ │ │ user clicks "Retry preferred" │ OR manually promotes preferred ▼ LIVE_PREFERRED ← snap back If FAILOVER exhausts all endpoints: EXHAUSTED → banner shown, no auto-retry SW restart → wipes in-memory state → LIVE_PREFERRED

The security bit

RPC endpoints are the network's view of the world. An attacker who controls one of your endpoints can lie to you about balances, transaction status, mempool inclusion. The threat model already exists in single-endpoint configurations; multi-endpoint doesn't make it worse, but it does open new attack surfaces:

  • Endpoint impersonation — an endpoint claims to be on chain X but isn't. Mitigation: probe chainId on every promotion. Mismatch = permanent quarantine for the session.
  • Forced failover — an attacker degrades your preferred endpoint to push your traffic onto their malicious backup. Mitigation: the wallet shows you when you're on a fallback (amber dot, toast, Settings markers). You can see "I'm not on my preferred endpoint anymore" and investigate.
  • Double-submit on retry — if a tx submission ambiguously failed, retrying on a different endpoint could land it twice. Mitigation: failover NEVER auto-retries writes. The user explicitly clicks retry; deterministic nonce makes mempool dedupe handle the rest.
  • Mid-failover PXE corruption — if we wiped chain state on rebind, your notes would disappear. Mitigation: we don't. The plan flags this as a critical landmine.

Open questions for you

The final codex pass trimmed my open questions down to just the two real user-facing ones. Everything else is an implementation detail I've made calls on — flagged in plan.md § "Decisions I've made" if you want to override.

1. Drop primaryEndpointId or keep it?

The plan drops it. endpoints[0] is implicitly the user-preferred. To make another endpoint preferred, reorder the array. The first codex pass argued for keeping it as an explicit pointer (more decoupled); the final codex pass confirmed dropping is fine if we add tests/docs asserting "array order is authoritative."

Confirm: drop?

2. No auto-snapback when preferred recovers?

The plan says: once failover happens, the wallet stays on the backup until you explicitly retry (button or manual selection). The alternative is "snap back automatically when preferred's cooldown elapses and a probe succeeds." Auto-snapback would feel magic but could cause flapping if both endpoints are intermittently bad.

Confirm: no auto-snapback?
