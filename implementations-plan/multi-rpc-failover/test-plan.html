Multi-RPC failover — manual test plan

Three tiers. Tier 1 proves nothing broke. Tier 2 exercises the engine. Tier 3 validates the security invariants. Skip down freely.

Open two DevTools windows alongside the popup: popup DevTools (right-click the extension icon → Inspect popup) and the service worker DevTools (chrome://extensions → find Nulo → "Inspect views: service worker"). Most observability comes through the SW console.

Tier 1 — Schema-collapse smoke

≈ 3 min. Verifies the Phase 1B schema collapse (drop primaryEndpointId; endpoints[0] is the preferred) didn't break the visible surface.

  1. Popup opens. Header dot is green (Testnet active, healthy).
  2. Settings → Networks → Testnet. Endpoint list renders. The preferred endpoint (endpoints[0]) is the row with a filled check-circle icon; the others show an empty circle. No text label, just the icon.
  3. Click "Add endpoint" → URL https://rpc.testnet.aztec-labs.com (same as preferred) → expect rejection with DUPLICATE_ENDPOINT. Cancel.
  4. New behavior: the delete button on the preferred endpoint (endpoints[0]) is now enabled. Used to be disabled with "can't delete primary". Do not actually click.
Regression signal: any of the above crashes, renders blank, or throws PRIMARY_ENDPOINT on delete.

Tier 2 — Failover engine

≈ 15 min. Needs at least two endpoints on a chain.

Setup

  1. Settings → Networks → Testnet → Add endpoint. Label Backup; URL a second known-good Aztec testnet RPC if available. If not, run the single-endpoint variant below.
  2. Confirm rpc.testnet.aztec-labs.com sits at position 0, Backup at position 1.

Force failover via DevTools network override

  1. Popup DevTools → Network panel → right-click rpc.testnet.aztec-labs.com → "Block request URL".
  2. In the popup, do something that hits the node (switch accounts, pull-to-refresh on Activity).
Expected: header dot turns amber within a few seconds. SW console logs: 
onPrimaryEndpointChanged { source: "failover", fromEndpointId, toEndpointId }
  1. Unblock the URL in DevTools. Wait ≈ 5 min (the cooldown). Trigger another node action.
Expected: dot returns green. SW logs onPrimaryEndpointChanged { source: "snapback" }.

Single-endpoint forced-break variant

If you can't get a second testnet RPC:

  1. Block the only endpoint via DevTools.
  2. Trigger any node action.
Expected: dot turns red (Inactive); SW logs onPrimaryEndpointDegraded { exhausted: true }. Unblock + trigger again → recovers to green.

Manual promote with snapback

  1. With two endpoints configured, promote the backup so it becomes endpoints[0].
Expected: dot stays green (probe-before-activate passes). Live route flips to backup. SW logs onPrimaryEndpointChanged { source: "manual" }. Promote the original back — same expectations.

Tier 3 — Security invariants

≈ 10 min. Optional but worth doing if you have a second local sandbox. These tests prove the codex blockers stay closed.

Chain-mismatched endpoint promotion (CRITICAL)

This validates the round-2 rework: a never-traffic'd network with a quarantined endpoint must not later activate that endpoint on chain switch.

  1. Get a URL responding to getNodeInfo with a different chainId. Easiest: a separate Aztec sandbox with a fresh genesis.
  2. Try addEndpoint with that URL → expect immediate rejection with ENDPOINT_CHAIN_MISMATCH (this is add-time protection; already shipped).
  3. The interesting case — what if a known-good endpoint later turns mismatched. Simulate: in SW DevTools console, mutate an endpoint's URL by reaching directly into chrome.storage.local bypassing the probe. Switch away from the network, then back. Promote the now-mismatched endpoint.
Expected: promoteEndpoint throws ENDPOINT_CHAIN_MISMATCH. The reorder commits in the persisted list (user preference is durable). The live route stays on the previously-preferred endpoint. The mismatched endpoint enters the invalidChain quarantine.

Concurrent promote interleave

Harder to trigger by hand; covered by unit tests. If you want to eyeball: open SW DevTools, fire two promoteEndpoint calls in quick succession via the client. The later-fired one wins (phase 3 re-reads endpoints[0] and drops stale activations).

What to look for in the SW console

The network service isn't globalThis-exposed, so the easiest observability is event logs. Grep the SW console for:

  • onPrimaryEndpointChanged — every route flip (manual / failover / snapback).
  • onPrimaryEndpointDegraded — exhaustion signal.
  • Failed to fetch node info — probe errors.
  • PxeServiceClient.rebindChain — offscreen PXE rebind issues.
What's NOT yet wired (Phase 4 follow-up):
  • Toast on failover / snapback.
  • Settings page "Preferred" vs "Active" split markers when they differ.
  • Persistent "All endpoints unreachable" banner + "Retry preferred" button on exhaustion.
The only new user-visible UI in this PR is the amber Degraded dot in the header. Everything else is engine-side behavior observable through the SW console.
