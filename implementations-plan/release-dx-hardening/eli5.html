Release DX Hardening

What we built so that shipping dev → main stops being a 45-minute hand-cranked ordeal. SHIPPED → PR #149 (into dev, not merged)

TL;DR. The last release (v0.23.0) hurt: a manual unstick step, a faucet that booted with the wrong chain and broke prod, a manual main→dev sync, and a lurking risk of accidentally jumping to 1.0.0. We automated or guarded every one of those. The new machinery lives in small, unit-tested TypeScript (85 tests) with thin GitHub-Actions glue. A robot reviewer (codex) then tore it apart and found 4 real bugs, which we fixed. Nothing is merged, nothing is live, no release was fired. The one thing I need from you: after your next normal release proves it works, flip a single switch to turn the automation fully on.

Why we did this

The v0.23.0 release exposed four recurring pains. Keep these in mind — every phase below maps back to one:

  • The "stuck release" dance. Our release tool (release-please) has a known bug: after you merge the Release PR, it aborts instead of tagging. Every release needed a ~45-second copy-paste "unstick" ritual.
  • The faucet broke prod. faucet.nulo.sh shipped a stale chain ID baked into an env file and threw "No network configured for chainId …" on load.
  • Manual main→dev sync. After a release you had to hand-merge main back into dev and re-baseline a manifest, or the next prerelease series broke.
  • Accidental 1.0.0. A single BREAKING CHANGE: commit could have auto-jumped the version to 1.0.0.

What we built

Eight phases. Each one's logic is a tiny tested TypeScript file under scripts/release/; the workflow just calls it.

Phases 1–3 — Foundations done

  • Extraction harness — pulled the fiddly bits (tag resolution, the chain-ID math) into testable functions instead of buried shell script.
  • No more accidental 1.0.0 — turned on bump-minor-pre-major: while we're in 0.x, a breaking change bumps the minor (0.23 → 0.24), never 1.0.0. Going 1.0 becomes a deliberate choice.
  • Faucet chain identity, single-sourced — deleted the stale env file that broke prod. The chain ID now comes from one constant in code (chain-constants.ts) and the build stamps a build.json so we can verify what's live.

Phase 5 — The safety net done

After publishing, the workflow redeploys the landing + faucet, then verify-live fetches both sites and checks they actually serve this release — fail-closed (anything it can't confirm is a failure). It even defeats a split CDN cache (a fresh data file served behind a stale page) and confirms the faucet's chain ID is right — directly catching the v0.23.0 prod bug class. It's advisory for now (reports problems without blocking) until it's proven on a real release.

Phase 6 — Auto-unstick: the big one ships OFF

This kills the 45-second manual ritual. When release-please aborts, a new job detects the exact situation — a merged Release PR sitting at the current commit — and creates the tag + release itself, then lets the rest of the pipeline continue in the same run. It's careful: it identifies the PR by commit (not by guessing from the title), it won't create a second tag if one exists, and if it finds a tag pointing at the wrong commit it refuses to touch it and fails loudly. It ships behind an off-by-default switch (see below).

Phase 7 — Auto main→dev sync done

After a stable release, a job opens one chore: sync main → dev PR carrying the version bump, changelog, and manifest re-baseline. It never auto-merges — it lets GitHub compute whether it's clean; a clean one waits for your squash-merge, a conflicting one gets labelled needs-manual-resolution so it's never silently dropped. It only fires on a real release (never on a re-publish of an old tag).

Phase 8 — A runbook a stranger could follow done

You said the old release doc was hard to follow. So the CLAUDE.md § Release runbook was rewritten happy-path-first: a "Start here" section with the 6-step flow and a who-does-what table, a troubleshooting table ("if X fails, do Y"), and a switches table — then the detailed manual steps as the fallback. A future agent (or you, in six months) can run a release cold from it.

Phase 4 (a throwaway test repo to rehearse in) — done, at your request. Initially skipped (it needed your go-ahead while you were away), then run in full once you asked for it. It found a real bug — a missing-label crash that would have stuck the very first flag-on release — plus two of my own harness mistakes. All fixed; the full orchestration is now validated end-to-end on a real repo. See lessons/phase-4-rehearsal.md.

The review that caught real bugs

Before calling it done, I ran a self-review, then handed the whole thing to codex (a different AI model) and explicitly asked it to break the code. It said "not ready" and found four genuine holes that the unit tests alone would not have — this was the highest-value hour of the whole effort:

What codex caughtWhy it mattered
A GitHub API hiccup looked identical to "no release to unstick"A transient network blip could leave a release stuck but showing green — the worst kind of failure. Now it fails loudly.fixed

Then a security pass tightened the workflow's permissions to least-privilege (build/test jobs no longer get a write-capable token they don't need). The full transcript + every decision is in audit-codex-postimpl.md.

The one idea to understand: the staged rollout

The auto-unstick is the riskiest piece — it creates tags and releases. So it ships off by default behind a switch (AUTO_UNSTICK_ENABLED). Here's the safety logic (and on top of it, we ran a full throwaway-repo rehearsal — see below):

  • Release N (switch OFF) — the new job runs but does nothing (it no-ops). The release behaves exactly like today: you do the manual unstick. This proves the new wiring didn't break anything, with zero risk.
  • You flip the switch.
  • Release N+1 (switch ON) — now the auto-unstick actually fires. This is the first time it does real work, and you're watching for it.

That two-release sequence is the rehearsal. The same pattern applies to verify-live (advisory until proven, then promoted to blocking).
