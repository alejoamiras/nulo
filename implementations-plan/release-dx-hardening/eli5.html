Why deep + how we test it without breaking real releases

deep because a wrong change here breaks every release (high blast radius + irreversible: it creates real tags/releases). The hard part you flagged — you can't test release automation by cutting 10 real releases — is handled by: (1) pulling the fragile logic out of the workflow YAML into small scripts we unit-test; (2) the existing dry_run switch; (3) release-please --dry-run for version math; (4) a throwaway test GitHub repo that rehearses the full "merge → tag → publish → deploy → sync" path end-to-end; and (5) the next real release as the final proof. Three independent planners (me + codex + a second model) converged on this; the trickiest piece (auto-fixing the release tool's known bug) ships last, behind an off-by-default switch.

The 8 phases

1 · Extraction harnessinfra

Move the brittle release logic out of YAML into small testable scripts (tag-resolver, live-checker, sync-opener, auto-unstick). No behavior change yet — just makes everything after this unit-testable.

Proves itself by: bun test on the scripts + actionlint, all green. No release.

2 · Cheap config winscheap

(a) Stop the accidental 1.0.0: breaking changes now bump 0.23→0.24, not 1.0.0 (you opted in; a real 1.0 becomes a deliberate choice). (b) Stop the spurious commit-lint failure on promote PRs (it re-checks old commit titles it can't edit). (c) Delete a dead inline script the strict security policy already blocks. (d) Fix stale docs.

Proves itself by: release-please --dry-run shows 0.24.0 not 1.0.0 (both stable + rc configs); a simulated promote PR goes green; the faucet builds + boots clean.

3 · Faucet chain-identity + build stampcode

The root of tonight's bug: a stale chain-version value (shipped in .env.example!) overrode the correct one. Fix: delete the override path — the faucet is testnet-only, so it reads one shared source of truth (so it can't drift from the wallet). Also stamp a build.json so the safety check (Phase 5) can read exactly what's live.

Proves itself by: unit tests resolve to the right chain; the build emits a correct build.json; faucet smoke green.

4 · Throwaway test repoinfra

Stand up a disposable GitHub repo (dummy secrets only — never real ones) that mirrors the release workflow, so we can rehearse the risky surgery (phases 5–7) safely. First we confirm it reproduces today's known bug — proving it behaves like the real thing.

Proves itself by: a full rehearsal in the test repo reaches the exact known-bug state. We also write down what it can't mirror (signing, real Cloudflare, branch rules).

5 · Deploys + live safety checksurgery

Deploy the landing AND faucet from the release pipeline (today the faucet is dashboard-only), then a "verify-live" gate fetches both sites and confirms they're actually serving the new release/chain — failing the release if anything's stale. This is the check that would've caught tonight's bug at release time instead of in your browser.

Proves itself by: unit tests (stale→fail, match→pass, can't-tell→fail); a real-site integration test; a test-repo rehearsal showing it both passing and intentionally failing.

6 · Auto re-sync main → devsurgery

After each release, automatically open the "sync main back to dev" PR (the step that was skipped tonight → caused the merge conflict). If it conflicts, it opens the PR labeled for you — never fails silently.

Proves itself by: test-repo rehearsal — clean case opens a mergeable PR; a forced conflict opens a labeled PR.

7 · Auto-fix the release-tool bugsurgery · last

The release tool has an upstream bug (all versions) that needs a 45-second manual nudge every release. We automate that nudge inside the same release run (the safest design — no second workflow to race it), idempotent + SHA-checked, and behind an off-by-default switch you flip after watching it work once. The manual nudge stays documented as a fallback.

Proves itself by: unit tests (won't double-tag, won't tag the wrong commit); a full test-repo rehearsal incl. a forced re-run; a real-repo dry-run pre-flight.

8 · Docs + closing gatewrap

Rewrite the runbook to the new mostly-automatic flow, delete the test repo, run code-review + a security hardening pass.

Proves itself by: docs match the shipped workflows; /harden security done. Final acceptance (later, tracked): the next real release runs push-button.
