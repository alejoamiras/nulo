Tools Recovery

The bridge's Activity page keeps a journal row for every deposit and exit. Three kinds of row get stuck today and can only be discarded, even when the money is fine. This plan teaches each row to prove what happened on-chain and finish itself — on your click, never on its own, and never by sending anything twice.

The pattern is the same three times: add one chain-proven fact to the row, then run the path the app already has. Every unsure case fails closed with a plain note and Discard still available.

Why this tier

Six risk dials: novelty low (the network already exposes the reads we need), blast radius moderate (the tools app's journal only), irreversibility low (no on-chain writes, only journal facts), migration cost none (one optional field), external coupling moderate (the L1 RPC and the Aztec node), security sensitivity high — these fixes decide when money counts as claimed. One high dial → mid: one plan plus a competing outline, two independent reviewers, a fresh final review.

Phases

Arc 1 · claimed by someone else
Phase 1

Recompute the message, read its spent-marker; the two locks

A small pure helper rebuilds the deposit's message from the row's facts and derives the marker the network keeps once a message is spent. The journal engine asks for it before doing any fee work, and again if the claim's dry run says "already spent". A row whose stored message does not match its own facts is refused as tampered, never completed. This phase also adds the two same-origin locks the later fixes rely on: one around the new saves this plan makes, one per running row.

the new helper's unit tests (public, private, a wrong secret, a token-and-gas row whose gas message is spent but the token one is not, a tampered row) plus the journal engine's tests, typecheck and lint, all green.

Phase 2

The card's copy and the browser cell

The row reads "Claimed by another submitter — your tokens arrived." The end-to-end cell that today pins the error is flipped: a relayer claims first, you press CLAIM, the row ends done, nothing is sent, the balance moved exactly once.

the recovery cells in a real browser against a local network, on the first try; then the whole tools suite in two parallel runs before the first PR.

Arc 2 · deposit with no Ethereum receipt
Phase 3

Find the deposit on Ethereum

A helper narrows the search to blocks since the row was created, lists the router's deposit events, keeps only those carrying this row's secret hash, then checks every detail inside the transaction data and that the transaction is confirmed on the canonical chain. Exactly one match wins; none, several, or an incomplete search each get their own answer.

unit tests over a fake Ethereum client: a match, a private deposit, a copied secret hash on another token rejected, two matches refused, a capped search reported as incomplete.

Phase 4

Wire CLAIM to it, flip the cell

CLAIM appears on the stuck row; the found id is written only if the row is still unchanged and still has no id, then today's claim path continues. The browser cell becomes: the wallet sends but never replies, reload, CLAIM finds it, the claim lands. A sibling cell keeps the honest case: nothing was ever sent, the search says so, Discard.

the journal and policy unit tests plus the Ethereum-wallet cells in the browser, first try; then the whole tools suite in two parallel runs.

Arc 3 · exit with no Aztec id
Phase 5

Find the burn on Aztec

A helper recomputes the exit's outgoing message from the row (destination, amount, the bridge and its portal) and scans recent Aztec blocks for the single transaction that emitted it as its first message, excluding transactions the journal already owns.

unit tests over a fake node: the recomputed message matches a known vector, one match, a taken one excluded, two refused, a pruned window reported as incomplete.

Phase 6

Wire FINISH to it, lock across tabs, flip the cell

FINISH appears on the stuck row; the found id is attached and the finish continues under the row's new identity, all inside one lock hand-off so two tabs cannot both do it. The browser cells become: the burn is sent but the page never hears back, reload, FINISH attaches and finishes (fee charged once, nothing burns twice); and the same with two tabs pressing FINISH at once — one finishes, the other is told another tab is on it.

the exit cells in the browser, then the whole tools suite in two parallel runs, then the repo-wide unit tests and lint, all green.

Human context

Money on a bridge is never lost by these fixes — every deposit and exit already sits safely on one chain or the other. What was lost was the app's knowledge of it. The earlier plan (tools-readiness) pinned these three rows exactly as they behave today so the warts were visible; this plan removes them. Two rules from the journal stay untouched: the app never re-sends anything from a saved row, and it never asks your wallet to sign anything on its own — the one signature (unsealing a private deposit's secret) still happens only when you press CLAIM.

Decisions surfaced by the reviews

  • One trusted node. The app already trusts its configured Aztec node for every stage and receipt; the "was this message spent?" read comes from the same node, with no second source, and only from blocks that have reached the same settlement level today's completions require (a reviewer caught that reading the very latest block could mark a deposit done from a block that later drops — and the journal would then delete that deposit's only secret). A lying node could already mislead the app; this plan does not widen that, and does not fix it either.
  • Attaching an exit when twins exist. Two exits of the same amount to the same address look identical on-chain. If exactly one candidate is not already known to this browser's journal, it is attached — the money goes to the same address either way; the residual risk is bookkeeping (a twin exit left untracked), not loss. Anything still ambiguous is refused.
  • Search vs paste. The competing outline let you paste a transaction id instead of searching. Reviewers split (one preferred a hybrid); the plan ships the search only, because users rarely hold these ids. A paste fallback can be a later follow-up.
  • The three-round stop, and what came after. The codex reviewer still had one material finding on round three (two tabs could attach the same exit at once). It was folded; a fresh reviewer then found seven defects in that fold (the journal is saved as one block, so a lock per row is not enough; a lock hand-off that re-locks itself; unbounded searches; copy that told users to discard evidence). All seven were folded; a second fresh reviewer then found six more (the lock must not touch the journal's existing saves, the settlement level of the "spent" read, the error handling after a row changes identity, copy, and how the two-tab test provokes the race). Those are folded too: the new writes run under one short lock shared by all your tabs, a second lock keeps two tabs from running the same row, searches have a deadline, and ambiguous results say "keep this record". A third fresh reviewer re-evaluated the result; its verdict is on the plan. You decide whether that closes it.
