Bun 1.4 Bump

Move the repo's Bun toolchain from 1.3.14 to 1.4.0 and pick up the easy wins that come with it: one shared CI setup instead of a duplicated copy, a cleaner lockfile format, four duplicate packages collapsed, scripts that run their independent steps at the same time, and one less Node-only workaround in CI. Nothing about the wallet's runtime, the Aztec pins, or how tests execute changes in this arc.

Why the "light" tier

Every change is a small edit to an existing file, fully revertable, with no novel surface: 0 of the 6 risk dimensions (novelty, blast radius, irreversibility, migration cost, external coupling, security sensitivity) score HIGH. One codex audit ran at maximum effort; it conditionally approved and all five of its conditions are folded in below.

The one thing that can bite: everyone must move together. We proved by experiment that Bun 1.3.14 cannot install from the new lockfile this change produces. So the merge has a precondition: the machine-wide Bun (and every active worktree) upgrades to 1.4 first. Until then the PR waits, green but unmerged.

Phases

PHASE 1

One version, written in one place

Bump the pinned version everywhere it lives, and delete the copy-pasted setup block one CI job kept for itself — it now reuses the shared one.

Proves itself by: workflow linter green, the CI-wiring guard test green, and a search showing no "1.3.14" left behind.

PHASE 2

Lockfile format upgrade, nothing else

Let Bun 1.4 rewrite its lockfile to the new format, in a commit that contains only that. We diff every package's name, version, and checksum before/after — if even one actually changed, the phase stops.

Proves itself by: an empty version/checksum diff, a second install changing nothing, and a strict frozen install passing.

PHASE 3

Collapse the four duplicate packages — carefully

The lockfile carries four packages at two versions each. Collapsing them can mean small downgrades, and one of the four can end up inside the shipped extension bundle — so each pair gets its release notes read, and we compare what the build actually bundles before and after. CI gets a warning-only check so duplicates never creep back silently.

Proves itself by: zero duplicates reported, the pair-by-pair review written down, unit tests and linters green.

PHASE 4

Let independent steps run at once

The pre-PR check runs typecheck, tests, and lint one after another though they don't depend on each other — now they run together, cutting the wait to the slowest one. The dual-browser dev mode drops its helper dependency for the built-in equivalent.

Proves itself by: the full pre-PR check passing end-to-end in its new parallel form, and both dev servers starting under the new command.

PHASE 5

Retire a workaround, tighten CI's badge

A config checker in CI had to run through Node because a native piece crashed under old Bun — we proved it works under 1.4 (warm and cold cache) and switch it over. The CI workflow also gets an explicit read-only permission badge. And we test, against a tiny fake package registry we control, whether Bun 1.4 fixed the known gap where its 7-day new-package safety delay skipped indirect dependencies — the docs then say whatever the experiment proves. If the experiment is inconclusive, the warning stays.

Proves itself by: the checker passing under Bun both warm and cold, workflow linter green, and the registry experiment's evidence written down for both Bun versions.

PHASE 6

Write down the new routine

The security docs gain the new review commands 1.4 provides (diff a package before trusting it, preview vulnerability fixes, list licenses, list who may run install scripts) and the "everyone on ≥1.4" requirement.

Proves itself by: the docs guard script green, then the whole battery re-run: pre-PR check, every package's test suite, the release-script tests, workflow linter — all green.

What the independent audit said

Codex (a different model family, maximum effort, fresh context) returned conditional approve. Its five conditions are all adopted — the two big ones were catches we then verified by experiment: the lockfile break for older Bun (now the merge precondition above), and the fact that one duplicate-collapse touches a package that ships inside the extension bundle (now Phase 3's build comparison). It also ruled the new CI duplicate check should warn, not block — adopted. One suggestion was deferred with a written reason: pinning GitHub Actions by commit hash is a repo-wide policy change, queued for its own pass rather than done inconsistently for one action.

Approved — decisions recorded (owner, 2026-08-24)

  1. Merge timing (A1): merge when green. Owner: "a runtime release ≠ npm dependency." Pin stays exactly 1.4.0.
  2. Duplicate check (A2): warn-only. In plain terms: Bun can now flag when the lockfile holds two versions of the same package; the choice was whether CI should fail over that or just warn. It warns — auto-collapsing can quietly downgrade packages, so a human stays in that loop.
  3. Fleet upgrade (A3): delegated to the agent. The agent installs Bun 1.4.0 over the machine-wide binary right before merge; the PR stays unmerged until that's done.
  4. Config-checker dependencies (A4): accept and document. In plain terms: the CI step that validates our Renovate config downloads its checker fresh each run, so the checker's own sub-dependencies aren't pinned by our lockfile. That was already true before this change (via npx) and stays exactly as true after it (via bunx) — the swap changes the runner, not the exposure. Vendoring the checker (a huge dependency tree for one config check) wasn't worth it.
