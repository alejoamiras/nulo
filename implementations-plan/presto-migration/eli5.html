plan presto-migration tier mid version 4.1 · at the gate 2026-09-15

Nulo moves from Aztec Accelerator to Presto, and starts telling you where each proof runs

Presto is the successor of the Aztec Accelerator app: same author, same job (prove transactions natively instead of in the browser), a cleaner story for the two ways it can fail on a modern browser, and a ready-made install pitch. This plan swaps the engine, teaches the wallet to say honestly whether Presto or the browser did the work, and rebuilds the onboarding step and a new Settings page on that honesty.

What changes, in three sentences

1 · The engine

The wallet talks to Presto instead of Accelerator, and the CI proving gate runs Presto's headless server. Nothing about how proofs look changes; the app behind them does.

2 · The truth

Every proof gets a tag saying who did it. The activity card reads "Proving with Presto ✦" or "Proving in browser…" instead of a generic line, and a declined Presto approval is remembered so Settings can explain it.

3 · The surfaces

The onboarding "Speed" step becomes Presto's own install card in Nulo's clothes when Presto is missing, and a clear status card with recovery steps for every other situation. Settings gains a Proving page.

Human context

Why the browser can now block Presto. Chrome 142+ asks a page before it may talk to anything on your own machine ("Local Network Access"). Presto answers on your computer, so a wallet page can be blocked — a case Accelerator never had a word for. Extensions that declare the address in their manifest are exempt, and the plan adds that declaration, but the blocked state still exists for older Chrome, Firefox, and managed machines, so the onboarding gets a card that explains the fix.

Why "encrypted connection" matters. The wallet sends private transaction data to Presto. Presto's browser policy is encrypted-only by default so that a stray program squatting Presto's port cannot receive that data. The wallet keeps that default with no escape hatch: if the encrypted connection is not working, the wallet proves in the browser and tells you how to turn encryption on in Presto. The reviewers made us state this guarantee precisely: it stops a squatter without a trusted certificate; it does not stop malware running as your own user. That is Presto's documented boundary, not something this plan can fix.

Why "not detected" instead of "not installed". Under encrypted-only, an uninstalled Presto and a Presto whose first-time prompt was dismissed look identical from the wallet. The copy says what we know.

Why the wallet cannot see a declined approval by asking Presto. Presto asks you to allow Nulo the first time a proof is sent, not when the wallet checks whether Presto is running. A declined prompt leaves the health check green while every proof silently falls back to the browser. The plan closes that gap: the proving engine reports each proof's outcome to the wallet's background worker, which remembers the last one, so Settings → Proving can say "Presto declined Nulo — open Presto → Sites → allow Nulo".

Why the reviewers rejected the first draft. Two independent reviews (Codex and Fable) found the same core hole: the first draft matched a proof's outcome to an activity card by chain, but two operations can be "proving" on the same chain at once, so the subtitle could lie. Version 2 gives every proof attempt its own id, threads it through, and applies the outcome across the whole attempt (Presto can start and then fall back mid-way). The same round moved the browser permission into the first delivery so it cannot ship a build that silently disables native proving, pinned the CI binary's archive as well as the binary, and dropped a duplicate browser-permission probe the Presto library already performs.

Why the fresh review rejected the second draft too. A reviewer with no memory of the earlier rounds read version 2 cold and found five more holes, all confirmed in the code: a declined Presto approval would have been overwritten a second later by the browser fallback's own progress events; the new subtitle would have stayed hidden behind the generic "Generating proof..." label in the ordinary case; Firefox's proving page carries an extra token in its address that the sender check would have rejected; the id-threading was described but not wired end to end; and the first delivery would have left the old onboarding page saying "active" over a plain-HTTP check while production had moved to encrypted-only. Version 3 fixes each with a concrete mechanism and adds a small temporary shim so the first delivery is honest on its own.

And the third draft. A second cold read of version 3 found the fixes right in shape but wrong in detail: the "who did this proof" verdict was still being inferred on the receiving side, so one lost message could wrongly clear a remembered denial; the id hand-off named the wrong file; the temporary shim invented a state vocabulary its own page did not understand; and the package-provenance check as written had nothing to check. Version 4 moves the verdict to the source (the proving page sees every step in order and stamps each message with what it concluded, plus a sequence number so late messages are ignored), names the four real hand-off sites, keeps the shim's exact vocabulary, and uses the same provenance procedure Presto itself uses. The reviewer also noted, for the third time, that one delivery instead of two would avoid the shim — that choice is yours below.

The third and last cold read. No design objection survived: the reviewer could not break the proof attribution under lost or reordered messages, the sender check, the download pinning, or the encrypted-only policy. Two things did fail, and both were acceptance criteria I had written without checking their premise. First, "no Aztec code reachable from onboarding" is already false today: the onboarding screen shares the wallet's page table, and one Settings page pulls a small Aztec helper, so the criterion cannot be met by this plan. Second, the recovery step "open Presto → Sites → allow Nulo" does not exist: Presto's Settings only lets you remove an approved site, and a declined prompt saves nothing, so the only recovery is to wait half a minute and send again. Those two became questions for you (A8, A9) rather than a fifth draft. One real gap it found was fixed: a slow message from an older proof could have cleared a denial recorded by a newer one.

Why mid

The rubric counts how many risk dimensions are high. One is: the work depends on an external app and its browser policy. Everything else is contained — same author's library, a rename at the code level, no stored-data changes, and a CI gate that already exists for the old engine.

DimensionScoreWhy
NoveltylowSame wire protocol, renamed library, the CI gate already exists.
Blast radiusmediumEvery proof path and the CI proving gate; a silent fallback would be user-invisible, which is why the truth channel exists.
IrreversibilitylowNo stored-data migration; a revert is a dependency swap.
Migration costlowUsers install a new app; the wallet needs nothing migrated.
External couplinghighPresto desktop + headless server, Chrome's local-network policy, Firefox's optional permissions.
Security sensitivitymediumPrivate witness data crosses a loopback boundary; the plan bounds the guarantee and names residual risks.

Phases

Eight phases in two deliveries. The first delivery is everything the wallet must get right underneath; the second is what you see. Each delivery builds and passes its own checks alone, so the first can land without the second.

Delivery 1 · runtime truth

Engine swap, browser permission, CI gate, and the proof-outcome channel

One pull request. When it lands, native proving works through Presto in production and CI, and the activity card already tells the truth.

P1

Dependencies and the 7-day gate

Add Presto's library, its small status client and banner kit alongside the old one (the old one leaves in P2, so nothing is ever half-renamed), verify each package's npm publishing provenance, and exempt from the 7-day age gate only what is still too fresh on install day (a dated follow-up removes the exemption). Adds a test pinning the wallet's Aztec version to the library's.

proves itself bya clean locked install, the residue check, lint, typecheck, and the version-lockstep test.
P2

Engine swap and the browser permission

The proving engine becomes Presto with encryption explicitly required in production; plaintext follows from the CI proving mode alone, with no switch to set wrongly. The manifest declares the encrypted local address so the browser never blocks the wallet's own proof. The old onboarding page gets a small temporary shim so it checks Presto the same encrypted way production does (no more "active" over plain HTTP) until its replacement lands, keeping its exact states so Skip and the download button still work; the false "not on Windows" note goes.

proves itself bythe engine unit tests (both modes, every failure phase, observer isolation), a client-level test that an encrypted failure never sends a plaintext proof, typecheck, lint, a build whose manifest lists both local addresses, and the onboarding smoke test on the shim.
P3

CI proves with headless Presto

The CI runners install Presto's headless server with both the archive and the binary pinned by hash, extract only the binary, and fail the network suite if any proof falls back to the browser. CI docs updated in the same step.

proves itself byworkflow lint, the CI-gating unit tests, and one real prover-on run of the two canary tests showing at least one native proof.
P4

Every proof carries its outcome

Each attempt gets an id; the proving page, which sees every step in order, stamps each report with its verdict ("Presto took it", "fell back to the browser", "Presto declined") and a sequence number; the background worker copies the verdict onto the operation, ignores anything late or out of order, and remembers the last outcome and any declined approval for Settings. Only the wallet's own proving page may send these reports. The activity subtitle reads it.

proves itself byunit tests across three packages (late, cancelled, mixed-order, spoofed reports), a local network run asserting "Proving in browser…", and a CI run asserting "Proving with Presto ✦".
P5

Docs and residue

Rewrite the remaining docs and skills; grep the repo for the old name until nothing is left outside the history.

proves itself bylint, the brand/path guard, and a zero-hit grep.

A second pull request stacked on the first. Pure UI on top of the truth channel.

proves itself bythe onboarding smoke test across four stubbed situations, the full smoke suite, a zero-residue grep, the bundle measurement, and a walk-through on the Mac with the real app (quit, encryption off/on, first-send approval).

A row in Settings with a live one-line status and a page with the status card, details, recovery steps, retry, and a Get Presto link when it is missing. A declined approval is remembered separately from ordinary progress and cleared only by a proof Presto actually produced, so the page cannot lose it.

Open questions for you

Each has a recommendation; answering "all as recommended" is enough.

A1 · Rename the CI kill-switch from "disable accelerator" to "disable presto"?

Recommended: yes. The variable is not set anywhere, so nothing to migrate; leaving the old name invites the stale-name drift this plan is cleaning up.

A2 · Rename the onboarding route and test ids from "accelerator" to "presto"?

Recommended: yes. The page is rebuilt anyway and the tests move with it.

A3 · Ask Presto to list Nulo's store extension id as a recognised site?

Recommended: yes, later. It only adds a "verified" badge to Presto's approval prompt; not needed to ship. Done in the Presto repo once the id is confirmed.

A4 · Accept the onboarding bundle growing by up to 60 kB (compressed) for the status client?

Recommended: yes. Measured in P7 against the pre-migration build. The Aztec-leak half of this check is A8.

A8 · from the last review How strict should "no Aztec code in onboarding" be?

Onboarding already reaches a little Aztec code today through the shared page table, so "none at all" cannot be met by this plan. Recommended: (a) "no Aztec module newly reachable from onboarding compared to before the migration" (a diff of the two builds). Option (b) is a separate small project to give onboarding its own page table, making it truly Aztec-free.

A9 · from the last review Accept that the only recovery from a declined Presto prompt is "wait ~30 s and send again"?

Recommended: acknowledge. Presto keeps no record of declines and its Settings can only remove approved sites; nothing on the wallet side can change that. A Presto-side "recently declined" list would be a request in the Presto repo.

A5 · Give development builds one fixed extension id?

Recommended: yes, dev builds only. Unpacked builds get an id from their folder path, so every worktree and machine is a different stranger to Presto and re-prompts. The store id is already stable.

A6 · Firefox: add a "grant access" step, or leave it best-effort?

Recommended: best-effort now, follow-up plan. Firefox grants the permission at install but lets users revoke it; the state card says "check the extension's permissions" without over-promising. A proper grant step needs its own tests.

A7 · Pin the wallet's Aztec version to the Presto library's with a test?

Recommended: yes. Both are 5.2.0 today; a test catches drift on the next Aztec bump.

Delivery · two stacked pull requests (with the temporary onboarding shim) or one?

Recommended: two. Two PRs are far easier to review and the first can land on its own; the price is a ~40-line shim that lives for one PR. One PR drops the shim and merges P6–P8 into the first delivery; nothing else changes.
