## Deviations from the plan text (small, recorded)

- The plan names the client event `provePhase` and a `recordDenial` constructor callback. The event is `onProvePhase` because the messaging layer dispatches an event to the client property of the same name (`EventsSpec`), and every existing event follows the `onX` convention. `recordDenial` was dropped: the denial generation logic needs the attempt map, so the coordinator owns both memory records and the service reads them through `getLastProveOutcome()` — a second callback would only have moved a field one object over.
- `updateProvingBackend` also short-circuits when the row already carries the same backend (the plan only required stage + `enteredProveAt` semantics). This keeps the popup from re-rendering on each of the 3–4 same-backend phases per attempt.
