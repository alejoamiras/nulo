New test runner, the old patch removed, and proof it still runs clean on Bun

Every unit test in the repo runs on vitest, driven by Bun. A year's worth of vitest is now out (version 5) and it contains the fix for the one Bun problem we had to patch around ourselves last month. This plan takes the new version, deletes our patch, and re-runs the same "does Bun behave like Node?" measurement we built for the original switch — on the new runner, at one commit, both engines — so the upgrade is proved rather than assumed. On the way it keeps the few things vitest 5 improves for free and measures, instead of guessing, whether its speed options are worth turning on here.

Human context

The patch. When we moved the tests onto Bun in August, one thing broke: vitest 4 looked at how Bun describes a module and wrongly treated it as old-style CommonJS, so a library like zod lost its named exports mid-test. We turned that heuristic off with a single config line and wrote next to it: "delete this when vitest ships the fix, and re-run the Bun soak". vitest 5.0 ships the fix (their PR #10363). This plan is that sentence, executed.

The calendar — your call, made. The repo refuses to install anything younger than seven days (a supply-chain rule); vitest 5.0.1 would clear on Monday 22 Sep and jsdom 30.1.0 (the fake browser the DOM tests run in — its 30.0.x has a selector bug fixed only in 30.1.0) on Wednesday 24 Sep. You chose to skip the wait for both, so everything runs now. What that costs: one and three days of the window the rule exists for. What limits it: the exemption names exactly those two packages (plus only what they require), lives on this machine only until the install and never reaches the PR; both packages ship an npm provenance record (the registry's statement that the tarball was built by the project's own CI from a tagged commit) — we read it and check it names the right repository and the same tarball, which is an inspection, not a cryptographic verification; the first install runs with install scripts off and the lockfile diff is read before the real one. Codex objected to running young code at all — that objection stays on the record as the plan's, and the decision as yours.

The proof. The soak tool runs a suite N times on Node and N times on Bun at the same commit and refuses to say "same" unless every single test has the identical pass/skip record on both sides. It also refuses to compare two runs made on different vitest versions or commits — so the August measurements can't serve as the Node side; both sides are recorded fresh. You asked for ten runs instead of thirty. Ten runs catch a test that flakes one time in ten with 65 % probability (thirty: 96 %); one in twenty, 40 % (thirty: 79 %). At ten the matrix is about 50 minutes unattended; at thirty, about 2½ hours. The plan records ten as this bump's exception — the standing thirty-run bar in CLAUDE.md stays as it is — and uses thirty for the one small package whose runtime actually changes (resolve-asset moves from Node to Bun; it takes a second per run). The matrix covers sixteen suites, four more than last time: three small packages added since, and the extension's component subset, which the original twelve missed.

The harvest. vitest 5 clears mock call-counts between tests by default (the extension's tests already did this by hand; the other packages now get it), and fails a test that forgot to await an async assertion — both are things we want, so nothing is switched off. It adds vi.when(), a cleaner way to say "when called with X, return Y" — the plan rewrites the seventeen mocks that branch on their arguments only where that reads better and behaves the same. It exports the default reporter list, which lets the e2e configs drop a hand-written "re-add the GitHub annotations" line. It also adds vitest doctor, which runs your suite under alternative settings and reports the measured speed — this PR records those numbers and changes nothing: a speed setting is a runtime change, and a runtime change gets the thirty-run bar in its own follow-up, if the numbers ever justify one.

One change that might bite. vitest 5 makes an assignment like window.addEventListener = spy reach the fake browser's real window (it used to stop at a shim). Two extension tests do exactly that. The plan runs them first, alone, and reads what happens — a red there is classified, not waved off as "an old test bug".

Phases

1 · The bump

First the things that must be in place before any vitest 5 run: delete the interop patch (and the now-empty shared config file), bring the one straggler package (resolve-asset) onto the Bun convention, ignore vitest 5's new .vitest/ output folder. Then, for vitest and again for jsdom: check the package's provenance record, install with scripts switched off, read the lockfile diff (new packages, changed install scripts, exact versions 5.0.1 / 30.1.0), install for real, run everything — vitest's fallout recorded and green before jsdom is added. Delete the local exemption and prove the lockfile holds without it. Run the known-sensitive tests first, alone; then classify every red — a test bug, a test that must follow the new contract, or a Bun-only difference (that one stops and comes to you). Never by turning a vitest 5 behavior off, never by skipping a test on Bun.

Proves itself by: frozen install clean, lint, typecheck, every workspace's suite green on Bun once, the soak tool's own tests green (they run on both engines, so this host's Node must be ≥ 24.15 first).

2 · The harvest, measured

Run vitest doctor on every suite and record the numbers (nothing adopted here). Rewrite the argument-keyed mocks with vi.when where clearer. Put the e2e reporter list on vitest's exported defaults. Update CLAUDE.md (vitest 5, the patch gone, this bump's ten-run exception named, the thirty-run bar unchanged) and close the loop in the August lessons file.

Proves itself by: lint, typecheck, all suites, audit:vue, the Node smoke e2e (it exercises the custom reporter and global-setup contracts on Node).

3 · The matrix

At one committed tree, after a frozen install, on an idle host, touching no file until the last run finishes: 16 suites × Node and Bun × 10 runs (30 for resolve-asset), each pair compared, the summaries committed under the soak tool's baseline folder. Then the CI-shaped concurrent run five times, and a manual CI dispatch bound to that exact commit. A red on the Node side is reproduced and classified before anything else: a real test bug gets fixed and the matrix restarts at the new commit; a regression in the new versions, an environment problem or a product defect comes to you.

Proves itself by: 16 × COMPARE OK with the full reports kept, five green fan-outs, the dispatch green at the matrix SHA. Any later change to a test, config or lockfile re-runs the whole phase.

4 · Review loop, then the PR

Codex reviews the whole diff first (any fix that touches code re-runs the matrix); only then one PR into dev, with the network and tools e2e labels added after it exists (adding them at creation cancels the sibling run). Merge is yours.

Proves itself by: the loop converged, then quality, smoke, network and tools statuses green; the new vitest job summary visible on the unit job.
